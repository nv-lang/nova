# Участие в Nova

Nova — живой компилятор с рантаймом и стандартной библиотекой, а не дизайн-документ.
Вклад принимается и от людей, и от агентов.

## С чего начать — очередь работы открыта

У нас нет скрытого списка задач. Всё, что мы знаем про собственные дефекты, лежит
в двух файлах:

| где | что там |
|---|---|
| [`docs/plans/221.1-bug-sweep.md`](docs/plans/221.1-bug-sweep.md) | **Реестр дефектов.** Каждая запись несёт приоритет (К1/К2/К3), **КЛАСС** дефекта и оговорку «фикс носителя приёмкой не считается» — то есть готовое техзадание |
| [`docs/plans/README.md`](docs/plans/README.md) | Незакрытые планы с приоритетами |

**Как выбрать задачу со стороны.** Записи К2 и К3 обычно самодостаточны: в них есть
репро, класс и приёмка. Записи К1 часто требуют контекста, которого нет в тексте, —
если берётесь за такую, напишите в issue до того, как писать код.

## Правила, которые проверяет машина

Весь список — в [AGENTS.md](AGENTS.md), раздел «Rules»; причины каждого и список всех
34 стражей — в [docs/dev/rules-for-agents.md](docs/dev/rules-for-agents.md). Самое
важное для внешнего участника:

* **Сообщения коммитов — по-английски** (заголовок и тело).
* **Фикс класса, а не носителя.** Патч, после которого проходит один упавший тест,
  сам по себе не принимается. Если такая же ошибка может быть в других местах —
  скажите, где искали и что нашли. Честный частичный фикс приветствуется;
  частичный, выданный за полный, — нет.
* **Доказательство — не «не упало».** Нужна фикстура, утверждающая наблюдаемое
  поведение, и проба «подсунь негодное»: сломайте свой же фикс, покажите красную
  фикстуру, верните — покажите зелёную.
* **Язык-меняющие правки идут со спекой** — D-блок в `spec/decisions/` в том же PR.
  Номер D-блока назначает сопровождающий, сами не берите.

## Условие приёма: зелёный гейт

```sh
bash scripts/gate.sh
```

Это единственный вердикт о готовности: он собирает компилятор, гоняет весь корпус
одним compile-unit'ом, проверяет `std`, собирает и **запускает** флагман-примеры и
прогоняет 34 стража. Идёт около сорока минут. Красный гейт — PR не рассматривается;
это не строгость, а единственный способ держать язык в собранном состоянии при том
темпе, с которым он меняется.

Если гейт краснеет НЕ от вашей правки — скажите это в PR с выводом; такое случается,
и это наша проблема, а не ваша.

## Как внести вклад

1. **Issue до кода** для всего, кроме очевидных исправлений: направление дешевле
   согласовать до, чем переделывать после.
2. Форк, ветка от `main`.
3. PR по шаблону. Каждый коммит подписан DCO (ниже).

Каноническая репозитория — **GitHub** (`nv-lang/nova`). Зеркала на GitVerse и
SourceCraft обновляются из неё; PR туда мы не видим.

## Developer Certificate of Origin (DCO)

Вместо CLA проект использует [DCO](https://developercertificate.org/) — лёгкий
способ подтвердить, что вы имеете право вносить изменения и согласны с лицензией
проекта.

Каждый коммит должен содержать строку `Signed-off-by` с вашим настоящим именем и
email:

```
Signed-off-by: Имя Фамилия <email@example.com>
```

Добавляется автоматически флагом `-s`:

```
git commit -s -m "сообщение"
```

Если забыли — можно дополнить последний коммит:

```
git commit --amend -s --no-edit
```

Или несколько коммитов сразу через rebase:

```
git rebase --signoff main
```

PR без подписей не пройдёт проверку CI.

## Опциональный pre-commit hook: `nova lint` (2026-07-10)

CI гейтит `nova lint` на `std/` и на самотест реестра правил (см.
`.github/workflows/nova-lint.yml`). Чтобы ловить находки ДО коммита (а не
после push в CI), в репозитории есть **opt-in** (не активирован по
умолчанию) pre-commit hook `.githooks/pre-commit` — прогоняет `nova lint`
только по staged `.nv`-файлам.

Активация (один раз на клон):

```sh
git config core.hooksPath .githooks
```

Отключение:

```sh
git config --unset core.hooksPath
```

Хук требует собранный `nova-cli` (`cargo build --release --manifest-path
nova-cli/Cargo.toml`); без бинаря он не блокирует коммит (просто
предупреждает). Обход для одного коммита: `git commit --no-verify`.
Легальное исключение конкретной находки — маркер `[M-...]` на строке (см.
[docs/dev/compiler-conventions.md](docs/dev/compiler-conventions.md) §4), а не
`--no-verify` систематически.

## Soundness-regression-suite (Plan 33.8 Ф.7)

Верификатор контрактов (Plan 33) обязан быть **sound**: вердикт «доказано»
должен строго влечь «истинно в рантайме». Два аудита нашли 6 soundness-дыр —
поэтому действует правило защиты от регрессий:

- **Нашли soundness-баг** (верификатор объявил контракт «доказан», хотя он
  ложен; или проверка молча пропущена) → **обязательно** добавьте тест,
  который ловит именно эту регрессию.
- Пометьте такой тест маркером-комментарием `// SOUNDNESS_REGRESSION`
  в первых строках файла (`.nv`-тест) или над `#[test]` (unit-тест).
- CI-job `soundness-regression-guard` следит, что число guard-тестов не
  убывает. Добавили новый — поднимите порог `MIN` в
  `.github/workflows/contracts-z3.yml`.
- НЕ ослабляйте и не удаляйте `SOUNDNESS_REGRESSION`-тесты без явного
  обоснования в PR — каждый стережёт конкретную закрытую дыру.
