# REPORT-p1448 — литерал записи против схемы своих полей (№1448, №1096)

Ветка: `p1448-record-literal-fields-xwe0r7` (имя ветки задано средой облачной
сессии; в задании — `p1448-record-literal-fields`). База: `origin/integrate`
c775a97, перед сдачей слит свежий `origin/integrate` ed90b40.

КОРЕНЬ: в `f1_expr_inner` ветка `RecordLit` обходила значения полей ради них
самих и ни разу не сверяла их с объявленным типом поля — у позиции «поле
литерала записи» не было двери `assignable`, какая есть у аргумента, `let`,
возврата и элемента массива. Анонимный литерал `{ .. }` в позиции с известным
типом записи не сверялся вовсе: у `assignable_direct` не было для него ветки, и
ответ был «не знаю». Полнота (№1142, `E_MISSING_FIELD_IN_LITERAL`) стояла только
у именованного литерала обычной записи; анонимный литерал (пример D52
`ro u User = { id: 2 }`), вариант суммы с полями и `Self { .. }` оставляли поле
неинициализированным. Лишнее поле доходило до компилятора C.

ФИКС: `compiler-codegen/src/types/record_lit_schema.rs` — дочерний модуль,
одна проверка `record_lit_faults` (стр. 154) с двумя входами:
`check_named_record_lit` (стр. 245; зовётся из `types/mod.rs:13740`,
`f1_expr_inner`) — именованный литерал, `Sum.V { .. }`, `V { .. }`,
`Self { .. }`; `anon_record_lit_compat` (стр. 263; зовётся из
`types/mod.rs:23157`, `assignable_direct`) — анонимный литерал в любой позиции,
где дверь уже есть (`let`, аргумент, возврат, элемент массива, вложенное поле).
Каждое поле идёт через `assignable` со всеми её коэрсиями (D44, D55 обёртка в
сумму и newtype-константа, D227, D54, D429). Вердикт анонимного литерала — новый
вариант `Compat::RecordLit { faults }` с диагностикой на каждом поле; выбор
перегрузки считает его несовпадением. Коды: тип поля — существующий `E7301`;
пропуск — существующий `E_MISSING_FIELD_IN_LITERAL` (текст №1142 вынесен в одну
функцию `missing_field_message`); лишнее поле — новый `E_RECORD_UNKNOWN_FIELD`;
источник спреда чужого типа — `E7301` (D60 п.5). Не судится намеренно: поле,
тип которого упоминает собственный параметр записи без известного аргумента
(голый generic-литерал — аргументы выводятся ИЗ полей), цель `#from_fields`
(D55 map-coercion), полнота литерала со спредом (остальное даёт донор).

ВОПРОСЫ ИНТЕГРАТОРУ:
1. Код пропуска поля. Задание просило `E_RECORD_MISSING_FIELD`, но №1142 уже
   завёл `E_MISSING_FIELD_IN_LITERAL` с фикстурой `neg_record_missing_field.nv`
   для той же причины. Варианты: (а) оставить один существующий код (сделано);
   (б) переименовать в `E_RECORD_MISSING_FIELD` во всех местах вместе с фикстурой
   №1142; (в) завести второй код для новых дверей. Рекомендация — (а): одна
   причина — один код; два кода на одно правило разошлись бы при первой правке.
   Если имя принципиально — (б), это механическая замена.
2. Фигурная форма именованного кортежа (`Pt { a: 1 }`, строка `№TBD` 🟡 К2):
   законна ли она? Спека называет конструктором `Pt(..)` (D215, D102) и не
   говорит, действуют ли умолчания полей в фигурной форме — это та развилка из
   задания («умолчание в одной форме объявления и нет в другой»), поэтому
   полноту для неё я НЕ включал, а форма и сейчас падает в C. Рекомендация —
   запретить фигурную форму для кортежа Nova-диагностикой: у неё нет кодогена и
   нет правила умолчаний, а скобочная форма покрывает всё.
