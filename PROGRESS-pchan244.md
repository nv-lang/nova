## Ф.1 — `Chan[T]` на Nova

Реализация — `std/src/concurrency/channel_v2.nv` (+ тесты рядом,
`channel_v2_test.nv`, конвенция «тесты std-модулей рядом с модулем»).
Живёт РЯДОМ со старой (компилятор-интринзик) реализацией; ничего не
снесено, старый путь не тронут.

### Имена — `V2`-суффикс, ПОЧЕМУ (находка, не следование плану буквально)

План называет новые типы буквально `Channel`/`ChanWriter`/`ChanReader` —
теми же именами, что старая реализация. Это НЕВОЗМОЖНО без коллизии:
грепом по `compiler-codegen/src/codegen/emit_c.rs` подтверждено, что
`"Channel"`/`"ChanReader"`/`"ChanWriter"` — literal STRING-совпадения в
кодогенераторе (`Channel.new`/`.send`/`.recv`/`ChanReader.close_after`
перехватываются по ИМЕНИ, а не через обычную таблицу методов
пользовательского типа). Объявление НОВОГО `.nv`-типа под тем же именем
либо конфликтует, либо будет молча ЗАТЕНЕНО этим перехватом — независимую
реализацию под тем же именем сейчас проверить/замерить невозможно. Взят
суффикс `V2` на всё окно Ф.1/Ф.2/Ф.3: `ChanV2[T]` (общее состояние,
`#share`), `ChanWriterV2[T]`/`ChanReaderV2[T]` (capability-типы, `value`),
`ChannelV2[T].new(cap)`, `ChannelPairV2[T]` (возврат — см. ниже). Ф.5
(снос) удаляет три C-интринзик-ветки И переименовывает в голые
`Channel`/`ChanWriter`/`ChanReader` — только тогда «публичная поверхность
не меняется» станет буквально верно.

### Представление — как в плане, за вычетом находок ниже

`ChanV2[T]` — ТОЧНО поля из плана (`mutex Mutex`, `not_empty`/`not_full
Condvar`, `buf []T`, `head`/`count`/`cap int`, `closed bool`, `tx_refs
AtomicInt`). Кольцевое обращение — **простое индексирование `% cap()` на
месте вызова** (не приватный `buf_put`/`buf_take` helper): план явно
предлагает выбор, инлайн проще и не расширяет поверхность `Chan[T]`.
Технически всё равно нужен `if idx < buf.len() { buf[idx] = v } else {
buf.push(v) }`, т.к. `[]T.new().cap(n)` (D372-амендмент, `with_capacity`
ретрактирован 2026-07-06 — план ссылался на устаревшее имя) резервирует
capacity, но не поднимает `.len()` — растёт `.push()`'ом на первом круге,
дальше — перезапись на месте.

### Компилятор-находки Ф.1 (докладываю, НЕ чиню — окно `compiler-codegen` не трогает)

Реализация упёрлась в **три РАЗНЫХ, ранее не документированных пробела в
кодогенераторе** для generic-типов — все воспроизведены МИНИМАЛЬНЫМИ
изолированными репро (без зависимости от модуля канала), все обойдены БЕЗ
изменения компилятора:

1. **Inline generic-литерал `TypeName[T] { field: value }` — не codegen'ится
   («anonymous record literal without spread not supported in codegen»)**,
   ПОЛНОСТЬЮ независимо от вложенности/`#share`/`consume` — воспроизведено
   на плоском `type Wrap[T] value { first T, second T }` тоже. Рабочая
   форма — **annotated-binding**: тип на `ro`/`mut`-биндинге, голый
   литерал справа (`ro w ChanWriterV2[T] = { ch: shared_ch }`) — тот же
   паттерн, что уже использует ПРОХОДЯЩИЙ conformance-тест
   `d277_generic_value_record_mono.nv` (`D277Pair[int]`). Использован
   везде в `channel_v2.nv` (`ChannelV2[T].new`, `ChanWriterV2[T] @share`).
2. **Tuple-возврат `(ChanWriterV2[T], ChanReaderV2[T])` из generic-функции —
   CC-FAIL** (`unknown type name 'NovaValue_ChanWriterV2____Nova_T_p'`):
   кодогенератор эмиттирует ДВА tuple-typedef'а — реальный конкретный
   (`..._nova_int`) и «неспециализированный шаблон» (`..._Nova_T_p`),
   ссылающийся на структуру, которая для `value`-generic-record'ов (D277:
   только КОНКРЕТНЫЕ моно-инстансы, шаблона нет) никогда не эмиттируется.
   Обход: возврат ИМЕНОВАННОЙ записью (`ChannelPairV2[T] { tx, rx }`)
   вместо кортежа — что и правильнее: `docs/guide/channels.md` и так
   документирует V1 как «пара — запись с полями tx/rx», не кортеж.
3. **Деструктуризация generic-записи `ro { a, b } = generic_fn[T]()` —
   CC-FAIL** (`no member named 'payload' in 'struct Nova_Pair____nova_int'`
   — трактуется как enum-payload деструктура, не record). Обход — простой
   доступ по полю (`ro p = f[T](); ro a = p.a; ro b = p.b`) вместо
   деструктуризации; использовано в тестах (`ro ch = ChannelV2[int].new(n);
   ro tx = ch.tx; ro rx = ch.rx`).

Ни один из трёх — не специфичен для канала; все три касаются ЛЮБОГО
generic user-типа с похожей формой. Стоит завести отдельные тикеты (не
делаю — не мой мандат в этом окне решать нумерацию/приоритет чужих
находок сверх уже занятого №290 ниже).

### №290 — КРИТИЧЕСКАЯ находка: field-cache (Plan 123) ломает `while … .wait(mutex) …` на `#share`-поле

Самая серьёзная находка сессии. `nova test` (АВТОРИТЕТНЫЙ гейт) **вешает
ЛЮБОЙ тест, вызывающий `.recv()`** — включая простейший однофайберный
случай `tx.send(1); rx.recv()` БЕЗ единого `spawn`. При этом:

- `nova build channel_v2_manual.nv -o exe && ./exe` (ручная сборка +
  прямой запуск) — **30+/30+ прогонов подряд корректны**: FIFO 3
  элемента, producer/consumer N=10 и N=100 через `supervised { spawn ...
  spawn ... }`, кольцевой буфер с перезаписью — всё сошлось побайтово
  (`sum=4950`, `got_count=100` и т.п., каждый раз).
- `nova test` **детерминированно** (не флейково — 10/10 повторов)
  вешает ЛЮБОЙ тест с `.recv()` в этом же самом коде.

Минимальный изолированный репро (БЕЗ зависимости от `channel_v2.nv`,
ровно эта форма):

```nova
#share
type MiniChan[T] {
    mut mutex Mutex, mut not_empty Condvar, mut not_full Condvar
    mut buf []T, mut head int, mut count int, ro cap int, mut closed bool
}
type MiniWriter[T] value { priv ch MiniChan[T] }
type MiniReader[T] value { priv ch MiniChan[T] }
// ... send()/recv() ровно как в channel_v2.nv ...
test "minimal reimplementation: single send then single recv" {
    ro w = mini_new[int](4)
    ro r = w.reader()
    w.send(10)
    ro a = r.recv()          // ВЕШАЕТ nova test (default), 0 проблем под --no-field-cache
    assert(a ?? -1 == 10)
}
```

**Корень (изолирован через `--no-field-cache`, который ОДИН чинит всё):**
Plan 123 field-caching кэширует чтение `@field` (`@ch.count` в цикле
`while @ch.count == 0 && !@ch.closed { @ch.not_empty.wait(@ch.mutex) }`)
как «безопасно кэшируемое» через границу `Mutex.lock()`/`Condvar.wait()`
— хотя именно ЭТО поле мутируется кодом, который мьютекс/кондвар и
охраняют. Цикл крутится на УСТАРЕВШЕМ закэшированном значении. Контрольные
проверки, сузившие причину:
- голый `Condvar.new()`×2 + `Mutex` без `.wait()` — ОК под `nova test`;
- `ChanV2`-формы generic-`#share`-запись САМА ПО СЕБЕ (без `send`/`recv`)
  — ОК;
- `ChannelV2[T].new()` + `.capacity()` (без блокировки) — ОК;
- один `send()` без `recv()` — ОК;
- `send()` ЗАТЕМ `recv()` (простейшая пара) — ВЕШАЕТ;
- ТОТ ЖЕ репро с флагом `--no-field-cache` — ОК, 100% (5/5 повторов
  всего теста, включая multi-fiber и risk-4 фикстуру).

**Не чиню** (Plan 123 — `compiler-codegen`, окно занято другой волной;
этот атом — `std/**` онли). Общий риск: ЛЮБОЙ будущий `while … cv.wait(m)
…` на `#share`-поле в std наступит на то же самое — не специфично для
каналов. Номер занят по grep (`№290`, `#290` — оба формата свободны на
момент старта). **Все прогоны `nova test`/`nova check` этого модуля в
этом окне и далее — ТОЛЬКО с `--no-field-cache`**, до фикса №290
компилятором.

### Проверка риска 5 (S1a, №289) — ПЕРВЫМ ДЕЛОМ, как требовал бриф

Не отклоняет. `ChanV2[T]` (`#share`, реальные поля — `Mutex`/2×`Condvar`/
`[]T`/`int`×3/`bool`/`AtomicInt`) компилируется и работает под
`supervised { spawn ... }` без единой ошибки S1a — `nova check` зелёный
на всём модуле, рантайм подтверждает (producer/consumer 2 fibers, risk-4
фикстура — 12 `spawn`'ов, каждый со своим `tx.share()`). Ф.1 **не хранит
замыканий-в-полях** (`waiters []SelectWaiter` — это Ф.2/select; Ф.1 без
select вообще не заводит списки ожидателей — вся парковка идёт через
`Condvar`, без единого поля-функции), так что буквальная форма риска 5
(«вызов поля-замыкания») здесь физически не возникает — она относится к
Ф.2. Побочно найдено (см. Ф.0 раздел выше): `E_CONCURRENT_MUT_CAPTURE`
(Plan 173.3, НЕ №289) отклоняет doc-канонический паттерн `mut sum`,
захваченный ДВУМЯ `spawn`, ВНЕ `bench`-блока — не блокирует Ф.1 (`ChanV2`
использует только `#share`-примитивы во всех mut-захватах), но стоит
отдельного внимания интегратора.

### Проверка риска 4 (справедливость) — фикстура зелёная

`Condvar.notify_one` FIFO-гарантий не документирует явно в сигнатуре (D170
описывает «wake one waiting fiber» без явного порядка) — решено НЕ вводить
отдельную явную очередь ожидателей в Ф.1: фикстура «risk 4: N senders on
cap=1 buffer, every one gets through (fairness)» (12 `spawn`'ов, каждый
со своим битом в `AtomicInt`-маске, буфер ёмкости 1) — **зелёная** (5/5
повторов под `--no-field-cache`, ни одного голодания). Если Ф.4's
нагрузочная 30/30-проба (за пределами этого окна) когда-нибудь покажет
голодание — тогда явная очередь; сейчас — не нужна, `Condvar` FIFO
реализации (`std/src/runtime/sync.nv`: «Wake one waiting fiber (FIFO —
oldest waiter first)») достаточно.

### `consume v T` — НЕ реализовано полностью (находка, не мой мандат чинить)

`send`/`try_send` в плане — `consume v T` (D131/№144 паритет: переиспользование
после отправки — ошибка линейного чекера). Эмпирически проверено (минимальное
изолированное репро): сохранение generic `consume v T` в ЛЮБОЙ slot
стандартной коллекции (`Vec[T].push(v)`, индекс-присваивание, обёртка в
`Some(v)`) не имеет ни одного из 5 механизмов discharge, признаваемых
D133-чекером, для неограниченного `T` — ни `Vec[T].push`, ни
`HashMap[K,V].insert` не объявляют `consume`-параметр нигде в std. Это
ОБЩИЙ, не специфичный для канала пробел (тот же эксперимент ломается
идентично для HashMap/Queue/Deque). `v` в Ф.1 — обычный (view) параметр;
