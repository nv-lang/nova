## Причина: какой коммит

Бисекция по `main` — 17 точек, на каждой полный модульный прогон `novac/src`, как в
double-build. Считал отказы в двух файлах.

|---|---|
| `bacdefa12`, затем внутри цепочки слияния `b202b7e4c`, `b40478ce0`, `603f826ae`, `e04bd596f` | 0 |
| `b77177e37` и все точки после него до `211023697` | 7 |

`b77177e37` — слияние `p274-carina-sweep` (поставки 3–4): value-записи по D488.

**Почему до него было 0.** На `e04bd596f` модуль `sem` давал ровно три отказа, все в
`sem/channel.nv`: «a method on a `value` record needs the receiver taken by POINTER». На них
типизация модуля останавливалась. Последующие файлы модуля, включая оба теста, **не судились
вообще**. `b77177e37` снял этот отказ. Типизация пошла дальше и впервые дошла до двух тестов.

**Что вскрылось.** Все семь отказов — один вопрос: `branch(0, NodeKind.File, []Node.new())`
при `export fn branch(id NodeId, ...)`, где `NodeId` — newtype над `int`. По D489 («где
применимо») и амендменту D55 2026-08-21 нетипизированная константа берёт newtype над числом по
правилу представления.

Карина на этой клетке отказывала **всегда**. Минимальное воспроизведение отказано на каждом
бинаре `main`, в том числе на `bacdefa12`, где два файла ещё были зелёными. Значит, ни один
коммит не сломал работавшее: проверка стала глубже, и пробел вышел наружу.

## Правка

Отказов два вида:

- **Одна строка** (`g(0, 3)`, все семь мест в двух файлах). «This argument's type is not the
  one this function declares». Закрыто ещё частью 7: аргумент типизируется под ожиданием
  параметра. Поэтому на ветке после части 7 оба файла уже зелёные, а в `main` (без части 7)
  красные.
- **Набор перегрузок** (`f(0)` при `f(i Id)` и `f(s str)`). «No overload accepts these
  argument types». Ожидания нет, и выбор строки спрашивает `lit_admits`
  (`sem/type_shape.nv`). Та знала только числовые примитивы.

`57cf601b1`: `lit_admits` смотрит сквозь newtype на его представление и судит литерал по
правилу представления. Рекурсия, так что работает и newtype над newtype.

**Тест** — `pipeline/overload_test.nv`:
- набор перегрузок и одна строка — приняты;
- **контроль**: дробный литерал `1.5` в newtype над `int` — по-прежнему отказ.

**В обе стороны.** Ветка newtype в `lit_admits` выключена → тест красный
(`overload_test.nv:181`, `ds.len() == 0`). Правка возвращена → зелёный.

**Проба `newtype-literal-arg`.** Оракул печатает `1 2 3 7`. Бинари части 7 (`q4`, `r4`)
отказывают на check. Теперь — SAME stdout.

## Чего правка не трогает

Сверено с оракулом на отдельной пробе:

- **Типизированная переменная в newtype.** `ro n = 7; f(n)`, `g(n, 3)`: Карина отказывает,
  оракул отказывает (E_NO_MATCHING_OVERLOAD, E7301). Совпадает с амендментом D55: переменная —
  только явно.
- **Арифметика констант** (`g(40 + 2, 3)`). Оракул принимает, Карина отказывает отказом
  подмножества. Это **не про newtype**. То же самое на `u8`: `k(40 + 2, 1)` и `h(40 + 2)` при
  `fn k(b u8, ..)` отказаны. Нетипизированную константу-выражение Карина не сворачивает ни в
  какую узкую позицию. Отказ честный (E_NOVAC_SUBSET), не тихий. Нужна строка реестра
  (Карина, 🟡 К2, `№TBD`). Маршрут не мой — это отдельная волна по D489.
