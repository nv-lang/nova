# План 235 — `std.math.bigint`: целые произвольной точности на чистом Nova

**Статус:** 📋 ОФОРМЛЕН 2026-07-23 (решение владельца из обсуждения «CPython/лицензия/bignum»).
Реализация НЕ начата. **Приоритет:** P3 (не блокирует v0.1; очередь — ПОСЛЕ тегов).

> ✅ **Карацуба в V1 ПОДТВЕРЖДЕНА владельцем 2026-07-30** («это же паритет или лучше,
> чем в Rust» — да: в Rust-std bignum нет вовсе, эталон num-bigint несёт лестницу
> школьное→Карацуба→Toom-3; V1 с Карацубой = паритет по среднему диапазону, Toom-3 —
> V2). Порог переключения Карацуба↔школьное — ИЗМЕРИТЬ, не выдумывать (Ф.0-замер).
> Остальные правки того же коммита (мутирующие `@add_assign`/`@sub_assign`/`@mul_assign`
> против GC-шума в циклах; явные `i128 @to_bigint` / `BigInt @to_i128`) — приняты сразу.
**Не язык-меняющее** (библиотека) → D-амендмент не требуется; ЕСЛИ Ф.0 вскроет дыру
операторного desugar'а для типов с heap-данными — амендмент поедет со слиянием той волны.

## 0. Мотив

Произвольная точность как std-опция уровня Python `decimal`/Go `math/big` — НЕ замена
машинным `int`/`i64` (ядро остаётся fixed-width + trap-политика D423). Путь реализации —
**чистый `.nv` без C/GMP/заимствований из CPython** (эталон — Go `math/big`, чистый Go):
- §3-конвенция (`[[feedback-maximize-nv-sourcing]]`): bignum — переносимая чистая
  арифметика, ровно тот класс кода, что обязан жить в `.nv`;
- лицензионно вставка CPython `longobject.c` возможна (PSF-2.0 пермиссивна, прецедент
  THIRD_PARTY minicoro/LuaCoco), но технически он врос в PyObject/refcounting — извлечение
  дороже написания с нуля; GMP — LGPL (статик-линковка = боль), libtommath — не нужен,
  раз пишем на Nova;
- витринная ценность: «серьёзная числовая библиотека на Nova» — dogfooding Vec/срезов/
  протоколов/операторного desugar'а, аргумент того же класса, что aggregator.

## 1. Объём V1 — ТОЛЬКО целые (ответ на вопрос владельца 2026-07-23)

**Плавающей точки в этом плане НЕТ.** `BigDecimal` (десятичная, деньги), `BigRat`
(рациональные), `BigFloat` (двоичная произвольной точности) — отдельные будущие типы,
ВСЕ строятся поверх BigInt (BigRat = пара BigInt; BigDecimal = мантисса-BigInt +
экспонента) — целочисленный фундамент первичен. Сосед по папке: `std/src/math/int128.nv`
(фиксированная ширина) — BigInt его произвольно-точное дополнение, не замена.

## 2. Дизайн (V1)

- **Представление:** `type BigInt value { sign Sign, limbs []u32 }`, где
  **`type Sign enum Neg | Zero | Pos`** (решение владельца 2026-07-29) — лимбы
  little-endian по 32 бита; промежуточные вычисления в `u64` (переполнение невозможно по
  построению — та же причина, по которой CPython держит 30-битные «цифры»: у Nova нет
  u128, значит u64-лимбы потребовали бы 128-битного умножения).

  **Value-record:** BigInt на стеке (копия = Sign-clr + slice header: ~24 байта). Vec-data
  лимбов — на GC-куче; при копировании BigInt копируется slice-указатель, данные разделяются.
  Иммутабельность гарантирует отсутствие alias-мутаций. `==` на value-record — структурное
  (field-by-field) по умолчанию (D328), `#impl(Equal)` не требуется для `==`.

  **Почему sum-тип, а не число.** Прежняя запись плана (`sign i8`) отвергнута:
  (а) памяти не экономит — `limbs` это Vec с выравниванием 8, так что один байт знака
  превращается в 1 + 7 паддинга, итог тот же, что у `int`; (б) плодит касты на каждом
  конструкторе и сравнении (`{ sign: 0 as i8, ... }`) и тянет за собой integer promotion
  узких типов в C — ровно тот класс, под который в плане 234 пришлось расписывать
  отдельную таблицу эмиссии; (в) допускает бессмысленные значения (`sign = 7`), из-за
  чего инвариант «знак ∈ {-1,0,+1}» приходится держать тестами вместо типа. Эталоны
  числового поля не используют: Go `math/big` — `neg bool`, Rust `num-bigint` —
  `enum Sign { Minus, NoSign, Plus }`, CPython кодирует знак в длине. С `Sign`-enum
  невалидное состояние невыразимо, а `-0` не может возникнуть ПО ПОСТРОЕНИЮ, а не по
  проверке. Цена — трёхстрочный `match` для умножения знаков.
- **Инварианты нормализации:** без ведущих нулевых лимбов; ноль = пустые limbs + `Zero`
  (каноничен, единственное представление). Каждая операция возвращает нормализованное.
- **Семантика значений:** immutable; операции возвращают НОВЫЙ BigInt (чистые fn, без
  эффектов; паника только на div-by-zero — паритет `int`).
- **API V1 (конверсии — СТРОГО `to_*`-канон, nv-coding-style §1/D410: `from_*` только для
  концептов-не-ресиверов; линт W_STATIC_CONVERSION):**
  `fn[T Ints] T @to_bigint() -> BigInt` (generic по образцу `T @to_millis` — все ширины
  одним методом, infallible) и `str @to_bigint() -> Option[BigInt]` (десятичная, ведущий
  `-`; fallible → Option) — extension-методы в модуле bigint; статики только
  не-конверсионные: `BigInt.zero()/one()`. Операции: `@plus/@minus/@times` +
  `@div_rem -> (BigInt, BigInt)` (деление trunc-к-нулю — паритет `int`), производные
  `@div/@rem`; `@neg/@abs`; `@compare/@equal` (операторы `==`/`<` через существующий
  desugar); `@to_str()`, `@to_int() -> Option[int]` (fits-проверка), `@is_zero()/@sign()`.
- **Операторный desugar:** `+`/`-`/`*`/`/`/`%` → `@plus/@minus/@times/@div/@rem` —
  прецедент: `str` (value-record с heap-данными) даёт `+` через `@plus`; DCE-seed арифметических селекторов уже починен (`d20e891a8`). Ф.0 пинует
  фикстурой ДО начала ядра.
- **Мутирующие операции (добавлено):** иммутабельность — семантически правильна, но в
  циклах (`acc = acc * n`) каждая операция аллоцирует новый BigInt, а старый идёт в GC.
  Для циклов и накопителей добавить `mut @add_assign(other)/@sub_assign(other)/
  @mul_assign(other)` — переиспользуют `limbs`-буфер (clear + fill), 0 дополнительных
  аллокаций. Не часть `+`-desugar'а (мутабельность не перегружается), явные методы.
- **Конверсия i128 ↔ BigInt (добавлено):** `fn[T Ints] T @to_bigint()` покрывает все
  примитивные ширины (i8..i64, u8..u64). i128 — библиотечный тип (i64, u64), не `Ints`,
  под этот generic не подпадёт. Нужен явный `i128 @to_bigint() -> BigInt` и
  `BigInt @to_i128() -> Option[i128]` (fits-проверка).
- **Литералов и коэрсий НЕТ:** никакого неявного `int → BigInt` (аллокация ≠ zero-cost —
  вне полос D429 #coerce принципиально); только явные `to_bigint`-вызовы. Литеральная форма
  `123456789012345678901n`-стиля — не в V1, отдельное решение владельца, если понадобится.
- **Дом — ОТДЕЛЬНЫЙ ПАКЕТ В СВОЕЙ РЕПЕ `nova-bigint`** (решение владельца, зафиксировано
  2026-07-29; прежняя запись «folder-module `std/src/math/bigint/`» была ОШИБОЧНОЙ —
  решение принималось в обсуждении и в план не попало, из-за чего первая проба ушла
  писать в `std/`). Раскладка — как у `nova-tls`/`nova-compress`/`nova-polaris`: своя
  репа, remote `origin`, дефолт-ветка `master`, свой `nova.toml`, свои теги. В `std`
  bigint НЕ живёт: ядро остаётся fixed-width (D423), произвольная точность —
  подключаемая зависимость, а не часть обязательной поставки.
  Тесты — рядом с модулем (`*_test.nv`, конвенция module-tests-beside-module).

## 3. Фазы

- **Ф.0 Разведка/дизайн-фиксация (короткая, интегратор или opus-полдня):** (1) фикстура
  операторного desugar на value-record с `@plus/@compare` — подтвердить, что `+`/`<`
  работают (иначе — вопрос владельцу + возможный D-амендмент той же волной); (2) выбор
  чанк-базы строковых конверсий `str @to_bigint`/`@to_str` (кандидат: 10^9 на u32-лимб —
  9 десятичных цифр за умножение); (3) замер threshold`а Карацуба↔школьное на
  репрезентативных размерах лимбов; (4) API-ревью владельцем (имена выше — предложение).
- **Ф.1 Ядро (sonnet):** представление + нормализация + `T @to_bigint`/`@to_int` + сложение/
  вычитание величин (limb add/sub с переносом на u64) + `@compare/@equal/@neg/@abs` +
  знаковая обвязка.
- **Ф.2 Умножение и деление (sonnet, отдельная волна — самый рискованный кусок):**
  умножение Карацубы O(n^log₂3) с переключением на школьное O(n²) для малых n
  (threshold — Ф.0); `@div_rem` — алгоритм Кнута D (нормализация делителя,
  quotient-догадка с коррекцией) — вектор-тесты обязательны на КАЖДЫЙ edge (см. Ф.4).
- **Ф.3 Строки (sonnet):** `str @to_bigint` (чанки по 9 цифр, `times(10^9)+chunk`),
  `to_str` (повторный `div_rem(10^9)` + паддинг).
- **Ф.4 Тесты (sonnet пишет карту+тонкие, haiku — вектора по литеральному образцу):**
  рядом с модулем; identities на seeded-PRNG малых значениях против `i64`-эталона
  ((a±b), (a*b), (a/b)*b+r==a, trunc-знаки — PRNG = splitmix64 с `.wrapping_*` по образцу
  aggregator/scenarios.nv); канонические вектора: 100!, 2^521-1, цепочки
  s.to_bigint→to_str==identity на 1000-значных числах; edge-вектора Кнута D (делитель из
  одного лимба / равные старшие лимбы / normalize-shift границы — образцы из Go
  math/big тест-набора ПО ЗНАЧЕНИЯМ, не по коду). Большие вектора — в репо, но НЕ в
  дефолт-прогон (feedback-large-tests-stored-not-in-regress).
- **Ф.5 Закрытие:** doc-комменты по nv-coding-style, STATUS-строка, запись в
  simplifications при упрощениях; (опц.) bench через std bench-харнесс — числа в план V2.

## 5. Риски

| Риск | Митигация |
|---|---|
| Кнут D — классика тонких багов (quotient-коррекция, normalize) | отдельная волна Ф.2 + обязательные edge-вектора по значениям Go-тестов + identity-тесты на PRNG |
| Операторы на value-record не desugar'ятся | Ф.0-пин ДО ядра; fallback V1 = методы без операторов, операторы отдельной волной |
| Перф: Карацуба в V1 сложнее школьного, threshold чувствителен | threshold — Ф.0-замер на репрезентативных размерах; fallback на школьное |
| GC-шум от иммутабельных операций в циклах ("a = a + 1" аллоцирует на каждом шаге) | mut-методы `@add_assign`/`@mul_assign` в том же V1 — переиспользуют буфер, 0 аллокаций. Если mut-методов нет — цикл из 10⁵ итераций породит 10⁵ × размер BigInt мертвых объектов |

## 6. Вне объёма (V2+ по отдельным решениям)

Тоом-Кука; битовые операции и сдвиги как публичный API; `gcd/modpow` (появятся при
crypto-запросе); `BigDecimal`/`BigRat`/`BigFloat`; неявные коэрсии/литералы; интеграция
в generic-числовые type-sets (D310) — отдельный языковой вопрос.
