# План 274.16 — Карина 0.3: все примеры и пакетные репозитории

**Статус:** ПЛАН СОГЛАСОВАН владельцем 2026-10-12; реализация не начата. Родитель —
[274, ступень 0.3](274-novac-self-hosted-compiler.md#03--карина-собирает-все-пакеты-nova-и-все-примеры).
Это исполнимый подплан трёх условий родителя, а не новая версия критериев. [274.11](274.11-carina-release.md)
ведёт выпуск и закрывается позже; здесь не дублируется его релизная процедура.

   **№1922 БЛОКИРУЕТ ТЕГ** ([221.1](221.1-bug-sweep.md), запись №1922):

   классификация каждого отказа корпуса примеров, требуемая Ш.5, штатным
   путём невозможна.

## Зачем отдельный подплан

У 274 §0.3 есть машинный финиш — примеры, все пакеты и CI на одном коммите, — но нет
порядка построения драйвера `nova build`/`nova test`, доказательного протокола для
peer-файлов без `main` и матрицы пакетных репозиториев. Подпланы 274.1–274.15
разбирают архитектуру, подмножество, самосборку и выпуск; ни один не соединяет
все три условия 0.3. Одна лишь `novac check`/`emit` не собирает и не запускает
пользовательскую программу. Граница архитектуры остаётся прежней:
компилятор не ведёт пакетный граф, зависимости и тулчейн; этим занимается драйвер
([novac-architecture](../dev/novac-architecture.md)). Наружу выходит бинарь `nova`
с привычными командами, не отдельный пользовательский `novac`.

## Исходная точка — измерение, а не база для ручного обновления

Срез 2026-10-12: `origin/main = 42732280e2d339ed5d955659dcc046771ca2d56b`;
сохранённый B Carina 0.2.0 из приёмки #55, SHA256
`b3df460726e92eca612d7df3497c1a6184c07f415bf58f80001717cb2cf8536f`.
Именно **эта пара разных ревизий** измерена, а не один CI-кандидат 0.3.

* `check-novac-differential.sh . <B>`: 285 фикстур, исходы совпали с учётом 11
  записей allow; этап поведения красный — 22 принятые обеими сторонами программы
  разошлись по сборке либо ответу. Стадия примеров в этом вызове **не достигнута**.
* Отдельно `NOVAC=<B> NOVAC_STALE_OK=1 sh scripts/tools/novac-diff-corpus.sh`:
  118 файлов `examples/` — 66 приняли оба, 5 отвергли оба, 43 отставание
  Карины, 4 «вне точки», DANGER 0, PANIC 0; 61 совпал поведенчески, 1 разрешённое
  расхождение и 4 принятых peer-файла без `main`, которые раннер не исполняет.
  `NOVAC_STALE_OK=1` здесь **объявляет** намеренный замер выпущенным старым B,
  а не разрешает использовать протухший бинарь на будущей приёмке.
* Девять локальных пакетов с `nova.toml`, всего 196 файлов `src`: `bignum` 18
  (check 5, emit 0), `compress` 16 (2, 0), `duckdb` 11 (0, 0), `http` 29
  (3, 0), `polaris` 70 (5, 1), `postgres` 29 (2, 0), `sdl` 4 (0, 0),
  `socks` 2 (0, 0), `tls` 17 (1, 0). Итого check 18/196, emit 1/196;
  таймаутов нет. Причины первых отказов: атрибуты эффектов, `Db` без runtime
  оболочки, parser/subset, composite newtype, поле без типа, имя `HttpError`,
  известный ICE анонимного конструктора №1484/№1705. Это **не** `build/test`:
  выпущенный B знает только `check`/`emit`; обе отсутствующие команды дают exit 2
  и `usage`.
* Исторический Oracle `pkg-gate` зелёный у семи пакетов, но в основном судит
  `nova test src`, не отдельный `nova build`. У `nova-duckdb` нет зелёного CI,
  локальный `nova-sdl` не имеет remote/GitHub CI. Ни один из этих фактов не
  заменяет пакетную приёмку Кариной.

Эти differential-числа — только историческая диагностика пары ревизий, не
критерий правильности и не expected-output oracle. Решение владельца 2026-10-14:
нормативный источник — D-блоки и остальная спецификация; Oracle не служит ни
ежедневным seed, ни судьёй ожидаемого результата. Oracle-сравнение ниже может
остаться необязательной диагностикой: его краснота означает «расследовать», но
не «Carina ошиблась», не `by-design` и не основание для allow. Например, D484
([03-syntax.md](../../spec/decisions/03-syntax.md#d484)) нормативно требует
лево-направо порядок аргументов; Oracle-нарушение зарегистрировано как №685 в
[221.1](221.1-bug-sweep.md#685). Это противоречие реализации спеке, а не
допустимое поведение Carina.

Подтверждённое решение владельца/интегратора 2026-10-14: #85/Oracle не является
зависимостью для landing #82 или начала 0.3; изменить критический путь можно
только конкретным измеренным blocker на закреплённом Carina B.

Числа **переснимаются командой на каждом кандидате**, не переписываются в этом
абзаце как текущие. Для полного дифференциала нужен годный scratch с ASCII-путём
и собранным оракулом: первый замер с Unicode-путём сломал PCH и дал 277 ложных
расхождений, которые в базу не вошли. Зелёное «судить нечего» не доказательство.

## Решения владельца и границы результата

1. Ступень 0.3 имеет ровно критерии 274 §0.3: сборка и запуск примеров без
   расхождения ожидаемого вывода; `nova build` и `nova test` в **каждом** пакетном
   репозитории тем же бинарём, взятым из фактического дерева; зелёный CI на том
   же коммите. Зелёный `check` либо выдача C этим не подменяются.
2. `emit` **остаётся временной публичной командой** по слову владельца
   2026-10-12. Появление `build` само по себе её не удаляет. Снятие — только
   отдельное решение владельца с миграцией вызывающих smoke/differential и
   проверкой совместимости CLI; до него осознанное исключение живёт в
   `novac/cli-divergences.allow`. Это уточняет прежнее обещание удалить `emit`
   той же волной, что `build` (274.13 §«Вопрос 7», П26/allow).
3. Для четырёх peer-файлов без `main` исполнитель проверяет компиляцию в
   составе их программы/модуля и доказывает, какая запускаемая точка входа их
   использует; запускаются точки входа. Голый файл без `main` не объявляется
   исполняемым бинарём и не исчезает из знаменателя. Это рабочее толкование
   согласованного владельцем плана; если найдётся сиротский peer-файл, приёмка
   красная до явного решения, а не зелёная по умолчанию.
4. Пять файлов, которые отвергают **оба** компилятора на исходном срезе, нельзя
   молча исключить из буквального «каждый файл» §0.3. Сначала назвать каждый
   и проверить, это намеренно негативный пример или дефект; спорную форму
   предъявить владельцу до закрытия ступени. Записать исключение вместо
   исправления можно только его явным решением с изменением критерия 274.

## Очередь работ и машинная приёмка каждой волны

### Ш.0 — закрепить release seed и доказать его воспроизводимость

**Уточнение решения владельца 2026-10-14:** pin — опубликованный release
asset и SHA; этот пункт заменяет прежнее предположение о незакреплённом B.
**Решение владельца 2026-10-19:** «Карина с0.2.1 собирается без запуска Oracle».
Для опубликованной Windows alpha это утверждение доказывает B1 emit:
опубликованный B1 при pinned source выдаёт B2raw.c, побайтно равный B1.c,
выданному stage A. Это C-level bootstrap fixed point, а не native B2 build.
Native EXE/PDB/LIB equality не доказана и не требуется; это отдельная цель
воспроизводимой сборки, не gate.

**Что:** для Windows взять Carina 0.2.1 alpha `nova-carina-0.2.1-windows-x86_64.zip`
и проверить SHA-256 по `SHA256SUMS`; это закреплённый кандидат Windows B. Для
C-level доказательства использовать SHA опубликованного B1
`824bf597f8f073c68961df8b824ef5d4e72c4b463c47b727a4e121716f6996f4` и exact
source tree `3729abcce42ec2d94efc898ec6eafe91ff6210d5`. Независимый
post-release прогон дал B1.c и B2raw.c по 13,250,302 bytes, SHA-256
`25c5404f1e8e175652f19c9ca6cb03d29de82cee70a7cd9f4258c6724115c8a0`, stderr
пуст; C стадии A имеет тот же ожидаемый digest. Первоначальную Carina A построил
published Oracle 0.1.0; A выдала B1.c, а Clang построил опубликованный B1 из
этого C. Это историческая одноразовая стадия A: verifier не исполняет Oracle.
Использованы GC headers Oracle 0.1.0 и saved run2 libraries/source3729.
Исходный независимый raw прогон был из cwd `<source-tree>` с
`NOVA_STD_PATH=<source-tree>/std/src`, относительным `NOVAC_SELF_PATH=novac/src`
и `cmd` raw stdout redirect, не PowerShell text redirection; absolute
`NOVAC_SELF_PATH` не проверялся. Повторяемая команда:
`python scripts/tools/verify-carina-bootstrap-c.py <pinned-source-tree> --asset <published-zip-or-executable> --work-dir <scratchpad>`.
Verifier берёт управляемый baseline `scripts/guards/carina-bootstrap-c.baseline`,
проверяет asset/source provenance, задаёт
`NOVA_STD_PATH` и `NOVAC_SELF_PATH`, проверяет сырые байты C и завершится
ошибкой при несовпадении. Локальный `RESULT.txt` был только входом для этой
записи, не долговременным/публичным путём. Baseline обновляется только явной
правкой с записанной причиной в `update_reason`. Вход — полный Git source tree,
не source archive: archive не несёт Git ancestry/cleanliness для provenance
проверки; Oracle fallback не используется. Pin — release asset + SHA. Никогда не
перезаписывать/заменять опубликованный asset:
исправление получает новое, различимое имя. Git manifest является только
метаданными (asset name, URL, SHA-256, source SHA/version, compiler provenance);
несовпадение должно дать ясный отказ. Сам manifest в #82 не менять: его правка
разрешена только в отдельно и явно названной владельцем задаче; такую задачу
здесь не создаём.

Для Linux требуется отдельное A→B→C byte-identical доказательство; Linux
release и pin будут отдельной будущей работой после этого доказательства.
До того Linux 0.3 может идти только с явно объявленным временным исключением:
Oracle — исключительно stage-A compiler исходников Carina, создающий Carina B;
затем Carina B строит Carina C на том же source SHA/platform. Linux examples и
packages запускаются под полученными Carina-built B/C, а отчёт сохраняет source
SHA и provenance каждой стадии. Это исключение не является Linux B pin: нельзя
заявлять Linux B≡C, Oracle-free bootstrap или полноценное Linux Carina-seeded
доказательство до отдельного Linux proof/release. Windows Ш.1 может начаться до
Linux proof. Specs/golden outputs остаются судьёй поведения и на Linux.

Для опубликованного закреплённого B Windows gate — сравнение B1→C выше, не
равенство native executable. C-level результат подтверждён; native EXE/PDB/LIB
equality — отдельная цель воспроизводимой сборки и не gate.
Неверный asset/SHA, изменённый source, отсутствующий output или stderr дают
отказ, не пропуск/PASS. Ограниченный Windows proof не распространяется на
Linux. Linux сохраняет отдельный A→B→C byte-identical proof; критерии 0.3
build/test/examples/packages не меняются.

**Приёмка:** verifier принимает опубликованный asset/digest и exact source SHA;
саботаж asset/SHA/source или expected C digest даёт RED, восстановление —
GREEN; пропуск стадии не может дать PASS. Приёмка глазами, потому что
независимый приёмщик должен подтвердить выбранный опубликованный asset и
stage provenance по trace. Linux exception принимается только с
явным label, stage provenance и Carina-built B/C как исполняемыми бинарями;
необъявленный fallback, запуск примеров/пакетов под Oracle, либо заявление
Linux B≡C/Oracle-free без отдельного Linux proof/release — FAIL. Не смешивать этот seed-proof
с Oracle-сборкой текущего `gate-novac.sh`: см. отдельную gate-волну ниже.

### Ш.1 — зафиксировать честную карту и программу испытаний

**Что:** после Ш.0 построить полный inventory всех `examples/` entry points и
peer-файлов, package roots и применимых conformance-кейсов; связать каждый
позитивный/негативный случай с нормативным D-блоком или явно назвать
спецификационный пробел. Для позитивов закрепить golden stdout/stderr/exit; для
негативов — line-pinned `nova:expect`. Классифицировать пять исходных случаев,
которые отвергали оба компилятора, по спецификации — не голосованием Oracle.
Для каждого класса — минимальный репро и положительный сосед. Зафиксировать
точные команды, seed mode (pinned asset либо Linux stage-A exception),
source SHA/stage provenance, platform, stdout/exit и evidence в named каталоге
волны. Oracle differential разрешён только отдельным диагностическим
отчётом с версиями обоих компиляторов: его краснота не является ни критерием,
ни разрешением записать intentional divergence.

**Приёмка:** inventory перечисляет каждый entry и peer ровно один раз, с
нормативной ссылкой, goldens или line-pinned negative и причиной каждого
исключения; пять общих отказов классифицированы по spec. Отсутствующий
пример/пакет, пустой filter, нулевая работа или удалённый expected output дают
ненулевой отказ. Тихое отключение smoke/corpus не PASS. Seed и кандидат имеют
проверенный provenance. Устаревший B нельзя использовать как текущий кандидат.

**Carina `env_bytes` probe; Oracle #1594/#1850 — только optional diagnostic
(результат Carina пока не измерен):** в Ш.1, до пакетной матрицы Ш.6, сохранить
в evidence точные `check`, `emit` и `build` выводы и коды возврата Carina
(clang и MSVC, если доступны) на вызовах
`env_bytes("RAW")` и `env_bytes("B", raw)`, включая строковый литерал в каждой
позиции, плюс на контрольной неперегруженной функции с параметром `[]u8` и на
несовпадающем типе. Сопоставить с существующей
`std/src/os/n1850_probe/env_bytes_str_literal_test.nv`; тест не ослаблять.
Разделять результаты: #1594 — конкретно codegen приведения литерала к `[]u8`
при разрешении перегрузки; #1850 — отдельно MSVC C2099 в Windows-единице
`std.os`. Oracle compare можно приложить отдельно как optional diagnostic;
зафиксировать его версии и результат, но не использовать для acceptance, не
объявлять Oracle-ошибку обязательным поведением Carina и не утверждать заранее,
что Carina проходит.

### Ш.2 — отдельное будущее Linux-доказательство

**Что:** в самостоятельной задаче провести на Linux A→B→C по
`scripts/tools/double-build.sh`, сравнить B≡C побайтно и привязать вывод к
точному SHA/CI; только затем отдельно решать выпуск Linux-артефакта. Linux CI
имела лишь одиночную сборку novac; Windows Carina 0.2.1 alpha не является
доказательством Linux fixed point.

**Приёмка:** сохранены B.c/C.c и B/C бинарные SHA/`cmp` с нулём различий,
команда и платформа, зелёный CI того же SHA; изменение одного байта в копии
одного сравниваемого артефакта даёт красный comparator, оригиналы сохранены.
Это **параллельный выпускной трек**, не притворяется пакетной приёмкой 0.3.

### Ш.3 — №895 после 0.2, до массового перехода на пакеты

**Что:** исправить дефект оракула при статическом вызове через type-parameter
bound: Nova-тип (включая newtype) входит в имя mono-инстанса, C-параметр остаётся
представлением. Не подменять фикс обходом `len()` в новых местах; измерить
дубли одинаковых тел для разных newtype.

**Приёмка:** четыре клетки 274 §«После 0.2 — №895»: newtype над примитивом и
над записью печатают значение; `mk[FnRow]` и `mk[int]` в одной программе
различимы; `I=int` без реализации протокола отвергается. Саботаж mono-ключа
возвращает именно красноту различимости, после восстановления все клетки
зелёные. Работа оракула живёт по его D/registry-процедуре отдельно от CLI
Карины; если она не блокирует волну, не утверждать обратное без замера.

**Критический путь:** №895 — параллельный долг Oracle, не prerequisite для 0.3.
Вернуть его на критический путь можно только по измеренному blocker на
закреплённом Carina B; Oracle differential/red само по себе blocker не создаёт.

### Ш.4 — штатный драйвер `nova build`, не переименование `emit`

**Что:** тонкий CLI передаёт драйверу вход/манифест/lock и std, драйвер
разрешает зависимости, выбирает программу, вызывает Карину для C, собирает
и линкует с runtime; без второй самодельной двери языка или интерпретатора.
Сверить входы, выходы и флаги с существующим Oracle CLI и П26. Публичная
`emit` остаётся доступной с прежним контрактом и названной allow-записью.

**Уточнение границы (решение интегратора для задачи 108):** Rust остаётся

Linux route не является доказательством Carina build и не расширяет Windows
partial milestone.

### Ш.5 — примеры: от класса отказа до совпадения ответа

**Что:** устранить измеренные группы parser/check/emit/driver и несоответствия
нормативной спецификации. Ratchet корпуса двигать **тем же коммитом** после
замера, без подгонки конечного числа; D-linked golden stdout/stderr/exit и
line-pinned negatives фиксировать для каждого запускаемого примера. Peer-файлы
проверять вместе с entry; пять общих отказов и четыре «вне точки» явно
классифицировать по Ш.1. Oracle differential — необязательное diagnostic-only
приложение, не acceptance.

**Приёмка:** каждый entry в `examples/` собран и исполнен Carina-built `nova`
из platform seed mode: pinned B, либо явно объявленный Linux stage-A exception;
совпадает с D-linked golden stdout/stderr/exit; каждый peer скомпилирован в
названной программе. Полный spec-conformance inventory даёт
вердикт по последнему случаю: нет непокрытых D-block требований и `lag = 0`
по применимой мере. Саботаж golden output и peer-импорта краснит; удаление
expected output/примера или нулевая работа тоже краснят. Oracle comparison —
необязательная диагностика, она не заменяет этот критерий и не создаёт allow.

### Ш.6 — штатный `nova test` и матрица спутников

**Что:** тестовый драйвер поверх той же сборки обнаруживает единицы и маркеры,
собирает и запускает, сохраняет диагностические/выходные контракты и отказ
при нуле найденных тестов. Затем **один и тот же** Carina-built `nova` проводит
`build` и `test` в каждом package root фактического дерева (на исходном срезе:
`bignum`, `compress`, `duckdb`, `http`, `polaris`, `postgres`, `sdl`, `socks`, `tls`).
Нативные зависимости DuckDB/SDL именуются в отчёте, не превращаются в silent skip.

**Приёмка:** для каждого репозитория — HEAD, команда, число найденных/исполненных
тестов, stdout/exit обоих вызовов и адрес точного CI, если он существует.
Оба вызова зелёные на одном Carina-built binary per platform: pinned-B-seeded,
либо Linux B/C из явно объявленного временного Oracle stage-A exception.
Зафиксировать режим, asset/digest если pinned, stage provenance, source/binary
SHA, platform и freshness. Отсутствие тестов, запуск под Oracle binary,
необъявленный stage-A fallback и любой пропуск краснеют проверкой
происхождения/счёта.
У `duckdb` исторически не было
зелёного CI, у локального `sdl` нет remote — это предел **прошлого контроля**,
не разрешение исключить пакеты из новой матрицы.

### Ш.7 — точный кандидат 0.3

**Что:** независимый приёмщик строит кандидат от свежего `origin/main`, фиксирует
seed mode (pinned release asset либо явно названное Linux stage-A exception),
digest если pinned, source SHA/stage provenance, SHA/platform/freshness
Carina-built `nova` и runtime/stdlib дерева, запускает полную матрицу и семь
обязательных CI workflows **на том же коммите**, без skip, затем штатные precheck,
замок и вливание только проверенной вершины. При сдвиге main — новый кандидат
и новый CI, не перенос старого зелёного ярлыка.

**Приёмка:** доказаны все три пункта 274 §0.3, все CI workflows exact-SHA
зелёные без skip, `check-push-proven-by-ci.py` отвечает `ok` на точном SHA;
неверный seed/SHA, запуск примера/пакета под Oracle, необъявленный Oracle
stage-A exception, один красный пакет/пример или skip не получают зелёную
приёмку. Разрешённый Linux exception должен быть явно помечен, с source SHA и
stage provenance, и не даёт права заявить Linux B≡C или Oracle-free bootstrap.
Публикация 0.3 и теги —
отдельное решение владельца после приёмки, не побочный эффект этой волны.

**Gate dependency (отдельная code/gate wave, не работа этого плана):** сейчас
`scripts/gate-novac.sh` (примерно строки 476–533) проверяет свежесть и строит
`novac` через Oracle; GitHub `nova-gate` вызывает этот ярус. До включения 0.3 CI
нужен fail-closed переход на проверенный pinned-B bootstrap и отдельный
spec-conformance lane; единственное временное исключение — явно объявленный
Linux stage A, который обязан завершиться Carina-built B/C без Oracle как
runtime/behavior judge. Старый Oracle-gate PASS не доказывает Carina; его краснота
не переписывает спеку и не оправдывает bypass/allow. Если текущий Oracle-gate
мешает новой lane, остановить кандидат и координировать отдельную gate-задачу;
не ослаблять CI.

**Параллельный Oracle debt:** №895 в Ш.3 и прочие дефекты Oracle не в критическом
пути 0.3. Пересмотр допустим только при измеренном blocker на закреплённом B;
сравнение с Oracle само по себе blocker не создаёт.

## Стоимость и машина

Факты исходного прогона на общей машине: девять пакетов `check/emit` — 6 мин;
корпус примеров — 10 мин; полный differential до ранней красноты — 11 мин.
Первый невалидный запуск с Unicode scratch занял 29 мин и в оценку продукта
не входит. Для полного дифференциала после исправлений резервировать
**20–40 мин как оценку, не обещание**, затем заменить фактической стеной.
Linux double-build — три тяжёлых звена с пределом скрипта до 900 с каждое,
фактическое время ещё не измерено. Девять native `build/test` до появления
драйвера не оценивать числом по Oracle. Все локальные тяжёлые команды — общая
`machine: true` очередь; полный `nova test`/мега-CU не запускать окном задачи.

## Не делаем

* Не удаляем `emit` в волне `build` и не обещаем автоматического срока удаления.
  Не меняем публичный CLI Oracle и язык ради временного шва.
* Не расширяем ступень 0.3 всеми тег-зависимыми планами 274.11: их очередь —
  после 0.3 к 1.0. `ИСКЛЮЧЕНИЕ 0.3` допустимо только для измеренного блокера
  ступени либо доказанной цены откладывания; причина пишется в статусе
  **того** плана. На исходном срезе ни одно исключение не доказано.
* Не выдаём Linux одиночную сборку за Linux B≡C, `check`/`emit` за `build/test`,
  старый зелёный Oracle CI за пакетный Carina CI, пропущенный тест за PASS.
* Не правим спутники ради маскировки дефекта компилятора и не снижаем
  ожидания тестов. Изменение пакета, нужное для новой нормы, — отдельная
  scoped задача с собственной приёмкой.
