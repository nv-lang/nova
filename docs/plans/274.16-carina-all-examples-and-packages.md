# План 274.16 — Карина 0.3: все примеры и пакетные репозитории

**Статус:** ПЛАН СОГЛАСОВАН владельцем 2026-10-12; реализация не начата. Родитель —
[274, ступень 0.3](274-novac-self-hosted-compiler.md#03--карина-собирает-все-пакеты-nova-и-все-примеры).
Это исполнимый подплан трёх условий родителя, а не новая версия критериев. [274.11](274.11-carina-release.md)
ведёт выпуск и закрывается позже; здесь не дублируется его релизная процедура.

## Зачем отдельный подплан

У 274 §0.3 есть машинный финиш — примеры, все пакеты и CI на одном коммите, — но нет
порядка построения драйвера `nova build`/`nova test`, доказательного протокола для
peer-файлов без `main` и матрицы пакетных репозиториев. Подпланы 274.1–274.15
разбирают архитектуру, подмножество, самосборку и выпуск; ни один не соединяет
все три условия 0.3. Одна лишь `novac check`/`emit` не собирает и не запускает
пользовательскую программу. Граница архитектуры остаётся прежней:
компилятор не ведёт пакетный граф, зависимости и тулчейн; этим занимается драйвер
([novac-architecture](../dev/novac-architecture.md)). Наружу выходит бинарь `nova`
с привычными командами, не отдельный пользовательский `novac`.

## Исходная точка — измерение, а не база для ручного обновления

Срез 2026-10-12: `origin/main = 42732280e2d339ed5d955659dcc046771ca2d56b`;
сохранённый B Carina 0.2.0 из приёмки #55, SHA256
`b3df460726e92eca612d7df3497c1a6184c07f415bf58f80001717cb2cf8536f`.
Именно **эта пара разных ревизий** измерена, а не один CI-кандидат 0.3.

* `check-novac-differential.sh . <B>`: 285 фикстур, исходы совпали с учётом 11
  записей allow; этап поведения красный — 22 принятые обеими сторонами программы
  разошлись по сборке либо ответу. Стадия примеров в этом вызове **не достигнута**.
* Отдельно `NOVAC=<B> NOVAC_STALE_OK=1 sh scripts/tools/novac-diff-corpus.sh`:
  118 файлов `examples/` — 66 приняли оба, 5 отвергли оба, 43 отставание
  Карины, 4 «вне точки», DANGER 0, PANIC 0; 61 совпал поведенчески, 1 разрешённое
  расхождение и 4 принятых peer-файла без `main`, которые раннер не исполняет.
  `NOVAC_STALE_OK=1` здесь **объявляет** намеренный замер выпущенным старым B,
  а не разрешает использовать протухший бинарь на будущей приёмке.
* Девять локальных пакетов с `nova.toml`, всего 196 файлов `src`: `bignum` 18
  (check 5, emit 0), `compress` 16 (2, 0), `duckdb` 11 (0, 0), `http` 29
  (3, 0), `polaris` 70 (5, 1), `postgres` 29 (2, 0), `sdl` 4 (0, 0),
  `socks` 2 (0, 0), `tls` 17 (1, 0). Итого check 18/196, emit 1/196;
  таймаутов нет. Причины первых отказов: атрибуты эффектов, `Db` без runtime
  оболочки, parser/subset, composite newtype, поле без типа, имя `HttpError`,
  известный ICE анонимного конструктора №1484/№1705. Это **не** `build/test`:
  выпущенный B знает только `check`/`emit`; обе отсутствующие команды дают exit 2
  и `usage`.
* Исторический Oracle `pkg-gate` зелёный у семи пакетов, но в основном судит
  `nova test src`, не отдельный `nova build`. У `nova-duckdb` нет зелёного CI,
  локальный `nova-sdl` не имеет remote/GitHub CI. Ни один из этих фактов не
  заменяет пакетную приёмку Кариной.

Числа **переснимаются командой на каждом кандидате**, не переписываются в этом
абзаце как текущие. Для полного дифференциала нужен годный scratch с ASCII-путём
и собранным оракулом: первый замер с Unicode-путём сломал PCH и дал 277 ложных
расхождений, которые в базу не вошли. Зелёное «судить нечего» не доказательство.

## Решения владельца и границы результата

1. Ступень 0.3 имеет ровно критерии 274 §0.3: сборка и запуск примеров без
   расхождения ожидаемого вывода; `nova build` и `nova test` в **каждом** пакетном
   репозитории тем же бинарём, взятым из фактического дерева; зелёный CI на том
   же коммите. Зелёный `check` либо выдача C этим не подменяются.
2. `emit` **остаётся временной публичной командой** по слову владельца
   2026-10-12. Появление `build` само по себе её не удаляет. Снятие — только
   отдельное решение владельца с миграцией вызывающих smoke/differential и
   проверкой совместимости CLI; до него осознанное исключение живёт в
   `novac/cli-divergences.allow`. Это уточняет прежнее обещание удалить `emit`
   той же волной, что `build` (274.13 §«Вопрос 7», П26/allow).
3. Для четырёх peer-файлов без `main` исполнитель проверяет компиляцию в
   составе их программы/модуля и доказывает, какая запускаемая точка входа их
   использует; запускаются точки входа. Голый файл без `main` не объявляется
   исполняемым бинарём и не исчезает из знаменателя. Это рабочее толкование
   согласованного владельцем плана; если найдётся сиротский peer-файл, приёмка
   красная до явного решения, а не зелёная по умолчанию.
4. Пять файлов, которые отвергают **оба** компилятора на исходном срезе, нельзя
   молча исключить из буквального «каждый файл» §0.3. Сначала назвать каждый
   и проверить, это намеренно негативный пример или дефект; спорную форму
   предъявить владельцу до закрытия ступени. Записать исключение вместо
   исправления можно только его явным решением с изменением критерия 274.

## Очередь работ и машинная приёмка каждой волны

### Ш.1 — зафиксировать честную карту и программу испытаний

**Что:** на свежем кандидате одинаковой ревизии снять полный differential,
корпус примеров и список package roots из дерева; разложить 43+4 отказа и 22
поведенческих расхождения по **классам**, отдельно отмечая проблемы оракула,
окружения и ожидаемые негативы. Для каждого класса — минимальный репро и
положительный сосед; не чинить файл по имени как замену класса. Сохранить
точные команды, бинарные SHA, платформы, stdout/exit и артефакты в named
evidence текущей волны, не во временном корне диска.

**Приёмка:** корпус перечисляет каждый файл ровно один раз, сообщает все корзины,
нулевую или ненулевую работу и причину каждого отказа; заведомо отсутствующий
пример/пакет либо пустой filter даёт ненулевой отказ, а не «PASS 0». Тихое
отключение smoke/корпуса не принимается за полный вердикт. Удержание 0.2 B как
контроля помечено `stale` явно; выпускной кандидат мерится свежим бинарём.

**Отдельная проверка Oracle #1594/#1850 для Carina (результат пока не измерен):**
в Ш.1, до пакетной матрицы Ш.6, сохранить в evidence точные `check`, `emit` и
`build` выводы и коды возврата для Carina и Oracle (clang и MSVC, если доступны) на вызовах
`env_bytes("RAW")` и `env_bytes("B", raw)`, включая строковый литерал в каждой
позиции, плюс на контрольной неперегруженной функции с параметром `[]u8` и на
несовпадающем типе. Сопоставить с существующей
`std/src/os/n1850_probe/env_bytes_str_literal_test.nv`; тест не ослаблять.
Разделять результаты: #1594 — конкретно codegen приведения литерала к `[]u8`
при разрешении перегрузки; #1850 — отдельно MSVC C2099 в Windows-единице
`std.os`. Записать фактический исход каждого компилятора/команды, включая
недоступность или ранний отказ стадии, не объявляя Oracle-ошибку обязательным
поведением Carina и не утверждая заранее, что Carina проходит.

### Ш.2 — отдельное Linux-доказательство 0.2.1

**Что:** в самостоятельной задаче провести на Linux A→B→C по
`scripts/tools/double-build.sh`, сравнить B≡C побайтно и привязать вывод к
точному SHA/CI; только затем решать выпуск Linux-артефакта 0.2.1. В 0.2.0
опубликован Windows B, а Linux CI имела лишь одиночную сборку novac.

**Приёмка:** сохранены B.c/C.c и B/C бинарные SHA/`cmp` с нулём различий,
команда и платформа, зелёный CI того же SHA; изменение одного байта в копии
одного сравниваемого артефакта даёт красный comparator, оригиналы сохранены.
Это **параллельный выпускной трек**, не притворяется пакетной приёмкой 0.3.

### Ш.3 — №895 после 0.2, до массового перехода на пакеты

**Что:** исправить дефект оракула при статическом вызове через type-parameter
bound: Nova-тип (включая newtype) входит в имя mono-инстанса, C-параметр остаётся
представлением. Не подменять фикс обходом `len()` в новых местах; измерить
дубли одинаковых тел для разных newtype.

**Приёмка:** четыре клетки 274 §«После 0.2 — №895»: newtype над примитивом и
над записью печатают значение; `mk[FnRow]` и `mk[int]` в одной программе
различимы; `I=int` без реализации протокола отвергается. Саботаж mono-ключа
возвращает именно красноту различимости, после восстановления все клетки
зелёные. Работа оракула живёт по его D/registry-процедуре отдельно от CLI
Карины; если она не блокирует волну, не утверждать обратное без замера.

### Ш.4 — штатный драйвер `nova build`, не переименование `emit`

**Что:** тонкий CLI передаёт драйверу вход/манифест/lock и std, драйвер
разрешает зависимости, выбирает программу, вызывает Карину для C, собирает
и линкует с runtime; без второй самодельной двери языка или интерпретатора.
Сверить входы, выходы и флаги с существующим Oracle CLI и П26. Публичная
`emit` остаётся доступной с прежним контрактом и названной allow-записью.

**Приёмка:** на минимальной однопакетной и многомодульной программе бинарь
`nova`, собранный Кариной, делает `build`, полученный native executable печатает
ожидаемые байты и код возврата, а отсутствие зависимости/entry/toolchain даёт
именованный ненулевой отказ. Проба: заменить в тестовой копии C либо убрать
линковочный вход — build краснеет, восстановить — зелёный; отдельно убедиться,
что `emit` продолжает отвечать. Нулевая работа, один лишь C-текст и Oracle
binary вместо Carina binary не считаются проходом.

### Ш.5 — примеры: от класса отказа до совпадения ответа

**Что:** устранить измеренные группы parser/check/emit/driver и тихие различия
поведения. Ratchet корпуса двигать **тем же коммитом** после замера, без
подгонки конечного числа; expected stdout/exit фиксировать для каждой
запускаемой программы. Peer-файлы проверять вместе с entry; пять общих
отказов и четыре «вне точки» классифицировать явно по Ш.1.

**Приёмка:** каждый entry в `examples/` собран и исполнен Кариной, ноль
расхождений stdout/stderr/exit с ожидаемым результатом; каждый peer принят
как часть названной программы. Полный `check-novac-differential.sh` доходит
до **последнего** вердикта без незарегистрированных расхождений; `lag = 0`
по применимой мере корпуса. Саботаж одного expected output и одного peer
импорта даёт красный путь, восстановление — зелёный. Нельзя удалить пример
или ослабить ожидание ради нуля.

### Ш.6 — штатный `nova test` и матрица спутников

**Что:** тестовый драйвер поверх той же сборки обнаруживает единицы и маркеры,
собирает и запускает, сохраняет диагностические/выходные контракты и отказ
при нуле найденных тестов. Затем **один и тот же** Carina-built `nova` проводит
`build` и `test` в каждом package root фактического дерева (на исходном срезе:
`bignum`, `compress`, `duckdb`, `http`, `polaris`, `postgres`, `sdl`, `socks`, `tls`).
Нативные зависимости DuckDB/SDL именуются в отчёте, не превращаются в silent skip.

**Приёмка:** для каждого репозитория — HEAD, команда, число найденных/исполненных
тестов, stdout/exit обоих вызовов и адрес точного CI, если он существует.
Оба вызова зелёные Carina binary; отсутствие тестов и подставленный Oracle
краснеют проверкой происхождения/счёта. У `duckdb` исторически не было
зелёного CI, у локального `sdl` нет remote — это предел **прошлого контроля**,
не разрешение исключить пакеты из новой матрицы.

### Ш.7 — точный кандидат 0.3

**Что:** независимый приёмщик строит кандидат от свежего `origin/main`, фиксирует
SHA Carina-built `nova` и runtime/stdlib дерева, запускает полную матрицу и
семь обязательных CI workflows **на том же коммите**, затем штатные precheck,
замок и вливание только проверенной вершины. При сдвиге main — новый кандидат
и новый CI, не перенос старого зелёного ярлыка.

**Приёмка:** доказаны все три пункта 274 §0.3, `check-push-proven-by-ci.py`
отвечает `ok` на точном SHA; отрицательный контроль — неверный SHA или один
красный пакет/пример не получает зелёную приёмку. Публикация 0.3 и теги —
отдельное решение владельца после приёмки, не побочный эффект этой волны.

## Стоимость и машина

Факты исходного прогона на общей машине: девять пакетов `check/emit` — 6 мин;
корпус примеров — 10 мин; полный differential до ранней красноты — 11 мин.
Первый невалидный запуск с Unicode scratch занял 29 мин и в оценку продукта
не входит. Для полного дифференциала после исправлений резервировать
**20–40 мин как оценку, не обещание**, затем заменить фактической стеной.
Linux double-build — три тяжёлых звена с пределом скрипта до 900 с каждое,
фактическое время ещё не измерено. Девять native `build/test` до появления
драйвера не оценивать числом по Oracle. Все локальные тяжёлые команды — общая
`machine: true` очередь; полный `nova test`/мега-CU не запускать окном задачи.

## Не делаем

* Не удаляем `emit` в волне `build` и не обещаем автоматического срока удаления.
  Не меняем публичный CLI Oracle и язык ради временного шва.
* Не расширяем ступень 0.3 всеми тег-зависимыми планами 274.11: их очередь —
  после 0.3 к 1.0. `ИСКЛЮЧЕНИЕ 0.3` допустимо только для измеренного блокера
  ступени либо доказанной цены откладывания; причина пишется в статусе
  **того** плана. На исходном срезе ни одно исключение не доказано.
* Не выдаём Linux одиночную сборку за 0.2.1 B≡C, `check`/`emit` за `build/test`,
  старый зелёный Oracle CI за пакетный Carina CI, пропущенный тест за PASS.
* Не правим спутники ради маскировки дефекта компилятора и не снижаем
  ожидания тестов. Изменение пакета, нужное для новой нормы, — отдельная
  scoped задача с собственной приёмкой.

## Открытые вопросы

* **Кому:** владельцу при классификации Ш.1. **Вопрос:** что представляют собой
  пять файлов `examples/`, отвергаемых обоими компиляторами: намеренные
  негативные примеры или живые дефекты? **Умолчание:** не исключать их и не
  закрывать 0.3, пока формы не названы и критерий «каждый файл» не согласован.
  **Срок:** до Ш.5/первого обновления приёмки 274.
* **Кому:** владельцу после работающего `build/test`. **Вопрос:** когда и по
  какому миграционному доказательству снимать публичную `emit`? **Умолчание:**
  оставить доступной по текущему контракту и allow; сам факт появления
  `build` её не снимает. **Срок:** до отдельной задачи на CLI-конвергенцию,
  не блокирует 0.3.
