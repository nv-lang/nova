# Plan 192 — Образцовый native-backed модуль (паттерн .c/.lib-зависимостей)

**Статус:** 📋 PROPOSED 2026-07-10 (решение владельца). **Приоритет:** P2 (developer-experience / документируемый паттерн).

## Мотивация (запрос владельца 2026-07-10)

Сейчас native-зависимости Nova-программ размещены ad-hoc:
- `nova_rt/` — C-рантайм (линкуется всегда);
- `tls_shim/` — Rust-staticlib (rustls), линковка **захардкожена** в
  `test_runner.rs` (`detect_tls`, `tls-cache`, `-lbcrypt -lntdll` вручную).

Пользователь, желающий сделать свой модуль поверх .c/.lib (например, обёртку над
чужой C-библиотекой), **не имеет образца и механизма**: как объявить native-артефакты,
чтобы при `import my.module` они автоматически компилировались/линковались.

Владелец: «надо сделать образцово-показательный модуль tls/http (возможно не в
std), чтобы показать пользователю, как делать свои такие модули. При подключении
модуля должны подключаться все необходимые файлы (.c, .lib). Можем сделать под
tls/http отдельную репу».

## Цель

1. **Механизм:** модуль декларирует свои native-зависимости в манифесте
   (`nova.toml` секция `[native]`), и билд-система **автоматически** компилирует/
   линкует их при импорте модуля — без правок компилятора под каждый модуль
   (убрать хардкод `detect_tls` из `test_runner.rs`).
2. **Образец:** `tls` + `http` как эталонные native-backed модули по этому
   механизму — живая документация паттерна.
3. **Организация:** возможно вынести в отдельную репу/каталог (не `std/`), чтобы
   подчеркнуть «это подключаемая native-зависимость, не ядро языка».

## Дизайн (эскиз, sign-off нужен)

### Манифест native-зависимости (`nova.toml`)
```toml
[native.tls_shim]
kind = "rust-staticlib"        # или "c-sources" / "prebuilt-lib"
path = "native/tls_shim"       # crate/исходники
outputs = ["nova_tls_shim.lib"]
link = ["bcrypt", "ntdll", "userenv", "dbghelp"]   # системные
build = "cargo build --release"                     # как собрать
cache = "target/native-cache/tls_shim"              # + mtime-инвалидация (см. governance-tooling)
```
Билд-система: при импорте модуля с `[native.*]` → resolve (cache→build→link),
mtime-инвалидация исходников (единый механизм с tls-cache-фиксом governance-волны).

### Обобщение brotli/D337 + tls detect
`detect_tls` и brotli-условная-линковка — частные случаи. Свести к ОДНОМУ
резолверу native-deps по манифесту (закрывает хардкод, класс «второе окно правды»
для линковки).

### Образцовые модули
- `tls` — поверх `tls_shim` (rustls): полный native-backed пример (Rust-staticlib).
- `http` — поверх tls + net: пример композиции.
- Каталог: кандидат `packages/` или отдельная репа `nova-tls` / `nova-http`
  (решение владельца — монорепо-каталог vs отдельная репа).

### Документация
`docs/guide/native-modules.md` — пошагово: «как обернуть C-библиотеку / Rust-крейт
в Nova-модуль»; манифест, extern-декларации (.nv ffi-слой), сборка, тесты.
Ссылка из module-conventions (native-dep — легитимный модуль-паттерн).

## Фазы

- **Ф.1** Дизайн манифеста `[native]` + sign-off (kind'ы, поля, кэш/инвалидация).
- **Ф.2** Резолвер native-deps в билд-системе (обобщает detect_tls/brotli); убрать
  хардкод из test_runner.rs.
- **Ф.3** Перевести `tls_shim` на манифест (первый потребитель) → tls/http как образцы.
- **Ф.4** Гайд `native-modules.md` + возможный вынос в отдельную репу/каталог.

## Гейты

std/tls + std/http собираются через новый резолвер (не хардкод); brotli/compress
не сломаны; conformance δ0; гайд воспроизводим на чистом клоне.

## Границы

Не пакетный менеджер (регистри/версии зависимостей — отдельно); только «модуль
несёт свои native-артефакты и они авто-линкуются». Координация с
[governance-tooling] (mtime-инвалидация кэша — общий механизм).
