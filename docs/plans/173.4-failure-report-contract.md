## 1. Зачем

Владелец 2026-08-15: «как вообще формируется сообщение паники, куда пишутся
`Result?` конструкция… я бы предложил, чтобы они формировались в совместимом для
json формате, и если никто не разбирает, то печаталось в юзер-френдли
сообщении».

Данные об отказе рантайм собирал и до этого — вид, сообщение, точку броска,
`?`-цепочку ([D437](../../spec/decisions/08-runtime.md#d437)), цепочку подавленных
([D158](../../spec/decisions/03-syntax.md#d158)). Не было **контракта вывода**:
четыре места печатали их своими `fprintf`'ами, машине текст приходилось разбирать
догадкой, а `novac` был вынужден клеить свой машинный формат ВНУТРЬ строки паники.

Разбор по ходу вскрыл, что обещанное D437 не печаталось вовсе для самого частого
случая, а обещанное D158 не доезжает до вывода до сих пор. То есть план не про
«добавить JSON», а про **приведение уже обещанного к исполнению** плюс доступ к
той же записи из кода.

## 2. Фазы

### Ф.1 — Один источник записи, два рендерера ✅ ЗАКРЫТА (2026-08-16, `0d4622dda`)

[D462](../../spec/decisions/08-runtime.md#d462), амендмент D437. Терминальный отказ —
ОДНА запись (kind, message, payload_type, site, trace, trace_dropped, suppressed),
печатает её одна функция; форму выбирает `NOVA_PANIC_FORMAT` **в момент запуска**:
не задана/`text` — прежний человеческий вывод байт в байт, `json` — одна строка
со стабильными ключами.

В той же фазе починено то, без чего запись рождалась пустой:

* **№445 (3 из 7 фикстур паник-дорожки).** Тело `main` — файбер; ошибка
  разматывается на его fail-frame и перебрасывается на ВЫЗЫВАЮЩЕМ C-потоке, а
  диагностический бакет — per-fiber (Plan 201). Замерено инструментированием:
  `bucket=…3D433D20` на броске против `…3B78C870` на печати. Сообщение переход
  переживало (идёт явным параметром), site и трасса — нет. Починено снимком
  рядом с `first_error` и восстановлением перед перебросом.
* **№679.** Сообщение упавшего `assert` было висячим указателем на стек
  (`char buf[512]` + non-owning `nova_str_from_cstr`, longjmp с того же кадра).
  Функция с `defer { println(...) }` печатала `panic:` и ни слова, 4/4 прогона.
  Близнецы в `contracts.h` починены тем же касанием.

**Приёмка (выполнена):** `neg/f5_uncaught_trace_throw`,
`neg/f5_uncaught_trace_panic`, `neg/f5_propagation_trace_full` зелены **без правки
самих фикстур**; страж `check-panic-report-contract.sh` проверяет контракт
ИСПОЛНЕНИЕМ (самотест 8/8, в гейте); conformance `--full` 790/7 → 812/4.

### Ф.2 — Довести D158 до вывода; не терять первопричину ✅ ЗАКРЫТА (2026-08-16)

**Все три дефекта закрыты, конформанс 815/4 → 821/1.** Из семи фикстур №445 закрыто
шесть: три правкой рантайма, три — исправлением УСТАРЕВШИХ ОЖИДАНИЙ (чтение тел
показало: `defer` там только печатают, составной ошибки нет, ярлык `(D158
composite)` был бы ложью) — вторая ветка гипотезы самой записи №445, теперь
измеренная. Седьмая выделена в №692 (типизированный `!!` теряет тип).

**Урок для следующих волн, стоивший соседнему окну трёх остановок (№693):**
сигнатуры рантайма НЕ меняются — расширенная форма получает имя `_diag`. На старые
ссылается вкомпилированный шаблон оболочки novac из другого дерева.


Замерено 2026-08-15 пробником (`defer { throw "CLEANUP-FAILED" }` поверх
`throw "PRIMARY-FAILED"`):

```
nova: unhandled Fail: PRIMARY-FAILED
  at sup3.nv:4 (throw site)          <- строка 4 = сам defer, а не первопричина
```
```json
{"kind":"fail","message":"PRIMARY-FAILED","site":{"line":4},"trace":[],"suppressed":[]}
```

Три дефекта, все — приведение кода к уже написанной спеке, амендмент не нужен:

* **(а)** `suppressed` в записи всегда пуст, хотя цепочка есть в fail-frame
  (D158 модель B её туда кладёт) — до рендерера не доезжает;
* **(б)** бросок в cleanup **затирает** throw-site первичной ошибки и обнуляет её
  трассу (`nova_throw_site_set` сбрасывает безусловно). Запись выходит
  противоречивой: сообщение первичное, точка броска — из cleanup'а;
* **(в)** карман пуст к моменту `on_child_fail` — замерено: `suppressed().len() == 0`
  в обработчике супервизора при заведомо упавшем cleanup'е. Карман наполняется в
  момент ЛОВЛИ, а обработчик супервизора — не ловля; снимок ребёнка лежит в слоте
  очереди (туда же, куда Ф.1 положила site и трассу).

### Диагнозы (разведка 2026-08-16, каждый проверен на опровержение)

Восемь агентов: четыре читали код, четыре пытались опровергнуть прочитанное. **Все четыре
диагноза устояли** (`refuted: false`), и все четыре получили поправки к ФОРМЕ ФИКСА — то
есть проверка отработала не вхолостую.

**(а) Цепочка D158 СОБИРАЕТСЯ ВЕРНО и теряется в ОДНОЙ точке.** Не «не собирается», а
«собрана и не передана»: узлы аллоцируются (`emit_fail_cleanup_compose`,
emit_c.rs:31011), связываются, записываются обратно в кадр (emit_c.rs:30296) и через
`nova_rethrow_with_suppressed` (effects.h:740) доезжают до `_ff` — fail-кадра, поставленного
`_nova_main_fiber_entry`. А дальше emit_c.rs:29692 зовёт
`nova_fiber_report_error_kinded(_ff.error_msg.ptr, _ff.error_kind, _ff.error_reason_ptr)` —
**цепочка просто не в аргументах**, а у `NovaFiberQueue` (fibers.h:334) нет поля, куда её
положить. Фибр умирает, стек уходит, цепочка мусор. Терминальный `nova_report_emit`
честно печатает `suppressed:[]` для `NULL`, который ему передали.

> **ПОПРАВКА проверки, КРИТИЧНАЯ.** Предложенное «передать `_ff.error_suppressed`»
> читает **НЕИНИЦИАЛИЗИРОВАННОЕ поле**: `nova_fail_push` (effects.h:115) пишет РОВНО два
> поля (`is_cleanup`, `prev`), а кодоген на всех трёх fiber-входах эмитит голое
> `NovaFailFrame _ff; nova_fail_push(&_ff);` (emit_c.rs:14272, 15545, 29671) — ни одного
> `_ff.error_suppressed = NULL`. Без явного обнуления фикс передаёт мусор, и
> `nv_compose_suppressed` пойдёт по нему гулять — краш на самом непроверяемом пути.

**(б) Бросок из cleanup затирает site и трассу первопричины.** `nova_throw_site_set`
(effects.h:380) сбрасывает безусловно. Рядом уже есть `nova_throw_site_mark` (без сброса)
и предикат `nova_in_cleanup_unwind()` (effects.h:125), у которого сегодня ТРИ потребителя
(гейтинг диспетчера обработчика) и ни одного для site/trace. **Фикс в РАНТАЙМЕ, не в
кодогене**, и причина решающая: тело defer пере-эмитится на ЧЕТЫРЁХ run-сайтах, и на
Success-копиях бросок из cleanup И ЕСТЬ первопричина — его site штамповать НАДО; кроме
того, бросок часто не лежит в теле лексически (`defer { helper() }`), и только рантайм в
момент броска видит, что идёт размотка.

> **ПОПРАВКА проверки.** Предложенный «близнец с обходом цепочки кадров» —
> **опасен и противоречит шапке самого заголовка**: effects.h:139-142 дословно говорит, что
> при interrupt-размотке fail-кадры НЕ снимаются, и `_nova_fail_top` может указывать на
> кадр, чьё стековое хранилище уже разрушено. Обход `->prev` разыменовывает именно эту
> цепочку — диагностический дефект превратился бы в segfault. Брать ближний предикат как
> есть. Вторая поправка: если ворота поставить без принудительного входа для паники,
> то cleanup, паникующий при размотке, станет первопричиной по сообщению, а site
> останется чужим — то же самопротиворечие, переехавшее на шаг. В радиусе —
> `standalone/defer_panic_mainflow`, одна из четырёх оставшихся фикстур №445.

**(в) Карман пуст в `on_child_fail` — тот же класс одним уровнем выше.**
`nova_fiber_report_child_kinded` (fibers.h:2662) берёт шесть параметров и НИ ОДНОГО под
цепочку; `NovaChildError` (fibers.h:222) — без поля. Форма та же, что у снимка site/trace
из №445: поле + параметр + запись В ОБЕИХ ветках под замком и СТРОГО ДО
release-стора `published` — тогда она едет по существующему happens-before и новой
синхронизации не требует. `nova_fiber_report_atomic_kinded` НЕ трогать — это
одноуказательный CAS-быстропуть, куда цепочку класть некуда.

> **ПОПРАВКА проверки.** Формулировка «сохранить/восстановить вокруг вызова —
> герметично» ПРЕУВЕЛИЧЕНА: `interrupt` из `on_child_fail` едет ОТДЕЛЬНЫМ стеком
> (`_nova_interrupt_top`) и longjmp'ит МИМО восстановления, оставляя чужой карман в drive-фибре.
> Это НЕ вносимая дыра, а структурная и уже существующая (тот же longjmp бросает и drive-цикл),
> но писать надо «герметично для Fail-пути; interrupt-путь — отдельный долг».

**№680 (вне Ф.2, но блокирует Ф.3).** Механизм подтверждён дословно: `Nova_Fail_fail`
(effects.h:1505-1519) меняет `_nova_handler_Fail` на `prev`, зовёт руку, и бросок из руки
идёт в `nova_throw` → ближайший fail-кадр — тот, что сам `with`-блок поставил для ТЕЛА.
`_nova_fail_top` в этой функции не трогается ни разу. Предложенная форма — пометить НЕ
ОШИБКУ, а САМ `with`-БЛОК: флаг `handler_arm_active` на `NovaInterruptFrame`, который блок и так
публикует руке через `owner_iframe` — тогда метка переживает любое число перебросов
и не требует правки vtable/ABI.

> **ПОПРАВКА проверки.** Покрытие ещё хуже, чем думалось: единственная фикстура
> рядом (`d65_rule_3_rethrow.nv`) делает ТИПИЗИРОВАННЫЙ re-throw, который идёт вообще не
> через `Nova_Fail_fail`. Для СТРОКОВОГО броска из руки покрытия НЕТ НИ ОДНОЙ СТРОКИ.

**Порядок работы, выведённый из диагнозов:** (б) первым — он только в `effects.h`, не
меняет ни одной сигнатуры и не требует кодогена; затем (а) и (в) одной волной — у них
общая форма (поле + параметр + инициализация) и общий риск необнулённого поля.

**Приёмка:** оставшиеся четыре фикстуры №445 —
`neg/neg_read_oob` (typed-маршрут), `standalone/defer_panic_mainflow`,
`standalone/defer_throw_single`, `standalone/multi_expect_stdout` (составной
маршрут D158) — зелены **без правки фикстур**; плюс фикстура «site указывает на
первопричину, а не на cleanup». После этого — включить `--full` в гейт
(пункт (а) записи №445, сегодня отложен именно потому, что дорожка красна по
известным причинам).

### Ф.3 — Та же запись, доступная из кода 📋 (D463, ждёт слова владельца)

Сегодня обработчик супервизора получает только сообщение: `err any` сужается
`try_as[str]()`, а site и трасса из Nova-кода недоступны в принципе. D462 сделал
запись читаемой машиной СНАРУЖИ процесса; внутри её нет.

Поверхность (после двух упрощений по замечаниям владельца — «переусложнено» и
«без слова `from` можно?»):

```nova
report()     -> str          // НОВОЕ: вся запись одной строкой, ТЕМ ЖЕ рендерером
cause()      -> Option[any]  // НОВОЕ: один шаг цепочки (Rust source / Java getCause)
suppressed() -> []any        // УЖЕ ЕСТЬ (D158), не меняется
```

Свободные аксессоры формы уже существующего `suppressed()`. **Ни одного нового
типа и ни одного нового слова:** причина проставляется НЕЯВНО — как `__context__`
в Python, но точнее, потому что место однозначно (рука обработчика, где
обрабатываемая ошибка это параметр `e`; точки конверсии `?`/`!!`). Развод с
`suppressed` принципиальный: cleanup бросил РЯДОМ с летящей первичной →
`suppressed`; обработчик бросил ВМЕСТО пойманной → `cause`.

**ВХОДЯЩИЕ БЛОКЕРЫ (замерены 2026-08-16, по вопросу владельца «разве это уже не
реализовано?»):**

* **№680** — бросок из руки `fail(e) -> never` **молча съедается**: обработчик
  входит, бросает, и выполнение продолжается за `with`-блоком с кодом 0. То есть
  механизм, на котором должен стоять `cause()`, НЕ РАБОТАЕТ вообще — чинить
  до Ф.3, и это блокер тега сам по себе (тихая потеря ошибки).
* **№681** — `try_as[T]()` по элементу `[]any` (то есть по `suppressed()`) даёт клеш
  C-typedef — мешает написать ровно тот код обработчика, ради которого затевается фаза.

Отвергнуто (и почему) — записано в [черновике D463](../../spec/decisions/08-runtime.md):
запись из семи полей с типами `Site`/`FailureKind` противоречит всем изученным
языкам: ни Go, ни Rust, ни Java, ни Python не выдают место и трассу ПОЛЯМИ —
только текстом; причина везде ОДИН необязательный шаг, а не дерево.

**Приёмка:** `report()` в обработчике и терминальная печать дают ОДИН И ТОТ ЖЕ
текст (иначе рендерер размножился); `NOVA_PANIC_FORMAT=json` меняет оба; цепочка
из трёх звеньев доходит до `cause()`; страж расширяется третьей проверкой.

## 3. Что этот план НЕ делает

* Полный Nova-callstack — решение владельца 2026-07-23 (D437), не делаем.
* `file`/`line` и звенья трассы как ОТДЕЛЬНЫЕ значения в Nova-коде: их нет ни у
  Go, ни у Rust, ни у Java. Понадобятся — добавляются полем в JSON без правки
  языка.
* Явный выбор причины (`raise X from None` питоновского рода) — неявное остаётся
  умолчанием; явная форма добавляется потом без ломки, если понадобится.
