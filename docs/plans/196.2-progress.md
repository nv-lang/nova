## Что сделано

1. **Порт def.** Метод `icr_trace(&self, _id: &'static str)` вставлен в `compiler-codegen/src/codegen/emit_c.rs`
   (current-main строка **49004**, тот же impl-блок, сразу после тела `infer_call_ret_c`, перед `infer_expr_c_type`).
   Env-gated (`NOVA_TRACE_ICR`), `#[cfg(debug_assertions)]`, dedup через `OnceLock<Mutex<HashSet>>`, печатает
   `[ICR-HIT] <id>` при первом хите каждого id. Release-сборка → тело пусто → byte-identical к legacy.
2. **Порт 114 вызовов.** Все 114 `self.icr_trace("<id>")` из `cb44c941e` (ветка typed-ir-p1). **Метод порта —
   доказанная эквивалентность:** тело `infer_call_ret_c` начинается на строке 46293 в ОБЕИХ версиях, а
   функция-region diff (cb vs current-main) содержит **исключительно** trace-строки (114 вызовов + 4 inline-форма +
   def-блок) — **ноль расхождений в самом коде резолюции.** То есть cb-функция ≡ current-main-функция + трейс.
   Поэтому 114 вызовов перенесены **дословно на идентичные структурные позиции**: для каждого id
   **current-main-строка == cb-строка** (верифицировано: 0 расхождений позиций). Каждый трейс стоит в СВОЕЙ
   логической ветке (match-арм / условие / прямо перед return) по построению, не по номеру строки.
3. **Сборка.** debug-сборка компилятора чистая (`cargo build --manifest-path nova-cli/Cargo.toml`, exit 0).
4. **Прогон корпуса.** См. команды ниже.

enumerate 135; базы Vec/VecIter/BoxIter/EnumerateIter/FilterIter — эрейзнутые generic-тела std-итераторов).
Чекерский `infer_method_call_channel_type` (mod.rs:13970) возвращает None здесь, т.к. НЕ может резолвить
chained/эрейзнутый receiver-тип PRE-mono: `?`-bail на нерезолвнутом recv (mod.rs:14008) + method-generic
bail (13752) + §4-лосс `[]T↔Vec` в цепочке. **Это ровно CAP-A/B/C (carrier-chain ResolvedType-протяжка) —
самое тяжёлое ядро плана, ещё НЕ построенное.** Снять арм сейчас → CC-FAIL всех 2292 residual-кейсов.

**Классификация:** это НЕ опровержение class-C (механизм доказанно работает) — это уточнение: **B07 не может
быть ПЕРВЫМ атомом**, он есть chained-receiver-residual, зависящий от CAP-A/B/C. Секвенирование: строить
CAP-A/B/C (протяжка generic-`ResolvedType` по receiver-цепочке итератор-адаптеров) → ТОГДА B07-арм снимется.
Per «не форсируй/не патчь legacy» — арм НЕ трогал. Трейс B07 НЕ потух (арм жив, как и должен до CAP-A/B/C).

## CAP-A суб-спайк — chained-receiver протяжка `v.iter().map(f)` — ПОДТВЕРЖДЕНА (УЖЕ ПОСТРОЕНА)

**Цель:** доказать, что ЧЕКЕР материализует 2-звенную цепочку итератор-адаптеров PRE-mono в generic
`ResolvedType`, неся тип ПО ЦЕПОЧКЕ. **Метод:** инструментировал `infer_method_call_channel_type`
(mod.rs:13970, `[CHAIN]`-dump) + poison-тест B07-арма + generic-body execution.

**API цепочки (std):** `Vec[T] @iter() -> VecIter[T]` (vec/iter.nv:32); `VecIter[T] @map[U](f fn(T)->U)
-> MapIter[VecIter[T], T, U]` (vec_iter.nv:195; adapter держит upstream `src I` inline, mono → nested
concrete `MapIter[VecIter[int],int,int]`).

**Результат — ПРОТЯЖКА УЖЕ ПОСТРОЕНА И РАБОТАЕТ:**
1. **Чекер несёт generic-тип по цепочке PRE-mono** (`[CHAIN]`-dump, receiver `Vec[T]` — ЭРЕЙЗНУТЫЙ):
   - `Vec[T].iter()` → `Some(VecIter[T])`
   - `VecIter[T].map(f)` → `Some(MapIter[VecIter[T], T, T])` ← **полный nested generic, T протянут через звено**
   `infer_method_call_channel_type` РЕКУРСИВНО резолвит receiver-link N→N+1 (mod.rs:13993), TypeRef-native —
   §4-лосс `[]T↔Vec` **НЕ непреодолим** (несёт полный TypeRef, не теряет).
2. **Материализовано И ПОТРЕБЛЕНО через Channel-2, НЕ legacy** (poison-тест: заглушил B07-арм → `iter`/`map`
   **НЕ выстрелили** в poison-списке [выстрелили только `Vec.len`/`Vec.ptr`/`VecIter.next` из чужих std-тел]).
   Т.е. codegen берёт материализованный протянутый тип из чекера, арм B07 для `iter`/`map` НЕ трогается.
3. **End-to-end корректно в generic-теле:** inline `fn first_mapped[T](v Vec[T]) -> Option[T] =>
   v.iter().map(|x| x).next()` **компилируется и исполняется верно** (`y=1`). Полная 3-звенная generic-цепочка
   резолвится+mono'ится корректно.

**§4-лосс вердикт:** НЕ непреодолим в чекере PRE-mono для этой цепочки. Движок протяжки СУЩЕСТВУЕТ и работает.

**Остаточные gap'ы (downstream, НЕ протяжка):**
- **Let-binding scope truncation:** `let m = v.iter().map(f); m.next()` — ПАДАЕТ (codegen: `return NOVA_UNIT` vs
  `Option[int]`). Причина: let-инференс кладёт тип `m` в scope через `infer_expr_type` (inline-путь), который
  **усекает** `MapIter[VecIter[T],T,T]` → `MapIter[VecIter]` (теряет T,U) → следующее звено `m.next()`
  резолвит против вырожденного receiver → `Option[U]`-unbound → unit. **Fix (bounded, 1 локус):** RHS
  method-chain let-binding'а класть в scope через `infer_method_call_channel_type` (канал уже протягивает
  верно), НЕ через усекающий `infer_expr_type`. Inline-цепочка не страдает (обходит let).
- **Adapter-internal terminator `.next()`:** внутри mono'd `MapIter.next()` тело `(@src).next()` (@src:VecIter)
  ещё падает в B07 (poison показал `VecIter.next`). Нужна mono-регистрация вложенных адаптеров (P2).

**Байт-паритет:** протяжка УЖЕ в продакшене (изменений компилятора НЕ вносил — суб-спайк = разведка);
conformance 95/0 неизменно. Trace-кейсы НЕ тухли (арм не трогал per gate).

**Рекомендация по полному CAP-A/B/C (для подтверждения владельцем ПЕРЕД раскаткой):** движок протяжки
готов. Порядок построения: (a) **let-binding scope propagation** (роутить RHS-chain через канал — снимает
`let m = chain; m.op()` класс, bounded 1-локус); (b) **P2 mono-registration emit-пасс** для вложенных
адаптер-инстансов (снимает adapter-internal `.next()`/terminator residual); (c) механически расширить на
filter/enumerate/take/… (тот же путь). B07-арм снимется как СЛЕДСТВИЕ (a)+(b), не как первопричина. Ни
одного PRE-mono-блокера — §4-лосс проходим TypeRef-native.

## W1-цикл iter/map — Шаг (a): let-binding scope propagation — ГОТОВ

**Локус:** `types/mod.rs` `Stmt::Let` scope-регистрация (~6892). Для method-call RHS (`let m = v.iter().map(f)`)
берём тип `m` в scope из КАНАЛА (`resolved_types_buf[d.value.id]` — материализован `f1_expr` выше, полный
`MapIter[VecIter[T],T,T]`) через `resolved_to_typeref_tp`, ПЕРЕД усекающим `infer_expr_type` (тот давал
`MapIter[VecIter]` — теряет T,U). Аннотация всё ещё выигрывает первой; канал консервативен (None→fallback);
гейт на `Call{Member}` (не-call/free-fn RHS не тронуты).

**Приёмка (gated):**
- **Функциональность:** `fn first_present[T](v Vec[T]) -> int { mut m = v.iter().map(|x| x); ro first =
  m.next(); match first {...} }` **компилится+исполняется** (`has=1`) С фиксом; **ПАДАЕТ БЕЗ** фикса
  (`field has incomplete type NovaValue_VecIter` — усечение). Т.е. фикс необходим и достаточен для этого класса.
  В `.c`: `m` теперь `NovaValue_MapIter____VecIter____int__int__int` (полный mono), было усечённый VecIter.
- **conformance 95/0** ✓ · **`nova test std` 63/3/66** (3 FAIL = пред-существующий tls-shim, БЕЗ новых) ✓.
- **byte-parity:** effects.c content-identical (sorted) vs baseline; расхождение только в недетерминированном
  порядке forward-decl typedef'ов (подтв.: два прогона ОДНОГО бинаря тоже расходятся → `[M-codegen-emission-
  nondeterminism]`, не эффект (a)). Фикс gated → non-chain код байт-идентичен by construction.

**Границы (a):** покрывает generic-body let-chain с INLINE-замыканием. НЕ покрывает: (i) `.map(f)` где f —
fn-ПАРАМЕТР (канал `resolve_method_return_with_closure_args` берёт только inline-closure → P67); (ii)
пред-существующий codegen-баг «trailing `return NOVA_UNIT`» при `return <expr>`-tail в generic-fn `-> Option[T]`

## Шаг (c) — снятие iter/map из арма: ЗАБЛОКИРОВАНО — ExprId non-coverage (СТОП)

**Замер после (a) (conformance, NOVA_B07_DUMP + NOVA_MAT_DUMP):**

  корпусе, не только на inline-пробе. **СТОП-условие «протяжка не несёт тип» НЕ сработало.**
- **CODEGEN-time:** 720 iter B07-хитов из **10 РАЗЛИЧНЫХ ExprId** (0, 24932, 24943, 24958, 32229, …); map 139.
- **КОРРЕЛЯЦИЯ (root-cause):** **0 из 10** codegen-B07-iter-id ∈ 468 материализованных чекером iter-id.

**Вывод:** (a)/(b) НЕ разблокируют (c). Арм НЕ снимается: снятие → CC-FAIL ~684 неметериализованных iter +

Δкод-строк `infer_call_ret_c` = **0** (per «не форсируй/не патчь legacy обходами» — арм не трогал).

**Точный блокер для арм-снятия (следующий, owner-gated шаг):** **ExprId-coverage** — обеспечить, чтобы

## УТОЧНЕНИЕ (A-спайк, owner-директива «MIR-отговорка убрана»): ТОЧНЫЙ root-cause + coupling

Owner-коррекция: A = Stage-1 (mono-клон переиспользует ярлыки чекера). Разведка A дала БОЛЕЕ ТОЧНЫЙ
root-cause, чем «ExprId-across-mono» выше:

1. **mono-клон УЖЕ СОХРАНЯЕТ template-ExprId.** `ExprId` — `Copy`; mono делает `fn_decl.body.clone()`
   (emit_c.rs:20568/21552) — `.clone()` копирует поле `id`; после клона renumber НЕТ. Гипотеза «mono
   резетит id» ОПРОВЕРГНУТА. Этот механизм A уже на месте.

2. **Настоящий root-cause iter/map-residual — `[]T.of(...)` НЕ резолвится чекером** (НЕ mono-clone):
   slice bare-ctor список (mod.rs:13077) = `new|with_capacity|from|default|filled` — **`of` отсутствует**.
   → `ro sv = []int.of(...)` RHS не резолвится → `sv` НЕ кладётся в scope (mod.rs:6904 None→remove) →
   `sv.iter()`/любой метод на sv → receiver нерезолвим в чекере → channel None → НЕ материализован → B07.
   `Vec[T].of` (TurboFish) резолвится через `resolve_generic_static_return`; slice-путь хардкодит список
   без `of`. **Подтверждено:** `Vec[int].of(...)` → iter AP-MISS **0**; `[]int.of(...)` → AP-MISS **4**.
   На conformance iter AP-MISS = **36**, ВСЕ `obj-Ident(scope=false)` = receiver-локал не-в-scope из `[]T.of`.

3. **1-словный фикс (`of` в список) РЕШАЕТ материализацию:** conformance iter AP-MISS **36→0**, map 32→20,
   **conformance 95/0**. НО **регрессит `nova test std`**: `std/collections/vec_lazy` + `std/testing/property`
   → **CC-FAIL** (`NovaOpt_Nova_Vec____nova_int_p returning from int`; `nova_fn_len undefined`). Т.е.
   материализация []T.of-локалов ОБНАЖАЕТ downstream consumption/mono-баги (Стадия-2). **Тот же класс**, что
   ломал B11w-removal и gen.nv (`NovaOpt from int` в adapter-terminator).

**Вывод A:** A-материализация РЕШАЕМА (1-словный `of`, не MIR) — но CLEAN-shipping СВЯЗАН с downstream
consumption/mono-фиксом (vec_lazy хрупок к изменению Channel-2-покрытия — ломается И от `of`, И от
B11w-removal). Per «не форсируй» — регрессящий `of` НЕ закоммичен (revert, tree green). **Следующий
owner-gated шаг = починить downstream consumption** (vec_lazy adapter-terminator `NovaOpt from int` +
testing/property резолв) → ТОГДА `of` материализация шипится чисто. Gate-1 line-removal ДОПОЛНИТЕЛЬНО требует
реструктуризации монолитного B07-арма (Channel-2-first dispatch). НИ A, ни B (B11w load-bearing) в текущем
объёме не дают gate-1 line-removal без downstream+arm-restructure. Всё зафиксировано; арм не тронут.
