# План 270 — имя против объявления: пользовательский метод на встроенном имени (№576)

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-11. Основание — воспроизведённый дефект
[№576](221.1-bug-sweep.md); подтверждение владельца («если это баг — заведи и
приоритизируй») и уточнение от окна, проверявшего симптом.

**Приоритет:** 🔴 **К1, до тега.** Пользователь не может дать своему типу
печать: он пишет `fn Colour @to_str() -> str`, а получает отказ Си-компилятора
про `Nova_Colour_method_to_str` и `nova_str` — имена, которых в его исходнике
нет. Это поставляемая поверхность языка, а не внутренний долг.

---

## 1. Что воспроизведено (факт, не пересказ)

Минимальный файл, три строки по существу, вне корпуса, без зависимостей:

```nova
type Colour enum Red | Green | Blue(int)
fn Colour @to_str() -> str => "blue7"
ro c = Blue(7)
print(c.to_str())
```

`nova build` падает внутри Си-компилятора:
`nova_print_str(Nova_Colour_method_to_str(c))` — `passing 'int' to parameter of
incompatible type 'nova_str'`. То есть **рукописный метод вызывается**, но
объявлен в C с возвратом `int` вместо `nova_str`.

Проверено в трёх формах вызова (`print(c.to_str())`, `"${c}"`, `"${c.to_str()}"`)
и в двух формах нагрузки (`Blue(int)`, `Bad { why str }`) — падают все.

## 2. Что НЕ проверено — и почему это сказано отдельно

Объяснение «имя решается раньше объявления» — **гипотеза**, пришедшая от
соседнего окна. Она правдоподобна и покрывает всё наблюдаемое, но независимой
проверкой не подкреплена: никто не показал ТОЧКУ, где выбор пути делается по
имени, и не снял её пробой.

Это записано здесь потому, что дальше по плану гипотеза превращается в
техническое задание, а задание, построенное на непроверенном диагнозе, стоит
окна впустую — так уже вышло с №457, когда бриф был написан по устаревшему
заголовку записи.

## 3. Область — уже, чем кажется, и это подсказка

Дефект **не проявляется** для имён, которых нет среди встроенных: `dial`,
`pump`, любое своё имя работает. Всплывает ровно там, где имя совпало со
встроенным путём: **`to_str`, `hash`, `eq`, `cmp`** и что ещё найдётся.

Отсюда два следствия. Первое: «дефект на суммах» — обманчивая формулировка,
сумма ни при чём, просто на ней столкнулись имя и встроенный путь. Второе:
искать надо не в эмиссии `to_str`, а в списке имён со встроенным путём и в том,
что происходит, когда пользователь объявляет такое имя сам.

**Известная граница** (проверено интегратором ДО получения точного файла):
форма `fn Colour @to_str() -> str => match self { … }` с
`ro c = Colour.Blue(7)` собирается и печатает верно. Значит расходится либо
голым конструктором `Blue(7)` против `Colour.Blue(7)`, либо телом-выражением
против `match`. **С этой развилки начинается Ф.1** — иначе починят не тот
носитель.

## 4. Фазы

### Ф.1 — сузить развилку до одной переменной (🔴 К1)

Четыре сборки: {голый / квалифицированный конструктор} × {тело-выражение /
`match`}. Выяснить, какая именно ось решает. Дешёвая работа, но без неё диагноз
остаётся гипотезой.

**Сделано 2026-08-11.** Файлы — `spec_tests/p270/f1_{bare,qualified}_{expr,match}.nv`.
Четыре сборки `nova build <файл> --strict-effects`:

| файл | конструктор | тело | результат |
|---|---|---|---|
| `f1_bare_expr.nv` | `Blue(7)` | expr | ОТКАЗ Си: `f1_bare_expr.c:6171:24: error: passing 'int' to parameter of incompatible type 'nova_str'` (`Nova_Colour_method_to_str`) |
| `f1_bare_match.nv` | `Blue(7)` | match | тот же отказ дословно (та же строка/тот же символ) |
| `f1_qualified_expr.nv` | `Colour.Blue(7)` | expr | собирается, `./f1_qualified_expr.exe` печатает `blue7` |
| `f1_qualified_match.nv` | `Colour.Blue(7)` | match | собирается, `./f1_qualified_match.exe` печатает `blue7` |

**Ось, которая решает: форма конструктора** (голый `Blue(7)` против
квалифицированного `Colour.Blue(7)`). Тело метода (expr vs `match`) роли не
играет — обе формы тела дают одинаковый результат при одной и той же форме
конструктора. Где именно резолв конструктора расходится по путям типизации —
не исследовано, это отдельный вопрос от Ф.2.

### Ф.2 — инвентаризация встроенных имён (🔴 К1)

Список ВСЕХ имён, у которых есть встроенный путь, и по каждому — проба:
пользовательское объявление перекрывает встроенное, молча игнорируется или
даёт отказ? Таблица с вердиктом по каждому имени и есть настоящий предмет этого
плана.

**Два имени уже проверены — не переделывать, начинать с третьего:**

| имя | что происходит | чем падает |
|---|---|---|
| `to_str` | вызов типизируется как `int` вместо `str` | отказ Си-компилятора: `passing 'int' to parameter of incompatible type 'nova_str'` |
| `equal` | вызов уходит на символ компилятора, пользовательское тело не собрано | отказ линковки: `undefined symbol: Nova_Tag_method_equal` |

Симптомы разные, ловушка одна. **Проверить осталось:** `hash`, `compare`, а
также `debug`, `display`, `clone`, `len` — и всё, что найдётся в самом списке
встроенных путей (его надо извлечь из кода, а не угадывать).

**Список встроенных имён извлечён из кода** (не угадан):
`compiler-codegen/src/protocols/auto_derive.rs:79-98` —
`builtin_protocol_names()` и `builtin_protocol_method()`: `equal`, `hash`,
`clone`, `compare`, `display`, `debug`, `serialize`, `deserialize`, `reflect`.
`to_str` в этот список НЕ входит — у него отдельный D410-путь (см. уже
проверенное выше), значит full inventory = этот список ∪ `to_str`.

**Начато 2026-08-11, продолжается.** Проверка: сверка отличимого значения, а не
просто «собралось».

| имя | исход | наблюдение | файл пробы |
|---|---|---|---|
| `hash` | ПЕРЕКРЫВАЕТ | `fn Colour @hash() -> u64 => 999999 as u64`, вызов `c.hash() == 999999 as u64` → печатает `OVERRIDE` | `spec_tests/p270/f2_hash.nv` |
| `compare` | ПЕРЕКРЫВАЕТ | `fn Colour @compare(other Colour) -> int => 424242`, вызов `c.compare(d) == 424242` → печатает `OVERRIDE` | `spec_tests/p270/f2_compare.nv` |

Молчаливый исход для `hash`/`compare` в этих двух пробах НЕ найден — обе
собираются, линкуются и зовут именно пользовательское тело.

**Опровергнуто по дороге, и это меняет приоритет в лучшую сторону:**
предполагалось, что подмена может пройти МОЛЧА — подменить поведение, и никто не
заметит. Для `equal` проверено: падает громко. Дефект не пропускает неверную
программу, а отказывается её собирать. Для `hash`/`compare` это НЕ проверено —
там молчаливый исход всё ещё возможен, и проверять их надо в первую очередь
именно поэтому.

### Ф.3 — фикс в одной точке (🔴 К1, чекер-канал плана 196)

Выбор «встроенный путь или пользовательское объявление» обязан делаться в ОДНОМ
месте и по ТИПУ, а не по имени. Отдельной двери для `to_str` не заводить — иначе
получим ровно тот класс, из-за которого заведены №564 и №567.

*Приёмка:* по фикстуре на каждое имя из Ф.2, где пользовательское объявление
перекрывает встроенное; проба «подсунь негодное» — снять фикс, фикстуры
краснеют. Фикстура обязана ЗВАТЬ метод и сверять результат: см. урок №577 —
неиспользуемый код вычищается и не проверяется ничем.

## 5. Связь с предложением о `to_str` как сокращении `Display`

Отдельное предложение (обсуждается с владельцем): считать `@to_str() -> str`
записью `@display(mut f Fmt)`, чтобы тип по-настоящему удовлетворял `Display` и
проходил в баунды `[T Display]` — сегодня не проходит, проверено пробой.

**Это НЕ фикс данного плана.** Оно убирает `to_str` из числа носителей, но
класс — «встроенное имя против пользовательского объявления» — остаётся у
`hash`, `eq`, `cmp`. Принять предложение как закрытие №576 значило бы починить
носителя. Порядок: сначала Ф.1–Ф.3, потом (или параллельно, это независимо)
решение по `Display`.
