# План 282 — числовые конверсии: один словарь, одна дверь на пару, грамматика чисел наша

**Статус:** Ф.0–Ф.4 ЗАКРЫТЫ 2026-09-05 (спека прежде реализации, std следом, тесты зелёные —
вердикты перепроверены интегратором 2026-09-05 запуском, см. приёмку каждой фазы);
Ф.5 ОТКРЫТА — ждёт фикса №962/№136 (общий словарь вариантов в `ParseFloatError` временно заменён
уникальными именами); Ф.6 ОТКРЫТА — указательный обход в двух парсерах, решение владельца
2026-09-05, исполнитель назначается интегратором. Все решения — владельца, 2026-09-04/05; исследование, на котором стоит
план, — [docs/dev/research/2026-09-04-numeric-widening.md](../dev/research/2026-09-04-numeric-widening.md)
(§5–§5.10); план его не пересказывает, он назначает работу и приёмку.

## Откуда план

Вопрос владельца 2026-09-04: «автоматическое расширение числа при операциях над разными типами —
чем плохо, делать ли нам». Ответ спеки (D405) уже был; проверка показала, что норма у́же принципа
в трёх дверях, `as` противоречит сам себе на одной паре (`int → uint`), проверяемой конверсии
float → целое нет вовсе, а имена и формы ошибок конверсий разошлись за три переименования. Работа
собрана в один план, потому что у неё одно правило: **конверсия между конкретными типами — метод
на источнике с определённым результатом; отказ — одним словарём; никаких частных строк по имени
типа.**

## Границы — «Не делаем»

- Собственный правильно-округляющий парсер float (Eisel-Lemire + bignum) — отдельный план, когда
  Карина пойдёт без libc. Здесь округление делегировано `strtod` **только** для строки, уже
  принятой нашей грамматикой.
- Слияние `ParseIntError`/`ParseFloatError` в `ParseNumError` — отклонено (D430 R1: не навязывать
  вызывающему невозможные варианты; у float нет radix). Общий словарь вариантов важнее общего типа.
- Тип кодовой точки `u32` против `int @to_char()` (D327) — не решалось.
- `int.MIN` из строки (`"-9223372036854775808".to_int()` → `Err`) — отдельная строка реестра.

## За чей счёт время

Месяц отдан плану 274 (`novac`, Carina); оракул по решению 274 §1.4 получает только блокеры
тега и работы 221. Эта работа законна по обоим основаниям, и вот почему — чтобы вопрос не
задавали заново: она начата ВОПРОСОМ ВЛАДЕЛЬЦА 2026-09-04, а её продукт — спека, и спека
одинаково обязательна для оракула и для Карины. Окно 274 уже строит по ней дверь возврата
(волна В5) и словарь ошибок. Реализация в std сделана тем же заходом потому, что спека без
исполнения в std не проверяема: имена ошибок читаются из `prelude/errors.nv`, а не из D-блока.
Из двух заведённых строк реестра одна (№962) — блокер тега.

## Фазы

### Ф.0 — спека (закрыта 2026-09-04/05)

Амендменты, все внутри существующих блоков, датированы, без новых номеров:
D405 (правило категорией: любой числовой оператор, сравнение, float, унарный минус, тип по имени,
не по ширине; Zig в таблице доноров), D55 (литералы и float), D427 R2 (унарный минус на unsigned),
D130 (`uint` ≠ `u64`; Q2 снят — `int as uint` bit-pattern), D54 (целочисленные строки таблицы —
одна операция; мёртвая ссылка `try_from`; канон двумя половинами; `int → char` одна дверь),
D430 (R6 float `to_*`, R7 имя `to_<T>` и `RangeError enum AboveMax | BelowMin`), D178 (`Overflow` →
направление; `InvalidDigit { at }`; грамматика float), D310 (`Floats`). Страницы `conversions.*`,
`syntax.*` — обе языковые версии.

**Приёмка:** каждая форма из амендментов либо собрана пробой, либо названа строкой реестра.
Выполнено.

### Ф.1 — `try_to_*` → `to_*`, `RangeError` с направлением (закрыта 2026-09-05)

56 вызовов в `try_narrowing_test.nv`, фикстуры p930/p941. `RangeError enum AboveMax | BelowMin`.
`TryFromCharError` снят. **Приёмка** (перепроверена 2026-09-05, все вердикты воспроизведены):
`nova-cli/target/release/nova.exe test std --filter try_narrowing` → `PASS: 1 FAIL: 0`;
`--filter char` → `PASS: 1 FAIL: 0 SKIP: 2`; `nova check` на `neg/p930_blanket_set_bound_{f64,str,newtype}_neg.nv`
и `neg/p941_{ctor,static}_arg_bound_neg.nv` → `[E_TYPE_NOT_IN_SET]` на каждом.
**Правило счёта для `try_to_`:** ноль в КОДЕ. Голый `grep -rn try_to_` даёт 9 совпадений, и все
девять — ПРОЗА: комментарии фикстур p930, объясняющие переименование, и README пробы 930, где
дефект описан под старым именем. Историческую запись не трогаем; формулировка «по дереву — ноль»
была неверна и исправлена здесь, чтобы следующее окно не «чинило» комментарии.

### Ф.2 — `int → char`: одна дверь, одна ошибка (закрыта 2026-09-05)

`CharError enum AboveMax | BelowMin | Invalid` заменил `CharFromError` и `InvalidCodepoint`;
`int @to_char()` — единственный валидатор; `str.try_from_codepoint` снят, `str.from_codepoint`
без экспорта; `json.nv` — через `utf16.decode_surrogate_pair` и `to_char()`. **Приёмка:** проба
границ `0x10FFFF`/`0x110000`/`-1`/`0xD7FF`/`0xD800`/`0xDFFF`/`0xE000` — по замеру; `nova test std
--filter json/char` — PASS.

### Ф.3 — `ParseIntError` по направлению (закрыта 2026-09-05)

`Overflow` → `AboveMax | BelowMin` (знак берётся из входа), `InvalidDigit { at int }`. Тесты
`string_test.nv`, фикстуры `parse_int_overflow_err`, `parse_int_invalid_digit_err`, `plan174_1`.
**Приёмка** (перепроверена 2026-09-05): `nova test spec_tests --filter parse_int` →
`PASS: 4 FAIL: 0 SKIP: 1` (пропущен `d325_retracted_parse_int_opt_neg` — compile-error-полоса,
требует `--full`); `nova test std --filter string` → `PASS: 2 FAIL: 0 SKIP: 2`.
**Замечание по размещению, не дефект:** обе фикстуры `parse_int_*_err` лежат в `neg/` и
кончаются на `_err`, но НЕ несут ни одного `EXPECT_*`-маркера — это позитивные рантайм-тесты,
проверяющие `Err`-значения ассертами. Раннер классифицирует по маркеру, а не по папке
(AGENTS.md), поэтому они исполняются и зелены — проверено запуском выше. Папка здесь
человеческий сигнал, и он вводит в заблуждение: читатель ждёт отказа компиляции.

### Ф.4 — грамматика float на Nova (закрыта 2026-09-05, имена временные)

**Приёмка** (перепроверена 2026-09-05, каждый вердикт снят запуском):

### Ф.5 — вернуть общий словарь в `ParseFloatError` (ОТКРЫТА, блокер №136)

Решение владельца — `Empty | Invalid { at } | AboveMax | BelowMin`. Замер: с этими именами
`ParseFloatError` компилируется неверно даже при квалифицированных конструкторах (строка реестра
**№962** «общее имя варианта у сумм разных модулей», носитель №136; проба
`repro/962-variant-name-collision/`). Номер выдан интегратором 2026-09-05 вместе с вердиктом
**БЛОКИРУЕТ ТЕГ: ДА** — строка оставляла вердикт открытым, и он проставлен по доводу самой
строки (имена вариантов ошибок std — публичная поверхность; тег заморозит не словарь владельца,
а обходные `Malformed`/`TooLarge`/`TooSmall`).
Временно: `Empty | Malformed { at } | TooLarge | TooSmall` с пометкой в doc типа. **Приёмка Ф.5:**
после фикса №136 — переименование обратно, фикстура на матчи всех четырёх вариантов из другого
модуля зелёная, пометка снята.

### Ф.6 — указательный обход в `parse.nv` + `parse_float.nv` (ОТКРЫТА, решение владельца 2026-09-05)

Перевести чтение байтов в `str @to_f64()` (`parse_float.nv`) и `parse_int_core` с соседями
(`parse.nv`) с `bytes[i]` на `@ptr()` + `read_at(i)` под `unsafe`. **Обоими файлами сразу, одним
коммитом, одной формой** — разная форма в двух парсерах одного модуля хуже, чем обход в обоих
или ни в одном.

**Форма — по D216 (амендмент Plan 174.5, `spec/decisions/02-types.md`):** методы
`p.read_at(i)`, операторные `*p` / `p[i]` ретрактированы (`E_POINTER_OP_USE_METHOD`). Проверено
2026-09-05: `read_at` — intrinsic компилятора (`emit_c.rs`, `types/mod.rs`), не std-функция;
`fn str @ptr() -> *u8` есть в `core.nv:81`; прецедент в std — `collections/vec/sort.nv`
(`unsafe { @data.read_at(a) }`).

**Что нельзя потерять.** Все проверки `i < n` ОСТАЮТСЯ — они и есть грамматика; уходит только
повторная проверка внутри `[]`. Инвариант `i < n` перед каждым `read_at(i)` держится теперь
глазами, доказателя больше нет — поэтому комментарий пишется ОДИН РАЗ над функцией («все чтения
под `i < n`, `n = @byte_len()`»), а не построчным «safe because». `E_UNSAFE_UNUSED` — hard error
(D216 §21), обёртка без реальной unsafe-операции не пройдёт; `read_at` — реальная.

**Приёмка (машинная):** `nova test std --filter string` → `PASS: 2 FAIL: 0`;
`--filter try_narrowing` → `PASS: 1 FAIL: 0`; `nova test spec_tests --filter parse_int` →
`PASS: 4 FAIL: 0`; `--filter plan174_1` → PASS. **Плюс замер, ради которого всё делается:**
`--keep-artifacts`, в сгенерированном C для `to_f64` и `parse_int_core` — **ноль** `nova_idx_chk`
(сегодня 11 и столько же по правилу счёта из followup'а ниже). Краснота доказывается обратной
пробой: вернуть один `bytes[i]` — `nova_idx_chk` появляется снова.

**Границы фазы.** `chars.nv` (6 чтений) и `transform.nv` (4) ходят так же, но владелец решал
про ДВА парсера; расширение — отдельное решение владельца, не инициатива исполнителя.

**Строка реестра не заводится:** это не дефект, а решение. Долг по элизии остаётся followup'ом.

## Followups

- **Bounds-check в парсерах не элидируется.** Замер по C-выводу (`--keep-artifacts`, 2026-09-05):
  в `str @to_f64()` все 11 чтений `bytes[i]` идут через `nova_idx_chk`, хотя каждое стоит под
  `i < n`. **Правило счёта (дописано при перепроверке 2026-09-05):** 11 — это число вызовов
  `nova_idx_chk` в СГЕНЕРИРОВАННОМ C для тела `to_f64`, а не число вхождений `bytes[` в
  исходнике: их в `parse_float.nv` девять. Числа расходятся законно (инлайн хелперов), но без
  этой строки читатель грепает исходник, получает 9 и перестаёт верить соседним числам —
  проверено на себе. Причина — доказатель Plan 140.2/D257 знает форму `for i in lo..v.len()`, а не
  `while i < n` с `n = @byte_len()` от другого объекта (`bytes = @bytes()`). Та же картина в
  `parse.nv`, `chars.nv`, `transform.nv`. Вариант «ходить указателем» (`@ptr.read_at(i)` в
  `unsafe`) был отклонён для Ф.4: в модуле `runtime.string` ни один парсер так не ходит, а 11
  `unsafe`-блоков в грамматике меняют класс кода ради compare+branch на байт при входе ≤ 25
  байт. Правильный фикс — в доказателе: связать `@byte_len()` с `@bytes().len()` и понимать
  `while i < n` c монотонным `i`.
