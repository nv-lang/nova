# План 295 — Oracle 0.1.0 alpha release

**Статус:** ОТКРЫТ (решение владельца 2026-10-11; только подготовка документации).

## Решение владельца и связь с планами

Владелец 2026-10-11 решил снова подготовить выпуск Oracle 0.1.0, но не
переоткрывать закрытый как незавершённый [221](221-release-v0-1.md): этот новый
план — его отдельный актуальный дом. Очерёдность выпусков — **сначала Oracle,
затем Carina**. Процедура Carina остаётся в финальном открытом плане
[274.11](274.11-carina-release.md) §7. Это решение не закрывает 274.11, не
изменяет критерии ступени 0.2 и не меняет scope Polaris.

Оба релиза — **alpha и pre-release**. Заголовок GitHub Release Oracle:
`Nova Oracle 0.1.0 (alpha)`. Тег — `oracle-v0.1.0`; последующие patch-теги —
`oracle-v0.1.1` и т. д. Alpha не добавляется в тег или имя файла.

## Артефакты Oracle

Имена файлов неизменны относительно alpha-решения:

- `nova-oracle-0.1.0-linux-x86_64.tar.gz`
- `nova-oracle-0.1.0-windows-x86_64.zip`
- `nova-oracle-0.1.0-src.tar.gz`
- `SHA256SUMS` (контрольные суммы всех публикуемых файлов выпуска)

Docker recipe/source — [`docker/release/`](../../docker/release/); имя образа
Oracle: `nova-oracle:0.1.0`.

Заметки основываются на обоих документах:
[`release-notes-v0.1.0.md`](../dev/release-notes-v0.1.0.md) и
[`release-announcement-v0.1.0.md`](../dev/release-announcement-v0.1.0.md).
В заметки включить ясную фразу о не-гарантиях: «This is an early alpha: the
language surface and APIs may change, and compatibility is not guaranteed.»

## Порядок и критерии приёмки выпуска

1. Сверить исходный commit, подготовить и проверить все три архивных артефакта;
   сформировать `SHA256SUMS` и проверить суммы повторным вычислением.
2. Подготовить Docker image из `docker/release/`, с именем `nova-oracle:0.1.0`.
3. После отдельного owner-go создать тег `oracle-v0.1.0`, затем GitHub Release с
   заголовком `Nova Oracle 0.1.0 (alpha)`, пометкой pre-release, тремя файлами и
   `SHA256SUMS`. Для зеркал проверить symref HEAD, объект, набор веток и теги.
4. Завершить Oracle-релиз до выпуска Carina; затем исполнить Carina-процедуру
   из [274.11 §7](274.11-carina-release.md#7-процедура-выпуска-бывш-a-v6-и-a-r2--переезжает-как-заготовка).

**Приёмка глазами, потому что** здесь записаны имена и порядок будущего выпуска,
а достоверность артефактов, выставленная pre-release-метка и доступность
опубликованных ссылок нельзя подтвердить документационной проверкой. На самом
выпуске приёмка требует точного набора имён выше, проверенных SHA256SUMS, точного
тега/заголовка, pre-release, проверенного Docker-образа и проверок зеркал.

## Bootstrap и границы

Для bootstrap Carina стадию A брать из релиза Оракула. Carina 0.2 уже принята на
`99756a8867f913bd6156ed10accf8a20edea00d1`; сохранённый receipt
`proof-and-accept-receipt.txt:1–15` и `bootstrap-stock.log:16–19` в acceptance-
evidence worktree связывает A→B→C, идентичность B/C executable и B.c/C.c, и
зелёный CI на том же SHA. Это receipt принятия ступени, не доказательство
публикации релиза.

**Не делаем:** не переоткрываем и не переписываем 221; не меняем критерии 0.2,
Polaris scope или реализацию/CI; не ставим тег и не публикуем релиз, бинарники,
Docker image, страницу или анонс в рамках подготовки этого плана.

**Открытые вопросы:** нет — идентификаторы и объём решения владельца 2026-10-11
зафиксированы. Публикация всё равно требует отдельного owner-go.
