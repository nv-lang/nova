# План 220 — TCC / быстрый dev-бэкенд (build-latency P3, разведочный)

**Статус:** ⏸️ ЗАМОРОЖЕН В Ф.0 2026-07-20 — гейт окупаемости пройден
([220-builtins-audit.md](wip/220-builtins-audit.md)): порт формально окупаем (блокеры не
тупиковые), НО реализацию НЕ начинать сейчас. Причины: (1) главный риск — `__atomic_*`
(412 сайтов) в Chase-Lev deque шедулера: TCC компилирует атомики с ПОДТВЕРЖДЁННЫМ багом
(теряет `lock`-префикс → тихая гонка), нужен свой inline-asm compat со stress-верификацией —
это ровно подсистема M-187/M-211 (клин/race, ловились только stress-тестом), макс.риск в
самой хрупкой части; (2) TLS — TCC не поддерживает (hard error) + per-effect handlers =
редизайн codegen; «однопоточный dev» НЕ спасает (TLS обслуживает fail-frame/effect-dispatch
даже в no-spawn); (3) выигрыш TCC реализуется только после 218 и пока НЕ ИЗМЕРЕН.
**Разморозка — по решению владельца после пересчёта выигрыша на замере (218+219 уже дают
основной build-latency рычаг).** **Приоритет:** P3 (разведочный, ВЫСОКИЙ риск). **Строго
ПОСЛЕ [218](218-prebuilt-runtime-archive.md).** **Основа:**
[startup-latency-research.md](wip/startup-latency-research.md).

## Амендмент 2026-08-14 (решение владельца): блокер атомиков снимается конструкцией

Целевая схема тулчейна записана в [274 §8.1](274-novac-self-hosted-compiler.md): dev=TCC
поверх предсобранных lib'ов (скорость компиляции — основной приоритет, даже в ущерб
производительности), release=clang со всеми оптимизациями, перспектива — libFirm или
подобный + предсобранные vendor-lib'ы.

Главный блокер Ф.0 — `__atomic_*` (TCC теряет `lock`-префикс) — решается НЕ
`__TINYC__`-компатом со stress-верификацией, а **единым механизмом, не зависящим от
C-компилятора**: атомик-операции собираются clang'ом один раз в предсобранную библиотеку
(механика 218), dev-кодоген эмитит вызовы — TCC атомики не компилирует никогда. Release
понижает те же операции в inline `__atomic_*`. Тот же приём для TLS (второй блокер).
Прямые `__atomic_*` вне этого механизма — под страж. Ревизия §2.1 при разморозке обязана
пересчитать список блокеров под эту схему: минус атомики, минус TLS; остаются
`__builtin_*_overflow`, `__builtin_expect` (не критичен) и minicoro (не аудирован).

## 0. Что решаем

Nova генерит C и зовёт полноценный Clang/GCC/MSVC даже в dev-режиме (уже без LTO/-O2, но
всё равно тяжёлый фронтенд). **TCC (Tiny C Compiler)** компилирует в РАЗЫ быстрее ценой
заметно худшего кодогена — ровно компромисс dev-режима. Прецеденты: Zig (собственный быстрый
бэкенд вместо LLVM для debug), Rust (cranelift-бэкенд для debug-сборок).

## 1. ⚠ Критическая оговорка (почему P3 и строго после 218)

Разведка: **TCC даёт выигрыш ТОЛЬКО после 218.** Сейчас 58% времени сборки (6.5с из ~11с) —
перекомпиляция рантайма (~10 `.c`), а НЕ компиляция пользовательского кода. Пока рантайм
пересобирается каждый раз (до 218), замена компилятора на TCC доминирующий кусок не убирает
— рантайм всё равно доминирует, выигрыш от TCC теряется. После 218 (рантайм предсобран в
`libnova_rt.a`) TCC ускоряет оставшуюся компиляцию generated app.c — вот тогда осмысленно.

## 2. Ключевые вопросы (высокий риск)

1. **Корректность кодогена TCC.** TCC — менее строгий/зрелый, чем Clang. Generated C Nova
   должен компилироваться TCC байт-корректно (те же семантики). Риск: TCC-специфичные баги
   на сложном generated C (atomics, coro, GC-hooks nova_rt). Обязателен полный conformance
   под TCC-бэкендом.

### 2.1. ★ TCC = ПОРТ РАНТАЙМ-БИЛТИНОВ, не toolchain-флаг (уточнение 2026-07-20)

TCC НЕ поддерживает целый ряд `__builtin_*`/`__atomic_*`, на которых стоит generated C и
рантайм. Это делает 220 **осознанным портом** (`__TINYC__`-гейт + compat-реализации), а не
добавлением `--toolchain tcc`. Конкретные блокеры (ревизия ОБЯЗАТЕЛЬНА перед оценкой):

- **Overflow-семейство** — `__builtin_add/sub/mul_overflow` (checked/overflowing/saturating/
  wrapping арифметика, D423-trap-политика; свежий numeric-parity добор — `@pow` через
  `@overflowing_mul`). TCC их НЕ имеет → `__TINYC__`-гейт + ручная compat-реализация overflow-
  детекции (тот же compat-подход, что уже применяется где-то в codegen).
- **`__atomic_*`** — **Chase-Lev work-stealing deque** M:N-планировщика (`nova_sched.h`/
  `runtime.c`), ACQUIRE/RELEASE/CAS по всей конвенции [[mn-coding-conventions]]. TCC-поддержка
  атомиков ЧАСТИЧНАЯ → это самый рискованный блокер (некорректный атомик = гонка в scheduler).
- **`__builtin_expect`** — branch-hint (hot/cold пути). TCC игнорирует/частично — не критично
  для корректности (только пессимизация), но ревизия нужна.
- **TLS (thread-local)** — active-scope/slot TLS воркеров (work-conserving pump §12 конвенции),
  fail-frame. TCC-поддержка TLS частичная/платформо-зависимая.
- **`minicoro.h` (возможный ЧЕТВЁРТЫЙ блокер, аудит Ф.0 §2 — НЕ аудирован, только чтение):**
  вендоренная coroutine-библиотека (fiber context-switch — самый низкоуровневый код рантайма)
  имеет свой `MCO_THREAD_LOCAL`-гейт (`_MSC_VER`/`__STDC_VERSION__`/GNU) БЕЗ ветки под TCC +
  платформо-специфичные asm-трамплины переключения стека; корректность TCC-ассемблера/линкера
  на них не проверена. Патч вендоренного файла = нагрузка upstream-дрейфа. Проверка — первое
  действие Ф.1 (до неё список блокеров считать неполным).

**Вывод:** прежде чем оценивать выигрыш TCC — провести аудит ВСЕХ `__builtin_*`/`__atomic_*`/
TLS в generated C + `nova_rt/**`, составить список требующих `__TINYC__`-compat. Возможно
блокеров столько (особенно atomics в scheduler), что порт дороже выигрыша — тогда 220
закрывается как «не окупается» ИЛИ ограничивается однопоточным dev-режимом (без M:N-atomics).
2. **Только dev.** TCC — dev-режим (быстрый, худший кодоген); release остаётся Clang/GCC/MSVC.
   Никогда не для release/бенчей.
3. **Интеграция toolchain.** Добавить `--toolchain tcc` (сейчас clang/gcc/msvc). Линковка с
   предсобранным `libnova_rt.a` (218) + libuv/Boehm — TCC-совместимость линкера.
4. **Платформа.** TCC на Windows — зрелость? Атомики/TLS/coro nova_rt под TCC-Windows.
5. **Fallback.** Если TCC не осилит конкретный generated C — авто-fallback на Clang для этого
   TU (не падать).

## 3. Фазы (эскиз — детализируется ПОСЛЕ 218)

- **Ф.0 (ГЕЙТ окупаемости)** Аудит ВСЕХ `__builtin_*`/`__atomic_*`/TLS в generated C +
  `nova_rt/**` (§2.1) → список требующих `__TINYC__`-compat. РЕШЕНИЕ: порт окупается ИЛИ
  закрыть 220 / ограничить однопоточным dev. Без этого гейта дальше НЕ идти.
- **Ф.1** (разведка) TCC-сборка минимального generated app.c + `libnova_rt.a` (218) — корректность
  на простом коде; замер vs Clang.
- **Ф.2** `--toolchain tcc` в build-пайплайн; линковка с предсобранным рантаймом.
- **Ф.3** ПОЛНЫЙ conformance + флагман под TCC — корректность кодогена (критический гейт, TCC
  менее зрелый). Любой TCC-specific провал = fallback на Clang для TU.
- **Ф.4** Замер: dev-build через TCC vs Clang (ПОСЛЕ 218) — реальный выигрыш на компиляции
  пользовательского кода.

## 4. Альтернатива (если TCC не осилит)

Cranelift-подобный собственный быстрый бэкенд (как Rust debug) — но это ОГРОМНАЯ работа
(свой codegen мимо C). TCC — дешёвая проверка гипотезы «быстрый dev-бэкенд» без своего
кодогена. Если TCC-корректность не вытянет — оценить, стоит ли собственный бэкенд (вероятно
нет на текущем этапе; C-codegen — сознательный компромисс проекта).
