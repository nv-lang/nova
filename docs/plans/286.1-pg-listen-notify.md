# План 286.1 — `nova-postgres`: LISTEN / NOTIFY (async-уведомления PostgreSQL)

**Статус:** ✅ РЕАЛИЗОВАН 2026-09-28 (пакет `nova-postgres`, коммиты `6367fd9`,
`2d85a51`, `8d81c0d`): декодер `NotificationResponse`, событие `PgEvent.Notify`
в любой фазе, очередь + `next_event`/`try_next_event`, `Listener` с
backoff/reconnect/re-LISTEN; живые прогоны: `notify` 20/20+10/10, `listener`
end-to-end с настоящим обрывом (pg_terminate_backend) — reconnect и повторная
доставка. **Отклонения от текста ниже (все из-за компилятора, замеры в
`nova-postgres/repro-local/integrator-report-d8c.md` §5–7):** (1) вариант
события назван `Notify`, не `Notification` — одноимённый record в соседнем
модуле ломает коэрсию конструктора (E7301, репро variant_record_collision);
(2) форма Listener — `@run(f)`/`@run_n(n, f)` с колбэком вместо пошагового
`next_event` на хранимом соединении: consume Connection не хранится и не
перезаписывается в поле записи, а сокет внутри `spawn` отклонён M:N-проверкой
(E_FIBER_UNSAFE_CALL) — паттерн «listener в файбере + канал» сегодня
невыразим (семья №866/№527); (3) `@ping` не сделан — некуда девать соединение
между вызовами, liveness опирается на ошибку чтения; (4) reconnect в живом
тесте проверен `pg_terminate_backend`, а не `docker restart`: прокси Docker
держит клиентский TCP полуоткрытым, обрыв не детектируется (общая проблема,
у pq та же физика, лечится keepalive — отдельный вопрос к std.net).

## Цель паритета

Что умеют драйверы в Go — это и наш минимум:

| Возможность | pq | pgx | Наш план |
|---|---|---|---|
| `LISTEN`/`UNLISTEN`/`NOTIFY` как обычный SQL | да (Query) | да (Exec) | **уже есть** (simple_query) |
| Принять 'A' в любой точке потока, не ломая диалог | handler на conn | WaitForNotification | ядро: событие Notification |
| Структура {be_pid, channel, payload} | Notification | pgconn.Notification | тип `Notification` |
| Уведомления, пришедшие во время обычных запросов, не теряются | handler доставляет | накапливаются в conn | буфер + `try_next_event` |
| Блокирующее ожидание события | <-chan | WaitForNotification(ctx) | `next_event()` (+ fibers) |
| Неблокирующий опрос | — (только канал) | ReceiveMessage | `try_next_event()` |
| Выделенный listener: динамический Listen/Unlisten по имени | Listener.Listen/Unlisten | вручную | `Listener @listen/@unlisten` |
| Авто-переподключение с экспоненциальным backoff | NewListener(min, max) | нет (самому) | `Listener` с backoff |
| Пере-LISTEN каналов после переподключения | resync | — | да, храним набор каналов |
| Liveness-пинг и события соединения | Ping, ListenerEvent* | Ping | `Listener @ping`, события enum'ом |
| Закрытие ресурса | Close | Close | consume @close/@cleanup |

## Протокольные заметки (важно для семантики)

- `NOTIFY chan, 'payload'` — payload **обязателен литералом** (< 8000 байт);
  параметризованная форма — `SELECT pg_notify('chan', 'payload')`
  (незаменимо для значений из переменных). В live-примере использовать её.
- NOTIFY доставляется на commit транзакции; несколько NOTIFY одного канала
  в одной транзакции схлопываются в одно (побеждает последний payload).
- В autocommit NOTIFY уходит по завершении запроса → доставка видна слушателю
  сразу; в явной транзакции — после COMMIT.
- 'A' приходит асинхронно; формально — между ReadyForQuery, практически
  декодер должен переживать его в любой точке (нарезка чанками — через
  существующий механизм «need more bytes»).
- LISTEN привязан к сессии: после reconnect набор каналов надо выдать заново.

## Изменения по файлам

### 1. `src/decode.nv`
- `decode_notification`: pid u32 be, channel `read_cstr`, payload `read_cstr`.
- Тег 'A' — в длина-префиксные кадры фреймера.
- Peer-тесты: эталонные байты, cut-at-every-point, пустой payload, не-UTF-8.

### 2. `src/session.nv` (ядро чистое)
- `PgEvent.Notification { pid int, channel str, payload str }`.
- Диспатч: принимать в любой фазе (async!), событие в текущий feed-вывод;
  в фазе Ready — легально (сейчас неизвестный тег = протокольная ошибка).
- Тесты: notification while idle; в середине ответа (между DataRow);
  порядок событий; cut tests; session-check.

### 3. `src/pgnet/conn.nv` — приём уведомлений
- Отдельная **очередь уведомлений** (не `pending`): `pump_once` фильтрует
  `PgEvent.Notification` в `iter.notifyq` (митигация семьи
  `query_error_live` — payload-enum не селится в record-vec буфера строк).
- `export fn Connection @try_next_event() Net -> Option[Notification]` —
  неблокирующий опрос очереди.
- `export fn Connection mut @next_event() Net -> Result[Notification, ConnError]` —
  блокирующее ожидание (read→feed→scan); только в фазе Ready, иначе
  структурная ошибка. Отмена — kill-ом fiber (как ctx-cancel у pgx).
- `export type Notification value { ro pid int, ro channel str, ro payload str }`.

### 4. `src/pgnet/listener.nv` — выделенный Listener (паритет pq.Listener)

```nova
export type ListenerEvent enum
    | Connected
    | Reconnecting(reason str)      // сеть упала, ждём backoff
    | Reconnected                   // вновь слушаем (каналы пере-выданы)
    | Closed

export type Listener consume { ... }   // opts, набор каналов, backoff bounds

export fn Listener.new(opts ConnectOptions, min_backoff_ms int, max_backoff_ms int) -> Listener
export fn Listener mut @listen(channel str) Net Random -> Result[(), ConnError]
export fn Listener mut @unlisten(channel str) Net Random -> Result[(), ConnError]
export fn Listener mut @next_event() Net Random Time -> Result[ListenerMsg, ConnError]
    //  ListenerMsg = Notification(...) | Event(ListenerEvent)
    //  внутри: владеет Connection, на сетевой ошибке — close,
    //  экспоненциальный backoff (min..max), connect + выдача набора
    //  каналов, события наружу; liveness-пинг через SELECT 1
export fn Listener mut @ping() Net -> Result[(), ConnError]
export fn Listener consume @close() Net -> ()
```

- Потребительский паттерн = fiber + `Channel[Notification]` (std):
```nova
with Net = real_net(), Random = ..., Time = ... {
    consume ln = Listener.new(connect_options(...), 100, 5000)?
    ln.listen("jobs")?
    ro ch = Channel[Notification].new(16)
    spawn {
        ro sh = ln.share()          // E_LINEAR_CAPTURE_IN_FIBER
        while ro m = sh.next_event()? {
            match m { Notification(n) => ch.tx.send(n), _ => () }
        }
    }
    ro n = ch.rx.recv()             // основной код просто читает канал
}
```

### 5. `examples/live/src/main.nv` — режим `notify`
- conn1: `LISTEN demo` + `next_event()` → assert {channel=="demo",
  payload=="hello", pid>0} → печать.
- conn2 (вторая сессия): `SELECT pg_notify('demo', 'hello')` (+ `pg_sleep(0.2)`
  для гарантии порядка на медленных машинах).
- Вариант B (паритет Listener): режим `listener` — `Listener` слушает
  "demo", conn2 шлёт notify, прогон через fiber+Channel; reconnect-прогон
  против СВОЕГО одноразового контейнера (стоп/старт; чужие контейнеры
  не трогаем — правило волны Д8).

## Риски (компилятор)

- Новый payload-вариант PgEvent → фильтр в отдельную очередь (схема
  `query_error_live`), 20× live-прогонов каждого шага.
- `Listener.next_event` со времянкой = Time-эффект; трёхэффектные
  сигнатуры (Net Random Time) — проверить мономорфизацию в большом TU.
- CU-content чувствительность: малые порции, каждая со сборкой.
