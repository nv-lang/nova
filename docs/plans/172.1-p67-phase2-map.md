## 🎯 ЗАДАЧА (директива владельца 2026-06-29): `[]T` → ОДИН канонический ResolvedType с `Vec[T]`
**Что.** §0/D315 «сахар нормализуется прочь»: `[]T` (D239 alias `Vec[T]`) сейчас даёт ОТДЕЛЬНЫЙ
`ResolvedType::Array(T)` (types/mod.rs:159 `from_type_ref`), а `Vec[T]` → `Named{Vec,[T]}` — **два
варианта RT + два пути лоуэринга** (`resolved_array_to_c` emit_c:1978 vs `resolved_named_to_c` :1976),
СХОДЯЩИЕСЯ к одному C-типу (`Nova_Vec____<elem>*`, когда Vec-шаблон загружен). Нормализовать в ОДИН
канонический RT = `Named{Vec,[T]}`; `R::Array` ретайрить как представление `[]T`.

**РЕКУРСИВНО, любая вложенность (директива):** `[]T`→`Vec[T]`, `[][]T`→`Vec[Vec[T]]`, `[][][]T`→
`Vec[Vec[Vec[T]]]`. Внешний `[]` оборачивает внутренний (`[][]T` ≡ `[]([]T)`). Достигается рекурсивным
`R::from_type_ref(inner)` в Array-арме (by construction). Замер: бинарь даёт `Nova_Vec*` (не NovaArray);
no-std erasure схлопывает глубину в C, но RT несёт `Named{Vec,[Named{Vec,…}]}` — проверить на mono-build.

**§2 (директива): тривиальные read-аксессоры → ПРЯМОЕ поле, не метод-вызов.** `[]T.len` лоуэрится в
поле (`xs->len`) — это ПРАВИЛЬНАЯ/эффективная форма; `Vec[T].len()` сейчас идёт через метод (`xs->len()`).
Аксессор `@len() -> int => @len` — тривиальная обёртка над полем; компилятор может/должен инлайнить его в
прямое чтение поля. End-state: `[]T` и `Vec[T]` (единый RT) оба читают `.len`/`.cap` как прямое поле
(унифицировано + быстро). Метод-вызов = лишняя индиректность для read-аксессоров.

**Почему.** Две дорожки = §0-несовершенность + источник timing-чувствительности 172.1.2 (порядок
Vec-mono-регистрации зависит от написания → перетряхнутый layout → conservative-GC segfault).
Один RT/путь = убирает этот класс by construction.

**Scope (§7.1).** 18 сайтов `R::Array`/`ResolvedType::Array` в 4 файлах (emit_c, types/mod,
const_fn_closure, const_fn_trampoline). Ключевой producer = `from_type_ref:159`. Producers TypeRef::Array:
parser:2866/6066, emit_c:12041, gc_layout:943, auto_derive, ast:3008. **EDGES (риск):**
(a) `resolved_array_to_c` спец-кейсы — closure-array `[]fn`→`NovaArray_void_p*` ([M-138.1]) + LEGACY
`NovaArray_<prim>` fallback когда Vec-шаблон НЕ загружен — `resolved_named_to_c(Vec)` их НЕ имеет →
дивергенция в no-template / closure-array; нужно перенести логику в общий хелпер, оба пути зовут.
(b) 18 R::Array-ПОТРЕБИТЕЛЕЙ (is_primitive_lowerable, is_typed_int, gc_layout char/size) — поведение
для `Named{Vec}` должно совпасть с прежним `Array`.
(c) **FixedArray `[N]T` — ОТДЕЛЬНЫЙ built-in** (stack-allocated fixed-size, `[32]u8`=32б inline;
emit_c:11458 «separate built-in», НЕ Vec/growable). НО `from_type_ref:158` СЕЙЧАС конфлейтит
`Array`+`FixedArray` → оба `R::Array` (pre-existing — теряет `N`). Канонизация ДОЛЖНА разделить:
`[]T`→`Named{Vec}`; `[N]T`→ОТДЕЛЬНЫЙ fixed-array RT (несущий `N`), НЕ Vec и НЕ conflated с `[]T`.

**§7-подход (ОБЯЗАТЕЛЬНО — это 172.1.2 GC-зона):** detect/xcheck байт-идентичности (probe `[]T` vs
`Vec[T]` → тот же C?) → если 0-divergence (ожидаемо где шаблон загружен) land; дивергентные edges
(no-template/closure-array) закрыть переносом resolved_array_to_c-логики в общий Vec-лоуэринг ПЕРЕД
финальным переключением → ПОЛНЫЙ регресс vs clean. Revert при регрессе.

**ЗАМЕР (detect-mode, 2026-06-29, откатан после измерения):** правка `from_type_ref:158` (`[]T`→`Named{Vec}`,
`[N]T` оставлен `R::Array`):
- **conformance ПОЛНЫЙ build (со std) → PASS, 0 FAIL** — в реальном build (Vec-шаблон загружен) канонизация
  НЕ ломает поведение. **Жизнеспособно.**
- **standalone no-std probe → C дивергирует** (артефакт отсутствия Vec-шаблона): `[]int`→legacy
  `NovaArray_nova_int*` (поле `->len`) vs `Named{Vec}`→erased `Nova_Vec*` (метод `->len()`). Подтверждает
  §0-расщепление (`.len` поле-vs-метод для одного алиаса) — ровно то, что канонизация чинит.
- **Остаётся до land:** (1) ПОЛНЫЙ регресс vs clean на std/nova_tests (conformance — малый CU); (2) убрать
  созданную FixedArray/Array асимметрию (решить — `[N]T` тоже канонизировать или нет); (3) перенести
  resolved_array_to_c спец-кейсы (closure-array `[]fn`, no-template fallback) в общий Vec-лоуэринг, чтобы
  edges не дивергировали. → focused-заход (Opus, §7).

## ✅ КАНОНИЗАЦИЯ `[]T`→`Vec[T]` — LANDED (09bce062, 2026-06-29)

**Что сделано (целевая форма, §0/§3, НЕ интерим-патч):**
- `from_type_ref`: `[]T`→`Named{name:"Vec",module:[],args:[T]}`, РЕКУРСИВНО (`[][]T`→`Vec[Vec[T]]`).
- **Edge (a) ЗАКРЫТ переносом, не дублём:** новый арм `"Vec" if args.len()==1 => resolved_array_to_c(&args[0])`
  в `resolved_named_to_c`. Теперь `[]T` И `Vec[T]` (оба `Named{Vec}`) лоуэрятся через ЕДИНСТВЕННЫЙ
  Vec→C источник `resolved_array_to_c` — closure-array (`NovaArray_void_p*`), stub-erasure→`nova_int`,
  Vec-mono worklist в ОДНОМ месте. `[]T` byte-identical (его путь и был `resolved_array_to_c`); `Vec[T]`
  теперь СОВПАДАЕТ с ним (раньше расходящийся generic-path — D239 требует идентичности).
- ArrayLit channel-population (`types/mod.rs` U.4.4) → канон `Named{Vec}` (byte-identical лоуэринг).
- `R::Array` больше НЕ носитель `[]T`: только FixedArray + внутренний категорийный ключ `resolved_cat_of`
  (никогда не лоуэрится в C) → D315 «два C-окна правды» закрыто здесь.

**Edge (b) — потребители:** `primitive_gate`/`is_primitive_lowerable`(R::Array)=false ≡ (Named{Vec})=false
→ U.4.4-сайты byte-identical (оба отвергают массивы). const_fn-файлы матчат `TypeRef::Array` (не RT) — нетронуты.

**Верификация (§7):** array-юнит-тесты + новый `nested_array_canonicalizes_recursively` зелёные; byte-identity
C-дифф clean-vs-patched на 42 standalone Vec/array/closure-программах = **0 реальных дивергенций** (1
false-positive = pre-existing недетерминизм overload-pick в neg-тесте `swap_oob_neg`, доказан clean-vs-clean
diff = 2 строки `AtomicU32`vs`AtomicBool`); 0 mixed на 303 файлах; 40 conformance test-build PASS (harnessed,

## 🎯 ДИАГНОСТИКА БАЗЫ — остаток гейтнут на U.4.3 (2026-06-29, data-driven)

**Замер** (debug + NOVA_U45_GAP, корпус standalone-программ): fall-through распределение —
Call rc=false доминирует, `recv=method.var` (instance-метод на переменной) + `TurboFish`.

**Что УЖЕ работает (не дыра):** не-генерик instance-методы с КОНКРЕТНЫМ возвратом флипаются:
`check_instance_overload` пишет callee-span в `resolved_callees` (7935) → `fn_ret_by_span` индексирует
возврат каждого не-extern метода (emit_c:9853) → consumer-flip (36370) читает. Producer+consumer
замкнуты для не-генериков.

**Что НЕ флипается (настоящий остаток = U.4.3):** GENERIC/mono методы — iterator-адаптеры
(`step_by`/`chunks`/`windows`/`map`/`filter`), turbofish `obj.m[T]()`. Их C-возврат зависит от
type-args НА CALL-SITE → declaration-span C-имя (`fn_ret_by_span`) НЕ контекстно-независимо →
запись привела бы к мис-флипу (wrong mono → CC-FAIL). Поэтому `check_instance_overload` правильно
их НЕ пишет (gated non-generic). Это U.4.3 tuple/mono-hazard.

**U.4.3 = keystone остатка базы (§0-правильный путь):** канал должен нести РЕЗОЛВНУТЫЙ ВОЗВРАТНЫЙ
ТИП как `ResolvedType` (с подстановкой generics приёмника/turbofish), НЕ готовое C-имя. Чекер
ЗНАЕТ резолвнутый возврат вызова (выбрал overload + имеет type-args приёмника) → пишет
`resolved_types[call_id] = <resolved return RT>` (§1 «материализуй резолв, не выбрасывай»); consumer
лоуэрит через `resolved_type_to_c` со СВОИМ mono-контекстом (`current_type_subst`). Тогда генерик-
методы флипаются корректно. **Канонизация `[]T`→`Vec[T]` (09bce062) — ПРЯМОЙ пререквизит:** канал
несёт `ResolvedType`, и `[]T`/`Vec` теперь ОДИН RT, который U.4.3-возврат лоуэрит единым путём.

**Edges U.4.3:** (a) `Self`-возврат (fluent) = тип приёмника, не `from_type_ref(Self)`; (b) generic-
подстановка type-args приёмника в возврат (`Vec[T].first()->Option[T]` + recv `Vec[int]` → `Option[int]`);
(c) byte-identity: `resolved_type_to_c(RT)` со mono-контекстом ДОЛЖЕН совпасть с legacy method-return

## 🔑 U.4.3 КОРЕНЬ partial-flip clash (2026-06-29, инкремент #3 диагностика)

flat_map_basic CC-FAIL с relax-10112+stub-guard: `NovaValue_BoxIter_____NovaTuple2` (erased
generic-tuple) vs `NovaValue_BoxIter_____NovaTuple_2_8_nova_int_8_nova_int` (concrete `(int,int)`).
ТОТ ЖЕ механизм, что d39/d85 (`NovaOpt_nova_byte` vs `NovaOpt_nova_int`): правка флипает ОДИН сайт
(method-return) в concrete, а СВЯЗАННЫЙ сайт (binding/variable type, через legacy) остаётся erased →
C-конфликт типов.

**КЛЮЧЕВОЙ ВЫВОД для comprehensive U.4.3:** erased-форма (`NovaTuple2`/`NovaOpt_nova_int`) используется
КОНСИСТЕНТНО по всему телу. Флип ТОЛЬКО method-returns недостаточен — clash'ит с binding/variable-
типами, которые legacy эрейзит. **Comprehensive U.4.3 ДОЛЖЕН флипать ВЕСЬ type-flow вместе:**
method-returns И binding-типы (`ro x = ...`) И variable-типы — все через канал, консистентно. Это и есть
причина неделимости: не «4 независимых fix», а ОДИН консистентный type-flow channeling (binding-типы =
след. слой после method-returns). Пятое эмпирическое подтверждение неделимости.
