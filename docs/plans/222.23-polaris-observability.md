# План 222.23 — наблюдаемость Polaris: Log / Metrics / Audit

**Статус:** ОТКРЫТ (вопрос владельца 2026-07-30: «как организовать сбор метрик,
аудит, лог по всем направлениям — пункт должен был быть записан ранее, но решения
не видел»). Проверено грепом по 222.x/221/std/polaris: решения действительно НЕ
БЫЛО — записывается здесь. `TimerMetrics`/`Mem` (std) — интроспекция рантайма, не
прикладные метрики; `Log` (222.20) — только логи.
**Дом:** `nova-polaris`. **Зависимость:** 222.22 Ф.1 (`serve` — главный источник
серверных метрик).

## Принцип

Все три канала — **эффекты**. Это ответ языка на вопрос «как организовать»:
- сигнатуры честные: `serve(...) Net Time Log Metrics` — видно, что функция меряет
  и пишет;
- тесты без моков: handler-swap и ассерт на счётчик/событие;
- прод-конфигурация = выбор хендлера в `main`, а не глобальный синглтон.

## Три канала — три разных контракта (НЕ сливать в один)

1. **Log** — уже есть (222.20: один `type Log effect {info/error}`,
   `#default_handler`→stdout). В этом плане только дисциплина: серверное ядро
   (222.22) и middleware говорят через него; агрегация анти-флуда — по решению
   222.22 Ф.1 («первый сразу, дальше сводка K за N сек»).

2. **Metrics** — новый эффект в polaris:
   `type Metrics effect { counter(name str, delta int), gauge(name str, v f64), histogram_ms(name str, ms f64) }`.
   - `#default_handler` → in-memory реестр (потокобезопасный, AtomicInt/шардированный
     по mn-конвенциям);
   - экспорт — **pull-модель**: route-хелпер `/metrics` в текстовом формате
     Prometheus (никаких push-агентов и внешних зависимостей);
   - источники V1: ядро serve (`inflight` gauge, `rejected_total`, `accepted_total`),
     middleware (счётчик ответов по классу статуса, гистограмма латентности по
     маршруту), пользовательские счётчики тем же эффектом;
   - **трезвая ловушка — кардинальность**: имена метрик = ограниченное множество;
     per-client ключи в имя НЕ зашивать (взрыв реестра = самоусиление атаки, как с
     логами в 222.22). Клиентские разрезы — это ratelimiter/audit, не metrics.

3. **Audit** — ОТДЕЛЬНЫЙ эффект, не уровень лога:
   `type Audit effect { event(kind str, subject str, detail str) }`.
   Обоснование разделения: у аудита гарантии, которых у лога принципиально нет —
   события НЕ сэмплируются, НЕ агрегируются, НЕ отключаются тихо конфигом
   многословности; поток append-only. События V1: auth успех/провал (middleware
   auth уже есть — вписать вызовы), отказ доступа, admin-действия. Дефолтный
   хендлер — в Log с маркером `audit`; прод — файл/внешний сток по выбору в main.

## Фазы

- **Ф.1 — Metrics-эффект + счётчики serve + `/metrics`** — едет ВМЕСТЕ с 222.22 Ф.1
  (serve и есть главный источник; дешевле сразу, чем вкручивать после).
- **Ф.2 — request-метрики middleware** (статусы, латентность по маршруту) + смок.
- **Ф.3 — Audit-эффект + события в auth-middleware** — отдельное окно.

Ф.1 — в объём тега вместе с A-V9 (сервер без счётчика отказов слеп — сам 503-отказ
222.22 требует `rejected_total`); Ф.2/Ф.3 — после тега, НЕ блокеры.

## Гейты приёмки

polaris `nova test src --strict-effects` δ0; смок: поднять serve, обстрелять,
`curl /metrics` показывает ненулевые `accepted_total`/гистограмму; handler-swap-тесты
на все три эффекта без моков.
