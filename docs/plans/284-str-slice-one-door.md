# План 284: срез строки — одна дверь, `s[a..b]` идёт через `str @index`

**Статус:** В РАБОТЕ. Ф.0 замерена; Ф.1 и Ф.2а СДЕЛАНЫ и доказаны прогоном (2026-09-07), спека D470 написана вместе с обзорной страницей; Ф.3 сделана частично — фикстура на четыре формы зелена, две пробы «сломай своё» не гонялись; Ф.4 НАЧАТА — строковая половина быстрого пути снята из эмиттера, шесть C-хелперов в `nova_rt/array.h` ждут зелёной фикстуры между шагами; сверх плана в волну вошёл фикс реестра №1022 (роль судится ПОДПИСЬЮ в обоих местах — предикат эмиттера и проверка чекера — плюс негатив `slice_role_int_index_only_neg.nv`), обе половины написаны и НИ ОДНА не проверена прогоном. НЕ ПУШЕНО: ждёт машины под три прогона (warning'и «после» против 73 «до», девять строковых фикстур с ассертом «PASS: 9», проба Ф.2 под `--mode release`) и затем гейта. Заведён 2026-09-07 по слову владельца («срочно переделать»).

**Одной фразой.** `s[a..b]` на строке сегодня НЕ доходит до `str @index(r Range)`:
кодоген обрабатывает Range-индекс по `str` встроенно и зовёт C-хелпер. Метод на
Nova существует, несёт `requires`-контракт — и управляет только явным
`s.index(a..b)`. Две двери одной операции, проверки в разных местах. У `Vec[T]`
это уже переделано (план 194 Ф.3, D238 «одно окно правды»); строка осталась.

## Почему срочно, и чем это хуже, чем кажется

Дело не в стиле: пока сахар идёт мимо метода, у двух форм записи ОДНОЙ операции
проверки живут в РАЗНЫХ местах, и какая сработает — зависит от того, как написан
вызов.

**ПОПРАВКА 2026-09-07, ЗАМЕРОМ (интегратор), и она УМЕНЬШАЕТ работу.** Здесь
стояло: «у `Vec[T]` проверку сделали всегда-включённым panic-guard'ом, а не
`requires`-контрактом (сказано в комментарии эмиттера)», и отсюда следовало
требование к Ф.2 сделать так же у строки. **Комментарий эмиттера НЕВЕРЕН.**
Тело `Vec[T] @index(r Range)` (`std/src/collections/vec/slice.nv:39-44`) несёт
РОВНО `requires r.start >= 0 && r.end >= r.start && r.end <= @len` и никакого
guard'а. И этот контракт СРАБАТЫВАЕТ в обоих режимах: проба `v[1..5]` на `Vec`
из трёх элементов дала «panic: slice.nv:40: requires failed: …», `exit=101`,
и в `dev`, и в `--mode release`. То есть опасение «политика снимет единственную
проверку» замером НЕ подтверждается: на недоказанном сайте enforce остаётся.

Отсюда правило для Ф.2: **строка сохраняет `requires`, как у вектора** — новых
guard'ов не заводим. Что при этом обязано быть проверено пробой (и записано в
приёмку): что после маршрутизации сахар `s[a..b]` действительно доходит до этого
контракта — то есть OOB-срез строки паникует в обоих режимах ТАК ЖЕ, как
векторный.

Второе следствие — мёртвый код с маркером: `len_expr = "_s.len"` в str-ветке
никогда не читается, потому что открытый конец всегда уходит в отдельный
`_to_end_*`-хелпер. Маркер `[M-open-range-len-source-hardcoded]` про это и стоит.

## Общее правило верхней границы: оно УЖЕ общее, и `str` из него исключён поимённо

Сверено 2026-09-07 по коду, а не по памяти. `emit_c.rs:38836-38842`:

```
if obj_ty != "nova_str"
    && !obj_ty.starts_with("NovaArray_")
    && self.structural_len_field_ty(&obj_ty).as_deref() == Some("nova_int")
{ return self.emit_generic_len_field_range_index(...) }
```

То есть открытый конец берётся из **структурного поля `len`** у ЛЮБОГО типа, у
которого это поле есть, — комментарий там же говорит: «механизм Vec, обобщённый:
сам Vec (больше не привязан к имени `Nova_Vec____`) и любой пользовательский тип
с тем же полем». Внутри `emit_generic_len_field_range_index` поле читается как
`.len`/`->len` по классу хранения, а его отсутствие — внутренняя ошибка
`[E_OPEN_RANGE_NO_LEN]`.

**Правило, как его закрыл владелец 2026-09-07: признак среза — ПРОТОКОЛ, а не поле.**

```
type RangeIndex[V] protocol {
    @index(r Range) -> V
    @end_index() -> int
}
```

Тип, удовлетворяющий этой роли, умеет срез; не удовлетворяющий — не умеет, и это
говорит компилятор, а не догадка кодогена по структуре. Протоколы у нас
СТРУКТУРНЫЕ (D9/D42): объявлять соответствие не нужно, оно следует из наличия
методов, — поэтому роль не вводит новой обязанности для тех, кто уже так написан.

**Почему `V`, а не `Self`.** Срез не обязан быть тем же типом: в дереве уже есть
`str @bytes() -> ro []u8` и `Vec[T].new(...) -> ro Self` — невладеющий вид
выражается режимом `ro` и/или другим типом. Жёсткий `Self` выставил бы такие типы
за роль, и им пришлось бы заводить свою дверь — ровно то расхождение, которое
этот план убирает. `str` — `RangeIndex[str]`, `Vec[T]` — `RangeIndex[Vec[T]]`.

**Почему `-> int`, а не параметр `I`.** `Range` не обобщён: `std/src/collections/range/core.nv:57-60`
— `export type Range value { ro start int; ro end int }`, полуоткрытый, границы
`int`. Параметр, всегда равный `int`, был бы запасом на будущее, а не свободой;
обобщение `Range` — предмет [плана 281](281-typed-index-vec.md) (`Range[I Ordinal = int]`,
его же раздел «Откуда план»), и когда оно ляжет, роль станет `RangeIndex[I, V]`:
`@index(r Range[I]) -> V`, `@end_index() -> I` — то же движение, не новая работа
(решение владельца 2026-09-07; связь записана в обоих планах, чтобы следующее окно
не переоткрывало вопрос). **D-блок на роль и на `Range[I]` — ОДИН, тот, что уже
запрошен в открытых вопросах плана 281.**

Отсюда четыре следствия, и они нормативны для этого плана:

1. **Признак — РОЛЬ, не структура.** Сегодня в общий путь попадает тип со
   структурным полем `len int`, даже если у него нет `@index(r Range)`; и
   наоборот, тип с методом, но без поля, до общего пути не доходит. Ключ —
   удовлетворение `RangeIndex[V]`.
2. **Верхняя граница открытого конца — `@end_index()`, а не чтение поля `len`.**
   Метод позволяет вычисляемую границу (кольцевой буфер, вид со смещением);
   поле — нет. Для `str` и `Vec[T]` это тривиальная обёртка над тем же `@len`.
3. **Нет `@end_index()` при наличии `@index(r Range)` — отказ «тип не
   удовлетворяет `RangeIndex`», с диагностикой автору типа.** Отдельной проверки
   писать не нужно: это обычная непринадлежность роли. Внутренняя
   `[E_OPEN_RANGE_NO_LEN] internal:` уходит вместе с чтением поля.
4. **Никаких имён типов в условии.** Именные `obj_ty != "nova_str"` и
   `!obj_ty.starts_with("NovaArray_")` уходят из диспетчера: срез решается ролью
   для всех одинаково, а свой быстрый C-хелпер тип держит ВНУТРИ тела `@index`.
   Приёмка следствия: греп диспетчера Range-индекса по этим именам даёт ноль.

**СПЕКА ВПЕРЁД КОДА (AGENTS.md).** `RangeIndex[V]` — новая роль в языке, значит
нужен D-блок или амендмент к [D238](../../spec/decisions/03-syntax.md) (`Index[K, V]`),
и он пишется ДО реализации, в том же слиянии. **НОМЕР: D470**, назначен интегратором 2026-09-07
(правило `AGENTS.md` адресует номер интегратору, а не владельцу; занятость проверена
грепом — в дереве были заняты номера до D469). Блок ОДИН и общий с планом 281:
`Ordinal` + `IndexVec` + alias-`Vec` + `Range[I]` + роль среза. Брать «следующий
свободный» самому исполнителю по-прежнему нельзя: при двух окнах номера сталкивались
(D109/D110/D111, D245, D278) — поэтому он и зафиксирован здесь, в тексте плана.
Что должен сказать блок: определение роли, отношение к `Index[K, V]` (строго
сильнее для `K = Range`), почему `V` и почему `int`, и что открытый конец
материализуется через `@end_index()`.

## РЕШЕНО ВЛАДЕЛЬЦЕМ 2026-09-07 — все три открытых вопроса закрыты

Окно принесло три вопроса с умолчаниями; владелец решил все три дословно:

1. **Открытый конец — `@end_index()`, и метод ДОБАВЛЯЕТСЯ обоим типам** —
   `str` и `Vec`. Этим снят «спор трёх голосов» ниже: пункт 3 (чтение поля
   `len`) отменён, а спека D238 получает амендмент в D470 на замену `v.len()`
   вызовом `@end_index()` в развёртке.
2. **`str` — не исключение**, работает по общему механизму, «как и `Vec` и
   потенциально любой др тип». Значит вариант 1 из раздела о рекурсии (оставить
   первичную форму и завести исключение в развёртке по КОНТЕКСТУ) отпадает
   целиком, а не остаётся на выбор.
3. **Тело строкового `@index` — переписать**, «кажется есть `str.new(ptr,
   len)`». Есть: `fn str.new(buf *u8, len int) -> Self` —
   `std/src/runtime/string/core.nv:167`, модуль-приватная, а `slice.nv` —
   co-equal файл того же модуля-папки, так что экспорт не нужен.

### Что Ф.1 сделала без машины (2026-09-07)

- **Четыре тела строкового вида** (`@index`, `@get`, `@split_at`,
  `@split_at_checked` — `std/src/runtime/string/slice.nv`) больше не идут через
  сахар `@[a..b]`: вид СТРОИТСЯ вызовом `str.new(buf, len)`, а арифметика
  указателя стоит СНАРУЖИ литерала, в `ro`-биндинге.
- **`@end_index()` заведён обоим типам:** `export fn str @end_index() -> int =>
  @byte_len()` и `export fn Vec[T] @end_index() -> int => @len`.
- **Охрана границы кодпоинта перенесена из C в Nova** — `fn str
  @slice_boundary_guard(off int) -> ()`, текст паники ДОСЛОВНО тот же.
- **Сети:** `spec_tests/conformance/str_view_built_not_sliced.nv` (пять тестов,
  включая паникующий на срезе сквозь кодпоинт) и тест `end_index` вектора в
  `d262_slice_ops.nv`.

### Три следствия, найденные ЗАМЕРОМ до правки — иначе уехали бы молча

1. **`[M-152.1-str-subview-record-ctor]` (ОТКРЫТ, P2, дом — план 152.2) — это
   ровно про переписываемое тело.** Он записывает, что конструкция
   `str { ptr: @ptr + off, len: n }` ВНУТРИ str-метода мис-компилируется
   («passing nova_str to nova_int»), а `runtime.string` линкуется в каждую
   программу, то есть ломает весь str-код. Выбранная форма его обходит по
   построению, а не надеждой: литерала в методе НЕТ вовсе — он живёт в
   `str.new`, чей параметр уже `*u8`, а арифметика вынесена в `ro`-биндинг. Это
   та же дисциплина, что у `[]u8 @into_str_unchecked()` (`core.nv:243-250`),
   которая в дереве работает. **Проба формы = первая же сборка std:** отдельной
   пробой не проверить, `str.new` модуль-приватная и снаружи недосягаема.
2. **Охрана границы кодпоинта НЕ покрывается `requires`.** Она сидела в
   C-хелпере `nova_str_slice_utf8_guard` (`compiler-codegen/nova_rt/array.h:1038`)
   с текстом `str: slice splits a UTF-8 codepoint`, зависит от ДАННЫХ и потому
   остаётся даже когда границы доказаны (`_nochk` её вызывает). Тело, написанное
   через `str.new` и без неё, молча выдавало бы невалидный UTF-8 вид. Перенесена
   в Nova с тем же текстом; фикстура пришпиливает текст.
3. **Текст паники при OOB ПОМЕНЯЕТСЯ, и одна фикстура его пришпиливает.**
   Сегодня `s[a..b]` идёт мимо метода, и OOB даёт C-текст `str: slice [a..b] out
   of bounds for byte-length N`; после маршрутизации сработает `requires` метода
   и текст станет `requires failed`. `spec_tests/conformance/neg_str_slice_oob.nv`
   пришпиливает подстроку `str: slice` и покраснеет. **Это приведение к паритету,
   а не ослабление теста:** у вектора маршрут через метод уже давно, и все три его
   фикстуры пришпиливают именно `requires failed` — `neg_slice_a_gt_b.nv`,
   `neg_slice_a_negative.nv`, `neg_slice_oob_to.nv`. Строковая фикстура
   правится В ТОМ ЖЕ слиянии, что и маршрутизация (не раньше: до неё старый
   текст ещё верен).

**Где живут сети и почему не рядом с модулем.** Конвенция std просит тест рядом
с модулем, и страж `check-std-module-coverage.sh` считает `std/src/runtime/string`
одним из трёх модулей без единого теста (замер 2026-09-07: `bare=3` из 39, вместе
с `std/src/ffi` и `std/src/unicode`). Тест рядом здесь НЕВОЗМОЖЕН по
документированной причине: в этом namespace выключен неявный prelude (защита от
цикла prelude→string→prelude), что ломает саму инфраструктуру `assert()` —
дословно описано для соседнего случая в `std/src/math/overflow_policy_test.nv:12-18`
(«ломает `assert()`-инфраструктуру … для ЛЮБОГО теста в этом namespace»). Поэтому
сети лежат там, где живут все прочие строковые тесты — в `spec_tests/conformance/`
(`str_slice_basic.nv`, `pos_str_methods_accurate.nv`,
`d109_primitive_methods_str_nv_sourced.nv`). Снятие `bare=3` — не работа этой
волны.
## РЕКУРСИЯ ЧЕРЕЗ СВОЁ ЖЕ ТЕЛО — риск Ф.1, найден чтением 2026-09-07

Ф.1 маршрутизирует `s[a..b]` в `str @index(r Range)`. Но тело этого метода —
`std/src/runtime/string/slice.nv:37` — САМО есть срез: `@[r.start..r.end]`.
Значит правило «любой `[a..b]` идёт через роль» отправляет метод в себя:
бесконечная рекурсия либо (если развёртка ленива) стек на первом же вызове.

Сравнение с моделью, на которую план ссылается, показывает разницу дословно —
`std/src/collections/vec/slice.nv:39-44`:

```nova
export fn Vec[T] @index(r Range) -> Self
    requires r.start >= 0 && r.end >= r.start && r.end <= @len
{
    ro n = r.end - r.start
    Self { data: unsafe { @data.offset(r.start) }, len: n, cap: n }   // НЕ срез
}
```

У вектора тело строит вид из `data`/`len` и сахара НЕ использует — поэтому
маршрутизация `v[a..b]` в метод рекурсии не даёт и никогда не давала. У строки
тело написано через сахар, и это разница не в стиле, а в достижимости.

**Что из этого следует для Ф.1 (одно из двух, выбор владельца/интегратора):**

1. **Первичная форма остаётся в языке под своим именем.** `@[a..b]` внутри
   `str`-методов — не сахар индекса, а ПЕРВИЧНАЯ операция байтового вида, и
   развёртка её не трогает (как `unsafe { @data.offset(..) }` у вектора не
   трогается ничем). Тогда в Ф.1 условие маршрутизации обязано отличать `@[..]`
   на неявном получателе внутри тела `@index` от `x[..]` в пользовательском коде —
   то есть у развёртки появляется исключение, и его надо назвать в D470, иначе
   это второй `obj_ty != "nova_str"`, только спрятанный.
2. **Тело строки переписывается, как у вектора** — строится `str` из указателя и
   длины напрямую (`unsafe`-конструктор вида `str { ptr, len }` либо существующий
   внутренний), и тогда сахар нигде внутри реализации не встречается, исключение
   в развёртке не нужно, а правило «`[a..b]` всегда через роль» становится
   безусловным. Цена: правка тела `@index`, `@get`, `@split_at`,
   `@split_at_checked` (`slice.nv:37,51,56-68`) и требование, чтобы у `str` был
   способ собраться из `(ptr, len)` — это надо проверить пробой ДО Ф.1.

**Умолчание окна — вариант 2**, потому что вариант 1 сохраняет в компиляторе
исключение по КОНТЕКСТУ («внутри этого метода сахар не разворачивать»), а весь
план про то, чтобы исключений по имени и по месту не осталось. Но вариант 2
дороже и трогает четыре тела в `std`, поэтому окно называет его умолчанием и не
начинает Ф.1 до слова интегратора: цена волны меняется с ~1,0 дня до ~1,3.
## ЧТО ОСТАЁТСЯ ЗАШИТЫМ В КОМПИЛЯТОРЕ — вопрос владельца 2026-09-07

Окно 274 сформулировало итог правки как «в компиляторе остаётся ровно одно имя —
имя роли»; владелец поправил: а вызовы `@index`, `@end_index` и конструирование
`Range`? Поправка верна, и вот честный список того, что ПОСЛЕ Ф.1 по-прежнему
знает компилятор:

| что зашито | зачем | можно ли убрать |
|---|---|---|
| имя роли `RangeIndex` | спросить удовлетворение | нет: чем-то спрашивать надо |
| имена методов `index` и `end_index` | синтезировать вызовы | нет: сахар разворачивается в вызов, имя обязано быть известно |
| тип `Range` и его конструирование из `a..b` | материализовать аргумент | нет: `a..b` — синтаксис языка |
| `+ 1` для inclusive-конца | `a..=b` -> `end + 1` | нет: часть развёртки сахара |

**Разница не в числе имён, а в их РОДЕ.** Сегодня зашиты имена КОНКРЕТНЫХ ТИПОВ
(`nova_str`, `NovaArray_`) — значит каждый новый тип со срезом надо дописывать в
кодоген, а тип с полем `len`, который срезать нельзя, проходит молча. После Ф.1
зашита ФОРМА РОЛИ, а какие типы ей удовлетворяют, решает проверка соответствия
(структурная, D9/D42) — то есть список типов исчезает, а не сокращается.
Сахар языка без имён в компиляторе невозможен: `s[a..b]` обязан во что-то
разворачиваться, и вопрос лишь в том, во что именно — в имя типа или в роль.

## D238 УЖЕ ОПИСЫВАЕТ САХАР — что из плана новое, а что приведение кода к спеке

Второй вопрос владельца того же дня: записано ли в спеке, как работает `s[a..b]`?
Записано, и это меняет вес плана. Сверено чтением 2026-09-07:

- `spec/decisions/03-syntax.md:11057` (амендмент D249 внутри D238): «`str`
  реализует ТОЛЬКО `Index[Range, str]` (byte-range slice…)». То есть спека уже
  говорит, что строковый срез идёт через `@index(r Range) -> str`, а реализация
  этого НЕ делает — обрабатывает встроенно в кодогене. Ф.1 не вводит новое
  правило, она приводит код к записанному.
- `spec/decisions/03-syntax.md:11073`: «Builtin пути (`[]T`, `str`,
  `NovaArray_*`) продолжают работать через compiler built-in dispatch». Эта
  строка РАЗРЕШАЕТ сегодняшнюю реализацию — и она же противоречит предыдущей,
  если читать «built-in dispatch» как «мимо роли». D470 обязан снять
  двусмысленность одной фразой: встроенная развёртка законна как деталь
  реализации, но ПРИЗНАК «умеет срез» — только роль, никогда имя типа.
- `spec/decisions/03-syntax.md:11116-11121`: «Open-ended bounds … компилятор
  подставляет», и пример дословно: `v[2..]   // → v.index(Range { start: 2,
  end: v.len() })`. **Спека называет источником открытого конца `v.len()`.**

**ТРИ ГОЛОСА ОБ ОДНОМ, и выбор не окна** (AGENTS.md: противоречие МЕЖДУ
уровнями решает владелец, окно приносит оба места дословно):

1. спека, D238 (03-syntax.md:11121): открытый конец — `v.len()`;
2. этот план, §Ф.1 строка 167: «Открытый конец материализуется вызовом
   `obj.end_index()`, а не чтением поля»;
3. этот же план, §Ф.1 строка 168, следующей строкой: «Открытый конец берётся
   из поля `len` получателя (`@len`…), через существующий структурный reroute».

Пункты 2 и 3 стоят рядом и говорят обратное друг другу — это дефект текста
плана, не разночтение реализаций. Умолчание окна, пока владелец не сказал
иное: **`@end_index()`**, потому что ролью проверяется именно метод, а поле
`len` у типа может быть и не длиной (счётчик, ёмкость) — ровно тот класс, из-за
которого структурный признак и снимается; тогда D470 несёт амендмент к D238 на
замену `v.len()` на `@end_index()` в развёртке. Если владелец выберет `len`,
роль сокращается до одного метода `@index`, а признак «умеет срез» опять
опирается на поле — то есть план теряет смысл; поэтому окно называет это
умолчанием, а не развилкой.
## Ф.1 — ИТОГ (2026-09-07), и почему снимка C нет

**СДЕЛАНО, тремя коммитами:** `85bcdf354` — четыре строковых тела строят вид
через `str.new(buf, len)` и `@end_index()` заведён обоим типам; `da46206ad` —
условие диспетчера переписано на удовлетворение роли, два носителя старого
признака мигрированы, негатив на OOB перешпилен на контрактный текст; спека —
D470 в `spec/decisions/03-syntax.md` плюс амендмент внутри D238 и строка в
индексе.

**СНИМОК ЭТАЛОННОГО C «ДО» НЕ СНЯТ, И ЭТО РЕШЕНИЕ, А НЕ ЗАБЫВЧИВОСТЬ**
(интегратор, 2026-09-07, дословно по смыслу). Приём заведён для ПЕРЕНОСА
эмиттера: там правка обязана быть поведенчески нейтральной, и побайтовый дифф
ловит расхождение, которого не видно тестами. Здесь правка НАМЕРЕННО меняет
эмиссию — сахар начинает идти через метод, — поэтому дифф был бы шумом, а не
уликой. Взамен в приёмку волны идут мега-CU, conformance-full и `nova test std`
(они и гарантируют, что эмиссия ВНЕ мест среза не поехала) плюс паритет трёх
вектор-негативов, который уже держится.

**Доказательство — дословные строки, а не «прогнал, зелено»:**

- до пересборки, СТАРЫМ бинарём: девять строковых фикстур прямыми путями —
  «PASS: 9  FAIL: 0»;
- после пересборки маршрутизация покраснела ровно там, где план предсказывал:
  `neg str slice oob — panic message did not contain "str: slice":`
  `slice.nv:68: requires failed: 0 <= r.start && r.start <= r.end && r.end <=`
  `@byte_len()`. Паника пришла ИЗ ТЕЛА Nova-метода — то есть сахар доходит до
  контракта, а это ставилось задачей Ф.2;
- одиннадцать фикстур после миграции носителей — «PASS: 10  FAIL: 1».
  Единственный отказ — SEGV в `mco_status`/`nova_supervised_step`, то есть в
  фибер-рантайме, которого правка не касается; НЕ воспроизводится (одиночный
  прогон того же файла — «PASS: 1  FAIL: 0»), улика скопирована до перезапуска
  в `scratch/evidence-284/`. Интегратору сообщено строкой вердикта и кадрами —
  на известную гонку M:N молча не списано.

**Ф.2а ПРИЕХАЛА ВМЕСТЕ С Ф.1, а не после.** Маршрутизация законно отвергла двух
носителей СТАРОГО признака — `openrange_len_field_heap.nv` и
`openrange_len_field_value.nv`: у типов есть поле `len` и `@index(r Range)`, но
нет `@end_index()`. Оба мигрированы одним методом, и фикстуры от этого стали
сильнее — теперь они доказывают то, что Ф.2а и просила: срез доступен
ПОЛЬЗОВАТЕЛЬСКОМУ типу через роль, в обоих классах хранения. Диагностика
переименована из `E_OPEN_RANGE_NO_LEN` в `E_SLICE_ROLE_UNSATISFIED`: имя
«NO_LEN» называло снятый механизм, а это ровно тот класс, который окно ловит у
других (№992, №1006), — держать других к правилу, которое сам нарушаешь, нельзя.
Негатив `neg/openrange_no_len_neg.nv` перешпилен и получил line-pinned
`nova:expect`.

**ОСТАЛОСЬ В Ф.1, одной строкой:** имя `NovaArray_` ещё стоит в условии
диспетчера, хотя следствие 4 требует убрать ОБА имени. Роль его и так не
пропускает — Nova-имя `NovaArray_<elem>` в реестре методов не значится, — то есть
проверка избыточна; снятие идёт отдельным шагом со своей проверкой, потому что
для массивов это поведенчески значимо, а «избыточна по чтению» — не замер.
## ПЕРЕПИСЬ НОСИТЕЛЕЙ ПЕРЕД ГЕЙТОМ (2026-09-07)

Правка задевает КАЖДЫЙ диапазонный индекс в языке, а руками окно проверило
пятнадцать фикстур. Перепись собрал агент на sonnet по трём каталогам
(`spec_tests`, `std/src`, `examples`); окно сверило чтением три её утверждения,
они помечены. Числа: **295** настоящих `receiver[range]` в коде (из 502 сырых
grep-совпадений: 122 внутри комментариев, 10 — не индекс, а литерал массива
диапазонов и rest-паттерн в `match`).

**СПИСОК РИСКА — ОДНА СТРОКА, и это своя же фикстура.** Тип с `@index(r Range)`
и без `@end_index()` в корпусе ровно один: `Weird` в
`spec_tests/conformance/neg/openrange_no_len_neg.nv`, заведённый специально
под этот отказ. Всех прочих объявлений `@index(r Range)` в дереве четыре —
`ByteBag`, `SmallBag` (мигрированы этой волной), `Vec[T]` и `str` (несут оба
метода). Значит маршрутизация на роль не ломает в корпусе ничего, кроме того,
что должна.

**Семейство, которое перепись нашла, а окно проверило само: фиксированные
массивы.** Четырнадцать получателей она пометила `unknown`, и все они одного
рода — `[N]u8`: дайджесты crypto и буфер `char.encode_utf8()`. Живой пример
**(сверено)**: `std/src/crypto/md5.nv:114` режет `digest[..16]`, где
`Md5.hash(data) -> [16]u8` (`:104`). Ни одного `.nv`-объявления
`@index(r Range)` для `[N]T` в дереве нет, то есть роли такой массив не
удовлетворяет — и это безопасно только из-за ПОРЯДКА ветвей в диспетчере:
ветка фиксированного массива отдаёт результат на `emit_c.rs:38831`, а проверка
роли стоит ниже, на `:38881` **(сверено обоими номерами)**. Порядок здесь —
не стиль, а условие того, что std-crypto продолжает собираться; если ветки
когда-нибудь поменяют местами, покраснеет `Hex.encode(digest[..16])`, а не
что-то со срезом строк.

**Что перепись НЕ доказывает:** она читает текст, а не собирает. Носителей
риска ноль — значит гейт не должен покраснеть по этой причине; но зелёный гейт
по-прежнему дают только мега-CU, conformance-full и `nova test std`, которые
интегратор назначил взамен снимка C.
## Границы (Не делаем)

- **Не трогаем UTF-8-гарантию.** Паника на разрезе не по границе кодпоинта
  остаётся паникой рантайма (данные-зависимая проверка), а не контрактом.
- **Не меняем семантику среза** — по-прежнему байтовый диапазон (D249). Никакой
  «умной» индексации по кодпоинтам этот план не вводит.
- **`Vec[T]` трогаем ровно одним методом** — `@end_index()`. Решение владельца
  2026-09-07: метод нужен ОБОИМ типам, иначе роль неполна у половины носителей и
  «общий механизм» остаётся общим только на словах. Маршрут `v[a..b]` у вектора и
  так идёт через метод — его не трогаем.
- **`@get` и `@split_at*` у строки трогаем.** Прежняя граница разрешала это
  «кроме случая, когда их тела ломает сам перенос», — и это ровно тот случай: их
  тела тоже написаны через сахар `@[a..b]`, то есть после маршрутизации звали бы
  сами себя. Прочие строковые методы (`@trim*`, `@strip_*`, split-семейство) НЕ
  трогаем: они строят вид тем же сахаром, но через `@index`, а не в обход него.
- **Не удаляем `nova_str_slice_panic` из рантайма.** Он остаётся реализацией
  внутри тела метода; удаление C-хелпера — отдельная работа и не этого плана.
- **Спека — только про `RangeIndex[V]`.** Роль требует D-блока или амендмента к
  D238 (см. выше); ничего СВЕРХ этого в спеке не трогаем: поведение среза не
  меняется, меняется место проверки и признак применимости.
  Если по ходу выяснится, что меняется НАБЛЮДАЕМОЕ поведение (например, точка
  паники или её текст), работа останавливается и D-блок спрашивается у владельца.

### Ф.1 — маршрутизация сахара в метод

- В диспетчере Range-индекса: **условие переписывается с имён типов и поля `len`
  на удовлетворение роли `RangeIndex[V]`** — для всех типов сразу, включая `str`;
  тело синтеза — `obj.index(materialized_range)`, ровно как у `Vec[T]`.
- Открытый конец материализуется вызовом `obj.end_index()` — РЕШЕНО владельцем
  2026-09-07, и метод заведён обоим типам (`str`, `Vec`). Прежняя вторая строка
  этого списка говорила обратное («берётся из поля `len` получателя») и снята: две
  строки рядом противоречили друг другу, выбор был не окна.
  Inclusive-конец материализуется как `end + 1` — как в общем пути.
- **Тела строкового вида переписаны** (сделано 2026-09-07): `@index`, `@get`,
  `@split_at`, `@split_at_checked` строят вид через `str.new(buf, len)`, а не через
  сахар `@[a..b]`, иначе маршрутизация отправила бы метод в себя. Охрана границы
  кодпоинта перенесена из C-хелпера в `@slice_boundary_guard` с тем же текстом.

**Приёмка Ф.1:** (а) выпущенный C для `s[a..b]` содержит вызов
`nova_str_index_*`-метода (имя — по факту мангла) и НЕ содержит прямого
`nova_str_slice_panic` в месте сахара; (б) девять строковых фикстур ПРЯМЫМИ
путями — `str_view_built_not_sliced`, `d262_slice_ops`,
`d249_str_coordinate_model`, `d251_str_surface`,
`d109_primitive_methods_str_nv_sourced`, `str_slice_basic`,
`pos_str_methods_accurate`, `neg_str_slice_oob`, `d238_index_protocol` —
и вердикт ассертится ЧИСЛОМ ПРОШЕДШИХ, «PASS: 9  FAIL: 0», а не одним
«FAIL: 0»: ноль отказов печатает и прогон, не запустивший ничего; (в) C-дифф корпуса
против снимка Ф.0: изменения ТОЛЬКО в местах строкового среза, список файлов
приложен.

### Ф.2 — контракт остаётся; доказать, что сахар до него ДОХОДИТ

**ПРЕМИСА ЭТОЙ ФАЗЫ ОПРОВЕРГНУТА ЗАМЕРОМ, и фаза переписана (2026-09-07).**
Она требовала заменить `requires` у `str @index(Range)` на всегда-включённый
guard в теле — «чтобы политика контрактов не могла снять единственную проверку
сахара». Интегратор проверил это на векторном близнеце, и страх оказался
необоснованным: `requires` у `Vec[T] @index(r Range)` срабатывает и в debug, и
в `--mode release` — «panic: slice.nv:40: requires failed», код выхода 101.
Значит замена обменяла бы контракт, у которого есть политика доказательства и
снятия, на рукописный guard, у которого её нет. **`requires` у строки ОСТАЁТСЯ,
новых guard'ов не заводим** (решение интегратора; окно согласно и не спорит с
замером).

**Настоящая задача фазы — доказать, что сахар доходит до контракта, — СДЕЛАНА
в Ф.1**, и доказательство сильнее того, какое просила эта фаза. После
маршрутизации выход за границы в `s[0..100]` паникует ИЗ ТЕЛА Nova-метода —
вердикт дословно приведён ВЫШЕ, в разделе «Ф.1 — ИТОГ», и здесь НЕ повторяется:
две копии одной строки расходятся на первой правке, и план начинает врать по
частям. Поймано стражем `check-plan-duplication` на слитом дереве 2026-09-07. До маршрутизации тот же вход давал C-текст мимо метода. Негатив
`neg_str_slice_oob.nv` пришпилен к началу самого условия, а не к голому
«requires failed», — то есть сеть ловит именно контракт СТРОКИ, а не любой
сработавший контракт в программе.

**ОСТАЛОСЬ В Ф.2 ровно одно: проба в обе стороны под `--mode release`.**
(а) фикстура с заведомо выходом за границы паникует и в debug, и в
`--mode release` — две дословные строки вердикта в отчёте; (б) сломать своё:
ослабить условие `requires` в `slice.nv` (например снять `r.end <= @byte_len()`)
→ та же фикстура КРАСНЕЕТ, вернуть → зеленеет.

**ПОЛЯРНОСТЬ ПРОБЫ — так, а не наоборот** (поправлено 2026-09-07; прежний текст
этого критерия обещал обратное). `neg_str_slice_oob.nv` ОЖИДАЕТ паники: снимешь
проверку — паники не будет, и фикстура покраснеет отказом «не паниковала».
Зеленеет она тогда, когда контракт на месте. Прежняя формулировка отправила бы
читателя искать поломку, которой нет, — тот же класс, что ложное слово в вердикте
стража (Г9 конвенции гейтов).

**Что проба доказывает:** не «контракт срабатывает» — это видно и без слома, — а
что фикстура судит ИМЕННО этот контракт, а не любую сработавшую панику в
программе. Пришпилено к началу условия (`requires failed: 0 <= r.start`) как раз
поэтому.

(в) Z3-приёмка контрактов не считает `@index` доказанным-и-снятым: контрактные
подпапки — «FAIL: 0».

**Чего в Ф.2 больше НЕТ и почему** (граница, чтобы следующее окно не доделало
«очевидное»): переписывания `requires` в guard — нет, премиса опровергнута;
снятия проверки из кодогена — нет, она там уже не живёт: условие диспетчера
не содержит ни одного имени типа, а str-ветка ниже мертва для сахара и
снимается в Ф.4 вместе с рантайм-хелперами.
### Ф.2а — неполная роль — честная ошибка компиляции

- Тип с `@index(r Range)` и без `@end_index()` не удовлетворяет `RangeIndex[V]`;
  `x[a..b]` на нём отвергается с диагностикой, называющей РОЛЬ и недостающий
  метод, — что и сделано: `E_SLICE_ROLE_UNSATISFIED` (см. Ф.1 — ИТОГ).
- Отдельного правила писать не нужно — это обычная непринадлежность роли;
  задача фазы в том, чтобы сообщение было человеческим и line-pinned.

**Приёмка Ф.2а:** негативная фикстура в `spec_tests/conformance/neg/` —
пользовательский тип с `@index(r Range)` и без `@len`; `EXPECT_COMPILE_ERROR` с
кодом, line-pinned `nova:expect`; проба в обе стороны (добавить `@len` — компилируется
и срез работает, включая `x[5..]`). Плюс позитив: пользовательский тип с обоими —
`x[a..b]`, `x[a..]`, `x[..b]` дают ожидаемые значения (доказательство, что срез
доступен НЕ только std).

### Ф.3 — фикстуры на все четыре формы

`spec_tests/conformance/standalone/` (позитивы) и `neg/` (негативы), по одному
файлу на форму, каждая с `EXPECT_*`:
`s[a..b]`, `s[a..]`, `s[..b]`, `s[a..=b]`; плюс пустой срез `s[k..k]`,
границы `s[0..0]` и `s[n..n]`, выход за границу, **разрез не по границе
кодпоинта** (`EXPECT_RUNTIME_PANIC`).

**Приёмка Ф.3:** каждая фикстура прогнана; для негативов — line-pinned
`nova:expect`; проба «сломай своё» на КАЖДОМ негативе (снять guard → фикстура
зеленеет). Число фикстур и вердикты — в отчёте фазы.

### Ф.4 — снятие мёртвого кода и маркера

- Убрать `len_expr = "_s.len"` и остатки str-ветки, ставшие недостижимыми.
- Снять маркер `[M-open-range-len-source-hardcoded]` из кода и **строку из
  `docs/plans/backlog-followups.md`** (правило жизненного цикла маркеров).

**НАБОР НА СНЯТИЕ — перечислен, а не «остатки» (2026-09-07).** Двадцать два
вхождения по семи именам; перепись собрал агент на haiku по точному списку
имён, две строки из неё окно сверило чтением само (они помечены).

| что снимать | где | почему мертво |
|---|---|---|
| ветка эмиссии str-среза | `emit_c.rs:38945-38953` **(сверено)** | печатает имена четырёх C-хелперов строковыми литералами; после Ф.1 сахар в неё не попадает |
| `nova_str_slice_chk` / `_nochk` | `nova_rt/array.h:1054`, `:1059` | зовутся ТОЛЬКО из той ветки |
| `nova_str_slice_to_end_chk` / `_nochk` | `nova_rt/array.h:1063`, `:1068` | то же; `*_to_end_*` существовали ровно для открытого конца, который теперь материализует `@end_index()` |
| `nova_str_slice_bounds` | `nova_rt/array.h:1045` **(сверено)** | зовётся только из двух `_chk`-хелперов; его текст паники заменён контрактом метода |
| `nova_str_slice_utf8_guard` | `nova_rt/array.h:1038` **(сверено)** | зовётся только из четырёх хелперов; его близнец уже живёт в Nova (`@slice_boundary_guard`) с тем же текстом |

**Что НЕ снимать, и это решение:** `nova_str_slice_panic`
(`nova_rt/nova_rt.h:150`) — другая функция, к срезу через сахар не относится; в
`emit_c.rs` она упоминается только в комментариях (три места), вызовов нет.
Граница плана про неё уже стояла, перепись её подтвердила.

**Порядок снятия важен:** сперва ветка в `emit_c.rs`, потом хелперы. Наоборот —
нельзя: ветка печатает ИМЕНА строками, компилятор Rust о них ничего не знает, и
снятие хелперов первым даст не ошибку сборки, а красноту на линковке С-кода уже
сгенерированной программы, то есть отказ уедет из сборки компилятора в прогон
фикстуры и будет искаться дольше.
**Приёмка Ф.4 — переписана 2026-09-07, прежняя была непроверяема в двух местах.**

1. **Маркер: ноль в КОДЕ, а не «по дереву».** Прежний критерий требовал ноль
   вхождений `M-open-range-len-source-hardcoded` по всему дереву. Замер того же
   дня: вхождений 15 в пяти файлах, и четыре из них — проза ЭТОГО плана,
   описывающая, чем маркер был, плюс одно в инвентаре ветки. Ноль по дереву
   недостижим, не переписав историю, а правило жизненного цикла требует другого.
   Проверяемая форма: ноль в `compiler-codegen/`, `novac/`, `std/` и
   `spec_tests/`; строки с маркером в `docs/plans/backlog-followups.md` нет;
   упоминания в планах — история, и они ОСТАЮТСЯ.
2. **Warning'и: САМОДОСТАТОЧНЫЙ ЗАМЕР вместо ссылки на несуществующую базу.**
   Прежний критерий велел сравнить число warning'ов с Ф.0 — а в
   `docs/dev/measurements/284-str-slice-before.md` слов `warning`/`warn`/
   `предупрежд` ноль вхождений на 104 строки: базы нет. Проверяемая форма: число
   warning'ов снимается ДО удаления и ПОСЛЕ, в ОДНОМ окне, одной и той же
   командой — `cd nova-cli && cargo build --release 2>&1 | grep -c '^warning'` —
   и не должно вырасти. Обе строки идут в отчёт фазы дословно.
3. **Сборка зелёная:** `cargo build --release` — строка `Finished` дословно.
4. **Порядок снятия соблюдён** (см. набор на снятие выше): сперва ветка эмиссии в
   `emit_c.rs`, потом хелперы в `nova_rt/array.h`. Обратный порядок даёт отказ не
   на сборке компилятора, а на линковке сгенерированной программы.
5. **Проба в обе стороны:** после снятия ветки, но ДО снятия хелперов, прогон
   `spec_tests/conformance/standalone/d470_slice_forms.nv` обязан быть зелёным —
   это доказывает, что сахар больше не ходит в снятую ветку. Если он краснеет,
   ветка была ещё живой, и снимать хелперы нельзя.

### Ф.5 — приёмка волны

**У КАЖДОГО ПУНКТА НАЗВАН ИСПОЛНИТЕЛЬ, и это не формальность.** Правило `AGENTS.md` (раздел Gates)
дословно: «Only the integrator runs the mega-CU and the full `nova test`. Yours
are targeted». Прежняя редакция этой приёмки состояла из четырёх пунктов, три из
которых окну ЗАПРЕЩЕНЫ, а четвёртый ссылался на снимок, которого не существует, —
то есть выглядела машинной, но исполнить её было нельзя ни мне, ни интегратору без
догадки, кто что делает.

**Окно (274):**

- девять строковых фикстур прямыми путями — ассертится ЧИСЛО прошедших
  «PASS: 9  FAIL: 0», а не «FAIL: 0» (ноль отказов печатает и прогон, не
  запустивший ничего). СДЕЛАНО 2026-09-07, строка вердикта в отчёте Ф.1;

**Интегратор:**

- мега-CU `spec_tests/conformance` одним CU — «FAIL: 0»;
- `nova test std` — отказы ровно по базе имён (`std-test-fail.baseline`), новых

- полный гейт яруса push — зелёный, вердикт дословно; и по правилу №997 вердикт

**Чего в приёмке БОЛЬШЕ НЕТ и почему.** C-диффа корпуса против снимка Ф.0 — нет:
снимок не снимался НАМЕРЕННО (решение интегратора 2026-09-07, записано выше). Приём
«снимок до, дифф после» заведён для ПЕРЕНОСА эмиттера, где правка обязана быть
поведенчески нейтральной и дифф ловит то, чего не видно тестами; здесь же правка
НАМЕРЕННО меняет эмиссию — сахар начинает идти через метод, — и побайтовый дифф был
бы шумом, а не уликой. Взамен назначены три прогона интегратора выше: они и есть
гарантия, что эмиссия ВНЕ мест среза не поехала.

## Чем это НЕ является

Не оптимизация: срез как был одним рантайм-вызовом, так и остаётся. Единственное
измеримое изменение — **где живёт проверка** и **сколько дверей** у операции.
