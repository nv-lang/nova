# План 284: срез строки — одна дверь, `s[a..b]` идёт через `str @index`

**Статус:** НЕ НАЧАТ, заведён 2026-09-07 по слову владельца («срочно переделать»).

**Одной фразой.** `s[a..b]` на строке сегодня НЕ доходит до `str @index(r Range)`:
кодоген обрабатывает Range-индекс по `str` встроенно и зовёт C-хелпер. Метод на
Nova существует, несёт `requires`-контракт — и управляет только явным
`s.index(a..b)`. Две двери одной операции, проверки в разных местах. У `Vec[T]`
это уже переделано (план 194 Ф.3, D238 «одно окно правды»); строка осталась.

## Почему срочно, и чем это хуже, чем кажется

Дело не в стиле. **Контракт `requires` подчиняется политике контрактов и может
быть снят** (Z3-доказанные сайты — ноль стоимости; в release — enforce-with-elision).
Пока сахар идёт мимо метода, у двух форм записи ОДНОЙ операции разные гарантии, и
какая из них проверяется — зависит от того, как написан вызов. Именно поэтому у
`Vec[T]` при переезде проверку сделали **всегда-включённым panic-guard'ом, а не
`requires`-контрактом** (сказано в комментарии эмиттера у синтеза вызова). Строке
нужен тот же ход, иначе маршрутизация сама по себе ослабит проверку сахара.

Второе следствие — мёртвый код с маркером: `len_expr = "_s.len"` в str-ветке
никогда не читается, потому что открытый конец всегда уходит в отдельный
`_to_end_*`-хелпер. Маркер `[M-open-range-len-source-hardcoded]` про это и стоит.

## Общее правило верхней границы: оно УЖЕ общее, и `str` из него исключён поимённо

Сверено 2026-09-07 по коду, а не по памяти. `emit_c.rs:38836-38842`:

```
if obj_ty != "nova_str"
    && !obj_ty.starts_with("NovaArray_")
    && self.structural_len_field_ty(&obj_ty).as_deref() == Some("nova_int")
{ return self.emit_generic_len_field_range_index(...) }
```

То есть открытый конец берётся из **структурного поля `len`** у ЛЮБОГО типа, у
которого это поле есть, — комментарий там же говорит: «механизм Vec, обобщённый:
сам Vec (больше не привязан к имени `Nova_Vec____`) и любой пользовательский тип
с тем же полем». Внутри `emit_generic_len_field_range_index` поле читается как
`.len`/`->len` по классу хранения, а его отсутствие — внутренняя ошибка
`[E_OPEN_RANGE_NO_LEN]`.

**Правило, как его сформулировал владелец 2026-09-07 (дословно по смыслу):**
«поддержка слайса — это наличие `@index(r Range)`; далее, если нет `@len` — это
ошибка компиляции; никаких хардкодов на типы; любой пользовательский тип может
поддержать слайс, если захочет».

Отсюда три следствия, и они нормативны для этого плана:

1. **Признак — МЕТОД, не поле.** Сегодня в общий путь попадает тип со структурным
   `len int`, даже если у него нет `@index(r Range)`; и наоборот, тип с методом,
   но без поля, до общего пути не доходит. Ключ — наличие `@index(r Range)`;
   `@len` остаётся ИСТОЧНИКОМ верхней границы открытого конца, но перестаёт быть
   ПРИЗНАКОМ применимости.
2. **Нет `@len` при наличии `@index(r Range)` — ОШИБКА КОМПИЛЯЦИИ, а не внутренняя.**
   Сегодня этот случай существует как `[E_OPEN_RANGE_NO_LEN] internal:` — то есть
   аварийное сообщение компилятора самому себе. Становится обычным отказом с
   диагностикой автору типа и негативной фикстурой (line-pinned `nova:expect`).
   **Требуется БЕЗУСЛОВНО**, а не только когда в коде встретился открытый конец:
   иначе тип поддерживает срез наполовину, и это выясняется у пользователя типа,
   а не у его автора. Решение принято при заведении плана; альтернатива
   («требовать только для `x[a..]`») отвергнута сознательно.
3. **Никаких имён типов в условии.** Именные `obj_ty != "nova_str"` и
   `!obj_ty.starts_with("NovaArray_")` уходят из диспетчера: строка идёт общим
   путём, как Vec, а свой быстрый C-хелпер держит ВНУТРИ тела `@index`. Легаси
   `NovaArray_` (по плану 172.12 почти мёртв) в этом плане не переписываем — но и
   его исключение выражается не именем в кодогене, а отсутствием метода у типа.
   Приёмка следствия: `grep -n 'nova_str\|NovaArray_' ` по диспетчеру Range-индекса
   даёт ноль.

## Границы (Не делаем)

- **Не трогаем UTF-8-гарантию.** Паника на разрезе не по границе кодпоинта
  остаётся паникой рантайма (данные-зависимая проверка), а не контрактом.
- **Не меняем семантику среза** — по-прежнему байтовый диапазон (D249). Никакой
  «умной» индексации по кодпоинтам этот план не вводит.
- **Не трогаем `Vec[T]`** — он уже переехал; и не трогаем `@get`, `@split_at*`,
  кроме случая, когда их тела ломает сам перенос.
- **Не удаляем `nova_str_slice_panic` из рантайма.** Он остаётся реализацией
  внутри тела метода; удаление C-хелпера — отдельная работа и не этого плана.
- **Не заводим новых D-блоков:** поведение не меняется, меняется место проверки.
  Если по ходу выяснится, что меняется НАБЛЮДАЕМОЕ поведение (например, точка
  паники или её текст), работа останавливается и D-блок спрашивается у владельца.

## Фазы

### Ф.0 — замер до правки (без изменений кода)

- Перечислить ВСЕ места в `emit_c.rs`, где Range-индекс по `str` обрабатывается
  отдельно от общего пути (греп по `nova_str_slice`, `_to_end_`, `obj_ty == "nova_str"`
  в окрестности диспетчера).
- Снять **эталонный C** корпуса до правки: `spec_tests/conformance` одним CU,
  сохранить выпущенный C (приёмка переноса эмиттера — сравнение C до/после).
- Собрать список носителей: `grep -rn '\[[^]]*\.\.' --include=*.nv std spec_tests examples`
  с отбором строковых получателей — сколько форм и какие (`s[a..b]`, `s[a..]`,
  `s[..b]`, `s[a..=b]`).

**Приёмка Ф.0 (машинная):** файл `docs/dev/measurements/284-str-slice-before.md`
содержит: число мест в эмиттере, число носителей по каждой из четырёх форм,
путь к сохранённому C-снимку; `nova test spec_tests --filter slice` — дословная
строка вердикта в том же файле.

### Ф.1 — маршрутизация сахара в метод

- В диспетчере Range-индекса: **условие переписывается с имён типов и поля на
  наличие метода `@index(r Range)` у типа получателя** — для всех типов сразу,
  включая `str`; тело синтеза — `obj.index(materialized_range)`, ровно как у `Vec[T]`.
- **Открытый конец берётся из поля `len` получателя** (`@len`, оно же байтовая
  длина), через существующий структурный reroute, а не через `_to_end_*`.
  Inclusive-конец материализуется как `end + 1` — как в общем пути.

**Приёмка Ф.1:** (а) выпущенный C для `s[a..b]` содержит вызов
`nova_str_index_*`-метода (имя — по факту мангла) и НЕ содержит прямого
`nova_str_slice_panic` в месте сахара; (б) `nova test spec_tests --filter slice`
и `nova test std/src/runtime/string` — «FAIL: 0» дословно; (в) C-дифф корпуса
против снимка Ф.0: изменения ТОЛЬКО в местах строкового среза, список файлов
приложен.

### Ф.2 — проверка границ переезжает в тело и перестаёт быть снимаемой

- В `slice.nv`: `requires` на `@index(Range)` заменяется **всегда-включённым
  guard'ом** в теле (форма — как у `Vec[T] @index(r Range)` в
  `std/src/collections/vec/slice.nv`), чтобы политика контрактов не могла снять
  единственную проверку сахара.
- Кодоген о проверке больше не знает: из str-ветки уходит всё, что её дублирует.

**Приёмка Ф.2 (проба в обе стороны, обязательна):** (а) фикстура с заведомым
выходом за границы паникует и в debug, и в **release** (`--mode release`), и это
две дословные строки вердикта; (б) снять guard в теле — та же фикстура ЗЕЛЕНЕЕТ
(доказательство, что судит именно он), вернуть — краснеет; (в) Z3-прогон
контрактов не считает `@index` доказанным-и-снятым: `nova test` контрактной
подпапки — «FAIL: 0».

### Ф.2а — `@index(r Range)` без `@len` — честная ошибка компиляции

- `[E_OPEN_RANGE_NO_LEN]` перестаёт быть `internal:`; сообщение называет тип,
  метод и то, чего не хватает, — по конвенции диагностик.
- Проверка стоит на ОБЪЯВЛЕНИИ типа с `@index(r Range)`, а не на месте среза.

**Приёмка Ф.2а:** негативная фикстура в `spec_tests/conformance/neg/` —
пользовательский тип с `@index(r Range)` и без `@len`; `EXPECT_COMPILE_ERROR` с
кодом, line-pinned `nova:expect`; проба в обе стороны (добавить `@len` — компилируется
и срез работает, включая `x[5..]`). Плюс позитив: пользовательский тип с обоими —
`x[a..b]`, `x[a..]`, `x[..b]` дают ожидаемые значения (доказательство, что срез
доступен НЕ только std).

### Ф.3 — фикстуры на все четыре формы

`spec_tests/conformance/standalone/` (позитивы) и `neg/` (негативы), по одному
файлу на форму, каждая с `EXPECT_*`:
`s[a..b]`, `s[a..]`, `s[..b]`, `s[a..=b]`; плюс пустой срез `s[k..k]`,
границы `s[0..0]` и `s[n..n]`, выход за границу, **разрез не по границе
кодпоинта** (`EXPECT_RUNTIME_PANIC`).

**Приёмка Ф.3:** каждая фикстура прогнана; для негативов — line-pinned
`nova:expect`; проба «сломай своё» на КАЖДОМ негативе (снять guard → фикстура
зеленеет). Число фикстур и вердикты — в отчёте фазы.

### Ф.4 — снятие мёртвого кода и маркера

- Убрать `len_expr = "_s.len"` и остатки str-ветки, ставшие недостижимыми.
- Снять маркер `[M-open-range-len-source-hardcoded]` из кода и **строку из
  `docs/plans/backlog-followups.md`** (правило жизненного цикла маркеров).

**Приёмка Ф.4:** `grep -rn 'M-open-range-len-source-hardcoded'` по дереву — ноль;
`cargo build --release` — зелёный; предупреждений о недостижимом коде не
прибавилось (сравнение числа warning'ов с Ф.0).

### Ф.5 — приёмка волны

- мега-CU `spec_tests/conformance` одним CU — «FAIL: 0»;
- `nova test std` — отказы ровно по базе имён (`std-test-fail.baseline`),
  новых нет;
- C-дифф корпуса против снимка Ф.0 — прочитан глазами и объяснён построчно
  («приёмка глазами, потому что» дифф C не выражается машинным критерием;
  машинная часть — что дифф ограничен местами среза);
- полный гейт яруса push — зелёный, вердикт дословно в отчёте.

## Чем это НЕ является

Не оптимизация: срез как был одним рантайм-вызовом, так и остаётся. Единственное
измеримое изменение — **где живёт проверка** и **сколько дверей** у операции.
