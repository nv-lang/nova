## Ф.U — унификация семьи (решения владельца 2026-08-03)

Три решения одним заходом. Все — ДО тега: после публикации переименование
пакета и смена типа ошибки станут ломающими.

### У.1 — единый тип ошибок разбора

Сейчас четыре перечисления: `ParseBigIntError` (3 варианта),
`ParseBigRatError` (4), `ParseBigDecimalError` (7), `ParseBigFloatError` (7).
**Семь вариантов десятичного и двоичного совпадают полностью**, а три
(`Empty`, `OnlySign`, `InvalidCharacter`) есть во всех четырёх. Ради этого
разнобоя живёт переходник `map_parse_int_err`.

Свести к ОДНОМУ `ParseNumberError` на пакет. Состав — объединение:
`Empty`, `OnlySign`, `InvalidCharacter`, `MultiplePoints`,
`MultipleExponents`, `EmptyExponent`, `EmptyMantissa`, `ZeroDenominator`.

**Обзор чужих решений (интегратор, 2026-08-03):** один тип на все разборы
чисел — Go (`strconv.NumError`, закрытый набор причин), Java
(`NumberFormatException`, но причина только текстом), C#, Python, Kotlin.
Отдельный тип на целевой тип — Rust (`ParseIntError`/`ParseFloatError`,
внутри закрытый перечень причин, сам тип непрозрачен). **Ни в одном языке
нет нашей нынешней формы — четырёх перечислений с пересекающимися
вариантами и ручными переходниками.** Наш вариант ложится ближе к Go и
лучше Java (причина разбираема). Дополнительный довод: у Rust половина
причин про переполнение диапазона, а у нас произвольная точность —
переполнения нет по построению, пространство ошибок меньше.

Принятая цена: в сигнатуре разбора целого будет присутствовать недостижимый
`ZeroDenominator`. Приемлемо — восемь читаемых вариантов против дублирования
и переходников.

Попутно: все четыре объявления написаны в СТАРОЙ форме с ведущей `|`,
отменённой D406 (проходит молча). Привести к канону тем же заходом.

### У.2 — знак к канону (№297)

`BigRat @sign()` возвращает `int`, тогда как `BigInt` и `BigFloat` — `Sign`
(решение владельца, план 235). Привести к `Sign`; вспомогательные
`sign_num`/`apply_sign` в bigfloat, существующие только ради разнобоя,
вычистить.

`@compare() -> int` НЕ трогать: `Ordering` удалён намеренно
(`spec/decisions/02-types.md`, единый стиль с `str.compare` и C `memcmp`).

Числовые дискриминанты (`Sign` со значениями -1/0/1) сейчас НЕДОСТУПНЫ —
см. №296: отрицательные отвергает парсер, приведение варианта к числу даёт
CC-FAIL. Как только №296 закрыт — вернуться и упростить.

### У.3 — переименование пакета в `nova-bignum`

Пакет содержит всю семью (BigInt, BigDecimal, BigFloat, BigRat), имя
`bigint` описывает одного члена. Новое имя очерчивает «числа произвольной
точности», ничего лишнего не обещает (в отличие от `math`, откуда ждали бы
тригонометрию — она исключена навсегда) и узнаваемо рядом с Go `math/big`
и Java `BigInteger`.

Объём: имя репозитория на ТРЁХ зеркалах, строка зависимости в манифестах,
все `import bigint.…`, файлы блокировок примеров, документация, ссылки в
планах 236/237/240/243.

## Свод отложенного (инвентарь по планам 235/236/237/240, снят 2026-08-03)

### Ф.A — функциональный добор (nova-bigint; sonnet + opencode по сложности)
1. **Свёртка вееров 10→1**: `@to_bigdecimal`/`@to_bigfloat` — по одному
   generic-бланкету `fn[T Ints]` + i128-перегрузка (образец — уже рабочий
   `@to_bigint`/`@to_bigrat`; №170 закрыт, генерик-путь доказан bigrat'ом);
   снять обход-комментарии в bigdecimal.nv:150-161 и зеркало в bigfloat.
2. **BigInt**: `@modpow(exp, mod)` (Евклид/бин-возведение поверх готовых
   @times/@rem); битовые `@bitand/@bitor/@bitxor` (D46-имена; @shl/@shr уже
   есть) — semantics two's-complement как Go big.Int; тесты-векторы малые
   против int-эталона.
3. **BigRat-добор** (вопросы 1/3/5/6 плана 240 — были «не в V1», теперь в
   объёме): `str @to_bigrat` понимает `"1.25"` (делегация to_bigdecimal →
   точный to_bigrat); `@to_int_floor()/@to_int_ceil()` рядом с trunc;
   `BigRat @to_bigfloat(ctx)` (округление деления в двоичной мантиссе — 
   аккуратность по образцу BigFloat @div); `@limit_denominator(max_den)`
   (Stern-Brocot / continued fractions, Python-паритет).
4. **№281-разворот**: после фикса компилятора вернуть while-форму в
   bigrat_slow-тестах, снять маркер (той волной, что примет фикс №281).

### Ф.P — перф-добор (после Ф.A; бенчи через std bench-харнесс, числа в отчёт)
5. **BigInt**: Karatsuba (порог — ИЗМЕРИТЬ Ф.0-замером, не выдумывать;
   Toom-3 — только если Karatsuba-замер покажет потолок); binary-gcd.
6. **BigDecimal**: trailing-zero-count через степени 10 (бинарный поиск)
   вместо O(n²)-цепочки div_rem(10); кэш малых степеней 10.
7. **BigFloat**: sticky-бит вместо мегасдвига при diff>prec+GUARD (MPFR-приём,
   §2.3/§5 плана 237); Dragon4/Grisu3 для str-пути — ТОЛЬКО при живом
   bench-болевом (иначе фиксируется замером и остаётся);
   sqrt: Tuckerman-проверка остатка (доказанный последний бит).
8. **Семья**: GC-шум аккумуляторов (`a = a + 1` в цикле) — buffer-reuse внутри
   операций ЛИБО мутабельный аккумулятор-тип; дизайн-записка ДО кода, решение
   формы — владельцу одним вопросом с рекомендацией.

### Ф.T — кортеж-миграция семьи (после №271/№272; целевая форма D215)
9. Все четыре типа → named tuples (`type BigInt(...)` и т.д.; код миграции
   BigInt уже написан и откачен — ветка p-tuple репы bigint, переиспользовать);
   BigRat/BigDecimal/BigFloat — той же волной; интерполяция в тестах — только
   после подтверждения №272-фикса.

### Ф.L — литеральные формы (ЯЗЫК; отдельное D-решение владельца ДО реализации)
10. `123456789...n` (BigInt) и `12.345bd`-стиль — лексер/парсер + D-блок;
    БЕЗ слова владельца не начинать (единственный пункт плана с таким гейтом);
    рекомендация интегратора: `n`-суффикс да, `bd` — обсудить формы.

### Явно НЕ входит (не «V2», а «никогда без отдельного решения»)
- Трансцендентные BigFloat (sin/cos/...) — паритет Go (у Go их нет).
- Неявные коэрсии int→Big* (D429 запрещает; литералы Ф.L — явная форма).
