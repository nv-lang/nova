# План 253.4 — Реестр дизарма: кодоген заново решает задачу резолва по именам

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-08. Подплан зонтика
[253](253-invariant-reduction-umbrella.md), трек Д. Дефект-корень —
[№480](221.1-bug-sweep.md). Основание — разбор владельца 2026-08-08 по следам
закрытого [№456](221.1-bug-sweep.md): «дизарм происходит в текущем блоке, зачем
всё переусложнять? для данной consume-переменной автоматически заводишь
переменную для дизарма — она известна компилятору, алгоритм простой и полностью
детерминированный, какие проблемы?»

**Номер 253.3 пропущен намеренно:** он был занят планом размещения значений,
который в тот же день признан не относящимся к предмету зонтика и перенесён в
[172.15](172.15-value-placement-abi-audit.md). Переиспользовать номер нельзя —
он остался в истории коммитов (реестр [№464](221.1-bug-sweep.md): номер плана
обязан быть уникальным).

## Почему это предмет зонтика 253, а не отдельная тема

Различающий вопрос нормы: *можно ли выразить состояние, нарушающее утверждение?*

Утверждение здесь: **«каждый взведённый флаг авто-очистки зарегистрирован в
реестре дизарма»**. Нарушающее состояние выразимо — и именно оно случилось:
эмиссия `Stmt::ConsumeScope` для формы `spawn consume a, b { … }` взводила флаг
`_defer_<блок>_<индекс>_active` напрямую, не попадая ни в один из двух реестров.
Правило держалось договорённостью между тремя местами кода.

Мерило числами тоже есть: было 2 независимых реестра плюс прямое взведение мимо
обоих → должно стать 1 или 0 (см. Ф.2).

## Что установлено

### Взведение и снятие идут разными путями

```rust
fn disarm_var_for(&self, name: &str) -> Option<String> {
    if let Some((_, bid))      = self.reconsume_scopes.iter().rev().find(|(n, _)| n == name) { … }
    if let Some((_, bid, idx)) = self.auto_cleanup_active.iter().rev().find(|(n, _, _)| n == name) { … }
    None
}
```

* флаг в сгенерированном C зовётся `_defer_<блок>_<индекс>_active` — имя
  составлено из номера блока и порядкового номера, **не из имени переменной**;
* поэтому `disarm_var_for` — не «сними флаг», а «вычисли, как он называется»;
  вычислить из имени переменной нельзя, нужен реестр;
* реестры наполняются в двух местах (`emit_c.rs:31057`, `:33055`), каждое —
  под свою форму объявления;
* третья форма взводила флаг сама и не регистрировалась нигде.

### Корень глубже реестра: у кодогена нет связи «использование → объявление»

Узел переменной в дереве несёт только имя-строку:

```rust
Ident { name: String, span: Span, is_mut: bool, is_consume: bool }
```

Идентификатора объявления нет. Встретив `x.close()`, эмиттер не знает, какое
именно объявление `x` имеется в виду — одноимённых в разных областях может быть
несколько. Отсюда стек реестров и поиск `.rev().find()`: **это самодельная
имитация разрешения имён внутри эмиттера**. Кодоген заново решает задачу, уже
решённую чекером, и решает её по строке — а любая вторая реализация расходится с
первой. Она и разошлась.

**КЛАСС: одна операция (завести флаг и уметь его снять) размазана по трём
местам, и одно из них можно забыть.** Тот же класс, что корень Б в
[253.2](253.2-contract-doors.md) (хук на одной из пяти веток конструирования) и
что снятые хардкоды `__sret` в [172.15](172.15-value-placement-abi-audit.md)
(четыре проявления одного неверно выбранного места решения).

Цена этого конкретного случая измерена: зависание, ловившееся раз на тысячу
прогонов, с порчей кучи и невозвратом из `GC_gcollect()` — [№456](221.1-bug-sweep.md).

## Решение владельца 2026-08-08 — нормативно

Дословно: «когда появилась в блоке consume-переменная, сразу создаёшь переменную
для её дизарма».

**Имя флага выводится из имени переменной, а не из номера блока.** Флаг
объявляется рядом с самой переменной, в том же C-блоке. Тогда:

* связь «переменная → её флаг» существует **по построению**, а не по записи в
  реестре — забыть зарегистрировать нечего, регистрации нет;
* дизарм пишет присваивание флагу по выводимому имени, ничего не разыскивая;
* **теневание разрешает сам C**: во вложенном блоке одноимённая переменная
  принесёт с собой свой флаг, объявленный там же, и он затенит внешний ровно
  так же, как затеняет сама переменная. Правила областей видимости C делают
  работу, ради которой эмиттер вёл собственный стек.

**Это снимает предпосылку типизированного IR.** Первая редакция плана
утверждала, что Ф.2 упирается в [172.12](172.12-typed-ir-mono.md), потому что
узел использования не несёт идентификатора объявления. Неверно: идентификатор
объявления и не нужен, если имя флага детерминировано именем переменной, а
разрешение отдано C. Ошибка интегратора, снята владельцем.

## Объём работы — решение владельца

Дословно: «делаешь одним окном для всех случаев с consume и дизармом».

**Одно окно закрывает ВСЕ формы разом, а не ту, на которой споткнулись.** Это
прямое следствие устройства дефекта: реестр наполнялся по одной форме на место,
и именно поэтому третья форма выпала. Чинить формы по одной значит
воспроизводить ту же ошибку, только медленнее.

В объём входит **всё, что заводит или снимает авто-очистку**, а не только
`Stmt::ConsumeScope`: bare consume-let (D432 §2), re-consume-скоуп
`consume X { … }`, форма `spawn`/`detach consume a, b { … }` (D415 §4),
потребление получателем (`X.method(...)`, `consume_receiver_methods`),
потребление аргументом на consume-позиции параметра
(`free_fn_consume_param_positions`), и любые формы, которые окно найдёт сверх
этого перечня. Перечень **не считается полным** — его пополнение есть часть
задачи, а не отклонение от неё.

## Фазы

* **Ф.0 — перечислить ВСЕ формы, заводящие или снимающие авто-очистку.**
  Без полного перечня Ф.1 повторит исходную ошибку: закроет известные формы и
  оставит ту, о которой не вспомнили. Каждая форма — с файлом, строкой и
  фикстурой, показывающей её поведение сегодня.
* **Ф.1 — флаг заводится вместе с переменной, имя выводится из имени — ДЛЯ ВСЕХ
  ФОРМ ИЗ Ф.0.** Один шаг вместо двух: объявление consume-переменной порождает и
  её флаг.
  Реестры `reconsume_scopes` и `auto_cleanup_active` снимаются целиком,
  `disarm_var_for` вырождается в построение имени. Мерило: реестров было 2 →
  стало 0; мест взведения было N → стало столько же, сколько объявлений.
  Единственное, что требует внимания: отображение имён Nova в C-идентификаторы
  (эмиттер его уже делает) — флаг обязан строиться из ТОГО ЖЕ отображённого
  имени, иначе разойдётся с переменной, которую сторожит.
* **Ф.2 — проверить, где ещё кодоген резолвит по имени.** Реестр дизарма найден
  по следам аварии. Вопрос: сколько ещё мест в эмиттере ведут собственный стек
  областей видимости и ищут в нём строкой. Инвентарь перечислением, не догадкой —
  каждое место с файлом и строкой.

## Приёмка

* **Фикс носителя приёмкой НЕ считается.** №456 уже закрыт тремя строками —
  третья форма подключена к существующему реестру. Предмет плана в том, что
  реестр вообще существует.
* Проба «подсунь негодное» на Ф.1: завести флаг в обход единой точки — сборка
  обязана стать невозможной (а не «тест краснеет»).
* Мерило Ф.1 числами: реестров было 2 → стало 0; форм покрыто N из N по
  перечню Ф.0 — **частичное покрытие приёмкой не считается**, это и был исходный
  дефект.
* Ф.2: перечень мест с самодельным резолвом, каждое с файлом и строкой.

## Порядок относительно тега

* **До тега — ничего из Ф.1.** №456 закрыт, живых носителей нет, а правка
  горячего места кодогена перед релизом рискованнее дыры, у которой носителей не
  осталось. Оговорка: после снятия предпосылки IR работа стала дешёвой, и
  соблазн сделать её «заодно» велик — не поддаваться, цена ошибки здесь измерена
  зависанием раз на тысячу прогонов.
* **Ф.2 (инвентарь) — можно до тега**: знание, изменений кода нет.
