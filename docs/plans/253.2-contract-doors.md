# План 253.2 — Двери контрактов: инвариант записи проверяется в одной точке из многих

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-08. Подплан зонтика
[253](253-invariant-reduction-umbrella.md), трек Б. Дефект-корень —
[№466](221.1-bug-sweep.md) (К1). Основание — подозрение владельца («в системе
контрактов куча дверей вместо одной»), подтверждено разведкой окна
`p-contract-doors`; сырой отчёт с пробами — `wip/RECON-contract-doors.md`.

## Что установлено (пробами, не чтением)

**Карта «три точки проверки» — НЕВЕРНА.** Считалось: инвариант записи
проверяется при конструкции литералом, при присваивании полю и на выходе из
мутирующего метода. **Реально работающая точка ОДНА** — обёртка на
`ExprKind::RecordLit` (`emit_c.rs:35637-35720`), единственный call-site
`record_invariants` (`:1108`). Проверок на присваивание и на выход из метода в
коде нет вовсе.

### Два структурных корня (не пять независимых дверей)

Отличие от прецедента бáундов (№381/№383/№384/№345/№386 — пять дверей,
найденных по одной и чиненных волнами): здесь двери сводятся к **двум** корням.

* **Корень A — единственный call-site.** Обёртка ставится только на
  AST-узел `RecordLit` с `type_name: Some(...)`. Всё, что меняет поля иначе,
  проходит мимо: голое присваивание, элемент контейнера, захват в файбер.
* **Корень B — четыре обходных ветки конструирования.** `emit_record_lit`
  (`:49458`) строит структуру теми же присваиваниями полей ещё в четырёх
  местах — D55-инференс-контекст (`:49846`), spread (`:49902`), by-value
  `NovaValue_` (`:49930`), аноним по типу возврата (`:49965`). Обёртка на
  `:35637` смотрит на AST-имя, а не на резолвнутое имя внутри `emit_record_lit`.

### Двери, проверенные прогоном

| Дверь | Вердикт | Наблюдение |
|---|---|---|
| `#debug invariant` в `--mode release` | **ОТКРЫТА, опаснее всех** | dev: `panic: invariant failed`, exit 101. release: `bad.v=999`, exit 0, **без предупреждений** |
| голое присваивание `p.v = 999` | ОТКРЫТА | `after set_bad: v=999`, exit 0 |
| элемент контейнера `arr[i].field = x` | ОТКРЫТА | `assert(arr[0].v==999)` PASS |
| формы D55/`#coerce` (аннотация, `=> {…}`, spread) | ОТКРЫТА, 3 из 3 | `assert(bad.v==999)` PASS дважды |
| клонирование испорченного значения | закрыта | клонирование само паникует |
| `requires` через fn-значение | закрыта | `panic: requires failed`, exit 101 |
| serde/derive-конструкция | закрыта | синтезируют именованный `RecordLit` |

**Почему `#debug invariant` — первый по опасности.** Он стирается именно в
`--mode release`, а `CLAUDE.md` требует release-сборку как **обязательный
авторитетный гейт**. То есть защита исчезает ровно там, где владелец считает её
включённой, и молча — ни предупреждения, ни пометки в выводе.

### Не установлено (нужен эксперимент)

* **FFI / raw-pointer** — проба сегфолтнула, вывод не получен. Нужна корректная
  проба без выхода за границы.
* **spawn-захват** и **деструктуризация + пересборка** — вывод сделан по коду
  (тот же корень A), прогоном не подтверждён.

## Фазы

* **Ф.0 — добить неустановленное.** Три пробы выше. Пока они не сделаны, состав
  дверей неполон, а история проекта показывает: неполный инвентарь даёт не
  пустой результат, а ложную уверенность (уроки плана 250, инвентарь промахнулся
  трижды).
* **Ф.1 — решение по `#debug invariant`.** Развилка владельца: (а) сделать
  стирание **явным** — предупреждение при сборке release о том, что такие
  инварианты выключены; (б) не стирать вовсе, оставив `#debug` только как
  подсказку оптимизатору; (в) запретить атрибут до реализации, как решено по
  `#zero_on_move` (№465). Молчаливое стирание не остаётся ни в одном варианте.
* **Ф.2 — корень A: перенести энфорс с формы на СВОЙСТВО.** Проверка должна
  вешаться не на AST-узел `RecordLit`, а на факт «значение типа с инвариантом
  получило новое содержимое». Кандидатные точки — присваивание полю, запись в
  элемент контейнера, выход из мутирующего метода. Обязательное требование:
  ни одна точка не добавляется «на глаз» — состав берётся из инвентаря Ф.0.
* **Ф.3 — корень B: свести четыре ветки конструирования к одной.** Пять
  ветвлений строят одну и ту же структуру; обёртка обязана применяться в общей
  точке, а не в той единственной, где о ней вспомнили. Это применение шага 0
  нормы (`conventions-governance.md`): не «поставить проверку в пяти местах», а
  **убрать пять мест**.
* **Ф.4 — фикстуры.** Из проб разведки: `p1_field_assign_main.nv`,
  `p2_batch.nv`, `p3_anon_variants.nv`, `p5_debug_erasure_main.nv` (dev против
  release — критичная), `p6_fnvalue_requires_main.nv` (позитив). Проба
  `p4_raw_ptr.nv` требует переделки.

## Приёмка

* **Фикс одной двери приёмкой НЕ считается** — закрываются ДВА КОРНЯ.
* Мерило по норме зонтика, числами: было — 1 работающая точка энфорса при
  ≥5 путях изменения; стало — N путей, покрытых M точками, с обоснованием,
  почему M минимально.
* Проба «подсунь негодное» на КАЖДУЮ закрытую дверь: сломать энфорс, показать
  что соответствующая фикстура краснеет.
* **Отдельная проба dev против release** — обе сборки на одной фикстуре с
  `#debug invariant`, вердикты дословно.

## Порядок относительно тега

**Ф.1 (решение по `#debug invariant`) — ДО ТЕГА**: молчаливое отключение
проверки в релизной сборке — ложное обещание безопасности, тот же класс, что
№465. Остальное — после: Ф.2/Ф.3 меняют кодоген в горячем месте, перед релизом
такая правка рискованнее самой дыры, у которой сегодня нет пользовательских
носителей.
