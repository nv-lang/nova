# План 251 — Аудит завершения процесса: 291 точки `abort()` в рантайме

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-07 по мандату владельца «нам нужны итоговые
программы БЕЗ крашей». Дефект-корень — [№436](221.1-bug-sweep.md). Двойник
плана [250](250-vela-state-consolidation.md): 250 убирает КЛАСС ГОНОК (причина
крашей), 251 приводит в порядок ЗАВЕРШЕНИЕ (как рантайм падает, когда падать
приходится).

## Зачем

**СЧЁТ ИСПРАВЛЕН 2026-08-08: точек не 98, а 291.** Прежнее число интегратор получил неверным грепом и повторял его в реестре и в разговорах. Механическое перечисление (opencode, по шаблону `docs/dev/promts/opencode-brief-template.md`) дало 291 вхождение и 291 строку таблицы — покрытие полное, без обрезки. Сырой инвентарь: [251-abort-inventory.md](251-abort-inventory.md).


В `compiler-codegen/nova_rt/**` — **291** вызов `abort()` (замер 2026-08-07).
Утром интегратор думал, что их два. Каждый `abort()` даёт пользователю `SIGABRT`
и дамп памяти — читается как «крах рантайма», даже когда рантайм отработал
корректно, а виноват пользовательский код или это просто тайминг.

Мандат владельца: краши не нравятся в любом виде. Но не всякое завершение —
краш: если пользователь сам просит выйти или бросил необработанную ошибку,
завершиться НАДО — вопрос в СПОСОБЕ.

## Рубрика (конвенция `mn-coding-conventions.md` §0.6)

Каждый из 98 `abort()` относится к одной строке матрицы по ИСТОЧНИКУ:

| Источник | Кто виноват | Целевой способ | Что делать с `abort()` |
|---|---|---|---|
| Пользователь ХОЧЕТ выйти | никто | `Os.exit(code)` | не наш путь, не трогаем |
| Необработанный `Fail`/`panic()` пользователя | пользователь | управляемый выход, код 101 + диагностика | ЗАМЕНИТЬ на `nova_exit_program_error()` |
| Гонка рантайма (поздняя отмена и т.п.) | МЫ | НЕ завершать — свернуть только фибр | УБРАТЬ (как в №431/№436) |
| Нарушен инвариант рантайма («этого не может быть») | наш баг | `abort()` с дампом — дамп НУЖЕН | ОСТАВИТЬ намеренно |

## Уже сделано (носители №436)

- Путь отмены: `abort()`/`exit()` убраны (№431, якорь фибра). ✅
- `unhandled Fail` / `panic()` пользователя (`effects.h`): переведены на
  `nova_exit_program_error()` код 101 (№436). ✅

## Фазы

- **Ф.0 — ИНВЕНТАРЬ 291 точки.** По файлам (`runtime.c` 19, `fibers.h` 12,
  `fiber_arena.c` 9, `nova_sched.h` 8, `effects.h`/`effects.c`, `net.c` 7,
  `channels.h` 6, `alloc*` — 27 из них «out of memory»). Для КАЖДОЙ: сообщение,
  строка матрицы, целевой способ. Таблица — отдельным коммитом до правок.
  Много «нет сообщения» — сначала прочитать контекст, не гадать.
- **Ф.1 — OOM отдельно (~27 точек).** Нехватка памяти — особый случай: продолжать
  чаще нельзя, но `abort()` без дампа + честное «out of memory» лучше SIGABRT.
  Решить единый способ для всей группы.
- **Ф.2 — ЗАМЕНА пользовательских путей** на управляемый выход (код 101), где
  виноват пользовательский код. Диагностика и flush уже стоят ПЕРЕД вызовом —
  менять только способ завершения.
- **Ф.3 — ОСТАВИТЬ инвариантные** (наш нарушенный инвариант) с `abort()` + дампом;
  каждый — с комментарием «почему это НАША авария, дамп нужен».
- **Ф.4 — фикстуры на код возврата:** пользовательский отказ → 101, не SIGABRT;
  `Os.exit(N)` → N; наш инвариант в отладке → дамп.

## Приёмка

- Таблица Ф.0 с вердиктом по КАЖДОЙ из 291 точки.
- После Ф.2/Ф.3: ни одна пользовательская ошибка и ни одна гонка не даёт
  `SIGABRT`; `abort()` остаётся ТОЛЬКО на строке «наш инвариант».
- Проба «подсунь негодное»: пользовательский отказ, паника, `Os.exit`, наш
  инвариант — четыре пробы прогоном на код возврата.
- **Фикс части точек приёмкой НЕ считается** — класс закрывается, когда КАЖДАЯ
  из 98 классифицирована и приведена к целевому способу.

## Порядок относительно тега
