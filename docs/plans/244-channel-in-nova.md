## Зачем

`Channel`/`ChanWriter`/`ChanReader` сегодня — **compiler-intrinsic без единого
`.nv`-объявления**: логика в C-рантайме, а сборка пары `(tx, rx)` держится на
**трёх написанных вручную ветках кодогенератора**
(`[M-59.1-channel-new-cleanup]`). Нарушение нормы «одна дверь» и конвенции
«компилятор берёт типы и функции из `.nv` по максимуму, в Rust — только
непортируемое».

## Ключевое наблюдение: всё нужное в Nova уже есть

| Нужно каналу | Есть в Nova | Где |
|---|---|---|
| взаимное исключение | `Mutex` (`#share`) | `std/src/runtime/sync.nv` |
| ожидание условия | `Condvar` — `@wait(mut m Mutex)`, `@wait_for`, `@wait_until`, `@notify_one`, `@notify_all` | там же |
| атомарный розыгрыш | `AtomicInt` + `@compare_exchange` | там же |
| буфер элементов | `[]T` — обычный `Vec[T]` | prelude |

`Mutex`/`Condvar`/`Atomic*` остаются `extern "nova"` — и это ПРАВИЛЬНО: они
часть планировщика, парковка файбера непортируема по определению. Канал же
поверх них — обычная структура данных, ей место в `.nv`.

## Что ИСЧЕЗАЕТ вместе с обёрточным подходом

Первая редакция тащила цепочку вопросов — все снимаются реализацией на Nova,
потому что буфер становится обычным `[]T`:

- `elem_size` / `size_of[T]()` при создании — **не нужно**;
- выравнивание области данных — **не вопрос** (`Vec[T]` сам о себе заботится);
- GC-безопасность байтового буфера — **не вопрос** (`Vec[T]` под сборщиком как
  любой другой);
- `mut slot uninit T` для приёма — **не нужно**, `recv` читает элемент буфера;
- `*mut u8`, приведения, `unsafe` — **ни одного**;
- типизированные FFI-ручки (№288) — здесь неприменимо, канал больше не ходит
  через FFI. Сам №288 остаётся, план [245](245-ffi-typed-handles.md).

## Представление

```nova
module std.concurrency.channel

/// Разделяемое состояние канала. #share — внутренняя синхронизация (D415):
/// тип по назначению живёт сразу в нескольких файберах.
#share
type Chan[T] {
    lock      Mutex
    not_empty Condvar
    not_full  Condvar
    buf       []T          // кольцевой буфер ёмкости cap
    head      int          // индекс головы
    count     int          // сколько элементов внутри
    closed    bool
    tx_refs   AtomicInt    // счётчик писателей: канал закрывается на нуле
    waiters   []SelectWaiter   // регистрации select-ветвей, см. ниже
}

export type ChanWriter[T](Chan[T])
export type ChanReader[T](Chan[T])
```

Разделение типов даёт безопасность следствием системы типов, а не особым
случаем в компиляторе: у писателя физически нет метода `recv`, у читателя —
`send`.

## Создание — обычная функция, кортеж собирается на месте

```nova
#stable(since = "0.1")
export fn Channel[T].new(cap int) -> (ChanWriter[T], ChanReader[T]) {
    ro ch = Chan[T] {
        lock: Mutex.new(),
        not_empty: Condvar.new(),
        not_full: Condvar.new(),
        buf: []T.with_capacity(cap),
        head: 0, count: 0, closed: false,
        tx_refs: AtomicInt.new(1),
        waiters: []SelectWaiter.new(),
    }
    (ChanWriter[T](ch), ChanReader[T](ch))
}
```

Ни кортежного FFI, ни плана [115](115-ptr-type-and-tuple-ffi.md) — зависимость
снята полностью.

## Отправка и приём — учебный ограниченный буфер

```nova
export fn ChanWriter[T] @send(consume v T) -> bool {   // consume: владение уходит (D131/№144)
    mut g = @.lock.lock()
    while @.count == @.buf.cap() && !@.closed {
        @.not_full.wait(@.lock)
    }
    if @.closed { return false }
    @.buf_put(@.head + @.count, v)
    @.count += 1
    @.not_empty.notify_one()
    @.wake_select_waiters()        // см. раздел select
    true
}

export fn ChanReader[T] @recv() -> Option[T] {
    mut g = @.lock.lock()
    while @.count == 0 && !@.closed {
        @.not_empty.wait(@.lock)
    }
    if @.count == 0 { return None }     // закрыт и пуст
    ro v = @.buf_take(@.head)
    @.head = (@.head + 1) % @.buf.cap()
    @.count -= 1
    @.not_full.notify_one()
    @.wake_select_waiters()
    Some(v)
}
```

`try_send`/`try_recv` — те же тела без `wait`: не готово → сразу `false`/`None`.
`close` у писателя уменьшает `tx_refs` и на нуле ставит `closed` плюс
`notify_all` на обоих условиях; `close` у читателя ставит `closed` и будит
ждущих отправителей.

**Кольцевое обращение** (`buf_put`/`buf_take` выше — рабочее имя) в Ф.1
выбирается между приватным помощником и обычной индексацией с `% cap()` на
месте; второе проще и не расширяет `Vec`. Обосновать в отчёте.

## `select { … }` — форма языка над обычным кодом Nova

`select` нельзя записать вызовом: у него ветви с телами и связыванием
переменных. Но компилятору НЕ нужно знать внутренности канала — ровно как
`for x in v` разворачивается в вызовы протокола итератора, ничего не зная про
устройство `Vec`.

### Ожидатель — тоже на Nova

```nova
#share
type SelectWaiter {
    lock  Mutex
    cv    Condvar
    fired AtomicInt      // -1 = никто не сработал; иначе индекс победившей ветви
}
```

Канал держит список зарегистрированных ожидателей. `wake_select_waiters`
(зовётся из `send`/`recv`/`close` под замком канала) проходит список и для
каждого делает `fired.compare_exchange(-1, arm_index)`. **Первый успешный
обмен и есть розыгрыш победителя** — остальные видят, что значение уже не -1,
и не трогаются. Победителю шлётся `cv.notify_one()`.

### Регистрация НЕ забирает значение

Это ответ на опасение «а вдруг заберём из всех каналов». Регистрация — только
добавление ожидателя в список канала; ни один элемент при этом не извлекается.

### Разворачивание формы

```nova
select {
    Some(v) = rx     => handle(v)
    tx <- payload    => sent()
    default          => busy()
}
```

разворачивается в обычный код:

```nova
ro w = SelectWaiter.new()
rx.register(w, 0)                    // просто добавить w в список канала
tx.register(w, 1)
mut which = -1
loop {
    which = try_arms(w)              // быстрый проход: try_recv/try_send по ветвям
    if which >= 0 { break }
    if has_default { break }         // ветвь default — не спим
    w.wait()                         // спим, пока кто-то не выиграет compare_exchange
    w.reset()                        // готовимся к повтору: значение могли перехватить
}
rx.unregister(w)
tx.unregister(w)
if which == 0 { ro v = ...; handle(v) } else if which == 1 { sent() } else { busy() }
```

Три свойства, ради которых устроено именно так:

1. **Победитель ровно один** — по `compare_exchange` на `fired`.
2. **Проигравшие каналы значений не теряют**: их значения остаются в их
   буферах, потому что забор происходит ТОЛЬКО в `try_arms` и только для
   победившей ветви.
3. **Пробуждение с повтором** вместо прямой передачи значения: разбудили —
   пробуем снова; если между пробуждением и попыткой значение перехватил
   другой файбер, цикл идёт на второй круг. Проще прямой передачи и заведомо
   корректно; цена — лишний проход в редком случае гонки.

**Случайный порядок ветвей.** Сегодняшний рантайм перемешивает ветви
(Фишера-Йетса, `nova_select_try_immediate`) — семантика Go, защита от
голодания: иначе первая ветвь всегда съедала бы вторую. Версия на Nova
ОБЯЗАНА сохранить это свойство: `try_arms` обходит ветви со случайного
смещения. Фикстура на голодание обязательна.

## Как достичь паритета с C-версией (вопрос владельца 2026-08-03)

Паритет достижим — но только если воспроизвести приёмы C-версии, а не
надеяться на оптимизатор. Разбор по источникам скорости.

### 1. Прямая передача значения — ГЛАВНОЕ

C-версия при парковке получателя НЕ кладёт значение в кольцевой буфер:
отправитель пишет его прямо в слот ожидателя и будит его
(`recv_val` в `channels.h`: «wake recv helper direct-writes value сюда»,
план 44.1 R1 B1). Экономится копирование и целый круг
«проснуться → взять замок → перепроверить → забрать».

На Nova это выражается один в один: ожидатель несёт типизированный слот.

```nova
#share
type RecvWaiter[T] {
    lock  Mutex
    cv    Condvar
    slot  Option[T]      // отправитель кладёт значение СЮДА
    ready AtomicInt
}
```

`send` под замком канала: если есть припаркованный получатель — положить
значение в его `slot`, отметить `ready`, разбудить, и в буфер НЕ писать.
Проснувшийся получатель читает свой слот, замок канала ему не нужен.

**Следствие для select:** «пробуждение с повтором» из раздела выше — это
УПРОЩЕНИЕ, которое стоит одного лишнего круга. Для паритета ветви тоже
получают прямую передачу: каждая ветвь регистрирует СВОЙ типизированный
`RecvWaiter[T_i]` (у ветвей разные `T` — общий нетипизированный ожидатель
слот нести не может), а «кто победил» решает ОДИН общий `AtomicInt`,
переданный всем ветвям. Тогда розыгрыш остаётся атомарным, а значение
приходит сразу в слот победившей ветви.

Порядок работ: Ф.2 делает простой вариант (пробуждение с повтором) —
он корректен и его легко проверить; **Ф.5 замеряет, и если разрыв
существенный, прямая передача включается и для select**.

### 2. Быстрый путь без сна

Незанятый `Mutex` обязан стоить одну атомарную операцию, без обращения к
планировщику. Если замер покажет иное — это дефект `Mutex`, а не канала,
и чинится он в своём месте (записать номером, не обходить внутри канала).

### 3. Встраивание малых методов — ЧЕСТНЫЙ ПРОБЕЛ

C-версия целиком `static inline` в заголовке: тела втягиваются в место
вызова. В Nova атрибута `#inline` НЕТ (проверено грепом по `std` — ноль
вхождений), и втягивание зависит от того, что сделает компилятор и затем
сишный оптимизатор.

Это единственный источник разрыва, который нельзя закрыть кодом самого
канала. Порядок действий: Ф.5 замеряет; если разрыв объясняется именно
вызовами — вопрос выносится владельцу отдельно (введение `#inline` —
язык-меняющее решение, не принимается внутри этого плана).

### 4. Проверки границ буфера

Индекс в кольце уже приведён по модулю ёмкости, значит проверка границ
при обращении к `buf` избыточна. Трогать это **только после замера**: если
вклад в разрыв мал — не трогать вовсе; преждевременное снятие проверок в
конкурентном коде — плохой размен.

### Правило приёмки по скорости

Паритет считается достигнутым при просадке **не более 5%** на каждом из
трёх сценариев Ф.5. Хуже — либо включается прямая передача для select
(п.1), либо вопрос идёт владельцу с числами и вариантами. Утверждать
паритет без чисел запрещено.

## Фазы

- **Ф.1 — `Chan[T]` на Nova:** структура, `send`/`recv`/`try_*`/`close`/
  `is_closed`/`len`/`cap`, без select. Существующие channel-фикстуры зелёные
  на НОВОЙ реализации (кроме требующих select).
- **Ф.2 — `select`:** `SelectWaiter`, регистрация и розыгрыш, новое
  разворачивание формы в кодогенераторе на вызовы `.nv`-слоя.
- **Ф.3 — снос:** три ad-hoc ветки `Channel.new`, отработавшая часть
  `channels.h`, ограждение `E_CHANNEL_UNSOUND_ELEM_TYPE` (беспредметно —
  буфер типизирован). **Ратчет обязан пойти ВНИЗ** — цель фазы, а не побочный
  эффект; считать ИТОГ (минус ветки `Channel.new`, минус старое опускание
  select, плюс новое).
- **Ф.4 — расширение и фикстуры:** `Channel[str]`, `Channel[f64]`, канал
  многополевых записей — всё, что запрещало ограждение; select над такими
  каналами; фикстура «проигравшие ветви не теряют значения» (два готовых
  канала, два прохода select обязаны выдать оба значения); фикстура на
  голодание (случайный порядок ветвей).
- **Ф.5 — замер производительности (ОБЯЗАТЕЛЬНАЯ, см. риск 1).**
- **Ф.6 — дока и спека:** `docs/guide/channels.md` (сейчас описывает
  ограничение word-safe), D91/D94-соседство — тем же слиянием.

## Риски

1. **Производительность — главный риск.** Сегодняшний канал — вылизанный C с
   прямой передачей значения ожидателю. Версия на Nova ходит через `Mutex` и
   `Condvar`, а они сами паркуют файбер — цепочка длиннее. Канал использует
   флагман и Полярис, регресс будет заметен. **Ф.5 обязана ПОДТВЕРДИТЬ ПАРИТЕТ числами** (рецепт — раздел «Как достичь паритета»): замер до/после
   на одинаковом сценарии: пропускная способность при разной ёмкости буфера,
   задержка на пустом канале, select с несколькими ветвями. Если просадка
   существенная — решение владельца: принять, оптимизировать (прямая передача
   значения ожидателю, как в C-версии) или откатить план. **Без замера план не
   закрывается.**
2. **`Condvar.wait` под `Mutex` в M:N.** Проверить корректность парковки при
   миграции файбера между потоками: механизм тот же, что у `Mutex`, но канал
   нагружает его иначе.
3. **`#share` и D415.** `Chan[T]` помечен `#share` — под энфорсом S1a это
   разрешает захват сторон канала в файбер. Проверить, что `consume`-семантика
   `send` (№144) не сломана: использование после отправки обязано отклоняться.
4. **Рантайм-гонки.** Текущая C-реализация вылизана годами, новая может
   принести свои. Приёмка статистическая (как в окне p-vela): нагрузочная
   фикстура прогоняется **30 раз**, проходной результат 30/30.
