# План 286.2 — `nova-postgres`: пул соединений (паритет pgxpool / database/sql)

**Статус:** 🔨 В РАБОТЕ, **ЗАБЛОКИРОВАН НА ЯЗЫКЕ** — подплан [286](286-db-driver.md),
волна Д8; заведён 2026-09-28 (рабочий файл `PLAN-pool.md` в `nova-postgres`
перенесён сюда словом владельца). Решение по API принято в обсуждении:
**блокирующий `acquire` + канонический `try_acquire`** (пара try_recv/recv, D325;
префикс `try_` — неблокирующий сиблинг блокирующей операции, не общий маркер
«может не сработать»). Пул — **не ядро драйвера**, а отдельный модуль поверх
(как pgxpool поверх pgx).

> **Блокер (замер 2026-09-28, репро `nova-postgres/repro-local/chan_conn`):**
> каналы std (`nvchan`) сегодня **не переносят consume-значения**: `@send(v)`
> принимает plain (copying) параметр — в std прямо отмечено «until generic
> consume-sinks exist». `Connection` — consume-тип, поэтому дизайн
> «idle-хранилище = `Chan[Connection]`» некомпилируем: `release` не может
> отдать conn в канал (D133), поля `ChanTx/ChanRx[Connection]` в записи
> тоже требуют consume-дисциплины, которую generic-инстанс не выражает.
>
> **Дозамер 2026-09-28 (репро `repro-local/chan_conn`, отчёт §8): Vec тоже
> поражён** — `Vec[T consume] @push/@exchange(consume v T)` не засчитываются
> чекером как consume-sink (D133-not-consumed) ни для кросс-модульного
> `Connection`, ни для локального consume-типа. Т.е. «consume в массиве»
> в языке объявлен (перегрузки в std есть), но чекером не работает; пул
> не строится ни на Chan, ни на Vec.
> **Развилка** — *адресат: интегратор* · *срок: до продолжения этого подплана*:
> (а) дождаться/заказать generic consume-sinks в языке (каналы и Vec с
> consume-пayload) — тогда дизайн ниже реализуется как написан;
> (б) перепроектировать пул без переноса `Connection` через generic-контейнеры
> (например, пул владеет conn'ами сам и выдаёт `@share()`-хэндлы — меняет
> семантику acquire/release) — требует отдельного слова владельца, т.к. это
> уже не «пул соединений» в смысле pgxpool.

## Дизайн (записан на случай разблокировки)

- Файл `src/pgnet/pool.nv` того же модуля `postgres.pgnet`.
- **Layout**: все поля `Pool` — plain-типы (ConnectOptions, два конца
  канала, счётчики). `Connection` не сидит в полях записи и не в vec —
  только внутри `Chan[Connection]` между release и acquire. Обоснование:
  смешанные consume/plain поля мис-лоуэряться на межмодульной границе,
  а payload-enum/vec-формы — семья query_error_live.
- **Канал = idle-хранилище**: `Chan[Connection].new(limit)`. Инвариант:
  `idle + out <= limit`, поэтому `release.send` никогда не блокирует.
- **acquire** (блокирующий): try_recv → поп; иначе новая сессия через
  `connect()`, пока `out < limit`; иначе `rx.recv()` (блок; отмена — kill
  fiber; None от recv = пул закрыт во время ожидания → структурная ошибка).
- **try_acquire**: то же без recv-ветки; на лимите — `Err(PoolExhausted)`
  (вариант `ConnError.PoolExhausted` уже добавлен в `src/pgnet/conn.nv`,
  документирован как «только try_acquire»).
- **release(consume conn)**: out -= 1; запомнена фатальная ошибка
  (не-Server) — conn.close() вместо pooling (ядовитые не крутятся);
  иначе send обратно. Недочитанные ответы не страшны — implicit drain
  на входе следующего query (Д8в).
- **close()**: drain канала, каждому idle — вежливый Terminate. Выданные
  conn — забота держателей (их @close работает). Дроп Pool без close() =
  утечка idle-сокетов (явный close, как sql.DB.Close).
- Эффекты: `Net Random` (каналы std — без эффектов в сигнатуре).
