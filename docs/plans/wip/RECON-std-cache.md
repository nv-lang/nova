### 1.1 Ответ на развилку окна

Развилка ставилась так: «по разу на файл, хотя модуль один → объединять
единицы компиляции; законно, но каждый раз заново разбирает `std` →
кэшировать разбор; оба сразу → сказать, что даёт больше».

**Ответ: ни то, ни другое в чистом виде — верен третий, но не тот, что
ожидался.**

1. **Единицы компиляции не размножены.** 568 файлов `neg/` → 481 вызов
   `resolve_imports_inline_ex` (у остальных компиляция обрывается раньше).
   Ровно по одному на компилируемый файл. Файлы `neg/` — независимые модули,
   объединять здесь нечего. Наблюдение 255 §3.1 про 1161 запись касается
   ВЕРХНЕГО уровня `spec_tests/conformance`, а не измеренного среза, и
   этим окном не проверялось (мандат — `neg`).
2. **Повторный разбор `std` есть — 416,7-кратный** (39 173 разбора над 94
   уникальными файлами, 442,9 MiB текста), **но он стоит 0,4 % стадии**:
   `imports-peer-parse` = 20,24 с из 4569,46 с. Кэш AST дал бы максимум
   ~0,4 %.
3. **Время съедало третье, в развилке не названное — повторное хождение по
   файловой системе.** Разбивка `imports-resolve` (4569,46 с, 480 замеров,

| `imports-canonkey` | 2269,13 с | 93 540 | 49,7 % |

`imports-canonkey` (`canonical_module_key`) почти целиком состоит из

### 1.2 Почему это стоило столько

Два места в `compiler-codegen/src/imports.rs`:

* `is_folder_module_peer(path)` — чтобы ответить «папка — это модуль?»,
  читает `read_to_string` **каждый** `.nv`-файл каталога целиком и сканирует
  в нём строку `module`. Вызывается из `canonical_module_key`, то есть на
  каждый резолв каждого импорта каждого компилируемого файла — 93 984 раза
  за прогон;
* `resolve_module_paths` — кандидат-поиск по каталогам (`read_dir`) плюс
  «orphan»-проверка, которая для файлового модуля читает объявление каждого
  соседа по каталогу. 89 749 вызовов.

Оба — чистые функции состояния дерева исходников, которое за один прогон
компилятора не меняется. Это и есть предмет кэша.

**Поправка к посылке плана.** План 252 исходил из того, что «~99 % работы
этих фаз — это ПОВТОРНЫЙ разбор `std` с нуля». Повторность 416,7× замер
подтвердил, а вот её ЦЕНУ — нет: разбор дёшев (0,4 %), дорого обходится
дорога к файлу, а не файл. Мерило плана («доля `imports-resolve`») при этом
осталось верным — просто лечится не тем, чем предполагалось.

## §2. Что реализовано и почему именно это

`compiler-codegen/src/source_cache.rs` — кэш **обращений к дереву
исходников**, внутрипроцессный, с проверкой актуальности на каждом
обращении. Три примитива:

| функция | что кэширует | чем проверяется |
|---|---|---|
| `file_text(path)` | содержимое `.nv`-файла | `mtime` + размер файла (`fs::metadata`) |
| `dir_nv_files(dir)` | список обычных `.nv` каталога | `mtime` каталога |
| `dir_derived(dir, tag, f)` | произвольный вывод, зависящий только от содержимого каталога | свежий снимок каталога: `(путь, mtime, размер)` каждого `.nv` |

Поверх них в `imports.rs`:

* `is_folder_module_peer` → вердикт целиком через `dir_derived`;
* `dir_module_decls(dir)` / `dir_declared_dotted(dir)` — объявления `module`
  всех соседей, посчитанные раз на каталог; ими питаются orphan-проверка,
  `collect_root_peers`, entry-sibling-скан и разбор «фасад + подпапка»;
* чтение peer-файлов, `_module.nv` и сканы объявлений — через `file_text`.

**Почему кэш, а не объединение единиц компиляции.** Ф.0 показала, что
единиц ровно столько, сколько компилируемых файлов; объединять нечего, и
стоп-условие окна («нужно объединение CU») не наступило. Правка целиком
внутри резолва импортов — чекер-канал; легаси `emit_c` не тронут.

**Почему НЕ кэшируется AST.** Замерено: 0,4 % стадии. Кэш разобранного
`Module` потребовал бы переназначения `file_id` во всех спанах при выдаче из
кэша (каждый peer при каждом резолве получает свой `FileId`) — риск
испорченной диагностики ради 0,4 %. Не сделано сознательно, по числу.

### 2.1 Корректность

* **Не «прочитали один раз за процесс и забыли».** Отпечаток сверяется при
  КАЖДОМ обращении; расхождение — запись считается протухшей, данные
  перечитываются. Стоимость проверки: один `stat` (для `dir_derived` — один
  `read_dir`, который на Windows отдаёт метаданные всех файлов вместе с
  именами, без отдельных сисвызовов) против чтения N файлов целиком.
* **Рваная запись не залипает.** После вычисления источник штампуется
  повторно; если он менялся, пока мы читали, результат отдаётся вызывающему,
  но в кэш не кладётся.
* **Промах кэша не может дать иной результат, чем его отсутствие**: на
  промахе выполняется тот же самый код, что и раньше. `NOVA_SRC_CACHE=0` —
  полный сквозной проход (аварийный рубильник и способ сравнения А/Б).
* Формат промежуточного представления не тронут, инференс не задет — в кэше
  лежит только текст файлов и списки путей.

**Известная граница (не дефект, но записана честно).** Отпечаток — `mtime` +
размер, как у `cargo`/`make`. Правка, сохранившая и время правки, и размер,
кэшем не заметится. Содержимое-хеш убрал бы и это, но потребовал бы читать
файл — то есть ровно ту работу, которую кэш убирает.

инструментирования лежат в пределах разброса, и сравнение 348 → 125
корректно.

**Как считается «доля».** `PerfTimer` суммирует по всем 16 воркерам, а мои
под-таймеры вложены в `imports-resolve` и потому попадают в `grand total`
дважды. Чтобы цифра была сопоставима с 95,2 % из
`RECON-compile-phases.md` (там вложенных таймеров не было), из `grand total`
вычтена сумма всех вложенных `imports-*`:

* до: `15850,44 − 11075,72 = 4774,72`; `4569,46 / 4774,72 = 95,7 %`
  (сходится с 95,2 % плана 255 — воспроизведение независимым прогоном);
* после: `4130,17 − 2740,75 = 1389,42`; `1227,50 / 1389,42 = 88,3 %`.

**Честно о мериле.** Доля упала только на 7,4 п.п., хотя абсолютное время
стадии упало втрое: остальные фазы (`type-check`, `codegen`) в абсолюте не
изменились, а стадия, даже урезанная втрое, всё ещё крупнейшая. Доля
`imports-resolve` не опустится заметно, пока стадия не станет дешевле
кратно ещё раз, — поэтому решающая цифра здесь абсолютная: **348 с → 125 с**.
