# PROGRESS — окно p409-cleanup-miscompile (№409, К1)

Worktree: `d:/Sources/nv-lang/nova-p409`, ветка `p409-cleanup-miscompile`.
Модель: **Sonnet** (везде — разведка, минимизация репро, диагностика, фикс, тесты).

## Итог одной строкой

Настоящая мискомпиляция подтверждена, минимизирована до репро БЕЗ канала/мьютекса/std,
диагноз доведён до конкретной строки в `field_cache.rs` × конкретной строки в `emit_c.rs`,
фикс — 1 строка (+ добавленное условие) в `emit_c.rs`, проба «подсунь заведомо негодное»
подтверждает регресс, `nova check std/src` не просел.

## Шаг 1 — минимальное репро (коммит ДО фикса)

Файл: `docs/plans/repro/p409_min.nv`. Полностью без std-канала, без std-мьютекса — свой тип
`P409Res consume { ro id int }` с `@cleanup`, свой явный consume-метод `@release()`
(зеркалит форму `MutexGuard consume @unlock()`), свой `value`-тип-обёртка `P409Container`.

Ключевая находка при минимизации: **не любая форма репродуцирует**. Потребовалось
8 итераций, чтобы отделить существенные условия триггера от случайных:

1. Первая попытка (обычная запись + повторное чтение ОДНОГО и ТОГО ЖЕ поля 3×,
   `@b.n`/`@b.n`/`@b.n`) — **не воспроизвелась**. Причина (прочитано в сгенерированном
   C): field-cache в этом случае делает VALUE-кэш (`nova_int _at_b_n_chain = …`,
   скаляр), не POINTER-кэш — безобидно.
2. Добавление ДВУХ РАЗНЫХ полей (`@b.n`/`@b.m`) — тоже не воспроизвелась (снова
   value-кэш каждого поля по отдельности).
3. Ключевой сдвиг: `value`-тип-обёртка (как `ChanTx[T] value { priv ch Chan[T] }`)
   + чтение поля-получателя ВНУТРИ инициализатора `consume`-létа, поданное как
   АРГУМЕНТ вызова (`Res.new(@b.cap - 3)`) — **не воспроизвелась** (field-cache
   выбрал chain-caching V4, кэширующий ЗНАЧЕНИЯ `_at_b_cap_chain`/`_at_b_n_chain`/
   `_at_b_closed_chain`, снова безобидно).
4. Финальный триггер (repro в файле): поле-получатель как **ПОЛУЧАТЕЛЬ ЦЕПОЧКИ
   ВЫЗОВА** внутри инициализатора consume-léta (`@b.locker.acquire()`, НЕ
   `Res.new(@b.cap)`) **плюс** мутирующий МЕТОД-ВЫЗОВ (`@b.buf.push(1)`, не
   простое присваивание `@b.n = @b.n`) в теле `while`, которое замыкает
   «регион» сразу после consume-léta. Именно эта комбинация переключает
   field-cache на POINTER-хойст (`Nova_P409Box* _at_b = …`) — тот же механизм,
   что и в реальном `nvchan.nv`.

Наблюдаемый КРАСНЫЙ сигнал (компилятор БЕЗ фикса, field-cache ВКЛ — дефолт):
детерминированная паника рантайма `nv_panic("D188-on-exit-double-invocation")`
— встроенный exactly-once guard ловит повторный диспетч auto-cleanup. 5/5
прогонов. С `--no-field-cache` (тот же компилятор, БЕЗ фикса) — 3/3 зелёных.

## Шаг 2 — чья это материя

**Эмиссионная** (196-дисциплина: НЕ типовая информация, не `resolved_types`) —
чистая AST-identity дисциплина между двумя AST-проходами: `field_cache.rs`
(rewrite-проход, ДО эмиссии) и `emit_c.rs`'s Plan-217 bookkeeping (во время

### Диагноз (прослежен через РЕАЛЬНЫЙ сгенерированный C, не гипотеза)

Поскольку минимальное репро подбиралось методом проб, диагноз ставился на
СНАЧАЛА восстановленной ИЗ ИСТОРИИ ГИТА (коммит `d8a0f8617`, ДО обхода
`cafc372ed`) форме `nvchan.nv`'s `ChanTx.send()` — единственный способ увидеть
РЕАЛЬНУЮ мискомпиляцию (в текущем main обход уже стоит, `mut ch = @ch`).
Восстановленный/помономорфизированный вручную (без генериков — они бьют по
несвязанному №412) probe собирался с `--keep-artifacts`, `.c` сравнивался
БАЙТ-В-БАЙТ между field-cache ВКЛ/ВЫКЛ (обе сборки — с полностью очищенным
`target/.nova-cache`/`rt-archive-cache`/`contracts-cache`, иначе content-addressed
build-cache Plan 81 Ф.9 отдаёт СТАРЫЙ `.c`, потому что его ключ **не включает**
`--no-field-cache`/`NOVA_FIELD_CACHE*` — это отдельная, не в объёме этого окна,
находка кэш-полноты, докладывается интегратору отдельно ниже).

Сгенерированный C (`ChanTx.send`, поле-cache ВКЛ) содержит:

```c
Nova_MutexGuard* guard = NULL;  /* Plan 217: hoisted for auto-cleanup FAIL/INTERRUPT run-site */
...
Nova_Chan* _at_ch = ((*nova_self).ch);
/* SRC: consume guard = @ch.mutex.lock() */
guard = Nova_Mutex_method_lock((_at_ch->mutex));
...
if (_defer_1_0_active) {
    ...
    Nova_MutexGuard_consume_cleanup(_at_ch, _nv_tmp_1207);   // <-- ЧУЖОЙ УКАЗАТЕЛЬ
    ...
}
```

Та же сборка с `--no-field-cache` не хойстит `_at_ch` вообще и корректно
эмитит `Nova_MutexGuard_consume_cleanup(guard, …)` во ВСЕХ трёх диспетч-сайтах
(FAIL/INTERRUPT/LEAVE). Также в fc-OFF-версии присутствуют ДВЕ строки
`_defer_1_0_active = 0;  /* Plan 217: consuming-вызов (receiver) — cleanup
дизармлен */` перед `Nova_MutexGuard_consume_unlock(guard)` — В fc-ON-версии
ЭТИ ДВЕ СТРОКИ ОТСУТСТВУЮТ ЦЕЛИКОМ (не просто другие — их НЕТ). Это два
СИМПТОМА ОДНОЙ причины (см. ниже), не два независимых бага.

### Корень (найден чтением исходников, не гаданием)

`compiler-codegen/src/field_cache.rs:3040`:

```rust
if region_first_span.is_none() {
    region_first_span = Some(stmt_span(s).unwrap_or(body_span));
}
```

`stmt_span` (line 3088) для `Stmt::Let(d) => d.span` — то есть **span ВСЕГО
statement**, где встретилось первое повторное обращение к полю. Если это
обращение внутри `consume guard = @ch.mutex.lock()` — `region_first_span`
СТАНОВИТСЯ РАВЕН `decl.span` ЭТОГО consume-léta.

`field_cache.rs:5169` (`build_at_field_let`, синтез hoist-létа) и его
братья-конструкторы `make_hoist_let` (6145), обе версии chain-prefix-sharing
(8954/8981) — **ВСЕ** (грепом подтверждено) конструируют
`Stmt::Let(LetDecl { ..., span: <переданный first_span>, consume: false, ... })`
— то есть НОВЫЙ, синтетический statement `Nova_Chan* _at_ch = @ch;` получает
**ТОТ ЖЕ САМЫЙ `Span`**, что и оригинальный `consume guard = …` — и вставляется
(`prefix_stmts.append(&mut b.stmts)`) ПЕРЕД ним.

`compiler-codegen/src/codegen/emit_c.rs` (Plan 217, ДО фикса), `enter_defer_scope`'s
пролог регистрирует `auto_cleanup_arm_sites.insert(decl.span, …)` для РЕАЛЬНОГО
consume-léta (корректно — фильтрует по `decl.consume`, см. `auto_cleanup_qualifies`).
НО `emit_stmt`'s диспетчер (строка ~30766, ДО фикса):

```rust
Stmt::Let(decl) if self.auto_cleanup_arm_sites.contains_key(&decl.span) => Some(decl.span),
```

проверяет ТОЛЬКО присутствие span в ключах — **без проверки `decl.consume`**.
Поскольку хойст-statement (`_at_ch = @ch`, `consume: false`) стоит ПЕРВЫМ и
несёт ТОТ ЖЕ span, что и зарегистрированный ключ — `emit_stmt` МАТЧИТ НА
ХОЙСТ-STATEMENT ПЕРВЫМ. Вызывается `emit_auto_cleanup_arm(hoist_decl, span)`:

```rust
let binding = self.pattern_binding(&decl.pattern)?;  // = "_at_ch" (не "guard"!)
...
policy.c_binding = c_binding_arg;  // патчится на "_at_ch"
self.auto_cleanup_active.push((binding, block_id, idx));  // регистрируется "_at_ch"
```

`auto_cleanup_arm_sites.remove(&span)` — **consuming** lookup: ключ УЖЕ ИЗЪЯТ.
Когда `emit_stmt` позже доходит до РЕАЛЬНОГО `consume guard = …` (тот же span!),
`contains_key` возвращает `false` — арм-сайт для `guard` НИКОГДА не срабатывает
по-настоящему.

Отсюда — ОДНА причина, ДВА видимых следствия:
- **(a) мискомпиляция-указатель**: диспетч auto-cleanup на выходе из функции
  читает `policy.c_binding` = `"_at_ch"` → `Nova_MutexGuard_consume_cleanup(_at_ch, …)`.
- **(b) «второй слой» (не отдельный баг, а то же самое)**: `guard.unlock()`'s
  disarm-механизм (`disarm_auto_cleanup_receiver_call`, ищет имя в
  `auto_cleanup_active`) никогда не находит `"guard"` (там записано только
  `"_at_ch"`) — флаг `_defer_1_0_active` никогда не снимается явным вызовом →
  cleanup срабатывает ПОВТОРНО (или, при отсутствии explicit-unlock вовсе,
  один раз — но всё равно через чужой указатель).

### Фикс

`compiler-codegen/src/codegen/emit_c.rs`, `emit_stmt` (было ~30766):

```diff
-Stmt::Let(decl) if self.auto_cleanup_arm_sites.contains_key(&decl.span) => Some(decl.span),
+Stmt::Let(decl) if decl.consume && self.auto_cleanup_arm_sites.contains_key(&decl.span) => Some(decl.span),
```

`decl.consume` истинен ТОЛЬКО для настоящего Plan-217 арм-сайта (тот же
инвариант, что уже используется прологом `enter_defer_scope`/
`auto_cleanup_qualifies`); ложно для ВСЕХ хойст-létов field-cache (грепом
подтверждено — `consume: false` во всех 5 конструкторах). Один булев guard,
без изменения структуры/типов данных, без правки чекера (материя не типовая
— identity двух AST-проходов).

## Шаг 3 — второй слой отдельно (закрыт, не молчком)

«Явный `unlock()` не снимает флаг» — НЕ отдельный дефект, это ТА ЖЕ причина
(см. выше, следствие (b)). Фикс шага 2 закрывает ОБА следствия ОДНИМ
изменением — подтверждено эмпирически (см. приёмку ниже: паника
`D188-on-exit-double-invocation` пропадает вместе с мискомпиляцией-указателем).

Отдельно, НЕ в объёме этого окна и НЕ трогается: №411 (D446 guard-liveness не
понимает `defer`) — самостоятельный, уже зарегистрированный дефект
(221.1-bug-sweep), докладывался окном p244 как ПРИЧИНА, по которой обход
внутри `nvchan.nv` вообще перешёл на explicit non-defer `unlock()` (что и
обнажило №409). №409 и №411 связаны исторически (одно привело к другому в
расследовании p244), но это два разных места фикса — №411 про
`fiber_safety.rs`, №409 про `emit_c.rs`/`field_cache.rs`. Не трогал
`fiber_safety.rs` в этом окне.

### 5. Размер `emit_c`

Фикс — один добавленный булев guard (`decl.consume &&`) в условии одного
`match`-плеча. Структурно НЕ добавляет/убирает эмитируемые C-операторы для
ПРАВИЛЬНОГО (не коллизирующего) кода — просто МЕНЯЕТ, КАКОЙ `Stmt::Let`
получает вызов `emit_auto_cleanup_arm` (с хойст-statement на реальный
consume-let), при этом `emit_auto_cleanup_arm` вызывается **ровно столько
же раз** (0 или 1 на арм-сайт) что и раньше — просто на правильном узле.
Для НЕ-коллизирующего (подавляющее большинство) кода `decl.consume` истинен
уже на первом (единственном) матче — ноль изменений в выводе. Ожидаемое
изменение размера сгенерированного `.c` для `std/src`/`examples/` в целом:
**0 (byte-identical)** — не перепроверялось построчным diff всего корпуса
(вне CPU-дисциплины окна), но структурная причина изменения C-вывода
(коллизия span) специфична ИМЕННО для функций с `consume`-létом внутри
region-0 совместно с полем, хойстящимся field-cache в POINTER-форме — редкая
комбинация, не встречающаяся в текущем `std/src`/`examples/` (в `nvchan.nv`
она есть, но там уже стоит обход `mut ch = @ch`, который сам по себе
исключает field-cache-хойст независимо от этого фикса). Если ratchet
всё-таки увидит расхождение — оно будет положительным (баг убирает
некорректно засчитанный лишний/отсутствующий emit) и подлежит поднятию
интегратором, как и оговорено в брифе.

## Побочная находка (докладывается, не в объёме фикса)

**Content-addressed build cache (`nova-cli/src/build_cache.rs`, Plan 81 Ф.9)
не включает field-cache флаги/env-переменные (`--no-field-cache`,
`NOVA_FIELD_CACHE*`) в свой ключ (`compute_c_key`).** Переключение
`--no-field-cache` БЕЗ изменения исходников молча отдаёт СТАРЫЙ
закэшированный `.c`, собранный с ДРУГИМ значением флага — что несколько раз
вводило в заблуждение в процессе диагностики этого окна (казалось, что `.c`
идентичен между fc-ВКЛ/fc-ВЫКЛ, пока не была обнаружена причина: кэш-хит).
`nova test` (test_runner.rs) этой проблеме НЕ подвержен (не использует
`build_cache`, честно перечитывает env на каждый прогон) — только
`nova build`. Не мискомпиляция рантайма, но подрывает доверие к
`nova build`-based bisection любого поведения, управляемого CLI-флагом/env
var, если КЛЮЧ кэша эти сигналы не учитывает. Номер не присваивался (не в
объёме этого окна — фикс НЕ трогает `build_cache.rs`), докладывается
интегратору для присвоения №TBD и отдельного окна при желании.
