## Дизайн-записка: где именно схлопывается ключ и почему

`mono_method_decls` (`compiler-codegen/src/codegen/emit_c.rs`, `HashMap<(String,
String), FnDecl>`, ключ = (receiver-typevar-буква, имя метода)) сам по себе
НЕ ломается: два бланкета §254 —

- direct: `export fn[I Next[T]] I mut @collect() -> Vec[T]` — ключ `("I", "collect")`
- delegate: `export fn[C Iter[I], I Next[T]] C @collect() -> Vec[T]` — ключ `("C", "collect")`

(`std/src/collections/vec_iter/core.nv`, строки 613 и 771; то же для
`reduce`/`min`/`max`) — регистрируются под РАЗНЫМИ ключами, коллизий при
вставке нет (см. уже существующий `mono_method_registry.rs` — тот страж от
№129 ловит коллизию ТОЛЬКО при совпадении ключа целиком, здесь ключи не
совпадают, страж молчит заслуженно).

Схлопывание — в ПОТРЕБИТЕЛЕ этого реестра, а не в самом реестре:
`infer_call_ret_c` (`emit_c.rs`, функция ~57151-59647), ветка B08 «blanket
protocol-receiver fallback» (было ~57829-57844 до правки). Для звонка вида
`recv.collect()`, когда `recv`'s конкретный C-тип не находится через
`method_overloads`/`generic_type_instance_info` (обычный путь для НЕсвоих
методов), код сканировал `mono_method_decls` в поисках ЛЮБОГО бланкета с
подходящим ИМЕНЕМ метода:

```rust
let blanket_fd = self.mono_method_decls.iter()
    .find(|((tvname, mname), fd)| {
        mname == mn_ref && tvname.len() <= 2
        && tvname.chars().all(|c| c.is_ascii_uppercase())
        && !fd.generics.is_empty()
        && fd.generics.iter().any(|g| !g.bounds.is_empty())
    })
    .map(|((tvname, _), fd)| (tvname.clone(), fd.clone()));
```

`.find()` на `HashMap::iter()` — ПЕРВОЕ совпадение по ХЭШ-порядку (не порядку
вставки), т.е. буквально монетка, которая переворачивается в зависимости от
состава/размера CU (хэш-таблица меняет внутреннюю раскладку с ростом числа
записей — отсюда порог по объёму: std/147 файлов держится, polaris/~40 и
conformance/636 — ловят). Кандидат НЕ проверялся на то, удовлетворяет ли ЕГО
protocol-bound конкретному ресиверу — просто первый попавшийся с тем же
именем метода. Если для ресивера, который сам реализует `Next[T]` напрямую
(например, `KeysIter[str, V]` — реализует `Next[str]`, никогда не
`Iter[Self]`), хэш-порядок выдавал СНАЧАЛА `("C", "collect")` (delegate), код
пытался связать `T` через `Iter[I]`-бáунд (`@iter()` на ресивере, которого у
`KeysIter` просто нет) — biind проваливался, `T` молча стирался в дефолт
`nova_int` (тот же erasure-путь, что существовал ДО дизайна №254 для
неизвестного `T`). Результат — `let keys Vec[nova_int]* = <call
KeysIter_str_collect>(...)`: тип переменной объявлен неверно, при этом сам
вызов кодогенился под правильным именем (`..._KeysIter____nova_str..._collect`)
— несовпадение всплывало НИЖЕ по потоку, когда `keys`-элемент (`nova_int`)
передавался туда, где ждали `nova_str` → CC-FAIL «passing nova_int to
nova_str». Живой репро — `nova-polaris/src/auth_test.nv:189`,
`JsonValue.static_object`: `fields.keys().collect()` → `HashMap[str,
JsonValue].get(fields, k)` c `k` неверно типизированным как `nova_int`.

Диспетч РЕАЛЬНОГО вызова (кодоген самого C-вызова, `emit_c.rs` ~43633-43809,
Plan 164 Ф.3) уже умел это правильно — там кандидаты собираются ВСЕ и
проверяются `protocols_match` против `type_impl_protocols`. B08
(«инференс типа для объявления переменной») этот же алгоритм не повторял —
отсюда расхождение: реальный C-вызов эмитился под верной, специфичной
инстанцией, а ДЕКЛАРАЦИЯ переменной (нужна раньше, для generic-type-arg
resolution) типизировалась по случайно выбранному, часто неверному бланкету.

## Фикс (чекер-канал / фаза мономорфизации, НЕ легаси-разрастание)

`emit_c.rs`, B08: заменил слепой `.find()` на:
1. Собрать ВСЕ синтаксически подходящие кандидаты (та же фильтрация).
2. Отсортировать: небáунд-`Iter` (т.е. `Next`-подобные) — первыми
   (зеркалирует уже существующий codegen-приоритет диспетча, ~43744, тот же
   принцип специфичности дизайна №254 п.2 — «свой Next[T] бьёт делегат»).
3. Взять ПЕРВОГО кандидата, чей protocol-bound реально удовлетворяется
   `type_impl_protocols` конкретного ресивера (по БАЗОВОМУ имени типа, без
   mono-суффикса `____...` — то же, что делает диспетч-сторона).
4. Если НИ ОДИН кандидат не проходит protocol-check (ресивер без записи в
   реестре вовсе — примитивы/opaque mono-типы) — fallback на старое
   поведение (первый найденный), чтобы не регрессировать случаи вне периметра
   этого класса бага.

Реестр `mono_method_decls` не тронут — правка ТОЛЬКО в потребителе
(`infer_call_ret_c`), т.е. в фазе резолва типа возврата генерик-вызова, не в
легаси emit-разрастании нового рода: код мимикрирует УЖЕ существующий
codegen-паттерн (`protocols_match`, ~43764-43781), не изобретает новый канал.
