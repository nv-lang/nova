Гейт (`scripts/gate.sh`, шаг «flagship aggregator --strict-effects», команда

### Механизм (найден прямым чтением + эмпирическим A/B, не гипотеза)

`examples/nova.toml` объявляет `tls` как git-зависимость с версионным
диапазоном:
```
[dependencies]
tls = { git = "https://github.com/nv-lang/nova-tls", version = "0.1" }
```
Зафиксированная версия лежит в **закоммиченном** `examples/nova.lock.toml`:
```
[[package]]
name = "tls"
pin = "version:>=0.1.0, <0.2.0"
version = "0.1.3"
commit = "910e14be86c3690f4b5ddd1d30d365437336f910"
```
Этот commit (тег `v0.1.3` nova-tls) **предшествует** переименованию метода
`read_to_vec` → `read_bytes` (nova-tls commit `3003b64...`, решение владельца
2026-08-01, тег `v0.1.5` — подтверждено `git ls-remote --tags origin` на
`d:/Sources/nv-lang/nova-tls`: `v0.1.3^{} = 910e14be...`, `v0.1.5^{} =
3003b64...`). То есть **на удалённом репозитории УЖЕ есть подходящий по
диапазону `>=0.1.0,<0.2.0` более новый тег (`v0.1.5`) с новым API**, но
`nova.lock.toml` его не подхватил (никто не гонял `nova update tls` после
переименования).

Тем временем `examples/flagship/aggregator/src/app/live.nv:95` и
`nova-polaris/src/net/servernet_tls.nv:114,126` **уже вызывают новое имя**
`stream.read_bytes(...)` — то есть закоммиченные исходники и закоммиченный
lock рассинхронизированы: честная сборка по локу обязана падать.

Главный репозиторий владельца (`d:/Sources/nv-lang/nova`, НЕ worktree) несёt
файл `examples/nova.override.toml` — **gitignored** (`.gitignore:52-53`),
никогда не коммитится, существует только как персистентный локальный файл на
диске главного чекаута:
```
[replace]
tls = { path = "../../nova-tls" }
http = { path = "../../nova-http" }
polaris = { path = "../../nova-polaris" }
compress = { path = "../../nova-compress" }
```
`[replace]` (D420, `imports.rs::lookup_dependency`) **обходит `nova.lock.toml`
целиком** и резолвит `tls` напрямую в живую рабочую копию
`d:/Sources/nv-lang/nova-tls` — которая у владельца всегда актуальна (сейчас
на `9fed100`, далеко за переименованием). Из-за этого сборка флагмана **с
главного репо всегда видит `read_bytes`**, даже когда закоммиченный лок его
не содержит.

Любое дерево БЕЗ этого persistent-локального файла — свежий `git worktree
add`, свежий `git clone`, CI-раннер — резолвит `tls` строго по
`nova.lock.toml`, получает commit `910e14be` (ДО переименования) и падает.

### Условия, при которых зелёное — ложно (для перепроверки сегодняшних приёмок)

Гейт лжёт зелёным ТОЧНО когда одновременно выполняются:
1. Гейт запущен из дерева, где физически лежит `nova.override.toml` (или
   `nova.local.toml`, тот же механизм) с `[replace]` на пакет, чья текущая
   рабочая копия (sibling-репозиторий) РАСХОДИТСЯ с тем, что зафиксировано в
   `nova.lock.toml` этого дерева;
2. Дерево, на которое ссылается override, содержит фикс/фичу/переименование,
   ЕЩЁ НЕ отражённое обновлением `nova.lock.toml` (никто не прогнал `nova
   update <pkg>` после локального изменения в sibling-репо).

**Практическое следствие для сегодняшних пяти приёмок:** если хоть одна из
них трогала `nova-tls`/`nova-http`/`nova-polaris`/`nova-compress` (все четыре
перечислены в `examples/nova.override.toml`) и гейт гонялся с главного репо
(а не со свежего дерева) — «built:» мог быть правдой ТОЛЬКО для локальной
копии владельца, не для `nova.lock.toml`, который реально коммитится и
достаётся любому третьему потребителю пакета. Автоматически определить,
какие из пяти волн задели эти пакеты, не входило в периметр этого окна
(периметр — `nova-cli`/раннер); нужен точечный `git log` по нужным окнам.

**Способ воспроизведения (для перепроверки в любой момент):**
```sh
# в любом дереве без nova.override.toml (или временно переименовав его):
NOVA_GC_LIB_DIR=... NOVA_INCLUDE_DIR=... \
  ./nova-cli/target/release/nova.exe build \
  examples/flagship/aggregator/src/main.nv --strict-effects
# ожидаемо: E7320 no field or method `read_bytes` on type `TlsStream`
# (3 сайта: aggregator/live.nv + 2× nova-polaris/servernet_tls.nv)
```
Не флейк: причина — присутствие/отсутствие конкретного файла на диске,
воспроизводится 100% раз за разом, пока состояние файла не меняется.

`examples/nova.lock.toml` в момент установления факта НЕ обновлялся (откат

  на время гейта прячут руками» (`mv nova.override.toml nova.override.toml.bak`

- Дефект был не в СУЩЕСТВОВАНИИ override, а в его МОЛЧАНИИ: `built:` и

  чинить нужно именно видимость.

## ЧАСТЬ 3 — записка: свести `cmd_build` и `test_runner` к одному конвейеру

### Масштаб проблемы, подтверждённый ЭТИМ окном, а не только брифом

За одну сессию, сверяя байт-в-байт всего ОДНУ фикстуру, найдено ДВА
независимых примера класса «`cmd_build` забыл вызов, который есть в
`test_runner.rs`» (field_cache — №304; `set_source_file_name` — побочная
находка выше). Сам код `cmd_build` уже несёт комментарии-шрамы от ТРЁХ
предыдущих инцидентов ТОГО ЖЕ класса, найденных до этого окна (видно
прямо в `nova-cli/src/main.rs` рядом с местом вставки):
- auto-derive-inject (bugfix A-Q3, 2026-07-21) — `cmd_build` не звал
  `inject_synthesized_methods`, `${p:?}` печатал сырой указатель.
- REAL `resolved_types` для `chain_norm` (Plan 184 Р7, «defect-B») —
  value-root guard был мёртв на `nova build`.
- `build_source_map`/`render_with_map` (`[M-diag-dep-file-span-misattribution]`)
  — диагностика зависимости указывала на entry-файл вместо реального.

Итого — **пять независимых, по одному находимых дефектов ОДНОГО класса**
за историю проекта, включая два из этой самой сессии. Находки идут
регулярно, каждая — отдельным патчем «на месте», потому что структурной
защиты от расхождения нет.

### Почему это не разовая заплатка, а системный риск

`cmd_build` (`nova-cli/src/main.rs`, ~250 строк одной функции) и
`test_runner.rs::run_one` (`compiler-codegen/src/test_runner.rs`) —
ДВЕ НЕЗАВИСИМЫЕ, вручную поддерживаемые копии одного и того же
19-шагового конвейера (resolve-imports → alpha-rename → build-cache-key
→ type-check → self-return-lower → effects-infer → lints →
auto-derive-inject → annotate-maps → desugar → callnorm → chain_norm →
field-cache → post-normalize-annotate → codegen). Каждый новый шаг
конвейера (а их становится больше почти с каждым языковым планом)
обязан быть вписан РУКАМИ в оба места; ничего не роняет сборку и не
пишет warning, если один из двух это пропустит — расхождение молчит,
пока кто-то не найдёт его byte-diff'ом (ровно то, что произошло пять
раз).

### Что мешает свести к одному конвейеру (структурная оценка, не план работ)

1. **Разная форма входа.** `cmd_build` работает с ОДНИМ файлом (единственный
   `path: &Path`, `nova build <FILE>`), `test_runner.rs` — с батчем файлов/
   каталогом + параллелизмом по воркерам (`--jobs`), плюс различает
   `test`/`test-build`/бенч-режимы через общий `run_one`, вызываемый из
   нескольких мест. Общая функция должна принять оба режима входа, не
   потеряв параллелизм теста.
2. **Разные пост-обработки после общего "ядра".** После codegen пути
   расходятся по-настоящему: `cmd_build` пишет один `.exe` и завершается;
   `test_runner.rs` запускает тесты, собирает PASS/FAIL/SKIP статистику,
   поддерживает мега-CU (весь `spec_tests/conformance` ОДНИМ CU — форма
   входа, которую `cmd_build` вообще не знает). Слияние обязано остановиться
   ДО этой развилки, не после.
3. **build_cache (Plan 81 Ф.9) сегодня знает только `cmd_build`.**
   `test_runner.rs` его не использует (у неё свой мотив — CU переиспользуется
   целиком через параллельные воркеры, не через content-addressed кэш
   отдельных сборок). Общее ядро должно решить, кэш общий или
   `build`-специфичный слой поверх общего ядра.
4. **Владелец состояния — `Module`, мутируемый ПОСЛЕДОВАТЕЛЬНО 14 проходами
   в обеих копиях.** Сведение — не «извлечь функцию», а «выбрать ОДНУ
   функцию-конвейер, принимающую `&mut Module` + конфиг (что запускать),
   возвращающую всё, что нужно ОБОИМ потребителям (`ModuleEnv`,
   `EmitOutput`, warnings)» — сигнатура должна устроить и `nova build`,
   и `nova test`, и `nova bench`, и `nova check --explain-cache`
   (диагностический родственник, тоже частично дублирующий кусок этого же
   конвейера — см. `cmd_check_explain_cache` в этом же файле).
5. **Периметр правки — оба крейта.** `nova-cli` (потребитель) и
   `compiler-codegen` (где физически живёт `test_runner::run_one` и куда,
   видимо, должно переехать общее ядро, раз `cmd_build` и так почти целиком
   зовёт `nova_codegen::*`). Это МЕЖкрейтовая работа, не однофайловая.

### Оценка стоимости (порядок величины, не оценка часов)

Не «переписать один файл» — **выделить общую функцию-конвейер** (сигнатура
по п.4 выше) в `compiler-codegen` (вероятно новый модуль, например
`pipeline.rs`, либо расширение `test_runner.rs`'s `run_one` с параметром
"что делать после codegen"), **перевести оба вызывающих сайта** на неё
(`cmd_build` в `nova-cli/main.rs`, `run_one` в `test_runner.rs`), **и
поставить гейт регресса** — byte-identity тест (метод этого окна: одна
фикстура, две сборки, диф `.c`) как ПОСТОЯННЫЙ, не разовый, чтобы шестой
инцидент этого класса ловился автоматически, а не следующим ручным
аудитом. Риск — не в объёме кода (конвейер уже ЛОГИЧЕСКИ идентичен, судя
по коммитам-зеркалам последних месяцев), а в тестовом покрытии: слияние
обязано пройти ПОЛНЫЙ мега-CU + флагман + `nova bench` без регрессий,
потому что это меняет код, через который проходит КАЖДАЯ Nova-программа
без исключения — максимальный blast radius в проекте.

### Рекомендация (не решение — решает владелец)

Ввести byte-identity гейт (как в этом окне, но постоянный: скрипт,
СРАВНИВАЮЩИЙ `.c` от `nova build --keep-artifacts` и `nova test-build
--keep-artifacts` на фиксированном наборе фикстур, ассертящий diff = 0
по не-косметическим строкам) — ДО слияния конвейеров, как немедленная,
дешёвая защита от шестого инцидента. Само слияние — отдельный план,
велик по blast radius, не тянет на «побочный фикс».
