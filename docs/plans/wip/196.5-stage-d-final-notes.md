## 1. Дизайн-выбор (разведка, задание п.1)

**Вопрос задания:** канал-запись per `(ExprId, instance)` ЛИБО прямая замена
входа ядро-веток композицией (Stage-C2-стиль)?

**Находка по коду (не по премисе):** этот выбор УЖЕ был сделан и реализован
предыдущей волной (документ `196.5-node-substs-channel.md` §W1.4-W1.5,
вариант (ii) "POST-mono emit-side резолвер" — рекомендован явно, вариант (i)
per-instance-канал и (iii) checker residual-канал отклонены явно с
обоснованием "0/6 покрытие, канал вырождается в мемо-кэш реконструкции").
Верификация по коду `resolve_instance_call_subst` (`emit_c.rs:20243`+)
подтвердила: резолвер РЕАЛЬНО существует, читает `current_type_subst`
(post-mono, установленный mono-обёрткой) + структурные реестры
(`generic_type_instance_info`/`generic_type_templates`/`generic_type_methods`)
+ arg/closure-return для method-level generics. Использован в B05 (`48887`),
B06a (`48920`), B07/B07r (`49048`) — ровно очередь W1-i.B из плана
("B07→B07r→B06→B11c→B05→B11x").

**Вывод разведки:** канал `node_substs` (checker-side, per bare `ExprId`)
СТРУКТУРНО не может покрыть эти сайты (RESUME-4: 850/850 `node_substs.get(&expr.id)
= NONE` — residual по построению, §7-гейт). Правильный "канал" per-instance —
именно POST-mono композиция через `current_type_subst`, что и реализовано.
Никакого нового design-решения эта волна не принимала — верифицировала
существующее и нашла в нём дыру (см. §2).

## 2. Найденная и починенная регрессия — `resolve_instance_call_subst` турбофиш-слепота

`resolve_instance_call_subst` собирает subst из (1) carrier-bind по конкретному
ресиверу-инстансу и (2) method-level bind из args/closure-return — но НЕ читал
explicit turbofish (`obj.method[T](...)`). Для метода, чей type-param стоит
ТОЛЬКО в return-позиции и вызван БЕЗ args/closures (`fn Res consume @into[T]()
-> Option[T]`, вызов `r.into[str]()`), turbofish — ЕДИНСТВЕННЫЙ источник T.
Это ровно исходный m176-фикс (`[M-codegen-method-return-turbofish]`, CLOSED
2026-07-06) — но при W1-i.B флипе (замена рукописной subst-реконструкции на
`resolve_instance_call_subst`) turbofish-seeding из фикса НЕ перенесли.

**Репро:** `nova_tests/plan176_holes/m176_method_return_turbofish.nv` —
CC-FAIL на базе `729e4b3bb` (`passing 'void' to parameter of incompatible type
'nova_str'`), не пойман 4-корпусным замером волн (conformance+collections+
data+net не содержат эту форму — "method-level generic только в return, 0
args, explicit turbofish").

**Фикс** (`emit_c.rs`, коммит `e16c0c8db`): `resolve_instance_call_subst`
получил `turbofish_args: &[TypeRef]` (уже извлекается вызывающим
`infer_call_ret_c` в самом начале функции для ЛЮБОЙ формы вызова — `TurboFish
{base:Member}` unwrap, существовало и раньше). Сидирует ещё-`None`
method-level слоты позиционно (порядок `callee.generics`) ПЕРЕД arg/closure-
выводом — тот же explicit-wins приоритет, что `resolve_method_level_subst`'s
`explicit_tf` (`infer_type_param_binding` никогда не перезаписывает занятый
слот, так что порядок сидирования = порядок приоритета). 4 call-site'а: 3
внутри `infer_call_ret_c` (B05/B06a/B07-B07r) получили `&turbofish_args`;
5-й (`infer_mono_method_ret_with_args`, chained-receiver dispatch, turbofish
вне скоупа) — `&[]`, byte-identical no-op.

Проверено: B10j (free-fn generic mono, отдельный код-путь, НЕ флипнутый на
`resolve_instance_call_subst`) уже сидирует из `turbofish_args` как Source 1
— регрессии там нет (флип затронул только method-уровневые арм'ы с
ресивером).
