# p238-f3 — Ф.8-НОВАЯ, фаза 3: автовывод требования безопасности параметра-замыкания

**Окно:** p238-f3, sonnet, ветка `p238-f3`, worktree `d:/Sources/nv-lang/nova-p238f3`.
**Задача:** план 238, финальная деталь — решение владельца 2026-08-06:
`#fiber_safe` (принят фазой 2 как явная пометка) не решает проблему в
одиночку — «умолчание без пометки — большая дыра, редкий пользователь
вспомнит». Целевая схема: требование параметра функционального типа
рассчитывается КОМПИЛЯТОРОМ автоматически (вывод из тела + проверка в
точке передачи), `#fiber_safe` остаётся ТОЛЬКО для границ, куда вывод не
может заглянуть (extern/no-body). Отчёты фаз 1-2:
`docs/plans/wip/PROGRESS-p238-f1.md`, `PROGRESS-p238-f2.md`.

## 1. Устройство вывода

Весь механизм — `compiler-codegen/src/types/fiber_safety.rs`, новая секция
«Plan 238 Ф.3» в конце файла (~700 строк), плюс точечные правки в уже
существующих Ф.1/Ф.2 функциях (см. §3).

### 1.1 Два правила, одна неподвижная точка

`compute_required_params(module, resolved_callees) -> RequiredParams`
вычисляет, для каждой пары `(fn Span, индекс параметра)`, требуется ли
Safe-замыкание, по двум правилам:

1. **Правило 1 (прямое).** Параметр `p` функции `F` требует, если тело `F`
   вызывает `p()` голым именем ГДЕ-ЛИБО внутри `spawn`/`detach`/
   `parallel for`, реализованных синтаксически в теле САМОЙ `F` (любая
   глубина вложенности, включая вложенные замыкания, написанные там же —
   `rp_walk_expr` с флагом `in_fiber`, взводится входом в
   `Spawn`/`Detach`/`ParallelFor`, НЕ взводится `Blocking` — та же
   позиция, что уже занимает `find_seeds_expr`: `Blocking` не сеет новый
   файбер).
2. **Правило 2 (транзитивное).** Если `F` передаёт СВОЙ параметр `p`,
   БЕЗ ИЗМЕНЕНИЙ (голым идентификатором — та же дисциплина, что
   `compute_guarded_params`/`arg_root_safe` уже применяют по всему файлу),
   аргументом в позицию параметра ДРУГОЙ, локально резолвящейся функции
   `G`, и параметр `G` в этой позиции сам требует (по правилу 1 или
   транзитивно) — параметр `F` требует тоже. Это ровно пример владельца:
   `middleware(f)` зовёт `helper(f)`, `helper` зовёт `g()` в своём
   `spawn` → `g` требует по правилу 1, `f` требует по правилу 2.

Обе части — ОДНА неподвижная точка (`forward_edges`, `while changed`-цикл,
зеркалит `run`'а собственный fixed point дословно — та же «пропагировать
по графу, пока не устаканится» форма, НОВАЯ ось: «требует ли параметр»,
а не «безопасна ли функция»). `ReqReason` (`Direct`/`ExplicitAttr`/
`Forward(Span,usize)`) хранит происхождение для обратной цепочки
(`RequiredParams::render_chain`, Ш.7-твин `render_chain`'а Ф.1/Ф.2).

### 1.2 `#fiber_safe`

Параметр-атрибут, парсится контекстно после `#` ровно как `#cancel_safe`
(`parser/mod.rs::parse_fiber_safe_attr`, образец — `parse_cancel_safe_attr`
дословно, тот же приём). Новое поле `Param.fiber_safe_attr: bool`
(`ast/mod.rs`) — потребовало починки 5 синтетических мест конструирования
`Param{..}` (`may_gc.rs`, `const_fn_closure.rs` ×2, `auto_derive.rs` ×2) —
никакого `Default`-деривации у `Param` не было, все явные литералы.
Принимается СИНТАКСИЧЕСКИ на любом параметре (парсер не спрашивает,
функционален ли тип или есть ли тело) — СМЫСЛ имеет только там, где вывод
не сработал: `compute_required_params` добавляет `#fiber_safe`-помеченные
параметры функционального типа в базовый набор БЕЗУСЛОВНО, независимо от
того, есть ли у функции тело — на функции С телом это строго
консервативный no-op («требует больше, никогда не меньше»).

В корпусе (`std`/`nova-polaris`) сегодня НЕТ ни одного extern/no-body
fn с параметром функционального типа (измерено — иначе `fn_param_in_sig`
на нём проявился бы раньше как отдельный класс) — фикстуры §4 синтетические,
как и предполагал бриф.

### 1.3 Проверка в точке ПЕРЕДАЧИ — `check_param_passing`, `E_FIBER_UNSAFE_ARG`

НЕ там, где требующий параметр вызывается (там теперь тихо — см. §3), а
на КАЖДОМ call-site во ВСЁМ модуле (не только внутри `spawn` — риск
кристаллизуется в момент передачи, замыкание может быть вызвано глубоко
внутри callee, необязательно синтаксически рядом с файбер-границей),
где аргумент попадает в требующую позицию:

- Аргумент резолвится в замыкание-литерал напрямую, ИЛИ через ОДИН шаг
  `let name = <литерал>` в той же функции (`resolve_arg_closure` +
  `collect_closure_lets`) — «захваты видны» ровно в этом объёме, дальше
  (значение из другой функции, из контейнера, из поля) декларируется НЕ
  прослеживаемым этим механизмом — молчаливо остаётся на прежних
  (индиректных/флаговых) путях.
- Бирка замыкания (`closure_own_facts`) считается ТЕМ ЖЕ проходом Пасса B
  (`pb_walk_closure_body`, переиспользован буквально), но с `mut_params`,
  РАСШИРЕННЫМ до `collect_capturable_mut` — mut-ПАРАМЕТРЫ **и**
  mut-ЛОКАЛЫ охватывающей функции (не только параметры: локальный
  аккумулятор, захваченный ЗАМЫКАНИЕМ и переданный дальше, эскейпит по
  построению факта захвата — не тот же случай, что «локальный
  аккумулятор, который эта функция сама никуда не передаёт», ради
  которого Ф.1 объявляет локалы нетронутыми). Каждый найденный touch
  ПРИНУДИТЕЛЬНО помечается `is_self=true` постфактум — захват ЛЮБОГО
  охватывающего mut-имени в замыкании, уходящем через границу, это
  ДОКАЗАННЫЙ класс (как self-поле), не мягкий «может, это свежий буфер»
  класс обычного mut-параметра.
- `tag_from_facts_and_callees` — новый маленький helper, вычисляет тег из
  `FnFacts` + уже устоявшейся карты `tags` (карта Ф.1, `run()` уже
  завершён к этому моменту) — концептуально та же «взять худшее среди
  локальных callee'ов», что `run`'а собственный fixed-point loop, НЕ
  рефакторено в общий код (риск трогать протестированный loop ради
  постороннего изменения — сознательно оставлено дублирование, тот же
  прецедент, что `typeref_named_base`/`callee_bare_name` в этом файле).
- `Safe` — тихо; иначе `E_FIBER_UNSAFE_ARG`, ДВЕ цепочки в тексте:
  «почему параметр требует» (`RequiredParams::render_chain`, НОВАЯ) и,
  если небезопасность самого замыкания сама транзитивна
  (`calls_unsafe`/`calls_undecided`), «собственная цепочка причины
  замыкания» (существующий `render_chain` Ф.1/Ф.2, переиспользован).

### 1.4 Умолчание безопасно в обе стороны (П.3 брифа)

Не выведено (и не помечено `#fiber_safe`) ⇒ `RequiredParams::is_required`
никогда не `true` ⇒ `check_param_passing` не создаёт НИ ОДНОЙ диагностики
для этого параметра, ни на одном call-site — не «забыли один сайт», а
структурно нечего проверять. Выведено (или помечено) ⇒ проверяется
БЕЗУСЛОВНО у ВСЕХ вызывающих во всём модуле — то же «нет памяти-по-месту»
свойство, ради которого весь Ф.1-Ф.3 придуман (П.1 «бирка тотальна» брифа
238, теперь и по этой оси).

### Почему остальные десять не закрылись — разобрано, не молчаливый провал

Ф.3 закрывает СТРОГО один периметр: замыкание пересекает границу как
АРГУМЕНТ вызова, в позицию параметра, который (транзитивно) требует.
Десять оставшихся проб пересекают границу ДРУГИМ путём:

- **p01, p05, p09** — замыкание УХОДИТ через `return` функции (плюс
  `Option`-обёртка у p05), затем вызывается там, где никакой параметр
  вообще не участвует — это ось «возврат», не «передача аргументом»,
  вне периметра И вывода, И проверки (задокументировано заранее в
  module-doc §"Enforcement" фазы 3 как известный предел — не находка
  постфактум).
- **p03** — замыкания собираются в ЛОКАЛЬНЫЙ `Vec[fn()->()]`, вызываются
  через `parallel for t in tasks { t() }` — `t` ЦИКЛОВАЯ переменная, не
  параметр НИКАКОЙ функции; структурно другой класс («вызов через элемент
  контейнера»), близкий к остатку §3, но не тождественный «полю» —
  честно новая, отдельно поименованная находка (см. §3 остатка).
- **p07, p11** — вызов через ПОЛЕ структуры функционального типа
  (`@hooks[0]`/`bus.hooks[0]`) — ровно `field_call_unresolved` (§3),
  остаётся под флагом ПО ИМЕНИ, как и предсказывал брифовый список
  остатка.
- **p08, p10, p10b, pC** — замыкание вызывается НАПРЯМУЮ внутри `spawn`
  (через локальное имя/каррирование/if-let-биндинг), НИКОГДА не проходя
  через вызов функции с параметром — здесь просто НЕТ call-site
  «передачи в требующий параметр», проверять нечего этим механизмом
  (это индиректный вызов классической формы D446 §4, который уже был и
  остаётся под флагом — не регрессия, не относится к периметру Ф.3).

## 3. Остаток под флагом (`NOVA_FIBER_INDIRECT`) — поимённо

1. **`field_call_unresolved`** (НОВЫЙ именованный reason, `Tag::Undecided`)
   — вызов через ПОЛЕ структуры функционального типа
   (`(@f)()`/`bus.hooks[0]()`), не резолвящийся в `Item::Fn` вообще —
   именно класс, который брифовый П.5 называет «вызовы через поля структур
   функционального типа». Обнаружен и зачинен В ЭТОМ ЖЕ окне как побочный
   эффект ретракции `fn_param_in_sig` (см. §5 «раунд регрессии») —
   раньше СЛУЧАЙНО маскировался блокет-Undecided'ом функций с
   fn-типизированными параметрами (не самим этим классом — совпадение
   путей, не намеренная защита).
2. **`unguarded_mut_param`** — touch на обычном `mut`-ПАРАМЕТРЕ (не `@`),
   недоказуемо ни в какую сторону из одной сигнатуры — БЕЗ ИЗМЕНЕНИЙ с
   Ф.2 (multi-hop `mut []T`-скретч-буфер класс, `nova-tls::flush_out`
   и аналоги).
3. **`cross_module_callee`** — БЕЗ ИЗМЕНЕНИЙ с Ф.1/Ф.2, компиляционная
   единица не видит тег за своей границей.
4. **Протокол-диспатч через generic bound** (`fn[T Write] w.write(..)`) —
   БЕЗ ИЗМЕНЕНИЙ, проявляется как `unguarded_mut_param`/`calls_undecided`.
5. **Истинно нерезолвленный (индиректный) вызов**, аргумент которого
   `check_param_passing` НЕ может проследить (не литерал и не один-хоповый
   `let`) — значение из контейнера (p03), из другой функции, из поля,
   через 2+ `let`-хопа. Измерено §2: 9 из 11 проб класса «молчит без
   флага» остаются здесь.
6. **Прямой вызов замыкания БЕЗ прохождения через параметр функции вообще**
   (p08/p10/p10b/pC) — локальная переменная/каррирование/if-let-биндинг,
   вызванные напрямую внутри `spawn` — структурно вне периметра «требование
   параметра» (нет параметра), классический D446 §4 индиректный вызов.

Пункты (5)/(6) — НЕ regressions и не открытые баги этого окна: это
предсказанная брифом граница («захваты видны» — ТОЛЬКО буквальный литерал
или один `let`-хоп) и естественный периметр «требование ПАРАМЕТРА», а не
«любое замыкание, вызванное где угодно внутри файбера».

## 5. Раунд регрессии — `field_call_unresolved` (найдено и зачинено в этом же окне)

Ретракция `fn_param_in_sig` из `signature_undecided_reason` (§1 брифа,
«fn_param_in_sig закрывается точной проверкой передачи») означает: функция
С параметром функционального типа больше НЕ блокет-Undecided только за
факт наличия параметра — её ТЕГ теперь считается Пассом B как у любой
другой функции (measured win: `Mutex.with_lock`/`RwLock.with_read`/
`with_write`/`Semaphore.with_permit` становятся `Tag::Safe` НАПРЯМУЮ,
а не Undecided — они сами ничего не трогают, только зовут параметр).

Первый прогон `nova check nova-polaris/src` дал **43 PASS / 12 FAIL**
(канон — 55/0). Разбор: `StreamBody { priv f fn() -> Option[[]u8] }`'s
`@next_chunk() => (@f)()` — вызов ЧЕРЕЗ ПОЛЕ функционального типа.
Пасса B's Call-arm СИНТАКСИЧЕСКИ не отличает «вызов через нерезолвленное
ПОЛЕ» от «вызов НЕРЕЗОЛВЛЕННОГО МЕТОДА» (оба — `Member{obj, name}`) и
раньше ВСЕГДА трактовал такую форму консервативно как `unguarded_mutation`
(`Tag::Unsafe`, ДОКАЗАННЫЙ класс) — `next_chunk` САМА не имеет
fn-типизированных параметров (fn_param_in_sig её не касался НАПРЯМУЮ), но
её вызывающие (`write_stream_chunks_keepalive` и аналоги) ИМЕЛИ, и раньше
блокет-Undecided на НИХ означал, что Пасс B для них вообще НЕ запускался
(`signature_undecided_reason` коротит ДО `analyze_fn_body`) — граф-ребро к
`next_chunk` никогда не записывалось, `Tag::Unsafe` у `next_chunk`
НИКОГДА не пропагировался вверх. После ретракции граф стал ПОЛНЫМ —
ранее скрытая ошибка классификации всплыла и потащила `serve_connection`
и цепочку вызывающих в `Tag::Unsafe`, enforced БЕЗУСЛОВНО (не по флагу).

**Фикс (не находка о коде — находка о классификаторе):** новый факт
`FnFacts::field_call_unresolved` + helper `field_call_is_func_type`
(структурная проверка: тип поля, ДЕКЛАРИРОВАННЫЙ на достигнутом типе,
сам функционален) — если вызов НЕ резолвится И имя — функционально-
типизированное поле, это D446 §4 «непрямой вызов» (`Tag::Undecided`),
НЕ доказанный touch. Проверено ДО старого консервативного
`_ => true`-умолчания в `pb_walk_expr`. `facts_to_intra` получил третью
терминальную ветку (после self-touch/mut-param-touch, перед
`cross_module_callee`).

**После фикса:** `nova check nova-polaris/src` (проверено на пришпиленном
снимке `d0fe9e8` — см. §6) — **55 PASS / 0 FAIL**, канон восстановлен.
`nova check std/src` — **148/26/61**, байт-в-байт не менявшееся ни ДО,
ни ПОСЛЕ этого фикса. Это ЕДИНСТВЕННАЯ правка компилятора, потребовавшаяся
поверх исходного плана — миграций КОРПУСА не понадобилось вообще (сам
`StreamBody`/`next_chunk` не тронуты).

## 5-bis. Второй раунд регрессии — untyped `mut`-локал в closure_own_facts

Полный (не выборочный) прогон `nova check spec_tests/conformance`
(единственным CU, свежесобранным `nova.exe`, после §5) обнаружил ЕЩЁ ОДИН
измеренный ложняк — на УЖЕ СУЩЕСТВУЮЩЕЙ, не моей, канонической
pos-фикстуре: `standalone/mut_capture_transitive_atomic_control_test.nv`
(Plan 238 Ф.6, репро C из ветки `p150-race-repro`) — собственное имя
файла ("control", "legal, exact count") ОБЕЩАЕТ, что этот код легален,
и до этого окна был легален.

**Причина.** `mut counter = AtomicInt.new(0)` — тип НЕ аннотирован явно
(идиоматичный Nova: тип выводится из RHS-конструктора). `collect_
capturable_mut`/`ccm_note_let` клали в `types`-карту тип ТОЛЬКО когда
`d.ty` явно написан в `let`; для этого (типичного!) untyped-случая
`touch_share_ok`'s `ctx.param_types.get("counter")` возвращал `None` →
`share_ok = false` БЕЗУСЛОВНО, даже для геную #share-типа — замыкание
`|| { counter.fetch_add(1) }`, легально закрывающееся на `AtomicInt`,
ложно получало `Tag::Unsafe`.

**Фикс (канал, не эвристика — §0/196):** `resolved_types_buf` (`HashMap<
ExprId, ResolvedType>`, ТОТ ЖЕ канал, которым весь чекер резолвит типы
выражений) заведён в `check_param_passing` рядом с `resolved_callees`
(тем же путём, что `types/mod.rs` уже прокидывает оба). `ccm_note_let`
для untyped `mut`-let смотрит `resolved_types.get(&d.value.id)`
(ExprId ПРАВОЙ части `let`), извлекает имя `ResolvedType::Named` (новый
маленький helper `resolved_type_named_ref`, зеркалит `touch_share_ok`'s
собственный синтетический `TypeRef::Named`-приём для `SelfBare`) и
кладёт в ту же карту. Threading (тот же скриптованный regex-приём, что
`own_param_names` в §3 — 4 функции семейства `ccm_walk_*`/`ccm_note_let`
получили новый параметр).

**Проверено:** `mut_capture_transitive_atomic_control_test.nv` — `ok:`
(было `E_FIBER_UNSAFE_ARG`). Двойник-негатив (та же форма, `Vec` вместо
`AtomicInt`, `neg/mut_capture_transitive_via_param_neg.nv`) — ПО-ПРЕЖНЕМУ
падает (двумя диагностиками, D415 + Ф.3, ожидаемо) — фикс НЕ ослабил
проверку, только снял ложняк на `#share`-типе. `std` 148/26/61,
`nova-polaris` 55/0 (пришпиленный `d0fe9e8`) — канон держится. Полный
`nova check spec_tests/conformance` (единый CU) ДО этого фикса: `PASS:
261 FAIL: 489`; ПОСЛЕ: `PASS: 262 FAIL: 488` (+1, ровно эта фикстура —
других изменений в счёте нет). `arch-ratchet` 64388/348 без изменений.

Как и §5, это НЕ находка о корпусе, а находка о собственном классификаторе
Ф.3 — единственная СИНТЕТИЧЕСКАЯ причина обеих регрессий: закрытие
блокет-`fn_param_in_sig`/`resolved_types`-канала для НОВОГО прохода вскрыло
два места, где Пасс B/новый Ф.3-проход раньше опирался на неполные данные
(поле функционального типа; untyped mut-локал) молча в консервативную
сторону — оба зачинены В ЭТОМ ЖЕ окне, ни один не потребовал миграции
корпуса.

## 9. Спек-амендмент (D446 §4/§5)

Правки в `spec/` не внесены этим окном (спеку не править — амендмент
текстом в отчёт, вносит интегратор при слиянии). Предлагаемый текст:

> **D446 §5 (Ф.3-амендмент, финал плана 238).** Требование безопасности
> параметра функционального типа выводится компилятором АВТОМАТИЧЕСКИ
> (`compute_required_params`, `fiber_safety.rs`), не объявляется как
> норма пользователем:
>
> 1. **Правило 1 (прямое).** Параметр `p` функции `F` требует
>    Safe-замыкания, если тело `F` вызывает `p()` по имени внутри
>    `spawn`/`detach`/`parallel for`, синтаксически принадлежащих телу
>    САМОЙ `F` (любая вложенность).
> 2. **Правило 2 (транзитивное).** Если `F` передаёт СВОЙ параметр `p`
>    без изменений (голым идентификатором) аргументом в позицию
>    параметра другой, локально резолвящейся функции `G`, требующего
>    (по правилу 1 или транзитивно) — `p` требует тоже. Одна неподвижная
>    точка над графом резолвнутых вызовов (та же инфраструктура, что
>    Ф.1's тотальная бирка, новая ось).
> 3. **`#fiber_safe`** — явная пометка параметра (парсер: `#cancel_safe`-
>    образец), ЕДИНСТВЕННЫЙ путь придать требование параметру функции БЕЗ
>    видимого тела (`extern`/`no_body`) — вывод не может заглянуть внутрь.
> 4. **Умолчание безопасно в обе стороны.** Не выведено и не помечено ⇒
>    ничего не требуется, диагностика невозможна структурно; выведено
>    (или помечено) ⇒ проверяется у ВСЕХ вызывающих без исключений.
>
> **Точка проверки — не вызов параметра, а ПЕРЕДАЧА аргумента.** На
> каждом call-site во всём модуле, где аргумент попадает в требующую
> позицию, и захваты аргумента синтаксически видны (литерал замыкания,
> либо один `let`-хоп в той же функции) — бирка аргумента (Safe/
> Undecided/Unsafe, тем же основанием, что Ф.1, но по ЗАХВАЧЕННЫМ
> mut-именам охватывающей функции — параметрам И локалам, поскольку
> захват в эскейпящее замыкание — доказанный, не мягкий класс) сверяется
> с требованием; не-Safe ⇒ `E_FIBER_UNSAFE_ARG`, с обратной цепочкой
> «почему параметр требует».
>
> **Судьба `NOVA_FIBER_INDIRECT` (Ф.2-класс `fn_param_in_sig`
> закрывается).** Прямой вызов СОБСТВЕННОГО требующего параметра внутри
> собственной `spawn`/`detach`/`parallel for`-точки посева (бывшая
> блокет-Undecided сигнатурная категория `fn_param_in_sig`) БОЛЬШЕ НЕ
> диагностика на самой точке вызова — ни с флагом, ни без: реальный риск
> ловится на ВСЕХ call-site'ах передачи (см. выше). Под флагом остаётся,
> ПОИМЕНОВАННО (не общей корзиной): (а) вызов через ПОЛЕ структуры
> функционального типа (`field_call_unresolved`) — компилятор структурно
> не отличает такое поле от параметра/переменной; (б) multi-hop `mut []T`
> touch (`unguarded_mut_param`, Ф.2, без изменений); (в) межмодульный
> разрыв (`cross_module_callee`); (г) протокол-диспатч через generic
> bound; (д) аргумент, чьи захваты СИНТАКСИЧЕСКИ не видны на call-site
> (контейнер/поле/чужая функция/2+ `let`-хопа); (е) прямой вызов
> замыкания, никогда не проходящий через параметр функции вообще
> (локальная переменная/каррирование/if-let, вызванные прямо внутри
> файбера). Измерено на 15 адверсарных пробах Ф.7/ревизии
> (`PROGRESS-p238-f3.md` §2) — 1 из 11 ранее-только-под-флагом проб
> закрылась этим окном без флага (двухступенчатая транзитивная передача,
> ровно правило 2 выше); остальные 10 — честно поимённо в остатке.
