## 1. Парсер: куда встаёт имя

`fn parse_type_attrs` (`compiler-codegen/src/parser/mod.rs:2638-2868`) — один
цикл `match next_name.as_str()` на семь имён: `from_fields`, `from_pairs`,
`share`, `impl`, `zero_on_move`, `pub_to`, `serde`. Список **не продублирован**
нигде рядом — единственное место разбора. (Строка ошибки "opaque" на
`:2478` — это ДРУГОЙ цикл, `parse_fn_attrs` для функций, не типов; тот же
токен-паттерн `#name`, но отдельная таблица имён. Подтверждает уточнение
из плана: «интегратор ранее называл восемь — список атрибутов функций».)

Добавление `no_copy`:
1. Одна ветка `"no_copy" => { ... }` в `parse_type_attrs` (~10-15 строк, по
   образцу `"zero_on_move"` — bare marker, no args, duplicate-check).
2. Сигнатура `parse_type_attrs` возвращает кортеж из 5 элементов
   (`Vec<TypeAttr>, Vec<String>, bool, Vec<String>, Vec<SerdeArg>`) —
   `no_copy` как ЕЩЁ ОДИН bare `bool` добавляет 6-й элемент кортежа. Это
   каскадом трогает: сигнатуру функции (`:2638-2639`), тело (return в
   `:2867`), ВСЕ call site'ы (`parse_type_attrs()?` на `:1370`), проверку
   guard-условия «атрибуты валидны только перед `type`» (`:1707-1712`,
   через `!type_attrs.is_empty() || zero_on_move_attr || ...` — нужно
   добавить `|| no_copy_attr`), проброс в `parse_type_decl` (сигнатура
   `:4099`, оба call site'а конструктора `TypeDecl` — `:4352`/`:4440`/`:4601`,
   три места, не одно — `Record`, судя по нумерации, и минимум ещё один
   `TypeDeclKind`).
3. Текст guard-диагностики `:1712` («from_fields / from_pairs / zero_on_move
   / pub_to / serde are only valid before type») — надо дописать `no_copy`
   вручную, это ОТДЕЛЬНАЯ строка от списка имён в matcher'е (та самая
   ловушка «текст диагностики и проверка расходятся», которую просил
   проверить бриф — здесь она реальна: два независимых места держат
   практически один и тот же список имён текстом).

Итог п.1: **одно место разбора**, но кортежное API `parse_type_attrs`
означает N call-site правок при добавлении 6-го bool-флага (не только
«одна ветка матчера»). Масштаб — как у `zero_on_move` в своё время (тот же
паттерн, тот же кортеж).

## 2. Где живёт признак типа — путь `zero_on_move` целиком

Проследил `zero_on_move` от парсера до кодогена, `no_copy` может пройти
БУКВАЛЬНО тем же путём:

1. **Парсер** — `parse_type_attrs` (see §1), локальный `bool`, ветка
   `"zero_on_move" => {...}` (`:2786-2801`).
2. **AST** — отдельное bool-поле `TypeDecl.zero_on_move`
   (`compiler-codegen/src/ast/mod.rs:1214-1222`), НЕ элемент
   `Vec<TypeAttr>` — тот же паттерн, что `consume: bool` (`:1187`).
   `no_copy` — по аналогии, отдельное поле `TypeDecl.no_copy: bool`, а не
   вариант enum `TypeAttr` (сохраняет единообразие: любой атрибут, влияющий
   на flow-семантику/линейность, — отдельное bool-поле; атрибуты, влияющие
   только на codegen-выбор представления/имени — элемент `TypeAttr`).
3. **Чекер** — валидация формы: `types/mod.rs:6324-6346` — `if td.zero_on_move`
   проверяет kind (`E_ZERO_ON_MOVE_INVALID_KIND`, применим только к
   Record/NamedTuple/Newtype). `no_copy` нуждается в СВОЁМ аналогичном
   guard (например, «применим только к Record value» — если решение
   ограничить `#no_copy` конкретно значение-внутри-формой).
4. **Кодоген** — прямое чтение `t.zero_on_move` из `TypeDecl` AST-узла
   (`emit_c.rs:17403-17417`, `emit_zero_on_move_helper`) — **никакого
   отдельного реестра типов кодоген не заводит**, поле читается прямо с
   AST-узла типа в момент эмита. Для `no_copy` кодогену вообще ничего не
   нужно менять (признак — ЧИСТО чекерный/checker-only, влияет только на
   диагностики, не на генерируемый C).

Итог п.2: 4 шага, 3 файла (`parser/mod.rs`, `ast/mod.rs`, `types/mod.rs`),
`emit_c.rs` не трогается вообще (в отличие от `zero_on_move`, у которого
есть codegen-шаг). Дешевле образца.

## 3. Чекер: `check_consume` — переиспользуется ЧАСТИЧНО, не «как есть»

Это ключевой пункт, и находка расходится с прогнозом плана
(«переиспользуется КАК ЕСТЬ, с одним изъятием»). Разбор по подпунктам:

### 3.1. Финальная проверка «на выходе ничего не Live»

`check_obligations_at_exit` (`types/mod.rs:36810-...`) — единая,
изолированная функция, единственный источник `D133-not-consumed` /
`D156-strict-forget`. Вызывается из ТРЁХ мест внутри `check_consume`:
`FnBody::Block` (`:38015`), `FnBody::Expr` (`:38039`), `Item::Test`
(`:38048`). Итерирует `ctx.consume_obligations` — множество, которое
пополняется ТОЛЬКО через `ctx.declare_consume_binding(...)`.

**Находка, меняющая план**: `declare_consume_binding` вызывается ТОЛЬКО
когда `decl.consume == true` (явное ключевое слово `consume` на
`let`/параметре). Обычный `ro`/`mut`/`let` без `consume` идёт через
`ctx.declare(...)`, которая **не создаёт obligation** — переменная
получает состояние `Live` в `states`, но НЕ попадает в
`consume_obligations`. Значит: если для `#no_copy`-типов НЕ требовать
ключевое слово `consume` при объявлении (а план явно говорит — не
требовать, это и есть «ритуал без содержания», от которого уходим), то
`check_obligations_at_exit` **и так НИКОГДА не увидит** `#no_copy`-переменные
в своём цикле — специальный «obligation, но без exit-проверки» режим,
предложенный в плане, физически не нужен: obligation просто не заводится.
Не «изъятие одной проверки», а «этот путь вообще не активируется».

Пробой подтверждено (`scratch_p248n2/probe1/main.nv`): `consume`-тип с
непустым `close()`-методом, вызов `takes_view(a)` (обычный НЕ-consume
параметр) компилируется чисто — экзит-проверка требует только явный
`a.close()`, за сам факт передачи в `takes_view` не наказывает вовсе (см.
§3.3 ниже — это как раз ДЫРА, не фича).

### 3.2. Что ловит копию (`ro b = a`)

Подтверждено: та же машина, но **уже, чем нужно**. Правило 2 (D180,
`E_VIEW_BINDING_FORBIDDEN`, `types/mod.rs:38927-38947`) срабатывает когда
`alias_src.is_some() && !decl.consume`, а `alias_src` вычисляется
(`:38843-38869`) **ТОЛЬКО для `ExprKind::Ident` RHS** (голый идентификатор)
и одного частного случая fluent-chain `Call{Member}`. `alias_obligated`
(`:38899-38904`) проверяется по ДВУМ путям — `consume_obligations.contains`
ИЛИ (что важно) `var_types.get(canon)`-тип входит в `lin_reg.consume_types`
— то есть чисто по ИМЕНИ ТИПА, независимо от того, заводилась ли
obligation. Это значит: если `no_copy`-типы попадут в тот же
`consume_types`-реестр (с меткой уровня, см. §3.3), `ro b = a` для
`no_copy`-типа поймается ДАЖЕ БЕЗ `declare_consume_binding` на `a` — чисто
по типу `a`. Пробой это подтверждено косвенно (наблюдение по коду; прямую
пробу делать не пришлось — логика однозначна по чтению условия).

**НО**: `alias_src` match НЕ покрывает:
- `ro b = @field` / `ro b = self.field` (`ExprKind::Member`/`SelfAccess`
  RHS) — НЕ распознаётся как alias вообще (падает в generic `else`-ветку,
  `ctx.declare(...)`, без всякой связи с состоянием источника).
- передачу как аргумент функции (`foo(a)`, НЕ-consume параметр) — вообще
  отдельный путь (`consume_walk_expr`, `ExprKind::Call`), не имеет никакого
  отношения к Rule 2. `use_var` (единственная проверка, применяемая к
  использованию идентификатора-аргумента) реагирует ТОЛЬКО на
  `Consumed`/`MaybeConsumed` state — не на «эта переменная типа X, X —
  no_copy, второй биндинг запрещён».
- встраивание в literal записи (`Type { field: a }`) — отдельный, более
  ранний путь `consume field`-маркера (`D133-field-marker-missing`), тоже
  никак не связан с bare-Ident alias-детектором.

**Пробой подтверждено** (`scratch_p248n2/probe1/main.nv`,
`takes_view(a)`): передача consume-обязательной переменной как
НЕ-consume аргумент компилируется БЕЗ ошибки и БЕЗ пометки `a` как
consumed — `a.close()` после `takes_view(a)` по-прежнему нужен и
компилируется штатно. Значит сегодняшняя машина **вообще не считает
переход значения через границу вызова использованием второго имени**.

**Второй эмпирический пробой (`scratch_p248n2/probe2/main4.nv`)** —
воспроизведение паттерна `share_copy` из `std/net/tcp.nv` (см. §5) на
игрушечном `value`-типе: функция принимает значение-тип обычным
(не-`mut`, не-`consume`) параметром и кладёт его в поле нового значения;
после этого мутация ОРИГИНАЛА не видна во «второй копии» —
`x.n=1 h.c.n=0`. Это прямое доказательство, что для VALUE-типов (в
отличие от текущих pointer-newtype consume-типов, где алиас безопасен по
конструкции) передача аргументом — это **настоящая физическая копия**, а
не безобидный «view» — то есть именно тот канал, который машина сегодня
не проверяет, для value-типов не косметика, а источник тихой порчи данных.

### 3.3. Реестр `consume_types` — рекомендация

`LinearityRegistry.consume_types: HashSet<String>` (`types/mod.rs:34620`),
заполняется в `LinearityRegistry::build` (`:34644-34719`) только по
`td.consume` (`:34681-34683`). Рекомендация окна, СОГЛАСНО коду, а не
вкусу: **один реестр, но НЕ просто `HashSet<String>` — потребуется
`HashMap<String, ConsumeLevel>`** (`enum ConsumeLevel { MustConsume,
NoCopy }`), потому что Rule 1 (`E_CONSUME_KEYWORD_MISSING`,
«ритуал `consume x = …` на каждом объявлении») и Rule 2
(`E_VIEW_BINDING_FORBIDDEN`, «второе имя запрещено») ЧИТАЮТ ОДНО И ТО ЖЕ
условие `rhs_yields_consume_type`/`alias_obligated`, оба идут через
`consume_types.contains`. Если `no_copy`-типы просто добавить в тот же
`HashSet`, Rule 1 сработает НА КАЖДОМ объявлении (`ro a = AtomicU32{...}`
потребует `consume a = …`) — ровно тот ритуал, который план явно отверг
(«Ритуал без содержания», раздел «Почему consume не годится»). Уровень
нужен, чтобы:
- Rule 1 (must-declare-with-`consume`) стрелял только для `MustConsume`;
- Rule 2 (no-second-name) стреляла для ОБОИХ уровней;
- `check_obligations_at_exit` даже не пришлось трогать отдельно — раз для
  `NoCopy`-уровня obligation не заводится (§3.1), финальная проверка
  естественным образом не видит эти переменные.

Один `HashMap` с уровнем — единственный вариант, не раздваивающий обход
(`type_is_consume_v`, рекурсия по полям/суммам/дженерикам/кортежам) — она
использует `consume_types.contains` в нескольких местах (`:34779`,
`:34798` и др.), и с `HashMap<String, ConsumeLevel>` эти сайты меняются на
`.contains_key`/`.get` без переписывания структуры обхода.

### Вывод по п.3

«Переиспользуется как есть» — верно ТОЛЬКО для узкого случая
`ro/mut b = a` (голый идентификатор). Для остальных каналов дублирования
(аргумент функции, `@field`-чтение в локальную, встраивание в литерал
записи) машина СЕГОДНЯ пропускает молча — и это не гипотетический
пробел: реальный код в корпусе (`std/net/tcp.nv`, см. §5) как раз и
использует именно эти пропущенные каналы, причём НАМЕРЕННО, для
организации shared-владения через copy-семантику указателя. Полное
покрытие «второго имени» требует расширения `alias_src`-детектора на
Member/SelfAccess RHS и отдельной проверки в `consume_walk_expr` на
Call-аргументы — заметно больше, чем «одно изъятие в конце».

## 4. Диагностики

**Новые коды** (нельзя переиспользовать тексты `consume` — другая семантика):
- Аналог Rule 2 (`E_VIEW_BINDING_FORBIDDEN`) под no_copy-смыслом: что-то
  вроде `E_NO_COPY_SECOND_NAME` / `D_NOCOPY-alias` — «значение типа `X`
  (`#no_copy`) уже связано с именем `a`; второе имя запрещено — передайте
  владение (`consume`-подобная передача остаётся ТОЛЬКО через параметр,
  или явно проектируйте API вокруг единственного владельца)». Текст должен
  явно НЕ говорить «потребите» (это неверно — потреблять нечего).
- Если решаем закрыть дыру §3.2 (аргумент/embed) — ЕЩЁ минимум два новых
  кода: «no_copy-значение передано аргументом функции без объявленного
  transfer» и «no_copy-значение встроено в поле литерала записи из
  существующего биндинга».
- Guard-диагностика формы (аналог `E_ZERO_ON_MOVE_INVALID_KIND`) — на
  какие `TypeDeclKind` атрибут применим (вероятно только `Record value`,
  учитывая, что искомое применение — `value priv { ... }`).
- Duplicate-attribute диагностика (`duplicate #no_copy attribute`) — по
  трафарету остальных шести атрибутов, тривиальна.
- Диагностика guard `:1712` («… are only valid before `type`») — текст
  списка имён нужно дописать вручную (см. §1, ловушка расхождения текста
  и проверки уже существует у остальных шести и должна быть закрыта
  одновременно, не по факту случайного обнаружения потом).

**Не нужно**: `D133-not-consumed`/`D156-strict-forget` — они специфично
про «обязан израсходовать», для no_copy семантически неверны и не должны
всплывать (см. §3.1 — по факту и не всплывут, т.к. obligation не заводится).

**Итог измерения**: НЕ «N мест не скомпилируется» в смысле «добавь
consume и всё заработает» — 3 конкретных места (все три — НЕСВЯЗАННЫЕ
файлы в ДВУХ репозиториях, но один и тот же осознанно повторяемый приём:
«держи `Atomic*`-поле внутри `value`-типа, полагаясь на то, что копия
`value`-типа копирует ТОЛЬКО указатель, поэтому все копии физически делят
одну ячейку») ТРЕБУЮТ ПЕРЕПРОЕКТИРОВАНИЯ логики, а не косметической правки
синтаксиса. Пробой (`probe2/main4.nv`, §3.2) подтверждено: при переходе
`AtomicInt` на value-внутри-без-адреса этот приём молча посчитает каждую
копию отдельным счётчиком — `TcpStream.@share()`-рефкаунт перестанет
работать (каждая «расшаренная» копия увидит rc=1 и закроет сокет
самостоятельно), `AccessLog`/`RejectLog` перестанут быть process-wide.
Это НЕ «места, которые перестанут компилироваться» — что хуже, это места,
которые (без `#no_copy`-enforcement на канале аргумент/поле, см. §3.2)
**молча перестанут быть корректными, продолжая компилироваться**.
Обнаружение и переписывание этих трёх мест ОБЯЗАНО войти в объём волны
(не «до 21 копии тегом, потом почистим») — иначе тег фиксирует тихий баг.

## 6. Взаимодействие с `#share`

Не противоречат — эмпирически подтверждено, но по НЕОЧЕВИДНОЙ причине.

`#share` (D415) — vouch на безопасность АЛИАСИНГА между фиберами
(отсутствие data race), НЕ механизм и не обещание «копия=шаринг». Заявка
плана «структурный вывод увидит `u32` внутри и решит скопировать
безопасно» — это про СТРУКТУРНУЮ проверку копируемости, отдельную от
`#share`.

Проверено пробой (`scratch_p248n2/probe2/main5.nv`): `#share`-размеченный
`value`-тип с `mut`-захватом внутри `spawn { ... }`-блока (`supervised`
scope) — мутация ВНУТРИ fiber'а видна СНАРУЖИ после `supervised` (`c.n=1`,
не 0). Это значит: `mut`-захват в spawn-closure для value-типа идёт НЕ
через byte-copy в замыкание, а через тот же механизм, что и
escape-promotion (`D228 amend «escape & auto-promote», Plan 127`,
`spec/decisions/02-types.md:13422+`) — значение, которое «убегает» через
closure-capture, получает pointer-семантику автоматически, ДО того, как
может случиться порча. Аналогично подтверждено для `mut`-ПАРАМЕТРОВ
(`probe2/main.nv`: `bump(x)` с `fn bump(mut c Counter)` мутирует `x`
снаружи — `mut param T` = «mutable view», D176, применимо к value-типам
без исключений).

**Вывод**: канал `#share` (межфиберный алиасинг через spawn-capture) и
предполагаемый запрет `#no_copy` (запрет на `let`-style второе имя внутри
ОДНОГО потока управления) идут по РАЗНЫМ путям кодогена — spawn-capture
уже сегодня pointer-based (escape-promote), значит `#no_copy`, даже если
бы запрещал spawn-capture буквально по своему определению («второе имя»),
технически МОГ БЫ сделать явное исключение именно для этого канала без
внутреннего противоречия (сам канал не дублирует память). Риск,
поднятый в §5 (`share_copy`, `AccessLog.counter`, `RejectLog`) — ДРУГОЙ
канал (явная передача аргументом + встраивание в структуру), и вот ОН
использует ИМЕННО ту семантику copy-by-pointer, которую `#no_copy`
призван закрыть. То есть: `#share` не конфликтует с `#no_copy`
концептуально, но существующий КОРПУС уже построил на пересечении обоих
признаков ровно тот шаблон («расшарь через явную copy указателя»,
`share_copy`), который переход на value-внутри обязан сломать и
перепроектировать — см. §5.

## 7. Переход на значение внутри — что уже есть, что ломается

**Синтаксис работает уже сегодня.** Пробой (`scratch_p248n2/probe3/main.nv`)
подтверждено: `type AtomicU32 value priv { v u32 }` + метод с `@`-ресивером
+ `unsafe { extern_fn(&@v) }` — берёт адрес ПРИВАТНОГО поля value-типа и
передаёт во внешнюю функцию. `nova check` — чисто (`[32mok[0m`). C-кодоген
(`nova build --keep-artifacts`, до стадии линковки) подтверждает корректную
лоуэринг: `atomic_load_u32((&(nova_self->v)))` — адрес приватного поля
берётся правильно, никакого дополнительного «размуровывания» приватности
не требуется — приватность это чисто-checker-уровневое ограничение, не
влияющее на кодоген адреса поля.

**Более важная находка (не из вопроса брифа, но прямо на него отвечает
сильнее ожидаемого)**: `compiler-codegen/nova_rt/sync_primitives.h` УЖЕ
содержит value-внутри реализацию ВСЕХ 11 атомиков —
```c
typedef struct { int64_t value; } Nova_AtomicI64;   // :194
typedef struct { int32_t value; } Nova_AtomicI32;   // :275
... (все 11 — I64/I32/I16/I8/U64/U32/U16/U8/Int/Uint/Bool, :194-716)
```
с ПОЛНЫМ набором методов через `__atomic_*` GCC/Clang builtins
(`load`/`store`/`swap`/`cmpxchg`/`fetch_add`/`fetch_sub`/`fetch_or`/
`fetch_and`/`fetch_xor`/`fetch_max`/`fetch_min`/`fetch_nand` —
`Nova_AtomicI64_method_*`, `:196-271`). Единственное отличие от того, что
нужно плану: `Nova_AtomicI64_static_new` (`:196-201`) делает
`nova_alloc(sizeof(Nova_AtomicI64))` и возвращает УКАЗАТЕЛЬ — это и есть
СЕГОДНЯШНЕЕ heap-размещение, которое `.nv`-newtype `AtomicI64(*())`
оборачивает. Сама структура (`{ T value; }`) и методы над НЕЙ (принимают
`Nova_AtomicI64*` — указатель НА структуру, неважно откуда взятый, со
стека или из кучи) УЖЕ ровно то, что нужно value-внутри форме — метод
`Nova_AtomicI64_method_load(const Nova_AtomicI64* a)` одинаково корректно
работает что с `&heap_ptr->value`-структурой, что с `&stack_var`.

**Вывод**: C-рантайм для «значение внутри» уже написан и уже
протестирован (эти функции реально используются сегодняшними
pointer-wrapped атомиками) — перевод на `value priv { v Txx }` НЕ требует
новых `nova_rt`-примитивов, только: (а) `.nv`-декларация типа меняется с
newtype-над-`*()` на `value priv { v Txx }`; (б) `extern "nova"`-сигнатуры
меняются с `(*())` на `(*Txx)`/эквивалент — принимают адрес поля, не
хранимый указатель; (в) вызовы меняются с `atomic_op(self.ptr, ...)` на
`atomic_op(&self.v, ...)` — паттерн ИЗ ПРОБЫ (`&@v`) уже работает. Из
брифового вопроса «чего не хватает» — ничего на уровне C; расхождение
только в том, ЧТО адресуется (heap-указатель, хранимый в поле, против
адреса стекового/inline поля) — обе формы одинаково легальны для
компилятора уже сегодня.

## ВЕРДИКТ

**Форма `#no_copy` выполнима как атрибут типа** — парсер/AST-путь дёшев
(§1-2: одна ветка разбора + отдельное bool-поле `TypeDecl`, 3 файла,
кодоген не трогается) и ИМЕЕТ готовый образец (`zero_on_move`). C-рантайм
для целевого применения (11 атомиков, значение внутри) **уже написан и
протестирован** (§7) — перевод .nv-декларации не требует новых
`nova_rt`-примитивов.

**НО заявленное в плане «check_consume переиспользуется как есть»
— НЕ подтверждено** (§3): существующая alias-детекция ловит ТОЛЬКО
голый `let/ro/mut b = a`. Она НЕ видит (и не будет видеть без отдельной
доработки): чтение поля в локальную (`x = @field`), передачу значения
аргументом функции, встраивание в литерал записи. Ключевая проблема —
эти ТРИ непокрытых канала **не гипотетические**: корпус (`std/net/tcp.nv`,
`nova-polaris/{middleware/log.nv, net/serve.nv}`) СЕГОДНЯ использует их
осознанно и явно задокументированно для реализации shared-владения через
copy-семантику указателя атомика (§5, три подтверждённых места). Переход
`AtomicInt` на значение-внутри без соответствующей доработки chекера
превратит эти три места из «работает по конструкции указателя» в «тихо
считает каждую копию отдельным счётчиком» — компилируется, но неверно.
`#no_copy`, реализованный буквально по узкому прочтению плана (только
`let`-алиас), НЕ поймает ни одно из этих трёх мест как ошибку компиляции
— они останутся молчаливо сломанными.

**Риски для волны, в порядке серьёзности:**
1. (**блокер объёма, не техники**) Минимум 3 существующих места
   (`TcpStream.share_copy`, `AccessLog.counter`, `RejectLog`) требуют
   ПЕРЕПРОЕКТИРОВАНИЯ (не косметики) ДО или ОДНОВРЕМЕННО с переводом
   атомиков на value-внутри — иначе релиз фиксирует тихий баг
   (правило «ужесточать до релиза» из плана прямо это требует).
2. (**объём реализации шире заявленного**) Полное покрытие «второго
   имени» по духу формулировки плана требует расширения
   alias-детектора на Member/SelfAccess RHS + новую проверку в
   `consume_walk_expr` для Call-аргументов — не «одно изъятие в
   конце», а два новых пути анализа. Если исполнитель ограничится
   узким `let`-алиасом (дешёвая, быстрая часть), это НАДО явно
   зафиксировать как принятое ограничение объёма, а не молчаливый
   пробел — три места из §5 иначе останутся непойманными.
3. (не блокер) Реестр `consume_types` нуждается в уровне строгости
   (`HashMap` вместо `HashSet`) — иначе Rule 1 (`E_CONSUME_KEYWORD_
   MISSING`) сработает на каждом объявлении no_copy-переменной, что
   план явно отверг как «ритуал без содержания».
4. (не блокер, разъяснено) `#share` и `#no_copy` НЕ противоречат друг
   другу — spawn-capture канал уже pointer-based (escape-promote,
   Plan 127), подтверждено пробой.

Числа: 19 кандидатных типов (не 21 — `CancelToken` вне `.nv`-грепа), из
них 3 реально используются за пределами `sync.nv` в нетривиальной форме
(`AtomicInt`, `AtomicBool`, `Semaphore`); из мест их использования — 3
конкретных файла с намеренным shared-через-указатель паттерном, ВСЕ
требуют переписывания перед/вместе с переходом на значение-внутри.
