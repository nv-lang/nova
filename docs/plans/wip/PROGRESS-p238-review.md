# p238-review — критическая ревизия плана 238 ДО реализации

**Окно:** p238-review, sonnet, ветка `p238-review`, worktree `d:/Sources/nv-lang/nova-p238r`.
**Задача:** не подтвердить план 238, а найти, где он повторит судьбу июльской
итерации. Ничего не менялось — ни компилятор, ни планы, ни спека. Три пробы
скомпилированы прекомпилированным `nova.exe` из main-репо (тот же коммит
`47f4cdaf9`, что и HEAD ветки) — они лежат в
`docs/plans/wip/p238-review-probes/` этого worktree.

---

## 1. Почему провалилась прошлая итерация — механизм, не «недосмотрели»

**Что заявили исполненным в июле.** Окно `p238-fiber-memory` (2026-07-30/31)
измерило 28 живых сайтов ОДНОГО идиома (`mut`-флаг в Fail-обработчике),
закрыло их тремя точками (§3 а/б/в плана — параметр в spawn-tainted fn,
канал-send, handler вокруг spawn-тела), прогнало race150 B/C-фикстуры,
получило зелёный гейт и было принято интегратором как «✅ ИСПОЛНЕНА И ВЛИТА».
D441 §0 сама формулирует метод: *«D415 §2 поставил capture-check РОВНО на
синтаксическую границу spawn/parallel for/detach»* — то есть проверка была
написана на конкретные СИНТАКСИЧЕСКИЕ места, найденные измерением конкретного
корпуса, а не выведена из грамматики.

**Механизм провала — не «забыли протестировать», а СПОСОБ приёмки.**
Приёмка спрашивала: «все ли 28 измеренных сайта закрыты? гейт зелёный?
race150 B/C ведут себя как задумано?» — и получала три «да». Она НЕ
спрашивала: «это свойство („любой путь X недостижим“) или список форм
(„эти конкретные шесть путей исправлены“)?». Между этими вопросами разница
ровно в кванторе: список проверяет ∃ (нашли — починили), свойство требует ∀
(докажи, что для ВСЕХ путей). Приёмка 31 июля проверяла первое и рапортовала
как второе.

**Симптом сформулирован самим планом (раздел «ПРОДОЛЖЕНИЕ»):** «гонки
находит ВЛАДЕЛЕЦ чтением кода, а не компилятор» — дважды подряд в одном
файле (`ratelimit.nv`, 01.08 и №341 04.08). Это прямое свидетельство: способ
приёмки (закрыть измеренный список) систематически пропускает ЛЮБУЮ форму,
не попавшую в список, потому что ничто в процессе приёмки не задавало
вопрос «а какие ещё формы есть».

**Устранена ли причина для Ф.8?** Частично. Ф.6/Ф.7 (2026-08-04/05) —
настоящий методологический разворот: вместо «нашли баг → закрыли» сначала
СФОРМУЛИРОВАНО утверждение (D446), затем ВЫВЕДЕН из грамматики список из 10
переходов, затем адверсарно проверен каждый (12 проб + честный контроль).
Это правильный порядок работ, и он уже окупился (нашёл 6 дыр до реализации,
а не после). НО: сама Ф.8 (алгоритм) на бумаге СНОВА рискует стать «списком
распознанных форм» — конкретные точки ниже (§2) показывают, что часть
машинерии, которую Ф.8 планирует ПЕРЕИСПОЛЬЗОВАТЬ («та же машина», «тот же
обход»), унаследует ровно те же ограничения источника (метод против
свободной функции, generic-параметры), которые уже один раз были причиной
дыры. И — что важнее для механизма провала конкретно — **план не меняет
САМ КРИТЕРИЙ ПРИЁМКИ**: Ф.9/Ф.10 (корпус фикстур, адверсарная ловушка на
будущее) запланированы ПОСЛЕ Ф.8 и, что важнее, за тег — то есть тот же
порядок «сделали → потом (не факт что) проверили», который и породил
исходную проблему, повторяется структурно, просто с одним циклом ревизии
раньше. Подробнее — §6.

## 2. Контрпримеры к Ф.8 — где алгоритм не даст заявленной гарантии

### 2.1. Центральный контрпример: реальный, `#stable`, принятый в корпусе тип падает под собственную машину Ф.8

Реальный код `nova-polaris` — не гипотеза, а два живых `#stable` файла:

```nova
// nova-polaris/src/metrics.nv (сокращено)
export type MetricsRegistry value priv {
    mutex     Mutex
    counters HashMap[str, int]
    gauges   HashMap[str, f64]
}
export fn MetricsRegistry @record_counter(name str, delta int) {
    consume g = @mutex.lock()
    ro prev = @counters.get(name) ?? 0
    ro _ = @counters.insert(name, prev + delta)
}
```

```nova
// nova-polaris/src/middleware/ratelimit.nv (сокращено)
type BucketTable value priv { mutex Mutex, buckets HashMap[str, TokenBucket] }
export fn ratelimit(capacity int, per_sec f64, per_client bool = false) Time -> Middleware {
    mut table = BucketTable.new()
    middleware(fn(req ServerRequest, next Handler) -> ServerResponse =>
        rl_apply(capacity, per_sec, per_client, table, next, req))
}
```

Оба — «мьютекс дисциплинирует соседнее поле» (canon-паттерн, банер
`ratelimit.nv` прямо ссылается на `metrics.nv` как образец). НИ у одного НЕТ
`#share`. Оба возвращают замыкание/регистрируют обработчик, захватывающий
разделяемое состояние, вызываемое позже из множества файберов — это
БУКВАЛЬНО форма №341, ради которой Ф.8 и пишется (Ш.4: «именно здесь
ловится случай №341»).

**Проба A (`pA_mutex_hashmap_capture/probe.nv`) — тот же тип, ПРЯМОЙ
захват в spawn:**

```nova
type Table value priv { mutex Mutex, entries HashMap[str, int] }
fn Table.new() -> Table => { mutex: Mutex.new(), entries: HashMap[str, int].new() }
fn Table @bump(key str) {
    consume g = @mutex.lock()
    ro prev = @entries.get(key) ?? 0
    ro _ = @entries.insert(key, prev + 1)
}
fn main() {
    mut table = Table.new()
    supervised { for _ in 0..4 { spawn { table.bump("k") } } }
}
```

**Вердикт компилятора (текущий, 47f4cdaf9):**

```
error: [E_CONCURRENT_MUT_CAPTURE] outer `mut` binding `table` captured by
reference in a `spawn`/.../body: `Table` is poisoned at
`Table.entries.buckets[..]::Occupied.key` (`K`): an unresolved type name
`K` (generic type-param or registry miss) — share-ness cannot be proven
```

Т.е. СЕГОДНЯ, если бы этот тип КОГДА-ЛИБО пересёк проверяемую границу
напрямую, `share_check.rs` (машина, на которой стоит и D441, и — по
формулировке D446 §1 — обязана стоять «проверка» типа) отказывает ему:
`HashMap[K,V]`'s generic-параметр не субституируется (`share_check.rs`
doc-комментарий строка 297-300: «Use-site generics are NOT substituted at
V1»), и generic-параметр консервативно ядовит.

**Проба B (`pB_mutex_hashmap_return_escape/probe.nv`) — ТОТ ЖЕ тип, форма
№341 (return-escape):**

```nova
fn make_bumper() -> fn() -> () {
    mut table = Table.new()
    || { table.bump("k") }
}
fn main() {
    ro bump = make_bumper()
    supervised { for _ in 0..4 { spawn { bump() } } }
    ro _honesty_control int = "not an int"   // честный контроль
}
```

**Вердикт компилятора:** ТОЛЬКО честный контроль (`E7301`, ожидаемая
посторонняя ошибка типов). Ни слова про `E_CONCURRENT_MUT_CAPTURE` — файл
дочитан целиком (контроль сработал бы на строке ПОСЛЕ проверяемого кода,
значит сканирование до неё дошло), путь молчит.

**Из этой пары следует прямой вывод.** Ф.8 явно ставит целью закрыть
ИМЕННО путь B (Ш.4: «замыкания, созданные снаружи... именно здесь ловится
случай №341») — тем же образом, каким уже устроена проверка типа на
безопасность (D446 §1: «тип может быть объявлен безопасным... компилятор
ОБЯЗАН убедиться, что все изменяющие операции атомарны либо защищены»).
Но проба A доказывает: КОГДА эта проверка типа реально прикладывается к
`Table`/`BucketTable`/`MetricsRegistry`, она их ОТВЕРГАЕТ. Значит закрытие
пути B тем же механизмом, что и путь A, **обязано либо (1) сломать
`ratelimit.nv`/`metrics.nv` как ложные срабатывания, либо (2) потребовать
для них `#share`-вауч, для которого НИГДЕ в Ф.8 не описана процедура
ПРОВЕРКИ** («компилятор ОБЯЗАН убедиться» — как именно убедиться, что КАЖДЫЙ
доступ к `entries`/`counters`/`buckets` в `Table`/`BucketTable`/
`MetricsRegistry` происходит ПОД `@mutex.lock()`, а не в обход? Это
дисциплина ручной блокировки, синтаксически НЕ гарантированная языком —
`entries`/`buckets`/`counters` остаются СОСЕДНИМИ полями, доступными любому
методу типа напрямую, а не «внутри» мьютекса, как `Mutex<T>` в Rust owns T).
Сегодня `#share` — честное слово автора (проверено — просто ЧИТАЕТСЯ
атрибут, ничего не доказывается). D446 §1 обещает, что «объявление
перестаёт быть ручательством... и становится проверяемым» — но алгоритм
Ф.8 (весь текст Ш.1-Ш.7) НЕ содержит ни одного шага, который проверял бы
именно ЭТО: что мьютекс реально дисциплинирует соседние поля. Единственная
описанная «проверка типа» — это структурная ходьба по составу
(`share_check.rs`), которая для композитных guard-типов (Mutex + сырое поле
рядом, а не Mutex, ВЛАДЕЮЩИЙ данными, как в Rust) не может пройти НИКОГДА —
она либо (а) отвергает их (проба A), либо (б) молча доверяет `#share`
(текущий статус-кво, никакого ужесточения).

**Это — не гипотетический, а измеримый корпус.** По `.nv`-исходникам пяти
пакетных реп (`nova-polaris`, `nova-http`, `nova-tls`, `nova-bignum`,
`std`) ровно ДВА файла сочетают поле `Mutex` с соседним `HashMap`/`Vec`
полем: `nova-polaris/src/metrics.nv`, `nova-polaris/src/middleware/
ratelimit.nv` — оба живые, `#stable`, экспортируемые API. Гейт СЕГОДНЯ
зелёный на них ТОЛЬКО потому, что путь их разделения (return-escape,
проба B) никем не проверяется. Как только Ф.8 закрывает путь 3
(своя заявленная цель), эти два файла — первые кандидаты на регресс, и
плану нечего им предложить, кроме несуществующей процедуры проверки
"замка".

**Прямой ответ на вопрос владельца:** так же, как ОЧЕВИДНОЕ рабочее
предположение («ro ⇒ разделяемо» держится вместе с линейностью для mut»)
однажды не учло Fail-обработчик, ЗДЕСЬ очевидное «типу можно доверять
проверку» не учитывает, что «проверка» типа физически умеет проверять
только СТРУКТУРУ (состав полей), а не ДИСЦИПЛИНУ (порядок операций внутри
методов). Guard-типы (мьютекс рядом с данными) — стандартная идиома Nova
(и `MetricsRegistry`, и `BucketTable` — canon-примеры в комментариях
корпуса) — целиком выпадают из того, что механизм физически способен
доказать.

### 2.2. Транзитивное распространение (Ш.3) явно наследует ограничение источника: методы вне периметра

Ш.3 предписывает: «Переиспользовать существующий транзитивный обход,
написанный для `#thread_affine`... механика «протащить свойство по
именованному графу вызовов» уже есть и работает». Но D441 §5 (тот самый
описанный механизм, дословно) сам документирует его границу: **«граф
ОСТАНАВЛИВАЕТСЯ»** там, где вызов идёт не по имени свободной функции —
и отдельно: **«методы (`obj.method()`) вне периметра — только свободные
fn по `Ident`-имени»**.

Идиоматичный Nova-код (весь корпус, включая ОБА примера из §2.1) —
`@`-метод-стиль насквозь: `table.bump()`, `bucket.acquire()`,
`@mutex.lock()`. Если Ш.3 буквально переиспользует граф, построенный для
`#thread_affine` (не расширяя его на методы — а расширение не названо
отдельной работой нигде в тексте Ф.8), то ТРАНЗИТИВНОЕ распространение
признака «файбер-достижимо» останавливается на первом же вызове метода.
Пример: `fn dispatch(h Handler) { spawn { h.call(req) } }` — если где-то
ГЛУБЖЕ по цепочке МЕТОДОВ (не свободных fn) лежит небезопасный захват, он
не будет протащен наверх тем же обходом, каким сегодня протаскивается
`#thread_affine`. Это не гипотеза «а вдруг» — это прямая цитата
собственной документации механизма, который Ф.8 called «переиспользовать»
без оговорки о расширении на методы.

### 2.3. Дженерики — не побочный вопрос, а условие, от которого зависит §2.1 буквально

Проба A показала: сегодняшний отказ `Table`/`BucketTable` происходит
ИМЕННО из-за нерезолвленного generic-параметра `K` внутри `HashMap[K,V]`
(«Use-site generics are NOT substituted at V1»). План сам честно относит
это к нерешённому («Дженерики и мономорфизация: свойство считается до или
после специализации?») — но не отмечает, что от ответа на этот вопрос
ЗАВИСИТ, сработает ли §2.1 контрпример как «ложный отказ» (если генерики
останутся нерезолвленными и практика продолжит консервативно отказывать
композитным типам) или как «тихая дыра» (если генерики резолвятся, а
verification для guard-типов так и не появится — тогда `share_check`,
возможно, для КОНКРЕТНОГО `HashMap[str,int]` даст другой ответ, не
обязательно более безопасный — структура его backing storage всё равно не
проверена НИКЕМ на предмет «доступ только под чужим мьютексом»). В любой
ветке этого нерешённого вопроса корпус `ratelimit.nv`/`metrics.nv` не
проходит чисто — там либо ложный отказ, либо тихая дыра, и план не выбрал,
какая.

## 3. Полон ли перечень десяти переходов?

**Метод проверки:** пройти по грамматике связывания (D19 match, D34
pattern-bind в `if`/`while`, D59 array/tuple/positional-patterns, D184
binding statements, D347 same-scope rebind) и спросить для каждой формы —
покрыта ли она списком 1-10 буквально или только «по духу».

**Вывод: одиннадцатого ГРАММАТИЧЕСКОГО перехода не нашёл.** Список 1-10
получен как перечисление AST-узлов, где значение получает новое имя или
входит в составное значение, и на этом уровне абстракции он действительно
исчерпывающий — каждая форма, которую нашёл дополнительно (ниже), сводится
к одному из 1-10 «по типу операции», просто через ДРУГОЙ синтаксический
путь связывания.

Но именно ЭТО — источник второй, более узкой находки:

**3.1. `if`/`while` pattern-bind (D34) — тот же переход 7/9, но ДРУГОЙ AST-
узел, и у этого узла уже есть прецедент отдельного, независимого от match
энфорс-провала.** D34 сама документирует: до амендмента №106 (закрыт
2026-07-25) «bare pattern-bind default immutable» была декларацией БЕЗ
энфорса именно в позиции `if`/`while` — L1-launder-таблица (D246 §ORACLE G,
СОВЕРШЕННО ДРУГОЙ энфорс, но структурно близкий по духу «проверка на
конкретном AST-узле») заводила match-arm-биндинги, но не заводила
`if`/`while`-биндинги, и они «тихо отмывали ro-заморозку», пока их не
завели явным амендментом. Это ПРЯМОЙ прецедент: у Nova-компилятора уже
БЫЛ случай «энфорс написан на match, а `if let` — соседний путь того же
семантического смысла — не учтён», и это баг, а не выдумка ревизии.

Проба C (`pC_iflet_closure_bind/probe.nv`) проверяет ровно эту гипотезу
на M:N-безопасности:

```nova
fn maybe_counter(flag bool) -> Option[fn() -> ()] {
    if flag { Some(make_counter()) } else { None }
}
fn main() {
    if Some(bump) = maybe_counter(true) {
        supervised { for _ in 0..8 { spawn { bump() } } }
    }
    ro _honesty_control int = "not an int"
}
```

**Вердикт:** только честный контроль (`E7301`), молчание про захват.
Это ПОДТВЕРЖДАЕТ, что переход 7 (Option-payload) течёт и через
`if`-pattern-bind, не только через `match` (как было измерено в Ф.7
`p05_option_wrapped_closure`) — не НОВЫЙ переход по типу операции, но
НОВАЯ подтверждённая точка утечки, которую список из 12 проб Ф.7 не
называл явно (там был только `match`).

**3.2. Комбинации — сам план честно признаёт непроверенными, и §2.1
даёт КОНКРЕТНЫЙ живой пример именно комбинации.** Ф.7 сама пишет:
«Комбинации переходов проверены лишь частично» — путь №11 (переход 2 +
переход 4/5, тэйнтованное поле аргументом свободной функции) был найден и
зафиксирован КАК КОМБИНАЦИЯ, не переехал в финальный список 1-10 отдельным
номером (справедливо — это не новый АТОМ грамматики). Мой контрпример §2.1
— это ЕЩЁ ОДНА живая комбинация (переход 3 «возврат» + переход 4 «запись
в поле структуры при конструировании» + структурная проверка типа) —
пройдена не пробой-выдумкой, а РЕАЛЬНЫМ файлом корпуса. Урок: комбинации —
не теоретический хвост «доделаем после», а то самое место, где сегодня
УЖЕ живут настоящие сайты.

**3.3. Проверил и ОТВЕРГ как false lead: `@cleanup`/автоочистка (D432).**
Гипотеза была: раз Fail-обработчик когда-то оказался «скрытой точкой
исполнения в чужом файбере» (D441 §0 п.2), не окажется ли `@cleanup`
(структурно похожая идея — код автора, вызываемый компилятором НЕ в месте
явного вызова) такой же скрытой точкой? Прочитано D432: авто-`@cleanup`
вызывается компилятором НА ВЫХОДЕ ТОГО ЖЕ лексического блока/тела (в
случае `spawn consume` — на выходе тела РЕБЁНКА, тем же файбером, что и
создал consume-scope — D441 §4 явно). Скрытого пересечения файбера здесь
НЕТ, гипотеза не подтвердилась, дальше не тянул.

**Итог по вопросу 3:** список из 10 переходов на уровне «типов операции
связывания» — обоснованно исчерпывающий, это настоящий результат Ф.7, не
переоценка. Но ГРАММАТИКА Nova даёт НЕСКОЛЬКО СИНТАКСИЧЕСКИХ путей к
одному и тому же переходу (match arm / `if let` / `while let` — три узла,
один переход 7/9), и Ф.7 адверсарно проверила не все из них — прецедент
№106 показывает, что для компилятора Nova это исторически ИМЕННО то место,
где дыры и заводятся. Рекомендация Ф.9 (корпус фикстур): на каждый переход
из 1-10 — не одна проба, а по одной на КАЖДЫЙ синтаксический узел,
реализующий этот переход (минимум: match arm И `if`/`while` pattern-bind
отдельно для переходов 7/9).

## 4. Что непонятно исполнителю — читая Ф.8 глазами того, кто сядет писать код

1. **Ш.3 «переиспользовать существующий обход» — переиспользовать КАК
   ЕСТЬ (с методным слепым пятном) или расширить на методы?** Текст не
   говорит. Если «как есть» — Ф.8 не покрывает подавляющее большинство
   реального Nova-кода (метод-стиль, `@`-сигилы), и это стоит признать
   явно ДО, а не после реализации. Если «расширить» — это отдельная,
   нигде не оценённая по объёму задача (метод-резолв на графе вызовов —
   качественно другая машинерия, чем `Ident`-имя свободной функции).

2. **Ш.5 «любое замыкание, присваиваемое этому типу» — на уровне какой
   области видимости?** Модуля? Всей программы (правдоподобно, раз «Nova
   собирает всю программу одним модулем»)? Если всей программы — тогда
   ЛЮБОЙ `fn(Request) -> Response` где-либо в программе (включая, скажем,
   тестовый код и dev-only маршруты) тэйнтует ВСЕ значения этого точного
   типа. Текст не уточняет, matчится ли тип НОМИНАЛЬНО (точная сигнатура)
   или структурно (любой совместимый функциональный тип) — при большом
   количестве структурно похожих `fn(ServerRequest) -> ServerResponse` по
   всему HTTP-стеку это может означать «весь Handler-типизированный код
   программы тэйнтован разом», то есть Ш.5 на практике эквивалентно
   «каждое замыкание, приводимое к Handler, всегда файбер-достижимо» —
   вопрос 5 ниже разбирает, что это значит для корпуса.

3. **Что именно означает «поле функционального типа» в Ш.5 — включает ли
   ЭЛЕМЕНТ коллекции функциональных значений?** `Vec[fn()->()]`,
   `HashMap[str, Handler]` — обычная форма таблицы маршрутов/middleware.
   Формулировка «параметр ИЛИ ПОЛЕ функционального типа» не упоминает
   контейнеры буквально. Путь 11 (Ф.7, «тэйнтованное поле, переданное
   аргументом свободной функции») и путь «переход 5 без обёртки-типа» уже
   показали, что коллекции замыканий — реальный, не краевой случай.

4. **D446 §1 «компилятор ОБЯЗАН убедиться, что все изменяющие операции
   типа атомарны либо защищены» — какой алгоритм это делает?** Во всём
   тексте Ф.8 нет ни одного шага, реализующего ИМЕННО эту фразу для
   произвольного пользовательского типа. Единственный описанный механизм
   (`share_check.rs`) проверяет СОСТАВ полей — структуру, а не порядок
   операций внутри методов. §2.1 показывает, что этого физически
   недостаточно для guard-типов вроде `MetricsRegistry`. Нужен явный
   ответ: это будущая, отдельно оцениваемая работа, или предполагается,
   что «убедиться» — фигура речи, и на деле проверяется только структура
   (тогда формулировку D446 §1 стоит смягчить, чтобы не обещать больше,
   чем алгоритм умеет)?

5. **Ш.6 «граница с C — атрибут только там»: как компилятор ОТЛИЧАЕТ
   «замыкание уходит в C» от «замыкание уходит в Nova-код, который уходит
   в C»?** Если Nova-функция-обёртка принимает замыкание и передаёт его
   ДАЛЬШЕ в `extern`-вызов не на границе (не в момент передачи, а через
   несколько кадров), Ш.5's консервативное правило и Ш.6's атрибут-на-
   границе могут не встретиться — по факту это ещё одна форма return-
   escape / многохоповой передачи (переход 2 глубже одного хопа, уже
   отмечен Ф.7 как текущий молча).

6. **Обратный обход (Ш.7) — на чём именно он останавливается?** Для
   `#thread_affine` диагностика печатает «минимум один промежуточный
   фрейм». Для Ш.4 (замыкания, созданные СНАРУЖИ и дошедшие до файбер-
   контекста) обратный обход должен дойти до МЕСТА СОЗДАНИЯ замыкания —
   но если оно дошло туда через return-escape + сохранение в поле
   структуры + чтение через несколько модулей (межмодульная форма,
   честно названная неразведанной), какая ГЛУБИНА обхода гарантируется
   текстом, а какая — эвристика «покажем что сможем»? Пользователю,
   получившему диагностику без пути до создания, будет так же непонятно,
   как непонятен был `on_child_fail` до расследования №173.

## 5. Достижим ли Ф.8 до тега — и не окажется ли грубый заслон слишком грубым

**Формулировка грубого заслона (СРОК ПРОДОЛЖЕНИЯ 2026-08-04):** «значение с
изменяемым состоянием уходит наружу в контекст, где позже возникает
параллельность». Проверено на реальных местах, не умозрительно (§2.1):

**Прямой ответ — ДА, окажется, если заслон реализовать буквально по этой
формулировке.** `ratelimit.nv`'s `ratelimit()` и `metrics.nv`'s
`metrics_export_handler` — оба буквально «значение (`table`/`reg`) с
изменяемым состоянием (мьютекс+хэшмап, реально мутируемые методами)
уходит наружу (возвращается как захват замыкания) в контекст, где позже
возникает параллельность (per-connection файберы сервера)». Это ТОЧНОЕ
описание обоих файлов. Грубый заслон, взятый буквально, обязан их
отклонить — а это два `#stable`, экспортируемых, реально работающих API,
canon-примеры «как делать шаренное состояние правильно» в собственных
комментариях корпуса.

**Минимальный заслон, который РЕАЛЬНО закрывает шесть путей, не отклоняя
этот корпус, потребует хотя бы одного исключения:** «если тип уходящего
значения (или всё, что оно транзитивно захватывает) уже несёт `#share`
ИЛИ композитно составлен целиком из `#share`/`ro`-безопасных типов —
пропустить». Но именно этого исключения `MetricsRegistry`/`BucketTable`
СЕГОДНЯ не удовлетворяют (у них нет `#share`, и структурная проверка
`HashMap`-поля отказывает — §2.1, проба A). Значит закрытие шести путей
логически ПРЕДПОЛАГАЕТ либо (а) снабдить оба типа `#share` ДО того, как
заслон встанет (миграция корпуса, ничем не гарантированная — Ф.4 плана
рассчитана на «мест по замеру», а замера для ЭТОГО класса пока нет), либо
(б) заслон ловит их как регресс в день влития, и их придётся чинить в
ТОЙ ЖЕ волне (что противоречит «одна волна энфорса» Ф.8, если чинка
требует новой примитивной формы вроде §2.1's нерешённого guard-verification
вопроса).

**Число известных живых сайтов этого класса — 2** (по грепу `.nv`-исходников
пяти пакетных реп на «поле `Mutex` рядом с полем `HashMap`/`Vec`»:
`nova-polaris/src/metrics.nv`, `nova-polaris/src/middleware/ratelimit.nv`).
Небольшое число — но оба на пути релиза (metrics-эндпоинт, rate-limiting
middleware — не периферийный код), и оба явно продвигаются в комментариях
корпуса как ОБРАЗЕЦ для будущего кода (`ratelimit.nv`: «Mutex-guarded
wrapper (canon `metrics.nv`'s own `MetricsRegistry`)») — то есть это не
«два случайных места», а ЗАЯВЛЕННЫЙ канон, которому, вероятно, будут
следовать новые файлы до тега.

**Рекомендация:** прежде чем ставить грубый заслон, замерить (тем же
методом, что план 248 Ф.1 — «пересчитать по корпусу») сколько мест
сочетают «мьютекс/RwLock рядом с незащищённым по структуре полем» И
уходят наружу возвратом/регистрацией. Без этого числа решение по заслону
принимается вслепую — тем же способом, которым принималось решение по
июльской итерации.

## 6. Чего в плане нет, но должно быть

1. **Критерий приёмки Ф.8 не включает адверсарную РЕВИЗИЮ ПОСЛЕ
   реализации как условие закрытия.** Ф.9 (корпус фикстур) и Ф.10
   (ловушка на будущее) запланированы, но ПОСЛЕ тега, отдельно от Ф.8.
   Именно отсутствие такого шага (спросить «а как ещё это можно
   обойти?» ПОСЛЕ того, как код написан, ДО того, как объявлено
   «исполнено») было механизмом провала §1. План рискует повторить его
   на дистанции в один цикл: «Ф.8 сделана» может снова получиться раньше,
   чем «Ф.7-стиль адверсарная проверка САМОЙ Ф.8» — а не после неё.
   **Рекомендация:** сделать мини-Ф.7 (переприменить 12+3 пробы этого
   окна и p238-paths к РЕАЛИЗОВАННОЙ Ф.8, включая пробы A/B/C из этого
   окна) частью критерия «Ф.8 закрыта», а не Ф.9/Ф.10 отдельным пунктом
   после тега.

2. **Нет измерения «сколько composite guard-типов (мьютекс рядом с
   незащищённым полем) в корпусе»** — притом что план 248 для СОСЕДНЕГО
   вопроса (линейность атомиков) именно с такого замера и начал (Ф.1
   «пересчитать по корпусу... без этой цифры решение принимать вслепую»).
   Ф.8 не содержит аналогичного шага для guard-типов, хотя §2.1 этого
   окна показывает — вопрос ровно того же типа и ровно того же риска.

3. **Дженерики/мономорфизация признаны нерешёнными, но не поставлены
   условием НАЧАЛА реализации.** §2.3 показывает: от ответа буквально
   зависит, в какую сторону сломается корпус (ложный отказ или тихая
   дыра). Пока ответа нет, нельзя написать даже одну строку кода Ш.2 без
   риска переписывать её после решения — стоит явно назвать это
   БЛОКЕРОМ старта реализации, а не открытым вопросом внутри уже идущей
   волны.

4. **Нет признака «волна закрыта по-настоящему», отличного от «гейт
   зелёный».** Ровно этого не хватало в июле (§1). D446 сама формулирует
   УТВЕРЖДЕНИЕ — но план нигде не говорит, ЧЕМ, кроме зелёного гейта и
   позитивных/негативных фикстур, ФАКТ реализации будет отличаться по
   методу приёмки от факта июльской «✅ ИСПОЛНЕНА» две недели назад.
   Предложение: явный чек-лист приёмки Ф.8, отдельный от «тесты зелёные»:
   (а) переприменены все пробы Ф.7 + этого окна к финальному коду с
   вердиктом по каждой; (б) `ratelimit.nv`/`metrics.nv` либо продолжают
   компилироваться БЕЗ послаблений в проверке, либо явно мигрированы —
   и объяснено, почему; (в) Ш.3 явно говорит, покрывает ли граф методы,
   с числом/пробой, а не текстовым обещанием «переиспользовать».

5. **Способ доказать полноту не назван вообще** — ни для перечня
   переходов (Ф.7 сама честно пишет «полноту доказать не могу»), ни для
   покрытия каждого перехода Ш.1-Ш.7. План мог бы явно принять как
   критерий не «доказательство», а «систематическая адверсарная проверка
   по чек-листу N синтаксических узлов × M переходов» (см. §3 —
   рекомендация «по одной пробе на каждый СИНТАКСИЧЕСКИЙ узел перехода»,
   не только на переход абстрактно) — это достижимо и честно, в отличие
   от недостижимого «доказано полностью».

## Вердикт

**План 238 (Ф.6/Ф.7/D446) в МЕТОДЕ — настоящий разворот, не косметика: он
впервые формулирует утверждение (D446), выводит границу из грамматики, а
не из списка найденных багов, и адверсарно проверяет её ДО того, как
написан код проверки. Это именно то, чего не хватало в июле, и это
следует признать прямо, а не размывать в общей критике.**

**Но Ф.8 — алгоритм, который эта ревизия проверяла, — в текущем виде НЕ
гарантирует D446 и рискует повторить прошлую судьбу по КОНКРЕТНОЙ,
проверенной причине: часть машинерии, на которую он опирается
(«переиспользовать граф `#thread_affine`» — методы вне периметра по
собственной документации; структурная проверка типа `share_check.rs` —
не умеет проверять дисциплину блокировки, только состав полей), уже
сегодня, эмпирически (пробы A/B), либо отвергает реальный `#stable`-корпус
(`MetricsRegistry`/`BucketTable`), либо молча его пропускает — и план не
выбрал, какая из этих двух ошибок случится, потому что не описал
процедуру, которой не хватает (проверка дисциплины блокировки guard-типов),
для решения этой развилки.**

Одной фразой: **план даст свойство в методе исследования, но конкретно
Ф.8 в написанном виде даст очередной список форм** — потому что
воспроизводит ту же дыру, которую сам план описывает как корень июльского
провала (D441 §0: «как и вызов любой функции из файбера... компилятор
ловит только...»), только теперь дырой служит не «синтаксическая граница
spawn», а «структурная проверка типа не видит порядок операций внутри
метода» — и эта дыра ловится не гипотезой, а двумя живыми `#stable`
файлами корпуса и тремя пробами компилятора в этом окне.
