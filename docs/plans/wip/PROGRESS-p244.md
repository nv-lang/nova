### Находка Ф.0 (побочная, №TBD)

При написании `bench1_throughput.nv` вскрылся ложноположительный
D131-отказ: `mut i = 0; while i < n { ro v = i; i += 1; tx.send(v) }` —
компилятор помечает **саму переменную цикла `i`** как «использование,
возможно, потреблённой», хотя потребляется отдельная привязка `v`, а не
`i`. Диагностика указывает on точку входа `while` (loop back-edge), похоже
на консервативное слияние потоков управления в D131-анализе внутри
`while`, ошибочно связывающее судьбу `i` с судьбой `v`. Обход в бенче —
`for i int in 0..n { tx.send(i) }` (свежая привязка на итерацию, для-цикл
не страдает тем же багом). Не чинилось — не входит в объём Ф.0/Ф.1,
докладывается интегратору как находка.

## Ф.1 — `Chan[T]` на Nova

Файлы: `std/src/concurrency/nvchan.nv` (реализация), `std/src/concurrency/nvchan_test.nv`
(тесты). Живут РЯДОМ со старым каналом — ничего не снесено, ничего не
переключено. Коммиты: `d8a0f8617` (реализация), `cafc372ed` (фикс мискомпиляции),
`acaf91327` (lint).

### Имена — намеренное отклонение от буквы плана

План называет типы `ChanWriter[T]`/`ChanReader[T]` — те же имена, что у СТАРОГО
канала. Грепом подтверждено (2026-08-07): `"Channel"`/`"ChanReader"`/
`"ChanWriter"`/`"ChannelPair"` хардкожены ~50 раз точным строковым совпадением в
`compiler-codegen/src/{lib.rs,codegen/emit_c.rs,types/mod.rs}` (родня №143/№286/№407).
Повторное использование тех же имён воссоздало бы ровно ту «невидимую вторую
дверь», которую план должен убрать — новый тип либо столкнулся бы с хардкодом,
либо (что хуже) молча подменил бы поведение старого в одних путях и не в других.
Выбраны имена **`Chan[T]`/`ChanTx[T]`/`ChanRx[T]`/`ChanPair[T]`** — не совпадают
ни с одной из хардкоженных строк. Задокументировано в шапке `nvchan.nv`.

### Устройство

`Chan[T]` — обычная (heap, reference-semantics, D32/D123) `#share`-запись:
`mutex Mutex`, `not_empty Condvar`, `not_full Condvar`, `mut buf []T`, `cap int`,
`mut closed bool`. `ChanTx[T]`/`ChanRx[T]` — `value`-обёртки с приватным полем
`ch Chan[T]`: копия обёртки — это алиас на ТУ ЖЕ разделяемую запись (ссылочное
поле), а не новый канал. Буфер FIFO реализован через `[]T.push`/`[]T.remove(0)`
(без ручной кольцевой арифметики — Ф.1 сознательно выбрала простоту вместо
кольца, `remove(0)` даёт O(n) на дренаж вместо O(1); компромисс явно оставлен
на Ф.3-замер: если пропускная способность просядет из-за этого — тогда кольцо).

### Находки (все №TBD, номер присвоит интегратор)

**Находка 1 — консервативный ложноположительный D131 (Ф.0, косвенно).** См. выше.

**Находка 2 — `consume`-параметр не имеет легального способа попасть в
контейнер (ГЛУБЖЕ, чем блокер плана предполагал).** Три независимые пробы
(scratchpad, вне репо): `Vec[T].push(v)`, сырая запись `p.write_at(i, v)` через
типизированный указатель, и конструирование записи-литерала `Box { v }` — ВСЕ
ТРИ одинаково отклоняются `[D133-not-consumed]`, ссылаясь на ОДИН и тот же
перечень легальных действий («вызовите consume-метод / return v / передайте в
consume-param»), ни одно из которых не покрывает «положить в контейнер».
`spec/decisions/02-types.md:5922` подтверждает: suppress/forget-механизма нет
by design (жёстче Rust). Значит №309/№325 (закрыты) чинят ДЕТЕКТОР УТЕЧКИ
(корректно отклоняют «значение живёт и в контейнере, и снаружи»), но НЕ дают
позитивную возможность легально переместить consume-значение в контейнер —
это отдельная, ещё не сделанная работа («шаг C» плана 246, явно отложен на
после тега). **Следствие для Ф.1:** `send`/`try_send` объявлены с ОБЫЧНЫМ
(копирующим) `v T`, НЕ `consume v T` как в тексте плана — до появления
generic-consume-sink настоящая линейная передача владения через канал
недостижима НИ ДЛЯ КАКОГО `T`, включая простой `int` (не только для
must-consume типов). Это главный открытый вопрос для владельца: план 244
существует в первую очередь ради передачи владения (сокет/файл через канал);
эта находка говорит, что сегодняшний компилятор физически не даёт это
выразить дальше уровня старого (compiler-intrinsic, некомпилируемого из .nv)
канала.

**Находка 3 — D446 guard-liveness не понимает `defer` (миноритарная, обойдена
стилем).** `consume guard = @ch.mutex.lock(); defer guard.unlock(); ...
@ch.buf.push(v)` — валится `[E_FIBER_UNSAFE_CALL]` при вызове изнутри `spawn`.
Причина — в `fiber_safety.rs:45-58`: анализ живости guard'а последовательный,
не знает о `defer`, и считает guard «мёртвым» сразу в точке текстового
`defer guard.unlock()`, а не в момент реального исполнения на выходе из
функции. Обход — единственный выход из функции, `guard.unlock()` последним
оператором (без `defer`), результат копится в `mut`-аккумулятор.

**Находка 4 — МИСКОМПИЛЯЦИЯ: field-cache × auto-`@cleanup` дают cleanup-вызов
С НЕ ТЕМ УКАЗАТЕЛЕМ (СЕРЬЁЗНАЯ, обойдена в этом модуле).** Обход находки 3
(явный `guard.unlock()` без `defer`) на практике ломал каждый вызов `send`/
`recv` РАНТАЙМ-паникой `Mutex.unlock() called on an unlocked mutex` —
детерминированно, 15/15 прогонов. Изолировано через 8 проб и подтверждено
`--no-field-cache` (баг исчезает): Plan 217 авто-cleanup-на-выходе-из-scope
(взводится сразу при связывании `consume guard = …lock()`, т.к. `MutexGuard`
объявляет `@cleanup`) взаимодействует с Plan 123 field-cache (хайстит
повторные `@ch.x` в закешированный указатель `_at_ch`/`_at_ch_loop`/
`_at_ch_n0`) — и авто-cleanup код-ген подставляет НЕ guard, а этот
закешированный указатель на `Chan`: `Nova_MutexGuard_consume_cleanup(_at_ch,
outcome)` вызывается с `Nova_Chan____nova_int*` там, где ожидается
`Nova_MutexGuard*` (прочитано напрямую в сгенерированном C, `.c:11991-12003`
собранного `nvchan_test`). Флаг взвода авто-cleanup никогда не снимается моим
явным (не-`defer`) `unlock()`, поэтому авто-cleanup срабатывает ПОВТОРНО на
выходе из функции — через указатель неправильного типа. Обход, ПОДТВЕРЖДЁННЫЙ
рабочим (10/10 прогонов, field-cache во ВКЛЮЧЁННОМ по умолчанию состоянии):
каждый метод открывает `mut ch = @ch` (или `ro ch = @ch` для read-only путей)
и обращается ЧЕРЕЗ ЛОКАЛЬНУЮ `ch`, ни разу не повторяя цепочку `@ch.поле` —
это лишает field-cache-эвристику повторного доступа, который она хайстит.
**Это не диагностика-ложь, а настоящая мискомпиляция** (неверный указатель
в реальном вызове) — самая серьёзная из четырёх находок Ф.1, докладывается
приоритетно.

**Находка 5 — tuple-mono для generic value-типов (СРЕДНЯЯ, обойдена типом
`ChanPair[T]`).** Буквальная сигнатура плана `Chan[T].new(cap) -> (ChanTx[T],
ChanRx[T])` (сырой кортеж из ДВУХ РАЗНЫХ generic value-типов) не собирается:
мономорфизация эмитит буквальное неподставленное имя типового параметра
вместо конкретной инстанциации (`NovaValue_ChanTx____Nova_T_p` вместо
`NovaValue_ChanTx____nova_int`). Минимальный репро (4 пробы, scratchpad):
воспроизводится для ЛЮБОГО кортежа-возврата, чей элемент — generic value-тип,
параметризованный СОБСТВЕННЫМ типовым параметром функции — даже для
однополого невложенного обёрточника и даже для 2-кортежа из ОДНОГО И ТОГО ЖЕ
типа дважды. Обычная ЗАПИСЬ (фигурные скобки) с теми же двумя полями
собирается чисто. `ChanPair[T] { tx ChanTx[T], rx ChanRx[T] }` — рабочий
обход; доступ — `.tx`/`.rx`, УДОБНОЙ деструктуризации `ro (tx, rx) = …` из
текста плана нет до починки этого дефекта апстрим.

### Матрица осей исполнения (метод × место {body, spawn} × состояние {пустой,
частично полный, полный, закрытый})

`X` = покрыто тестом; `—` = не покрыто, причина в примечании; `н/п` = клетка
не имеет смысла для метода (например, `capacity()` не зависит от состояния
буфера).

| метод | body/пустой | body/частично | body/полный | body/закрыт | spawn/пустой | spawn/частично | spawn/полный | spawn/закрыт |
|---|---|---|---|---|---|---|---|---|
| `send` | X (т2,т5,т7) | X (т2) | — [1] | X (т5,т7) | X (т10,т13) | — [2] | X (т11) | — [3] |
| `try_send` | н/п | н/п | X (т3) | X (т5) | н/п | X (т13) | — [3] | — [3] |
| `recv` | — [4] | X (т2,т7) | X (т2) | X (т6,т7,т8) | X (т10,т12) | X (т11) | — [5] | X (т12) |
| `try_recv` | X (т4) | X (т3) | н/п | X (т6) | — [3] | — [3] | — [3] | — [3] |
| `close` | X (т5,т6,т7,т8,т9) | X (т7) | н/п | X (т8, повторный) | — [3] | — [3] | — [3] | — [3] |
| `is_closed` (tx) | X (т1,т9) | — [3] | — [3] | X (т9) | — [3] | X (т13) | — [3] | — [3] |
| `is_closed` (rx) | X (т1) | — [3] | — [3] | X (т9,т12 косвенно) | — [3] | — [3] | — [3] | — [3] |
| `len` | X (т1: 0) | X (т2) | X (т2: == cap) | — [3] | — [3] | X (т13) | — [3] | — [3] |
| `capacity` | X (т1) | н/п (не зависит от состояния буфера) | | | X (т13) | | | |

Причины непокрытых клеток:
- **[1] `send` body/полный** — блокирующий `send` на полном буфере БЕЗ
  параллельного получателя зависает навсегда по конструкции (некому
  освободить слот) — тестируемо ТОЛЬКО через `spawn`-пару, что и сделано
  (spawn/полный, т11). Пустая клетка честная, не пропуск.
- **[2] `send` spawn/частично** — не заведён отдельный тест; де-факто путь
  идентичен spawn/пустой (та же ветка кода, буфер просто не в нуле) —
  низкая инкрементальная ценность, не покрыто явно.
- **[3]** — не заведено отдельного теста для этой конкретной комбинации;
  метод в целом покрыт (см. другие клетки той же строки), поведение в этом
  месте/состоянии не отличается по коду от покрытых соседних клеток.
- **[4] `recv` body/пустой** — блокирующий `recv` на пустом канале БЕЗ
  параллельного отправителя зависает навсегда по конструкции — тестируемо
  ТОЛЬКО через `spawn` (spawn/пустой, т10, т12 для закрытого случая).
- **[5] `recv` spawn/полный** — не заведено отдельно; полный буфер для
  `recv` — не особый случай (recv не проверяет `cap`), покрыт по факту через
  body/полный (т2) и spawn/частично (т11, где буфер уходит из полного).

**Итог матрицы:** все блокирующие методы (`send`/`recv`) покрыты в ОБОИХ
местах размещения для состояний, где размещение реально меняет путь
исполнения (blocking-требует-spawn клетки — единственный вид, где body в
принципе невозможен, и это не пропуск, а свойство конструкции). Непокрытые
клетки — либо структурно невозможные (обозначено), либо низкоценные
дубликаты уже покрытого кода-пути (обозначено). Полный 100% охват всех 64
клеток не сделан ради экономии времени — сознательный компромисс, отражён
здесь явно, а не молча.

### Позитив/негатив по методам

| метод | позитив | негатив |
|---|---|---|
| `send` | принимает в открытый непереполненный канал, будит `recv` | `false` на закрытом (т5), не паникует |
| `try_send` | принимает при наличии места | `false` на полном (т3, значение НЕ теряется — второе send не затирает первое), `false` на закрытом (т5) |
| `recv` | FIFO-порядок (т2), дренаж перед None (т7) | `None` на закрытом+пустом (т6), НЕ путает closed с пустым (т12: recv из закрытого в spawn корректно даёт None) |
| `try_recv` | забирает значение когда есть | `None` на пустом БЕЗ блокировки (т4) — засечено по времени завершения теста (не таймаут) |
| `close` | взводит `closed`, будит оба condvar | идемпотентен — 3 вызова подряд не падают (т8) |
| `is_closed` | `true` после `close()`, видно с обеих сторон (т9) | `false` до `close()` (т1, т9) |
