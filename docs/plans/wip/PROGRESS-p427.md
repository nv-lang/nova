## Шаг 1 — воспроизведение и классификация

### Метод

Команда мега-CU — байт-в-байт из `.github/workflows/nova-gate.yml`:
```
./nova-cli/target/release/nova test --positive --compile-error --timeout 300 --jobs 4 spec_tests/conformance
```
(без `--mode` → C-компиляция в Dev-режиме — подтверждено отдельным
`--keep-artifacts`-прогоном одного файла, «Toolchain: clang, mode=Dev»; это
ТОЧНО совпадает с тем, что реально гоняет CI, никакого расхождения режимов
нет).

Стресс-скрипт (`~/stress_mega.sh`, локальный, не коммитится) гоняет эту
команду в цикле, парсит `PASS: N FAIL: M` (правило «ассертить строку PASS,
не просто built» — `feedback-gate-filter-must-assert-pass-line`) и грепает
stderr на 6 известных сигнатур (SIGSEGV/MCO_NOT_SUSPENDED/stack
smashing/cancel-throw/core dumped/panic).

Отдельно, для быстрой итерации по наиболее вероятному носителю (см. ниже) —
`~/bin/pmfc_standalone`: `fn main()`-обёртка вокруг ТЕЛА
`spec_tests/conformance/standalone/pos_max_fibers_concurrent.nv`
(единственное отличие от `test`-блока — синтаксическая обвязка, тело
идентично: `CancelToken.new()` → `supervised(cancel: tok)` → 2000×`spawn{
(10_000).to_millis().sleep() }` + один `spawn` с `(30).to_millis().sleep();
tok.cancel()`), собранная напрямую через `nova build -o` (минуя эфемерный
`--keep-artifacts`-каталог test-harness'а — см. «Протокольная находка» ниже).
`ENV NOVA_MAX_FIBERS=20000 NOVA_MAXPROCS=1` того же файла воспроизведены как
переменные окружения при запуске.

### Протокольная находка (для памяти следующего исполнителя)

`nova test`/`nova test-build --keep-artifacts` кладёт артефакты в
`/tmp/nova_tests-<pid>/t-<hash>/`, и `TmpDirGuard`/`TempSubdir` в
`main.rs`/`test_runner.rs` формально уважают флаг `keep` (Drop
пропускается). Тем не менее на этой машине каталог исчезает **между двумя
последовательными командами одной и той же WSL-сессии** (подтверждено:
`find`/`ls` находит файл сразу после сборки, тот же путь через одну команду
позже — уже нет; не связано с PID-коллизией, не связано с `find -type f`
против `-iname`, воспроизведено многократно). Похоже на внешний агрессивный
`/tmp`-уборщик (systemd-tmpfiles или аналог), не на баг `--keep-artifacts`
как такового — не расследовано до конца (не входит в мандат этого окна,
не concurrency-баг). **Обход:** для standalone-повторов с `fn main()`
собирать через `nova build -o <путь-в-HOME>` (не эфемерный tmp, кладётся
куда велено). Для мега-CU (harness сам синтезирует объединённый `main()` из
всех `test`-блоков — руками не воспроизводимо) этот обход не годится:
использован просто повторный вызов `nova test` целиком, без попытки
удержать сам собранный `a_q3`-бинарь для отдельного gdb-постмортема.

### Честная статистическая оценка (почему это НЕ опровергает реестр)

По плейбуку (`debugging-races.md` §1, эвристика `n ≥ ⌈-ln(0.01)/p⌉`): при
заявленных владельцем 3-5% нужно `n=92..154` для 99%-уверенности поймать
хотя бы одно срабатывание. На **~20** прогонах полного мега-CU вероятность
«чисто, хотя баг реален» — `(1-p)^20`: при `p=0.03` → **54.4%**, при
`p=0.05` → **35.8%**. То есть чистая серия из ~20 прогонов **statистически
ожидаема**, даже если реестровые 3-5% верны, — это НЕ опровержение находки
p418, а просто недостаточная выборка для этого бюджета окна.

`pos_max_fibers_concurrent`-эквивалент (200 прогонов) — более сильный
сигнал ИМЕННО для этой фикстуры: `(0.97)^200 ≈ 0.23%`, `(0.95)^200 ≈
0.0035%`. Если бы весь реестровый флейк концентрировался в этом ОДНОМ
сценарии (что было гипотезой — см. ниже), 200 чистых прогонов делают это
практически невозможным. Значит: **либо флейк НЕ сконцентрирован в
`pos_max_fibers_concurrent`** (он размазан по другим ~695 файлам мега-CU
или зависит от порядка/состояния, которое даёт именно СОВМЕСТНЫЙ прогон
всех 696 тестов подряд в одном процессе — накопление GC-давления,
фрагментация арены, drift счётчиков воркеров), **либо конкретно этот
исторический носитель (`[fix-boehm-eager-cost]`, 2026-07-18, см. ниже) уже
закрыт последующими волнами** (211-spawnctx, Go-style gopark/goready
переписывание) и текущий №427 — это ДРУГОЙ, ещё не идентифицированный
носитель той же ОБЩЕЙ проблемы (гонка cancel-wake/park в мега-CU-масштабе).

### Побочная находка — уже известный, вероятно закрытый исторический носитель

`docs/plans/wip/boehm-eager-cost-notes.md` (2026-07-18, коммит `09b3194ff`,
волна `[fix-boehm-eager-cost]`, **не влита, эскалирована, не закрыта

как принятое). **200/200 чистых прогонов в ЭТОМ окне на семантически той же

park/wake на Go-модель gopark/goready, обе датированы позже 07-18 и обе

## Раздел «ранний Go как референс» (обязателен по указанию владельца)

Прочитан код планировщика Nova (`nova_sched.h`, `fibers.h`, `runtime.c`,
`driver.c`, `fiber_arena.c`) целиком в объёме, необходимом для этого
расследования. Вывод: **Nova УЖЕ архитектурно переписана под модель
раннего Go в решающей части** — это не гипотеза, а факт из кода: park/wake
называются `nova_gopark`/`nova_goready` (не эвфемизм, буквальная калька),
каждая функция несёт doc-comment с явной ссылкой `Go runtime/proc.go::
casgstatus` / `gopark`/`goready`, работа датирована «Plan 83-go-cmn»
(отдельный план именно под эту миграцию). Атомарный fiber-state (`IDLE`/
`RUNNING`/`PARKED`/`DEAD`, CAS-переходы в `nova_fiber_state_cas`) —
прямая калька `casgstatus`/`_Gidle`/`_Grunning`/`_Gwaiting`/`_Gdead`.
By-pointer (не by-index) wake через `expected_co` — прямая калька Go
`goready(gp *g, ...)` (по указателю на `g`, не по индексу очереди).

### Инварианты, которые ЕСТЬ у раннего Go и НЕТ (или устроены иначе) у Nova

1. **Канонический реестр стеков — по значению, не по вероятностному
   зонду.** Go хранит `stack.lo`/`stack.hi` ПРЯМО в структуре `g` каждой
   горутины и глобальный список `allgs` — GC сканирует РОВНО эти границы,
   у каждой горутины СВОЙ явный, актуальный диапазон, обновляемый АТОМАРНО
   при копировании/росте стека, ДО того как горутина возобновит работу на
   новом стеке. Никакого «угадывания» диапазона через карту памяти процесса
   нет и не может быть в принципе — сканер спрашивает объект, а не
   инфраструктуру ОС.
   Nova (POSIX, `fiber_arena.c`) для ГЛАВНОГО (main-body-как-fiber, №108)
   потока делает ОБРАТНОЕ: публикует один «probe»-адрес
   (`_nova_main_stack_probe`, CAS first-caller-wins — фикс №418 корня B) и
   на КАЖДОМ GC-цикле заново парсит `/proc/self/maps`, ищет VMA, содержащую
   этот адрес, и пушит её целиком. Это работает, но структурно хрупче: (а)
   зависит от успешного парсинга `/proc/self/maps` каждый раз; (б) зависит
   от того, что «первый вызывающий» гарантированно окажется правильным (сам
   факт, что для этого понадобился CAS «кто первый» — симптом отсутствия
   канонического владельца данных, а не просто гонки); (в) для НЕ-главных
   файберов диапазон берётся из арены (слот), что ближе к Go-модели
   (объект знает свои границы), но для главного — нет. **Оставшиеся
   sig-1/sig-2 SIGSEGV (не идентифицированы в этом окне) — первый
   подозреваемый по архитектурной аналогии с Go, раз этот класс УЖЕ дал
   один подтверждённый баг (№418 корень B) ровно на этой границе.**

2. **Отмена — кооперативный сигнал через канал, НЕ принудительный throw
   извне.** У Go `context.Context.Done()` — это КАНАЛ; горутина, которая
   его не слушает, просто не узнаёт об отмене — рантайм НИКОГДА не
   разворачивает чужой стек снаружи. У Nova отмена — ИСКЛЮЧЕНИЕ
   (`nova_throw_cancel`, `longjmp` в `_nova_fail_top->jmp`), доставляемое
   ИЗВНЕ в момент wake. Отсюда СТРУКТУРНО следует, что у Go **не может быть
   аналога §11** («cancel-throw outside any supervised scope» — throw в
   файбер, у которого на данный момент нет активного fail-frame): у Go
   нет никакого «throw в горутину», которое могло бы состояться до/после
   готовности приёмника — есть только чтение канала, которое горутина
   делает сама, когда сама готова. Это НЕ баг Nova, это осознанное
   архитектурное решение (ближе к Kotlin `CancellationException`/.NET
   `CancellationToken`+`OperationCanceledException`, чем к Go) — но именно
   ОНО открывает пространство для целого класса гонок (порядок
   fail-frame-restore относительно wake, §10/§11 mn-coding-conventions.md),
   которого у Go нет и не может быть. Если сигнатура §11 когда-то поймается
   повторно — это ЦЕНА архитектурного выбора, не «недоделанный Go-паттерн»;
   единственный Go-подобный способ её закрыть НАВСЕГДА — не «дошлифовать
   fail-frame-restore», а сменить модель отмены на кооперативную (вне
   мандата этого окна, архитектурное решение уровня owner).

3. **Завершение процесса при живых горутинах — Go НЕ гарантирует
   дренаж.** `os.Exit`/возврат из `main()` у Go убивает процесс, ЛЮБЫЕ
   недоделанные горутины просто исчезают — Go никогда не ждёт «сирот».
   Nova, наоборот, даёт БОЛЕЕ СИЛЬНУЮ гарантию: `nova_runtime_drain_
   orphans` (детач-файберы дожидаются завершения перед выходом,
   Plan 83.4.5.2). Это НЕ пробел Nova относительно Go — это Nova
   добровольно взявшая на себя более сложный контракт, которого у
   референса просто нет. Именно эта ДОПОЛНИТЕЛЬНАЯ сложность (порядок
   drain относительно закрытия event-loop) была корнем A в №418 — то есть
   ценой более сильной гарантии, а не заимствованным у Go дефектом.

4. **Sysmon / preemption-поток.** У Go — выделенный `sysmon`-поток без
   привязки к `P`, мониторящий зависшие горутины и будящий netpoller. У
   Nova — своя реализация того же по духу (worker preempt_flag +
   отдельный I/O-driver-поток, `driver.c`), архитектурно близко, не
   выявлено структурных расхождений в объёме, прочитанном в этом окне.

**Итог раздела:** Nova не «забыла» скопировать Go-инварианты — она
СОЗНАТЕЛЬНО выбрала более сильную/другую модель в двух ключевых местах
(cancel = исключение, а не канал; orphan-drain при выходе, а не «выживший
не гарантирован»), и именно эти ДВА расхождения — единственные места, где
Go-модель структурно ИСКЛЮЧАЕТ целый класс багов, которого у Nova нет по
конструкции. Обе цены уже частично материализовались как найденные дефекты
(№418 корень A — orphan-drain-ordering; §11-класс — cancel-как-throw).
Третье место (канонический реестр стеков vs probe-зонд) — единственное, где
Go-модель СТРОГО лучше БЕЗ компромисса по семантике (просто больше
инженерной работы: завести явный per-fiber stack-bounds registry, обновляемый
атомарно при spawn/resume, вместо probe+`/proc/self/maps`) — рекомендация
следующему окну, если оставшиеся 2 SIGSEGV окажутся в этом классе.

## Диагноз для владельца — честно, не приукрашивая

**Корень №427 НЕ найден в этом окне.** Это не «частично закрыто» и не
«закрыто с оговоркой» — это **невоспроизведено при бюджете ~26 полных +
200 изолированных прогонов**, что playbook (`debugging-races.md` §1)
прямо называет недостаточным для заявленной частоты 3-5% (нужно n≥92-154).
Zero-tolerance повторяю явно: недоказанный concurrency-фикс не отгружался,
никаких спекулятивных правок в `nova_rt/**` в этом окне нет (`git diff`
пуст, кроме этого файла и файла реестра — если такие правки будут
запрошены отдельно).

**Что сделано и что осталось предметно полезным для следующего окна:**
1. Подтверждена команда/режим воспроизведения (байт-в-байт CI, Dev-mode).
2. Найдена и задокументирована протокольная ловушка `--keep-artifacts`
   (эфемерный `/tmp` теряет файлы между командами на этой машине) — обход
   через `nova build -o` в HOME для standalone-случаев.
3. Сильный (200 прогонов) сигнал, что исторический носитель §11
   (`pos_max_fibers_concurrent`, волна `[fix-boehm-eager-cost]`,
   2026-07-18, НЕ закрытая формально) — по всей видимости, закрыт ПОБОЧНО
   более поздними волнами (211-spawnctx и/или Go-style gopark/goready).
   Стоит формально закрыть тот старый маркер отдельной проверкой (вне
   мандата №427).
4. Найдена и задокументирована честно (не починена) унаследованная
   perf-регрессия latency +84.5% относительно эталона Ф.0 плана 244 —
   вероятная причина названа (SEQ_CST на пути park), не доказана
   экспериментально (потребовало бы трогать код параллельно с активным
   поиском гонки — риск смешать два расследования).
5. Раздел «ранний Go» — 3 архитектурных расхождения, с честной оценкой
   какие — цена сознательного выбора, а какое — кандидат на улучшение.
6. **Рекомендация следующему окну:** серия минимум n=100+ полных
   мега-CU-прогонов (при ~250с/прогон это ~7 часов чистого времени —
   спланировать отдельным бюджетом, не внутри обычного окна) ЛИБО
   целенаправленный state-dump/tripwire-инструментаж (R1-R3 по
   mn-coding-conventions.md §12), поставленный ПРЕВЕНТИВНО в cancel-wake/
   park-путь и оставленный включённым на много прогонов подряд — это
   даст находку быстрее, чем догонять голую частоту.
