Окно: p363-operand. Модель: sonnet. Дата: 2026-08-05. Ветка `p363-operand`,

## Вердикт одной строкой

**Тихая порча НЕ ПОДТВЕРЖДЕНА.** Дефект реален, но во ВСЕХ опробованных
формах (вид оператора, вид операнда, глубина вложенности, размер
compile-unit'а) он даёт **детерминированный жёсткий отказ сборки на этапе
C** ("passing 'NovaTuple_X' to parameter of incompatible type
'NovaTuple_X *'; take the address with &"), никогда — неверное значение при
успешной компиляции. Корень найден точно (файл+строки), фикс внесён в
чекер-соседний легаси-файл `emit_c.rs` **net-zero по числу строк**
(64545 → 64545, храповик не тронут), проверен на репро и на
`nova check std/src --strict-effects` (канон 148/26/61 байт-в-байт).
RUN-FAIL, который окно p-bignum-tuple наблюдало для `@mant * other.mant` в
`BigDecimal @times`, по структурному разбору **не может быть этим
дефектом** (см. «Почему BigInt не задет» ниже) — вероятная причина в
другом месте (скорее всего дефект C из того же PROGRESS, кросс-файловый
`Nova_BigInt_method_equal` conflicting types).

## Корень дефекта

`compiler-codegen/src/codegen/emit_c.rs`, десугаринг бинарных операторов
на `NovaTuple_X` (named tuple):

- арм `==`/`!=`/`+`/`-`/`*`/`/` (было ~34246-34266, до фикса);
- арм `<`/`<=`/`>`/`>=` через `@compare` (было ~34288-34294, до фикса) —
  тот же паттерн, отдельная копипаста (№247 [M-named-tuple-compare-
  operators-no-dispatch]).

Оба materialize'уют ЛЕВЫЙ операнд (`l`, ресивер) в адресуемый temp
(`&(recv_tmp)`) — это обязательно, т.к. ресивер именованного кортежа
**всегда** передаётся по указателю (D215/128, Plan 172.13). Но ПРАВЫЙ
операнд (`r`, аргумент `other`) до фикса передавался **всегда как есть**,
без `&(...)`, независимо от того, чего хочет C-сигнатура вызываемого
метода.

ABI параметра `other` (значение vs указатель) для именованных кортежей
решается ДРУГИМ, независимым проходом — `method_byref_flag` (Plan 172.14,
`emit_c.rs:55918`, "a large — >16B — `ro` value-struct param is
auto-by-ref"), потребляемым в `params_c` (`emit_c.rs:19790`, строка
~19831) при эмиссии САМОЙ сигнатуры метода. Десугаринг оператора (два арма
выше) эту функцию не консультировал вовсе — притом что СОСЕДНИЕ ветки того
же файла (структурный `emit_field_eq`, value-record арифметика) её уже
консультируют (`emit_c.rs:21021`, `:34385`, `:34427` — грепом видно, что
паттерн `|| self.method_byref_flag(...)` для этого класса решений уже
существовал в трёх других местах, просто не в этих двух).

Итог до фикса: когда `other`-параметр — **значение** (маленький тип, не
вкладывает другой named tuple), бага НЕТ — бинарный оператор просто
случайно совпадает с ожидаемой C-сигнатурой. Когда `other`-параметр —
**указатель** (`method_byref_flag` истинна — тип >16 байт, типично
named tuple, вкладывающий ДРУГОЙ named tuple полем), бинарный оператор
даёт CC-FAIL 100% воспроизводимо, в любом контексте.

## Почему BigInt (реальный репро-кейс дефекта Б) не задет

`BigInt(sign Sign, limbs []u32)` — оба поля ПРИМИТИВНЫ с точки зрения ABI
(enum-тег + Vec-хендл), внутри себя НЕ вкладывает другой named tuple.
`method_byref_flag("BigInt", "times"/"equal", 0)` для такого типа с высокой
вероятностью **false** (структура укладывается в 16 байт или около того) —
то есть `@mant * other.mant` (обе стороны — `BigInt`) идёт по by-value ветке
ABI, где дефект Б не проявляется вовсе, компиляция и значение корректны.
`BigRat(num BigInt, den BigInt)` — ВКЛАДЫВАЕТ `BigInt` дважды → >16 байт →
`method_byref_flag` true → `a == b` на `BigRat` ловит дефект Б жёстким
CC-FAIL (это и есть подтверждённый минимальный репро окна p-bignum-tuple).
`BigDecimal(mant BigInt, scale int)` — сам `@times`/`@equal` НЕ вызывает
дефект Б через `*`/`==` НА СЕБЕ (BigDecimal как операнд), а `@mant *
other.mant` — это `BigInt * BigInt`, у которого other-ABI by-value.
Наблюдавшийся RUN-FAIL в связке `div→times→equal` — вне зоны действия
исправленного здесь дефекта; см. §"Смежные находки" ниже.

Границы явления, установленные таблицей:
- **Оператор**: не важен — `==`, `+`, `*`, `<`/`>` все идут через одни и те
  же два арма (метод-имя различается, код общий).
- **Вид операнда**: не важен — `@field`, `other.field`, голая локальная
  все ломаются одинаково, когда `other`-ABI указатель (это НЕ то, что
  предполагал исходный диагноз "теряет адресацию именно для проекции
  поля" — на самом деле теряется адресация ВСЕГДА для правого операнда,
  просто для голых локальных типов с by-value ABI потеря незаметна).
- **Определяющий фактор — РАЗМЕР/ФОРМА ТИПА ОПЕРАНДА**: вкладывает ли он
  другой named tuple полем (>16 байт, `method_byref_flag` true). Named
  tuple из только примитивов/коллекций — не задет никогда.
- **Глубина цепочки / размер compile-unit'а**: не влияет вовсе — репро №4
  воспроизводится и в изолированной однофайловой сборке, и не
  воспроизводится в раздутом 6-файловом/15-тестовом CU для §5/6 (by-value
  случай остаётся верным в обоих масштабах).
- **Компиляция vs исполнение**: во всех формах, где дефект вообще
  проявляется, это ЖЁСТКИЙ ОТКАЗ СБОРКИ, не тихая порча значения.

## Фикс

`compiler-codegen/src/codegen/emit_c.rs`, два site:
- ~34248-34263 (арм `==`/`+`/`-`/`*`/`/` на `NovaTuple_X`);
- ~34289-34295 (арм `<`/`<=`/`>`/`>=` через `@compare` на `NovaTuple_X`).

В обоих: правый операнд `r` теперь оборачивается в `&(...)`, когда
`self.method_byref_flag(type_name, method_name, 0)` истинна (тот же предикат,
что уже используют `emit_field_eq`-путь и value-record арифметика для
ИДЕНТИЧНОГО решения — паттерн `|| self.method_byref_flag(...)` был скопирован
из существующих трёх мест, не изобретён заново). Изменение внесено
**net-zero по числу строк** файла (переписаны существующие строки, не
добавлены новые) — храповик стоял ровно в базе (64545/64545), любая новая
строка немедленно роняла бы гейт; после фикса файл всё ещё ровно 64545
строк.

Известное ограничение фикса (не покрыто исходным репро №363, не чинил): если
`r` — RVALUE (например `a == P363Rat.new(x, y)`, а не переменная), `&(r)` на
rvalue незаконен в C — по тому же классу, что уже решён для `l` через
`recv_tmp`-материализацию (комментарий "rvalue-receiver concern" на месте
правки). Правый операнд `l` этого никогда не требовал раньше, потому что
он никогда не терял адресацию (только приёмник материализовался). Оставлено
как есть — вне заявленной формы бага (там `r` — всегда lvalue: `@field`,
`other.field`, голая локальная).

## Смежные находки (текстом, номера не присваиваю)

1. **№247-копипаста дублировала дефект Б.** Арм `<`/`<=`/`>`/`>=` через
   `@compare` (закрыт под №247 как "no dispatch at all" — до того момента
   операторы ordering вообще не диспетчились) скопировал ТОТ ЖЕ паттерн
   потери адресации правого операнда, что и арм `==`/арифметики — при
   закрытии №247 симптом (CC-FAIL на >16Б типах через `<`/`>`) видимо не
   тестировался с достаточно большим named tuple, чтобы поймать. Фикс
   этого окна закрывает обе копии разом.
2. **RUN-FAIL из PROGRESS-p-bignum-tuple.md (дефект Б, "побочное
   наблюдение") по структуре НЕ объясняется этим дефектом** — см. разбор
   выше ("Почему BigInt не задет"). Вероятный кандидат — дефект C того же
   документа (кросс-файловый `Nova_BigInt_method_equal` conflicting types,
   implicit-declaration гонка) — тот класс УЖЕ известен как потенциально
   тихий (implicit declaration в C иногда warning, не error, в зависимости
   от того, что компилятор увидел первым) и остаётся неисследованным в
   ЭТОМ окне (вне мандата — задание было специально про дефект Б/№363).
   Рекомендация: отдельное окно на дефект C с той же методологией (сначала
   ВЫЧИСЛИТЬ значение, не только "собирается ли").
3. **Исходная формулировка задания ("теряет адресацию именно для
   проекции поля") была диагнозом по симптому, не по коду.** Прямое чтение
   `emit_c.rs` показывает: адресация правого операнда терялась ВСЕГДА
   (не только для `@field`/`other.field`), но для типов с by-value
   `other`-ABI (в т.ч. `BigInt`) это не давало наблюдаемого эффекта —
   отсюда иллюзия, что дело в форме операнда, тогда как реальный фактор —
   форма/размер ТИПА.
