### Классификация каждого попадания

По намерению копирования — три класса:

**А. Свежее объявление + прямой захват (безопасно и без разбора).**
Подавляющее большинство: `mut x = Atomic*.new(...)` объявлена один раз,
дальше либо используется напрямую, либо захватывается mut'ом в ОДНО
(или несколько, но из ОДНОЙ и той же лексической переменной) замыкание
`spawn`/`detach`/effect-хендлера. Сюда попадают: все тестовые файлы
(`sync_test.nv`, `core_test.nv`, `supervised_deadline_test.nv`,
`supervisor_test.nv`, `background_test.nv`), `net/policy.nv`'s
`timed_out AtomicBool` (захват в `Fail`-хендлер), `net/serve.nv`'s
`failed AtomicBool` в `run_request` (захват в `Supervisor`-хендлер +
`spawn`), все 9 examples-файлов, включая флагман-агрегатора
`main.nv`'s `mut inflight = AtomicInt.new(0)` — тот же паттерн, что и
`serve.nv`'s `inflight`/`reject_log`: объявлена ДО `while`-цикла,
`fetch_add`/`fetch_sub` вызываются и снаружи, и внутри `detach`,
заведённого на КАЖДОЙ итерации цикла accept-loop'а.

Для класса А доказано пробой (см. «Проба 1» ниже), что общая ячейка
после перехода на значение-внутри СОХРАНЯЕТСЯ автоматически — никакой
переделки не требуется.

**Б. Поле в value-record, скопированное с намерением разделить ячейку.**
Ровно 3 места во всём корпусе (подтверждает число из p248-nocopy2, но с
полным пересчётом по расширенному списку файлов — новых мест не
нашлось):

1. `std/src/net/tcp.nv:39,58,60` — `TcpStream.rc AtomicInt` +
   `share_copy(h, rc) -> TcpStream => { handle: h, rc }` (`@share()`,
   строка 296). Разбор — ниже, класс Б1.
2. `nova-polaris/src/middleware/log.nv:56-65` — `AccessLog.counter
   AtomicInt`. Уже заведено в реестре как
   [№354](../221.1-bug-sweep.md) (🔴 открыт на момент этого окна),
   починка описана: перенести счётчик в замыкание, которое
   `@middleware()` строит (образец `ratelimit.nv`). Разбор — класс Б2.
3. `nova-polaris/src/net/serve.nv:71-112` — `RejectLog{count,
   window_start_ms AtomicInt}`, метод `@record()`. Разбор — класс Б2
   (НОВАЯ находка этого окна: чинится тем же приёмом, что и AccessLog,
   но не идентичным способом — см. ниже).

### Проба 1 (класс А) — переживает ли общая ячейка переход на значение-внутри для «объявлена один раз, захвачена в цикле spawn/detach»

Имитация `serve()`/`main.nv`'s формы (`mut` вне `while`-цикла, новое
`spawn`/`detach`-замыкание на каждой итерации): `scratch_p248sc/probeA2/
main.nv`.

```nova
#share
type ShareCounter value priv { n int }
fn ShareCounter.new() -> ShareCounter => { n: 0 }
fn ShareCounter mut @bump() { @n = @n + 1 }
fn ShareCounter @get() -> int { @n }

fn main() Detach {
    mut sc = ShareCounter.new()
    mut i = 0
    while i < 5 {
        supervised { spawn { sc.bump() } }
        i = i + 1
    }
    println("probeA2 sc.get()=${sc.get()}")
}
```

`nova check` — ok. `nova build` + запуск: **`probeA2 sc.get()=5`** — все
5 замыканий, заведённых на разных итерациях цикла, мутировали ОДНУ
ячейку (не 5 независимых копий, что дало бы `0`). Проверено на
сгенерированном C (см. проба 3 ниже) — переменная, чей адрес убегает
через захват, аллоцируется в куче (`nova_alloc`) СРАЗУ в точке
объявления, поэтому все обращения к ней (в т.ч. из разных
замыканий-литералов на разных итерациях) идут через один и тот же
указатель.

**Вывод по классу А: 0 мест требуют переделки.** Механизм
эскейп-промоута (D216, ниже) работает по лексической переменной, а не
по экземпляру замыкания — не важно, сколько раз и в скольких циклах
создаётся замыкание, если оно каждый раз захватывает ОДНУ И ТУ ЖЕ
внешнюю переменную.

### Класс Б1 — `TcpStream.rc` (`@share()`) — ДЕЙСТВИТЕЛЬНО нуждается в общей ячейке

`@share()` — это НЕ захват переменной в замыкание, это функция
(`share_copy(h, rc) -> TcpStream => { handle: h, rc }`), возвращающая
НОВОЕ, структурно независимое значение `TcpStream`, которое может быть
`consume`-передано в другой файбер, сохранено, возвращено из функции —
то есть ровно то самое «N независимых значений языка обязаны разделять
одну ячейку», для чего лексический эскейп-промоут (привязанный к ОДНОЙ
переменной) не помогает: у каждой копии — своя переменная-декларация.

**Проба 2** (`scratch_p248sc/probeA8/main.nv`) — прямая имитация формы
`share_copy`:

```nova
#share
type ShareCounter value priv { n int }
type Handle value priv { rc ShareCounter }
fn Handle.new() -> Handle => { rc: ShareCounter.new() }
fn share_copy(rc ShareCounter) -> Handle => { rc }

fn main() {
    mut original = Handle.new()
    original.rc.bump()
    original.rc.bump()
    mut second = share_copy(original.rc)
    second.rc.bump()
    println("probeA8 original=${original.rc.get()} second=${second.rc.get()}")
}
```

Результат сборки и запуска: **`probeA8 original=2 second=3`**. Если бы
ячейка была общей, оба числа совпали бы (`3`/`3`); вместо этого `second`
унаследовал значение `original` НА МОМЕНТ КОПИРОВАНИЯ (2), затем разошёлся
после своего `bump()` (3), а `original` остался при своих двух —
**независимые ячейки, ровно тот тихий баг**, который план и разведка
p248-nocopy2 предсказывали для этого места.

**Вывод: `TcpStream.rc` — единственное место в корпусе, где общая ячейка
нужна ПО СУЩЕСТВУ**, и её не получить эскейп-промоутом — нужен настоящий
указатель (или другой механизм разделяемого владения).

### Класс Б2 — `AccessLog.counter` и `RejectLog` — чинятся БЕЗ общей ячейки, но РАЗНЫМИ приёмами

**`AccessLog.counter`** — уже разобран и заведён как
[№354](../221.1-bug-sweep.md): перенести счётчик из поля конфига в
переменную, которую замыкает СТРОЯЩЕЕСЯ ОДИН РАЗ замыкание
`@middleware()` (образец — `ratelimit.nv`'s `mut table = BucketTable.new()`
+ `middleware(fn(...) => rl_apply(..., table, ...))`). Это класс А
(одна декларация, один захват), после переноса разделение исчезает
как вопрос вовсе — подтверждено пробой 1 (класс А работает).

**`RejectLog` — НОВАЯ находка этого окна: чинится, но НЕ переносом в
замыкание (замыкания в `serve()` создаются ЗАНОВО на каждой итерации —
устройство другое, чем у `@middleware()`), а удалением промежуточной
локальной копии внутри `@record()`.**

Сегодняшний код (`serve.nv:87-91`):
```nova
fn RejectLog @record() Time {
    mut count = @count
    mut window_start = @window_start_ms
    ro n = count.fetch_add(1) + 1
    ...
}
```
Паттерн `mut count = @count` — тот же обход, что и в `AccessLog`'s
`fresh_id` (№334/337) — работает СЕГОДНЯ только потому, что `AtomicInt`
— указатель: копия несёт тот же адрес. Проба (ниже) подтверждает: после
перехода на значение-внутри эта форма молча заводит независимый
счётчик.

**Проба 3a** (`scratch_p248sc/probeA3/main.nv`) — точная форма (RO-ресивер
`@record()`, копия поля в `mut`-локаль, RO-захват `rl` в цикле
spawn/detach): сборка+запуск дают **`probeA3 rl.peek()=0`** — подтверждён
тихий баг, ровно как предсказано планом.

**Проба 3b** (`scratch_p248sc/probeA7/main.nv`) — та же форма, но БЕЗ
промежуточной копии (`@count.bump()` напрямую по цепочке self, `@record()`
остаётся RO-ресивером — сигнатура НЕ меняется), `rl` объявлена `mut`
(как и сегодня — `mut reject_log = RejectLog.new()` в `serve()`, строка
528):

```nova
fn RejectLogSim @record() {
    @count.bump()          // было: mut count = @count; count.bump()
}
fn main() Detach {
    mut rl = RejectLogSim.new()
    mut i = 0
    while i < 5 {
        supervised { spawn { rl.record() } }
        i = i + 1
    }
    println("probeA7 rl.peek()=${rl.peek()}")
}
```

Результат: **`probeA7 rl.peek()=5`** — все 5 итераций накопились в ОДНОЙ
ячейке. Решающий фактор — не мутабельность РЕСИВЕРА метода (RO-ресивер
`@record()` работает одинаково в обеих пробах), а мутабельность
БИНДИНГА `rl` самого по себе: если внешняя переменная объявлена `mut`
(даже если внутри вызывается только RO-метод), она эскейп-промоутится
при захвате в spawn/detach, и ВСЕ последующие замыкания разделяют один
и тот же промоут. Контрольная проба (`scratch_p248sc/probeA6/main.nv`,
`ro rl` вместо `mut rl`, тот же код метода) даёт **`probeA6
rl.peek()=0`** — независимые копии, подтверждает, что дело именно в
мутабельности биндинга, а не в чём-то ещё.

**Вывод по `RejectLog`: не нужно ни разделение по существу, ни перенос
в замыкание — достаточно убрать паттерн «скопировать поле в mut-локаль,
мутировать копию» внутри `@record()` (2 строки правки).** Сегодняшний
`mut reject_log = RejectLog.new()` (биндинг уже `mut`) остаётся как
есть. Правка чисто механическая, не найдена в реестре 221.1 — стоит
завести отдельным пунктом при реализации волны (номер не присваиваю,
не мой мандат в этом окне).

### ИТОГОВОЕ ЧИСЛО (вопрос 1)

| место | тип разделения | нужна ли общая ячейка после починки |
|---|---|---|
| `TcpStream.rc` (std/net/tcp.nv) | `@share()`, независимые Nova-значения | **ДА** |
| `AccessLog.counter` (nova-polaris) | поле конфига, копия-с-намерением | нет (№354, перенос в замыкание) |
| `RejectLog` (nova-polaris) | поле, копия-с-намерением, цикл spawn | нет (убрать локальную копию в `@record()`) |
| все места класса А (≈15 попаданий, 6 файлов std-тестов + 2 std/polaris + 9 examples) | прямой захват одной переменной | нет (эскейп-промоут работает как есть) |

**Общая ячейка нужна в 1 месте из всего корпуса, и оно ВНУТРИ std**
(`std/src/net/tcp.nv`). **Вне std — 0 мест.**

Это меняет вывод предыдущего окна (p248-nocopy2), которое консервативно
насчитало 3 места «требуют переписывания» — переоценка была в том, что
все три места разбирались КАК ОДИН класс («поле в value-record,
разделяемое через copy-семантику указателя»), без пробы на то, чинится
ли каждое эскейп-промоутом. Проба показала: чинится 2 из 3, причём
разными, не взаимозаменяемыми приёмами (AccessLog — вынос состояния;
RejectLog — снятие локальной копии), и только `TcpStream.rc` устоял.

## Вопрос 2 — требует ли указатель на атомик пользовательского `unsafe`

### Метод

Пробы на игрушечном `type Counter value priv { n u32 }` — представитель
целевой формы `AtomicU32 value priv { v u32 }` — без атомарности как
таковой (сама атомарность не влияет на unsafe-гейтинг, это чисто
про доступ через указатель). `nova check` на каждой пробе отдельно,
дословные вердикты ниже.

### Дословные вердикты

| проба | код | вердикт `nova check` |
|---|---|---|
| `probeB1` | `type Holder value priv { p *mut Counter }` (объявление поля-указателя) | `ok` |
| `probeB2` | `ro p = &c` (взятие адреса) | `ok` |
| `probeB3` | `ro p = &c; ro n = p.get()` (авто-деref, RO-метод, БЕЗ `unsafe`) | `ok` |
| `probeB4` | то же, обёрнуто в `unsafe { }` | `[E_UNSAFE_UNUSED] unsafe {{ }} block contains no operation that requires unsafe context (D216 §21 map: raw &x, *p/p[i] deref-family, pointer order-compare, calling unsafe fn/*unsafe fn(...), reading/narrow-casting a uninit T binding, or calling a raw-pointer intrinsic method — .read()/.write()/.read_at()/.write_at()/.offset()/.dist()/etc). Remove the unsafe {{ }} wrap...` |
| `probeB7` | `mut p = &c; p.bump()` (авто-деref, MUT-метод через указатель, БЕЗ `unsafe`) | `ok` |
| `probeB5` | `ro cc = *p` (явный деref, БЕЗ `unsafe`) | `[E_UNSAFE_REQUIRED] *expr pointer dereference requires unsafe context (Plan 118 D216 §8). Wrap expression в unsafe { ... } block, или mark enclosing fn #unsafe.` |
| `probeB5b` | то же, обёрнуто в `unsafe { }` | `ok` |
| `probeB6` | `p.write(v)` (raw-pointer intrinsic-метод), `mut p = &c`, БЕЗ `unsafe` | `[E_POINTER_RO_ASSIGN] cannot call .write() through a readonly pointer — *T is a readonly pointee...` (не unsafe-ошибка — ДРУГАЯ, о мутабельности pointee) |
| `probeB6b` | то же ВНУТРИ `unsafe { }`, `mut p = &c` (без явной аннотации типа) | ТА ЖЕ ошибка `E_POINTER_RO_ASSIGN` — `mut p = &c` НЕ авто-выводит `*mut Counter` для `.write()`-intrinsic-пути (хотя для авто-деref-метода `p.bump()` в probeB7 то же самое `mut p = &c` сработало) |
| `probeB6c` | `mut p *mut Counter = &c` (явная аннотация pointee-mut) + `unsafe { p.write(...) }` | `ok` |

### Прогон runtime (подтверждение, что мутация через указатель видна снаружи)

`scratch_p248sc/probeB7ctrl3/main.nv` (поле `int`, не `u32` — см.
оговорку ниже): `mut p = &c; p.bump(); p.bump(); ro r = c.get(); ro rp =
p.get()` → сборка ok, запуск: **`probeB7ctrl3 r=2 rp=2`** — две мутации
через указатель видны и через сам указатель, и через оригинальную
переменную `c`.

**Оговорка (не по теме вопроса, но встретилась и стоит записать):**
ровно тот же код с полем `u32` вместо `int` (`type Counter value priv {
n u32 }`, `@n = @n + 1u32`) НЕ СОБИРАЕТСЯ — codegen-ошибка `use of
undeclared identifier 'u32'` / `no member named 'u32' in struct
NovaValue_Counter` (компилятор путает суффикс литерала `1u32` с именем
поля при генерации C для `mut`-метода с арифметикой на `u32`-поле).
Не мой мандат чинить (компилятор не трогать), но это ПОТЕНЦИАЛЬНО
блокирует буквальную форму `AtomicU32 value priv { v u32 }`, ЕСЛИ её
методы реализованы через нативную Nova-арифметику. Реальные методы
`AtomicU32` в плане — `extern "nova" fn ... @fetch_add(...)` (внешние
интринсики, не Nova-уровня `+`), так что этот баг, скорее всего, НЕ
блокирует реализацию — но стоит перепроверить пробой в фазе реализации,
не полагаясь на этот вывод молча.

### Вывод (вопрос 2)

**Указатель на атомик НЕ требует пользовательского `unsafe` для обычного
доступа через методы** (в т.ч. мутирующие). Unsafe требуется ТОЛЬКО для:
- явного `*p` (голый деref-read/write) — retракция по D216 §4amend/174.5
  здесь фактически НЕ действует буквально: компилятор принимает `*p`
  как READ-операцию, требующую `unsafe`, а не отклоняет её отдельным
  кодом `E_POINTER_OP_USE_METHOD`, как формулировка спеки предполагала
  (спека и реализация здесь разошлись — сообщаю фактом, не чиню);
- raw-pointer intrinsic-методов (`.write()`/`.read()`/...) — и здесь
  ЕЩЁ нужна ЯВНАЯ аннотация `*mut T` на биндинге указателя, авто-вывод
  из `mut p = &c` для этого пути НЕ срабатывает (в отличие от
  авто-деref метода `p.bump()`, где срабатывает).

Значит: если общая ячейка (для `TcpStream.rc` и любых будущих
аналогов) реализуется как указатель НА value-внутри атомик, а доступ к
нему всегда идёт через METHOD CALL (`p.fetch_add(...)`, `p.load()`) —
ровно так, как сегодня написаны все методы `AtomicInt`/`AtomicU32` —
**пользовательский код, вызывающий эти методы через такой указатель, НЕ
обязан оборачивать вызовы в `unsafe`.** `unsafe` понадобится только
ВНУТРИ реализации самого разделяемого типа (в `std`), если она использует
`*p`/`.write()`/`.read()` напрямую — что и сегодня так (текущий
`AtomicInt` уже реализован через `extern "nova"` без пользовательского
`unsafe` в вызывающем коде).

## Вопрос 3 — где живёт ячейка: не получим ли висячий указатель

### Метод

Проба на функцию, которая объявляет значение ЛОКАЛЬНО и возвращает
указатель на него — самый прямой тест на то, работает ли эскейп-промоут
для escape-через-`return`, а не только для escape-через-захват-в-файбер
(о чём явно спрашивает бриф).

### Проба (`scratch_p248sc/probeC1/main.nv`)

```nova
type Counter value priv { n int }
fn Counter @get() -> int { @n }
fn Counter mut @bump() { @n = @n + 1 }

fn make_counter() -> *mut Counter {
    mut c = Counter { n: 0 }
    return &c
}

fn main() {
    mut p = make_counter()
    p.bump(); p.bump(); p.bump()
    ro n = p.get()
    println("probeC1 n=${n}")
}
```

`nova check` — `ok`. Сборка (`nova build --keep-artifacts`) — успешна.
Запуск: **`probeC1 n=3`** — указатель, возвращённый из функции, после
возврата из неё по-прежнему адресует ЖИВУЮ, корректно мутируемую
ячейку (не висячий указатель на освобождённый кадр стека).

### Дословная проверка по сгенерированному C

```c
static NovaValue_Counter* nova_fn_7probec112make_counter(void) {
    /* SRC: mut c = Counter { n: 0 } */
    NovaValue_Counter* _nv_tmp_433 = (NovaValue_Counter*)nova_alloc(sizeof(NovaValue_Counter));
    _nv_tmp_433->n = ((nova_int)0LL);
    NovaValue_Counter* c = _nv_tmp_433;
    /* SRC: return &c */
    return c;
}
```

`c` скомпилирована СРАЗУ как `nova_alloc`-аллокация (GC-куча), а не как
стековая переменная со взятием адреса постфактум — компилятор увидел
`return &c` на этапе компиляции этой же функции и решил разместить `c`
в куче С САМОГО ОБЪЯВЛЕНИЯ. Это статический (compile-time) анализ, не
рантайм-решение — совпадает с текстом D216 §4: «x starts on stack;
promoted to heap AT ITS DECLARATION POINT if address escapes function
scope (**return** / closure / heap-field store / fn arg)».

### Вывод (вопрос 3)

**Механизм эскейп-промоута — ОБЩИЙ, не специфичный для захвата в
файбер.** Он покрывает `return`-escape (проверено пробой выше),
согласно спеке — также `closure`, `heap-field store`, `fn arg`
(документировано в D216 §4, не переоткрывалось отдельной пробой в этом
окне, т.к. `return`-случай — строго более жёсткий тест: живёт короче
всех остальных путей эскейпа). Память — GC-управляемая (`nova_alloc`,
Boehm-куча, как и весь остальной язык) — сборщик не двигает объекты
(уже установлено в разведке p248-nocopy2, «reference-gc-fresh-mono-
safe»), поэтому указатель, переживший кадр, продолжает адресовать
живой объект, пока на него есть хоть одна ссылка, которую сборщик
видит (consервативный скан стека/регистров — тот же механизм, что и
для любого другого указателя в языке сегодня).

**Блокера нет.** Механизм из Plan 127/D228, о котором говорила разведка
p248-nocopy2 («продвижение захваченных значений в кучу»), — это ЧАСТНЫЙ
СЛУЧАЙ более общего эскейп-анализа D216 §4, а не отдельный,
специфичный для файберов механизм. Будущий указатель на value-внутри
атомик (или обёртка над ним — «общая ячейка» для `TcpStream.rc`) может
быть безопасно возвращён из фабрики/конструктора, сохранён в поле
другого heap-объекта, передан аргументом — во всех этих случаях
компилятор уже сегодня размещает адресуемое значение в куче
статически, в точке объявления.

## ИТОГОВЫЙ ВЕРДИКТ

**Общая ячейка нужна в 1 месте, из них 0 вне std.**

Единственное место всего корпуса (std, nova-polaris, nova-http,
nova-tls, nova-bignum, examples/**), которое после перехода атомиков на
представление «значение внутри» ПО СУЩЕСТВУ нуждается в разделяемой
ячейке (не эскейп-промоутом, а настоящим разделяемым владением между
структурно независимыми Nova-значениями) — `TcpStream.rc`
(`std/src/net/tcp.nv`), и оно уже находится ВНУТРИ `std`, где указатель
и `unsafe`-реализация приемлемы по конвенции проекта.

Два других места, которые предыдущее окно (p248-nocopy2) консервативно
отнесло к той же категории — `AccessLog.counter` и `RejectLog`
(оба `nova-polaris`) — по факту пробы чинятся БЕЗ общей ячейки:
`AccessLog` — переносом счётчика в замыкание (уже заведено, №354),
`RejectLog` — снятием двухстрочной локальной копии внутри `@record()`
(новая находка этого окна, номер не присваиваю).

**Указатель на атомик НЕ требует пользовательского `unsafe`** при
обычном доступе через методы (мутирующие в т.ч.) — доказано пробой
(вопрос 2). `unsafe` нужен только для голого `*p`/raw-intrinsic-методов,
которые сегодняшняя и будущая реализация `Atomic*`-методов не
использует на пользовательской стороне (только внутри `std`, через
`extern "nova"`).

**Висячего указателя не будет** — эскейп-промоут (D216 §4) общий,
покрывает `return`/heap-field-store/fn-arg, не только захват в файбер;
подтверждено пробой на самом жёстком случае (return из функции).
Boehm-куча не двигает объекты, консервативный скан находит все живые
ссылки.

### Рекомендация

Указателя (`*mut` на value-внутри атомик, с методами-обёртками для
атомарных операций) **достаточно для ЕДИНСТВЕННОГO нуждающегося места
(`TcpStream.rc`)**, оно и так внутри `std`. Отдельный языковой тип
«общая ячейка»/`SharedCell[T]` для этого одного места избыточен —
дешевле локально переписать `TcpStream.rc` на `*mut AtomicU32-подобный`
указатель (та же форма, что уже пробована и работает: методы через
авто-деref без `unsafe` для вызывающей стороны, `unsafe` только при
самом взятии `&`-адреса внутри `std`, если потребуется). Если позже
найдётся ВТОРОЕ место с тем же паттерном «независимые Nova-значения,
обязанные разделять ячейку» — тогда стоит вернуться к вопросу о
переиспользуемом типе; сегодня для этого нет второго прецедента в
корпусе.
