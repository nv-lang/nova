# Разведка: два «времени старта» Nova — build-latency и runtime-startup

**Статус:** исследование (материал для решения владельца, НЕ решение и НЕ реализация)
**Ветка:** `p-latency-research` (worktree `nova-latres`), база `134248143`
**Модель:** opus (только разведка/замеры, кода не трогал)
**Дата:** 2026-07-19

Цель — отделить «УЖЕ сделано» от «миф» от «реальная возможность» по 12 идеям ускорения
(а) latency цикла разработки (`nova build`) и (б) latency старта самого бинаря. Каждая
идея проверена по коду; где дёшево — измерено на минимальных программах.

## 0. Краткая сводка (TL;DR)

**Вердикты по 12 идеям:** УЖЕ ЕСТЬ — 3 · ЧАСТИЧНО — 4 · МИФ — 2 · РЕАЛЬНАЯ ВОЗМОЖНОСТЬ — 3
(+1 новая возможность, всплывшая из замеров).

**Главная находка (build):** для пустышки `fn main(){}` фаза `c-compile` = **6.5 с из ~11 с
(58%)** и она НЕ кэшируется — платится каждую сборку. Приложение пустое, libuv.lib и Boehm
предсобраны → эти 6.5 с почти целиком = **перекомпиляция РАНТАЙМА** (~10 `.c`-файлов
`nova_rt/*.c`, каждый ~0.6-0.8 с). Content-cache (`build_cache.rs`) экономит только фронтенд
(type-check+codegen, ~0.5 с на пустышке), но не C-компиляцию.
→ **№1 рычаг: предсобранный объектник/архив рантайма** (`libnova_rt.a`, скомпилировать
`nova_rt/*.c` один раз, линковать) — по образцу уже существующего кэша `libuv.lib`.

**Главная находка (runtime-startup):** это в основном **МИФ как проблема**. Голый C-бинарь
стартует ~80 мс (пол harness/ОС), Nova-пустышка ~95 мс → **вклад рантайма Nova ~15 мс**
(Boehm `GC_INIT` + libuv default loop + загрузка 2.2 МБ бинаря). `auto_arm` для программы
без `spawn` поднимает **0 worker-потоков** (подтверждено кодом и замером) — не стоимость старта.

**Топ-3 реальных возможности (с числами):**
| # | Возможность | Эффект | Сложность | Риск |
|---|---|---|---|---|
| 1 | Предсобранный архив рантайма (`libnova_rt.a`) | dev-rebuild ~11 с → ~5-6 с (−~5 с c-compile) | средняя | низкий |
| 2 | Персистентный build-демон | −~1-3 с/сборку (dep-lock 1 с + toolchain/libuv detect) | высокая | средний |
| 3 | Быстрый dev-бэкенд (TCC/cranelift) | app-`.c` компилится мгновенно; значимо ТОЛЬКО после №1 | высокая | высокий |

## 1. Замеры

Стенд: Windows 11, clang 22.1.5, релиз-бинарь `nova.exe` (16.6 МБ, 2026-07-19), `nova build`
default = **dev-режим** (`-O0 -g -Wno-everything`, `main.rs:441`), GC = Boehm (хардкод,
`main.rs:5238`), single-CU. Программа: `module …_latres_empty / fn main(){}`.
Все тайминги — усреднения; harness = Git Bash (spawn-overhead большой, поэтому по стартам
даю **дельту к голому C**, где overhead сокращается).

### 1.1. Build — фазовый разбор (`NOVA_PERF_TIMER=1`, один полный miss-прогон)

| фаза | время | заметка |
|---|---|---|
| parse | 0.1 мс | |
| **dep-lock** | **987 мс** | резолв манифестов workspace + внеш. репо (http/compress/tls) |
| imports-resolve | 426 мс | нужна и на cache-hit (строит `peer_files` для ключа) |
| type-check | 398 мс | **пропускается на cache-hit** |
| post-normalize-annotate | 349 мс | |
| codegen | 97 мс | **пропускается на cache-hit** |
| прочее (embed/alpha/lints/desugar/callnorm/effects) | ~30 мс | |
| **c-compile** | **6452 мс** | **58% всего; НЕ кэшируется** |
| **wall total** | **~11 с** | |

### 1.2. Build — cold vs warm (эффект content-cache)

- **WARM** (cache hit, `build_cache.rs`): ~9.9-12.9 с. В `NOVA_PERF_TIMER` фазы `type-check`
  и `codegen` **исчезают** — подтверждает, что кэш реально переиспользуется и срезает фронтенд.
- **COLD** (`NOVA_CACHE=0`): ~10.9-16.8 с. `type-check` (0.39 с) + `codegen` (0.10 с) присутствуют.
- **Вывод:** кэш экономит ~0.5 с на пустышке (масштабируется с объёмом std-использования, где
  type-check дороже), но `c-compile` 6.5 с платится ВСЕГДА. Кэш keyed по контенту исходников +
  отпечаток exe + cfg (features/target/mono-depth/contracts/strict/embed) — не mtime. Кэшируется
  **весь `.c` целиком** (inline-expansion → один Module → один `.c`; раздельной компиляции нет),
  НЕ `.o`.

### 1.3. Build — стоимость компиляции рантайма (потенциал архива)

Одиночные TU рантайма, чистый прогон (dev-флаги): `runtime.c` (136 КБ) = **647 мс**,
`driver.c` = **739 мс**. Всего ~10 TU (`fibers/runtime/driver/typeid/segv_diag/net/fs/eventloop/
alloc_boehm/fiber_arena`), суммарно ~6 с — совпадает с envelope `c-compile` 6.5 с. (Точную
per-TU макро-сборку не реплицировал — часть TU падает на порядок-специфичных `-D`; envelope
достаточен: пустой app + предсобранные libuv/Boehm ⇒ 6.5 с = рантайм.) libuv собирается один раз
в `libuv.lib` (`detect_or_build_libuv`), Boehm — предсобранная либа; **рантайм Nova — нет**.

### 1.4. Runtime-startup

| бинарь | размер | старт (ср., 20 прогонов) | дельта к голому C |
|---|---|---|---|
| голый C (`int main(){return 0;}`) | 109 КБ | 79.8 мс | — (пол harness/ОС) |
| Nova пустышка, default | 2.2 МБ | 95.3 мс | **+15.5 мс** |
| Nova пустышка, `NOVA_AUTOARM=0` | 2.2 МБ | 104 мс | +24 мс (в пределах шума — AUTOARM не даёт стоимости) |

- **+15 мс** вклада Nova = `GC_INIT` (Boehm) + libuv default loop + `nova_consts_init` +
  загрузка 2.2 МБ vs 109 КБ. Разбить дешевле нельзя (нет `--gc` на `nova build`), но потолок ~15 мс.
- **Первый в жизни запуск** свежесобранного exe: 10.5 с (одноразово — Windows Defender/page-in),
  устойчивое состояние ~85-95 мс.
- **`auto_arm` = 0 потоков** для программы без `spawn` (`runtime.c:498-499`:
  «_armed=true, но _materialized=false → 0 worker-потоков»; пул материализуется лишь при первом
  `spawn`). Замер on/off это подтверждает (дельта в шуме).

## 2. Вердикты по 12 идеям

### Build-latency

**(а) Разбить монолитный `.c` на TU по модулям — ЧАСТИЧНО / отчасти МИФ.**
Multi-TU УЖЕ есть (Plan 209), но бьёт по **РАЗМЕРУ, не по модулям**: `exceeds_multi_tu_threshold`
= CU > 2 МБ ИЛИ > 200 top-level fn (`emit_c.rs:2033-2064`); part-target 1.5 МБ
(`MULTI_TU_PART_THRESHOLD_BYTES`, `:2045`). Opt-in `NOVA_MULTI_TU=1`, **дефолт off**
(`emit_c.rs:2336`; Plan 209 Ф.6 default-on запланирован, не начат). Split **обходит content-cache**
(`main.rs:4950` «Split bypasses the cache entirely»). Перекомпилируется НЕ только изменившаяся
часть — раздельной компиляции модулей нет (inline-expansion сливает всё в один Module,
`build_cache.rs:9-16`). `.o` между вызовами не кэшируются (obj_dir = свежий temp, `main.rs:5233`).
Инкрементальная по-модульная сборка = отдельная крупная архитектура (separate compilation), «не v1».

**(б) Content-addressed build cache — УЖЕ ЕСТЬ (работает).**
`nova-cli/src/build_cache.rs` (Plan 81 Ф.9). Ключ = хэш(контент всех исходников + mtime/size
exe-компилятора + features + target OS + mono-depth + contracts_mode + embed-файлы + strict_effects)
— **по контенту, не mtime/пути** (`compute_c_key`, `:56-135`). Персистентный:
`target/.nova-cache/<key>.c`, без eviction, `NOVA_CACHE=0` выключает. Кэширует **`.c` целиком,
НЕ `.o`** — clang запускается всегда (`main.rs:4947-4953`, 5119-5124). Замер подтвердил:
на hit фазы type-check+codegen исчезают. **Это ровно идея (б), уже реализована — достраивать,
не дублировать.** Пробел: не кэширует результат C-компиляции (см. №1 ниже).

**(в) Быстрый dev-бэкенд TCC — РЕАЛЬНАЯ ВОЗМОЖНОСТЬ.**
Toolchain = `auto|clang|msvc|gcc` (`test_runner.rs:297-311`), **TCC отсутствует**. TCC ускорил бы
компиляцию app-`.c`, но рантайм-`.c` всё равно надо собрать (⇒ комбинировать с №1). Прецедент:
Zig (собственный бэкенд), cranelift-debug у rustc, TCC у ряда игровых движков. Риск высокий:
на Windows MSVC-ABI + линковка Boehm/libuv через tcc сомнительна; tcc не даёт `-flto`/оптимизаций
(но dev и не нужны). **Значимость появляется ТОЛЬКО после №1** (иначе рантайм доминирует).

**(г) Персистентный компилятор-демон — РЕАЛЬНАЯ ВОЗМОЖНОСТЬ (нет).**
Каждый `nova build` = свежий процесс, платит dep-lock (~1 с), `detect_toolchain`,
`detect_or_build_libuv`, `detect_boehm` заново. Демон амортизирует это + держит фронтенд-состояние
в памяти. Прецедент: Roslyn `VBCSCompiler`, Bazel persistent workers, Nailgun (JVM), Gradle daemon.
Замер: dep-lock 987 мс + overhead ~2 с потенциально снимаются. Сложность высокая (протокол, инвалидация).
Смежно с LSP-кэшем (Plan 215) — можно переиспользовать инфру.

**(д) PCH для рантайм-заголовков — РЕАЛЬНАЯ, но доминируется №1.**
PCH сейчас нет (build просто `-I`-инклудит). Но узкое место — компиляция **тел** рантайм-`.c`
(647-739 мс/TU), а не парсинг заголовков. Предсобранный **архив** рантайма (№1) строго сильнее PCH
и проще кэшируется. PCH отдельно = низко-средний эффект.

**(е) Более глубокий DCE / mono-pruning — В ОСНОВНОМ УЖЕ ЕСТЬ.**
(1) **Mono демандный**: worklist-коллектор (`emit_c.rs:231` «uninstantiated one is never emitted»;
`mono_worklist`/`mono_instantiated` `:1588-1594`) — неиспользуемые инстанциации дженериков
**вообще не генерируются**, поэтому «прунить» нечего (rustc-style collector; `--mono-depth`/
`NOVA_MONO_DEPTH` — только предохранитель глубины, не источник мусора). (2) `NOVA_REACH_DCE`
(default on, `emit_c.rs:274`) прунит мёртвые free fn + const/ro-globals + **методы** (body-level DCE,
anchored к достижимости receiver-типа). (3) Linker-DCE: `-ffunction-sections -fdata-sections` +
`--gc-sections`/`OPT:REF` (`test_runner.rs:1393`). Осталось мало; over-keep консервативен
(коллизия имён держит) — маргинальные доводки, низкий приоритет.

**(ж) Параллельная генерация C по units — ЧАСТИЧНО.**
Multi-TU компилирует части **параллельно** (`compile_multi_tu_to_exe`), но сам **codegen
однопоточный**; split происходит уже над готовой строкой. Codegen = 0.1 с — параллелить не стоит.
Параллельна КОМПИЛЯЦИЯ (есть, opt-in), не генерация.

**[НОВОЕ, из замеров] Предсобранный объектник/архив рантайма — РЕАЛЬНАЯ ВОЗМОЖНОСТЬ (№1).**
Не входит явно в 12 (ближайшие: к/статик-линк, д/PCH). Компилировать `nova_rt/*.c` один раз →
`libnova_rt_<mode>_<gc>.a`, линковать. Каждый TU рантайма — независимая единица компиляции уже
сейчас (build отдаёт clang'у несколько `.c`), поэтому архивирование **байт-эквивалентно**. Кэш-ключ
для dev тривиален: флаги стабильны (`-O0 -g`, `NOVA_GC_BOEHM`, `NOVA_USE_LIBUV`, без `-march`).
Образец — уже работающий кэш `libuv.lib` (`detect_or_build_libuv`).

### Runtime-startup

**(з) `--gc malloc` vs boehm — ЧАСТИЧНО / малый эффект.**
`nova build` **не имеет `--gc`** (`GcKind::default()` = Boehm хардкодом, `main.rs:5238`;
`bench/corpus.rs:38` «nova build не имеет --gc»). `GC_INIT` (`GC_set_no_dls(1)`+`GC_INIT()`+
`GC_set_all_interior_pointers(1)`, `alloc_boehm.c:74-95`) — часть тех ~15 мс. Malloc убирает его,
но течёт (только для бенчей). Общий эффект мал (~единицы мс) и не для продакшна.

**(и) Ленивая инициализация libuv — МИФ / малый.**
libuv default loop инициализируется eager на старте (`nova_evloop_init` в main, `emit_c.rs:25236`),
но это дёшево: `uv_default_loop()` (`eventloop.c:73-86`), потоки НЕ спавнятся (threadpool env
выставляется, но воркеры ленивы до первого blocking-op). Sub-ms. Экономить нечего.

**(к) Статическая линковка рантайма — УЖЕ ЕСТЬ (для бинаря).**
Рантайм компилится в бинарь, Boehm + libuv статические. Не рычаг старта. **Reframe:** это и есть
build-latency идея №1 (предсобранный архив).

**(л) Профилирование через `nova bench --profile` — ЧАСТИЧНО.**
`--profile cpu` работает — оборачивает внешний `samply` (`bench/profile.rs:72-103`, требует
samply в PATH). `--profile heap` и `--profile gc` — **заглушки** (пишут JSON-placeholder,
`:105-166`, «runtime integration TBD Plan 57.B»). Startup-breakdown этим НЕ снять (нет
инструментации самого старта); я мерил дельтой к голому C.

программ; «старт бинаря» доминируется созданием процесса ОС, не рантаймом.

## 4. Что — отдельные планы, что — мелкие маркеры

**Отдельные планы (номера 218+ свободны):**
- **План 218 — предсобранный архив рантайма** (`libnova_rt.a`): компиляция `nova_rt/*.c` один раз,
  кэш по (mode, gc, march, отпечаток clang, хэш rt-исходников), линковка вместо перекомпиляции;
  образец `detect_or_build_libuv`. Гейт: byte-identical поведение (TU уже независимы),
  conformance один CU + флагман-examples под `--strict-effects`. **Приоритет P1.**
- **План 219 — персистентный build-демон** (или подпроект Plan 215/LSP): держать процесс,
  амортизировать dep-lock + toolchain/libuv/boehm detect + фронтенд-состояние. **Приоритет P2**,
  делать после 218.
- (опционально) **План 220 — TCC/fast dev-бэкенд**: только если после 218 app-компиляция станет
  заметной долей. **P3, разведочный** (риск MSVC-ABI/линковка высок).

**Мелкие followup-маркеры (не планы):**
- `[followup-nova-build-gc-flag]` — прокинуть `--gc malloc` в `nova build` (сейчас хардкод Boehm,
  `main.rs:5238`); дёшево, полезно для профилирования старта/бенчей.
- `[followup-heap-gc-profile-wiring]` — `--profile heap/gc` заглушки (`bench/profile.rs:105-166`);
  уже отслеживается как Plan 57.B.
- Multi-TU Ф.6 default-on — уже в Plan 209 (не новый маркер).
- Ленивая libuv (и), глубже DCE (е) — закрыть как «не стоит» (эффект sub-ms / уже сделано).
