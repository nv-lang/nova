## Место фикса

Предыдущее окно (p-ice-pack) честно остановилось: «настоящий фикс»
(retroactive-insert declaraции ПОСЛЕ собственного C-объявления
захватываемой mut-переменной) требует либо byte-offset retroactive-insert в
`self.out` с запоминанием offset КАЖДОЙ `mut`-локали, либо pre-scan
«будет ли эта переменная когда-либо box-нута» перед эмитом её `Stmt::Let` —
оценено как непропорциональная инфраструктура для узкого окна.

Нашёл вариант ПРОЩЕ, требующий только ОДНОГО якоря НА ФУНКЦИЮ (не на
переменную): `emit_block_stmts` — единственная точка входа в тело КАЖДОГО
top-level C-функции (fn/test/generic-метод/lambda; вложенные конструкции
`while`/`if`/match-arm НИКОГДА не проходят через неё повторно — используют
свои отдельные inline stmt-loop'ы). В её начале (сразу после открывающей
`{` функции) фиксирую `(self.out.len(), self.indent)` в новом поле
`detach_box_hoist`. `hoist_box_decl` ретроактивно вставляет туда ГОЛОЕ
объявление (`T* bv;`, без инициализатора) — присваивание (`nova_alloc` +
запись значения) остаётся на исходном (возможно вложенном) месте. Голое
объявление на верхнем уровне функции всегда доминирует и точку захвата, и
любое более позднее чтение в той же функции — ЛЕГЧЕ инвариант, чем
«после собственного объявления `cap`», и не требует per-переменных offset'ов.

### Ratchet: emit_detach вынесен в дочерний модуль

`emit_c.rs` был РОВНО на baseline (64545 строк) — нулевой запас. Вынес

## Найденный ПОБОЧНЫЙ дефект (НЕ фиксил, вне периметра этого окна)

При тестировании обнаружил ОТДЕЛЬНЫЙ, более узкий дефект того же семейства:
если вмещающий `while`/`if` НИ РАЗУ не выполняется во время выполнения
(`while false { detach {...} }` или `iters=0`), box-указатель никогда не
получает присваивание — голое объявление (`T* bv;`, без инициализатора)
остаётся неинициализированным, и чтение ПОСЛЕ блока разыменовывает мусор
(UB), а не даёт корректное «пусто»/исходное значение.

**До фикса №240 эта ветка была НЕДОСТИЖИМА** — вся программа такой формы
попросту НЕ КОМПИЛИРОВАЛАСЬ (та же самая ошибка `undeclared identifier`,
безусловно, независимо от значения аргумента `iters` в рантайме —
компиляция не знает будущих значений аргументов). Значит это не
регрессия «было работало → сломал», а НОВООТКРЫВШИЙСЯ путь кода.

Рассмотрел и ОТКЛОНИЛ два кандидата на месте:
1. **NULL-инициализация** голого объявления (`T* bv = NULL;`) — превращает
   тихое UB в детерминированный SEGV. Отклонил: в этом же самом файле есть
   прецедент `[M-conformance-megacu-intermittent-run-crash]` — проект уже
   обжигался ИМЕННО на тихом мид-ран крэше мега-CU от detach-путей; новый
   гарантированный краш-вектор в общем detach-коде — риск того же класса,
   несоразмерный узкому окну.
2. **Условное чтение с фоллбэком** (`bv ? *bv : cap` на месте каждого
   чтения через `var_boxed`) — технически корректно (если box никогда не
   создавался, `cap` не могла быть переписана записью-через-box, значит её
   родное значение актуально), но требует правки ОБЩЕЙ точки чтения
   `ExprKind::Ident` в `emit_c.rs` — используется ТАКЖЕ путями
   `emit_spawn`/`emit_effect_handler_literal`/лямбдами (тот же `var_boxed`).
   Риск регрессии на горячем разделяемом пути, тоже несоразмерный.

Настоящий фикс (по образцу диагноза предыдущего окна для самого №240)
требует ЛИБО eager-boxing переменной сразу при её собственном объявлении
(если она КОГДА-ЛИБО захватывается — нужен pre-scan), ЛИБО per-переменных
retroactive-insert ПОСЛЕ её собственного объявления с немедленной
инициализацией текущим значением — оба варианта той же тяжести
инфраструктуры, что диагноз предыдущего окна уже отклонил для самого
№240. Оставляю как отдельную, более узкую находку для интегратора —
номер не присваиваю (нумерация — за интегратором), текст диагноза записан
в комментарии фикстуры
(`spec_tests/conformance/standalone/m240_detach_box_while_loop_read_after.nv`,
блок «SCOPE NOTE»).
