## Ф.0 — механизм и связь с №129/№130/№170

Три свежих минимальных репро в `nova-p2223/scratch_repro/` (НЕ закоммичены,
worktree-only, компилятор не менялся):

- `p140_repro.nv`/`p140_repro2.nv` — generic-функция ПРЯМО вызывающая свой
  fn-параметр `f(x)` работает СЕГОДНЯ (два разных T в одном CU, вывод верный).
- `p140_repro3.nv` — та же форма + результат `f(x)` matched (`Ok(r) =>
  r.into_resp()`) — `[E_UNKNOWN_TYPE_METHOD] ... Single-key fallback на
  'Upgrade.into_resp' отвергнут — strict-mode` (guard "Plan 82 followup",
  2026-05-23, emit_c.rs:43490).
- `p140_repro6.nv` — прямая цепочка `f(x).into_resp()` (без match) — тот же
  класс, другая диагностика: `use of undeclared identifier 'nova_self'` —
  erased protocol-stub эмитится без ресивер-параметра.
- `p140_closure_var_call.nv`/`…3.nv` — СМЕЖНАЯ (не №140, не generic) находка:
  вызов через локальную переменную, связанную с результатом вызова функции,
  возвращающей `fn(...)->...` (даже НЕ generic), тоже разбит —
  `ld: undefined symbol: nova_fn_g` (codegen эмитит вызов несуществующей
  `nova_fn_<var>` вместо диспетча через сохранённое замыкание).

Корень (общий для №129/№170/№140): single-key реестры (`mono_method_decls`,
`method_receivers`) без оси для «производного от вызова fn-параметра»
выражения — субституция typevar'а трекается ТОЛЬКО для ПАРАМЕТРОВ
(`fn_param_sigs`/`current_fn_param_typerefs`), НЕ для `match`-биндингов/
локалов, производных от вызова fn-типизированного параметра. №129/№170
закрыли СВОИ узкие формы (blanket-коллизия по букве typevar'а; self-call
диспетч по голому имени typevar'а) — №140 живёт РЯДОМ, не пересекаясь с их
фиксами напрямую.

**Фикс:** НЕ сделан. Чекер-канал (resolved_types/node_substs) для
match-bound переменной несёт ТОЛЬКО символьный тип ("R"), не substituted —
для реального фикса нужно на этапе body-emission комбинировать канал с
`current_type_subst`, аналогично уже существующему
"recv_is_candidate"/blanket-dispatch пути (~emit_c.rs:43230-43450), но тот
путь читает C-тип через `infer_expr_c_type(obj)`, которая для match-bound
локала возвращает erased/нет данных — нужно протянуть `fn_param_sigs`'ный
inner_ret через var_types в момент pattern-binding'а. Объём работы —
не «одна точка», риск регресса на 63795-строчном файле под ratchet — вне
бюджета разведки этого окна. Ratchet НЕ сдвигался (63795/348 — без изменений,
emit_c.rs не трогался вообще).

## Ф.1 — что уже работает / чего не хватает

- fn-значение с типизированными параметрами КАК АРГУМЕНТ — работает (после
  тех же фиксов №129/№170, до этого окна).
- Вызов ПРЯМО параметра `f(x)` внутри generic-тела — работает.
- Вызов ЧЕРЕЗ ПЕРЕМЕННУЮ, связанную с результатом ВЫЗОВА fn-возвращающей
  функции — СЛОМАН (даже не-generic случай, см. выше). Не проверялось
  раньше в периметре 222.3 — новая находка.
- Дальнейший protocol-диспетч НА РЕЗУЛЬТАТЕ вызова fn-параметра — сломан
  (№140, реконфирмировано).
- **Вывод:** язык ДОСТАТОЧЕН для низкоуровневой формы (`TypedRoute{handler:
  fn(req)->...}` + явные `.from_path`/`.from_query`/`.from_body` вызовы на
  КОНКРЕТНЫХ типах внутри НЕ-generic closure — это НЕ упирается ни в одну
  из сломанных форм выше). НЕ достаточен для generic
  `post_typed[T1,T2,T3](path, h)`-перегрузки, которая должна была бы сама
  диспетчить `h` и протокольно кодировать результат — это именно №140.

## Ф.2/Ф.3 — что сделано

`nova-polaris` ветка `p2223-parity`:
- `src/extract.nv`: `FromPath`/`FromQuery`/`FromBody` протоколы (после
  `flat key/value Deserializer engine`-баннера, до самого движка).
- `examples/03-json-api/src/main.nv`: `TodoIdParam.from_path`/
  `NoteQuery.from_query`/`NoteBody.from_body` — конкретные (НЕ generic)
  `#impl`, форвардят на уже проверенные `PathParam[T]`/`Query[T]`/`Json[T]`
  `.from_request`. `add_note(id TodoIdParam, opts NoteQuery, note NoteBody,
  items Vec[Todo]) -> ServerResponse` — голый хендлер. Регистрация ОСТАЁТСЯ
  низкоуровневой (`TypedRoute{handler: fn(req)->...}` — hand-written
  НЕ-generic closure, зовёт `.from_path`/`.from_query`/`.from_body` затем
  `add_note`), НЕ bare-arity-sugar `post_typed(path, add_note)` (блокировано
  №140). `req_shape` теперь `Some(...)` — hand-built `TypeShape.Record` с
  ролью по имени (та же конвенция, что читает `openapi.nv`'s `wrapper_role`),
  `.reflect()` на КОНКРЕТНЫХ типах напрямую (не через generic-wrapper
  field-walk — П1 не задет).
- `examples/03-json-api/openapi.golden.json` — обновлён живым выводом
  (path/query/body параметры маршрута note теперь непустые).
