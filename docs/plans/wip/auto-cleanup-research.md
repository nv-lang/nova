# Исследование: авто-`@cleanup` для непотреблённых consume-переменных

> **Статус:** РАЗВЕДКА (материал для решения владельца, НЕ решение). Модель opus.
> Ветка `p-cleanup-research` / worktree `nova-cleanupres`. Код и спека НЕ правились.
> Вопрос владельца (2026-07-19): «возможно, следует делать вызов `@cleanup()`
> автоматически во ВСЕХ скоупах, где consume-переменная не потребляется, а не
> только в блоке `consume … { … }`?»
>
> **Сужения владельца в ходе разведки:**
> 1. Речь ТОЛЬКО о гибриде C — авто-cleanup для типов с объявленным `@cleanup`;
>    явность остаётся для линейных ЗНАЧЕНИЙ.
> 2. Тезис на проверку: «по сути consume-типы наверное ДОЛЖНЫ иметь `@cleanup`».
> 3. Рабочее предпочтение по п.3: `@cleanup` **опционален** — есть → тип
>    авто-прибирается в конце скоупа (аффинный); нет → старое строгое «обязан
>    потребить явно» (линейный).

---

## 0. Резюме (3 строки + вывод)

- **Сейчас:** `type X consume` (D133) обязывает потребить значение на КАЖДОМ
  exit-пути явным consume-методом/передачей/`return`; непотребление = compile-error
  `D133-not-consumed`. `@cleanup` (протокол `Cleanup[E]`, D188) вызывается
  автоматически ТОЛЬКО на выходе из scope-блока `consume X = e { body }` /
  `consume X { body }` — вне блока наличие `@cleanup` от must-consume НЕ освобождает
  (подтверждено эмпирически, §1.4).
- **Предложение (гибрид C, опциональный `@cleanup`):** для consume-типа, объявившего
  `@cleanup`, снять правило «обязан потребить до конца скоупа» — компилятор сам
  вставляет `@cleanup(Success/Failure/Panic)` на выходе из ЛЮБОГО скоупа, где такая
  переменная осталась Live. Семантика типа сдвигается с линейной (=1) на аффинную (≤1).
- **Ключевой вывод:** предложение технически дёшево (механизм D188/D314 уже есть —
  это тот же defer-desugar, просто применённый к «остатку скоупа» вместо явного
  `{body}`), ОРТОГОНАЛЬНО плану 216 (тот про видимость ПЕРЕДАЧ владения, а не про
  конец скоупа) и снимает реальный бойлерплейт. Но: (1) прямо конфликтует с уже
  ЗАФИКСИРОВАННЫМ отвержением «Drop-method auto-cleanup» в D133; (2) упирается в
  `Fail[E]`-эффект-row у `@cleanup` (прецедент 214 R12 — скрытый эффект в неявной
  позиции запрещён под strict-effects); (3) для типов-ЗНАЧЕНИЙ (StringBuilder) авто-дроп
  = тихая потеря работы. **Рекомендация: принять гибрид C с опциональным `@cleanup`,
  но с двумя жёсткими ограждениями (эффект-свобода авто-пути + отдельная диагностика
  для infallible-vs-fallible) — детали в §7.**

## 1. Факт-база (цитаты из спеки/кода, не по памяти)

### 1.1. Что делает `type X consume` сегодня — линейность «ровно 1 раз» (D133)

`spec/decisions/02-types.md` D133 (§«Правило — must-consume на каждом exit-path'е»,
строки 5183-5205):

> Compiler проводит flow-sensitive анализ … Для каждой переменной consume-типа
> отслеживается `VarState` [`Live`/`Consumed`/`MaybeConsumed`]. На каждой точке
> выхода scope'а … `Live` или `MaybeConsumed` → **compile error E (D133-not-consumed)**.

Точки выхода (там же): конец function body; `return expr`; `panic`/`!!`/`?`/unwinding;
`loop break`; branch join (`Live ⊔ Consumed = MaybeConsumed`).

Удовлетворить обязательство можно 5 способами (02-types.md:5479-5494): closed locally
(consume-метод), Returned, Transferred (consume-param), Stored in escaping record-field,
Covered by defer.

**D131** (05-memory.md:390-391) фиксирует ось: `D131 = affine (≤1 раз; забыть OK);
D133 = must-consume (≥1 раз; обязан потребить)`. Комбинация D131+D133 = **линейность**
(ровно 1). Именно «ровно 1» и есть то, что предложение владельца ослабляет до «≤1».

### 1.2. Что такое `@cleanup` и когда он зовётся АВТОМАТИЧЕСКИ сейчас (D188)

`std/src/prelude/protocols.nv:477-479`:

```nova
export type Cleanup[E] protocol {
    consume @cleanup(outcome ScopeOutcome) Fail[E] -> ()
}
```

`spec/decisions/03-syntax.md` D188 (8470-8472): scope-block `consume X = expr { body }`
гарантирует **exactly-once** вызов `@cleanup` при выходе из `body`
(success/throw/panic/cancel). Десугаринг (8527-8542) — `nv_run_body_capturing`
захватывает исход, затем `match _outcome { Success => cleanup(Success); Failure(e) =>
{cleanup(Failure(e)); throw e}; Panic(m) => {cleanup(Panic(m)); nv_panic(m)} }`.

Вторая форма — re-consume существующего owned-биндинга `consume X { body }` (амендмент
2026-07-13, 8550-8571): та же гарантия для параметра/локала.

**Критично:** авто-вызов `@cleanup` привязан к СИНТАКСИЧЕСКОМУ блоку. Вне блока
`@cleanup`-тип подчиняется общему D133 — см. §1.4.

### 1.3. `@cleanup` уже низведён до сахара над `defer` (D314) — механизм для авто уже есть

`spec/decisions/03-syntax.md` D314 §3 (11304-11310):

> **`consume X = e { body }` → САХАР** над outcome-defer:
> `{ ro X = e; defer(o) { X.@cleanup(o) }; body }`. … Разница `consume` vs bare
> `defer(o)` — **must-consume (D133) + exactly-once (D188 R2) + partial-init (D188 R1)
> + ResourceTrace-события**, НЕ «добежит/не добежит».

Весь unwind-редиспатч идёт через ОДНУ runtime-точку `nova_scope_exit(NovaFailFrame*
primary, policy)` (D314 §4, 11312-11324), `policy ∈ {CATCH, TRANSPARENT}`. Это и есть
общая «fail-frame»-механика (координатор назвал её D408; фактически D408 — это
`supervised(deadline:/timeout:)`, ИСТОЧНИК cancel, а сам unwind-транспорт — `nova_scope_exit`
из D314). Панк-доминирование composition — единая таблица D314 §4a (11346-11350).

**Смысл для предложения:** «авто-cleanup для непотреблённой @cleanup-переменной» — это
буквально «на binding-сайте `consume X = e` эмитить `defer(o){ X.@cleanup(o) }`,
охватывающий ОСТАТОК скоупа, с дизармом на любом пути, где `X` всё-таки потреблён явно».
Инфраструктура (defer-frame, LIFO scope-stack, дизарм-флаг `_defer_<bid>_0_active`,
outcome-материализация) уже построена и оттестирована.

### 1.4. Эмпирика (release-компилятор, read-only, temp-фикстура)

Фикстура: `type Res consume` с объявленным `@cleanup`, оставлена Live к концу скоупа.

```
acheck/probe.nv:13: error: [D133-not-consumed] переменная `r` (тип `Res`)
  не consumed до scope-exit. Добавьте вызов одного из: cleanup, либо `return r`,
  либо передайте в consume-param.
  help: consume `r` via method (D133-not-consumed quick fix)
```

**Вывод факта:** наличие `@cleanup` СЕГОДНЯ не даёт никакого авто-поведения вне блока —
компилятор требует явного потребления и даже предлагает `cleanup` как один из ручных
вариантов. Именно это поведение предложение владельца и меняет.

### 1.5. Уже ЗАФИКСИРОВАННОЕ отвержение (прямой прецедент против B, релевантно C)

`spec/decisions/02-types.md` D133 §«Что отвергнуто» (5533-5534):

> **Drop-method auto-cleanup** (Rust-style RAII) — размывает выбор commit/rollback.
> D133 требует **явный** consume-метод.

И (5530-5532):

> **Suppress-механизм `let _ = v`** — anti-Rust `#[must_use]` gateway. Единственный
> канал — consume-метод. Если «иногда хочу забыть» — знак, что тип неправильно помечен
> `consume`.

**Это не блокер, но требует явного амендмента:** предложение владельца — пересмотр
именно этого пункта. Гибрид C смягчает конфликт (см. §5): авто-cleanup зовёт ЕДИНЫЙ
метод `@cleanup(outcome)`, а не «drop»; «размывание commit/rollback» решается тем, что
`@cleanup` сам ветвится по `outcome` (Success→commit / Failure→rollback) — тот же приём,
что уже канонизирован в D188. Т.е. аргумент «размывает выбор» частично устарел после
введения `ScopeOutcome`.

### 2.2. Класс (b) — линейные ЗНАЧЕНИЯ (авто-cleanup семантически СПОРЕН / вреден)

| Тип | Файл | Почему «значение», а не «ресурс» |
|---|---|---|
| `StringBuilder` | `std/src/runtime/string_builder.nv:35` | Потребление даёт ЦЕННОСТЬ: `consume @into_str() -> str` (229) — zero-copy MOVE буфера. Авто-cleanup тихо выбросил бы построенную строку = **скрытая потеря работы**. У типа НЕТ «отменяющего» cleanup — потребить = забрать результат. **✅ СОГЛАСОВАНО владельцем (2026-07-19): «авто-прибрать = молча выбросить построенную строку — полностью согласен»** — канонический пример существования линейного класса (без `@cleanup`, строгая явность). |
| `WriteBuffer` | (finalize-полоса 214: `@into_bytes()`) | То же: `into_bytes()` отдаёт накопленное; тихий дроп = потеря. |
| линейные «доказательства»/токены | паттерн D133 (пока не в std как отдельные типы) | Смысл линейности — заставить РОВНО одно использование (proof-of-work, capability-token, «этот путь пройден»). Авто-дроп молча гасит инвариант «должен быть использован». |

### 2.3. Выводы инвентаря (прямой ответ на тезис владельца)

1. **Из 14 consume-типов класса (a) `@cleanup` объявлен лишь у 6** (4 lock-guard + TcpStream +
   TlsStream). Остальные 8 (File, TcpListener, оба half, UdpSocket, OnceGuard, Body, часть
   ffi) закрываются ЯВНЫМИ методами (`@close`/`@drain`) и `@cleanup` НЕ имеют. То есть
   тезис «consume-типы наверное должны иметь `@cleanup`» today НЕ выполнен даже для
   очевидных ресурсов — это работа по добавлению `@cleanup` ~8 типам.
2. **Класс (b) — ровно тот случай, ради которого нужен ОПЦИОНАЛЬНЫЙ `@cleanup`.**
   StringBuilder/WriteBuffer/токены — конкретный ответ на «пока не знаю, зачем может
   понадобиться НЕ делать `@cleanup`»: у них потребление = извлечение ценности, тихий
   авто-дроп = баг (потерянная строка / несоблюдённое доказательство). Для них правильно
   ОСТАВИТЬ строгое линейное «обязан потребить явно».
3. Следовательно правильная граница — **не «ресурс vs значение» по интуиции, а по
   наличию `@cleanup`**: автор объявляет `@cleanup` там и только там, где «молча прибрать
   на выходе» — корректная семантика. Это ровно опциональная модель владельца.

## 3. Теоретическая рамка

- **Линейные типы** (ровно 1 использование): текущая Nova (D131 affine + D133 must-consume
  = линейность). Гарантия: ресурс не забыт И не потреблён дважды. Цена: бойлерплейт
  `@cleanup`/`defer` на каждом error-пути; шумные `D133-not-consumed`.
- **Аффинные типы** (≤1, авто-drop в конце скоупа): Rust `Drop`, C++ RAII, Swift `deinit`.
  Гарантия: не забыт (компилятор добьёт). Цена: точка освобождения не всегда видна глазами;
  «drop» смешивает случаи (commit vs rollback) — если у drop один путь.
- Предложение владельца = **сдвиг @cleanup-типов из линейных в аффинные**, при сохранении
  линейности для типов без `@cleanup`. Это гибрид, где `ScopeOutcome`-параметр `@cleanup`
  снимает главное возражение против affine-drop (drop видит исход и ветвится).

## 5. Ортогональность с планом 216 (ключевой вопрос владельца п.2)

**216** (`docs/plans/216-consume-enforce-a.md`) — вариант А, ЗАФИКСИРОВАН владельцем
2026-07-18. Суть (строки 15-37): enforce ВИДИМОСТИ ПЕРЕДАЧ владения —

- consume-пейлоад в `match`/`if-let` по rvalue обязан связываться `Ok(consume tcp)`, иначе
  `E_CONSUME_PATTERN_REQUIRED`;
- алиас `mut x = consume_var` → `E_VIEW_BINDING_FORBIDDEN` (Rule 2);
- пропагация consume-обязательства через Option/Result-пейлоад.

**Разбор ортогональности.** 216 отвечает на вопрос «КАК владение ПЕРЕДаётся/алиасится»
(binding-сайты, паттерны). Авто-cleanup отвечает на вопрос «что происходит, если владение
НИКУДА не передано К КОНЦУ скоупа». Это разные оси:

- Правила 216 (consume-паттерн на rvalue, запрет view-алиасов, пропагация через пейлоад)
  — про то, что ЛЮБОЙ переход владения виден в тексте. Авто-cleanup их НЕ трогает: если
  значение передаётся/алиасится, это по-прежнему обязано быть явным по 216.
- Единственное правило, которое авто-cleanup ослабляет, — это **D133 «обязан потребить до
  конца скоупа» (то же, что D180 Rule 6 «consume obligation в-scope check», 05-memory.md:554-556)**
  и только для @cleanup-типов: «не потребил» перестаёт быть ошибкой, потому что компилятор
  сам вставит `@cleanup`.

**Вывод (явно, как просил владелец): да, ортогональны.** Гибрид C может ОСТАВИТЬ весь
периметр 216 (видимость передач, запрет тихих алиасов, E_CONSUME_PATTERN_REQUIRED,
E_VIEW_BINDING_FORBIDDEN) без изменений и снять ТОЛЬКО Rule 6/`D133-not-consumed` для
@cleanup-типов. Напряжение «216 ужесточает — авто-cleanup ослабляет» снимается чисто:
216 ужесточает ПЕРЕДАЧУ (её видимость), авто-cleanup ослабляет НЕПЕРЕДАЧУ (конец скоупа).
Они даже дополняют друг друга — 216 гарантирует, что любой явный move виден, а всё
остальное (не-move) детерминированно прибирается.

**Одна тонкость для протокола:** после C формулировка `D133-not-consumed` расщепляется:
для @cleanup-типа «не потребил» = OK (авто), для не-@cleanup — ошибка. Флоу-анализ уже
различает эти классы типов (проверка `type_is_consume` + наличие метода `@cleanup`
структурно резолвится, как в D196 init-constraint). Кода на различение — минимум.

## 6. Обязательные углы для гибрида C (п.4 владельца)

### 6.1. Точки вставки на ВСЕХ exit-путях

Механизм уже определён D314 §3: авто-cleanup = `defer(o){ X.@cleanup(o) }`,
зарегистрированный на binding-сайте `consume X = e` и охватывающий остаток скоупа.
Defer-frame по построению срабатывает на ЛЮБОМ выходе (D314 §1): normal end-of-scope,
`return v`, `throw e`/typed-throw, `cancel` (structural, D90 §7), `panic(msg)` — кроме
`exit(N)`. Отображение exit-path→`ScopeOutcome` — готовая таблица D314 §2 (11289-11295).
Unwind-редиспатч — единая точка `nova_scope_exit(NovaFailFrame*, policy=TRANSPARENT)`
(D314 §4). Панк/cancel-доминирование — таблица §4a. **Ничего нового строить не надо** —
это ровно то, что уже гоняет `consume X = e { body }`.

**Дизарм на явном потреблении.** Если `X` всё-таки потреблён (передан в consume-param,
`return X`, `X.commit()`, #coerce-финализация) — defer-frame должен дизармиться на этом
пути. Прецеденты дизарма УЖЕ реализованы: (1) tail/return-вынос D188 v3 (03-syntax.md:8785-8797,
дизарм в момент передачи владения); (2) 214 finalize×поток-управления (неявная #coerce в
if-ветке → MaybeConsumed на join). То есть флоу-анализ дизарма existing.

### 6.2. Порядок нескольких cleanup — LIFO

D188 R5 (03-syntax.md:8976-8994): вложенные `consume{}`/`defer{}` — единый per-fiber
scope-stack, LIFO. Авто-cleanup встраивается в тот же стек: несколько непотреблённых
@cleanup-переменных в одном скоупе прибираются в обратном порядке объявления, как
если бы каждая была `consume X = e { <остаток> }` вложенно. Совпадает с Rust drop-order.

### 6.3. Эффект-row у `@cleanup` vs strict-effects — ГЛАВНОЕ ограждение (прецедент 214 R12)

`@cleanup` в общем случае эффектен: `consume @cleanup(outcome ScopeOutcome) Fail[E] -> ()`
(protocols.nv:478). Для ресурсов вроде `File` cleanup = `Fs.close(@fd)` c `Fail[IoError]`
(fs.nv:274 — `consume @close() Fs -> Result`, эффект `Fs`!).

**Прецедент 214 R12** (`docs/plans/214-coerce-attribute.md:97-98`):

> **Эффект-свобода (R12):** пустой effect-row обязателен — `E_COERCE_EFFECTFUL`; скрытый
> эффект в голой позиции недопустим (strict-effects).

214 запретил НЕЯВНУЮ вставку эффектного вызова (`into_str` обязан быть pure). Авто-cleanup
— ровно такая же неявная вставка вызова в конце скоупа. Если `@cleanup` несёт `Fail[E]`
или `Fs`/`Net` — компилятор молча внёс бы эффект, невидимый в сигнатуре функции. Это
конфликтует с `--strict-effects` (обязателен для `std/**` и `examples/**`).

**Три развилки для владельца:**
1. **Разрешить авто только для `Cleanup[never]` + без прочих эффектов** (как lock-guards,
   TcpStream, TlsStream — все `[never]`). Fallible-cleanup-типы (File с `Fail[IoError]`)
   ОСТАЮТСЯ строго-линейными (авто не для них). Самый безопасный, совпадает с hot-path
   элизией D194. НО: File — именно тот тип, где авто-close желаннее всего.
2. **Пропагировать эффект `@cleanup` в effect-row функции** (авто-cleanup «заражает»
   объемлющую функцию `Fail[E]`/`Fs`). Тогда эффект виден в сигнатуре — strict-effects
   соблюдён, но появляется неявная точка throw (что делать с ошибкой close на normal-path?
   → композиция D314 §4a: cleanup-throw становится primary на Success-выходе).
3. **Требовать, чтобы fallible-`@cleanup` не проглатывал ошибку молча** — но это уже
   политика обработки, а не row.

Рекомендация — §7.

### 6.4. Детерминизм vs Boehm-финализаторы — сильный плюс C

Boehm GC финализаторов НЕ гарантирует своевременность/порядок/факт вызова. Авто-cleanup
компилятором — детерминированная альтернатива: точка (конец скоупа) и порядок (LIFO)
статичны, вызов гарантирован exactly-once (D188 R2, runtime-счётчик). Это аргумент ЗА C:
Nova получает RAII-надёжность освобождения БЕЗ зависимости от GC-финализации, сохраняя
compile-time видимость там, где владение передаётся (216).

### 6.5. Взаимодействие с 214 finalize-полосой

214 finalize: `#coerce fn StringBuilder consume @into_str() -> str` — НЕЯВНОЕ потребление
В ПОЗИЦИИ (typed position, вкл. call-arg: `log(sb)` → `log(sb.into_str())`, `sb` разряжен;
214-plan:42-54). Вопрос: не выстрелит ли авто-cleanup ПОСЛЕ такой финализации?

Ответ: **нет, флоу-анализ это уже видит.** 214 §finalize×поток-управления (214-plan:239-240):
неявная #coerce-финализация переводит переменную в `Consumed`; использование после →
`use-after` (`log(sb); sb.write(...)` → compile error, 214-plan:216-217). Раз `sb` после
#coerce-финализации уже `Consumed`, к концу скоупа он НЕ Live → авто-cleanup не
регистрируется/дизармится. Тот же дизарм-путь, что §6.1. **Дополнительно:** StringBuilder
всё равно относится к классу (b) и `@cleanup` НЕ объявляет — для него авто и не включается
вовсе, вопрос снимается по построению. Взаимодействие безопасно.

## 7. Рекомендация

**Принять гибрид C с опциональным `@cleanup` (рабочий кандидат владельца), с двумя
жёсткими ограждениями и поэтапным внедрением.**

Обоснование: (1) устраняет реальный бойлерплейт на error-путях ресурсов; (2) ортогонален
216 — периметр видимости передач сохраняется целиком (§5); (3) для типов-значений
опциональность оставляет строгую линейность, закрывая регресс «потеря работы» (§2.2);
(4) реализация — расширение уже существующего D188/D314-desugar, не новая машинерия (§1.3,
§6.1); (5) даёт детерминированный RAII без Boehm-финализаторов (§6.4).

**Ограждение 1 (эффекты).** Первый шаг — авто-cleanup ТОЛЬКО для `Cleanup[never]` и
эффект-чистых `@cleanup` (развилка 6.3.1). Это покрывает все 6 сегодняшних `@cleanup`-типов
(lock-guards/TcpStream/TlsStream — все `[never]`) без конфликта со strict-effects и без
неявных throw. Fallible-cleanup (File `Fail[IoError]`, Transaction `Fail[DbError]`)
включается ОТДЕЛЬНЫМ решением (развилка 6.3.2, эффект-пропагация) — как самостоятельный
под-вопрос, не блокирующий базовую фичу.

**Ограждение 2 (D133-амендмент).** Язык-меняющее → в том же слиянии амендмент D133
§«Что отвергнуто»: пункт «Drop-method auto-cleanup — отвергнут» пересматривается на
«авто-`@cleanup` разрешён как opt-in через объявление `@cleanup`; выбор commit/rollback
НЕ размывается, т.к. `@cleanup(outcome)` ветвится по `ScopeOutcome`». Плюс амендмент
D131/D180 Rule 6: «consume obligation в-scope check» не применяется к типам с `@cleanup`.

**Самый дешёвый первый шаг.** Технически минимальный keystone: в check_consume, на точке
выхода скоупа, где переменная `Live`/`MaybeConsumed` И её тип объявляет
эффект-чистый/`[never]` `@cleanup`, — вместо `D133-not-consumed` эмитить тот же
defer-desugar, что D314 §3 уже эмитит для `consume X = e { body }`, взяв «остаток скоупа»
как `body`. Это переиспользует готовый codegen (nv_run_body_capturing / nova_scope_exit /
дизарм-флаг). Оценка: ядро — точечная правка одного места в types/mod.rs (класс типа +
переключение диагностики на desugar) + перенацеливание существующего эмиттера. Миграция
кодовой базы — НУЛЕВАЯ на старте (существующий явный `consume X = e { body }` продолжает
работать; авто лишь ДОБАВЛЯЕТ разрешённость непотребления). Добавление `@cleanup` прочим
ресурсам (File, TcpListener, halves, UdpSocket, OnceGuard) — отдельная постепенная работа.

**Совместимость с очередью:** 216 сериализован ДО 214 (216-plan:52-53). Авто-cleanup —
после обоих: он опирается и на 216-периметр видимости, и на 214 finalize-дизарм-флоу.
Ставить в очередь ПОСЛЕ 214.

## 8. Открытые решения владельца (это выбирает владелец, не разведка)

1. **Эффект-политика (§6.3) — главное.** Вариант первого шага: авто только для
   `Cleanup[never]`/эффект-чистых. Включать ли fallible-`@cleanup` (File/Transaction)
   через эффект-пропагацию в сигнатуру объемлющей функции — сразу или отдельным решением?
   Что делает авто-cleanup с ошибкой `@cleanup` на **normal-path** (Success): throw
   наружу (D314 §4a: cleanup-throw = primary) или это запрещённая конфигурация для авто?
2. **Опциональный vs обязательный `@cleanup` (§5, тезис владельца п.3).** Рабочий кандидат
   — опциональный. Но обязательный (`type X consume` без `@cleanup` → ошибка, значения
   помечаются отдельным маркером `linear`/`value`) честнее по философии «visible ownership»
   (каждый consume-тип ЯВНО декларирует: авто-прибираемый ИЛИ строго-линейный, третьего
   нет). Опциональный оставляет молчаливую двусмысленность «нет @cleanup = линейный по
   умолчанию». Решение: оставить опциональным (меньше миграции, StringBuilder не трогаем)
   ИЛИ ввести явный маркер линейности для симметрии. Разведка склоняется к опциональному
   как первому шагу, но помечает симметрию как достойную рассмотрения.
   **Канонический пример линейного класса (✅ согласовано владельцем 2026-07-19):**
   `StringBuilder` — потребление (`@into_str`) извлекает ценность; авто-`@cleanup`
   молча выбросил бы построенную строку. Владелец: «полностью согласен». Именно такие
   типы обосновывают, зачем `@cleanup` НЕ делать: значения, где тихий дроп = потеря
   работы/доказательства. Для них строгая явность (D133, без `@cleanup`) — правильна.
3. **Добавлять ли `@cleanup` 8 ресурсам без него** (File, TcpListener, TcpReadHalf,
   TcpWriteHalf, UdpSocket, OnceGuard, Body, ffi-примеры) — и когда. Отдельная волна,
   не часть keystone.
4. **Судьба явного `consume X = e { body }`-блока после C.** Остаётся как способ ЯВНО
   ограничить время жизни ресурса под-скоупом (освободить РАНЬШЕ конца функции) — не
   вытесняется авто (авто = «до конца объемлющего скоупа»). Подтвердить, что обе формы
   сосуществуют (аналогия: Rust `drop(x)` явный vs авто-drop в конце блока).
5. **Диагностический UX.** Нужна ли информационная подсказка (не ошибка) в местах, где
   авто-cleanup вставлен неявно (для читаемости «здесь ресурс освобождается»), или это
   молча — как Rust. Прецедент 214 требовал, чтобы неявные точки были объяснимы в
   диагностике use-after.
