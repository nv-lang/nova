## Ф4. «STACK OVERFLOW» ДЛЯ ЭТИХ ФИКСТУР НЕВОЗМОЖЕН ПО ГЛУБИНЕ (установлено)

Развёртка размера слота на собранных `.exe` (дефолт — 4 МБ):

    p577_reflect.exe:  stack=262144 ec=0 | 524288 ec=0 | 1048576 ec=0 | 2097152 ec=0 | 4194304 ec=0
    p581_nested.exe:   stack=262144 ec=0 | 524288 ec=0 | 1048576 ec=0 | 2097152 ec=0 | 4194304 ec=0
    p581_probe.exe:    stack=262144 ec=0 | 524288 ec=0 | 1048576 ec=0

Все три reflect-фикстуры проходят при слоте **256 КБ** — в 16 раз меньше
дефолта. Пиковая глубина у них меньше 256 КБ, то есть запас к дефолту ≥16×.
Отсюда: наблюдавшийся отказ не мог быть отказом по глубине стека, и
«починка» его переменной `NOVA_FIBER_STACK=8388608` не могла работать как
увеличение запаса. Это подтверждает вывод записи №593 о том, что сообщение —
приманка, но НЕ подтверждает второй половины: причина осталась ненайденной,
потому что самого отказа нет.

**Таблица ничего не различает и различать не может: базовая линия зелёная.**
Дискриминатор «X убирает отказ» имеет смысл только при отказе без X. Это
надо сказать прямо, потому что исходная запись №593 сделала вывод о классе
именно из такой таблицы — а таблица снимается на отказе, который в этом
дереве не воспроизводится.

Отдельно: `NOVA_MAXPROCS=1` как дискриминатор в связке с `nova test` вообще
малоинформативен — раннер САМ выставляет `NOVA_MAXPROCS` тестовому процессу
(бюджет `NumCPU / jobs`, `test_runner.rs:3622`, `:7245`). При `--jobs 1` это
16, при `--jobs 16` — 1. То есть значение переменной в оболочке раннер
перекрывает своим, если фикстура не объявила `// ENV NOVA_MAXPROCS=…`.

## Ф6. ПРОВЕРЕННАЯ И ОПРОВЕРГНУТАЯ ГИПОТЕЗА ПО РАНТАЙМУ (установлено)

Аудит `compiler-codegen/nova_rt/fiber_arena_win.c` дал кандидата: Plan-151
захват `_nova_fw_main_stack_base` идёт из `_materialize_pool` через
`__readgsqword(0x08)` (NT_TIB.StackBase). Минкоро на Windows **свопает** поля
TIB на каждом переключении (`minicoro.h`, блоб `_mco_switch_code`, строки
710–726: `mov %gs:0x30,%r10`, затем обмен `0x08`/`0x10`/`0x1478`). А по
№108 тело `main` само стало файбером. Если бы `_materialize_pool` шёл уже
внутри файбера main-body, опубликованный «главный стек» был бы адресом
АРЕНЫ, и настоящий нативный стек main выпадал бы из обхода — ровно корень B
из p418, который на POSIX закрыт CAS'ом first-caller-wins
(`fiber_arena.c:1036…1084`), а на Windows соответствующего второго
call-site нет.

**Проверено точечной пробой (§1 шаг 4 плейбука), а не рассуждением.** Во
`nova_fiber_arena_set_main_stack` временно добавлен `getenv`-гейтед вывод;
прогон `p583_probe.exe` (единственная фикстура со `spawn`/`supervised`):

    [mainstack] published=000000DCA9C00000 in_arena=no local=000000DCA9BFF970 in_arena_local=no

`in_arena=no` для опубликованного адреса И для локальной переменной —
значит в момент `_materialize_pool` main действительно на НАТИВНОМ стеке,
публикуется корректный диапазон. **Гипотеза опровергнута; проба снята,
рабочее дерево чистое (`git status --short` пуст).**
