## Дефект №2 (корень) — общая дыра в `infer_expr_type`, не `.clone()`-специфика

**Репро (проба на обеих формах, уникальные имена):**
```
export type P362BInt(sign int, limbs Vec[u32])
export type P362BDec(mant P362BInt, scale int)
export fn P362BDec @bogus_method_probe() -> P362BInt {
    mut mant = @mant.frobnicate_nonexistent_xyz()   // выдуманный метод
    mant
}
```
До фикса `nova check` отвечал `ok:` — ЛЮБОЙ несуществующий метод/поле,
поставленный после `@field.`, где `field`'s owner (`Self`) — именованный
кортеж, проходил БЕЗ диагностики. Проверено на четырёх независимых формах:
голый вызов метода, bare-statement, аннотированный `let`, бесаннотационный
`let` — все молчали одинаково. Контрольная проба — то же самое на `Record`
(не кортеже) поймала ошибку немедленно (сравнение `p362_probe10.nv` в
рабочем прогоне окна).

**Корень:** `infer_expr_type`'s `Member`-арм (`compiler-codegen/src/types/mod.rs`,
~19151–19269) резолвил тип поля ТОЛЬКО для `TypeDeclKind::Record` — арма для
`TypeDeclKind::NamedTuple` не было вовсе (Record-арм добавлен `ice-p67-http`
2026-07-08, NamedTuple-парность не проведена). Значит `infer_expr_type(@field,
scope)` возвращал `None`, когда ОХВАТЫВАЮЩИЙ тип `@field` (`Self`) сам —
именованный кортеж, НЕЗАВИСИМО от типа самого поля. Этот `None` глушит
`f3_check_member_ctx` (~15042: `let Some(obj_tr) = self.infer_expr_type(obj,
scope) else { return; }`) — единственную функцию, которая валидирует ЦЕПНОЙ
доступ `obj.member`. Отсюда и симптом бэклога: `E_RECV_METHOD_MISMATCH`
«получатель мисрезолвится в чужой тип» на `.div_rem(...)` после
`@mant.clone()` — чекер тип канала для `@mant.clone()` тоже не материализовал
(та же `None`-цепочка), эмиссия падала в last-wins fallback по имени метода.

**Фикс:** добавлена `TypeDeclKind::NamedTuple`-ветка, зеркалящая Record-ветку
(bare + generic-подстановка через `subst_receiver_generics`), в тот же блок.
Один файл, чекер-канал, emit_c не тронут.

**Верификация фикса:**
- 4 ранее молчавшие пробы (метод-вызов/bare-statement/annotated-let/
  unannotated-let) → все стали честным `[E7320] no field or method ...` —
  подтверждено.
- Контрольная позитивная проба: РЕАЛЬНЫЙ метод, реально существующий на
  типе поля, вызванный через ту же цепочку (`@mant.total()`), продолжает
  резолвиться в ПРАВИЛЬНЫЙ тип и исполняется с ПРАВИЛЬНЫМ значением
  (`3*3=9`) — то есть фикс не просто запрещает, а восстанавливает верную
  типизацию канала (закреплено позитивной фикстурой, см. ниже).

## Дефект №1 — совет `.clone()` не проверял, есть ли `Clone` у поля вообще

**Что было:** текст `E_READONLY_COERCE` (field-launder форма,
`compiler-codegen/src/types/mod.rs` ~11192–11212) безусловно предлагал
`(b) скопируй явно — .clone() (D230)`, не проверяя, реализует ли ТИП ПОЛЯ
`Clone` вообще. `Clone` — opt-in протокол (D230: auto-derive только через
`#impl(Clone)`); без него `.clone()` не существует НИ НА ЗАПИСЯХ, НИ НА
КОРТЕЖАХ — совет был одинаково лжив для обоих (не тupleспецифика: контрольная
проба на именованном кортеже С `#impl(Clone)` → `.clone()` есть в
method_table, `synth_clone_registered_in_method_table`-тесты это уже
покрывали). До фикса №2 это расхождение не диагностировалось ВООБЩЕ
(молчаливый `None`); после фикса №2 расхождение стало честным `E7320` — но
сам ТЕКСТ совета продолжал бы указывать в тупик.

**Решил:** не «реализовать настоящий `@clone` для кортежей» — он УЖЕ
реализован (auto-derive через `#impl(Clone)` одинаково для Record и
NamedTuple, `types/mod.rs` тесты `synth_clone_registered_in_method_table`/
`synth_all_six_protocols_registered_together` это подтверждают на уровне
method-table). Дешевле и честнее — обусловить ТЕКСТ совета: диагностика
теперь проверяет доступность `clone` на типе поля (`t_provides_method` +
`protocol_method_satisfiable_for`, те же проверки, что использует общий
call-site валидатор) и подставляет:
- если `clone` доступен — прежний текст, без изменений;
- если НЕТ — честная альтернатива: добавить `#impl(Clone)` на декларацию
  ЛИБО санкционированный D326 in-out-хелпер с `mut`-параметром напрямую (без
  `.clone()`, без лаундера через локальную `mut`).

**Верификация:** проба `p362_probe11.nv` — тип БЕЗ `#impl(Clone)` получает
расширенный текст (`#impl(Clone)`/D326-хелпер); тип С `#impl(Clone)`
получает прежний краткий текст «(b) скопируй явно — `.clone()`». Оба случая
подтверждены дословно.

## Новые находки (НЕ чинил — вне скоупа `emit_c` этого окна; для номерации интегратором)

### Находка A: `#impl(Clone)` на ИМЕНОВАННОМ КОРТЕЖЕ ломает кодоген безусловно

Минимальный репро (БЕЗ поля, БЕЗ field-launder вообще):
```nova
#impl(Clone)
export type P362ZPoint(x int, y int)
test "..." {
    ro a = P362ZPoint(1, 2)
    ro b = a.clone()
}
```
`nova test` → `CC-FAIL`: `unknown type name 'Nova_P362ZPoint'; did you mean
'NovaTuple_P362ZPoint'?`. Синтезированный `Nova_P362ZPoint_method_clone`
эмитится с HEAP-ABI (`Nova_X*`, `nova_alloc(sizeof(Nova_X))`) — а реальный
C-тип именованного кортежа (D215, value ABI) — `NovaTuple_X`, без
указателя. Это НЕ дефект чекера — он живёт в синтезаторе/эмиссии
auto-derive `Clone` (`auto_derive.rs`/`emit_c.rs`), НЕ проверялся раньше:
существующие `synth_clone_*`-тесты в `types/mod.rs` покрывают только
регистрацию в method-table, ни один существующий тест/фикстура не
компилировал `#impl(Clone)` на bare именованном кортеже до конца через C.
Значит `#impl(Clone)` на именованных кортежах, скорее всего, никогда не
работал. Затрагивает мою же изначальную идею «показать позитивно, что
совет (b) работает, когда Clone реализован» — пришлось заменить позитивную
фикстуру, см. выше.

### Находка B (важнее): «санкционированный» D326 mut-param-хелпер из текста записи №362 сам НЕ даёт независимую копию — K1-класс тихой порчи

Текст записи №362 в `docs/plans/221.1-bug-sweep.md` утверждает: «Законный
обход найден и санкционирован: объявить параметр приватного помощника сразу
`mut` (D326, форма in-out) — отмывание не нужно вовсе», ссылаясь на приём из
`docs/plans/wip/PROGRESS-p-bignum-tuple.md`. Проверил буквально:
```nova
fn helper(mut mant P362AAInt) -> P362AAInt {
    mant.limbs.push(999)      // heap-backed поле, in-place мутация
    mant
}
export fn P362AADec @normalize() -> P362AAInt {
    helper(@mant)              // @mant — ro-ресивер, БЕЗ mut @
}
```
`nova check` пропускает без единой диагностики. Рантайм: `d.mant.limbs.len()`
после вызова МЕНЯЕТСЯ (было 2, стало 3) — то есть `@mant`, прочитанный из
RO-ресивера (метод БЕЗ `mut @`), передан в хелпер НЕ КОПИЕЙ, а
УКАЗАТЕЛЕМ на исходное хранилище получателя. Подтверждено сгенерированным
C: `helper((&(((*nova_self).mant))))` + `(*mant).limbs.push(...)` внутри
хелпера. Это ТОЧНО ТОТ ЖЕ класс звучности, который весь пакет
`[M-router-handler-mut-capture-escape-soundness]` закрывал для ЛОКАЛЬНОГО
ребиндинга (`mut x = @field`) — но через АРГУМЕНТ-позицию вызова функции с
`mut`-параметром, и существующий чекер это не проверяет вовсе (ни
`E_READONLY_COERCE`, ни диагностика «аргумент связан как readonly»,
~38679, не покрывает self-field-read RHS в этой позиции). D326-R3
описывает in-out ТОЛЬКО для параметра ТЕКУЩЕЙ функции, откуда пишешь
через свой же `mut`-параметр — расширение на «передай `@field` в НОВУЮ
функцию с `mut`-параметром = независимая копия» из прогресс-документа
`p-bignum-tuple` было домыслом, не подтверждённым фактом. Рекомендация
интегратору: (1) присвоить номер этой находке отдельно от №362 — она выше
приоритетом (K1, silent corruption, а не «совет ведёт в тупик»), (2)
поправить формулировку записи №362 (убрать «санкционирован» из текста, пока
не появится настоящая проверка на границе аргумента), (3) диагностика,
аналогичная `E_READONLY_COERCE`, но для позиции call-argument →
mut-parameter, где RHS — самофиксируемый `@field`/`ro`-локал с не-fully-stack
типом, — отдельное окно чекер-канала.
