## Шаг 0 — валидация (ЗАВЕРШЕНО, без checkpoint — форма и специализация ВАЛИДНЫ)

- `fn[T] T @to_str() -> str => "${@}"` — форма ВАЛИДНА: D145 (02-types.md:6489)
  явно даёт пример `fn[T] T @identity() -> T => @` — bare-T receiver blanket,
  ТОЧНО та же форма без bound. Прецедент identity-blanket для `T.from`
  (Path-form, D183 amendment, 02-types.md:7305-7323) подтверждает паттерн
  bare-T-blanket в языке уже есть (хотя это Path-form, не receiver-form).
- Специализация (инвариант 2) — ПОДТВЕРЖДЕНА: D84 (10-overloading.md:82-83)
  "Concrete побеждает generic. `fn f(v int)` выбирается раньше, чем `fn f[T](v T)`".
  D285 (10-overloading.md:696-719) — receiver-compatibility rule: конкретный
  метод ВСЕГДА приоритетнее blanket по receiver-типу (codegen `emit_c.rs`
  ~25289, Plan 164 Ф.3). Это применимо и к unbounded bare-T blanket (не только
  protocol-bounded D355 blanket) — механизм тот же (`method_receivers`
  lookup + last-wins fallback устранён receiver-compatibility блоком).
- **Существующий прецедент `[]u8 @to_str() -> Result[str, Utf8Error]`**
  (std/src/runtime/string/core.nv:279) УЖЕ существует и УЖЕ специфичнее
  blanket (другой arity/семантика — decode, не format). Blanket никогда не
  инстанцируется для `[]u8`, т.к. конкретный метод есть → безопасно, инвариант
  2 не нарушается.
- `char @to_str() -> str => str.from(@)` (runtime/char.nv:32) — уже существует,
  concrete override, тоже безопасно (просто нужно сменить тело в Шаге 4,
  т.к. str.from(char) удаляется).

## ВАЖНАЯ находка вне карты (не в исходном brief'е оркестратора)

`std/src/prelude/protocols.nv`:
- Строка 301: `Display protocol { @display(...) { w.write(str.from(@)) } }` —
  ОБЩИЙ (не примитивный) DEFAULT BODY протокола Display, синтезируется
  для ЛЮБОГО типа T с `#impl(Display)` но БЕЗ явного `@display`
  (`try_synthesize_default_method_with_gate`, emit_c.rs:8937). `@` тут —
  генерик T (НЕ примитив — примитивы имеют явные @display, которые ВСЕГДА
  побеждают default-synthesis, т.к. `all_methods.contains((T,"display"))`
  проверяется раньше синтеза). Это тоже надо мигрировать (str.from
  удаляется целиком) — решение: `w.write(@.to_str())`. Рекурсии НЕ будет:
  если T также не имеет `@to_str()`, применится blanket → `"${@}"` →
  интерполяция T снова попробует synthesize display для T → сработает
  cycle-guard (`synthesizing_default_methods`, emit_c.rs:8958) → вернёт
  None → упадёт в konfetti-fallback `nova_int_to_str((nova_int)(v))`
  (тот же деградант-фоллбэк, что и был РАНЬШЕ с str.from(@) для такого
  вырожденного T без display/to_str — poведение не хуже старого, не
  бесконечный цикл).
- Строка 348: `Debug protocol { @debug(...) { w.write(str.from_debug(@)) } }`
  — `str.from_debug` НИГДЕ не задекларирован как `fn str.from_debug(...)`
  (не extern, не Nova-body) — это ОТДЕЛЬНЫЙ (не `str.from`) символ, вне
  scope удаления str.from. Возможно вообще мёртвый/нерабочий код (не нашёл
  dispatch-ветку в emit_c.rs для `str.from_debug` Path-call — похоже
  actual record-Debug auto-derive идёt другим путём, НЕ через этот
  протокольный default-body текст). РЕШЕНО: НЕ трогать (вне scope — другой
  символ, не `str.from`), оставить как есть, если full conformance
  зелёный — значит не задет.

## ⛔ [ИСТОРИЧЕСКОЕ] CHECKPOINT + СТОП (2026-07-14) — до фикса D164 в main
## компилятор НЕ поддерживал специализацию unbounded bare-T blanket на примитиве

**Симптом.** Полный прогон `spec_tests/conformance` (пересобранный бинарь,
все Шаги 1-4 применены) дал:
```
NEG-NO-ERROR   spec_tests/conformance/neg/int_to_str_effect_collision_neg
  # expected `EXPECT_COMPILE_ERROR E_UNKNOWN_METHOD` but codegen succeeded
```
Это старый негатив-тест `[M-183-int-to-str-module-method-collision]`
(Plan 183 Ф.4 followup) — раньше он ПРОВЕРЯЛ, что `int` не имеет `to_str` и
`x.to_str()` (x int) в модуле, где ТАКЖЕ объявлен `NetErr @to_str()`, честно
падает `E_UNKNOWN_METHOD`. После Шага 1 (`int` теперь ИМЕЕТ `@to_str()` через
blanket) тест ожидаемо перестал компилироваться-с-ошибкой — САМ ПО СЕБЕ
это нормально (нужно было бы просто инвертировать тест в позитив). НО я
проверил СГЕНЕРИРОВАННЫЙ C — и это НЕ безобидная инверсия теста, это
**подтверждённый silent-miscompilation баг**:

```c
static Nova_StringBuilder* Nova_StringBuilder_method_append__nova_int(Nova_StringBuilder* nova_self, nova_int n) {
    (void)(Nova_StringBuilder_method_append(nova_self, Nova_NetErr_method_to_str(n)));
    //                                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //   nova_int передан в функцию, ожидающую Nova_NetErr* (enum-указатель) —
    //   type confusion, UB/SEGV на рантайме (n трактуется как pointer).
}
```
Это `StringBuilder mut @append(n int)` из Шага 3-правки (`string_builder.nv`),
тело которой — `@append(n.to_str())`. `n.to_str()` вместо диспатча в blanket
`Nova_int_method_to_str` (моя Шаг-1 моно-инстанциация) МИС-ДИСПАТЧИТСЯ в
`Nova_NetErr_method_to_str` — конкретный `@to_str()` НЕСВЯЗАННОГО типа
`NetErr`, который просто оказался ЗАРЕГИСТРИРОВАН ПОСЛЕДНИМ в этом CU
(единственном мега-CU `spec_tests/conformance`, где `NetErr` объявлен в
neg-тест-файле того же прогона). Та же картина — `f64`/`f32 @append`
(string_builder.nv), `str @trim_start_matches`/`@trim_end_matches`/
`@pad_start`/`@pad_end`/`@pad_center` (transform.nv, `c.to_str()`/
`fill.to_str()` на `char`).

**Корень (найден в коде, precisely):** `compiler-codegen/src/codegen/emit_c.rs`
~37005-37035 — блок «Plan 164 Ф.3: protocol-aware blanket dispatch» (D285,
receiver-compatibility rule). Это ЕДИНСТВЕННЫЙ механизм, который умеет
приоритизировать unbounded/bounded blanket над «last-wins single-key
`method_receivers`» fallback. Но:
```rust
// Skip primitives — they have their own dispatch above.
let recv_is_candidate = !recv_base.is_empty()
    && !matches!(recv_base,
        "nova_int" | "nova_bool" | "nova_char" | "nova_str"
        | "nova_f32" | "nova_f64" | "int" | "bool" | "char"
        | "str" | "f32" | "f64" | "void")
    && !recv_base.starts_with("nova_");
```
— ПРИМИТИВЫ ЯВНО ИСКЛЮЧЕНЫ из receiver-compatibility guard (комментарий
«they have their own dispatch above» — но ЭТОТ «свой путь для примитивов»
НЕ содержит эквивалентной blanket-vs-concrete-на-другом-типе проверки: для
примитивного ресивера метод резолвится через ДРУГОЙ (более старый,
pre-D285) механизм, который страдает от ТОЙ ЖЕ «last-wins по имени метода»
болезни, что D285 чинил для non-примитивных ресиверов в Plan 164 Ф.3.

**Почему это ИМЕННО checkpoint, не обычный баг-фикс той же волной.**
Экспериментально подтверждённая специализация РАБОТАЕТ (D84 «concrete
побеждает generic», D285) — но ТОЛЬКО для non-primitive ресиверов. Для
primitive ресиверов (int/f64/f32/bool/char/str) — ИМЕННО тот тип, для
которого весь этот план (174.2) существует — механизм СЛОМАН при коллизии
имени метода с НЕСВЯЗАННЫМ конкретным типом в том же CU. Задание прямым
текстом: «Если Nova не поддерживает специализацию ИЛИ сама форма
`fn[T] T @to_str()` невалидна — checkpoint+СТОП (это меняет весь дизайн,
решает владелец)». Форма ВАЛИДНА (D145), но специализация для примитивов —
НЕТ. Это системный архитектурный гэп в компиляторе (не в std/**), затрагивает
ЛЮБОЙ bare-T unbounded blanket на примитивном ресивере (не только мой
`@to_str()`) — исправление требует расширения D285-механизма на примитивы
(нетривиально: нужно понять, что это за «свой путь для примитивов выше»,
почему он не ловит blanket-vs-concrete коллизию, и не сломать существующие
примитивные dispatch-пути, включая уже принятые в conformance `fn[T] T
@identity()`/`@d145_self()` precedents — которые, ВОЗМОЖНО, тоже уязвимы,
просто не сталкивались с коллизией имени в существующих тестах).
