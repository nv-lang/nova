# Аудит: грамматика (`compiler-codegen/src/parser/mod.rs`) против норм записи в `spec/decisions/`

Повод — дефект №487 (`docs/plans/221.1-bug-sweep.md`): D406 (`spec/decisions/02-types.md:725`)
нормирует ровно две формы записи суммы (inline без `|` перед первым вариантом /
многострочная с `|` у каждого варианта включая первый), гибрид не разрешён ни одной —
парсер гибрид принимает молча (`PASS: 1 FAIL: 0`). Класс: **норма есть, энфорса нет** —
расхождение спеки и реализации, не путать с планом 254 («правило нигде не записано»).

Задача: перечислением (не догадкой) найти, сколько ЕЩЁ D-решений о **форме записи**
(синтаксис — как ты это буквально пишешь, а не типы/семантика/эффекты) грамматика
допускает нарушать вопреки норме.

Метод: `spec/decisions/*.md` грепом по маркерам нормативности («обязателен»,
«запрещено», «не допускается», «каноническая форма», «единственная форма») →
для каждого найденного правила о форме записи — проверка `compiler-codegen/src/parser/mod.rs`
(и `lints.rs`, если правило отдано линту), при необходимости `compiler-codegen/src/lexer/mod.rs`,
`compiler-codegen/src/types/mod.rs`, `compiler-codegen/src/argbind.rs` (там, где парсер
делегирует проверку формы дальше по пайплайну). Билдов НЕ запускалось (запрещено
условиями задачи + на машине параллельно шли замеры времени) — все вердикты установлены
статическим чтением кода, без единого прогона `nova check`.

### Список «БЕЗ энфорса» — чем грозит нарушение

- **D406, гибридная форма enum (seed-кейс №487).** Неоднозначность чтения: код выглядит
  как единый канон записи суммы, а на деле смешивает два разрешённых образца в один
  неразрешённый третий; молчаливое согласие грамматики гарантированно повторит находку
  №487 при следующем таком написании где угодно в дереве.
- **D406, старый leading-`\|` синтаксис без `enum` (явно отвергнут тем же решением).**
  Расхождение спеки и кода хуже, чем в предыдущем пункте: это не гибрид, а ПОЛНОСТЬЮ
  ретироnированная форма, которая тем не менее компилируется как ни в чём не бывало —
  риск, что новый или скопированный из старого носителя код тихо использует мёртвый канон.
- **D52, single-variant sum.** Потенциальная ошибка намерения: `type X enum A` — вырожденный
  sum там, где норма прямо требует record; синтаксически «валидно», семантически —
  автор писал не то, что думал.
- **D52, избыточная форма field punning `{ name: name }`.** Косметика / расхождение стиля:
  ничего не ломается, но норма явно требует shorthand словом «обязан» — без энфорса
  дрейф стиля копится по кодовой базе незаметно.
- **D49, пустые `;`.** Косметика с лёгким привкусом потенциальной ошибки: висящий или
  задвоенный `;` не диагностируется, хотя норма называет его «всегда баг» — типичный
  нераспознанный след неаккуратного merge / codegen / copy-paste.
- **D44, `_` в числовых литералах без проверки позиции.** Неоднозначность чтения:
  `1__0` или `10_` компилируются молча (underscore чисто декоративный, стирается
  безусловно) — читатель видит нестандартную группировку разрядов, которая ничего не
  значит и никем не проверяется, что создаёт ложное впечатление смысла.
- **D45, `-> T` необязателен на практике в block-body.** Самое серьёзное из семи:
  меняется ФАКТИЧЕСКОЕ поведение программы, а не только стиль записи — забытая
  аннотация возврата молча превращает функцию в «функцию без результата», trailing-
  значение тела отбрасывается без единого предупреждения.
