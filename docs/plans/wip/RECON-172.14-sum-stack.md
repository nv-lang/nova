## 0. Две поправки к тексту плана — обе установлены чтением кода

### 0.1 Детектора рекурсии НЕТ. Обе ссылки плана неверны

План (`172.14:349`) и `172.4:76-78` утверждают: «Детектор рекурсии есть
(Plan 62.A.bis / 08-runtime ~:8211)». Проверено:

* Plan 62.A.bis — это `codegen/sum_schema_registry.rs`, реестр схем сумм
  (имена вариантов, C-типы полей, захардкоженный `SumAbi`). Анализа
  рекурсии в нём нет ни строки.
* `spec/decisions/08-runtime.md` около :8211 — секция fiber-arena
  (guard-страницы, VA-бюджет, D276). К рекурсии типов отношения не имеет.

Единственный настоящий детектор — `check_infinite_type` /`infinite_dfs`
(`compiler-codegen/src/types/mod.rs:7181` и `:7271`), DFS по графу
inline-вложенности с `on_path`-множеством: ловит и прямую, и взаимную
рекурсию. **Но суммы исключены из него дважды и намеренно:**

* как субъект — `types/mod.rs:7186`, `subject_inlineable` матчит только
  `Record(!heap) | NamedTuple | Newtype | Alias`, для `Sum` ранний выход;
* как ребро — `types/mod.rs:7311-7315`, комментарий в коде: «BOXING
  short-circuit — the load-bearing branch. A Sum is ALWAYS heap»,
  `boxed_to_pointer ⇒ return None`.

То есть `type List enum Nil | Cons(int, List)` детектором даже не
обходится: он не «разрешён», о нём просто **не производится факта**.
Потребитель у детектора один — диагностика `E_INFINITE_TYPE`; кодоген в
него не ходит.

**Следствие для плана:** предпосылка Ф.2 «детектор есть, остаётся его
спросить» ложна. Детектор надо написать — это отдельный атом (A2), и он
дешёвый, потому что каркас обхода (`infinite_dfs`) уже стоит рядом и его
надо лишь перестать коротить на `Sum`.

### 0.2 GC-риск сформулирован в брифе строже, чем есть. Сборщик консервативный

Тезис «значение на стеке не сканируется как объект кучи» для Nova неверен
в общем виде. Сборщик — Boehm, консервативный, с включёнными
interior-указателями:

* `compiler-codegen/nova_rt/alloc_boehm.c:1-4` — «Boehm GC implementation.
  Full tracing GC»; `:254` — `nova_alloc` это `GC_malloc`;
* `alloc_boehm.c:218` — `GC_set_all_interior_pointers(1)` по умолчанию
  (выключается только диагностическим `NOVA_GC_NO_INTERIOR=1`, и там же
  написано, что выключение НЕ сохраняет корректность).

Значит указатель, лежащий инлайном в стековой структуре, сборщик найдёт
машинным сканом стека и регистров. Прецедент, работающий сегодня и
доказывающий это, — `nova_str` (`nova_rt/nova_rt.h:65-68`): GC-указатель
внутри передаваемой по значению структуры, удерживаемый исключительно
консервативно. Тем же способом живут все `NovaValue_X` и `NovaOpt_T`.

Ни описателей, ни битмап, ни типизированной аллокации в системе нет
вообще: `nova_alloc_atomic`, `GC_make_descriptor`,
`GC_malloc_explicitly_typed` в дереве отсутствуют. Единственный
примитив — нетипизированный сканируемый `GC_malloc`.

**Где риск ВСЁ ЖЕ реален** (это и есть содержание атома A1):

1. **Статики.** `alloc_boehm.c:175` — `GC_set_no_dls(1)`, сегмент данных
   не сканируется; корни регистрируются явно, `emit_c.rs:10177`
   (`nova_gc_add_root(&_nova_const_N_value, … + sizeof(…))`). Сумма-значение
   в статике обязана попасть в этот же вызов и целиком.
2. **Области вне GC.** `nova_alloc_uncollectable` для `SpawnCtx`
   (`nova_rt/alloc.h:22-39`), calloc'нутые стеки Windows-каналов
   (`nova_rt/channels.h:592-593` — «calloc'нутые stacks НЕ GC roots»),
   TLS (`emit_c.rs:12263` — ручной pin «TLS not scanned»). Сегодня payload
   там держится зарегистрированным heap-объектом; после правки указатели
   payload лежат инлайном.
3. **Ложное удержание.** `GC_malloc` зануляет; стековая структура — нет.
   Неинициализированные байты неактивного варианта union'а будут
   просканированы как потенциальные указатели.
4. **Фибро-стеки.** Приостановленные стеки фибр лежат вне OS-стека и
   сканируются отдельным механизмом (`nova_rt/fibers.h:61-63`,
   `fiber_arena_win.c:194` — `GC_push_all_eager`). Зависимость та же, что
   и сегодня, но проверить обязательно.

## 2. Существующие фундаменты

### 2.1 `AllocKind` — есть, но для сумм не спрашивается

`ast/mod.rs:1067`: `enum AllocKind { Heap, Value, ValueHeapPromoted }`,
ровно как в плане 127. Помощники `is_heap` / `is_stack_value` /
`is_promoted`, C-префикс `Nova_` / `NovaValue_` / `Nova_`.

Диспетч по `AllocKind` стоит **только внутри ветки `TypeDeclKind::Record`**
(`emit_c.rs:17938-17939`). Для `TypeDeclKind::Sum` поле `allocation` не
читается нигде: греп `AllocKind::` даёт 102 вхождения по всему
`compiler-codegen/src`, и ни одно не в контексте суммы.

При этом парсер модификатор `value` принимает **до** тела типа
(`parser/mod.rs:4473-4478`, контекстное ключевое слово, rank 1), поэтому
`type X value enum A | B` разбирается и кладёт `allocation = Value` в
`TypeDecl` — просто дальше это молча игнорируется. То есть носитель
решения в AST уже есть и уже доезжает до кодогена.

### 2.2 `SumAbi` — целевая форма УЖЕ описана

`codegen/sum_schema_registry.rs:59-72`:

* `ValueOptionLike` — `NovaOpt_<T>` на стеке, `.tag`/`.value` (Option);
* `PointerErrorLike` — `Nova_<Name>*` через `nova_alloc`, `->tag` /
  `->payload.<V>._<i>` (Result + **все пользовательские суммы**);
* `ValueTagPayload` — **инлайновая value-структура `tag + union payload`**,
  `.tag` / `.payload.<V>._<i>`.

`ValueTagPayload` — это в точности целевая форма Ф.2, и она уже заведена
(`sum_schema_registry.rs:518`, для `RuntimeError`). Разветвление кодогена
на её основе — то, ради чего Ф.1 плана 62.A.bis реестр и строила.

Оговорка, найденная проверкой: у `RuntimeError` метка ABI **устарела** —
реестр говорит `ValueTagPayload`, а `nova_rt/array.h:796` возвращает
`Nova_RuntimeError*` из `nova_alloc`. Значит рабочего примера
`ValueTagPayload` в дереве нет; есть только объявленный контракт.

### 2.3 `escape_analyze.rs` (Plan 127) — два независимых анализа, оба готовы

`compiler-codegen/src/escape_analyze.rs`, 1367 строк, `EscapeResult`
несёт **две** карты:

* `promoted_per_fn` — локалы value-записей, чей **адрес** (`&v`) достигает
  синка (return / захват замыканием / запись в heap-поле / глобал /
  аргумент вызова) ⇒ промоушен на кучу (`AllocKind::ValueHeapPromoted`).
  V1 OVER-promote: любая неопределённость ⇒ на кучу;
* `ident_escapes_per_fn` (добавлено самим 172.14 под sret/`_out`) — локалы,
  чьё **значение-идентификатор** достигает синка. Это уже готовый
  placement-предикат стек-слота, независимый от value-записей и
  работающий по имени.

Для Ф.2 существенно: `ident_escapes` пригоден как есть — он не завязан на
`AllocKind`, а `promoted_per_fn` собирается только по множеству
value-записей (`collect_value_record_types`), и его надо будет расширить
множеством value-сумм.

### 2.4 `NovaOpt_<T>` — образец формы, но НЕ переиспользуемый механизм

Проверено по коду и по сгенерированному C:

1. **Объявление** — `emit_c.rs:56531-56543`: типдеф синтезируется **строкой**
   в буфер, ключ — `sanitize_for_novaopt(c_ty)` (`emit_c.rs:55945`, `*`→`_p`),
   склейка по маркерам `__NOVAOPT_TYPEDEFS__`. Runtime-макрос
   `NOVA_OPT_DECL(T)` — `nova_rt/array.h:52-56`. Один тип **на C-тип
   payload**, а не на Nova-тип.
2. **Конструирование** — `emit_c.rs:56652-56669`: составной литерал C,
   **без аллокации**: `((NovaOpt_X){.tag = NOVA_TAG_Option_Some, .value = v})`.
3. **Матчинг** — `emit_c.rs:56673-56689`: `.tag == NOVA_TAG_Option_None`,
   либо под NPO — `v.value == NULL`.
4. **Параметр** — `emit_c.rs:56931-56935`: возвращается голое
   `NovaOpt_<sani>` **без `*`**, по значению. Требует пре-пасса
   `ensure_novaopt_decls_for_typeref` (`emit_c.rs:56199`), иначе типдеф не
   успевает объявиться.
5. **В Vec** — элемент хранится **инлайном**, что заставляет полное
   определение структуры предшествовать инстансу Vec; отсюда машинерия
   упорядочивания `emit_c.rs:11252-11274`.

Вывод: как **образец целевой формы** — да. Как **механизм для повторного
использования** — нет: двухвариантные захардкоженные теги
`NOVA_TAG_Option_None/Some`, одно плоское поле `.value`, спецслучай NPO,
три вручную упорядочиваемых буфера. Для N-вариантной суммы с `union
payload` придётся заново решать ровно то, что `emit_sum_type` уже умеет;
переиспользуется от NovaOpt только **урок про порядок объявлений**
(п. 5) — и он обязателен.

## 3. Критерий пригодности — что должно быть истинно, чтобы сумма жила на стеке

| Условие | Ответ в коде есть? | Где / чего не хватает |
|---|---|---|
| **Нерекурсивность прямая и взаимная** | **НЕТ** | Каркас DFS есть — `types/mod.rs:7271` `infinite_dfs` с `on_path`; но суммы из него вырезаны (`:7186` как субъект, `:7311-7315` как ребро). Нужен новый `sum_is_recursive`, переиспользующий обход |

## 6. Что может пойти не так

**Где правка меняет ABI.**
(1) Сигнатура любой функции с параметром/возвратом суммы: `Nova_X*` →
`NovaValue_X` — прямое изменение C-ABI, задевает FFI
(`external_registry.rs:620`, `:675`). (2) Mangled-имена моно-инстансов
теряют `_p` — меняются имена символов `Nova_Vec____*`. (3) `Option[Sum]`
меняет и размер, и раскладку (NPO → tagged). (4) Ресивер метода
(`emit_c.rs:20139`) перестаёт быть указателем — на `mut @` включится
in-out-указательный контракт Р10/D326, что для суммы сегодня не
применялось.

**Где `match` может испортиться молча.** Тернарка `:52888` — не
единственное решение: четыре сайта печатают `->payload.…` хардкодом
(`:52960`, `:53087`, `:53264`, `:53646`). Если поправить тернарку и
забыть их, получится `x.tag` рядом с `x->payload` — C не соберётся, то
есть отказ **громкий**. По-настоящему тихие два: `is_struct_type`
(`emit_c.rs:48208`, проверяет `starts_with("Nova_")`) переключит
memset-vs-assign, и `with_result_category` (`:285`, `t.contains('*')`)
переведёт результат with-блока из `Pointer` в `ValueStruct`, меняя
инициализацию с `NULL` на что-то другое (`:12590`, `:12643`). Оба обязаны
быть в чек-листе A4.

**Что будет с `Result`.** Не трогается: `NovaRes_<ok>_<err>` —
самостоятельный путь, `PointerErrorLike`
(`sum_schema_registry.rs:456`), heap. Но он **содержит** пользовательские
суммы в payload, и это уже работает с value-типами: проба показывает
`NovaRes_nova_str_NovaValue_Utf8Error` с `NovaValue_Utf8Error _0` инлайном.
Прецедент положительный. Отдельно отмечено: `NovaRes` несёт
нетипизированное поле `void* err_typed_payload` — ещё одно слово, живущее
исключительно консервативным сканом.

**Что будет с суммами в `Vec[T]`.** Сегодня `Vec[Colour]` — это
`Nova_Colour** data`, массив указателей. После A5 — массив структур:
буфер растёт в `sizeof(NovaValue_X)/8` раз, зато исчезает N аллокаций и
разыменований. Буфер аллоцируется `RawMem.alloc` → `nova_alloc`, значит
остаётся сканируемым; отдельного GC-действия не нужно. Риск — не GC, а
**порядок объявлений**: инлайновое хранение требует полного определения
типа до инстанса Vec (та же машинерия, что у NovaOpt).

**Что будет с рекурсией через `Option[Self]`.** Это главная ловушка
детектора. `NovaOpt_T` — по значению, поэтому `type N enum Leaf |
Node(Option[N])` — **настоящая бесконечная** структура, если `N` сделать
значением, и она обязана уходить в heap. Сегодня она компилируется только
потому, что `N` — указатель, и `Option[N]` под NPO вырождается в тот же
указатель. В корпусе таких сумм сейчас нет (проверено: множество
рекурсивных совпадает при обоих способах трактовки контейнеров), но
правило обязано стоять в A2 до того, как A4 начнёт что-то менять.

**Отдельно, не предмет Ф.2, но найдено по дороге — см. §7.** Правый
операнд `==` над суммой **вычисляется больше одного раза**: доказано
прогоном, 2 раза. Это дублирует побочные эффекты и умножает аллокацию.
Для Ф.2 существенно тем, что после перевода суммы в значение цена
повторного вычисления меняется, но сам дефект — сегодняшний.

### A2.1 Почему нельзя было переиспользовать `check_infinite_type`

Он отвечает на **другой** вопрос — «конечен ли layout value-типа СЕГОДНЯ» — и
вырезает суммы из графа дважды намеренно: как субъект (`types/mod.rs:7186`)
и как ребро (`:7311-7315`, «A Sum is ALWAYS heap»). При сегодняшнем ABI
ссылка на сумму и правда указатель, поэтому цикл она замкнуть не может.
Размещение спрашивает контрфакт — «а если бы сумма лежала инлайном» — значит
ребро суммы надо вернуть. Все прочие правила оставлены совпадающими с
size-обходом, чтобы две функции не разъехались молча.

Правила рёбер и причина каждого:

| ребро | вердикт | почему |
|---|---|---|
| payload варианта суммы | INLINE | сама проверяемая гипотеза |
| поле value-записи / кортежа / newtype / alias | INLINE | лежит на месте |
| поле HEAP-записи | STOP | это указатель, им и останется |
| `Option[T]` | **INLINE** | `NovaOpt_T` — структура по значению |
| `Vec`/`HashMap`/`Set`/`Chan`[T] | STOP | буфер в куче за указателем |
| `Result[..]` | STOP | `NovaRes_*` — указатель в кучу |
| `[]T`, `*T`, `ref T` | STOP | указатель либо `{ptr,len}` |
| `[N]T` | INLINE | n инлайн-копий |
| кортеж | INLINE | каждый элемент |
| примитив, `str` | STOP | конечный лист |
| неразрешимое имя | STOP | цикл недоказуем |

Направление ошибки выбрано осознанно: **пере-обнаружение безопасно**
(рекурсивна → остаётся в куче → ровно сегодняшнее поведение),
недо-обнаружение — нет. Единственное правило, которому приходится гадать
(неизвестная generic-инстанциация), обходит и тело шаблона, и аргументы
типа — это может только добавить циклов, но не спрятать.

Хардкод-список контейнеров — страховка, а не механизм: `IndexMap`, которого
в нём нет, отсекается структурно (heap-запись ⇒ указатель), что и показал
разбор `JsonValue` ниже.

## 7. Поправка к §6: равенство сумм — что снято и что доказано

Интегратор не воспроизвёл утверждение «равенство сумм сравнивает только
теги» и потребовал либо минимальный файл, который печатает ложь, либо
вычеркнуть. Перепроверено прогоном, не чтением.

**Снято.** Утверждение неверно. Проба `172.14-f2-probes/p5-eq.nv`,
собрана и **запущена**:

```
Circle(1)==Circle(2) -> false     Text(one)==Text(two) -> false
Circle(1)==Circle(1) -> true      Text(one)==Text(one) -> true
Circle(1)==Rect      -> false     Text(one)==literal   -> false
Rect(1,2)==Rect(1,3) -> false     Num(5)==Num(5)       -> true
Red==Red             -> true      Num(5)==Num(6)       -> false
Red==Green           -> false     Num(5)==Blank        -> false
```

Эмиттер разворачивает полное по-вариантное сравнение вида
`l->tag == r->tag && (l->tag != Num || l->payload.Num._0 == r->payload.Num._0)
&& (l->tag != Text || nova_str_eq(l->payload.Text._0, r->payload.Text._0))`.
Ошибка в первой редакции — обобщение вырожденного случая: я смотрел
`Colour`, где ВСЕ варианты unit, и там сравнение тегов и есть полное
правильное сравнение. Класс ошибки — ровно тот, против которого стоит
правило «судить по прогону»: форма, у которой частный случай выглядит как
общий.

**Доказано взамен — правый операнд `==` вычисляется больше одного раза.**
Проба `172.14-f2-probes/p6-eq-reeval.nv`, собрана и **запущена**:

```
result=true rhs_evaluated=2 times      // n1 == bump(log, 5), где n1 = Num(5)
blank result=false rhs_evaluated=1 times
```

Причина видна в развёртке: каждая `&&`-клауза печатает выражение правого
операнда заново. Для совпадающего `Num` берутся клауза тега и клауза
payload'а `Num` ⇒ 2 вычисления; клауза `Text` отсекается
короткозамкнутым `tag != Text` ⇒ третьего вычисления нет. Для `Blank`
обе payload-клаузы отсекаются ⇒ 1.

Следствия: (1) побочные эффекты правого операнда **дублируются** — это
дефект наблюдаемого поведения, а не только производительности;
(2) `x == Variant(...)` аллоцирует правый операнд столько же раз.

**Заведён как реестр 221.1 №744 (K1, блокер тега) и ЗАКРЫТ 2026-08-22** —
до Ф.2 намеренно: значимая сумма унаследует ту же цепочку `&&`-клауз, и
чинить после размещения значило бы переселить дефект, а не убить.
Замер по формам (тот же бинарь, `NOVA_KILL_744=1` — было → стало):
сумма-совпавший вариант 2 → 1, вариант-запись с двумя полями 3 → 1,
вложенный payload 2 → 1, значимая запись 2 → 1, кортеж 2 → 1;
несовпавший вариант и unit были 1 и остались 1 (клаузы отсекаются `&&`).
Общее правило до правки: вычислений = 1 + число полей совпавшего варианта.
Сторож — `spec_tests/conformance/standalone/n744_eq_operand_single_eval_pos.nv`.

**Также уточнено.** `emit_c.rs:21921` в первой редакции описан как
«вырождает равенство сумм в сравнение указателей». Формулировка слишком
широкая: откат охраняется флагом `novaopt_early_gen` и срабатывает только
в раннем NovaOpt-проходе, когда тела структур ещё не выпущены (комментарий
на `:21913-21919`). Достижим ли он так, чтобы дать неверный ответ, я не
проверял, и утверждения об этом не делаю.

## A1 — GC-правда прогоном. ЗАКРЫТ 2026-08-22

Кодоген не тронут. Всё ниже — прогон.

### A1.0 Почему инструмент именно такой

Вопрос A1: **значение-сумма живёт инлайном в слоте, а не за `nova_alloc`;
когда активный вариант её union'а держит GC-указатель, видит ли его
сборщик.** Boehm консервативен, поэтому вопрос сводится к другому:
**какие слоты вообще сканируются.**

Очевидный способ проверить — прочитать объект обратно и посмотреть, целы
ли байты — **не работает**: ручка, которой читаешь, сама становится
корнем. Поэтому сигнал — `GC_register_finalizer`: финализатор срабатывает
ровно тогда, когда объект стал недостижим, и наблюдение не стоит нам ни
одной ссылки.

Каждая область меряется **дважды**, и засчитывается только когда оба
прогона легли туда, куда предсказано:

* **live** — инлайновый указатель на месте ⇒ ждём 0 собранных;
* **dead** — тот же слот обнулён перед сборкой ⇒ ждём N собранных.

Фикстура, зелёная при снятом указателе, не доказывает ничего; **dead-прогон
и есть то, что придаёт смысл live-прогону.**

Инициализация зеркалит `nova_gc_init` (`alloc_boehm.c:165-230`) построчно,
включая `GC_set_no_dls(1)` и `GC_set_all_interior_pointers(1)`.

### A1.1 Результат — C-стенд `scripts/tools/gc-inline-ptr-experiment.c`

Форма под тестом — `struct { intptr_t tag; void* p; }`, указатель на
**ненулевом смещении** (иначе мерили бы «указатель в начале аллокации», а
не «инлайном в структуре»). N = 200 объектов по 64 Б на область.

```
область                              live   dead   вердикт
R1  кадр стека (локальный массив)       0    200   СКАНИРУЕТСЯ
R2a статик, без add_root              200    200   НЕ СКАНИРУЕТСЯ  <-- экспозиция
R2b статик, С add_root                  0    200   СКАНИРУЕТСЯ
R3  uncollectable (SpawnCtx)            0    200   СКАНИРУЕТСЯ
R4  calloc (стеки каналов)            200    200   НЕ СКАНИРУЕТСЯ  <-- экспозиция
R5  GC-буфер кучи (backing Vec)         0    200   СКАНИРУЕТСЯ
R6  НЕГАТИВНЫЙ КОНТРОЛЬ (xor)         200    200   КОНТРОЛЬ ИСПРАВЕН
R7  ложное удержание (без scrub)     1/200 объектов удержано мусорным словом
```

Числа чистые: каждый dead-прогон собирает ровно 200/200, каждый
положительный live-прогон — ровно 0. Три прогона подряд идентичны.

**Первый прогон стенда соврал, и это важнее самих чисел.** Он показал
`R1 кадр стека — НЕ СКАНИРУЕТСЯ`, что невозможно. Причина: `measure()`
нигде не читала массив слотов, поэтому на `-O1` записи в него — мёртвые,
и clang их удалил. Стенд мерил пустой массив. Починка — обратное чтение
слотов через `volatile`-сток ПОСЛЕ сборки (`measure()`, комментарий на
месте). Вывод на будущее: невозможный результат — это не шум, это
сломанный инструмент, и его нельзя объяснять «особенностями Boehm».

### A1.2 Результат — Nova-стенд `172.14-f2-probes/p7-gc-inline-nova.nv`

Области, которые может породить только Nova. `type Held value { ro tag
int, ro p Blob }` понижается ровно в `struct NovaValue_Held { nova_int
tag; Nova_Blob* p; }` (проверено в сгенерированном C) — это и есть
целевая раскладка Ф.2.

```
R1n кадр стека, инлайн-указатель жив           -> true
R5n элемент Vec, инлайн-указатель жив          -> true
КОНТРОЛЬ спрятан-как-int: цел  47 / 200        -> детектор ловит потерю
Rfn стек ФАЙБЕРА, инлайн-указатель жив         -> true
```

Три прогона подряд идентичны, до последней цифры.

Попутно подтверждено сгенерированным C: `Vec[Held]` монолитизируется в
`Nova_Vec____NovaValue_Held` — **без суффикса `_p`**, то есть элемент
лежит инлайном. Это ровно то, что атом A5 сделает с суммами, и здесь оно
уже работает.

**Контроль пришлось чинить дважды, и обе ошибки поучительны.**

1. Первая версия держала `ro raw = RawMem.alloc(...)` живым до конца
   блока — указатель оставался в кадре, буфер, естественно, выживал.
   Аллокация уехала в хелпер `hide64()`, чей кадр умирает до churn'а.
2. Вторая версия всё равно дала **200/200 цел**. Причина принципиальная:
   консервативный сборщик **не читает статические типы Nova**. Обычный
   `int` с адресом внутри, лежащий в сканируемом backing-буфере
   `Vec[int]`, неотличим от указателя и удерживает свою цель. Спрятать
   адрес можно только **обфускацией** — XOR.

После XOR контроль даёт 153 из 200 потерянных ⇒ детектор доказанно ловит
потерю. (47 выживших — блоки, которые аллокатор просто не переиспользовал;
детектор на переиспользовании иначе и не бывает, а требуется от него
только не быть слепым.)

Второй пункт стоит запомнить и вне A1: **любое `int`-поле в сканируемой
памяти удерживает то, на что оно случайно похоже.** Это же и объясняет,
почему сумма, спрятанная в erased-слот через `(nova_int)(intptr_t)`
(сайты M4), сегодня не теряется.

### A1.3 Ответ на вопрос, решающий форму фазы

**Находит ли Boehm указатель, лежащий ИНЛАЙНОМ в структуре, во всех пяти
областях? — Нет. В пяти из семи находит, в двух нет.**

| область | сканируется | чем держится |
|---|---|---|
| кадр стека | **да** | машинный скан стека |
| стек файбера | **да** | `GC_set_push_other_roots` + `GC_push_all_eager` на занятый слот арены (`fiber_arena_win.c:278`, POSIX — `fiber_arena.c:505`) |
| буфер GC-кучи / backing `Vec` | **да** | обычный трейс кучи; буфер идёт через `RawMem.alloc` → `nova_alloc` |
| `nova_alloc_uncollectable` (SpawnCtx) | **да** | `GC_malloc_uncollectable` сканируется, только не подметается |
| статик С `nova_gc_add_root` | **да** | явный корень, `emit_c.rs:10177` |
| **статик БЕЗ `nova_gc_add_root`** | **НЕТ** | `GC_set_no_dls(1)`, `alloc_boehm.c:175` |
| **plain `calloc`/`malloc`** | **НЕТ** | никто не регистрирует |

Прецедент `nova_str` действительно закрывал ровно одну область из семи —
замечание интегратора справедливо. Но проверенными оказались все семь, и
две из них красные.

Дополнительно: результат **не зависит** от `GC_set_all_interior_pointers`.
Прогон с `NOVA_GC_NO_INTERIOR=1` даёт ту же таблицу — payload-указатель
суммы это **базовый** указатель, а не внутренний. Это усиливает вывод:
безопасность value-суммы не висит на диагностическом флаге, который сам
рантайм называет не сохраняющим корректность (`alloc_boehm.c:208-218`).

Ложное удержание (R7) существует, но мало́: 1 объект из 200 удержан
мусорным словом. И оно **не новое** — любой указатель на стеке имеет ту же
природу; value-сумма лишь добавляет к ней неинициализированные байты
неактивного варианта union'а.

### A1.4 Где значение-сумма окажется в НЕсканируемой области — поимённо

Обе красные области достижимы, но ни одна не достигается кодогеном
сегодня по умолчанию:

1. **Статик без корня.** `GC_set_no_dls(1)` — `alloc_boehm.c:175`.
   Компилятор уже закрывает это: `emit_c.rs:10176-10179` эмитит
   `nova_gc_add_root(&_nova_const_N_value, (char*)(&_nova_const_N_value) +
   sizeof(_nova_const_N_value))` для каждого ленивого статика, и диапазон
   берётся через `sizeof`, то есть покрывает структуру **целиком** — для
   value-суммы это верно ровно так же, как для указателя.
   **Требование к A4/A7:** не появиться статику суммы мимо `emit_lazy_const`
   (`emit_c.rs:10142`). Под RC/malloc-бэкендами `nova_gc_add_root` — no-op
   (`alloc.c:60`), там вопрос не стоит.
2. **`calloc`/`malloc`-память.** Единственный такой путь в рантайме —
   `BaseWaiter` в `channels.h:601-606`, и он под `#if` уходит в
   `nova_alloc` на Windows, то есть в GC-кучу. Пользовательские данные
   туда не попадают.
   **Требование:** ни одна value-сумма не должна лечь в память, полученную
   не через `nova_alloc`/`nova_alloc_uncollectable`.
3. **Erased/`void*`-позиции.** Красными не оказались (R5 зелёный), но
   правило A7 остаётся: боксить по образцу `emit_c.rs:43248`, а не класть
   адрес стекового temp.

**Расхождение доки и кода, найденное по дороге.** `channels.h:590-593` и
`fibers.h:68-72` утверждают: «Windows: calloc'нутые stacks НЕ GC roots».
Это устарело. `fiber_arena.h:54` включает арену для `_WIN32` (Plan 82 Ф.1),
`fiber_arena_win.c:278` регистрирует `GC_set_push_other_roots` — и
измерение `Rfn` **на Windows** это подтверждает: объект пережил
приостановку файбера и принудительную сборку. Комментарий описывает мир,
которого больше нет; `#if` при этом безвреден (GC-куча всегда безопасна),
просто больше не нужен. Класс — тот же, ради которого заведён страж
`check-doc-truth`.

### A1.5 Вердикт A1

**Value-сумма GC-безопасна во всех областях, куда её сегодня способен
занести кодоген** — стек, стек файбера, backing `Vec`, GC-куча,
uncollectable, статик с корнем. Оговорка одна и она процедурная:
статик суммы обязан идти через `emit_lazy_const`, а сумма не должна
попадать в память, добытую мимо `nova_alloc`.

Это **понижает** риск, записанный в первой редакции отчёта как главный.
Ф.2 может стартовать с A2 (детектор рекурсии), не дожидаясь никакой
GC-машинерии: точная битмапа `gc_layout.rs:816` для value-сумм **не
требуется** — консервативного скана достаточно.

**Байпродукты — два отказа кодогена, пойманные прогоном** (не Ф.2, каждому
нужен свой минимальный repro до номера в реестре):

* `v[q].p()` над `Vec[value-record]` → `[E_CODEGEN_TYPE_UNKNOWN] method
  call .p return type unknown; obj_ty="Nova_Vec____NovaValue_Held*"`.
  Обход — связать элемент в локал. Прямо по курсу A5.
* захват второго `Atomic*` во **втором** `spawn` одного `supervised` даёт
  невалидный C: `Nova_AtomicBool_method_store_bool(&((*_c->ran_b)), true)`
  при `ran_b` типа `nova_int` → «member reference type 'nova_int' is not a
  pointer».
