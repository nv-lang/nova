## №51 `[M-crossmodule-samename-typecheck-bleed]`-вариант (peers-версия №28) — НЕ ВОСПРОИЗВОДИТСЯ

**Вердикт: не воспроизводится на текущем бинаре. Закрыт БЕЗ фикса.**

### Проба (первый заход — ложная тревога)

Первая проба: два peer-файла ОДНОГО модуля, каждый объявляет `#impl(Serialize)
type User { ... }` с РАЗНЫМИ полями (мимикрируя `auth.nv`/демо-peer из
реестра). На pristine-бинаре — компилируется ЧИСТО, БЕЗ «duplicate
top-level name» — СОВПАДАЕТ с описанием бага. Прогнал полную RCA:
`f1_check_call`'s дубликат-детект (`compiler-codegen/src/types/mod.rs`,
`for item in &module.items { Item::Type(td) => ... }`) действительно
видит ОБЕ декларации `User` (подтверждено прямой инструментацией —
`module.items` User-count=2), но `classify_dup("User")` возвращает
`Some(false)` («merged_from_imports — codegen-only, silent») —
классификация приходит из `lints::collect_prelude_visibility`, чья Pass-1
(строка ~1562) кладёт имя КАЖДОГО итема из ЛЮБОГО non-entry peer-файла в
`merged_from_imports`, БЕЗ проверки `is_prelude_peer` (та проверка гейтит
только `visible`, не `merged_from_imports`) — то есть обычный
co-equal-peer файл ТОГО ЖЕ пользовательского модуля неотличим от
транзитивно-смёрженного prelude/std-контента на этом уровне.

Попробовал два фикса:
1. Гейтить `merged_from_imports.insert` тем же `is_prelude_peer` —
   СЛОМАЛО `nova check std/src` катастрофически (148/26 → 4/170: std
   сам полагается на широкое `merged_from_imports` для СВОИХ
   внутренних cross-file merge-паттернов, напр. `std/src/runtime/
   write_buffer.nv`'s `INITIAL_CAPACITY`).
2. Точечная проверка НАПРЯМУЮ в `check_module`'s duplicate-детекте:
   сравнивать `PeerFile.module_name` обеих сторон коллизии с
   `module.name` (авторитетный сигнал «тот же модуль», не полагаясь на
   `is_entry_module`/`merged_from_imports`) — канон std/src
   ВОССТАНОВЛЕН байт-в-байт (148/26/61), НО когда ретестировал пробу —
   она ТОЖЕ стала чисто компилироваться на pristine-бинаре! Инструментация
   вскрыла причину: `User` — ЗАНЯТОЕ имя, `std/src/encoding/serde/
   record_autoderive_test.nv:14` УЖЕ объявляет `type User value { ... }`
   (тестовая фикстура std для той же autoderive-фичи) — моя проба
   «сталкивалась» НЕ со своим demo-peer, а со СЛУЧАЙНО одноимённым
   std-тестовым типом из СОВСЕМ ДРУГОГО модуля (транзитивно достижимого
   через `import std.encoding.serde`) — ложное срабатывание диагностики
   ИЗ-ЗА выбора распространённого имени `User`, не баг компилятора.

### Решающая проба (переименовал в уникальное `P51Widget`)

Тот же файл-парный сетап (два peer-файла ОДНОГО модуля,
`#impl(Serialize)`, РАЗНЫЕ поля), но тип назван `P51Widget` (гарантированно
не пересекается ни с чем в std) — на PRISTINE (нефикшенном) бинаре:

```
[31mFAIL:[0m sub/a.nv
  ...\sub\b.nv:6:1: error: duplicate top-level name `P51Widget`
```

**Компилятор УЖЕ корректно ловит дубликат** — «duplicate top-level name»
диагностика на pristine-бинаре работает как задумано для genuine
same-module peer-file коллизии с уникальным именем. Проба №1 («User» без
коллизии не ловится) была ложной тревогой от случайного совпадения с
std-тестовым типом, не от бага резолва peer-файлов.

Обе точечные правки (`compiler-codegen/src/types/mod.rs`,
дубликат-детект-цикл) **отменены** (`git checkout --`) — они были
основаны на ложной предпосылке и не нужны: механизм и так работает
корректно на решающей пробе. Дерево вернулось в состояние ПОСЛЕ №45/№50
фикса (коммит `40b750e46`), без изменений от №51-разведки.

### Смежная находка (для интегратора, НЕ дефект — задокументированное
поведение, отмеченное здесь т.к. найдено в процессе)

`lints::collect_prelude_visibility`'s Pass 1 (`compiler-codegen/src/
lints.rs`, строка ~1562) кладёт имя КАЖДОГО item'а любого non-entry
peer-файла в `merged_from_imports`, не только реально prelude-файлов
(`is_prelude_peer`-гейт применяется ТОЛЬКО к `visible`). Эмпирически это
похоже на НАМЕРЕННОЕ поведение (std САМ полагается на широкий охват для
собственных внутренних cross-file merge-паттернов — правка узкого
гейта сломала 144 std-файла), но семантически сбивает с толку: имя
функции («prelude visibility») уже, чем фактическая роль (де-факто «весь
non-entry-peer merged namespace»). Не трогал — широкий охват, вне
объёма подтверждённого дефекта; если интегратор захочет разобраться —
начать с `std/src/runtime/write_buffer.nv`'s `INITIAL_CAPACITY` (что
именно она «мержится» с — не выяснял).

## №45 `[M-fn-type-expected-any-bypass]` + №50 (живое подтверждение №45)

**Воспроизведено — чисто, красно-зелёная пара получена.** Один фикс
закрывает ОБА номера: №50 в реестре прямо помечен как «ЖИВОЕ ПОДТВЕРЖДЕНИЕ
№45» (не отдельный дефект, а живой пример того же корня на флагмане).

### Проба на актуальность

Проба на pristine-бинаре главной репы (`d:/Sources/nv-lang/nova/nova-cli/
target/release/nova.exe`, собран 2026-08-05) — дефект воспроизводится
дословно: fn-типизированный аргумент СО СТРУКТУРНО НЕСОВПАДАЮЩЕЙ
сигнатурой (`fn(int) -> str`, передан туда, где ожидался `fn(int) -> int`)
проходит `nova check` БЕЗ единой ошибки/предупреждения (`PASS: 1 FAIL: 0`).

### Корень

`compiler-codegen/src/types/mod.rs`, `resolved_cat_of_depth` (строка
~22432): `TypeRef::Tuple(_, _) | TypeRef::Func { .. } => R::Any` —
ЛЮБОЙ fn-типизированный EXPECTED-тип схлопывается в категорию `Any`
(общий, намеренный коллапс — трогать его саму НЕ стал, он используется
повсеместно и намеренно permissive для erased/generic fn-типов).
`assignable_direct`'s ранний `if matches!(exp_rt, ResolvedType::Any) {
... return Compat::Ok; }` (строка ~17935) на этом основании пропускал
АБСОЛЮТНО ЛЮБОЕ значение на fn-типизированную позицию без единой
структурной проверки сигнатуры — единственная существующая узкая
пере-проверка внутри этой Any-ветки (`protocol_mismatch_found`) касалась
ТОЛЬКО протокольных типов, для `TypeRef::Func` явно возвращала `None`
(строка ~18327: `_ => return None, // Any/never/Self, func, tuple, ...`).

### Фикс (канал, `compiler-codegen/src/types/mod.rs`)

Новый метод `fn_type_mismatch_found` (вставлен сразу после
`protocol_mismatch_found`, зеркалит его же узко-гейтованный паттерн —
НЕ трогает общий `resolved_cat_of_depth`-коллапс, отдельная адресная
пере-проверка ТОЛЬКО для источника `Any` = `TypeRef::Func`): peel'ит
L2-обёртки (`ro`/`mut`/`uninit`/`ref`) с обеих сторон, требует, чтобы
И expected, И `infer_expr_type(expr)`-тип аргумента peel'ились в
КОНКРЕТНЫЙ (не generic/erased) `TypeRef::Func` — иначе `None`
(permissive, поведение не меняется). При совпадении арности параметров
сравнивает КАЖДЫЙ параметр + возврат через уже существующий
`cat_compatible_rt` (та же permissive категорийная проверка, что
`assignable` использует повсюду — `(Any,_)|(_,Any) => true`, так что
вложенные generic/fn/tuple-параметры остаются permissive на обеих
сторонах и НЕ дают ложных срабатываний). Несовпадение арности ИЛИ
категорийное несовпадение хотя бы одного параметра/возврата →
`Compat::Bad` → существующий E7301 (переиспользован, новый код ошибки
не заводил).

Вызов пришит в `assignable_direct` сразу после
`protocol_mismatch_found`, тем же паттерном (строка ~17958-17966).

### Фикстуры

`spec_tests/conformance/fn_type_signature_mismatch_pos.nv` (позитив —
совпадающая сигнатура через explicit closure-full + closure-light с
выводом типа из контекста — оба должны остаться зелёными, никакого
ложного срабатывания) + `spec_tests/conformance/neg/

**Вердикт: дефект №45/№50 воспроизведён (RED на pristine-бинаре),

## №49 `[M-module-name-shadows-local]`

**Воспроизведено — частично, на уровне внутреннего состояния чекера, НЕ на
уровне внешне наблюдаемого поведения.** Подробности ниже — это НЕ
«дефект закрыт», это «корень найден и починен, но красно-зелёного прогона
через видимое поведение программы получить не удалось» — см. дисклеймер в
конце раздела.

### Корень

`compiler-codegen/src/types/mod.rs`, `f1_stmt`, ветка `Stmt::ConsumeScope`
(было — строка ~8206). В отличие от `f1_block`, который для `Stmt::Let`
снимает snapshot/restore и потому корректно прячет ("shadow") имя модуля
локальной переменной, ветка `Stmt::ConsumeScope` НИКОГДА не вносила
`binding` (имя `consume`/`spawn consume`-биндинга) в `scope: &mut
HashMap<String, TypeRef>` на время обхода `body`. Из-за этого
`f1_check_call`'s `ExprKind::Member`-ветка (строка ~14340,
`scope.contains_key(prefix)`) не видит биндинг как локаль и трактует
`ws.foo(...)` внутри `spawn consume ws = ... { ws.foo(...) }` как вызов
СВОБОДНОЙ функции `foo` модуля `ws`, а не instance-метод на биндинге —
именно симптом, описанный в реестре (`ws.read_to_vec(...)` резолвился в
модуль вместо переменной в nova-http `net/policy.nv`, обход — переименование
локали в `shs`, комментарий там же сохранён).

### Проба на актуальность

Прямой E7401 из оригинального отчёта (`no function read_to_vec in module
ws`) **не воспроизводится дословно** — `read_to_vec` в текущем `std/src`
не существует вообще (`grep -rn read_to_vec std/src` — ноль совпадений),
API с тех пор переименовано/убрано. Это ожидаемо попадает под правило
дока §9 (реестр отстаёт от кода) — сам факт стал неактуальным, но
МЕХАНИЗМ (сам скоуп-геп) — нет, он воспроизведён прямой инструментацией
компилятора (см. ниже), это не гипотеза.

### Прямое доказательство (инструментация, не гипотеза)

Временно вставил `eprintln!` в обе точки чекера (`f1_check_call`'s
`ExprKind::Member`-ветка) и прогнал изолированный probe-пакет
(`scratch/p49_probe/`, вне git, временный) с бинарём БЕЗ фикса:

1. `scope.contains_key("ws")` внутри тела `consume ws = ... { ws.foo() }`
   — **`false`** во всех прогонах (3 независимых сборки, разные имена
   методов) — сам геп подтверждён напрямую, не по догадке.
2. С коллизией имён (модуль `p49_49_wsmod` экспортирует свободную функцию
   `p4549_marker()`, а локальный биндинг `ws` — ЛОКАЛЬНОГО типа
   `P4549Guard`, у которого ТОЖЕ есть метод `p4549_marker()`, объявленный
   в ДРУГОМ peer-файле) — `self.sig.fn_decls.get("p4549_marker")`
   находит `Some([<FnDecl из wsmod, span_file=2>])` — то есть чекер
   **резолвит `ws.p4549_marker()` в ЧУЖУЮ свободную функцию модуля**, а
   не в метод локали, и это записывается в `resolved_callees` (канал
   §0/Plan 196) — объективно НЕВЕРНАЯ запись.

### Почему это НЕ ловится внешне наблюдаемым тестом (RED-фикстуры нет)

Несмотря на п.2 выше — прогон программы всё равно даёт ПРАВИЛЬНЫЙ
результат (компилируется, `assert` проходит с верным значением) что ДО
фикса, что после. Причина — прямо в комментарии того же файла
(`compiler-codegen/src/types/mod.rs`, около строки 14403): запись в
`resolved_callees` для этой формы вызова помечена как «**ADDITIVE:
written, not yet read → byte-identical**» — т.е. codegen (`emit_c.rs`)
для `.method()`-вызовов ПОКА не читает этот канал (только для голого
`Ident`-вызова свободной функции), у него СВОЙ, отдельный и корректный
путь резолва через `var_types`/`method_table` (тот самый codegen-side
guard `is_local_var = self.var_types.contains_key(prefix)` в
`emit_c.rs:39148`, который УЖЕ делает это правильно — асимметрия
чекер-канал vs codegen, ровно тот класс, который §0/Plan 196 просит
чинить в канале).

Итог: чекер объективно пишет НЕВЕРНЫЙ резолв в `resolved_callees`, но
пока это мёртвая (не читаемая) запись для формы `obj.method()` — поэтому
дефект **латентный**: не ломает поведение СЕГОДНЯ, но взорвётся молча
(тихая порча, K1) в момент, когда codegen начнёт консультировать этот
канал для Member-вызовов (что и есть заявленное направление Plan 172.1 —
цитата из самого файла: «Codegen will READ this... and lower THAT
callee instead of re-resolving the overload»).

### Фикс (канал, `compiler-codegen/src/types/mod.rs`, `f1_stmt`/`Stmt::ConsumeScope`)

`binding` теперь вносится в `scope` (тип — `type_annot`, иначе
`infer_expr_type(init)`, иначе канал `resolved_types_buf`, иначе
плейсхолдер `Any`) ПЕРЕД обходом `body`, снимается по snapshot/restore
после — байт-в-байт тот же паттерн, что `f1_block` уже делает для
`Stmt::Let`. Фикс сделан в чекер-канале (§0), НЕ в `emit_c.rs` (легаси
уже был правильным — эталон для канала).

### Фикстуры

`spec_tests/conformance/p45_49_wsmod/mod.nv` (вспомогательный модуль,
экспортирует `ping()`/`p4549_marker()`) +
`spec_tests/conformance/p45_49_module_shadows_local_consume.nv` (позитив,
`consume`+`spawn consume` формы). Прогон через изолированный
scratch-probe (byte-identical содержимое, packagename `p49_probe`, вне
git) — **`PASS: 1 FAIL: 0`** (JSON-формат raннера) на ФИКСИРОВАННОМ
бинаре, обе test-секции внутри проходят (assert'ы верны). На реальном
пути `spec_tests/conformance/...` (мега-CU всей папки — папка = один
модуль в модели Nova) `nova test <файл>` не уложился в 590с (мега-CU по
докам ~60-90 мин, это ожидаемо — интегратор гонит его отдельно);
`nova check conformance/p45_49_module_shadows_local_consume.nv`

### Смежные находки (не в объёме этого номера, для интегратора)

- `is_known_fn` (`compiler-codegen/src/types/mod.rs:4535`) —
  «известность» имени функции проверяется ГЛОБАЛЬНО по ВСЕМУ
  reachable-графу (`sig_table`, `collect_all_signatures`), включая
  МЕТОДЫ (не только свободные функции — `collect_module_signatures_from_items`,
  `compiler-codegen/src/imports.rs:117`, трактует `Item::Fn` одинаково
  вне зависимости от `is_instance`), и включая СОБСТВЕННЫЙ модуль
  (`collect_all_signatures`: "Seed the table with the entry module's own
  items"). Из-за этого `[E7401]` практически никогда не стреляет для
  метода, который реально существует ГДЕ УГОДНО в достижимом графе —
  что на практике почти всегда так. Это отдельный (уже существующий,
  намеренный) предохранитель Plan 162.2 Ф.3 — не трогал, но он ЖЕ
  объясняет, почему оригинальный E7401-симптом сегодня не
  воспроизводится буквально.
- `resolved_callees`, записанный в `ExprKind::Member`-ветке
  `f1_check_call`, СЕГОДНЯ не читается codegen'ом для `.method()`-формы
  (только для голого `Ident`-вызова) — «ADDITIVE, not yet read» по
  собственному комментарию файла (строка ~14403). Когда это изменится
  (по заявленному Plan 172.1 направлению), №49-класс дефектов ОЖИВЁТ как
  видимая тихая порча для ЛЮБОГО имени, совпадающего со свободной
  функцией модуля-омонима локали — стоит держать в уме при миграции
  read-side канала.
