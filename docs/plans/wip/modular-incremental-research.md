# Разведка: модульная инкрементальная C-компиляция vs предсобранный архив рантайма (218)

**Статус:** исследование (материал для решения владельца, НЕ решение и НЕ реализация)
**Ветка:** `p-modular-incr-research` (worktree `nova-modincr`), база `dd683d7a2`; замеры на main `536682579`
**Модель:** opus (замеры + анализ; кода компилятора НЕ трогал — только временный 1-символьный
хак в `examples/flagship/aggregator/src/app/live.nv` для diff-пробы, откачен, working tree чист)
**Дата:** 2026-07-20

Закрывает пробел прошлой latency-разведки (`startup-latency-research.md`): та мерила **пустышку**
`fn main(){}`, где пользовательского кода ~0 → C-compile целиком = рантайм. Владелец спросил
правильно: на **реальном** многомодульном проекте, где между сборками правят 1-2 модуля, — не
окажется ли модульная инкрементальная C-компиляция (модуль→свой `.o`, кэш `.o` по хешу, пересборка
дельты + перелинковка) **большим** рычагом, чем план 218 (предсобранный `libnova_rt.a`)? Ответ —
измерен на флагмане `examples/flagship/aggregator`.

---

## 0. TL;DR (вердикт)

**Модульная инкрементальная C-компиляция — МЕНЬШЕ 218, причём радикально. На реальном коде рантайм
всё равно доминирует в C-compile.**

Замер флагмана (dev, `--strict-effects`), фаза `c-compile` = **5.74 с**, разложена изолированными
`-c` компиляциями:

| компонент C-compile | время | доля |
|---|---|---|
| **пользовательский app `.c`** (1.95 МБ, 33 023 строки) → `.o` | **~0.85 с** | **~15 %** |
| **рантайм** (12 core `.c` из `nova_rt`) → `.o`, последовательно | **~4.0 с** | **~70 %** |
| линковка | ~0.9 с (остаток) | ~15 % |

- **218** (предсобранный архив рантайма) снимает ~**4.0 с** каждую сборку → C-compile 5.74→~1.75 с.
- **Модульный `.o`-кэш** снимает лишь часть от **0.85 с** app-доли на дельте одного модуля. Верхняя
  оценка (идеальное разбиение на ~6 модулей, правится 1) — **~0.7 с**. Реально меньше.
- **Вывод по оси C-compile: 218 (~4.0 с) строго больше модульного `.o` (<0.7 с) в ~6 раз.** Даже на
  большом проекте пользовательская доля C-compile мала, потому что рантайм-TU дорогие не объёмом
  тела (438 КБ на 12 файлов), а **повторным парсингом тяжёлых системных заголовков** (`windows.h`
  через `uv.h`, Boehm `gc.h`, pthreads) в каждом из 12 TU — ровно то, что архив устраняет разом.

**Два жёстких препятствия делают модульный `.o`-кэш ещё хуже, чем «просто мало»:**

1. **Нет стабильной границы модуль→`.o`.** Inline-expansion (`resolve_imports_inline`) сливает entry
   + все импортируемые модули в **один** `Module` → **один** `.c` → **один** CU. Multi-TU (209) режет
   готовую строку `.c` по **размеру** (round-robin ~1.5 МБ/часть), **не по модулям**, и `.o` между
   сборками не переиспользует. Раздельной компиляции нет — её пришлось бы **построить** (крупная
   архитектура), прежде чем `.o`-кэш вообще возможен.
2. **Codegen НЕ детерминирован run-to-run.** Пересборка **неизменного** исходника даёт **другой**
   `.c` (≈44 изменённых строки-маркера: переставлены fwd-typedef'ы, строковые литералы, конъюнкты
   в sum-equality). Источник — итерация `HashMap`/`HashSet` в эмиссии (подтверждено кодом:
   `emit_c.rs:51638` явно называет «benign HashMap-order classes: fwd-typedef order + sum-eq conjunct
   order»). Content-addressed `.o`-кэш по фрагментам генерённого C **промахивался бы КАЖДУЮ сборку**
   (0 переиспользования). Предпосылка к любому `.o`-кэшу — сперва **сделать вывод codegen
   порядко-детерминированным** (сортировать typedef'ы/mono/литералы/арм-ы sum-eq по стабильному
   ключу). Это отдельный кусок работы.

**Важный reframe (то, что вскрыл флагман).** C-compile — лишь ~35 % холодной сборки (5.7 из 16.6 с).
**Фронтенд** (`type-check` 3.33 с + `post-normalize-annotate` 2.97 с + `codegen` 0.39 с ≈ 6.7 с) —
~40 %, и он **полностью перезапускается на любую правку** (content-cache помогает только при
НУЛЕВОЙ правке). Настоящий инкрементальный приз на реальном проекте — **инкрементальный ФРОНТЕНД**
(per-module type-check/normalize), а не `.o`-кэш. Но это separate-compilation-масштаб, крупнее и
218, и `.o`-кэша.

**Рекомендация:** плана «модульная инкрементальная C-компиляция (.o-кэш)» **не заводить приоритетно**
— эффект <0.7 с, обнулён недетерминизмом codegen. 218 остаётся P1. Если владелец хочет 221 — его
следует определить как то, что реально показывает флагман (инкрементальный фронтенд, крупный,
долгий), а НЕ как быстрый `.o`-кэш. Мелкий полезный атом-предпосылка (и сам по себе ценный —
reproducible builds): **детерминизировать порядок вывода codegen**.

## 1. Замеры (флагман `examples/flagship/aggregator`, dev, `--strict-effects`)

Стенд: Windows 11, clang 22.1.5 (`C:\Program Files\LLVM`), релиз-бинарь main-репы
`nova-cli/target/release/nova.exe` (16.77 МБ, 2026-07-20), Boehm GC, libuv предсобран
(`target/libuv-cache/libuv.lib`), vcpkg-Boehm предсобран. Флагман: 7 non-test `.nv` в build-set
(1627 строк исходника), 4 модуля-каталога (`app/`, `api/`, `domain/`, корень `main.nv`).

### 1.3. Разложение c-compile 5.74 с (изолированные `clang -c`, медиана x3)

Дефолтный single-TU путь (`build_command`) отдаёт clang'у ОДНОЙ командой: app `.c` + 12 рантайм-`.c`
(`net fs alloc_boehm effects fibers fiber_arena fiber_arena_win fiber_stats runtime driver typeid
segv_diag`) → clang компилирует их **последовательно** в одном процессе, затем линкует. Разложение:

**App `.c` (1 946 611 байт, 33 023 строки) → `.o`:** 0.866 / 0.856 / 0.843 с → **~0.85 с**.

**Рантайм core `.c` (12 TU), каждый `-c`:**

| файл | с | | файл | с |
|---|---|---|---|---|
| fiber_arena_win.c | 0.649 | | effects.c | 0.368 |
| net.c | 0.547 | | driver.c | 0.358 |
| fs.c | 0.536 | | segv_diag.c | 0.260 |
| runtime.c | 0.426 | | fiber_arena.c | 0.216 |
| alloc_boehm.c | 0.422 | | fibers.c | 0.107 |
| | | | typeid.c | 0.076 |
| | | | fiber_stats.c | 0.058 |

**Рантайм последовательный итог: ~4.02 с.** app 0.85 + рантайм 4.02 + линк ~0.9 ≈ **5.77 с** —
совпадает с наблюдённым c-compile 5.74 с (проверка сходится).

**Ключевой парадокс и его причина:** app `.c` = 1.95 МБ компилится за 0.85 с, а рантайм = 438 КБ (12
файлов) за 4.0 с. Потому что рантайм-TU дороги **не телом**, а `#include` тяжёлых заголовков
(`uv.h`→`windows.h`, `gc.h`, pthreads) — каждый из 12 TU заново парсит их. App `.c` инклудит только
`nova_rt/nova_rt.h` (лёгкий, один раз). Значит рантайм-стоимость — **фиксированная per-TU цена
заголовков**, идеальная мишень для предсобранного архива (218).

### 1.4. Размер генерённого app `.c` и TU-разбивка

- **1 946 611 байт (~1.95 МБ), 33 023 строки, ~4157 top-level определений** (≈3634 `") {"`-прокси
  fn-сигнатур — далеко за порогом `MULTI_TU_FN_COUNT_THRESHOLD` = 200).
- Дефолт: **single-TU** (`NOVA_MULTI_TU` off). Флагман переходит multi-TU гейт **не по размеру**
  (1.95 МБ < 2 МБ `MULTI_TU_SIZE_THRESHOLD_BYTES`), а по **>200 fn**.
- С `NOVA_MULTI_TU=1`: **2 части** (порог 1.5 МБ, текущий main) или 4 части (историч. 500 КБ) —
  из `209-f4-measures.md`. Multi-TU режет **по размеру round-robin**, НЕ по модулям.

### 1.5. Правка 1 модуля: насколько локальна регенерация `.c`

Проба: 1-символьная правка одного строкового литерала в одной функции `live.nv`
(`"resolve: no address for "` → `"...NO address..."`), пересборка `NOVA_CACHE=0`, diff генерённого `.c`.

- Изменилось **~54 строки-маркера в 23 hunk'ах**, разбросанных по всему 33k-строчному файлу:
  - сам литерал (ожидаемо);
  - **переставлены fwd-typedef'ы** (`Nova_D/T/I/V/E/K/F/R` в другом порядке);
  - **переставлены строковые литералы** (новый литерал получил другой хеш-суффикс, сдвинув соседей);
  - **переставлены конъюнкты `&&`** в ~10+ НЕсвязанных sum-equality функциях (`ErrSource`, `TlsError`,
    `ParseJsonError`, `JsonValue`, `Base64Error`, `Token`, …) — семантика идентична, порядок арм-ов иной.
- **Правка НЕ локальна** — рябь по всему CU.

### 1.6. Детерминизм codegen (решающая проба)

Пересборка **того же неизменного** исходника (после restore) → `.c` **отличается**: тот же размер
(1 946 611 байт), но **~44 изменённых маркера** (та же природа: переставлены typedef'ы / литералы /
sum-eq конъюнкты). **Codegen run-to-run НЕ детерминирован** — итерация `HashMap`/`HashSet`.
Подтверждено кодом: `compiler-codegen/src/codegen/emit_c.rs:51638` — команда сама называет это
«two known **benign HashMap-order classes: fwd-typedef order + sum-eq conjunct order**» и нормализует
их при byte-identity DCE-верификации.

**Следствие для `.o`-кэша:** любой ключ по фрагментам генерённого C нестабилен между запусками →
промах каждую сборку. Content-cache (`build_cache.rs`) выживает только потому, что ключ — хеш
**исходных `.nv`** (не генерённого C), и на hit он отдаёт **те же байты `.c` с диска** (не перегенерит).

## 2. Сложность: mono cross-module граница + инвалидация

### 2.1. Границы (почему нет модуль→`.o`)

- **Inline-expansion в один CU.** `build_cache.rs` (док-коммент, Plan 81 Ф.9) авторитетно:
  «Nova использует inline-expansion (`resolve_imports_inline` сливает entry + все импортированные
  модули в один `Module` → один `.c`); раздельной компиляции модулей в архитектуре нет».
  Границы «модуль → `.o`» **не существует**. Сегодня это буквально 1 `.c` на всю сборку.
- **Mono эмитится на use-site.** Инстанциация дженерика (`Vec[Foo]`, `HashMap[str,JsonValue]`)
  эмитируется туда, где **использована**, а не где определён `Vec`. Правка модуля A может изменить C,
  эмитируемый «в» B. Коллектор mono (`mono_worklist`/`mono_instantiated`, `emit_c.rs:1594,1588`) —
  worklist над **всем** слитым CU; чёткого «этот mono принадлежит этому модулю» нет.
- **Multi-TU (209) — не основа для инкрементальности.** `split_tu.rs` — чистый текстовый пост-проход
  над готовой `.c`-строкой, classify+round-robin по байтам (§ док split_tu). Часть НЕ соответствует
  модулю; правка одного модуля сдвигает размеры → все части перетасовываются; `.o` между сборками не
  живут (`obj_dir` = свежий temp). Плюс split **обходит content-cache**.
- **Сравнение с rustc (эталон, feedback-rustc-as-reference).** rustc: MIR + codegen-units +
  per-CGU fingerprinting + query-based incremental — стабильные границы и детерминированный вывод
  дизайнятся с нуля. Наш AST-only без MIR, mono = коллектор-фаза над слитым CU — **у нас нет ни
  промежуточного IR с owner-модулем на инстанс, ни детерминированного порядка**. Построить
  модуль→`.o` = построить separate compilation + reproducible codegen — крупная многофазная работа.

### 2.2. Инвалидация (ширина протухания)

Даже если бы separate compilation существовала, ключ `.o`-кэша = хеш(исходник модуля +
**транзитивные mono-зависимости** + флаги + отпечаток компилятора). Ширина:

- **Лист-модуль** (напр. `live.nv`, не экспортирует типы вширь): узкая инвалидация — свой `.o` + TU,
  куда попали его mono-инстансы.
- **Базовый тип / prelude / широко-используемый дженерик** (`Vec`, `HashMap`, `Result`, доменный
  enum `AggError`): инвалидируется **транзитивное замыкание** — практически весь CU (все use-site'ы
  mono). Правка `domain.nv` (общий enum, участвует в sum-eq всюду — см. рябь §1.5) → почти всё.
- Итог: распределение выигрыша бимодально — тонкая правка листа дёшева, любое касание общего типа
  ≈ полная пересборка. На реальном цикле «правлю доменную модель + пару листьев» средний выигрыш
  ближе к нижней границе.

## 3. Вердикт vs 218 (с числами)

| ось / рычаг | что снимает | эффект/сборку | риск | сложность |
|---|---|---|---|---|
| **218 — архив рантайма** | рантайм-доля c-compile | **~4.0 с** (5.74→~1.75) | низкий | средняя |
| **модульный `.o`-кэш** (гипотет.) | часть app-доли c-compile на дельте | **<0.7 с** (из 0.85) | высокий | **очень высокая** (нужны separate compilation + детерминизм codegen) |
| whole-app `.o`-кэш (тривиальный, в build_cache) | app-доля на HIT | ~0.85 с, но только при НУЛЕВОЙ правке (бесполезно) | низкий | низкая |
| инкрементальный фронтенд (реальный приз) | type-check+normalize на дельте | до ~6 с | средний | очень высокая |

**Доминирует ли рантайм на большом коде?** ДА. Даже на флагмане (1.95 МБ app `.c`, реальный
многомодульный проект) пользовательская C-компиляция = ~0.85 с (~15 % c-compile, ~5 % полной
сборки), рантайм = ~4.0 с. Модульный `.o` пилит меньшую часть меньшей части. **218 строго больше в
~6 раз по оси c-compile и намного дешевле/безопаснее.**

## 4. Рекомендация по плану 221 + приоритет

**Не заводить «модульную инкрементальную C-компиляцию (.o-кэш)» как приоритетный план.** Причины:
эффект <0.7 с (при 218, снимающем 4.0 с); недетерминизм codegen обнуляет content-addressed `.o`
до нуля переиспользования; реализация требует separate compilation (нет ни границ, ни IR) —
несоразмерно выигрышу.

**Приоритет ОТНОСИТЕЛЬНО 218/219/220:**
- **218 (P1)** — без изменений, самый большой и дешёвый рычаг c-compile (~4.0 с).
- Модульный `.o`-кэш — **НИЖЕ 219 и 220**, не уровня 218. Для сценария «правлю 1-2 модуля» **219
  (build-демон)** сильнее и дешевле: демон, держащий фронтенд-состояние в памяти, амортизирует
  дорогой фронтенд (~6.7 с на miss) на тёплых правках без всякой separate compilation — это прямое
  попадание в сценарий владельца, тогда как `.o`-кэш пилит лишь ~0.7 с.

**Если владелец всё же хочет 221 — переопределить его как то, что вскрыл флагман:**
1. **Мелкий атом-предпосылка (рекомендую в любом случае):** *детерминизировать порядок вывода
   codegen* — сортировать fwd-typedef'ы, mono-инстансы, интернированные литералы, конъюнкты sum-eq
   по стабильному ключу. Мал, самодостаточно полезен (**reproducible builds**, чище DCE-верификация,
   стабильнее diff'ы), и **обязателен** перед любым фрагментным `.o`/`.c`-кэшем.
2. **Крупный, долгосрочный (если вообще):** *инкрементальный фронтенд* (per-module
   type-check/normalize) — это и есть separate compilation масштаба rustc-incremental. Настоящий
   приз (~6 с/дельта), но горизонт большой; на нём же естественно вырастает и per-module `.o`.

**Связь с существующей инфрой:**
- **multi-TU (209):** режет по размеру, не по модулям, обходит content-cache, `.o` не живут между
  сборками → достраивать инкрементальностью **нельзя без редизайна** (сначала separate compilation).
- **build_cache (81 Ф.9):** ключ по исходникам, кэширует весь `.c`. Расширить на `.o` тривиально
  ТОЛЬКО для whole-app `.o` (тот же ключ) — но это экономит 0.85 с лишь на HIT (= нулевая правка =
  бесполезно). Per-module `.o` требует separate compilation.
