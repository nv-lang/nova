# p248-recon — во что обойдётся линейность разделяемых ручек (план 248, Ф.1)

**Окно:** p248-recon, модель Sonnet. **Разведка с числами, не починка.** Компилятор,
std, спека и пакетные репы НЕ менялись — все измерения читающие; единственное
исключение — раздел E, точечная проба на throwaway-типе в `examples/_probe_p248e/`,
**откачена** (директория удалена, в ветке остался только этот отчёт).

Корпус: `std` + `examples` (в `nova-p248r`, ветка на коммите
`de062775d`, ancestor `main`), `nova-http`, `nova-tls`, `nova-compress`,
`nova-bignum`, `nova-polaris` (все — соседние директории на диске, читались
как есть, без правок).

Инструмент измерения A/B — Python-скрипт (regex-парсер `type`-деклараций +
неподвижная точка по замыканию полей), сверен вручную по каждой находке
чтением исходников. Ложные срабатывания вычищены (см. ниже).

## Главный вывод коротко

Транзитивное заражение — **6 типов, все в nova-polaris**, максимальная глубина
цепочки — **1** (не 2, не 10). Из них **1 устраним** переносом состояния в
замыкание (в точности пример владельца — `AccessLog`), **5 неустранимы** —
это готовые Mutex/Atomic-обёртки без примеси конфига, ровно то, для чего
разделяемые примитивы существуют. Итоговое число после устранимого переноса —
**5 новых линейных типов** сверх 23 примитивов, все в одном пакете.

Но нашлась находка крупнее самого числа: **проба на форме записи (раздел E)
показала, что предложенная владельцем форма (`consume value` + `#share()`,
как у `TcpStream`) требует у КАЖДОГО из 23 типов завести искусственный
consume-метод** — компилятор жёстко отказывает без него
(`D133-empty-consume`), а атомикам и мьютексам буквально нечего "закрывать"
(GC-ячейка, не ОС-ресурс). Это не эргономическая шероховатость, а структурное
расхождение между существующим языковым механизмом (`consume` = D133,
рассчитан на реальные ресурсы) и тем, что владелец хочет получить
(copy-запрет без обязательства освобождения). Подробности — раздел E.

## Раздел A — заражение (транзитивное замыкание)

### Метод

Извлечены все `type`-декларации (593 штуки) по 7 корням; для каждой — список
полей (для record-формы `{ ... }` и tuple-формы `(...)`), включая обёрнутые в
дженерики (`Vec[X]`, `Option[X]`, кортежи, `fn(...)`) — поиск по имени типа
внутри строки поля. Неподвижная точка от 23 seed-имён (все `#share`-носители).

### Что нашлось (сырое, до чистки)

| Итерация | Найдено новых имён |
|---|---|
| 1 | AccessLog, BucketTable, MetricsRegistry, OrderLog, RejectLog, SharedLog, TcpStream |
| 2 | ServerResponse, TlsStream, WebSocket (все — через `TcpStream`) |

10 имён сверх 23 seed. Но **3 из них — не относятся к цене плана 248** и
**1 — ложное срабатывание парсера**:

- **`TcpStream`** (`std/src/net/tcp.nv:39`) уже сегодня `consume value` с
  полем `rc AtomicInt` — это САМ прецедент, на который план 248 ссылается, а
  не новая цена плана. Он был линейным ДО этого окна.
- **`TlsStream`** (`nova-tls/src/stream.nv:53`) и **`WebSocket`**
  (`nova-polaris/src/ws/socket.nv:42`) — оба уже `consume`/`consume value`
  сегодня, с полем `priv consume tcp TcpStream` / `priv consume stream
  TcpStream` — то есть их линейность УЖЕ вызвана существующей линейностью
  `TcpStream`, а не 23 примитивами плана 248. Ноль новой цены.
- **`ServerResponse`** (`nova-polaris/src/server.nv:88`) — **ложное
  срабатывание**: поле `upgrade Option[fn(TcpStream) Net -> ()]` — это
  СИГНАТУРА функции, принимающей `TcpStream` параметром, а не хранимое
  значение. Само поле — обычный неконсьюмируемый `Option[fn...]`, тип не
  заражён. Проверено: единственное совпадение `fn(...)` + имя типа во всём
  скане (проверил регексом по всем 593 декларациям — других таких
  случаев нет).

### Реальное заражение (после чистки) — 6 типов, все nova-polaris

**По репам:** `nova-polaris` — 6 (5 в `src/`+`examples/`, 1 в тестовом файле);
`std`, `nova-http`, `nova-tls`, `nova-compress`, `nova-bignum`, `examples`

`std.runtime.sync`/`std.prelude.concurrency` (grep по `runtime.sync\|prelude.

используются НИ РАЗУ.

**Побочная находка:** вне `std` пометку `#share` несёт ещё один тип —
`OrderLog` (`background_test.nv:47`) — но это record с полем `Mutex`, НЕ
newtype-над-указателем. То есть утверждение "все 23 носителя — newtype" верно
для `std`, но за его пределами уже есть прецедент `#share` на составном
record. Не противоречит плану (OrderLog и так неустраним), но стоит
зафиксировать: дисциплина `#share` уже просачивалась за пределы raw-newtype
формы ДО этого окна.

### Классификация по заданию координатора (устранимо / нет)

**`AccessLog` — устранимо (категория 2).** Поля: `request_id bool`,
`real_ip bool` (конфиг) + `counter AtomicInt` (рабочее состояние генерации
id). `@middleware()` (`log.nv:85-88`) уже строит ОДНО замыкание на конфиг
(`ro cfg = @; middleware(fn(req, next) => log_apply(cfg, next, req))`) — то
есть паттерн "состояние в замыкании" уже в этом самом месте, просто состояние
сегодня зашито ВНУТРЬ конфига, а не рядом с ним. Аналог рядом есть буквально
в соседнем файле: `ratelimit.nv:63` — `mut table = BucketTable.new()`,
захватывается замыканием `middleware(fn(req, next) => rl_apply(...,
table, ...))`, ОДИН closure, ОДИН владелец.

Перенос: вынести `counter` из `AccessLog` в отдельную `mut`-переменную,
захватываемую ТЕМ ЖЕ замыканием `@middleware()` рядом с `cfg` (теперь без
counter — чистый конфиг из двух bool). `log_apply`/`request_id_of`/
`fresh_id` получают `counter` отдельным `mut`-параметром (threaded, как
`BucketTable` в `rl_apply`), а не полем `ro`-конфига.

Бонус, не только линейность: это заодно убирает обходной путь №334
(`mut counter = cfg.counter` — локальная копия, чтобы обойти
`E_PARAM_NOT_MUT` на цепочке из трёх readonly-параметров) — после переноса
`counter` идёт СВОИМ `mut`-параметром через всю цепочку, и
`counter.fetch_add(1)` вызывается прямо, без копии-обхода. Замыкание строится
РОВНО ОДИН раз на `AccessLog.new().middleware()` — значит после переноса
`counter` вообще не нуждается в `.share()`: один closure, один владелец,
ноль остаточной цены линейности.

**`BucketTable`, `MetricsRegistry`, `OrderLog`, `RejectLog`, `SharedLog` —
неустранимо (категория 1).** У всех пяти — **никаких конфиг-полей вообще**:
только `Mutex`/`Atomic*` + структура данных, которую он охраняет (`HashMap`,
`Vec[int]`, `[]str`, счётчики). Это не "конфиг с примесью состояния" —
это ЧИСТОЕ состояние, canonical use-case Mutex/Atomic. Комментарии авторов
(`metrics.nv:64`, `ratelimit.nv:72`) прямо называют это "value record over
reference-semantics fields — every copy aliases the SAME table" — то есть
design-намерение, не случайность. Переносить их некуда: сам тип и есть то
состояние, которое переносили бы.

**Оговорка честности:** классификация построена чтением полей и
doc-комментариев всех 6 деклараций плюс мест их использования (не только
сигнатур) — уверенность высокая, но НЕ исключаю, что где-то в коде есть
использование, которое я не нашёл grep'ом по имени типа (например, доступ
через алиас/реэкспорт под другим именем — не встретилось, но не proof).

**Итоговое число, которое просил владелец:** после устранимого переноса —
**5 новых линейных типов** (не 6), все в nova-polaris, максимальная глубина
цепочки 1. Оговорка из задания повторяю явно: перенос НЕ делает Mutex/Atomic
внутри этих 5 менее опасными — они как были общим ресурсом на много файберов,
так и остаются; перенос убирает только ОДИН тип (AccessLog) из списка
заражённых, а не потребность в защите его counter'а (защита остаётся —
просто без share(), см. выше, ровно ОДИН владелец).

## Раздел C — прецедент TcpStream, цена на живом

`TcpStream.@share()` (`std/src/net/tcp.nv:296-299`):

```nova
export fn TcpStream @share() -> TcpStream {
    @rc.fetch_add(1)
    share_copy(@handle, @rc)
}
```

**7 реальных вызовов** `.share()` в корпусе (не считая doc-комментариев,
которые ОПИСЫВАЮТ паттерн ещё в ~6 местах, но не вызывают): 5 в
`std/src/net/tcp_share_test.nv`, 2 в `nova-polaris` (`net/serve.nv:199`,
`net/policy.nv:63`).

Три дословных фрагмента:

```nova
// std/src/net/tcp_share_test.nv:20 — простейший случай
mut s = must(TcpStream.connect(SocketAddr.loopback(0)))
assert(s.rc.load() == 1)
mut s2 = s.share()
assert(s.rc.load() == 2)
```

```nova
// std/src/net/tcp_share_test.nv:84-88 — конкурентные share-копии per-fiber
spawn consume w1 = c.share() {
    ...
}
spawn consume w2 = c.share() {
    ...
}
```

```nova
// nova-polaris/src/net/serve.nv:199 — боевой код, accept-loop на каждое соединение
spawn consume shs = s.share() {
    mut resp = handler(raw)
    ...
}
```

**Читаемость:** естественная, не многословная. `s.share()` — один
дополнительный вызов метода на месте, где раньше было бы неявное копирование;
`spawn consume shs = s.share() { … }` читается как обычный
consume-биндинг с одним лишним словом `.share()` — не то ощущение "ритуала",
которое дают многословные API. Цена на месте использования — **одно слово**,
а не переписывание сигнатур (то, что тяжело — не "share() многословен", а
то, что каждая ФУНКЦИЯ по пути должна либо принимать тип `consume`/по
ссылке, либо получать уже share-копию — это архитектурное решение на уровне
сигнатур, не текстовая тяжесть самого вызова).

## Раздел D — каналы вне системы

Проверено И чтением компилятора, И живым фактом в дереве.

**Компилятор:** `Channel[T]` объявлен `external type Channel[T]`
(`compiler-codegen/src/parser/mod.rs:12447`, `types/mod.rs:5780-5792`) —
ЧИСТО namespace для `Channel.new(cap)`/`Channel.with_capacity(cap)`; рантайм
никогда не материализует значение типа `Channel[T]` — конструктор возвращает
пару `(ChanWriter[T], ChanReader[T])` (`nova_rt/channels.h`'s
`Nova_ChannelPair`). Ни `ChanWriter`, ни `ChanReader` не зарегистрированы как
обычные `TypeDecl` — `share_check.rs`'s `ShareQuery::lookup_type` (единственный
канал, которым `#share`-предикат вообще способен что-то узнать о типе) про
них **не знает ничего**: они не проходят через ту же машинерию, что
проверяет `#share`-типы.

**Живой факт** (`std/src/concurrency/cancellation.nv:70-93`, уже в дереве,
проходит гейт сегодня):

```nova
ro (tx, rx) = Channel.new(2)

supervised(cancel: tok) {
    spawn {
        ...
        tx.try_send(r)   // мутирующий метод через ro-биндинг
        ...
    }
    spawn {
        ...
        tx.try_send(r)   // ТА ЖЕ tx, ВТОРОЙ независимый файбер
        ...
    }
}
```

`tx` захвачен `ro`-биндингом в **два независимых** `spawn`, каждый вызывает
мутирующий `try_send` — ни `#share`, ни `.share()`, ни какой-либо линейный
маркер не участвуют. Это компилируется и работает СЕГОДНЯ.

**Пробел, названный явно:** каналы уже обладают ИМЕННО тем свойством, ради
которого затевается план 248 для 23 примитивов — безопасное совместное
использование из многих файберов без явного разделения — но получают его
даром, будучи вне досягаемости системы типов: не `TypeDecl`, не
`lookup_type`-ируемы, не проверяемы `share_check`. Защита сегодня —
исключительно допущение о потокобезопасности C-рантайма
(`nova_rt/channels.h`), НЕ доказанная тем же механизмом, которым проверяются
`#share`-типы. Если план 248 введёт полноценную линейность для
пользовательских типов, разрыв станет виднее: пользовательский `#share`-тип
потребует явного `.share()` на каждой границе файбера, а встроенный канал —
как был, так и останется бесплатным по построению. Это отдельный пробел
(и он уже зафиксирован в плане 238 как открытый), не предмет починки этого
окна.

## Раздел E — проба смены представления (сделана, ОТКАЧЕНА)

**Метод.** Throwaway-тип `ProbeHandle` в `examples/_probe_p248e/` (2 файла,
по одному на форму — избежал ловушки раннера, каждый checked отдельно):

- `probe_a.nv` — baseline, форма всех 23: `type ProbeHandle(*())`.
- `probe_b.nv` — предложенная форма: `type ProbeHandle consume value priv {
  handle *() }`.

Оба — `nova check`/`nova build` (release), запущено на реальном `nova.exe`
(main-репо, `nova-cli/target/release/nova.exe` — сам компилятор не менялся,
использовать бинарник из main корректно). Директория удалена по завершении
пробы; ниже — сухой остаток находок.

**Находка 1 — `probe_b.nv` С ПЕРВОЙ ПОПЫТКИ НЕ КОМПИЛИРУЕТСЯ.**

```
[D133-empty-consume] type `ProbeHandle` помечен `consume` но не имеет ни
consume-полей, ни consume-методов — добавь хотя бы один consume-method
(`fn ProbeHandle consume @method() -> ()`) либо убери `consume` с type-decl.
```

Компилятор ОТКАЗЫВАЕТ объявлять `consume`-тип без реального
consume-метода. Ни у одного из 23 примитивов такого метода сегодня нет — им
физически нечего закрывать (GC-ячейка в памяти, не файловый дескриптор/сокет).
Значит форма `TcpStream` "как есть" **не накладывается** на атомики/мьютексы
без изобретения искусственного no-op метода на каждый из 23 типов
(`fn AtomicInt consume @discard() -> () {}`-подобное, у 22 типов).

**Находка 2 — привязка требует ключевого слова `consume` ВЕЗДЕ.**

```
[E_CONSUME_KEYWORD_MISSING] binding `h` держит consume-обязательную
инстанс типа `ProbeHandle` — требуется keyword `consume` (D180).
```

Даже читающий локальный биндинг (`ro h = ProbeHandle.new()`) отказывает без
`consume h = …`. Измерено по корпусу (constructor-call sites `= Type.new(`)
для всех 23 seed-типов: **67 мест** конструирования вне
`sync.nv`/`concurrency.nv` (17 `AtomicInt`, 23 `AtomicBool`, 6 `Mutex`, 5
`CancelToken`, 4 `Semaphore`, остальные единично) — каждое потребует
добавления `consume`.

**Находка 3 (смягчение) — `Cleanup[never]` снимает РУЧНОЙ вызов
разрядки, но НЕ снимает `consume`-ключевое слово на биндинге.** Проверено
чтением (не отдельной пробой — вывод из уже принятого в дереве паттерна):
`TcpListener` реализует `Cleanup[never]` (`std/src/net/tcp.nv:137-143`, cleanup
= `@close()`), и тем не менее биндинги `TcpListener` в живом коде по-прежнему
пишутся как `consume listener = TcpListener.bind(...)` — то есть Cleanup
избавляет от ЯВНОГО вызова `.close()`/`.discard()` на каждом выходе из
scope (паника/throw/обычный return — все ветки закрываются автоматически),
но НЕ избавляет от `consume`-пометки на самой привязке. Значит реальная цена
после смягчения — только: (а) добавить `consume` к типу + no-op
`@cleanup`-метод (23 раза, дёшево, механическая работа), (б) добавить
`consume` к 67+ местам конструирования (механически, но задевает КАЖДЫЙ файл,
который вообще создаёт атомик/мьютекс — включая тестовый код по всему std).

**Находка 4 — представление меняется на уровне C, но есть прецедент.**
Сгенерированный C:

```c
// probe_a (newtype) — bare pointer typedef
typedef void* Nova_ProbeHandle;
static void* Nova_ProbeHandle_static_new(void);
static nova_bool Nova_ProbeHandle_method_is_null(Nova_ProbeHandle* nova_self);

// probe_b (consume value record) — настоящий struct
struct NovaValue_ProbeHandle { void* handle; };
static NovaValue_ProbeHandle Nova_ProbeHandle_static_new(void);
static nova_bool Nova_ProbeHandle_method_is_null(NovaValue_ProbeHandle* nova_self);
static nova_unit Nova_ProbeHandle_consume_discard(NovaValue_ProbeHandle* nova_self);
```

Размер не меняется (структура из одного `void*`-поля — те же 8 байт), но
ABI receiver'а меняется: методы принимают `&struct` вместо голого указателя.
Для ВСЕХ 22 `extern "nova"`-методов `sync.nv` (`fetch_add`/`load`/`store`/…,
реализованных прямо в C-рантайме) это означает пересогласование сигнатуры
С-стороны. **Это НЕ путь в неизвестность** — прецедент уже есть в ЭТОМ ЖЕ
файле: `MutexGuard`/`ReadGuard`/`WriteGuard`/`Permit`/`OnceGuard`
(`sync.nv:1406-1463`) уже объявлены как `consume { ptr int }` (record, не
newtype) и уже дергают `extern "nova"`-методы сегодня — то есть компилятор
УМЕЕТ маршалить record-обёрнутый скаляр в extern-nova вызов, просто не с
`*()`-полем, а с `int`. Риск обозначаю как реальный, но не блокирующий:
нужно распространить уже работающий паттерн Guard-семейства на 22 типа,
а не изобретать заново.

**Вердикт пробы дословно:** форма `type X consume value priv { handle *()
}` **компилируется и работает** (probe_b собрался и запустился, exit 0) —
но НЕ "как есть", а только после добавления искусственного consume-метода;
скомпилированное дерево генерирует иной C ABI (struct вместо голого
указателя) с прецедентом в том же файле (Guard-семейство), и требует
`consume`-пометки на каждой из 67+ измеренных точек конструирования по
корпусу.

## Что я бы измерил ещё

1. **Реальная семантика `mut`-параметров для record-типов** (borrow vs
   copy) — раздел B про `BucketTable`/`rl_apply` опирается на комментарий
   в коде ("genuinely in-out"), не на отдельную пробу компилятора. Дешёвая
   проверка: собрать минимальный repro с `mut`-параметром record-типа,
   посмотреть сгенерированный C (по образцу раздела E) — принимает ли
   функция указатель на вызывающую переменную или копию.
2. **Действительно ли `consume`-keyword снимается при наличии
   `Cleanup`** — находка 3 раздела E построена на чтении существующего кода
   (`TcpListener`), не на прямой пробе с ProbeHandle+Cleanup. Отдельная
   10-минутная проба закрыла бы это до конца.
3. **Совместимость `consume`-биндинга с текущими match-паттернами** —
   E_LINEAR_CAPTURE_IN_FIBER код (`types/mod.rs:28941-28958`) отдельно
   упоминает `Ok(consume {n})`-паттерны как отдельную ветку диагностики;
   не проверено, требует ли КАЖДЫЙ `match`/`if let`, распаковывающий одно
   из 23 полей, добавления `consume` в паттерн — это ещё один класс мест
   копирования, не учтённый в 67 из раздела E (тот счёт — только
   `= Type.new(...)`-присваивания).
4. **MetricsRegistry в реальном многофайберном use-case** — корпус
   показывает только 1 замыкание; стоило бы проверить boевые примеры/тесты
   nova-http или будущих пакетов, которые могли бы использовать общий
   registry из многих обработчиков одновременно — раздел B честно помечает
   это как недомеренное.
5. **Цена на уровне `#share`-энфорса самого себя** (В.3 из плана 248) —
   этот скан не трогал вопрос, ловит ли сегодняшний `#share`-чек копирование
   ИЗ `ro` (баг №337 сам по себе) — отдельная, не связанная с формой записи
   тема, которую придётся решать вместе, но не измерялась здесь.
