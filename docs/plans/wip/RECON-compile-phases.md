# RECON — профиль этапов компиляции (план 255, Ф.0)

Окно `p255-profile`, ветка `p255-profile`, модель **sonnet**. Коммиты:
`3d59e6de0` (инструментирование). Машина: Windows, 16 логических CPU,
`available_parallelism()` → `--jobs 16` по умолчанию у `nova test`.

**Итог одной строкой (числа ниже, без домыслов): в измеренных срезах 61-95 %
суммарного времени работы уходит в стадию `imports-resolve` (резолв
`import`/std-библиотеки нашим же компилятором на Rust) — не в `clang`, не в
линковку, не в исполнение тестов. Доля растёт вместе с размером корпуса.**
Полный мега-CU (`spec_tests/conformance` целиком, как в гейте) замерить
целиком в этом окне не удалось — см. §3, причина техническая (потолок
инструмента), не методологическая.

## §0. Что и как мерил

Инструментирование (коммит `3d59e6de0`, `compiler-codegen/src/test_runner.rs`
+ `nova-cli/src/main.rs`):

* У `nova test` (в отличие от `nova build`) не было `PerfTimer` вокруг вызова
  cc — гейт идёт именно через `nova test`/`test_runner::run_one`, не через
  `cmd_build`. Добавлен таймер `c-compile` (оборачивает и single-TU путь
  `build_command`, и multi-TU `compile_multi_tu_to_exe` — какой из них
  сработает, зависит от `NOVA_MULTI_TU`, по умолчанию выключен → всегда
  single-TU, один процесс `clang` делает и компиляцию, и линковку).
* Добавлен таймер `run` (исполнение собранного бинаря) — раньше в
  агрегированную таблицу `PerfTimer` не попадал вовсе (только в отдельный
  `compile_ms`/`run_ms` JSON, план 169.1, не рядом с остальными проходами).
* Оба используют уже существующий (план 57.C.1/57.D.1) переключатель
  `NOVA_PERF_TIMER_AGGREGATE=1` — молчит по умолчанию, накапливает `__PERF__`
  замеры по всем скомпилированным файлам в один процесс и печатает таблицу
  в конце (`share`, `total`, `median`, `count`).
* Добавлен `NOVA_PERF_TIMER_LOG=<файл>` — `measure.sh` глушит stdout/stderr
  измеряемой команды (`>/dev/null 2>&1`), без файлового стока таблицу было бы
  не забрать с прогона, прошедшего вороты занятости машины. Аппендит
  (не перезаписывает) — виден каждый прогон серии `-n N`.

Все числа ниже сняты **исключительно** через `bash scripts/tools/measure.sh`
(вороты занятости машины + разброс — прошли, см. цифры). Три картины: один
маленький изолированный файл, представительный срез мега-CU (127 файлов),
ещё один срез большего размера (568 файлов) — как проверка масштабирования.
Полный мега-CU не уложился в потолок инструмента этого окна (§3).

| 1 | 2.44 s | 827.8 ms (34.0%) | 596.3 ms (24.5%) | 272.8 ms (11.2%) |

Остальное внутри «генерации .c» (parse, type-check, codegen, field-cache,

искомая «постоянная издержка, не зависящая от объёма» — для одного крошечного

Группировка по 4 категориям плана (доля от wall-time 5с, среднее по 3
прогонам): **генерация .c ≈ 29 %, clang (компиляция+линковка одним
вызовом) ≈ 16 %, исполнение ≈ 5 %, неучтённый оверхед процесса ≈ 50 %.**

## §3. Мега-CU целиком (`spec_tests/conformance`, как в гейте) — НЕ измерено

Команда, дословно совпадающая с `scripts/gate.sh:199`:
```
NOVA_GC_LIB_DIR=... NOVA_GC_INCLUDE_DIR=... \
bash scripts/tools/measure.sh -n 1 -l "mega-cu-full" -- \
  ./nova-cli/target/release/nova.exe test --positive --compile-error \
  --results-file /tmp/measure_megacu_results.jsonl \
  spec_tests/conformance
```

**Результат: команда не завершилась за 9 мин 50 с (потолок инструмента этого
окна — 600000 мс/10 мин на синхронный вызов) и была прервана снаружи.**
Ни `PerfTimer`-таблица (пишется только после завершения `run_all`), ни
results-файл (тоже дописывается по завершении) не сохранились — частичных
данных с этого прогона нет.

**Причина — техническая, не методологическая:** правила этого окна
запрещают фоновые запуски и ожидание фоновых уведомлений («Всё синхронно»),
а инструмент (Bash/PowerShell) ограничивает синхронный вызов 10 минутами.
Сам план оценивает мега-CU в ~37 минут (из вычитания времени стражей
`gate-profile.sh` из ~40-минутного гейта) — если оценка верна, ни один
синхронный вызов в этом окне физически не мог его измерить целиком.

После прерывания в системе остался висящий процесс `nova.exe`
(`/d/Sources/nv-lang/nova-p255/nova-cli/target/release/nova`) — потребовалось
`taskkill //F //IM nova.exe`, иначе последующие `measure.sh`-прогоны
отказывали по воротам занятости машины. Отмечено для тех, кто будет
повторять.

**Существующая (не мной снятая) цифра для контекста, НЕ измерение этого
окна:** `scripts/guards/mega-cu-time.baseline` фиксирует историческую чистую
базу **270с** (2026-08-07), и сам файл прямо предупреждает, что текущее
состояние может быть деградировавшим (там же зафиксирован недоверенный замер
~1008с под нагрузкой окон). Между 270с и оценкой плана «~37 минут» —
расхождение почти на порядок, которое это окно закрыть не смогло (не было
физической возможности снять валидную цифру для полного дерева).

### §3.1 Побочная находка при попытке — не улучшение, требует разбора

При подготовке к измерению обнаружено: **1160 из 1161 файлов верхнего уровня
`spec_tests/conformance/*.nv` объявляют один и тот же `module
spec_tests.conformance`** (проверено `grep -h "^module "` по всем
top-level `.nv`), что по `reference-nova-module-model-folder` должно
схлопывать их в ОДИН compile-unit (папка = один модуль). Однако:

* `nova test --positive --compile-error --list spec_tests/conformance`
  печатает эти файлы как **1161 отдельную запись**, а не одну — то есть код
  discovery (`walk_nv_selected_ex`/`is_folder_module_dir`,
  `compiler-codegen/src/test_runner.rs:6628-6664`) в дереве, как оно есть
  сегодня, папку-модуль **не распознаёт** (при полном совпадении деклараций
  функция обязана вернуть `true` и схлопнуть до одного алфавитно-первого
  файла — по коду это должно было произойти, по `--list` не произошло);
* попытка скомпилировать один такой файл в изоляции
  (`--filter a_q3_println_debug_record --jobs 1`) падает с
  `[E_D78_MODULE_PATH_MISMATCH]` — то есть в одиночку он невалиден, его
  `module spec_tests.conformance` легален только как peer папки-модуля.

Это противоречие (discovery видит 1161 независимую запись, но ни одна из них
не компилируется в одиночку) не разобрано до конца — разбор кода дальше
входит в архитектурный анализ, а не в измерение, и вышел бы за мандат Ф.0.
**Фиксирую как наблюдение для Ф.1-бис/Ф.2, не как вывод**: не измерено, во
сколько раз (если вообще) это умножает стоимость top-level части мега-CU;
возможно (не доказано), что реальный полный прогон делает существенно
меньше независимых компиляций верхнего уровня, чем 1161, — или наоборот,
существенно больше, если каждая «отдельная запись» из `--list`
всё же тянет за собой всех peer'ов через `resolve_imports_inline_ex`
(это отдельный участок кода `compiler-codegen/src/imports.rs`, не
затронутый данным замером). Без прогона внутри тайминга — только домысел,
поэтому в §1/§2 использовались файлы вне этой папки (§1) и её
под-каталоги, где такого противоречия при `--list`-проверке не
обнаружено (`standalone/`, `neg/`).

## §4. Что это отвечает и чего не отвечает

**Отвечает** (числа выше, воспроизведено 3× на срезе в 127 файлов, разброс
11 %, и качественно подтверждено на независимом срезе в 568 файлов):
время массово уходит не в `clang` и не в линковку (это один процесс,
раздельно не разложен — см. §5) и не в исполнение тестов, а в стадию
`imports-resolve` нашего же компилятора — резолв `import`/std-библиотеки,
доля растёт с 25-33 % на файле без явных импортов до 61-65 % на срезе из 127
файлов и 95 % на срезе из 568. Это согласуется (независимо найдено этим
окном, не позаимствовано) с уже заведённым [планом
252](../252-std-analysis-cache.md), который тем же классом наблюдения
(«std разбирается заново на каждый файл») объяснял конкретно чекер; здесь
находка распространяется на всю остальную стадию генерации .c и
подтверждена по всей ширине пайплайна (parse→codegen→cc→run), не только по
чекеру.

**НЕ отвечает:** абсолютное время полного мега-CU (§3) и не даёт разложения
`clang`-компиляции отдельно от линковки (§5) — оба зафиксированы как
неудавшиеся измерения с причиной, не как «вероятно X».

## §5. Что не удалось разложить и почему

**`clang`: компиляция и линковка не разделены.** Гейт запускает `nova test`
без `--mode`, то есть в режиме `dev` (не `release`) — по умолчанию это
single-TU путь (`build_command`/`compile_c_to_exe`,
`compiler-codegen/src/test_runner.rs:1836`), где ОДИН вызов `clang <file>.c
-o <exe>` делает препроцессинг, компиляцию и линковку внутри одного
процесса — с точки зрения `Command::spawn` это один дочерний процесс, замерить
его подэтапы раздельно на уровне wall-clock без правки самого `clang`-вызова
(например `-ftime-report`, отдельный `-c`+отдельный link) нельзя. Multi-TU
путь (`compile_multi_tu_to_exe`, план 209 Ф.2) разделяет compile/link на
отдельные процессы, но включается только через `NOVA_MULTI_TU=1`,
выключенный в гейте по умолчанию — включать его ради замера значило бы
мерить не тот путь, которым реально идёт гейт. Оставлено неразложенным,
помечено как единственный вызов `c-compile` (компиляция+линковка вместе).

**Полный мега-CU целиком** — см. §3, причина техническая (потолок
инструмента 10 минут на синхронный вызов + запрет фона в этом окне).
