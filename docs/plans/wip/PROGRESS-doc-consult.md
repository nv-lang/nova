## Вопрос 1. Форма out-параметра в FFI-примере

**Вывод.** Канонический для сегодняшнего состояния спеки и компилятора — `buf
*uninit u8` (без `mut`); форма `buf *mut uninit u8` — не ошибка, но
опережающая документация нереализованного фикса. Заодно: сам пример живёт **не
в `docs/guide/ffi-cookbook.md`**, а в `docs/guide/typed-pointers.md` (и его
`.ru.md`-паре) — в ffi-cookbook.md/ffi-cookbook.ru.md такого примера нет
вообще (проверено grep по `os_read`, `buf.*uninit` — ноль совпадений в обоих
файлах пары).

**Обоснование.**

1. Расположение форм:
   - `docs/guide/typed-pointers.md:115` — `extern "C" fn os_read(fd int, buf *mut uninit u8, n usize) -> int`, с комментарием на 118-120: «pointee writable (*mut) + possibly-uninit (uninit)».
   - `docs/guide/typed-pointers.ru.md:122` — то же самое на русской стороне пары.
   - `spec/decisions/02-types.md:10660` — канонический D246-пример: `extern fn os_read(fd int, buf *uninit u8, n int) -> int` (без `mut`).
   - `docs/guide/ffi-cookbook.md` / `.ru.md` — примера `os_read`/`buf *…uninit u8` НЕТ (grep пустой). Гипотеза автора вопроса о месте примера не подтвердилась — actual место для правки, если решите унифицировать, — `typed-pointers.md`/`typed-pointers.ru.md`, не `ffi-cookbook.md`.

2. Семантика по типовой таблице D246 (`spec/decisions/02-types.md:10591-10594`):
   `*uninit T` = `Pointer(Uninit(T))` — **CANONICAL** форма для «pointer к
   possibly-uninit T». `mut`/`uninit` — независимые postfix-модификаторы
   pointee (V2.2), их можно комбинировать (`*mut uninit T`), но комбинация не
   требуется для write-права: по write-таблице (`02-types.md:9936-9937`)
   `.write()` разрешён **и на `*mut T`, и на `*uninit T`** — голый `*uninit T`
   уже даёт право записи, потому что запись в uninit-память — это
   инициализация, а не мутация валидного значения (`§V2.3`, `02-types.md:10665-10692`: «Write `unsafe T` slot — safe (transitions to valid)»).

3. **НО** это же поведение — открытый, поименованный баг, не «фича по
   недосмотру». `docs/plans/backlog-followups.md:1948`
   (`[M-174.5-pointer-ops-methods]`, OPEN, P2): «write-cap-баг ЖИВ (spec §11a
   `02-types.md:8522` голый `*unsafe T` writable; checker `.write()` минует
   `pointee_is_writable`…)». Корень дыры: коэрция `*T → *uninit T` безопасна
   (`02-types.md:9970-9971`), а `*uninit T` пишем — значит можно взять
   read-only `*T`, тихо привести к `*uninit T` и записать сквозь номинально
   ro-указатель. Фикс (Plan 174.5, Ф.1: «write-cap-fix для старых форм»)
   спроектирован, но НЕ слит — `docs/plans/174.5-pointer-ops-methods.md:5`
   («Ф.1 … остаётся OPEN/deferred») и `:224-226` («Ф.1 … НЕ трогалась …
   заблокирована §10a-вердиктом», требует правки `02-types.md` в зоне Plan
   172/196, «не в одиночку»). После фикса писать через голый `*uninit T`
   станет невозможно — обязательным будет `*mut uninit T`.

4. Проверено по коду компилятора — `compiler-codegen/src/types/mod.rs:23988-24005`,
   `fn pointee_is_writable`: ветка `TypeRef::Mut(..) | TypeRef::Uninit(..) =>
   true` — **сегодня** `*uninit T` и `*mut uninit T` дают компилятору
   ОДИНАКОВЫЙ вердикт «writable». Разницы в поведении между двумя формами
   сейчас нет; обе компилируются и обе пропускают `.write()`.

5. Реальный, компилируемый прецедент в дереве — `examples/typed_pointers/basic_pointer.nv`:
   - строка 28, `fill_buffer(buf *mut Buffer, value i64)` — комментарий «for
     FFI out-params» — это форма для «structура уже существует, мы её
     мутируем».
   - строка 53, `raw_alloc_slot(slot *uninit Buffer)` — БЕЗ `mut`, комментарий
     «raw allocator output before init» — это форма для «слот ещё не
     инициализирован, первая запись = инициализация». `os_read`-паттерн
     (OS-буфер, куда читаются байты) семантически ближе именно к этому
     случаю, а не к «мутации готовой структуры».
   - В `std/**` живого примера ни на одну из форм НЕТ (grep по `\*uninit`/
     `\*mut uninit` в `std/` — пусто).

6. Кто пишет — Nova или C — на итог не влияет: mut-capability проверяется
   компилятором ТОЛЬКО в момент вызова `.write()`/`*p=v` **из Nova-кода**
   (`docs/plans/174.5-pointer-ops-methods.md` §12.3: гейт добавлен «на
   CALL-сайте» для `write`/`write_at`/…). Для параметра `extern fn`, куда
   Nova сама ничего не пишет (пишет вызываемая C-функция), ни `pointee_is_writable`,
   ни любой другой чекер-гейт не срабатывает вовсе — `mut` в типе параметра
   `extern fn` сегодня НЕ несёт рантайм/чекер-последствий, только
   документирующую роль для читателя (и потенциально — будущего
   ABI-чекера/bindgen).

**Как класть в гайд одной фразой** (если решите унифицировать): «`*uninit T`
уже даёт право записи (запись = инициализация, не мутация); `*mut uninit T` —
то же самое сегодня, но именно эта форма переживёт закрытие бага
`[M-174.5-pointer-ops-methods]`, после которого голый `*uninit T` станет
read-only». Технически строго правильны обе формы; они расходятся не как
«верно/неверно», а как «текущее поведение» (спека, `*uninit T`) vs
«forward-compatible идиома» (гайд, `*mut uninit T`), и разница объясняется
конкретным трекнутым (не выдуманным) багом, а не небрежностью авторов.

## Вопрос 2. Вес страницы D-блоков

**Вывод.** Разбивать URL/файлы не стоит — цена (редиректы для якорей,
переписывание сотен внутренних `NN-topic.md#dNNN`-ссылок по всей `spec/decisions/`,
постоянная дисциплина при каждом новом D-блоке) велика и постоянна для
соло-проекта, а выгода на слабом канале меньше, чем кажется из сырого числа
1,4 МБ: реальная передача — gzip ~403 КБ (замерено на собранном `dist/spec/decisions/types/index.html`,
1 392 828 байт исходный HTML → 403 114 байт gzip), а GitHub Pages (реальный
хостинг сайта) отдаёт gzip/brotli по умолчанию. Более дешёвый и безопасный
для соло-мейнтейнера рычаг — не резать страницу по URL, а срезать историческую
«шубу» амендментов внутри уже существующей структуры файла.

**Обоснование.**

1. Замер: `spec/decisions/02-types.md` — 1 160 202 байта исходника (самый
   тяжёлый файл; для сравнения — `03-syntax.md` 683 950, `04-effects.md`
   593 901, `06-concurrency.md` 560 782, `08-runtime.md` 497 689 — «того же
   порядка», как и написано в вопросе). Собранная страница
   `d:/Sources/nv-lang/www/site/dist/spec/decisions/types/index.html` — 1 392 828 байт;
   gzip той же страницы — 403 114 байт. Т.е. реальная плата на канале — не 1,4 МБ,
   а ~400 КБ (HTML — чистый текст, сжимается хорошо; тяжёлых картинок/шрифтов на
   странице нет).

2. Механика URL: `www/site/scripts/sync-decisions.mjs` строит ОДНУ страницу
   сайта на ОДИН файл решений (`pathToSite`, строки 44-56: `spec/decisions/NN-name.md`
   → `/spec/decisions/<topic>/`), а карту «D-номер → URL раздела» (`dMap`,
   строки 84-93 и продублирована в `www/site/astro.config.mjs` `buildDMap`)
   строит динамически по `## D<N>.`-заголовкам КАЖДОГО файла. Если разбить
   `02-types.md` на несколько файлов, каждый получит СВОЙ URL (топик = имя
   файла) — то есть буквальное разбиение файла ломает не только якоря, но и
   сам URL страницы для примерно половины из 97 D-блоков файла (сколько бы
   их ни попало в «отрезанные» файлы).

3. HTTP-фрагменты (`#d246`) не долетают до сервера — браузер никогда не
   отправляет `#...`-часть в запросе, поэтому серверный редирект по d-номеру
   технически невозможен без JS: единственный работающий вариант — держать
   старый URL живым как JS-заглушку («прочитай `location.hash`, посмотри
   заранее собранную карту, `location.replace()»), что требует чтобы старая
   страница НЕ удалялась НИКОГДА (иначе внешние ссылки с других сайтов/из
   самого репозитория `nova` ломаются без предупреждения) — то есть
   «редиректы по каждому D-якорю» на практике означает «дополнительный
   вечный слой инфраструктуры», а не разовую миграцию.

4. Внутри самого репозитория `nova` D-блоки массово ссылаются друг на друга
   строкой вида `../../spec/decisions/02-types.md#d246` (только в самом
   `02-types.md` таких перекрёстных упоминаний D246 — свыше 30, см. вывод
   `grep -n "D246"` на этот файл в ходе разведки). Разбиение файла означает
   пересборку ВСЕЙ этой сети ссылок по всему `spec/decisions/` (не только на
   сайте, но и в исходнике репозитория) — и это придётся переделывать заново
   при каждом будущем переносе D-блока между «подфайлами», то есть это не
   разовая, а постоянная эксплуатационная нагрузка на соло-автора.

5. Вариант «страница-контейнер с ленивой подгрузкой разделов» (единый URL,
   единый набор якорей, но контент секций подгружается по требованию) —
   единственный из трёх, который НЕ ломает существующие ссылки вообще (URL и
   id остаются на месте). Но это добавляет клиентский JS туда, где сейчас его
   нет (сайт — статический Astro-вывод без клиентского фреймворка на этих
   страницах), и создаёт риски: без JS — пустая страница; поиск по странице
   (Ctrl+F) перестаёт находить ещё не подгруженные секции; при прямом заходе
   по `#d246` в глубине документа нужен доп. код «догрузить нужную секцию до
   скролла» — для страницы, чей смысл существования — как раз глубокие
   якорные ссылки, это критичный кейс, который легко сломать тихо.

6. Более дешёвая альтернатива, которую не назвали в вопросе, но которая
   напрашивается из структуры репозитория: часть веса — не 97 «живых»
   решений, а накопленная история амендментов ВНУТРИ них. `grep -c
   "RETRACTED\|RETIRED\|SUPERSEDED\|устарел\|amend\b"
   spec/decisions/02-types.md` → 171 совпадение на 97 D-блоков (`grep -c "^## D[0-9]"` → 97) —
   то есть в среднем почти два амендмент/ретракт-маркера на решение. У
   проекта уже ЕСТЬ прецедент разделения «текущее» / «история»:
   `spec/decisions/history/*.md` (собранный размер — 120 345 байт,
   публикуется на сайте как `/spec/history/<slug>/`, тот же
   `sync-decisions.mjs`). Перенос части исторической/ретрактированной прозы
   из тела активных D-блоков в `history/` с оставлением в теле только
   финальной формулировки + ссылки «полная история решения — здесь» снижает
   вес БЕЗ смены URL/якоря самого D-блока (заголовок `## D246.` остаётся в
   том же файле на том же топике) — то есть не требует ни редиректов, ни
   переписывания перекрёстных ссылок. Это не проверено количественно (не
   мерил, сколько байт именно в retracted-блоках), но структурно самый
   дешёвый из вариантов.

**Итог по цене/выгоде.** На медленном канале ~400 КБ gzip — заметно, но не
катастрофично (HTML рендерится браузером по мере получения байт, верх
страницы читаем раньше, чем докачается низ) — это НЕ «белый экран пока не
докачается всё». Цена разбиения по URL (редиректы навечно + постоянная
дисциплина перекрёстных ссылок) для соло-проекта явно выше, чем текущая
неудобность. Если резать вес — начать с истории/ретрактов внутри файла, а не
с топологии страниц.

## Вопрос 3. Публикация roadmap.md пакета polaris

**Вывод.** Неуместно как публичная страница до v0.1 — стоит исключить из

**Обоснование.**

1. Формально страница не нарушает БУКВУ нормы `release-neutrality`

   GitHub Releases/теги nova, обещаний бинарных артефактов») — в
   `roadmap.md` нет ни дат, ни версий, ни ссылок на релизы; каждый пункт

     compiler.»
   - «Extractor arity-overload sugar» (`:25-67`) — заблокирован апстрим-багом
     компилятора, без ETA.
   - «`Path[T]` rename» (`:69-77`) — заблокирован апстрим-дефектом типчека,

   заголовок «Roadmap» на официальном сайте языка — это обещание независимо

   Разделы вроде «Request validation» и «Sessions: generic store» читаются

3. Прецедент внутри самого проекта nova: `docs/plans/` (тот же жанр — «что
   сделано, что планируется», только по компилятору, а не по polaris) на

   было распространено на пакетные репы при их подключении к сайту.

4. Почему полариса до сих пор публикуется — не отдельное решение, а

   `routing` и т.д. Это подтверждает: включение roadmap.md — не осознанное
   решение «это ок для публики», а побочный эффект правила «публикуем всё
   найденное» на волне, которая явно закрывала дыру подключения пакетных
   доков, а не оценивала уместность конкретной страницы.

5. `nova-polaris/docs/PUBLISHED.list:1-4` сам формулирует канон: «Один slug
   в строке = страница публикуется... Исключение = строка, закомментированная
   '#' с причиной» — механизм для точечного исключения уже есть, дело за

## Что я бы сделал иначе (не спрашивали, но бросается в глаза)

1. **`PUBLISHED.list` пакетных реп не имеет редакторского чек-листа, только
   инвентарный.** Механизм плана 241 Ф.2b («стартово — все N файлов
   инвентаря») по конструкции не задаёт вопрос «а стоит ли ЭТУ страницу
   показывать публике до v0.1» — он проверяет только парность (RU/EN) и
   технические свойства (доступность страницы, ссылки). Roadmap.md — не
   единственный кандидат такого рода: при появлении новых пакетных реп (или
   новых страниц в существующих) тот же механический паттерн снова пропустит
   любую страницу «внутреннего» жанра (roadmap/changelog-с-обещаниями/
   design-notes) в публикацию, если её просто добавят в docs/ пакета. Стоит
   явно прописать в `docs/dev/site-conventions.md` рядом с
   `release-neutrality` короткое правило-фильтр по ЖАНРУ страницы (roadmap/
   plans/wip — не публиковать по умолчанию, независимо от полноты
   RU/EN-пары), а не полагаться на то, что кто-то вспомнит об этом при
   каждой новой пакетной репе.

2. **Расхождение спеки и гайда по `*uninit`/`*mut uninit` — не единичный
   случай, а симптом того, что открытые (`OPEN`) пункты `backlog-followups.md`
   не имеют явной связи с `docs/guide/*`.** Гайд `typed-pointers.md` уже
   потихоньку документирует то, что должно стать правдой ПОСЛЕ
   `[M-174.5-pointer-ops-methods]`, а спека — то, что правда СЕЙЧАС; читатель
   не может отличить одно от другого без раскопок, которые я проделал для
