## Дизайн-запись (что кэшируется и где обязана быть инвалидация)

### Что вообще кэширует Plan 123.4 (chain-cache)

`compiler-codegen/src/field_cache.rs`, функция `chain_cache_fn_impl`: для
METHOD-тела ищет цепочки вида `@a.b.c...` (доступ к полю через ДРУГОЕ поле
получателя, глубина ≥2), и если путь встречается в теле функции ≥
`chain_threshold` раз — эмиттирует ОДИН `let _at_a_b..._chain = @a.b.c...`
ПРЕФИКСОМ функции (до любого другого стейтмента) и переписывает ВСЕ
вхождения этого пути на этот локал.

Критерий «безопасно» — эвристика «путь никогда не пишется в теле функции»
(`body_writes`/`self_method_writes`). Ключевая находка №291: этот критерий
был СЛОМАН для путей глубины ≥2.

### Корень (изолирован через генерируемый `.c`, не только через теорию)

Три функции детекции «это запись» — `collect_body_writes_stmt` (эксклюзивность
кэша chain-cache), `collect_writes_stmt` (IPA write-set реестр, использует
LICM/pure-cache/chain-cache-with-IPA) и `collect_body_writes_expr`'s
`ExprKind::Call` — ВСЕ трое узнавали «поле записано» ТОЛЬКО через
`match_self_field`, который матчит ИСКЛЮЧИТЕЛЬНО одноуровневый `@F = ...`
(`obj` должен быть буквально `SelfAccess`). Для цепочки глубины ≥2
(`@a.b = ...` / `@a.b op= ...`, ИЛИ вызов метода через цепочку
`@a.b.method()`) `match_self_field` возвращает `None`, и код падал в
обычный expression-walk, который НЕ фиксирует запись вообще.

Итог: `chain_cache_fn_impl`'s `body_writes`-гейт не видел, что путь
`["ch","count"]` пишется (`@ch.count -= 1` в `ChanReaderV2.recv`,
`@ch.count += 1` в `ChanWriterV2.send`) — трактовал цепочку как read-only,
кэшировал `_at_ch_count_chain = @ch.count` ОДНИМ `let` В САМОМ НАЧАЛЕ
функции (до `Mutex.lock()`!), и ПЕРЕПИСЫВАЛ TARGET присваивания на тот же
локал — реальное поле `count` в `#share`-структуре НИКОГДА не
инкрементировалось/декрементировалось, кэш-локал жил и умирал в стеке
вызова, невидимый для любого другого вызова метода.

Подтверждено эмпирически на реальном `.c` (см. «Второй симптом» ниже) —
буквально:
```c
nova_int _at_ch_count_chain = (_at_ch->count);      // once, before mutex.lock()
...
while (1) {
    if (!((_at_ch_count_chain == 0) && ...)) break; // stale forever
    (void)(Nova_Condvar_method_wait_Mutex(...));    // parks forever
}
...
nova_int* _nv_ca_1063 = &(_at_ch_count_chain);      // write redirected to LOCAL
*_nv_ca_1063 = nova_int_checked_sub(*_nv_ca_1063, 1); // real struct field never touched
```

Однофайберный кейс (`tx.send(1); rx.recv()`, БЕЗ единого `spawn`) висит по
той же причине БЕЗ КОНКУРЕНТНОСТИ ВООБЩЕ: `send()`'s `@ch.count += 1`
записывает только в свой одноразовый локал (никогда не долетает до
реального поля) → после возврата `send()` реальное `count` остаётся 0 →
`recv()` (СВЕЖИЙ вызов, читает РЕАЛЬНОЕ поле = 0) входит в цикл, вызывает
`wait()` — и больше НИКТО не вызовет `notify_one()` (send уже вернулся) →
вечная парковка.

### Где обязана быть инвалидация (фикс)

Три места (все три — тот же класс дефекта, три независимых проявления):
1. `collect_body_writes_stmt`'s `Stmt::Assign`/`Stmt::TupleAssign` —
   вместо `match_self_field(target)` теперь `extract_chain_path(target)`
   (уже существующий helper, тот же, что использует rewrite-сторона) —
   фиксирует ВСЕ сегменты цепочки-таргета как «записано».
2. `collect_writes_stmt`'s `Stmt::Assign`/`Stmt::TupleAssign` — то же (эта
   функция кормит IPA write-set реестр — `build_write_set_registry`,
   используемый LICM/pure-cache/chain-cache-with-IPA для «звонок на M
   пишет F?»).
3. `collect_writes_expr` (уже частично умел это для ОДНОУРОВНЕВОГО
   `@field.method()` — комментарий явно ссылается на прежний прецедент
   `@src.next()` в `SkipIter.next()`) и `collect_body_writes_expr`'s
   `ExprKind::Call` (не умел ВООБЩЕ) — оба теперь используют
   `extract_chain_path(obj)` вместо `match_self_field(obj)`, распознавая
   МЕТОД, вызванный через цепочку ЛЮБОЙ глубины (`@ch.not_empty.wait(...)`,
   ровно граница, за которой другой файбер меняет поле, которое `while`
   проверяет) — не только глубину 1.

Кэш НЕ отключён (см. позитивный тест — `ro`-цепочка без записи ВСЁ ЕЩЁ
кэшируется), инвалидация целевая и по документированному классу дефекта.

## Второй симптом: расхождение `nova build` vs `nova test` (объяснение)

**Гипотеза «кэш собранного дистрибутива»/«гонка»/«toolchain» — ОПРОВЕРГНУТЫ
эмпирически** (пробовал: другой toolchain явно, тот же файл в той же
папке-модуле, обёртка `supervised{}`, изолированный единственный тест без
соседей, `--jobs 1`) — во всех вариантах `nova build`-скомпилированный
бинарник (ручная сборка ИЛИ `nova test-build`) НИКОГДА не вешался, а
`nova test`/`nova test-build` (при коде ДО фикса) — вешался ДЕТЕРМИНИРОВАННО.

**Реальный корень — механический, найден прямым чтением исходников
компилятора, НЕ гипотеза:** `nova build` (обработчик `Cmd::Build` в
`nova-cli/src/main.rs`) **вообще никогда не вызывает
`field_cache::cache_module`**. Полный путь пайплайна там —
type-check → effects → lints → desugar → call-norm → `emit_module_multi_tu`
— БЕЗ единого упоминания `field_cache`/`cache_module` (грепом по всему
файлу — оба совпадения принадлежат СОВСЕМ ДРУГОЙ команде,
`nova check --explain-cache`, диагностика, не компиляция). `nova
test`/`nova test-build` идут через ОТДЕЛЬНУЮ, независимую реализацию —
`compiler-codegen/src/test_runner.rs`'s `run_one`, которая ДЕЙСТВИТЕЛЬНО
вызывает `field_cache::cache_module`.

Подтверждено прямым осмотром сгенерированного `.c` для ОБОИХ путей на
одном и том же исходнике: у `nova build` — буквальные `self->field` на
каждом чтении, ноль `_at_*`-локалов; у `nova test` — полный набор
chain-cache преобразований. `--no-field-cache` «чинит» `nova test` именно
потому, что она — единственная из двух реализаций, которая ВООБЩЕ
применяет field-cache; отключать там нечего для `nova build`, кэш там и
так неактивен.

**Следствие, отдельное от P0:** Plan 123 (field-cache, вся оптимизация —
V1-V7) НИКОГДА не применялась ни к одной программе, собранной через
пользовательский `nova build` — то есть заявленный перф-выигрыш (план
123's `AU.4`: «≥30% improvement») валидировался ТОЛЬКО через
`nova test`/`nova bench`, никогда через реальный путь конечного
пользователя. Это НЕ баг field-cache correctness (он МОЖЕТ быть
намеренным design-gap — cache отключён для release build намеренно?), но
это явно НЕ задокументировано нигде и выглядит как забытая проводка, а не
решение. Доложено интегратору, НЕ чинил (вне периметра «инвалидация кэша»
этого окна — подключение целой оптимизационной фазы в другой,
независимый компиляторный пайплайн требует отдельного ревью порядка
проходов/семантической эквивалентности, не одной строки).
