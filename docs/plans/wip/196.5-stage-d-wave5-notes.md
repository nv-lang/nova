## Часть 1 — B11ai (по-веточная таблица)

| Ветка (census) | Трафик (census) | Диагноз волны-5 | Вердикт | Доказательство |
|---|---|---|---|---|
| `B11ai_serialize_contract` | 0 (не доказателен — блокирован P67-паникой §1.1 census, снятой волной-3) | ЖИВОЙ: 1+ hit на `std/src/encoding` даже с исправленной P67-паникой. Два под-класса receiver'а: (а) **for-loop** (`fn[T Serialize] []T @serialize(...) { for v in @ { v.serialize(s) } }`) — receiver `v` типизируется чекером как `Named{["T"]}` через `infer_expr_type`/scope, ГЕЙТ `gs.contains("T")` проходит; (б) **match-arm-bound** (`fn Option[T Serialize] @serialize(...) { match @ { Some(v) => v.serialize(s) } }`) — receiver `v` НЕ в `scope` И НЕ в `resolved_types_buf` (`ExprKind::Match` в f1_expr не сеет pattern-bound имена в `scope` перед walk тела арма) | **ЧАСТИЧНЫЙ producer** (класс (а) закрыт), branch НЕ снесена (класс (б) остаётся) | Прямой трейс (`NOVA_B11AI_TRACE`-стиль probe, вычищен): класс (а) — Channel-2 лоуэрится `Ok("NovaRes_nova_unit_NovaValue_SerError*")`, БАЙТ-В-БАЙТ легаси-строка; класс (б) — `recv_ty` лукап молча падает (outer `if let Some` не входит), легаси остаётся единственным источником |

**Producer:** `compiler-codegen/src/types/mod.rs` f1_expr Member-арм (~7960,
`else if method == "serialize"`): receiver резолвится через
`infer_expr_type`/`resolved_types_buf`-fallback → если peeled-тип это
`Named{path:[n]}` с `n` в `gs` (in-scope generic) — читает `Serialize`
protocol's `serialize` return type ИЗ ДЕКЛАРАЦИИ (`self.types.get(
"Serialize")`, НЕ хардкод), гейт на `!mentions_self` (Serialize контракт
receiver-invariant в отличие от Deserialize) → материализует
`resolved_types_buf`.

**Остаток (для будущей волны):** match-arm pattern-bound receiver typing —
`ExprKind::Match` handler в f1_expr не регистрирует `Pattern::Variant`'s
bound names (`Some(v)`'s `v`) ни в `scope`, ни в канал, ПЕРЕД walk тела
арма. Это ШИРЕ Serialize — затрагивает ЛЮБОЙ generic call на pattern-bound
переменной внутри match arm. Фикс — не точечный (затрагивает каждый match
arm в чекере), явно вынесен за периметр этой волны, задокументирован в
`types/mod.rs` (комментарий у B11ai-легаси-арма в `emit_c.rs` ~50748) для
следующей волны.

**Другие ≤12-hit ветки census §3.2** (`B11ac_novavtable_effect`,
`B11ak_self_recursive_generic_method`) — НЕ тронуты в этой волне (время
ушло на глубокую диагностику B11ai; оба остаются кандидатами для
следующей волны, ни один не является core/W1-классом).

## Часть 2 — facet C (сводка; полная карта — отдельный файл)

См. `docs/plans/196.5-facet-c-map.md`. Кратко: `callnorm.rs`'s
`collect_sigs`/`try_normalize_call` строят СВОИ ТРИ грубые name/arity-based
таблицы (`free`/`static_methods`/`instance_by_name`) для резолва «какие
params у этого call-site», ДУБЛИРУЯ то, что чекер уже решил
type-aware'но и записал в `ModuleEnv.resolved_callees` (`HashMap<ExprId,
Span>`) — канал, к которому `callnorm.rs` НИКОГДА не был подключён (создан
до Plan 172.1's resolved_callees). Самый широкий дефект-класс:
`instance_by_name` молча ВЫКЛЮЧАЕТ нормализацию для ЛЮБОГО метода, чьё имя
встречается у ≥2 типов в модуле (частое: `len`/`push`/`new`/…) — в
мега-CU конформанса такие коллизии почти гарантированы.

**Экземпляр:** `normalize_module`/`collect_sigs` теперь принимают
`resolved_callees: &HashMap<ExprId, Span>`; `Sigs` получил `by_span:
HashMap<Span, Vec<Param>>` (индекс по декларации). `try_normalize_call`
СНАЧАЛА пробует `resolved_callees[e.id] → by_span[span]` — при попадании
использует ЭТИ params напрямую (минуя все три грубые таблицы), при
промахе — падает на старую эвристику без изменений. 9 call-site'ов
`normalize_module` по дереву обновлены (5 — реальный `ModuleEnv`/`check_env`
уже в scope → передан `&env.resolved_callees`; 2 — explain-cache diagnostic
+ doc-test interp path, чекер-состояние и раньше отбрасывалось → пустой
`HashMap::new()`, byte-identical к прежнему поведению).

**Гейт:** нет живого red-кейса в текущем корпусе (единственный instance-
метод с default-параметром во всём std — `str.to_int`, имя уникально, не
коллизирует) → byte-parity доказательство: conformance 468/0/12,
collections 13/0/6, data 3/0/3 — все байт-в-байт база. Доп. корроборация
(examples/ 18/10/8) — все 10 FAIL пре-существующие, ни один не относится к
callnorm.
