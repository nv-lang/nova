# PROGRESS — окно p349-ptr-l3

Модель: sonnet. Ветка `p349-ptr-l3` в `d:/Sources/nv-lang/nova-p349` (main репо
не трогать). Задача: №349 (К1, чекер пропускает запись за `*T` при
mut-связывании) + №350 (внутренняя ошибка компилятора на интерполяции).

## №349 — ИСПРАВЛЕНО (чекер-канал)

**Место фикса:** `compiler-codegen/src/types/mod.rs`,
`TypeCheckCtx::check_target_readonly`, arm `ExprKind::Member`.

**Диагноз.** `p.field = v` где `p` — сырой указатель — это auto-deref сахар
для `(*p).field = v` (D216 §5). Существующий Member-arm проверял ТОЛЬКО
L1/L2 (binding/content-view) через `root_view_is_mut_type` /
`root_view_is_ro_type` / `is_through_ro_binding` / `is_readonly_path`, а
затем прямую проверку `ro`/`priv`-полей через `tr.strip_readonly()` — но
это последнее выражение матчится ТОЛЬКО на `TypeRef::Named`, и для
`TypeRef::Pointer` (обычный указатель) всегда даёт `None`. Итог: L3
(pointee-capability, единственная ось, которая реально решает разрешена ли
запись за `*T`) вообще не проверялась для формы `p.field = v` — в отличие
от `*p = v` (`ExprKind::Unary { op: Deref, .. }`) и `p[i] = v`
(`ExprKind::Index`), которые уже гейтились через `pointee_is_writable`
(Plan 147/D246, тот же файл). `p.field = v` — единственная из трёх форм
записи-через-указатель, которая была пропущена при первоначальной
реализации D246.

**Фикс.** В начало Member-arm добавлена L3-проверка: если тип `obj`
(получателя) — указатель (`pointee_is_writable` возвращает `Some(_)`), то:
- `Some(false)` (голый `*T ≡ *ro T`) → `[E_POINTER_RO_ASSIGN]` с текстом,
  зеркальным Deref/Index-веткам, ссылкой на D246 и явной подсказкой про
  `*mut T`; `return` — L1/L2 value-binding проверки ниже не выполняются
  (они не относятся к записи через указатель, D246 §2: L1 binding
  контролирует только reassignment `p`, не pointee);
- `Some(true)` (`*mut T`) → запись через указатель разрешена по L3, но
  ПОЛЕ pointee-типа может всё ещё быть `ro`/`priv` (D175/D220) — этот
  случай не был протестирован в фикстурах брифа, но исправлен заодно:
  общий код прямой field-attr проверки вынесен в новый метод
  `check_field_write_attrs(tr, field_name, target, errors)`
  (использовался раньше только для value-получателей), вызывается здесь с
  типом pointee (через новый `pointee_named_type`), а не типом указателя.

Новые свободные функции: `pointee_named_type` (рядом с
`pointee_is_writable`, тот же файл) — распаковывает `*mut T`/`*uninit
T`/`*ro T`/`*T` до типа pointee для field-lookup.

**Побочный эффект рефакторинга:** старый прямой field-lookup блок (~57
строк, readonly + priv + module-priv диагностики) вынесен в helper
`check_field_write_attrs`, используется и с прежнего (value) сайта, и с
новой pointer-веткой — без дублирования текста диагностик.

## №350 — НЕ РЕПРОДУЦИРУЕТСЯ на валидном Nova; ложная тревога, найден иной, уже отслеженный дефект

**Гипотеза брифа («тип получателя подменяется типом StringBuilder,
которым интерполяция собирает результат») НЕ подтвердилась.**

Проверка: дословный репро из брифа —

```nova
module strbuild_probe
type Counter { v int }
fn main() {
    mut a = Counter.new(1)
    println("${a.v()}")
}
```

действительно роняет компилятор с ТЕМ ЖЕ текстом (`[P67-LEGACY] … obj_ty="Nova_StringBuilder*" obj=Ident(a)`).
Но изоляция показала: **порча типа `a` происходит ДО интерполяции, на
самой строке `mut a = Counter.new(1)`, независимо от println** —
убрал `println("${…}")`, оставил только `println("ok")`: сборка всё равно
падает (linker: `undefined symbol: Nova_Counter_static_new`), и
сгенерированный C показывает `Nova_StringBuilder* a =
Nova_Counter_static_new(...)` — **`a` объявлена с типом StringBuilder ещё
на строке своего собственного создания**, ДО того как интерполяция вообще
начала эмититься. Интерполяция здесь — не источник порчи, а просто первое
место, где чтение уже-испорченного `a` попадает в жёсткий `panic!`
(`[P67-LEGACY]`) вместо тихого/отложенного сбоя.

**Корень: `type Counter { v int }` НЕ ИМЕЕТ метода `.new()` вообще** —
`fn Counter.new` нигде не определён в репро. По D372 (`spec/decisions/
02-types.md`, «Canonical `.new()` constructors (convention)», статус
«convention (stdlib provides, compiler does NOT auto-generate)»):
**компилятор осознанно НЕ автогенерирует `.new()` для user records** —
это design discipline, разработчик обязан написать конструктор явно.
D372 прямо перечисляет user records в списке типов БЕЗ canonical `.new()`
и ссылается на уже заведённый followup:
`[M-91.7-default-new-enforcement]` (`docs/plans/91.7-array-methods-and-
default-new.md:425`): *«compile-error для user types без явного `.new()`
… сейчас silently routes via single-key fallback»* — то есть чекер и
codegen СЕГОДНЯ (задолго до этого окна, задокументированно) не проверяют,
что `.new()` реально существует у типа-получателя, и вызов молча
маршрутизируется через какой-то общий/неспецифичный резолвер, который в
данном случае коллизирует с `StringBuilder.new(cap int)` — единственный
builtin `.new()` с сигнатурой «один `int`-аргумент», совпадающей по форме
с `Counter.new(1)`.

**Подтверждение экспериментом:** добавил РЕАЛЬНЫЙ конструктор —

```nova
fn Counter.new(v int) -> Counter {
    return Counter { v }
}
```

— с ним ТОТ ЖЕ репро (`println("${a.v()}")`) **собирается и работает
корректно** (`nova check` ok, `nova build` ok, бинарник печатает `1`).
Значит интерполяция метод-вызова `.v()` — это авто-геттер записи (D117,
«поля = property-методы») — сама по себе исправна; проблема ИСКЛЮЧИТЕЛЬНО
в том, что исходный репро вызывал несуществующий метод `Counter.new`, а
компилятор не сообщил об этом честной ошибкой (это и есть
`[M-91.7-default-new-enforcement]`).

**Смежность с №338 — НЕТ, разные корни.** №338 — синтезированный AST-узел
вызова (для default-параметра) наследовал НЕУСТАНОВЛЕННЫЙ `ExprId`, из-за
чего обе двери чекер-канала (resolved_types/resolved_callees) гейтились на
«id установлен» и молча пропускались; фикс — однострочный, в `callnorm.rs`.
№350 — не про синтезированные узлы и не про `ExprId`: узел вызова `Counter.
new(1)` реальный, из исходника, с установленным id; проблема в том, что
резолвер СТАТИЧЕСКОГО КОНСТРУКТОРА для типа без объявленного `.new()` не
проверяет существование метода вообще (`[M-91.7-default-new-enforcement]`,
известный, отдельно заведённый gap, требующий, по собственной пометке
марки, «BoundCtx type registry» — заметно больше объёма, чем однострочный
чекер-канальный фикс).

**Решение: №350 НЕ чинить в этом окне.** Обоснование:
1. Это не новый дефект — это ПОВТОРНОЕ обнаружение уже заведённого и
   намеренно отложенного followup'а (`[M-91.7-default-new-enforcement]`,
   Plan 91.7, автор пометки уже знал про «single-key fallback» и явно
   отложил полноценный фикс).
2. Полноценный фикс (реальная enforcement-диагностика «нет `.new()` у
   типа X») по своей же пометке требует нового реестра типов
   (`BoundCtx type registry`) — это отдельная фича, не однострочный
   чекер-фикс уровня К1 этого окна, и она **behavior-changing в куда
   большем масштабе**, чем №349 (ЛЮБОЙ существующий код, вызывающий
   `.new()` на типе без объявленного конструктора, начнёт падать на
   `nova check` — нужен отдельный корпус-свип, отдельное окно).
3. Бриф: «если корень общий [с №338] — закроем оба одним фиксом; если
   нет — не притягивай». Корень НЕ общий → не притягиваю.
