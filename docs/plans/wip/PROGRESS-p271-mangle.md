# PROGRESS — p271-mangle (№271, `[M-static-selfreturn-value-mangle-conflict]`)

Модель: sonnet. Ветка `p271-mangle`, worktree `d:/Sources/nv-lang/nova-p271`.

## Вердикт: воспроизводится, но НЕ по той причине, что записана в реестре

Дефект реален — `nova test`/`nova build` на реальном мигрированном `bigint.nv`
(коммит `bfd1194` в `nova-bignum`, ветка `p-tuple`) даёт CC-FAIL
`conflicting types for 'Nova_BigInt_method_equal'`. Но формулировка записи
№271 («статик-конструкторы + instance-методы одного кортежного типа в одном
CU конфликтуют») **опровергается живым кодом ДО фикса**: `Complex`
(`std/src/math/complex.nv`) — именованный кортеж со статик-конструктором
`Complex.from_polar(...) -> Self` (`:82`) и 23 instance-методами включая
`@equal` (`:217`) — собирается чисто (`nova check std/src` = канон
`148/26/61`). Более того, эмпирически (см. «Дифференциальный анализ» ниже)
я показал: статик-конструктор дефекту вообще НЕ НУЖЕН. Реестровая
формулировка и имя маркера (`static-selfreturn`) описывают ДРУГОЙ, уже
закрытый дефект (Plan 172.13, коммит `d28e9459a`, 2026-07-08) — тот
действительно был про `Self`-return static-ctor ABI и чинился тем же днём,
фикстура `spec_tests/conformance/static_ctor_instance_method_named_tuple.nv`
жива и по-прежнему зелёная. №271, судя по всему, был заведён по мини-репро
из `nova-bignum/PROGRESS.md` (ветка `p-tuple`, ныне не в git-истории репы
nova, только в `nova-bignum`), но диагноз в реестре ошибочно унаследовал
формулировку/имя маркера от соседнего 172.13-класса вместо независимого
расследования.

## Настоящий корень: recursive Option/Result-of-tuple-of-named-tuple eq-helper эмитится РАНО

**Файл:** `compiler-codegen/src/codegen/emit_c.rs`
**Функция:** `debt_is_late_emitted_value_payload` (было — строки 54855-54868)
**Вызывается из:** `register_novaopt_decl` (~54338-54559) и `register_novares_decl`-путь (~54979-54980)

Триггер — **`@equal` СОСУЩЕСТВУЕТ с ЛЮБЫМ методом, возвращающим
`Result[(Self, Self), E]` (или `Option[(Self, Self)]`)** на именованном
кортеже. У `BigInt` это `@equal` (`bigint.nv:380`) + `@div_rem(...) ->
Result[(BigInt, BigInt), DivError]` (`bigint.nv:650`). Статик-конструкторы
`.zero()`/`.one()` — НЕ участвуют (см. дифференциальный репро ниже).

Механизм (C-выхлоп, строка нумерация — сгенерированный `bigint.c`):
```c
// строка ~537, РАНЬШЕ любой forward-decl метода BigInt:
static inline nova_bool nova_opt_eq__NovaTuple_2_16_NovaTuple_BigInt_16_NovaTuple_BigInt(...) {
    ...
    return (Nova_BigInt_method_equal(&((a.value).f0), (b.value).f0) && ...);
}
// строка ~2084, НАСТОЯЩАЯ forward-declaration метода:
static nova_bool Nova_BigInt_method_equal(NovaTuple_BigInt* nova_self, NovaTuple_BigInt other);
// clang: conflicting types — первая ссылка создала implicit-декларацию
// раньше, чем эта настоящая появилась.
```

Компилятор авто-синтезирует structural-equality helper для составного
`Option`/`Result`-типа, оборачивающего 2-кортеж из `BigInt` (нужен для
`==`/производного равенства на таком составном значении). Диспетчер выбора
"эмитить рано или поздно" — `register_novaopt_decl` — уже умеет откладывать
эмиссию ("early proto + late body" split) для ПРЯМОГО payload'а
(`NovaTuple_X`/`NovaValue_X____...`, через `debt_is_late_emitted_value_payload`)
и для heap-payload (`Nova_X*`, через `debt_opt_payload_needs_structural_eq`) —
оба класса уже чинились в Plan 172.13/172.1. Но **позиционный кортеж
(`_NovaTuple_N_...`), СОДЕРЖАЩИЙ такой payload КАК ЭЛЕМЕНТ**, не был
покрыт: по комментарию у старой версии функции он явно и осознанно исключён
("positional `_NovaTuple_…` are emitted EARLY and excluded") — это верно
для кортежа из скаляров, но неверно, когда элемент сам — `NovaTuple_<X>`
с пользовательским `@equal`.

## Фикс

Расширил `debt_is_late_emitted_value_payload` рекурсивным случаем: для
позиционного кортежа декодирую элементы через УЖЕ существующий
структурированный декодер `parse_mono_tuple_elements` (строка ~20358 —
парсит length-prefixed формат `_NovaTuple_<arity>_<L1>_<T1>_...`, уже
используется в 10+ местах файла для той же цели) и рекурсивно проверяю,
не является ли какой-то элемент сам late-payload'ом. Это **не** новая
string-эвристика поверх формата — это переиспользование существующего
парсера имени, которое компилятор САМ формирует по фиксированной грамматике
(единственный источник правды о составе кортежа на этом уровне; отдельного
`tuple_schemas`-реестра в этой кодовой базе нет — декодер имени и есть
канал для этого факта).

```rust
fn debt_is_late_emitted_value_payload(c_ty: &str) -> bool {
    (c_ty.contains("____") && c_ty.starts_with("NovaValue_"))
        || (c_ty.starts_with("NovaTuple_") && !c_ty.ends_with('*'))
        || Self::parse_mono_tuple_elements(c_ty).is_some_and(
            |es| es.iter().any(|e| Self::debt_is_late_emitted_value_payload(e)))
}
```

Один предикат, три вызывающих места (`register_novaopt_decl`'s NovaOpt-путь
и `NovaRes_`-путь) — правится централизованно, дублирования не потребовалось.

**Почему это emit-слой, а не чекер-канал.** Дефект — это ЧИСТО C-эмиссионная
проблема порядка forward-declaration'ов (когда конкретно в однопроходном
текстовом выхлопе появляется прототип/тело функции), а не вопрос типов или
резолва — чекеру порядок C-деклараций неизвестен и не должен быть. Это тот
самый "genuinely emit-layer" случай, для которого сам `arch-ratchet.sh`
явно оставляет путь роста с обоснованием. Тем не менее диф **net-zero**
(0 строк дельты) — уложился без роста бюджета, подрезав документацию
рядом (было 14 строк функция+доки, стало 13; в тестовом модуле аналогично
скомпенсировано).

## Проба на актуальность (уникальные имена)

Первая попытка — минимальный репро с заведомо уникальными именами
(`Qzz271`/`Bzz271` + `@equal`/`@plus`, БЕЗ метода, возвращающего кортеж
Self) — **НЕ воспроизвела** дефект (собралось и отработало чисто). Это
важный сигнал: сама комбинация "static ctor + instance-метод на именованном
кортеже" недостаточна. Только когда я взял РЕАЛЬНЫЙ `bigint.nv` из
`nova-bignum` (ветка `p-tuple`, коммит `bfd1194`) целиком — дефект
воспроизвёлся сразу, с тем же текстом ошибки, что в `PROGRESS.md` того
окна. Дальнейшее сужение (см. ниже) нашло точный минимальный триггер.

## Дифференциальный анализ (по указанию интегратора: взять `Complex` эталоном)

Прогнал контрфактическую проверку на ДОФИКСОВОМ компиляторе (сохранил
патч, `git checkout --` файла, пересобрал, прогнал, восстановил патч,
пересобрал — рабочее дерево вернулось в зафиксированное состояние):

- `Qzz271`/`Bzz271` (§выше, 1-2 статик-конструктора + `@equal`/`@plus`,
  БЕЗ `Result[(Self,Self),E]`-метода) — **собирается на ДОФИКСОВОМ
  компиляторе тоже**. Число статиков не влияет.
- Минимальный репро **БЕЗ единого статик-конструктора** —
  `Czz271(x int, y int)` + `@equal` + `@split(...) ->
  Result[(Czz271, Czz271), Ezz271]` — **CC-FAIL на дофиксовом
  компиляторе** (дословно: `conflicting types for
  'Nova_Czz271_method_equal'`, `previous implicit declaration` на строке
  auto-eq-хелпера) и **PASS на фиксовом**.

Вывод: единственная необходимая и достаточная комбинация —
**`@equal` (или другой метод, чьё имя совпадает с тем, что синтезирует
структурная эквивалентность) + метод, возвращающий кортеж/составной тип ИЗ
Self-подобных элементов в `Option`/`Result`**. `Complex` не триггерит ЭТОТ
класс не потому, что у него один статик (у него их 0 сейчас, было больше
до 2026-07-08), а потому что **у него нет ни одного метода, возвращающего
кортеж/Result из `Complex`** — `from_polar` возвращает голый `Complex`, не
`(Complex, Complex)`. Формулировка реестра требует поправки: заменить
условие на «`@equal` + метод, возвращающий `Result[(Self,Self),E]` /
`Option[(Self,Self)]`, на именованном кортеже», статик-конструкторы убрать
из формулировки как нерелевантные.

## Дополнение интегратора: `@compare` на именованном кортеже — РАБОТАЕТ

Отдельно проверил `@compare` (`nova-bignum/src/bigint/core.nv:383`,
`export fn BigInt @compare(other BigInt) -> int`; в `p-tuple`-версии —
строка 390) — **исход 1 из трёх предложенных: работает, память
владельца устарела**. Проверил все уровни:
- прямой вызов `z.compare(o)` — работает;
- производные операторы `<`/`>`/`<=`/`>=` (D46/D363, деривация из `@compare`)
  — работают;
- `Vec[BigInt].sort()` (использует `@compare` внутри) — работает,
  результат отсортирован корректно.

Всё это — в ОДНОМ CU вместе с `@equal`+`@div_rem` (после фикса №271), т.е.
`@compare` не открывает отдельного блокера. Миграция `nova-bignum` НЕ
блокируется дефектом `@compare` на кортежах — такого дефекта в текущем
компиляторе НЕТ.
