# PROGRESS — окно p390-read-hang

Модель: sonnet. Worktree: `d:\Sources\nv-lang\nova-p390` (branch `p390-read-hang`).

## Резюме (то, что нужно знать первым делом)

Исходная жалоба («второй `read()` виснет, `supervised(timeout:)` его НЕ
будит») — **частичная неверная диагностика**. Дословно:

1. **`timeout:`/cancel ДЕЙСТВИТЕЛЬНО будит второй `read()`** — проверено
   инструментальной трассировкой C-уровня (см. §3): `nova_scope_deliver_cancel`
   → `_nn2_stream_stop_cb` → `nova_loop_defer_close` → `_nn2_stream_close_cb`
   → `nova_sched_wake` — вся цепочка отрабатывает штатно, `net_tcp_read`
   возвращает `UV_ECANCELED` в пределах заявленного дедлайна.
2. Наблюдавшееся «виснет НАВСЕГДА, таймаут не спасает» в
   `docs/plans/repro/p249_second_read_after_partial_hangs.nv` — это
   **отдельный, куда более тривиальный баг в САМОМ репро-файле**: гонка
   двойной отправки в канал ёмкости 1 (см. §2). Доказано: замена ёмкости на
   2 (`p390_scratch_diag_cap2.nv`) убирает зависание полностью, тест зелёный.
3. **Реальный, воспроизводимый и НЕ M:N-специфичный баг существует** — но он
   не в отмене, а в том, что второй `read()` **сам по себе** (без всякой
   отмены) никогда не получает собственное завершение от ОС/libuv на Windows,
   если пир закрылся ПОСЛЕ первого успешного частичного чтения на том же
   хендле. Доказано минимальным ПОСЛЕДОВАТЕЛЬНЫМ (без единого `spawn`)
   репро — см. §4. Корень локализован до конкретного механизма
   (Windows AFD zero-byte-`WSARecv`-readiness после `uv_read_stop`+restart),
   но **фикс НЕ дошёл до пригодного к слиянию состояния в бюджете этого
   окна** — см. §5 (что пробовал, почему откатил, что нужно для реального
   фикса).
4. Маркер `[M-supervised-cancel-no-interrupt-parked-accept]` — **другой
   баг, НЕ тот же корень**, этим окном не тронут и не закрыт (см. §6).

**Итог по коду: ВСЕ правки в `compiler-codegen/nova_rt/**` и в vendored
`libuv` за это окно ОТКАЧЕНЫ.** Ни один найденный фикс не прошёл
самопроверку («репро виснет ДО и проходит ПОСЛЕ») — сохранять недоказанный
код в рантайме противоречило бы «нулевой толерантности к багам». В репозитории
остались только два диагностических `.nv`-репро (§2, §4) и этот отчёт.

Пробы «подсунь заведомо негодное»:
- **`timeout: 0.to_millis()`** — **НЕ рескьюит вообще** (протестировано:
  `supervised(timeout: 0.to_millis())` вокруг заведомо висящего `read()` —
  процесс висит все 72с до внешнего `nova test`-таймаута). Причина видна по
  коду: `fibers.h`, `nova_supervised_run_impl` — `_dl_ns = q->deadline_ns`,
  дедлайн-гейт условен на `_dl_ns != 0`. **`0` — тот же сентинел, что и
  «дедлайна нет»**, поэтому `timeout: 0ms` тихо ведёт себя как «без
  таймаута», а не как «истёк немедленно». Это отдельная, не диагностированная
  этим окном находка (возможно намеренный сентинел-дизайн, возможно баг
  UX — не разбирался дальше, вне мандата окна). Файл-проба не сохранён
  (диагностика, не репро окна) — воспроизводится тривиально любым
  `supervised(timeout: 0.to_millis()) { <висящий read> }`.
- **`timeout` больше времени операции**: покрыто имплицитно — КАЖДЫЙ зелёный
  сетевой тест в `std/src/net/*` — это ровно этот случай (операция
  завершается сама, дедлайн не успевает сработать).
- **Вложенные scope с разными дедлайнами**: не тестировано (бюджет окна).
- **Отмена во время частичного чтения**: это ровно сценарий №2 — cancel
  ПРИХОДИТ во время парковки второго read'а и форсит close (см. §3),
  но пары «естественное завершение сломано» это не чинит.

## §2. Диагноз №1 — двойная отправка в канал ёмкости 1 (НЕ баг рантайма)

`docs/plans/repro/p249_second_read_after_partial_hangs.nv` (оставлен как
был, НЕ трогал) устроен так:

```
ro ch_result = Channel.new(1)
with Fail[TimeoutError] = |_e| { ro _ = ch_result.tx.send(-777) } {
    supervised(timeout: 2000.to_millis()) {
        spawn { ...сервер... }
        spawn {
            ...
            ro n2 = match conn.read(buf2) { Ok(k) => k  Err(_) => -2 }  // -2 при cancel
            ch_result.tx.send(n1 * 100 + n2)   // ①
        }
    }
}
ro combined = match ch_result.rx.recv() { ... }
```

Трассировка C-уровня (см. §3 за методом) доказала: на дедлайне 2000мс
`nova_scope_deliver_cancel` форсит close второго read'а — `net_tcp_read`
возвращает `UV_ECANCELED` **в пределах дедлайна**, спавн-фибра **продолжает
исполняться** (по дизайну: `Net`-операции возвращают `Result`, а не бросают
исключение при отмене — «cancel-safe» в докстроке `TcpListener.accept()`
буквально это и означает), доходит до `①` и **успешно** шлёт `100 + (-2) =
98` в канал ёмкости 1.

Параллельно `supervised`-скоуп (все дети реально дожили до конца, дедлайн
всё равно уже сработал — по дизайну Plan 174/D349: «CANCEL-only or
error-free scope → TimeoutError» безусловно) бросает `TimeoutError`,
пойманный `Fail[TimeoutError]`-обработчиком, который **тоже** шлёт в **тот
же** канал (`-777`). Канал ёмкости 1 уже полон (98), никто его не читает
(чтение — `ch_result.rx.recv()` — идёт ПОСЛЕ всего этого блока) →
**блокирующий `send()` виснет навсегда**. Это гонка (какой send придёт
первым — не гарантировано) в **пользовательском .nv-коде теста**, не в
рантайме.

**Доказательство**: `docs/plans/repro/p390_scratch_diag_cap2.nv` — байт-в-байт
та же сцена, только `ch_result = Channel.new(2)` и `rx.recv()` дважды.
Результат: **`PASS: 1 FAIL: 0`, мгновенно**, оба значения (`98` и `-777`, в
любом порядке) успешно вычитываются. Зависаний нет.

**Вывод**: `p249_second_read_after_partial_hangs.nv`'s собственный вывод
(«timeout не рескьюит») — артефакт этой гонки, а не свойство рантайма.
Файл НЕ правил (не мой мандат — репро чужого окна), но интегратору стоит
знать при закрытии находки №4 из `PROGRESS-p249-socks.md`.

## §3. Метод — как доказано, что cancel действительно достаёт второй read

Временная C-инструментация (`fprintf` за `getenv("NOVA_NET_DEBUG")`,
**полностью откачена**, не в дереве) в `net.c`
(`net_tcp_read`/`_nn2_stream_stop_cb`/`_nn2_stream_close_cb`) и в
`nova_sched.h`/`fibers.h` (`nova_scope_deliver_cancel`/
`nova_sched_cancel_all_pending`) показала для
`p249_second_read_after_partial_hangs.nv` при истечении 2000мс:

```
[nn2] nova_scope_deliver_cancel q=... count=0
[nn2] _nn2_stream_stop_cb ENTER s=... stage=0
[nn2] _nn2_stream_stop_cb defer-close s=... loop=...
[nn2] _nn2_stream_close_cb s=... op_scope=0 read_scope=... write_scope=0
[nn2] net_tcp_read WOKE s=... read_done=0 stage=3 read_n=0 read_eof=0 read_err=0 cancel=1
```

`stage=3` = `NN2_CLOSED`, `cancel=1` — второй `read()` реально вернул
`UV_ECANCELED` в рамках дедлайна. Это прямое опровержение исходной жалобы
«timeout не рескьюит второй read».

## §4. Диагноз №2 — реальный баг: второй read не получает собственное завершение

**Минимальное репро БЕЗ единого `spawn`, БЕЗ `supervised`, БЕЗ `Channel`**
(один фибр делает всё последовательно: bind → connect через backlog →
accept → write 1 байт → close → read → read):
`docs/plans/repro/p390_scratch_sequential_no_spawn.nv`.

```
bound port=63902
client connected
server accepted
server wrote 1 byte
server closed
client first read n=1
client second read n=-2      ← только supervised(timeout: 5000ms) спасает; без
                                него — виснет НАВСЕГДА (проверено ≥25с прямым
                                запуском .exe с трассировкой, НОЛЬ событий
                                завершения на хендле клиента)
FAIL: ... supervised-timeout: scope deadline exceeded
```

**Это доказывает, что баг НЕ в M:N/Vela-планировщике**: всё происходит в
ОДНОМ фибре на ОДНОМ OS-потоке, никакого `spawn`/work-steal/cross-worker
wake в принципе не участвует. `nova_sched_park_until`/
`nova_sched_register_pending`/`nova_sched_cancel_all_pending` — весь
Vela-механизм park/wake/cancel — отработал корректно во ВСЕХ прогонах;
единственная сломанная часть — то, что **сама ОС никогда не постит
завершение** для второго `uv_read_start()`-зарегистрированного
zero-byte-`WSARecv` на этом хендле.

### Локализация (C-трассировка libuv/win/tcp.c, откачена)

- Оба чтения (`net_tcp_read` → `uv_read_start` → `uv__tcp_queue_read`)
  корректно ставят zero-byte `WSARecv` в очередь: `result=-1
  wsaerr=997 (WSA_IO_PENDING)` — ОС приняла асинхронную операцию.
- **Первое** чтение получает `uv__process_tcp_read_req ENTER … success=1`
  быстро (данные уже лежат в приёмном буфере ОС) → `_nn2_read_cb nread=1`.
- **Второе** чтение: `uv__tcp_queue_read` тоже возвращает `WSA_IO_PENDING`
  (ОС приняла операцию) — но `uv__process_tcp_read_req` для этого хендла
  **больше никогда не вызывается**, даже когда сервер определённо закрылся
  (`closesocket()` подтверждённо выполнился — прослежено до
  `uv__tcp_close`/`uv__tcp_endgame`/`_nn2_stream_close_cb` для СЕРВЕРНОГО
  хендла отдельно).
- Попытка объяснить это «тем же readable-edge» (что первый `read_cb` глотает
  edge, где уже был готов и trailing EOF) **опровергнута экспериментально**:
  синхронный `MSG_PEEK`-проверка ВНУТРИ `_nn2_read_cb` первого чтения в
  момент его завершения показала `WSAEWOULDBLOCK` (10035) — сервер ЕЩЁ НЕ
  закрылся к этому моменту (`close()` на сервере — fire-and-forget,
  `nova_loop_defer_close`, обрабатывается позже). Значит проблема НЕ
  «тот же edge, частично осушенный» — второй `WSARecv` реально висит через
  ПОЗДНЕЕ наступившее закрытие пира и не видит его.

### Отвергнутая гипотеза-race (тоже проверена и снята)

Подозрение «второй `read()`-фибр не добирается до `conn.close()` из-за
гонки с параллельным закрытием listener'а (32 висящих `AcceptEx`)» —
**опровергнуто**: (а) вариант с отложенным `lst.close()` (после обработки
коннекшена) висит так же; (б) финальный последовательный тест (§4, без
`spawn` вовсе, единственный фибр) висит идентично при полностью
детерминированном порядке (`server closed` печатается строго до первого
`client read`). Раннее наблюдение «сервер не доходит до `close()`»
(в одном из промежуточных прогонов с `println`) оказалось шумом от
инструментации/тайминга, не воспроизвелось повторно и не является частью
итогового диагноза.

## §5. Что пробовал как фикс — и почему откатил

**Попытка**: opportunistic `MSG_PEEK` внутри `_nn2_read_cb` сразу после
успешного чтения данных — если пир УЖЕ закрылся «в том же edge», закешировать
факт (`read_eof_cached`) и на следующем `net_tcp_read()` вернуть `Ok(0)`
немедленно, без парковки.

**Почему не помогло**: см. §4 — в конкретном воспроизводимом случае сервер
ЕЩЁ НЕ закрылся в момент первого `read_cb` (`MSG_PEEK` → `EWOULDBLOCK`),
close наступает ПОЗЖЕ, уже во время парковки второго read'а — а
«peek один раз при первом read_cb» этот более поздний момент не покрывает.
Тест `p390_scratch_sequential_no_spawn.nv` с этим фиксом **всё ещё висел**
(проверено — не помогло).

**Почему не довёл до конца в этом окне**: правильный фикс общего случая
(запаркованный `read()` должен УЗНАТЬ о более позднем закрытии пира, если
сама ОС не постит событие) требует ЛИБО патча vendored `libuv`
(`uv__tcp_queue_read` — заменить zero-byte trick на реальный 1-байтовый
`WSARecv` при restart, что меняет поведение ВСЕХ TCP-чтений на Windows,
широкий блэйк-радиус) ЛИБО polling-fallback через `uv_timer_t`
(периодический `MSG_PEEK` пока запарковано) — оба варианта требуют
осторожного concurrency-дизайна по `mn-coding-conventions.md` (§9 lifetime
таймера, §10/11 порядок wake/cancel, R1-R3 трипваеры ДО опасного кода), а
не спешного патча за оставшееся время окна. Отгружать недоказанный
concurrency-код в `nova_rt/**` — прямое нарушение «нулевой толерантности к
багам»; поэтому весь код отката (§ниже) и НИЧЕГО не осталось в дереве.

**Что осталось в дереве**: НИЧЕГО из фикса. `git diff --stat` в
`compiler-codegen/nova_rt/**` — пусто. `libuv/` — восстановлен побайтно из
`d:\Sources\nv-lang\nova\compiler-codegen\nova_rt\libuv` (тот же коммит, что
и в `nova`, `.git` подмодуля не инициализирован — как и было при старте
этого окна).

## §6. Маркер `[M-supervised-cancel-no-interrupt-parked-accept]` — НЕ тот же корень

Определение маркера (`docs/plans/backlog-followups.md`): `supervised(cancel:
tok)` вокруг `accept()` **БЕЗ вложенного `spawn`** — cancel не прерывает
парковку. Отличия от найденного в этом окне бага:

1. **`cancel: tok` (прямая токен-отмена), не `timeout:`** — разные
   код-пути доставки (`nova_cancel_token_cancel_reason` → `bound_scope`-ветка
   vs scope-дедлайн-гейт в `nova_supervised_run_impl`), хотя оба в итоге
   зовут `nova_scope_deliver_cancel`.
2. **БЕЗ `spawn`** — прямой блокирующий вызов в теле `supervised{}` паркуется
   под `owner_scope`/`owner_slot` (см. `nova_sched_cancel_pending_slot`,
   §221.1 №165) — ОТДЕЛЬНЫЙ путь доставки cancel, специально добавленный
   для этого класса (direct-body-op vs spawned-child).
3. **Симптом другой**: маркер — это «cancel НЕ доставляется вообще»
   (парковка не прерывается доставкой отмены). Найденный в этом окне баг —
   «cancel доставляется и форсит close корректно (§3), но САМО естественное
   завершение операции никогда не приходит от ОС» — ортогональная проблема.

**Вывод**: не закрываю этот маркер этим окном — не тот корень, не
переисследовал его отдельно (вне мандата, другой P1-трек). Владельцу: НЕ
закрывать формулой на основании этого окна.

## §9. Что дальше (для следующего окна, если владелец решит продолжать)

1. Реальный фикс §4 — либо patch vendored `libuv` (`uv__tcp_queue_read`
   restart-path → non-zero-byte probe), либо `uv_timer_t`-based
   polling-fallback в `net.c` (эскиз в §5) — С трипваерами ПЕРЕД кодом
   (mn-coding-conventions §12), с доказательством на ОБОИХ репро (§2 и §4)
   плюс regression на `pingpong_test.nv`/`tcp_test.nv`/`stress_test.nv`
   (чтобы не сломать существующий зелёный трафик).
2. `timeout: 0.to_millis()` ведёт себя как «без дедлайна», не как
   «истёк немедленно» (§1, проба) — стоит отдельного тикета/уточнения в
   спеке (Plan 174/D349), не обязательно баг, но точно не самоочевидное
   поведение.
3. Маркер `[M-supervised-cancel-no-interrupt-parked-accept]` (§6) остаётся
   открытым, отдельный трек.
4. Симметрия `write()`/`connect()` (табл. §1, строки 5/7) — код визуально
   симметричен `read()`, но НЕ переподтверждена отдельным «специально
   сконструированным висящим write/connect»-сценарием — стоит закрыть explicit
   пробой в след. окне, если это в скоупе.
