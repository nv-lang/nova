**Окно:** p248-nocopy. **Модель:** sonnet. **Характер:** ЧИСТАЯ РАЗВЕДКА —

## Шаг 1 — что парсер сегодня принимает после имени типа

Разбор в `compiler-codegen/src/parser/mod.rs`, функция парсинга
type-декларации, модификаторный цикл — **строки 4143–4212** (комментарий над
циклом, 4130–4142, даёт явную канон-таблицу):

| модификатор | форма токена | rank (D241) | где в коде |
|---|---|---|---|
| `consume` | `TokenKind::KwConsume` (настоящее keyword) | 0 | mod.rs:4150–4158 |
| `value` | `TokenKind::Ident("value")` (контекстный, НЕ keyword — backward compat с переменными/полями по имени `value`) | 1 | mod.rs:4200–4210 |
| `priv` / `priv(type)` | `TokenKind::KwPriv` (keyword) + опциональный `(type)` | 2 | mod.rs:4159–4199 |

Цикл (`loop { … break }`) на каждой итерации проверяет ровно эти три случая
по порядку; первый нераспознанный токен — `break` из цикла, дальше идёт
проверка канонического порядка (**строки 4218–4261**, `E_MODIFIER_ORDER`,
если ранги не строго возрастают) и переход к телу типа (`{ ... }` /
newtype-форма / `external`).

**Место для четвёртого модификатора есть** — паттерн однороден: контекстный
`Ident` (как `value`) или новое keyword (как `consume`/`priv`), плюс
собственный rank для проверки канон-порядка. Расширение планировалось
автором кода заранее — комментарий mod.rs:4140–4142: «правило обобщается на
любые будущие type-модификаторы: новый модификатор получает rank … и
автоматически попадает в проверку монотонности».

Отдельно — **атрибуты перед `type`** (`#…`), функция `parse_type_attrs`
(mod.rs:2638–2868). Список ЗАКРЫТ, распознаются РОВНО СЕМЬ имён (не восемь —
см. «Расхождение с брифом» ниже), каждое — свой `match`-рукав:

| атрибут | строка |
|---|---|
| `#from_fields` | mod.rs:2659 |
| `#from_pairs` | mod.rs:2671 |
| `#share` | mod.rs:2683 (D415, `TypeAttr::Share`) |
| `#impl(...)` | mod.rs:2697 |
| `#zero_on_move` | mod.rs:2786 |
| `#pub_to(...)` | mod.rs:2803 |
| `#serde(...)` | mod.rs:2858 |

Всё, что не совпало ни с одним `match`-рукавом — `_ => break` (mod.rs:2863) —
и `#`-токен остаётся непотреблённым в потоке, что на верхнем уровне
декларации вызывает parse error (см. пробу 2 ниже).

**Расхождение с брифом.** Бриф говорит «восемь имён зашиты в парсер». По
факту в `parse_type_attrs` (единственная точка, разбирающая `#`-атрибуты
непосредственно перед `type`) — **семь**. Возможно, имелась в виду другая
точка входа (`parse_contract_attrs`, mod.rs:2380–2623, тоже closed-list —
`verify`/`unverified`/`verify_timeout`/`pure`/`trusted`/`opaque`/`fuel`/
`fn_eval_max_depth`/`test_access` — девять имён, но это атрибуты для `fn`,
не для `type`) либо более широкий подсчёт где-то ещё в файле — не нашёл
восьмого имени именно в type-атрибутах. Фиксирую как факт, не подгоняю под
ожидаемое число.

## Шаг 2 — пробы форм

Все пробы — `docs/plans/repro/p248/<имя>.nv.txt`, каждая в своём каталоге (иначе
`nova check`/`test` тянет ВСЕ файлы каталога как peer-модули — проверено на

(`nova-cli/target/release/nova.exe` из главного репо, компилятор не менялся).

### 2.1 — новый модификатор рядом с `consume`/`value`

`type Handle nocopy value { x int }` (`docs/plans/repro/p248/p1_modifier.nv.txt`):

```
scratch_p248/p1_modifier\probe.nv:3:20: error: expected fn / type / let / const / test, got identifier
3 | type Handle nocopy value { x int }
  |                    ^^^^^
```

`type Handle nocopy { x int }` (без `value`,
`docs/plans/repro/p248/p1b_alone.nv.txt`):

```
scratch_p248/p1b_alone\probe.nv:3:20: error: expected fn / type / let / const / test, got `{`
3 | type Handle nocopy { x int }
  |                    ^
```

Ожидаемо: `nocopy` не входит ни в один из трёх распознаваемых случаев →
цикл ломается на нём → остаток строки (`nocopy value { ... }` /
`nocopy { ... }`) не является валидным продолжением декларации (нет body
сразу после имени/generics без модификатора-триггера тела) → parse error на
уровне «жду следующий item». Диагностика верно указывает точку останова
(колонка 20 = начало `nocopy`), текст читается целиком без искажений.

### 2.2 — атрибут перед типом с выдуманным именем

`#nocopy` + `type Handle { x int }` (`docs/plans/repro/p248/p2_attr.nv.txt`):

```
scratch_p248/p2_attr\probe.nv:3:1: error: expected fn / type / let / const / test, got `#`
3 | #nocopy
  | ^
```

Подтверждено: `nocopy` не входит в закрытый список из семи имён
`parse_type_attrs` → цикл атрибутов сразу `break` на первом же `#` → токен
`#` остаётся на месте «начала item» → parse error того же класса, что и 2.1.

### 2.3 — забирающий тип (`consume value`) + очистка с ПУСТЫМ телом

Три пробы, все с `type Handle consume value { x int }` +
`fn Handle consume @cleanup(_outcome ScopeOutcome) -> () { }` (тело пустое,
по образцу `TcpListener.@cleanup`, `std/src/net/tcp.nv:142`, но без реального
закрытия внутри):

**(a) связывание БЕЗ `consume`** (`ro h = Handle { x: 1 }`,
`docs/plans/repro/p248/p3a_affine_nokw.nv.txt`):

```
scratch_p248/p3a_affine_nokw\probe.nv:9:5: error: [E_CONSUME_KEYWORD_MISSING]
  binding `h` держит consume-обязательную инстанс типа `Handle` — требуется
  keyword `consume` (D180).
9 |     ro h = Handle { x: 1 }
  |     ^^^^^^^^^^^^^^^^^^^^^^
    note: consume-обязательные значения должны быть явно ownership-bound
    через `consume X = …`. Альтернатива: передать в function-параметр для
    view-borrow.
    help: add `consume` keyword: `consume h = …` [machine-applicable]
```

**(b) связывание С `consume`** (`consume h = Handle { x: 1 }`,
`docs/plans/repro/p248/p3b_affine_kw.nv.txt`):

```
ok: scratch_p248/p3b_affine_kw\probe.nv
PASS: 1  FAIL: 0
```

Подтверждает вывод плана дословно: пустая `@cleanup` снимает обязанность
РЕАЛЬНО что-то делать при выходе из scope (компилятор вставит вызов cleanup,
он ничего не делает — и это ОК, никакой ошибки о «пустом cleanup» нет — в
отличие от `consume` без cleanup вообще, см. 2.4), но **ключевое слово
`consume` на связывании остаётся обязательным** — убрать его нельзя, форма
(a) падает всегда независимо от того, что делает cleanup.

### 2.4 — линейный тип (`consume value`) БЕЗ единого consume-метода

`type Handle consume value { x int }`, ни `@close`, ни `@cleanup`, биндинг
`consume h = Handle { x: 1 }` (`docs/plans/repro/p248/p3c_linear_nokw.nv.txt`):

```
scratch_p248/p3c_linear_nokw\probe.nv:3:1: error: [D133-empty-consume]
  type `Handle` помечен `consume` но не имеет ни consume-полей, ни
  consume-методов — добавь хотя бы один consume-method (`fn Handle consume
  @method() -> ()`) либо убери `consume` с type-decl.
3 | type Handle consume value { x int }
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

scratch_p248/p3c_linear_nokw\probe.nv:5:60: error: [D133-not-consumed]
  переменная `h` (тип `Handle`) не consumed до scope-exit. Добавьте вызов
  одного из: объявите consume-метод для этого типа, либо `return h`, либо
  передайте в consume-param.
    help: consume `h` via method (D133-not-consumed quick fix)
    [maybe-incorrect]
```

Оба диагноза бьют СРАЗУ, ещё до попытки что-то потребить — `D133-empty-consume`
безусловен (тип без consume-полей/методов запрещён декларативно), плюс
отдельно `D133-not-consumed` на самой переменной. Подтверждает: голая
линейность (`consume` без `@cleanup`) для атомика невозможна в принципе —
нужен ХОТЯ БЫ пустой `@cleanup`/`@close`, а он всё равно требует ключевое
слово на каждом связывании (67 мест по корпусу — цифра из Ф.1, этой пробой
не пересчитывалась, только подтверждён механизм).

### 2.5 — существует ли уже в языке смысл «нельзя копировать» отдельно от consume

Грепнул `spec/decisions/`, `docs/guide/` на `non-copyable` / `noncopyable`
/ `no-copy` / `move-only` / `~Copyable` / «нельзя копировать» (с
`LC_ALL=C` для русской формы). Единственное совпадение —
`docs/guide/consume-types.ru.md:32`, где «значения нельзя копировать» —
формулировка ВНУТРИ описания consume-типов, не отдельная сущность:

> *Потребляемый тип* — это тип, чьи значения представляют владение
> неразделяемым ресурсом … Значения нельзя копировать, им нельзя создавать
> псевдонимы или неявно отбрасывать; владелец обязан явно их потреблять.

Т.е. «нельзя копировать» в языке сегодня — ВСЕГДА побочный эффект
`consume`-декларации, привязанный к обязанности потребления. Отдельного,
развязанного с consume/`@cleanup`, механизма запрета копирования в спеке и
парсере — НЕТ. Значит запрошенная точка («слабее аффинности») сегодня
буквально не существует ни в каком виде — не только под другим именем.

## Шаг 3 — обобщённая `extern "nova" fn[T Bound] …`: проба

Плану 248 нужно на будущее знать, реален ли путь «свести 21 тип в один
обобщённый» — упирается в то, есть ли у компилятора обобщённая ВНЕШНЯЯ
(compiler-intrinsic) функция с bound по type-set. `spec/decisions/04-effects.md:7466`
(раздел «Неопределённости» D423) говорит прямо: **прецедента нет**
(`@overflowing_add` реализован как D109-класс hardcoded per-name intrinsic,
НЕ через `extern "nova" fn[T Bound] …` декларацию). Грепом по `std/` —
подтверждено: НИ ОДНОГО `extern "nova" fn[T ...] ...` free-function с
bound'ом в корпусе. Единственная смежная форма — `extern "nova" fn OnceCell[T]
@method(...)` (`std/src/runtime/sync.nv:2123` и далее) — это МЕТОД на
обобщённом ТИПЕ (T приходит от типа-носителя, без bound-протокола), не
свободная функция с `[T Bound]`.

**Проба** (`docs/plans/repro/p248/p4_generic_extern_bound.nv.txt`):

```nova
extern "nova" fn[T Ints] nova_probe_double(x T) -> T

test "..." {
    ro r = nova_probe_double(21)
    assert(r == 42)
}
```

**Результат — и это ГЛАВНАЯ находка шага 3, опаснее, чем «не реализовано»:**

- `nova check` — **проходит без единой диагностики** (`ok:`, PASS 1 FAIL 0).
  Парсер и чекер полностью принимают форму, типизируют `T` по `Ints`-бáунду,
  резолвят вызов `nova_probe_double(21)` на конкретный `int`.
- `nova build` / `nova test` — **тоже компилируется и ЛИНКУЕТСЯ без единой
  ошибки/ворнинга**, программа реально запускается. Тест падает не
  compile-error'ом, а **RUN-FAIL**: `assert failed: r == 42` (получили не 42).
- Сгенерированный C (`probe.c`, удалён после пробы — не коммитился, слишком
  большой; текст ниже — точная цитата, зафиксированная во время прогона):

  ```c
  static nova_int nova_fn_12scratch_p24823p4_generic_extern_bound17nova_probe_double____nova_int(nova_int x) {
      /* preempt-check elided: provably-leaf (Plan 143.2) */
  }
  ```

  Тело функции — **буквально пустое**, нет `return` вообще, при
  задекларированном возврате `nova_int`. Это C-UB (функция без `return` в
  non-void функции — неопределённое значение в регистре возврата). clang
  собрал это БЕЗ warning'а в выводе `nova build` (обычный `-Wreturn-type`
  либо подавлен, либо не включён в тулчейне nova). Рантайм-результат
  оказался НЕ 42 (не x*2 и не x) — то есть буквально мусорное значение из
  регистра, ассерт словил это как FAIL, но с тем же успехом могло
  совпасть случайно или дать segfault на другой платформе/оптимизации.

**Вывод шага 3:** обобщённая `extern "nova" fn[T Bound]` — не «не
реализовано» в смысле «отвергается», а гораздо хуже: **принимается на всех
уровнях (парсер → чекер → codegen → линковка) и молча генерирует функцию с
пустым телом** — потому что имя `nova_probe_double` не входит ни в один
hardcoded-intrinsic match компилятора, а checker для `extern "nova"`
деклараций, по-видимому, не требует существования соответствующего
codegen-обработчика на этапе type-check (разрыв между checker-принятием
сигнатуры и codegen-наличием реализации). Для плана 248 это значит: путь
«обобщённый тип + hardcoded intrinsic-функция с bound по `Ints`-подобному
набору» СЕГОДНЯ небезопасен как есть — потребует либо нового
codegen-intrinsic'а per операция (аналогично `@overflowing_add`, НЕ через
голую `extern "nova" fn[T Bound]` декларацию), либо отдельного чекер-энфорса
«extern nova без известного intrinsic-имени = ошибка компиляции», которого
сегодня нет.

## Рекомендация

Из проверенного — **новая точка «нельзя копировать без обязанности
потребления» сегодня не существует НИ В КАКОЙ форме**, ни как модификатор,
ни как атрибут, ни как побочный эффект чего-то ещё. Придётся добавлять
компилятору новую сущность в любом случае — вопрос только в форме записи и
размере правки.

**Минимальна по правке компилятора — атрибут `#nocopy` перед `type`, не
type-level keyword-модификатор.** Обоснование:

1. **Точка расширения уже существует и используется тем же классом задач.**
   `#share` (D415) — тоже голый маркер-вауч без аргументов на type-decl,
   тоже про безопасность разделяемых ручек, добавлен тем же паттерном
   (`parse_type_attrs`, ~15 строк на атрибут) и энфорсится отдельным
   dedicated-модулем (`protocols/share_check.rs`). `#nocopy` ложится в тот
   же слот механически — не нужно трогать модификаторный цикл
   (`mod.rs:4143–4212`) и его canonical-order state machine (D241,
   `mod.rs:4218–4261`), которая рассчитана на composable OWNERSHIP/
   REPRESENTATION/VISIBILITY оси, а не на «свойство без обязанности».
2. **`consume`-модификатор — концептуально неверный слот.** У `consume` rank
   0 закреплён семантикой «must-be-consumed obligation» (D133) — сама его
   позиция в каноне это фиксирует. «Нельзя копировать» — ортогональное
   свойство (Swift 6 держит `~Copyable` отдельно от `~Escapable`/ownership
   ИМЕННО по этой причине, см. план 248). Пихать `nocopy` в ту же
   модификаторную ось означало бы либо путать её с `consume` (риск
   регрессии проверки канон-порядка), либо заводить новый rank в ТОЙ ЖЕ
   строгой last-writer-wins state machine ради свойства, для которого она
   не проектировалась.
3. **Проверка на связывании — самая дешёвая версия того, что уже есть.**
   `E_CONSUME_KEYWORD_MISSING`/`D133-not-consumed` — про ОБЯЗАННОСТЬ,
   `nocopy` нужен только диагноз ПРИ ПОПЫТКЕ скопировать (второй owner на
   ту же ручку), т.е. по силе — подмножество того, что уже делает
   `share_check.rs` для `#share` (там тоже отслеживается, не ушла ли ручка
   в захват без вызова `.share()`). Вероятно, переиспользуем тот же обход
   AST, только с другим триггером диагностики.
4. **Не требует правки D241** (модификаторный canonical-order) — атрибуты и
   type-level модификаторы (`consume value priv`) в парсере — РАЗНЫЕ,
   независимые синтаксические позиции (атрибуты строго ДО `type`,
   `parse_type_attrs` вызывается на mod.rs:1370, до имени и generics;
   модификаторы — ПОСЛЕ имени/generics, mod.rs:4100+). Атрибуты сегодня НЕ
   участвуют в D241-проверке порядка вообще — значит добавление `#nocopy`
   не трогает ни один существующий D-документ про синтаксис модификаторов,
   только добавляет новую строку в перечень атрибутов (по прецеденту
   `#share`/D415).

**Что остаётся за кадром рекомендации (честно) — сама СЕМАНТИКА энфорса.**
Форма записи не решает: (а) где именно ловить «копирование» (присваивание в
новую переменную? передача по значению в параметр без `mut`/`consume`?
поле-в-поле?) — у `#share` этот вопрос решён для ОДНОГО случая (захват в
файбер), для `#nocopy` придётся решать для ОБЩЕГО случая «любая копия»,
это заведомо шире share_check.rs по охвату AST-обхода, даже если механизм
похож. (б) представление «значение внутри, не по указателю»
(`AtomicU32(u32)` вместо `AtomicInt(*())`) — вторая часть выгоды из плана
248 — это ОТДЕЛЬНАЯ codegen-работа (allocation strategy), `#nocopy`-атрибут
сам по себе её не даёт, только делает её БЕЗОПАСНОЙ.
