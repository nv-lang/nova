# PROGRESS — окно p238-paths (план 238, Ф.7: адверсарный вывод полноты границы M:N)

**Модель:** sonnet. **Ветка:** `p238-paths`, worktree `d:/Sources/nv-lang/nova-p238p`.
**Задача:** не чинить, не нумеровать находки — вывести из модели языка ВСЕ пути,
которыми изменяемое (не-`#share`, не read-safe) значение может достичь
параллельного исполнения, и на каждый путь дать пробу с вердиктом.

**Метод:** каждая проба — отдельная директория
(`docs/plans/wip/p238-paths-probes/pNN_.../probe.nv`), проверена
`nova check` (main-репо бинарь `nova-cli/target/release/nova.exe`, HEAD
worktree и main совпадают на `compiler-codegen/src/types/mod.rs`
— `6c47cd21d5c5aacc5d3eebe4998724ec5f29237e` — проверено `git log -1` в обеих
репах перед стартом). Для каждого «не ловится» — контрольный прогон с
намеренно ВПИСАННОЙ посторонней синтаксической ошибкой того же файла (см.
раздел «Контроль честности» ниже): если компилятор репортит именно
ПОСТОРОННЮЮ ошибку и молчит про mut-захват, значит файл дочитан целиком, а
не оборвался раньше — вердикт «не ловится» не является побочным эффектом
краша/тайм-аута/раннего выхода.

### Контроль честности (санити-проверка «не ловится» ≠ «файл не дочитан»)

Для путей №1, №7, №8, №10 в файл дописывалась заведомо ошибочная строка
(`ro bogus int = "not an int"`, `E7301` type-mismatch) и `nova check`
прогонялся заново. Во всех четырёх случаях компилятор репортил РОВНО эту
постороннюю ошибку и НИЧЕГО про mut-захват — то есть анализатор доходит до
конца файла и полноценно резолвит все имена/типы, просто не флагает
конкретно эту гонку. Файлы контроля не сохранены в репо (временные, в
scratchpad сессии) — текст команд и полный вывод приведён выше по каждому
пути.

## Что предлагаю считать полным списком

**Модель, из которой я выводил пути** (не список известных багов, а
структура): любое «виновное» значение (изменяемое, не read-safe, не
`#share`) начинает жизнь в какой-то ОДНОЙ точке создания (литерал замыкания
или `mut`-биндинг) и должно ПЕРЕСЕЧЬ границу файбера, чтобы стать гонкой.
Есть ровно конечный список синтаксических «переходов», которыми значение
может двигаться между точкой создания и точкой пересечения границы:

1. прямой лексический захват на самой границе (`spawn`/`detach`/
   `parallel for`/`supervised`-тело);
2. передача АРГУМЕНТОМ через вызов функции;
3. ВОЗВРАТ значения как результата вызова функции;
4. запись в ПОЛЕ структуры/записи;
5. запись в ЭЛЕМЕНТ коллекции (индекс, `push`, обход `for`);
6. отправка через КАНАЛ;
7. упаковка в вариант СУММЫ (`Option`/`Result`/пользовательский enum);
8. установка как ОБРАБОТЧИК эффекта (`with X = handler {...}`);
9. ПЕРЕПРИВЯЗКА к новому имени (`let b = a`) — синтаксически «переход»
   не пересекает НИКАКУЮ границу сам по себе, но ломает трассировку,
   которая нужна ПОЗЖЕ на любом из переходов 1-8;
10. модуль-level глобальное хранилище — ЗАКРЫТО языком (D184,
    `E_MUT_AT_MODULE_LEVEL`), не существует как путь.

**Вывод по факту проб:** сегодняшний энфорс — это не общий анализ
достижимости, а КОНЕЧНЫЙ allowlist конкретных ОДНОХОПОВЫХ форм переходов
2/5/6/8, подобранных под ранее найденные регрессии (№150/№117/№242/№289/
№167/№168), плюс базовый переход 1. Каждый переход, на который явно
писался код (`spawn_tainted_params_of_fn`/`check_transitive_closure_arg`
для 2; `spawn_tainted_fields_of_module`/`spawn_tainted_method_params_of_
module` для 4/5 с конкретным списком имён мутаторов; `chan.send`-эвристика
для 6; `check_handler_capture` для 8) — ловится ТОЛЬКО пока форма совпадает
буквально с закрытым классом. Всё, что НЕ совпадает буквально — переход 3
(return, вообще без механизма), переход 5 без обёртки-типа (путь №3),
переход 7 (Option/Result, путь №5), переход 9 даже на первом хопе (путь
№10, №8 — курринг это скрытый случай перехода 9 внутри одного `let`),
переход 4/5 нестандартной формой записи (путь №7 — индексное присваивание),
переход 2 глубже одного хопа (путь №2) — проходит МОЛЧА. Правило владельца
(«значение может быть достижимо из >1 файбера ТОЛЬКО если оно неизменяемо,
единолично, либо тип сам гарантирует синхронизацию») сегодня НЕ проверяется
как свойство — оно проверяется как набор из ~6 распознанных форм нарушения
одного и того же более общего факта.

**Честно: полноту вывода 1-10 доказать не могу.** Обоснование, что это
«структура», а не догадка: список 1-10 получен перечислением всех МЕСТ В
ГРАММАТИКЕ, где значение может сменить владельца-переменную или попасть в
составное значение (запись/присваивание/аргумент/возврат/канал/
match-payload/handler-install/module-scope) — это исчерпывающий список
конструкций **связывания** в языке, каждая проверена отдельной пробой.
Но:

- **Комбинации переходов проверены лишь частично.** Путь №11 — измеренная
  комбинация «переход 2 (аргумент, обычный не-fn тип) + переход 4/5 (поле)»
  — тоже течёт. Остальные комбинации (переход 2 глубиной 2 + переход 4 в
  одном пути; переход 9 несколько раз ПОСЛЕ перехода 2 и т.д.) НЕ
  проверены отдельно — по духу путей №2/№7/№8/№10/№11 они, скорее всего,
  текут так же, но это экстраполяция, не измерение.
- **Не проверял дженерики** — обёртка вида `type Box[T] { v T }` с
  `T = fn()->()`, инстанцированная как контейнер замыкания, вместо
  конкретного `Vec[fn()->()]`/`Option[fn()->()]` — структурно похоже на
  путь №5/№7, но не измерено отдельно.
- **Не проверял cross-module/cross-package** формы (импорт функции-фабрики
  из ДРУГОГО файла/пакета) — все пробы однофайловые; граница модуля/пакета
  теоретически может вести себя иначе (более или менее консервативно), не
  измерено.
- **Не проверял пользовательские `effect`-блоки** с собственными методами,
  которые сами прячут замыкание в поле эффект-хендлера (не `with X =
  \|e\|{...}`-литерал, а `effect X { method(...) { ... сохранил в mut-поле
  ... } }`, вызванный ПОЗЖЕ из другого файбера через diспетчеризацию
  эффекта) — родственно путям №1/№5, но именно эту форму не собрал.
- **Не проверял взаимодействие с `consume`** на каждом из путей 2-8 (везде
  использовал `ro`/plain `mut`, не `consume`-передачу) — по духу `consume`
  должен закрывать путь (единоличное владение), но отдельно не измерено.
- Диагностика для путей №167/№168 (`#thread_affine`, узкая граница «через
  closure-значение/метод») пересекается с семейством путей 2/3/9 этого
  окна, но я НЕ строил отдельную пробу конкретно для thread-affine листа —
  она уже задокументирована как честный пробел в D441 §5, я её не
  переоткрывал.
