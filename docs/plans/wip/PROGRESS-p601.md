# Чекпоинт p601-std-tests

Статус на момент записи: оба целевых фикса (№601, №602) зелёные локально, по
одному прогону; предстоит 3x-прогон, sabotage-проверка, фикстуры в

строк из `scripts/guards/std-test-fail.baseline`, коммит.

## №601 — civil_arith_test — ЗАКРЫТО (код готов)

Корень: `digits_at` (`std/src/time/civil/parse.nv`) содержал
`.map_err(|_| FormatMismatch(i, "digit"))` ВНУТРИ `while`-цикла. Компилятор
ломает мутацию `mut`-переменной цикла (`i += 1` перестаёт быть видна на
следующей итерации), если внутри тела `while` создаётся closure-литерал,
захватывающий эту переменную, — ДАЖЕ если closure ни разу не вызывается.
Подтверждено минимальным репро вне civil/parse.nv (`mut i=0; while i<5 { ro
f = |_| "${i}"; ... i += 1 }` — `i` замирает на 0 навсегда). `i` замирает на
первом значении → `while i < pos+n` не сходится → `v = v*10+d` крутится на
одной цифре → integer overflow. Фикс: `match c.to_int() { Ok(x) => x, Err(_)
=> return Err(...) }` вместо `.map_err(closure)` — не создаёт closure внутри
цикла. `nova test std/src/time/civil` — PASS: 1 FAIL: 0 (гонял дважды подряд,
третий прогон ещё нужен для приёмки).

Компиляторный дефект (НЕ починен, зафиксирован для реестра):
`[M-TBD-closure-while-mut-capture]` — closure-литерал внутри `while`,
захватывающий mut-переменную условия цикла, ломает её последующую мутацию,
даже без вызова closure. Воспроизводится вне std.

## №602 — json_test — ЗАКРЫТО (код готов), №505 — уже закрыт ранее

**№505 вердикт: УЖЕ ЗАКРЫТ на main, ДО ветвления p601** — коммит
`bc4857537 std(№505): IndexMap.remove сохраняет порядок; быстрый вариант —
swap_remove` (виден в `git log -- std/src/collections/index_map/core.nv`).
`@remove` сейчас делает сдвиг (сохраняет порядок), `@swap_remove` — быстрый
вариант с честным именем. №602 НЕ пересекается с №505 — ни один из двух
падающих тестов json_test не вызывает `remove`/`swap_remove` вообще (оба —
про `@iter()`/`@keys()` после `insert`). **Один дефект в реестре (№505)
закрыт раньше, второй (№602) — отдельный, независимый корень.**

Корень №602 (НЕ порядок, а ДЛИНА — подтверждено печатью списка ключей):
`JsonObject.@keys()` (`std/src/encoding/json.nv`) — `JsonObject` это `type
JsonObject alias IndexMap[str, JsonValue]`. Компилятор резолвит
`m.keys()` (m: JsonObject) ВСЕГДА против метода АЛИАС-ЦЕЛИ
(`IndexMap[str,JsonValue].@keys()`), ИГНОРИРУЯ собственный
передекларированный `@keys()` на `JsonObject` — подтверждено в
сгенерированном C: вызывается `IndexMap____...method_keys`, никогда
`Nova_JsonObject_method_keys`, независимо от тела фасада. `IndexMap.@keys()`
(реестр №506) возвращала ленивый `IndexKeysIter` — чужеродный тип
присваивался в `[]str`-слот без конверсии → `keys.len()==0` (мусорное
чтение). Печать списка ключей ДО фикса: `len=0`, ключей не напечатано вовсе
(не "3 вместо неверного порядка", а буквально ноль).

Перебрано и отброшено: (а) `.collect()` внутри фасада — либо unreachable
(тот же alias-баг), либо (для не-facade вызовов) ломается ОТДЕЛЬНЫМ
компиляторным дефектом cross-module `.collect()`; (б) `JsonObject` как
настоящий wrapper-struct (не alias) — чинит `.keys()`, но ломает
`JsonValue.Object(m)` в существующих тестах (`json_test.nv:176`,
`jwt.nv:38`), которые полагаются на прозрачную assignability alias↔IndexMap;
(в) `#impl(Index[int,K])` на кастомном `IndexKeysIter` — компилируется, но
`a[i]`-синтаксис в codegen НЕ маршрутизируется через Index-протокол для
пользовательских типов (падает как raw C pointer indexing → сегфолт,
подтверждено).

**Финальный фикс:** `IndexMap[K,V].@keys()` возвращает материализованный
`[]K` напрямую (НЕ ленивый итератор) — единственный путь, где
`keys.len()`/`keys[i]` работают через встроенный (не пользовательский)
codegen-путь для `[]T`, независимо от alias-резолюции. `JsonObject.@keys()`
facade УДАЛЁН из json.nv (был мёртвым кодом — реально никогда не
вызывался). `index_map_test.nv`'s `m.keys().collect() == [...]` продолжает
работать: `Vec[T]` сам имплементирует `Iter[VecIter[T]]`, так что generic
`.collect()`-бланket применяется и к `Vec`-приёмнику (безобидная копия).

**ВНИМАНИЕ ИНТЕГРАТОРУ:** это отменяет часть перформанс-решения №506
(«ленивый keys(), не материализовывать Vec на каждый вызов») — `for k in
m.keys()` снова аллоцирует Vec каждый раз, как ДО №506. Причина —
задокументированная выше цепочка из ДВУХ компиляторных дефектов, которые не
оставляют пути сохранить ленивость keys() и одновременно поддержать
`JsonObject`-фасад. Компромисс сделан в рамках моего мандата (только
std/src/{time/civil,encoding,collections}, без правки компилятора). Нужна
сверка владельца — не заявляю это финальным архитектурным решением, только
рабочим фиксом под текущие ограничения.

Компиляторные дефекты (НЕ починены, зафиксированы для реестра):
- `[M-TBD-alias-method-shadow-cross-module]` — `type X alias Y`: `x.method()`
  резолвится против МЕТОДА `Y`, если `Y` имеет метод с тем же именем, ИГНОРИРУЯ
  собственную передекларацию `X` — даже с разными return-типами (никакой
  compile error, тихий checker/codegen mismatch).
- `[M-TBD-generic-collect-cross-module-empty]` — `.collect()`
  (`fn[I Next[T]] I mut @collect() -> Vec[T]`) даёт пустой `Vec` при вызове
  через границу модуля (facade в одном файле, caller в другом), корректный —
  в пределах одного файла.
- `[M-TBD-user-index-protocol-bracket-codegen-gap]` — `#impl(Index[K,V])` на
  пользовательском типе компилируется, но `a[i]` синтаксис не маршрутизируется
  через него в codegen — падает на raw C pointer indexing.
