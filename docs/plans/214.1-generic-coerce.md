# План 214.1 — generic-`#coerce`: снятие R14 (реестр пар → матчер образцов)

**Статус:** 📋 ДИЗАЙН, СОГЛАСОВАН к исполнению (владелец 2026-07-23: «это было упущение, надо
исправить сейчас»). **Родитель:** [214](214-coerce-attribute.md) / D429.
**Движущий кейс:** [222.3](222.3-extractors.md) — растворение обёрток extractors (`Json[T] → T`),
чинит «некрасивость №1» из [research §3](../research/http-frameworks-gap.md).
**Язык-меняющее** → D429-амендмент (ретракт R14 + новые правила) в том же слиянии, что код.

## 0. Проблема (факт из кода)

`#coerce` реализован: реестр пар — `coerce_pairs: HashMap<String, Vec<CoercePairEntry>>`
(`compiler-codegen/src/types/mod.rs:3255`, строится `collect_coerce_pairs`). Ключ — **имя типа
строкой** → это **словарь-lookup**, а не сопоставление по образцу.

**Следствие (R14, D429):** `#coerce` на generic-форме запрещён явной ошибкой
`E_COERCE_GENERIC_UNSUPPORTED` — «реестр пар это конкретный lookup, не унификация;
параметрические пары взорвали бы R5-однозначность».

**Почему это упущение, а не осознанное ограничение:** пара `Json[T] → T` — **идеальный кандидат
именно view-полосы** (нулевая стоимость: чтение поля; one-level; exact-wins сохраняется).
То есть семантика ровно та, ради которой `#coerce` создавался — упирается лишь в форму реестра.

## 1. Что нужно

```nova
// Целевая декларация (сейчас — E_COERCE_GENERIC_UNSUPPORTED):
#coerce
export fn Json[T] @data() -> T => @data
```
Значение `Json[User]` в позиции, ожидающей `User`, разворачивается автоматически.

## 2. Дизайн: ДВА реестра, не один

Конкретные пары остаются как есть (быстрый lookup, ноль регрессий). Generic-пары — **отдельная
таблица образцов**, проверяемая ТОЛЬКО при промахе конкретной:

```
lookup(I, O):
  1. concrete_pairs[(I,O)]      → hit? вернуть (текущий путь, байт-в-байт как сейчас)
  2. generic_patterns           → унификация образца с (I,O); ноль/один/много (см. R5')
```
`GenericCoercePattern { recv_shape: TypeRef, ret_shape: TypeRef, params: [TypeParam], decl }`.
Унификация — односторонняя (образец против конкретной пары), без рекурсии в глубину:
`Json[?T] → ?T` сопоставляется с `(Json[User], User)`, связывая `?T := User`.

## 3. Правила D429, которые ОБЯЗАНЫ сохраниться (и что с ними делает generic-форма)

| Правило | Как переносится на образцы |
|---|---|
| **R2** zero-cost (view/finalize) | без изменений — проверяется на декларации, до всякой унификации |
| **R3** одна декларация на пару | становится **«один образец на пару-форму»**: два образца, унифицируемых с одной конкретной парой → `E_COERCE_DUPLICATE_PAIR` в точке ПРИМЕНЕНИЯ (не декларации — конфликт может быть неочевиден статически) |
| **R4** один уровень | без изменений; **критично**: `Json[Json[T]]` НЕ разворачивается дважды |
| **R5** exact > coercion + однозначность | **R5'**: сначала конкретные пары, потом образцы; ≥2 подходящих образца → `E_COERCE_AMBIGUOUS` с перечислением |
| **R12** эффект-свобода | без изменений |
| **R13** само-применение исключено | **усиливается**: внутри тела `Json[T] @data()` его же образец не применяется (иначе саморекурсия на любом `T`) |
| **R6** позиции | без изменений |

## 4. Риски (именно они породили R14 — снимаем осознанно, не отменой)

1. **Взрыв однозначности.** Два образца `Json[T]→T` и `Wrapper[T]→T` конфликтуют, только если
   значение одновременно `Json[X]` и `Wrapper[X]` — невозможно (тип один). Реальный конфликт —
   `Json[T]→T` и `Json[T]→str` (разный O): ловится R5' как ambiguity в позиции, где подходят оба.
2. **Стоимость поиска.** Образцы проверяются ТОЛЬКО при промахе конкретного lookup'а — горячий
   путь (str→[]u8) не замедляется. Число образцов мало (единицы).
3. **Термination.** Унификация односторонняя, без рекурсии; R4 (один уровень) не даёт цепочек.
4. **Взаимодействие с перегрузками.** Порядок незыблем: точное совпадение → конкретная пара →
   образец. Пин-тесты обязательны.

## 5. Фазы

- **Ф.0 Спека:** D429 — ретракт R14 (баннер, как у прочих ретрактов), новые R3'/R5'/R13',
  раздел «generic-образцы»; код ошибки `E_COERCE_GENERIC_UNSUPPORTED` уходит.
- **Ф.1 Чекер:** таблица образцов + унификация + двухступенчатый lookup; валидации R3'/R5'.
- **Ф.2 Тесты:** pos (`Json[T]→T` на двух разных `T`; конкретная пара приоритетнее образца);
  neg (два конфликтующих образца → AMBIGUOUS; `Json[Json[T]]` не разворачивается; само-применение
  в теле → type mismatch, не рекурсия); байт-паритет существующих конкретных коэрсий (str→[]u8
  не тронут — обязательный гейт нулевой регрессии).
- **Ф.3** — снятие ограничения в 222.3 (обёртки extractors помечаются `#coerce`).
