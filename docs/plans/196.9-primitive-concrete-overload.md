# 196.9 — Concrete-vs-concrete на РАЗНЫХ примитивах (одно окно для pattern-bound receiver scope)

**Родитель:** [196 — одно окно правды](196-one-truth-closeout.md) (трекер-closeout).
**Статус:** 🔧 В РАБОТЕ (ветка `p196-9-overload`, worktree `nova-p196-9`; в main вливает оркестратор — `types/mod.rs` конкурентно правится семьёй 196.7/196.8).
**Модель:** sonnet.

## Проблема (маркер `[M-primitive-concrete-overload-receiver-dispatch]`, P1, backlog `9b02925d3`)

Два CONCRETE-метода одного имени на РАЗНЫХ примитивах: `int @clamp(lo,hi)` и
`f64 @clamp(lo,hi)` (`std/src/runtime/defaults.nv:180,182`; **i64-оверлоада
НЕТ, бланкета НЕТ**). Вызов `r.clamp(lo,hi)` с ресивером `i64`,
pattern-bound из `Option[T]`-деструктуризации (`match a.checked_add(b) {
Some(r) => r.clamp(lo, hi), ... }`, реальная форма —
`sat_add_i64`, `std/src/time/duration.nv:378-382`, Пункт 10/200) ТИХО
мис-диспатчился в `Nova_f64_method_clamp` — implicit `int64_t<->double`
cast на границе C-вызова (оба скалярны → НЕ CC-FAIL), потеря точности на
i64-крайних значениях → **RUN-FAIL** `Ф.1c/D317: Duration saturating_*
clamps to ±MAX (no wrap)` (`duration.nv:1276`). Найдено попутно при
верификации 196.8 (закрытый маркер `[M-i64-clamp-primitive-collision-
dispatch]`, тот же баг, более ранняя формулировка).

Изолированный чекер-репро подтверждал ассиметрию: голая `ro r i64 = …;
r.clamp(...)` (НЕ pattern-bound) корректно давала `[E_UNKNOWN_METHOD]`; та
же форма ЧЕРЕЗ `match`-pattern-binding — НЕТ диагностики, НЕТ
`resolved_callees`-записи, codegen тихо мис-диспатчил по имени.

## Root cause (ОДИН сайт, чекер: `types/mod.rs::f1_expr_inner`, `ExprKind::Match`)

Файл: `compiler-codegen/src/types/mod.rs`, функция `f1_expr_inner`, ветка
`ExprKind::Match { scrutinee, arms }` (было ~8771-8788, до правки).

Каждый match-арм проверялся так:
```rust
match &arm.body {
    MatchArmBody::Expr(e) => self.f1_expr(e, gs, scope, errors),
    MatchArmBody::Block(b) => self.f1_block(b, gs, scope, errors),
}
```
`scope` — ТОТ ЖЕ HashMap, что и у наружного match-выражения, БЕЗ
расширения именами, которые связывает паттерн арма (`Some(r) => …` не
добавляет `r: i64` в `scope`). Метод-вызов внутри арма (`r.clamp(lo, hi)`)
идёт через `f1_check_call` → `check_instance_overload` (`types/mod.rs:10504`),
у которой ПЕРВАЯ строка:
```rust
let Some(recv_ty) = BoundCtx::infer_arg_ty(obj, scope) else { return; };
```
— `obj` = `Ident("r")`, `scope` не содержит `"r"` → `infer_arg_ty` возвращает
`None` → **вся функция молча возвращается**: НИ диагностики (`[E_UNKNOWN_METHOD]`
из §7.3-гейта, ~10562-10583), НИ записи в `resolved_callees` (~10628/10702) —
для ЛЮБОГО метод-вызова на pattern-bound ресивере, не только `clamp`.

Кодоген уже ИМЕЕТ инфраструктуру для обоих недостающих кусков (по факту
семьи 196.7/196.8, `emit_c.rs`):
- диспетч ЧЕРЕЗ канал `resolved_callees[call_id] → FnDecl.span` (Plan 196.7,
  ~37673-37760) — если канал пуст, кодоген падает в name-keyed
  `method_receivers` last-wins (метод "clamp" зарегистрирован дважды —
  `int` затем `f64` — последний побеждает → всегда `f64`, независимо от
  реального типа ресивера);
- существующий §7.3-гейт `[E_UNKNOWN_METHOD]` для примитивного ресивера без
  подходящего оверлоада/бланкета/билтина (Plan 177 Ф.3, ~10562-10583) — уже
  доказанно корректно работает на НЕ-pattern-bound форме (`ro r i64 = …;
  r.clamp(...)`).

Единственный пробел — `scope` не видел pattern-bound имя ВООБЩЕ на этом
пути. `match_arm_bindings` (Plan 172.1 tally АТОМ 2a, `types/mod.rs:10211`)
уже существует и уже вычисляет ИМЕННО эти биндинги (консервативное
подмножество: `Some(x)`/`Ok(x)`/`Err(x)` при конкретных generic-args
скрутини; одно-payload non-generic user-sum; catch-all) — но использовался
ТОЛЬКО в `infer_match_common_primitive` (материализация ТИПА самого
match-выражения в канал, Plan 172.1 U.4.4), НЕ в основном f1-обходе тела
армов, где реально резолвятся вызовы.

## Фикс (одно окно — читаем ФАКТ существующих каналов, НЕ новый name-guard)

**Слой (а)+(б) — ОДНИМ изменением, чекер (`types/mod.rs`, `f1_expr_inner`,
`ExprKind::Match`):** перед обходом тела арма — расширить (mutable
insert/remove, тот же save/restore паттерн, что уже используется для
closure-arg seeds чуть выше в файле, ~7801-7856) `scope` биндингами
`self.match_arm_bindings(&arm.pattern, scrut_ty.as_ref())`; после обхода —
восстановить. `scope: &mut HashMap<String, TypeRef>` (уже `&mut` в
`f1_expr_inner`), никаких новых полей/каналов не заведено — переиспользуется
ТОЧНО тот же геттер, что 172.1 уже использует для match-типа.

Эффект каскадом, БЕЗ отдельной правки codegen и БЕЗ отдельной "семантики
i64.clamp":
- (а) `check_instance_overload` теперь видит `recv_ty = i64` →
  `type_name = "i64"` → если оверлоад для `i64` СУЩЕСТВУЕТ (метод-таблица
  содержит запись) — пишет `resolved_callees[call_id]` как обычно, и
  кодоген (Plan 196.7 канал, УЖЕ в дереве) диспетчит ПО ЭТОЙ записи, не по
  имени — типобезопасно для ЛЮБОГО метода, не только `clamp`.
- (б) для `i64.clamp` оверлоада НЕТ (только `int`/`f64`) → тот же §7.3-гейт
  (Plan 177 Ф.3, УЖЕ в дереве), что раньше молчал из-за пустого `scope`,
  теперь корректно видит `recv_ty = i64` и эмитит
  `[E_UNKNOWN_METHOD]` — ЧЕСТНАЯ диагностика вместо тихой порчи. i64-оверлоад
  для `@clamp` НЕ добавлен (API-решение владельца — см. Follow-up ниже).

Оба пункта (а)/(б) задачи закрываются ОДНИМ и тем же диффом (не два
отдельных окна) — ровно потому, что 196.7 (channel dispatch) и 177 Ф.3
(unknown-method gate) уже реализованы и ждали только корректного `scope`.

`ExprKind::IfLet` (соседняя ветка, ~8761-8770) имеет ТОТ ЖЕ класс пробела
(`then`-блок обходится с необогащённым `scope`) — НЕ тронут (вне
конкретного репро/маркера; см. Follow-up).

Зона frozen `infer_call_ret_c` (46293-48883) НЕ тронута — фикс целиком в
чекере (`types/mod.rs`), не в `emit_c.rs`. Plan 164 Ф.3 guard тоже не
тронут — не тот слой.

вместо того, чтобы полагаться на случайный f64-каст.

## Follow-up (НЕ в объёме этого окна)

1. `ExprKind::IfLet` имеет ТОТ ЖЕ класс scope-пробела (pattern-bound имя
   не в scope для `then`-блока) — не задет ни одним известным репро/
   маркером сейчас; логировать в backlog как отдельный NOT-YET-OPEN
   потенциальный пробел (симметричный этому, но без живого репро — не
   заводить P1 без наблюдаемого симптома).
2. `i64 @clamp` НЕ добавлен в std — это API-решение владельца (нужен ли
   overload для `i64` вообще, или `sat_add_i64` должен явно `as int`
   кастовать перед `.clamp()`, или использовать другой путь). Данный
   маркер закрывается как "диспетч честный", НЕ как "i64.clamp работает".
   `duration.nv::sat_add_i64` (Пункт 10/200, чужой worktree `nova-p200dur`)
   остаётся блокированным до решения владельца — CC-FAIL сменился на
   компиляторную ошибку `[E_UNKNOWN_METHOD]` вместо RUN-FAIL, что
   разблокирует диагностику, но НЕ саму семантику `sat_add_i64`.

## Амендмент

Не язык-меняющее (checker dispatch/scope-фикс, переиспользует существующий
`[E_UNKNOWN_METHOD]`-гейт и `resolved_callees`-канал; не меняет
поверхностный синтаксис/семантику языка) → D-амендмент НЕ требуется.
