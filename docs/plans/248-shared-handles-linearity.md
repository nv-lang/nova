# План 248 — Разделяемые ручки: линейность вместо честного слова

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-04 (заказ владельца: «выглядит так, что `AtomicInt`
должен быть линейным типом»). **Приоритет:** P1, **ПОСЛЕ тега v0.1** — работа
язык-меняющая и затрагивает весь рантайм.
**Дефекты:** [№337](221.1-bug-sweep.md) (корневой вопрос), смежно [№334](221.1-bug-sweep.md).

## 1. С чего началось

Владелец читал `nova-polaris/src/middleware/log.nv` и спросил про такой код:

```nova
fn fresh_id(cfg AccessLog) -> str {
    mut counter = cfg.counter
    ro n = counter.fetch_add(1) + 1
    "req-${n}"
}
```

Запись в изменяемую копию значения, доступного только для чтения. Вопрос
владельца: «`AtomicInt` — это значение на стеке или в куче? Видимо на стеке, раз
ты присваиваешь `ro` в `mut`. Я лично вижу в этом дыру».

## 2. Что установлено пробами (факты, не гипотезы)

**`AtomicInt` — ручка на кучу, а не значение.** Объявление
(`std/src/runtime/sync.nv:1061`):

```nova
#stable(since = "0.1")
#share
export type AtomicInt(*())
```

Newtype поверх сырого указателя. Копия копирует **указатель**, поэтому:

- мутация через `mut`-копию, снятую с `ro`-значения, **видна через оригинал** —
  измерено: два вызова дают 1 и 2;
- у обычного поля копия независима — измерено: два вызова дают 1 и 1.

**`ro` защищает привязку, а не то, на что она указывает.** Это внутренняя
изменяемость, как атомик за ссылкой в Rust. Разница в видимости: в Rust
указатель виден в типе, в Nova спрятан за именем типа.

**В std дисциплина соблюдена.** Все шесть указательных newtype несут `#share`:
`AtomicInt`, `AtomicUint`, `AtomicBool`, `Mutex`, `RwLock`, `CancelToken`; у
части — письменный аудит вауча в доккомментарии.

**Но компилятор пометки НЕ ТРЕБУЕТ.** Пользовательский `type Handle(*())` без
`#share` объявляется и проходит проверку (проба 2026-08-04). Значит гарантия
держится на дисциплине авторов, а не на языке.

## 3. Предложение владельца и почему оно верно

Сделать `AtomicInt` (и родню) **линейным типом**. Линейное значение нельзя
тихо скопировать — значит `mut counter = cfg.counter` перестанет быть
возможным, и утечка через копию исчезает **по построению**, а не потому, что
автор не забыл пометку.

**Прецедент в языке уже есть, и ровно этот.** `TcpStream`
(`std/src/net/tcp.nv:39`):

```nova
export type TcpStream consume value { priv handle *(), priv rc AtomicInt }
```

Линейная ручка + явный `@share()`, заводящий второго владельца через счётчик
ссылок; сокет закрывается последним владельцем. То есть «линейная ручка с
явным разделением» — **принятая в Nova форма**, и разделяемые примитивы под
неё просятся.

Выигрыш не только в закрытии дыры: разделение становится **видимым в коде**.
Сейчас `mut counter = cfg.counter` выглядит как копия числа, а на деле заводит
второго владельца общей ячейки — читатель этого не видит.

## 4. Цена, названная честно

- Атомики и мьютексы разбросаны по всему рантайму и std; перевод — крупная
  миграция, каждое место разделения станет явным вызовом.
- Частый случай «счётчик внутри конфига, переданного по чтению» станет
  заметно шумнее — ровно тот, с которого начался разговор.
- Линейность в контейнерах уже работает (связка К1, 2026-08-04), но
  `Vec[AtomicInt]` и подобные места придётся пересматривать.
- Работа язык-меняющая: без D-амендмента не уходит.

**Поэтому — после тега.** Делать миграцию такого объёма за день до релиза
нельзя; заслон и дисциплина std держат ситуацию до тех пор.

## 5. Три вопроса, которые решаются вместе

Они об одном и том же и порознь дадут несогласованный результат.

**В.1 — линейность разделяемых примитивов.** Перевести `AtomicInt`,
`AtomicUint`, `AtomicBool`, `Mutex`, `RwLock`, `CancelToken` на форму
«линейный + явный `@share()`», как `TcpStream`? Или ограничиться частью
(например, только мьютексами, где владение и так подразумевается)?

**В.2 — обязательность пометки у указательных newtype.** Должен ли
`type X(*())` ТРЕБОВАТЬ `#share` либо иной явной пометки «это ручка»? Сегодня
не требует, и пользовательский FFI-код может завести немаркированную ручку.
Если В.1 решается положительно, В.2 может закрыться сам собой: линейность
станет обязательной для этой формы.

**В.3 — где стоит настоящий энфорс.** Сегодня `#share` проверяется на захвате
в файбер, а не на копировании из `ro`. Достаточно ли этого? Если да — В.2
теряет остроту, и вопрос сводится к документированию. Если нет — нужен второй
энфорс, и тогда В.1 предпочтительнее как более общий.

## 6. Порядок работ

**Ф.1 — разведка.** Пересчитать по корпусу (std, examples, пять пакетных реп):
сколько мест копируют разделяемую ручку, сколько из них станут явным
`share()`, сколько окажутся внутри цепочек только для чтения (как `fresh_id`,
где обход и понадобился). Без этой цифры решение по В.1 принимать вслепую.

**Ф.2 — D-решение владельца** по В.1/В.2/В.3, одним блоком. Записывается
амендментом к D415 (`#share` vouch) и, при положительном В.1, новым D на форму
разделяемого примитива.

**Ф.3 — реализация**, только после Ф.2. Волна плана 196: энфорс в чекер-канал,
`emit_c` не наращивать.

**Ф.4 — миграция корпуса** по числам из Ф.1, с прогоном полного гейта и смоков
пакетов.

## 7. Что НЕ входит

- Правка `fresh_id` в полярисе — там обход **необходим** по правилу цепочки
  lvalue (проверено окном p-battery-doors: прямая форма даёт `E_PARAM_NOT_MUT`,
  а пометка `mut` на параметре — `E_READONLY_COERCE`, потому что `cfg` идёт
  цепочкой из трёх параметров только для чтения). Комментарий там уже
  исправлен на правдивый; см. [№334](221.1-bug-sweep.md).
- Смежная шероховатость эргономики, вскрытая тем же разбором: чтобы изменить
  разделяемую ячейку внутри значения, переданного по цепочке только для
  чтения, приходится делать локальную копию — семантика ячейки этого не
  требует, требует правило цепочки. Отдельный вопрос; если В.1 пройдёт,
  переформулируется.
