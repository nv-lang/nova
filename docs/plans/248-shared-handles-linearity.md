# План 248 — Разделяемые ручки: линейность вместо честного слова

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-04 (заказ владельца: «выглядит так, что `AtomicInt`
должен быть линейным типом»). **Приоритет:** P1, **ДО тега v0.1** (пересмотрено 2026-08-04 по принципу
«ужесточать до релиза, ослаблять после» — см. план 221 и раздел «Пересмотр
срока» в конце). Работа язык-меняющая и затрагивает весь рантайм, поэтому при
нехватке времени ставится грубый заслон, а точность добирается после тега.
**Дефекты:** [№337](221.1-bug-sweep.md) (корневой вопрос), смежно [№334](221.1-bug-sweep.md).

## 1. С чего началось

Владелец читал `nova-polaris/src/middleware/log.nv` и спросил про такой код:

```nova
fn fresh_id(cfg AccessLog) -> str {
    mut counter = cfg.counter
    ro n = counter.fetch_add(1) + 1
    "req-${n}"
}
```

Запись в изменяемую копию значения, доступного только для чтения. Вопрос
владельца: «`AtomicInt` — это значение на стеке или в куче? Видимо на стеке, раз
ты присваиваешь `ro` в `mut`. Я лично вижу в этом дыру».

## 2. Что установлено пробами (факты, не гипотезы)

**`AtomicInt` — ручка на кучу, а не значение.** Объявление
(`std/src/runtime/sync.nv:1061`):

```nova
#stable(since = "0.1")
#share
export type AtomicInt(*())
```

Newtype поверх сырого указателя. Копия копирует **указатель**, поэтому:

- мутация через `mut`-копию, снятую с `ro`-значения, **видна через оригинал** —
  измерено: два вызова дают 1 и 2;
- у обычного поля копия независима — измерено: два вызова дают 1 и 1.

**`ro` защищает привязку, а не то, на что она указывает.** Это внутренняя
изменяемость, как атомик за ссылкой в Rust. Разница в видимости: в Rust
указатель виден в типе, в Nova спрятан за именем типа.

**В std дисциплина соблюдена.** Все шесть указательных newtype несут `#share`:
`AtomicInt`, `AtomicUint`, `AtomicBool`, `Mutex`, `RwLock`, `CancelToken`; у
части — письменный аудит вауча в доккомментарии.

**Но компилятор пометки НЕ ТРЕБУЕТ.** Пользовательский `type Handle(*())` без
`#share` объявляется и проходит проверку (проба 2026-08-04). Значит гарантия
держится на дисциплине авторов, а не на языке.

## 3. Предложение владельца и почему оно верно

Сделать `AtomicInt` (и родню) **линейным типом**. Линейное значение нельзя
тихо скопировать — значит `mut counter = cfg.counter` перестанет быть
возможным, и утечка через копию исчезает **по построению**, а не потому, что
автор не забыл пометку.

**Прецедент в языке уже есть, и ровно этот.** `TcpStream`
(`std/src/net/tcp.nv:39`):

```nova
export type TcpStream consume value { priv handle *(), priv rc AtomicInt }
```

Линейная ручка + явный `@share()`, заводящий второго владельца через счётчик
ссылок; сокет закрывается последним владельцем. То есть «линейная ручка с
явным разделением» — **принятая в Nova форма**, и разделяемые примитивы под
неё просятся.

Выигрыш не только в закрытии дыры: разделение становится **видимым в коде**.
Сейчас `mut counter = cfg.counter` выглядит как копия числа, а на деле заводит
второго владельца общей ячейки — читатель этого не видит.

## 4. Цена, названная честно

- Атомики и мьютексы разбросаны по всему рантайму и std; перевод — крупная
  миграция, каждое место разделения станет явным вызовом.
- Частый случай «счётчик внутри конфига, переданного по чтению» станет
  заметно шумнее — ровно тот, с которого начался разговор.
- Линейность в контейнерах уже работает (связка К1, 2026-08-04), но
  `Vec[AtomicInt]` и подобные места придётся пересматривать.
- Работа язык-меняющая: без D-амендмента не уходит.

**Срок пересмотрен 2026-08-04 — ДО тега** (см. раздел в конце): это
ужесточение, а ужесточения после релиза ломают пользователям сборку. При
нехватке времени — грубый заслон вместо полной миграции.

## 5. Три вопроса, которые решаются вместе

Они об одном и том же и порознь дадут несогласованный результат.

**В.1 — линейность разделяемых примитивов.** Перевести `AtomicInt`,
`AtomicUint`, `AtomicBool`, `Mutex`, `RwLock`, `CancelToken` на форму
«линейный + явный `@share()`», как `TcpStream`? Или ограничиться частью
(например, только мьютексами, где владение и так подразумевается)?

**В.2 — обязательность пометки у указательных newtype.** Должен ли
`type X(*())` ТРЕБОВАТЬ `#share` либо иной явной пометки «это ручка»? Сегодня
не требует, и пользовательский FFI-код может завести немаркированную ручку.
Если В.1 решается положительно, В.2 может закрыться сам собой: линейность
станет обязательной для этой формы.

**В.3 — где стоит настоящий энфорс.** Сегодня `#share` проверяется на захвате
в файбер, а не на копировании из `ro`. Достаточно ли этого? Если да — В.2
теряет остроту, и вопрос сводится к документированию. Если нет — нужен второй
энфорс, и тогда В.1 предпочтительнее как более общий.

## 6. Порядок работ

**Ф.1 — разведка.** Пересчитать по корпусу (std, examples, пять пакетных реп):
сколько мест копируют разделяемую ручку, сколько из них станут явным
`share()`, сколько окажутся внутри цепочек только для чтения (как `fresh_id`,
где обход и понадобился). Без этой цифры решение по В.1 принимать вслепую.

**Ф.2 — D-решение владельца** по В.1/В.2/В.3, одним блоком. Записывается
амендментом к D415 (`#share` vouch) и, при положительном В.1, новым D на форму
разделяемого примитива.

**Ф.3 — реализация**, только после Ф.2. Волна плана 196: энфорс в чекер-канал,
`emit_c` не наращивать.

**Ф.4 — миграция корпуса** по числам из Ф.1, с прогоном полного гейта и смоков
пакетов.

## 7. Что НЕ входит

- Правка `fresh_id` в полярисе — там обход **необходим** по правилу цепочки
  lvalue (проверено окном p-battery-doors: прямая форма даёт `E_PARAM_NOT_MUT`,
  а пометка `mut` на параметре — `E_READONLY_COERCE`, потому что `cfg` идёт
  цепочкой из трёх параметров только для чтения). Комментарий там уже
  исправлен на правдивый; см. [№334](221.1-bug-sweep.md).
- Смежная шероховатость эргономики, вскрытая тем же разбором: чтобы изменить
  разделяемую ячейку внутри значения, переданного по цепочке только для
  чтения, приходится делать локальную копию — семантика ячейки этого не
  требует, требует правило цепочки. Отдельный вопрос; если В.1 пройдёт,
  переформулируется.

## Ф.1 ИСПОЛНЕНА 2026-08-05 (окно p248-recon) — ЧИСЛА ДЛЯ РЕШЕНИЯ

**Заражение — 5 новых линейных типов, не десятки.** Транзитивное замыкание от
23 носителей дало 10 имён, после вычитания: `TcpStream`/`TlsStream`/`WebSocket`
УЖЕ линейны (не новая цена), `ServerResponse` — ложное срабатывание разбора
(поле хранит подпись замыкания, а не ручку). Остаётся **6 типов, все в
nova-polaris, глубина 1**. Из них `AccessLog` УСТРАНИМ переносом счётчика в
замыкание, которое `@middleware()` и так строит (образец — `ratelimit.nv`);
заодно снимается обход из №334 и не требуется ни одного явного разделения.
**Итог: 5 типов.** В nova-http, nova-tls, nova-compress, nova-bignum —
заражения НОЛЬ, они этих примитивов не используют вовсе.

**Места, где разделение реально нужно:** `OrderLog` (12 независимых замыканий),
`SharedLog` (2), `RejectLog` (захват в цикл порождения на соединение — рядом,
тремя строками ниже, уже стоит такой же явный вызов разделения). У
`BucketTable` и `AccessLog` после переноса — скорее всего не нужно.

**Прецедент `TcpStream`:** 7 реальных вызовов разделения, запись читается
естественно, не многословна.

**ГЛАВНОЕ — ЦЕНА НЕ В СИНТАКСИСЕ (раздел E, проба сделана и откачена).**
Перевод в линейный тип упирается в два требования компилятора:

1. **линейный тип обязан иметь метод потребления** — а у этих 23 закрывать
   нечего, они не ресурсы (диагностика `D133-empty-consume`);
2. **ключевое слово на каждом связывании** — измерено **67 мест** по корпусу
   (`E_CONSUME_KEYWORD_MISSING`).

Частично лечится «очисткой, которая не падает» (подтверждено на существующем
`TcpListener`), но требование ключевого слова остаётся. Смена представления
реальна: порождённый C меняется с голого указателя на структуру с полем —
однако рабочий прецедент уже есть в том же файле (семейство `MutexGuard`).

**Вывод для решения владельца:** цена не в числе типов (5), а в 67 местах
связывания и в том, что линейность здесь работает не по назначению — она про
«обязан быть потреблён», а нам нужно «нельзя молча копировать». Возможно,
правильнее не линейность, а отдельный запрет копирования без обязанности
потребления. Это вопрос владельцу.


## ЗАПРЕТ КОПИРОВАНИЯ ДАЁТ НЕ ТОЛЬКО БЕЗОПАСНОСТЬ, НО И ПРОИЗВОДИТЕЛЬНОСТЬ

**Вопрос владельца 2026-08-05:** зачем атомику выделять память, почему не
`AtomicU32(u32)` с изменением самого значения на месте?

**Почему сегодня выделяется.** Потому что значения в языке КОПИРУЮТСЯ. Будь
атомик числом внутри, при передаче или присваивании копировалось бы само
число — каждый файбер получил бы СВОЙ счётчик, и атомарность стала бы
бессмысленной: операции атомарны, но над разными ячейками. Указатель решает
это грубо — копируется указатель, ячейка одна. Цена: выделение на каждый
атомик и переход по указателю на каждой операции.

**Что даёт запрет копирования.** Как только копирование запрещено,
`AtomicU32(u32)` становится возможен: значение лежит ВНУТРИ содержащего
объекта, операции идут по месту, выделения нет, косвенности нет, счётчик
попадает в ту же строку кэша, что и соседние поля.

Условия выполнены: сборщик не двигает объекты (наш — не двигает), выравненность
для атомарной операции обеспечивает сишный компилятор для полей структуры.

### Как это сделано в других языках

| язык | представление | чем запрещено копирование |
|---|---|---|
| **Swift 6** | inline, без выделения | **тип некопируемый** (`~Copyable`) — ровно предложение владельца |
| **Rust** | inline (`UnsafeCell` внутри) | тип не `Copy`; делятся ссылкой, `Sync` пускает её между потоками; выделение только когда нужно разделяемое ВЛАДЕНИЕ |
| **C++** | inline (`std::atomic<T>`) | копирующий конструктор удалён |
| **C#** | поля вообще без обёртки — `Interlocked` работает по ссылке на поле | обёртки нет, копировать нечего |
| **Go** | inline-структура, используется по указателю | только соглашение `noCopy` + внешний анализатор, компилятор НЕ запрещает |
| **Java** | ОБЪЕКТ НА КУЧЕ на каждый атомик | никак; для обхода есть отдельный механизм атомарных операций по полю |

**Вывод:** мейнстрим — значение внутри, без выделения, а копирование запрещено
ТИПОМ. Единственный, кто выделяет объект на каждый атомик, — Java, и она же
предоставляет обходной механизм, чтобы этого избегать. Сегодняшняя Nova ближе
всего к Java, то есть к самому слабому варианту.

Swift 6 — прямой прецедент предложения владельца: атомик там inline и
**некопируемый**.

**Следствие для решения:** переход на запрет копирования — не только
ужесточение ради безопасности, но и снятие выделения памяти и косвенности с
каждой атомарной операции. Аргумент «дорого» разворачивается в обратную
сторону.

**Оговорка про замки.** Мьютекс/RwLock/повторно-входимый так не переделать:
там не число, а объект операционной системы с инициализацией и уничтожением.
Они остаются ручками, и им линейность нужна по прямому назначению — заодно
чинится утечка [№348](221.1-bug-sweep.md).


## ВЫВОД ФАЗЫ (2026-08-05): 23 типа — это ДВЕ РАЗНЫЕ ГРУППЫ, а не одна

Главный результат разбора: носители пометки разделяемости неоднородны, и
решение для них тоже должно быть разным.

> **ПОПРАВКА ПО ФАКТУ 2026-08-05 (интегратор, пересчёт по исходникам).**
> Разбивка ниже неверна в числах, и это меняет объём работ. Фактический
> состав 23 носителей пометки (`grep '^export type' std/src/runtime/sync.nv`
> + один в `prelude/concurrency.nv`):
>
> - **атомики — 11, не 20:** `AtomicI64/I32/I16/I8`, `AtomicU64/U32/U16/U8`,
>   `AtomicInt`, `AtomicUint`, `AtomicBool`. Именно они переводятся на
>   значение внутри; `AtomicU32` **уже существует** под этим именем, менять
>   надо представление, не имя;
> - **замки на несобираемой памяти — 3:** `Mutex`, `RwLock`,
>   `ReentrantMutex` (`nova_alloc_uncollectable`, строки 909/1169/1569
>   `nova_rt/sync_primitives.h`);
> - **прочие примитивы — 8, В ПЛАНЕ НЕ РАССМАТРИВАЛИСЬ ВОВСЕ:** `Barrier`,
>   `Condvar`, `CountDownLatch`, `Lazy[T]`, `Once`, `OnceCell[T]`,
>   `Semaphore`, `WaitGroup`. Память под сборщиком (`nova_alloc`), но
>   `WaitGroup` и `Once` заводят внутри себя мьютекс
>   (`nova_mutex_init`, строки 1815/1927) — то есть по составу они ближе к
>   замкам, чем к атомикам;
> - **токен отмены — 1.**
>
> Итого 11 + 3 + 8 + 1 = 23. Решение «запрет копирования без обязанности
> потребления» выведено для атомиков и токена (12 типов), а для восьми
> прочих НЕ проверялось — их надо разобрать отдельно, прежде чем
> распространять на них вывод фазы.

### Группа 1 — 21 тип: атомики (20) + токен отмены

Память под сборщиком (`nova_alloc`), **освобождать нечего**. У токена отмены
несобираемое выделение пробовали и ОТКАЗАЛИСЬ (заметка в `nova_rt/fibers.h`
рядом с `nova_cancel_token_new`).

Им нужен **только запрет копирования**, без обязанности потребления —
ни линейность, ни аффинность не подходят: обе добавляют обязанность, которой
у них нет.

Дополнительно, по вопросам владельца 2026-08-05:

- **Свести в ОДИН обобщённый тип** вместо 21 копии. Прецедент рядом, в том же
  файле: `OnceCell[T]` — обобщённый, с пометкой разделяемости и внешними
  методами. Бáунды по набору типов существуют (D310).
- **Держать значение ВНУТРИ, а не по указателю.** Тогда исчезают выделение
  памяти и косвенность на каждой операции; безопасность приходит вместе с
  ускорением. Возможно ровно потому, что копирование запрещено — иначе каждая
  копия стала бы отдельным счётчиком.
- **`extern "nova"` — не выход в чужой код**, а привязка к тому, что компилятор
  порождает сам (`nova_fn_`-префикс). Выбор инструкции по ширине при
  специализации — его собственная кухня, препятствия нет. НО: обобщённой
  внешней функции с бáундом по набору типов ещё никто не писал — при работе
  над арифметикой переполнения от этой конструкции отказались именно из-за
  отсутствия прецедента (`04-effects.md:7466`). Проверить пробой.

### Группа 2 — 3 типа: мьютекс, блокировка чтения-записи, повторно-входимый

Несобираемая память + объект операционной системы, **никто не освобождает** —
утечка [№348](221.1-bug-sweep.md). Это настоящие ресурсы: **линейность
подходит по прямому назначению** и попутно чинит утечку.

### Отдельно — каналы

Полностью вне системы проверок ([№347](221.1-bug-sweep.md)): объявлены внешним
типом, проверка разделяемости их не видит. Лечится планом
[244](244-channel-in-nova.md), когда канал станет обычным типом.

### Чего не хватает языку — ОДНА новая сущность

Точка слабее аффинности: **копировать нельзя, но ни потреблять, ни прибирать
не нужно**. Сегодня такой точки нет: линейность требует потребления,
аффинность (забирающий тип + объявленная очистка) требует очистки.

Мировой прецедент — Swift 6: атомик там inline и **некопируемый**
(`~Copyable`), причём это свойство сознательно ОТДЕЛЕНО от механизмов
владения. Форма записи для Nova — проверяется пробой (окно p248-nocopy),
выдумывать её запрещено.


## ФОРМА «НЕЛЬЗЯ КОПИРОВАТЬ» — вердикты компилятора (окно p248-nocopy, 2026-08-05)

**Что парсер принимает в позиции модификатора типа:** РОВНО ТРИ —
`consume`, `value`, `priv` (`parser/mod.rs:4143-4212`), со строгим
каноническим порядком. Место для четвёртого предусмотрено комментарием
(`:4140-4142`).

**Атрибуты перед `type`:** закрытый список из **семи** имён — `from_fields`,
`from_pairs`, `share`, `impl`, `zero_on_move`, `pub_to`, `serde`
(`parse_type_attrs`, `:2638-2868`). *Уточнение: интегратор ранее называл
восемь — это был список атрибутов ФУНКЦИЙ, а не типов; списки разные.*

| форма | вердикт |
|---|---|
| `type X nocopy value {…}` | ошибка разбора — ломает модификаторный цикл |
| `type X nocopy {…}` | ошибка разбора |
| `#no_copy` перед `type` | ошибка разбора — нет в семи именах |
| `consume value` + очистка с ПУСТЫМ телом | обязанность действовать снята; **требование ключевого слова при связывании ОСТАЁТСЯ** (`E_CONSUME_KEYWORD_MISSING`) |
| голый `consume value` без метода потребления | `D133-empty-consume` + `D133-not-consumed` сразу |

**Существующего смысла «нельзя копировать», развязанного с обязанностью
потребления, в языке НЕТ** — проверено грепом по спеке и доке; единственное
упоминание описывает это как побочный эффект обязательства.

**Рекомендация окна:** атрибут (примерно 15 строк в разборе атрибутов) дешевле
нового модификатора — не задевает строгую машину канонического порядка
модификаторов (D241) и переиспользует существующий образец выделенного
модуля-проверки (`protocols/share_check.rs` — ориентир масштаба самого
энфорса, не атрибута).

**Зацепка для дизайна:** среди семи атрибутов типа уже есть `zero_on_move` —
то есть атрибуты, влияющие на семантику перемещения, в языке уже водятся.
Проверить, не ближе ли искомое к нему, чем к `#share`.

**Побочная находка, заведена как [№351](221.1-bug-sweep.md):** обобщённая
внешняя функция с бáундом по набору типов принимается молча и порождает пустое
тело — неопределённое поведение вместо ошибки. Это прямо блокирует идею свести
21 атомик в один обобщённый тип.


## ПОВОРОТ «УНИФИКАЦИЯ КОПИРОВАНИЯ» — ИССЛЕДОВАН И ОТКЛОНЁН (окно p248-copyflip, 2026-08-05)

Владелец предложил: связывание всегда даёт второе имя, копия всегда явная
через `.clone()`, дешёвая неявная копия — по согласию пометкой (образец
`Duration`). Мотив — сегодня одна запись `ro b = a` значит две противоположные
вещи в зависимости от того, объявлен тип значением или живёт в куче.

### Ключевая находка: унификация УЖЕ в основном реализована

Не единым решением, а связкой существующих механизмов — установлено чтением
`types/mod.rs` и пробами:

- протокол клонирования (D230) — явная копия уже есть;
- запрет пере-связывания `ro`→`mut` для не-полностью-стековых типов
  (амендмент D246 от 2026-07-23) — молчаливое отмывание уже блокируется;
- структурная проверка «полностью стековое значение» — это фактически
  `#copy` БЕЗ пометки автора, выводится из состава полей;
- намеренное исключение для разделяемых типов (D415).

**Сценарий №337/№334 (`mut c = cfg.counter`) оказался НЕ ДЫРОЙ**, а работающим
по замыслу исключением: для разделяемых типов отмывание разрешено осознанно —
делить их и есть их назначение. Проба интегратора проходила именно поэтому.

### Что действительно сломано — две узкие дыры, обе шире 23 ручек

1. **Отмывание через поле проверяется на ОДИН шаг проекции.** Два и более
   (`cfg.inner.counter`) проходят молча — false-negative задокументирован в
   самом коде, подтверждён пробой.
2. **Сахар `[]T` не распознаётся проверкой так же, как `Vec[T]`** — копия
   записи-значения с полем `[]int` РАЗДЕЛЯЕТ изменения с оригиналом,
   подтверждено сборкой и прогоном. Тот же тип с `Vec[T]` корректно
   блокируется существующей фикстурой. Заведено как
   [№352](221.1-bug-sweep.md), класс К1.

### Гипотеза интегратора опровергнута

Предположение «сменить у 23 ручек скобки объявления» пробой отклонено как
неэффективное: расшаривание идёт через содержимое указателя, а не через
обёртку — смена формы объявления не меняет ничего.

### Числа

Деклараций типов вне схемы «запись = куча = второе имя» по корпусу — около
317. Реальных мест, где сегодня происходит отмывание через проекцию поля, —
порядка 6-8, а не 67, как в измерении для линейности 23 ручек.

### Сравнение языков

Ни один проверенный язык со сборщиком мусора (Swift, C#, Go, Java, Kotlin,
Pony; Rust не в счёт — без сборщика) не сочетает «выбор значение/ссылка по
типу» с «обязательным `.clone()` даже для значения». Комбинация
беспрецедентна — это не запрет, но требует объяснения, почему мы первые.

### ВЕРДИКТ: не унифицировать

Сделать две прицельные правки в существующем канале — расширить проверку
отмывания на N шагов проекции и нормализовать `[]T` к `Vec[T]`. Это закрывает
**строго больше подтверждённого риска**, чем оба обсуждавшихся варианта, без
миграции корпуса и без новых языковых сущностей.


## ВЕТКА «`#no_copy`» ЗАКРЫТА 2026-08-05 — ПРИЗНАК НЕ НУЖЕН

Ветка велась несколько часов: искали форму записи для признака «нельзя
копировать», проверили модификатор, атрибут и забирающий тип с пустой
очисткой (окно p248-nocopy, вердикты в плане выше).

**Итог: признак не нужен, случая применения не осталось.** Основание —
вердикт окна p248-copyflip:

- где копировать нельзя, **уже запрещено ВЫВОДОМ**: структурная проверка
  «полностью стековое значение» решает по составу полей, а запрет
  пере-связывания `ro`→`mut` для не-полностью-стековых типов действует с
  амендмента D246 от 2026-07-23. То, что предлагалось писать пометкой,
  компилятор выводит сам;
- где копировать можно — **разрешено осознанно**: 23 ручки помечены
  разделяемыми, и делить их есть их назначение (D415). Запрещать нечего.

**Вместо признака — две прицельные правки** (обе шире и дешевле):
расширить проверку отмывания с одного шага проекции на N и нормализовать
сахар `[]T` к `Vec[T]` в структурной проверке. Вторая закрывает
подтверждённую прогоном незвучность — [№352](221.1-bug-sweep.md).

**Что вернуло бы вопрос:** появление типа, который НЕ разделяемый, НЕ
стековый, и при этом не должен копироваться по причинам, невыводимым из
состава полей. Такого случая в корпусе не нашлось.


## РАЗВОРОТ 2026-08-05: ветка «нельзя копировать» ПЕРЕОТКРЫТА — по причине ПРЕДСТАВЛЕНИЯ, не безопасности

Напоминание владельца: планировался атомик **без указателя**, со значением
внутри. Интегратор отложил это как «про скорость, после тега» — **ошибка**,
проверка по принципу плана 221 даёт обратное.

**Переход на значение внутри — ЛОМАЮЩЕЕ изменение.** Сегодня `mut c =
cfg.counter` даёт вторую ссылку на ТУ ЖЕ ячейку. При значении внутри та же
строка даст либо ОТДЕЛЬНЫЙ счётчик (тихо сломает работающий код), либо ошибку
компиляции. Оба исхода ломают программы, которые собирались.

По правилу «ужесточать до релиза, ослаблять после» это **обязано попасть в
тег**: выпустив указательную форму, мы запираем её навсегда — сменить
представление потом значит сломать пользователям семантику.

**Признак «нельзя копировать» возвращается, но по ДРУГОЙ причине.** Закрытие
ветки выше остаётся верным в своей части: для БЕЗОПАСНОСТИ признак не нужен,
структурный вывод справляется. Но для ПРЕДСТАВЛЕНИЯ он необходим: если
значение лежит внутри объекта, молчаливая копия обязана стать ошибкой, иначе
каждая копия окажется собственным счётчиком, и атомарность превратится в ложь.

**Что остаётся за тегом:** сведение 21 типа в один обобщённый — оно упирается
в [№351](221.1-bug-sweep.md) и от представления НЕ зависит. Можно перевести 21
тип на значение внутри по отдельности, а объединить позже.

**Замки (3) под этот разворот НЕ подпадают:** там объект операционной системы,
он останется за указателем. Им — линейность и починка утечки
[№348](221.1-bug-sweep.md).


## МЕХАНИЗМ ЗАПРЕТА КОПИРОВАНИЯ — РЕШЁН 2026-08-05 (интегратор)

Вопрос владельца: «нужен механизм блокировки копирования, он решён у нас, как
будем делать?» Ответ: механизм анализа готов целиком, недостаёт **одной формы
записи**. Ниже — почему именно её, с вердиктами компилятора.

### Существующее — таблица и пустая клетка в ней

[D133](../../spec/decisions/02-types.md) разделяет две строгости:

| | D131 `consume` | D133 `type X consume` | **искомое** |
|---|---|---|---|
| потребить ≤1 раз (нельзя копировать) | да | да | **да** |
| потребить ≥1 раз (обязан израсходовать) | нет, забыть можно | да | **нет** |
| ставится на | получатель/параметр метода | **тип** | **тип** |

Аффинность в языке есть, но только на получателе метода. На **типе** доступна
одна лишь must-consume-форма. Искомое — аффинность на типе — пустая клетка.

### Почему `consume` для атомика не годится — проба, а не рассуждение

```nova
type AtomicU32 consume value priv { v u32 }
fn main() { ro a = AtomicU32 { v: 0u32 } }
```

Вердикт release-компилятора (2026-08-05, `nova check`):

```
[D133-empty-consume] type `AtomicU32` помечен `consume` но не имеет ни
  consume-полей, ни consume-методов — добавь хотя бы один consume-method
  либо убери `consume` с type-decl.
[E_CONSUME_KEYWORD_MISSING] binding `a` держит consume-обязательную инстансу
  типа `AtomicU32` — требуется keyword `consume` (D180).
```

Обе ошибки принципиальны, а не косметичны. Первая требует придумать
метод-расход, которого у счётчика со значением внутри нет и быть не может:
память не выделяется, закрывать нечего. Вторая требует писать `consume a = …`
на КАЖДОМ объявлении переменной-счётчика. Ритуал без содержания — и он бы
разъехался с назначением: обязательный расход существует, чтобы не забыли
закрыть ресурс, а тут ресурса нет.

### Решение — `#no_copy`: аффинность на уровне типа

`#no_copy` не дублирует `consume`, а достраивает таблицу до полной. Смысл:
**значение этого типа нельзя связать вторым именем; забыть — можно.**

Объём работы мал, потому что анализ уже написан:

1. **Парсер** — имя `nocopy` в список атрибутов типа. Сегодня его там нет:
   окно p248-nocopy получало «ошибка разбора — нет в семи именах» (таблица
   вердиктов выше). Соседство обоснованное — среди семи уже есть
   `zero_on_move`, то есть атрибут, влияющий на семантику перемещения.
2. **Тип** — флаг в объявлении, рядом с существующим признаком consume-типа.
3. **Чекер** — `check_consume` (flow-sensitive, состояния
   `Live`/`Consumed`/`MaybeConsumed`, `compiler-codegen\src\types\mod.rs`)
   переиспользуется КАК ЕСТЬ, с одним изъятием: для `#no_copy`-типа не
   выполняется финальная проверка «на выходе из области не осталось Live».
   Именно эта проверка и есть разница между «≥1 раз» и «≤1 раз».
4. **Транзитивность** — `type_is_consume` уже тянет свойство через поля
   записи, варианты суммы, обёртки-дженерики и кортежи, с защитой от циклов
   (`type_is_consume_v`). Для `#no_copy` нужен тот же обход; вопрос
   исполнителю: разделять ли реестры типов или вести один с двумя уровнями
   строгости. Рекомендация — один реестр с уровнем, чтобы обход не
   раздваивался.
5. **Диагностика** — своя, не переиспользовать текст `consume`: там речь про
   «обязан потребить», здесь про «нельзя завести второе имя».

### Форма объявления атомика — решение владельца 2026-08-05

Кортежная обёртка **отклонена владельцем**: до значения внутри неё легко
добраться кортежным доступом, приватность теряется. Принято:

```nova
#no_copy type AtomicU32 value priv { v u32 }
```

Целевой вариант — тот же тип с параметром: `Atomic[T Ints]`. Он упирается не в
представление, а в [№351](221.1-bug-sweep.md) (обобщённая внешняя функция с
бáундом по набору типов даёт пустое тело молча), поэтому 21 тип переводится на
значение внутри по отдельности, а сведение в один обобщённый — после починки
№351.

### РАЗВЕДКА ВЫПОЛНИМОСТИ ИСПОЛНЕНА (окно p248-nocopy2, 2026-08-05)

Отчёт — `docs/plans/wip/PROGRESS-p248-nocopy2.md`. Вердикт: **форма выполнима,
но объём, заявленный выше, ЗАНИЖЕН.** Поправки к оценке — по пунктам, с
фактами:

**1. Парсер и представление — подтверждено дёшево.** `parse_type_attrs`
(`compiler-codegen/src/parser/mod.rs:2638-2868`) — единственное место разбора
имён; `no_copy` встаёт восьмой веткой по образцу `zero_on_move`, отдельным
булевым полем объявления типа. Кодоген не трогается вовсе: признак чисто
чекерный.

**2. Оценка «одно изъятие в `check_consume`» НЕВЕРНА.** Существующая проверка
второго имени (`E_VIEW_BINDING_FORBIDDEN`, D180 Rule 2) ловит ТОЛЬКО голую
форму `ro b = a`. Она НЕ видит: чтение поля в локальную (`x = @field`),
передачу значения аргументом функции, встраивание в литерал записи.
Подтверждено пробой: `takes_view(a)` для consume-типа проходит без единого
замечания. Для `#no_copy` нужны именно эти три случая — то есть машину
придётся расширять, а не только изымать из неё финальную проверку.

**3. Реестр — с уровнем строгости, а не второй.** Подтверждено: без уровня
Rule 1 потребует писать `consume` при каждом объявлении no_copy-переменной —
ровно то, что план отверг как ритуал.

**4. ГЛАВНОЕ — три места корпуса СОЗНАТЕЛЬНО живут на указательном
представлении.** `std/src/net/tcp.nv` (`TcpStream.rc` + `@share()`: в
доккомментарии прямо сказано, что копии несут ТОТ ЖЕ `AtomicInt` — на этом
стоит подсчёт ссылок и закрытие сокета последним владельцем),
`nova-polaris/src/middleware/log.nv` (`AccessLog.counter`),
`nova-polaris/src/net/serve.nv` (`RejectLog`, с явной ссылкой на «тот же
приём»). Проба показала: при переходе на значение внутри этот приём **молча**
начинает заводить независимые счётчики — код компилируется, но работает
неверно. Для `TcpStream` это означает, что сокет закроется раньше времени.

Отсюда предусловие: перевод атомиков на значение внутри **обязан** идти
вместе с перепроектированием этих трёх мест, иначе тег зафиксирует тихий
баг — вопреки собственному правилу «ужесточать до релиза».

**5. `#share` и `#no_copy` не противоречат.** Проверено пробой: канал захвата
в файбер уже сегодня работает через продвижение в кучу, мутация внутри
`spawn` видна снаружи. Пометки ортогональны.

**6. Рантайм для значения внутри УЖЕ НАПИСАН.** `nova_rt/sync_primitives.h`
содержит `Nova_AtomicI64/I32/…/Bool` — все одиннадцать — в виде `{ T value; }`
с полным набором атомарных операций. Единственное отличие от нужного —
выделение в куче вместо значения на месте. Передача адреса приватного поля во
внешнюю функцию тоже работает: `&@v` лоуэрится в `&(nova_self->v)`,
подтверждено пробой.

### ОБЩАЯ ЯЧЕЙКА — СЧЁТ ЗАКРЫТ (окно p248-sharedcell, 2026-08-05)

Вопрос владельца: если атомик станет значением, чем делить ячейку там, где
делить НАДО? Он же отверг отдельный тип и предложил указатель. Проверено
счётом и пробами, отчёт — `wip/PROGRESS-p248-sharedcell.md`.

**Мест, которым общая ячейка нужна ПО СУЩЕСТВУ, — одно. Вне `std` — ноль.**
Пересчёт по всему корпусу (std, полярис, nova-http, nova-tls, nova-bignum,
examples) новых мест сверх трёх известных не дал, а из трёх остаётся одно:

- **`std/src/net/tcp.nv`, `TcpStream.rc`** — нужна по-настоящему. Проба:
  копирование значения между независимыми значениями (не захват одной
  переменной) даёт независимые ячейки — `original=2 second=3` вместо `3/3`.
  Продвижение в кучу здесь не спасает, указатель необходим. Место внутри
  `std`, пользователю не видно;
- **`AccessLog.counter`** — не нужна, счётчик переносится в замыкание
  ([№354](221.1-bug-sweep.md));
- **`RejectLog`** — не нужна, но починка иная, чем думали: не перенос, а
  снятие двухстрочной локальной копии внутри `@record()` (`@count.bump()`
  вместо `mut count = @count; count.bump()`). Заведено как
  [№355](221.1-bug-sweep.md): сегодня код верен по случайности —
  правильность держится на продвижении в кучу, о котором в коде ни слова.

**Указатель пользователю `unsafe` НЕ навяжет.** Пробы: объявление поля-
указателя, взятие адреса, вызов методов через указатель — включая мутирующие
— проходят без `unsafe`. Он требуется только для голого разыменования и
сырых операций чтения/записи, а методы атомиков зовутся как обычные методы.

**Висячего указателя не будет.** Проба: функция объявляет значение локально
и возвращает его адрес — после возврата запись через указатель корректна, а
в порождённом C переменная сразу размещается в куче. Компилятор определяет
уход значения за пределы кадра общим эскейп-анализом (D216 §4), не только
для захвата в файбер. Блокера нет.

**Вывод: отдельный языковой тип общей ячейки избыточен.** Схема владельца
принимается целиком: атомики — значение внутри с `#no_copy`; единственное
место, которому нужно делить ячейку, обходится указателем внутри `std`.
Вернуться к вопросу — если в корпусе появится второй такой прецедент.

### Что это НЕ отменяет

Отклонение разворота «копируются только примитивы, остальное через `.clone()`»
остаётся в силе и по прежнему основанию: где копировать нельзя — уже запрещено
структурным выводом, где можно — разрешено осознанно (D415). `#no_copy` нужен
для случая, который вывод покрыть не может **в принципе**: структурная проверка
посмотрит на `AtomicU32 { v u32 }`, увидит внутри обычное число и заключит
«копировать безопасно». Семантика противоречит структуре — значит, признак
обязан быть объявлен, а не выведен. Это ровно тот случай, который раздел
«ВЕТКА ЗАКРЫТА» называл возвращающим вопрос: тип не разделяемый, не стековый по
смыслу, и не копируется по причине, невыводимой из состава полей.
