любой тест, зарегистрированный ПОСЛЕ него в исполнении того же шарда, никогда не
запускается, но и не считается ни PASS, ни FAIL (счётчик не ассертит сумму против

явно исключён из CU на время проверки) — то есть минимум ДВА независимых
источника одного и того же RUN-FAIL-симптома, и любой из них может тихо съедать
хвост шарда. **Практическое следствие: НИ ОДНО закрытие этой сессии, опирающееся
ТОЛЬКО на агрегатный счёт мега-CU (без явной standalone-проверки новой фикстуры
с исключением известных крашащих файлов), не гарантирует полного покрытия.**
Детали/приём диагностики — см. `[M-conformance-megacu-intermittent-run-crash]`
запись P0. Требуется: (1) отдельное окно на настоящий фикс креша(ей), (2)
`test_runner.rs` ассерт суммы PASS+FAIL+SKIP против числа .nv-файлов (громкий
провал при расхождении вместо тихого недосчёта).

изменений, и ни одна не была видна, пока приёмка шла ручными фильтрами.

## Перепроверка (2026-07-29, разбор интегратором)

Следующие пункты требуют перепроверки перед закрытием/переходом к реализации — гипотезы или зависимости, не измеренные в полном объёме:

### №150 — Sync-сторона тремя кирпичами: Шаг 1 (repro) не сделан

Решение владельца («Migrate не заводить, Sync тремя кирпичами») чисто в теории, но **ШАГ 1 НЕ ВЫПОЛНЕН**: репродуктор (общий Vec в замыкании + N spawn-писателей под нагрузкой) не написан. Без него весь дизайн — гипотеза; реальные паттерны во флагмане и std могут вскрыть нюансы, не учтённые тремя кирпичами. Например: (2) «линейность для mut — пересечение границы spawn = ошибка» — false-positive на per-fiber аккумуляторах (structured concurrency, await-граница); (3) «белый список синхронизированных типов» — где граница для `std::collections`? `HashMap` несинхронизирован по построению, но может быть wrapped в `Mutex`. **Рекомендация:** не закрывать №150 как «решение согласовано» без репро + прогона на реальном коде (хотя бы флагман).

### №148 — JSON field order: блокирует №141 (Класс А'), цепочка к тегу v0.1

№148 (P1, serde) — не изолированный баг. Он **БЛОКИРУЕТ №141** (emit_record_json hand-rolled → typed serde во флагмане, Класс А' — блокер тега v0.1). Пока порядок полей недетерминирован, `json_encode` не может заменить ручную склейку — байтовый контракт SSE (сайт www) сломается. **Цепочка к тегу:** №148 → №141 → v0.1 tag. Если №148 не будет закрыт до заморозки, №141 придётся решать через костыль (стабильная сортировка полей + обновление golden-эталонов) — что меняет требование «порядок объявления» на «порядок сортировки». **Рекомендация:** явно зафиксировать стратегию fallback для тега: (а) сортировать поля по имени (ломает golden, но детерминированно) vs (б) замиксовать JSON-encode целиком (возврат к ручной склейке как контракт). Решение владельца до заморозки.

### №136 — тихая генерация неверного кода: класс P0, не P1

№136 (bare variant name resolves to unrelated type) — **тихая порча данных без ошибки/предупреждения**. Сейчас классифицирован как P1. По критериям плана («молчаливая порча — первые в очереди», §Ф.2 рядок 71) это класс P0: байт-разные типы, разное семантическое значение, ноль диагностики. Пользователь получает `int` там, где ожидал `str` — без единого намёка. Единственная причина «не P0» — обход через квалифицированные имена (`SumRepr.Tagged`), который команда знает. Но для внешнего пользователя это мина. **Рекомендация:** повысить до P0, либо явно мотивировать почему P1.

### №137 + №146 — один корень, одно окно эффективнее

№137 (generic static dispatch collision) и №146 (reflect fieldwalk generic field not monomorphized) — **один и тот же класс дефекта**: резолв статик-метода generic-ресивера теряет T. Описаны как отдельные окна, но чинить их вместе (auto_derive field-walk + mono-резолв) — дешевле и снижает риск повторной коллизии. Оба блокают OpenAPI-схемы для бандлов 222.8. **Рекомендация:** смержить в одно компилятор-окно (канал, вместе с №129-аудитом single-key реестров — downstream effect №125-остатка).

### №149 — inline-cast fix checkpointed, НЕ верифицирован

Шаг 1 (фикс инлайн-каст-резолва) зачекпоинчен в ветке `p234-bitwise`, но верификация НЕ ЗАВЕРШЕНА. Если фикс регрессирует, под ударом blanket-делегирование в to_i128 (рекурсия через `(@ as i64).to_i128()` для `T=i64`), а это — тихая порча (переполнение стека). **Рекомендация:** не разблокировать №149 (и не вливать p234) без standalone-подтверждения: (а) `i64.to_i128()` не рекурсирует, (б) мега-CU не регрессирует, (в) фикстуры на все 10 членов SignedInts/UnsignedInts.
