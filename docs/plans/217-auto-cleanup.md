## 0. Что решаем (вопрос владельца 2026-07-19)

Сегодня `@cleanup` вызывается автоматически ТОЛЬКО в блоке `consume X = e { body }`.
Вопрос: делать ли авто-вызов во ВСЕХ скоупах, где consume-переменная с `@cleanup` не
потреблена? Владелец сузил до **гибрида C**: авто-cleanup — только для типов, объявивших
`@cleanup`; для типов без `@cleanup` — старая строгая линейность (обязан потребить явно).

## 1. Согласованная семантика (гибрид C, опциональный `@cleanup`)

- `type X consume` С объявленным `@cleanup` → **аффинный (≤1)**: не потребил к концу
  скоупа = НЕ ошибка, компилятор сам вставляет `@cleanup(outcome)` на висячих exit-путях.
- `type X consume` БЕЗ `@cleanup` → **линейный (=1)**, как сейчас: непотребление =
  `D133-not-consumed` (строгая явность).
- Выбор аффинный/линейный делается САМИМ фактом наличия `@cleanup` в декларации — видимый
  выбор автора, без скрытой магии.

**Канонический пример линейного класса (✅ согласовано владельцем):** `StringBuilder` —
потребление (`@into_str`) извлекает ценность (zero-copy move буфера); авто-`@cleanup`
молча выбросил бы построенную строку = потеря работы. Владелец: «полностью согласен».
Такие типы (StringBuilder/WriteBuffer/линейные токены-доказательства) — ответ на
«зачем НЕ делать @cleanup»: где тихий дроп = баг, оставляем строгую явность.

## 2. ★ ПОПРАВКА ВЛАДЕЛЬЦА №1 (2026-07-19) — авто-cleanup НЕ равен буквальному defer-сахару

Разведка (§1.3) назвала авто-cleanup «сахаром над `defer(o){ X.@cleanup(o) }` на остаток
скоупа». **Владелец уточнил: это НЕ совсем так — consume-переменная может быть ВОЗВРАЩЕНА
(или иначе передана) внутри скоупа, и тогда `@cleanup` авто-вызываться НЕ должен.**

`defer` срабатывает БЕЗУСЛОВНО на каждом выходе. Авто-cleanup обязан быть
**flow-sensitive**: он охватывает остаток скоупа, но **дизармится** на каждом пути, где
`X` покидает владение — `return X`, передача в consume-param, `X.commit()`/любой
consume-метод, #coerce-финализация (214), move в escaping record-field. То есть:

> Авто-cleanup вставляет `@cleanup(outcome)` ТОЛЬКО на тех exit-путях, где `X` к моменту
> выхода в состоянии `Live`/`MaybeConsumed`. На путях, где `X` уже `Consumed` (в т.ч.
> возвращён/перемещён), cleanup НЕ выполняется. Это семантика Rust `Drop`: возвращённое/
> перемещённое значение НЕ дропается.

**Механика дизарма уже существует** (не новьё): (1) tail/return-вынос D188 v3
(03-syntax.md:8785-8797 — дизарм в момент передачи владения); (2) 214 finalize×поток
(MaybeConsumed на join). Формулировку «сахар над defer» в D314-контексте заменить на
«flow-sensitive авто-`@cleanup` с дизармом по VarState D131»: базовый транспорт (defer-frame,
LIFO, outcome-материализация, `nova_scope_exit`) тот же, НО регистрация/дизарм ведётся
flow-анализом консюма, а не безусловным defer. Это КЛЮЧЕВОЕ отличие от исходной
формулировки разведки — реализация обязана его нести (иначе `return X` дважды освободит
или освободит переданное наружу владение = двойной cleanup / use-after-free).

**★ Ревью-находка (интегратор 2026-07-19) — `MaybeConsumed` на ОБЩЕМ exit-пути: механика
НЕ существует, нужен выбор владельца (§8 п.6).** Оба прецедента выше покрывают только
вырожденные случаи: у D188 v3 дизарм совпадает с немедленным выходом (tail/return — общего
продолжения нет), у 214 `MaybeConsumed` на join даёт compile error на ИСПОЛЬЗОВАНИЕ
(cleanup там не бежит вовсе). Сегодня сценарий «потреблён в одной ветке, ветки слились,
общий выход» невозможен в принципе — D133 ошибка и на `Live`, и на `MaybeConsumed`
(разведка §1.2). 217 его ЛЕГАЛИЗУЕТ — а статическая вставка cleanup на общем выходе =
двойное освобождение на потребившей ветке. Механизм исполнения — развилка §8 п.6
(drop-флаг / запрет / ранний cleanup); цитата-формулировка выше становится нормативной
ТОЛЬКО после этого выбора.

## 3. ★ ПОПРАВКА ВЛАДЕЛЬЦА №2 (2026-07-19) — актуальность блока `consume … { … }`

Владелец: «рассмотри необходимость блока `consume … { … }` в связи с 217, не потерял ли
он актуальность?»

**Разбор.** Блок `consume X = e { body }` сегодня несёт ДВА смысла одновременно:
1. **Гарантия cleanup на выходе** из `body` (exactly-once, D188).
2. **Ограничение времени жизни** `X` под-скоупом `body` (освобождение в конце `body`,
   а не в конце объемлющей функции — раннее освобождение ресурса).

После введения гибрида C смысл (1) **становится автоматическим** для @cleanup-типов в
ЛЮБОМ скоупе — явный блок для этого больше не нужен. Остаётся смысл (2): блок как
**инструмент явного СУЖЕНИЯ времени жизни** — «освободить ресурс здесь, не дожидаясь конца
функции». Прямая аналогия: Rust — авто-`drop` в конце блока по умолчанию, но остаются
вложенный `{ }`-scope и явный `drop(x)` для раннего освобождения.

**Вывод (на ревизию владельца):** блок НЕ теряет актуальность, но его роль **сужается** с
«cleanup + scope» до «scope (раннее освобождение)». Три под-варианта — выбор владельца:
- **(3a) Оставить блок как есть** — сосуществует с авто (авто = до конца объемлющего
  скоупа; блок = явно раньше). Минимум изменений; две формы = как в Rust.
- **(3b) Депрекировать блок** для @cleanup-типов (авто покрывает основной кейс), оставив
  для раннего освобождения отдельную явную форму (например `consume X.@cleanup()` или
  вложенный `{ }`). Меньше форм в языке, но убирает рабочий синтаксис.
- **(3c) Переосмыслить блок** как чистый lifetime-scope без cleanup-семантики (cleanup
  всегда авто; блок только сужает жизнь). Требует аккуратной ревизии D188/D314.
Рекомендация интегратора: **(3a)** на первом шаге (не ломать существующее; авто лишь
ДОБАВЛЯЕТ разрешённость непотребления вне блока), ревизию (3b/3c) — отдельным решением
после обкатки. Это НЕ окончательно — владелец выбирает.

## 3а. ★ Вопрос владельца (2026-07-20): чем отличаются `consume tx = e { … }` и `{ consume tx = e; … }`?

**Сегодня (до 217) — РАЗНЫЕ по семантике:**
- `consume tx = e { body }` (форма-БЛОК, D188) — гарантирует авто-`@cleanup(outcome)` на
  выходе из `body` (exactly-once). `tx` живёт в `body`, прибирается автоматически.
- `{ consume tx = e; body }` (обычный consume-биндинг, D180) — `tx` = must-consume-
  обязательство: ОБЯЗАН быть потреблён явно до конца скоупа, иначе `D133-not-consumed`.
  Авто-`@cleanup` НЕТ. Для НЕ-@cleanup-типа голая форма — единственно осмысленная
  (обязана явно потребить); для @cleanup-типа сегодня — тоже ошибка непотребления.

**После 217 (для @cleanup-типов) — ПОЧТИ СОВПАДАЮТ, разница только в ГРАНИЦЕ жизни:**
- `consume tx = e { body }` — `tx` умирает в конце `body` (явная под-граница), cleanup там.
- `{ consume tx = e; body }` — `tx` умирает в конце ОБЪЕМЛЮЩЕГО `{}`, cleanup там.

```
fn f() {
    consume tx = open() { use(tx) }   // tx закрыт ЗДЕСЬ (конец блока)
    other()                            // tx уже закрыт
}
// эквивалентно после 217:
fn f() {
    { consume tx = open(); use(tx) }   // tx закрыт в конце этого {} (авто)
    other()                            // тот же эффект
}
```

**Вывод:** после 217 форма-блок = «сахар для читаемости + явная под-граница жизни»
(«этот ресурс живёт ровно этот блок»), голая форма = «до конца объемлющего скоупа». Обе
дают одинаковое авто-закрытие; блок лишь делает границу явной и позволяет освободить
раньше конца функции. Это ровно причина решения **3a** (оставить блок) — §3.

## 4. Ортогональность с 216 (подтверждена разведкой §5)

216 (вариант А) enforc'ит ВИДИМОСТЬ ПЕРЕДАЧ владения (consume-паттерны на rvalue, запрет
view-алиасов, пропагация через пейлоад). Авто-cleanup управляет тем, что происходит с
владением, НЕ переданным к концу скоупа. Оси разные → гибрид C оставляет ВЕСЬ периметр 216
и снимает только правило «обязан потребить до конца скоупа» (D133 / D180 Rule 6) для
@cleanup-типов. Напряжение «216 ужесточает — 217 ослабляет» снимается: 216 ужесточает
ПЕРЕДАЧУ (её видимость), 217 ослабляет НЕПЕРЕДАЧУ (конец скоупа). Дополняют друг друга.

## 5. Обязательные ограждения (разведка §6-7)

- **Ограждение 1 (эффекты) — ГЛАВНОЕ.** `@cleanup` в общем случае эффектен
  (`Fail[E]`; File-close несёт `Fs`). Прецедент 214 R12: скрытый эффект в неявной позиции
  запрещён под strict-effects. Первый шаг — авто ТОЛЬКО для `Cleanup[never]`/эффект-чистых
  (покрывает все 6 сегодняшних `@cleanup`-типов: lock-guards/TcpStream/TlsStream, все
  `[never]`). Fallible-cleanup (File/Transaction) — отдельным решением (эффект-пропагация
  в сигнатуру объемлющей функции ЛИБО запрет авто для них). См. §8-развилка 1.
- **Ограждение 2 (амендмент).** Язык-меняющее → в том же слиянии: D133 §«Что отвергнуто»
  пункт «Drop-method auto-cleanup отвергнут» пересматривается (смягчение: `@cleanup(outcome)`
  ветвится по `ScopeOutcome`, «размывание commit/rollback» устарело после ScopeOutcome);
  D131/D180 Rule 6 «consume obligation в-scope check» не применяется к @cleanup-типам;
  D314 — уточнение flow-sensitive (§2). Спек-амендмент ОБЯЗАН ехать в слиянии реализации.
- **Ограждение 3 (периметр — НЕ рекурсивен; ревью 2026-07-19).** Авто-cleanup применяется
  ТОЛЬКО к именованным consume-биндингам; drop-glue НЕТ: record с @cleanup-полем,
  `Vec[TlsStream]` и прочие агрегаты/контейнеры полем/поэлементно НЕ прибираются, правила
  передач (Stored-in-escaping-field = Transferred, D131) не меняются. Читателю с Rust-фоном
  проговорить явно: рекурсивного Drop в 217 НЕТ (отдельное будущее решение, если понадобится).
- **Ограждение 4 (отброшенные временные; ревью 2026-07-19).** Несвязанный результат
  @cleanup-типа (`acquire_lock()` стейтментом) остаётся ошибкой непотребления — авто НЕ
  применяется. Иначе ловушка Rust «`lock()` без `let _guard`»: временный guard умирает в
  конце стейтмента, критическая секция схлопывается молча. Авто — только для именованных
  биндингов. Neg-фикстура в Ф.3.

## 6. Самый дешёвый первый шаг (keystone, разведка §7)

Механизм D188/D314 уже построен (defer-frame, `nova_scope_exit`, дизарм-флаг,
outcome-материализация). Keystone: в check_consume на точке выхода скоупа, где переменная
`Live`/`MaybeConsumed` И её тип объявляет эффект-чистый/`[never]` `@cleanup` — вместо
`D133-not-consumed` эмитить тот же defer-desugar (D314 §3), взяв «остаток скоупа» как body,
С flow-sensitive дизармом (§2). Точечная правка types/mod.rs (класс типа + переключение
диагностики + регистрация/дизарм по VarState) + перенацеливание существующего эмиттера.
Миграция кодовой базы — НУЛЕВАЯ на старте (явный `consume X = e { body }` продолжает
работать). Добавление `@cleanup` прочим 8 ресурсам — отдельная постепенная волна.

**Оговорка (ревью 2026-07-19, ОБНОВЛЕНО 2026-07-20):** владелец выбрал §8 п.6 вариант **(а)
рантайм drop-флаг** (паритет с Rust). Значит оценка «точечная правка» НЕ применима —
Ф.2 (codegen) несёт РЕАЛЬНЫЙ новый код: скрытый булев drop-флаг per MaybeConsumed-биндинг,
вставка/сброс флага на путях потребления, условный cleanup на выходе. Keystone ширится:
не только «переключение диагностики + переиспользование D314-эмиттера», но и drop-flag-
машинерия в codegen. Прецедент — rustc drop-flags (feedback: rustc = эталон).

6. **§8 п.6 MaybeConsumed:** ✅ **(а) рантайм drop-флаг** (решение владельца 2026-07-20:
   «паритет с Rust как минимум, зачем делать хуже»). На путях, где `X` может быть
   `MaybeConsumed` (потреблён в одной ветке, не в другой, ветки слились), компилятор
   вставляет скрытый булев drop-флаг: cleanup на выходе бежит ТОЛЬКО если флаг «жив».
   Это семантика Rust drop-flags. **Следствие для keystone (§6):** авто-cleanup больше НЕ
   чисто «перенацеливание эмиттера» — добавляется рантайм drop-флаг в codegen (Ф.2 несёт
   реальный новый код, не только диагностику). Оценка «точечная правка» пересмотрена вверх.

## 8. Открытые решения владельца (ВЫБОР ВЛАДЕЛЬЦА — не интегратора)

1. **Эффект-политика (главное).** Авто только для `[never]`/эффект-чистых на первом шаге —
   ОК? Fallible-`@cleanup` (File/Transaction): эффект-пропагация в сигнатуру vs запрет авто —
   сразу или отдельным решением? Что делает cleanup-ошибка на normal-path (Success): throw
   наружу (D314 §4a) или запрещённая конфигурация?
2. **Опциональный vs обязательный `@cleanup`.** Рабочий кандидат — опциональный (нет
   `@cleanup` = линейный по умолчанию). Альтернатива для симметрии «visible ownership»:
   `type X consume` ОБЯЗАН явно объявить либо `@cleanup` (авто), либо маркер `linear`
   (строгая явность) — третьего нет. Опциональный дешевле (StringBuilder не трогаем);
   обязательный честнее. Выбор владельца.
3. **Судьба блока `consume … { … }`** (§3): (3a) оставить / (3b) депрекировать / (3c)
   переосмыслить как lifetime-scope. Рекомендация — (3a) на старте.
4. **Добавлять ли `@cleanup` 8 ресурсам без него** (File, TcpListener, halves, UdpSocket,
   OnceGuard, Body, ffi) и когда. Отдельная волна.
5. **Диагностический UX.** Информационная подсказка в местах неявной вставки авто-cleanup
   («здесь ресурс освобождается») или молча, как Rust?
6. **★ `MaybeConsumed` на общем exit-пути — механизм исполнения (ревью 2026-07-19,
   БЛОКИРУЕТ Ф.0: решение нормативное, войдёт в D-блок).** Гибрид C легализует «потреблён
   в одной ветке, ветки слились» — статическая вставка cleanup на общем выходе даёт двойное
   освобождение на потребившей ветке (§2 ревью-находка). Варианты:
   - **(а) рантайм drop-флаг** на переменную (динамический drop Rust): взводится при
     объявлении, сбрасывается в каждой точке потребления, exit-путь читает флаг. Точная
     семантика — cleanup в конце скоупа с настоящим `ScopeOutcome`; цена — новый
     кодген-механизм (keystone дорожает, см. §6-оговорку).
   - **(б) запретить** `MaybeConsumed`-выход и для @cleanup-типов: диагностика «потребление
     в одной ветке — сбалансируйте явно (потребите во всех ветках или ни в одной)». Ноль
     новой механики, авто только для определённо-`Live`; ослабить до (а) можно позже.
   - **(в) ранний cleanup** в конце НЕ-потребившей ветки до join (статически корректно —
     использование после join и так запрещено). Дёшево, НО меняет момент И outcome: cleanup
     бежит с `Success` до конца скоупа, даже если скоуп потом throw'ит — расходится с
     заявленной §2 семантикой Rust Drop (Rust держит до конца скоупа drop-флагом).
   Рекомендация интегратора: **(б) для keystone**, (а) — отдельным решением после обкатки.
