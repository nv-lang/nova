## 0. TL;DR (резюме дизайна)

Канал Call-expr `ResolvedType` **уже существует** — это `resolved_types_buf[call.id]` (Канал-2, читается codegen
`infer_expr_c_type:48795` перед легаси `infer_call_ret_c`). Q5 («ни одной записи для Call») уточнена: записи
ЕСТЬ, но для **generic-возврата вызова** чекер кладёт residual-`TypeParam` (`mark_type_params`) или ничего →
codegen перевыводит. Tier-2 заблокирован **дырой в ПОКРЫТИИ**, не отсутствием канала. Фундамент subst уже в базе
(влитый typed-ir-p1): constraint-solver (`Solver`/`Constraint::{Eq,Join,Project}`/fresh-`TypeVar` anti-d119) +
`resolve_return_channel` (carrier-binding через solver, сейчас в SHADOW-режиме). **Stage-1 (без MIR):** достроить
`resolve_return_channel` на method-level generics (`Constraint::Eq` param↔arg) + флип SHADOW→authoritative →
концкретный `Result[ok,err]`/`Option[t]`/sum-возврат материализуется в канал; codegen-потребление уже
channel-first. Гейт byte-parity = propose-then-verify (установлен). Разблокирует Q1/Q2/Q5 (D30/D85/D182/D52/D407);
удаление легаси-хелперов гейтится волной-1 (они внутри замороженной `46293`–`48883`). Объём ядра ~100–250 строк,
риск средний (митигизация: fresh-var + parity-assert + gs-gate + CC-FAIL-as-signal).

## 1. Проблема — УТОЧНЕНИЕ Q5 по коду (канал ЕСТЬ, дыра в ПОКРЫТИИ, не в отсутствии)

Q5 сформулировала: «чекер аннотирует `resolved_types` для Ident/SelfAccess/Index/Member/Range/RecordLit,
но для `ExprKind::Call` — НИ ОДНОЙ записи». **Разведка 196.4 это уточняет (по коду):** записи для Call ЕСТЬ, и
их несколько путей. Точная граница Tier-1/Tier-2 не «Call не ключуется», а **«Call ключуется концкретным типом
только когда subst полностью разрешается на чек-тайме; иначе чекер помечает residual-`TypeParam` и откладывает
subst в codegen (`resolved_type_to_c` + `current_type_subst`), ЛИБО не аннотирует вовсе → codegen падает в
легаси `infer_call_ret_c` (зона волны-1)»**.

Существующие продюсеры Call-аннотации (`compiler-codegen/src/types/mod.rs`):
- **`f1_check_call`** (`~10200`–`10494`): резолвит однозначный callee (free-fn single/multi-compat,
  `Type.method`, module-fn) → `resolved_callees[call_id]` + аннотирует `resolved_types_buf[call_id]`:
  - non-generic возврат (гейт `!typeref_mentions_any`) — прямо (`10450`);
  - `-> Self` static — subst `Self`→receiver-тип через `subst_type_ref_pub` (`10433`–`10451`);
  - **free-fn generic возврат** (`10452`–`10492`): ВЫВОДИТ type-args из АРГУМЕНТОВ через
    `const_fn_trampoline::unify_type` + `subst_type_ref_pub` → материализует КОНКРЕТНЫЙ `Result[[]int,str]`;
    гейт «только при полном разрешении (нет residual)».
- **`f1_expr_inner` Call-арм** (`~7854`–`7929`): `infer_method_call_channel_type` (instance-метод возврат) →
  `mark_type_params(from_type_ref, gs)` → `resolved_types_buf[e.id]`; плюс fallbacks: TurboFish-static-ctor
  (`infer_expr_type`), `size_of/align_of` (→int), `Some(x)` (→`Option[type-of-x]`).
- **`check_instance_overload`** (зовётся из `10347`) — instance-overload → `resolved_callees` + канал.

Потребление codegen — `infer_expr_c_type` (`emit_c.rs:48686`), порядок:
1. спец-кейсы (`try_as[T]`, generic-wrapper-ctor mono → `infer_generic_static_ctor_ret`);
2. **Канал-1** (`48746`): `resolved_callees[id]`→`fn_ret_by_span[span]`, НО `!debt_is_generic_stub_c` — любой
   generic-возврат `Result[T,E]`/`Option[T]` лоуверится при регистрации в стаб → **пропускается**;
3. **Канал-2** (`48770`–`48795`): `resolved_types[id]`→`resolved_type_to_c` — ЭТО и есть канал Call-expr
   ResolvedType; если чекер аннотировал КОНКРЕТНЫЙ тип — codegen читает здесь и НЕ идёт в легаси;
4. промах → легаси `infer_call_ret_c` (`46405`, зона волны-1 `46293`–`48883`) → `resolve_result_option_ret`
   / `resolve_result_te` / `infer_static_method_ret` / `infer_method_level_return_for_sum` перевыводят.

**Вывод:** канал (Канал-2) уже существует и авторитетен. Tier-2 заблокирован НЕ отсутствием канала, а тем, что
**чекер не кладёт в него полностью-подставленный конкретный `ResolvedType` для класса «generic-возврат вызова,
subst которого приходит из method-level generics / sum-обёртки / static-generic, а не из уже-покрытых
receiver-carrier / free-fn-arg»**. Где чекер помечает residual-`TypeParam` (`mark_type_params`) и отдаёт subst в
codegen — это и есть остаток «codegen перевыводит», подлежащий переносу в фазу-коллектор (кроме законно-erased
тел, см. §7).

## 2. Как чекер СЕЙЧАС заполняет `resolved_types_buf` (recon-1)

`f1_expr` (`7152`) = обёртка: `f1_expr_inner` (walk, тот же поведенческий обход) + опциональная IDE-запись. Общий
паттерн продюсера: для ExprKind вызывается `infer_expr_type(e, scope)` (синтаксический TypeRef-инференс) →
`ResolvedType::from_type_ref` → `resolved_types_buf.insert(e.id, rt)`. Ключ ВСЕГДА `e.id` (`ExprId`), значение —
`ResolvedType` (перечень в `types::ResolvedType`: `Scalar/Float/Bool/Str/Unit/Ptr/Named{name,module,args}/
Tuple/Func/TypeParam/…`).

Покрытые ExprKind (все в `f1_expr_inner`, преамбула `7249`–`7717`):
- **Ident** (`7249`), **SelfAccess** (`7266`), **Index** (`7279`, + 172.1.2 контейнер→элемент через
  `project_channel`), **Member** (`7308`), **Range** (`7324`, всегда `Named{Range}`), **RecordLit**
  (`7332`/`7462`, гейт non-generic), **HandlerLit**/**ProtocolLit** (`7350`/`7373`), **Block/If/IfLet/Path**
  (`7394`), numeric-const `T.MAX` (`7423`), Tuple all-primitive (`7608`), loop→Unit (`7626`), ParallelFor→`Vec[T]`
  (`7637`), литералы (`7688`).
- **Call** — арм `7718`–`7930` (см. §1): аннотация через `infer_method_call_channel_type` / static-ctor /
  size_of / Some(x), с `mark_type_params`-гейтом. Плюс `f1_check_call` (`10200`+) даёт callee+прямой канал.

Где Call пропускается (нет концкретной аннотации → codegen в легаси): (а) instance/static-возврат, чей
type-param выводится из method-level generics или sum-обёртки, а `resolve_instance_method_return_arity` не
разрешает; (б) когда `mark_type_params` оставляет residual (erased-тело — законно; concrete-caller — дыра); (в)
0-или-≥2 compat overload (`_ => return`, «gap, not wrong»).

## 3. Где чекер УЖЕ вычисляет подставленный тип результата вызова (recon-2)

Машинерия subst на чек-тайме УЖЕ существует и переиспользуема (это ключ к минимальности Stage-1):
- **`const_fn_trampoline::unify_type(param_ty, arg_ty, generic_names, &mut subst)`** — структурный унификатор:
  сопоставляет объявленный параметр с выведенным типом аргумента, накапливает `subst: HashMap<String,TypeRef>`.
  Тот же унификатор, что `build_recv_subst` применяет к ресиверам. Используется в `f1_check_call` для
  free-fn generic-возвратов.
- **`const_fn_trampoline::subst_type_ref_pub(ty, &subst)`** — применяет `subst` к `TypeRef` (T→конкрет).
- **`build_recv_subst(receiver, recv_ty)`** — строит subst из receiver-carrier (T контейнера → элемент из
  инстанс-типа ресивера).
- **`resolve_instance_method_return_arity`** (`13589`) / **`resolve_instance_method_return`** (`13579`) —
  возврат instance-метода с carrier-subst.
- **`resolve_method_return_with_closure_args`** — method-level generic (`map[U]`) из closure-аргумента при
  известном carrier-subst (`closure_arg_param_seeds` `14053` сеет типы closure-параметров из
  СУБСТИТУИРОВАННОЙ сигнатуры callee).
- **`mark_type_params(rt, gs)`** — помечает residual-параметры явным `ResolvedType::TypeParam`; лоуэринг:
  codegen `resolved_type_to_c` + receiver-instance-map/`current_type_subst`.

**Итог recon-2:** чекер уже умеет: (1) receiver-carrier subst, (2) free-fn-arg subst, (3) method-level generic
из closure-арга. НЕ покрыто концкретной аннотацией (класс Tier-2): method-level generic из НЕ-closure арга,
sum-обёртка возврата (`infer_method_level_return_for_sum`), static-generic не-ctor, и общий случай, где
`resolve_instance_method_return_arity` возвращает residual → `mark_type_params` откладывает в codegen. Канал
Stage-1 = **достроить subst этих форм на чек-тайме и класть КОНКРЕТ в `resolved_types_buf[call.id]`**, а НЕ
плодить новый IR.

## 4. Задел typed-ir-p1 / коллектор — УЖЕ В БАЗЕ, переиспользуем (recon-3)

Ветка `typed-ir-p1` (`cb44c941e`) практически влита в main: merge-base = `f6b475376` (на 2 коммита ниже
головы; сверх main только трейс-инструментация `infer_call_ret_c`, 114 бакетов, `emit_c.rs` +143 строки). **Всё
переиспользуемое scaffolding УЖЕ в нашей базе `4c02d346d`:**
- **`types/constraint_solver.rs`** (1235 строк): HM-стиль решатель. `Ty` (Var/Concrete/Named/Tuple/Array/Func),
  `enum Constraint { Eq, MemberOf, Join, Project }`, `struct Solver { subst: HashMap<TypeVar,Ty> }`,
  `Solver::solve()` (Eq→Join→Project→MemberOf, fresh-var subst, occurs-check), `VarGen` (fresh numeric identity —
  **anti-d119 by construction**: var = число, не написание), `resolve_return` primitive.
- **`types/mod.rs`**: `ty_from_resolved_vars` (`9523` — лифт `ResolvedType`→solver-`Ty`, carrier-имена→fresh
  `Var`), **`resolve_return_channel`** (`9577` — маршрутизирует carrier-binding instance-метода через solver:
  unify(recv_pattern, concrete_recv) → instantiate(ret_template); `Self` пред-связан byte-parity с легаси).
- Продюсеры Ф.4a/4b уже переведены на решатель: **`Constraint::Join`** (Binary-арифметика,
  `number_exprs::promote_arith_rt`), **`Constraint::Project`** (Index/Member-tuple, `project_channel` `9500`).

**Критично для минимальности:** канал Stage-1 НЕ пишется с нуля — это **расширение уже-подключённого
`resolve_return_channel`**. Сегодня он БЕЙЛИТ (`return None`, `9624`) когда возврат содержит residual
method-level generic (`[U]`, class-(b)) — solver принял бы выжившее имя за ложный concrete-лист. Достройка Stage-1
= добавить в solver `Eq`-констрейнты param↔arg для method-level generics (тот же `unify_type`, но через
`Constraint::Eq` на fresh-var), чтобы `[U]` связался из аргументов и возврат материализовался КОНКРЕТНО.

## 5. rustc-эталон: mono collector + Instance-subst (recon-4)

rustc: типы ОДИН раз в `typeck` (HIR)→`TyCtxt`; HIR→THIR→**MIR**; **мономорфизация — ОТДЕЛЬНАЯ ФАЗА**
(`rustc_monomorphize::collector`: обход достижимого от корней → worklist `Instance = def_id + substs`; НЕ
side-effect резолва). codegen берёт МОНОМОРФИЗОВАННЫЙ MIR и лоуэрит `ty`→LLVM через чистую fn `Instance`.

**Наш Stage-1 аналог БЕЗ MIR (директива владельца — Stage-1/Stage-2 в 196):**
- rustc `Instance = def_id + substs` per call-site ⟷ наш `(callee FnDecl.span, subst: карта carrier+method-generic
  → concrete)` — но мы НЕ материализуем worklist инстансов, а сразу лоуэрим subst-результат в `ResolvedType` в
  side-table `resolved_types_buf[call.id]`.
- rustc «subst происходит в mono-фазе, codegen читает готовое» ⟷ наш «subst происходит в ЧЕКЕРЕ (per call-site,
  на fresh-var solver), codegen читает `resolved_types[call.id]` через `resolved_type_to_c`». Это ровно перенос
  «codegen перевыводит» → «чекер решает» = целевая арх 196 (§0, строки 198-217 родителя).
- Разница со Stage-2: у нас НЕТ типизированного IR-узла и НЕТ worklist-инстанса как объекта — subst «одноразовый»
  на call-site, результат кладётся в side-table. Полный MIR + mono-фаза как объект — Stage-2 (будущее). Stage-1
  «симулирует одно окно side-table'ом без полного IR» (родитель, строка 238).

## 6. ДИЗАЙН канала Call-expr ResolvedType

**Принцип (no-new-window, §3 196.3):** НЕ новый codegen-сайт и НЕ новый side-table. Канал = уже существующий
`resolved_types_buf[call.id]` (Канал-2). Дизайн = ДОСТРОИТЬ ПОКРЫТИЕ существующих продюсеров чекера так, чтобы
для класса Tier-2 (generic-возврат вызова) они клали КОНКРЕТНЫЙ `ResolvedType`, а не residual/ничего.

### 6.1 Точка внедрения в чекере (сходимость на существующие продюсеры)

Три существующих продюсера, БЕЗ новых сайтов:
1. **Instance-методы:** `resolve_instance_method_return`(`13579`)→`resolve_return_channel`(`9577`) →
   `infer_method_call_channel_type`(`14000`) → аннотация в `f1_expr_inner` Call-арм (`7873`–`7879`).
   Сейчас `resolve_return_channel` работает в SHADOW-режиме (`13832`: `debug_assert!` parity против
   `build_recv_subst`, возвращается легаси `out`; solver read-only). **Внедрение Stage-1a:** (i) расширить
   `resolve_return_channel`, чтобы он связывал method-level generics из аргументов (сейчас `9624`: бейл на
   residual `[U]`); (ii) снять SHADOW — ФЛИПнуть продюсер на возврат solver-результата (live-swap
   `build_recv_subst`, помечено «next wave» на `13830`). Тогда концкретный `Result[ok,err]`/`Option[t]`/sum-
   возврат материализуется в канал вместо `mark_type_params`-residual.
2. **Free-fn / Type.method / module-fn:** `f1_check_call` (`10200`+) — уже аннотирует non-generic (`10450`),
   `-> Self` static (`10433`), free-fn-generic-из-args (`10452`–`10492`). **Внедрение Stage-1b:** тем же
   `unify_type`+`subst_type_ref_pub` покрыть static-generic (`Foo[T].make()`) и method-fn generic-возвраты.
3. **Static-ctor / TurboFish:** `infer_expr_type` ctor-армы + `resolve_generic_static_return` (уже через
   `f1_expr_inner` `7885`). Здесь дыр по Tier-2 нет (Tier-1, покрыто d372).

### 6.2 Данные — откуда subst на чек-тайме (generic-space каллиси → space вызывающего)

Всё уже доступно чекеру на call-site; НОВЫХ источников не нужно:
- **carrier-subst** (T контейнера-ресивера → элемент): `build_recv_subst(recv, recv_ty)` / solver
  `resolve_return_channel` (unify recv_pattern↔concrete_recv на fresh-var).
- **method-level generic из args** (`[U]` из `map[U]` и т.п.): выводится структурным `unify_type(param_ty,
  arg_ty, generic_names, &mut subst)` по каждому не-вариадик параметру (arg-тип = `infer_expr_type(arg)` /
  канал). В solver-форме = `Constraint::Eq(lift(param), lift(arg))` на fresh-var per generic-имя — ЭТО
  недостающая достройка `resolve_return_channel`.
- **explicit turbofish** type-args — прямая подстановка.
- **generic-space переход:** имена generic-параметров КАЛЛИСИ (`fn_generic_scope(callee)` + `recv.generics` +
  `fn.generics`) → per-call-site FRESH `TypeVar` (числовая идентичность, `VarGen`, **anti-d119**); унифицируются
  с КОНКРЕТНЫМИ типами вызывающего (arg/receiver уже в space вызывающего); затем `ret_template` инстанцируется.
  Type-параметры САМОГО вызывающего (erased-тело, `gs`) НЕ подставляются — остаются residual `TypeParam` →
  канал их НЕ материализует концкретно (законная граница erased-body, лоуэринг void*/Nova_T* в mono, §7).

### 6.3 Потребление codegen (channel-first — уже на месте)

Изменений в codegen-потреблении НЕ требуется: `infer_expr_c_type` Канал-2 (`emit_c.rs:48795`) уже читает
`resolved_types[call.id]`→`resolved_type_to_c` ПЕРЕД падением в легаси `infer_call_ret_c`. По мере того как
чекер аннотирует больше Call-id концкретным типом, всё меньше вызовов достигает `infer_call_ret_c`. `resolve_
result_option_ret`/`resolve_result_te`/`infer_static_method_ret`/`infer_method_level_return_for_sum` перестают
вызываться для покрытых форм. `resolved_type_to_c` уже C-lossless для `Result[T,E]`/`Option[T]`/sum (D315).

## 7. Минимальность — границы Stage-1

**НЕ делаем (это Stage-2 / вне 196.4):**
- НЕ вводим типизированный IR-узел, НЕ материализуем worklist `Instance` как объект, НЕ строим MIR.
- НЕ мигрируем mono-машинерию (`compute_mono_name`/`compute_generic_type_c_name`/`register_generic_instances`)
  — остаётся в codegen (целевая арх/rustc: манглинг = отдельная фаза, но НЕ в Stage-1).
- НЕ трогаем замороженную зону волны-1 `infer_call_ret_c` (`46293`–`48883`) — редактирует только волна-1/196.2.
- НЕ материализуем концкретный тип для ЗАКОННО-erased тел (вызов внутри `fn foo[T]` где `T` не связан
  вызывающим) — там тип ЕСТЬ `T`, лоуэрится erased (`void*`/`Nova_T*`), subst происходит при mono-инстанциации.
  Канал ОСТАВЛЯЕТ residual `TypeParam` для них (гейт на `gs`/`method_names`), НЕ ошибка.

**Делаем (Stage-1, минимальное ядро):** расширить `resolve_return_channel` (+обвязку продюсеров) так, чтобы для
CONCRETE-CALLER класса Tier-2 subst полностью разрешался на чек-тайме и в `resolved_types_buf[call.id]` лёг
КОНКРЕТНЫЙ `ResolvedType`. Ядро правки локально (одна функция + `Constraint::Eq` param↔arg + флип SHADOW→
authoritative). Гейт byte-parity = **propose-then-verify** (уже установлен: `13833` `debug_assert!` + приёмка
результата ТОЛЬКО когда round-trip воспроизводит легаси-binding).

**Порядок закрытия (dependency-first — ЭНЭЙБЛЕР сначала):**
1. **Stage-1a (энэйблер):** достроить `resolve_return_channel` на method-level generics + флип SHADOW→
   authoritative. Разблокирует generic-instance-возврат (Result/Option/sum) = `infer_method_level_return_for_sum`
   + `resolve_result_option_ret`/`resolve_result_te` для method-путей. → Q2, Q5.
2. **Stage-1b:** static-generic возврат в `f1_check_call`. → Q1 (`infer_static_method_ret` D182/D372).
3. **Stage-1c (верификация + флип статусов):** прогнать `NOVA_TRACE_ICR=1` bucket-трейс (114 бакетов,
   инструментация из typed-ir-p1) → замерить, какие Tier-2-бакеты ещё стреляют; довести до нуля для покрытых
   форм; флипнуть D30/D85/D182/D52 в 196.3-трекере на channel-first (приёмка (1)-(5)).
4. **Stage-1d (зависит от волны-1):** физически УДАЛИТЬ легаси-функции — ТОЛЬКО когда `infer_call_ret_c`
   недостижим для них (доказано трейсом = 0 hits) ИЛИ когда волна-1 удаляет `infer_call_ret_c` целиком. До того
   — `panic!("[MIGRATED-<D>]")` в ветке, если она физически отделима; иначе оставить (зовётся волной-1).

## 9. Связь с терминальным кластером волны-1

`infer_call_ret_c` (`46293`–`48883`) — единолично зона волны-1 (196.2), редактируется по 114 веткам bottom-up.
Канал Call (этот план) — top-down комплемент: волна-2 наполняет Канал-2 концкретными generic-возвратами,
волна-1 гасит ветки легаси. **Встреча:** когда КАЖДЫЙ `Call` имеет либо Канал-1 (non-stub `fn_ret_by_span`),
либо Канал-2 (`resolved_types[call.id]`) запись → ни одна ветка `infer_call_ret_c` недостижима → весь кластер
`46293`–`48883` удаляется (финал обеих волн, «второе окно физически нет»). Метрика сходимости = ICR-bucket-трейс
→ 0 (для generic-return-бакетов — вклад этого плана; для остальных — вклад волны-1). Легаси Tier-2-хелперы
(`resolve_result_option_ret` и др.) живут ВНУТРИ этой зоны как её ветви → удаляются вместе с кластером или раньше
через `panic!`-detach, если ветвь отделима без правки замороженного диапазона.

## 10. Оценка объёма / рисков / поэтапность

**Объём.** Ядро (Stage-1a энэйблер) — МАЛОЕ-СРЕДНЕЕ: правка `resolve_return_channel` (~9577) + врезка
`Constraint::Eq` param↔arg для method-generic + снятие SHADOW-гейта (~13832) + аккуратный флип продюсера. Оценка
ядра ~100–250 строк в `types/mod.rs`, БЕЗ нового файла (solver уже есть). Stage-1b (static) — аналогично малое в
`f1_check_call`. Основной объём — НЕ код, а **верификация + пер-D флип** (Stage-1c: тест + ICR-трейс + приёмка
на каждую D — это очередь Q1/Q2/Q5 в 196.3). Удаление легаси (Stage-1d) — тривиально, но гейтится волной-1.

**Риски и митигизация:**
- **d119 (spelling-collision generic-имён)** — снят конструктивно: solver на fresh числовых `TypeVar` (`VarGen`),
  имя не используется как идентичность.
- **byte-parity дрейф** — гейт propose-then-verify (`debug_assert!` solver≡legacy + приёмка только round-trip-
  совпадения). Прецедент Ф.4a/4b/4c зелёный (conformance 95/0).
- **over-annotation erased-тел** (residual `T` подставлен ошибочно) — гейт на `gs`/`method_names`: residual →
  НЕ аннотируем концкретно (лоуэринг erased в mono). Точно так же, как сейчас `mark_type_params`.
- **mono side-effects** (typedef/`register_novares_decl`/`register_novaopt_decl` в легаси `resolve_result_
  option_ret`) — канал ЧИСТ (только тип). Регистрация должна жить в emit-pass, не в type-инференсе (§1). Риск:
  пропущенный typedef → CC-FAIL. Митигизация: CC-FAIL — сигнал, где нужен proper emit-pass (директива §0
  родителя); на Stage-1c ловим ICR-трейсом + targeted-conformance до флипа.
- **frozen-zone связанность** — Tier-2-хелперы внутри `46293`–`48883`; нельзя удалять до волны-1. Митигизация:
  channel-first делает их МЁРТВЫМИ по достижимости (трейс=0), удаление откладываем — статус 🔄 до волны-1, как
  D239 (`.or_else`-fallback жив = ещё 🔄).

**Поэтапность (гейты на каждом шаге — conformance 95/0 + byte-parity + `nova test std` без новых фейлов):**
- Stage-1a → generic-instance Result/Option/sum возврат в канале (Q2/Q5). Гейт + ICR-трейс дельта.
- Stage-1b → static-generic возврат (Q1).
- Stage-1c → верификация трейсом + флип D30/D85/D182/D52 на channel-first в 196.3.
- Stage-1d → удаление легаси-хелперов (гейт: волна-1 освободила зону ИЛИ трейс=0 + отделимый `panic`-detach).

**Границы Stage-1 vs Stage-2:** Stage-1 = side-table `resolved_types` полнота (этот план) — БЕЗ MIR. Stage-2
(будущее) = типизированный IR + mono-фаза как объект = нативная rustc-модель. 196.4 закрывает Tier-2 в рамках
Stage-1; полный «одно окно» = Stage-1 (обе волны) достаточно для 196, MIR не требуется для закрытия 196.
