# План 209 — Multi-TU codegen: большой CU → N `.c`-единиц (параллельная компиляция)

**Статус:** 📋 ПРЕДЛОЖЕН 2026-07-15 (владелец: «путь 2 — общая идея, не только conformance»).
**Приоритет:** **P1** (блокирует надёжность/скорость ВСЕХ мега-CU гейтов — сейчас полный
`nova test spec_tests` зависает на codegen+компиляции 13-МБ `.c` из 963 файлов).

## Мотив

Codegen эмитит **один compile unit → один `.c`-файл**. Для большого CU (conformance: 963 файла →
**13 МБ `.c`**) это упирается в **суперлинейность** C-компилятора (clang/msvc на одной гигантской
translation unit) + медленный Rust-codegen гигантского буфера. Результат: полный гейт непрактично
долог/зависает. 187-волна добавила тестов → CU перевалил порог, время взорвалось.

**Ключ:** проблема — в ОДНОМ гигантском `.c`, НЕ в логическом CU. Логический CU (кросс-файловый
резолв имён, mono-коллектор, D307 folder-module) уже отработал ДО эмиссии. Значит **вывод** можно
резать на N translation units, СОХРАНИВ единый логический CU (полное кросс-файл-покрытие цело).

## Целевая картина

Codegen эмитит большой CU как:
- **1 общий заголовок** `<cu>_common.h` — все typedef'ы, forward-decl'ы, глобалы, схемы, extern'ы,
  runtime-includes. Эмитится ОДИН раз, инклудится каждым TU.
- **N `.c`-единиц** `<cu>_part0.c … <cu>_partK.c` — подмножества ОПРЕДЕЛЕНИЙ функций (каждая функция
  целиком в одном TU), каждая `#include "<cu>_common.h"`.
- Тулчейн: компилирует N `.c` **параллельно** (по числу ядер) → N `.o` → линкует в один бинарь.

Суперлинейный C-compile → почти линейный (N параллельных мелких TU). **Общий механизм** — не только
conformance: любой большой `nova build`/`test`-таргет выигрывает.

## Развилки / рабочий дизайн (рекон Ф.0 подтверждает file:line + безопасность)

1. **`static` через границу TU (ГЛАВНАЯ).** Функция/глобал с internal linkage, вызванный из ДРУГОГО
   TU → link-error. **РЕШЕНИЕ: промотировать cross-TU-static'и в external** (убрать `static`), их
   декларации — в `_common.h`. Безопасно, т.к. codegen УЖЕ манглит имена **уникально внутри CU**
   (D381 collision-aware) → коллизий при промоушне нет. Проще граф-разбиения. **Fallback** (если
   рекон найдёт риск): держать взаимозависимые static-кластеры в одном TU (граф-партиция).
2. **Стратегия разбиения.** По накопленному **размеру-порогу** (~0.5–1 МБ/TU), идём по функциям в их
   текущем **детерминированном** порядке, новый TU при переполнении. **Каждая функция целиком** в одном
   TU. Детерминизм (тот же порядок → те же границы) → byte-stability результата + кеш.
3. **`_common.h` (пролог).** Всё из шапки `.c` → в общий заголовок: typedef'ы, определения структур,
   **forward-decl'ы всех функций**, extern-глобалы, схемы, NOVARES-typedef'ы, runtime-`#include`'ы.
   Инклудится КАЖДЫМ part'ом. Глобал с ОПРЕДЕЛЕНИЕМ (не extern) → в РОВНО один part + `extern` в `.h`
   (иначе multiple-definition при линковке).
4. **Порог включения.** Multi-TU только для CU выше порога (напр. >2 МБ / >200 функций) — мелкие
   остаются одним `.c` (оверхед split+link не окупается).
5. **Build-cache-ключ.** Порог+стратегия разбиения — часть ключа (смена инвалидирует кеш).

## Фазы (модель по [feedback-cheap-models])

- **Ф.0 Дизайн + развилки (opus-рекон, ИДЁТ):** разрешить static-cross-TU (промоушн vs граф),
  стратегию разбиения, формат `_common.h`, порог — с file:line-якорями. Карта Ф.1/Ф.2 для дешёвого
  исполнения. D-блок (codegen emission model) ТОЛЬКО если меняет наблюдаемое (имена символов при
  промоушне static → external). Read-only. Гейт: карта на руках.
- **Ф.1 Codegen split (sonnet по карте):** вынести пролог в `_common.h`; резать определения функций на
  N буферов по порогу; промотировать cross-TU static'и в external. АДДИТИВНО за флагом (старый
  одно-`.c` путь — дефолт, пока не включим). Точечная верификация: мелкий CU → 1 `.c` (без изменений);
  большой → N `.c` + компилится. Мега-CU НЕ гонять — авторитетный гейт оркестратор.
- **Ф.2 Тулчейн (sonnet):** параллельная компиляция N `.c` → `.o` → линк (test_runner.rs + nova-cli
  build); порог-гейт (>2МБ → multi-TU). Верификация: линк без multiple-definition, бинарь бежит.
- **Ф.3 Включить для conformance (оркестратор-гейт):** полный `nova test spec_tests` быстрее+надёжнее;
  замер до/после; **байт-паритет РЕЗУЛЬТАТА** (тот же бинарь/вывод, меняется только раскладка `.c`).
- **Ф.4 Общий (sonnet/haiku):** включить для `nova build`/крупных std-таргетов; мелкие CU не задеты.

## Гейты
Полный conformance один-CU (теперь multi-TU) зелёный + БЫСТРЕЕ (замер); байт-паритет РЕЗУЛЬТАТА
(вывод программ идентичен — режем только раскладку `.c`, не семантику); линк без multiple-definition;
детерминизм (тот же split при тех же входах).

## Границы
Не меняет логический CU (кросс-файл-резолв/mono/D307 — как есть). Не меняет семантику программ.
Только физическая раскладка codegen-вывода (1 `.c` → `_common.h` + N `.c`) + параллельная компиляция.
Ортогонально Plan 200.1 (там папочные CU + кеш; здесь — split ОДНОГО CU).
