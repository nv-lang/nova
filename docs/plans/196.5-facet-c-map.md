# Plan 196.5 Facet C — карта callnorm.rs/argbind.rs (волна-5 разведка)

**Ветка:** `stage-d-wave5` (worktree `nova-174`). Модель: sonnet. Задание: карта
(где callnorm ре-резолвит то, что чекер уже знает) + ОДИН доказательный
экземпляр перевода на чтение `resolved_callees`. НЕ рефакторинг всего facet C.

## 0. Что такое facet C

`callnorm.rs` (703 строк) — AST→AST pass: переписывает call-site с именованными
аргументами/дефолтами в чистый позиционный (двухфазный `Block`, см. модульный
doc-comment). `argbind.rs` (279 строк) — чистая функция `bind_call_args(params,
args) -> Result<Vec<ArgBinding>, BindError>`, сопоставляет args↔params БЕЗ
резолва callee-идентичности (params ей передаются готовыми) — используется И
чекером (`types::check_module`, diagnostics), И `callnorm.rs` (десугаринг). Сам
`argbind.rs` НЕ ре-резолвит ничего — вся ре-резолюция живёт в `callnorm.rs`'s
`collect_sigs`/`try_normalize_call`.

Пайплайн-позиция (подтверждено `test_runner.rs` ~3330-3422): `check_module`
(чекер, пишет `ModuleEnv.resolved_callees`) → … → `callnorm::normalize_module`
→ `chain_norm::normalize_chains_module` (этот СОСЕДНИЙ pass УЖЕ читает
`module_env.resolved_types` — прецедент чтения чекер-канала на этой же стадии
пайплайна, которого `callnorm.rs` до волны-5 не имел).

## 1. Карта: где callnorm ре-резолвит (до волны-5)

`collect_sigs(module)` строит СВОИ ТРИ независимые таблицы, сканируя ТОЛЬКО
`module.items` (после `resolve_imports_inline` — импортированные декларации
уже влиты в один `Module`, так что cross-module само по себе не отдельная
дыра, но обостряет остальные, см. §2):

| Форма вызова | Таблица | Ключ | Ре-резолв (в обход чекера) | Дефект-класс |
|---|---|---|---|---|
| `f(...)` free-fn | `sigs.free: HashMap<name, Params>` | имя | оставляет ТОЛЬКО unambiguous (1 overload) — при ≥2 глобальных overload'ов с этим именем ВСЯ нормализация этого call-site пропускается, ДАЖЕ если чекер уже выбрал ровно один по типам args | **overloaded free-fn** — named/default никогда не десугарится |
| `Type.method(...)` static | `sigs.static_methods: HashMap<(type,method), Vec<Params>>` | (тип, метод) | держит ВСЕ overload'ы, `pick_static_params` дизамбигуирует ТОЛЬКО по arity + `bind_call_args`-success (слеп к ТИПАМ аргументов) | **arity-ambiguous static overload** — риск выбрать НЕ ТОТ overload, если 2 кандидата совпадают по arity, но разные по типу параметра |
| `obj.method(...)` instance | `sigs.instance_by_name: HashMap<method_name, Params>` | ТОЛЬКО имя метода (тип ИГНОРИРУЕТСЯ) | оставляет ТОЛЬКО unambiguous ГЛОБАЛЬНО (1 запись на ВЕСЬ модуль/CU) — если ЛЮБЫЕ 2 разных типа в модуле имеют метод с таким именем (частое: `len`, `push`, `map`, `new`…), нормализация ВЫКЛЮЧЕНА для ЭТОГО ИМЕНИ ПОВСЮДУ | **cross-type name collision** — самый широкий класс; в мега-CU (конформанс = один CU ~169 файлов) коллизии частых имён почти гарантированы |
| `Type[Args].method(...)` / `[]T.method(...)` generic-static | производный `static_key` внутри `Member`-арма → тот же `static_methods` | derived (тип, метод) | то же, что static + доп. эвристика распознавания формы (`TurboFish`/`Path(["__array",elem])`) | тот же класс, что static |
| `Self.new()` внутри generic-static/instance тела | `sigs.self_type` (RefCell, мутируется `normalize_item`) → `static_methods` | `Self` → enclosing type name | резолвит `Self` ПРАВИЛЬНО (единственная точка, где реально нужен контекст, которого чекер тут не даёт напрямую — но и чекер, и callnorm сходятся на одном и том же `f.receiver.type_name`) | не дефект — этот один узкий случай УЖЕ корректен |

**Не покрыто вообще** (`_ => return None` в конце `try_normalize_call`):
сложный `func` (например Path на generic-параметр — `T.deserialize(d)`,
см. волна-5 Часть 1 B11ai — callnorm даже не пытается, т.к. `T` не входит ни
в одну таблицу; для этих форм именованные/дефолтные аргументы, если бы они
были, легли бы НЕнормализованными на codegen).

## 2. Почему это дублирует чекер

Чекер уже делает ПОЛНОЕ, type-aware разрешение overload'а для КАЖДОГО
call-site (`resolve_instance_method_return_arity`,
`overload_applicability`+`compat_spans` — types/mod.rs ~10600-10651) и,
когда выбор однозначен, пишет `ModuleEnv.resolved_callees: HashMap<ExprId,
Span>` (call-site → **span декларации**, `f.span`/`chosen.span`/
`callee.span`). `callnorm.rs` строился РАНЬШЕ этого канала (Plan 46, до
Plan 172.1's resolved_callees) и никогда не был подключён к нему —
`normalize_module(module: &mut Module)` до волны-5 не принимала вообще
никакого чекер-состояния. Свои три таблицы — по сути ВТОРАЯ, более грубая
overload-резолюция (arity/имя, без типов), обслуживающая ровно ту же задачу
(«для этого call-site — какие params?»), которую чекер уже решил лучше.

Конкретный риск (не только «медленнее» — потенциально НЕВЕРНО): `emit_c.rs`
имеет СВОЙ ОТДЕЛЬНЫЙ «single-key fallback» для method-диспатча (~37544,
`E_RECV_METHOD_MISMATCH`, "single-key fallback резолвит имя в чужой тип...
last-wins") — тот же класс ошибки (имя метода резолвится в ЧУЖОЙ тип при
коллизии), СУЩЕСТВУЮЩИЙ и ЗАДОКУМЕНТИРОВАННЫЙ уже В КОДЕ (не привнесён этой
сессией) как error-diagnostic, а НЕ silent-wrong-answer — то есть где-то в
пайплайне ЭТОТ класс коллизий уже подтверждённо возникает на практике
(`examples/real_world/orm_decorators`: `FilterIter.len()` резолвится в
`WriteBuffer`). `callnorm.rs`'s `instance_by_name`-таблица — тот же корень
проблемы на ОДИН pass раньше: она молча ВЫКЛЮЧАЕТ нормализацию (не падает),
но если бы у коллизирующего метода был named/default arg, желаемого
десугаринга бы не случилось и codegen получил бы `CallArg::Named` сырым (см.
§3).

## 3. Downstream-риск: что происходит, если callnorm НЕ нормализовал

Если `try_normalize_call` вернула `None` (в т.ч. из-за коллизии/overload),
`CallArg::Named`/пропущенные default-параметры доходят до `emit_c.rs`
КАК ЕСТЬ. Специализированные call-emission пути ЧАСТИЧНО умеют `CallArg::
Named` (byref-обёртка ~31944/48090, record-lit ~32572/32602 — но это ДРУГОЙ
семантический случай, анонимный record-литерал, не вызов функции), но
родовой финальный tail (`for a in args { arg_strs.push(self.emit_expr(a.
expr())?); }`, найден в нескольких местах ~32377/33xxx) эмитит `a.expr()` —
разворачивает `CallArg::Named` в ГОЛОЕ значение-выражение и кладёт его
ПОЗИЦИОННО В ПОРЯДКЕ ИСХОДНОГО СПИСКА args, **отбрасывая имя параметра**.
Для call-site, где args ЛЕКСИЧЕСКИ уже совпадают с param-порядком (типичный
случай — named args пишут для читаемости, не для reorder) результат
случайно совпадает; при РЕАЛЬНОМ reorder (`f(b: 2, a: 1)` при `fn f(a,b)`)
это была бы TIXAYA неверная перестановка аргументов. Не нашёл живого
воспроизводимого кейса в текущем корпусе (см. §4 — единственный instance-
метод с default-параметром во всём std, `str.to_int`, имя уникально →
коллизии не бывает), поэтому это ЛАТЕНТНЫЙ риск, не подтверждённый баг —
именно поэтому точечный фикс (§4) сделан как STRICT SUPERSET
(byte-parity-доказанный), а не через сконструированный red-тест.

## 4. Один экземпляр (реализовано, волна-5)

**Клетка матрицы:** ВСЕ формы (free/static/generic-static/instance) ×
аспект «какие params использовать для bind+desugar» — единая точка входа
`try_normalize_call`.

**Фикс:** `normalize_module`/`collect_sigs` теперь принимают
`resolved_callees: &HashMap<ExprId, Span>` (в реальном пайплайне —
`ModuleEnv.resolved_callees`, уже вычисленный чекером НА ЭТОЙ ЖЕ стадии,
до `callnorm` — ровно то, что `chain_norm`'s сосед по пайплайну уже читает
для `resolved_types`). `Sigs` получил `by_span: HashMap<Span, Vec<Param>>`
(индекс ПО ДЕКЛАРАЦИИ, а не по имени/типу — строится тем же проходом по
`module.items`, что и старые три таблицы) и хранит клон `resolved_callees`.
`try_normalize_call` теперь СНАЧАЛА пробует
`resolved_callees.get(&e.id).and_then(|sp| by_span.get(sp))` — если чекер
уже выбрал ОДНУ декларацию для этого ИМЕННО call-site, её params
используются НАПРЯМУЮ, минуя все три грубые таблицы целиком. `None`
(чекер не дал однозначного пика — 0/≥2 type-compatible overload'ов, или
форма вне его резолвера, напр. erased generic-mono тело) → падение на
СТАРУЮ эвристику, без изменений (byte-identical fallback).

Синтаксический флаг `is_static_generic_recv` (нужен ДАЛЬШЕ по функции для
receiver-hoist — «obj это TYPE-выражение или VALUE-ресивер») вычисляется
НЕЗАВИСИМО от источника params (чистая проверка формы `obj.kind` —
`TurboFish`/`Path(["__array",_])`), так что канальный fast-path не теряет
эту информацию.

**Плюмбинг:** `normalize_module`'s единственный параметр `&mut Module` не
менялся структурно — добавлен ВТОРОЙ параметр. 9 call-site'ов по всему
дереву (`compiler-codegen/src/{main,test_runner,doc/test_runner}.rs`,
`nova-cli/src/{main,bench/run,bench/field_cache_wallclock}.rs`) обновлены:
там, где `ModuleEnv`/`check_env`/`bench_env`/`build_env` уже был в scope —
передан `&env.resolved_callees` (5 сайтов, реальный build/test/bench
пайплайн); там, где чекер-состояние ОТБРАСЫВАЛОСЬ существующим кодом ДО
этой правки (explain-cache diagnostic-режим `nova-codegen check`,
doc-test интерпретатор-путь) — передан пустой `HashMap::new()`,
воспроизводя ПРЕЖНЕЕ поведение byte-identical (эти два пути и раньше не
видели чекер-канал; волна-5 их не расширяла — вне узкого blast radius).

**Гейт (доказательство):** нет живого red-кейса в текущем корпусе (§3) →
byte-parity подход per заданию. release-бинарь, полный прогон:
- `spec_tests/conformance` (мега-CU, БЕЗ `--jobs`): **PASS 468 / FAIL 0 /
  SKIP 12** — байт-в-байт база.
- `std/src/collections`: **PASS 13 / FAIL 0 / SKIP 6** — база.
- `std/src/data`: **PASS 3 / FAIL 0 / SKIP 3** — база.
- Доп. корроборация (не входит в обязательный гейт, для уверенности при
  широком blast radius правки): `examples/` — PASS 18 / FAIL 10 / SKIP 8;
  все 10 FAIL — ПРЕ-СУЩЕСТВУЮЩИЕ и задокументированные (orm_decorators
  single-key-fallback §3, orm_demo E7001 closure-param-bind, nova-tls
  order-sensitive CC-FAIL, `_wip` unsupported-syntax заглушки,
  `net/echo_server` bind-timeout окружения) — ни один текст ошибки не
  относится к callnorm/argbind.

## 5. Что НЕ сделано (за пределами узкого экземпляра)

- Инструментальный live-red-тест (искусственный: два типа с одноимённым
  методом с default-параметром в одном CU) НЕ создавался — задание просило
  ОДИН экземпляр перевода, не новый тест-фикстур; byte-parity на реальном
  корпусе — достаточное доказательство для strict-superset правки.
- `emit_c.rs`'s собственный «single-key fallback» (~37544, ДРУГОЙ,
  codegen-стадийный дубль того же класса резолва) НЕ трогался — отдельный
  facet (ближе к facet B/method-dispatch codegen, не facet C/callnorm),
  вне периметра этой волны.
- Полный перевод `pick_static_params`/`instance_by_name`/`sigs.free` на
  ПОЛНОЕ вычищение (снос грубых таблиц) НЕ делался — они остаются
  необходимым fallback для call-site'ов, которые чекер НЕ резолвит
  однозначно (генерик erased-тела, форвард-ссылки внутри одного prelude-
  файла до полного checker-прохода и т.п.); только ДОБАВЛЕН приоритетный
  канал перед ними.

**Диагноз (debug-бинарь, `RUST_BACKTRACE=1`, точный трейс):**
`emit_test → emit_block_stmts → emit_expr(assert) → emit_call →
emit_expr(Binary ==) → infer_expr_c_type(Block) → infer_expr_c_type(Call,
рекурсия) → infer_call_ret_c → resolve_instance_call_subst →
infer_expr_c_type(Ident("tag")) → panic`. `try_normalize_call` (`callnorm.rs`)
на верхнем `let base = match func.kind { TurboFish{base}=>base, _=>func }`
СНИМАЕТ top-level `TurboFish{base:Member}` (метод-turbofish форма — Plan
91.1, СТРУКТУРНОЕ ЗЕРКАЛО generic-static-ctor формы `Member{obj:
TurboFish{base:Ident(Type)}}`, где turbofish на ОДИН уровень ГЛУБЖЕ), после
чего `base.kind` — плоский `Member`, резолвится как обычный instance-call
через `sigs.instance_by_name`, и проходит двухфазный Block-rewrite (синтезит
свежие `let tag=…`/`let note=…` с `ExprId::UNSET`). `final_func` при этом
клонируется КАК ЕСТЬ (receiver-hoist арм проверяет `func.kind==Member`,
проваливается — `func.kind` это TurboFish — receiver НЕ хостится, но
исходный TurboFish{type_args} сохраняется нетронутым в клоне). Проблема —
НЕ в этом; проблема в том, что метод-turbofish call-emission
(`infer_call_ret_c` → `resolve_instance_call_subst`, ОБЕ функции — frozen/
W1-зона этой волны 196, НЕ трогать) делает EAGER inference аргументов
(`infer_expr_c_type(arg.expr())`) для резолва метод-уровневого `U` — и
делает это ДО того, как охватывающий Block успел заэмитить свои `let`ы
(`var_types` пуст для синтезированных имён на этот момент — чистое
type-inference предшествует emission этого КОНКРЕТНОГО Block, т.к. вызывается
СНАРУЖИ для определения типа Block-как-выражения, напр. операнд `==`).

**Фикс (`callnorm.rs`, МОЯ зона, НЕ frozen):** guard в начале
`try_normalize_call` — если `func.kind` ИМЕННО TurboFish (не пусто) И
`base.kind` (после снятия) — Member, ПРОПУСТИТЬ нормализацию (`return None`)
для ЭТОЙ формы целиком, тем же путём, что и остальные «не покрыто» формы
(нижний `_ => return None`). Не регрессия: если такой call НЕ нуждался в
normalize (все аргументы позиционные без дефолтов) — behaviour byte-identical
(needs_norm и так был бы false); если нуждался — раньше ВСЕГДА крашило
(минимальный репро уже краш), теперь — либо компилируется как есть (если
codegen’s собственный дефолт/арность справится), либо честная arity-ошибка
компиляции (не крэш). Строка кода: `if matches!(func.kind,
ExprKind::TurboFish{..}) && matches!(base.kind, ExprKind::Member{..}) {
return None; }` сразу после вычисления `base`.

generic_default.nv` (новый файл) пинует ДВЕ рабочие пересечения: (1)

перегрузку, инференс типа возврата берёт ОТ ДРУГОЙ (str вместо int) →
CC-FAIL (str/int type clash) в моём репро; в общем случае — потенциально
ТИХО неверный ответ. Задокументировано `[M-196-freefn-arity-overload-
default-ret-mismatch]` в `docs/plans/backlog-followups.md` (P1, Plan 196

этим атомом: другой механизм (checker `f1_check_call` + frozen
