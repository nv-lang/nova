## 0. TL;DR (резюме дизайна)

- **Находка.** И `f1_check_call` (`types/mod.rs:10279`), и `resolve_return_channel` (`types/mod.rs:9631`) УЖЕ
  вычисляют полную карту подстановки generic-параметров на чек-тайме (`unify_type` → `subst: HashMap<String,
  TypeRef>` соотв. solver `Constraint::Eq` на fresh-var), применяют её к возврату и **ВЫБРАСЫВАЮТ** — в канал
  уходит только тип-результат (196.4), сама карта — локальная переменная, гибнущая в конце арма.
- **Канал.** `node_substs: HashMap<ExprId, Vec<(String, ResolvedType)>>` — упорядочен по декларации
  generic-параметров каллиси. Ключ — СУЩЕСТВУЮЩИЙ `call_id: ExprId` (тот же, что у `resolved_types` /
  `resolved_callees`; `f1_check_call` его уже принимает, `emit_call` уже принимает — `emit_c.rs:30460`).
  Значение — карта `(имя параметра → КОНКРЕТНЫЙ ResolvedType)`, лоуэрится в C через `resolved_type_to_c` (D315).
- **Плумбинг** — механический зеркал `resolved_callees` (5 точек, §6.1). НОВОГО инференса нет: точки записи
  переиспользуют УЖЕ вычисленные `subst`/solver-bindings из Stage-1a/1b.
- **Потребление.** Три движка (`resolve_mono_type_args` / `resolve_method_level_subst` / инлайн) → тонкие
  читатели канала: `node_substs[call_id]` есть → взять готовое; промах → текущий re-inference (переходный
  fallback). Consumer-scaffolding УЖЕ частично построен (Plan 172.12 A1″: `rt_slots_from_args` +
  `subst_map_adopt_rt`, `emit_c.rs:2557`–`2721`) — 196.5 заменяет per-arg re-derive на ОДИН авторитетный
  channel-lookup.
- **Гейт** — propose-then-verify (тот же принцип 1a): адоптируем channel-subst ТОЛЬКО когда он лоуэрится в тот
  же C-string, что легаси (`subst_map_adopt_rt` уже реализует ровно эту byte-identity-проверку).
- **Мономорфизация.** `compute_mono_name` (`18387`) + `register_mono_method_instance` (`20461`) читают карту из
  канала вместо результата re-inference — subst = ФАЗА (чекер), манглинг = чистый lowering (rustc-эталон).
- **Объём/риск.** Ядро (плумбинг + запись в 2 продюсерах + флип 3 читателей на channel-first) — МАЛОЕ-СРЕДНЕЕ,
  ~150–300 строк; риск средний, снят propose-then-verify + fresh-var (anti-d119) + fallback. НЕ MIR, НЕ новый
  IR-узел; erased-residual остаётся законным (residual `TypeParam` → канал не пишет → mono-erased как сейчас).

## 1. Проблема — почему 196.4-канала НЕ хватает (граница return-type vs subst-value)

196.4 доказал: return-type-канал (`resolved_types[call.id]`) закрывает потребителей, которым нужен ТИП
результата (`resolve_result_option_ret`, `resolve_result_te`, sum-возврат). Но Q10 показал ПО КОДУ, что
mono-движки принимают НЕ `Call`-Expr и им нужен НЕ тип-результат, а **сами значения** `T`/`U`:

- `resolve_mono_type_args` возвращает `Vec<(String, String)>` = `(имя-параметра → C-тип)` — это вход для
  `compute_mono_name` (манглинг `Nova_foo____nova_int`). Return-type тут не помогает: из `Result[int,str]`
  нельзя однозначно восстановить, что `T=int, E=str`, если возврат — не тождественная функция параметров
  (напр. `fn zip[A,B](a []A, b []B) -> []Pair[A,B]` или `-> int` при generic-параметрах, участвующих лишь в
  аргументах). Нужна КАРТА, не её свёртка.
- Отсюда «three hand-duplicated inference engines» синхронно чинились (см. `emit_c.rs:19053`–`19060`,
  `[M-exp-promotion-blockers]`): каждый движок повторно решает `param TypeRef ⋂ arg C-type → param`, что чекер
  уже решил для type-check вызова, но не экспортировал.

**Вывод.** Недостающий фундамент — не «канал типа результата» (он есть, 196.4), а **канал значения
подстановки**: per-call `ExprId → упорядоченная карта generic-параметров каллиси в конкрет вызывающего`.

## 2. РАЗВЕДКА-1 — где чекер УЖЕ вычисляет subst и ВЫБРАСЫВАЕТ (по коду, nova-spike @ `a90a557d0`)

Две точки чек-тайма вычисляют полную unify-карту и роняют её на пол — ровно то, что должно попасть в канал.

### 2.1 `f1_check_call` — free-fn / static generic-возврат (`types/mod.rs:10597`–`10618`)

```
let mut subst: HashMap<String, TypeRef> = HashMap::new();
for (p, a) in callee.params.iter().zip(args.iter()) {
    if p.is_variadic { break; }
    if let Some(a_ty) = self.infer_expr_type(a.expr(), scope) {
        let _ = crate::const_fn_trampoline::unify_type(&p.ty, &a_ty, &callee_gs_inner, &mut subst);
    }
}
if !subst.is_empty() {
    let concrete = crate::const_fn_trampoline::subst_type_ref_pub(ret_ty, &subst);
    ... self.resolved_types_buf.borrow_mut().insert(call_id, rt);   // ← только ВОЗВРАТ уходит в канал
}                                                                    // ← `subst` гибнет здесь
```

`subst` содержит именно `node_substs` для этого call-site (`callee_gs_inner` = generic-имена каллиси, значения
— конкрет вызывающего). В канал (`resolved_types_buf[call_id]`) кладётся ТОЛЬКО применённый к возврату
результат; **сама `subst` — локальная, выбрасывается**. Ключ `call_id` уже на руках (параметр функции,
`10288`). Это Stage-1b-продюсер 196.4 (static/free-fn).

### 2.2 `resolve_return_channel` — instance-метод, carrier + method-level (`types/mod.rs:9631`–`9727`)

Solver-путь Stage-1a. Строит fresh-`TypeVar` per carrier-имя (`9658`) И per method-generic (`9662`, anti-d119
by construction), даёт `Constraint::Eq(param↔arg)` для method-level (`9688`–`9724`), затем:

```
let mut solver = Solver::new();
solver.unify(&recv_pattern, &concrete_recv).ok()?;         // carrier-binding в solver.subst
for (a, b) in &extra_eqs { let _ = solver.unify(a, b); }   // method-generic binding в solver.subst
let resolved_ret = solver.resolve(&ret_template);          // ← применяем к возврату
solver.as_concrete_leaf(&resolved_ret)                     // ← отдаём ТОЛЬКО тип-результат
```

`solver.subst: HashMap<TypeVar, Ty>` после двух `unify` содержит ПОЛНУЮ подстановку (carrier `T`→элемент,
method `U`→из аргумента). Наружу уходит только `as_concrete_leaf(resolved_ret)`. **Per-параметрные bindings
роняются вместе с `solver`.** Чтобы получить `node_substs`, достаточно после `solve` прочитать
`solver.resolve(Ty::Var(v))` для каждой пары `(имя, var)` из `vars` (карта `9657`) и снять `as_concrete_leaf` —
БЕЗ нового инференса, тот же solver.

## 4. РАЗВЕДКА-3 — ключ канала: `ExprId` достаточно (формы вызова)

| Форма | AST | Ключ | Комментарий |
|---|---|---|---|
| instance `obj.method(args)` | `Call{func:Member{obj,name}}` | `call_id` вызова | продюсер — `resolve_return_channel`/`f1_expr_inner` Call-арм |
| static `Type.method(args)` | `Call{func:Path[Type,method]}` / `Member` | `call_id` | продюсер — `f1_check_call` static-арм (`10549`+) |
| free-fn `f(args)` | `Call{func:Ident(f)}` | `call_id` | `f1_check_call` free-fn-арм |
| turbofish `Type[T].method(args)` / `f[U](args)` | `Member{obj:TurboFish}` / `Call{func:TurboFish}` | `call_id` внешнего Call | type-args ЯВНЫ → Source-1 обоих движков; канал их просто фиксирует |

`ExprId` достаточно во ВСЕХ формах: один вызов = один `Call`-узел = один `call_id`. Turbofish не требует
особого ключа — явные type-args это входные данные того же продюсера (он их и так подставляет). Метод-vs-static
различаются продюсером-писателем, не ключом. **Никакого нового идентификатора не нужно** (§10 минимальность).

## 5. rustc-эталон (recon-4)

rustc: `typeck` пишет `node_substs` (ныне `node_args`) в `TypeckResults`, keyed by `HirId` — per-call-site
`SubstsRef` (`&[GenericArg]`, упорядочен по декларации). mono-collector берёт `Instance{def_id, substs}` и
codegen лоуэрит БЕЗ повторного инференса. **Наш аналог БЕЗ MIR:** `node_substs: HashMap<ExprId,
Vec<(String,ResolvedType)>>` ⟷ `TypeckResults.node_substs: HirId → SubstsRef`. `ExprId`⟷`HirId`,
`Vec<(String,ResolvedType)>`⟷`SubstsRef` (порядок декларации). Разница со Stage-2: у нас НЕТ `Instance` как
worklist-объекта и НЕТ типизированного IR — карта одноразовая в side-table, манглинг/регистрация читают её на
месте эмита. Это ровно перенос «codegen перевыводит subst» → «чекер решает subst, codegen читает» = целевая
арх 196 (mono = ФАЗА, не codegen-side-effect).

## 6. ДИЗАЙН канала `node_substs`

### 6.1 Тип + плумбинг (механический зеркал `resolved_callees`)

```rust
// Ключ — call-site ExprId (тот же, что resolved_types/resolved_callees).
// Значение — subst каллиси, УПОРЯДОЧЕННЫЙ по декларации generic-параметров
// (carrier-generics ресивера, затем method-level — тот же порядок, что читают
// compute_mono_name / infer_type_param_binding). Vec, не HashMap: порядок
// параметров нужен манглингу; имя дублируется как ключ-строка для читателей,
// которые ищут по имени (три движка) — O(k), k≤~4, дешевле HashMap.
type NodeSubsts = HashMap<ExprId, Vec<(String, ResolvedType)>>;
```

Пять точек плумбинга — ТОЧНАЯ калька существующего `resolved_callees` (проверено по коду nova-spike):
1. `TypeCheckCtx.node_substs: RefCell<HashMap<ExprId, Vec<(String,ResolvedType)>>>` — рядом с
   `resolved_callees` (`types/mod.rs:3332`) и `resolved_types_buf` (`3342`); инициализация в `new`
   (`~3925`).
2. Лифт после чек-пасса: `env.node_substs = ctx.node_substs.take();` — рядом с `1892`/`1895`.
3. `ModuleEnv.node_substs: pub HashMap<ExprId, Vec<(String,ResolvedType)>>` — рядом с `resolved_types`
   (`874`) / `resolved_callees` (`888`).
4. `CEmitter.node_substs` (поле, `emit_c.rs:894`/`905`) + сеттер `set_node_substs` (зеркал
   `set_resolved_types` `2441` / `set_resolved_callees` `2453`).
5. Проводка в `main.rs` — тот же сайт, где зовут `set_resolved_types`/`set_resolved_callees`.

Никаких новых модулей/типов: `ResolvedType` уже сериализуемо-lossless (D315), `ExprId` уже ключ каналов.

### 6.2 Точки ЗАПИСИ в чекере (переиспользуют уже вычисленный subst — НЕ новый инференс)

**Продюсер А — `f1_check_call` (`10608`).** В существующем `if !subst.is_empty()`-блоке (где сейчас пишется
только возврат) ДОБАВИТЬ параллельную запись карты по `callee_gs_inner` в порядке `callee.generics`:

```
// уже есть: subst: HashMap<String,TypeRef>, concrete-возврат материализован
let ordered: Vec<(String, ResolvedType)> = callee.generics.iter()
    .filter_map(|g| subst.get(&g.name).map(|tr| (g.name.clone(), ResolvedType::from_type_ref(tr))))
    .filter(|(_, rt)| !rt_mentions_any(rt, &callee_gs_inner) && !rt_mentions_any(rt, gs)) // тот же гейт
    .collect();
if ordered.len() == callee.generics.len() {           // все параметры разрешены → пишем
    self.node_substs.borrow_mut().insert(call_id, ordered);
}                                                      // иначе — не пишем (residual, §7)
```

**Продюсер Б — `resolve_return_channel` (`9725`).** После `solver.solve`/двух `unify` прочитать per-параметр
из ТОГО ЖЕ solver (bindings уже есть в `solver.subst`):

```
// уже есть: vars: HashMap<String,TypeVar>, solver с carrier+method bindings
let ordered: Vec<(String, ResolvedType)> = decl_order_names.iter()   // carrier-generics ++ method_names
    .filter_map(|n| vars.get(n).and_then(|v|
        solver.as_concrete_leaf(&solver.resolve(&Ty::Var(*v))).map(|rt| (n.clone(), rt))))
    .collect();
// вернуть (resolved_ret, ordered); вызывающий кладёт ordered в node_substs[call_id]
```

`resolve_return_channel` — `&self`; запись в канал делает вызывающий (`f1_expr_inner` Call-арм /
`infer_method_call_channel_type`), у которого `call_id` на руках. Сигнатуру расширить: вернуть
`Option<(ResolvedType, Vec<(String,ResolvedType)>)>` вместо `Option<ResolvedType>` (byte-parity: тип-результат
не меняется, subst — additive).

**Критично:** обе записи — ADDITIVE и в ТЕХ ЖЕ блоках, что 196.4-запись возврата. Никакого нового прохода,
нового `unify`, нового solver. Subst уже посчитан для type-check вызова — мы перестаём его выбрасывать.

### 6.3 Propose-then-verify гейт (как 1a — уже реализован для потребителя)

Consumer-адопция канала гейтится `subst_map_adopt_rt` (`emit_c.rs:2664`), который УЖЕ адоптирует RT в subst
ТОЛЬКО когда `resolved_type_to_c(rt) == legacy_c_string` (byte-identity). 196.5 подаёт в него `node_substs`-RT
вместо `rt_slots_from_args`-RT — гейт тот же, byte-identity сохраняется по построению: промах/несовпадение →
`Raw`-fallback → легаси-строка. `NOVA_A1PP_TRACE` меряет adopt-vs-raw yield.

Продюсер-сторона: `debug_assert!` (только debug) что channel-subst, лоуэренный в C, совпадает с тем, что
даёт легаси re-inference на первых прогонах — как `resolve_return_channel` SHADOW-assert Stage-1a. После
зелёного корпуса SHADOW снимается.

### 6.4 Потребление codegen (три движка → тонкие читатели, fallback переходный)

Каждый из трёх движков получает channel-first преамбулу, тело остаётся fallback:

```
fn resolve_mono_type_args(&self, fn_decl, turbofish_refs, args, call_id) -> Result<Vec<(String,String)>,String> {
    // channel-first: чекер уже решил subst для этого call-site
    if let Some(ordered) = self.node_substs.get(&call_id) {
        if ordered.len() == fn_decl.generics.len() {
            return Ok(ordered.iter().map(|(n, rt)| (n.clone(), self.resolved_type_to_c(rt)?)).collect());
        }
    }
    // ... существующее тело (Sources 1..4) как FALLBACK на переходный период ...
}
```

`resolve_method_level_subst` — аналогично, но канал даёт carrier+method целиком; `receiver_subst`-аргумент
остаётся для сайтов, где ресивер-subst приходит из объемлющего mono-контекста (не из этого call-site).
Инлайн-третий-движок — та же преамбула. **Сигнатуры трёх движков += `call_id: ExprId`** (тривиально: сайты ⊂
`emit_call`, `call_id` в скоупе).

### 6.5 Влияние на мономорфизацию (`register_generic_instances` читает канал)

`compute_mono_name` (`18387`) и `register_mono_method_instance` (`20461`) потребляют `Vec<(String,String)>`,
который сегодня — выход re-inference (`resolve_mono_type_args`). После §6.4 этот выход СТАНОВИТСЯ прямым
чтением канала → манглинг лоуэрит уже-решённый чекером subst = чистая механическая подстановка (rustc-эталон:
`compute_mono_name`⟷`Instance`-name mangling). НИКАКОЙ правки самих `compute_mono_name`/`register_*` не нужно —
меняется только ИСТОЧНИК их аргумента (re-inference → канал). Это и есть «mono = ФАЗА, читающая node_substs».

## 7. Минимальность — границы Stage-1 (node_substs)

**НЕ делаем:**
- НЕ вводим типизированный IR-узел, НЕ материализуем `Instance` как worklist-объект, НЕ строим MIR.
- НЕ трогаем `compute_mono_name`/`register_generic_instances`/`compute_generic_type_c_name` внутри (только
  ИСТОЧНИК их subst-аргумента).
- НЕ пишем канал для ЗАКОННО-erased тел: вызов внутри `fn foo[T]`, где `T` не связан вызывающим → параметр
  остаётся residual `TypeParam` → `ordered.len() != generics.len()` → **канал НЕ пишется**, mono-erased
  (`void*`/`Nova_T*`) как сейчас. Это не ошибка — это граница erased-body (тот же гейт, что `mark_type_params`
  / `as_concrete_leaf → None`).
- НЕ трогаем замороженную зону волны-1 `infer_call_ret_c` (`46293`–`48883`) — её сайты (`47607`,
  `infer_mono_method_ret_with_args`) флипаются на канал ТОЛЬКО когда волна-1 освободит зону.

**Делаем:** канал = существующий `ExprId`-ключ + `Vec<(String,ResolvedType)>`-значение; запись = перестать
выбрасывать УЖЕ вычисленный subst в двух продюсерах; чтение = channel-first преамбула у трёх движков + смена
источника mono-манглинга. Ядро локально; residual остаётся законным; erased-тела residual — по-прежнему валидны.

## 9. Оценка объёма / рисков / поэтапность

**Объём.** Плумбинг (§6.1) — механический, ~40 строк по 4 файлам. Запись (§6.2) — ~30 строк в 2 продюсерах
(переиспользуют посчитанное). Чтение (§6.4) — ~15 строк преамбулы ×3 движка + прокидка `call_id` в 3 сигнатуры
и ~8 сайтов. Итого ядро ~150–300 строк, БЕЗ нового файла (solver/`ResolvedType`/A1″ уже есть). Основной труд —
НЕ код, а верификация + пер-D флип (Stage-C ниже).

**Риски и митигизация.**
- **d119 spelling-collision** — снят конструктивно: продюсер-Б на fresh числовых `TypeVar` (`VarGen`);
  продюсер-А по `callee.generics`-именам В ПРЕДЕЛАХ одного каллиси (нет пересечения space вызывающего).
- **byte-parity дрейф** — propose-then-verify: `subst_map_adopt_rt` byte-identity-гейт (уже есть) + продюсер
  `debug_assert!` SHADOW. Промах → `Raw`-fallback → легаси-строка. Прецедент 196.4 Stage-1a зелёный (95/0).
- **over-annotation erased-тел** — гейт `ordered.len()==generics.len()` + `as_concrete_leaf`/`mentions_any`:
  residual → не пишем. Идентично текущему `mark_type_params`-контракту.
- **mono side-effects** (typedef-регистрация в легаси-движках) — канал ЧИСТ (только subst-значения);
  регистрация остаётся в emit-pass. Пропущенный typedef → CC-FAIL = сигнал (ловим ICR-трейсом + targeted-conf).
- **frozen-zone связанность** — MIXED-сайты (`47607`) не флипаем до волны-1; статус 🔄 до тех пор.

**Поэтапность (гейт на каждом шаге — conformance 95/0 + byte-parity + `nova test std` без новых фейлов):**
- **Stage-A (плумбинг + запись, SHADOW):** §6.1 + §6.2, канал ПИШЕТСЯ, но НЕ читается (ADDITIVE →
  byte-identical). Гейт: 95/0, `debug_assert!` SHADOW не падает, `node_substs` непуст на generic-корпусе.
  Приёмка: канал заполнен для d119/d122-форм (трейс-дамп размера карты > 0).
- **Stage-B (channel-first чтение):** §6.4 преамбула у трёх движков + смена источника mono (§6.5). Гейт: 95/0
  + byte-parity C-вывода + `NOVA_A1PP_TRACE` adopt-доля растёт, raw-доля падает; ни один сайт не регрессит.
  Приёмка: `resolve_method_level_subst`/`resolve_mono_type_args` дают тот же subst из канала, что легаси.
- **Stage-C (пер-D флип + detach):** прогнать ICR-bucket-трейс → довести subst-бакеты до нуля для покрытых
  форм; флипнуть d119/d122/d30/d85/d52 в 196.3-трекере на channel-first; SEP-движки → удаление, SHARED →
  `panic!("[MIGRATED]")`. Приёмка: приёмка (1)-(5) 196.3 ПО КОДУ (легаси мёртв/недостижим, сведение полное).
- **Stage-D (зависит от волны-1):** флип carrier-chain-веток + удаление зонных легаси-движков вместе с
  коллапсом `infer_call_ret_c`.

**Критерии приёмки per-стадия (сводно):**
| Стадия | Гейт | Приёмка |
|---|---|---|
| A | 95/0 + SHADOW-assert цел | канал непуст на generic-формах (трейс) |
| B | 95/0 + byte-parity + adopt↑/raw↓ | channel-subst ≡ legacy-subst (ни один сайт не регрессит) |
| C | 95/0 + ICR-subst-бакеты→0 | d119/d122/d30/d85/d52 channel-first, легаси detach/panic, приёмка (1)-(5) |
| D | 95/0 после коллапса | `infer_call_ret_c` пуст, зонные движки удалены |

## 10. Связь с 196.4 и волной-1

- **196.4 (return-type-канал) ⟂ 196.5 (subst-value-канал)** — комплементарны, не пересекаются: 196.4 пишет
  `resolved_types[call.id]` (что вернул вызов), 196.5 — `node_substs[call.id]` (чем инстанцирован каллиси).
  Оба продюсера 196.5 — те же блоки, что 196.4-запись возврата (переиспользуют тот же посчитанный subst) →
  196.5 буквально «второй insert рядом с первым».
- **Встреча волн:** `infer_call_ret_c` коллапсирует, когда каждый `Call` покрыт Канал-1 ∨ Канал-2 ∨
  `node_substs`. 196.5 закрывает именно subst-зависимые бакеты (mono/method-generic), которые Канал-2 не
  покрывал (return-type не восстанавливает subst). Волна-1 гасит остальные ветки bottom-up.

## 11. Путь к 196.5 (сводка)

1. Владелец санкционирует развилку (A) (построить канал) — 196.5 = развилка (A) уровня subst-value (196.4 был
   (A) уровня return-type).
2. Stage-A: плумбинг + запись SHADOW (одна волна, SEP от волны-1, worktree `nova-pXX`).
3. Stage-B: channel-first чтение трёх движков + mono-источник.
4. Stage-C: пер-D флип d119/d122 → d30/d85 → Q5-sum, detach SEP, panic SHARED.
5. Stage-D: синхронно с коллапсом `infer_call_ret_c` волной-1 — удаление зонных легаси + carrier-chain флип.

**Язык-меняющего эффекта НЕТ** (чисто внутренний канал компилятора, поведение байт-идентично) → спек-амендмент

## §W1-instance addendum — per-instance конкретика 6 W1-армов (закрытие gap RESUME-4)

> **Контекст.** RESUME-4 (`AGENT_HEARTBEAT.txt` [RESUME-4]) инструментировал вход шести армов
> (`B05`/`B06*`/`B07`/`B07r`/`B11c`/`B11x`, все внутри `infer_call_ret_c`, `emit_c.rs:47343`) и получил
> `node_substs[expr.id]` = **850/850 NONE** (B07=310, B07r=242, B06=289, B11c=6, B05=2, B11x=1). Эти армы —
> W1-ядро (generic-instance-method / iterator-adapter mono-клоны). Ниже — дизайн-ответ: почему канал
> `node_substs` (Stage-A) СТРУКТУРНО не покрывает эти сайты и как дать им per-instance subst минимальными
> средствами. Проверено по коду дерева `w1-core-substs @ bd7bf6588`.

### W1.1 Диагноз по коду (не по премисе задания)

Три факта из дерева:

1. **`node_substs` keyed by ГОЛЫЙ `ExprId`, писатель — чекер** (`types/mod.rs:896` тип; продюсеры `10717`
   producer-A, `14243` B-method-residual, `14333` B-carrier). Один шаблонный `call_id` эмитится N раз (по разу
   на mono-клон объемлющего тела) с РАЗНЫМИ конкретными T/U. `HashMap<ExprId,_>` физически не вмещает N
   значений на ключ — one-call-id : many-instances.
2. **Гейт продюсеров** — `!subst.is_empty()` + `ordered.len()==callee.generics.len()` И
   `!typeref_mentions_any(tr, gs)`, где `gs` = generic-scope ОБЪЕМЛЮЩЕГО тела (`10678`/`10698` producer-A,
   `14185` producer-B). Для этих 6 сайтов резолвнутое значение упоминает T объемлющего шаблона → гейт запись
   ВЫБРАСЫВАЕТ (§7 erased-body контракт — намеренно, не баг). Множества «node_substs покрыл» и «арм жив»
   дизъюнктны ПО ПОСТРОЕНИЮ.
3. **Чекер НЕ хранит residual-subst per-call.** `resolved_callees: HashMap<ExprId, Span>` (`types/mod.rs:888`)
   — только Span каллиси, НЕ карта подстановки. За call-site чекер материализует лишь `resolved_types`
   (тип-РЕЗУЛЬТАТ, 196.4) и Span. Никакого «residual T-биндинга» в side-table нет (Q5 «для Call мало» —
   подтверждено буквально: единственные per-call side-table = `resolved_types_buf` + `resolved_callees` +
   `node_substs`, все три либо тип-результат, либо Span, либо полностью-конкретный subst).

### W1.2 Ключевая находка: per-instance данные УЖЕ в emit-state

Все 6 армов достижимы ТОЛЬКО во время эмита mono-клона объемлющего generic-тела (RESUME-4: из конкретного
top-level caller'а их бы упредил Channel-2/196.4, и они были бы NO-HIT). В этот момент emit-state содержит всё,
что арму нужно:

- `current_type_subst` (`emit_c.rs:1468`) населён инстанс-подстановкой объемлющего тела (`{T_объемл→int}`) —
  ставится `mem::replace(&mut self.current_type_subst, seeded)` в mono-обёртке (`18707`, `19879`, `20576`,
  `20652`, `20763`, `34504`, `34866`, `35028`, …) на время эмита тела клона.
- Ресивер арма `rt` УЖЕ конкретен (`Vec____nova_int`) — именно потому, что `infer_expr_c_type(obj)` прогнал
  его тип через `current_type_subst`.
- Carrier-аргументы каллиси доступны СТРУКТУРНО (не парсингом строки): `generic_type_instance_info[Nova_{rt}]`
  → `(base, Vec<ResolvedType>)` (`emit_c.rs:1557`; арм читает на `47858`). Mono-имя — лишь КЛЮЧ реестра, args
  хранятся типизированным `ResolvedType` (A1‴, `47863`).
- Method-level generics (U из `zip[U]`/`map[U]`) арм связывает из КОНКРЕТНЫХ args и closure-return через
  `infer_type_param_binding` (`emit_c.rs:19655`), затем лоуэрит возврат тем же хвостом —
  `value_aware_subst_to_ref`/`apply_type_subst_to_ref` (`18173`/`20367`).

**Вывод.** Недостающего КАНАЛА нет. Per-instance конкретика целиком carried конкретным ресивером-инстансом +
конкретными args, оба материализованы в emit-state к моменту арма (а причина их конкретности — тот самый
`current_type_subst`). 6 армов — это 6 рукописных копий ОДНОЙ операции: «дан структурный signature каллиси +
конкретный ресивер-инстанс + args → собрать per-instance subst каллиси → лоуэрить возврат через него». Проблема
не «нет данных», а «нет единой точки» + «для per-instance факта ошибочно выбран checker/bare-ExprId канал».

### W1.3 rustc-сверка — какой канал ПРАВИЛЬНЫЙ для per-instance

У rustc per-call `node_args` (ex-`node_substs`) в `TypeckResults` — RESIDUAL, в терминах ОБЪЕМЛЮЩЕГО body
(может содержать параметры). КОНКРЕТНЫЙ per-instance subst codegen берёт НЕ из `node_args`, а из
`Instance{def_id, args}` — композицией `node_args.instantiate(enclosing_instance.args)` во время
mono-коллектора. Т.е. даже у эталона `node_substs` НЕ несёт per-instance значения — их даёт mono-инстанцирование.
Наш аналог `enclosing_instance.args` = ровно `current_type_subst`. Значит правильный per-instance «канал» для 6
армов — это НЕ checker-side `node_substs`, а POST-mono `current_type_subst`-композиция (rustc: `Instance.args`).
Это прямо диктует вариант ниже (feedback-rustc-as-reference: mono = ФАЗА/collector-шаг со substs).

### W1.4 Три варианта — оценка по коду

**(i) instance-keyed канал `node_substs_per_instance[(template_call_id, mono_instance_key)]`.**
- Писатель: чекер инстансов НЕ знает → писать может ТОЛЬКО emit. Но чтобы ЗАПОЛНИТЬ запись, надо СНАЧАЛА
  реконструировать subst — ровно та работа, которую хотим убрать. Канал вырождается в мемо-кэш
  emit-вычисленного, нового знания не даёт. `mono_instance_key` берётся из `current_type_subst`/mono-имени —
  тех же данных, что арм и так держит. (У rustc эквивалент — `Instance` как worklist-объект; у нас его нет,
  §7 явно «НЕ материализуем Instance».)
- Покрытие: **0/6 армов снято самим каналом** (кэш поверх реконструкции, не замена её).
- Объём: +плумбинг составного ключа (~40 строк) + fill = реконструкция (без экономии) → нетто ПОЛОЖИТЕЛЬНЫЙ,
  армы живы. Отклонить как первичный механизм.

**(ii) POST-mono emit-продюсер (collector-шаг). — РЕКОМЕНДОВАН.**
- На эмите каждого mono-клона codegen владеет `current_type_subst`. ОДИН унифицирующий помощник собирает subst
  каллиси из (структурный signature каллиси из реестров `generic_type_templates`/`generic_type_methods`/
  `mono_method_decls` — что армы и так читают) + (конкретный ресивер-инстанс из `generic_type_instance_info` +
  method-level из args под `infer_type_param_binding`), хвост — существующий `value_aware_subst_to_ref`.
  Значения выведены из чекер-структур + instance-substs, БЕЗ реверса C-строк, БЕЗ нового checker-канала.
- rustc-верно: `node_args.instantiate(Instance.args)` = «mono = ФАЗА со substs» (§5, W1.3); это НЕ второе окно
  — помощник вызывается в тех же emit-точках, где сейчас сидят армы, при уже-выставленном `current_type_subst`.
- Покрытие: **6/6** — все 6 армов делят предусловие (конкретный ресивер-инстанс + emit-state); помощник —
  их общий знаменатель → 6 армов КОЛЛАПСируют в один резолвер внутри `infer_call_ret_c` (целевой снос ICR).
- Гейт: propose-then-verify — C-тип помощника == C-тип легаси-арма на корпусе перед снятием арма (та же
  дисциплина, что Stage-B `subst_map_adopt_rt` byte-identity / SHADOW-assert `2775`). Доказуемо.
- Объём: извлечь ~1 помощник (~60-100 строк, консолидируя логику, размазанную по 6 армам) + тонкая
  propose-verify обёртка; снятие армов даёт НЕТТО-ОТРИЦАТЕЛЬНУЮ дельту (6 армов ~500+ строк → один помощник).
  Нового плумбинга НЕТ (переиспользует `current_type_subst`/реестры/`value_aware_subst_to_ref`). Риск средний,
  полностью под гейтом.

**(iii) прямое чтение residual в армах: чекер пишет residual `node_substs` (снять gs-гейт для отдельного
residual-поля) + арм применяет `current_type_subst`.**
- Чекер residual per-call НЕ хранит (W1.1 п.3) → нужен НОВЫЙ checker-продюсер: вычислить+сохранить
  residual-subst (с TypeParam) keyed by call_id, отдельное поле, ослабленный гейт. Это НЕ «переиспользование
  существующего», а второй параллельный канал — против минимальности.
- Даже построив его: армы ОСТАЮТСЯ (каждый всё равно применяет `current_type_subst` к residual + лоуэрит
  возврат) — `infer_call_ret_c` НЕ коллапсирует, ICR не снимается. Композиция residual∘`current_type_subst` —
  ровно то, что (ii) делает на эмите одним шагом; (iii) дробит на две фазы и два канала без выигрыша.
- Риск утечки: канал, который все прочие потребители считают полностью-конкретным, начнёт нести TypeParam —
  ровно то, от чего gs-гейт защищает (§7). RESUME-4 доказал: сайты residual ПО ПОСТРОЕНИЮ (значение упоминает
  объемлющий T) → ослабление гейта записало бы TypeParam-запись, а не «спуриозно упущенный конкрет».
- Покрытие: **0/6** (армы переплюмблены, не сняты); нужен новый checker-продюсер. Отклонить.

### W1.5 Рекомендация — вариант (ii): единый emit-side резолвер + снятие армов под гейтом

Ввести ОДИН emit-side резолвер, консолидирующий per-instance реконструкцию, общую для всех 6 армов:

```
fn resolve_instance_call_subst(
    &self, call_id: ExprId, callee_decl: &FnDecl,
    recv_instance_rt: &str, args: &[CallArg],
) -> Vec<(String, ResolvedType)>   // упорядочен по декларации: carrier ++ method-level
```

Тело — фактор-аут уже-существующей логики армов:
1. **carrier-биндинг** из конкретного ресивера-инстанса: `generic_type_instance_info[Nova_{recv_instance_rt}]`
   → `(base, Vec<ResolvedType>)`, zip с `template.generics` (как B07 `47865`-`47869`);
2. **method-level биндинг** из args/closure-return: `infer_type_param_binding(param.ty, arg_c, …)` по
   method-generics (как B07 `47983`-`48007`, B05 `47701`-`47738`);
3. **хвост-лоуэринг** возврата — существующий `value_aware_subst_to_ref(callee.return_type, subst)`
   (`.or_else` на `resolve_result_option_ret`/`apply_type_subst_to_ref`, как B06a `47778`-`47780`).

Return-потребители (сами 6 армов) заменяются на `resolve_instance_call_subst(…)` → `value_aware_subst_to_ref`.
Никакого нового канала/поля/составного ключа; `current_type_subst` уже выставлен mono-обёрткой (обеспечивает
конкретность ресивера/args, шаги 1-2 читают конкрет).

**Поэтапность (гейт на каждом шаге — conformance 98/0 + byte-parity C + `std/collections` PASS 13/0/6):**

- **W1-i.A (extract + SHADOW).** Вынести реконструкцию в помощник; на входе каждого из 6 армов `debug_assert!`,
  что C-тип помощника == C-тип легаси-арма (инвертированный `w1_probe` RESUME-4: probe уже умеет обходить те же
  850 сайтов). Поведение НЕ меняется — армы ведут, помощник только сверяется. Приёмка: помощник воспроизводит
  легаси-C-тип на 850/850 probe-сайтах (conf + std/collections), SHADOW-assert цел.
- **W1-i.B (flip + retire, propose-verify).** Generic-instance-method путь зовёт помощник → `value_aware_subst_
  to_ref` под byte-identity гейтом (адоптируем ТОЛЬКО если C-строка совпала с легаси, иначе — легаси-fallback,
  как `subst_map_adopt_rt`). Снимать в порядке размера бакета: **B07 (310) → B07r (242) → B06 (289) → B11c (6)
  → B05 (2) → B11x (1)**. Каждое снятие — под гейтом ICR-бакет→0 (`NOVA_TRACE_ICR=1`) + byte-parity + 98/0 +
  std без новых фейлов. B07r несёт side-effect `register_generic_instances_in_typeref` (`48043`) — перенести в
  помощник ДО снятия (иначе пропущенная регистрация инстанса → segfault на `.collect()`/`.next()`, §9 риск
  «mono side-effects»).
- **W1-i.C (опц. мемоизация).** Если профиль покажет горячую повторную реконструкцию на `(call_id, instance)` —
  кэш под составным ключом (вариант (i) КАК КЭШ, не источник знания). НЕ требуется для корректности; вводить
  только по метрике.

**Приёмка (сводно):**

| Шаг | Гейт | Приёмка |
|---|---|---|
| W1-i.A | 98/0 + SHADOW-assert цел | помощник ≡ легаси-C-тип на 850/850 probe (conf + std/collections) |
| W1-i.B | 98/0 + byte-parity + ICR-бакеты B05/B06/B07/B07r/B11c→0 | 5 армов сняты/недостижимы, C байт-идентичен, B07r-регистрация перенесена |
| W1-i.C | 98/0 | (опц.) кэш только при доказанной горячей точке |

**Покрытие армов по вариантам:** (i) **0/6** · (ii) **6/6** · (iii) **0/6**.

**Объём (ii):** нетто-ОТРИЦАТЕЛЬНАЯ дельта строк (консолидация 6 армов ~500+ строк в 1 помощник ~60-100 +
propose-verify обёртка). 0 нового плумбинга, 0 нового checker-канала, 0 составного ключа. НЕ MIR, НЕ новый
IR-узел. Риск средний, снят propose-then-verify + существующим `w1_probe` + переносом B07r-side-effect.

**Замечание о B11x.** `B11x_novaarray_methods` (`49153`) — не user-generic dispatch, а таблица билтин-методов
`NovaArray_<elem>` (`get`→`NovaOpt_elem`, `push`→`@`, `len`→int и т.п.); elem — из конкретного имени ресивера.
Снимается тем же emit-state-derived помощником ЛИБО остаётся тривиальной билтин-таблицей (крошечная, низкий
риск, последняя в очереди). В любом случае каналы (i)/(iii) её не касаются (нет generic-subst) — довод в пользу
(ii)-семейства как единственного, кто закрывает и её.

**Граница с волной-1 / §8.** W1-i снимает return-type арма `infer_call_ret_c` — это шаг к терминальному
коллапсу кластера (§8 п.5). Зонные carrier-chain ветки (`infer_mono_method_ret_with_args` `43924`, вызовы
`47154`/…) флипаются на тот же помощник синхронно с опустошением зоны волной-1 (Stage-D), не в этой волне.
