# Plan 196.5 — Канал `node_substs`: per-call значения подстановки generic-параметров

**Родитель:** [196-one-truth-closeout.md](196-one-truth-closeout.md) (матрица одного окна + rustc-эталон).
**Пара:** [196.4-call-resolvedtype-channel.md](196.4-call-resolvedtype-channel.md) (канал РЕЗУЛЬТАТ-ТИПА вызова,
Stage-1a/1b — уже в main). **Триггер:** «Q10-подтверждение» + «★★ СТРУКТУРНАЯ НАХОДКА (Q5)» в
[196.3-wave2-d-driven.md](196.3-wave2-d-driven.md) — Tier-2-ядро волны-2 (`resolve_mono_type_args` /
`resolve_method_level_subst` + инлайн instance-dispatch = «three hand-duplicated inference engines», плюс
`infer_method_level_return_for_sum` / `resolve_result_option_ret` / `resolve_result_te`) заблокировано
отсутствием у Nova аналога rustc `node_substs`: per-call-site ЗНАЧЕНИЙ подстановки (`T`→конкрет), вычисленных
чекером и СОХРАНЁННЫХ. **Статус:** 🔄 ДИЗАЙН (opus-разведка, worktree `nova-spike`, ветка `node-substs-design`).
**Это ДИЗАЙН, НЕ реализация — кода канала в этом заходе НЕ пишется.**

> Разница с 196.4 в одной фразе: 196.4 материализует **РЕЗУЛЬТАТ вызова** (`Result[int,str]`) в
> `resolved_types[call.id]`; 196.5 материализует **САМУ подстановку** (`T→int, E→str`) в `node_substs[call.id]`.
> Первого достаточно return-type-потребителям; второго требуют mono-манглинг и method-generic-движки, которым
> нужны отдельные ЗНАЧЕНИЯ параметров, не только их «свёртка» в тип возврата.

## 0. TL;DR (резюме дизайна)

- **Находка.** И `f1_check_call` (`types/mod.rs:10279`), и `resolve_return_channel` (`types/mod.rs:9631`) УЖЕ
  вычисляют полную карту подстановки generic-параметров на чек-тайме (`unify_type` → `subst: HashMap<String,
  TypeRef>` соотв. solver `Constraint::Eq` на fresh-var), применяют её к возврату и **ВЫБРАСЫВАЮТ** — в канал
  уходит только тип-результат (196.4), сама карта — локальная переменная, гибнущая в конце арма.
- **Канал.** `node_substs: HashMap<ExprId, Vec<(String, ResolvedType)>>` — упорядочен по декларации
  generic-параметров каллиси. Ключ — СУЩЕСТВУЮЩИЙ `call_id: ExprId` (тот же, что у `resolved_types` /
  `resolved_callees`; `f1_check_call` его уже принимает, `emit_call` уже принимает — `emit_c.rs:30460`).
  Значение — карта `(имя параметра → КОНКРЕТНЫЙ ResolvedType)`, лоуэрится в C через `resolved_type_to_c` (D315).
- **Плумбинг** — механический зеркал `resolved_callees` (5 точек, §6.1). НОВОГО инференса нет: точки записи
  переиспользуют УЖЕ вычисленные `subst`/solver-bindings из Stage-1a/1b.
- **Потребление.** Три движка (`resolve_mono_type_args` / `resolve_method_level_subst` / инлайн) → тонкие
  читатели канала: `node_substs[call_id]` есть → взять готовое; промах → текущий re-inference (переходный
  fallback). Consumer-scaffolding УЖЕ частично построен (Plan 172.12 A1″: `rt_slots_from_args` +
  `subst_map_adopt_rt`, `emit_c.rs:2557`–`2721`) — 196.5 заменяет per-arg re-derive на ОДИН авторитетный
  channel-lookup.
- **Гейт** — propose-then-verify (тот же принцип 1a): адоптируем channel-subst ТОЛЬКО когда он лоуэрится в тот
  же C-string, что легаси (`subst_map_adopt_rt` уже реализует ровно эту byte-identity-проверку).
- **Мономорфизация.** `compute_mono_name` (`18387`) + `register_mono_method_instance` (`20461`) читают карту из
  канала вместо результата re-inference — subst = ФАЗА (чекер), манглинг = чистый lowering (rustc-эталон).
- **Объём/риск.** Ядро (плумбинг + запись в 2 продюсерах + флип 3 читателей на channel-first) — МАЛОЕ-СРЕДНЕЕ,
  ~150–300 строк; риск средний, снят propose-then-verify + fresh-var (anti-d119) + fallback. НЕ MIR, НЕ новый
  IR-узел; erased-residual остаётся законным (residual `TypeParam` → канал не пишет → mono-erased как сейчас).

## 1. Проблема — почему 196.4-канала НЕ хватает (граница return-type vs subst-value)

196.4 доказал: return-type-канал (`resolved_types[call.id]`) закрывает потребителей, которым нужен ТИП
результата (`resolve_result_option_ret`, `resolve_result_te`, sum-возврат). Но Q10 показал ПО КОДУ, что
mono-движки принимают НЕ `Call`-Expr и им нужен НЕ тип-результат, а **сами значения** `T`/`U`:

- `resolve_mono_type_args` возвращает `Vec<(String, String)>` = `(имя-параметра → C-тип)` — это вход для
  `compute_mono_name` (манглинг `Nova_foo____nova_int`). Return-type тут не помогает: из `Result[int,str]`
  нельзя однозначно восстановить, что `T=int, E=str`, если возврат — не тождественная функция параметров
  (напр. `fn zip[A,B](a []A, b []B) -> []Pair[A,B]` или `-> int` при generic-параметрах, участвующих лишь в
  аргументах). Нужна КАРТА, не её свёртка.
- Отсюда «three hand-duplicated inference engines» синхронно чинились (см. `emit_c.rs:19053`–`19060`,
  `[M-exp-promotion-blockers]`): каждый движок повторно решает `param TypeRef ⋂ arg C-type → param`, что чекер
  уже решил для type-check вызова, но не экспортировал.

**Вывод.** Недостающий фундамент — не «канал типа результата» (он есть, 196.4), а **канал значения
подстановки**: per-call `ExprId → упорядоченная карта generic-параметров каллиси в конкрет вызывающего`.

## 2. РАЗВЕДКА-1 — где чекер УЖЕ вычисляет subst и ВЫБРАСЫВАЕТ (по коду, nova-spike @ `a90a557d0`)

Две точки чек-тайма вычисляют полную unify-карту и роняют её на пол — ровно то, что должно попасть в канал.

### 2.1 `f1_check_call` — free-fn / static generic-возврат (`types/mod.rs:10597`–`10618`)

```
let mut subst: HashMap<String, TypeRef> = HashMap::new();
for (p, a) in callee.params.iter().zip(args.iter()) {
    if p.is_variadic { break; }
    if let Some(a_ty) = self.infer_expr_type(a.expr(), scope) {
        let _ = crate::const_fn_trampoline::unify_type(&p.ty, &a_ty, &callee_gs_inner, &mut subst);
    }
}
if !subst.is_empty() {
    let concrete = crate::const_fn_trampoline::subst_type_ref_pub(ret_ty, &subst);
    ... self.resolved_types_buf.borrow_mut().insert(call_id, rt);   // ← только ВОЗВРАТ уходит в канал
}                                                                    // ← `subst` гибнет здесь
```

`subst` содержит именно `node_substs` для этого call-site (`callee_gs_inner` = generic-имена каллиси, значения
— конкрет вызывающего). В канал (`resolved_types_buf[call_id]`) кладётся ТОЛЬКО применённый к возврату
результат; **сама `subst` — локальная, выбрасывается**. Ключ `call_id` уже на руках (параметр функции,
`10288`). Это Stage-1b-продюсер 196.4 (static/free-fn).

### 2.2 `resolve_return_channel` — instance-метод, carrier + method-level (`types/mod.rs:9631`–`9727`)

Solver-путь Stage-1a. Строит fresh-`TypeVar` per carrier-имя (`9658`) И per method-generic (`9662`, anti-d119
by construction), даёт `Constraint::Eq(param↔arg)` для method-level (`9688`–`9724`), затем:

```
let mut solver = Solver::new();
solver.unify(&recv_pattern, &concrete_recv).ok()?;         // carrier-binding в solver.subst
for (a, b) in &extra_eqs { let _ = solver.unify(a, b); }   // method-generic binding в solver.subst
let resolved_ret = solver.resolve(&ret_template);          // ← применяем к возврату
solver.as_concrete_leaf(&resolved_ret)                     // ← отдаём ТОЛЬКО тип-результат
```

`solver.subst: HashMap<TypeVar, Ty>` после двух `unify` содержит ПОЛНУЮ подстановку (carrier `T`→элемент,
method `U`→из аргумента). Наружу уходит только `as_concrete_leaf(resolved_ret)`. **Per-параметрные bindings
роняются вместе с `solver`.** Чтобы получить `node_substs`, достаточно после `solve` прочитать
`solver.resolve(Ty::Var(v))` для каждой пары `(имя, var)` из `vars` (карта `9657`) и снять `as_concrete_leaf` —
БЕЗ нового инференса, тот же solver.

### 2.3 Итог РАЗВЕДКИ-1

| Продюсер | Форма вызова | Карта уже вычислена | Как достать в канал (без нового инференса) |
|---|---|---|---|
| `f1_check_call` `10597` | free-fn / static generic | `subst: HashMap<String,TypeRef>` (`unify_type`) | по `callee_gs_inner` собрать `(имя → from_type_ref(subst[имя]))` |
| `resolve_return_channel` `9631` | instance-метод (carrier+method) | `solver.subst` на fresh-var + `vars: HashMap<String,TypeVar>` | по `vars` собрать `(имя → as_concrete_leaf(solver.resolve(Var)))` |

Оба УЖЕ гейтят «материализуем только полностью-разрешённое» (`typeref_mentions_any` / `as_concrete_leaf` →
`None`). Тот же гейт годится каналу: параметр, оставшийся residual (erased-тело вызывающего), в `node_substs`
НЕ пишется — законная граница (§7).

## 3. РАЗВЕДКА-2 — потребители и их входы (что каждый ждёт от канала)

Ключ ко всем: `call_id: ExprId` доступен в `emit_call` (`emit_c.rs:30460`) — все нижеперечисленные сайты ⊂
`emit_call`.

- **`resolve_mono_type_args`** (`emit_c.rs:18755`) — free-fn / static generic, вход `(fn_decl, turbofish_refs,
  args)`, выход `Vec<(String,String)>`. Тело — ~10 ad-hoc Sources (1 turbofish, 2/2b/2c/2d/2e/2e-bis array/fn/
  closure/instance-info, 2f forwarding, 3 return-context, 4 effect-clause), каждый гоняет
  `infer_type_param_binding` по C-типам. **Ждёт от канала:** готовую `Vec<(имя, ResolvedType)>` по `call_id`;
  лоуэрит `resolved_type_to_c`. Сайты: `36398`, `36678`, `47607` (последний — в замороженной зоне волны-1).
- **`resolve_method_level_subst`** (`emit_c.rs:19706`) — instance-метод с method-level `[U]`, вход `(fn_decl,
  args, receiver_subst, diag_context)`, выход `Vec<(String,String)>`. Steps 1/2/2f/3 (non-closure, closure-
  return, ident-forwarding, effect-clause). **Ждёт:** `node_substs[call_id]` за method-level часть;
  `receiver_subst` он получает извне (carrier). Сайты: `31540`, `32082`, `32349`, `34844`, `35137`.
- **Инлайн instance-method dispatch** (третий движок, ~`emit_c.rs:34308`+ `subst_pending`→`type_subst`) —
  hand-duplicated с двумя выше (сам код признаёт это, `19059`). **Ждёт:** тот же `node_substs[call_id]`.
- **`infer_type_param_binding_rt`** (`emit_c.rs:2557`) + `rt_slots_from_args` (`2623`) + `channel_arg_rt`
  (`2611`) + `subst_map_adopt_rt` (`2664`) — **Plan 172.12 A1″: УЖЕ читает `resolved_types[arg.id]` per-arg и
  адоптирует RT в `current_type_subst` под byte-identity-гейтом.** Это consumer-сторона будущего канала, но
  сейчас RE-DERIVE per-call из АРГУМЕНТОВ. 196.5 подменяет источник: вместо `rt_slots_from_args(params, args,
  names)` — прямой `node_substs[call_id]` (одна карта, авторитетна; per-arg RT-slots остаются fallback).
- **`infer_method_level_return_for_sum`** (`emit_c.rs:44357`), **`resolve_result_option_ret`** (`18054`),
  **`resolve_result_te`** (`45003`) — return-type-потребители (частично закрыты 196.4-каналом), но внутри
  тоже принимают `receiver_subst` / re-derive method-generic → выигрывают от `node_substs` как источника subst.
- **Ветки carrier-chain волны-1** — внутри `infer_call_ret_c` (`46293`–`48883`, замороженная зона; напр.
  `47607` выше, `infer_mono_method_ret_with_args` `43757` вызывается из `47154`/`47255`/…). Вход — carrier
  subst через `build_recv_subst`/`current_type_subst`. **Ждут** канал так же, но правятся ТОЛЬКО когда волна-1
  освободит зону (Stage-1d).
- **Мономорфизация:** `compute_mono_name(base, &type_subst)` (`18387`) + `register_mono_method_instance(fn_decl,
  type_subst, mono_name, recv_type)` (`20461`) + `register_mono_instance` (`20404`) — потребляют
  `Vec<(String,String)>`. **Ждут:** ту же карту из канала (→ манглинг = чистый lowering по уже-решённому subst).

## 4. РАЗВЕДКА-3 — ключ канала: `ExprId` достаточно (формы вызова)

| Форма | AST | Ключ | Комментарий |
|---|---|---|---|
| instance `obj.method(args)` | `Call{func:Member{obj,name}}` | `call_id` вызова | продюсер — `resolve_return_channel`/`f1_expr_inner` Call-арм |
| static `Type.method(args)` | `Call{func:Path[Type,method]}` / `Member` | `call_id` | продюсер — `f1_check_call` static-арм (`10549`+) |
| free-fn `f(args)` | `Call{func:Ident(f)}` | `call_id` | `f1_check_call` free-fn-арм |
| turbofish `Type[T].method(args)` / `f[U](args)` | `Member{obj:TurboFish}` / `Call{func:TurboFish}` | `call_id` внешнего Call | type-args ЯВНЫ → Source-1 обоих движков; канал их просто фиксирует |

`ExprId` достаточно во ВСЕХ формах: один вызов = один `Call`-узел = один `call_id`. Turbofish не требует
особого ключа — явные type-args это входные данные того же продюсера (он их и так подставляет). Метод-vs-static
различаются продюсером-писателем, не ключом. **Никакого нового идентификатора не нужно** (§10 минимальность).

## 5. rustc-эталон (recon-4)

rustc: `typeck` пишет `node_substs` (ныне `node_args`) в `TypeckResults`, keyed by `HirId` — per-call-site
`SubstsRef` (`&[GenericArg]`, упорядочен по декларации). mono-collector берёт `Instance{def_id, substs}` и
codegen лоуэрит БЕЗ повторного инференса. **Наш аналог БЕЗ MIR:** `node_substs: HashMap<ExprId,
Vec<(String,ResolvedType)>>` ⟷ `TypeckResults.node_substs: HirId → SubstsRef`. `ExprId`⟷`HirId`,
`Vec<(String,ResolvedType)>`⟷`SubstsRef` (порядок декларации). Разница со Stage-2: у нас НЕТ `Instance` как
worklist-объекта и НЕТ типизированного IR — карта одноразовая в side-table, манглинг/регистрация читают её на
месте эмита. Это ровно перенос «codegen перевыводит subst» → «чекер решает subst, codegen читает» = целевая
арх 196 (mono = ФАЗА, не codegen-side-effect).
