# План 231 — Выход из цикла точечных фиксов (систематизация качества компилятора)

**Статус:** ✅ УТВЕРЖДЁН владельцем (2026-07-26, «ДА» — порядок: аудит+матрица немедленно, IR — дизайн-нота).
**Связи:** 196 (единый канал — родитель трека В), 221.1 (реестр — симптоматика), test-conventions.md.

## 0. Диагноз (по фактам сессий 221.x, честно)

1. **AST-only эмиссия без IR** — семантика размазана по emit_c per-синтаксическую-позицию.
   Доказательство: fn-newtype семья = 7 разрывов ОДНОЙ конструкции по позициям
   (№53→78→90→96→97→104→116: let / method-return / member-call / closure-param /
   match-bind / record-literal). Фикс каждой позиции локален ПО ПОСТРОЕНИЮ — ощущение
   владельца «чинится локально, соседнее бажит» структурно точное.
2. **Контекстозависимость CU** — код зелёный standalone и в малом CU, красный в
   folder-CU (№122 Permit/@cleanup, №99 entry-порядок). Спека валидировалась на малых
   файлах; реестры компилятора несут per-CU состояние с порядковыми эффектами.
3. **Энфорс-гэпы** — спека декларирует «иначе compile error», проверка не написана:
   №95 (if-let), №106 (launder-паттерны), №113 (`!!`/Fail), №114 (D55-⛔), №119 (линт R9),
   №120 (handler-типы) — шесть за три дня, все найдены вопросами владельца, не гейтом.
4. **Покрытие от фич, не от матрицы** — одна фикстура на решение; «конструкция × позиция
   × контекст CU» не покрывается. №107: «паттерн не покрывался ни одной фикстурой».
   Живой код (polaris) находит больше, чем спек-корпус.

## 1. Трек А — Спека-энфорс-аудит (дёшево, немедленно)

Механическая инвентаризация: греп spec/decisions по маркерам нормативности
(«иначе compile error», «запрещён», «обязан», «= ошибка», «E_[A-Z_]+» без реализации)
→ таблица «норма | D-блок | энфорс реализован? | neg-фикстура есть?».
Выход: конечный список беззубых норм → пакет энфорс-окон (класс №113/106/120).
Исполнение: sonnet-волна (греп+сверка с чекером), приёмка интегратора.
Мерило: 0 норм без энфорса ЛИБО явная D-пометка «não энфорсится, потому что …».

## 2. Трек Б — Матрица контекстов + дифференциальный прогон (средняя цена, до релиза)

1. **Матрица фикстур**: генератор «конструкция × позиция» для горячих конструкций
   (fn-newtype, Option[fn], sum-lift, consume/@cleanup, generic-инстанс) ×
   (let / arm / param / return / field / element / generic-arg / map-literal).
   Не все клетки — приоритет клеткам, где семьи уже стреляли.
2. **Дифференциальный прогон**: каждый runtime-тест исполняется в ДВУХ контекстах —
   standalone и внутри folder-CU; расхождение вердиктов = автоматический FAIL
   класса №122/№99 (ловится машиной, не вопросом владельца).
3. Инвариант тихих дыр: «check зелёный ⇒ build зелёный» на всём корпусе —
   CC-FAIL после чистого check (класс №114б) = красный гейта, не «известное».

## 3. Трек В — 196-финал: инвентаризация легаси-веток (форсировать)

Сейчас канал — надстройка: данные в resolved_*, потребители — те же разбросанные
ветки emit_c. Перейти от «сносим по мере встречи багов» к инвентаризации:
полный список легаси-веток разбора/типов в emit_c (icr_trace-класс) → для каждой:
канальный потребитель есть? NO-HIT-доказательство есть? → снос пакетами.
Мерило: счётчик живых легаси-веток → 0. Ведётся в 196-плане, здесь — обязательство темпа.

## 4. Трек Г — Дизайн-нота typed-IR (стратегический выход)

rustc-путь: AST → typed-IR (типы/резолв ИЗ ЧЕКЕР-КАНАЛА, один лоуэринг конструкции
для всех позиций) → C. Единственный ход, закрывающий класс «per-position багов»
по построению. Реалистичный горизонт — финал 196 ПОСЛЕ v0.1; СЕЙЧАС — дизайн-нота
(структура IR, какие каналы уже дают нужные данные, порядок миграции эмиссии),
чтобы сегодняшние канальные фиксы ложились в его сторону, а не поперёк.

## 5. Порядок и гейты

А (волна, дни) → Б.2 дифф-прогон (в test_runner, дни) → Б.1 матрица (итеративно,
приоритет по семьям) → В (постоянный темп в 196) → Г (нота сейчас, реализация после v0.1).
Каждая волна — стандартные гейты (мега-CU + флагман + внешние репы). Найденное
трек-А/Б — в реестр 221.1 обычным порядком.
