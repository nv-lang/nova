## ★ ПЕРВЫЙ ШАГ — инвентаризация недостающих тестов (директива владельца 2026-07-12)

**ДО миграции** — сначала инвентаризация тест-покрытия. Для КАЖДОЙ D-фичи (инвентарь-функции) определить,
каких тестов НЕ ХВАТАЕТ **по плану** (матрица 196: формы `static` / `generic-static` / `+кросс-модуль` /
`приватные` × аспекты `args` / `generic-args` / `default` / `generic-default` + edge-формы, что legacy
обрабатывал в РАЗНЫХ местах). Сравнить с 307 существующими conformance (таблица ниже) → **записать ПРОБЕЛЫ per
D сюда** (какие ситуации не покрыты).

По ходу — можно СРАЗУ добавить недостающие тест-файлы, ЕСЛИ это оптимально, **НО без исправлений компилятора и
без прогонов/проверок** (только НАПИСАТЬ тесты — установить покрытие; НЕ чинить компилятор, НЕ верифицировать,
НЕ мигрировать). Миграция/закрытие D — отдельным заходом ПОТОМ.

## Метод (идти по инвентарю → D)

Для КАЖДОЙ сиблинг-функции инвентаря:
1. Сопоставить её **D-фиче** (языковой фиче, которую она обслуживает; уточнить точные D-номера).
2. Покрыть фичу **полным conformance-набором** (`d<NNN>_*.nv`; red-до/green-после где применимо). Тесты —
   независимые файлы, параллельно-безопасны обеим волнам.
3. **Переписать на новый путь** (резолв/инференс → чекер → `resolved_types`/`resolved_callees`, per «Целевая
   архитектура» в 196; rustc-эталон; **no new window / §3** — сходимость на существующий путь, не новый сайт).
4. **ЗАКРЫТИЕ D = D работает через новый компилятор (по архитектуре) + удаление legacy-функции ИЛИ
   `panic!("[MIGRATED-<D>]")`** (если переплетена / SHARED-хелпер зовётся волной-1 → detach/panic, НЕ удалять
   пока зовётся).

## ★★ ПРИЁМКА КАЖДОГО D (принятие работ оркестратором — ПО КОДУ, НЕ по отчёту агента)

Оркестратор при принятии закрытого D ОБЯЗАН перепроверить ПО КОДУ (греп + чтение), не доверяя отчёту:
1. **Одно окно в ПРАВИЛЬНОМ месте.** D резолвится ОДИН раз в ЧЕКЕРЕ → `resolved_types`/`resolved_callees` →
   codegen ЧИТАЕТ (не перевыводит). В колонке «Закрыто в» — КОНКРЕТНАЯ функция нового пути; убедиться, что это
   ПРАВИЛЬНОЕ место (чекер/канал, а НЕ новый codegen-сайт = не «второе окно №2»).
2. **Legacy для D МЁРТВ.** Соответствующие legacy-функции/ветки/места УДАЛЕНЫ ИЛИ `panic!("[MIGRATED-<D>]")`.
   Грепом убедиться: работа D физически НЕ может пойти через legacy (нет тихого fallback).
3. **Legacy было РАЗБРОСАНО → новое СВЕДЕНО.** Legacy реализовывал эту фичу в РАЗНЫХ местах (несколько функций/
   веток). Убедиться ПО КОДУ, что ВСЕ они сведены в ОДНО окно — не осталось параллельного legacy-обработчика той
   же фичи в другом месте (грепнуть все места, что обслуживали D).
4. **Полное тест-покрытие ВСЕХ ситуаций.** Тесты покрывают ВСЕ возможные ситуации, которые legacy обрабатывал в
   разных местах (не только happy-path: edge-формы, generic/кросс-модуль/приватные варианты из матрицы 196).
   Перепроверить, что ни одна legacy-ситуация не осталась непокрытой.
5. **Гейты зелёные.** conformance 95/0 + byte-parity + `nova test std` без новых фейлов.

**Только при (1)-(5), подтверждённых оркестратором ПО КОДУ, статус D → ✅.** Иначе — вернуть агенту с
конкретикой (что не сведено / не покрыто / где ещё жив legacy).

**Закрыто в** — конкретная функция НОВОГО пути (чекер/канал), где D теперь резолвится (заполняет волна-2, сверяет

мигрирует, закрывает — флип статуса + запись «Закрыто в».
**Одно окно ✔ (проверено оркестратором по коду)** — заполняется ТОЛЬКО оркестратором при приёмке ✅, НЕ агентом.
Значение = вердикт ПО КОДУ (греп+чтение), а не по отчёту агента: D резолвится ОДИН раз в чекере → канал → codegen
ЧИТАЕТ (не перевыводит); legacy для D физически мёртв (удалён / `panic!("[MIGRATED-<D>]")`, тихого fallback нет);
все ранее разбросанные legacy-места сведены в ОДНО окно; покрытие полное (все ситуации матрицы 196). `✔` = приёмка
(1)-(5) подтверждена мной по коду; `—` = ещё не принято (миграции/закрытия нет — 🔍 значит лишь coverage-проверено).
Эта колонка ОТДЕЛЯЕТ «покрыто тестами» (🔍, «Закрыто в») от «закрыто через одно окно в правильном месте и лично
проверено оркестратором» (✅).
