## [M-172.14-vrange-nv-route] — 🟢 ЗАКРЫТ Plan 194 Ф.3 атом A3 (2026-07-15) — анализ 2026-07-10, закрытие ниже

**Цель маркера:** маршрутизировать `v[a..b]` (Vec range-slice) через .nv-тело
`Vec[T] @index(r Range) -> Self` (slice.nv:34) вместо codegen-магии
`nova_vec_slice_chk`/`_nochk` — «единый источник» bounds-check + конструирования
вида (принцип владельца: «bounds-check и конструирование вида живут в .nv
@index/@get — codegen только вызывает + плейсмент»).

**СДЕЛАНО (не требует маршрутизации):** перф-цель — 0-alloc размещение
не-эскейпящего дескриптора вида — УЖЕ достигнута волной view-descriptor-sret
через sret `_out`-механизм (`nova_vec_slice_chk_out` в caller-стек-слот;
view_descriptor_stack.nv δ alloc=0). «Плейсмент»-половина принципа владельца
закрыта; открыта только «единый источник»-половина.

**ТРИ КОНКРЕТНЫХ БЛОКЕРА полной маршрутизации (все — язык-семантика, требуют
решения владельца + D-амендмент, feedback-lang-change-needs-spec):**

1. **Модель безопасности среза меняется под `--contracts=off`.**
   `nova_vec_slice_chk` (array.h:987) — ВСЕГДА-вкл hard `nv_panic` на OOB,
   независимо от политики контрактов (codegen элидит на `_nochk` ТОЛЬКО на
   verifier-proven-in-range сайтах). `@index(Range)` bounds-check =
   `requires r.start >= 0 && r.end >= r.start && r.end <= @len` — контракт-
   прекондишн, ЭЛИДИРУЕТСЯ под `--contracts=off`. Маршрутизация → срез Vec
   теряет bounds-check под contracts=off (сегодня always-on) = safety-регрессия.

2. **Byte-parity: panic-сообщение пиновано тестами.**
   `nova_tests/plan96/neg_slice_oob_to.nv` / `neg_slice_a_gt_b.nv` ожидают
   `panics "Vec: slice"` (сообщение `Vec: slice [a..b] out of bounds for
   length N`, D239). `@index`'s `requires` даёт `nova_contract_violation`
   («precondition failed») — другое сообщение → эти тесты падают.

3. **Потеря `_nochk`-элизии = перф-регресс на hot-path.**
   Codegen элидит bounds-check (`nova_vec_slice_nochk`) на proven-in-range
   сайтах (напр. `for i in 0..v.len()`). `@index`-тело проверяет всегда;
   codegen не может элидировать .nv-внутренний check → hot-петли со срезами
   получают лишнюю проверку. Обход (dual-path: элидированные → inline nochk,
   прочие → @index) оставляет codegen-магию для nochk → НЕ «единый источник».

**Вариант «переписать slice.nv @index с `requires` на явный always-on
`if...panic(«Vec: slice...»)`»** снимает блокеры 1+2, но: (а) теряет блокер 3
(элизию) без dual-path; (б) меняет авторский дизайн slice.nv (`requires`
документирует прекондишн и парен с `@get(Range)->Option`); (в) сам по себе —
семантическое решение о модели среза. Требует владельца.

**Готовность:** механизм sret ПРИНИМАЕТ маршрутизацию без изменений (design §1
стартовый периметр уже перечисляет `Vec[T] @index(Range)`/`@get(Range)` как
sret-leaf). Как только владелец ратифицирует модель (панковское-vs-контрактное
bounds + сообщение + элизия), маршрутизация = mono-форсинг @index(Range) +
Range-конструирование на call-site + sret-arming. НЕ механическая работа —
язык-решение. Оставлен ЧЕСТНЫМ маркером по инструкции «не насилуй».

**ЗАКРЫТ Plan 194 Ф.3 (2026-07-15, атом A3, vrange-роутинг):** владелец
ратифицировал модель в Plan 194 (D-амендмент, «bounds-check среза = safety,
не контракт») — снимает все три блокера разом. `slice.nv @index(Range)`
переписан с `requires` на явный always-on `if r.start < 0 || r.end < r.start
|| r.end > @len { panic("Vec: slice range out of bounds") }` (блокер 1+2:
проверка больше не элидируема политикой контрактов; panic-текст сменился,
пиновые тесты обновлены). `_nochk`-элизия (блокер 3) больше не нужна как
codegen-магия — будущий Z3 sound-elision проход (Plan 194 Ф.2) сможет
оптимизировать proven-in-range сайты ВНУТРИ этого же `.nv`-тела; сегодня без
него тело всегда проверяет (не хуже прежнего `_chk`-пути на непроверенных
сайтах). `emit_c.rs` больше не строит вид inline — `v[a..b]` синтезирует
`v.index(range)` (материализуя open-ended/inclusive границы в call-site
Range-литерал) и переэмиттит через обычный Call/Member-путь; это ДАРОМ
получает sret `_out`-форму через существующий `sret_maybe_rewrite_call`
(тот же armed-ExprId механизм, без Vec-slice-специфичного кода). Побочный
фикс: `infer_expr_c_type` не умел структурно типизировать «голое» значение
`ExprKind::Range` (нужно было для overload-выбора `@index(i int)` vs
`@index(r Range)` на синтетическом call-сайте без checker-ExprId) — добавлен
недостающий arm (не зависит от контекста subst, Range — конкретный тип).
См. compiler-codegen/src/codegen/emit_c.rs (`ExprKind::Index`+`Range`
Vec-ветка, `infer_expr_c_type` верх) + std/src/collections/vec/slice.nv.

Решение владельца (2026-07-10): функция, возвращающая КОНСТРУИРУЕМОЕ значение,
получает в C доп. параметр `_out` — готовый указатель, куда callee конструирует
результат ПО МЕСТУ. Caller решает размещение; callee один для обоих случаев.
Прецеденты: C++ sret/RVO, Swift indirect result. ЕДИНЫЙ механизм — общий
предикат по ФОРМЕ (сигнатура+тело), НЕ per-типовые ветки.

### 1. Классификация (пре-пасс по AST, fixpoint)

`sret-eligible(f)` ⇔ все из:
- f — .nv-метод/статик-метод с value-конструируемым возвратом: C-тип возврата
  `S*`, где S — heap-record ≤ 3 слов (24Б; NovaArrHdr-семейство `Nova_Vec____*`
  в стартовом периметре), И
- tail-результат тела f — (a) record-литерал `Self{...}` того же S («лист»),
  ЛИБО (b) tail-вызов другой sret-eligible функции («цепочка», fixpoint ≤2
  итераций закрывает bytes→from_raw_parts).

Стартовый периметр (расширение — только после зелёных гейтов): Vec-возвраты
.nv-тел — `Vec[T].from_raw_parts` (лист), `str @bytes()` (цепочка),
`Vec[T] @index(Range)`/`@get(Range)` (лист, mono-инстансы). Плюс тот же
_out-принцип на уровне runtime-хелпера среза (`nova_vec_slice_*_out`) — до
маршрутизации `v[range]` на .nv `@index(Range)` (снятие «codegen magic»,
slice.nv:33 — остаётся followup-маркером, второе окно правды НЕ создаётся:
хелпер строит тот же вид, что .nv-тело, и оба идут через один _out-механизм).

### 2. ABI callee

Для sret-eligible f эмитятся ДВЕ формы (дедупликация тела, нулевой риск для
непереведённых call-sites):
- `S* f__sret(args..., S* _out)` — тело из AST; tail `Self{...}` пишет поля
  прямо в `_out->…` (без nova_alloc); tail-вызов sret-callee прокидывает
  `_out` дальше (элизия temp'ов Ф.3 обобщена на цепочку); `return _out`.
- классическая `S* f(args...) { return f__sret(args..., (S*)nova_alloc(sizeof(S))); }`
  — тонкая обёртка; ВСЕ существующие call-sites работают без изменений
  (вывод-паритет автоматом), аллокация одна на верху цепочки.

Механика emit_c: поле `sret_out: Option<String>` (имя C-параметра `_out`) +
карта `sret_fns: C-имя → S`. Взвод «armed» на эмиссии tail/return sret-тела;
потребители: (1) emit_record_lit — top-level Self-литерал совпавшего типа S
пишет в _out (take-семантика; вложенный Self-литерал в аргументах — экзотика,
не совпадёт по take до листьев — отмечено ограничением V1), (2) точка эмиссии
вызова — callee ∈ sret_fns → `callee__sret(args, _out)`.

### 3. Call-site: единый предикат размещения

В `emit_let`, RHS = прямой вызов sret-eligible (или Range-срез Vec):
- биндинг `ro` И имя ∉ `escaped_idents(fn)` → СТЕК-слот:
  `S _slot_N = {0}; S* x = f__sret(args, &_slot_N);`
  Zero-init `= {0}` ДО любой GC-точки (аргументы вычисляются после
  декларации слота) — консервативный скан Boehm видит нуль/валидные
  указатели, ложное удержание исключено.
- иначе (mut-биндинг, эскейп, не-Let позиция) → классическая форма (GC-куча),
  семантика неизменна.

`escaped_idents` — обобщение эскейп-анализа волны (escape_analyze.rs),
НЕЗАВИСИМЫЙ walker (existing value-record promoted НЕ трогается): локал x
эскейпит ⇔ Ident(x) достигает: return/tail/throw; тела замыкания (любое
упоминание); arg-позиции вызова (НЕ receiver-позиции метод-вызова — receiver
Vec-методов не сохраняется сверх собственных полей, допущение V1
документировано); RHS Assign/Let к другому имени (alias, V1 консервативно);
поля RecordLit/TupleLit/ArrayLit; store в Member/Index. OVER-эскейп безопасен
(промах = heap = сегодняшнее поведение).

GC-заметка (виды): стек-слот содержит `data`-указатель ВНУТРЬ родительского
буфера — консервативный скан C-стека удерживает буфер, как heap-дескриптор
сегодня (GC_all_interior_pointers, Plan 138 Ф.2). Snapshot-семантика при
realloc родителя сохраняется тождественно.
Самоперезапись `x = x[a..b]` (Assign-путь) остаётся классической в V1 —
`nova_vec_slice_chk_out` тем не менее безопасен при `out == src` (чтения
src-полей предшествуют записям out).

Инструмент `compiler-codegen/tests/plan172_14_blast_radius.rs` (permanent,
`#[ignore]`-тест — `cargo test --test plan172_14_blast_radius -- --ignored
--nocapture`) сканирует std/ + nova_tests/ + spec_tests/ (4031 файлов,

известное упрощение recon-инструмента, НЕ полный module-резолв) и
классифицирует КАЖДЫЙ non-receiver параметр по (a) режиму (`mut`/`consume`/
`variadic`/`const` — уже имеют свою ABI-историю, не трогаются Ф.1) и
(b) вычисленному C-размеру (`const_fn_eval::type_size_or_align_resolved`,

**Ключевая находка: кандидаты НЕ равномерно размазаны — концентрация в
keystone-типах**, в отличие от framing «keystone A6 ×180» (180 независимых
точечных правок). Из 66 подтверждённых:
- **~20** — `std/fs/fs.nv` (`path Path` параметр, 24Б) — ОДИН тип (`Path`),
  повторяющийся почти в каждой fs-функции. Фикс на уровне типа/сигнатуры
  закрывает пачку сайтов разом, не 20 независимых правок.
- **~6** — `std/http/{client,server,message,header,mime,body}.nv`
  (`Request`/`Response`/`HeaderMap`/`ContentType`/reader-типы, 24-112Б).
- **3** — `std/crypto/hmac.nv` (`[u8; N]`-подобные fixed-size буферы, 32Б).
- Остальные ~35 — рассеяны по `nova_tests`/`spec_tests` fixtures (tuple/
  value-record demo-типы, не production-hot-path).

**Вывод:** реальный blast-radius для Ф.1 в ~3 раза меньше исходной оценки
(66 подтверждённых vs ~180) и структурно проще (keystone-кластеры, не
равномерная россыпь) — НО «470 неизвестных» требуют уточнения инструмента
(вероятно newtype/alias-обёртки над примитивами, которые
`type_decl_size_or_align` не полностью резолвит — не проверено, followup
`[M-172.14-blast-radius-tool-refine]`) прежде чем финальное число можно
считать окончательным. Даже верхняя граница (66+470=536) — того же порядка,
не радикально больше исходной оценки.

**Осознанное решение НЕ начинать Ф.1-Ф.3 codegen в этой волне:** реализация
auto by-ref требует НОВОГО анализа «второго владельца» (обобщение
`escape_analyze.rs` на параметры — по конструкции похоже на chain-gating
фикс этой же сессии, где escape-анализ уже пришлось расширять на новые
формы receiver'а), materialize-temp на call-site для неадресуемых
аргументов, auto-deref в теле (можно переиспользовать `ref_params`
механизм — прецедент есть, см. Plan 184/172.5 codegen), и escape-доказательство
на каждом из 66+ сайтов. Это полноценный НОВЫЙ codegen-механизм, не
косметика — рашить его в хвосте той же сессии, где уже был найден и
исправлен один реальный soundness-баг (chain-gating), нарушило бы явное
требование методологии §2/§7 «не рашить крупный ABI в хвосте сессии».
Следующая волна: начать с Ф.1 keystone-кластера `Path` (std/fs) как
наименьшего по риску (один тип, ~20 сайтов, non-generic, не в hot-path
конкурентности) — де-риск ПЕРЕД масштабированием на http/generic случаи.
**Зонт:** [172-compiler-rework.md](172-compiler-rework.md).
**Deps:** 172.4 correctness-core ✅ (единый receiver-ABI VR+NT; value-типы работают корректно).
**Приоритет:** P3 (производительность; корректность НЕ затрагивается).

## Мотивация

172.4 закрыл КОРРЕКТНОСТЬ value-ABI (fluent, `==`, единый receiver-carrier). Осталась
ПРОИЗВОДИТЕЛЬНОСТЬ размещения/передачи — три P3-оптимизации, все behavior-changes с широким
blast-radius (замер 2026-07-04: value-record 117, value-параметры ~180, named-tuple 4).
Владелец (2026-07-04) развёл: correctness-core (owner-acceptance) закрыт в 172.4; perf —
самостоятельный измеренный focused-эффорт, НЕ автопродолжение в хвосте марафона.

## Фазы (перенесены из 172.4 §3 Ф.4-Ф.6 — детали там)

- **Ф.1 (=172.4 Ф.4) — авто by-ref передача параметров.** Большие value передавать указателем
  когда копия НЕ наблюдаема (закрывает ЗА-аргумент Q29 без `ref T`). Foundation: `escape_analyze.rs`
  (Plan 127) промоутит value-records на heap при escape — ОБОБЩИТЬ на by-ref-передачу (новый анализ
  «второго владельца»). **Blast-radius: ~180 param-сайтов** (сигнатура + call-site взятие-адреса +
  тело deref + escape-доказательство на каждый). Масштаб = keystone A6 ×180.
- **Ф.2 (=172.4 Ф.5) — авто heap↔stack placement, нерекурсивный sum→стек.** Нерекурсивные/
  перечислительные sum → tagged-union на стеке (как builtin Option/NovaOpt vs Result/heap).
  **ПОПРАВКА 2026-08-22 (разведка окна `p17214-sum-stack`, проверена
  интегратором по коду): ДЕТЕКТОРА РЕКУРСИИ ДЛЯ СУММ НЕТ.** Обе ссылки
  этой строки били мимо: Plan 62.A.bis — реестр схем сумм, а раздел
  `08-runtime` — про арену файберов. Единственный настоящий детектор
  `check_infinite_type` (`compiler-codegen/src/types/mod.rs:7181`, DFS
  с `on_path`, ловит и взаимную рекурсию) вырезает суммы ДВАЖДЫ и
  намеренно — как субъект цикла и как ребро, с комментарием в коде
  «A Sum is ALWAYS heap». То есть факта «эта сумма рекурсивна» не
  производится нигде, и фаза начинается не с использования детектора,
  а с его написания. Каркас обхода лежит рядом, цена невелика — но
  строка выше обещала готовое основание, и это было неверно.
  Консервативное правило «рекурсия→heap» остаётся в силе как замысел.
- **Ф.3 (=172.4 Ф.6) — copy-elision RVO/NRVO + move-on-last-use.** Свежие/уникальные value
  (escape доказал отсутствие второго владельца) строятся в слоте-назначении / move вместо memcpy.
  Прозрачно (value: копия ≡ move наблюдательно). БЕЗ нового синтаксиса. Маркер
  `[M-172.4-rvo-move-on-last-use]`. Обобщает D326 R7/R8.

## Методология (172.1/172.4-класс)

- §7 де-риск ПЕРЕД фаталом: detect-режим + blast-radius + карта сайтов (ultracode-разведка).
