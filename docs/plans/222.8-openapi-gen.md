## 0. Почему нужен НОВЫЙ механизм, а не готовая машина

В компиляторе есть ТОЛЬКО `const_fn_eval`-арифметика (числовые constexpr) — общей
comptime-reflection/call-site-метаданных фасилити НЕТ. auto_derive.rs УЖЕ вычисляет per-тип
wire-shape (`wire_name_for`, rename/rename_all/alias-резолв, `compiler-codegen/src/protocols/
auto_derive.rs:472`) для кодогена `Serialize`/`Deserialize` — эта логика **переиспользуется**
(не пишем второй раз), но она даёт форму ТИПА, не форму РЕГИСТРАЦИИ (путь-литерал ↔ тип-хендлера).
Для последнего нужен НОВЫЙ универсальный примитив — сбор метаданных с call-site'ов.

## 1. Языковое расширение — **ТРЕБУЕТ D-амендмента** (владелец, до реализации)

Новый атрибут (рабочее имя, финал — за владельцем): **`#reflect`** — на объявлении функции/метода.
Компилятор, встретив атрибут, для КАЖДОГО call-site этой функции эмитит запись в JSON-сайдкар:

```nova
#reflect
export fn Router mut @route(path str, mr MethodRouter) -> Result[Router, HttpError] { ... }

#reflect
export fn get(h Handler) -> MethodRouter { ... }
```

**Это ЯЗЫКОВОЕ расширение** (новый атрибут с новой семантикой, не косметика) — по правилу
CLAUDE.md «язык-меняющее слияние не пушится без D-амендмента в спеке в том же слиянии».
Ф.0-исполнитель ОБЯЗАН дописать `spec/decisions/` (новый D-номер, атрибуты — раздел 05 или
смежный) ПЕРЕД реализацией, не после. Имя атрибута, точная грамматика аргументов (если будут) —
согласовать с владельцем в той же волне, что и D-текст (не изобретать в одиночку — конвенция
«синтаксис не выдумывать»).

## 2. Что записывается на call-site (JSON-схема записи)

Для каждого вызова `#reflect`-функции — один объект:

```json
{
  "fn": "polaris.Router.route",
  "site": "src/main.nv:42:5",
  "args": [
    {"kind": "literal_str", "value": "/users/{id}"},
    {"kind": "chain_ref", "site_id": 17}
  ]
}
```

- **`literal_str`** — аргумент был строковым литералом на call-site (путь). НЕ строится из
  конкатенации/переменной — если аргумент не литерал, запись помечается
  `{"kind": "non_literal"}` (честно — механизм не пытается угадывать динамику).
- **`type`** — аргумент функционального/closure-типа: полная резолвнутая сигнатура (параметры +
  возврат), КАЖДЫЙ тип-параметр рекурсивно разворачивается в JSON-schema-подобную форму,
  переиспользуя auto_derive.rs `wire_name_for`/rename_all-резолв для типов с
  `#impl(Serialize/Deserialize)`. Не-serde типы — просто `{"kind": "opaque", "name": "..."}`.
- **`chain_ref`** — аргумент/ресивер САМ был построен цепочкой вызовов ДРУГИХ `#reflect`-функций
  (пример: `get(h1).post(h2)` строит `MethodRouter` до того, как тот передан в `.route(path, mr)`)
  — ссылка на `site_id` того вызова (массив записей адресуется по индексу/id, не по указателю).
  Это ОБЩИЙ механизм отслеживания provenance значения через builder-цепочку — не знает про
  «Router»/«MethodRouter», просто видит «значение X произошло от call-site Y».

**Почему this достаточно для OpenAPI и остаётся универсальным:** nova-polaris помечает
`#reflect`-ом ИМЕННО те свои функции, что участвуют в регистрации (`@route`/`@get`/`@post`/…,
свободные `get`/`post`/…) — компилятор не знает их роли, просто собирает call-graph+типы+литералы
по МАРКЕРУ. Другой .nv-пакет мог бы использовать ТОТ ЖЕ атрибут для CLI-парсера/GraphQL-схемы/
чего угодно — механизм не завязан на HTTP ничем, кроме ТОГО, ЧТО именно nova-polaris помечает.

## 3. Эмиссия

`nova build` (без нового CLI-флага компилятора, специфичного под "openapi" — флаг ОБЩИЙ):
`--emit-reflect <path.json>` — если хотя бы одна `#reflect`-функция достижима в CU, пишет массив
записей по формату §2 в `<path.json>`. Ноль записей → пустой массив, не ошибка (пакет может не
использовать рефлексию вовсе). Нулевая рантайм-цена — чисто build-time артефакт, не влияет на
сгенерированный C/бинарь.

## 4. Сборка OpenAPI (ВСЯ HTTP-семантика — здесь, в nova-polaris)

Новый модуль/тул в nova-polaris (не в компиляторе!) — читает `--emit-reflect`-JSON (парсинг —
обычный `Json[Vec[ReflectEntry]]` через уже существующий serde, никакой новой инфраструктуры),
и:
1. Фильтрует записи по известным именам ФУНКЦИЙ РЕГИСТРАЦИИ (`Router.route`/`Router.get`/…,
   свободные `get`/`post`/…) — это и есть граница, где HTTP-знание входит в игру, ЦЕЛИКОМ на
   стороне polaris.
2. Резолвит `chain_ref` (MethodRouter-цепочки) в плоскую таблицу `(path, verb) → handler_type`.
3. Из `handler_type`'а сигнатуры хендлера различает параметры-экстракторы (`PathParam[T]` →
   OpenAPI `parameters[].in=path`, `Query[T]` → `in=query`, `Json[T]` → `requestBody`) — по ИМЕНИ
   типа-обёртки (`extract.nv`'s `PathParam`/`Query`/`Json`), не по компилятор-уровневому знанию.
4. Разворачивает `type`-shape каждого связанного Serialize/Deserialize-типа в OpenAPI
   `components/schemas` (прямое отображение wire_name→JSON Schema property).
5. Пишет итоговый `openapi.json` (OpenAPI 3.x) — артефакт сборки приложения, не пакета nova-http.

**CLI-удобство** (не обязательно первой волной): обёртка `nova-polaris openapi-gen <emit.json>
<out.json>` (свой бинарь/скрипт в репе polaris) — тонкий, вызывает шаги 1-5.

## 5. Что НЕ входит (по решению владельца)

- **(б) route-верификация** ({id}↔поле Path[T] на компиляции) — ОТЛОЖЕНА, не начинать; описанный
  здесь `#reflect`-механизм её НЕ реализует (только собирает данные, не сверяет). Возврат к (б) —
  отдельным решением ПОСЛЕ v0.1, когда/если строится общий comptime-reflection facility
  (§2 этого плана — кандидат-фундамент для будущего (б), не сам (б)).
- **`#route(...)`-атрибут на хендлерах** — остаётся отклонён (третья дверь, D9).
- **Верификация ВНЕ compile-time** (напр. рантайм-consistency-чек при старте сервера) — вне
  объёма; если понадобится — отдельный вопрос, не часть 222.8а.
