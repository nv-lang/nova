# План 219 — build-демон (build-latency P2)

**Статус:** 📋 УТВЕРЖДЁН владельцем 2026-07-20 («заводить — да»). **Приоритет:** P2
(после [218](218-prebuilt-runtime-archive.md)). **Основа:** [startup-latency-research.md](wip/startup-latency-research.md).

## 0. Что решаем (замер разведки)

Каждый вызов `nova build` заново платит за подготовительную работу, не зависящую от
пользовательского кода: разрешение зависимостей из lockfile, обнаружение тулчейна
(clang/gcc/msvc), detect libuv/Boehm, парсинг общих заголовков рантайма, старт процесса.
Замер: **dep-lock resolution ~0.99с** на каждую сборку + toolchain/libuv/boehm detect.
Демон держит это резидентно в памяти → выигрыш **−1–3с/сборку**.

**Прецедент:** `rust-analyzer`, Bazel persistent worker, `tsc --watch`. Плюс — LSP (Plan 215)
УЖЕ держит резидентный процесс с распарсенным индексом; часть инфры переиспользуема.

## 1. Механизм

Долгоживущий процесс `nova`-демона, к которому `nova build` подключается по IPC (сокет/pipe)
вместо холодного старта. Демон держит в памяти: resolved dep-graph (по хешу lockfile),
toolchain-конфиг, libuv/Boehm-пути, кеш распарсенных рантайм-заголовков. При `nova build`:
клиент шлёт запрос → демон переиспользует готовое состояние → компилирует только дельту.

## 2. Ключевые вопросы реализации

1. **Инвалидация резидентного состояния.** dep-graph перечитывается при изменении lockfile
   (хеш), toolchain — при изменении env/конфига. Как у 218 — по содержимому, не mtime.
2. **Lifecycle демона.** Старт по требованию (первый `nova build`), простой-таймаут, явный
   `nova daemon stop`. Один демон на workspace (по пути), не глобальный.
3. **Переиспользование LSP-инфры (Plan 215).** LSP уже держит резидентный индекс модулей —
   оценить, можно ли шарить процесс/состояние (единый резидентный сервис build+lsp) ИЛИ это
   отдельный демон. Развилка: общий сервис дешевле по памяти, но связывает lifecycle.
4. **Конкурентность.** Несколько `nova build` к одному демону (параллельные сборки) —
   сериализация vs пул. Изоляция состояния между запросами.
5. **Windows-специфика.** Старт процессов на Windows дороже (разведка §startup) — демон там
   выигрышнее. Но IPC-надёжность (named pipe) + отсутствие зомби-процессов.

## 3. Фазы (эскиз)

- **Ф.1** Резидентный процесс + IPC-протокол (клиент `nova build` → демон); держать
  resolved dep-graph + toolchain/detect в памяти.
- **Ф.2** Инвалидация по хешу lockfile/env; lifecycle (idle-timeout, `daemon stop`).
- **Ф.3** (опц.) Слияние с LSP-резидентом (Plan 215) — общий сервис ИЛИ отдельный.
- **Ф.4** Замер: холодный `nova build` vs через демон — подтвердить −1–3с; conformance/флагман
  без регрессий (демон = те же артефакты, что холодная сборка).

## 4. Зависимость и очередь

- **ПОСЛЕ 218.** 218 (предсобранный рантайм) убирает доминирующие 6.5с C-компиляции; демон
  снимает оставшийся per-invocation overhead (~1-3с). До 218 демон-выигрыш теряется на фоне
  рантайм-перекомпиляции.
- Далее **[220](220-tcc-dev-backend.md)** (TCC, P3) — ускоряет саму C-компиляцию пользовательского
  кода, тоже осмысленно только после 218.
