## 2. Классы промахов (вход для Stage-D)

### Класс R1 (доминирует в B1, ~98% всех miss) — turbofish пробрасывает РЕЗИДУАЛЬНЫЙ T объемлющего тела

Форма: внутри метода `Vec[T]`/`HashMap[K,V]` собственного тела вызывается ДРУГАЯ generic-функция с
ЯВНЫМ turbofish, повторяющим СОБСТВЕННЫЙ (ещё не конкретный на чек-тайме) generic-параметр
объемлющего тела: `alloc_buf[T](n)`, `null_buf[T]()` (`std/src/collections/vec/core.nv`),
`copy_n_nonoverlapping[...]` (RawMem, checksums), `new_buckets[K,V](cap)`
(`std/src/collections/hashmap.nv:640`). Атрибуция по функции (conformance-прогон, временная
`fn=`-метка на miss-трейсе, см. §5): `alloc_buf` 188, `copy_n_nonoverlapping` 94, `null_buf` 93,
`new_buckets` 13 — 388/395 (98%) одного прогона. Это ТОТ ЖЕ «legitimate erased-body boundary»,
что §7 дизайн-документа: T объемлющего тела residual на чек-тайме (конкретен только
POST-mono, `current_type_subst`), продюсер честно молчит. Мелкий хвост того же корпуса:
`d122f_leaf`(3)/`d122f_mid`(1)/`d239_elem_generic_first`(1)/`box_iter`(1) — уже
задокументированный в 196.5-perd-verification.md erased-body-caller паттерн.

### Класс R2 (доминирует в B2 baseline) — method-generic связывается ТОЛЬКО аргументом, чей СОБСТВЕННЫЙ тип резидуален

Форма: `fn Vec[T] mut @append[S AsSlice[T]](other S) -> @` (`std/src/collections/vec/mutate.nv:267`)
— `S` не встречается в возврате (`Self`), связывается ТОЛЬКО из `infer_expr_type(other)`; когда
`.append(...)` вызывается ИЗНУТРИ другого generic-тела (типичный случай в generic-коллекциях), сам
аргумент `other` резидуален на чек-тайме → `infer_expr_type` не даёт конкрет → solver'ный
`extra_eqs`-путь `resolve_return_channel` (`types/mod.rs:9802`-`9850`) не связывает `S` → whole-map
completeness gate (`9882`) режет ВЕСЬ `ordered` (не только `S`) → канал молчит для этого call-site.
Доминирует в трёх контекстах: `Vec____nova_byte.append` (423 в conformance), `Vec____nova_int.append`
(8), `Vec____nova_int.extend` (3) — структурно идентичный R1, только через arg-position, а не
turbofish.

### Класс C1 (МЕНЬШИЙ остаток, частично закрыт producers-widen/closure-lowering-fix) — closure-return-bound method-generic

Форма: `.map`/`.map_err`/`.fold`/`.with_lock` — U/Acc/R связывается ЗНАЧЕНИЕМ ВОЗВРАТА
closure-литерала. `closure_arg_return_peek` (введён волной producers-widen) закрыл БОЛЬШУЮ часть
этого класса (см. `Result.map` hit=52/miss=2, `Option.map` hit=2/miss=3, `BoxIter.map` hit=3/miss=1
— СМЕШАННЫЙ hit/miss на ОДНОМ И ТОМ ЖЕ имени метода, значит форма частично покрыта), но НЕ 100%:
`D119Box____nova_int.map`/`D119Box____nova_str.map` — 0 hit / 7 miss (не покрыт вовсе для этого
типа-носителя); `MapIter.map` 0/1; `D30RorBox.try_double`/`try_get` 2/2 miss (closure-lowering-fix
закрыл whole-file `d30_ror_from_closure`, но не все `D30RorBox`-формы в остальном корпусе);
B3-параллель: `.map`(missing=U)×4, `.fold`(missing=Acc)×1, `.with_lock`(missing=R)×1,
`d145_map`(missing=U)×1. Volume меньше R1/R2 (≈30-40 в B2, 7 в B3), но это ГРАНИЦА, требующая
самостоятельной работы над `closure_arg_return_peek` (различные формы closure-тела — вложенный
`match`/multi-statement block/цепочка вызовов внутри тела), не просто «добавить продюсеру ещё один
gs-случай».

### mismatch/partial = 0 везде

Ни одного `fallback=mismatch` (B1) и ни одного `reason=partial` (B2) на полном корпусе — канал,
когда пишет, пишет ВЕРНО; вопрос Stage-C был чисто про ПОКРЫТИЕ, не про корректность. SHADOW/
byte-parity гейты (`shadow_check_node_substs`, `subst_map_adopt_rt`) не тронуты, остаются как есть.

## 3. Почему детач не выполнен ни для одного потребителя

Задание: детач ТОЛЬКО при fallback-использовании = 0 на ВСЁМ корпусе. Классы R1/R2 — СТРУКТУРНЫЕ
(residual generic внутри generic-тела; §7 дизайн-документа именует их «законной границей
erased-body», W1-addendum независимо диагностировал ТУ ЖЕ границу для 6 W1-армов) — не «недоделанный
продюсер», а фундаментальное ограничение checker-side канала: продюсеры пишут `node_substs` ТОЛЬКО
когда ВСЕ generic-параметры каллиси разрешились до КОНКРЕТНОГО типа на чек-тайме; вызов из ВНУТРИ
generic-тела, где вызывающий сам ещё не мономорфизирован, структурно не может дать этой конкретики
до POST-mono (rustc-эталон: `Instance.args`-композиция, W1.3) — то есть ИМЕННО то, что решает
`current_type_subst`/W1-i резолвер, а НЕ checker-side `node_substs`. Снятие R1/R2 потребовало бы
POST-mono-композиции (аналог W1-i варианта (ii)), не расширения самих B1/B2/B3/B5 — вне объёма
Stage-C (это задача для Stage-D/W1-i-подобного расширения на non-instance генерики). Класс C1 —
не структурная граница, а незавершённое покрытие `closure_arg_return_peek` для части closure-тел;
тоже не закрывается детачем читателя (fallback = ЕДИНСТВЕННЫЙ источник истины для этих сайтов
сегодня), а требует расширения продюсера (отдельная волна).
