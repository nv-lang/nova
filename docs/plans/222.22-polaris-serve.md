# План 222.22 — `polaris.serve` + `ServerPolicy`: высокоуровневый старт сервера

**Статус:** ОТКРЫТ (решение владельца 2026-07-30: «в свою сессию и исправить до релиза»).

> **Реальность-чек 2026-07-30 (после написания плана):** параллельная сессия УЖЕ
> приземлила большую часть Ф.1 — `polaris.net.serve(listener, handler, policy)`
> (полный accept-цикл: Semaphore-пермиты, 503 при `reject_with_503: true` — решение
> «не молчаливый обрыв» уже в коде, backoff на transient accept-ошибке, deadlines,
> body-cap, keep-alive) + `serve_router`-сахар + `ServerPolicy` с `max_inflight: 16`.
> Диагноз «высокоуровневого старта нет» был ошибкой разведки интегратора (греп не
> заглянул в `src/serve/`, `src/net/`). ОСТАТОК Ф.1 (см. брифы окна): (а) строковая
> форма адреса `serve_addr(router, ":8080", policy)` поверх свежих
> `to_socket_addr`/`any`; (б) **graceful shutdown — цикл не умеет останавливаться**,
> `running` никогда не сбрасывается; (в) `Retry-After` в 503-ответе; (г) 222.23 Ф.1
> — Metrics/Log; (д) лживый комментарий `background.nv:59` («accept-loop ещё нет»).
> Ф.2 (миграция витрины на serve) — без изменений, главный видимый выигрыш.
**Дом:** `nova-polaris` (API) + `examples/flagship/aggregator` (миграция витрины).
**Блокер релиза:** да — README polaris обещает `polaris.serve(app, ":8080")`, которого
не существует; витрина вручную собирает accept-цикл, admission-лимит и graceful-путь.

## Диагноз (сверено по репам 2026-07-30)

Один корень у трёх наблюдений владельца:

1. Витрина зовёт низкоуровневый `TcpListener.bind` — потому что высокоуровневого старта
   в Polaris НЕТ: `serve_once(router, raw)` обслуживает один запрос (мок-тесты + живой
   раннер), а accept-loop честно помечен «в этом репо ещё нет»
   (`src/background.nv:59`).
2. HTTPS в Polaris не завезли: `nova-tls` умеет серверный хендшейк, `nova-http`
   использует TLS только клиентски (`transport/real.nv`: `TlsStream.connect`);
   серверного слушателя нет ни в http, ни в polaris.
3. `inflight >= MAX_INFLIGHT_CONNS` в витрине — НЕ middleware и НЕ ratelimiter
   (ratelimiter уже есть: `middleware/ratelimit.nv`, token bucket per-client). Это
   admission-контроль на границе accept — решение ДО траты ресурсов на парсинг;
   middleware физически поздно (`middleware.nv:7`: «backpressure живёт на accept-loop,
   222.7 admission-bounded»). Но писать его руками пользователь не должен — это
   конфиг серверного ядра.

## Целевая форма

```nova
polaris.serve(app, ":8080", ServerPolicy.new().max_inflight(16).graceful_drain(5s))
```

- `serve(router Router, addr str, policy ServerPolicy) Net Time -> Result[(), ServeError]`
  — блокирует до shutdown-сигнала; `":8080"` = все интерфейсы (Go-конвенция,
  `[M-socket-addr-port-only-form]`, приземляется конверсионным окном).
- `ServerPolicy` — value-record, fluent-строитель по D117/D84 (with_* → новое значение;
  поля = одноимённые методы-свойства): `max_inflight` (admission-лимит, дефолт
  разумный, 0 = без лимита), `graceful_drain` (дедлайн дожития соединений при
  остановке), позже TLS (Ф.3).
- Внутри: `supervised` + accept-цикл (форма витрины: `consume stream = lst.accept()
  ?? break`, `detach consume stream`), admission через AtomicInt как в витрине,
  drain по D439-семантике (прямая блокировка тела паркуется штатно; ограничение
  timeout/cancel — реестр №164/№165).
- Порт/адрес: строго ПОСЛЕ конверсионного окна — `to_socket_addr`, `SocketAddr.any`,
  `port int` + `requires port >= 0 && port <= 0xffff` (решения владельца 2026-07-30).

## Фазы

- **Ф.1 — `serve` + `ServerPolicy` (max_inflight, graceful_drain)** в nova-polaris,
  поверх nova-http servernet-раннера; интеграционный смок: поднять, обстрелять
  параллельными запросами, убедиться в 503/отказе сверх лимита, штатно погасить.

  **Отказ сверх лимита (решение владельца 2026-07-30 «подумай трезво», разобрано):**
  НЕ молчаливый обрыв — клиент видит «connection reset», неотличимый от сетевой
  аварии, и слепо ретраит, усиливая шторм. Дефолт: статический, заранее
  сериализованный **`503 Service Unavailable` + `Retry-After` + `Connection: close`**,
  пишется сразу после accept БЕЗ парсинга запроса (смысл admission — не тратить
  ресурсы на разбор — сохраняется; цена = запись константного буфера, slowloris-
  поверхность не растёт: читать ничего не нужно). Второй рубеж бесплатно: сверх
  admission-окна соединения копятся в kernel-backlog — естественный backpressure.
  Ручку `Close`-без-ответа в V1 НЕ заводить — не плодить API без запроса.

  **Логирование (то же решение):** серверное ядро говорит через существующий
  `Log`-эффект polaris (222.20: `#default_handler`→stdout), честно в сигнатуре —
  `serve(...) Net Time Log`. События: отказ по max_inflight, ошибка accept, drain
  по дедлайну (позже TLS-handshake-fail, Ф.3). ЛОВУШКА, закрытая по построению:
  строка лога на КАЖДЫЙ отказ = самоусиление атаки (флуд соединений → флуд диска).
  Агрегация: первый отказ — немедленно, дальше сводка «отклонено K за N сек».
  Тесты — handler-swap `Log`, ассерт события, без моков.
- **Ф.2 — миграция витрины**: main.nv сжимается до роутера+конфига+`polaris.serve`;
  нынешний ручной цикл СОХРАНЯЕТСЯ отдельным учебным примером «под капотом»
  (examples/, вне флагмана). README polaris перестаёт врать.
- **Ф.3 — TLS-слушатель**: `ServerPolicy.tls(cert, key)` поверх nova-tls
  (серверный хендшейк готов); https-смок. Отдельное окно после Ф.1/Ф.2.

## Порядок и зависимости

Старт Ф.1 — после приёмки конверсионного окна (`p-convfix`): serve строится на
`to_socket_addr`/`any`/`port int`, иначе переделка через час. Ф.3 — после Ф.2.
