# План 253 — Сокращение инвариантов и «дверей»: зонтик

**Статус:** 🆕 ЗАПЛАНИРОВАН 2026-08-08, ЗОНТИК (по образцу плана
[221](221-release-v0-1.md) с под-реестром [221.1](221.1-bug-sweep.md)).
Владелец, дословно: «план 253 — зонтик, что найдено для починки оформляй в
подпланы». Этот файл — ТОЛЬКО зонтик: цель, норма-основание, список
под-треков со статусами и ссылками, общее мерило приёмки. Конкретика починки
(числа, файл:строка, фазы, приёмка каждого пункта) живёт в подпланах
`253.N-*.md`, по одному на готовый к исполнению трек — ровно как 221 держит
только порядок, а вся конкретика дефектов — в подплане 221.1.

## Цель

Компилятор, `nova-cli` и LSP накопили правила, которые **держатся на честном
слове** (комментарием, соглашением на N сайтах), а не на структуре, которая
делает нарушение невыразимым. Норма-основание —
`docs/dev/conventions-governance.md`, раздел «Инварианты: как можно меньше, и
ни одного на честном слове» (требование владельца 2026-08-08, дословно:
«добавление инвариантов… должно быть только под чётким и реальным
обоснованием с независимой автопроверкой», и «инвариантов должно быть как
можно меньше»). Зонтик — систематический проход по репозиторию с этой нормой,
трек за треком, а не разовый фикс одного носителя.

Различающий вопрос нормы, применяемый в каждом треке: *можно ли записать
состояние, нарушающее утверждение?* Можно → инвариант (кто-то обязан
следить, дефект — вопрос времени). Нельзя → свойство (следить некому).
Порядок шагов: **убрать вовсе → сделать невыразимым (тип) → машинный энфорс
(страж + селфтест, подключённый к гейту) → комментарий-инвариант ЗАПРЕЩЁН.**
Единственное законное основание для НОВОГО инварианта — схлопывание
нескольких существующих, числами «было N → стало M».

### Трек А — режимы (`ro`/`mut`/`consume`)

Разведка (p-inv-compiler) уже дала точные числа: пара `mutable`/`consume`
переизобретена в компиляторе шесть раз (`Receiver`, `EffectMethod`, `LetDecl`,
`Param`, `RecordField`, `TypeDecl`), плюс смежная асимметрия
`ro_binding_names`/`consume`. Приоритет «до тега» — три пункта (остатки
№370 уже закрыты, симметрия `ro_binding_names`, `ReceiverMode` двухшаговым
приёмом). Полная разведка, счёт по каждому носителю, фазы и приёмка — в
[253.1-receiver-mode.md](253.1-receiver-mode.md).

### Трек Б — двери контрактов (заглушка, разведка идёт)

**Не готов к исполнению.** Подозрение владельца обосновано прецедентом того
же класса, уже в реестре: бáунды протоколов/типов находились «дверь за
дверью», ценой живого К1 каждый раз, а не единым узлом —
[№381](221.1-bug-sweep.md) (бáунд протокола на call-site свободного вызова),
[№383](221.1-bug-sweep.md) (бáунд типопараметра МЕТОДА — вторая дверь),
[№384](221.1-bug-sweep.md) (протокол `Equal` с default-телом — третья дверь,
UB), [№345](221.1-bug-sweep.md) (бáунд свободной функции — родоначальник
серии), [№386](221.1-bug-sweep.md) (бáунд на декларации типа — четвёртая
дверь). Все пять несут в реестре одну и ту же формулировку: «ФОРМА-НОСИТЕЛЬ
ПРОВЕРКИ БÁУНДА… фикс одного носителя приёмкой НЕ считается». Разведка,
запущенная отдельным окном (p-contract-doors) параллельно этому плану,
обязана дать: полный список дверей (не ограничиваясь уже известными пятью),
для каждой — есть ли уже единый узел проверки, и число «было N дверей →
стало M». **Подплан `253.2-*.md` заведёт интегратор по результатам этой
разведки** — до тех пор трек существует только как раздел-заглушка здесь.

### Трек В — среда/флаги (после тега)

Побочная находка разведки Трека А: 158 мест чтения переменных окружения
(107 различных имён), одно семейство field-кэша на 18 независимых
переключателях. Целиком после тега — сведение чтения env-переменных в
структуру меняет МОМЕНТ чтения, которым сегодня пользуются существующие
тесты (переопределение переменной между шагами прогона); правка требует
аудита каждого такого теста, несовместимого со сроком «до тега». Подплан не
заводится, пока нет посчитанного целевого числа M (нужен отдельный инвентарь
— задача, которую этот трек ставит перед собой, но не начинает).

### Не трек: размещение значений и ABI — вынесено в 172.15

Заводилось как «трек Г», снято вопросом владельца в тот же день. Предмет
([№469](221.1-bug-sweep.md): `__sret` работает, но в спеке не описан, периметр
задан именем C-типа) роднится с зонтиком лишь признаком «правило задано формой,
а не свойством». Сокращения инвариантов там не происходит — наоборот, нужно
ДОБАВИТЬ нормативные правила в спеку, а следствия относятся к ABI и
производительности. Дом — семейство 172:
[172.15](172.15-value-placement-abi-audit.md).

Запись оставлена намеренно: она показывает границу зонтика. Признак «периметр
задан формой» встречается и вне предмета 253, и сам по себе основанием для
трека не является.

## Общее мерило зонтика

Ни один трек и ни один подплан не закрывается формулировкой «сделано» —
только таблицей приёмки с числами «было N → стало M»
(`conventions-governance.md`, «Когда новый инвариант оправдан»: без чисел это
не обоснование, а намерение). Трек Б, будучи заглушкой, обязан прийти к
такой же таблице, что и Трек А, прежде чем в нём появится хоть одна фаза с
кодом.

## Оговорки

- Треки НЕЗАВИСИМЫ по исполнению: незавершённая разведка Трека Б не блокирует
  вход в Трек А, и наоборот.
- **Не заводить новый трек без числа.** Побочные находки будущих разведок (по
  образцу того, как Трек В сам был побочной находкой разведки Трека А)
  добавляются под-разделом сюда же, с собственной строкой в таблице
  «Под-треки», а не отдельным несвязанным планом.
- Порядок относительно тега — ПО ТРЕКАМ, не общий: см. «Оговорки» подплана
  каждого готового трека (для Трека А — [253.1](253.1-receiver-mode.md)).
  Трек Б — фазы стартуют не раньше завершения разведки. Трек В — целиком
  после тега.
