# План 222.4 — модуль `polaris.middleware`: ядро композиции

**Статус:** 📋 ДИЗАЙН, НЕ СОГЛАСОВАН. **Слой:** 2 (Polaris-ядро).
**Зависит:** 222.1 (✅ влит). **Блокирует:** [222.12](222.12-http-batteries.md) (все батарейки —
это middleware поверх этого ядра).
**Основа:** **Go/`chi`** — их `func(http.Handler) http.Handler` **один-в-один** наш
`fn(next Handler) -> Handler`. tower-`Service` (generic + `poll_ready` + backpressure) НЕ переносится.
**Родитель:** [222](222-http-framework.md) · [222.0](222.0-module-map.md).

## 1. Типы

```nova
/// Обёртка вокруг хендлера. Newtype (не голый fn-тип) — единообразно с `Handler`
/// (server.nv:329) и позволяет вешать методы композиции.
export type Middleware value { priv f fn(Handler) -> Handler }

export fn Middleware.new(f fn(Handler) -> Handler) -> Middleware => { f }

/// Применить к конкретному хендлеру.
export fn Middleware @apply(next Handler) -> Handler => (@f)(next)

/// Композиция двух: `a.then(b)` — сначала a (внешний), потом b (внутренний).
export fn Middleware @then(inner Middleware) -> Middleware =>
    Middleware.new(fn(next Handler) -> Handler => @apply(inner.apply(next)))
```

## 2. Подключение к `Router`

```nova
/// Копит цепочку; применяется при РЕГИСТРАЦИИ маршрута (не при dispatch — дешевле).
export fn Router mut @layer(mw Middleware) -> @

/// Слой только на группу — работает через уже существующий `nest` (222.1):
/// сначала `sub.layer(mw)`, затем `parent.nest("/api", sub)`.
```

**Порядок применения (зафиксировать в доке, частый источник путаницы):** слой, добавленный
ПОЗЖЕ, оборачивает СНАРУЖИ (как chi/Express `use`). Т.е. `r.layer(a); r.layer(b)` → запрос идёт
`b → a → handler`. Пин-тест обязателен.

## 3. Взаимодействие с `nest`

Слои родителя применяются к вложенным маршрутам; слои саб-роутера — только к его маршрутам.
Реализация: при `nest` слои родителя навешиваются на уже собранные хендлеры саб-роутера.
**Ловушка:** двойное применение, если саб-роутер уже был вложен куда-то ещё — пин-тест.

## 4. Что НЕ делаем (и почему)

- **tower-`Service`-модель** (poll_ready/backpressure) — не переносится в нашу синхронную
  фибро-модель и не нужна: backpressure у нас на уровне accept-loop (222.7 admission bounded).
- **Middleware, меняющий тип запроса/ответа** (Axum умеет через generic `Service`) — усложнение
  без спроса; наш контракт строго `Handler -> Handler`.

## 4а. Плоская форма `middleware(req, next)` — канон (решение владельца 2026-07-23)

**Факт 2026-07-23:** `src/server/middleware.nv` УЖЕ РЕАЛИЗОВАН в двухуровневой форме
(`Middleware.new(f fn(Handler) -> Handler)`, `@apply`, `@then`, `Router.layer`). Ниже —
**аддитивная** добавка, не переделка.

**Проблема (унаследована от Go/chi):** двойная вложенность на каждое middleware —
`Middleware.new(fn(next) -> Handler.new(fn(req) -> …))`. У chi ровно та же многословность.
Против цели «минимум кода» (222 §0в).

**Канон — плоская форма, одно замыкание:**
```nova
export fn middleware(f fn(ServerRequest, Handler) -> ServerResponse) -> Middleware

ro logging = middleware(fn(req, next) -> ServerResponse {
    ro resp = next.handle(req)          // next — обычное значение Handler
    resp
})
```
Двухуровневая `Middleware.new(fn(next) -> Handler)` ОСТАЁТСЯ — но как **power-форма** для
middleware с разовой работой при композиции (скомпилировать шаблон, выделить пул): там внешнее
замыкание оправдано, оно выполняется один раз при регистрации.

**Про `next` (вопрос владельца — «как в Express?»):** Express-колбэк `(req, res, next)` нам НЕ
нужен — он следствие callback-модели, а не удобство. Наша форма строго лучше по четырём осям:
код ПОСЛЕ `next.handle(req)` выполняется буквально (у Express с async — классическая ловушка);
двойной вызов невозможен по построению (ответ — ЗНАЧЕНИЕ, вернуть можно одно, а не «headers
already sent»); короткое замыкание = просто вернуть свой ответ, забыть нельзя (функция обязана
что-то вернуть); цепочка собирается ОДИН раз при регистрации, а не на каждый запрос.
