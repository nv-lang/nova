## 3. Формы, попадающие в fallback (вход для доработки продюсеров)

### Класс 1 — closure-return-bound method-level generic (частично закрывает d119×2, d277-chain-подформа)

Форма: `fn Recv[T] @method[U](f fn(T) -> U) -> Recv[U]` (или builtin `Option[T]@map[U]`/`Result[T,E]@map[U]`/
`@map_err[F]`), где U/F/… связывается ЗНАЧЕНИЕМ ВОЗВРАТА замыкания-аргумента, а не структурным типом самого
аргумента. Наблюдаемо: `D119Box.map` 0/7, `Option.map` 0/3, `Result.map` 0/2, `Result.map_err` 0/2,
`VecIter.map`/`MapIter.map` 0/4 (d277) — единообразный 0% hit во ВСЕХ шести случаях этого класса в корпусе.

**Диагноз (по коду, `types/mod.rs` Producer B / `resolve_return_channel` ~14290-14355).** Метод-байндинг
method-generic делается через `unify_type(&p_seeded, &a_ty, &method_names, &mut full_subst)`, где `a_ty =
self.infer_expr_type(a.expr(), call_scope)` — ЧЕКЕРНАЯ инференция типа АРГУМЕНТА-ВЫРАЖЕНИЯ. Для non-closure
арга (`.replace(v)`) это тривиально даёт конкретный тип. Для closure-литерала (`|x| str.from(x)`) чекер НЕ
прогоняет тело замыкания за пределы своей обычной проверки — вывод РЕАЛЬНОГО C-типа возврата замыкания (Steps
2/2b в легаси `resolve_mono_type_args`/`resolve_method_level_subst`, `emit_c.rs`) живёт ТОЛЬКО в codegen
(`infer_expr_c_type` на теле замыкания), которому чекер на момент `f1_check_call`/`resolve_return_channel`
не имеет доступа. Отсюда — `infer_expr_type` на closure-литерале либо возвращает `None`, либо тип без
достаточной конкретики → `unify_type` не связывает U → `full_subst` неполон → whole-map completeness gate
(`ordered.len()==generics.len()`) режет запись → канал НЕ пишется → гарантированный miss. **Это НЕ баг**: сам
196.5-дизайн-документ (§9 «Риски», W1-addendum) предвидел этот класс как «переходный fallback» — легаси
codegen-путь (`Steps 2/2b`) остаётся единственным источником для closure-return-bound U вплоть до отдельного
расширения продюсера (нужен чекер-side closure-body-return-type inference — самостоятельная, более крупная
задача, не в объёме этого захода). Безопасность НЕ под вопросом (fallback = легаси-строка, byte-identical по
построению) — вопрос только о ПОКРЫТИИ.

### Класс 2 — generic-параметр используется ТОЛЬКО в позиции аргумента/bound, возврат конкретен (d122×2, 0% hit)

Форма: `fn f[K Bound](a K, b K) -> bool` / `fn g[S Bound](s mut S) -> int` — весь generic-параметр служит
только для типизации аргументов/протокол-диспетчеризации ВНУТРИ тела, а ДЕКЛАРИРОВАННЫЙ возврат — конкретный
примитив (`bool`/`int`), НЕ упоминающий генерик вообще.

**Диагноз (по коду, `types/mod.rs` `f1_check_call` ~10635-10771).** Точка записи Producer A — ветка `else if`
условия `(callee.receiver.is_none() || Static) && !callee_gs_inner.is_empty()` (~10667), которая исполняется
ТОЛЬКО когда ПЕРВАЯ ветка (~10636 `if !typeref_mentions_any(ret_ty, &callee_gs_inner) && …`) НЕ сработала —
то есть только когда ДЕКЛАРИРОВАННЫЙ ВОЗВРАТ упоминает generic-параметр каллиси. Для `d122_same_bucket`
(`-> bool`) и `d122f_leaf/mid/outer` (`-> int`) первая ветка ВСЕГДА истинна (возврат не упоминает `K`/`S`) →
код идёт по первой ветке (материализует `resolved_types_buf` напрямую для конкретного `bool`/`int`, что
корректно для 196.4-цели этой ветки) → **Producer A блок вообще НЕ исполняется** → `node_substs` для этого
call-сайта никогда не пишется, независимо от того, насколько тривиально unify'ится `K`/`S` из аргументов.
100% детерминированный structural gap, не зависящий от корпуса/формы вызова — воспроизводится на ЛЮБОМ
generic-fn с конкретным (не generic-зависимым) возвратом. **Минимальный репро** (уже данные файлы —
`d122_bound_method_mono_dispatch.nv`/`d122_generic_bound_forwarding.nv` САМИ являются минимальным репро;
дистиллированная форма):
```
fn f[T](a T) -> bool => true   // ЛЮБОЙ generic-параметр, возврат НЕ его упоминает → 0% hit
```
**Не mismatch, не баг** — Producer A корректно НЕ материализует несуществующий факт (первая ветка уже
корректно закрывает 196.4-возврат); дело в том, что `node_substs` (196.5) — ДРУГОЙ канал (значения подстановки,
не тип результата) — не получает отдельной точки записи, когда возврат конкретен. Готовый вход для доработки
продюсера A: добавить БЕЗУСЛОВНУЮ (не только в `else if`-ветке) попытку заполнить `node_substs`, если
`callee.generics` непусты, независимо от того, попал ли путь в ветку "прямая материализация возврата" или нет
— т.е. поднять блок ~10715-10770 из-под условия ветки `else if` и исполнять его ВСЕГДА, когда
`!callee_gs_inner.is_empty()` (условие на `subst.is_empty()`/полноту уже присутствует внутри, независимой
регрессии не создаёт — additive канал). Не реализовывалось в этом заходе (только чтение+трейсы+документ,
код не менялся).
