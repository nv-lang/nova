# 274.6 — Кортеж есть запись на стеке: свести бухгалтерию к одной

**Статус:** 🚧 В РАБОТЕ с 2026-09-03 (подплан [274](274-novac-self-hosted-compiler.md),
номер унаследован от родителя по конвенции подпланов; интегратор вправе переименовать).
Время — окна 274 в счёт месяца novac (плану 274 месяц отдан владельцем);
чужих окон и оракульих волн план не занимает.

**Требование владельца (2026-09-02, о `novac/src/emit_c/emit_tuple.nv`):** «ты
нагородил второе окно для кортежей, хотя кортежи это те же записи на стеке; это
нарушение, это приведёт к двойной бухгалтерии, т.к. у кортежей так же как и у записей
есть перегруженные операторы, методы и т.п.» → «убрать отдельную бухгалтерию для
кортежей под ноль». Дополнения того же дня: «кортежи могут быть и именованые, тогда не
будет f0»; «у кортежей могут быть параметры со значением по умолчанию, также как у
функций, поэтому это всё одно окно». Уточнение устройства 2026-09-03: у записи заводится
внутренняя характеристика-перечисление `Record | ValueRecord | NamedTupleRecord |
AnonymousTupleRecord`, где `Record` — на куче, остальные на стеке; `ValueRecord` —
отдельная форма языка (`type X value { ... }`), не синоним кортежа.

**ЦЕЛЕВОЕ УСТРОЙСТВО ЖИВЁТ НЕ ЗДЕСЬ**, а в архитектуре:
[docs/dev/novac-architecture.md](../dev/novac-architecture.md), раздел «4б. Форма
записи — одно перечисление». Там написано, КАК ДОЛЖНО БЫТЬ. Этот документ — про то, как
сейчас неправильно, и что сделать, чтобы стало как там.

Документ самодостаточен: замеры, разбор и критерии — здесь; читать переписку не нужно.

## 0. Правило слова (владелец, 2026-09-03) — усиление, судит страж

Дословно по смыслу: «слово tuple может встречаться в комментариях и в
`Record | ValueRecord | NamedTupleRecord | AnonymousTupleRecord`, больше нигде;
конструктор по созданию кортежа это и есть его декларация, т.е. обычная функция
со всеми обычными возможностями, в том числе параметры по умолчанию; если
хочешь завести слово tuple в имени файла или в коде — только при моём
согласовании; всё, что касается сейчас tuple, должно быть удалено».

Из этого следуют три вещи, и все три уже механизированы:

1. **Особой сущности «кортеж» в коде нет.** Не только «нет второго окна
   эмиссии» — нет идентификаторов, видов узлов (`TupleExpr`, `TupleBind`),
   видов типов (`TkTuple`), дверей (`is_tuple`, `mono_tuple_name`,
   `@tuple`-интернер) и файлов со словом tuple. Знание о форме несут ровно два
   имени вариантов перечисления. Это МЕНЯЕТ волны В1–В3 ниже из «свести двери»
   в «удалить сущность»: `TkTuple` уходит в `RecordShape.AnonymousTupleRecord`
   на строке декларации, `TupleExpr`/`TupleBind` растворяются в обычных узлах
   конструктора-вызова и биндинга.
2. **Конструктор кортежа = его декларация = обычная функция.** `type Pair(x
   int, y int = 5)` регистрирует конструктор-функцию `Pair` с обычными
   слотами D102 (умолчания, именованные аргументы, режимы) — никакой своей
   механики построения. `Pair(1)` законен, как законен вызов функции с
   умолчанием. Это упрощает В2: не «научить путь записи скобочной форме», а
   «декларация рождает функцию, дальше всё уже умеет резолвер вызовов».
3. **Новое слово tuple — только с согласования владельца.** Механизм: страж
   (ниже) держит рост красным, так что согласование не на честном слове —
   без правки базы слово физически не заводится, а правка базы видна в диффе.

**Страж усилен тем же днём** (v2): правило СЛОВА по всему `novac/src` — строка
кода (не комментария) со словом `tuple` в любом регистре вне двух разрешённых
идентификаторов, плюс имена файлов. База переснята прогоном: **101** (100 строк
в 23 файлах + `emit_c/emit_tuple.nv`), крупнейшие носители: `sem/mangle.nv` 15,
`emit_c/emit_c.nv` 12, `check/typing.nv` 9, `types/types.nv` 8. Храповик вниз,
цель 0; закрытие плана = `tuple_words=0` и строка стража «цель достигнута».

## 1. Как сейчас неправильно — четыре замера 2026-09-02/03

**1.1. Второе окно эмиссии существует и названо.** `novac/src/emit_c/emit_tuple.nv` —
три двери (`@emit_tuple_typedefs`, `@emit_tuple_lit`, `@emit_tuple_bind`), то есть
typedef, конструктор и деструктуризация; ровно то, что путь записи уже умеет
(`@emit_record_decl` в `emit_decls.nv`, `@emit_record_ctor` в `emit_c.nv:850`).
Построчно разница между `@emit_tuple_lit` и `@emit_record_ctor` сводится к двум вещам:
имя поля (`f{i}` против настоящего) и выбор стек/куча, которого у кортежа нет.

**1.2. Объявленная кортеж-форма молча превращается в НЬЮТАЙП.** Замер:

```nova
type Pair(x int, y int)
fn main() {
    ro p = Pair(1, 2)
    println(p.x)
}
```

Оракул собирает и печатает `1`. novac отказывает:

```
outside the subset: constructing a newtype takes exactly one argument -- its representation
unknown name: nothing with this name is bound at this point
```

То есть `Pair` для novac — ньютайп над `int`: оба имени полей и второе поле отброшены.
Трасса (делегированный агент, сверено запуском):

1. `parse/parse.nv:499-518` — хвост объявления типа уходит в `@type_ref()`; ветки на
   скобочную форму `type X(...)` НЕТ вовсе;
2. `parse/type_ref.nv:114-126` — `@type_ref` читает `(x int, y int)` как один плоский
   прогон листьев, без единого узла `Field`;
3. `sem/slots.nv:361-383` (`shape_of_decl`) — без `Field`-детей классифицирует
   объявление как `ShapeNewtype`, а не `ShapeRecord`;
4. `sem/slots.nv:432-471` (`repr_of_decl`) — берёт ПЕРВЫЙ резолвящийся тип в хвосте
   (`int`) как представление; имя `x` игнорируется как «слово без типа», поле `y`
   теряется целиком;
5. `sem/sem.nv:515-531, 579-645` — `ctx.fields` для `Pair` остаётся пустой навсегда;
   `TypeDef` окончательно `kind: TkNewtype`.

**Первая точка потери — шаг 1.** Починка начинается там.

**Оговорка к замеру, важная для доверия к цифрам.** В первой редакции этой записи были
процитированы другие тексты отказа («unknown field», «#812 names a field the type does
not declare») — они сняты с ФИГУРНОЙ формы `Pair { x: 1, y: 2 }`, а не с канонической
вызов-формы. Неточность нашёл агент-трассировщик, сверка запуском подтвердила. Форму
проверяют `build`, а не `check`: у оракула `check` пропускает то, что валит кодоген.

**1.3. Флаг `by_value` не выражает того, что нужно.** Он двоичный («на стеке или на
куче»), а различать надо ЧЕТЫРЕ формы. Правило счёта: `grep -rn "by_value\|is_value_record"
novac/src --include=*.nv` — 34 строки в 11 файлах (2026-09-03; включая импорты,
сиды-константы и тесты). Из них ПРЯМОЕ чтение поля одно — `sem/mangle.nv:191`,
тело `is_value_record`; перенос значения между проходами один (`sem/sem.nv:616`);
форму по источнику определяют два места (`sem/sem.nv:519`, `sem/harvest.nv:175`,
оба через `decl_is_value`); остальное — вопросы к двери. Значит переход стоит:
одно тело двери + два места классификации + сиды-константы.

**1.4. Мнимый блокер, снятый разбором.** Разведка подала как непреодолимое: у кортежа
`head_id` — это АРНОСТЬ, ключ структурного интернирования (два равных по составу
кортежа — одна строка типа, D123), «значит декларации у него быть не может»
(`types/types.nv:218-224`, `sem/sem.nv:272-279` — `decl_head_of` для `TkTuple` это ICE
по построению). Это смешение ТОЖДЕСТВА и ПРЕДСТАВЛЕНИЯ. Тождество остаётся в интернере
нетронутым; представление переезжает в строку декларации. Невозможна смена тождества, а
не заведение представления.

### В2 — ЗАМЕР НЕПОДВИЖНОЙ ТОЧКИ (шаг 0, 2026-09-03) переформатирует объём

Правило «форму проверяют build, не check» применено к трём формам оракулом
(артефакты C прочитаны):

1. **Именованный кортеж-тип СОБИРАЕТСЯ.** `type Pair(x int, y int)` +
   `Pair(1, 2)` + `p.x`/`p.y` → оракул печатает `1`/`2`. Компилируется как
   ОБЫЧНАЯ запись с полями x, y и позиционным конструктором — ровно
   «конструктор есть функция».
2. **Умолчания конструктора СОБИРАЮТСЯ.** `type Complex(re f64 = 0.0,
   im f64 = 0.0)` + `Complex()` → `0`, `Complex(re: 3.5)` → `3.5`. Обычная
   семантика D102 (умолчание + именованный аргумент).
3. **Позиционный кортеж-тип НЕ собирается — дефект ОРАКУЛА.**
   `type Pt(int, int)` (и `Point(f64, f64)`) + `Pt(1, 2)` + `p.0` → оракул
   валится в C: `error: unknown type name '_NovaTuple_2_8_nova_int_8_nova_int'`.
   Форма законна по D215 (позиционные поля `.0`/`.1`), а кодоген оракула её не
   несёт — тот же класс «принято check, валит codegen», что мы чиним в novac.
   Замер обеих проб (int и f64) 2026-09-03, окно 274.

**Что из этого следует для объёма В2:**

- В2 берёт ТОЛЬКО именованную форму (`type Pair(x int, y int)`, с умолчаниями)
  — она оракулом поддержана, и это дом `RecordShape.NamedTupleRecord`. Это
  запись с именованными полями и функцией-конструктором; всё уже почти умеет
  путь записи, недостаёт разбора скобочного ОБЪЯВЛЕНИЯ и вызов-формы
  конструктора.
- ПОЗИЦИОННАЯ форma (`type Point(f64, f64)` + `.N`) из В2 УХОДИТ: раз оракул её
  сам не собирает, novac по дифф-правилу не обязан её компилировать, и
  «байт-в-байт» тут значило бы повторить сбой сборки. Форма переезжает в В3
  (`AnonymousTupleRecord`-территория) с ОГОВОРКОЙ, что сперва нужен вердикт по
  дефекту оракула (запись в реестр 221.1 заводит интегратор, заготовка ниже).

**Заготовка интегратору для реестра 221.1** (номер даёт он; страж не пускает
TBD в гейт — потому заготовка живёт здесь, как №850): **ОРАКУЛ НЕ СОБИРАЕТ
ПОЗИЦИОННЫЙ КОРТЕЖ-ТИП.** `type Pt(int, int)` + `Pt(1, 2)` + `p.0` — `nova
build` даёт C-ошибку `unknown type name '_NovaTuple_2_8_nova_int_8_nova_int'`;

### В2 разделена по шву «читать» / «конструировать»

Объём В2 оказался двумя связными половинами, и вторая требует машинерии
хойстинга: конструкция-вызовом строит структуру НЕСКОЛЬКИМИ операторами
(временная + присваивания по полям), то есть узел `Call` с ктор-вызываемым
должен хойститься, как `RecordCtor`. Это отдельная механика, а не хвост
разбора, — потому шов:

- **В2а — форма ЧИТАЕТСЯ** (парсер + sem): скобочное объявление даёт узлы
  `Field`, классификатор видит запись, поля попадают в таблицу, форма
  `NamedTupleRecord`. Фигурная конструкция при этом ОТКАЗЫВАЕТСЯ по имени.
- **В2b — конструкция ВЫЗОВОМ** (`Pair(1, 2)`): чекер типизирует позиционные
  аргументы против полей по порядку (умолчания — слоты D102), эмиттер строит
  структуру через хойст во временную.

#### В2а. СДЕЛАНО 2026-09-03 (окно 274)

Разбор: ветка `LParen` в `@type_decl` (parse.nv) читает поля тем же парным
разбором «[режим] имя + `@type_ref()`», что фигурная ветка, плюс умолчание
`= expr` той же формой, что параметр функции; запятая — тривия объявления.
Классификация: `shape_of_record_decl` различает три формы одним сканом
(VALUE_MARKER → ValueRecord, лист `LParen` → NamedTupleRecord, иначе Record).

**Фигурная конструкция отказана НАМЕРЕННО, и это замер, а не вкус:** оракул
принимает `Pair { x: 1, y: 2 }` своим `check` и валится в C
(`undeclared identifier 'Nova_Pair'`), то есть эмитить её значило бы придумать

### В2b. Конструкция вызовом — СДЕЛАНО 2026-09-03

**Ваше правило сэкономило всю механику.** Конструктор зарегистрирован обычной
строкой таблицы функций (`register_paren_ctors`, sem.nv), поэтому арность,
именованные аргументы, умолчания и коэрсия — ответы СУЩЕСТВУЮЩЕГО резолвера;
волна не написала для них ни строки. Отказ на `Pair(1)` вышел ТОЧНЕЕ оракулова:
он называет пропущенный параметр («this call omits `y`, a parameter with no
default value»), а оракул говорит «expects exactly 2 arguments».

**Три структурных риска решены замером, а не выбором:**

1. Строка конструктора заводится ПОСЛЕ `collect_types_with`: `own_cnt`
   фиксируется его последней строкой (sem.nv:886), и строка, добавленная
   внутри, отвечала бы `compiles_body == true` — то есть врала бы, что у неё
   есть тело. Снаружи она честно отвечает false, и эмиттер по этому признаку
   печатает конструкцию, а не вызов.
2. В `defs` конструктор НЕ пишется: там одно плоское пространство с
   last-put-wins, и запись под именем типа вытеснила бы сам тип. Резолв вызова
   этого и не требует — `FnIndex` строится напрямую из `fns.rows`
   (resolve.nv:85-101). Оба факта сверены мной по коду.
3. Записывается `CalleeFn(row)`, а не `CalleeCtor(type)` — потому что
   конструктор ЕСТЬ функция, и эмиттеру нужна СТРОКА, чтобы прочитать значения
   умолчанных слотов. Первая проба `Complex()` иценула ровно на этом. Инвариант
   «тип в позиции вызова — не вызов функции» (type_of.nv) снят: он и был тем,
   что правило владельца отменяет; арм отвечает возвращаемым типом строки.

**Эмиссия — форма неподвижной точки:** составной литерал одним выражением,
`((NovaTuple_Pair){((nova_int)1LL), ((nova_int)2LL)})`, снят с C оракула. Хойст
не нужен (в отличие от фигурного конструктора, который строится по полям через
временную) — прежняя редакция карты его планировала зря.

**Приставка `NovaTuple_` — цитата ABI оракула, одной константой.** Наша эмиссия
линкуется в его оболочку, переименовать имя нельзя (P25). По P5 оно живёт в
`builtins` как данные (`PAREN_RECORD_C_PREFIX`), читает дверь манглинга. База
слова 101 → 102 поднята ОКНОМ и помечена ОТМЕНЯЕМОЙ: правило владельца
защищает от собственных сущностей со словом, а не от цитаты чужого ABI (тот же
класс `_NovaTuple_` уже в базе); при вето строка снимается вместе с эмиссией.

**Приёмка:** носитель `examples/basics/named_tuple.nv` (`Pair(1, 2)`,

#### В3-1. Анонимный кортеж строится дверью записи — СДЕЛАНО 2026-09-03

`@emit_tuple_lit` УДАЛЁН. Анонимный кортеж строится тем же
`@emit_record_ctor(init, vtype, positional)`, что и запись: пять его вызывателей

же хойстом каждого компонента перед своей строкой присваивания (замер §3а). Составной
литерал C дал бы другую гарантию — порядок вычисления инициализаторов там не
определён, — поэтому дверь строит временное значение и присваивает по полю.

**Доказано:** три носителя совпадают с оракулом байт-в-байт штатным сверщиком
`scripts/tools/novac-e1-smoke.sh` — `tuple_pair_projection` (`1|2`),

**РЕВЕРС:** арм позиционной сборки заглушён (`false &&`) — носитель печатает

**База слова 102 -> 97 — храповик пошёл ВНИЗ впервые** (первое движение вниз за
всю жизнь стража), летопись в самой базе.

##### Три находки внутри волны, каждая — «верно по совпадению»

1. **Владелец (по диффу):** `@judge_record_ctor` судил `NamedTuple => true`, а
   скобочных ОБЪЯВЛЕННЫХ форм после расщепления стало две. `Point { ... }` фигурную
   конструкцию не отказал бы. Стало `NamedTuple | PositionalTuple => true`. Не
   проявлялось лишь потому, что парсер позиционное объявление ещё не читает, —
   тот же класс, что чтение по `LParen`.
2. **Причина отказа названа НЕВЕРНО — развернул интегратор (реестр №889).**
   Комментарий говорил «оракул не умеет фигурную форму». По D215 («Конструирование»,
   амендмент 2026-08-05) конструирование скобочного типа ПОЗИЦИОННОЕ, а фигурной
   формы спека не определяет вовсе. Значит дефект не в кодогене оракула, а в том,
   что его ЧЕКЕР принимает форму вне языка; novac здесь строже и правее, и его
   отказ остаётся ПОСЛЕ починки №889, а не отменяется ею. Заодно сужен №888:
   ломаются позиционные ОТ ДВУХ компонентов, `type One(int)` собирается (потому
   `type CStr(*u8)` в std никогда этого не задевал).
3. **Стражи П21 и П31 тянули один `else` в разные стороны.** `else` при накоплении
   флага `paren` был заведён ради П31 (ветка про отсутствие), а П21 требует, чтобы
   `else` после проверки ВИДА был честным отказом. Разрешено не заглушением, а
   снятием ветвления: `paren = paren || leaf_kind(c) == TokenKind.LParen` — накопление,
   а не диспетчер, и судить нечего обоим.

   записи»: **дверь записи надо построить, и сразу одну на обе формы**, как

2. **`ro Point(x, y) = p` ВНЕ ОБЪЁМА.** Оракул её отказывает как опровержимый
   образец, значит неподвижной точки для неё нет и совпадать не с чем. См.
   §2д — это противоречие спеки с компилятором, и решает его владелец.
3. **Правило `..` энфорсится оракулом** и текстом, который стоит взять
   дословно: «record-pattern binding lists N of M field(s) of `X` without `..`».
   D411 даёт ему код-тег `[E_RECORD_PATTERN_NEEDS_REST]` — свой не выдумывать.
4. **Приёмник вычисляется РОВНО ОДИН РАЗ** — замерено: `mk()` печатает `99`
   один раз. Это то же свойство порядка эффектов, что доказано в В3-1 для
   конструктора, и носитель у него уже есть.

**Объём волны:** `parse` учится читать фигурный образец в биндинге; `check`
получает ОДНУ дверь, судящую «подходит ли ФОРМА образца типу» вместо нынешнего
`is_tuple` (`typing.nv:812`); `emit` получает одну дверь, кладущую приёмник во
временное ОДИН раз и биндящую по полю. Имя двери — не `tuple_*` (правило
слова): по D411 это `pattern`/`destructure`.

**Приёмка (машинная):**

- носитель `examples/basics/destructure_record.nv` — обе формы (`{x, y}` и
  `{x, ..}`) плюс кортежная в одном файле — совпадает с оракулом байт-в-байт по
  `scripts/tools/novac-e1-smoke.sh`;
- носитель порядка эффектов: приёмник с побочным эффектом печатает его РОВНО
  ОДИН раз (`99` однажды, не дважды);
- негативная фикстура: частичный список без `..` отказывается, и сообщение
  цитирует поля («N of M»), а не общую фразу;
- **реверс:** заглушить биндинг полей — носитель краснеет; заглушить правило
  `..` — краснеет негативная фикстура. Каждый реверс краснит СВОЮ пробу;
- храповик корпуса двигается на носитель; слово `tuple` в коде НЕ растёт
  (сегодня 97).

**Не делаем (границы).** `ro Point(x, y) = p` — оракул отказывает, форма вне
объёма до решения владельца (§2д). Вложенный образец внутри элемента кортежа
(`ro (a, {x, ..}) = pair`) — сама D411 объявляет его не проходящим правило `..`
в оракуле; если novac его тоже не возьмёт, это ПАРИТЕТ, а не пробел.
Переименование `X` в `{поле: имя}` (D411 разрешает) — не в этой волне: у
оракула форма есть, но носителя в корпусе нет, и добавлять её вместе с новой
дверью значит мешать два риска.

**Открытые вопросы.** Один, и он с умолчанием: брать ли переименование
`{поле: имя}` в эту же волну — **умолчание «нет»** (см. границы), адресат —
окно 274 при планировании В3-3, срок — до начала кода В3-3. Блокирующих
вопросов у волны нет: всё, что решала спека, D411 уже решила.

**Спека уже решила это за нас, и решила в пользу правила владельца.** Искать
развилку не пришлось — D411 «Record-деструктуризация в биндингах `ro`/`mut`»
(03-syntax.md:12005) говорит прямо:

- «Грамматика паттерна — **ровно match'евская** (один паттерн-язык, ноль особых
  случаев)»;
- «Irrefutability: паттерн обязан быть неопровержимым — **записи и named-tuple
  да**» — то есть спека ставит их в один ряд ЯВНО, а не по нашей аналогии;
- «Семантика — pattern-native, **БЕЗ отдельного AST-десугара**»: кодоген
  `emit_record_destructure` эмитит `T tmp = <e>;` РОВНО один раз, затем биндит
  поля;
- сама D411 объявляет себя симметричной «уже принятой кортежной
  деструктуризации (`ro (a, b) = ...`)», то есть кортежная форма старше и
  записная пристроена К НЕЙ.

Плюс `03-syntax.md:1975`: `ro Point(x, y) = p` — разбор ИМЕНОВАННОЙ скобочной
формы по её же конструктору.

**Что из этого следует для novac, без выбора с моей стороны:**

1. Двери на разбор кортежа заводить НЕЛЬЗЯ — не потому, что так велит правило
   слова, а потому что спека требует одного паттерн-языка. Вторая дверь была бы
   нарушением D411, а не только 274.6.
2. Временное значение вычисляется РОВНО ОДИН РАЗ. Это тот же порядок эффектов,
   что доказан в В3-1 для конструктора: `e` вычисляется однажды, дальше идут
   чтения полей. Носитель обязан это ловить — побочный эффект в `e`, напечатанный
   один раз, а не дважды.
3. `..` обязателен при частичном списке полей и запрещён при полном — правило
   D411, и оно НЕ наше, значит и диагностика должна ссылаться на её код-тег
   (`[E_RECORD_PATTERN_NEEDS_REST]`), а не выдумывать свой.
4. Опровержимый паттерн в биндинге — отказ `[E_REFUTABLE_BINDING]`, не молчание.

**Замер шага 0 (обязателен ДО кода, как в В2):** прогнать через ОРАКУЛ четыре
формы и записать неподвижную точку — `ro (a, b) = p` на анонимном кортеже,
`ro Point(x, y) = p` на именованной скобочной, `ro {x, y} = p` на ней же,
`ro {x, ..} = p` частичный. В В2 такой замер переформатировал объём волны, и
предполагать вместо замера здесь нельзя тем более: D411 помечена IMPLEMENTED
2026-07-07, но реализована она в ОРАКУЛЕ, и что из этого он берёт СЕГОДНЯ —
вопрос к бинарю, а не к статусу в спеке.

**Границы:** вложенный record-паттерн внутри элемента кортежа (`ro (a, {x, ..})
= pair`) сама D411 объявляет не проходящим `..`-правило в оракуле — значит это
НЕ наш долг и не наш дефект; если novac его тоже не берёт, это паритет, а не
пробел.

## 2б. ПРОТИВОРЕЧИЕ В СПЕКЕ — вопрос владельцу, оба места дословно

`AGENTS.md` («Order of precedence»): противоречие МЕЖДУ уровнями окно не
разрешает, а докладывает владельцу с цитатами. Здесь противоречие внутри одного
уровня — спеки, — и потому тем более не наше.

**Место А — D102, `spec/decisions/03-syntax.md:5623`, `:5615`, `:5631`:**

> 2. **Параметр без дефолта** связывается позиционно **или** по имени.
> `f(required: 1, opt: 5)     // обязательный тоже можно по имени`
> 6. ... параметр без дефолта — обязателен (позиционно или по имени).

**Место Б — D215, `spec/decisions/02-types.md`, амендмент 2026-08-05:**

> `// Construction — ПОЗИЦИОННО (амендмент 2026-08-05: см. ниже «Конструирование`
> `// и деструктуризация»; прежние примеры показывали именованные аргументы для`
> `// полей БЕЗ дефолтов, что противоречит D102)`

Амендмент объявляет именованные аргументы для полей БЕЗ дефолтов противоречащими
D102 — а D102 их прямо РАЗРЕШАЕТ, причём отдельной строкой с примером.

**Третье, проверено грепом по всему `spec/`:** раздела «Конструирование и
деструктуризация», на который ссылается амендмент, в спеке НЕ СУЩЕСТВУЕТ — ноль
вхождений. Правило опирается на несуществующую цитату.

**Как это ведут два компилятора** (замерено, `probes/.../f2b_*`, `.../f2c_*`,
контроль `.../h1_named_arg_plain_fn/`):

| форма | оракул | novac |
|---|---|---|
| `type Pair(x int, y int)` + `Pair(x: 1, y: 2)` | ОТКАЗ `E_TUPLE_NAMED_ARG_NO_DEFAULT` | принимает |
| `type Pair(x int, y int = 5)` + `Pair(1, 2)` | печатает `1`,`2` | ОТКАЗ по D102 |
| обычная `fn` + именованный аргумент без дефолта | принимает | принимает |

То есть у оракула у кортежного конструктора правило СВОЁ и зеркальное D102, а у
обычной функции — общее. novac применяет общее везде.

**Умолчание окна, чтобы работа не встала:** novac НЕ меняется, потому что его
поведение следует и D102, и правилу владельца «конструктор кортежа есть обычная
функция со всеми обычными возможностями». Если владелец решит иначе — это
амендмент к D102 либо к D215, и номер D-блока назначает интегратор.

**СНЯТО 2026-09-04 — вопроса нет, была моя ошибка рассуждения (поймал
владелец).** Здесь стояло: «`value` и скобочная форма — НЕЗАВИСИМЫЕ оси, и
`type Point value(x int, y int)` есть и то, и другое, оракул её собирает;
значит перечисление надо разводить по осям». Довод неверен целиком.

**Спека:** D215, таблица allocation contract, — `type X(T1, T2)` и
`type X(name1 T1, name2 T2)` суть **stack, value**; `type X { name T }` —
**heap, reference**. То есть скобочная форма УЖЕ value по построению. D241
(канонический порядок модификаторов) весь про фигурную форму
(`export type Point value priv { x f64, y f64 }`) и описывает `value` как то,
что переводит тип С КУЧИ НА СТЕК. Кортеж уже на стеке — переводить нечего.

**Значит оси НЕ независимы, и перечисление владельца верно как есть:** у
скобочной формы «value» не свободный признак, а её собственное свойство, и
второго измерения тут нет.

**Чем была ошибка:** доводом «оракул её собирает». По `AGENTS.md` («Order of
precedence») компилятор НИЖЕ спеки, поэтому форма, которую оракул принимает, а
спека не определяет, — дефект оракула, а не доказательство существования формы.
Это ТРЕТИЙ случай того же класса за два дня: фигурная конструкция скобочного
типа (№889) и `ro Point(x, y) = p` (§2д) — там оракул тоже принимает или
отказывает мимо спеки, и оба раза novac оказывался прав.

**Что остаётся настоящим:** сам порядок тестов в `shape_of_record_decl`
(`VALUE_MARKER` проверяется раньше скобки) на ЗАКОННЫХ формах не ошибается —
законной формы `value(` не существует. Находка Н4 отчёта сохраняет силу лишь
как замер поведения оракула на форме вне языка; строкой реестра она проходит по
классу «оракул принимает форму, которой спека не знает», вместе с №889, и
номер ей — интегратора.

## 2в. В3-1а. ПОЧИНКА №TBD-A — порядок объявлений в эмиссии (2026-09-03)

Охота нашла дефект в худшем направлении: `novac check` МОЛЧИТ, а выпущенный C
не собирается. Правило «дефект чинится той же волной» — поэтому починка здесь, а
не в очереди.

**Две причины под одним симптомом, и лечатся они РАЗНЫМ.** Это главное, что
дала проба, и без разделения починка была бы половинчатой:

| поле | почему ломалось | чем держится |
|---|---|---|
| указатель (`type Boxed { node Node }`, куча) | имя типа не объявлено к моменту использования | ПРОХОД 1 — `typedef struct X X;` на каждую запись и сумму ДО всех тел |
| по значению (`type Inline { at Point }`, `Point value`) | нужен ПОЛНЫЙ тип, typedef не заменяет | ПРОХОД 2 — тела в порядке зависимостей |

Проход 2 — цикл до неподвижной точки, а не рекурсия: он очевидно завершается, не
требует состояния на эмиттере, и его отказ говорит по делу — раунд, не выпустивший
НИЧЕГО при непустом остатке, есть цикл полей по значению, то есть тип бесконечного
размера, который обязан был отказать чекер.

**Признак «лежит инлайн» не выдуман:** `c_type` пишет указатель ТОЛЬКО для формы
`Record`, остальные формы спеллит инлайн (`sem/mangle.nv`). Поэтому дверь
`@dep_done` НЕ разбирает вид типа сама, а спрашивает `is_value_record` и
`is_value_sum`. Первая редакция разбирала — и страж правила слова поймал её как
рост (99 > 97): второй исчерпывающий match по одному закрытому множеству и БЫЛ
вторым диспетчером (П18), а слово оказалось лишь тем, как это стало видно. По той
же причине проход 1 не завёл своего match: оба прохода идут через ОДНУ дверь
`@emit_decl_kind(t, fwd_only)` — один разбор, два поведения.

**Приёмка — четыре доказательства, все запуском:**

1. носитель `examples/basics/forward_type_ref.nv` (обе раскладки в одном файле)
   совпадает с оракулом побайтно: `9`/`4`/`7`;

#### В3-3. Снос `emit_tuple.nv` — что там осталось и куда уезжает (замер 2026-09-03)

Владелец спросил 2026-09-03, законен ли ещё этот файл. **Не законен: имя файла

станет упорядочен наравне с записью. Сегодня такой пробы нет; она и будет
приёмкой.

волной В3-2, и это не наше решение: D411 требует ОДНОГО паттерн-языка («ровно
match'евская грамматика, ноль особых случаев»), значит вторая дверь разбора
нарушала бы спеку, а не только этот план.

**Порядок волн, и он вынужденный:** В3-2 (разбор) снимает вторую дверь, В3-3
(объявление) — первую; файл удаляется, когда обе пусты. Раньше В3-2 файл не

## 2д. ВТОРОЕ ПРОТИВОРЕЧИЕ — спека против компилятора (замер 2026-09-04)

По `AGENTS.md` («Order of precedence») спека СТАРШЕ компилятора, но
противоречие МЕЖДУ уровнями окно не разрешает, а докладывает с цитатами. Здесь
оно чистое.

**Место А — спека, `spec/decisions/03-syntax.md:1969-1976`.** Раздел
нормативный: «Что отвергнуто» начинается НИЖЕ, со строки 1987, — то есть форма
показана как ЗАКОННАЯ:

> Pattern matching как альтернатива:
> ```nova
> match p {
>     Point(x, y) => x + y
> }
> ro Point(x, y) = p      // деструктуризация
> ```

**Место Б — оракул, замерено на пробе `docs/plans/repro/p274-6-v32-step0/f2_paren_ctor_bind/`:**

```
./nova-cli/target/release/nova.exe build docs/plans/repro/p274-6-v32-step0/f2_paren_ctor_bind/f2_paren_ctor_bind.nv -o /tmp/x.exe
error: refutable pattern in `let`: `Point` is a variant-pattern
```

То есть оракул считает `Point(...)` в биндинге ОПРОВЕРЖИМЫМ образцом (как
вариант суммы), тогда как `Point` здесь — скобочная ЗАПИСЬ, у которой вариантов
нет и опровергнуть нечего. Соседняя форма из того же примера — `match p { Point(x, y) => ... }` — вопросов не вызывает.

**Что это значит для В3-2.** Форма выведена из объёма волны: неподвижной точки
для неё нет, совпадать не с чем. Умолчание окна — **novac эту форму НЕ учит**,
пока владелец не решит.

**Три возможных исхода, и выбор не окна:** (1) прав оракул — тогда пример в
спеке надо снять или перенести в «Что отвергнуто»; (2) права спека — тогда это
дефект оракула (опровержимость определяется по ВИДУ объявления, а не по тому,
что имя стоит перед скобкой), и ему нужен номер; (3) форма законна, но только
для сумм — тогда пример двусмыслен и требует оговорки.

**Связь с §2б:** это ВТОРОЕ противоречие в области скобочных форм за два дня.
Первое — D102 против амендмента D215 (именованный аргумент для поля без
умолчания). Оба про одно: что именно значит «скобочная форма» — вызов
конструктора, образец варианта или запись. Разводить их по отдельным решениям
можно, но стоит посмотреть вместе.

## 2е. РЕШЕНИЯ ВЛАДЕЛЬЦА 2026-09-04 — четыре из пяти вопросов закрыты

**1. Аргументы: обязательный — ПОЗИЦИОННО.** Из D102 уходит «или по имени».
Спека поправлена тем же слиянием (`03-syntax.md`, правила 2 и 6, плюс пример,
ставший ошибочным). Правило стало симметричным и читается одной фразой:
**обязательный — позиционно, дефолтный — по имени**, место аргумента само
говорит, какой он. Побочно исчезает противоречие §2б: амендмент D215 уже
исходил из этого чтения.

**ЧТО ЭТО МЕНЯЕТ В novac — он теперь НЕПРАВ и должен измениться.** Замер
охоты (`f2b_named_required_with_default`): оракул отказывает
`E_TUPLE_NAMED_ARG_NO_DEFAULT`, а novac собирает и печатает. После правки
спеки прав оракул. Волна: отдельная, после В3-2; носитель уже есть.

**2. `ro Point(x, y) = p` — ЗАПРЕЩЕНА.** Разбор не называет тип: позиционная
форма — `ro (x, y) = p`, именованная — `ro {x, y} = p`. Пример снят из спеки
тем же слиянием. Это подтверждает границу В3-2, поставленную по замеру.

**3. Шестая форма `(file str, line int)` — ВВОДИМ.** Изменение языка, значит
нужен D-амендмент в том же слиянии, а номер D-блока даёт интегратор — запрошен.
Цена в novac мала и названа заранее (§4а): шестой вариант перечисления плюс арм
разбора, потому что классификатор уже различает «имя у поля есть/нет».

**4. ABI-имя `_NovaTuple_...` — СОГЛАСОВАНО** как названный интероп в дверях
мангла. Значит храповик слова останавливается на этом остатке, а ноль
достижим вместе с собственной прелюдией. Владелец добавил: **после релиза
Карины пересмотреть имя** — заведено маркером `[M-abi-tuple-name-after-carina]`.

**5. `f0..fN` — вопросом не является.** Замерено: так поле называет ОРАКУЛ в
своём C (`typedef struct { nova_int f0; nova_int f1; } _NovaTuple2;` в снимке
оболочки), значит novac обязан писать те же имена и свободы тут нет.
Пользовательская сторона в спеке закреплена и другая — доступ через `obj.0`
(`03-syntax.md:1928`).

**ОСТАЛСЯ ОДИН ВОПРОС — зеркальная половина того же правила.** D102 п.1
(«параметр с дефолтом — keyword-only, позиционно нельзя») владелец не трогал, а
замер показывает, что **оракул его нарушает**: `type Pair(x int, y int = 5)` +
`Pair(1, 2)` он собирает и печатает `1`/`2`
(`docs/dev/hunts/novac/probes/2026-09-03-sem-k4/f2c_defaulted_positional/`),
тогда как novac отказывает по D102. То есть по первой половине правила прав
оракул, по второй — novac. **Умолчание: п.1 остаётся как есть**, novac не
меняется, а поведение оракула — строка реестра. Адресат — владелец; срок — до
волны, которая будет чинить аргументы конструктора.

#### В3-2а. Связыватель образца — УЗЕЛ, и тип имени лежит в канале — СДЕЛАНО 2026-09-04

**Волну назначили два стража, и ни одному нельзя было уступить.**
`check-novac-channel-one-writer` запрещает эмиттеру спрашивать дверь ПОДБОРА
(`field_type`, `has_field`) — «разрешение имени есть решение, и решает его
чекер». `check-novac-resolve-discipline` запрещает линейный скан по именам в
`sem`. Щели между ними нет, и это не досада: они вдвоём называют единственную
законную конструкцию — **тип связываемого имени обязан ЛЕЖАТЬ В КАНАЛЕ,
записанный чекером**. Мешало ровно одно — связыватель был голым ТОКЕНОМ, а
идентичность в этом дереве выдаётся только ветвям.

**Что сделано.** Парсер (`@push_binder`, `parse/expect.nv`) заворачивает каждое
имя образца в узел `Name` — форма уже существовала, `expr.nv:675` строит её же
для имени в выражении. Чекер записывает тип связывателя в канал (обе формы,
включая путь после отказа — там он пишет `no_ty()`). Эмиттер читает
`@out.type_of(b.id_of())` и больше не спрашивает ничего.

**Ловушка, названная в самой двери:** инициализатор `ro (a, b) = p` — тоже узел
`Name`, поэтому дверь `pattern_binders` идёт по образцу и ОСТАНАВЛИВАЕТСЯ на
`=`. Обход «все ветви — связыватели» принял бы разбираемое значение за одно из
связываемых имён.

**Доказано:** носитель `destructure_record.nv` байт-в-байт, держатели 13/13,
корпус 53/45 без изменений, самочтение 70/71 -> **71/72**.
**РЕВЕРС:** запись типа в канал заглушена — носитель краснеет; восстановлено —
зелёный.

**Урок, который дороже волны.** В3-2 я закоммитил, прогнав ТЕ стражи, которые
чинил, и не прогнав остальные. Правка под `resolve-discipline` красила
`channel-one-writer`, и коммит уехал с красным стражем. Правило простое и
теперь записано: **после правки под страж гоняется вся развёртка, а не
исправленный страж.**

#### В3-4а. `for` не пересчитывает тип элемента — СДЕЛАНО 2026-09-04

Эмиттер брал тип элемента цикла сырым обращением к интернеру, тогда как чекер
спрашивал дверь `for_head_elem` — тот же К4, что найден в `fits` и в разборе.
Дверь жила в `check/`, эмиттеру недоступной (`emit_c` не импортирует `check` ни

**Почему свой файл, а не `mangle.nv`, где уже сидят `shape_of`/`is_tuple`:** роль

#### В3-4. `for` ходит по ПРОТОКОЛУ, а не по методам одного типа (запрошено владельцем трижды)

**Взято в план 2026-09-04 после ТРЕТЬЕГО вопроса владельца об этом файле.**
Дважды до того я отвечал по существу и не заводил волну — заметка работой не
становится, и это записано здесь, чтобы следующий раз не понадобился.

**Что не так в `novac/src/emit_c/emit_for.nv` — три вещи в семнадцати строках:**

1. **Дверь знает ОДНУ коллекцию по имени.** `VEC_LEN_METHOD` и
   `VEC_GET_METHOD` (`emit_for.nv:42-43`) захардкожены, поэтому `for` умеет
   ходить только по `Vec`. Класс — К6 (энфорс перечислением форм): любой другой
   источник дверь просто не увидит.

   **ССЫЛКА НА D238 БЫЛА МОЯ И БЫЛА НЕВЕРНА (снята 2026-09-04, шаг 0).**
   Владелец назвал файл, а не D-блок; D238 я подставил сам. Спека решает иначе:
   `for x in c` управляется **D58** («Range-литерал, `Iter[T]` protocol,
   `for x in c` implicit iter», 03-syntax.md:3991) и десугарится
   `{ mut _it = c.iter(); loop { match _it.next() { Some(x) => body, None => break } } }`,
   протоколы — `Next[T]`/`Iter[I]` (D241+D242). D238 описывает `a[key]`, то есть
   ИНДЕКСИРОВАНИЕ, а не обход, — что и сказано в границах этой же волны абзацем
   ниже; я написал границу верно и всё равно построил приёмку на неверном
   блоке. Порядок старшинства (`AGENTS.md`, Order of precedence) ставит спеку
   выше моей памяти, и это ровно тот случай.
2. **`.value` руками.** `get(v, i).value` лезет в поле `Option`, минуя языковой
   механизм разворачивания.
3. **Тип элемента ПЕРЕСЧИТЫВАЕТСЯ** — `@ctx.tys.arg(ht, 0)` (`emit_for.nv:35`),
   хотя док-комментарий строкой выше сам говорит: «чекер связал переменную
   цикла, эта дверь только произносит решённое». Тот же К4, что найден сегодня
   в `fits` (§2ж) и подтверждён охотой (`emit_c × К4`, подозрение по
   `emit_for.nv:41`).

##### ЗАМЕР ШАГА 0 (2026-09-04) РАЗДЕЛИЛ ВОЛНУ НАДВОЕ

Пробы — `docs/plans/repro/p274-6-v34-step0/`, каждая в своём каталоге.

**Неподвижная точка ЕСТЬ.** `iter_protocol/iter_protocol.nv` — тип `Count` с
`@iter() -> CountIter` и `CountIter mut @next() -> Option[int]`, ни одного
`Vec`. Оракул собирает и печатает `012`. То есть протокольный обход D58 у
оракула работает, и совпадать есть с чем.

**novac на той же пробе не отказывает, а ИЦАЕТ** — «check: call target not in
the registry (#652 class)». И вот что выяснила бисекция, и она переворачивает
волну: **ICE не про обход вообще.**

| проба | форма | novac |
|---|---|---|
| `unknown_call/` | вызов несуществующего имени | отказ ПО ИМЕНИ (верно) |
| `some_return/` | `fn mk(n int) -> Option[int] => Some(n)` | отказ ПО ИМЕНИ |
| `return_none/` | то же тело блоком, с `if n < 0 { return None }` | **ICE** |
| `opt_some/`, `iter_calls/`, `iter_protocol/` | всё, что содержит `return None` | **ICE** |

То есть застава подмножества стоит на ОДНОМ входе (хвостовое выражение) и не
стоит на другом (`return`): одна и та же форма на одном пути — диагностика, на
другом — ICE. Это самостоятельный дефект novac (реестр, номер запрошен у
интегратора 2026-09-04), и он БЛОКИРУЕТ протокольный обход: любой честный
итератор кончается `return None`.

**Отсюда волна делится, и порядок вынужденный:**

- **В3-4а — снять К4 из `emit_for.nv`** (тип элемента пересчитывается, хотя
  чекер его уже связал). Не зависит ни от протокола, ни от Option, доказуема
  сегодня. Приёмка ниже.
- **В3-4б — обход по D58** (`iter()`/`next()`), ПОСЛЕ починки заставы `return`
  и введения конструкторов `Option` в подмножество. Её приёмка пишется, когда
  застава закрыта: раньше носитель нельзя даже собрать.

**Приёмка В3-4а (машинная):**

- существующие носители циклов по `Vec` (`for_call_head`,
  `for_call_effect_once`, `for_name_head`) остаются байт-в-байт;
- держатель канала: тип элемента цикла читается из канала, а не выводится
  повторно; `@ctx.tys.arg(ht, 0)` в `emit_for.nv` больше нет (греп);
- **реверс:** вернуть пересчёт — держатель канала краснеет.

**Приёмка В3-4б (пишется после заставы, здесь только неподвижная точка):**
носитель по `iter_protocol/iter_protocol.nv` печатает `012` байт-в-байт;

**Не делаем (границы).** Протокольный обход по КЛЮЧУ (словарь) — не эта волна:

## 3а. Порядок эффектов — проверен ДО правки В3-1 (2026-09-03)

Дверь `@emit_tuple_lit` строит кортеж ТРЕМЯ операторами и объясняет почему:
каждый компонент хойстится перед СВОЕЙ строкой присваивания, «so a
component's side effect runs where the source puts it». В корпусе на это
стоит носитель `tuple_ctor_effect_order` (`(tick(1), tick(2))`). Составной
литерал, которым В2b печатает объявленную форму, порядок инициализаторов в C
НЕ фиксирует — значит перевод анонимного кортежа на ту же дверь мог бы тихо
сменить порядок эффектов.

**Проверено пробой, а не рассуждением:** `Pt(one(), two())` на объявленной
форме — оракул печатает `one`/`two`/`1`, а novac ОТКАЗЫВАЕТ по имени:
«outside the E1 subset: two arguments that both call something, and the
emitter does not fix their order yet (F65)». То есть форма, в которой порядок
мог бы разойтись, у нас не эмитится ВООБЩЕ — застава F65 стоит выше и
покрывает обе конструкции, и мой составной литерал В2b дефекта не внёс.

**ОТВЕТ СНЯТ ПРОГОНОМ, и он переворачивает В3-1.** Носитель
`tuple_ctor_effect_order` (`(tick(1), tick(2))`) F65 НЕ отказывает — он
проходит чекер без единой диагностики и ЭМИТИТСЯ:

    _NovaTuple_2_8_nova_int_8_nova_int _novac_tmp_t1;
    _novac_tmp_t1.f0 = ...tick(1);
    _novac_tmp_t1.f1 = ...tick(2);

то есть порядок эффектов зафиксирован ИМЕННО этими двумя присваиваниями. F65
стоит на объявленной форме (её конструктор — обычный вызов, и там застава
работает), а на анонимном литерале — нет.

**Следствие: составной литерал для анонимного кортежа НЕЛЬЗЯ.** C не
фиксирует порядок вычисления инициализаторов, так что перевод на форму В2b
либо тихо сменил бы порядок эффектов, либо потребовал бы отказать носителю —
то есть потерять способность, которая уже есть. Прежняя редакция карты вела
ровно туда; поймано пробой ДО правки, а не гейтом после.

**Правильный фолд В3-1:** не составной литерал, а ДВЕРЬ ЗАПИСИ.
`@emit_record_ctor` строит запись ТЕМ ЖЕ способом — временная плюс
присваивания по полям с хойстом каждого компонента перед своей строкой, — и
различие между ним и `@emit_tuple_lit` сводится к тому, откуда берётся имя
поля (объявление против позиции `f{i}`). Значит анонимный кортеж должен ходить
в дверь записи, а `@emit_tuple_lit` — исчезнуть, и порядок эффектов при этом
сохраняется по построению, а не по осторожности.

## 3б. Пятая форма — замечание владельца 2026-09-03

«`AnonymousTupleRecord` не полностью однозначен: у нас есть неименованные
кортежи и анонимные кортежи». Верно, и код это подтверждал буквально: одним
именем звались (а) объявленный тип с позиционными полями — у него ЕСТЬ имя,
безымянны ПОЛЯ; и (б) структурный терм `(1, 2)` — у него нет декларации
вообще. Я эту путаницу сам же усилил, назвав `TkTuple` анонимной формой за
минуту до замечания.

Разделено: `PositionalTupleRecord` — объявленная позиционная форма;
`AnonymousTupleRecord` — структурный терм. Заодно `shape_of` перестал врать
про `TkTuple`: он отвечал `Record`, то есть «на куче», хотя кортеж на стеке —
это было невидимо ровно потому, что у кортежа была своя дверь.

**Пятое имя формально выходит за перечень разрешённых написаний слова
(правило владельца 2026-09-03) — помечено ОТМЕНЯЕМЫМ**, как строка ABI: если
владелец назовёт форму иначе, переименование стоит одной правки, потому что
имя живёт в одном перечислении.

**Полнота проверена компилятором, а не вниманием:** добавление варианта сразу
покраснело `E_MATCH_NON_EXHAUSTIVE` на непокрытом арме — та самая опора П21,
ради которой выбрано перечисление вместо флагов.

## 4а. ШЕСТАЯ КЛЕТКА: анонимный тип с ИМЕНОВАННЫМИ компонентами

**Замечание владельца 2026-09-03:** «может быть ещё без имени: `(file str,
line int)`; возможно, это не оговорено в спеке, надо добавить».

Форма ложится в решётку из двух осей — есть ли имя у ТИПА и есть ли имена у
ПОЛЕЙ:

| | поля именованы | поля позиционны |
|---|---|---|
| тип объявлен | `NamedTupleRecord` (`type Pair(x int, y int)`) | `PositionalTupleRecord` (`type Point(f64, f64)`) |
| типа нет | **ПУСТО — форма владельца** | `AnonymousTupleRecord` (`(1, 2)`) |

**ЗАМЕР (2026-09-03, до всякого кода):** формы в языке СЕЙЧАС НЕТ. Оракул
отказывает на разборе — `fn loc() -> (file str, line int)` даёт
`expected ')', got identifier`; грепом по `spec/decisions/` она не описана.
Значит это не «novac отстал», а форма, которой в языке ещё нет.

**Что из этого следует.** (1) novac её принимать НЕ должен, пока её нет у
неподвижной точки — иначе мы примем программу, которую поставляемый компилятор
не берёт (ровно то расхождение, которого этот план и избегает). (2) Ввод формы
— ЯЗЫК-МЕНЯЮЩЕЕ решение: нужен D-амендмент, а номер D-блока окно не берёт само
(правило AGENTS.md). (3) Имя шестого варианта напрашивается симметричное —
`AnonymousNamedTupleRecord`, — но заводить его до решения значит держать в
перечислении форму, которой нет.

## 5. Открытые вопросы

1. Позиционному кортежу нужны имена полей в таблице полей: брать `f0..fN` (**умолчание**,
   совпадает с нынешним спеллингом эмиссии) или хранить поля без имён с доступом по
   индексу? Адресат — владелец; срок — старт В3; при молчании принимается умолчание.
1а. **Шестая клетка (§4а): вводим ли `(file str, line int)`?** Адресат —
   владелец (это решение о ЯЗЫКЕ, D-амендмент, номер даёт интегратор).
   **Умолчание при молчании: НЕ вводим** — формы нет у оракула, и novac,
   приняв её, разошёлся бы с неподвижной точкой в опасную сторону.
   Срок — не блокирует ни одну волну 274.6: В3 работает с четырьмя
   существующими формами. Если решение придёт, цена его в novac мала:
   шестой вариант перечисления плюс арм разбора, потому что классификатор уже
   различает «имя у поля есть/нет», а форма уже отделена от тождества.
2. **ABI-спеллинг `_NovaTuple_...`** — C-имя структуры анонимного кортежа,
   которым его называет ОРАКУЛ (снято с его вывода; линковка в оболочку идёт по
   этому имени). Правило слова его не милует: строки мангла с этим литералом
   сидят в базе стража и давят вниз, но переименовать их нельзя — имя не наше.
   Варианты: (а) ваша санкция на слово в ОДНОЙ двери мангла как названный
   интероп («уходит с собственной прелюдией») — тогда база останавливается на
   этом остатке до Э5; (б) без санкции — ноль достижим только вместе с
   собственной прелюдией. Адресат — владелец; умолчания НЕТ (правило говорит
   «только при моём согласовании»); срок — старт В3, до него ноль не нужен.
