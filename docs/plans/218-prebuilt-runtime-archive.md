## 0. Что решаем (замер разведки)

C-компиляция ПУСТОЙ программы (`fn main(){}`, dev -O0) = wall ~11с, из них **c-compile
6.5с (58%) и НЕ кэшируется**. Приложение пусто, libuv.lib/Boehm предсобраны → эти 6.5с ≈
перекомпиляция **самого рантайма** (~10 `.c`: runtime.c=647мс, driver.c=739мс, fiber_arena,
alloc_boehm, sched и т.д. — каждый заново на КАЖДУЮ сборку пользовательского кода).
Content-cache (`build_cache.rs`, Plan уже влит) покрывает фронтенд (.c-генерацию), но НЕ
C-компиляцию рантайм-TU.

**Рычаг:** собрать `nova_rt/*.c` ОДИН раз в статический архив `libnova_rt.a` и линковать
готовый — как уже делается для `libuv.lib` (`detect_or_build_libuv`). Эффект: dev-rebuild
**~11с → ~5-6с (−~5с/сборку)**. Сложность средняя, риск низкий (TU рантайма уже независимы).

## 1. Прецедент (уже в кодовой базе)

`detect_or_build_libuv()` — libuv собирается один раз в `libuv.lib`, кешируется, линкуется.
`libnova_rt.a` — тот же паттерн для СВОЕГО рантайма. Аналоги: ccache (C), Go stdlib .a,
Rust prebuilt std.

## 2. Ключевые вопросы реализации

1. **Инвалидация архива.** `libnova_rt.a` перестраивается ТОЛЬКО при изменении `nova_rt/**`
   (хеш содержимого, НЕ mtime — иначе touch ломает). Ключ: хеш всех `nova_rt/*.{c,h}` +
   toolchain-флаги + GC/платформа. Хранить рядом с libuv-кешем.
2. **Флаги-конфигурации.** dev(-O0)/release(-O2+LTO) — РАЗНЫЕ архивы (разные корзины кеша).
   GC boehm|malloc, платформа (win/posix), TSan — тоже отдельные варианты. Не смешивать.
3. **Символьная граница.** Рантайм-TU не должны зависеть от пользовательского кода
   (проверить: generated app.c включает только `nova_rt/*.h`, линкуется с .a — без обратных
   зависимостей). Разведка: «TU рантайма уже независимы».
4. **Заголовки vs объекты.** Архив = только объектники рантайма; `nova_rt/*.h` по-прежнему
   #include'ятся в generated app.c (нужны декларации). PCH для заголовков — отдельный
   меньший рычаг (доминируется этим, см. разведку — НЕ в 218).
5. **Первый холодный build.** Первая сборка после изменения рантайма всё равно платит 6.5с
   (собирает .a). Экономия — на ПОСЛЕДУЮЩИХ (архив переиспользуется). Это ровно dev-rebuild-
   цикл (правка своего кода → рантайм не тронут → архив готов).

## 3. Фазы (эскиз)

- **Ф.1** Сборка `nova_rt/*.c` → `libnova_rt.a` в build-пайплайне (аналог detect_or_build_libuv);
  линковка generated app с архивом вместо per-build перекомпиляции TU.
- **Ф.2** Инвалидация по хешу содержимого `nova_rt/**` + флаги-корзины (dev/release/gc/платформа).
- **Ф.3** Замер: dev-rebuild пустышки cold (собрать .a) vs warm (архив готов) — подтвердить −~5с.
  Гейт: byte-identical поведение (архив = те же объекты, что per-build); conformance/флагман
  без регрессий.

## 5. Runtime-startup — вне 218 (разведка: оптимизировать нечего)

процесса ОС. Ленивая libuv — МИФ (init суб-мс). auto_arm=0 потоков для no-spawn. Отдельных
планов по startup НЕ требуется.
