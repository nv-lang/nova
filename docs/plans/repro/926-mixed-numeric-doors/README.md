# Пробы к №TBD — D405 закрывает арифметику разных ширин, но не сравнение, не int/float и не унарный минус на unsigned

Заведено исследовательским окном (owner-research) 2026-09-04 по вопросу владельца «чем плохо
автоматическое расширение числа при операциях над разными типами, делать ли нам, например
`-u8 → i16`?». Ответ спеки уже есть — D405 (2026-06-30): смешанная арифметика целых — ошибка,
расширение только явным `as`; D54: неявных числовых конверсий нет нигде. Проверено, где D405
держит, а где буква D54 не исполняется. Исследование: `docs/dev/research/2026-09-04-numeric-widening.md`.

## Замер 2026-09-04 (owner-research, `nova-cli/target/release/nova.exe`)

| проба | выражение | `nova check` | `nova build` → stdout | что не так |
|---|---|---|---|---|
| `ctrl_arith` | `u8 + i16` — КОНТРОЛЬ | `E_MIXED_WIDTH_ARITH` (D405) | — | держит |
| `cmp_signedness` | `u32(4294967295) == i32(-1)`, `u32 < i32` | `ok` | built → `true false` | **сравнение вне списка D405**: 4294967295 «равно» −1 — классическая ловушка C, ради которой D405 и писали |
| `cmp_width` | `i64 < i32` | `ok` | built → `true` | сравнение разных ширин — молча |
| `int_float` | `i64 + f64` | `ok` | built → `6.5` | **неявная промоция int → float**; D405 говорит только о целых, D54 — «нигде» |
| `neg_unsigned` | `-a` при `a u8 = 200` | `ok` | built → `56` | **унарный минус на unsigned без правила**: заворот по модулю 256; Rust — ошибка компиляции |
| `float_width` | `f32 + f64`, `f32 < f64` | `ok` | built → `4 true` | **смешение ширин float** — D405 говорит только о целых; правила для float в спеке нет вовсе |
| `float_lit_ok` | `f64 + 1` (int-литерал к float), `ro x f32 = 1.5` (float-литерал в f32) | `ok` | built → `3.5 1.5` | принимается, но D55 п. 4 перечисляет только целые цели — литеральное правило для float **не записано** |
| `float_lit_neg` | `ro n int = 1.5` — КОНТРОЛЬ | `E7301` | — | держит: float-литерал в int отвергается |

D405 перечисляет операторы `+ - * / % >> << & | ^` и говорит «оба операнда — целые одной
ширины и знаковости». Четыре двери вне списка: операторы сравнения, целое с float, разные ширины float,
унарный минус. На всех трёх чекер молчит, Си собирает, программа печатает неверное без
диагностики. Форма та же, что у №904/№906: правило записано там, где о нём вспомнили
(арифметика), а не там, где через него всё проходит (любой бинарный/унарный оператор над числами).

## Дополнение 2026-09-05 (интегратор): те же int/float, но на дверях присваивания и аргумента

Найдено при разборе №959 (проверки возврата нет вовсе). Носитель (2) выше — `int_float`
— показывал смешение целого с float на ОПЕРАТОРЕ. Оказалось, то же самое проходит и там,
где никакого оператора нет, и в ОБРАТНУЮ сторону, с потерей значения.

| проба | выражение | `nova check` | `nova build` -> stdout |
|---|---|---|---|
| `float_to_int_assign` | `ro x f64 = 3.9` затем `ro i int = x` | `ok` | built -> `3` |
| `float_to_int_arg` | `sink(x)` при `sink(i int)`, `x f64 = 3.9` | `ok` | built -> `3` |
| `float_lit_neg` (уже был) | `ro n int = 1.5` | `E7301` | отвергнуто |

**Что добавляет эта пара к строке реестра.** Дверь присваивания судит ЛИТЕРАЛ и не судит
ПЕРЕМЕННУЮ того же типа: `ro n int = 1.5` отвергается, `ro i int = x` при `x f64` —
принимается и молча усекает. Значит дело не в том, что «правила про float в спеке нет»
(этот довод верен для ширин float), а в том, что дверь спрашивает УЖЕ, чем объявляет:
она умеет отвергать `int -> u8` (`E_IMPLICIT_NARROWING`, замерено 2026-09-05 тем же
заходом), но пара float/int в её вопрос не входит.

Это та же форма, что и №959, и потому строки разные: у №959 двери НЕТ вовсе, здесь дверь
есть и отвечает не на весь вопрос. Фикс №959 (`assignable` в позиции возврата) эту пару
НЕ закроет — он зовёт ровно ту дверь, которая float/int пропускает.

### Где именно (локализация 2026-09-05, чтением кода)

Пара int/float проходит ДВА слоя подряд, и каждый пропускает её НАМЕРЕННО:

1. **Слой сужения** — `ResolvedType::would_narrow_into`
   (`compiler-codegen/src/types/mod.rs`). Его докстрока говорит прямо:
   «Non-int on either side => false (permissive, D54)». `int_width_sign()` даёт
   `None` для `Float`, то есть любая пара с float выходит из этого
   слоя без вопросов. Именно этот слой ловит `int -> u8`
   (`E_IMPLICIT_NARROWING`), и именно поэтому сужение целых работает,
   а усечение float — нет.

2. **Слой категорий** — `cat_compatible_rt`, там же. Четыре рукава
   отвечают `true` одной строкой:

   ```rust
   (R::Scalar { .. }, R::Scalar { .. })
   | (R::Float  { .. }, R::Float  { .. })
   | (R::Scalar { .. }, R::Float  { .. })
   | (R::Float  { .. }, R::Scalar { .. }) => true,
   ```

   С комментарием «Permissive on int width/sign AND float width
   (assignability) — the generic-arg type-identity check is what compares those
   exactly (U.5.3)». То есть точность делегирована проверке,
   которая работает только над АРГУМЕНТАМИ ОБОБЩЁННЫХ типов
   (`distinct_mono`, U.5.3), а на простом присваивании и аргументе не
   вызывается вовсе. Та же форма, что у №959: «проверено
   где-то ещё», где это где-то судит ДРУГОЙ случай.

**Форма фикса, вытекающая из этого** (не реализовано, записано,
чтобы следующее окно не искало заново): НЕ трогать четырёх
рукавную строку `cat_compatible_rt` — она разделяется с проверкой
generic-аргументов, и там пермиссивность законна. Правильно
добавить СЛОЙ рядом с `would_narrow_into` — точно так же, как сделано
со сужением: предикат «ровно одна сторона Float» -> свой вариант
`Compat` и своя диагностика. Два условия обязательны:

* **Литерал — исключение, и это УЖЕ ЗАПИСАНО** — амендмент к D55 от 2026-09-04
  (`spec/decisions/02-types.md`, строки 1310-1325). Float-литерал в позиции
  float-типа принимается без `as`; литерал без точки адаптируется к float-
  операнду (`b + 1` при `b f64` есть `b + 1.0`, донор — Go); в позиции целого
  типа float-литерал — по-прежнему `E7301`. Никакого спек-амендмента
  фиксу больше не требуется — спека ложится перед фиксом, и здесь она
  уже легла.
* **Ширины float — ТОЖЕ отвечены, и это НЕ вопрос к владельцу.**
  Амендмент D405 от 2026-09-04, п. 1, называет этот случай дословно:
  «одинаковую ширину для чисел с плавающей точкой (`f32` с `f32`, `f64` с
  `f64` — `f32 + f64` сегодня молча расширяется до `f64`, проба `float_width`);
  целое и число с плавающей точкой не смешиваются». А амендмент D55
  закрывает и присваивание: «Оба правила касаются только литералов.
  Значения типа `int`/`f32` с float-операндом другой ширины — по-прежнему
  ошибка».
