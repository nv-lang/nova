# Проба к №942 — один пир с `EXPECT_STDOUT` глушит `test`-блоки всех остальных пиров folder-module CU

Найдено 2026-09-05 при перепроверке фикстуры к №930. Позитивная фикстура была
написана пиром в `spec_tests/conformance/`, и **проба живости провалилась**: с
заведомо ложным `assert(c.abs() == 6)` мега-CU по-прежнему дал `PASS: 899 FAIL: 0`.
Подтверждено на ЧУЖОЙ фикстуре — `append_as_slice.nv`, `assert(a == [1, 2, 3])` при
пятиэлементном `a`: `PASS: 901 FAIL: 0`.

## Механизм

`assert` не сломан: standalone-CU с ложным `assert` даёт `RUN-FAIL`, а собранная
программа паникует с `exit=101`. Folder-module тоже исполняет пиров — пока среди них
нет ни одного с маркером `EXPECT_*`. Один такой пир переводит ЯРУС всего CU
(`# (stdout/stderr)`), и дальше CU судится только по выводу той программы, а
`test`-блоки остальных пиров компилируются и не запускаются.

## Как запускать

```sh
sh docs/plans/repro/942-folder-module-tests-silenced/cmd.sh
```

Скрипт делает два прогона одного и того же ложного `assert`, различающихся ровно
одним добавленным файлом.

## Замер 2026-09-05

| прогон | состав | вердикт |
|---|---|---|
| 1 | `a_entry` + `b_peer` (в `b_peer` ложный `assert(1 == 2)`) | **`RUN-FAIL … FAIL: deliberately FALSE`** |
| 2 | те же два + `c_stdout` с `// EXPECT_STDOUT hello930` | **`PASS: 1  FAIL: 0`** |

## Масштаб на реальном корпусе

| что | сколько |
|---|---|
| `.nv` в корне `spec_tests/conformance/` | 1177 |
| из них несут `test`-блок | 1168 |
| `assert(...)` внутри них | 6207 |
| из них имеют свой `fn main()` (то есть исполнялись бы иначе) | 4 |
| пиров с `// EXPECT_STDOUT`, задающих ярус всему CU | 6 |

## Побочная находка

В прогоне 1 отказ приписан не тому файлу: `FAIL: second peer: deliberately FALSE —
a_entry.nv:4`, тогда как `assert` стоит в `b_peer.nv:3`. Имя файла и строка берутся
от entry-пира, а не от того, где стоит упавшее утверждение. Записано в строке №942
как её часть, а не отдельной строкой: чинится тем же местом.
