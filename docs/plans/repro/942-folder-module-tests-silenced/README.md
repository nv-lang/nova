# Проба к №942 — маркер `EXPECT_STDOUT` у ПИРА подменяет вердикт всего folder-module CU, и результат `test`-блоков отбрасывается вместе с ним

Найдено 2026-09-05 пробой живости позитивной фикстуры к №930 — то есть тем, что
фикстуру проверили на способность падать, а не сочли зелёную строку доказательством.
Фикстура была написана пиром в `spec_tests/conformance/`, и с заведомо ложным
`assert(c.abs() == 6)` мега-CU по-прежнему дал `PASS: 899 FAIL: 0`. Подтверждено на
ЧУЖОЙ фикстуре: `append_as_slice.nv`, `assert(a == [1, 2, 3])` при пятиэлементном `a`
— `PASS: 901 FAIL: 0`.

## Механизм — и поправка к первой записи

**Первая запись этой строки (коммит `90b9e95d0`) называла причину неверно:** «`test`-блоки
не исполняются». Они исполняются. Случай **C** ниже показывает это прямо — раннер в
тексте своего же отказа цитирует `Running 3 tests...` и построчные результаты, среди них
упавший. Подменяется не исполнение, а **вердикт**: `collect_marker_sources`
(`compiler-codegen/src/test_runner.rs`) собирает заголовочные директивы с entry-файла
**и со всех пиров того же модуля**, и `EXPECT_STDOUT`, приехавший с пира, становится
критерием для всего CU. Дальше прогон судится по совпадению подстроки, а PASS/FAIL
харнесса в вердикт не входит.

Расширение на пиров сделано намеренно и по делу — чтобы `// ENV ...`, живущий на том
пире, который объявляет тесты, доезжал до шага запуска. `EXPECT_STDOUT` едет той же
дорогой и увозит с собой вердикт.

`assert` при этом жив и не при чём: standalone-CU с ложным `assert` даёт `RUN-FAIL`,
собранная программа паникует с `exit=101`.

## Как запускать

```sh
sh docs/plans/repro/942-folder-module-tests-silenced/cmd.sh
```

Четыре прогона. Ложное `assert(1 == 2)` в `b_peer` во всех четырёх ОДНО И ТО ЖЕ;
меняется только третий файл.

## Замер 2026-09-05

| прогон | третий файл | вердикт | что доказывает |
|---|---|---|---|
| A | нет | **`RUN-FAIL`** | без маркера вердикт даёт харнесс, ложный assert пойман |
| B | `fn main`, без маркера | **`PASS: 1 FAIL: 0`** | ВТОРАЯ, независимая причина глушения |
| C | маркер, образец НЕ совпадает | **`NEG-WRONG-STDOUT`**, в тексте `Running 3 tests…` и `FAIL: second peer` | блоки ИСПОЛНЯЮТСЯ; меняется, какому вердикту верят |
| D | маркер, образец совпадает | **`PASS: 1 FAIL: 0`** | основная причина: совпавшая подстрока делает упавший assert невидимым |

## Масштаб на реальном корпусе

| что | сколько |
|---|---|
| `.nv` в корне `spec_tests/conformance/` | 1177 |
| из них несут `test`-блок | 1168 |
| `assert(...)` внутри них | 6207 |
| пиров с `// EXPECT_STDOUT`, подменяющих вердикт CU | 6 |
| из них пишут маркер запрещённой формой с двоеточием | **5** |
| файлов с `^fn main` (случай B) | **0** |

Пять из шести написаны как `// EXPECT_STDOUT: ok`. `AGENTS.md` запрещает эту форму
дословно — «No colon after the marker name — the colon would become part of the matched
substring; the corpus never uses that form», — и запрещает ровно по случившейся причине:
искомой подстрокой становится `: ok`. Шестой — `// EXPECT_STDOUT 42`
(`pos_effect_nongeneric_handler_value.nv`), и он единственный написан правильно.

**Поправка к собственному замеру:** в первой записи стояло «четыре файла имеют свой
`fn main()`». Это был греп без якоря `^`, поймавший упоминания в комментариях. На деле
их **ноль**, и случай B в conformance сегодня носителя не имеет — он записан, но не
засчитан.

## Побочная находка того же места

В прогоне A отказ приписан не тому файлу: `FAIL: second peer: deliberately FALSE —
a_entry.nv:4`, тогда как `assert` стоит в `b_peer.nv:3`. Имя файла и строка берутся от
entry-пира, а не от того, где стоит упавшее утверждение. Записано в строке №942 как её
часть, а не отдельной строкой: чинится тем же местом.
