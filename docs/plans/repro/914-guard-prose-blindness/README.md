# Проба к реестру №914 — страж читает doc-комментарий как код

## Находка

Заведено охотником 2026-09-04 (трек guards). `scripts/guards/
check-novac-no-string-keys.py`'s подстроковая проверка `"NamespaceId" in
line` ловит слово, где бы оно ни стояло на строке — включая trailing
`///`-doc-комментарий. Носитель: `novac/src/names/names.nv:80` —
`map HashMap[str, int] /// the NamespaceId key component is @ns, one
field up` — комментарий ОБЪЯСНЯЕТ инвариант, но код (`HashMap[str, int]`)
сам по себе НЕ несёт `NamespaceId`. Страж это не видел: слово в прозе
снимало предупреждение так же, как настоящий композитный ключ снял бы его
по правилу.

## Метод

Прочитан `names/names.nv` целиком, не по цитате находки. `NameTable` —
ОДНА таблица на `NamespaceId` (`NameTable.new(ns NamespaceId)` создаёт
новый инстанс на каждый namespace); вызывающий физически не может
положить имя в таблицу чужого namespace, потому что таблицы — разные
объекты. Инвариант «строковый ключ несёт NamespaceId» здесь держится
КОНСТРУКЦИЕЙ (поле `ns` соседнее с `map`), а не текстом ключа — это
РАВНОЦЕННАЯ композитному ключу форма, не более слабая. Значит правило
стража (только composite-ключ) было СЛИШКОМ УЗКИМ, а не код неверным.

**Почему чинить обе половины разом обязательно, а не по одной:** снять
только слепоту к комментарию, не расширив правило — покрасило бы гейт на
корректном коде, живущем сорок дней. Расширить только правило, не сняв
слепоту — оставило бы находку непроверенной: страж продолжал бы верить
любому комментарию со словом `NamespaceId`, даже на файле, где реального
поля нет вовсе.

## Фикс

Два рукава разом:
1. `strip_comment()` — отрезает `\s//`-хвост строки ПЕРЕД матчингом (и для
   `"Map[str"`, и для `"NamespaceId"`), так что прозу больше не путают с
   кодом.
2. `file_declares_ns_sibling()` — сканирует файл на `type X { ... }` блоки
   и внутри каждого ищет поле `ns NamespaceId`-подобной формы; если файл
   несёт такой тип, ЛЮБОЕ `Map[str`/`HashMap[str` в этом файле (включая
   конструкторы вне самого блока `type`, например `NameTable.new`'s
   `{ ns, map: HashMap[str, int].new() }`) считается защищённым тем же
   инвариантом.

## Замер ДО фикса

Прогнала исходный (реверченный) страж на реальном дереве:
`check-novac-no-string-keys ok: ...` — ЗЕЛЁНЫЙ, ложно: не находка ложной
тревоги, а находка ЛОЖНОГО ПРОПУСКА (по букве старого правила `names.nv`
обязан был краснеть — composite-ключа там нет, — но комментарий гасил
проверку). Это и есть "красное" состояние класса #914: не крах, а тихая
неправда.

## Замер ПОСЛЕ фикса

Тот же прогон на исправленном страже: `check-novac-no-string-keys ok:
файлов .nv: 101, строковых ключей вне закона: 0` — теперь ЗЕЛЁНЫЙ ПО
СУЩЕСТВУ (оба места в names.nv признаны законными новым правилом, а не
пропущены слепотой к комментарию).

## Самотест

(12) `ns` соседним полем структуры — зелёный; (13) тот же инвариант на
конструкторе вне блока `type` — зелёный. Все 12 старых случаев
перепроверены без регрессии.
