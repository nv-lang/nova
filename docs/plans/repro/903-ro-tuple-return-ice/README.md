# Проба к №903 — чекер принимает `-> ro (T, U)`, кодоген падает ICE

Заведена интегратором 2026-09-04 при починке пакета `nova-bignum`.

## Как воспроизвести (настоящее дерево)

Форма всплыла как ОДНО из трёх решений, которые компилятор сам предлагает на
`[E_READONLY_COERCE]`: «(c) объяви возврат `-> ro T`». В `nova-bignum` это
решение приводит к ICE.

```sh
# в nova-bignum, поверх ce8574c:
#   src/bigfloat/core.nv, функция round_to_precision
#   было:  -> (BigInt, int) {   ... if b <= 0 { return (BigInt(...), 0) }
#   стало: -> ro (BigInt, int) { ... if b <= 0 { return (mant_abs, 0) }
NOVA_STD_PATH=<nova>/std/src NOVA_RT_DIR=<nova>/compiler-codegen/nova_rt \
NOVA_CG_INCLUDE=<nova>/compiler-codegen \
  <nova>/nova-cli/target/release/nova.exe test src
```

Ответ:

```
[INTERNAL-PANIC] [E_CODEGEN_TYPE_UNKNOWN] Ident `bits_lost` not in var_types
  --> core.nv:280:1
  hint: the type-checker did not annotate this expression's C type
```

`bits_lost` — второй элемент пары, разбираемой из вызова
`round_to_precision(...)`. `nova check` на том же файле говорит `ok`.

## Пять кандидатов, которые НЕ сработали — и чего им всем не хватало

К двум прежним попыткам добавлены пять (`not_a_trigger_3..7`), собранные не наугад,
а по одному отличию каждая: A — ранний `return` с пользовательским типом; B — то же
без раннего `return`; C — КОНТРОЛЬ без `ro` на возврате; D — разбор пары внутри
метода; E — первый элемент пары несёт вектор. **Собираются все пятеро.**

Отрицательный результат — тоже результат, и вот чем он оказался ценен: пять промахов
подряд заставили перечитать не строку реестра, а ПОДЛИННИК. Ответ лежал в сообщении
коммита `ce8574c` в `nova-bignum` — того самого, которым владелец обошёл дефект:

> `round_by_dropping` and both `round_to_precision` functions **return their
> `mant_abs` parameter unchanged** on the "nothing to drop" fast path. Parameters
> are `ro` by default (D176) [...] (c) declare `-> ro (BigInt, int)` — the CHECKER
> accepts this and the CODEGEN then dies [...] What works is a fourth form the hint
> does not list: **return a freshly built value**, `BigInt(mant_abs.sign,
> mant_abs.limbs)`. [...] `BigInt` **is a named tuple** and has no `clone`.

Отсюда видно, чего не было НИ В ОДНОМ из семи кандидатов, и это два ингредиента:

1. **ранний `return` отдаёт САМ ПАРАМЕТР**, а не заново построенное значение. Все
   семь строили новое — то есть ни один не создавал ситуацию, ради которой `ro` на
   возврате вообще понадобился;
2. **тип — ИМЕНОВАННЫЙ КОРТЕЖ** (`export type BigInt(sign Sign, limbs []u32)`), а не
   value-запись. Коммит говорит это прямо: именно потому у `BigInt` нет `clone` и
   второе решение из подсказки не подошло.

Поэтому в каталоге появились `cand_f_returns_the_parameter.nv.txt` (оба ингредиента)
и `cand_g_control_fresh_value.nv.txt` — контроль, отличающийся РОВНО одним: ранний
путь строит свежее значение. Разбор исходов записан в самом файле G, чтобы вердикт
нельзя было подогнать задним числом: `F красный + G зелёный` пришпиливает механизм к
возврату параметра; `оба красные` означают, что строка реестра названа неверно и её
надо править; `F зелёный` — ингредиентов всё ещё мало, и тогда F с G ложатся сюда
седьмым и восьмым отрицательным результатом, БЕЗ догадки в тексте.

**На момент записи F и G НЕ ЗАПУЩЕНЫ** (машина занята соседним окном). Строка
«не запускал» стоит здесь нарочно: пять предыдущих кандидатов доказали, что
правдоподобие формы к падению отношения не имеет.
## ВОСПРОИЗВЕДЕНИЕ ЕСТЬ (2026-09-06) — и это меняет способ поиска

Девять кандидатов подряд собрались. Девять промахов — это уже не невезение, а
сигнал о МЕТОДЕ: угадывать вверх от зелёного бессмысленно, потому что каждый
промах не сужает пространство, а лишь вычёркивает одну точку из бесконечного.
Поэтому взят обратный ход — воспроизвести от заведомо КРАСНОГО, сняв обход
владельца в подлиннике, и сужать ВНИЗ. Это сработало с первого раза.

```sh
# 1. снять обход на ОДНОЙ площадке (nova-bignum, src/bigfloat/core.nv:58,60):
#      -> (BigInt, int)                                 =>  -> ro (BigInt, int)
#      return (BigInt(mant_abs.sign, mant_abs.limbs),0) =>  return (mant_abs, 0)
# 2. env рантайма ОБЯЗАТЕЛЕН: без него прогон падает не по делу, а на
#    `pathspec 'compiler-codegen/nova_rt/libuv' did not match any file(s)`
R=/d/Sources/nv-lang/nova
export NOVA_STD_PATH="$R/std" NOVA_RT_DIR="$R/compiler-codegen/nova_rt" \
       NOVA_CG_INCLUDE="$R/compiler-codegen"
cd /d/Sources/nv-lang/nova-bignum
$R/nova-cli/target/release/nova.exe test src --filter bigfloat
```

Выдача, дословно:

```
CODEGEN-FAIL   src/bigfloat/core  # [INTERNAL-PANIC] [E_CODEGEN_TYPE_UNKNOWN]
    Ident `bits_lost` not in var_types / not a sum-variant — unknown type
PASS: 0  FAIL: 1
```

Файл после пробы восстановлен побайтово из копии, `git status` пакета чист.

### Что девять промахов уже ВЫЧЕРКНУЛИ

Спусковой крючок — НЕ любое из этого, каждое проверено сборкой по отдельности и
в сочетаниях: ранний `return`; `ro` на возврате кортежа; пользовательский тип
первым элементом; разбор пары внутри метода; поле-вектор в элементе;
**возврат САМОГО ПАРАМЕТРА** (кандидат F); **именованный кортеж** вместо
value-записи (F); **именованный кортеж С полем-вектором** (кандидат H, то есть
буквальная форма `BigInt(sign Sign, limbs []u32)`).

Последние два были главными подозреваемыми — их называет сам коммит-обход
`ce8574c` («return their `mant_abs` parameter unchanged», «`BigInt` is a named
tuple and has no `clone`»). Оба зелёные. Значит подозрение, взятое из
формулировки подлинника, тоже оказалось ложным, и это стоит записать: цитата
объясняет, почему автор поступил так, а не что ломает компилятор.

### Куда смотреть дальше, и почему теперь это механика

Осталось то, чего ни один изолированный файл не воспроизводит: размер и форма
ЕДИНИЦЫ КОМПИЛЯЦИИ. Подлинник — папка-модуль с шестью площадками разбора
(`core.nv:371,478,564,583,613` + сигнатура на 58), длинное тело с ВТОРЫМ
`return` в ветке `if rbl > prec`, вызовы методов на параметре, enum-параметры.
Имея красное состояние, дальше идёт не угадывание, а деление пополам: резать
подлинник, пока не перестанет падать.

**Догадку о причине сюда по-прежнему не пишу.** Девять раз правдоподобие
оказалось не при чём.
## Чего проба НЕ содержит, и это названо нарочно

**Минимальной формы у меня нет.** Две попытки свести — в этом же каталоге,
`not_a_trigger_1.nv.txt` и `not_a_trigger_2.nv.txt`, — обе СОБИРАЮТСЯ. Вторая повторяет
всё, чем настоящий случай отличается от первой: поле-вектор в кортеже, разбор
внутри другой функции, арифметика над целым из пары.

Это отрицательный результат, и он положен в дерево нарочно: следующий читатель
иначе начнёт ровно с этих двух форм. Что-то в настоящем случае ещё —
дженерики, `@`-поля, глубина модуля или размер единицы компиляции, — и это «что
именно» пока не измерено. Догадку сюда не пишу.

## Почему это важнее, чем выглядит

Форму `-> ro T` СОВЕТУЕТ сам компилятор в тексте `[E_READONLY_COERCE]`, третьим
из трёх решений. То есть диагностика ведёт пользователя в ICE — и ведёт именно
тогда, когда первые два решения не подходят, как и вышло в `nova-bignum`
(`(a)` меняет контракт, `(b)` требует `clone`, которого у именованного кортежа
нет).
