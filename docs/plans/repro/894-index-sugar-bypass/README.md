# Проба к №894 — сахар `[]` обходит проверку типа ключа

Заведена интегратором 2026-09-04 при вынесении вердикта «блокирует тег».
Строка №894 ссылалась на пробы `examples/_pidx1..3/`, **которых в дереве нет** —
ни одного каталога по этому шаблону. Правило плана 278 (Ф.5/Ф.6) на этот счёт
прямое: находка без файла-пробы в дереве не считается доказанной. Поэтому проба
воспроизведена заново и положена сюда; строка на неё теперь и ссылается.

И `examples/` в любом случае был бы неверным домом: это поставляемый корпус, а
не место для улик.

## Как запускать

```sh
D=docs/plans/repro/894-index-sugar-bypass
cp $D/sugar.nv.txt    /tmp/p894_sugar.nv
cp $D/explicit.nv.txt /tmp/p894_explicit.nv
nova-cli/target/release/nova.exe check /tmp/p894_sugar.nv
nova-cli/target/release/nova.exe check /tmp/p894_explicit.nv
```

**Почему через копию, а не прямо по `.nv.txt`, как было записано здесь утром
(поправка 2026-09-04, вечер):** с этого дня CLI отказывает нес-`.nv` путям —
`error: not a Nova source: …sugar.nv.txt`. Проверку завёл я сам тем же днём
(`require_nova_source`, `nova-cli/src/main.rs`), и она сломала команду
воспроизведения в этом файле — обнаружено запуском записанной команды, а не
чтением. Проверка правильная и остаётся: `.nv.txt` — договорённость
репозитория, а не свойство языка, и учить поставляемый инструмент про наши
каталоги улик значило бы протащить внутреннюю конвенцию в чужие руки.
Значит платит команда, а не CLI, — и платит одной строкой `cp`.

**Суффикс тут остаётся `.nv.txt`, и это не противоречит п. 2а правила №695.**
Исключение 2а — про пробы, которые ЗАПУСКАЮТ по записанной команде, и на
первый взгляд это ровно наш случай. Но страж `check-repro-evidence-suffix`
разделяет каталоги по признаку: `NNN-*` — улика реестра (обязана быть
`.nv.txt`, её видит ссылка из строки), `pNNN-*` — рабочая проба окна (может
быть `.nv`). Этот каталог — `894-*`, то есть реестровая улика. Хочешь
запускать без `cp` — заводи пробу в своём `pNNN-*`, а сюда клади улику.
Единственный способ, которым эти два правила МОГЛИ бы разойтись, —
переименование этого каталога, и тогда сдвигать надо базу стража со
строкой-причиной, а не суффикс молча.

## Что замерено 2026-09-04 (интегратор, один бинарь)

| проба | ответ |
|---|---|
| `sugar.nv.txt` — `t[k]`, ключ `TyId`, параметр `FnRow` | **`ok`, rc=0** |
| `explicit.nv.txt` — `t.index(k)`, тот же ключ | **`[E_NO_MATCHING_OVERLOAD]`** |

Контроль — это половина, которая делает находку дефектом, а не отсутствующей
возможностью: компилятор проверку УМЕЕТ и делает её на явном вызове, а на сахаре
не делает. Одна операция, две двери, противоположные ответы.

Код ошибки у меня вышел `E_NO_MATCHING_OVERLOAD`, а строка называет `E7301` —
расхождение записано в самой строке и не сглажено: по существу оба суть отказ,
но чинящему важно знать, что дверь отказа может быть не та, которую он ждёт.

## Поправка 2026-09-04: суффикс

Файлы лежали как `.nv`, и это нарушение правила №695 (шапка
`docs/plans/repro/README.md`, п. 2): улику держат под `.nv.txt`, потому что по
`**/*.nv` ходят восемь стражей, а улика по природе КРАСНАЯ — иначе она не улика.
Заметил не я, а окно-исследователь, сверяя свои шесть каталогов с моим: у него
правило соблюдено везде. Переименовано, ссылки в этом файле поправлены; строка
реестра №894 ссылается на КАТАЛОГ и правки не потребовала.

Стоит назвать, почему я его нарушил: каталог заводился в спешке, ради вердикта
по чужой строке, и шапку соседнего README я не открыл. Ровно та же причина, по
которой исходные пробы этой находки вообще исчезли из дерева.
