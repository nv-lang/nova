# №1083 — `Result[<псевдоним указателя>, <сумма>]` инстанцируется как `Result[int, str]`

Найдено окном 283 (2026-09-13) при написании эффект-семейства `Db` в
`nova-duckdb`. **Сетка пересобрана интегратором НЕЗАВИСИМО** и сошлась клетка в
клетку — чужой замер не берётся на слово, даже точный.

## Команда

Из корня репозитория, на каждый файл (переименовав в `.nv`):

```sh
nova-cli/target/release/nova check <проба>.nv
nova-cli/target/release/nova build <проба>.nv -o /tmp/probe.exe
```

## Таблица: ось — ПАРА, а не любая из половин

| проба | `Result[Ok, Err]` | `check` | `build` |
|---|---|---|---|
| `a_alias_str` | `Result[CResultHandle, str]` — псевдоним + обычная строка | ✅ | ✅ |
| `d_int_sum` | `Result[int, DuckError]` — обычный тип + сумма | ✅ | ✅ |
| `b_alias_sum` | `Result[CResultHandle, DuckError]` — **обе половины сразу** | ✅ | ❌ |
| `c_newtype_sum` | `Result[ResultRef, DuckError]`, newtype-**запись** вокруг той же ручки | ✅ | ✅ |

Ни одна половина не виновата поодиночке. Это показала сетка, и рассуждение бы не
показало: псевдоним живёт с обычной ошибкой, сумма живёт с обычным типом.

## Улика в сгенерированном C, дословно

```
nova_make_NovaRes_nova_int_nova_str_Err
error: incompatible type 'nova_str'
error: no member named 'payload'
error: no member named 'tag'
```

Конструктор назван по `Result[int, str]` при **объявленном**
`Result[CResultHandle, DuckError]`: мономорфизатор свернул псевдоним `*()` к
`nova_int`, а сумму, все варианты которой несут `str`, — к `nova_str`.

## Что ОТВЕРГНУТО по дороге

**«Виновата граница эффекта»** — нет. Носитель `b` есть свободная функция в семь
строк без единого эффекта. Окно 283 потратило на эту гипотезу две пробы и назвало
это в своём отчёте; повторять её не нужно.

## Обход лучше обходимого

Ручки в эффекте делаются newtype-**записями**, а не `*()`-псевдонимами (проба `c`
зелена). Это ровно то, чего требует **D456 п.5** — «дескриптор — именованный тип,
а не сырой указатель». Псевдоним удовлетворял правилу ПО БУКВЕ, сохраняя
представление, и мономорфизатор увидел его насквозь. Так что правка чинит и
сборку, и форму. Проверено в обе стороны: вернуть псевдоним — суита краснеет.

## Подкласс, которого нет в плане 196

Канал 196 говорит: кодоген ВЫВОДИТ там, где обязан ЧИТАТЬ. Здесь хуже: он выводит
**дважды** — имя конструктора из свёрнутых типов, типы аргументов из объявленных, —
и два вывода расходятся между собой. Обычный случай даёт один неверный ответ; этот
даёт два, не согласованных ни с чем, поэтому и диагностика приходит от clang, а не
от Nova.

## Про «три случая за сутки»

Окно 283 предположило общую ось: «`check` и эмиттер расходятся там, где тип имеет
ПРЕДСТАВЛЕНИЕ, отличное от объявления». **Это верно для ОДНОГО из трёх.** У №1077
ломается имя C (манглинг), у №1082 — резолв поля, здесь — сворачивание
представления. Общее у всех трёх уже названо планом 196 и ШИРЕ их гипотезы:
эмиттер вычисляет сам вместо того, чтобы прочитать решение чекера. Новой строки в
конвенциях не требуется — требуется, чтобы каждая из трёх строк называла канал
местом починки.
