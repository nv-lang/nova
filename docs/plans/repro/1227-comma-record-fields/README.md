# Проба к реестру №1227 — запятая между полями однострочной записи

## Находка

Найдено помощником 2026-09-21, третья строка таблицы 274.5 §5в
(`examples/tour/types.nv:5`). `novac/src/parse/type_decl.nv`'s doc-
комментарий над `@type_decl()` (датирован разбивкой файла 2026-09-03,
задолго до находки) прямо признавал узость: «fields are newline-
separated pairs of idents, no commas» — цикл чтения полей записи ждал
только `Ident`/mode-слово, запятую не читал вовсе.

## Метод

Поле-читающий цикл брейс-формы (`type_decl.nv`, условие `while @peek()
== TokenKind.Ident || @at_mode_word()`) не имел ветки на `Comma`.
Скобочная форма (`type Pair(x int, y int)`, D215) уже читает запятую
между полями как trivia (`@push_if(kids, TokenKind.Comma)`), и все
потребители `Field`-детей (`sem/collect.nv:431`, `sem/sem.nv:492`,
`sem/slots_decl.nv:75,156,187`) фильтруют по ВИДУ узла
(`kind_of() == NodeKind.Field`), не по позиции — значит запятая-лист
между полями брейс-формы ничего не ломает у существующих потребителей,
ровно как и у скобочной формы уже сегодня.

## Фикс

Тот же `@push_if(kids, TokenKind.Comma)` добавлен в брейс-форму сразу
после каждого `Field`-узла — дословно тот же приём, что уже стоит в
скобочной форме десятком строк ниже. Устаревший doc-комментарий
поправлен.

`type_decl.nv` (`git checkout --`, пересборка), `novac.exe check` на
`type Point { x f64, y f64 } / fn main...` — безымянный
`E_NOVAC_SUBSET` («did not parse this»). Контроль (та же запись,
построчно, без запятых) остаётся чистой (уже была чистой до фикса —
не тестировалась заново, поведение не менялось).

## Замер ПОСЛЕ фикса

`git apply` тем же патчем обратно, пересборка:

```
novac.exe check p1227.nv       (однострочная запись с запятой) -> exit=0
novac.exe check p1227_ctrl.nv  (построчная запись, без запятых) -> exit=0
```

Обе формы компилируются одним и тем же `@type_decl()`, как требовала
приёмка строки.
