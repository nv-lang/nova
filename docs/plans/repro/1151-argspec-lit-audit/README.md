# Проба к реестру №1151 — второй носитель того же класса (`ArgSpec.lit`)

## Контекст

Строка №1151 несла явную оговорку: фикс носителя (`novac/src/sem/collect.nv:140`,
коммит `f6fdf665a`) не считается приёмкой — `nova check` судит ПОФАЙЛОВО и слеп
к конструкторам, чей тип объявлен в ДРУГОМ файле (класс E2-b2), значит «носитель
один» было верно только «этой меркой видно один», не «их один».

## Метод

Аудит (агент sonnet, фон, без правок) прочитал все 45 совпадений
`type <Name> value {` в `novac/src` (41 реальная декларация записи — 4 были
упоминаниями в комментариях/строковых фикстурах парсера), нашёл все места
конструирования литералом каждого типа по всему дереву (включая `*_test.nv`,
~109 мест) и сверил с полным списком объявленных полей. Spread-синтаксис
(`...base`) в проекте существует, но не встретился НИ В ОДНОМ из проверенных
мест — так что гипотеза «пропуск мог быть законным через spread» ни к одной
находке не относится.

## Находка

`ArgSpec` (`novac/src/sem/binding.nv:137`, поля `type_id, cls, name, lit`) —
два безымянных литерала в `novac/src/sem/binding_test.nv:34,37`
(`pos_arg`/`named_arg`) присваивали только `type_id, cls, name` и опускали
`lit LitArg`. Все прочие семь мест конструирования `ArgSpec` по дереву
(`check/exprs.nv`, `check/methods.nv`, `check/operators.nv`, `check/type_of.nv`,
`check/typing.nv`) поле `lit` пишут явно, обычно значением `LitArg.NotLit`.
Тот же самый `TypeDef` (носитель №1151) при этом проверен ЗАНОВО в 10 местах
конструирования по всему дереву — регрессии нет, все 8 полей на месте
(включая явную ссылку на №1151 в комментарии `collect.nv:160`).

Остальные 39 из 41 проверенных типа-записи — чисты: во всех найденных
литералах присвоены все объявленные поля.

## Замер ДО фикса

`pos_arg`/`named_arg` возвращали `ArgSpec` с полем `lit` не инициализированным
— тот же класс, что у №1151 («поле записи остаётся неинициализированным, а
компилятор молчит», записи в Nova не имеют дефолтов для полей). `nova check
novac/src` не ловит это ни до, ни после (файл типа лежит в другом модуле,
чем конструктор, — E2-b2), поэтому единственный измеримый признак «до» —
чтение деклараций (сделано аудитом и перепроверено вручную).

## Фикс

`novac/src/sem/binding_test.nv:34,37` — добавлено `lit: LitArg.NotLit` в оба
литерала, той же формой, что используют все семь прочих мест конструирования
`ArgSpec` по дереву.

## Замер ПОСЛЕ фикса

```
nova-cli/target/release/nova.exe check novac/src
===== SUMMARY =====
PASS: 16  FAIL: 0  WARN: 471
```
(без изменений относительно «до» — ожидаемо, мерка слепа к этому классу).

```
nova-cli/target/release/nova.exe test novac/src/sem
PASS           novac/src/sem/binding
===== SUMMARY =====
PASS: 1  FAIL: 0
```
Тест, упражняющий `pos_arg`/`named_arg` в 11 местах сценариев связывания
аргументов, зелёный и после фикса — `lit` в этих тестах не читается сравнением
(тестируется P14, классы аргументов, а не D227, литеральность), так что
поведение теста не менялось; проверка здесь — что литерал теперь ТИПОБЕЗОПАСНО
полон, а не что тест это заметил бы сам.

## Итог по оговорке №1151

Приёмка оговорки закрыта: аудит по всему `novac/src` дал РОВНО ОДИН
дополнительный носитель того же класса (этот), он тот же волной исправлен,
41 тип-запись и ~109 мест конструирования проверены, находок больше нет.
