# Попытка пересобрать носителя строки №791 (К1, блокирует тег)

**Главное, и это отрицательный результат:** носитель по трём условиям строки
**НЕ пересобирается**. Две формы, обе построены буквально по записанным
условиям, обе **ВЫХОДЯТ** за доли секунды. Значит список условий в строке №791,
как он записан, **не достаточен** — в нём не хватает детали, которую окно p790
знало по своему файлу, а файл не сохранился.

## Замер 2026-08-31 (интегратор)

Команды целиком, из корня репозитория:

```sh
nova-cli/target/release/nova.exe build docs/plans/repro/p791/hang.nv  -o /tmp/p791_hang.exe
timeout 20 /tmp/p791_hang.exe;  echo "exit=$?"     # -> after-supervised, exit=0, 0s

nova-cli/target/release/nova.exe build docs/plans/repro/p791/hang2.nv -o /tmp/p791_hang2.exe
timeout 20 /tmp/p791_hang2.exe; echo "exit=$?"     # -> after-supervised, exit=0, 0s
```

`exit=124` означал бы повис (убит по таймауту). Его нет ни разу.

```sh
nova-cli/target/release/nova.exe build docs/plans/repro/p791/hang3.nv -o /tmp/p791_hang3.exe
timeout 20 /tmp/p791_hang3.exe; echo "exit=$?"     # -> after-supervised, exit=0, 3 прогона из 3
```

| файл | что в нём есть | замер |
|---|---|---|
| [hang.nv](hang.nv) | условия (2) и (3); accept УЖЕ вернулся к моменту отмены | **выходит**, exit=0 |
| [hang2.nv](hang2.nv) | (1) фибра A запаркована на следующем accept, (2) отмена из spawn-ребёнка под вложенным supervised, (3) запись в сокет из ТОЙ ЖЕ фибры | **выходит**, exit=0 |
| [hang3.nv](hang3.nv) | то же, но пишет и отменяет **ОБРАБОТЧИК**, владеющий **ПРИНЯТЫМ** сокетом (`spawn consume s`) — проверка гипотезы (а) | **выходит**, exit=0, **3/3** |

**Гипотеза (а) СНЯТА замером:** «писать должен обработчик в принятый сокет» —
недостаточно; отмена из обработчика гасит всё чисто и процесс выходит.
Остаются (б) и (в).

## Что это значит, и чего НЕ значит

**НЕ значит, что дефекта нет.** Строка №791 опирается на два независимых
воспроизведения в разные дни на разных сборках (окно p790 матрицей из девяти
зондов; интегратор — витриной `09-graceful` с эндпоинтом `GET /shutdown`).
Отрицательный результат моей реконструкции — про РЕКОНСТРУКЦИЮ, а не про дефект.

**Значит вот что:** формулировка «три необходимых условия» в строке читается как
достаточная, а она не достаточна. Следующее окно, взявшее строку и построившее
форму по её тексту, потратит то же время, что потратил я, и придёт к тому же
`exit=0` — и может ошибочно счесть дефект несуществующим. Поэтому результат
записан здесь и в самой строке.

**Недостающая деталь — одна из этих, и она не угадывается:**

* чья именно фибра делает uv-запись: в витрине это ОБРАБОТЧИК соединения,
  пишущий в ПРИНЯТЫЙ (серверный) сокет, а в `hang2.nv` — клиентская фибра,
  пишущая в свой клиентский сокет. «Сокет соединения» в строке допускает оба
  чтения;
* висит ли требование, чтобы отменяющая фибра была потомком ТОГО ЖЕ скоупа,
  что и accept-цикл (в `hang2.nv` они сиблинги);
* участвует ли `consume`-скоуп с авто-`@cleanup` (D432): его cancel-щит
  (`nv_consume_enter_shield`, D188 R3) держит `cancel_mask_count > 0` на ВСЁ
  тело — это отдельно задокументировано в
  `spec_tests/conformance/standalone/m2217_15_cancel_busyloop_scope_mismatch.nv`
  и в моих формах присутствует не так, как в витрине.

## Урок, который дороже самих проб

Носитель `p791_helper_cancel.nv`, названный в строке, **не существует в дереве
и никогда не коммитился ни в одну ветку** (проверено `git log --all
--diff-filter=A -- '*p791*'` — пусто; в worktree `nova-p790` его тоже нет,
незакоммиченного там ноль). Это ровно тот случай, против которого написано
правило плана 278 Ф.5/Ф.6: **отчёт без пробы В ДЕРЕВЕ не двигает часы долга.**
Строка сохранила ВЫВОД («три условия»), но потеряла УЛИКУ, а вывод без улики
не воспроизводится — что и показано здесь двумя прогонами.

## Инструмент для следующего захода

`NOVA_DIAG_M456=1` — готовый выключатель в `compiler-codegen/nova_rt/fibers.h:3748`.
Печатает `[m456] pending_driver_jobs wait ENTER` и `STILL WAITING … iters=N` из
спин-ожидания на хвосте `supervised_run_impl` (`fibers.h:3755`). Если при повисе
он печатает `STILL WAITING` — виснет именно там. Но строка говорит, что порт
закрывается и `serve()` ВОЗВРАЩАЕТСЯ, а живёт процесс — тогда спин-ожидание уже
пройдено, и вероятнее жизнь процесса после возврата: драйверный поток,
`driver.c:192` (`while (uv_loop_alive(&_nova_driver.loop))`). Поэтому проба с
`NOVA_DIAG_M456` — на ИСКЛЮЧЕНИЕ, и отрицательный её результат тоже информативен.
Два места декремента счётчика — `driver.c:362` и `driver.c:399`.
