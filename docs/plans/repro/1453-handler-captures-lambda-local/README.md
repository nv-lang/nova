# №1453 — литерал обработчика (и замыкание) внутри лямбды не видит локал этой лямбды

Найдено окном nova-63 на `claude-limits` `serve_mode` 2026-10-01: nova main не собрал
его, clang `use of undeclared identifier 'got'`. Пробы `f1`/`f2` перенесены из
`claude-limits/probes/handler-captures-lambda-local/` (там же `FINDING.md`).

**Как запускать:** переименовать `nova.toml.txt` → `nova.toml`, `<проба>.nv.txt` →
`<проба>.nv`, затем `nova build <проба>.nv -o p.exe && ./p.exe`. Вне репозитория
задать `NOVA_STD_PATH`, `NOVA_CG_INCLUDE`, `NOVA_RT_DIR` на дерево компилятора. Для
пробы выключателем — `NOVA_CACHE=0`: кэш сборки ключуется исходниками и бинарём,
но НЕ окружением, и иначе отдаёт прежний `.c`.

## Корень

№1441 решает для каждого чтения, связано ли имя там, где оно стоит
(`free_idents::bound_read_ids`), и связанное чтение минует коробку захвата
(`var_boxed`). Две двери:

1. **Множество накапливалось.** `enter_capture_body` расширял его, а не заменял:
   вложенное тело (оп литерала, замыкание) наследовало чтения объемлющего, где
   локал лямбды связан. В опе `t` — захват `_c->t`, но чтение числилось
   «связанным» и эмитилось голым `t` — в C-функции опа такого имени нет.
2. **Коробка не сверялась.** Свой локал тела, взятый в коробку `_box_x`, когда его
   захватило вложенное замыкание, читался мимо коробки. На main это пряталось за
   дверью 1 (сборка падала раньше); с закрытой дверью 1 и открытой 2 выключатель
   дал тихо неверные числа: `b 0` вместо `b 2`, `c 1510` вместо `1515`,
   `d 3110` вместо `3618`, `e 1` вместо `11`, `f 10705` вместо `10706`.

Фикс: у каждого тела захвата своё множество (замена, не расширение) и снимок
коробок его СОБСТВЕННЫХ захватов на входе; связанное чтение минует коробку,
только если это та самая коробка захвата — то есть локал затеняет захват (случай
№1441).

## Не этот класс

`n1_spawn_in_lambda` красный и до №1441 (integ 8900d9a61): тело `spawn` внутри
лямбды ссылается на `_nova_spawn_0`, которого в C нет. Отдельный дефект, номер у
интегратора.
