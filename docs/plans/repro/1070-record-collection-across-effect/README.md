# №1070 — коллекция ЗАПИСЕЙ не проходит через границу эффекта

Замер 2026-09-12, окно интегратора. Найдено при закрытии открытого вопроса плана
286 («переживает ли `Result[[]Row, DbError]` границу эффекта») — вопрос был
записан как решаемый пробой, а не словом, и проба ответила.

Бинарь: `nova-cli/target/release/nova.exe` (сборка 2026-09-09 21:30). Команда на
каждую пробу из корня репозитория:

```sh
./nova-cli/target/release/nova build <файл>.nv -o /tmp/probe.exe
```

(файлы лежат с расширением `.nv.txt`, чтобы их не подхватывал ни один прогон.)

## Таблица: ось — ЭЛЕМЕНТ коллекции, а не коллекция и не `Result`

| проба | что возвращает операция эффекта | исход |
|---|---|---|
| `a_vec_int.nv.txt` | `[]int` | ✅ `built`, печатает `n=3 second=2` |
| `b_single_record.nv.txt` | `Flat` и `Option[Flat]` | ✅ `built`, печатает `one=a@b.c` / `next=c@d.e` |
| `c_vec_record_flat.nv.txt` | `[]Flat` (поля — только скаляры) | ❌ `codegen error` |
| `d_vec_record_result.nv.txt` | `Result[[]Row, DbErr]` | ❌ `codegen error` |
| `e_vec_sum.nv.txt` | `[]<сумма с полезной нагрузкой>` | ✅ `built` (7.09s), ИСПОЛНЕНА: `in=3` `out=a@b.c` |
| `f_record_holding_vec_record.nv.txt` | `Row { schema []ColumnDef, vals []Val }` и `Option[Row]` | ❌ `codegen error` (та же строка) |
| `g_schema_as_vec_sum.nv.txt` | `[]Col` и `Option[[]Val]`, где колонка — СУММА | ✅ `built` (6.54s), ИСПОЛНЕНА: `cols=2 first=id` `val=a@b.c` |

**Пробы e/f/g прогнаны 2026-09-13 в 00:52 мест.**, когда слот освободился. Ожидание по
каждой было записано В ФАЙЛЕ ПРОБЫ ДО прогона (`e` зелёное, `f` красное, `g` зелёное) —
именно затем, чтобы исход нельзя было подогнать задним числом; все три совпали.
Зелёные СУДИМЫ ИСПОЛНЕНИЕМ, а не словом `built`: обе запущены, обе напечатали
ожидаемое. `built` без запуска доказывает компиляцию, а предмет здесь — проходит ли
ЗНАЧЕНИЕ через vtable целым.

Вердикт красных клеток, дословно:

```

`copy_n_nonoverlapping` — appears in param `src` (#0), param `dst` (#1);
use turbofish: `copy_n_nonoverlapping[T](...)`
```

## Что проба ОТВЕРГЛА по дороге

Каждое из этих объяснений проверено и оказалось ложным:

* **«виноват `Result`»** — нет: `[]Flat` без `Result` падает так же (`c`);
* **«виноват литерал массива внутри тела обработчика»** — нет: массив,
  построенный ОТДЕЛЬНОЙ функцией и только возвращённый, падает так же;
* **«виноваты вложенные коллекции в полях записи»** — нет: `Flat` с полями
  `int` и `str` падает так же (`c`);
* **«коллекции вообще не проходят границу»** — нет: `[]int` проходит (`a`).

Остаётся ровно одно: **элемент-ЗАПИСЬ в коллекции, возвращаемой операцией
эффекта.**

## Почему это дорого

1. **Целевая форма плана 273 непостроима.** `docs/plans/273-…:291-301` объявляет
   `query(q Sql) -> Result[[]DbRow, DbError]` — ровно проба `d`.
2. **Это третья клетка класса №47**, закрытого 2026-07-24 «на уровне носителя»:
   тот же корень (вывод тип-аргумента считает `void*` нерезолвленным, не отличая
   «непрозрачен по замыслу» от «непрозрачен, потому что ещё обобщён»), та же
   диагностика. Вторая клетка — №1069 (статик по тип-параметру в цикле).
3. **ЗДЕСЬ СТОЯЛО ОБЕЩАНИЕ ВЫХОДА, И ОНО СНЯТО КАК НЕДОКАЗАННОЕ** (правка
   2026-09-13). Текст гласил: одиночная запись и `Option[Record]` границу проходят
   (`b`), значит курсорная форма `@next() -> Option[Row]` собирается уже сегодня.
   **Проба `b` мерила не тот предмет.** Её `Flat` — запись со СКАЛЯРНЫМИ полями,
   а несущий тип 286 — `Row { schema []ColumnDef, vals []SqlValue }`, то есть запись,
   СОДЕРЖАЩАЯ коллекцию записей. Наследует ли она отказ своего поля — это
   отдельный вопрос, и отвечает на него проба `f`, а не `b`. **ПРОБА `f` ОТВЕТИЛА:
   КРАСНО.** Запись НАСЛЕДУЕТ отказ своего поля — той же строкой кодогена. То есть
   курсорная форма `@next() -> Option[Row]` НЕ собирается сегодня, вопреки тому, что
   здесь было написано, и у плана 286 не остаётся ни списочной формы, ни курсорной,
   пока `Row` несёт коллекцию записей.
4. **Обход «непрозрачная ручка + фасад над границей» закрывает РЕСУРСЫ и НЕ
   закрывает ДАННЫЕ** (предложен окном `nova-9c` 2026-09-13, проверен чтением спеки).
   `Conn`/`Rows`/`Stmt`/`Tx` в 286 и так newtype-хендлы, и у фасада над границей есть
   прямой прецедент в самом D456 (`Db.in_transaction[T, E]` был УБРАН, а тело
   пользователя вынесено СНАРУЖИ границы). Но вытащить ЗНАЧЕНИЯ из ручки
   можно только обходом по индексу, а его D456 запрещает дословно («Чего на границе
   эффекта быть не должно», п. 3: «Три операции обязаны договориться между собой:
   мок отдаст пять ключей и четыре значения — и не покраснеет НИЧЕГО. Правильно —
   одна операция, возвращающая коллекцию»). Поэтому кандидат остаётся один —
   проба `g`: колонка как СУММА, не как запись.
5. **КАНДИДАТ РАБОТАЕТ — проба `g` зелёная и исполнена.** `describe() -> []Col`, где
   `Col` — сумма, несущая имя и nullable вариантом, плюс `next() -> Option[[]Val]`,
   собирается и печатает `cols=2 first=id` / `val=a@b.c`. Это ОДНА операция,
   возвращающая коллекцию (D456 п. 3 соблюдён), без обхода по индексу и без
   счётчиков рядом с данными (п. 6). **Значит у плана 286 форма границы ЕСТЬ, и цена
   её названа честно: на границе колонка — сумма, а привычную запись `ColumnDef`
   собирает фасад НАД эффектом.** Это не обход дефекта, а следствие того, что
   элемент-запись в коллекции через vtable сегодня не проходит; когда №1070 починят,
   фасад можно будет упростить, а граница останется законной в обоих случаях.
