# Проба к реестру №1251 -- литерал в образце `match` не судит никто

## Находка

НАЙДЕНО ОХОТНИКОМ 2026-09-21 (novac, клетка `check`×К4), отчёт
`docs/dev/hunts/novac/2026-09-21-check-k4.md` (Н2), проба
`p6-match-literal-unjudged`. Родня #1250 (Н1) -- та же пара дверей.

## Минимальное репро

`p1-match-too-wide.nv.txt`:
```nova
fn f(x int) -> int {
    match x {
        99999999999999999999999 => 1
        _ => 2
    }
}
```

`novac check` -- чист (rc=0). Оракул отвергает файл («number too large to
fit in target type»). `novac emit` пишет
`_novac_l1 == 99999999999999999999999LL`, и clang на эту строку отвечает
«integer literal is too large to be represented in any integer type».

## Замер ДО фикса

`rc=0` у `check`; `emit` пишет `99999999999999999999999LL` дословно (проверено
грепом по сгенерированному C).

## Замер ПОСЛЕ фикса

`rc=1`, `E_NOVAC_SUBSET`, "this integer literal does not fit any integer
type novac knows..." -- та же дверь и тот же текст, что #1250 уже подал
магнитудной двери, просто позиция теперь СПРОШЕНА.

## Корень

Величина литерала судится двумя дверями (`literal_rules.nv`): магнитудная
(`int_text_fits`, зовётся из обхода узла `Lit`) и рядная
(`int_text_fits_row`, зовётся из `@lit_fits_or_refuse` с позиции
call-аргумента/`return`). `Pattern` -- НЕ `Lit`-узел (парсер оборачивает
литерал образца в `NodeKind.Pattern`, не в `NodeKind.Lit`, `parse/expr.nv:369`),
так что обход `Lit` его не видит вовсе; а рядная дверь с позиции образца
никогда не звалась. Обе двери Н1 сюда не дотягиваются -- и получается
ровно то, ради чего магнитудная дверь заводилась (#810): «the emitter
prints its text with an `LL` suffix and C wraps it», только теперь падение
приходит не тихой порчей, а отказом СИШНОГО компилятора.

## Фикс, и почему НЕ рядная дверь

`match_arms.nv`, `@bind_arm_pattern`: когда голова образца -- `IntLit`,
дверь зовёт `int_text_fits` (МАГНИТУДНУЮ, ту же, что #1250 подчинил `u64`)
и отказывает тем же `INT_TOO_LARGE_MSG`, если литерал не влезает ни в
какой ряд вообще.

**Намеренно НЕ рядная дверь (`@lit_fits_or_refuse`).** Соседняя форма,
измеренная охотником и НЕ вынесенная отдельной находкой: `match x { 300
=> .. }` при `x u8` компилируется чисто ОБОИМИ компиляторами (оракул тоже
принимает, хоть сравнение и не бывает истинным) -- трек `oracle` по этой
форме закрыт, оракул сам не применяет D227 п.3 (рядную границу) на
позиции образца. Позвать здесь рядную дверь означало бы НОВОЕ расхождение
в обратную сторону (novac строже оракула), не фикс. Контроль
`ctrl-u8-300-match.nv.txt` подтверждает: с фиксом эта форма остаётся
чистой у novac.

## Контроль отсутствия регрессии

- `novac/src/check/check_test.nv`, `novac/src/parse/parse_test.nv` --
  оба PASS (прогнаны напрямую по пути файла).
- `check-novac-grammar-kinds`, `check-novac-no-default-branch`,
  `check-novac-file-size` -- зелёные.
- `spec_tests/conformance/d49_statement_separator_newlines.nv` -- 5
  диагностик, без изменений.
- Тест-свидетель -- `check_test.nv`, "literal magnitude: a match
  pattern's own literal is judged too (registry #1251)" -- несёт ТРИ
  формы: 23-цифровой литерал (отказан), `300` при `u8` (принят, по
  оракулу), обычный маленький литерал (принят).
- Оба пути проверены прямыми пробами: откат `match_arms.nv` (двери
  величины из #1250 остаются в дереве) -> 23-цифровая форма чиста
  (rc=0), эмиссия пишет `99999999999999999999999LL` дословно (грепом по
  сгенерированному C) -> фикс восстановлен -> та же форма честно
  отказана, `u8=300` и малый литерал не сдвинулись.
