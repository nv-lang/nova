# Пробы к №971 — НЕОБЪЯВЛЕННОЕ имя типа принимается везде и молча выключает проверку

Найдено интегратором 2026-09-05 попутно, при уточнении остатка №959: я мерил, судится ли
непримитивный возврат, взял для пробы `type Meters value { ro m float }` — и получил не тот
отказ, которого ждал. `float` не тип Nova.

## Что происходит

`nova check` НИКОГДА не проверяет, что имя типа в аннотации было ОБЪЯВЛЕНО. Причина
прочитана в коде, а не выведена из симптома: `compiler-codegen/src/types/mod.rs`, ветка
разбора `TypeRef::Named` — после `f32`/`f64`/`str`/`bool`/`never` идёт

```rust
Some(n) => R::Named { name: n.to_string(), module: …, args: … },
```

то есть **любое** нераспознанное имя становится непрозрачным номинальным типом. Шага «а
объявлен ли такой тип?» в этом пути нет. Дальше сверка присваиваемости против непрозрачного
неизвестного ничего не находит — и вся проверка в этой позиции исчезает беззвучно.

Кодоген потом манглит имя в `Nova_<имя>`. Отсюда единственная разница между громким и тихим
носителем: **дошёл тип до эмиттера или нет**. Не дошёл — программа собирается и работает.

## Как запускать

```sh
cp docs/plans/repro/971-undeclared-type-name-accepted/<файл>.nv.txt /tmp/t.nv
nova-cli/target/release/nova.exe check /tmp/t.nv
nova-cli/target/release/nova.exe build /tmp/t.nv -o /tmp/t.exe && /tmp/t.exe
```

## Что доказывают контроли

Правило существует и исполняется: обе двери аргумента — примитивная (`int`) и обобщённая
(`Vec[int]`) — отвергают несовпадение через `E7301`. Носитель 2 отличается от своего
контроля РОВНО ОДНОЙ БУКВОЙ в имени типа (`Vecc` против `Vec`), и этой буквы достаточно,
чтобы проверка исчезла, а программа собралась и выполнилась.

То есть это не «проверки ещё нет», а «проверка есть и её можно случайно отключить опечаткой».

## Границы: чего проба НЕ утверждает

* **ТИХОЙ МИСКОМПИЛЯЦИИ ЗДЕСЬ НЕ ПОКАЗАНО.** Три носителя тихие в том смысле, что
  собираются и работают без единого слова, — но во всех трёх неверно типизированное
  значение НЕ ИСПОЛЬЗУЕТСЯ. Я пробовал довести его до операции (`x.len()` на неизвестном
  типе) — там кодоген обязан выпустить тип и отказ становится громким. Форму, где неверное
  значение реально читается и даёт неверный результат, я НЕ НАШЁЛ и НЕ ОПРОВЕРГ, что она
  есть. Это первое, что стоит померить чинящему.
* **Не мерил другие позиции аннотации:** поле записи проверено только через `float`;
  переменная-локаль проверена (`ro x float = 1.5` — громкая); НЕ мерил: параметр типа в
  границе (`[T: Zzz]`), тип в `extern`-сигнатуре, тип в контракте, алиас.
* **Не искал, нет ли где-то ОТДЕЛЬНОГО прохода**, который объявленность имён проверяет и
  просто не добирается до этих позиций. Замер говорит только, что в четырёх позициях он не
  срабатывает. Чинящий начинает с поиска такого прохода: если он есть, работа — довести его
  до всех позиций, а не писать новый.
* **FFI не рассматривался.** Прежде чем запрещать необъявленные имена, надо ответить, не
  опирается ли на эту дыру описание непрозрачных сишных типов, — иначе фикс уронит FFI.

## Почему `float` — самый вероятный носитель на практике

Он читается как настоящее имя. Проза самой спеки пишет «int и float — РАЗНЫЕ роды»
(`spec/decisions/02-types.md:1521`), таблицы D54 говорят «float → int truncation», а тип при
этом называется `f64`. Пользователь, прочитавший спеку, напишет `float` — и получит либо
ошибку сгенерированного Си про `Nova_float`, либо, если тип не дошёл до эмиттера, молча
непроверяемую программу.
