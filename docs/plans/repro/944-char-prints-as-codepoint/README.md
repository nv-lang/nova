# Проба к №944 — `println(c)` на `char` печатает КОД, а тот же `char` в интерполяции печатает СИМВОЛ

Найдено 2026-09-05 при аудите таблицы D54 по приёмке строки №931(а) — то есть
попутно, при проверке, существуют ли формы, к которым спека отсылает. Проба
`65 as char` печатала `65`, и первое чтение «cast не сработал» оказалось неверным:
значение — настоящий `char` (`a == (65 as char)` даёт `true`, интерполяция печатает
`A`). Сломан не cast, а ОДНА из четырёх дверей отображения.

## Как запускать

```sh
sh docs/plans/repro/944-char-prints-as-codepoint/cmd.sh
```

## Замер 2026-09-05

| форма | вывод | верно? |
|---|---|---|
| `println(a)` при `ro a = 'A'` | `65` | **нет** |
| `print(a)` | `65` | **нет** |
| `a.to_str()` | `A` | да |
| `"${a}"` | `A` | да |
| `char`-параметр, печать внутри вызываемой | `65` | **нет** |
| `'я'` в интерполяции | `я` | да |
| `'я'` напрямую | `1103` | **нет** |
| `Vec[char].of('A','B')` в интерполяции | `Vec[A, B]` | да |

Три двери из четырёх согласны между собой и печатают символ. Расходится ровно
путь «аргумент `print`/`println` напрямую» — и он же самый частый.

## Почему это дороже, чем выглядит

`println(c)` — первая строка, которую человек пишет на новом языке. Неверный ответ
здесь не падение и не диагностика, а правдоподобное ЧИСЛО на месте буквы: читатель
заподозрит свои данные, а не компилятор. И это необратимо после тега — починка
меняет вывод уже написанных программ.

## Что НЕ является причиной (проверено, чтобы не искали заново)

- **не cast**: `'A'` из литерала печатается так же неверно, без всякого `as`;
- **не Unicode**: `'я'` ведёт себя ровно так же, `1103` против `я`;
- **не отсутствие `Display`**: `to_str()` у `char` есть и даёт правильный ответ,
  и интерполяция им пользуется.
