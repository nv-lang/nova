# №1187: разбиение долга кодов `E_*` — шаг 1, места печати

**Заказ:** интегратор, 2026-09-20 15:01. Из 178 кодов базы
`ecode-fixture-debt.baseline` назвать, сколько ЖИВЫХ, сколько ЗАТЕНЁННЫХ
перехватчиком (и чем это доказано), сколько НЕДОСТИЖИМЫХ; ключ — код,
знаменатель назвать; стража не трогать, базу не двигать. **Вердиктов здесь нет.**

## Почему первым шагом идёт место печати, а не список проб

Разделить долг на три кучи можно только пробой, а пробу нельзя написать, не зная,
ГДЕ код печатается и при каком условии. Карта 1186 давала ПЕРВОЕ вхождение имени —
а это часто doc-комментарий этажом выше; оговорка той карты куплена на
`E_UNSAFE_REQUIRED`, у которого имя впервые встречается в одном файле, а печать
живёт в другом.

Здесь местом печати считается строка, где код стоит ВНУТРИ строкового литерала в
исполнимом коде, то есть ровно то, что уезжает в текст диагностики.

## Замер (полная выдача — `print-sites.txt`, пересчёт — `print-sites.py`)

| величина | число |
|---|---|
| кодов в базе долга | 178 |
| файлов `.rs` прочитано в `compiler-codegen/src` | 109 |
| **место печати найдено** | **166** |
| **место печати НЕ найдено** | **12** |

**Двенадцать без места печати — это не «мёртвые коды», и назвать их так было бы
подменой.** Текст диагностики может собираться иначе: у `argbind.rs` сообщения
строятся в методе `fn message(&self) -> String`, а код приклеивается выше по
течению — ровно поэтому носитель строки 1197 не ловился ключом-кодом. Эти
двенадцать идут отдельной кучей и требуют ЧТЕНИЯ, а не грепа:
`E_CONST_CONSUME_CONFLICT`, `E_CONST_MUT_CONFLICT`, `E_CONST_RO_REDUNDANT`,
`E_INVALID_ORDERING_LOAD`, `E_INVALID_ORDERING_STORE`, `E_LINT_ALLOW_NO_REASON`,
`E_LINT_EXPECT_NO_REASON`, `E_PROTO_IMPL_CONSUME_FOR_MUT`,
`E_PROTO_IMPL_MUT_FOR_CONSUME`, `E_PROTO_IMPL_MUT_FOR_RO`, `E_READONLY_`,
`E_TYPE_ARITY_MISMATCH`.

Среди них сразу виден и другой сорт: `E_READONLY_` — ОБРЫВОК имени, а не код
(тот же вид, что `E_BANG_` в замере 1197). То есть куча «без места печати»
неоднородна по построению, и это названо до того, как её считать долгом.

## Границы шага, названные явно

* имя функции берётся ближайшим `fn` выше по файлу — для вложенных замыканий это
  ГРУБО, и здесь так и написано, а не выдано за точность;
* судится только `compiler-codegen/src`; `novac/src` — другой компилятор, другой
  владелец и другая база;
* шаг НЕ отвечает на вопрос заказа: он даёт материал, без которого на него нельзя
  ответить. Сколько кодов живых, затенённых и недостижимых — следующий шаг, и он
  делается пробами по одной на код, с контролем у каждой.

`E_CONST_FIELD_IN_LITERAL` не поднимается, потому что раньше срабатывает

только когда **у перехватчика фикстура есть**; проверено:
`spec_tests/conformance/neg/neg_record_missing_field.nv` закрепляет именно его.
Пометку `nova:shadowed-by E_MISSING_FIELD_IN_LITERAL` ставит тот, кто ЧИНИТ, — не я.

### Третья куча названа честно: это «не дошла», а НЕ «недостижим»

Восемь кодов не поднялись МОЕЙ формой. Утверждать по этому недостижимость нельзя —
проба показывает только то, что моя форма до места печати не добралась. Что с ними
дальше и почему они собраны вместе:

* `E_CONST_RO_REDUNDANT`, `E_CONST_MUT_CONFLICT`, `E_CONST_CONSUME_CONFLICT` — из
  тех самых двенадцати без места печати: код выбирается `match` по следующему
  токену (`parser/mod.rs:5514`), а в литерале сообщения его нет. Формы `const ro X = 1`
  и её сёстры прошли ЧИСТО — значит либо путь не тот, либо диагностика не
  срабатывает; отличить может только чтение ветки парсера, и это следующий шаг;
* `E_LINT_EXPECT_NO_REASON` — это ЛИНТ (`LintWarning`), а не ошибка компиляции, и
  `nova check` его в этом прогоне не печатал. То есть нужен другой канал вывода, а
  не другая форма;
* `E_BAD_FORMAT_SPEC`, `E_BOUND_UNKNOWN`, `E_BOUND_NOT_PROTOCOL`,
  `E_TYPE_ARITY_MISMATCH` — формы переписывались по чтению условия ОДИН раз и всё
  ещё не дошли; вторая попытка требует чтения того, при каком составе входа
  проверка вообще вызывается.

**Что партия уже доказала о методе:** конвейер (проба + контроль + классификация по
поднятому коду) работает и различает все три исхода — живой, затенённый и
недошедший — на живых носителях, а не на фикстурах. **Чего НЕ доказала:** что
«не дошла» можно сводить к «недостижим»; для этого нужен другой инструмент —
чтение условия в месте печати, а не проба формой.

## Шаг 3: восемь недошедших разобраны ЧТЕНИЕМ условия — шесть живых, два недостижимых

Задание интегратора (15:34): у каждого из восьми — один из трёх исходов, и у
каждого исхода СВОЁ доказательство; «недостижим» доказывается чтением ветки в
месте печати фразой «условие требует X, а X невозможно, потому что Y», а
отсутствие срабатывания доказательством не является.

### ЖИВЫЕ — 6 из 8, и у каждого названа форма, которой не хватало

| код | чего требовало условие | форма, которая подняла |
|---|---|---|
| `E_CONST_RO_REDUNDANT` | `ro`/`mut`/`consume`, за которым идёт `const`, **в позиции ПОЛЯ внутри тела типа** (`parser/mod.rs:5504`) | `type RecBox { ro const A int }` |
| `E_CONST_MUT_CONFLICT` | то же | `type RecBox { mut const A int }` |
| `E_CONST_CONSUME_CONFLICT` | то же | `type RecBox { consume const A int }` |
| `E_BOUND_UNKNOWN` | имя границы, неизвестное таблице сигнатур (`types/mod.rs:29270`) | `fn f[T NoSuchProtocol](x T)` |
| `E_BOUND_NOT_PROTOCOL` | граница — объявленный тип, но НЕ протокол и не примитив | `fn f[T RecBox](x T)` |
| `E_LINT_EXPECT_NO_REASON` | это ЛИНТ, а не ошибка компиляции | `nova check --lint` на `// nova:expect …` без причины |

**Две мои ошибки, из-за которых они числились недошедшими, названы прямо:**

* у тройки `const` я перепутал И ПОРЯДОК, и ПОЗИЦИЮ: пробовал `const ro X = 1`
  на верхнем уровне, а условие требует `ro const` в поле типа. Порядок взят из
  кода, а не из догадки, — и в этом вся разница;
* у границ дженерика я написал `[T: Proto]` ПО АНАЛОГИИ с другими языками, тогда
  как корпус пишет `[T Proto]` без двоеточия (`d122_bound_method_mono_dispatch.nv:38`).
  Это ровно тот запрет, который `AGENTS.md` называет первым: синтаксис не
  выдумывать, спрашивать компилятор и корпус.

Контроль у каждой пробы чист: `type RecBox { ro a int }` и `fn f[T](x T)`
принимаются без единого кода. **Первая редакция контроля была ГРЯЗНОЙ** — имя
типа `T` подняло `E_RECV_GENERIC_SHADOWS_TYPE` и `E_PREFIX_SHADOWS_NAMED_TYPE`,
и клетка доказывала бы не то; имя заменено на `RecBox`.

### НЕДОСТИЖИМЫЕ — 2 из 8, и это доказано чтением, а не молчанием

**`E_BAD_FORMAT_SPEC` — условие требует вызова, которого в поставляемом коде
нет.** Код собирается только в `parse_rich_format_spec` (`ast/format_spec.rs:260`).
Все вызовы этой функции в `compiler-codegen/src` находятся внутри
`#[cfg(test)] mod tests` того же файла (строка 382 и ниже), а в `nova-cli/src`
вызовов НОЛЬ. То есть из пользовательского кода функция не вызывается вовсе, и
поднять код формой нельзя в принципе.

**`E_TYPE_ARITY_MISMATCH` — места сборки не существует.** Во всём
`compiler-codegen/src` и `nova-cli/src` имя встречается РОВНО ДВАЖДЫ, и оба раза
в КОММЕНТАРИИ (`types/mod.rs:30911` и `:30937`), причём оба комментария говорят
«это его работа, не наша». Ни одного места, где код попадал бы в диагностику,
нет — значит это имя без носителя.

### Побочный ответ: «двенадцать без места печати» — не куча, а ЧЕТЫРЕ механизма

Интегратор просил проверить, правда ли двенадцать особенные. Проверено чтением, и
особенность у них одна общая — **код не написан литералом в своём же сообщении**, —
но механизмов четыре, и они разные:

1. **подстановка переменной:** `format!("[{code}] …")` — тройка `const`-конфликтов
   (`parser/mod.rs:5514`); во всём дереве таких мест ровно одно;
2. **именованная константа:** `pub const E_INVALID_ORDERING_LOAD: &str = "…"`
   (`types/mod.rs:53503`) — код живёт значением, а не текстом;
3. **правило линта:** `rule: "E_LINT_EXPECT_NO_REASON"` (`lints.rs:3620`) — другой
   канал вывода, `--lint`;
4. **табличная диагностика:** `("E_PROTO_IMPL_MUT_FOR_RO", …)` (`types/mod.rs:38892`)
   — код стоит элементом таблицы.

И пятый элемент, который механизмом не является: **`E_READONLY_` — обрывок имени**
(`E_READONLY_COERCE`, `E_READONLY_CONTENT`), то есть ложный элемент знаменателя.
Значит база долга 178 завышена как МИНИМУМ на единицу, и это находка, а не уборка:
двигать базу — не моя работа.

**Что это меняет для моего же сканера мест печати:** его предикат («код литералом
в строке») уже предмета, и двенадцать — не свойство кодов, а СЛЕПОТА СКАНЕРА.
Названо здесь, а не исправлено молча.

## Шаг 4: сканер починен — и его вывод СОШЁЛСЯ с чтением, хотя они независимы

Шаг 1 объявил «без места печати» двенадцать кодов; шаг 3 показал, что это была
СЛЕПОТА СКАНЕРА (он искал только литерал `[КОД]`, а механизмов четыре). Сканер
переписан и теперь называет МЕХАНИЗМ, а не только место. Новый замер по той же
базе (`print-sites.txt` перезаписан второй редакцией):

| механизм | кодов | что это значит |
|---|---|---|
| `literal` | 163 | `"[E_X] текст"` прямо в сообщении |
| `bare-name` | 4 | имя в исполнимом коде без кавычек (переменная, сравнение) |
| `other-literal` | 4 | имя строкой, но не в форме `[КОД]` |
| `const` | 2 | `pub const E_X: &str = "E_X"` |
| `lint` | 2 | `rule: "E_X"` — другой канал вывода (`--lint`) |
| `table` | 2 | `("E_X", …)` элементом таблицы |
| **только в комментариях** | **1** | места сборки нет |
| не встречается нигде | 0 | — |

Итого **177 из 178** имеют механизм попадания в диагностику.

**Сошлось независимо, и это главный результат шага.** Единственный код в куче
«только комментарии» — `E_TYPE_ARITY_MISMATCH`, то есть РОВНО тот, который шаг 3
доказал недостижимым чтением обеих его строк. Два разных инструмента — чтение
ветки и переписанный сканер — пришли к одному имени, не зная друг о друге. Это не
доказательство недостижимости (её даёт чтение), но это проверка ИНСТРУМЕНТА:
сканер, чья куча совпала бы с чтением случайно, совпал бы и на других именах.

**Чего шаг НЕ говорит:** механизм ≠ достижимость. `literal` у кода означает лишь,
что текст собирается в строке; вызовут ли эту ветку на пользовательской программе
— отдельный вопрос, и `E_BAD_FORMAT_SPEC` тому пример: механизм у него `literal`,
а вызывается функция только из собственных тестов.

## Шаг 6: партия 2, вторая волна — коэрсия подтверждена живой, свой же контроль сначала соврал

`E_COERCE_NOT_ZERO_COST` подтверждён живым: `#coerce fn int @to_str() { "x" }`
(без возвращаемого типа) поднимает код. **Первая редакция контроля упала САМА**
— я написал полноценную пару из двух `#coerce fn`, и один из них потребовал
параметр, что нарушает другое правило (`E_COERCE_NOT_UNARY`), а второй не нёс
`ro`-обёртку возврата и попал под ТОТ ЖЕ код по другой причине (D429 R2:
zero-cost view обязан возвращать `ro O`, а не голый `O`). Сообщение
компилятора назвало точное требование текстом, и верный контроль
(`-> ro str`) оказался чист. Счёт партии 2 теперь: живых 4, недостижим 1,
честно открыто 2, не пробовалось 3.
