# E_CONST_FN_DIV_ZERO — не воспроизводится, вероятный дефект метода/пайплайна

`p.nv` использует ТОЧНЫЙ структурный шаблон доказанно рабочей негативной
фикстуры `spec_tests/conformance/neg/d199_non_const_arg_neg.nv` (`#no_prelude`,
`module neg.…`, вызов внутри обычной `fn`, литеральные аргументы) — заменено
только тело (`a / b` вместо `a + b`) и аргументы (`5, 0` вместо `x, 3`).
Даёт чистый `ok`, а не `[E_CONST_FN_DIV_ZERO]`.

## Что проверено, а не предположено

1. **Сам пайплайн работает**: та же фикстура-донор (`d199_non_const_arg_neg.nv`)
   даёт `[E_CONST_FN_NON_CONST_ARG]`, запущенная тем же бинарём той же командой.
2. **`nova check` действительно должен ловить эти коды** — в исходнике
   (`compiler-codegen/src/main.rs:314`, внутри `cmd_check`) стоит буквально:
   «Plan 114.4.2 (D199) Ф.3 + 114.4.3 (V2): const fn AST rewrite + eval также
   должен запускаться в check-режиме чтобы evaluator errors
   (E_CONST_FN_EVAL_OVERFLOW / DIV_ZERO / DEPTH_EXCEEDED) fired.»
3. **Условие в источнике реально существует и выглядит достижимым**:
   `div_zero_err` (`const_fn_eval.rs:792`) вызывается из `eval_binary`
   (`:648`, ветки `BinOp::Div`/`BinOp::Mod`), `eval_binary` вызывается из
   `OwnedEvaluator::eval_expr` (используемого `eval_call_inner`, `:1664`),
   а `eval_call_inner` вызывается из `walk_expr` (`:2422`) через
   `ev.eval_call(...)` — и `walk_expr` идёт от `rewrite_const_fn_calls`
   (`:1450`, публичная точка входа, вызывается из `cmd_check` дважды по
   коду).
4. **Простая арность тоже не ловится**: `divide(5)` (не хватает аргумента)
   вместо ожидаемой ошибки арности из того же `eval_call_inner`
   (`fd.params.len() != args.len()`) тоже дал чистый `ok` — то есть
   проблема не специфична для деления, а шире: `eval_call_inner`
   для этой формы вызова, похоже, вообще не достигается, хотя
   `E_CONST_FN_NON_CONST_ARG` (более ранний гейт в ТОМ ЖЕ `walk_expr`,
   проверяющий, что аргументы constexpr, ДО вызова `eval_call`) работает
   штатно.
5. **Возможная зацепка, НЕ подтверждённая**: `try_literal_to_value`
   (`const_fn_eval.rs:1369`) сама умеет частично вычислять `Binary`/`Unary`
   через `eval_binary(...).ok()` — глотая диагностику в `None`. Если где-то
   ДО `walk_expr`/`eval_call_inner` тело простой `=>`-const-fn пытается
   быть свёрнуто через этот путь вместо полного `eval_call`, ошибка могла
   бы тихо превращаться в «не constexpr» вместо диагностики — но прямого
   вызова `try_literal_to_value` на ТЕЛЕ функции (а не на аргументах
   вызова) в файле не найдено; это гипотеза для следующей волны, не вывод.

## Почему не гадаю дальше

Дальнейшее продвижение требует либо инструментированной сборки
(`eprintln!`/отладчик) компилятора, либо чтения `check_module`
(types/mod.rs) на предмет отдельного, более раннего пути валидации
вызовов const-fn, который мог бы решать «это runtime-вызов» ДО того,
как `rewrite_const_fn_calls` вообще увидит узел. Это выходит за рамки
черного ящика (только `.nv` + бинарь), которым велось расследование
1187 до сих пор, и вероятно быстрее для того, кто уже держит
`const_fn_eval.rs`/`types/mod.rs` в контексте кода.

## Итог

Записано в реестр 221.1 как отдельная методологическая находка (не как
обычное «недостижимо») — доказательства сильнее, чем «проба не сработала»,
и класс дефекта другой: часть пайплайна (пост-валидационное вычисление)
выглядит вообще не достигаемой из `check`, при том что соседняя часть
ТОГО ЖЕ пайплайна (пре-валидация аргументов) работает штатно.
