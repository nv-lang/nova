## Семь кодов без условия в окне: прочитаны отдельно, в МЕСТЕ ПОСТРОЕНИЯ

У этих семи условие не стоит рядом с печатью, потому что печать и решение
РАЗНЕСЕНЫ: текст собирается в методе сообщения либо в `?`-цепочке, а условие
живёт там, где значение ошибки СОЗДАЁТСЯ. Это тот же случай, что `argbind.rs`
в замере 1197, и именно из-за него окно поиска в 15 строк ничего не находит.

* `E_AUTO_DERIVE_UNKNOWN_PROTOCOL` — текст в `DeriveError::diagnostic_message()`
  (`protocols/auto_derive.rs:182`), а УСЛОВИЕ в `synthesize_method`
  (`:958`): `if !is_builtin_protocol(protocol)`.
  **Форма пробы:** `@derive` с именем, которого нет среди встроенных протоколов.
* `E_AUTO_DERIVE_UNSUPPORTED_KIND` — тот же метод сообщения (`:192`); условие —
  соседняя ветка того же построения, читать `synthesize_method` целиком.
* `E_CONST_FN_ALLOCATION` — условие прямо в разборе тела (`types/mod.rs:2836`):
  ветка `E::ArrayLit(_) | E::MapLit { .. } | E::InterpolatedStr { .. }`.
  **Форма пробы:** `const fn`, в теле которого литерал массива, карты или
  интерполяция строки.
* `E_CONST_FN_CLOSURE_BODY` (`const_fn_closure.rs:531`, `:635`) и
  `E_CONST_FN_CLOSURE_EXTERNAL` (`:626`) — про тело `const fn`-замыкания:
  первое требует, чтобы тело БЫЛО closure literal, второе запрещает внешнее
  замыкание. Формы строятся из этих двух требований.
* `E_COERCE_NOT_ZERO_COST` — условие `let Some(ret_ty) = &f.return_type else`
  (`types/mod.rs:28041`). **Форма пробы:** `#coerce fn` БЕЗ объявленного
  возвращаемого типа.
* `E_BLOCKING_FN_DECL_MISSING` — особый случай и назван отдельно: текст живёт в
  `ok_or_else` при поиске в `mono_fn_decls` (`codegen/emit_c.rs:16224`), то есть
  это ВНУТРЕННЯЯ ошибка эмиттера, а не диагностика пользовательской формы.
  Пробу пользовательским кодом на неё, скорее всего, не построить — и это надо
  проверять чтением, а не подбором формы.

**Что из этого следует для классификации:** «место печати» и «условие» — РАЗНЫЕ
вещи, и у части кодов они в разных функциях. Сканер мест печати отвечает на
первый вопрос и не отвечает на второй; для второго нужен либо путь построения
значения ошибки, либо чтение. Названо здесь, чтобы следующая партия не искала
условие там, где его нет по устройству.

## Три кода closure-returning const fn: формы взяты из doc-комментария модуля

`const_fn_closure.rs` не имеет ни одной фикстуры в корпусе (`grep -rn "const fn("
spec_tests std` — 0 совпадений), поэтому канонической формой служит РАБОЧИЙ
пример из doc-комментария модуля (`const_fn_closure.rs:6-7`), а не догадка:

```nova
fn make_adder(const n int) -> const fn(int) -> int =>
    |x| x + n
```

Это КОНТРОЛЬ для всех трёх кодов ниже — он обязан оставаться чист в каждой
пробе.

* `E_CONST_FN_CLOSURE_BODY` (`:531` и `:635`, ДВА места одной сути) — тело
  функции, объявленной как `-> const fn(...) -> R`, обязано быть closure
  literal (`Lambda`/`ClosureLight`/`ClosureFull`). **Форма пробы:** тело —
  голое выражение, не замыкание:
  `fn make_adder(const n int) -> const fn(int) -> int => n`.
* `E_CONST_FN_CLOSURE_EXTERNAL` (`:626`) — внутри `ClosureFull` (полностью
  аннотированного замыкания вида `fn(x int) -> int => …`) тело не может быть
  `extern`. Синтаксис аннотированного замыкания в корпусе тоже не встречается
  (0 совпадений `fn(x int)` внутри `=>`), поэтому форма пробы остаётся
  ГИПОТЕЗОЙ до чтения грамматики `ClosureFull` в парсере — записываю это прямо,
  а не подставляю недоказанный синтаксис.
* `E_CONST_FN_CLOSURE_ARITY` (`:650`, функция `lambda_params_to_fn_params`) —
  число параметров закрытия не совпадает с arity `fn(...)` в объявленном типе
  возврата. **Форма пробы:** `fn make_adder(const n int) -> const fn(int) ->
  int => |x, y| x + y + n` (два параметра при объявленной arity 1).

**Почему это не догадка по аналогии, а вывод из чтения:** канонический пример
взят ДОСЛОВНО из doc-комментария реализации (Plan 114.4.4.4 V4.3), а не
сконструирован по внешнему языку — этого требует правило `AGENTS.md` про
синтаксис.
