# №699 — пере-снятие носителя 2026-09-20

**Заказ:** интегратор. Строка реестра 221.1 №699 говорит о себе «НОСИТЕЛЬ ЗАНОВО
НЕ ГОНЯЛСЯ», а механизм, которым она объясняла коллизию, в build-режиме
отфильтрован. Замер снят помощником; **вердикт по строке выносит интегратор** —
здесь только три ответа и их границы.

Запуск (бинарь можно назвать снаружи, если своего `target/` нет):

```sh
NOVA=/путь/к/nova.exe sh docs/plans/repro/699-test-peer-leaks-into-cu/cmd.sh
```

## 0. Носитель ЖИВ — проверено чтением до всякой пробы

`std/src/encoding/serde/tagging_test.nv:49` по-прежнему объявляет `type Node enum`.
Если бы его не было, работа кончалась бы здесь: предмет испарился.

## 1. Три режима — три ответа (их оказалось не три, а один)

Бинарь `nova.exe` 19 444 736 байт, собран 02:17 того же дня. Потребитель —
посторонний пакет `p699probe`, объявляющий свой `type Node` и РЕАЛЬНО зовущий
`json_encode` (первая редакция только импортировала его, и компилятор сказал
«unused import»: модуль мог не попасть в единицу, а «столкновения нет» читалось
бы как ответ при пустой мишени).

| режим | команда | вердикт дословно |
|---|---|---|
| check | `nova check <pkg>/src` | `ok: … main.nv (1 warning)`, `PASS: 1 FAIL: 0 WARN: 1` |
| test | `nova test <pkg>/src` | `PASS: 1 FAIL: 0` |
| build | `nova build <pkg>/src/main.nv -o a.exe` | `built: …a.exe (7.2s)` |

**`[INTERNAL-PANIC]` не встретился ни на одном пути** — строка требовала именно
этого.

## 2. ГРАНИЦА ОТВЕТА: чистота НЕ доказана, она НЕ ОПРОВЕРГНУТА

Три контроля должны были показать, что проба вообще способна увидеть
столкновение. Ни один не покраснел:

* **контроль-1** — файл объявляет тип с именем ИМПОРТИРОВАННОГО (`SerError`):
  ЧИСТО. Это законно (объявление в файле старше импорта), и сам импорт получает
  лишь лint «unused» — контроль слабый, он ничего не доказывает;
* **контроль-2** — ДВА peer-файла одного модуля объявляют `Node` (форма из самой
  строки, D281 Rule C): ЧИСТО, `PASS: 1`;
* **контроль-3** — тот же peer назван ПРЯМО, чтобы отличить «файлы не читались»
  от «читались и промолчали»: ЧИСТО, и в выводе стоит предупреждение о ДРУГОМ
  файле модуля (`main.nv`). Значит peer-файлы грузятся ВМЕСТЕ, и молчание про
  два `Node` — ответ, а не слепота.

**Отсюда прямое следствие, и оно важнее самой пробы:** «чисто» в разделе 1
означает «диагностики нет ни в одном из трёх режимов», а НЕ «утечка закрыта».
Построить положительный контроль пользовательским кодом не удалось — значит
проба не умеет отличить «столкновения нет» от «столкновение есть, но о нём
молчат».

## 2а. Ловушка для следующего, кто будет строить пробу НА ИМПОРТЕ

Первая редакция этой пробы импортировала `json_encode` и ни разу его не звала.
Проба прошла ЧИСТО — и это был бы честный на вид ответ на вопрос, который в неё
не входил: модуль, который только импортирован, мог вовсе не попасть в единицу
компиляции, а значит столкновению неоткуда было взяться. Мишень была пуста, а
выглядела чистой.

Поймал это не замысел, а **предупреждение компилятора** `unused import` в его же
выводе. Отсюда правило, которое дешевле выучить здесь, чем на своей строке
реестра: **проба, доказывающая ОТСУТСТВИЕ чего-то, обязана показать, что предмет
в неё входил.** Для пробы на импорте это значит: импортированное ВЫЗЫВАЕТСЯ, и
в выводе нет «unused import» на том имени, ради которого проба написана.

## 3. Замечено по дороге, вердикта не выношу

* `nova check <каталог>` на каталоге из ДВУХ файлов печатает `PASS: 1` и
  называет только `main.nv`; второй файл в счёт не попадает. Родня — строка
  реестра №1165 («раннер называет каталогом один файл из шестнадцати»).
* Два peer-файла ОДНОГО модуля, объявляющие один и тот же тип, не дают никакой
  диагностики, хотя по D281 Rule C это один модуль. Загрузку обоих доказывает
  контроль-3.

Оба наблюдения — предмет чужих строк и чужих вердиктов; здесь они названы,
чтобы не потеряться.
