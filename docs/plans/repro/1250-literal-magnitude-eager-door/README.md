# Проба к реестру №1250 -- магнитудная дверь бьёт рядную раньше типа

## Находка

НАЙДЕНО ОХОТНИКОМ 2026-09-21 (novac, клетка `check`×К4), отчёт
`docs/dev/hunts/novac/2026-09-21-check-k4.md` (Н1). Родня #1251 (Н2) --
обе бьют из той же пары дверей.

## Минимальные репро, все четыре формы

`p1-u64-max.nv.txt`:
```nova
fn take(x u64) -> u64 => x
fn main() Io -> () {
    println(take(18446744073709551615))
}
```

`p2-int-min.nv.txt` -- `take(-9223372036854775808)` при параметре `int`.

`p3-u64-max-hex.nv.txt` -- тот же `u64`-максимум шестнадцатеричным
(`0xFFFFFFFFFFFFFFFF`).

`p4-fn-return.nv.txt` -- `fn big() -> u64 => 18446744073709551615`.

Оракул принимает все четыре; novac отвергал все четыре одним и тем же
сообщением -- «this integer literal does not fit in `int`».

## Замер ДО фикса

`rc=1` на всех четырёх, `E_NOVAC_SUBSET`, "...does not fit in `int`...".
Контроль `take(7)` при `u64` -- чист у обоих (не задет).

## Замер ПОСЛЕ фикса

`rc=0` на всех четырёх. Контроль `u8=300` -- по-прежнему честно отказан
(`E_LIT_OUT_OF_RANGE`, "the type holds at most 255"); контроль -- литерал
шире `u64` (33 девятки) -- по-прежнему честно отказан магнитудной дверью.

## Корень

Величина целого литерала судится ДВУМЯ дверями в `literal_rules.nv`:

* `int_text_fits` (магнитудная) -- зовётся из общего обхода узла `Lit`
  (`check.nv:810`) для ЛЮБОГО литерала ДО того, как его позиция назвала
  тип; до фикса бралась граница `int`'s own (`INT_MAX_TEXT`,
  9223372036854775807, знак не участвует вовсе -- дверь не смотрит на
  предшествующий `-`);
* `int_text_fits_row` (рядная) -- зовётся из `@lit_fits_or_refuse` ПОСЛЕ
  того, как позиция (аргумент вызова, `return`) назвала точный ряд;
  отвечает ВЕРНО (граница ряда, с учётом знака).

Магнитудная дверь стоит раньше по обходу и уже отказывает, когда рядная
ещё не вызвана -- второе вычисление уже решённого суждения, и первая
дверь бьёт вторую, которая отвечает правильно.

## Фикс

Магнитудная дверь ПОДЧИНЕНА рядной: вместо границы `int`'s own она берёт
границу САМОГО ШИРОКОГО ряда языка -- `u64` (`U64_MAX_TEXT`,
18446744073709551615, 20 цифр; шестнадцатеричная ветка -- 16 значащих
цифр без ограничения на старший нибл, ровно как у `int_text_fits_row`
для `bits=64, signed=false`). Она больше не отвечает на вопрос «влезает
ли в `int`» -- это вопрос рядной двери, задаваемый ПОЗЖЕ, когда позиция
уже известна; она отвечает на вопрос «влезает ли хоть в КАКОЙ-то ряд
этого языка вообще», и это ровно то, что можно честно спросить ДО того,
как тип назван.

`int_max_text`'s собственная ветка `bits==64, !signed` теперь читает ту
же константу `U64_MAX_TEXT`, а не отдельный литерал того же текста --
одна строка текста, не две копии.

## Контроль отсутствия регрессии

- `novac/src/check/check_test.nv`, `novac/src/parse/parse_test.nv` --
  оба PASS (прогнаны напрямую по пути файла -- `nova test novac` без
  явного пути пропускает часть модулей, тот же К7-класс, что и раньше).
- `check-novac-grammar-kinds`, `check-novac-no-default-branch`,
  `check-novac-file-size` -- зелёные.
- `spec_tests/conformance/d49_statement_separator_newlines.nv` -- 5
  диагностик, без изменений.
- Тест-свидетель -- `check_test.nv`, "literal magnitude: the eager
  Lit-walk door defers to the row door, not `int`'s own bound (registry
  #1250)" -- несёт все четыре формы плюс ДВА контроля (литерал шире
  `u64` остаётся отказан магнитудной дверью; `u8=300` остаётся отказан
  рядной -- расширение ЕДИНОЙ двери не расширило ДРУГУЮ).
- Оба пути проверены прямыми пробами: откат файлов -> все четыре формы
  красны тем же сообщением, что нашёл охотник -> фикс восстановлен ->
  все четыре честно приняты, оба контроля не сдвинулись.
