# №1071 — `undefined identifier` всегда рапортует позицию 1:1

Замер 2026-09-12, окно интегратора. Найдено побочно: проба Д0б плана 286
проверяла, что линейность не ослабевает при одалживании ресурса обработчику —
отказ пришёл ВЕРНЫЙ, а позиция у него оказалась первой строкой файла.

Бинарь: `nova-cli/target/release/nova.exe` (сборка 2026-09-09 21:30).

```sh
./nova-cli/target/release/nova build probe.nv -o /tmp/probe.exe
```

## Что видно

`probe.nv` — одиннадцать строк, неизвестное имя стоит на строке **10**:

```
error: …/probe.nv:1:1: error: undefined identifier `nosuchname`
1 | // Позиция диагностики на неизвестном имени: ожидается строка 8, не 1:1.
  | ^^^^^^^^^^
```

Подчёркивание длиной **десять** символов — ровно длина `nosuchname`. То есть
длина спана верна, а начало — нет: оно всегда `1:1`. Компилятор указывает на
комментарий в первой строке.

## Чем это отличается от №687

№687 — про **LSP** и про конкретный путь: резолв импортов падает целиком, и
причина печатается со спаном `Span::new(0,0)` (`nova-lsp/src/compiler.rs:328`).

Здесь — **`nova build`**, файл **без единого импорта**, обычное неизвестное имя в
теле функции. Резолв импортов не участвует вовсе. Симптом тот же (позиция 1:1),
инструмент и путь другие, поэтому строки не дублируют друг друга.

## Почему это дорого

В файле на тысячу строк диагностика указывает на первую. Читатель ищет ошибку
там, где её нет, а потом ищет глазами по всему файлу — при том, что ИМЯ в
сообщении названо верно. Особенно больно на сгенерированных и на длинных
`.nv`-файлах std, где имён много.

Побочно: та же позиция пришла и на настоящем сценарии — обращение к
`consume`-ресурсу после его блока (`probe_after_scope.nv.txt`), где отказ верен
по существу, но найти место в большом файле по нему нельзя.
