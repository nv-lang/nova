# №1100 — авто-`@cleanup` снимается overload'ом, который никогда не вызывается

Найдено окном 274 (`nova-6e`) 2026-09-14. Два файла, отличающиеся ОДНИМ объявлением, дают
противоположное поведение: в первом cleanup срабатывает, во втором не срабатывает вовсе.

## Как воспроизвести

Бинарь — `nova-cli/target/release/nova` из корня дерева.

```sh
nova build docs/plans/repro/1100-cleanup-disarm-union/control-one-overload.nv -o /tmp/a1.exe
/tmp/a1.exe ; echo "exit=$?"
#   => stderr: panic: cleanup fired
#      exit=101          -- ПРАВИЛЬНО: обязательство аффинное, cleanup вставлен

nova build docs/plans/repro/1100-cleanup-disarm-union/leak-two-overloads.nv -o /tmp/a2.exe
/tmp/a2.exe ; echo "exit=$?"
#   => stdout: 1
#              reached the end without cleanup
#      stderr пуст, exit=0   -- ДЕФЕКТ: cleanup не сработал
```

## Что различает файлы

Ровно одно объявление:

```nova
fn use(consume x Boom) -> int { x.defuse()  9 }
```

Оно **никогда не вызывается** — вызов `use(g, 1)` разрешается во второй overload, берущий
позицию 0 ВИДОМ. Но D432 §4 п.3 дизармит флаг вызывающего по КОНСЕРВАТИВНОМУ UNION ПО ИМЕНИ:
«на позиции, которая `consume`-режима хотя бы на ОДНОМ overload'е этого имени». Union видит
`consume` у невызванного overload'а, флаг снимается, и чистить оказывается некому: вызываемый
взял вид и обязательства не имеет.

## Почему первый файл — КОНТРОЛЬ, а не «ещё одна проба»

Симптом «cleanup не сработал» одинаково объясняется двумя причинами: (а) union по имени видит
чужой overload; (б) дизарм вообще не сверяется с разрешённым вызовом. Контроль с ОДНИМ
видовым overload'ом делает вторую невозможной: там cleanup срабатывает, значит сверка с
разрешённым вызовом существует и ломает её именно union. Без контроля в строку реестра
поехал бы верный симптом с неверной причиной, и чинили бы не то.

Ось контроля предложил интегратор.

## Чем сторож наблюдает

`@cleanup`, который ПАНИКУЕТ (приём `D201Boom` из
`spec_tests/conformance/d188_reconsume_block.nv`). Печать внутри `@cleanup` не годится: D432 §1
требует ПУСТОЙ effect-row, а `println` — это `Io`, и авто-cleanup к такому типу не применяется
вовсе. Паника эффектом не является, поэтому она — единственный наблюдаемый сигнал, не меняющий
условий применимости правила.
