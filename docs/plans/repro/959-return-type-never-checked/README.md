# Пробы к №959 — тело функции никогда не сверяется с ОБЪЯВЛЕННЫМ ТИПОМ ВОЗВРАТА

Найдено интегратором 2026-09-05, когда не воспроизвёлся контроль соседней пробы (№957):
я спрятал в невызываемую функцию отказ №760 и ждал, что при вызове он сработает, — он не
сработал ни при вызове, ни без. Разбор «почему» и вскрыл настоящую причину: **проверки
возврата нет вообще**, а №957 был неверно истолкованным её следствием.

Правило, которое здесь не исполняется, записано и работает в двух других местах:
D405 (амендмент 2026-09-04) — «операнды любого числового оператора имеют один и тот же
конкретный числовой тип ПО ИМЕНИ, а не по ширине»; D54 — «неявных числовых конверсий нет
нигде»; `spec/conversions.ru.md` — сужение только явным `try_from`. Дверь аргумента и дверь
аннотированного биндинга это правило держат. Дверь возврата его не спрашивает.

## Как запускать

```sh
sh docs/plans/repro/959-return-type-never-checked/cmd.sh
```

Скрипт сам копирует `.nv.txt` во временный каталог, гоняет `check` и `build`, запускает
собранное и печатает таблицу ниже. Ничего в дереве не оставляет.

## Замер 2026-09-05 (`nova-cli/target/release/nova.exe`, main @ d59365c0f)

| проба | что написано | `nova check` | `nova build` → stdout |
|---|---|---|---|
| `ret_str_literal` | `fn f() -> int => "not an int"` | `ok` | **ошибка СИШНОГО компилятора** |
| `ret_narrowing_u8` | `fn wrap(n int) -> u8 => n`, `wrap(300)` | `ok` | built → **`44`** |
| `ret_f64_to_int` | `fn trunc(x f64) -> int => x`, `trunc(3.9)` | `ok` | built → **`3`** |
| `ret_int_to_bool` | `fn as_bool(n int) -> bool => n`, `as_bool(5)` | `ok` | built → **`true`** |
| `ret_var_not_literal` | `fn f(s str) -> int => s` | `ok` | ошибка сишного компилятора |
| `ret_block_body` | `fn f() -> int { return "not an int" }` | `ok` | ошибка сишного компилятора |
| `ctrl_arg_narrowing` | КОНТРОЛЬ, дверь аргумента: `sink(n)` при `n int = 300`, `sink(b u8)` | `E_IMPLICIT_NARROWING` | отвергнуто |
| `ctrl_bind_narrowing` | КОНТРОЛЬ, дверь биндинга: `ro b u8 = n` | `E_IMPLICIT_NARROWING` | отвергнуто |

## Что именно доказывают контроли

Одно и то же значение `int 300` в один и тот же тип `u8`, три двери:

```
аргумент      sink(n)            отвергнут   E_IMPLICIT_NARROWING
биндинг       ro b u8 = n        отвергнут   E_IMPLICIT_NARROWING
возврат       -> u8 => n         ПРИНЯТ  ->  печатает 44
```

Это не «в языке нет правила о сужении» и не «литералы адаптируются» — правило есть,
исполняется и звучит одинаково для всех трёх мест. Просто третья дверь его не спрашивает.
Две пробы отдельно закрывают напрашивающиеся возражения: `ret_var_not_literal` показывает,
что дело не в адаптации ЛИТЕРАЛА (возвращается переменная), а `ret_block_body` — что дело
не в arrow-теле (явный `return` в блоке ведёт себя так же).

## Почему это блокер тега, а не просто плохая диагностика

Три строки таблицы — **тихая мискомпиляция**: программа собирается, ничего не сообщает и
печатает неверное значение. `300` становится `44`, `3.9` становится `3`, целое становится
`true`. Три другие строки громкие, но громкие НЕ ТАМ: пользователь получает ошибку
сгенерированного C с координатами вида `main.c:5259` вместо диагностики Nova с координатами
своего файла.

## Границы пробы

Не мерил и потому не утверждаю: методы (`fn T.m() -> U`), замыкания, `-> @`-возврат
(D409 — там своя проверка, `d409_return_wrong_value_neg.nv` зелёная), обобщённые функции,
возврат из `match`/`if`-ветвей. Перечень форм — часть приёмки строки реестра, а не этой
пробы; здесь показан класс на самой простой форме.

В компиляторе нет ни одной диагностики про несовпадение тела с объявленным возвратом:
греп по всем текстам `[E...]`, содержащим `return`, даёт только const-fn, `??`-fallback,
consume-block и D409 — ни одной общей.

## Что говорит спека

Это не неспецифицированная область и не вопрос к владельцу: спека называет
позицию возврата типизированной прямым текстом, в трёх местах.

* **D55, таблица «Позиции с явно ожидаемым типом»**
  (`spec/decisions/02-types.md`, строка 1361): строка `fn f() -> T => value`
  (return-выражение), колонка «Coercion применяется?» — **да**. То есть
  компилятор точно знает целевой тип в этой позиции — и действительно
  знал: `materialize_literal_coercion` вызывается ровно там. Не было второй
  половины: зная целевой тип, он ПОДГОНЯЛ под него литералы и НИ
  РАЗУ не спросил, что делать с тем, что подогнать нельзя.
* **D54** — неявных числовых конверсий нет НИГДЕ; сужение — только явным
  `as` / `try_from`.
* **D405, амендмент 2026-09-04, п. 4** — «одна дверь сверки операндов для всех
  числовых операторов; чекер, не Си (`EXPECT_CC_ERROR` для этих случаев —
  не приёмка)». Здесь три формы из шести ловил именно Си — ровно то,
  что амендмент объявил НЕ-приёмкой.

Значит спек-амендмент для фикса №959 НЕ требуется: правило записано трижды,
не было только исполнения. Этим строка отличается от №926, где правил про
float до 2026-09-04 действительно не было вовсе.
