# План 222.3 — модуль `polaris.extract`: типизированное извлечение из запроса

**Статус:** 📋 ДИЗАЙН, НЕ СОГЛАСОВАН. **Слой:** 2 (Polaris-ядро).
**Зависит:** 222.1 (Router — ✅ влит), [180.1](180.1-serde-parity-and-beyond.md) Ф.1 (serde
field-атрибуты — без `rename_all` любой реальный JSON-API мимо).
**Основа:** Axum `FromRequest` (форма) + **наш serde как ЕДИНЫЙ движок** (механизм).
**Родитель:** [222](222-http-framework.md) · **Карта:** [222.0](222.0-module-map.md).

## 1. Протокол

```nova
/// Извлечение значения из запроса. ВСЕГДА синхронно — тело уже буферизовано
/// (`ServerRequest.body []u8`), в отличие от Axum, где extractors async.
export type FromRequest protocol {
    .from_request(req ServerRequest) -> Result[Self, HttpError]
}
```

## 2. Встроенные extractor-типы (все — `value`-record с одним полем + property-аксессор)

```nova
export type Path[T]  value { priv data T }      // {name}-параметры пути
export type Query[T] value { priv data T }      // ?a=1&b=2
export type Json[T]  value { priv data T }      // тело как JSON
export type Bytes    value { priv data []u8 }   // сырое тело
export type Text     value { priv data str }    // тело как UTF-8
export type Headers  value { priv data HeaderMap }

// Доступ — property-метод по конвенции D117 (НЕ голое поле):
export fn Path[T]  @data() -> T => @data
export fn Query[T] @data() -> T => @data
export fn Json[T]  @data() -> T => @data
export fn Bytes    @data() -> []u8 => @data
export fn Text     @data() -> str => @data
export fn Headers  @data() -> HeaderMap => @data
```
**Синтаксис Nova не меняется:** Rust-паттерн `Json(input): Json<T>` невозможен и не нужен —
в теле `req.data()`.

## 3. Реализации `FromRequest`

```nova
#impl(FromRequest)
export fn Json[T Deserialize].from_request(req ServerRequest) -> Result[Json[T], HttpError] {
    match json_decode_body[T](req.body_bytes()) {   // существующий мост 178/180
        Ok(v)  => Ok(Json { data: v })
        Err(e) => Err(e)
    }
}

#impl(FromRequest)
export fn Path[T Deserialize].from_request(req ServerRequest) -> Result[Path[T], HttpError] {
    mut d = ParamsDeserializer.at(req.params())
    match T.deserialize(d) {
        Ok(v)  => Ok(Path { data: v })
        Err(e) => Err(HttpError.decode_error(e.to_str()))
    }
}
// Query[T] — зеркально через QueryDeserializer.at(req.query())
// Bytes/Text/Headers — тривиальные (без serde)
```

## 4. Источники-`Deserializer` (ключевой архитектурный кусок: 0 строк Rust)

Реальный API (сверено `std/src/encoding/serde/serde.nv:124-165`): навигация по имени
`@enter_field(key) -> Result[Self, DeError]` + чтение по ТИПУ `@deser_int()`/`@deser_str()`/…
Синтез компилятора генерит `d.enter_field("id")?.deser_int()?`.

```nova
/// Плоский источник над [](str, str) — path-параметры.
export type ParamsDeserializer value { priv pairs [](str, str), priv cur Option[str] }
export fn ParamsDeserializer.at(pairs [](str, str)) -> ParamsDeserializer

/// Тот же контракт над query-строкой (percent-decode + split '&'/'=').
export type QueryDeserializer value { priv pairs [](str, str), priv cur Option[str] }
export fn QueryDeserializer.at(query str) -> QueryDeserializer
```
Оба реализуют `Deserializer`: `@enter_field(key)` находит пару и ставит под-курсор;
`@deser_int()` парсит строковое значение текущего курсора (`str.to_int()`, ошибка → `DeError`);
`@deser_str()` отдаёт как есть; `@is_null()` — курсор пуст (для `Option`-полей).
**`T` синтезируется `#impl(Deserialize)` ОДИН раз и работает со всеми тремя источниками.**

## 5. Регистрация хендлеров с extractors (арность-перегрузки на `Router`)

```nova
export fn Router mut @get[R IntoResponse](path str, h fn() -> R) -> Result[(), HttpError]
export fn Router mut @get[T1 FromRequest, R IntoResponse](path str, h fn(T1) -> R) -> Result[(), HttpError]
export fn Router mut @get[T1 FromRequest, T2 FromRequest, R IntoResponse](path str, h fn(T1, T2) -> R) -> Result[(), HttpError]
// … до 4; @post/@put/@delete/@patch — то же семейство
```
Тело (остальные — механическая копия по арности):
```nova
=> @get(path, Handler.new(fn(req ServerRequest) -> ServerResponse {
       match T1.from_request(req) {
           Ok(v1) => h(v1).into_response(),
           Err(e) => e.into_response(),
       }
   }))
```
Существующая форма `@get(path, Handler)` ОСТАЁТСЯ (низкоуровневый эскейп-люк).

**ЛОВУШКА (протокол «стоп+отчёт», НЕ обход):** резолв generic-overload по арности+bound —
класс `[M-concrete-instance-arity-overload-mangle]` (стрелял на П21). Если споткнётся —
чекпоинт + отчёт интегратору.

## 5а. Снос `Handler`-newtype и `handler_fn` (вопрос владельца 2026-07-23) — 🔬 проба

**Наблюдение владельца:** `handler_fn` — лишний слой, «внутри же просто функция».
**ПОПРАВКА 2026-07-23 (владелец заметил): `Handler.new` в тексте этого плана — НЕ существующий
API.** В коде есть ТОЛЬКО `handler_fn` (server.nv:345); `Handler.new` я писал как презумпцию
переименования. Реальная развилка — два исхода ОДНОЙ задачи, решает проба ниже:
(а) newtype `Handler` ОСТАЁТСЯ → `handler_fn` переименовать в `Handler.new` (чистка конвенции
«конструкторы = Type.new»; рядом `Middleware.new` уже правильный — налицо несогласованность);
(б) newtype УБИРАЕМ → исчезают оба, передаётся голая функция.
**Факт из кода** (`server.nv:325-333`): `Handler` — конкретный newtype
`value { priv f fn(ServerRequest) -> ServerResponse }` + `handler_fn` — конструктор к нему.
Комментарий прямо называет причину: **«the plan's `impl Handler` fallback … without existential
boxing»** — в 178 хотели протокол `impl Handler`, но существенциальные типы (сложить РАЗНЫЕ
реализации протокола в один `[]Route`) не поддерживались → взяли обходной newtype.

**Гипотеза (требует пробы, НЕ реализовывать по догадке):** ограничение снято/неактуально.
**Проба интегратора 2026-07-23 (усилила гипотезу):** свободная fn как значение — PASS;
**unbound-instance method value** (`Account.@add`, `int.@max`, спека D35 §Method values форма 2)
— **PASS**. Т.е. функции/методы как значения в языке РАБОТАЮТ. Известные дыры рядом (не блокеры
для этого пункта, но знать): static-форма `Type.method` как значение даёт ICE
(`[M-method-value-static-ret-type-ice]`), бланкет-методы не находятся
(`[M-method-value-blanket-not-found]`).
Если голый тип `fn(ServerRequest) -> ServerResponse` хранится в поле record'а с generics и
в `[]`-коллекции, то `Handler`+`handler_fn` — лишняя церемония:
```nova
r.post("/users", create_user)          // вместо handler_fn(…) / Handler.new(…)
```
**РЕШЕНИЕ ВЛАДЕЛЬЦА 2026-07-23 — развилка (а)/(б) СНЯТА третьим вариантом:**
```nova
type Handler fn(ServerRequest) -> ServerResponse   // NEWTYPE (не alias!), авто-коэрсия fn→Handler
```
- **`fn → Handler` — автоматически** (голая функция подставляется где ожидается `Handler`);
  **`Handler → fn` — НЕТ** (однонаправленно, тип не растворяется).
- **`handler_fn` УДАЛЯЕТСЯ** — авто-подъём заменяет конструктор: `r.post("/users", create_user)`.
- **newtype ОСТАЁТСЯ** → методы (`@handle`), внятная диагностика («ожидался `Handler`», а не
  «`fn(ServerRequest) -> ServerResponse`»), тип не путается с произвольной функцией.

**Почему НЕ `alias`** (рассматривался, отклонён): алиас прозрачен → нельзя методы, диагностика
хуже, направление симметрично (любая fn проходит везде). Плюс проба 2026-07-23 нашла, что
алиас fn-типа сейчас ВООБЩЕ не вызывается — `[M-alias-of-fn-type-not-callable]`.

**ФОРМА ВЫЗОВА (вопрос владельца 2026-07-23): `next(req)`, НЕ `next.handle(req)`.**
Если `Handler` — newtype над fn-типом, вызов обязан работать напрямую; `@handle` тогда —
ВТОРАЯ ДВЕРЬ и удаляется. Прецедент — Go: `type HandlerFunc func(…)` вызывается напрямую
`h(w, r)` И имеет методы. Почему fn-newtype форвардит вызов, а int-newtype НЕ форвардит `+`:
вызов — единственная осмысленная операция над функцией (Handler, который нельзя позвать,
пришлось бы разворачивать в каждой точке), тогда как `UserId + UserId` семантически бессмыслен.
Различие не в механике, а в осмысленности операции для нового типа.

**ОБЪЁМ ЯЗЫКОВОЙ РАБОТЫ — ТРИ КУСКА (проба 2026-07-23; больше, чем казалось):**
| # | Что | Статус пробы |
|---|---|---|
| 1 | Парсинг `type Handler fn(A) -> B` | ❌ **не парсится**: `expected identifier, got '('` — newtype принимает только ИМЕНОВАННЫЙ тип |
| 2 | Авто-подъём `fn → Handler` | ❌ нет: fn-типы вне таблицы «родов» D55 |
| 3 | Прямой вызов `next(req)` (call-through) | ❌ нет (следствие №1 — до вызова дело не доходит) |

Всё три — ЯЗЫК-меняющие (D52-амендмент на форму newtype + D55-амендмент на род), делаются
ДО миграции 25 файлов и, возможно, заслуживают собственного номера плана.

**Механизм для №2 — УЖЕ СУЩЕСТВУЮЩИЙ, не новая фича:** «obvious single-wrapper coercion»
(D55-амендмент, Plan 200) — значение рода `Y` в позиции `type W Y` авто-оборачивается.
**Единственное, чего не хватает: fn-типы не входят в таблицу «родов»** (сейчас там int-семья,
f32/f64, bool, str, `[]u8`/Vec, именованный тип по имени). **Работа = точечное расширение
таблицы родов fn-типами** (структурное совпадение `fn(A)->B` с `fn(A)->B`) + D55-амендмент.
Это ЯЗЫК-меняющее → отдельный под-план/амендмент, ДО миграции 25 файлов.

**Что проверить пробой (Ф.0):** (1) голый fn-тип в поле `value`-record внутри `[]Route`;
(2) не держится ли на newtype что-то ещё (метод `@handle`, будущие `#impl`); (3) как это
взаимодействует с арность-перегрузками регистрации (§5) и с middleware (`fn(Handler) -> Handler`
станет `fn(fn(..)->..) -> fn(..)->..` — читаемость может ПОСТРАДАТЬ, тогда newtype оправдан
как имя типа, а сносить надо только `handler_fn`).
**Ценность:** цель «минимум кода» (222 §0в) + чинит часть «двойной двери регистрации» из
[research §3](../research/http-frameworks-gap.md).

**АКТУАЛЬНЫЙ ОБЪЁМ (инвентарь 2026-07-23 — с момента написания пункта вырос ВТРОЕ, потому что
222.3/222.4/222.12/222.13 УЖЕ РЕАЛИЗОВАНЫ параллельными волнами):** `handler_fn` — **22 сайта
вне тестов + 14 тест-файлов**, всего 25 файлов:
`server/{server,extract,auth,middleware}.nv` · `middleware/{cors,compress,log,ratelimit}.nv` ·
`static.nv` · `servernet/rt/{handle_connection_smoke,streaming_smoke}.nv` + пиры-тесты.
**Следствие для исполнителя:** это уже не «поправить конструктор», а сквозная миграция —
делать ОДНОЙ волной (греп `handler_fn` = 0 в приёмке), иначе половинчатое состояние с двумя
формами. Порядок: сперва проба §5а (решить исход а/б), затем миграция.
