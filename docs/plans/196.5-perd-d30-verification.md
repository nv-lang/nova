## 0. TL;DR

- **Q5-класс (`resolve_result_option_ret`/`resolve_result_te`) остаётся Tier-2 в СВОЁМ прежнем смысле** —
  обе точки вызова `resolve_result_option_ret` (`B06a_method_overload_sentinel_mono` ~47988,
  `B10j_generic_fn_mono_resolve` ~48802) по-прежнему живут ВНУТРИ замороженной зоны волны-1
  (`infer_call_ret_c`, 46293-48883) и по-прежнему строят `subst` РУЧНОЙ inline-унификацией
  (`infer_type_param_binding`/`infer_type_param_binding_from_ref`), НЕ читая `node_substs` вовсе —
  код этих двух арм не тронут волной 196.5 (что и ожидалось: §7 плана 196.5 явно исключает
  замороженную зону из Stage-A/B).
- **НО soседний слой (196.5 Stage-A/B4/B5) РЕАЛЬНО заработал** для смежных потребителей ВНЕ зоны:
  `resolve_mono_type_args_ch` (propose-then-verify, Stage-B1) и особенно **`resolve_method_level_subst`
  (ИСТИННОЕ channel-first усыновление на `complete`-хите, БЕЗ verify-гейта — Stage-B, не B1)** —
  эмпирически подтверждено трейсом `NOVA_NODE_SUBSTS_TRACE` на всех 6 целевых фикстур: канал
  ПОПУЛЯРНО пишется и читается для generic free-fn `Result[T,E]`/`Option[T]` через turbofish
  (`producer=A`/`producer=D-freefn-turbofish` → `consumer=mono_type_args hit`) и для builtin
  `Option.ok_or[E]` DeclaredBody-диспетча (`consumer=resolve_method_level_subst … hit`).
- **Ключевая находка:** `resolve_result_option_ret` сама остаётся ПОЛНОСТЬЮ легаси (ни разу не читает
  `node_substs`) — Q5-структурный блокер (нет `ExprId` у declared-return `TypeRef` каллиси, §«СТРУКТУРНАЯ

  `resolve_result_option_ret` — см. §3), теперь либо channel-verified, либо channel-adopted — то есть
  ЧАСТЬ ВХОДНЫХ ДАННЫХ Q5-класса уже идёт через канал, даже когда сама точка сборки Result/Option

- **Орфанный артефакт найден:** `spec_tests/conformance/d30_result_option_ret_generic.nv` (матрица
  покрытия Q5, упомянутая в 196.3 §«★★ СТРУКТУРНАЯ НАХОДКА» и в 196.5 §8 п.2) **физически отсутствует

## 1. Метод

- Debug-сборка `compiler-codegen` (`nova-codegen.exe`, `cargo build` из `compiler-codegen/`) +
  `nova-cli` (`nova.exe`, для гейта). `NOVA_GC_LIB_DIR`/`NOVA_GC_INCLUDE_DIR` → main-репо
  (`d:/Sources/nv-lang/nova/compiler-codegen/vcpkg_installed/...`) — у `nova-199` пустой
  `vcpkg_installed/` (см. `project-worktree-nova-test-setup`).
- **`nova-codegen compile <file> -o out.c`** (без запуска) даёт ЧИСТЫЙ, малый трейс (только реально
  ДОСТИЖИМОЕ для конкретного файла), но **НЕ инжектит prelude-функции, определённые в `.nv`** (`sequence`/
  `partition`/`str.to_int()` — упало `undefined identifier`/`E_UNKNOWN_METHOD`), хотя языковые intrinsics
  (`Ok`/`Err`/`Some`/`None`) резолвятся. Похоже на пробел в `cmd_compile`, не обновлённый под Plan 195
  (`std/` → `std/src/`, влит СЕГОДНЯ, 2026-07-13) — используется только для файлов без prelude-зависимых
  вызовов (d30_try_op_unwrap_pair дал чистый образец на 4 ICR-бакета / 0 NODE_SUBSTS).
- **`nova-codegen test-build <file>`** — рабочий путь для всех остальных (полный prelude/manifest,
  компилирует+линкует+запускает). Компилирует ВЕСЬ транзитивный std/prelude (не только целевой файл) —
  трейс глобален по процессу (`icr_trace`/`trace_mlrfs` — `OnceLock<HashSet>`, first-hit-only,
  ОБЩИЙ на весь процесс), поэтому **бакет-присутствие НЕ дискриминирует файлы** (все 6 фикстур дают ОДИН
  и тот же набор из 41 ICR-бакета — это бакеты, достижимые ГДЕ УГОДНО в std/prelude, не специфично файлу).
  Файл-специфичный сигнал — **только** строки `NODE_SUBSTS`, отфильтрованные по `callee=<имя функции
  фикстуры>` / `ctx=<Type>.<method>` (оба поля несут имя из AST, не привязаны к файлу напрямую, но
  однозначно матчатся на объявления фикстуры по имени).
- **ЛОВУШКА (нашёл эмпирически):** `spec_tests/conformance/` — ОДИН folder-CU (все `.nv` там = один
  модуль `spec_tests.conformance`). `test-build` одного файла из этой папки **фактически компилирует ВСЮ
  папку** (подтверждено: положил туда восстановленный `d30_result_option_ret_generic.nv` → ВСЕ 4
  следующих `test-build`-запуска других d30/d85-фикстур упали с ОДНИМ и тем же CC-FAIL (`Nova_T*`/`nova_str`
  несовместимость) — убрал файл → все вернулись в PASS). Для изоляции орфанного файла использовал
  `--rt-dir`/`--cg-include` на путь ВНЕ `spec_tests/conformance` (в scratchpad) — работает (repo-root
  резолвится от `cwd`, не от пути файла).
- **RUN-FAIL vs трейс:** первая попытка (test-build d30 с обоими трейсами) дала RUN-FAIL при ОДНОВРЕМЕННОМ
  фоновом запуске нескольких параллельных сборок (контеншн CPU) — повтор БЕЗ конкурентной нагрузки дал
  чистый PASS с теми же трейс-переменными → это НЕ баг трейса (изолированно `ICR only`/`NODE_SUBSTS only`/
  `оба вместе` все дали PASS без конкуренции). d408/d325 RUN-FAIL — ОТДЕЛЬНЫЙ, воспроизводимый И БЕЗ
  трейса, И без конкурентной нагрузки (см. TL;DR) — не тот же эффект.
- Трейс включён строго как указано: `NOVA_TRACE_ICR=1` + `NOVA_NODE_SUBSTS_TRACE=1`, debug-сборка.

## 4. Почему `resolve_result_option_ret` НЕ подключена к `node_substs` (код, не гипотеза)

Прочитано по коду (`emit_c.rs`, оба caller'а):

- **`B06a_method_overload_sentinel_mono`** (~47987): `subst_opt` строится из `self.resolve_mono_type_args(&fn_decl, &turbofish_args, args)` — **ЛЕГАСИ-функция напрямую** (`emit_c.rs:18978`), НЕ `resolve_mono_type_args_ch` (`19407`). Канал не участвует вовсе на этом сайте.
- **`B10j_generic_fn_mono_resolve`** (~48760-48802): `subst` строится ИНЛАЙН через `infer_type_param_binding`/`infer_type_param_binding_from_ref` (Source 2f, «infer-twin of the emit-side source») — третий, отдельный, рукописный инференс-движок (в духе «three hand-duplicated inference engines», Q10), НЕ вызывающий ни `resolve_mono_type_args`, ни `_ch`-обёртку.

Оба caller'а — ВНУТРИ замороженной зоны волны-1 (46293-48883), что 196.5 §7/§9 явно исключает из Stage-A/B
(«НЕ трогаем замороженную зону волны-1… флипаются ТОЛЬКО когда волна-1 освободит зону»). Это ТОЧНО
соответствует диагнозу оригинального (орфанного) коммита `4d9fc2298`: «оба caller'а живут внутри 46293-48883,
этому окну редактировать запрещено». **196.5 Stage-A..B5 НЕ меняла эту границу и не могла** — она флипнула
ТРИ ДРУГИХ, вне-зонных консьюмера (`resolve_mono_type_args_ch`, `resolve_method_level_subst`,
`rt_slots_from_call`), которые кормят РАЗНЫЕ call-сайты (mono-манглинг метод-инстансов, DeclaredBody-диспетч
builtin Option/Result), НЕ те два caller'а, что кормят `resolve_result_option_ret`. Поэтому наблюдение «канал
популярно HIT для d30_ror_make/sequence/partition/d325_forward» — ПРАВДА на уровне `resolve_mono_type_args_ch`
(верификация), но эта верификация НЕ протекает в `resolve_result_option_ret`, потому что B06a/B10j её не
вызывают — они держат СВОЙ собственный, отдельный, легаси `subst`.

**Вывод: Q5-класс (`resolve_result_option_ret`/`resolve_result_te`) остаётся структурно Tier-2 РОВНО по
причине, зафиксированной в 196.5 §8 п.4/§9 «frozen-zone связанность» — не по недостатку самого канала.**
Канал технически ГОТОВ (Stage-A/B4 продюсеры пишут его для ровно этих же call-сайтов — см. `producer=A`/
`producer=D-freefn-turbofish` в трейсе), но два единственных потребителя `resolve_result_option_ret` сидят в
зоне, которую 196.5 намеренно не трогает. Разблокировка требует **либо** волны-1 освободить зону (Stage-D

эксклюзив, как было сделано для отдельных Path-форм в 196.2).

### 3.2 CC-FAIL репро (closure-return-peek подкласс, `d30_ror_from_closure`)

Файл (восстановлен из `4d9fc2298`), функция:
```
fn d30_ror_from_closure[T](tag int, f fn() -> T, err_msg str) -> Result[T, D30RorErr] { ... }
...
ro r = d30_ror_from_closure(true, || 7, "boom")
```
Генерируемый C (`nova_lambda_0_body`) объявлен с эрайзд-возвратом `Nova_T*` (шаблон generic-closure-параметра),
тело — `return ((nova_int)7LL);` → clang: `returning 'const nova_str' from a function with incompatible result
type 'Nova_T *'` (для другого closure-кейса в том же файле) и `returning 'int' from … 'nova_str'` (третий
кейс). Три отдельных ошибки компиляции C — весь файл `CC-FAIL`. Трейс подтверждает: `node_substs` дал
`fallback=miss` для этих ДВУХ call_id (`consumer=mono_type_args`) — closure-return-based T НЕ материализуется
ни продюсером A (нет arg типа T), ни B4-турбофиш-продюсером (нет явного turbofish). Это ОЖИДАЕМЫЙ канал-miss
(§7 196.5 — erased/непокрытый источник), НО легаси-путь, который ДОЛЖЕН его закрыть (closure-return peek,
Source 2 в `resolve_mono_type_args`), в ТЕКУЩЕМ дереве для ЭТОЙ конкретной комбинации (B10j inline-подстановка
+ closure-lambda C-сигнатура) codegen'ит erased `Nova_T*` вместо конкретного лоуэринга — воспроизводимый,
детерминированный CC-FAIL (не флак — 2/2 повторных прогона идентичны). **Не мой регион для фикса** — фиксирую
как находку для separate волны (вероятно, продолжение W1/Q5 расследования, а не 196.5-канала — сам канал тут
корректно MISS-нул, легаси-фоллбэк неисправен).
