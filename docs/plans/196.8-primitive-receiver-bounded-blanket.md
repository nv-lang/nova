# 196.8 — Bounded-бланкет на примитивном ресивере (одно окно для D310 type-set bound)

**Родитель:** [196 — одно окно правды](196-one-truth-closeout.md) (трекер-closeout).
**Статус:** ✅ ЗАКРЫТ 2026-07-16 (ветка `p196-8-dispatch`, worktree `nova-p196-8`; в main вливает оркестратор — `emit_c.rs` конкурентно правится).
**Модель:** sonnet.

## Проблема (маркер `[M-primitive-receiver-bounded-blanket-dispatch]`, P1)

`i64.checked_add(b)` (примитивный ресивер) в CU, где рядом ЕСТЬ concrete
`Duration @checked_add`, МИС-ДИСПАТЧИЛСЯ в Duration-метод → CC-FAIL
`passing 'int64_t' to parameter of incompatible type 'NovaValue_Duration'` +
`NovaOpt_int64_t` vs `NovaOpt_NovaValue_Duration`. `@checked_add` = BOUNDED-
бланкет `fn[T Ints] T @checked_add(rhs T) -> Option[T]`
(`std/src/prelude/protocols.nv:697`); чекер резолвит вызов в i64-инстанс
бланкета, codegen перевыбирал по ИМЕНИ (name-keyed фолбэк `method_receivers`,
last-wins) → брал чужой Duration. Репро: Пункт 10/200 заменил
`checked_add_i64(a,b)` → `a.checked_add(b)` в `duration.nv`.

Семейство D164 (106ae7207, unconstrained bare-`fn[T]` бланкет на примитиве,
гард) / 196.7 (bf997c0b6, `[]u8`/Vec-фасад + same-name concrete, канал
`resolved_callees`) — но НЕ покрытый случай: BOUNDED-бланкет (`[T Ints]`,
непустые bounds) + примитивный ресивер + concrete-коллизия.

## Root cause (двойной пробел, `emit_c.rs`, Plan 164 Ф.3 guard, ~37744-37888)

Место: `emit_c.rs`, блок «Plan 164 Ф.3: protocol-aware blanket dispatch»
(до правки — строки ~37730-37888; после правки сдвинуты на актуальные,
диф — коммит).

1. **`recv_is_candidate`** (было ~37780): примитив-ресивер признавался
   кандидатом на blanket-dispatch ТОЛЬКО через эскейп-хэтч
   `has_unconstrained_blanket` — булев флаг, истинный ТОЛЬКО когда у метода
   есть бланкет с ПУСТЫМ bound-листом (`g.bounds.is_empty()`). BOUNDED
   бланкет (`fn[T Ints] T @checked_add`, bound = `Ints`, непустой) никогда
   не включал этот флаг → примитивный ресивер (`int64_t`, `nova_int`, …)
   вообще НЕ рассматривался как кандидат, гейт падал сразу.
2. **`protocols_match`** (было ~37799-37817): для непустого bound-листа
   проверял ТОЛЬКО `#impl(Protocol)`-опт-ин через `self.type_impl_protocols`
   (популяция — `t.impl_protocols` из `Item::Type` деклараций, т.е. только
   НОМИНАЛЬНЫЕ типы с явным `#impl(...)`). D310 type-set bound (`Ints` —
   `type Ints set i8 | i16 | i32 | i64 | int | u8 | u16 | u32 | u64 | uint`,
   `std/src/prelude/protocols.nv:672`, `TypeDeclKind::TypeSet`) — СОВСЕМ
   ДРУГОЙ механизм членства (§17057-17206 `types/mod.rs`
   `check_generic_bound_declarations`: type-set — валидный bound, membership
   проверяется чекером `BoundCtx::check_satisfaction`, НЕ через
   `type_impl_protocols`). `type_impl_protocols` НИКОГДА не содержит записи
   для type-set-члена — ни для примитива (примитивы не получают `#impl`),
   ни в принципе (type-set membership ≠ protocol impl). Итог: **любой**
   бланкет с type-set bound не матчился ВООБЩЕ НИ ДЛЯ КАКОГО ресивера через
   этот гард (не только примитивного) — гейт (1) просто скрывал это для
   примитивов раньше, чем до (2) доходило дело.

Оба пробела совместно объясняют мис-диспатч: гейт (1) не пускал примитив
дальше; даже если бы пустил — гейт (2) всё равно вернул бы `false`.

## Фикс (одно окно — читаем факт D310-декларации, НЕ name-guard)

Новое поле `type_set_members: HashMap<String, Vec<String>>` на `Codegen`
(рядом с `type_impl_protocols`), популяция — параллельный проход по
`module.items` (там же, где популяция `type_impl_protocols`), собирающий
`TypeDeclKind::TypeSet(members)` → `{ set_name: [member_bare_names] }`
(bare-имя через `TypeRef::Named { path, .. } → path.last()`).

- **`recv_is_candidate`**: добавлен `has_typeset_blanket_for_primitive` —
  истинный, когда у метода есть бланкет, чей receiver-bound — ЕДИНСТВЕННЫЙ
  type-set (`self.type_set_members.get(bound_name)`), И каноническое
  Nova-имя примитива-ресивера (`Self::debt_nova_type_name_from_c(recv_base)`
  — УЖЕ существующий helper, `emit_c.rs:47959`, ранее использовался только
  для `NovaValue_`/`Nova_`-strip и числовых C-алиасов) — ЧЛЕН этого
  type-set. `recv_is_candidate` теперь: `!recv_is_primitive ||
  has_unconstrained_blanket || has_typeset_blanket_for_primitive`.
  (Заодно `recv_is_primitive`'s match-список расширен sized-int C-типами
  — `int8_t..int64_t`/`uint8_t..uint64_t`/`nova_byte`/`nova_uint` — они
  раньше не считались «примитивом» этим гардом вообще, что для i64
  СЛУЧАЙНО обходило гейт (1), но не (2); явное перечисление делает
  инвариант читаемым и не полагается на эту случайность.)
- **`protocols_match`**: для непустого bound первым делом проверяет
  `self.type_set_members.get(proto_name)` — если bound есть type-set,
  membership по каноническому имени ресивера решает `protocols_match`
  НАПРЯМУЮ (`members.iter().any(|m| m == recv_canon_name)`); иначе —
  старая ветка `type_impl_protocols` (protocol opt-in) без изменений.

Один источник данных (`type_set_members`) читается в ОБОИХ местах —
никакого нового name-keyed фолбэка; расширение факта чекера (D310-
декларация уже часть чекнутой программы) до codegen, аналогично тому, как
196.7 расширил `resolved_callees`-канал.

## Найдено попутно (ВНЕ объёма — НЕ фикшу здесь)

Дисп-фикс убрал CC-FAIL, но обнажил **отдельный, ранее замаскированный** баг:
`duration` теперь `RUN-FAIL` на тесте `"Ф.1c/D317: Duration saturating_*
clamps to ±MAX (no wrap)"` (`duration.nv:1276`). Root — `sat_add_i64`
(`duration.nv:378`) зовёт `r.clamp(lo, hi)` на `i64`-значении, pattern-bound
из `match a.checked_add(b) { Some(r) => … }`; `@clamp` объявлен ТОЛЬКО для
`int`/`f64` (`std/src/runtime/defaults.nv:180,182`) — ни i64-оверлоада, ни
бланкета. Codegen молча мис-диспатчит в `Nova_f64_method_clamp` (implicit
int64_t↔double на границе C-вызова — оба скалярны, компилятор C НЕ ругается,
но f64-мантисса режет точность на i64-крайних значениях типа `i64.MIN`) →
неверное число, НЕ CC-FAIL. Изолированный репро подтвердил: чекер
**корректно** даёт `E_UNKNOWN_METHOD` для голого `ro r i64 = …; r.clamp(...)`,
но НЕ флагает то же самое, когда `r` — pattern-bound из `Option[T]`-
деструктуризации бланкетного возврата — отдельный чекер-side пробел
(родственный «receiver-inference gap», который 196.7 отметил для codegen).
Залогировано как новый P1-маркер `[M-i64-clamp-primitive-collision-dispatch]`
(`docs/plans/backlog-followups.md`) — своё окно (codegen + checker), НЕ
трогал в рамках 196.8 (другая форма коллизии: concrete-vs-concrete без
бланкета, а не bounded-blanket-vs-concrete).
