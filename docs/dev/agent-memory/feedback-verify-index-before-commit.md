Перед `git commit` после `git add <specific files>` обязательно запускать
`git diff --cached --stat` (или `git status`) для проверки **полного**
содержимого индекса, не только своих файлов.

**Why:** в session 2026-05-30 я сделал `git add` трёх своих файлов для
коммита rename Plan 111→110. В индексе были pre-staged 9 deletions
nv_tests/plan100_{5,7}/*.nv от другой сессии (или от ручного действия
пользователя). Git автоматически включает все already-staged изменения
в коммит. В результате коммит 33b4ad22cb7 содержал не 3, а 12 files
changed — 9 случайных удалений рабочих фикстур закрытых планов. Пришлось
делать второй коммит 437402978da для restore.

**Why (2): same-file concurrent edits — 2026-06-14.** Коммит 9e1b1021 (backlog-маркер
`[M-fiber-stack-lazy-decommit]`) затащил правки соседней сессии Plan 153.x в **ТОМ ЖЕ**
файле `backlog-followups.md` (маркеры 153.1/138.2). `git add <file>` стейджит **весь**
файл целиком, включая чужие unstaged-хунки в этом же файле — file-specific add НЕ спасает,
если другой агент редактирует тот же файл. Усугубил тем, что склеил `add && diff --cached
--stat && commit` в ОДНУ Bash-команду: увидел «17/6» в выводе, но `&&` уже выполнил commit.
Запушено в 2 remote → не переписывал (хуже с конкурентными сессиями); контент чужой
сохранён, не потерян, просто под моим коммитом.

**Why (3): split-commit — 2026-07-20.** Обратная сторона той же проверки: в f32-волне правил
3 файла (string_builder.nv + fmt_buf.nv + nova_rt.h), закоммитил 2 — `diff --cached --stat`
ВЫПОЛНИЛ, но смотрел только «нет ли чужого», не сверил «есть ли ВСЕ свои». Определения уехали
в dirty, использование — в main → `undefined identifier` каскадом уронил весь conformance
мега-CU; чужой агент потратил разведку на диагноз моего недосмотра.

**How to apply:**
- Сверка staged-стата — В ОБЕ СТОРОНЫ против ЯВНОГО перечня файлов волны: (а) нет чужого,
  (б) есть ВСЕ свои. Использование и определение одной фичи — всегда в одном коммите.
- После push нового имени — мгновенный смок `git grep <имя> HEAD -- <файл-определения>`
  ловит split сразу.
- Каждый раз перед `git commit` (даже после специфичного `git add file1 file2`)
  → `git diff --cached --stat` для проверки что в индексе только то что
  ожидается
- **НЕ склеивать `add && diff --cached && commit` в одну команду** — `&&` закоммитит
  раньше, чем ты посмотришь на diff. Проверку индекса делать ОТДЕЛЬНЫМ шагом и реально
  ОСТАНОВИТЬСЯ, если staged больше ожидаемого (как «17/6» вместо «+1 строка»)
- Если файл может редактироваться **соседней сессией** (shared working tree) — стейджить
  **хунками**: `git add -p <file>` (выбрать только свои), а не `git add <file>` целиком.
  File-specific add защищает от чужих ДРУГИХ файлов, но НЕ от чужих хунков в том же файле
- Если в индексе видны unexpected staged changes — НЕ коммитить, разбираться
  что это (`git diff --cached -- <unexpected_path>`) и согласовать с
  пользователем перед действиями
- Особенно критично в multi-agent контексте [[feedback-isolated-worktree]]
  где параллельные агенты могут оставлять staged-изменения в shared индексе
- Связано с [[feedback_git_add_specific]] — указание конкретных файлов
  снижает blast radius, но не страхует от pre-staged changes других сессий
  ни от чужих хунков в том же файле
