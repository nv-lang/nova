Владелец (2026-08-01, по big-pickle shutdown-окну с 7ч нуля кода): «не надо
столько ждать, 1 час работы без толку — останавливай». **УЖЕСТОЧЕНО
владельцем 2026-08-01 (после 8ч-простоя comments2): «если полчаса молчит —
это не дело» → порог 30 минут.**

enforcement: МАШИННОЕ в рамках сессии — cron-будильник каждые ~28 минут
(CronCreate) принудительно вызывает проверку независимо от занятости
интегратора; ритуал «проверю когда освобожусь» ПРОВАЛЕН дважды (7ч shutdown,
8ч comments2) и запрещён как единственный механизм. В НАЧАЛЕ КАЖДОЙ НОВОЙ
СЕССИИ с живыми окнами — первым действием пересоздать cron (session-only,
умирает с сессией). Проверка: `git log -1 --format=%ar` И mtime dirty-файлов;
оба старше 30 минут → kill/TaskStop + перезапуск.

**ПРЕЦЕДЕНТ 2026-08-03 (третий провал ритуала):** две opencode-волны 241
(перевод спеки, актуализация paradigm) встали молча на 2,5-3,5 часа —
обнаружено ТОЛЬКО по вопросу владельца «завис?». Будильник не был взведён при
запуске, ждал по отменённому порогу «час». Правило: будильник ставится ТЕМ ЖЕ
ходом, что и запуск фонового агента, иначе запуск не считается сделанным.
Причина зависания (тип «г»): агент ушёл вдлинную разведку (чтение D-блоков,
изучение стиля) и не сделал ни одного коммита — лечение: перезапуск с явным
«НАЧНИ СРАЗУ С РАБОТЫ, первым действием сделай мелкий файл и немедленно
закоммить+запушь», разведку запретить.

**Why:** вялые окна съедают wall-clock всей воронки; big-pickle склонен
молча вязнуть (serve, shutdown, полярис-хвост, comments2 — прецеденты).

**How to apply (УТОЧНЕНО владельцем 2026-08-01: не «просто перезапустить» —
СНАЧАЛА РАЗОБРАТЬСЯ В ПРИЧИНЕ):** при стопе обязательная диагностика ДО
перезапуска: хвост вывода/сессии агента, PROGRESS/чекпоинт, какие файлы
трогал последними, git-состояние. Классифицировать причину и лечить её:
(а) авто-отказ прав/путей → чинить конфиг/бриф (самодостаточность);
(б) сетевой обрыв → реанимация с контекстом (SendMessage «продолжай с git»);
(в) модель вязнет на сложности (big-pickle на серверном/архитектурном) →
СМЕНА МОДЕЛИ на sonnet; (г) бриф плох (нет каданса, неясная задача,
слишком крупные шаги) → ПЕРЕПИСАТЬ ПРОМПТ (мельче шаги, явный каданс,
образцы); (д) процесс убит извне (перезагрузка) → перезапуск как был;
(е) СЕРВЕРНЫЙ RATE-LIMIT провайдера opencode (владелец 2026-08-01) —
симптом: процесс жив, но долго ни вывода, ни tool-вызовов; лечение:
пауза-бэкофф перед перезапуском (15-30 мин), НЕ держать несколько
big-pickle-окон одновременно (совокупный лимит), при срочной задаче —
эскалация на sonnet вместо ожидания.
