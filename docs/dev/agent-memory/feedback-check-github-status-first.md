enforcement: немашинное — порядок диагностики в голове агента; машинная половина уже есть в репе (scripts/guards/check-ci-status.sh: STALE при нуле прогонов на хеше + pre-push-хук)

Когда CI/деплой GitHub ведёт себя странно (нет раннеров, «job was not acquired
by Runner», 500/502 на API, запуски висят в очереди, push не порождает прогонов)
— ПЕРВЫМ действием смотреть https://githubstatus.com, и только потом внутренние
гипотезы (права, настройки, skip-маркеры, биллинг).

**Why:** инцидент 2026-08-06 (Actions = major outage, Critical): я трижды
перезапускал деплой www и гонял ретраи, интегратор перебрал полдюжины внутренних
гипотез — а ответ был на статус-странице. Урок сформулирован интегратором для
обоих: «сначала внешнее, потом своё».

**How to apply:**
- симптом из списка выше → curl/открыть githubstatus.com; если инцидент —
  НЕ чинить и НЕ перезапускать по кругу: очередь разберётся сама после закрытия;
- во время инцидента ручной workflow_dispatch обычно проходит, webhook-триггеры
  (push/PR) отваливаются — срочный выкат делать ручным диспатчем;
- зелёный/красный CI в это время — не сигнал: прогона может просто не быть;
  сверяться с [[project-ci-monitoring-protocol]] и check-ci-status.sh.
