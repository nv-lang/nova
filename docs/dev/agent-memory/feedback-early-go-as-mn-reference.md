enforcement: машинное частично — раздел 0 в `docs/dev/mn-coding-conventions.md`
(конвенция нормативна, отклонение только по согласованию с владельцем), плюс
обязательный раздел отчёта «какие инварианты есть у референса и нет у нас» в
каждом брифе M:N-окна; отсутствие раздела = работа неполная и не принимается.
Полностью машинной проверки быть не может — сверка архитектуры это суждение.

**Правило владельца 2026-08-07, дословно:** «Go как референс для M:N уже давал
положительные фиксы в прошлом — нужно использовать».

**Что это значит на практике.** Перед проектированием собственного решения задачи
планировщика, парковки/пробуждения, взаимодействия с GC или завершения процесса
при живых фибрах — СНАЧАЛА сверяйся с ранним Go, чей рантайм был написан на C и
решал ровно этот класс задач в тех же условиях (M:N, сборщик мусора,
переключение стеков).

Берём **инварианты, а не код** (лицензия). Вопросы, на которые там уже есть
проверенный ответ:
* кто и когда сообщает сборщику границы стека при переходе между стеком фибра и
  системным;
* как гасятся оставшиеся фибры при завершении процесса и в каком порядке
  относительно закрытия цикла событий;
* что считается точкой безопасной остановки и кто гарантирует согласованность
  состояния;
* как разделены обязанности планировщика и драйвера ввода-вывода при парковке.

**Прецедент, породивший правило (№418, 2026-08-07):** два корня SIGSEGV на Linux
оказались ровно из этого списка — осушение осиротевших фибров шло через `atexit`,
то есть ПОСЛЕ закрытия цикла событий, по закэшированному указателю; и установка
границы главного стека для GC затиралась вторым вызывающим, чей комментарий «мы
гарантированно на нативном стеке» стал ложным после того, как тело `main` стало
настоящим фибром. Оба — классические места, где у референса инвариант проговорён
явно.

**Второе обязательное условие для M:N-работ (тот же разговор):**
производительность критична, целевой ориентир — **паритет с эталоном или лучше**.
Регресс скорости НЕ является приемлемой платой за стабильность; замедлил —
доложи цифру и предложи альтернативу, не отгружай молча. Методика замера готова:
Ф.0 плана 244 (`docs/plans/wip/bench-p244/*.nv`, три сценария), эталонные числа —
в `PROGRESS-p244.md`.

**Аналогия по устройству:** для системы типов, резолва и мономорфизации таким же
эталоном служит `rustc` — см. [[feedback-rustc-as-reference]]. Для M:N — ранний Go.
