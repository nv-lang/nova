**ГЛАВНОЕ ПРАВИЛО, ВЫВЕДЕННОЕ ЦЕНОЙ ЭТОГО СЛУЧАЯ: диагностику начинать
СНАРУЖИ.** Первый шаг — https://www.githubstatus.com/api/v2/summary.json (одна
секунда через WebFetch). 2026-08-06 я перебрал полдюжины внутренних гипотез —
настройки организации, состояние воркфлоу, skip-маркеры, check-suites, права,
биллинг, версию про «GitHub гасит автотриггеры за красноту» — и только потом
посмотрел статус-страницу. Там висел **Major Outage компонента Actions**
(инцидент с 15:22 UTC, воздействие Critical) с дословной формулировкой: «многие
события push и pull request не запускают новые workflow runs», плюс вторичное
воздействие на Pages. Все внутренние гипотезы были неверны; правильный порядок —
внешнее, потом своё.

**Симптом:** пуши в main проходят, GitHub их видит (`PushEvent` в
`repos/<org>/<repo>/events`), но прогонов НЕТ вовсе. Локальный гейт зелёный —
кажется, что всё хорошо. Молчащий гейт опаснее красного.

**Решающий признак — НОЛЬ check-suites:**
`gh api repos/<org>/<repo>/commits/<sha>/check-suites --jq '.total_count'` → `0`.
Если suites создаются и падают — это обычная краснота. Ноль suites означает,
что событие до движка Actions не дошло: причина НЕ в YAML, НЕ в тестах.

**Порядок диагностики (5 минут, всё через `gh`, снизу вверх по стоимости):**

1. `gh api repos/<org>/<repo> --jq '{private,archived,disabled}'` — репа жива.
2. `gh api repos/<org>/<repo>/actions/workflows --jq '.workflows[]|"\(.state) \(.name)"'`
   — все ли `active` (а не `disabled_inactivity`/`disabled_manually`).
3. `gh api repos/<org>/<repo>/commits/<sha>/check-suites` — тот самый ноль.
4. Skip-маркеры в сообщении head-коммита: `[skip ci]`, `[ci skip]`, `[no ci]`,
   `[skip actions]` — GitHub тихо не запускает прогон, следов не остаётся.
5. **РЕШАЮЩАЯ ПРОБА — ручной запуск:** `gh workflow run <wf>.yml --ref main`.
   Стартовал → бана нет, лимиты целы, раннеры доступны, сломан именно
   АВТОТРИГГЕР. Не стартовал → копать биллинг/приостановку аккаунта.

**Что проверено и НЕ подтвердилось 2026-08-06** (чтобы не копать заново):
бан за расход (публичная репа — минуты бесплатны), отключение Actions на
уровне организации (политика `Allow all actions`, все репозитории, standard
runners включены), `disabled`-состояние воркфлоу, skip-маркеры в коммитах.

**ОПРОВЕРГНУТАЯ гипотеза (оставлена как урок):** «GitHub гасит автотриггеры при
повторяющихся сбоях воркфлоу, оставляя `workflow_dispatch`». Выглядела стройно —
последний push-прогон упал, дальше тишина, ручной идёт мгновенно. Неверна:
письма от GitHub не было (владелец проверил), а причиной оказался глобальный
инцидент. Урок: стройность гипотезы не заменяет проверки внешнего статуса.

**Практический вывод:** организация может быть внутри enterprise (признак —
подсказки «Your enterprise has set a maximum limit» в настройках); политики
enterprise перекрывают организационные, смотреть и там.

**Механизм, поставленный после этого случая:**
`scripts/guards/check-ci-status.sh` (вердикты OK/RED/STALE/SKIP) шагом в
`gate.sh` + хук `scripts/githooks/pre-push`, который останавливает отправку в
main при красном ИЛИ молчащем CI. До него дыра держалась 24 слияния подряд
(реестр 221.1 №395), потому что проверка зависела от памяти интегратора.
