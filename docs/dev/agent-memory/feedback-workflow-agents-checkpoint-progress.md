Фоновые агенты в Workflow иногда падают на серверном rate-limit (сигнал от владельца 2026-07-02).

**Why:** упавший агент возвращает null → его работа теряется целиком, если он не сохранял промежуточный прогресс.

**How to apply:**
- В промпт каждого workflow-агента добавлять: «после каждого завершённого под-шага (сайт/кластер/файл) дописывай результат в checkpoint-файл `<scratchpad>/<run>/<label>.md` — при падении респаун продолжит с него».
- Батчи делать мелкими (агент = 3-5 под-задач, не 20) — меньше теряется при смерти.
- Использовать resumeFromRunId (завершённые агенты кэшируются; перед диагностикой пустых результатов читать journal.jsonl).
- Фильтровать null (`.filter(Boolean)`) и логировать, сколько агентов умерло — не выдавать частичный результат за полный (§ no silent caps).
- Также: агентам ЗАПРЕЩЁН git stash ([[feedback-worktree-shared-stash]]).

**ДОПОЛНЕНО 2026-07-07 (владелец повторил + практика сессии):** правило распространяется и на
одиночных Agent-фоновиков, не только Workflow: (1) в КАЖДОМ задании — «промежуточные коммиты
после каждого логического пункта» (агент http-props дважды оборвался БЕЗ коммитов и потерял
всю работу — с тех пор обязательный пункт шаблона); (2) МОНИТОРИНГ: при уведомлении failed —
немедленный SendMessage-резюм с контекстом «оцени git log/status, продолжай С МЕСТА, не
начинай заново» (сегодня так спасены: волна D410 после серверной ошибки, http-props ×2,
sweep ×2); (3) фантомные «stopped by user» — тоже класс обрыва: проверять живость давно
молчащих агентов пингом; (4) haiku-агентам ЯВНО писать «в main-репу не заходить вообще»
(двое сегодня переступили: самослияние hexquad, маркер-коммит ptails).
