Правя файл серией точечных замен (python replace / Edit), НЕ считать работу
законченной, пока файл не перечитан ЦЕЛИКОМ. Точечная правка обновляет одно
вхождение, а тот же фрагмент часто живёт в нескольких местах документа
(основная секция + примеры + раздел открытых вопросов).

**Why:** 2026-08-02, план 244: владелец трижды подряд ловил в одном файле
следы прежних редакций — `addr_of(v)` (форма ретрактирована планом 118.6),
`@0` вместо `@`, `ChanTx.null()` вместо `mut tx uninit ChanTx`. Каждый раз
правка вносилась в ОДНУ копию фрагмента, вторая оставалась старой. Владелец:
«так и не обновил?». Дороже самой правки обходится потеря доверия к
документу — исполнитель окна работает по плану буквально.

**How to apply:** после блока замен — `grep` по СНЯТОЙ форме (должно быть 0
вхождений) и чтение файла целиком перед коммитом. Для планов, которые пойдут
в работу агенту, чтение целиком обязательно: план — исполняемый документ.
Родственное: [[feedback-read-files-efficiently]], [[feedback-one-pass-fix]],
[[feedback-no-done-claims-on-documents]].

enforcement: немашинное — правило о МОЁМ порядке работы с файлом, а не о
содержимом репозитория; машинный страж не может отличить «правка забыта» от
«так задумано». Частичная механизация возможна и применяется точечно: при
снятии формы грепать снятую форму на 0 вхождений (как сделано для `addr_of`
и `.null()` в плане 244).
