Каждый компилятор-баг чинится в ЕДИНОМ канале чекера (resolved_types/resolved_callees/node_substs), а не добавлением веток/таблиц в легаси-слой emit_c. Это действующая конвенция (compiler-conventions.md §0 «checker must annotate» — легаси-паники сами её цитируют) + направление плана 196 (свод дублей разбора в одно место, легаси удаляется по NO-HIT).

**Why:** владелец дважды поднял 2026-07-25: «196 переделывает легаси с кучей дублей в единое место — одно окно» и «разве не было задачи чинить в рамках единого канала чекера?». Урок сессии: окна №78/№90/mvinfer я сам направил в легаси-реестры (`fn_param_sigs`/`fn_returns_fn_sig*`/`resolve_mono_type_args`) по прецеденту №53 — функционально зелёные, архитектурно долг (№94 консолидация). «Минимальный фикс дефекта» ≠ «правильное место фикса».

**How to apply:**
- В КАЖДЫЙ компилятор-бриф — обязательный пункт: «Фикс — в чекер-канал (§0/196): сначала проверь/заполни resolved_types|resolved_callees; emit_c читает канал; легаси-ветки НЕ добавлять; если после фикса легаси-бакет недостижим — пометить 196-NO-HIT-кандидатом; если канал неподъёмен в окно — стоп и доклад, не пилить легаси молча».
- Прецедент «прошлое окно чинило в легаси» — НЕ оправдание (№53 → №78 → №90 — так долг и вырос).
- При приёмке проверять НЕ только гейты, но и МЕСТО фикса (diff: types/mod.rs-канал vs emit_c-реестры).

Связано: [[feedback-rustc-as-reference]] (mono = фаза, не codegen-side-effect), [[feedback-zero-tolerance-bugs]], реестр №94 [M-fn-newtype-resolve-consolidation-196].
