enforcement: немашинное — выбор модели под задачу делает интегратор при
составлении брифа, автоматической проверки быть не может. Частичная страховка,
которая уже работает: результат дешёвой модели ОБЯЗАН проходить ревизию
интегратора перед записью в реестр (это и вскрыло сдвиг), а в брифе стоит
инструкция «сомневаешься — ставь A и пиши "требует ручной проверки"» — она
оставляет честный след, по которому ревизия находит ошибку.

**Граница применимости haiku, измеренная на живой задаче.**

Задача: 76 кодов ошибок есть в спеке и отсутствуют в компиляторе; разнести по
категориям A (настоящая дыра) / B (честно помечена отложенной) / C (реализована
под другим именем) / D (обрубок из примера).

Результат haiku на 12 кодах: **10 категории A**. Машинная перепроверка (поиск
кодов, у которых совпадают ≥2 значимых слова имени) — **5 из 10 сомнительны**;
две проверены вручную и оказались C: `E_FIELD_NOT_MUT` реализован как
`E_READONLY_FIELD`, `E_DUP_DEFINITION` присутствует голым сообщением.

**Почему так:** различение «дыра vs переименование» и ЕСТЬ суть задачи. Модель
не находит эквивалент под другим именем и по умолчанию пишет «дыра» — сдвиг
систематический, не случайный. Формально бриф выполнен: она искала по тексту
сообщения, просто не догадалась искать шире.

**Правило:** haiku — механика по списку, где ответ ИЗВЛЕКАЕТСЯ (собрать факты,
свести таблицу, прогнать по шаблону). Не давать haiku задачи, где ответ
ВЫВОДИТСЯ поиском эквивалента, синонима или переименования — там sonnet либо
машинное сопоставление плюс ревизия.

**Что сработало и стоит повторять:** чекпоинт-коммит после каждых 3 пунктов
(прогресс не потерян), явный запрет заходить в main-репу, `LC_ALL=C` в каждой
команде с grep.

**Второй урок того же дня:** предыдущее haiku-окно (триаж 4 расхождений
реестр/backlog) **зависло на 600 с без прогресса** и было снято сторожем. Для
haiku дробить задачу мельче и требовать чекпоинт чаще, чем кажется нужным.
