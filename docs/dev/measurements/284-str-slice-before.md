# Замер ДО правки — план 284, Ф.0 (`s[a..b]` через `str @index`)

**Кто и когда:** окно 274 (Карина), 2026-09-07, дерево `nova-p274` на ветке
`p274-novac`. **Зачем:** приёмка Ф.0 требует числа, а не впечатления: сколько
мест в эмиттере оракула обрабатывают Range-индекс по строке отдельно, сколько
носителей у каждой из четырёх форм среза, и какой C выпускался ДО правки.
Плана касается только ОРАКУЛ (`compiler-codegen`), `novac` тут не участвует.

## 1. Места в эмиттере, где строка идёт отдельно от общего пути

Файл эмиттера — `compiler-codegen/src/codegen/emit_c.rs` (67 680 строк).
Грепы (из корня дерева, дословно):

```sh
grep -c -E 'nova_str_slice|_to_end_|"nova_str"' compiler-codegen/src/codegen/emit_c.rs
grep -n -E 'obj_ty != "nova_str"|structural_len_field_ty' compiler-codegen/src/codegen/emit_c.rs
```

| что | число |
|---|---|
| упоминаний `nova_str_slice` / `_to_end_` / `"nova_str"` во всём эмиттере | 149 |
| из них в окрестности диспетчера Range-индекса (по чтению) | 3 узла: явное исключение строки перед структурным reroute, ветка открытого конца, ветка inclusive |

Ключевое место названо в самом коде (комментарий эмиттера, дословно):
исключение `obj_ty != "nova_str"` стоит ПЕРЕД `structural_len_field_ty`, то есть
строка выведена из общего структурного пути ПОИМЁННО, а не по отсутствию поля
`len`. Это и есть предмет плана: признак «умеет срез» решается двумя именами
типов и наличием поля, а не ролью.

## 2. Носители четырёх форм среза в дереве

Счёт скриптом `scratch/slice_carriers_284.py` по `std`, `spec_tests`,
`examples` (2688 файлов `.nv`); форма определяется по написанию индекса,
получатель — по объявлению имени в том же файле.

| получатель | `s[a..b]` | `s[a..]` | `s[..b]` | `s[a..=b]` |
|---|---|---|---|---|
| строка (по чтению) | 31 | 8 | 5 | 1 |
| вектор (по чтению) | 52 | 12 | 21 | 1 |
| **не решается чтением** | 79 | 42 | 27 | 5 |

Всего 284 места среза в 89 файлах. **Третья строка таблицы — честная, а не
ленивая:** тип получателя знает чекер, а не греп; `combined[0..22]` из
`insecure_demo_kdf.nv` или `@src[..sn]` из `vec_iter/core.nv` читаются
одинаково, а получатели у них разные. Для приёмки Ф.0 важно, что форм ЧЕТЫРЕ
и что строковых носителей не единицы, а сорок пять по нижней оценке; точное
разделение даст сам компилятор, когда Ф.1 переведёт диспетчер на роль —
тогда каждая форма, не удовлетворяющая роли, скажет об этом сама.

Примеры строковых носителей, которые Ф.1 переводит на роль:
`std/src/encoding/url.nv:130,148,159,208` (`s[..i]`, `s[i + 1..]`, пары
`(s[..i], s[i..])`), `std/src/encoding/json.nv:491,680,685,690,694`
(`@input[p..]`, `@input[hi_start..hi_start + 4]`).

## 3. Эталонный C корпуса

Снимок C всего `spec_tests/conformance` одним CU до правки — **не снят в этом
окне**: он требует машины, а слот в этот час принадлежал соседним окнам
(протокол окна машины, `feedback-machine-window-protocol-with-integrator`).
Снимается первым же шагом Ф.1 в одном окне с первой сборкой — иначе снимок
и правка окажутся из разных состояний дерева, и дифф перестанет быть уликой.
Команда записана здесь, чтобы её не пришлось выдумывать заново:

```sh
nova-cli/target/release/nova.exe test spec_tests --filter slice   # вердикт ДО
sh scratch/emit_corpus.sh target/284-c-before                     # C корпуса ДО
```

## 4. Вердикт прогона `nova test spec_tests --filter slice`

**Не снят в этом окне** — та же причина (машина). Строка вердикта дословно
ляжет сюда в окне Ф.1, рядом со снимком.

## 5. Что этот замер уже говорит о плане

- Форм четыре, и `s[a..=b]` — редчайшая (7 мест во всём дереве, из них
  строковая одна): фикстуры Ф.3 обязаны нести её отдельно, потому что корпус
  её почти не покрывает — тот же класс, что дыра с `else` в подплане 274.8
  (форма есть в языке, носителя под проверкой нет).
- Строка выведена из общего пути ПОИМЁННО, значит после Ф.1 удаление имени
  из условия — уже не «упрощение», а снятие носителя дефекта: пока имя стоит,
  любой новый тип со срезом наследует ту же развилку.
