# Реестр расхождений novac ↔ оракул

Контракт (план [274](../plans/274-novac-self-hosted-compiler.md) §10.3а; машинная
половина — `novac/divergences.allow`, судья — `check-novac-differential.sh` и
корпусный раннер `scripts/tools/novac-diff-corpus.sh`): каждая строка allow
обязана иметь здесь историю — что расходится, почему наше поведение верно, и
D-блок, если расхождение видимо как поведение языка. Каждая запись и каждый
прогон несут ревизию оракула и режим сборки novac (§10.3: иначе классификация
невоспроизводима через неделю). Пустой allow — здоровое состояние.

## Сознательные расхождения (зеркало allow)

Пока НЕТ ни одного: `novac/divergences.allow` пуст, дифф-страж на фикстурах и
корпусный раннер зелёные без исключений.


## Пробел подмножества: однострочная форма `match` (2026-08-17)

Спека даёт две формы разделения арм (`spec/syntax.ru.md:90, 104, 115`):
многострочную — только перенос строки, запятая в конце арма ЗАПРЕЩЕНА
(`E_MATCH_ARM_COMMA_MULTILINE`, D452/план 264), и однострочную — армы через
запятую: `ro s = match code { 200 => "ok", 404 => "not found" }`.

**novac разбирает только многострочную.** Проба 2026-08-17:
`ro r = match n { 1 => 10, _ => 2.5 }` — оракул принимает и печатает 2.5,
novac отвечает «outside the E1 subset: construct not in the MVP grammar».
Отказ честный и по форме правильный (подмножество уже языка, не шире), но
это дыра в покрытии спеки, а не решение: однострочная форма нормативна.

**Как нашлось.** Владелец поправил пример в моём отчёте — я записал армы в
одну строку без запятых, чего язык не допускает. Проба, поставленная чтобы
проверить поправку, показала, что ПРАВИЛЬНАЯ однострочная форма тоже не
проходит. Поправка к прозе вскрыла пробел в коде.

**Куда:** Э2, вместе с ростом грамматики подмножества по корпусу. Отдельного
дефекта нет — есть незакрытая форма.

## Ревизия формы эмиссии после амендмента §7.0 (2026-08-16)

Указание владельца: «где лучше иначе — обязаны иначе, с записью в реестр
расхождений» и «не забудь применить это на уже написанный код». Прошёл все
одиннадцать мест, где `emit_c` ссылается на форму оракула, и разделил их на
три группы. Это ревизия УЖЕ НАПИСАННОГО, а не план на будущее.

### А. Зеркалирование ОБЯЗАТЕЛЬНО — это ABI, а не чужое решение

| место | что зеркалим | почему обязано совпадать |
|---|---|---|
| `emit_c.nv:7-8` (шаблон оболочки) | набор хелперов std/рантайма из зонтичной пробы | символы линкуются; отсутствующий хелпер = ошибка линковки |
| `emit_c.nv:610` (строковые литералы) | форма `static const nova_str` | тип из `nova_rt.h`, поля `.ptr/.len` — ABI |
| `emit_c.nv:628` (мономорфные имена методов) | `Nova_str_method_*`, `Vec____nova_int_method_*` | это ИМЕНА СИМВОЛОВ std; разойдёмся — не слинкуется |
| `emit_c.nv:322` (теги std-сумм) | теги `Option` в написании оракула | значения из std, приходят чужими |
| `emit_c.nv:673` (f64-арифметика сырыми операторами) | без checked-хелперов | семантика языка: у float нет переполнения |

Здесь «идентично» остаётся навсегда, и это не копирование устройства.

### Б. Форма СВОБОДНА, и лучшая форма уже названа — ждёт своей волны

| место | нынешняя форма (оракульская) | как правильнее | почему не сделано сейчас |
|---|---|---|---|
| `emit_expr` Call/MethodCall | аргументы печатаются вложенными вызовами прямо в C | вынести каждый аргумент во временную В ИСХОДНОМ ПОРЯДКЕ (F65) | требует, чтобы эмиссия выражения ВОЗВРАЩАЛА текст, а не дописывала в общий буфер; проверяется только поведением, а смоуки заблокированы рассинхроном рантайма (см. ниже) |
| `emit_c.nv:509` (ctor записи) | tmp-переменная, потом присваивания полей | прямая инициализация без временной, где нет spread | косметика; в одной волне с F65, чтобы поведенческая проверка была одна |
| `emit_c.nv:297` (схема match) | scrutinee + result + флаг `matched` + цепочка if | цепочка `else if` без флага: флаг существует, потому что оракул не умеет иначе | та же волна; выход меняется, нужна поведенческая приёмка |

### В. Уже разошлись сознательно — и это правильно

| место | наше отличие | причина |
|---|---|---|
| имена пользовательских сущностей | `novac_user_*`, `NOVAC_TAG_*`, `novac_make_*` вместо оракульских | собственное пространство имён: эмиссия novac не может столкнуться с символом рантайма или std (П24, `mangle.nv`) |
| кортежи (когда войдут) | значение на стеке, не GC-указатель | решение владельца 2026-08-16, 274.1 |
| `println` неизвестного типа | `ice`, а не «печатать как int» | оракул молча печатает GC-указатель числом; наше поведение ПРАВЕЕ (F66) |
| порядок вычисления аргументов | novac откажет там, где не может гарантировать порядок | оракул нарушает собственную нормативную гарантию (F65); честный отказ лучше тихо неверного кода |

Строк в `novac/divergences.allow` по-прежнему НЕТ: группа В — это либо наше
собственное пространство имён (поведение не расходится), либо места, где
расхождение ещё не наблюдаемо на корпусе. Как только расхождение станет
видимым поведением — строка allow заводится той же волной.

### Почему группа Б не сделана этой волной

Смена формы эмиссии проверяется ТОЛЬКО поведением (побайтовое сравнение с
самим собой тут бесполезно — выход и должен измениться). Поведенческая
приёмка — смоуки против оракульского бинаря — сегодня заблокирована: шаблон
оболочки зовёт `nova_fiber_report_error_kinded` с тремя аргументами, а в
незакоммиченном `fibers.h` главного дерева сигнатура шире. Менять эмиссию,
не имея возможности проверить поведение, — ровно то, что этот проект не
делает. Волна Б идёт сразу после того, как интегратор запушит рантайм, а мы
перегенерируем шаблон и сдвинем `oracle-pin`.

## Предсказания Э2-а — внесены ДО кода (274 §7; 2026-08-14, пин c5a0bc425)

Расширение подмножества на basics целиком (strings → records → demo →
match_demo). Что ожидаю от дифф-гейта ЗАРАНЕЕ:

1. **match_demo.nv объявляет сумму старой формой** (`type Shape` + leading-`|`,
   без enum-маркера D406) — оракул на пине её ПРИНИМАЕТ (проверено корпусным

   оракулу на пине: парсер Э2 принимает эту форму. Если оракул ужесточит D406,
   дифф покраснеет — штатный сигнал «пин двигается, novac ужесточается той же
   волной». Язык здесь не меняю (правка формы корпуса — земля интегратора).
2. **№652 на basics не проявится**: файлы типо-корректны; ложных принятий
   оракула на них нет — контракт-совпадение будет честным.
3. **f64 в records/demo/match_demo**: печать чисел с плавающей точкой должна
   выйти байт-в-байт (формат печати — из оракульской эмиссии фикс-пойнтом,
   не из моих представлений о printf).
4. **Поведенческое число растёт только через смоук**: каждый новый файл
   подмножества входит в behavior-match исключительно побайтовым диффом
   stdout+exit — «собрался» не считается.

## Классы дефектов оракула — сводка для канала 196 (2026-08-17)

**Зачем этот раздел, если экземпляры уже перечислены ниже.** Вопрос владельца
2026-08-17: «для всех определён класс бага (группировать по общему корню)?
выставил приоритет? чтобы не было попыток фиксить конкретный баг — фиксить
надо класс дефекта через одно окно в рамках 196». Проверка показала, что
записи ниже — это список ЭКЗЕМПЛЯРОВ: у каждого свой маркер и своя история, а
общий корень не назван нигде. Три из шести живых носителей — один и тот же
корень, и чинить их по одному значит трижды заплатить за одно решение и
трижды не закрыть класс. Ниже — корни, приоритет и признак, по которому класс
считается закрытым; экземпляры остаются на своих местах как доказательства.

**Что означает приоритет.** P1 — молчаливая мискомпиляция (ответ неверен, C
валиден) ИЛИ блокирует Э2. P2 — обходится маркером, стоит времени, не
блокирует. P3 — качество диагностики и удобство.

| класс | корень | экземпляры | P | признак, что класс закрыт |
|---|---|---|---|---|
| **О-1. ## `%` на `f64` — ЗАКОНЕН, расхождение перевёрнуто (2026-08-17)

**Было записано наоборот.** Я записал расхождение «в сторону строгости»:
novac отвергает то, что оракул принимает и не может собрать. Интегратор
ответил и починил кодоген: **`%` на плавающих законен**, и запрещать его
нельзя — таблица приоритетов не ограничивает `%` по типам, D46 делает `@rem`
перегружаемым (значит операция мыслится общей), C и Rust её имеют, запрещает
только Go. Запрет сузил бы ЯЗЫК ради обхода дефекта КОДОГЕНА.

**Что теперь делает novac** (амендмент D46 (F), реестр №707): принимает `%`
на плавающих и лоуэрит через `fmod`. Знак остатка — от ДЕЛИМОГО (как в C и
Rust, не евклидов); ошибки деления на ноль здесь НЕТ — IEEE-754 даёт NaN, и
паника целых (D427) к плавающим не применяется, ровно как у `/`.
`f32 → fmodf` появится вместе с арифметикой на `f32` (сейчас операнды
подмножества — `int` и `f64`).

**Что этот же ответ вскрыл у МЕНЯ.** Предупреждение интегратора «у составного
присваивания ОТДЕЛЬНЫЙ путь эмиссии, я на этом попался» проверил у себя — и
попался тем же: `c_binary_form(op, false)` с жёстко зашитым `false`, поэтому
`f += 0.25` на `f64` эмитило `nova_int_checked_add` целочисленным хелпером.
C компилировался, а ОТВЕТ расходился с оракулом. Починено одним правилом
`is_call_form(op, is_float)` на оба пути (выражение и присваивание), тип
операнда читается из канала. Проверено поведением: `+= -= *= /=` на
плавающих совпадают с оракулом байт-в-байт.

## `[]int` и `Vec[int]` — ОДНО имя, но `check` оракула считает их двумя (замер 2026-08-21)

**Вопрос владельца:** «а `[]int` & `Vec[int]` — дают одинаковое имя?»

**Ответ: да, одно и то же — и это правильно.** D239: `[]T` — синтаксический
псевдоним `Vec[T]`, разворачивается на уровне type resolution, `[]T ≡ Vec[T]`.
В эмиссии оракула оба написания дают один C-тип `Nova_Vec____nova_int*`.

**Но по дороге к этому ответу вскрылся дефект оракула — класс О-1в** (`check`
принимает то, что его же кодоген отвергает). Проба:

```nova
module main
fn f(a []int) -> int => a.len()
fn f(a Vec[int]) -> int => a.len()
fn main() { ro xs = [1, 2, 3]  println(f(xs)) }
```

`nova check` — **`ok`**: перегрузка принята, то есть подбор считает типы
параметров РАЗНЫМИ (D84 требует различия). `nova build` — падает в clang:

```
dup.c:5289:17: error: redefinition of 'nova_fn_4main1f'
 5289 | static nova_int nova_fn_4main1f(Nova_Vec____nova_int* a) {
dup.c:5283:17: note: previous definition is here
 5283 | static nova_int nova_fn_4main1f(Nova_Vec____nova_int* a) {
```

Оба определения — с одинаковой сигнатурой и одинаковым именем.

**Корень — две двери на один вопрос «это один тип или два», и D239 слушает
только одна.** Мэнглинг разворачивает `[]T` в `Vec[T]` (потому имена совпали),
подбор перегрузки — нет (потому объявления приняты). Контроль: настоящая
перегрузка `g(int)`/`g(str)` собирается и даёт `nova_fn_4main1g` и
`nova_fn_4main1g__nova_str` — суффикс типов параметров у ВТОРОГО носителя имени.
То есть механизм различения имён у оракула есть и работает; здесь он честно
сказал «типы те же», а чекер до этого сказал «разные».

**Верный исход по спеке:** `check` обязан отвергнуть это как
`duplicate definition with same signature` (D84) — ровно то, что он говорит,
если написать `f([]int)` дважды. Эскалировано интегратору; фикс — класс О-1в,
канал 196, не отдельный баг.

**Что это значит для novac.** Сегодня novac отвергает ОБА написания в подписи
честным `E_NOVAC_SUBSET` («this type form is not compiled yet … arrive with
generics, E2-b»), поэтому расхождения нет и в храповик это не входит. Требование
к Э2-б записано: `[]T` и `Vec[T]` обязаны интернироваться в ОДИН терм
(`Interner.app(vec_decl, [int])`) — у интернера `types.nv` форма для этого уже
есть, разворот обязан жить ОДНОЙ дверью на входе (parse/sem), а не двумя
правилами в подборе и в мэнглинге. Иначе novac воспроизведёт ровно этот дефект.

## Оракул не проверяет СОДЕРЖИМОЕ turbofish — класс О-1в, ещё два носителя (замер 2026-08-21)

Найдено при подборе negative-фикстуры к форме `generic_call`: фикстура обязана
быть отвергнута ОБОИМИ, и две очевидные кандидатуры оказались приняты оракулом.

**Носитель 1 — лишний type-аргумент. `check` принимает, кодоген компилирует,
программа работает.**

```nova
fn dbl[T](x T) -> T => x + x
fn main() { println(dbl[int, f64](21)) }
```

`nova check` — `ok`; `nova build` — собирается; запуск печатает `42`. То есть
второй аргумент просто игнорируется. D84/D122 требуют, чтобы число
type-аргументов совпадало с числом связываемых параметров: `dbl` связывает один.

**Носитель 2 — НЕСУЩЕСТВУЮЩИЙ тип в turbofish. `check` принимает, падает clang.**

fn dbl[T](x T) -> T => x + x
fn main() { println(dbl[Zork](21)) }

типа, которого нет, не диагностируется ВООБЩЕ, а T выводится из аргумента.

**Что делает novac.** Отвергает оба по имени: «the call gives a different

type novac does not know». Расхождение СОЗНАТЕЛЬНОЕ и в пользу novac; в
`divergences.allow` не заводится, потому что фикстур на эти формы нет — вместо
них в `novac/fixtures/generic_call/neg_1.nv` стоит арность ЗНАЧЕНИЙ
(`dbl[int](1, 2)`), которую отвергают оба, а причина выбора написана в самой
фикстуре.

Эскалировано интегратору: класс О-1в, канал 196, не отдельный баг.

## ИМПОРТ НЕСУЩЕСТВУЮЩЕГО ИМЕНИ проходит `check` молча (замер 2026-08-22)

Проба на самом novac: в живой список импорта вписано имя, которого нет ни в одном

же формы: путь, ведущий вне пакета, он отвергает (`relative import ... выходит за
границу пакета`), то есть механизм разбора импортов есть, а сверки СОСТАВА нет.

**Механизм в novac до починки:** страж `check-novac-import-exists.py` (471 имя,
плечи сумм и методы учтены). Он не заменяет фикс оракула: страж судит только
`novac/src`, а форма общая для всякого кода на Nova.

Эскалировано, канал 196.

## ЭМИССИЯ ЗАВИСИТ ОТ ПОРЯДКА ОБЪЯВЛЕНИЙ: newtype в плече суммы (изолировано на 12 строках, 2026-08-22)

Один и тот же файл, отличается только ПОРЯДОК двух объявлений.

Компилируется:

```nova
type Row int

type Holder enum
    | HRow(Row)
    | HInt(int)
```

Не компилируется:

```nova
type Holder enum
    | HRow(Row)
    | HInt(int)

type Row int
```

```
error: typedef redefinition with different types
       ('struct Nova_Row' vs 'nova_int' (aka 'long long'))
```

**Что происходит.** Плечо суммы с полезной нагрузкой ИМЕНОВАННОГО типа эмитится
как боксированный `struct Nova_X*`, если объявление самого типа не было
выпущено раньше. А newtype над примитивом выпускается как `typedef nova_int
Nova_X` — и второй `typedef struct Nova_X Nova_X` его переопределяет. В Nova нет
предварительных объявлений: порядок в файле не значит ничего, и эмиссия не имеет
права от него зависеть.

**Как нашлось.** Волна В2 подплана 9.1г.1 заворачивала строку варианта, и
`VariantRow` попал в плечи ДВУХ сумм. В эмитированном C у одной суммы три плеча,
все три — newtype над `int`, и среднее вышло указателем:

```c
struct Nova_CalleeTarget {
    Nova_CalleeTarget_Tag tag;
    union {
        struct { nova_int _0; }          CalleeFn;      // FnRow  — верно
        struct { Nova_VariantRow* _0; }  CalleeVariant; // VariantRow — БОКС
        struct { nova_int _0; }          CalleeCtor;    // TyId   — верно
    };
};
```

`FnRow`, `TyId` и `DeclId` дефекта не встретили не потому, что они «другие», а
потому что живут в файлах и модулях, эмитируемых раньше. Внутри одного модуля то
же правило идёт по ФАЙЛАМ в их порядке: `VariantRow` кормит `DefTarget` (sem.nv)
и `CalleeTarget` (channel.nv), поэтому объявление пришлось поднять в файл,
который идёт раньше обоих.

**Обход в novac:** объявление стоит не там, где ему место по смыслу (рядом с
`VariantDef`), а в первом файле модуля, под маркером
`[LEGACY-#TBD-newtype-order-in-sum-arm]` и с этой причиной в комментарии. Когда
оракул перестанет зависеть от порядка — объявление вернётся на место.

**Почему это важнее одной обёртки:** зависимость эмиссии от порядка объявлений
бьёт по КАЖДОМУ newtype, попавшему в сумму, а суммы с нагрузкой — обычная форма
языка. И отказ приходит не от Nova, а из clang, сообщением про C-структуру,
которой в исходнике нет.

Эскалировано, канал 196.

## ПЕРЕГРУЗКА `main`: оракул принимает на чеке и падает в clang с `redefinition` — класс О-1в (замер 2026-08-22)

```nova
fn main(x int) -> int => x + 1

fn main() {
    println(main(41))
}
```

`nova check` — **ok**. `nova build`:

```
error: use of undeclared identifier 'x'
error: redefinition of 'nova_fn_main_impl'
```

**Два дефекта в одном файле, и оба от одной причины:** «точка входа» решается
СРАВНЕНИЕМ ИМЕНИ, поэтому любой вызываемый, написанный как `main`, наследует все
льготы точки входа. Отсюда `redefinition` (обе строки получили символ, который
диктует рантайм) и `undeclared identifier 'x'` (параметры «точки входа» не
связывают — их у неё нет).

**Найдено не пробой оракула, а вопросом владельца о МОЁМ коде:** «почему у нас на
`ENTRY_FN` хардкод, чем `ENTRY_FN` отличается от других функций?». У novac была
ровно та же болезнь и ровно от того же условия — шесть сравнений имени в четырёх
модулях. Разница только в исходе: novac отказывал в чеке («unknown name» про свой
же связанный параметр), оракул принимает и падает в clang.

**Как правильно, и это уже сделано в novac:** точка входа — свойство СТРОКИ, а не
написания, и правило состоит из трёх фактов (`is_entry_fn`): имя `main`, ноль
параметров, нет получателя. Перегрузка `main` — ОБЫЧНЫЙ вызываемый: язык её
разрешает, оракул её принимает на чеке, и имя ей положено обычное, с типами
параметров. Замер после починки: novac эмитит `nova_fn_main_impl` для точки входа
и `novac_fn_main__nova_int__to_nova_int` для перегрузки — два разных символа,
программа собирается.

**Почему исключение для точки входа само по себе законно** (и не является
хардкодом в смысле П5): её C-символ диктуют СНАРУЖИ — оболочка, которую эмитит
оракул, зовёт `nova_fn_main_impl()`, поэтому это имя не может нести типы
параметров, как все прочие наши имена (§7.0). Написание `main` живёт в
`builtins` одной константой. Незаконным было не исключение, а его УСЛОВИЕ.

**Фикстуры нет специально:** дифф-гейт сверяет исход с оракулом, а здесь novac
ПРАВ, а оракул падает в clang — фикстура покраснела бы на правильном поведении.
Придёт вместе с фиксом оракула. Эскалировано, канал 196.

**Попутное наблюдение того же файла (НЕ новое):** метод, названный `main`
(`fn Cel @main() -> int`), оракул принимает, а novac отвечает ICE — но по
зарегистрированной причине: методы СВОЕГО файла в таблицу вызываемых не попадают
(она наполняется из ПРОЧИТАННЫХ деклараций), и отказ за это отвечает маркером
`[LEGACY-#700-user-error-as-ice until:E2b3]` — пользовательская ситуация уходит
внутренней паникой, пока чек не владеет набором кандидатов.

## ro-launder не снимает newtype до носителя: `int` вернуть можно, `type Row int` — нельзя (замер 2026-08-21)

```nova
type Row int

fn pass_int(v int) -> int => v      // ok

fn pass_row(r Row) -> Row => r      // E_READONLY_COERCE
```

Оракул на втором:

```
error: [E_READONLY_COERCE] возврат `r` — источник связан как `ro` (D176-дефолт,
  P7 freeze), но объявленный тип возврата НЕ `ro`: `mut w = f()` у caller'а дал
  бы запись, видимую внутреннему источнику `r`
  (D246-амендмент, [M-ro-launder-via-mut-binding], Ф.1б)
```

**Почему это дефект, а не правило.** Newtype ЕСТЬ своё представление в рантайме
(zero-cost, D-newtype): у caller'а после `mut w = pass_row(r)` лежит КОПИЯ
размером с `int`, и «запись, видимая источнику» физически не существует — ровно
как для самого `int`, который эта же проверка пропускает. Анализ не снимает
newtype до носителя, хотя печать снимает (`println(Row(7))` печатает 7) и
раскладка снимает. Верный исход: спрашивать НОСИТЕЛЯ (как `carrier_of`), и тогда
newtype над примитивом ведёт себя как примитив.

**Цена, и она не разовая.** Это блокирует ЛЮБОЕ заворачивание примитивного
индекса: `return t` в дверях вида `fn f(t Wrapped) -> Wrapped` становится
незаконным, а таких дверей в подплане 9.1г.1 семь волн. Обход в novac — дверь
`types.same_ty` (тот же id, пересобранный конструктором; в C то же целое) под
маркером `[LEGACY-#TBD-newtype-ro-launder]`, шесть вызовов. Когда починят —
каждый вызов становится `t`, дверь уходит, поверхность `types` падает с 22 на 21.

**Почему `FnRow` этого не встретил:** его двери не возвращают собственный
параметр — `raw_row` кастует, `no_row` конструирует. Наступает на грабли ровно
тот, у кого есть тождественная дверь.

Эскалировано интегратору, канал 196.

содержимого turbofish.

**novac строже:** отказывает по имени, на самом аргументе — «this argument is
not the newtype's representation» и «constructing a newtype takes exactly one
argument». Верный исход по спеке — ошибка типа в чеке, на позиции аргумента.
Эскалировано интегратору тем же каналом 196.

Фикстура `novac/fixtures/newtype/neg_1.nv` закрепляет ОТКАЗ novac, а не согласие
сторон; дифф-страж судит только `pos_*`, поэтому расхождение живёт здесь.

## Ось режима: где novac СТРОЖЕ оракула, и где не судит вовсе (замер 2026-08-21)

Волна правила Р14 ([10-overloading.md](../../spec/decisions/10-overloading.md),
амендмент 2026-07-06 к ревизии D326) дала два расхождения, и оба сознательные.

**1. `ro`-биндинг в `mut`-параметр ЗНАЧИМОГО типа: оракул принимает, novac
отвергает.**

```nova
fn bump(mut v int) -> int => v + 1
fn main() { ro x = 41  println(bump(x)) }
```

Оракул — `ok` (для `int` `mut`-параметр это своя копия у callee, не in-out).
Для КУЧЕВОГО типа тот же силуэт оракул отвергает сам:
`E_READONLY_COERCE` — «readonly источник гарантирует immutability у caller'а».
novac держит правило Р14 единообразно: `mut`-параметру нужно изменяемое МЕСТО,
поэтому `ro`-биндинг ему не подходит. Расхождение в СТРОГУЮ сторону, и оно на
незакрытом заходе самой спеки — `[M-184-value-mut-mode-overload-abi]`
(«для value/prim `mut`-mode-overload — отдельный заход»). Когда заход закроется,
эта строка либо исчезнет, либо станет правилом «для значимого типа `mut` берёт
и ro-аргумент».

**2. D133 novac не судит: `consume`-параметр может остаться непотреблённым.**

```nova
fn tag(consume c Cel) -> int => 2   // `c` не потреблён
```

Оракул отвергает: «consume `c` via method (D133-not-consumed)». novac принимает —
линейности у него нет вовсе. Это расхождение в ОПАСНУЮ сторону (novac принимает
то, что оракул отвергает), и потому оно записано здесь, а не умолчано: novac
СЕЛЕКТИРУЕТ по `consume` правильно (замер: `pick(mk())` выбирает consume-версию
байт-в-байт с оракулом), но ОБЯЗАТЕЛЬСТВО потребления не проверяет. Фикстур на
эту форму нет специально — фикстура закрепила бы приём того, что язык не
разрешает.

## Вывода type-аргументов в novac нет — turbofish обязателен (решение плана, Э2-б2)

`fn dbl[T](x T) -> T => x + x` + `dbl(4)`: оракул выводит `T = int`, novac
отвергает — «this function is generic, so the call needs explicit type
arguments -- novac infers none». Это РЕШЕНИЕ этапа, а не дефект: вывод приходит
на Э2-б3 вместе с `InferCx`, а turbofish на Э2-б2 — вся карта соответствия
параметр→тип. Пишется здесь, чтобы «novac отверг то, что оракул принял» не
читалось как поломка при следующем чтении корпуса: такие файлы корпус числит
ОТСТАВАНИЕМ, и это правильная графа.

## ПОЗИЦИЯ КОНТРАКТА std приписана ЧУЖОМУ ФАЙЛУ и НЕСУЩЕСТВУЮЩЕЙ строке, и число разное на разных платформах (замер 2026-08-23)

**Что видно.** В эмиссии оракула по `novac/probe/shell_probe.nv` (файл в 56
строк) вызовы `nova_contract_violation` несут такие места:

```
nova_contract_violation(NOVA_CONTRACT_PRE, "alloc_copy", "n >= 0", "shell_probe.nv", 57, NULL)
nova_contract_violation(NOVA_CONTRACT_PRE, "int_fmt",   "cap >= 0 && ...", "shell_probe.nv", 57, NULL)
nova_contract_violation(NOVA_CONTRACT_PRE, "index",     "0 <= r.start && ...", "shell_probe.nv", 46, NULL)
```

Строка **57 в файле из 56 строк** — доказательство само по себе: номер взят не
из этого файла. Строка 46 — комментарий, а не вызов. Сами контракты объявлены в
std (`std/src/runtime/string/slice.nv:35` для `index`), то есть в эмиссию едет
ИМЯ файла вызывающего с номером, который этому файлу не принадлежит.

**Чем это плохо для пользователя, а не только для нас.** Упавший контракт
печатает место, которого нет: «shell_probe.nv:57». Человек идёт смотреть строку
57 в файле, где её нет, — и это худший вид диагностики, потому что он выглядит
точным.

**Почему это НАШЕ дело (замер 2026-08-23).** `novac/src/emit_c/shell.tpl.c` —
снимок этой самой эмиссии, и он обязан совпадать с тем, что оракул эмитит
сейчас. На Windows число ДЕТЕРМИНИРОВАНО (четыре сборки подряд — 46; копия probe
в CRLF — тоже 46), в CI (Linux) то же место эмитится как **45**. Исходники
компилятора и std между ветками идентичны байт-в-байт (`git diff --stat` пуст),
probe одинаков в индексе и в дереве и не содержит CR. То есть снимок НЕ МОЖЕТ
быть свеж одновременно на обеих платформах, пока номер зависит от платформы, —
и страж свежести оболочки краснеет на CI не по своей вине.

**Класс:** позиция диагностики берётся не от узла, к которому относится. Это
семья дефекта «имя файла из одного места, номер строки из другого»; отличается
от прочих записей этого реестра тем, что виден не в отказе чека, а в
СГЕНЕРИРОВАННОМ коде.

**Канал:** компилятор-фикс идёт в канал 196 (чекер/кодоген), не в novac. До
починки снимок оболочки на CI будет расходиться в этом одном месте; см. план
274 §9.1д К9.

## НЕОПРЕДЕЛЁННЫЙ type-параметр (только в возврате) проходит `check` оракула и падает в КОДОГЕНЕ — класс О-1в (замер 2026-08-23)

Минимальный носитель, три строки:

```nova
fn make[T]() -> T => make()

fn main() { println("x = ", make()) }
```

* оракул: `check` — **PASS**; `build` — `codegen error: cannot infer type
  argument 'T' for generic function 'make' (returned only — turbofish
  required)`;
* novac (после волны В1 подплана §9.1е): отказ НА ЧЕКЕ, названный — «no
  argument fixes this type parameter -- novac deduces from arguments only, never
  from the return position (E2-b3)».

**Почему это записано, а не сделано фикстурой.** По дисциплине фикстур
`neg_*.nv` утверждает СОГЛАСИЕ с оракулом об исходе; здесь исход расходится
(оракул принимает на чеке), и фикстура закрепила бы расхождение вместо правила.
Ровно та причина, по которой `dbl[Zork](21)` и `dbl[int, f64](21)` не стали
фикстурами (см. `generic_call/neg_1.nv`).

**Класс тот же, что у пяти предыдущих носителей О-1в:** ошибка, которую чекер
обязан назвать, доживает до кодогена. Здесь она хотя бы названа кодогеном
внятно — но названа ПОСЛЕ того, как программа прошла проверку типов, то есть
`check` оракула утверждает про эту программу неправду.

**Для novac это не долг, а подтверждение границы:** вывод из возвратной позиции —
работа bidirectional-половины (донор rustc `InferCtxt`), и она сознательно не в
волне В1. Пока её нет, отказ на чеке строже оракула и честнее его.

## КОНФЛИКТ ДЕДУКЦИИ проходит `check` оракула и умирает в clang — класс О-1в, седьмой носитель (замер 2026-08-23)

Носитель, четыре строки:

```nova
fn clash[T](a T, b T) -> int => 2

fn main() { println("clash = ", clash(1, "s")) }
```

`T` обязан быть одновременно `int` и `str`. Что делают два компилятора:

* оракул: `check` — **PASS**; `build` — clang: `passing 'const nova_str' to
  parameter of incompatible type 'nova_int'`. То есть подстановка выбрана
  МОЛЧА (по первому аргументу), тело инстанцировано под `int`, и в него передан
  `str`;
* novac (волна В1 подплана §9.1е): отказ на чеке, названный — «two arguments
  want different types for one type parameter -- novac names the conflict
  instead of choosing».

**Почему это опаснее прочих носителей О-1в.** Остальные шесть — ошибка, дожившая
до кодогена. Здесь ошибка ПЕРЕЖИЛА вывод типов: компилятор не отказался, а
ВЫБРАЛ, и выбор был не назван. Поймал его C-компилятор — то есть чужой
инструмент, который про Nova не знает ничего. На типе, где clang промолчал бы
(два разных типа с одной раскладкой), это уехало бы в бинарь.

**Канал:** 196. Правило для novac обратное и уже действует: применимость
считается по ВСЕМ позициям, конфликт называется, выбор не делается.

## КОНСТРУКТОР С ПРОПУЩЕННЫМ ПОЛЕМ: оракул принимает, СОБИРАЕТ и ЗАПУСКАЕТ; поле молча нулевое (замер 2026-08-23, ВОПРОС спеке)

Носитель, четыре строки:

```nova
type Two { a int, b int }

fn main() {
    ro t = Two { a: 1 }
    println("a = ", t.a)
}
```

* оракул: `check` — **PASS**; `build` — успешно; запуск печатает `a = 1` и
  выходит нулём. Поле `b` не названо нигде и не инициализировано автором;
* novac: отказ (`E_NOVAC_SUBSET`).

**Как это нашлось — и это часть записи.** Я добавил поле в `Ctx` (таблица
протоколов, волна 3б) и НЕ дописал конструктор. `check` оракула прошёл. То есть
компилятор, которым собирается novac, не назвал незаполненное поле в собственном
компиляторе — а novac его называет.

**ПОЧЕМУ ЭТО ВОПРОС, А НЕ СРАЗУ ДЕФЕКТ.** Спека молчит: поиск по `spec/`
(«все поля», «поле без значения», «zero-init», `E_MISSING_FIELD`) даёт правила
про РАЗБОР (`..` в деструктуризации, D-блоки 05-memory) и про
zero-init в рантайме, но ни одного правила про ПОЛНОТУ конструктора записи. Три
возможных положения дел, и выбрать обязан владелец либо спека:

1. неполный конструктор ЗАКОНЕН, остальные поля нулевые по определению — тогда
   правило обязано быть записано D-блоком, а novac обязан его принять;
2. неполный конструктор НЕЗАКОНЕН — тогда это дефект оракула худшего класса из
   встреченных: не «check принял, а clang упал» (О-1в), а **молча неверная
   программа**, которая собирается и работает;
3. законен только для `value`-записей или только при наличии умолчаний — тогда
   правило узкое, и его тоже надо записать.

**Пока не решено, novac держит строгую сторону** (отказ): принять молча — значит
воспроизвести случай (2), если он окажется дефектом, а отказ по имени всегда
можно ослабить.

**Канал:** вопрос спеке/владельцу; если (2) — компилятор-фикс каналом 196.
