# Охота (novac): сверка «что эмиттер спрашивает» против «что чекер записывает» — ОТРИЦАТЕЛЬНЫЙ результат по видам узлов, и где осталась настоящая поверхность

**Кто:** интегратор, 2026-09-09. **Метод:** перечисление двумя агентами на haiku,
сопоставление и проверка — мои. Без запусков.

**Зачем записан отрицательный результат.** Проверенное и не давшее находки — это
не пустая работа, а снятый вопрос: следующий, кому придёт та же мысль, увидит, что
здесь уже смотрели, и не потратит на это день.

## Что сверялось

`@out.type_of` — **тотальная** дверь канала: на дыре не `Option`, а ICE. Значит
каждое обращение к ней есть утверждение «здесь тип точно записан». Вопрос:
подтверждается ли утверждение тем, что чекер действительно пишет.

Две таблицы, обе собраны перечислением, а не выборкой:

* **19** обращений `@out.type_of(` в `novac/src/emit_c/*.nv`;
* **54** вызова `@record(` в `novac/src/check/*.nv`, с видом узла для каждого.

## Результат А: по видам узлов расхождений НЕТ

Из 19 обращений **восемь** стоят внутри ветки, определяющей вид узла:

| место | вид | чекер пишет |
|---|---|---|
| `emit_c.nv:698` | ArrayLit | да |
| `emit_c.nv:705` | TupleExpr | да |
| `emit_c.nv:728` | RecordCtor | да (`check/exprs.nv:946`) |
| `emit_expr.nv:546` | MethodCall | да |
| `emit_expr.nv:672` | Unary | да |
| `emit_expr.nv:733` | Bin | да |
| `emit_expr.nv:762` | Bin | да |
| `emit_place.nv:177` | TupleExpr | да |

**Все восемь подтверждены.** `RecordCtor` сперва выглядел расхождением — его не
было в списке видов, собранном агентом, — и это оказалось изъяном ТАБЛИЦЫ, а не
кода: запись стоит в `check/exprs.nv:946`, дальше тридцати строк, которые агент
просматривал. Проверено чтением до того, как из «находки» что-то последовало.

## Результат Б: настоящая поверхность — там, где вида нет

Остальные **одиннадцать** обращений стоят ВНЕ ветки по виду узла, то есть
спрашивают тотальную дверь о **произвольном выражении**:

```
emit_c.nv:500, 501, 816
emit_destructure.nv:62, 85
emit_expr.nv:864
emit_flow.nv:170, 295
emit_interp.nv:68
emit_match.nv:45
emit_place.nv:201
```

**Почему это и есть поверхность.** У восьми первых гарантия имеет источник: вид
узла назван, и для него запись есть. У этих одиннадцати источника гарантии в самом
месте НЕТ — она может прийти только из положения в обходе, то есть из знания «сюда
доходят лишь такие выражения». А это ровно то знание, которое устаревает молча,
когда появляется второй потребитель.

**Это не гипотеза, а уже случившийся случай.** `emit_expr.nv:864` — из этих
одиннадцати: аргумент `println`. Именно там окно 274 получило ICE, когда их волна
сделала второго спрашивающего, а `check/typing.nv:846` намеренно не публикует тип
строкового литерала с обоснованием *«the emitter never asks its type»*.

## Чего я НЕ утверждаю

Одиннадцать мест **не проверены поштучно** — я не читал каждое до конца обхода и
не доказал ни достижимости, ни безопасности ни одного из них. Утверждается только
структурное: у них гарантия не может исходить из вида узла, потому что вид не
назван.

Не проверено и то, полна ли таблица 54 записей: она собрана по вызовам `@record(`
и `record_type(`, и запись, сделанная третьим способом, в неё не попала бы.

## Что с этим делать (решает окно 274)

Дешёвое и проверяемое: у каждого из одиннадцати мест назвать источник гарантии
одной строкой комментария — «сюда доходит только X, потому что Y». Тогда
утверждение станет читаемым, а его устаревание — заметным. Сегодня оно
подразумевается, и заметить его смену можно лишь получив ICE.
