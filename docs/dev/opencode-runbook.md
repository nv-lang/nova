# OpenCode как параллельное окно — как запускать

> **Зачем.** Разгрузить лимиты главной сессии-интегратора: механику по списку
> (правки `.nv` по образцу, миграции сайтов, тесты по существующей фикстуре,
> переименования) отдавать бесплатным моделям через `opencode`, оставляя себе
> решения, разведку, приёмку и слияния.
> **Актуально на 2026-07-29**, opencode `1.18.9`. Флаги и разрешения перепроверены
> 2026-09-21 на `1.18.31` — расхождений не найдено; проба `kimi-code/kimi-for-coding`
> добавлена тем же числом.

## Установка и состояние

- Ставится npm-ом глобально (`npm i -g opencode-ai`); проверка — `opencode --version`.
- Конфиг пользователя: `~/.config/opencode/opencode.jsonc` (под Windows — в профиле пользователя).
- Данные/сессии: `~/.local/share/opencode/` (`opencode.db`, `auth.json`).
- Проверить провайдеров: `opencode auth list`.

## Auth НЕ нужен для бесплатных моделей (проверено 2026-07-30)

Модели с префиксом `opencode/` (весь список ниже) идут через собственный шлюз
opencode и работают **без единого credential**: проверено фактом — `opencode auth
list` → `0 credentials`, `auth.json` отсутствует, env-переменных нет, а
`opencode run -m opencode/big-pickle` выполнил полное задание. `opencode auth login`
нужен ТОЛЬКО для чужих провайдеров (`anthropic/...`, `openai/...`,
`openrouter/...`). То есть для нашего сценария «бесплатное параллельное окно»
никакой настройки не требуется: поставил → `opencode run` → работает.

## Команда запуска (headless — то, что нужно)

```sh
opencode run --dir D:/Sources/nv-lang/nova-pNN --auto -m opencode/<модель> "<бриф>"
```

| флаг | зачем |
|---|---|
| `--dir <путь>` | рабочая директория — **всегда отдельный worktree**, никогда не главная репа |
| `--auto` | авто-подтверждение разрешений; без него headless-запуск встаёт на первом же запросе |
| `-m provider/model` | модель, напр. `-m opencode/north-mini-code-free` |
| `--format json` | машинный вывод событий (для разбора результата скриптом) |
| `--agent <имя>` | кастомный агент, если заведён в конфиге |
| `-c` / `--session <id>` | продолжить прошлую сессию (дешевле нового окна — контекст сохраняется) |
| `--fork` | ответвить сессию при продолжении |
| `--variant <high\|max\|minimal>` | reasoning effort, если провайдер поддерживает |
| `--thinking` | показывать блоки размышления |
| `--pure` | без внешних плагинов |

Долгий запуск — в фоне; вывод забирать из файла, а не из терминала.

**`--variant high`/`max` — не косметика, а условие работоспособности некоторых моделей.**
Измерено 2026-07-30: `laguna-s-2.1-free` на дефолтном варианте ДВА захода подряд делала
только разведку и завершалась «успешно», не написав ни строки кода; писать начала
только с `--variant high`. `deepseek-v4-flash-free` на дефолте оборвалась на середине,
на `--variant max` довела задание до конца. Правило: **если модель вернулась быстро и
без правок — перезапускай с `--variant high` (для крупных моделей `max`), прежде чем
записывать её в негодные.** Продолжать сессию при этом можно флагом `-c` — наработки
и контекст сохраняются.

## Разрешения и рабочий каталог (2026-08-09, наступлено на всё лично)

**`--auto` — не удобство, а условие запуска.** Без него headless-прогон
отклоняет разрешения САМ и падает на середине, теряя уже сделанную работу:

```
! permission requested: external_directory (C:\Users\<имя>\AppData\Local\Temp\*); auto-rejecting
✗ cd /tmp && ... failed
Error: The user rejected permission to use this specific tool call.
```

**Вторая половина той же ошибки — путь.** opencode отклоняет любой путь ВНЕ
корня проекта. Поэтому брифу не должен требоваться внешний путь вообще: в корне
заведён **`scratch-opencode/`** (содержимое под `.gitignore`, сам каталог
существует и отслеживается). Логи и промежуточные файлы — только туда:

```sh
cd d:/Sources/nv-lang/nova && <команда> > scratch-opencode/step1.log 2>&1
echo "RC=$?"
```

Проверено живым прогоном: запись и чтение внутри проекта проходят без разрешений.

**Ослаблять защиту opencode конфигом — неверный ответ.** Правильный — не давать
брифа, которому внешний путь нужен.

### Прогон может не завершиться сам

Проба записала файл за секунды, а процесс не вышел и за пять минут. Судить о
результате нужно **по артефактам в `scratch-opencode/`**, а не по коду возврата и
не по ожиданию выхода. Это согласуется с правилом «долгий запуск — в фоне, вывод
забирать из файла» выше, но стоит сказать прямо: отсутствие выхода НЕ означает,
что работа не сделана.

### Наблюдение без диагноза

Однажды обёртка упала так: путь до `opencode.exe` потерял кириллическое имя
пользователя и превратился в `C:\Users\` + `/node_modules/...`. Гипотеза про
`LC_ALL=C` **проверена и не подтвердилась** — `HOME` под ним разрешается верно.
Причина не установлена; записано как наблюдение. Повторится — смотреть на
обёртку `npm`, а не на локаль.

### `kimi-code/kimi-for-coding` (проба 2026-09-21, платный провайдер через oauth)

**Отличие от «бесплатного пула» выше: это НЕ префикс `opencode/`.** Модель идёт
через провайдер `kimi-code`, который уже стоял авторизованным (`opencode auth
list` → `kimi-code oauth`, поставлено отдельно от этой сессии) — то есть
`auth login` для неё нужен, просто кто-то его уже сделал. Список моделей
проверяется командой `opencode models | grep -i kimi`; на 2026-09-21 доступны
`kimi-code/k3`, `kimi-code/kimi-for-coding`, `kimi-code/kimi-for-coding-highspeed`.

**Задача пробы:** написать один файл `clamp.nv` (чистая функция + `fn main`
с EXPECT_STDOUT) по образцу живого кода — та же категория задач, что и у
бесплатного пула. Свой worktree (`nova-opencode-kimi`, отдельный от главной репы).

**Вердикт: ПРОШЛА, с одной оговоркой по флагам CLI.**

- Синтаксис не выдумала: перед письмом сама прогнала `Glob`/`Grep` по
  `spec_tests/conformance/standalone/*.nv` и `std/src/**`, нашла живые примеры
  `fn main() Io -> ()`, `println("${...}")`, `export fn f(a int, b int) -> int`,
  цепочку `if … } else if … { … } else { … }` — и процитировала ТОЧНЫЙ файл и
  строку для каждого скопированного куска в отчёте.
- **Проверено НЕ на слово, а запуском:** `nova check` → `ok`; `nova test` →
  `PASS 1/1` (это компиляция в C и исполнение бинаря, не только разбор);
  собранный бинарь напечатал `0 10 7 0 10` — **дословно** то, что модель
  назвала в отчёте до запуска, включая посчитанное ею значение маркера
  `EXPECT_STDOUT 0`. Отчёт и факт сошлись без единого расхождения.
- Отчёт был по форме, которую требовал бриф (файл → источники синтаксиса
  с путями → как посчитан маркер), без лишней прозы.

**Находка по флагам `opencode run`, а не по модели:** `-f/--file` — это
`[array]`-флаг у yargs, и если поставить его ПЕРЕД позиционным текстом
сообщения, он молча поглощает этот текст как ещё одно имя файла
(`Error: File not found: <текст сообщения>`). **Порядок обязателен:
сначала позиционное сообщение, потом `-f`:**

```sh
opencode run "<текст>" --dir <worktree> --auto -m kimi-code/kimi-for-coding -f <путь-к-брифу>
```

**Побочный эффект первого запуска `nova test` в свежем worktree:** он сам
клонирует `libuv` (submodule) и собирает `libnova_rt`, если их там нет —
это не разовая проба opencode, это устройство `nova test`/`nova build` в
новом дереве; занимает ~30-40 секунд один раз на worktree.

**Один прогон — не полный отбор.** Прошёл ровно тот же протокол (пункт 1 и 2:
синтаксис по образцу, числа сходятся), что и остальные модели, но всего на
ОДНОЙ маленькой задаче. Ставить наравне с `big-pickle` по надёжности рано —
нужны минимум задачи-измерения (репро гонки, точная сверка заявки), как у
него, прежде чем доверять без перепроверки.

**ПРЕДПОЧТЕНИЕ ВЛАДЕЛЬЦА 2026-09-21: `kimi-code/kimi-for-coding` — модель ПО
УМОЛЧАНИЮ для запуска через opencode**, впереди бесплатного пула (`big-pickle`,
`deepseek-v4-flash-free`) для новых заданий. Бери её первой; к бесплатному пулу
возвращайся, только если `kimi-code` недоступна (не авторизована на машине) или
задача явно требует сравнения нескольких моделей.

**СЛОВО ВЛАДЕЛЬЦА 2026-09-21 (второе, тем же днём): для `kimi-code/kimi-for-coding`
можно пускать МНОГО работы ПАРАЛЛЕЛЬНО** — в отличие от бесплатного пула
(`opencode/...`), где параллельность не проверялась и не заявлялась, здесь она
явно разрешена владельцем. Практически это значит: несколько `opencode run` с
`-m kimi-code/kimi-for-coding` можно запускать ОДНОВРЕМЕННО, каждый в СВОЁМ
отдельном worktree (см. «Дисциплина запуска» ниже — правило одного worktree на
задание никуда не делось, параллельность про ЧИСЛО заданий, не про общий
каталог). Число реально проверенных одновременных прогонов и потолок машины
этим словом не установлены — не заявляй большего, чем сказано; если предел
понадобится узнать, мерить самому, а не считать написанное здесь потолком.

**СЛОВО ВЛАДЕЛЬЦА 2026-09-22 (третье): `kimi-code/kimi-for-coding` -- МОЩНАЯ
МОДЕЛЬ, её можно пускать ВМЕСТО СЕБЯ (окна Claude Code), когда цель --

границу (там: перечисления/сверки/механические замены -- да, классификация/
суждение/проектирование/приёмка -- нет, отдавать sonnet/opus). Теперь

можно вместо этого отдать `kimi-code/kimi-for-coding`, если цель -- беречь
лимит, а не потому что задача чисто механическая. **Это НЕ отменяет
приёмку:** окно, отдавшее задачу, всё равно проверяет результат само --
отчёт модели остаётся сырьём, а не вердиктом, та же граница, что у любого
делегирования (`/delegate`). Протокол отбора и критерии ниже остаются в
силе для НОВЫХ моделей; для `kimi-code/kimi-for-coding` конкретно отбор
уже пройден (см. пробу выше) -- это слово владельца о ШИРЕ доверия ей, а
не новая проба.

и модульные тесты -- и приложить список красных ДОСЛОВНО, а не «PASS»;
(2) в докладе у каждого «проверено» называть, ЧТО именно запускалось;
(3) строка леджера `docs/dev/novac-time-ledger.md` за каждую дату коммитов в
`novac/**`. Приёмка по-прежнему за окном, отдавшим задачу: этот замер её не
заменяет, он делает её короче. **С того же вечера пункт (1) — одна команда, а не
перечень стражей:** `bash scripts/tools/merge-precheck.sh --report <дерево>`;
блок сдачи для брифа, готовый к копированию, —
[opencode-brief-template.md](prompts/opencode-brief-template.md), раздел «Задание
на ВЕТКУ».

**Протокол отбора (если проверяешь новую модель):** одна и та же маленькая полностью
проверяемая задача, свой worktree на каждую, одинаковый бриф. Критерии в порядке важности:
1. **не выдумывает ли синтаксис Nova** — главный риск (прецедент: 7 из 7 фикстур с
   несуществующими конструкциями `ro x: T` / `protocol X {`);
2. **сходятся ли её числа с твоими** — прогоняй заявленное сам, это ловит и «упростил
   задачу под себя», и приукрашенные отчёты;
3. соблюдает ли запреты (не лезет в главную репу, ничего не копирует, коммитит чекпоинты);
4. не выходит ли за объём задания.

## Дисциплина запуска (те же правила, что для haiku-агентов)

В КАЖДЫЙ бриф, без исключений:

- **Свой worktree; вход в главную репу `d:/Sources/nv-lang/nova` запрещён** (чтение — можно, правки — нет).
- **`compiler-codegen/**` не трогать** — компиляторное окно ровно одно и оно у интегратора.
- **Синтаксис Nova не выдумывать** — только по образцу живого кода в `std/src/**`, `examples/**`, `spec/decisions/`. Не знаешь формы — найди существующий пример и скопируй.
- **Обходы запрещены**: не работает — доложи, а не закомментируй и не «упрости».
- **`git add` только по именам файлов**, никогда `-A`/`.`; `git config` не трогать (общий `.git` у worktree — травит авторство всей репы).
- **Суб-агентов не спавнить.** Чекпоинт-коммиты каждые 5-10 минут.
- **Мега-CU (`spec_tests/conformance`) не гонять** — авторитетный гейт делает интегратор; беречь CPU.
- **Отчёт обязан содержать вердикты прогонов дословно** — числа, которых модель не видела своими глазами, не приводить.
- **Не пушить и не сливать в main** — слияние за интегратором.

Сборка вне главной репы — **ничего не копировать**, только переменные (полный
блок — в [read-project.md](read-project.md) §«Сборка вне главной репы»);
копия `compiler-codegen/` внутрь worktree запрещена и ловится стражем в гейте.

**Изолированное `.nv`-репро — ВСЕГДА в своей пустой поддиректории.** Найдено окном
№141 (2026-07-29): общий scratchpad сессии не изолирован — там копятся файлы прошлых
сессий (на момент находки 625 файлов, из них 120 `.nv`). Из-за конвенции «папка =
ОДИН модуль из co-equal файлов» брошенный в корень scratchpad `module main` молча
подхватывает импорты чужих соседей (`import polaris` из чьего-то старого `orig_main.nv`)
— репро перестаёт быть репро, а диагноз получается ложным. Тот же механизм делает
недостоверным «прогон одного файла в `spec_tests/conformance`»: он компилирует ВСЮ
папку одним CU. Правило: `mkdir <своя-папка>` → один файл со СВОИМ `module` → прогон.

## Что отдавать, а что нет

**Отдавать:** миграции сайтов по списку, правки `.nv` по образцу, тесты по
существующей фикстуре, переименования, вычистка устаревших комментариев,
механическая доводка доков.

**Не отдавать:** архитектуру, разведку корня дефекта, любые правки компилятора,
решения по спеке, приёмку. Отчёту исполнителя на слово не верить — проверять
самому (прецедент: окно отчиталось о трёх «предсуществующих поломках», все три
оказались артефактами его worktree).
