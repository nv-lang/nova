# Конвенция компилятора `novac`

**Нормативный документ.** Как ПИСАТЬ код `novac/**`. Имя и место выбраны владельцем
2026-08-14 (274 §10.5): предмет в имени; старая
[compiler-conventions.md](compiler-conventions.md) остаётся адресом своего предмета,
пока жив нынешний компилятор.

**Чем этот документ отличается от предшественника — способом, не содержанием.**
Содержание — оплаченные уроки старой конвенции и реестра; но здесь **правило без
стража в документ не попадает** (№636: правило прозой не действует). У каждого правила
строка «Страж:» — имя механизма и его статус. Статусы — как в сводном аудите
[274 §10.3а](../plans/274-novac-self-hosted-compiler.md): ✅ в гейте · 🕐 этап, ДО кода,
которому подсуден (Э1-каркас не принимается без своего набора) · ⚖ суждение приёмки,
честно.

Общие конвенции проекта (`nv-coding-style`, `naming-conventions`, `module-conventions`,
`test-conventions`) действуют как есть и здесь не дублируются.

## П1. Один источник истины; потребители читают, не перевычисляют

Тип, резолв, подстановка вычисляются ОДИН раз своей дверью (`check` → `sem`); всякий,
кому нужен факт, читает таблицу. Перевывод чужого факта — дефект, даже если даёт тот же
ответ сегодня (завтра разойдётся молча — весь план 196 был демонтажом этого).
**Страж:** `check-novac-deps.sh` — рёбра и «что течёт»; `sem` пишет только `check`. 🕐 Э1.

## П2. Идентичность — не имя

Имя — ключ ровно в одной двери (`names`); дальше только `DeclId`/`NodeId`
(архитектура §4а; носители класса — №576, B11q, №534, №617).
**Страж:** `check-novac-no-string-keys.sh`. 🕐 Э1.

## П3. Порядок проходов живёт в одном месте

Фазы зовёт только `pipeline`; факт не используется до готовности его производителя
(фаза-корректность старой конвенции, урок LSP с десятью проходами по именам).
**Страж:** `check-novac-deps.sh` — ни у кого, кроме `pipeline`, нет рёбер к фазам как
к исполняемым шагам. 🕐 Э1.

## П4. Отравление вместо пермиссивности; никаких молчаливых fallback-типов

Ошибка помечает узел; правило одно: «уже репортнуто — молчи». Пермиссивный
unknown, глотающий настоящие ошибки, запрещён — цена измерена (№652:
`fn f() -> int { "str" }` и `if 5` проходят нынешний check зелёным). Auto-выведенный
неверный тип «чтобы собралось» — дефект, не сервис.
**Страж:** `check-novac-no-cascade.sh` (опечатка → ровно один диагностик) +
`check-novac-diag-schema.sh` (`poisoned_by` обязателен у вторичных). 🕐 Э1.

## П5. Никакого хардкода имён Nova в компиляторе

Методы, типы, операции — из деклараций (`.nv` / декларированные интринсики);
захардкоженное имя `to_str`/`Vec`/`equal` в коде компилятора — дефект (уроки D109,
№576; легитимный остаток — только то, чего в декларациях нет, и он перечислен явно).
Интринсик обязан декларировать свою репрезентацию — тип и эмит не расходятся (урок D77).
**Страж:** `check-novac-no-name-hardcode.sh` ✅ (заведён 2026-08-15 — с опозданием на
волну: правило стояло 🕐 Э2, Э2 начался, стража не появилось, и `subset_method_ret` +
seed-строки std-инстансов проросли в три модуля; владелец поймал ревью). Единственный
законный дом строковых литералов имён — `novac/src/builtins`; всё вне него — красное.

**Дополнения по вердикту 2026-08-15** (эталоны: rustc `sym`/LangItem +
`rustc_symbol_mangling`, Go `types.Universe` + `LinkString`, Zig builtins):

- **компилятору законно знать**: (а) universe — примитивы и их ABI-имена рантайма
  (факт `nova_rt.h`), (б) точки входа языка (`main`, форма `println`), (в) правила
  мэнглинга **как функцию**; всё остальное — ЧИТАЕТСЯ: сигнатуры методов std
  novac берёт из деклараций, поданных двери (`novac check --std <dir>`), и
  принимает только те, у которых известны ВСЕ типы — ресивер, параметры,
  возврат (так перегрузки std отбирает типовая система, а не список имён;
  исполнено 2026-08-16 по слову владельца «временный хардкод не принимается» —
  таблица `builtin_method_ret` удалена, а не помечена долгом); **НЕзаконно**: имена типов/методов std (это ДЕКЛАРАЦИИ —
  читаются, Э2-б), инстансы дженериков (приходят из `mono`), C-имена чего-либо, кроме
  примитивов, строкой;
- **C-идентификатор эмитируется ТОЛЬКО через дверь мэнглинга** `sem/mangle`
  (`c_type`/`c_struct`/`c_tag`/`c_maker`/`c_method`/`c_fn`) — функцией от сущности;
  константа «на комбинацию типов» (`C_VEC_INT_TYPE`) — первый член бесконечного ряда,
  класс П1 (потребитель не перевычислил чужой факт, а захардкодил его значение).
  **Страж:** `check-novac-mangle-fixed-point.sh` ✅ — каждый оракульский символ в
  эмиссии novac обязан существовать в оболочке (эмиссия оракула по probe) или
  заголовках рантайма; правило держится диффом, не прозой (самотест: сломанное правило
  краснит);
- **инстанс дженерика — только через `mono`**; seed-таблица предзасеянных типов не
  может содержать инстансы. Прецедент 2026-08-15: demo.nv был «взят» одним
  захардкоженным `[]int` — К7-полукапабилити (компилятор «умеет» `[]int` и молча не
  умеет `[]str`); откачен из подмножества с записью в храповике; П6 важнее
  монотонности §10.4.

## П6. Никаких тихих дыр

`_ => return`/пустая ветка без диагностики или маркера — дефект. Непокрытая форма
callee — ранняя диагностика, не поздний ICE (уроки B11al/B12q/r/s).
**Страж:** общий `check-marker-registry-sync.sh` (маркер без записи в реестре) ✅ +
`check-novac-no-panic.sh` (ICE ловится фаззингом). 🕐 Э1.

## П7. Расхождение с оракулом — только через реестр

Поведение видимо → любое отличие от нынешнего компилятора несёт запись в
`novac-divergences.md` (корзина + номер/D-блок). Молчаливое расширение или сужение
языка запрещено — включая «у нас случайно заработало» (bootstrap §6: реализация не
закрывает открытые вопросы).
**Страж:** `check-novac-differential.sh` — расхождение вне реестра красное. 🕐 Э1.

## П8. Снос легаси — только NO-HIT

Удалять ветку/функцию можно после трейс-доказательства недостижимости на корпусе
(методология D182; мета-урок Wave-1: демонтаж ветками без трейса дал 0 снесённых и
откаты по первому репро).
**Страж:** ⚖ — суждение приёмки с обязательным трейсом в тексте слияния; машинного
критерия «доказательство приложено» нет, и это сказано честно.

## П9. Файл ≤ 1000 строк; модуль = одна ответственность

Жёстко с первого коммита (274 §10.4: легаси нет — лимит стоит ноль).
**Страж:** `check-novac-file-size.py`. 🕐 Э1.

## П10. Фикстура на каждый фикс; баг в реестр — минимизированным

Закрытый дефект оставляет красневшую фикстуру навсегда; запись в реестр несёт
минимальное репро (авто-редьюсером, когда он есть).
**Страж:** общий `check-test-fixture-coverage.sh` ✅ (после №639 понимает обе формы);
`check-novac-repro-min.sh` 🕐 Э2.

## П11. Инварианты считаются и минимизируются конструкцией

Каждый раздел карты несёт счётчик; новый инвариант в коде — через
`conventions-governance` («как можно меньше, и ни одного на честном слове»).
**Страж:** `check-novac-arch-invariants.sh` ✅ в гейте + общий
`check-invariant-discipline.sh` ✅.

## Что сознательно НЕ правило

Стиль и длина функций сверх общих конвенций — не нормируется: правило, которое
нечем держать и незачем, разжижает документ. Список правил растёт только вместе
со стражами. (Форма документации типов/полей/функций с 2026-08-15 — правило П13,
у него есть страж.)

## П12. Внутренние инварианты: одна дверь `ice()`, паника — транспорт до супервизора

Выработано 2026-08-14 разбором эталонов по вопросам владельца (полный разбор —
ревью Э1; сюда перенесена вечная часть, wip-файл смертен).

**Как у эталонов.** rustc: голый `panic!` в исходнике запрещён внутренним
линтом; двери `bug!`/`span_bug!` дают ICE с привязкой к месту, а
`span_delayed_bug` откладывает ICE и гасит его, если компиляция уже выдала
настоящую ошибку — это убивает класс «ICE на сломанном вводе». Roslyn:
внутренняя ошибка наружу выходит ДИАГНОСТИКОЙ «internal compiler error»,
процесс цел. Go: `base.Fatalf` — всегда именованная дверь. LLVM/Clang —
антиобразец для цели «стабильность»: release без ассертов превращает
`llvm_unreachable` в UB (мискомпиляция вместо краха); у Clang берём другое —
crash-репродьюсер (родня методики автоминимизации, план 274 §12.3).

**Три факта Nova, на которых стоит правило** (поправки владельца 2026-08-14):
assert/контракты/границы работают И В РЕЛИЗЕ — «debug-яруса» не существует,
анти-LLVM позиция встроена в сам язык; `?? panic(...)` — по сути assert;
паника ЛОВИТСЯ на выходе из файбера в супервизоре — граница рендера, которую
rustc делает catch_unwind'ом драйвера, у нас есть в языке.

**Правило.**

1. Голый `panic(` в `novac/src` — под страж (`check-novac-no-naked-panic`,
   завести вместе с этим правилом): явный инвариант идёт через одну дверь
   `ice(...)`/`ice_at(span, ...)` в `diag` — с местом и по схеме §7
   (`E_NOVAC_ICE`, machine-first, «это баг компилятора, не вашего кода»),
   а не строкой свободной формы.
2. Рендер границы — **включён с 2026-08-16** (Э2, поправка владельца:
   «контракты и assert есть везде, в том числе в stdlib; компилятор нужно
   завернуть в супервизор и файбер»). Драйвер `main` держит
   `with Supervisor = effect Supervisor { on_child_fail(...) }` вокруг
   `supervised { spawn { run(...) } }`: компиляция целиком идёт в дочернем
   файбере, а долетевшая паника — ЛЮБАЯ, включая assert, контракт и проверку
   границ из глубины std — рендерится обработчиком одной §7-строкой и даёт
   код возврата двери. Свой panic файбер не ловит; ловит родитель (D13, спека
   выправлена 2026-08-14).
3. **Инвариант заявляют `assert(cond, "текст")`, а не `ice("текст")** —
   поправка владельца 2026-08-16, проверенная пробой: обработчик получает
   `main.nv:227: assert failed: novac: <текст> (a.len() < 0)`, то есть
   ФАЙЛ И СТРОКУ места, свой текст и исходник условия. `ice()` этого не даёт
   и дать не может: обёртка сообщает site своего тела (см. П20), потому и
   просился `#[track_caller]`. Запрос СНЯТ — язык уже отвечает на вопрос,
   просто другим механизмом. `ice()` остаётся дверью там, где §7-строку
   строят осознанно (она паникует уже готовой строкой, и граница печатает её
   как есть).
4. `delayed_ice` по образцу rustc — с Э2, когда чекер держит инварианты
   поверх Err-узлов: сломанный инвариант при уже выданной пользовательской
   ошибке гасится; при чистой компиляции — стреляет.
5. Языковая защита (assert/контракты/границы) не выключается никаким
   профилем сборки novac — и это не настройка, а определение цели
   «стабильность прежде скорости».
6. **`ice` на ошибке ПОЛЬЗОВАТЕЛЯ запрещён** (интегратор 2026-08-16, ревью
   ice-мест: «`match x { }` — это ошибка пользователя, не инвариант»). Ice —
   про сломанный инвариант КОМПИЛЯТОРА; всё, что пользователь может набрать
   руками (неизвестное поле, несвязанное имя, арифметика на не-числах, match
   без рук, перегрузка), — диагностика §7 из `check`, нулевая терпимость.
   Пока `check` эту проверку не держит, место живёт под маркером
   `[LEGACY-#NNN-user-error-as-ice until:<этап>]` — обязательно СО СРОКОМ;
   наступил этап — страж красный, перенос в `check` той же волной. Класс
   тот же, что у временных рёбер §3: срок якорится строкой `stage:` в
   `novac/nova.toml`, поэтому носитель проверки — тот же страж, не второй.


**Механизм.** `check-novac-no-naked-panic.sh` — голый `panic(` вне двери `ice()`; `check-novac-temp-edges.py` — маркер `user-error-as-ice` без `until:` или переживший этап `stage:` красный (п. 5); `check-novac-ice-messages.sh` — текст каждого `ice()` уникален и начинается с модуля (П20: site схлопнут обёрткой, текст его заменяет); `check-novac-no-panic.sh` и мутационный фаззер — ноль паник на любом входе. ⚖ Немашинная половина, названная честно: «этот инвариант стоит проверять здесь, а не там» — суждение приёмки, скриптом не формализуемо.
## П13. Документация — у каждого типа, поля и функции; данные — value-записями, kind — суммой

Требование владельца 2026-08-14 (типы и поля) и 2026-08-15 (функции: «все
функции описаны простыми словами, коротко, ///-док, всё по-английски»).
Судья — `check-novac-type-field-docs.py`; дисциплину резолва рядом держит
`check-novac-resolve-discipline.sh`.

1. **Каждая `type`-декларация и каждая `fn` — `///`-док строкой выше**:
   простыми словами, коротко (одна-две строки — что это / что делает), **по-
   английски** — это относится ко ВСЕМ `///`-докам novac. Атрибуты (`#impl`,
   `#stable`) между доком и декларацией допустимы. Внутренние функции — тоже
   `///`: LSP hover не различает export, а читатель кода — тем более.
2. **Каждое поле записи и каждый вариант суммы — `///`-док** (D104 rev-2, влит
   `9a69411b3` 2026-08-15 по брифу этого окна): две законные формы — **trailing**
   `lo int /// start, inclusive` (короткое описание; табличная читаемость — предпочтение
   владельца) и **строкой выше** `/// ...` над полем (длинная дока); обе на одном
   элементе — `E_DOC_BOTH_FORMS`; trailing на декларации — `E_DOC_TRAILING_ON_DECL`.
   Обычный `//` у поля больше НЕ считается докой (LSP hover его не видит). Переход
   novac на `///` полей — той же волной, что двигает `oracle-pin` на ≥ `9a69411b3`
   (блокер: регресс std serde после `b088c5bb0`, реестр расхождений); до этого страж
   принимает `//` как переходную форму по флагу пина. Комментарий-заглушка хуже
   отсутствия — это приёмка, страж судит наличие.
3. **Связанные параллельные векторы объединяются в запись-строку** (модель
   rustc `IndexVec<Idx, RowDef>`): забытый push в один из параллельных
   векторов — тихий сдвиг индексов; запись делает рассинхрон непредставимым.
   Пара, что всегда ходит парой по сигнатурам (таблица имён + строки), — тоже
   одна запись с методами (`DefTable`, `FieldTable`, `Scope`).
4. **Записи-строки реестров — `value`-типы**: обычная запись Nova — GC-
   указатель, т.е. аллокация на строку и потеря локальности; `value` держит
   строки в буфере вектора (лагерь Zig InternPool / rustc по цене хранения,
   читаемость записи сохранена).
5. **Перечислимый разряд — сумма, не int-константы**: `kind int` с
   константами пропускает произвольный int и лишает match-полноты;
   `type Kind enum | ...` отдаёт суждение самому языку.
6. **Никаких хардкод-индексов предзасеянных сущностей** (модель rustc
   `CommonTypes`): seed возвращает фактический id, потребители сравнивают с
   полями `Prims`; тексты вида «ids 0..3» и проверки вида `t >= 4` — красные
   на ревью (устаревают молча).
7. **`[]T` — канон в коде, `Vec[T]` — компиляторная форма** (владелец
   2026-08-15): в исходниках novac, в именах типов реестра и в диагностиках
   пишется `[]int`; оракульское моно-имя `Nova_Vec____nova_int*` живёт ТОЛЬКО
   в поле `c_name` реестра как факт эмиссии оракула. Линт `W_VEC_SPELLING`
   держит это на письме.

## П14. Цена итерации — секунды; схема сборки — целевая, под храповиком

Требование владельца 2026-08-15 («секунды, а не минута» → «ещё в 4 раза» → «целевая
схема — в конвенцию + страж, чтобы ничего не сломалось и не просело внезапно»). Разбор и
числа — план [274.2](../plans/274.2-novac-iteration-cost.md). Судья —
`check-novac-iteration-cost.sh` (храповик цены в обе стороны).

**Целевая схема — что обязано быть верно всегда:**

1. **Оракул не в горячем пути.** Эталонный бинарь файла кэшируется по (cksum файла,
   mtime оракула); `nova build` оракула вызывается только при промахе кэша и ВНЕ пакета
   `examples/` (dep-lock не платится). Прогон, где оракул собирается на каждый файл, —
   дефект.
2. **Флаги C — оракульские, снятые машиной.** argv clang перехватывается один раз через
   дверь `NOVA_CLANG` (test_runner.rs) и кэшируется по mtime оракула; руками флаги не
   пишутся; `-g` снят, `-fuse-ld=lld` добавлен — это ЕДИНСТВЕННЫЕ две правки, обе
   записаны.
3. **PCH прелюдии рантайма** (`nova_rt.h`) строится раз на ревизию оракула и лежит в кэше
   рядом с argv; компиляция тела идёт против PCH.
4. **Один процесс на батч.** Всё, что судит МНОГО файлов (фаззер, дифф-раннер, страж
   мэнглинга), кормит `novac check <список>` / (когда появится) `novac emit --batch`
   одним процессом; MSYS-fork на файл — дефект (70–200 мс каждый под нагрузкой).
5. **Цена — число, не ощущение, и число ОТНОСИТЕЛЬНОЕ.** Каждый скрипт цикла печатает
   свою цену; база `scripts/guards/novac-iteration-cost.baseline` держит на ключ бюджет
   и последний факт. Судится в обе стороны: просадка сверх бюджета — красная; факт втрое
   лучше записанного — красное (база обязана подняться тем же коммитом, иначе гниёт и
   просадку потом не увидеть). Три поправки, купленные двумя ложными красными
   2026-08-15 (274.3/F10): (а) порог ускорения считается от ФАКТА, не от бюджета;
   (б) замеры мельче 0.2 с на ускорение не судятся — там шум планировщика больше
   сигнала; (в) бюджет масштабируется КАЛИБРОВКОЙ машины в том же прогоне (эталонный
   fork оболочки против записанного `cal-ms`): под полным гейтом тот же `novac check`
   даёт 3.3 с против 150 мс на тихой машине, и без поправки страж краснел бы на
   соседнем процессе, а не на коде. Плюс: rc замеряемой команды проверяется — цена
   упавшего механизма не считается ценой.

смоук тёплый 17 000 при факте 1.6–2.7 с · `novac check` 2 400 при факте 150–950 мс ·
фаззер 192 кейса 90 000 при факте 12–16 с · дифф-раннер examples 140 000 при факте

хуже), а не 20% шума на занятой машине; узкий коридор выключили бы, как №475/№587.

**Урок для драйвера novac (Э5/Э6), обязательный:** dep-lock только при изменении

## П15. Контекст компиляции — данные на ресивере; эффект — только способность

Вопрос владельца 2026-08-16 («во многих местах передаётся `ctx Ctx` — это не
эффект случайно?»). Ответ и правило:

1. **Эффекты Nova моделируют СПОСОБНОСТИ и управление** — `Fs`, `Os`, `Time`,
   `Random`, `Fail`, `Supervisor`. Семантический контекст (реестр типов,
   таблица методов, позиции) — чистые данные, и эффектом он НЕ становится.
   Три причины: (а) амбиентный контекст прячет поток данных, на видимости
   которого стоит карта §3/§4 архитектуры («что течёт по ребру» — под
   стражем `check-novac-deps.sh`); (б) каждое чтение платило бы диспетчеризацией
   через TLS-vtable в самом горячем цикле (`type_of`), при П14 «скорость —
   приоритет №1»; (в) эталоны единодушны: rustc держит `TyCtxt` явным, а
   амбиентный `ty::tls` оставляет для диагностик и отладки; Roslyn — `Binder`,
   Go — `*Checker`, Zig — `*Sema`.
2. **Плуминг снимается РЕСИВЕРОМ, а не амбиентностью.** Тройка `src`, `out`,
   `ctx` в каждой сигнатуре — это не «нужен эффект», это «нужна запись
   состояния прохода»: `type Checker { src, ctx, out }` и методы `@walk`,
   `@report_*`. Форма ровно та же, что у эталонов, и поток данных остаётся
   виден в типе.
3. **Признак, по которому отличать:** если сущность можно ПОДМЕНИТЬ на границе
   (реальная ФС против фиктивной, реальные часы против замороженных) — это
   способность, ей место в эффекте. Если её можно только ПРОЧИТАТЬ и она
   целиком вычислена нами же — это данные, им место в ресивере.



**Механизм.** `check-novac-effects-at-door.sh`: ниже двери (`novac/src/main.nv`) запрещены установка обработчика `with X = ...`, объявление эффекта и эффект в строке сигнатуры. Проверено при заведении: во всём `novac/src` ровно одно вхождение эффекта — `Fs` в самой двери. ⚖ Немашинная половина: признак «подменяемо на границе — способность, только читается — данные» остаётся суждением приёмки.
## П16. Страж не принят, пока самотест не ДОКАЗАЛ, что страж ловит

Требование владельца 2026-08-16: «при написании стража должна быть
самопроверка — страж обязан доказать, что ловит то, что требуется».

1. **Самотест обязан быть двусторонним.** Зелёная сторона — «чистый вход не
   краснеет» (нет ложняка). Красная сторона — «нарушение ВПРЫСНУТО, страж
   покраснел, и в stderr назван виновник поимённо». Самотест, в котором есть
   только зелёная сторона, ничего не доказывает: он останется зелёным и над
   стражем, который вообще ничего не делает.
2. **Проверка этого — не на честном слове, а мутацией.** Критерий приёмки:
   подменяем стража заглушкой из двух строк (`#!/bin/sh` и `exit 0`) и гоняем
   его самотест — самотест ОБЯЗАН упасть. Если он проходит над заглушкой,
   значит он не судит стража, а только рапортует. Это ровно мутационное
   тестирование, и обмануть его декларацией нельзя.
   Механизм: `check-novac-selftest-proves-red.sh` делает это для каждого
   стража novac на каждом прогоне гейта.
3. **У стража обязан быть ШОВ для подложки.** Аргумент `$2` (а где надо и
   `$3`) — override сканируемой директории, чтобы самотест строил крошечное
   дерево во временной папке, а не портил рабочее. Страж без шва вынуждает
   самотест либо трогать настоящее дерево, либо ограничиться зелёной
   стороной — и правило 1 становится невыполнимым.
4. **Красный случай обязан быть достижим на машине БЕЗ тяжёлых зависимостей.**
   Если часть самотеста требует оракула или сборки, у него должна остаться и
   дешёвая половина со своим красным случаем (урок `shell-freshness`):
   иначе на машине без оракула самотест тихо превращается в зелёную пустышку.
5. **Порядок работ:** страж и его самотест пишутся ОДНОЙ волной и одним
   слиянием. «Стража завёл, самотест потом» запрещено — это долг без
   механизма, тот самый класс, который правило и закрывает
   (см. план 254 «правила без механизма»).

## П17. Одно понятие — одна таблица строк; вызываемое имеет одну форму

Находка владельца 2026-08-16 («методы и функции создают две двери, а нам
этого не надо»). Класс, а не запись: в `sem` жили `DefTable` + `fn_rets` для
функций и отдельная `MethodTable` для методов, и каждый проход обязан был
знать про них два случая. План 273 §2 называет этот корень поимённо и
перечисляет, чем он оплачивается (№576, №536/534/514, №600, №611).

1. **Метод есть функция, у которой первый параметр помечен получателем**
   (форма плана 273). В novac это одна строка `FnDef { recv, name, ret, dup }`,
   где `recv = -1` означает свободную функцию, и одна таблица `FnTable`.
2. **Индекс — не реестр.** Над одними строками может быть сколько угодно
   дверей поиска (`by_key` для точной пары «получатель, имя», `by_name` для
   слабого «есть ли такое имя у кого-нибудь»). Второй реестр — это когда
   расходятся СТРОКИ, а не когда добавился ключ.
3. **Приёмка формулируется как УДАЛЕНИЕ** (план 273 §4.1): названо, какой
   второй путь снят, и показано, что поведение не изменилось — критерий
   §4.2: побайтово идентичный C на корпусе до и после.
4. **Механизм:** набор таблиц строк в `Ctx` перечислен в плане 274 §10.3б и
   сверяется стражем `check-novac-ctx-tables.sh`. Появление новой таблицы
   требует правки плана — то есть решения, принятого вслух, а не тихо.
   Почему именно так: правило «одно понятие — одна таблица» машине не
   формализуемо, а вот «состав реестров объявлен и сверен» — вполне, и оно
   ставит вопрос «зачем вторая?» ровно в тот момент, когда вторую заводят.

## П18. Дверь поиска не аллоцирует; составной ключ — не текст

Требование владельца 2026-08-16 после разбора синтезированного ключа:
«давай запретим этот класс». Класс шире ключа, поэтому правило — про
аллокацию в горячем пути, а не про одну его форму.

1. **Функция, которая ищет, ничего не строит.** Ни строк (интерполяция,
   `concat`, `StringBuilder`), ни временных векторов. Живой случай:
   `FnTable`/`FieldTable` собирали составной ключ как `"${owner}.${name}"` —
   аллокация и форматирование на КАЖДЫЙ поиск, в самом горячем цикле
   компилятора, при П14 «скорость — приоритет №1».
2. **Составной ключ выражается структурой, а не текстом.** Дверь берёт ОДИН
   ключ, который у зовущего уже есть (имя или id), одноимённые строки
   связаны полем `next`, второй ключ сравнивается ЦЕЛЫМ ЧИСЛОМ при обходе
   цепочки. Цепочки короткие по природе — в них попадают только вызываемые,
   буквально разделившие имя. Образцы: `FnTable.row_of`,
   `FieldTable.field_type`.
3. **Дверь и эмиттер различаются по делу, а не по имени.** Дверь только
   СПРАШИВАЕТ; эмиттер СТРОИТ текст, и строить — его работа. Признак
   эмиттера: буфер ему ДАЛИ снаружи (`StringBuilder` в сигнатуре или
   `@body`). Локальный `StringBuilder` внутри двери ролью эмиттера не
   считается — иначе дверь пряталась бы за собственным билдером. Метод
   таблицы (`*Table`) — дверь всегда, что бы ни было в теле: такие типы
   существуют ради поиска.
4. **Почему одного стража строковых ключей не хватило.** Он судит ТИПЫ
   таблиц (`Map[str`), а дверь `names` легальна — значит склейку ключа он
   пропускал по построению. И даже дописанная в него проверка вызова
   (`find("${…")`) не поймала бы форму, с которой всё началось: ключ
   собирался строкой ВЫШЕ, а в дверь уходила переменная. Правило судит
   функцию целиком — поэтому ловит обе формы.
5. **Механизм:** `check-novac-no-alloc-in-lookup.py`, самотест содержит и
   историческую форму дефекта, и регресс-случай на живой ложняк (эмиттер,
   который законно зовёт дверь).

## П19. Поле-ссылка называет пространство, куда ссылается

Вопрос владельца 2026-08-16: «`owner int` — почему не `owner_type_id`?
`owner_id`? насколько выбор имён в едином ключе?» Честный ответ на тот
момент: **не в едином**. `type_id` нёс суффикс, а `owner`, `recv`, `ret`,
`sum` были голыми — хотя все они хранят одно и то же, id типа. Конвенция
об этом молчала, стража не было; общепроектные `naming-conventions` и
`nv-coding-style` имена полей внутри кода намеренно не регламентируют.

1. **Два пространства — два суффикса.** В novac ровно два вида ссылок, и
   имя обязано говорить, в какое ссылается:
   * `_id` — **id сущности**, выданный реестром (id типа): `owner_id`,
     `recv_id`, `ret_id`, `sum_id`, `type_id`, `int_id`;
   * `_row` — **индекс строки** в названном векторе: `next_row`.
   Диапазон строк остаётся парой `_off`/`_cnt` (`row_off`, `row_cnt`,
   `payload_off`, `payload_cnt`) — это уже был единый ключ, он не менялся.
2. **Голое имя допустимо ровно одно — `payload`,** и только потому, что его
   смысл ПОЛИМОРФЕН: у `Def` он значит то id типа, то строку вариантов, то
   строку вызываемых, в зависимости от `kind`. Такое поле обязано сказать об
   этом в своём `///`-доке. Придумать ему суффикс — значит соврать в трёх
   случаях из трёх.
3. **Почему суффикс, а не тип.** Правильный ответ — типизированные индексы
   (`TypeId`, `FnRow` как newtype), и он записан задачей волны 3 плана 274.3.
   Пока все ссылки — голый `int`, единственный носитель пространства — имя.
   Когда типы появятся, правило смягчается до «имя ИЛИ тип», не раньше.
4. **Смысловая проверка на будущее:** если поле `int`, спроси «куда оно
   ссылается?». Нет ответа одним словом — поле, скорее всего, лишнее или
   полиморфное; ответ есть — он и становится суффиксом.
5. **Механизм:** `check-novac-ref-field-names.sh` судит поля `int` в записях
   `sem` — единственное место, где живут реестры. Смещения в тексте
   (`lo`/`hi`, `start`/`end` в `source`/`lex`/`tree`) ссылками не являются и
   правилу не подсудны.

## П20. Текст `ice()` заменяет собой место падения

Вопрос владельца 2026-08-16: «панику не возвращаем на место появления, чтобы
место возникновения было точным?» Проверено пробой — **не возвращаем, и это
не наш выбор, а предел языка**.

1. **Факт.** `ice()` — функция-обёртка над `panic`, поэтому рантайм пишет
   site ТЕЛА ОБЁРТКИ. Проба 2026-08-16: сломалось в вызывающей функции, а
   машинная запись дала `site: {file: icesite.nv, line: 5}` — строку самого
   `ice()`; `trace` при этом пуст. Значит все ICE новака схлопываются в одну
   строку `diag.nv`.
2. **Правильное лечение — языковое, и оно не наше.** Нужен аналог
   `#[track_caller]`: обёртка должна пробрасывать место вызова.
   `__FILE__`/`__LINE__` в Nova есть только внутри кодогена для контрактов и
   пользовательскому коду не отдаются. Просьба записана интегратору; до неё
   правило ниже.
3. **Пока места нет — носитель места это ТЕКСТ.** Каждое сообщение `ice()`
   обязано быть **уникальным** в пределах novac и начинаться с `<модуль>: `.
   Два одинаковых текста при схлопнутом site неразличимы — живой случай:
   `sem: expected a leaf` стоял сразу в `leaf_text` и в `leaf_kind`. Текст
   называет функцию или условие: `sem: leaf_text on a branch node`.
6. **Чего правило НЕ требует:** класть в сообщение позицию в ИСХОДНИКЕ
   пользователя. `ice` — про сломанный инвариант компилятора, а не про
   пользовательский файл; пользовательская позиция живёт в диагностике §7,
   и путать эти две вещи нельзя.
5. **Предусловие двери — `requires`, и их может быть НЕСКОЛЬКО** (владелец
   2026-08-17: «почему не два requires?»). Условие на аргумент живёт в
   СИГНАТУРЕ, где его читает вызывающий, а не в теле, где его видит только
   реализующий. Язык допускает список клауз — проверено пробой, — поэтому
   «первое условие в requires, второе assert'ом в теле» это не форма, а
   недоделка: у каждой строки `requires <усл>, "текст"` своё сообщение и своё
   место в отказе. Внутри тела `assert` остаётся для инвариантов, которые
   зависят от уже вычисленного, а не от входа.
6. **Условный инвариант — `assert`, не `ice`** (поправка владельца
   2026-08-16, после включения границы супервизора). `assert(cond, "текст")`
   сообщает файл, строку, свой текст и исходник условия; `ice()` не может ни
   того, ни другого — обёртка сообщает site своего тела, ради чего и просился
   `#[track_caller]` (запрос СНЯТ). За `ice()` осталось ровно то, где нужен
   `never`: позиция ЗНАЧЕНИЯ (`?? ice(...)`, арм-значение) и недостижимая
   точка отдельным оператором. Перевод сделан волной: 39 условных мест стали
   assert'ами, 46 вызовов `ice` осталось.
7. **Механизм:** `check-novac-ice-messages.sh` — уникальность текстов И
   запрет формы `if <усл> { ice(...) }`.

## П21. На закрытом множестве ветки «всё остальное» нет

Требование владельца 2026-08-16 по живому месту в `emit_type_decls`:
`if kind == TkRecord { … } else { emit_sum(…) }`.

1. **Что здесь плохо.** `else` значит «всё, что не запись, — сумма».
   Появится четвёртый вид типа — он молча уедет в эмиссию суммы. Это тот же
   №652 («тихий дефолт»), только на диспетчере, и он не даст ни ошибки, ни
   диагностики: программа просто сделает не то.
2. **Правило.** Разбор по виду — исчерпывающий `match` с именованной веткой
   на каждый вариант. Тогда новый вариант даёт ошибку компиляции ровно в том
   месте, которое обязано решить, что с ним делать.
3. **Различие, без которого правило вредит** (вопрос владельца 2026-08-17
   «в `bin_op_opt` на match не красивше?»). Есть два разных match'а, и
   запрет относится только к первому:
   * **диспетчер, обязанный РЕШИТЬ за каждый вариант** (вид типа в эмиттере,
     оператор в форме C) — исчерпывающий, `_` запрещён: новый вариант обязан
     дать ошибку компиляции ровно здесь;
   * **частичное отображение, у которого ТИП объявил частичность**
     (`-> Option[T]`, и ветка `_ => None`) — законно и читается лучше цепочки
     `if`: «этот токен не оператор» это ОТВЕТ для сорока трёх из шестидесяти
     двух видов токенов, а не догадка. Цепочка `if` тут ничего не защищала:
     забытый токен даёт `None` в обеих формах.
   Машинный признак ровно такой: ветка `_ => None` законна, любая другая
   `_ =>` на именованных вариантах — красная.
4. **Таблица пишется `match`, а не цепочкой `if`** (владелец 2026-08-17:
   «все три таблицы на match — такое предпочтительно»). Девятнадцать строк
   `if k == TokenKind.X { return Some(...) }` говорят ровно то же, что
   `match`, но читаются построчно вместо одного взгляда, повторяют имя
   переменной в каждой строке и прячут главное: это ОТОБРАЖЕНИЕ. Порог
   машинный — три ветки подряд: две ещё читаются как условие, три уже
   таблица. Держит `check-novac-table-is-match.sh`.
5. **Арм-заглушка `_ =>` запрещена** по той же причине. Подстановочник
   ВНУТРИ образца (`Leaf(_)`, `Branch { .. }`) — законен: это payload, а не
   ветка «всё остальное».
4. **Если ветка «остальное» всё же нужна — она обязана быть ОТКАЗОМ:**
   `ice(…)` для сломанного инварианта компилятора, `@refuse(…)` для формы вне
   подмножества, `NodeKind.Err` для парсера. Отказ — это честно; правдоподобная
   работа за неизвестный вариант — нет.
5. **Где правило НЕ применяется** (разобрано на живом дереве): заглядывание
   вперёд `peek() == TokenKind.X` — это вопрос «да/нет», у него `else` значит
   «не эта форма», и разбор идёт другим путём; и обычные булевы условия.
   Страж судит только разбор ПО ВИДУ (`kind`).
6. **Механизм:** `check-novac-no-default-branch.py`. При заведении он нашёл
   шесть таких мест в `emit_c` — среди них разбор `DefKind`, где имя типа в
   позиции вызова молча эмитилось как вызов функции.
8. **Уточнение владельца 2026-08-18: `_` не запрещён — он обязан быть
   ОБЪЯСНЁН.** Пункт 5 выше был строже намерения, и строгость имела цену.
   `TokenKind` — семьдесят вариантов; диспетчеру парсера, различающему
   пять из них, `match` был недоступен вовсе: либо семьдесят армов, либо
   запрещённый `_`. Осталась цепочка `if` — и оба стража (`table-is-match`,
   `no-default-branch`) вписали себе под неё исключения («диспетчеры с
   телами не судятся», «заглядывание `peek()` — вопрос да/нет»). Правило
   подгонялось под код вместо обратного, и это худший исход из возможных:
   конвенция цела на бумаге и мертва в дереве.

   **Новая формулировка.** Законных форм остатка три:
   * `_ => None` — частичность, объявленная ТИПОМ (как было, п.3);
   * отказ — `ice(…)` / `@refuse(…)` / `NodeKind.Err` (как было, п.6);
   * `_` с ОБЪЯСНЕНИЕМ — комментарием строкой выше или хвостом той же
     строки, не короче пяти слов, который говорит ЧТО туда попадает и
     почему это безопасно. Пять слов — тот же порог, что у «Donor: none»:
     «прочее» и «остальное» не объясняют, они переименовывают молчание.

   Молчаливый `_` остаётся красным: именно он проглатывает будущий вариант.
   Держит `check-novac-no-default-branch.py` (правило и самотест обновлены
   тем же слиянием).

## П22. Производное — функция, а не поле; состав полей строки объявлен

Требование владельца 2026-08-16 после разбора `recv_id`: «это противоречит
плану 273 и конвенции одной двери — придумай, как исключить появление такого
класса + страж».

1. **Класс называется так:** форма, объявленная канонической в плане,
   реализуется «почти» — таблицы свели, а строка сохранила ПРИВИЛЕГИРОВАННУЮ
   или ПРОИЗВОДНУЮ копию того, что должно читаться из общей структуры.
   Снаружи выглядит выполненным, внутри исключение живо. Три случая одной
   волны: `recv_id` рядом с параметрами (а прочие параметры выбрасывались),
   `dup bool` вместо сохранённого второго кандидата, `fn_rets []int` рядом с
   таблицей определений.
2. **Правило.** Значение, выводимое из уже хранимого, выражается ФУНКЦИЕЙ, а
   не полем. Образец: получатель — это `params[param_off]` у метода, и знает
   об этом ровно одна функция `FnTable.recv_of`; все прочие спрашивают её.
   Это та же норма, что у двери мэнглинга («имя — функция от сущности,
   никогда сохранённая строка»), распространённая с имён на любые факты.
3. **Механизм — тот же приём, что сработал для состава таблиц (§10.3б):**
   «производность» машине не формализуема, а СОСТАВ полей формализуем.
   Поля каждой строки реестра перечислены в плане 274 §10.3в с колонкой
   «зачем это поле, а не функция», и `check-novac-row-fields.sh` сверяет
   список с кодом в обе стороны. Новое поле требует правки плана — то есть
   ответа на этот вопрос в ту минуту, когда поле заводят, а не через полгода.
4. **Плюс узкий признак самого класса**, который страж проверяет отдельно:
   строка, хранящая общий список (пара `*_off` + `*_cnt`), не имеет права
   нести поле, именующее ОДИН выделенный его элемент (`recv*`, `self*`,
   `first*`, `head*`). Ровно эта форма и была. Признак срабатывает даже если
   поле честно вписано в план — потому что вписать можно и неверное решение.
5. **Признак для человека, до всякого стража:** если поле отвечает на вопрос
   «какой из уже хранимых элементов особенный» — это производная. Особенность
   выражается функцией доступа, иначе поле и список разойдутся.

## П23. Представление не допускает состояний, запрещённых инвариантом

Находка владельца 2026-08-16 на `ParamDef.is_recv`: «получатель может быть
только первым параметром, а флаг сидит во всех — кажется, это увеличение
инвариантов, которое страж не ловит».

1. **Что было не так.** Флаг на КАЖДОМ параметре допускает «третий параметр —
   получатель» и «получателей два». Язык это запрещает, но представление —
   нет, и инвариант держится дисциплиной. Каждый такой бит — новый инвариант,
   который кто-то обязан помнить.
2. **Как решается.** Отделить ДАННЫЕ от ПРАВИЛА. Позиция получателя — не
   данные: её фиксирует план 273 §4.4 («первым параметром, без исключений»).
   Остаётся ровно одно данное — есть получатель или нет, факт вызываемого, и
   он выражается одним битом на вызываемом. Запрещённое состояние становится
   невыразимым, а не запрещённым.
3. **Порядок проверки при заведении поля:** перечисли состояния, которые
   новое поле делает выразимыми. Есть среди них запрещённые языком — поле
   стоит не на том уровне. Свойство, которое по инварианту может держать лишь
   ОДИН элемент, принадлежит владельцу списка, а не элементу.
4. **Осторожно с маятником.** Обе крайности — ошибки одного рода: бит на
   контейнере, дублирующий уже хранимое (П22), и бит на каждом элементе,
   выражающий свойство всего списка (П23). Вопрос один: **это свойство
   элемента или списка?** — и ответ на него определяет уровень.
5. **Механизм и его предел.** `check-novac-row-fields.sh` требует, чтобы
   булево поле строки-ЭЛЕМЕНТА несло в §10.3в пометку «[на элемент]». Это не
   доказательство — это принудительный вопрос: автор обязан вслух сказать,
   что бит различается у разных элементов. Для `is_recv` честный ответ был бы
   «нет», и поле не появилось бы. Формализовать «не допускает запрещённых
   состояний» машине нельзя; заставить задать вопрос — можно.

## П24. Дверь мэнглинга односторонняя: C-имя не разбирают обратно

Реакция владельца 2026-08-16 на нормативный алгоритм D285 §3 («извлечь
base-type: strip `Nova_`/`NovaValue_`, `*`, часть до первого `____`») — «это
бред какой-то, бери практики из раста и других языков с дженериками». Он
прав, и вот почему это не вкусовщина.

1. **Что там происходит.** Идентичность типа восстанавливается РАЗБОРОМ
   МАНГЛ-ИМЕНИ: компилятор выбрасывает структурную информацию в строку и
   потом парсит строку обратно, чтобы понять, какой это тип. Идентичность
   протекает через слой ABI — то есть через самый нижний слой, который по
   определению ничего не обязан сохранять.
2. **Почему это ломается именно на дженериках.** Разделитель `____`
   становится значащим, и всякий тип, чьё имя его содержит, разбирается
   неверно; вложенность (`Vec[Vec[int]]`) не восстанавливается вовсе;
   а любое изменение схемы имён меняет СЕМАНТИКУ резолва.
3. **Как у эталонов.** rustc резолвит по `Ty`/`DefId`; `rustc_symbol_mangling`
   — односторонняя функция от инстанса, и символьные имена не парсятся ради
   семантики (демангл существует для человека и отладчика, не для чекера).
   Swift: резолв по `CanType`/декларациям, мангл — вывод. Go: `types.Type`,
   имена символов вторичны.
4. **Правило.** Дверь мэнглинга — функция ИЗ сущности В строку, и обратного
   хода у неё нет. Всякий вопрос «какой это тип» задаётся РЕЕСТРУ (id типа,
   голова конструктора, строка вызываемого), а не имени.
5. **Спека сама себе противоречит,** и это эскалировано: D315 запрещает
   хранить ABI-факты в типе («мангл-имя — решение лоуэринга, не свойство
   типа»), D285 §3 предписывает через них резолвить. Описанный там алгоритм
   — описание реализации оракула, а не язык.
6. **Механизм:** `check-novac-mangling-one-way.py`. На сегодня novac чист:
   `____` встречается только в комментариях, ОПИСЫВАЮЩИХ форму чужих имён, и
   это законно (самотест держит отдельным случаем).

**Вторая половина правила: у имени есть ПРОСТРАНСТВО, и оно говорит, чьё имя**
(вопрос владельца 2026-08-17 по `NOVAC_TAG_`/`novac_make_`/`Nova_..._method_`:
«есть какая-то система?»). Система была, но не была записана — а незаписанная
система это привычка, которая расходится при первом же новом имени.

| префикс | чьё | примеры | кто стережёт |
|---|---|---|---|
| `Nova_...`, `nova_...` | **оракула и его рантайма** — мы их не выдумываем, совпадение с ними И ЕСТЬ ABI | `Nova_<Тип>_method_<имя>` (точки входа std), `nova_fn_main_impl`, `nova_alloc`, `nova_print_*`, `nova_int_checked_*` | `check-novac-mangle-fixed-point.sh` — каждое такое имя обязано существовать в оболочке |
| `novac_...` | **наше**, функции | `novac_user_<имя>`, `novac_make_<Сумма>_<Вариант>` | `check-novac-emitted-names.py` |
| `NOVAC_...` | **наше**, константы перечисления (заглавные — конвенция C) | `NOVAC_TAG_<Сумма>_<Вариант>` | там же |
| `_novac_...` | **наше**, временные; ведущее подчёркивание значит «не имя пользователя» | `_novac_tmp_*`, `_novac_scr_*`, `_novac_match_*`, `_novac_strlit_*` | там же |

Приставка `c` в наших префиксах — не украшение: она гарантирует, что ничто
выдуманное novac'ом не столкнётся с рантаймом, даже если оракул однажды
заведёт функцию с тем же смыслом. Регистр тоже не произволен: он говорит, ЧТО
это в C — тип оракула сохраняет его регистр, константа перечисления заглавная,
функция и локаль строчные.

## П25. Оракул — неподвижная точка ПОВЕДЕНИЯ, а не образец УСТРОЙСТВА

Указание владельца 2026-08-16: «не надо брать плохое из текущего
компилятора, а там всё, я подозреваю, плохое; бери практики из раста и
других языков с дженериками».

1. **Разделение, которое обязано быть явным.** У novac есть два совершенно
   разных отношения к оракулу, и их легко спутать, потому что вся приёмка E1/E2
   держится на слове «идентично»:
   * **ABI и наблюдаемое поведение — копируем точно.** Имя входного слота
     рантайма, форма эмиссии записи и суммы, набор хелперов, коды выхода,
     текст диагностик по схеме §7. Это неподвижные точки: расхождение здесь
     ломает линковку или тесты, и стражи (`shell-freshness`,
     `mangle-fixed-point`, дифф-корпус, смоуки) существуют ровно чтобы их
     держать. Копировать ВЫХОД оракула — законно и обязательно.
   * **Устройство — не копируем НИКОГДА.** Как у оракула устроены типы,
     резолв, каналы, мономорфизация — это не образец. Замер этой сессии:
     три параллельных представления типа без единственной правды, две копии
     нормализации ресивера, согласованные комментарием «Mirror of…»,
     `Raw(String)` внутри перечисления типов как «transitional debt carrier»,
     `ResolvedType` без `Eq`/`Hash` — тип, который физически не может быть
     ключом словаря, и резолв через разбор мангл-имени (П24).
2. **Образец берётся у эталонов, а не у соседа.** Для слоя типов и
   мономорфизации это rustc (интернированный `Ty`, `TyKind::Adt(def, args)`,
   `Instance(DefId, substs)`), Swift, Go 1.18, C#. Карта эталонов уже записана
   в 274.1 §2 — правило лишь запрещает подменять её оракулом «потому что он
   рядом и его код можно прочитать».
3. **Признак нарушения:** фраза «сделаем как в оракуле» про ВНУТРЕННЕЕ
   устройство. Законная форма той же фразы — «повторим ВЫХОД оракула на этой
   фикстуре», и она всегда сопровождается фикстурой.
4. **Механизм.** Машинно проверяется только половина: законное зеркалирование
   выхода держат `check-novac-mangle-fixed-point.sh` и дифф-корпус, а
   незаконное зеркалирование идентичности через имена — `check-novac-mangling-one-way.py`
   (П24). «Не копировать устройство» целиком не формализуемо: это суждение
   приёмки, и оно помечено таким честно, как требует норма 254 — правило без
   механизма обязано быть НАЗВАНО правилом без механизма, а не притворяться
   проверенным.

## П26. Командная поверхность novac — подмножество nova-cli, и по именам, и по действиям

Указание владельца 2026-08-16: «в `main.nv` ты выдумываешь свои команды, а
должен брать команды nova-cli — не только названия должны совпадать, но и
действия».

1. **Почему это не мелочь.** novac делается ЗАМЕНОЙ nova-cli, а не соседом:
   однажды пользователь перестанет замечать, какой бинарь у него под рукой.
   Всякая выдуманная команда — это работа по её последующему сносу плюс
   расхождение в привычках, в чужих скриптах и в документации.
2. **Имена.** Множество команд novac обязано быть ПОДМНОЖЕСТВОМ команд
   nova-cli. Обратное включение не требуется: novac не обязан уметь всё.
   Проверено при заведении правила: `check` совпадал, `emit` был выдуман.
3. **Действия.** Одноимённая команда обязана делать ТО ЖЕ: тот же вердикт,
   тот же код выхода, тот же смысл аргументов. Машинная половина уже есть и
   работает — `check` судится дифференциально против оракула на корпусе
   (`check-novac-differential.sh`, `novac-diff-corpus.sh`): совпадение
   «принял/отверг» и кодов выхода. **Новая общая команда не заводится без
   дифференциальной фикстуры** — иначе её поведение никем не сверяется.
4. **Расхождение — только осознанное и записанное.** Файл
   `novac/cli-divergences.allow`: строка «команда # причина и УСЛОВИЕ
   СХОЖДЕНИЯ». Условие схождения обязательно: расхождение без условия — это
   не решение, а долг без срока. Сегодня в файле ровно одна строка, `emit`.
5. **Что НЕ входит в машинную половину** (и потому названо честно): совпадение
   флагов, текстов помощи и формулировок ошибок. Это следующая волна правила;
   пока — приёмка.
6. **Механизм:** `check-novac-cli-surface.sh` (имена + allow) и
   `check-novac-differential.sh` вместе с дифф-корпусом (действия).

## П27. Решение называет донора указателем — или честно говорит, что донора нет

Требование владельца 2026-08-16: «в каждом коммите должно быть доказательство,
что мы не изобретаем велосипед, а взяли то, что коммитим, у донора».
Сформулировано так, чтобы это было проверяемо, а не ритуально.

1. **Что считается доказательством.** Не «взяли у rustc» — это утверждение,
   его нельзя проверить, и оно за неделю превращается в дежурную фразу (ровно
   так «идентично оракулу» жило до §7.0). Доказательство — **указатель**:
   донор **плюс сущность**, по которой читающий может открыть источник и
   сравнить сам. `rustc TyCtxt (rustc_middle::ty)` — да; `rustc` — нет.
   `Go types2.Info`, `Zig InternPool`, `Roslyn Binder`, «Dragon Book §6.3»,
   ссылка на статью — да. Имя языка без сущности — нет.
2. **Три части, не одна** (уточнение владельца 2026-08-16: «должно быть
   указано кто донор и зачем это нужно в общем плане, как и кем будет
   использоваться дальше»). Указатель без места в общей картине — просто
   ссылка; читающему нужны:
   * **Donor** — у кого взято, сущностью; и что НЕ взято: донора никогда не
     берут целиком (у rustc интернер, но не арены; у Go предикат протокола, но
     не словари; у Roslyn зелёное дерево, но не красное);
   * **Role** — зачем это в общем плане: какое место в карте слоёв занимает,
     какой класс задачи закрывает, что было бы без него;
   * **Used by** — кто потребитель дальше: какой слой или модуль читает это и
     на каком этапе (Э2-б1/б2/б3, Э3, Э4). Решение, которого никто не
     потребляет, — подозреваемое; решение, потребитель которого не назван,
     потеряет своего потребителя при первой же переделке;
   * **Guarded by** — кто и как АВТОМАТИЧЕСКИ проверяет, что решение
     используется правильно дальше: имена стражей (файлы `check-*.sh`) или
     тестов, которые покраснеют при неверном использовании. Это замыкает
     круг с П16 и П22: решение без названного стража невидимо механизму, и
     его правильное использование держится памятью — то есть не держится.
     Названный страж обязан **существовать файлом**; несуществующий — красный.
     Честная форма для решения, которое пока держит только компилятор или
     приёмка: `Guarded by: compiler — <что именно ловит>` либо `Guarded by:
     acceptance — <почему машиной пока нельзя>` (норма 254: правило без
     механизма обязано быть НАЗВАНО таковым).
   В заголовке модуля все ЧЕТЫРЕ обязательны; в сообщении коммита — Donor
   обязателен, остальные желательны.
2а. **Оракул донором быть НЕ МОЖЕТ** (владелец 2026-08-16: «мы должны
   использовать в качестве доноров другие современные компиляторы, но никак
   не наш текущий»). Это прямое следствие П25 — оракул есть неподвижная точка
   ПОВЕДЕНИЯ, а не образец устройства — но записывается отдельно, потому что
   первый же аудит донорских строк нарушил его: `emit_c` получил «Donor: the
   oracle's emission», то есть форму своей эмиссии объяснил ссылкой на то, что
   она совпадает с оракулом. Совпадение выхода — не донорство. Законные доноры
   формы: rustc, Go, Swift, Zig, Roslyn, clang/LLVM, C#/.NET, Koka, учебники и
   статьи. Слова «oracle», «нынешний компилятор», `nova-cli`,
   `compiler-codegen`, `emit_c.rs` в строке `Donor:` — красный. Если форма
   взята ниоткуда, кроме как «повторяет оракула», честный ответ —
   `Donor: none — <причина>`; ниже поведение всё равно держит дифф-гейт.
2б. **Иерархия доноров** (владелец 2026-08-16: «основной донор — rust, go для
   M:N»). Не всякое имя в строке `Donor:` весит одинаково, и указатель обязан
   это отражать:
   * **основной — rustc**: слои типов, вывода, канала чекера, mono, layout,
     мэнглинга; когда rustc и другой донор расходятся, побеждает rustc, если
     спека Nova не требует иного;
   * **слоевые**: **Go** — M:N-рантайм (уже вендорено: `runq.h`) и
     СТРУКТУРНЫЙ предикат протоколов (`types2`: наши протоколы по D53
     структурные, как интерфейсы Go, а не номинальные, как трейты; брать
     rustc trait selection значило бы тащить когерентность и orphan-правила,
     которых у нас нет); **Roslyn** — фронтенд и IDE-слой (у rustc нет
     полнофидельного дерева: rust-analyzer держит второй парсер, Roslyn один
     раз сделал так, что компилятор и IDE читают одно дерево — это наше Э3);
   * **точечные**: Zig `InternPool` — только форма плоского интернера (у rustc
     он на аренах, нам под GC не годится); Koka — только evidence passing для
     быстрых эффектов; Nim/Chicken — только «C как текст из типизированного
     дерева» для эмиттера;
   * **антипримеры, не доноры**: Swift и C# — записаны в карте слоёв как
     «расходятся, и вот от чего это зависит» (ранжирование перегрузок,
     словари вместо mono); ссылаться на них можно только формой «НЕ взято у X
     потому что».
   Указатель на точечного донора там, где решение принадлежит основному
   слою, — красный на ревью: «Zig InternPool» для интернера — да; «Zig» для
   резолва методов — нет.
3. **Честное «донора нет».** Часть решений действительно наши: `Verdict`
   суммой вместо int-кода, честный отказ вместо тихо неверного кода, маркер
   `[LEGACY-#NNN]`. Их форма — `Donor: none — <причина>`. Прятать своё
   решение за фальшивым донором **хуже**, чем сказать прямо: фальшивый донор
   потом кто-нибудь пойдёт сверять.
4. **Граница правила — РЕШЕНИЯ, не правки.** Форма данных, алгоритм, слой,
   дверь — решение. Починка ложняка стража, переименование, перенос строки —
   нет, и выдумывать для них донора запрещено; законная форма —
   `Donor: none -- mechanical fix, no design decision` (в СООБЩЕНИИ коммита тире
   пишется `--`: сообщения по норме ASCII, и хук `check-commit-hygiene` красит
   длинное тире; в заголовке `.nv` допустимы обе формы).
5. **Где живёт указатель.** Дважды, и это не дубль: в **заголовке модуля** —
   как постоянная правда о его форме (с границей «взято / не взято»); в
   **сообщении коммита**, который вводит или меняет решение, — как след во
   времени. Замер при заведении: из четырёх коммитов волны Э2-б1 донор был
   назван в одном, и без сущности.
6. **Механизм.** `check-novac-commit-donor.sh` — из хука `commit-msg` через
   `check-commit-hygiene`, только когда в индексе есть `novac/src/*.nv` (не
   тесты): строка `Donor:` обязательна, голое имя языка — красный, `none` без
   причины — красный. Заголовки модулей судит `check-novac-module-donor.sh`:
   у каждого модуля novac ЧЕТЫРЕ строки — `// Donor:` (сущность либо честное
   `none — причина`), `// Role:` (место в общей картине), `// Used by:` (кто
   потребитель и когда) и `// Guarded by:` (какие стражи держат правильное
   использование; каждый названный `check-*.sh` обязан существовать).
   Правдивость указателя машина не проверяет — это приёмка, и это сказано
   честно; страж заставляет **назвать**, а не доказывает.

## П28. Предкомпилированная прелюдия обязательна во ВСЕХ режимах компиляции

Указание владельца 2026-08-17: «PCH обязателен во всех режимах, в конвенцию +
страж».

1. **Факт, из которого правило.** `nova_rt.h` тянет `gc.h` и libuv — 82 тыс.
   строк после препроцессора. Без предкомпилированной прелюдии их разбирает
   КАЖДЫЙ вызов компилятора C: 0.43 с на файл против 0.22 с (план 274.2 §2).
   На горячем цикле это половина времени; смоук стал 1.7 с вместо 40 с ровно
   на этом.
2. **Правило.** Любой режим, который компилирует C, несёт `-include-pch`.
   Прелюдия строится ОДИН раз на ревизию оракула (`-x c-header` → `*.pch`,
   имя со штампом ревизии) и переиспользуется, пока файл существует.
   Исключены ровно две вещи: сборка самого PCH и ЛИНКОВКА — она ничего не
   разбирает.
3. **Почему «во всех», а не «в смоуке».** До этого правило жило одной
   строчкой в одном инструменте и держалось памятью автора: убери
   `-include-pch` — и увидит это только страж цены цикла по бюджету времени, у
   которого восьмикратный запас, то есть скорее всего не увидит. Цена,
   добытая заменой, обязана быть под замком.
4. **Что НЕ покрыто и почему это записано, а не забыто.** `nova build`
   оракула PCH не использует вообще (замер 2026-08-17 перехватом командной
   строки: один вызов clang, `-O0 -g`, ноль упоминаний pch), а механизм уже
   написан и работает у нас. Это не наша земля: требование записано в 274.2
   §1а как ЦЕЛЕВАЯ СХЕМА СБОРКИ и передано интегратору; страж держит нашу
   половину, чтобы правило было живым, а не декларацией.

**Механизм:** `check-novac-pch.sh` — каждая компиляция C в инструментах novac

## П31. Ветвление обязано быть полным, а несколько `if` об одном предмете — это `match`

**Правило владельца, 2026-08-17, дословно:** «все ветвления обязательны, else
обязателен, если условие пусто, ты должен явно это обозначить, что это
валидная ситуация» и «несколько if объединяй в match».

**Часть 1 — полнота.** Ветвление считается полным в одной из трёх форм, и все
три ЯВНЫЕ:

1. `if ... { ... } else { ... }` — обе ветки написаны;
2. then-ветка кончается ТЕРМИНАТОРОМ (`return`, `continue`, `break`, `throw`,
   `ice`) — тогда «иначе» это остаток функции или следующая итерация, и он
   явен по конструкции;
3. `else { }` пустой — законен, но ОБЯЗАН нести комментарий с причиной:
   почему ничего не происходит и почему это правильно.

**Часть 2 — несколько `if` об одном предмете collapse в `match`.** И это не
стилистика, а единственная форма, которую держит МАШИНА: `match` по сумме
исчерпаем по конструкции — компилятор сам не даёт пропустить вариант
(реестр №703, а с 2026-08-17 то же правило есть и у novac). Цепочка `if` этой
гарантии не даёт никогда: пропущенная ветка выглядит не как ошибка, а как
отсутствие кода.

**Откуда правило.** За смену 2026-08-17 четыре дефекта родились из одной
формы — решение принимается в `if`, вторая ветка не названа, вход
проваливается мимо:

* тип параметра читался как один идентификатор, `Vec[T]`/`[]int`/`fn(A) -> B`
  разваливали сигнатуру;
* тип ВОЗВРАТА не судил никто: `fn make() -> []int => 1` принимался молча;
* каноническая сумма `type X enum ...` не разбиралась, а отменённая форма —
  разбиралась;
* объявление метода в пользовательском файле роняло компилятор через ice.

Ни один не выглядел как ошибка В коде. Все выглядели как ОТСУТСТВИЕ кода —
ровно то, что даёт `if` без `else`.

**Механизм: `check-novac-branch-complete.py`, и он ЗАПРЕТ.** Правило введено
2026-08-17 храповиком — неполных ветвлений было 191 из 533, и запрещать их
одним движением значило бы либо красный гейт на неделю, либо 191 механическую
правку без разбора. **Ноль достигнут в тот же день**, поэтому база
`novac-branch.baseline` стоит на нуле, и любое новое неполное ветвление
краснеет немедленно.

База осталась числом, а не флагом, по одной причине: если правило когда-нибудь
придётся ослабить, послабление будет ВИДНО цифрой в файле и в диффе, а не
спрятано исключением внутри стража.

**Чем закрывались 191 — по формам, а не штампом.** Одиночный `if` в теле цикла
стал инвертированным стражем `if !cond { continue }` (полон по терминатору, и
работа вышла из вложенности). Накопители перестали быть ветвлениями вовсе:
`flag = flag || cond`, `n += if cond { 1 } else { 0 }` — флаг, который только
включается, ЕСТЬ дизъюнкция. Разделители и запасные значения ушли внутрь
вызова выражением: `@body.append(if first { "" } else { ", " })`. Закрытая
сумма внутри ветки стала исчерпаемым `match`. И только там, где у второй ветки
действительно нет работы, стоит пустой `else` — с причиной, объясняющей ПОЧЕМУ
ничего не происходит, а не пересказывающей условие.

## П30. Сборка novac идёт без предупреждений компилятора

**Правило.** Ноль предупреждений в логе сборки novac. Не «поменьше», не «не
считаем doc-warning'и» — ноль. Предупреждение о ЧУЖОМ коде (std, рантайм,
оракул) нашим красным не является; предупреждение, указывающее в
`novac/src`, — является всегда.

**Откуда взялось.** 2026-08-17, при правке диагностики, сборка напечатала
двадцать пять раз: «doc-comment (`///`) before bare module-level `ro` is
ignored». То есть двадцать пять мест, где я писал документацию, а компилятор
её ВЫБРАСЫВАЛ, — и месяц никто этого не видел, потому что предупреждения
проматывались вместе со строкой `built:`. Предупреждение, на котором никто не
краснеет, — это правило, которого нет; ровно тот же корень, что у класса О-2
в реестре расхождений («правило объявлено, механизма нет»), только с другой
стороны: механизм говорил, а слушателя не было.

**Что делать с неустранимым.** Если предупреждение чужое и снять его нельзя —
оно подавляется маркером `[LEGACY-#NNN]` со сроком, как любой другой обход, а
не привычкой пролистывать.

**Механизм.** `check-novac-build-clean.sh` судит лог `target/novac-build.log`,
который пишет шаг `novac-build` гейта; если лога нет — собирает сам, а не
отвечает «судить нечего» (274.3/F1: молчание, выходящее нулём, — это дыра, а
не зелёный). Самотест доказывает красноту подложным логом и отдельно
проверяет, что предупреждение о чужом коде красным НЕ становится.

## П29. Строка не длиннее 120 символов

Указание владельца 2026-08-17 по живой строке в 258 символов
(`is_expr_kind` одной цепочкой): «определить максимальную разумную длину
строки и соблюдать её».

1. **Предел 120, и он замерен, а не выдуман.** По `novac/src`: при 120
   нарушают 66 строк из ~6000, при 100 — 141, при 140 — 36. Сто двадцать —
   норма отрасли (rustfmt ставит 100, ядро Linux ушло с 80 на 100) и та
   граница, за которой строку перестают читать целиком: диффы, обзор бок о
   бок и терминал на половину экрана рвут её молча.
2. **Четыре исключения, и каждое — предел ЯЗЫКА, а не лень.** Проверено
   пробой в тот же день: Nova не позволяет перенести ни список импорта
   (`expected identifier, got newline`), ни образец арма (`expected =>, got
   newline`). Поэтому не судятся: строка `import`; образец арма (до `=>`
   только имена вариантов и `|`); строка с ОДНОЙ длинной строковой литерой
   (60+ символов) — резать текст диагностики пополам хуже, её потом ищут
   грепом; хвостовой `///`-док у поля, если код до него укладывается (форма
   `field int /// текст` установлена D104 rev-2).
3. **Проза комментария судится.** Она переносится по словам, и почти все
   нарушения были именно ею — шапки `Role:/Used by:/Guarded by:`.
4. **Побочный урок, оплаченный тут же:** перенос прозы РАЗОРВАЛ подавление
   линта — маркер `// nova:allow ...` должен стоять строкой ВПЛОТНУЮ над
   армом, линтер сопоставляет построчно. Правило: длинную причину пишем
   выше, а на строке-маркере оставляем короткую.

**Механизм:** `check-novac-line-length.sh`.

несёт `-include-pch`; есть сборка PCH со штампом ревизии и с проверкой
«файла нет».

## П32. Коллекция не перекладывается поэлементно

**Правило.** Цикл, чьё тело — ровно один `push` его же переменной, писать
нельзя: `for n in @type_ref() { out.push(n) }` — это `out.append(@type_ref())`.
В std есть дверь `Vec[T].append(other AsSlice[T])`, и она была там всё время.

**Откуда.** Владелец, 2026-08-18, глядя на седьмой такой цикл подряд в парсере:
«почему не `out.append(@type_ref())`?». Честный ответ — потому что я ни разу не
спросил std, есть ли у Vec эта операция. Семь циклов писались один за другим,
и каждый следующий копировал форму предыдущего, а не проверял её.

**Почему это не вкусовщина.** Своя копия операции повторяет её реализацию:
читатель обязан разобрать имя переменной, порядок обхода и то, что копируется
КАЖДЫЙ элемент, — лишь чтобы узнать «здесь дописали хвост». `append` говорит
это одним словом, не может ошибиться в границе и получает правки std даром.
Ровно тот же довод, по которому таблица пишется `match`, а не цепочкой `if`
(П21 п.3): конструкция обязана показывать НАМЕРЕНИЕ, а не его развёртку.

**Границы.** Цикл законен там, где он НЕСЁТ работу: `Z.push(f(x))`, условие
внутри тела, накопление рядом с push. Страж этого не трогает — он ловит ровно
переливание один-к-одному.

**Механизм:** `check-novac-no-copy-loop.sh` (запрет, не храповик: база 0 с
первого дня, потому что все семь носителей сняты тем же слиянием).
