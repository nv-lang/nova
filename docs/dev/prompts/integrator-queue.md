# Очередь интегратора — наблюдаемая, а не в голове

**Зачем этот файл.** Владелец 2026-08-09: «ты когда написал мне, остановился…
я же говорю работай без остановки»; и на предложение записать правило в память —
«память это ненадёжно». Он прав дважды.

Правило «ход не заканчивается текстом, если работа не закрыта» проверяемо только
если «работа не закрыта» — **наблюдаемый факт**, а не моё воспоминание. Отсюда
этот файл: пока в нём есть незакрытые строки, остановка после отчёта есть
нарушение, видимое снаружи.

**Второй механизм, сильнее первого:** заканчивать ход **запуском фонового
действия** (гейт, окно, прогон). Тогда следующий ход приходит по уведомлению сам,
без реплики владельца. Шестичасовой простой 2026-08-09 (гейт упал в 04:50,
обнаружено в 10:47) случился ровно потому, что гейт был запущен через `nohup`
внутри команды — уведомления не было.

## Известные ограничения среды — чтобы не наступать заново

* **Мега-CU не укладывается в 10-минутный потолок команды.** Прямой
  `nova test --positive --compile-error spec_tests/conformance` даёт `RC=124`
  (таймаут) даже на 590 с. Запускать его следует ТОЛЬКО через
  `scripts/gate.sh` в фоновом режиме инструмента — гейт ведёт свой лог и пишет
  вердикт в `/tmp/gate_full.done`. На это же ограничение наткнулось окно
  `p255-profile` и честно доложило, что полный мега-CU измерить не смогло.
* **Фон через `nohup ... &` внутри команды НЕ даёт уведомления.** Так был
  потерян шестичасовой простой 2026-08-09 (гейт упал в 04:50, обнаружено в
  10:47). Запускать долгое только фоновым режимом инструмента.
* **`cargo build` из корня репозитория падает** (там нет `Cargo.toml`), но код
  возврата в фоне может прийти нулевым. Собирать из `nova-cli`, результат
  проверять по времени бинаря — `scripts/tools/rebuild-if-stale.sh`.

## Замер, который надо доделать: устраняется ли одноразовая `ro`-привязка

Владелец 2026-08-09 предложил для `IndexMapIter.@next()` заменить

    ro pair = @map.entries[@pos]
    @pos += 1
    Some(pair)

на `Some(@map.entries[{ ro i = @pos; @pos += 1; i }])`.

**Измерено (по порождённому C):** форма А заводит временную СТРУКТУРУ кортежа
(16 байт), форма Б — временный СКАЛЯР (8 байт). На уровне C разница реальна.

**НЕ измерено:** совпадает ли машинный код под `-O2`. Попытка получить
ассемблер не удалась (clang не отдал `.s`), обход не сделан. Осторожно: наивный
`diff` двух ПУСТЫХ выборок печатает «совпадает» — так и вышло в первой попытке,
результатом это не считается.

**Позиция до замера:** правка исходника отклонена. Одноразовая `ro`-привязка —
задача кодогена, а не стиля: её устранение чинит ВСЕ такие места, а
переписывание одного `next()` — один носитель. Если замер покажет разницу в
машинном коде — заводить дефект на кодоген, а не менять стиль. `post_inc()` на
всех `Ints` отклонён отдельно: поверхность языка ради неизмеренного выигрыша.

## Не проверено: входят ли `standalone` и `neg` в авторитетный гейт

Наблюдение 2026-08-09, **гипотеза, не факт** — проверять после того, как окна
отработают (мои тяжёлые прогоны сегодня трижды роняли их).

* Семь фикстур падают в `spec_tests/conformance/standalone` (формат
  panic-сообщений) — и при этом гейт зелёный. Значит `standalone` в
  авторитетный прогон, похоже, не входит.
* Обычный `nova test spec_tests/conformance/neg` даёт `PASS: 18 SKIP: 548` —
  почти вся neg-часть пропускается без `--compile-error`. Мега-CU этот режим
  включает и пишет `SKIP: 65` против базы 574, то есть храповик на пропуски
  там есть.
* В корне `spec_tests/conformance` 1161 файл, мега-CU отчитывается
  `PASS: 716 SKIP: 65`. Куда делись остальные — не установлено.

Проверять так: посчитать, какие ИМЕННО файлы попадают в мега-CU (лог мега-CU
пишется в `$MEGA_LOG`, сохранить его), и сверить множество с `find`. Если
`standalone`/`neg` вне гейта — это тот же класс, что №516: гейт проверяет
меньше, чем кажется.

## Потолок параллельных окон на этой машине — четыре

Установлено 2026-08-09 по ДЕСЯТИ срывам подряд. Окна падают с
`Agent stalled: no progress for 600s` не по задаче, а по нагрузке: при пяти-шести
одновременно работающих отдельные вызовы инструментов растягиваются дольше
сторожевого порога. Усугубляет любая тяжёлая команда интегратора параллельно —
полный `nova test`, `cargo build --release`, долгий прогон opencode; в те моменты
валилось по два-три окна разом.

Правила, выведенные из этого:

* держать **не более четырёх** окон; пятое — в очередь, а не в запуск;
* пока окна работают, у себя — только греп, чтение и правка файлов;
* в брифе требовать **чекпоинт-коммит перед каждым долгим замером** и дробление
  серий (не «200 прогонов одной командой», а по 25–50 с коммитом счёта каждой);
* упавшее окно возобновлять **сообщением**, а не новым запуском — оно продолжает
  со своей ветки и не перечитывает контекст.
