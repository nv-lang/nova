# Шаблон брифа окну (агент-исполнитель на sonnet/opus)

Соседний файл [opencode-brief-template.md](opencode-brief-template.md) — про
механического исполнителя, которому нельзя давать суждение. Этот — про **окно**:
агента, который сам ставит пробы, читает код и принимает мелкие решения внутри
поставленной рамки.

**Почему шаблон появился.** 2026-08-11 три окна подряд были сняты сторожем за
десять минут без вывода: одно собирало компилятор (две с половиной минуты
молчания), второе копировало libuv, третье гоняло `nova test`. Ни одно не
зависло — все три работали. Виноват был бриф: в нём не было сказано, что
молчание убивает. Правило, которое приходится вспоминать в каждом брифе, — не
правило, а забывчивость; поэтому оно теперь здесь, в §2, и копируется вместе с
остальным.

Копируй **целиком** и заполняй, а не сочиняй заново.

---

## 1. Запреты — дословно, без сокращений

```
# ЗАПРЕТЫ (нарушение = работа не принята)
- НЕ трогать главное дерево `d:/Sources/nv-lang/nova`. Только свой worktree.
- НЕ спавнить суб-агентов.
- НЕ гонять мега-CU и полный `nova test` — авторитетный гейт гоняет интегратор.
  Тебе только точечная верификация.
- `git add` ТОЛЬКО по именам файлов. Никогда `-A`, `.`, `-u`, `git commit -a`.
  Никогда `git stash` (worktree делят один `.git`).
- НЕ трогать `git config`. НЕ добавлять `Co-Authored-By`.
- Сообщения коммитов — ПО-АНГЛИЙСКИ (заголовок и тело). Отчёт — по-русски.
- Состояние-меняющие git-команды звать с явным `-C <путь>`: рабочий каталог
  оболочки дрейфует между вызовами.
- Номера дефектов и D-блоков сам не присваивай — пиши `№TBD`.
- Синтаксис Nova не выдумывай: написал код — прогони `nova check <файл>`.
  Компилятор авторитет, не твоя память.
```

## 2. Выживание под сторожем — вставлять ВСЕГДА

```
# КАК НЕ БЫТЬ СНЯТЫМ
- ДОЛГИЕ КОМАНДЫ ЗАПУСКАЙ ЧЕРЕЗ ОБЁРТКУ — она печатает отметку и не даёт
  прогону выглядеть молчанием:
      bash scripts/tools/with-progress.sh 30 cargo build --release --manifest-path nova-cli/Cargo.toml
      bash scripts/tools/with-progress.sh 20 ./nova-cli/target/release/nova.exe test <путь>
  Код возврата прокидывается без изменений — обёртка НЕ превращает провал в
  успех.
- КОММИТЬ ПО ЧАСТЯМ, а не в конце. Сделал измеримый кусок — запиши в файл и
  закоммить. Обрыв тогда стоит одного куска, а не всей работы.
- Не уводи в фон то, чего сам же ждёшь: фоновая команда без вывода — это
  молчание, и оно тебя убьёт.
```

**Почему обёртка, а не «печатай почаще».** 2026-08-11 сторож снял ПЯТЬ окон за
десять минут «без вывода», и ни одно не зависло: все собирали компилятор или
гоняли тесты. Молчит не окно, а КОМАНДА — `cargo build` пишет в свой лог, а не в
поток агента. Требовать дисциплины там, где нужен инструмент, — это «правило
вместо машины», от которого мы уходим везде (№574, №578, №596).

## 2-бис. Экономия лимитов — правило владельца, повторяется в каждом брифе

**Сначала спроси себя: нужна ли тут МОДЕЛЬ.** Перечисление, сверка, замена по
точному списку, сборка таблицы фактов — это `opencode`
([шаблон](opencode-brief-template.md)), а не окно на sonnet. Окно дороже в разы;
брать его на механику — трата лимитов.

**Чем детальнее бриф, тем дешевле исполнитель.** Точные команды целиком,
точные пути внутри проекта, явный список запретов и ОБРАЗЕЦ строки результата
позволяют отдать работу дешёвой модели. Расплывчатый бриф вынуждает брать
дорогую — то есть цена модели это следствие качества брифа, а не свойство
задачи.

```
# ДИСЦИПЛИНА CPU И ЛИМИТОВ
- НЕ гонять мега-CU и полный `nova test` — сорок минут чужой машины.
  Авторитетный гейт гоняет ИНТЕГРАТОР. Тебе — точечная верификация:
  своя фикстура, свой подкаталог, свой пакет.
- НЕ спавнить суб-агентов ни при каких обстоятельствах.
- Фоновые прогоны иногда ловят серверный rate-limit и падают. Поэтому
  СОХРАНЯЙ ПРОГРЕСС: каждый измеримый кусок — в файл и в коммит, сразу.
  Обрыв должен стоить одного куска, а не всей работы.
- Не пересобирай компилятор без нужды: 2.5 минуты за прогон.
```

**Если исполнитель — haiku:** добавить дословно
`НЕ ЗАХОДИТЬ в d:/Sources/nv-lang/nova ни для чтения, ни для записи — работай
ТОЛЬКО в своём worktree`. Причина: haiku путает деревья чаще прочих, а цена
ошибки в общем дереве — чужая работа. И не давать haiku классификацию и длинные
перечисления (дважды зависал по десять минут).

## 2-тер. Грепы, обязательные к исполнению

```
# ПЕРЕД КАЖДЫМ КОММИТОМ — В ОДНОЙ КОМАНДЕ С НИМ
git -C <дерево> diff --cached | grep -cE '^\+(<<<<<<<|=======|>>>>>>>)'
```
Ноль — коммить; иначе разбирай конфликт. **Именно в одной команде**: отдельным
шагом его забывают, и маркер уезжает в историю (правило владельца).

**Слияние, меняющее язык, не пушится без спек-амендмента** — D-блок в
`spec/decisions/` и правка обзорной `spec/<тема>.md` тем же слиянием.

## 3. Настройка worktree

```
git -C /d/Sources/nv-lang/nova worktree add -b <ветка> /d/Sources/nv-lang/nova-<имя> main
cd /d/Sources/nv-lang/nova-<имя> && cargo build --release --manifest-path nova-cli/Cargo.toml
```
Worktree только в `d:/Sources/nv-lang/` (страж `check-worktree-location.sh`).
Если сборка ругается на GC/libuv — переменные на главное дерево:
`NOVA_GC_LIB_DIR`, `NOVA_INCLUDE_DIR`, `NOVA_GC_INCLUDE_DIR`,
`NOVA_RT_DIR=/d/Sources/nv-lang/nova/compiler-codegen/nova_rt`,
`NOVA_CG_INCLUDE=/d/Sources/nv-lang/nova/compiler-codegen`.
(`git worktree add` НЕ инициализирует подмодули — libuv в свежем дереве нет.)

## 4. Задача — три обязательных части

**Репро или отправная точка** — команда целиком, с ожидаемым выводом дословно.
Если репро уже поставлен интегратором, так и скажи: «воспроизведено, повтори
первым делом».

**Что факт, а что гипотеза.** Разделять ЯВНО. Бриф, написанный по чужому
непроверенному диагнозу, стоит окна целиком — прецедент №457. Формулировка:
«ФАКТ — …; ГИПОТЕЗА — …, независимо не подтверждена; если не подтвердится —
ОСТАНОВИСЬ и доложи, не чини по неверному диагнозу».

**Границы находки, если известны.** «Форма A падает, форма B работает» экономит
окну полдня и не даёт починить не тот носитель.

## 5. Приёмка — без неё работа не принимается

```
- Фикстура, утверждающая НАБЛЮДАЕМОЕ поведение (значение, счётчик, код возврата),
  а не отсутствие падения.
- Фикстура обязана ЗВАТЬ проверяемое: неиспользуемый код вычищается компоновщиком
  и не проверяется ничем (урок №577).
- Проба «подсунь негодное»: сломай свой фикс — покажи красное, верни — покажи
  зелёное. Вывод дословно в обе стороны.
- Фикс КЛАССА, а не носителя. Скажи, где ещё искал ту же ошибку и что нашёл.
  Честный частичный фикс принимается; частичный, выданный за полный, — нет.
- `nova check std/src` ДО и ПОСЛЕ — обе строки `PASS/FAIL/WARN` дословно.
```

## 6. Образец строки результата — обязателен

Без него отчёт приходит в произвольной форме и его приходится разбирать руками.

```
# ФОРМАТ ОТЧЁТА
РЕПРО: <подтверждён / не подтверждён — как проверил>
ТОЧКА: <файл>:<строка> — <что там происходит>
ФИКС: <что изменено, файл:строка>
ФИКСТУРЫ: <пути>
САБОТАЖ: <вывод красный> / <вывод зелёный>
std/src: ДО <строка> / ПОСЛЕ <строка>
ВЕТКА/КОММИТ: <ветка> <хэш>
ЧТО НЕ СДЕЛАНО: <прямым текстом>
```

## Выбор модели

| задача | модель |
|---|---|
| перечисление, сверка, механическая замена по точному списку | opencode (см. соседний шаблон) |
| проба, фикс по готовому диагнозу, инвентаризация с суждением | **sonnet** |
| разведка неизвестного, проектирование | opus |

**haiku не давать** ни классификацию, ни длинные перечисления: дважды зависал по
десять минут на ровном месте. Экономия оборачивается потерянным окном.
