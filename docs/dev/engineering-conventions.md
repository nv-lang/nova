# Инженерные конвенции — обязательные нормы и отклонения Nova

Проект применяет общие инженерные конвенции из репозитория
[unitcraft/engineering-conventions](https://github.com/unitcraft/engineering-conventions).
Этот документ — точка применения: какая конвенция к какой части проекта относится,
где у нас принятая форма и какие отклонения записаны. Конвенции обязательны; отклонение
без записи в таблице ниже считается дефектом документации (§13 конвенции по релизам).

## 1. Применяемые конвенции

| Конвенция | К чему применяется у нас |
|---|---|
| [technical-writing.md](https://github.com/unitcraft/engineering-conventions/blob/main/technical-writing.md) | Техническое письмо на русском: отчёты владельцу, `docs/dev/`, задания, реестр 221.1, сообщения сессий. Основа — ASD-STE100: короткие предложения, знакомые слова, одно действие на предложение. |
| [release-notes.md](https://github.com/unitcraft/engineering-conventions/blob/main/release-notes.md) | Все релизы: Oracle (`oracle-vX.Y.Z`), Карина (`carina-vX.Y.Z`), спутниковые пакеты (`vX.Y.Z` в своих репозиториях). Чек-лист §14 конвенции — часть конвейера публикации окна релиза. |
| [api.md](https://github.com/unitcraft/engineering-conventions/blob/main/api.md) | HTTP-поверхности пакетов (nova-http и потребители, например сервисные контракты Алулы). |
| [database.md](https://github.com/unitcraft/engineering-conventions/blob/main/database.md) | Схемы хранения пакетов с персистентностью (реестры/миграции Алулы и подобные). |

Конвенция по релизам уже отражена в корневом `CHANGELOG.md` (Keep a Changelog 2.0.0,
SemVer 2.0.0, линия `0.Y.Z` с флагом prerelease). Публичный контракт продукта назван
во введении журнала: команды CLI и коды выхода, язык Nova, форматы `nova.toml` /
`nova.lock.toml`.

## 2. Отклонения от конвенции по описанию релизов

| Правило | Принятое решение | Причина | Цена | Условие снятия |
|---|---|---|---|---|
| §3: тег `v<X.Y.Z>` | Теги `oracle-v<X.Y.Z>` и `carina-v<X.Y.Z>` в монорепе | Два продукта с независимой нумерацией в одном репозитории — конвенция это допускает; записано для полноты | Нет | Не требуется (не отклонение, фиксация формы) |
| §9: повторять все действующие Known issues в каждой версии | С 0.1.9 — повторяем полный список на тег; страницы 0.1.7/0.1.8 дополнены правкой с датой | Полный список восстановлен по реестру на теге; до правки читатель 0.1.8 видел только новые ограничения | Одна правка страниц + дисциплина при каждом релизе | — |
| §7: ссылки на отслеживание | Ссылки на записи реестра `docs/plans/221.1-bug-sweep.md` в зафиксированной ревизии тега (blob-ссылки), а не GitHub Issues | Реестр 221.1 — принятая в проекте система отслеживания дефектов; дубликаты в Issues не нужны | Ссылки ведут в большой файл; якорь — номер строки реестра | Переход на Issues, если проект его примет |

## 3. Порядок применения

1. Новый релиз любого продукта сверяется с чек-листом §14 конвенции по релизам до публикации.
2. Новая HTTP-поверхность или схема хранения сверяется с `api.md` / `database.md` на ревью.
3. Тексты на русском (отчёты, docs/dev, реестр) пишутся по `technical-writing.md`.
4. Новое отклонение вносится в таблицу §2 тем же слиянием, что и код/текст, его породивший.
