# Конвенция именования — продуктовые имена и имена артефактов

**Нормативна** (см. [conventions-governance.md](conventions-governance.md)) · создана по запросу
владельца, согласовано 2026-07-23.

Документ отвечает на два вопроса: **как выбирается новое имя** и **какие имена заняты сейчас**.
Имена сущностей внутри кода на Nova (типы, методы, поля) здесь НЕ дублируются — только ссылки
(§3), чтобы не плодить вторую редакцию правил, которая разойдётся с первой.

## 1. Продуктовые имена (бренды)

### 1.1 Критерии выбора

1. **Тема — звёзды и небесная навигация.** Логотип языка — звезда; имена держат одну линию.
2. **Метафора рабочая, а не декоративная** (критерий зафиксирован в
   [222 §0а](../plans/222-http-framework.md)). Имя обязано объяснять, что делает вещь. «Просто
   красивая яркая звезда» — недостаточное основание, такие кандидаты отклоняются сразу.
3. **Коротко и одинаково читаемо латиницей и кириллицей.** Имя мелькает в доках, диагностиках и
   разговоре; `Polaris`/`Полярис` проходит, восьмибуквенное с ловушкой в написании — нет.
4. **Свободно в системном софте.** Занятое известным продуктом имя (особенно в компиляторах,
   рантаймах, инфраструктуре) не берём.
5. **Не совпадает с именем, уже занятым в проекте** (§1.2) — два живых похожих имени читатель
   доков будет путать.
6. **Имя — сначала бренд в доках, а не переименование путей.** Прецедент Polaris: имя
   зафиксировано, пакеты остались `nova-http` до раскола. Переименование каталогов/пакетов —
   отдельный механический заход одной волной, если вообще понадобится.

### 1.3 История отказов — по конкретному выбору

> **По умолчанию отказ НЕ блокирует имя** (· решение владельца 2026-07-23). Отказ относится к
> **одному конкретному выбору**: кандидат, не подошедший фреймворку, при выборе имени для
> рантайма, модуля или инструмента **возвращается в рассмотрение автоматически**. Раздел ведётся
> как ход рассуждения — чтобы был виден разбор, а не чтобы запрещать.
>
> **Полный отказ** (имя выбывает навсегда, из всех будущих выборов) существует, но ставится
> **только явным словом владельца** — таблица §1.3.2. Агент такой отказ не проставляет.

### 2.4 Диагностики

| Класс | Схема | Пример |
|---|---|---|
| Ошибка | `E_SCREAMING_SNAKE_CASE` | `E_READONLY_COERCE`, `E_TYPE_NAME_TOO_SHORT` |
| Линт/предупреждение | `W_SCREAMING_SNAKE_CASE` | `W_MANUAL_MIN_MAX`, `W_PARAM_TYPE_POS_MUT` |

Имя кода описывает **нарушенное правило**, а не место в компиляторе. Коды стабильны: однажды
опубликованный код не переименовывается (он попадает в тесты, доки и мышечную память) — при
изменении семантики заводится новый.

### 2.5 Тесты и фикстуры

| Что | Схема |
|---|---|
| Тест модуля std | `<модуль>_test.nv` **рядом с модулем**, не в общей папке |
| Фикстура conformance | `spec_tests/conformance/<тема>.nv`; привязанные к D-блоку — с префиксом `dNNN_` (`d52_newtype_fn_type.nv`) |
| Негативная фикстура | тот же файл с суффиксом `_neg` (`d52_newtype_fn_reverse_coerce_neg.nv`) |

Подробности — [test-conventions.md](test-conventions.md).

### 2.6 Ветки и worktree

| Что | Схема | Пример |
|---|---|---|
| Ветка задачи | `p-<тема>` или `p-fix-<тема>` | `p-coalesce`, `p-fix-mn-crash` |
| Worktree под тему | `nova-<короткий-тег>` | `nova-coalesce`, `nova-okno5` |
| Worktree под план | `nova-pNN` | `nova-p222` |

Голый `fix-<тема>` без префикса `p-` встречается в истории — это **дрейф**, для новых веток не
использовать.

## 3. Имена внутри кода на Nova — где искать (не дублируем)

| Правило | Источник |
|---|---|
| Имя типа — PascalCase, **минимум 2 символа** (`E_TYPE_NAME_TOO_SHORT`) | D30 §naming, `spec/decisions/03-syntax.md` |
| Имена несут семантику: полные слова, домен-квалифицированные ошибки | [nv-coding-style.md §21](nv-coding-style.md) |

| `with_*` всегда возвращает НОВОЕ значение; поля — одноимённые методы-свойства по арности | D117-амендмент (2026-07-06), D84/D409, nv-coding-style |
| Итераторы/view — единый суффикс `*Iter` | nv-coding-style §8 |
| Перегрузки одного имени — все в одном модуле; не различаются — называй по-разному | nv-coding-style §22 |
| ASCII vs Unicode в именах методов | nv-coding-style §2 |
| Устаревшие имена ловятся линтами | `W_RETIRED_NAME`, `W_RETIRED_PREFIX`, `W_VEC_SPELLING` |

## 4. Порядок фиксации нового продуктового имени

1. Кандидаты проверяются по критериям §1.1 — в том числе греп по репозиторию на коллизии.
2. Решение принимает владелец; агент предлагает и обосновывает, но не фиксирует.
3. Зафиксированное имя вносится в §1.2 этого файла **и** в профильный план (как Polaris в
   222 §0а) — одной правкой.
4. Не подошедшие кандидаты вносятся в §1.3.1 с причиной и указанием, при каком выборе
   отвергнуты. Запись **не запрещает** предлагать то же имя для другой вещи. Перенести имя в
   §1.3.2 (полный отказ) может только владелец явным решением.
