## 1. Слои

Референс — **Go** (`cmd/go` ↔ `cmd/compile`): один бинарник наружу, разделённые программы
внутри.

| слой | что делает | в месяц |
|---|---|---|
| **компилятор** (`novac/src/**`) | исходники + конфиг → диагностики + артефакты; не знает про пакеты, тулчейны, сеть | пишется |
| **драйвер** (Rust, как есть) | граф пакетов, зависимости, кэш, тулчейн, линковка, демон | не трогается |
| **CLI** | разбор аргументов, печать | тонкий `novac`-бинарь для дифф-гейта; остальное — Rust |

Инварианты слоя: (1) компилятор читает только переданное — ни обхода ФС, ни резолва
пакетов. Счётчик: **1**.

## 2. Карта модулей — до листьев

Референс размещения — Go (`cmd/compile/internal/*`: мелкие пакеты по фазам). Папка =
один модуль (конвенция проекта). Лимит — 1000 строк на файл, жёстко.
«Одна дверь»: у каждого класса задачи ровно один модуль-решатель.

| модуль | назначение (одна строка) | дверь какого класса задач | инв. |
|---|---|---|---|
| `source` | текст исходника: `FileId`, `Span`, строчный индекс | представление исходника | 1 |
| `diag` | `Diagnostic` по схеме §7; человеческий текст рендерится ИЗ структуры | форма диагностики | 2 |
| `lex` | текст → токены **с тривией** | токенизация | 1 |
| `tree` | зелёное дерево: неизменяемые узлы, тривия, узлы-ошибки; ширины, не позиции | синтаксис-как-данные | 2 |
| `syntax` | красный вид поверх `tree`: родители, позиции, типизированные аксессоры; **типизированная проекция КАНОНИЗИРУЕТ**: поверхностные формы живут только в зелёном дереве, `check` видит канонические узлы | навигация + канонизация | 2 |
| `parse` | токены → зелёное дерево; восстановление после ошибок | построение дерева | 1 |
| `types` | канон типа: конструкция и интернирование `ResolvedType` | **конструкция типа** | 2 |
| `names` | резолв имён и модулей: «имя → объявление»; **порядконезависим**: collect → resolve, два прохода (урок B10m: write-once pre-scan ломал forward-reference) | резолв имени | 2 |
| `builtins` | ЕДИНСТВЕННЫЙ файл, где имена ЯЗЫКА законны строковыми литералами (П5, страж `check-novac-no-name-hardcode.sh`; модель `rustc_span::sym`/Go `Universe`): universe-примитивы с ABI-именами рантайма и точки входа языка (`main`, `println`). Лист графа. НЕ содержит: имён типов и методов std (это ДЕКЛАРАЦИИ — читаются `sem` из сигнатур, поданных двери), инстансов дженериков, C-имён неприм. типов (вердикт владельца 2026-08-15, исполнено 2026-08-16 — таблица методов удалена) | имена-константы | 0 |
| `check` | чекер; **единственный писатель** `sem` | типизация и правила | 1 |
| `sem` | семантическая модель: `resolved_types`, `resolved_callees`, `node_substs` — дом каналов 196; **`sem/mangle` — дверь мэнглинга**: каждый C-идентификатор — функция от сущности реестра (rustc_symbol_mangling), правило держит `check-novac-mangle-fixed-point.sh` | правда о типах/вызовах; C-имя сущности | 2 |
| `lower` | понижение в бэкенд-агностик форму; **место будущего MIR** | понижение | 1 |
| `mono` | сбор инстанцирований | мономорфизация | 1 |
| `emit_c` | бэкенд A: C-текст | выпуск C | 1 |
| `pipeline` | **единственный владелец порядка проходов**; API `compile(files, cfg) → (диагностики, артефакты)` | оркестровка | 1 |
| `main` (бинарь) | тонкий CLI поверх `pipeline` | — | 0 |

Ключевые «одно окно», закреплённые картой (примеры владельца, 274.1 §2б):

- **тип строится только в `types`**: кортеж — обычный тип; «без дженериков» — частный
  случай «с дженериками» (пустой список), не вторая ветка;
- **позиция типа не выбирает конструктор** (пример владельца 2026-08-14: именованный
  кортеж инлайном `[](a: int, b: str)` сейчас НЕ работает — только через объявление
  `type`; значит у инлайн- и объявленной формы разные пути — вторая дверь). Формулировка владельца:
  «если позиция — тип, он должен РАСПАРСИВАТЬСЯ и РЕСОЛВИТЬСЯ одним и тем же окном,
  а не в зависимости от того, где тип в коде написан». То есть окно — вся цепочка:
  **один нетерминал грамматики** `Type` в `parse` (каждая позиция — параметр, возврат,
  аннотация let, generic-аргумент, объявление `type`, каст — ссылается на него; второй
  входной точки вида `parse_type_str` не существует) → **одно понижение**
  `TypeExpr → ResolvedType` в `check`/`types` → **один конструктор** в `types`
  (D315 доказал третье звено ретайром `type_ref_to_c` — четвёртого дубля таблицы;
  `novac` обязан держать все три). `type X = …` лишь ПРИВЯЗЫВАЕТ имя к типу,
  построенному тем же конструктором; каждая форма типа работает в каждой позиции типа
  по построению. Если спека запрещает
  форму в позиции — это одно правило-проверка в `check`, а не отсутствующая ветка
  конструктора. Расхождения с нынешним компилятором в таких местах — в реестр
  (`bug-legacy` либо `by-design` с D-блоком), молча не расширять;
- **метод = функция с receiver-параметром**: `names`/`check` не имеют «методного» пути
  рядом с «функциональным»;
- **порядок проходов существует только в `pipeline`** — урок LSP, звавшего десять
  проходов по именам.

Счётчик раздела: **20** (сумма колонки).

## 3. Рёбра — с колонкой «что течёт»

Вход стража `check-novac-deps.sh` (Э1). Ребро вне таблицы — красный. Ребро без «что течёт» —
красный. Референс дисциплины — модель `rustc_codegen_ssa`: бэкенд не видит ничего выше
понижения.

| из | в | что течёт |
|---|---|---|
| `lex` | `source` | читает `SourceText`; наружу отдаёт `Token[]` (тривия внутри токенов) |
| `parse` | `lex` | `Token[]` |
| `parse` | `tree` | строит `GreenNode` |
| `parse` | `diag` | выпускает синтаксические диагностики |
| `tree` | `lex` | листья зелёного дерева — `Token` ДАННЫМИ; tree не зовёт лексер, только несёт его тип |
| `tree` | `diag` | только дверь `ice()`: классификатор `bin_op` спрашивают ПОСЛЕ `is_binop`, поэтому токен-не-оператор здесь — сломанный инвариант компилятора, а не диагностика пользователю (то же правило, что у `types`/`builtins`) |
| `syntax` | `tree`, `source` | проекция: позиции из ширин + текст для рендера |
| `names` | `syntax`, `diag` | читает объявления/области; выпускает диагностики резолва |
| `check` | `syntax`, `names`, `types`, `diag` | читает КАНОНИЧЕСКИЕ узлы проекции (поверхностных форм на этом ребре нет — контракт); строит типы ТОЛЬКО через `types`; пишет `sem` (единственный) |
| `check` | `lex`, `parse` | ТОЛЬКО тесты (`check_test.nv`, 2026-08-17): чтобы судить правило о ФОРМЕ тела, тест обязан построить это тело из текста, а фронтенд лежит НИЖЕ чекера — направление слоёв не нарушено. Рабочий код `check` этих модулей не зовёт: проверяется грепом по `check.nv`/`typing.nv`. |
| `check` | `builtins` | таблица методов подмножества (`builtin_method_ret`) и имя entry — константы, не семантика |
| `check` | `tree`, `lex`, `source` | **временное until:E2b1** (Э1-временное, до появления `syntax`): мини-чекер читает зелёное дерево, токены и позиции напрямую; снимается при Э2-red-слое — ревью среза обязано это ребро удалить |
| `sem` | `tree`, `lex`, `diag`, `names`, `builtins` | **временное until:E2b1** (Э2-временное; ревью владельца 2026-08-15: реестр типов/сводная таблица деклараций/типизация выражений — НЕ бекендная материя, дом — `sem`, модель rustc_middle): sem строится в emit-фазе из зелёного дерева (`collect_types`); `builtins` — seed-строки и таблица методов (П5-остаток); `names` — только `NameTable`; при Э4 единственным писателем sem становится `check` (целевая строка выше), решётка вырастает в настоящий чекер — МЕСТО модуля не двигается |
| `emit_c` | `tree`, `lex`, `diag`, `sem`, `builtins` | **временное until:E4** (с Э2-б1 типовые вопросы — ЧТЕНИЕ канала `sem.CheckOut`, а не вывод: `type_of`/`Scope` эмиттеру больше не видны, решётка уехала в `check`) (Э1/Э2-временное, до `lower`): ТОЛЬКО C-рендер — типовые вопросы задаёт `sem`; `builtins` — оракульские C-имена моно-инстансов/тэгов/префиксов (факт эмиссии оракула, не знание novac); `diag` — только дверь `ice`; при Э4 канон типов приходит ДАННЫМИ через `lower` и весь ряд снимается — целевая строка ниже это уже запрещает |
| `mono` | `sem` | читает инстанцирования |
| `mono` | `builtins` | имя точки входа: корень обхода -- `main`, и знает его тот же модуль, что и остальные имена языка |
| `mono` | `diag` | `ice()`: сломанный инвариант таблицы вызываемых -- это падение с текстом, а не тихий пропуск |
| `mono` | `tree` | узлы деклараций и вызовов: коллектор ходит по ДЕРЕВУ, пока пониженной формы нет (ВРЕМЕННОЕ ребро, до Э4 — с приходом `lower` коллектор переезжает на неё, и это ребро снимается) |
| `lower` | `syntax`, `sem`, `diag` | тела + типы → бэкенд-агностик форма; MIR-пассы владения (К5) выпускают СВОИ диагностики |
| `emit_c` | `lower`, `mono` | **только** пониженная форма (несёт ДАННЫМИ интернированный канон типов И `DeclId`-пути для мэнгла §4а п.5); рёбер-импортов к `syntax`/`tree`/`check`/`names`/`types` НЕТ |
| `sem` | `types` | Э2-б1: реестр деклараций получает `Interner` и интернирует терм каждой декларации (`TypeDef.ty`); что течёт — `Ty` (id терма) и три двери `prim`/`record`/`sum`, ничего сверх. Направление верное: sem выше types, types не знает о sem |
| `builtins` | `diag` | только дверь `ice()`: ординал примитива вне универсума — сломанный инвариант компилятора (Э2-б1: `prim_c_name` спрашивают по ординалу из терма) |
| `types` | `diag` | только дверь `ice()`: индекс вне интернера, частичная подстановка — сломанный инвариант компилятора, не диагностика пользователю |
| `types` | `builtins` | универсум языка: сумма `TypeKind` (виды терма — ОДНА на весь компилятор, а не по копии в каждом модуле; вторая копия с теми же вариантами вскрыла дефект резолва оракула 2026-08-16) и `TYPE_KIND_COUNT`. Ниже этих двух рёбер интернер не читает ничего и ничьих решений не знает (слой 4 карты) |
| `check` | `sem` | Э2-б1: ПИШЕТ канал (`CheckOut` живёт в `sem` — там же, где реестр, и потому эмиттеру не нужно ребро к `check`); читает контекст: реестр типов файла и таблицу методов, ПРОЧИТАННУЮ из деклараций std — суждение «такого метода нет» принимает check, а не эмиттер (граница подмножества падает в check). Э2-временное until:E4 — при Э4 `check` сам СТРОИТ `sem`, а не читает готовый |
| `pipeline` | `tree` | несёт `Node` между фазами (тип-данные, как `lex` у `tree`): контекст строится по разобранному дереву файла и деклараций |
| `pipeline` | `sem` | СТРОИТ контекст файла: типы файла + сигнатуры методов из ПРОЧИТАННЫХ деклараций std (тексты подаёт дверь `main`, компилятор ФС не обходит — §1). Э2-временное until:E4 — при Э4 контекст строит `check`, а `pipeline` только зовёт фазы |
| `pipeline` | `source`, `lex`, `parse`, `check`, `lower`, `mono`, `emit_c`, `diag` | оркеструет (ЕДИНСТВЕННЫЙ, кто зовёт фазы); наружу — `(Diagnostic[], Artifact[])` |
| `main` | `pipeline`, `diag` | зовёт compile; печатает из структуры |

Запреты, которые страж держит отдельно: `emit_c` (и будущий `backend_native`) не
импортируют ничего выше `lower`; никто, кроме `check`, не пишет `sem`; никто, кроме

**Референс хранения реестров (решения владельца 2026-08-14, Э2):** плоские
id-индексированные пулы с off/cnt-диапазонами — лагерь Zig InternPool / rustc
`IndexVec` (data-oriented, кэш-локальность — цель «паритет с Go»), НЕ объектные
графы Go/Roslyn (они опираются на GC и жертвуют локальностью). Резолв имени —
одна сводная таблица деклараций: одна выборка отвечает «что это за имя»
(kind + payload-id; модель rustc `Res`/Go `Object`), каскад по таблицам сортов
запрещён; str→id — только дверь `names.NameTable` (страж
`check-novac-resolve-discipline.sh` держит оба правила плюс запрет тихих
int-дефолтов — класс №652). Долг, записанный до её наступления: типизированные
индексы (rustc `VariantIdx`/`FieldIdx`) — при Э4; интернер типов — при Э2-б
(mono потребует структурной дедупликации инстанцирований).

Инварианты: (1) рёбра только из таблицы, и каждое несёт контракт «что течёт»;
ацикличность отдельным инвариантом не считается — она следует из самой таблицы (вердикт
К4, §16). Счётчик: **1**.


## Слои компилятора — карта с донором на каждый (2026-08-16)

Требование владельца: «нам нужны рабочие проверенные временем архитектуры и
алгоритмы с тех языков, которые могут быть донорами». Разбор четырёх эталонов
(rustc, Swift, Go 1.18+, C#/.NET) дал общую форму, в которой они совпадают, и
одну развилку, где расходятся. Ниже — цепочка слоёв novac, собранная из этой
общей формы, с указанием донора и честным статусом.

| № | слой | что на нём известно | донор | статус у нас |
|---|---|---|---|---|
| 1 | `lex` | байты и границы токенов, тривия | Roslyn / rust-analyzer | ЕСТЬ |
| 2 | `tree` + `parse` | форма, не смысл; дерево ре-сериализуемо побайтово | общая форма всех четырёх | ЕСТЬ |
| 3 | `names` | «имя → объявление», у декларации стабильный `DeclId`, не зависящий от позиции | rustc `DefId` · Go `types.Object` · Roslyn `Symbol` | ЕСТЬ |
| 4 | **`types`** | `TyKind = Prim │ Record(DeclId) │ Sum(DeclId) │ App(DeclId, args) │ Param{index} │ Infer{vid} │ Fn │ Ptr`; `Ty` = индекс интернера; **равенство типов = равенство индексов**; `subst(ty, args)` по индексу | rustc `TyCtxt` + `GenericArgsRef` · Zig `InternPool` · clang canonical types | **НЕТ — ни модуля, ни формы** |
| 5 | **`infer`** | вывод внутри ОДНОГО тела: ожидаемый тип вниз, унификация вверх; свежие переменные в откатываемом union-find | rustc `InferCtxt` (bidirectional, **не HM**) + аргумент-направленная дедукция Go 1.18 | **НЕТ вовсе** |
| 6 | **`bounds`** | удовлетворяет ли конкретный `Ty` протоколу `P` и каким набором методов | **Go (method set / type set, структурно)**, а НЕ rustc trait selection: у нас нет impl'ов, когерентности и orphan-правил (D53) | **НЕТ** |
| 7 | `check` | тип каждого узла, выбранный кандидат, подстановка на call-site; пишет канал | rustc `TypeckResults` · Go `types2.Info` · Roslyn BoundTree | ЕСТЬ ИМЕНЕМ, содержания и канала нет |
| 8 | `lower` / MIR | типизированное тело, **полиморфное**: `Param` ещё жив | rustc MIR · Swift SIL · Go IR | ЭСКИЗ, Э4 |
| 9 | **`mono`** | множество достижимых `(DeclId, substs)` | rustc mono collector `Instance` · Go stenciling · Zig мемоизация Sema | место есть, **алгоритма, ключа и модуля нет** |
| 10 | **`layout`** | размер, выравнивание, C-имя — **только для типа без `Param`/`Infer`** | rustc `layout_of` | **НЕТ — не упомянут нигде** |
| 11 | `emit_c` / нативный | всё конкретно | — | ЕСТЬ |

### Где появляются РЕАЛЬНЫЕ типы — это три разных события

Спор не сходится, пока их не развести:

1. **Семантический тип** (канонический `Ty`, возможно с `Param`) — слой 4, и он
   обязан появиться ДО чекера. Сегодня такого события нет вовсе: типизация
   выражений это `sem.type_of`, пересчёт на каждом сайте — тип не «появляется»,
   а каждый раз вычисляется заново. Это ровно тупик, который план 196 назвал
   «три independent, hand-duplicated inference engines».
2. **Вывод** (инференс-переменные) живёт только внутри тела, слои 5–7, и умирает
   на границе тела. **Ни одна переменная не переживает функцию** — это инвариант
   с ассертом, а не пожелание.
3. **Конкретный тип** (ноль свободных параметров) появляется на слое 9, `mono`.
   Не раньше — тело дженерика тайпчекается ОДИН раз обобщённо, а обязанность
   доказать bound лежит на вызывающем. Не позже — `layout` и C-имена физически
   невычислимы при свободных параметрах. Это техническая граница, не вкусовая.

### Развилка эталонов — и почему наш лагерь rustc/Zig

Расходятся эталоны ровно в одном: **кто платит за конкретику**. Требуешь
статический layout и ноль индирекции — платишь временем компиляции и размером
кода и не можешь отдать дженерик через бинарную границу без тела (rustc, C++,
Zig). Готов платить рантайм-метаданными и словарями — получаешь раздельную
компиляцию и стабильный ABI (Swift, C#), но теряешь zero-cost.

У Nova нет ни стабильного ABI, ни рефлексии, ни cross-crate инстанцирования, а
спека требует mono прямо: D122 («zero-cost, паритет Rust `impl<T: Hash>`»),
02-types.md:1173 («vtable только для Effect-kind, Protocol — compile-time-only»),
D122:4527 («effectful protocol bounds ОБЯЗАНЫ mono-dispatch'иться»). Значит
**полная мономорфизация принята сейчас**, а не откладывается до Э4; на Э4
остаётся лишь словарный путь как ОПЦИЯ, и шов коллектора сохраняется, чтобы она
осталась добавляемой.

### Что это значит для нынешнего реестра типов

`TypeDef {kind, name, c_name, row_off, row_cnt}` ломается **не тем, что он
плоский вектор** — индекс как id это и есть интернирование, форма верна. Ломается
тремя вещами: (а) нет `TyKind` с `App`/`Param` — тип не умеет быть «Vec,
применённый к аргументам»; (б) `c_name` лежит в декларации, а C-имя обязано быть
функцией `(DeclId, substs)` — у `Vec[int]` и `Vec[str]` оно разное; (в)
`row_off/row_cnt` описывают поля ДЕКЛАРАЦИИ, а поля инстанса — производная
подстановки.

Отсюда правка: **две таблицы вместо одной** — декларация (`DeclId` → параметры,
схема строк, где типы полей могут быть `Param`) и инстанс (`(DeclId, substs)` →
`Ty`, `c_name`, layout). Инстанс-таблица — это и есть мемоизация коллектора, а не
отдельная сущность.

### Уроки эталонов, которые мы берём сознательно

* **MIR с первого дня — нельзя откладывать анализы на дерево.** Сожаление rustc
  номер один: MIR появился в 2016, и borrowck, исчерпаемость, const-eval, drop
  elaboration пришлось переделывать. Мы откладываем MIR до Э4, и это безопасно
  ТОЛЬКО при двух условиях: до Э4 ни один анализ (исчерпаемость, consume,
  эффекты) не садится на дерево, и канал чекера существует.
* **Обязательства — данные, а не рекурсия по месту.** Сожаление rustc номер два:
  ad-hoc рекурсивный solver без кеша пришлось переписывать. Наивный решатель
  допустим; форма данных — нет.
* **Ассоциированных типов и нормализации у нас нет — и это ставка.** D15 их
  отверг, значит мы избегаем `Alias`-узлов и нормализации проекций, хронической
  боли rustc. Ставка держится ровно до цепных bounds (D355 §6): если они
  появятся, нормализация вводится ДО них.
* **Неоднозначность — ошибка, ранжирования нет** (лагерь rustc/Go). У Swift
  ранжирование по score дало экспоненту («expression too complex»), у C# — спеку
  на десятки страниц. Переход «ошибка → ранжирование» совместим, обратный нет.
* **Глобального вывода и HM не будет никогда.** Ни один из четырёх эталонов
  этого не делает: подтипирование, перегрузка и протоколы убивают принципиальные
  типы. Сигнатуры аннотируются, вывод ограничен телом.
* **Проверка тела дженерика в точке ОПРЕДЕЛЕНИЯ против объявленных bound'ов.**
  Иначе автоматически получается модель шаблонов C++ — «ошибка всплывёт, только
  если тело реально позовёт метод». Это дословно дефект реестра №303, и он уже
  случался у оракула. Самое трудновозвратное решение из всего списка: C++ и Zig
  не могут вернуть его никогда.


### Что такое чекер и что такое кодоген — граница по донорам

Слова «чекер» и «кодоген» несут в этом документе много веса, поэтому граница
определяется явно и не по тому, как сложилось у нынешнего компилятора.

**Чекер устанавливает СМЫСЛ.** Вход — дерево с разрешёнными именами. Выход —
для каждого узла его тип, выбранный кандидат вызова и подстановка, плюс
решение всякого вопроса, у которого ответ мог бы звучать «зависит от того, что
имел в видуавтор кода»: какой из кандидатов применим, держится ли ограничение,
приводим ли тип, экзистенциал это или универсал. Все решения публикуются в
канал. Доноры: rustc `rustc_hir_typeck` → `TypeckResults`; Go `types2` → `Info`;
Swift констрейнт-система → применение решения к AST; Roslyn `Binder` →
BoundTree.

**Кодоген ПЕРЕВОДИТ уже принятые решения** и не принимает ни одного
семантического. Он читает канал и понижает. Донор: rustc `rustc_codegen_ssa`
от MIR к LLVM — он не резолвит метод по имени и не выводит тип, потому что к
этому моменту и то и другое уже решено и записано.

**Между ними — механические слои** (`lower`/MIR и `mono`): они ничего не
судят. Мономорфизация не принимает решений, она перечисляет инстансы по
подстановке; вопрос «какой метод» к этому моменту закрыт.

**Правило границы, одной фразой.** Вопрос, ответ на который может зависеть от
намерения автора кода, принадлежит чекеру. Всё, что является механическим
следствием уже принятого решения, принадлежит слоям ниже. Если кодогену
приходится РЕШАТЬ — это не «так удобнее», это дефект: значит в канале не
хватает поля.

**Проверка границы, применимая к любому спору.** Замените кодоген целиком
(другой бэкенд — нативный, libFirm, что угодно). Если смысл программы не
изменился — граница проведена верно. Если новому бэкенду пришлось заново
выводить типы или заново резолвить методы — граница проведена неверно, и
починка не в бэкенде, а в канале. Это ровно принцип §2 («бэкенды потребляют,
не владеет никто»), доведённый до проверяемой формулировки.

**Отсюда прямое следствие для протоколов.** Предикат «тип удовлетворяет
протоколу» живёт в чекере всегда: его ответ зависит от объявленных методов,
то есть от намерения автора. Кодоген его не воспроизводит и не перепроверяет —
он читает решение. Нормативный алгоритм, восстанавливающий базовый тип
разбором мангл-имени в кодогене, границу нарушает дважды: решает в кодогене и
пропускает идентичность через слой ABI (П24).

### Решение владельца 2026-08-16: структурная семантика остаётся

По двум расхождениям спеки, вынесенным на решение, ответ владельца:
**оба амендмента структурную семантику НЕ отменяют — они только усиливают
проверку в точке декларации.**

Что это значит по пунктам:

1. **Соответствие протоколу остаётся СТРУКТУРНЫМ.** Тип удовлетворяет
   протоколу, если у него есть нужные методы; маркера-разрешения для этого не
   требуется. D186, раздел «Семантика», дословно: use-site остаётся
   structural, `#impl` не делает тип номинальным, и через bound использование
   любого структурно подходящего типа работает без него.

   **Два механизма, которые легко слить в один — и мы их не сольём** (уточнено
   окном компилятора 2026-08-16; моя прежняя формулировка называла это
   противоречием спеки, и это было неверно — спека не противоречит себе,
   она нечётко разделяет два разных механизма):
   * **Использование по bound'у** — `[T Protocol]`. Структурное, маркер НЕ
     нужен. Это то, что делает предикат удовлетворения протокола.
   * **Амбиентный синтез** — голый вызов авто-выведенного метода и голая
     интерполяция значения. Здесь маркер `#impl` ОБЯЗАТЕЛЕН: он ворота, через
     которые автор типа явно разрешает компилятору синтезировать поведение
     без единого слова на месте использования.

   Для novac это разделение — правило двери: предикат удовлетворения протокола
   НЕ смотрит на маркер никогда. Если однажды появится амбиентный синтез, он
   спрашивает маркер — но это другой вопрос, другая дверь и другой ответ.
2. **Проверка усиливается в точке ДЕКЛАРАЦИИ.** Тело дженерика проверяется
   против ОБЪЯВЛЕННЫХ ограничений там, где оно написано, а не там, где его
   инстанцировали. Это и есть отличие от модели шаблонов C++, и оно —
   самое трудновозвратное решение слоя типов (C++ и Zig вернуть его не могут).
3. **Bound остаётся входом отбора кандидатов** (режим-фильтр) и остаётся
   ошибкой на инстанцировании (режим-ошибка) — оба режима сохраняются, и
   усиление касается первого: кандидат, чей bound не держится, ОТПАДАЕТ, а не
   выбирается молча.

### Детали слоёв — по разделу на дверь

Ниже — по разделу на каждый слой карты, который сегодня не существует.
Каждый называет донора, форму данных, единственную дверь и инвариант.

#### Подстановка — единственная дверь, которой исчезает `Param`

Мономорфизация полная (D122: zero-cost, паритет с Rust; vtable остаётся только за
Effect-kind). Значит каждый дженерик доезжает до C как набор конкретных функций, и
переход «обобщённое → конкретное» обязан выполняться ровно в одном месте. Это
`subst`. Она переписывает терм типа и больше не делает ничего: не проверяет,
не диагностирует, не смотрит в AST.

Ниже все блоки кода — нотация формы данных, а не готовый текст `.nv`: нормативны
имена полей и функций, синтаксис приводится к спеке при реализации.

##### Что известно на слое

* Интерн-таблица типов (`TyCtxt`). Виды узлов: `Prim`, `Record(DeclId)`,
  `Sum(DeclId)`, `App(DeclId, ArgsId)`, `Param{index}`, `Infer{vid}`, `Fn`, `Ptr`.
  Равенство типов — равенство `TyId`.
* Обобщённый номинальный тип — всегда `App(decl, args)`; `Record`/`Sum` без
  аргументов — необобщённый. Другого способа записать «`List` с параметрами» нет.
* Позиционный список параметров каждой декларации. Порядок фиксирует резолвер
  один раз (D145, префикс `fn[T]`), `Param{index}` адресуется позицией; имени на
  этом слое уже нет.
* Bounds проверены чекером до вызова (D72, D355). `subst` получает пару
  «сигнатура + аргументы», про которую уже известно, что она законна.

Не известно и не нужно: AST, спаны, области видимости, канал диагностик, layout.

Отсюда сигнатура без канала ошибок:

```
fn subst(cx: TyCtxt, ty: TyId, args: ArgsId) -> TyId
```

Возврат — `TyId`, не `Result[TyId]`. Это решение: если бы `subst` могла провалиться,
каждый вызывающий в mono тащил бы обработку ситуации, которую чекер уже исключил, и
диагностика расползлась бы по двум слоям.

##### Форма данных

```
TyFlags   { has_param: bool, has_infer: bool }   // считаются при интернировании
                                                 // как OR по детям
Args      { id: ArgsId, tys: []TyId }            // интернируется целиком
InstKey   { decl: DeclId, args: ArgsId }         // ключ инстанса: два u32
SubstCache: Map[(TyId, ArgsId), TyId]
```

`ArgsId` — интернированный вектор аргументов, а не список типов по значению. Это
даёт дешёвый ключ инстанса: дедупликация мономорфных копий и очередь mono работают
на `InstKey` из восьми байт, без глубокого сравнения векторов типов. Тот же приём
делает `SubstCache` осмысленным: ключ — пара идентификаторов.

`TyFlags` — быстрый путь. Флаги вычисляются один раз при интернировании узла, и
`subst` начинается с проверки `has_param`; для типа без параметров она возвращает
аргумент немедленно. При полной мономорфизации подавляющее большинство типов,
которые встретит обход, параметров не содержат, так что этот один тест и есть
основная оптимизация слоя.

##### Алгоритм

```
fn subst(cx, ty, args) -> TyId:
    if !cx.flags(ty).has_param:  return ty
    if let hit = cx.subst_cache.get((ty, args)):  return hit
    r = match cx.kind(ty):
        Param{index}  -> cx.args(args).tys[index]
        App(d, a)     -> cx.intern_app(d, subst_args(cx, a, args))
        Fn(ps, ret)   -> cx.intern_fn(map(ps, subst), subst(ret))
        Ptr(p)        -> cx.intern_ptr(subst(p))
        _             -> ice("subst: has_param на листе")
    cx.subst_cache.put((ty, args), r)
    r
```

Тотальность по индексу. `Param{index}` берёт `args.tys[index]` — без поиска, без
окружения, без вопроса «а вдруг параметр не связан». Промах невозможен по
построению: вектор всегда полон для своей декларации, а выход за границу — не
пользовательская ошибка, а ICE.

Рекурсия по структуре с интернированием на каждом уровне. `subst` не создаёт
неинтернированных узлов: результат каждого уровня немедленно проходит через
`intern_*`, поэтому структурное равенство остаётся равенством `TyId` и после
подстановки. Это то же требование, что у `InternPool` в Zig: интернирование —
не кэш, а определение идентичности.

Ветка `_` недостижима: `Prim`, `Record`, `Sum`, `Infer` — листья без параметров,
они отсеклись первой строкой. `Infer` внутри составного типа `subst` проходит
насквозь как лист и оставляет как есть — переменные вывода подставляются не
подстановкой, а резолвом инференс-контекста (раздел про вывод).

Аргументы могут содержать `Param` — это законный случай «дженерик вызывает
дженерик»: тело `f[T]` вызывает `g[Vec[T]]`, вектор для `g` полон, но состоит из
термов внешнего тела. Это не частичная подстановка: `subst_partial` не существует,
вектор всегда полон для своей декларации.

##### Почему подстановка — не повторный тайпчек AST

Альтернатива, которую мы отвергаем: инстанцировать шаблон, повторно прогнав по телу
проверку типов. Это модель шаблонов C++ (и, частично, до-концептного C++20). Её
цена известна: сигнатура перестаёт быть контрактом, ошибки в теле дженерика видны
только тому, кто его инстанцировал, диагностика превращается в стек инстанцирования,
а время компиляции умножается на число инстансов.

Решение: тело дженерика тайпчекается ровно один раз, обобщённо, против своих bounds
(D72, D355). Всё, что происходит на mono, — механическое переписывание терма.
Следствия, которые надо удерживать:

1. У mono нет канала диагностик и нет спанов. Если mono «не может» — это ICE, а не
   сообщение пользователю.
2. Любая новая проверка едет в чекер, а не в mono. Соблазн «поймаем на
   инстанцировании» — это возврат к C++.
3. D310 (звучность в чекере) читается здесь буквально: mono ничего не доказывает,
   он только раскрывает уже доказанное.

Единственное исключение — бесконечное разрастание инстансов (`f[T]` вызывает
`f[Vec[T]]`). Оно неразрешимо статически, и его платит каждый компилятор с полной
мономорфизацией: rustc упирается в recursion limit ровно тут. Значит у mono есть
ровно одна собственная ошибка — `mono_depth_limit`, с цепочкой инстанцирования в
тексте. Одна, названная и ограниченная — не дверь для остальных.

##### Единственная дверь

Звать `subst` вправе двое:

* **`check`** — при инстанцировании сигнатуры в точке вызова. Аргументы на этом
  этапе могут содержать `Infer`; результат уходит в унификацию. Это в точности роль
  `EarlyBinder::instantiate` у rustc.
* **`mono`** — при создании инстанса, с полностью конкретным вектором.

Не вправе никто больше. Отдельно и жёстко: **эмиттер не зовёт `subst` никогда**.
К моменту, когда функция доходит до C-кодогена, все типы её тела уже конкретны —
их переписал mono. Появившаяся в эмиттере потребность в подстановке означает, что
mono не доделал работу, и чинится она в mono. Граница держится архитектурно:
`subst` живёт в модуле `TyCtxt`, модуль эмиттера его не импортирует. `layout` тоже
не зовёт `subst` — он принимает только тип без `Param` и `Infer`.

Отдельная ловушка: `TyId` и `ArgsId` не стабильны между запусками — это порядковые
номера интернирования. Ни один id не имеет права попасть в выходной артефакт:
манглинг символа, ключ дискового кэша, debug-info строятся структурно, от самих
типов. Донор поведения — rustc, где интернер-индексы внутренние, а наружу идёт
стабильный хеш.

##### Инвариант и ассерты

Главный инвариант: **после `subst` с полным конкретным вектором в типе нет `Param`.**
Точнее — флаги результата не могут внести `Param`, которого не было в аргументах:

```
flags(subst(ty, args)).has_param  ==>  flags_of_args(args).has_param
```

Формулировка именно такая, а не «результат всегда без `Param`»: в случае
«дженерик внутри дженерика» аргументы законно содержат параметры внешнего тела.
Слишком сильный ассерт здесь — типовая ошибка реализации.

* `A-SUBST-1` (арность): при построении `Args` для декларации —
  `args.tys.len() == decl.params.len()`.
* `A-SUBST-2` (индекс): в ветке `Param{index}` — `index < args.tys.len()`, иначе
  ICE с именем декларации.
* `A-SUBST-3` (главный инвариант): проверка флагов по формуле выше — один тест бита,
  можно держать включённым всегда.
* `A-SUBST-4` (вход mono): при постановке инстанса в очередь —
  `!has_param && !has_infer` для каждого элемента вектора.
* `A-SUBST-5` (вход эмиттера): у каждого типа тела `!has_param && !has_infer`.

##### Донор

rustc: `GenericArgsRef<'tcx>` (интернированный слайс аргументов), `EarlyBinder<T>` с
`instantiate(tcx, args)`, механика `TypeFolder`/`fold_with`, быстрый путь по
`TypeFlags::HAS_TY_PARAM`. Идентичность типа — `TyCtxt`; дисциплина интернирования —
`InternPool` Zig.

Берём: интернированный позиционный вектор аргументов, адресацию параметров
индексом, флаги как быстрый путь, свёртку с немедленным интернированием, дешёвый
ключ инстанса.

Не берём: различение `EarlyBinder`/`Binder` и всю машинерию поздно-связанных
регионов (у нас нет лайфтаймов — связывать нечего); `ParamEnv` и caller bounds;
`normalize`/проекции ассоциированных типов (ассоциированных типов нет, нормализовать
нечего — как и в Go); стирание регионов; `TypeFoldable` над всем HIR/MIR — наша
свёртка покрывает ровно терм типа.

##### Чего не делаем и почему это решение

* **Не окружение по именам.** Никаких `Map[Name, TyId]`. Позиционный вектор даёт
  дешёвый ключ, снимает вопросы захвата и затенения имён и делает манглинг
  детерминированным. `Param{index}` имя уже выбросил — возвращать его назад значит
  заводить второй источник истины.
* **Не ленивая подстановка.** Никаких отложенных замыканий-подстановок и цепочек
  байндеров в стиле Dotty. Подстановка энергичная и мемоизированная: при полной
  мономорфизации лень окупается только когда большинство инстансов не
  материализуется, а у нас материализуется всё.
* **Не проверяем bounds.** Это работа чекера в точке вызова. Двойная проверка
  означала бы диагностику в слое без спанов.
* **Не нормализуем.** Нормализовать нечего: протоколы структурные, ассоциированных
  типов нет — отказ от них снял целый слой (`Projection`, обязательства, циклы
  нормализации), и это цена, которую мы сознательно уже заплатили.
* **Нет вариантности и подтипирования.** Подстановка буквальна: `args[i]` встаёт на
  место `Param{i}` без каких-либо преобразований.
* **Не выбираем диспетч.** Для bound-методов гибрид диспетча (D122) решает mono;
  `subst` только переписывает терм.

#### Вывод типов — внутри одного тела, и умирает на его границе

Глобального вывода и HM не будет никогда. Вывод — локальное удобство внутри одного
тела функции: он заполняет то, что не написано в выражениях, и обязан полностью
исчезнуть к моменту, когда тело закрывается. Всё, что уходит из тела наружу
(сигнатуры, `resolved_callees` по D458, вход mono), инференс-переменных не содержит.

##### Что известно на слое

* Сигнатуры всех деклараций уже разрешены и не содержат `Infer` — вывода сигнатур не
  существует. Тело проверяется против известного контракта: типы параметров и тип
  возврата даны.
* Bounds параметров (D72) и параметры протоколов, выводимые из bound-а (D355).
* Предикат «тип удовлетворяет протоколу» структурный: method set / type set, донор —
  Go. Ни impl-ов, ни когерентности, ни orphan-правил, ни выбора реализации.
* Единый канал разрешённых вызовов `resolved_callees` (D458) — это и есть выходной
  артефакт проверки тела, который потом читает mono.
* Неоднозначность — ошибка. Ранжирования кандидатов по score нет.

`Infer{vid}` — отдельный вид узла типа в той же интерн-таблице, наравне с `Param`.
Он не «тип-заглушка сбоку»: он интернируется, участвует в `App`, `Fn`, `Ptr` и
попадает в флаг `has_infer`. Именно поэтому граничный ассерт стоит один тест бита.

##### Форма данных

```
InferVid = u32
InferKind enum General | IntLit | FloatLit

InferCx {
    parent: []InferVid          // union-find
    rank:   []u8
    value:  []Option[TyId]      // решение корня, пусто пока не решено
    kind:   []InferKind
    origin: []Span              // где переменная родилась — для «cannot infer»
    trail:  []TrailEntry        // журнал записей для отката
    pending: []Obligation       // отложенные обязательства bound-ов
}
TrailEntry { vid: InferVid, prev_parent: InferVid, prev_value: Option[TyId] }
Snapshot   { trail_len: u32 }
Obligation { ty: TyId, proto: DeclId, args: ArgsId, span: Span }
Expect enum NoExp | HasTy(TyId) | HintTy(TyId)
```

##### Откатываемый union-find

Union-find с журналом. Любая запись в `parent` или `value` идёт через одну функцию
`set(...)`, которая пишет старое значение в `trail`; сжатие путей — тоже запись,
тоже журналируется. `Snapshot` — просто длина `trail`; откат — раскрутка журнала до
этой длины. Другого способа изменить состояние вывода нет: это единственная дверь
внутри слоя.

Две операции наружу:

```
fn probe[R](cx, f: fn() -> R) -> R          // всегда откатывает
fn commit_if_ok[R](cx, f: fn() -> Result[R]) -> Result[R]
```

Снапшот берётся ровно в одном сценарии — **проба кандидата**. Кандидаты возникают
при разрешении метода по имени в method set типа и при сопоставлении членов
протокола. Правило, вытекающее из «неоднозначность — ошибка»: пробы только
*собирают* применимые варианты, не ранжируя; ноль — ошибка «нет такого метода»,
больше одного — ошибка неоднозначности, ровно один — коммит. Проба **никогда не
печатает диагностику**: провал внутри пробы — это факт для подсчёта, а не сообщение;
сообщение печатает только зафиксированная ветка. Нарушение этого правила — источник
классического мусора в выводе ошибок.

##### Bidirectional

Две функции и одно правило.

```
fn check_expr(cx, e: ExprId, exp: Expect) -> TyId   // ожидание течёт вниз
fn infer_expr(cx, e: ExprId) -> TyId                // тип синтезируется вверх
```

Ожидаемый тип течёт вниз по дереву, унификация — вверх. `HasTy` — требование
(несовпадение есть ошибка в этой точке), `HintTy` — подсказка (несовпадение
разрешает сообщить об ошибке уровнем выше, у всего выражения). `HintTy` нужен ровно
там, где претензию надо предъявлять целому, а не части: ветки `if`, рукава `match`,
литералы, лямбды.

Места, где ожидание несущее, а не декоративное: числовые литералы; конструкторы
пустых коллекций; типы параметров лямбды; `return`; поля литерала записи; аргументы
вызова. Список закрытый — если ожидание нужно где-то ещё, это изменение спеки.

##### Аргумент-направленная дедукция type-аргументов

Донор — Go 1.18, `function argument type inference` в `types2`. Порядок:

1. Явно заданные аргументы (D145: `f[int](x)`) заполняют префикс вектора; остальные
   позиции получают свежие `Infer{vid}`.
2. Сигнатура инстанцируется этим вектором через `subst` — это точка стыка двух
   разделов: вывод не «подставляет сам», он строит вектор и зовёт единственную дверь.
3. **Проход A.** Унификация подставленных типов параметров с типами тех аргументов,
   которые уже полностью известны, слева направо.
4. **Проход B.** Дедукция из bound-а (ниже) — до неподвижной точки вместе с A.
5. **Проход C.** Умолчания литералов для переменных вида `IntLit`/`FloatLit`,
   оставшихся без решения.
6. Лямбды-аргументы проверяются последними: типы их параметров берутся из уже
   подставленного ожидаемого типа. Пока переменные, от которых зависит сигнатура
   лямбды, не решены, тело лямбды не смотрим — так же поступают и Go, и rustc.

Оставшаяся нерешённой переменная — ошибка «cannot infer» со спаном из `origin`.
Не «подставим что-нибудь», не «возьмём первый кандидат».

##### Дедукция из bound-а — отдельный механизм

D355 требует выводить параметры протокола из bound-а. Это не частный случай прохода
A: параметр может вообще не встречаться в типах аргументов — `fn f[T: Iterable[E]](xs: T) -> E`
не даёт про `E` ни одного уравнения из аргументов, `E` добывается только из bound-а.

Механизм. После прохода A для каждого параметра `P` с bound-ом `Proto[A1..An]`, где
`P` уже решён в конкретный `C`: найти в method set `C` члены, требуемые `Proto`, и
унифицировать их сигнатуры с объявленными в `Proto` сигнатурами, инстанцированными
вектором `[A1..An]`. Каждое совпадение даёт уравнения для ещё свободных переменных
среди `A1..An`. Прогон до неподвижной точки: решённая переменная может разблокировать
следующий bound; число итераций ограничено числом переменных, завершаемость
тривиальна. Конфликт двух уравнений на одну переменную — ошибка несоответствия, а не
повод откатываться и искать другой разбор.

Структурность протоколов делает это прямым: свидетель — сам тип `C`, искать
реализацию не надо, сопоставление идёт по имени и арности члена, а имена в method
set уникальны.

Почему это отдельный пункт, а не сноска. Go пришёл к тому же и вынужден был добавить
это **вторым, отдельным механизмом** — constraint type inference, потому что вывод
по аргументам до него не дотягивается. C# зафиксировал обратное правило —
ограничения в выводе не участвуют — и публично об этом жалеет: команда языка
десятилетиями объясняет, почему `where` не помогает вывести аргумент, и называет это
ограничением дизайна. У нас D355 закрывает вопрос на уровне спеки, и реализация
обязана иметь проход B как самостоятельную фазу с собственным списком обязательств,
а не как побочный эффект унификации аргументов.

Обязательства (`pending`) откладываются только внутри тела: если на момент проверки
вызова тип ещё содержит `Infer`, проверка bound-а кладётся в список и повторяется на
неподвижной точке. Перед границей тела список обязан опустеть.

##### Единственная дверь

* Создавать `Infer{vid}` вправе только `check` тела, через `InferCx.fresh(kind, origin)`.
* Менять состояние вывода вправе только `set(...)` под журналом.
* Закрывать тело вправе только `finish_body`.
* `mono`, `layout`, эмиттер про `InferCx` не знают и не имеют к нему доступа —
  модуль вывода живёт внутри чекера и наружу экспортирует только результат.

##### Инвариант и ассерты

**Ни одна инференс-переменная не покидает тело.**

```
fn finish_body(cx) -> BodyTypes:
    solve_pending_to_fixpoint(cx)
    apply_literal_fallback(cx)
    let unresolved = cx.collect_unresolved()
    if !unresolved.is_empty:
        report_cannot_infer(unresolved)      // ошибка пользователя, спан = origin
        return BodyTypes.poisoned()
    for t in cx.all_recorded_types():
        let r = resolve_full(cx, t)          // глубокая замена решённых переменных
        assert(!flags(r).has_infer)          // A-INFER-1: здесь это уже ICE
        out.put(t, r)
```

Порядок важен: сначала диагностика по нерешённым переменным, потом ассерт. Ассерт
охраняет путь экспорта, а не пользователя: если нерешённых нет, `has_infer` в
результате означает дырку в резолве, то есть баг компилятора.

* `A-INFER-1`: каждый экспортируемый тип тела — `!has_infer`.
* `A-INFER-2`: каждая запись в `resolved_callees` (D458) — `(DeclId, ArgsId)` с
  вектором без `Infer` и без `Param`, кроме параметров объемлющего тела.
* `A-INFER-3`: `pending` пуст на границе тела.
* `A-INFER-4`: `trail` пуст на границе тела — незакрытых снапшотов не осталось.

Структурная причина, почему граничного ассерта достаточно: сигнатуры `Infer` не
содержат по построению (вывода сигнатур нет), поэтому ни один тип на уровне модуля
не может нести переменную. Единственный путь утечки — экспорт типов тела, и он
перекрыт `finish_body`.

##### Fallback — решение, а не умолчание по недосмотру

Целочисленный литерал без контекста получает тип `int` (машинное слово). Литерал с
плавающей точкой без контекста — тип двойной точности. Правило применяется ровно
один раз и в определённой точке: проход C внутри вызова и `apply_literal_fallback`
перед границей тела. Никогда — посреди унификации.

Это решение, потому что альтернатива известна и отвергнута: требовать аннотацию на
`let x = 1`. Так делают языки с полноценным HM; Rust выбрал fallback на `i32`, Go —
умолчания нетипизированных констант, и по той же причине: цена ошибки «annotations
needed» на самом частом выражении в языке выше, чем цена одного зафиксированного
умолчания.

И вторая половина решения, столь же важная: **fallback применяется только к
переменным литеральных видов**. `General` без решения — ошибка. Никакого умолчания
в `unit`, `never`, `Any` или «первый подходящий тип» не существует; динамического
люка в языке нет.

##### Донор

Go 1.18 (`types2`): двухфазный вывод по аргументам, constraint type inference как
отдельный механизм, умолчания для нетипизированных литералов. Берём именно это.
Не берём слой нетипизированных констант целиком (арифметика произвольной точности на
константах — отдельная подсистема, у нас её нет) и не берём ограничение Go на
единственный core type: у нас сопоставление идёт по членам method set, что прямее.

rustc (`InferCtxt`, `ena`): union-find с журналом и снапшотами, `probe` /
`commit_if_ok`, `Expectation` в bidirectional-проверке, список отложенных
обязательств, финальный полный резолв на границе. Берём это.
Не берём: вывод регионов; trait selection со сборкой и отсевом кандидатов (у нас
структурный предикат — донор Go, а не rustc); `ParamEnv`; opaque types / `impl Trait`
в возврате, то есть любой вывод, пересекающий границу элемента.

C#: берём только урок — ограничения обязаны участвовать в выводе. Механизм не берём.

##### Чего не делаем и почему это решение

* **Нет Хиндли–Милнера и алгоритма W.** Сила HM — в генерализации и главных типах;
  она конфликтует со структурными протоколами, bounds и полной мономорфизацией:
  генерализованное локальное связывание потребовало бы собственного инстанцирования
  и собственного множества mono-копий. Плюс диагностика: в глобальном графе
  ограничений ошибка всплывает далеко от причины.
* **Нет генерализации `let`.** Локальное связывание монотипно. Нужен полиморфизм —
  пишется функция с параметрами.
* **Нет глобального вывода.** Тело не влияет на сигнатуру другого тела, поэтому тела
  проверяются независимо и в любом порядке. Это жёсткое требование к параллельной и
  инкрементальной проверке, и мы платим за него явными сигнатурами.
* **Нет вывода сигнатур.** Ни типов параметров, ни типа возврата верхнего уровня.
  Сигнатура — контракт и ABI: то, что написано, и есть тип. Лямбды — единственное
  место, где типы параметров приходят из контекста, и этот вывод не покидает тела.
* **Нет ранжирования кандидатов.** Пробы считают, а не сортируют; больше одного
  применимого варианта — ошибка неоднозначности с перечислением вариантов.
* **Нет вывода, управляемого подтипированием.** Решётки вариантности нет, унификация
  симметрична, список допустимых преобразований закрыт.
* **Вывод не участвует в выборе диспетча.** Для bound-методов гибрид (D122) решает
  mono; вывод работает с такими типами как с обычными и не заводит для них
  отдельного вида переменных.

# Границы: удовлетворение протокола и обязательства

#### Удовлетворение протокола — один предикат, три источника метода

##### Донор

Донор предиката — **Go**: `method set` типа и `type set` интерфейса. Берём:
структурность (тип удовлетворяет протоколу, если у него есть требуемые методы —
без объявления связи), продвижение методов через встраивание с правилом глубины,
проверку по имени и точной сигнатуре.

Не берём у Go: расщепление method set между `T` и `*T` (у нас нет неявного
взятия адреса при вызове метода, получатель различается только изменяемостью),
и молчаливое непродвижение при коллизии на равной глубине — см. ниже.

Не берём у **rustc**: `trait selection`. У нас нет `impl`-ов, нет когерентности,
нет orphan-правил, нет ассоциированных типов. Из этого следует главное: нет
проекций (`<T as Trait>::Assoc`) и нет нормализации. Проекции и нормализация —
хроническая боль rustc: половина её trait-подсистемы существует, чтобы приводить
проекции к нормальной форме, и ошибки нормализации живут в трекере годами. Мы не
платим за это, потому что структура протокола — это конечный список методов,
известный в момент объявления, а не результат вывода.

Композиция протоколов (протокол требует другой протокол) разворачивается
**в момент объявления** в объединение требуемых методов. Графа супертрейтов на
слое решения нет: к моменту вызова предиката протокол — плоский список.

##### ЧТО известно на слое

- Все декларации разрешены: `DeclId` типов и протоколов, таблицы методов,
  граф `use`-встраивания, дефолтные тела протоколов (D183), списки bound-ов
  параметров (D72).
- Типы — интернированные термы; равенство типов есть равенство `TypeId`.
  На этом слое терм может содержать `Param{index}` и `Infer{vid}`.
- Для `Param{index}` метод-сет задаётся **не типом, а его bound-ами**: предикат
  отвечает из окружения параметров, а не из таблицы методов. Поэтому окружение —
  явный вход предиката, а не глобальное состояние.
- На терме хранится флаг-битсет свойств (донор — `TypeFlags` в rustc):
  `has_param`, `has_infer`. Флаг наследуется при интернировании и стоит O(1) —
  на нём построены и ключ кеша, и ассерты.

Не известно: реальные типы (они появляются только на mono), layout, множество
инстанциаций. Также не известно, какой кандидат вызова будет выбран — выбор
кандидата является клиентом предиката, а не его частью.

##### ФОРМА ДАННЫХ

```nova
type ProtoRef
    proto ProtoId
    args  []TypeId          # параметры протокола; могут содержать Infer (D355)

type SatVerdict enum Satisfied | Missing

type Satisfied
    witness  []MethodSrc    # ровно по методу протокола, в порядке объявления
    bindings []TyEq         # уравнения на параметры протокола (D355)
    needs_mut_place Bool    # хотя бы один свидетель требует mut-получателя

type Missing
    subject TypeId
    req     ProtoRef
    names   []Str           # имена непокрытых методов, порядок объявления
    causes  []MissCause     # параллельно names

type MissCause enum NotFound | ArityMismatch | SigMismatch | RecvMutability | EmbedAmbiguous

type MethodSrc enum Direct | Embedded | Default

type Direct
    owner  DeclId
    method MethodId

type Embedded
    path   []FieldId        # цепочка use-embed полей, сверху вниз
    owner  DeclId
    method MethodId

type Default
    proto  ProtoId
    method MethodId
```

Предикат:

```nova
fn satisfies(cx Checker, subject TypeId, req ProtoRef, env EnvId) SatVerdict
```

`witness` — не диагностика, а рабочий результат: он говорит, **какое тело**
вызывается. Без него эмиттер вынужден повторять поиск, а это ровно то легаси,
которое мы снимаем.

`bindings` существуют потому, что параметры протокола выводятся из bound-а
(D355): сопоставление сигнатуры найденного метода с сигнатурой требования даёт
уравнения на `req.args`. Предикат их **возвращает и не применяет** — применение
принадлежит инференс-контексту. Так предикат остаётся чистой функцией. Если два
источника метода дают разные `bindings` — это неоднозначность, ошибка;
ранжирования по score нет.

##### Три источника метода — порядок и правила

1. **Прямой метод на типе.** Для `App(DeclId, args)` — метод обобщённой
   декларации с подстановкой `args`. Побеждает всегда.
2. **`use`-встраивание, рекурсивно в глубину.** Правило глубины из Go: побеждает
   наименьшая глубина. Две находки на одной глубине — **ошибка**
   `EmbedAmbiguous`, а не молчаливое непродвижение как в Go: молчаливое
   непродвижение вырождается в `Missing(name)`, то есть в диагностику, которая
   врёт о причине. Это правило язык-меняющее и требует амендмента
   (D-блок назвать).
3. **Дефолтное тело протокола (D183)** — только если 1 и 2 не дали ничего.
   Дефолт виден **исключительно через протокол**: он не попадает в метод-сет
   конкретного типа и не доступен прямым вызовом на значении. Иначе дефолты
   протекали бы в пространство имён типа и метод-сет перестал бы быть свойством
   типа.

Сверка изменяемости получателя выполняется точным совпадением: требование с
`mut self` не покрывается методом без `mut` и наоборот. Расхождение сообщается
причиной `RecvMutability`, а не как «метода нет» — это самая частая ошибка
пользователя, и она обязана называться. Ослабление (немутирующий метод покрывает
мутирующее требование) — аддитивное изменение на будущее, тоже через амендмент
(D-блок назвать). `needs_mut_place` уходит в канал: требование изменяемого места
в точке вызова — забота чекера, звучность в чекере (D310).

##### Кеш

Ключ — пара `(subject, proto)`, расширенная идентификатором окружения:

```nova
type SatKey
    subject TypeId
    proto   ProtoId
    args    ArgsId          # интернированный список req.args
    env     EnvId           # EnvId.empty, если subject.has_param == false
```

Кешируются только **основательные** запросы: `subject.has_infer == false` и ни
один `req.args` не содержит `Infer`. Запрос с `Infer` не кешируется никогда —
его ответ содержит `bindings`, то есть зависит от состояния вывода. Запрос без
`Param` не зависит от окружения, и тогда ключ вырождается ровно в пару
(тип, протокол).

##### ДВА РЕЖИМА BOUND-а

Режимы разведены явно и не выводятся из контекста угадыванием. Режим — вход
клиента предиката, а не свойство самого предиката:

```nova
type BoundMode enum Filter | Require
```

**(А) `Filter` — пред-фильтр применимости.** Кандидат, чей bound не
удовлетворён аргументами, **отпадает** из множества применимых. Ноль
выживших — ошибка «нет применимого кандидата» с перечислением, почему отпал
каждый (накопленные `Missing`). Больше одного выжившего — ошибка
неоднозначности. Ранжирования нет.

**(Б) `Require` — ошибка на инстанцировании.** Кандидат единственен или назван
явно (прямой вызов дженерика, явная инстанциация, bound на декларации типа).
Неудовлетворённый bound — жёсткая ошибка прямо здесь, с именами из `Missing`.

Сам `satisfies` о режимах не знает: он возвращает вердикт, режим решает, что с
вердиктом делать. Единственный резолвер (D458) выбирает режим по форме места
вызова и записывает выбор в канал вместе с результатом.

**Спека держала оба режима и не разводила их — до D464 (2026-08-16).**
D72 задаёт bound-ы, D122 — гибрид диспетча bound-методов, D355 — вывод
параметров протокола из bound-а, D458 — единый резолвер; ни один из них не
формулировал правило «неудовлетворённый bound отсекает кандидата, а не является
ошибкой». Теперь формулирует **D464** («бáунд как фильтр отбора: отсев без
ранжирования»): фильтр 2б в цепочке D84 между типами аргументов и типом
результата; кандидат с неудовлетворённым bound'ом отбрасывается; `#impl` к
отбору отношения не имеет (остаётся воротами ambient-синтеза, D186). Слияние,
вводящее режим `Filter` в novac, ссылается на D464 — язык-меняющая
кодификация исполнена спекой ДО реализации, как и требует правило проекта.

##### ЕДИНСТВЕННАЯ ДВЕРЬ

`satisfies` живёт в модуле чекера и оттуда не экспортируется. Реализация одна.
Результат — вердикт целиком, вместе со свидетелями — уходит в канал рядом с
`resolved_callees` (D458), таблицей `bound_witnesses`, ключ — точка вызова или
точка инстанцирования.

Эмиттер предикат **не воспроизводит**: он не ходит по цепочкам встраивания, не
смотрит в таблицы методов, не решает, взять дефолтное тело или прямой метод. Он
читает свидетеля. Mono читает того же свидетеля, чтобы выбрать тело для
инстанциации.

Сегодня в оракуле эмиттер воспроизводит поиск (D285 §3). Это легаси: две
реализации одного правила расходятся молча, и расхождение видно только как
неправильный сгенерированный вызов. **novac обязан это снять, а не скопировать.**

##### ИНВАРИАНТЫ

```nova
# I1. Предикат — чистая функция ключа. Кеш есть реализация, не семантика.
#     Под NOVAC_VERIFY_SAT_CACHE каждое попадание пересчитывается и сверяется.
assert(cached == recomputed)

# I2. Satisfied всегда несёт полного свидетеля.
assert(v.witness.len() == cx.proto(req.proto).methods.len())

# I3. Missing никогда не пуст: пустой список означает, что предикат потерял причину.
assert(m.names.len() > 0 and m.names.len() == m.causes.len())

# I4. Вход предиката основателен по Infer: не-основательное идёт через обязательства.
assert(not subject.has_infer())

# I5. У эмиттера нет запасного поиска: отсутствие свидетеля — ICE, не fallback.
assert(channel.bound_witnesses.has(site))
```

##### ЧЕГО НЕ ДЕЛАЕМ

- **Никаких `impl`-ов, когерентности, orphan-правил, ассоциированных типов** —
  и, как следствие, никаких проекций и нормализации. Это решение: они покупают
  выразительность ценой нелокальности ответа. Структурный предикат отвечает
  локально и полно, за один проход по типу.
- **Никакого ранжирования кандидатов**, никакого «лучшего совпадения».
  Неоднозначность — ошибка. Лагерь rustc и Go; лагерь C++/Swift с их
  ранжированием оставляет пользователю правило, которое он не может держать в
  голове, а компилятору — таблицу, которую нельзя изменить, не сломав код.
- **Никаких автоприведений и авто-разыменований в поиске метода.** Поиск точный:
  имя плюс сигнатура после подстановки.
- **Никакого негативного рассуждения** («тип не удовлетворяет P» как
  используемый факт) и никакой специализации: обе конструкции немонотонны, а
  немонотонность ломает и кеш, и раздельную компиляцию.

#### Обязательства — данные, а не рекурсия по месту

##### Донор

Донор — **rustc**: `PredicateObligation`, `ObligationCause`,
`FulfillmentContext`. Берём **форму**: обязательство — это значение с причиной,
а разрешение — цикл над рабочим списком, который просыпается при уточнении
переменной вывода.

Не берём: канонизацию, снапшоты и откаты `InferCtxt`, `ObligationForest` с
отслеживанием циклов, `SelectionContext` с лимитом глубины, кеши селекции и
оценки. Все они обслуживают `impl`-ы и глобальную когерентность, которых у нас
нет.

Сожаление rustc номер два — прямая причина этого раздела: раннее разрешение
трейтов было ad-hoc рекурсией внутри typeck, без кеша и без явного
представления; переписывание в fulfillment + selection заняло годы и стало
возможным только там, где обязательство уже существовало как значение.
Отсюда правило: **наивный решатель поверх правильной формы данных заменяется
малой кровью, неправильная форма — нет.** Поэтому форма данных закладывается с
первого дня, даже когда решатель — цикл по вектору.

##### ЧТО известно на слое

- Вывод ограничен телом функции; глобального вывода и HM не будет никогда.
  Значит, множество обязательств тела конечно, замкнуто и целиком видно к концу
  проверки тела.
- Известны: интернированные термы (возможно с `Infer`), окружение bound-ов
  объемлющих параметров, точка возникновения, причина.
- Не известны: окончательные типы до завершения унификации в теле. Именно это и
  есть причина, по которой обязательство не может быть немедленным вызовом
  предиката.

##### ФОРМА ДАННЫХ

```nova
type Obligation
    id      ObId
    subject TypeId          # может содержать Infer
    req     ProtoRef
    origin  Origin          # откуда пришло
    site    SpanId
    env     EnvId
    mode    BoundMode
    state   ObState

type ObState enum Pending | Deferred | Resolved | Failed

type Origin enum CallBound | DeclBound | EmbedBound | ExplicitInst | DefaultBody

type CallBound
    callee      DeclId
    param_index Int

type DeclBound
    decl        DeclId
    param_index Int

type ObligationSet
    items    []Obligation
    pending  []ObId                 # рабочий список
    by_var   Map[VarId, []ObId]     # индекс пробуждения: переменная -> ждущие её
    verdicts Map[ObId, SatVerdict]
```

`origin` — не только текст диагностики: он несёт подсказку исправления
(«добавьте bound `P` параметру `T` функции `f`») и он же определяет, в какую
запись канала уходит свидетель.

##### Цикл разрешения

```nova
fn drain(cx Checker, mut obs ObligationSet) []Diag
```

Шаг: снять `ObId` с `pending`; довести `subject` по подстановкам вывода; если в
голове терма всё ещё `Infer{vid}` — состояние `Deferred`, регистрация в
`by_var[vid]`; иначе вызвать `satisfies` и перевести в `Resolved` (со
свидетелем в канал и `bindings` — в унификацию) либо `Failed` с диагностикой.

Доразрешение: когда унификация уточняет `Infer{vid}`, все `ObId` из
`by_var[vid]` возвращаются в `pending`. Обратного хода нет — снапшотов и откатов
у нас нет, уточнение монотонно, решётка конечной высоты. Отсюда завершаемость
цикла: число событий пробуждения ограничено числом уточнений, а каждое
уточнение случается один раз.

Остановка без прогресса при непустом `pending` не является успехом: все
оставшиеся `Deferred` превращаются в ошибки «тип не выведен для обязательства»
с указанием переменной и места. Молчаливого выхода нет.

##### ЕДИНСТВЕННАЯ ДВЕРЬ

- Обязательства создаёт только инференс-контекст чекера, и только через
  `ObligationSet.push`. Резолвер вызовов, проверка литералов, проверка
  методов — все идут через `push`.
- Прямой вызов `satisfies` разрешён исключительно на основательном типе
  (`I4` выше). Не-основательный тип имеет ровно один путь — очередь.
- `drain` запускается ровно один раз на тело функции, в конце его проверки, до
  записи результатов в канал.
- Ниже по конвейеру обязательств не существует: на mono все типы основательны,
  все bound-ы уже имеют свидетелей. Mono и эмиттер не создают и не разрешают
  обязательств.

##### ИНВАРИАНТЫ

```nova
# J1. Ни одно обязательство не остаётся неразрешённым молча.
assert(obs.items.all(|o| o.state == Resolved or o.state == Failed))

# J2. Каждый Failed отражён хотя бы одной диагностикой (тождество счётчиков ловит
#     классическое «проглоченное обязательство» без разбора текстов).
assert(obs.count(Failed) == diags.count(is_bound_error))

# J3. Обязательство никогда не удаляется из множества — меняется только состояние.
#     Множество есть журнал тела; «разрешилось исчезновением» невозможно.
assert(obs.items.len() == obs.pushed_total)

# J4. Каждое Resolved внесло свидетеля в канал.
assert(obs.count(Resolved) == channel.bound_witnesses.for_body(bid).len())
```

`J3` — тот инвариант, который стоит держать даже ценой памяти: почти все
известные классы «тихо потерянной проверки» в компиляторах суть удаление записи
вместо смены её состояния.

##### ЧЕГО НЕ ДЕЛАЕМ

- **Канонизация.** В rustc она нужна, чтобы переиспользовать ответ между разными
  инференс-контекстами. У нас контекст один на тело, межтеловых запросов нет —
  канонизация купила бы ноль и стоила бы целого слоя переписывания термов.
  Откладывается безопасно: обязательство уже значение с ключом
  `(subject, proto, args, env)`, канонизация вводится как функция над этим
  значением, не трогая места создания.
- **Кеш запросов и query-система.** novac — пакетный компилятор в C; кеш
  `satisfies` — обычная карта внутри одной компиляции, а не запрос с
  жизненным циклом. Query-система вводится тогда, когда появится IDE-нагрузка,
  и вводится над той же формой.
- **Инкрементальность.** Нет графа зависимостей, нет отпечатков. Это откладывается
  безопасно ровно потому, что форма данных заложена: узел графа зависимостей
  позже цепляется к стабильному ключу обязательства. Будь решатель рекурсией по
  месту, цеплять было бы не к чему, и работа стала бы переписыванием — история
  rustc буквально об этом.
- **`ObligationForest`, детекция циклов, лимит глубины.** Структурные протоколы
  не порождают производных обязательств: из `T: P` не следует `U: Q` через
  `impl`, потому что `impl`-ов нет. Единственный источник неограниченных цепочек —
  циклы `use`-встраивания, и они отсекаются раньше, проверкой ацикличности
  графа встраивания на слое деклараций. Машинерия леса обязательств у нас была бы
  защитой от невозможного.
- **Умный решатель в v1.** `drain` — рабочий список над вектором, без
  приоритетов и без кеширования промежуточного. Это принято сознательно: цена
  наивности линейна и локальна, цена неправильной формы — переписывание.

#### 1. Канал чекера — единственный источник правды о типах для всех, кто ниже

##### Что известно на слое

Имена уже разрешены (`names`): каждый идентификатор указывает на `DeclId`. Сигнатуры
собраны. Типы — интернированные термы, равенство типов есть равенство `TypeId`.
Тело дженерика тайпчекается **один раз обобщённо**, поэтому в канале законно лежат
термы с `Param{index}`; закрытых типов на этом слое ещё нет — они появляются на mono.
`Infer{vid}` живёт только внутри тела функции и к моменту закрытия тела обязан быть
решён: нерешённая переменная есть ошибка неоднозначности, а не дефолт (глобального
вывода и HM нет и не будет).

##### Форма данных

Канал — три боковые таблицы, ключ везде `NodeId` (стабильный идентификатор узла AST,
не `Span`; `Span` живёт рядом и нужен только диагностике):

```nova
type CheckOut {
    ro resolved_types   Map[NodeId, TypeId]   // узел -> его тип
    ro resolved_callees Map[NodeId, Callee]   // узел-вызов -> (объявление, подстановка)
    ro node_substs      Map[NodeId, Subst]    // не-вызов, инстанцирующий дженерик -> аргументы
}

type Callee {
    ro decl  DeclId       // объявление, выбранное единым резолвером (D458)
    ro subst Subst        // подстановка ровно этого узла
    ro kind  CalleeKind   // Static | BoundStatic | BoundDynamic (D122: vtable только Effect-kind)
}

type Subst { ro args []TypeId }   // по ИНДЕКСУ параметра; имён параметров в ключах нет

type CalleeKind enum
    | Static
    | BoundStatic
    | BoundDynamic
```

`node_substs` не дублирует `Callee.subst`: домены не пересекаются. В `resolved_callees`
попадают только узлы-вызовы; в `node_substs` — узлы, которые инстанцируют дженерик, но
вызовом не являются: литерал записи `Point{...}`, конструктор варианта суммы, паттерн
над обобщённой суммой, путь с префиксными аргументами `fn[T]` (D145), выведенные
параметры протокола из bound-а (D355).

##### Единственная дверь

Пишет **только** `check`, через `Checker.record_type`, `Checker.record_callee`,
`Checker.record_subst`. Наружу отдаётся неизменяемый `CheckOut` с тремя тотальными
читателями:

```nova
fn CheckOut.type_of(n NodeId)   -> TypeId
fn CheckOut.callee_of(n NodeId) -> Callee
fn CheckOut.subst_of(n NodeId)  -> Subst
```

Читатели не возвращают `Option`. Отсутствие записи есть **баг чекера**, и функция падает
ассертом с `Span` узла. Опциональный возврат — это приглашение написать ветку «а если
нет, посчитаю сам»; именно такая ветка и есть болезнь, которую лечил план 196.

Модуль вывода (`check/infer`) не экспортируется за границы `check`. Страж: греп по
`novac/src/**` вне `novac/src/check/` даёт ноль вхождений `unify`, `infer_`, `fresh_var`.

##### Инвариант

**После чекера ни один потребитель не вызывает вывод типа.** Потребители — mono-коллектор,
layout, C-эмиттер, линты, LSP — только читают.

Ассерты:

* `assert(resolved_types.contains(n))` внутри `type_of` — дыра в канале падает на месте,
  а не превращается в тихий перевывод;
* `assert(!ty.has_infer())` при записи любого типа в канал по закрытию тела функции;
* `assert(resolved_callees.keys().is_disjoint(node_substs.keys()))` по завершении `check`;
* `assert(callee.subst.args.len == decl.type_params.len)` — подстановка тотальна по
  арности объявления, частичных подстановок в канале не бывает;
* звучность записи (что записанный тип действительно выводится из посылок) — забота
  чекера, D310; ниже её никто не перепроверяет и не «уточняет».

##### Донор

* **rustc `TypeckResults`** (`node_types`, `node_args`, `type_dependent_defs`) — берём:
  побочные таблицы per-body, ровно один писатель, потребители читают. **Не берём**:
  `InferCtxt` с канонизацией и regions, trait selection cache — у нас протоколы
  структурные (D53, D72), предикат решается как в Go по method set / type set, а не
  через selection.
* **Go `types2.Info`** (`Types`, `Uses`, `Selections`, `Instances`) — берём деление на
  «тип узла» / «куда указывает узел» / «чем инстанцирован узел»: это ровно наши три
  таблицы. **Не берём** `Defs`/`Uses` как отдельные карты — разрешение имён у нас
  завершено слоем раньше, дублировать его в канале незачем.
* **Roslyn `BoundTree`** — берём принцип «после связывания узел несёт готовый тип и
  готовый символ». **Не берём** материализацию второго дерева: это копия AST, которая
  расходится с оригиналом и удваивает память; боковые таблицы дают тот же результат
  без копии.

##### Зачем это существует

План 196 закрывал ровно одну болезнь: кодоген перевыводил типы мимо чекера. В оракуле
(текущий Rust-компилятор) это видно буквально — `emit_c.rs` держит собственные
`var_types`, `current_type_subst`, `infer_mono_method_ret_with_args`. Это второй,
независимый вывод типов, и он неизбежно расходится с первым; каждый такой расход —
класс багов, а не баг. Канал есть отказ от второго вывода как от возможности.

##### Следствие для LSP

LSP не имеет собственного тайпчекера и не имеет права его иметь. Hover есть рендер
`type_of(node)`. Go-to-definition есть `callee_of(node).decl` и `Span` его объявления.
Inlay hints для аргументов типа есть `subst_of(node)`. Find-references есть обратный
индекс по `resolved_callees`. Всё, что LSP умеет показать про типы, — это то, что
чекер уже записал; чего нет в канале, того нет в редакторе.

##### Чего не делаем и почему это решение

* **Не кладём тип в поле узла AST** (`expr.ty`). AST иммутабелен после `names`.
  Мутабельное поле — вторая дверь: любой проход сможет дописать туда своё, и порядок
  проходов станет частью семантики. Rust идёт тем же путём; Roslyn — обратным и платит
  вторым деревом.
* **Не даём потребителю fallback** «нет в канале — выведи сам». Мягкий fallback и есть
  механизм 196: он маскирует дыру, пока она не выстрелит в рантайме.
* **Не храним в канале строки типов.** Только `TypeId`. Строка — это спеллинг, а
  спеллинг не есть идентичность (см. §2).
* **Не делаем канал мутабельным после `check`.** Никаких «уточним на mono». Mono
  производит новый артефакт — список инстансов, — а канал читает.
* **Не кэшируем в канале производное** — layout, размер, C-имя. Это §3.

#### 2. Коллектор инстансов — ключ (объявление, подстановка)

##### Что известно на слое

Канал закрыт и тотален. Корни известны. Подстановки корней закрыты: ни `Param`,
ни `Infer`. Внутри тела дженерика подстановки узлов содержат `Param{index}` — они
закрываются тотальной подстановкой по индексу из подстановки текущего инстанса.
Принято: **полная мономорфизация сейчас** (D122 требует zero-cost и паритет с Rust;
`vtable` — только Effect-kind, и такие вызовы коллектор не разворачивает, а помечает).

##### Форма данных

```nova
type ItemKey enum
    | Fn { decl DeclId, subst Subst }    // инстанс функции/метода
    | Ty { decl DeclId, subst Subst }    // инстанс записи/суммы (нужен эмиттеру структур)

type Instance {
    ro key    ItemKey
    ro origin NodeId     // узел, который первым его затребовал — для цепочки диагностики
    ro depth  int        // глубина инстанцирования от корня
}

type Collector {
    ro roots []ItemKey
    mut work []ItemKey
    mut seen OrderedSet[ItemKey]   // мемоизация ДО мэнглинга; порядок = детерминизм вывода
    mut out  []Instance
}

fn Collector.collect(roots []ItemKey) -> []Instance
fn Subst.apply(outer Subst) -> Subst     // тотальная подстановка по индексу
```

Равенство `ItemKey` — равенство `DeclId` и поэлементное равенство `TypeId`. Никаких
строк ни в ключе, ни в множестве `seen`.

Корни: `main`; экспортируемые точки компилируемой единицы; тестовые функции в тестовом
режиме; точки входа, адресуемые из C (колбэки рантайма). Всё, что от корней недостижимо,
не собирается и потому не печатается — DCE есть следствие корней, а не отдельный проход.

Обход: снять ключ; если `seen` уже содержит — пропустить; иначе внести и пройти тело
`key.decl`, **читая канал** — `callee_of` для каждого вызова, `subst_of` для каждого
инстанцирующего узла. Дочерний ключ:

```
child = ItemKey.Fn(callee.decl, callee.subst.apply(key.subst))
```

`apply` заменяет каждый `Param{index}` на `outer.args[index]`; `assert(index < outer.args.len)`.
Тотальность означает: если `outer` закрыт, то `child` закрыт — проверяется ассертом на
push, а не надеждой.

##### Единственная дверь

`Instance` создаёт только `mono::Collector`. C-эмиттер получает готовый, закрытый,
упорядоченный список и **не имеет права** дописать инстанс по ходу печати. Ленивое
enrollment во время эмиссии — то, что делает оракул, дренируя `mono_worklist` внутри
`emit_c` — запрещено: оно делает состав программы функцией порядка печати, и любая
перестановка вывода меняет набор инстанцированного.

##### Почему ключ — пара id и НИКОГДА строка

У оракула ключи строковые, и обе формы этой ошибки задокументированы прямо в его коде:

* `mono_method_decls: HashMap<(String, String), FnDecl>` — ключ есть
  **спеллинг ресивера** и имя метода. Для blanket-метода (метод на `T` под bound-ом)
  спеллинг ресивера — это буква типопараметра, `"T"`. Два разных blanket-а с одной буквой
  получают один ключ и молча вытесняют друг друга (last-wins). Заплата — по-span-овый
  близнец `mono_method_decls_by_span` — есть признание, что ключом обязан быть
  идентификатор объявления, а не его текст.
* `mono_instantiated: HashSet<String>` — дедуп по **мэнглированному имени**, то есть
  ПОСЛЕ мэнглинга. Тот же порок в другую сторону: мэнглинг схлопывает различимые ключи
  в одну строку, и второй инстанс тихо не эмитится (см. silent type collapse в §3).
* `mono_method_fndecl_for_name` — ещё одна заплата, против first-wins по голому имени
  при перегрузках.

Правило: **ключ есть пара идентификаторов; строка появляется только на выходе, у
печатника C, и никогда не участвует в сравнении.** Дедупликация выполняется по `seen`
до мэнглинга; мэнглинг вызывается ровно один раз на выживший инстанс.

##### Шов

Коллектор — единственное место, где решается «инстанс или словарь»:

```nova
fn policy(key ItemKey) -> Lowering    // Stencil | Dictionary
type Lowering enum | Stencil | Dictionary
```

Сейчас `policy` возвращает `Stencil` всегда. Шов сохраняется даже при вечной полной
мономорфизации, потому что он стоит один `enum` и одну функцию, а без него решение
«моно всегда» зашивается в сотню мест кодогена — ровно как у оракула, где обратный ход
уже невозможен. Шов — единственное, что делает словарный путь добавляемым позже, если
объём C станет проблемой.

##### Инвариант

**Каждый достижимый инстанс инстанцируется ровно один раз.**

Ассерты:

* `assert(!key.subst.has_param() && !key.subst.has_infer())` на каждый push;
* `assert(out.len == seen.len)` после дренажа;
* `assert(work.is_empty())` — фикспойнт достигнут;
* детерминизм: `seen` упорядочен, обход идёт в порядке `NodeId`, повторный `collect`
  на тех же корнях даёт побайтово тот же список (иначе несравнимы сборки);
* инъективность имён проверяется здесь же, хотя имя считает §3:
  `assert(out.map(c_name_of).to_set().len == out.len)` — владелец списка обязан
  поймать коллизию до печати.

##### Донор

* **rustc mono collector**: `Instance { def, args }`, worklist от монотонных корней,
  `MonoItem` дедуплицируется по `Instance`, символьное имя считается позже и отдельно.
  Берём: структура ключа, worklist, дедуп до имени, DCE как следствие корней.
  **Не берём**: варианты `InstanceDef` для shim-ов (`ReifyShim`, `DropGlue`,
  `ClosureOnceShim`) — у нас нет trait-объектов вне Effect-kind; не берём
  CGU-партиционирование и `share-generics`.
* **Go stenciling** (unified IR): полная копия тела на инстанс. Берём именно stenciling.
  **Не берём** GC shape и словари формы — гибридный путь остаётся за `policy`, но
  выключен, потому что D122 требует zero-cost.
* **Zig `Sema`**: мемоизация инстанса по структурному значению ключа. Берём принцип
  структурного мемо-ключа. **Не берём** comptime-исполнение как механизм инстанцирования.

##### Чего не делаем и почему это решение

* **Не инстанцируем по ходу печати** (см. дверь).
* **Не собираем всё подряд с последующей чисткой.** Обратный порядок требует отдельного
  анализа достижимости — у оракула он есть (`compute_dead_decls_with`) и существует
  ровно потому, что коллектора нет.
* **Не допускаем строковых ключей ни в одном промежуточном контейнере** mono. Страж:
  греп по `novac/src/mono/**` даёт ноль карт с ключом `str` для инстансов.
* **Не молчим на полиморфной рекурсии.** `F[T] -> F[Box[T]]` даёт растущий worklist;
  ограничение по `Instance.depth` и ошибка `E_MONO_DEPTH` с цепочкой `origin` от корня.
  Это ошибка компиляции, а не тихий обрыв обхода (D-блок назвать).
* **Не мемоизируем по сигнатуре после стирания** — стирание склеит инстансы с разным
  layout, что и есть силовой вариант той же коллизии.

#### 3. Layout — единственное место, где считаются размер, выравнивание и C-имя

##### Что известно на слое

Тип **закрыт**: в терме нет ни `Param`, ни `Infer`. Известны все поля записи и все
варианты суммы по `DeclId`, известны аргументы `App`. Это единственный слой, где вообще
осмысленно говорить о байтах.

##### Форма данных

```nova
type Layout {
    ro size   int
    ro align  int              // степень двойки, > 0
    ro kind   LayoutKind       // Scalar | Aggregate | Tagged | Ptr | Opaque
    ro fields []FieldPlace     // по индексу поля, в порядке объявления
    ro tag    ?TagPlace        // сумма: смещение и ширина дискриминанта, смещение payload
    ro c_name str              // каноническое имя типа в C
}

type FieldPlace { ro index int, ro offset int, ro ty TypeId, ro c_name str }
type TagPlace   { ro offset int, ro width int, ro payload_offset int }

type LayoutCx {
    mut cache       Map[TypeId, Layout]
    mut in_progress Set[TypeId]      // ловит рекурсию по значению
}

fn LayoutCx.layout_of(ty TypeId) -> Layout
fn c_name_of(item ItemKey) -> str
```

##### Единственная дверь

`layout_of` — единственный производитель чисел. Ни эмиттер, ни рантайм-дескрипторы,
ни GC-карты, ни FFI-обвязка не считают размер, выравнивание или смещение сами и не
выводят их из текста типа. Всё, что нужно в байтах, берётся из `Layout`.

`c_name_of` — **чистая функция от пары (объявление, подстановка)**, а не поле, которое
кто-то заполняет по дороге. Свойства обязательны и проверяемы: детерминированность,
инъективность, стабильность между запусками. Имя кодирует `DeclId` (полный путь модуля,
имя, дизамбигуатор) и рекурсивно имена аргументов подстановки с разделителем, который
не встречается в идентификаторах; сверхдлинные имена схлопываются хешом канонической
строки с сохранением читаемого префикса.

##### Почему C-имя не поле-строка

Если имя есть поле, заполняемое по пути, два разных инстанса получают одно имя — и
второй молча перезаписывает первый в таблице эмиттера. Тело одного инстанса печатается
под именем другого: компилируется, линкуется, падает в рантайме на чужом layout.
У оракула это ровно `mono_instantiated: HashSet<String>` (дедуп после мэнглинга) плюс
заплата `mono_method_fndecl_for_name` против first-wins по голому имени. Имя-функция
делает коллизию обнаружимой: карта `Map[str, ItemKey]` при сборке падает с
`E_C_NAME_COLLISION` и обеими сторонами в диагностике.

##### Инвариант

**`layout_of` принимает только закрытый тип, и это ассерт, а не соглашение.**

```
assert(!ty.has_param() && !ty.has_infer(), "layout_of on open type")
```

— первым выражением функции. Именно этот ассерт физически удерживает слои честными:
если он сработал, нарушение произошло **выше** — чекер положил открытый тип туда, где
ждали закрытый, или коллектор не выполнил подстановку. Мягкая ветка «если `Param` —
считаем размером указателя» превратила бы нарушение порядка слоёв в тихий неверный
layout, и падение случилось бы за километр от причины.

Остальные ассерты:

* `size % align == 0`; `align` — степень двойки;
* чистота: `layout_of(t) == layout_of(t)`, кэш есть только ускорение
  (`assert(cache.get(ty) == fresh)` под debug-флагом);
* `assert(!in_progress.contains(ty))` — цикл по значению есть ошибка `E_INFINITE_SIZE`
  с указанием, где вставить указатель;
* сверка с C: для каждого инстанса с ненулевым размером эмиттер печатает
  `_Static_assert(sizeof(T_c) == N)` и `_Static_assert(offsetof(T_c, f) == K)`.
  Novac считает layout, C-компилятор проверяет — расхождение падает на сборке, а не
  в рантайме.

##### Донор

**rustc `layout_of`**: запрос на `TyAndLayout`, кэш, `FieldsShape`, `Variants`,
требование закрытости типа. Берём: единственная дверь-запрос, кэш, разделение
«размещение полей» и «размещение вариантов», отказ считать layout по открытому типу.

**Не берём**: `Abi`/`Scalar` для register-passing и niche-filling оптимизации — ABI у нас
задаёт C-компилятор, и переупаковка сломала бы `_Static_assert`-сверку. **Не берём**
`LayoutError` как обычный результат: незакрытый тип у нас не пользовательская ошибка,
а баг компилятора, и потому ассерт. Пользовательских ошибок на этом слое ровно две —
`E_INFINITE_SIZE` и обращение по значению к extern-непрозрачному типу (D-блок назвать).

##### Чего не делаем и почему это решение

* **Не переупорядочиваем поля.** Порядок объявления нормативен: он держит FFI и делает
  возможной сверку `_Static_assert`. Zero-cost в D122 — про диспетч, не про переупаковку.
* **Не считаем размеры в эмиттере** и не используем `sizeof` как источник чисел для
  рантайма и GC — только как перекрёстную проверку.
* **Не кладём `Layout` в канал чекера** (§1) и **не кэшируем C-имя в `Instance`** (§2):
  производное значение, хранимое рядом с исходным, расходится с ним.
* **Не поддерживаем `Param` через «размер указателя».** Это и есть словарный путь; он
  войдёт через `policy` в §2, если войдёт, а не через дырку в layout.
* **Не выдаём размер для `Opaque`.** Extern-непрозрачный тип используется только по
  указателю; попытка по значению — ошибка на этом слое, а не «нулевой размер».

#### Экзистенциал против универсала — два лоуэринга протокола, выбирает чекер

Одно имя протокола стоит в двух позициях, и D72 различает их **позицией, а не
ключевым словом**: `fn f(x Hash)` — тип значения, `fn f[T Hash](x T)` — bound.
Запись похожа, лоуэринги разные и несводимые. В первом случае значение несёт с
собой таблицу методов, и вызов идёт через неё; во втором методов в рантайме нет
вовсе — на mono подставлен конкретный тип и вызов прямой. Первое —
**экзистенциал** («существует T, для которого выполнено P»), второе —
**универсал** («для любого T с P»). D72 разводит эти формы таблицей позиций; наша
работа — сделать так, чтобы разведение произошло **один раз, в чекере**, и дальше
только читалось.

##### Донор

* **Go** — interface value как пара `(itab, data)` и предикат принадлежности как
  method set. **Берём**: двухсловное представление экзистенциала и структурный
  предикат — без impl-ов, когерентности и orphan-правил (D53, D15/D42).
  **НЕ берём**: gcshape stenciling + dictionaries Go 1.18 — там универсал
  лоуэрится в словарь, у нас он лоуэрится в mono (D122).
* **Swift** — `any P` против `some P`/`<T: P>`. Swift годами писал обе формы
  одинаково и был вынужден вводить `any` ретроспективно, ломая читателей.
  **Берём урок**: различие форм обязано быть **материализовано полем в IR**, даже
  когда поверхностный синтаксис его не показывает. **НЕ берём**: runtime witness
  tables и value witnesses — они куплены за resilience и стабильный ABI, которых
  у Nova нет и не планируется.
* **rustc** — `dyn Trait` против `<T: Trait>`. **Берём**: само разделение и
  таблицу методов у динамической формы. **НЕ берём**: trait selection,
  object safety на декларации, coherence.

##### Что известно на слое

* `bounds`: удовлетворяет ли конкретный `Ty` протоколу `P` и **каким набором
  методов** (упорядоченным).
* `check`: позиция употребления, значит — форма; плюс подстановка на call-site.
* `mono`: `substs`, то есть конкретный `self_ty` для каждого сайта упаковки.
* `emit`: про протоколы **ничего**. Он видит запись в канале и лоуэрит её.

##### Форма данных

```
type ProtoForm enum Existential | Universal

type ProtoUse {
    site       NodeId
    proto      DeclId
    proto_args []Ty        // D355: выводятся из bound-а, руками не пишутся
    form       ProtoForm
    witness    WitnessId   // валиден только при Existential
    param_ix   int         // валиден только при Universal: индекс Param
}

type Witness {
    proto      DeclId
    self_ty    Ty          // конкретный: ни Param, ни Infer
    methods    []FnInstId  // порядок = порядок объявления методов в protocol
}

type CallLowering enum Direct | ThroughWitness

type ResolvedCallee {
    site       NodeId
    lowering   CallLowering
    target     FnInstId    // при Direct
    witness    WitnessId   // при ThroughWitness
    slot       int         // индекс метода в witness.methods
}
```

`ResolvedCallee` кладётся в существующий канал `resolved_callees` (D458) — новой
шины не заводим. Рантайм-форма экзистенциала — фат-указатель в две ячейки:

```
struct NovaExist { void *data; const NovaWitness *wit; };
```

и это тот же бокс `NovaBox_<proto>`, что эмитится сегодня (Plan 97.1, D142).
Vtable-структура **декларации** эмитится только для Effect-kind
(`02-types.md:1173`); у протокола таблица собирается **на сайте упаковки** — там и
только там известен `self_ty`.

##### Единственная дверь

* Решает `bounds.witness_of(ty, proto) -> Result[WitnessId]` — единственное место
  во всём компиляторе, где вообще проверяется принадлежность типа протоколу.
* Записывает `check` — единственный писатель `ProtoUse` и `ResolvedCallee`.
* Читает `emit`. У эмиттера **нет ни одной функции**, которая принимает протокол
  и возвращает решение; есть только чтение по `site`.
* Новые поля канала фиксируются D-амендментом в том же слиянии (D-блок назвать).

##### Инвариант

**Эмиттер не решает, какой это протокол, — он читает решение.** Ассерты:

1. `lower_call(site)`: запись обязана быть. Её отсутствие — `ICE("callee not
   resolved at site")`, а не запасной путь. Ни одного `default`-плеча в match по
   `CallLowering`.
2. `assert(rc.lowering == Direct => target.substs.has_no(Param | Infer))`.
3. `assert(rc.lowering == ThroughWitness => witness.self_ty.is_concrete())`.
4. Архитектурный страж `check-novac-emitter-reads-decision.sh`: в модуле эмиттера
   ноль вхождений `witness_of` / `protocol_specs` / `method_set` и ноль строковых
   сравнений с именами протоколов. Страж обязан доказывать красноту на подсаженной
   регрессии — как остальные `check-novac-*`.

##### Как это устроено у оракула сегодня и почему это компромисс, а не архитектура

`compiler-codegen/src/codegen/emit_c.rs` держит `protocol_vars: HashMap<String,
String>`, `fn_protocol_params`, `protocol_method_registry`, `protocol_var_vtable`,
`protocol_decl_file`, `current_fn_returns_protocol`, `current_array_protocol_box` —
семь таблиц, которыми **эмиттер восстанавливает по именам то, что чекер уже
знал**. Там же `infer_protocol_structural_binding` с ограничителем глубины
`proto_unify_depth: Cell<u8>`: унификация протоколов в эмиттере не сходится сама и
обрезается числом. Причину называет комментарий в том же файле (≈ строка 808):
protocol-типизированный параметр «erases to `void*`», и тип аргументов вложенного
вызова «cannot be inferred from C types alone». Это прямое признание — решение
потеряно между чекером и эмиттером, и эмиттер угадывает его заново из C-типов и
строк. Ни одну из этих таблиц мы не переносим: вместо них поле `form` и
`WitnessId`.

##### Чего не делаем и почему это решение

1. **Не делаем универсальный словарный путь (dictionary passing) — ни сейчас, ни
   на Э4.** Не «не успели»: D122 (amend 2026-05-20) разрешил эффекты у
   protocol-методов и тем же абзацем зафиксировал, что vtable-ABI не пробрасывает
   effect-handler-ы, значит effectful bound **обязан** mono-диспетчиться. Пока
   эффекты допустимы в bound-ах, словарного универсала в общем случае не
   существует. Частичный словарь «только для чистых bound-ов» — это две модели
   диспетча в одном компиляторе, то есть второе место, где эмиттер снова начнёт
   угадывать. Отказ — решение.
2. **Не вводим object safety на декларации протокола.** Экзистенциал легален ровно
   тогда, когда `witness_of` смог построить witness; метод, упоминающий `Self` вне
   позиции получателя, роняет построение — и диагностика садится на **сайт
   упаковки**, где `self_ty` есть, а не на объявление, где его нет. Это
   противоположно rustc, и намеренно: протоколы структурные, у декларации нет
   списка реализаторов, запрещать её целиком не за что. (D-блок назвать.)
3. **Не даём эмиттеру запасного пути «не знаю — заверну в бокс».** Незнание — ICE.
   Бокс без записи в канале это ровно тот класс, который сегодня и порождает
   угадывание.
4. **Не выводим `proto_args` в эмиттере.** Они выводятся из bound-а (D355) и
   передаются полем; повторный вывод — второй источник истины.

#### Решения и развилки — что принято, что открыто, что переходится только в одну сторону

Раздел читается **до** слоя `types` и ни от одного слоя не зависит. Для
реализатора существует только то, что записано здесь и подтверждено D-блоком; всё
остальное — не «пока не решено», а «не существует».

**Донор — журнал решений rustc (RFC + FCP).** Берём форму записи: утверждение,
причина, **явная обратимость**, имя стража. НЕ берём машинерию editions и
stability-атрибутов: у Nova нет ни стабильного ABI, ни релиза, и заводить механизм
совместимости раньше первого пользователя значит платить за необратимость,
которой ещё нет.

| решение | что принято | почему | обратимо ли |
|---|---|---|---|
| **Полная мономорфизация — сейчас, не на Э4** | Каждый вызов bound-метода лоуэрится в прямой вызов инстанса `(DeclId, substs)`; vtable остаётся только у Effect-kind и у экзистенциала | D122 требует дословно zero-cost и паритет Rust `impl<T: Hash>`; `02-types.md:1173` — protocol compile-time-only; у Nova нет ни стабильного ABI, ни рефлексии, ни cross-crate инстанцирования, то есть **нет ни одного покупателя словарей** | **Частично и только вверх.** Словарный путь остаётся *добавляемым*, пока сохранён шов коллектора `(DeclId, substs)`: добавление не ломает написанный код. Для effectful bound-ов — **никогда**: vtable-ABI не несёт effect-handler-ов (D122 amend). Обратный ход (словарь как единственный путь) невозможен вовсе — это отказ от zero-cost, то есть от D122 |
| **Неоднозначность — ошибка, а не ранжирование по score** | Два и более подходящих кандидата → диагностика с перечислением. Нет score, нет «более специфичный побеждает», нет tie-break по конверсиям | Лагерь rustc/Go. У Swift ранжирование дало экспоненциальный солвер и пользовательскую ошибку «expression too complex»; у C# правила «better function member» занимают десятки страниц спеки и правятся до сих пор | **Односторонне, и мы в правильном конце.** Переход ошибка → ранжирование **совместим**: он расширяет множество принимаемых программ, ни одна работавшая не ломается. Обратный переход ломает любой код, который на ранжирование опёрся. Значит отложить ранжирование бесплатно, ввести — навсегда |
| **Нет ассоциированных типов и узла `Alias` с нормализацией** | В `TyKind` нет проекций и нормальных форм; равенство типов остаётся равенством интернированных id | Ассоциированный тип втягивает нормализацию: сравнение типов перестаёт быть сравнением id и становится сравнением нормальных форм — хроническая боль rustc (`normalize`, циклы, «overflow evaluating»). Контракт у нас есть набор сигнатур и ничего кроме (D15/D42) | **Обратимо, но цена растёт монотонно** с числом сайтов сравнения типов; это **ставка**, а не отсутствие вопроса. Держится ровно до цепных bound-ов (D355 §6, параметрический возврат). Если они появятся — нормализация вводится **до** них, отдельным слиянием: задним числом придётся переписать каждое место, где сегодня стоит равенство id |
| **Вариантности нет — записано инвариантом** | Присваиваемость есть равенство id. `Vec[Cat]` не является `Vec[Animal]` ни в какую сторону; коэрция не имеет права смотреть внутрь `App(DeclId, args)` | Без записанного инварианта вариантность просачивается **ad-hoc**: первый «удобный» частный случай в коэрции (массив, `Option`, функциональный тип) вводит подтипирование де-факто, но без правила вывода — и дальше каждое новое место решает по-своему. Так она и попадает в язык: не решением, а поблажками | **Обратимо вверх — но только при соблюдении инварианта сегодня.** Ввести вариантность позже есть расширение, оно совместимо. Если же коэрция успела её сэмулировать в частных случаях, обратного хода нет: правило придётся согласовывать с уже написанным кодом, и оно выйдет не тем, каким должно быть. Поэтому это инвариант с ассертом, а не «пока не делаем» |
| **Тело дженерика проверяется в точке ОПРЕДЕЛЕНИЯ против объявленных bound-ов** | `fn f[T P](…)` тайпчекается один раз обобщённо; всё, чего нет в bound-е, — ошибка в теле, а не на инстанцировании. Обязанность доказать bound лежит на вызывающем | Иначе автоматически получается модель шаблонов C++: ошибка всплывает, только если конкретная инстанциация реально дошла до строки. Это дословно дефект реестра №303, и у оракула он уже случался | **Самое трудновозвратное решение из всех — считаем невозвратным.** Ослабить (проверять на инстанцировании) можно в любой момент и дёшево; вернуть строгость нельзя **никогда** — весь написанный к тому времени код будет опираться на позднюю проверку. C++ и Zig в этой ловушке навсегда: у C++ concepts добавлены, но старая модель обязана работать; у Zig проверка тела comptime-функции принципиально ленивая |
| **Глобального вывода нет никогда** | Вывод ограничен телом одной функции; сигнатуры аннотируются; ни одна инференс-переменная не переживает границу тела (ассерт) | Ни один из четырёх эталонов глобального вывода/HM не делает: подтипирование, перегрузка и протоколы убивают принципиальный тип. Плюс инженерное: выведенная сигнатура становится публичным API де-факто и меняется молча | **«Никогда» здесь — решение, а не оценка сложности.** Формально ослабление (вывод сигнатур) расширяет и потому «обратимо вверх»; практически необратимо: каждая выведенная сигнатура превращается в контракт, который нельзя ужесточить обратно, не сломав вызывающих. Строку считаем закрытой и не открываем |

##### Что известно на слое

Утверждение, причина, класс обратимости, имя стража. Не известно и не должно
быть: **как это реализовано** — реализация меняется, решение нет.

##### Форма данных

```
type Reversibility enum Free | UpOnly | Never

type Decision {
    id     str            // номер D-блока; пока не выдан — «(D-блок назвать)»
    claim  str
    why    str
    rev    Reversibility
    guard  str            // имя стража; пусто допустимо только у Free
}
```

`UpOnly` — переход в одну сторону; **направление** пишется в `why` явным словом
(«ослабить можно, вернуть нельзя» либо наоборот). `Never` — обе стороны закрыты.

##### Единственная дверь

Решение вступает в силу **только** D-блоком в `spec/decisions`, и номер даёт
интегратор — сам не берёшь, пишешь «(D-блок назвать)». Язык-меняющее слияние без
амендмента в том же слиянии не пушится. Реализация не вправе завести новое решение
комментарием в коде: комментарий, противоречащий D-блоку, — дефект, а не
уточнение.

##### Инвариант

Каждая строка с `rev != Free` **обязана назвать стража**. Ассерт реестра:

```
assert(d.rev == Free or d.guard != "")
```

Смысл прямой: необратимое решение, за которым никто не следит, живёт до первого
удобного случая. Конкретно: вариантность стережёт греп по коэрции (ноль мест, где
присваиваемость не сводится к равенству id); определение-против-инстанцирования —
тест, обязанный краснеть на теле, зовущем метод вне bound-а; мономорфизацию —
страж отсутствия второго пути диспетча в эмиттере (см. первый раздел).

##### Чего не делаем и почему это решение

1. **Не держим здесь «открытых вопросов».** Строка — либо решение с причиной и
   обратимостью, либо её тут нет; вопросы живут в `spec/open-questions`. Смешение
   двух жанров в одной таблице через полгода делает их неотличимыми.
2. **Не пишем «следует рассмотреть», «возможно позже», «в будущем можно».**
   Формулировка без обратимости — не решение, а отложенный спор, и реализатор
   закроет его как удобнее.
3. **Не отвечаем в колонке обратимости словом «да».** Колонка честная: каждая
   строка называет **направление** перехода и его цену, включая строки, где цена —
   «никогда».

## 4. Карта информации

Референс — каналы 196, доказанные живьём (mismatch=0 на флипнутых классах). Каждый
класс информации — одна дверь-производитель; потребители читают, не перевычисляют
(урок 196: `infer_call_ret_c` мимо чекера стоил месяцев).

| класс информации | дверь-производитель | потребители |
|---|---|---|
| токены | `lex` | `parse` |
| синтаксис | `parse` (строит) / `tree` (владеет) | `syntax` → все |
| позиции | `syntax` (вычисляет из ширин) | `diag`, LSP, все |
| «имя → объявление» | `names` | `check`, LSP |

чужой класс. Счётчик: **2**.

## 4а. Идентичность — не имя

Требование владельца 2026-08-14: имена повторяются — между модулями, между вариантами
разных сумм, между методами разных типов — и в нынешнем компиляторе это источник
постоянных багов. Класс измерен многократно: №576/№613 — обход достижимости ходит по ИМЕНАМ (голый
конструктор варианта терял метод-сет типа; ранняя гипотеза «имя решает раньше
объявления» опровергнута окном плана 270 — правим по финальному вердикту реестра), B11q
(нить из одних имён — баунды потеряны), №534 (захват `spawn` берёт чужое имя), №617
(алиас утекает за пределы файла), [M-d289] (коллизия модульно-квалифицированных путей);
корневой класс окна C так и называется — «резолв по имени, а не по типу».

**Правило: имя — ключ ровно в одной двери (`names`), идентичность — везде дальше.**

1. Каждая декларация при резолве получает **`DeclId`** — уникальный, стабильный внутри
   компиляции (эталон — rustc `DefId`). После фазы `names` ни одна таблица не ключуется
   строкой: `sem`, `mono`, `lower`, `emit_c` знают только `DeclId`/`NodeId`.
2. **Вариант суммы = (DeclId суммы, индекс варианта)**, не имя. Имена вариантов свободно
   повторяются между суммами — коллизия невозможна по построению, а не по дисциплине.
3. **Метод**: пара «(DeclId типа-носителя, имя)» существует только ВНУТРИ резолва; наружу
   выходит `DeclId` метода. «Метод = функция с receiver» (§2) делает это бесплатным.
4. **Области видимости — пространствами**: варианты живут в пространстве своей суммы,
   методы — своего типа, top-level — своего модуля. Голого глобального пространства имён
   нет вовсе.
5. **Мэнглинг — функция от DeclId-пути** (модуль → тип → имя → substs), а не от имени:
   ровно то, что `ResolvedType::Named{module}` уже начал в текущем каноне.
6. **Страж** (входит в `check-novac-deps.sh`-семейство): `Map[str, …]` как таблица резолва вне
   модуля `names` — красный. Строка законна как ключ только там, где происходит
   сопоставление написанного текста с декларацией, — и это одно место.

Инварианты: (1) после `names` строковых ключей нет; (2) `DeclId` стабилен внутри
компиляции. Счётчик: **2**.

## 5. Дерево

Референс — **Roslyn** (красно-зелёные деревья). Решение 5 зонтика.

- **Зелёный слой** (`tree`): неизменяемые узлы; хранят **ширины**, не абсолютные позиции;
  тривия (пробелы, переводы строк, комментарии) прикреплена к токенам
  (leading/trailing); переиспользуются между правками.
- **Красный слой** (`syntax`): родители и абсолютные позиции, вычисляются лениво;
  типизированный AST — **проекция**, не вторая структура.
- **Узлы-ошибки — по построению**: нераспознанная конструкция остаётся поддеревом сырых
  токенов. Сломанный и недописанный ввод представим всегда; «продолжить после ошибки»
  есть куда записывать.

Инварианты: (1) **ре-сериализация зелёного дерева побайтово равна исходнику** — главный,
проверяется на каждом файле корпуса дифф-гейтом; (2) у каждого узла есть span (через
ширины); (3) зелёные узлы неизменяемы. Счётчик: **3**.

Нормативно в [274 §4](../plans/274-novac-self-hosted-compiler.md); здесь — как карта их

## 7. Диагностика

Референс — **rustc** (`--error-format=json`). Первый потребитель — агент (274 §6),
поэтому схема нормативна, а человеческий текст — рендер из неё, никогда наоборот.
Страж — `check-novac-diag-schema.sh` с Э1.

```json
{
  "id": "стабильный-в-выдаче идентификатор диагностика",
  "code": "E_...",
  "severity": "error | warning",
  "primary": { "file": "...", "start": 0, "end": 0 },
  "message": "...",
  "notes": [ { "span": {}, "text": "..." } ],
  "suggestion": { "span": {}, "replacement": "..." },
  "poisoned_by": "id первопричины | null"
}
```

**Отравление:** узел, построенный по сломанному вводу, помечен; фазы по нему молчат;
вторичный диагностик либо подавлен, либо несёт `poisoned_by`. **Явный сентинел
обязателен** — измеренная альтернатива хуже: нынешний чекер держит «нет каскадов» на
пермиссивном unknown («не вывелось — пропусти проверку»), и та же механика глотает
настоящие ошибки: `fn f() -> int { "str" }` и `if 5` проходят `nova check` зелёным
(№652, подтверждено пробой). Отравление отличается от пермиссивности одним: у него есть
правило «ошибка УЖЕ репортнута», у пермиссивности — нет. «Одна ошибка — одна
причина» держит `check-novac-no-cascade.sh` (фикстуры «одна посеянная опечатка → ровно один
диагностик»), потому что дифф-гейт каскады не ловит — оракул сам каскадит.

Инварианты: (1) каждый диагностик валиден против схемы; (2) у error всегда есть
`primary`-span. Счётчик: **2**.

## 8. Семантический слой

Референс — **свой канон, доказанный 196-м, + rustc** (интернирование). Дом урожая 196
(§14): каналы становятся полями `sem`, а не изобретаются заново.

- `types`: `ResolvedType` — единственная форма правды о типе (D315); интернирование —
  структурно равные типы суть один объект; **без арен** — у нас GC, протяжка времён
  жизни не нужна (аренная механика rustc — обход отсутствия GC, не переносится);
- **generic-параметр — полный объект с первого дня**: TypeVar несёт свои constraints
  (баунды, share-ness, thread-safety) от объявления до точки использования — эталон
  rustc `ParamTy`+predicates. Урок корня B11q (нить `gs` из одних ИМЁН через 31 сайт —
  тупик, на котором консолидация 196 упёрлась) и №150: это ОДНА абстракция под оба
  класса, проектируется один раз;
- `sem`: `resolved_types: NodeId → ResolvedType`, `resolved_callees`, `node_substs` —
  только данные, ноль логики;
- `check` — единственный писатель; после него `sem` заморожен.

Инварианты: (1) один интерн на структурно равный тип; (2) `sem` неизменяем после
`check`. Счётчик: **2**.

## 12. MIR — эскизы (полная проработка на Э4)

Эскиз = референс + границы + «что берём/не берём», БЕЗ разрешения вопросов уровня Э4.

- **Скелет** (rustc MIR): базовые блоки, локалы с типами из `sem`, терминаторы.
  Берём форму; не берём четыре промежуточных уровня rustc (AST→HIR→THIR→MIR —
  наросшая история, нам хватит одного понижения).
- **Дропы и перемещения** (rustc drop elaboration / move-check): D432 auto-cleanup и
  линейность D131/D133 — явными инструкциями на CFG; `spawn consume` проверяется по
  графу — на дереве это либо отвергает корректное, либо пропускает гонку (№456 —
  измеренная цена).
- **Владение и протоколы** (Swift SIL): экзистенциалы и структурные протоколы —
  напряжение «обобщённый код против стёртого значения» (разбор Display/to_str).
- **Эффекты** (Koka, evidence passing): хендлер как значение-свидетельство; у rustc
  ответа нет. Стык с файберами — §15.
- **Safepoint'ы и GC-карты** (Go SSA): точки приостановки — явные в MIR, стек-карты
  для Boehm-замены в перспективе; в месяц не трогается.

## 12а. Развилка мономорфизации — варианты и цены (решение на Э4, не здесь)

| вариант | за | против |
|---|---|---|

| **B. GC-shape словари** (Go 1.18) | код на КЛАСС форм (все указательные — одна); резко меньше C; быстрая компиляция | непрямые вызовы; словари в ABI; стык со структурными протоколами и эффектами через словарь — не исследован |
| **C. Гибрид** (mono для примитивов/малых, shape для указательных) | баланс цены и скорости | опасность класса «второе вычисление» (К4, §16): две механики. Легален ТОЛЬКО если выбор стратегии — решение ВНУТРИ одной двери `mono` (per-instance политика), а не два пути кода по конвейеру |

Решение здесь НЕ принимается (274 §9, Э4); эскиз существует, чтобы Э1–Э2 не заложили
ничего, что закрывает вариант B или C — а именно: подстановки только через `node_substs`
(§14.1), никакой mono-логики в `emit_c`.

Пробы `compiler-codegen/src` (файл:строка — доказательства, не мнения).

| требование | вердикт | доказательство | что берёт novac |
|---|---|---|---|

| отравление | **формально выполнено — механикой, которая сама дефект** | каскадов нет, но за счёт пермиссивного unknown (`types/mod.rs:24171`, `:12213`, `:6911`); та же механика глотает реальные ошибки — №652, подтверждено пробой (`fn f() -> int { "str" }` и `if 5` — PASS) | §7: явный poison-сентинел с правилом «уже репортнуто» |

Оговорка переноса (холодное чтение §4а/§8 иначе видит противоречие): ключи и
идентичности в таблице выше — ФАКТЫ нынешнего компилятора (`ExprId`, «identity = span
декларации»); в `novac` при переносе ключ = `NodeId`, идентичность callee = `DeclId`
(§4а) — span-ключ деталью не переезжает.

Контракт каналов, который переносим дословно: **«материализуй только полностью
разрешённое»** — residual generic не пишется, отсутствие ключа = легальный miss, не
ложь; ложная материализация хуже молчания (хвост d119 — измеренный случай).

## 15. Непокрытые места — поимённо

Ни один референс не покрывает; проектируем сами, каждое — с записанной причиной.

1. **Эффекты × M:N-файберы.** Koka компилирует эффекты без тредов; Go даёт M:N без
   эффектов. Комбинации целиком нет ни у кого. Открыто; черновик — на Э4 (MIR-эффекты).
2. **Эффекты через границу `spawn`.** Хендлер — значение; что происходит при переносе
   продолжения на другой воркер. Открыто; решается вместе с 1.
3. **Линейность при отмене `supervised`.** consume-обязательства на пути отмены/таймаута
   (D408/D449 × D131) — пути появляются не там, где написаны. Открыто; Э4, дропы на CFG.
4. **Рантайм-градусные контексты** (no-alloc/no-GC код планировщика и клея аллокатора) —
   нужны Э6 (Vela-на-Nova); Go решает `nosplit`-дисциплиной вне языка. Кандидат в
   языковое решение — D-блоком, не раньше Э4.
5. **Шов LSP** — каналом что: in-proc FFI или IPC-процесс. **Решить перед Э3** —
   дедлайн из 274.1; на месяц не влияет.

## 16. Классы проблем двух месяцев — и их конструктивное решение

Требование владельца 2026-08-14: классы, с которыми проект возится последние два месяца,
извлечены из реестра №221.1 (не выдуманы), и на каждый — правильная реализация в `novac`
с тремя доказательствами: **Верность** (почему решение убивает класс), **Место**
(модуль/слои карты), **Минимальность** (что ломается при снятии каждого инварианта).
Структуру держит страж `check-novac-arch-class-proofs.sh` (самотест 5/5); содержательность
— приёмка 274.1.

Источник: кластеризация реестра четырьмя чтецами (№390–652 + backlog), семь классов.
Статус: адверсарная проверка завершена — 7/7 вердиктов, ДВЕ волны (вторая — по
исправленному тексту). Все находки внесены; переатрибуции носителей отражены в блоках.
Выжившее ядро: К4 — верность и место устояли со второй волны; остальные пересобраны.

### К1. M:N-рантайм: множество несогласованных учётов вместо одного владельца

Носители после адверсарной чистки: ядро — №438, №427, №443, №498 и родня (гонки
учётов самой Vela). Переатрибуции: №456 — корнем в К5 (симптом рантаймный, корень
компиляторный — consume-identity, так пишет и реестр); №458 — протокольная
недоведённость parной операции (род К7), не учёт; №457 — не перевоспроизведён
(гипотеза реестра: носитель №456/№498); M-218 — гонка Rust-ДРАЙВЕРА, закрыта локально
2026-07-20, слой решением К1 не покрывается. Механизм:
каждая фича заводит свой учёт — ~28 атомиков состояния фибра, два счётчика владения
одним сокетом, свой путь доставки отмены у каждого примитива; комбинации не
спроектированы, дефекты видны только под нагрузкой (257 следов починки гонок).

**Решение:** одно слово состояния на сущность, переходы — CAS по явной таблице; один
владелец учёта на ресурс. Реализуется при переезде Vela на Nova (Э6), вход —
консолидация состояния [250](../plans/250-vela-state-consolidation.md).
**Верность:** референс продакшеном — ранний Go держал ОДНО слово `gstatus` с явными
переходами и жил без этого класса. Честно о ролях: оракул C-Vela держит только
СОХРАНЕНИЕ поведения (он сам несёт дефекты класса); класс убивают конструкция + машинный
инвентарь слов состояния ([250](../plans/250-vela-state-consolidation.md)) +
стресс-гейт [debugging-races.md](debugging-races.md) как приёмка.
**Место:** рантайм (Э6, 274 §1.3), НЕ карта компилятора; компилятора касается ДВУМЯ
рёбрами: «одна дверь атомиков» (§10) и consume-identity половин ресурса — это К5
(`check`/`lower`), где живёт корень №456.
**Минимальность:** инвариант «состояние сущности меняется одним CAS-переходом таблицы»
заменяет ~28 согласований пар атомиков; «один владелец учёта на ресурс» — его СЛЕДСТВИЕ
(второй счётчик того же ресурса = второе слово той же сущности, запрещён тем же
инвариантом), не отдельный. Отдельное плечо — доставка отмены: инвариант «отмена
приходит переходом слова состояния, не отдельным каналом»; цена его снятия — вечные
зависания под cancel (семья №457/№480). Итого два инварианта, и меньше нельзя: слово без
правила доставки отмены оставляет живым второй по цене под-механизм класса.

### К2. Резолв по голой строке имени через плоские last-wins таблицы

30 носителей (№536, №576, №617, №534, №623, M-d289 и родня; по вердикту К3 сюда же
переатрибутированы №613 — «обход достижимости ходит по именам», род №576 — и №627 —
выбор не того callee через границу алиаса, род №536/№617). Механизм: CU-широкие
таблицы ключуются именем без модуля/типа/области; последняя запись выигрывает, диспетч
молча берёт чужое объявление; исход зависит от состава CU.

**Решение:** §4а целиком — `DeclId` после единственной двери `names`; пространства имён
на сумму/тип/модуль; `names` порядконезависим (collect → resolve).
**Верность:** двухчастная (вердикт: одночастная держала только пол-класса). НИЖЕ
`names` коллизия невыразима — таблицы ключуются идентичностью, совпадение имён не
совпадение ключей (rustc `DefId`, продакшен). ВНУТРИ `names` — единственного места, где
строки легальны, — класс держит инвариант (а): резолв ключуется парой
(`NamespaceId`, имя), плоской CU-широкой таблицы кандидатов не существует; квалификатор
и тип приёмника ФИЛЬТРУЮТ пространство, а не гейтят пост-фактум (механизмы №536/№627 —
ровно пост-фактум-гейт над плоской таблицей). Оговорка носителей: №623 — заявленная
форма не воспроизведена пробой 2026-08-13, его механизм («единственный кандидат без
проверки годности») — правило годности в `check`, не ключевание.
**Место:** `names` (единственная строковая дверь; дом инварианта (а)) + `sem` (носит
DeclId); `parse` не резолвит; `emit` имён не РЕЗОЛВИТ — имя доезжает компонентом
`DeclId`-пути данными пониженной формы (§3, мэнглинг §4а п.5).
**Минимальность:** ДВА инварианта: (а) внутри `names` ключ несёт `NamespaceId` — снять
при зелёном (б): №536/№627/остаток №534 возвращаются, страж строковых ключей их не
видит; (б) после `names` строковых ключей нет (`check-novac-no-string-keys.sh`; для (а)
тот же страж получает второй чек: таблица в `names` без `NamespaceId`-компонента —
красная) — снять: №617-кодоген и №613-достижимость возвращаются. Каждый контрпример
бьёт по своему инварианту.

### К3. C-представление порождается посайтно из текста типа

26 носителей (№581, №483, M-valuerecord-семья и родня). Переатрибуции по вердикту:
№613 и №627 — в К2 (реестр сам вяжет их к №576 и №536/№617: там неверен РЕЗОЛВ, и
каноничное имя неверного метода остаётся неверным методом); №619 — вне семи классов
(комментарий-дрейф, род №484: текст, не поведение). Механизм: имя/форма C
форматируются локально на сайте из текстового представления типа — две схемы имени
одного типа, heap-допущения зашиты в бокс/mono/vtable-пути, value-записи и составные
payload-формы дают CC-FAIL на прошедшем check коде.

**Решение:** §9 — бэкенд читает ТОЛЬКО пониженную форму; C-имя — одна чистая функция от
канона `ResolvedType` + `DeclId`-путь (§4а п.5); формы значений (value/tuple/payload) —
явные в `lower`, а не допущение эмиттера.
**Верность:** источник один И дверь одна: всё вычисление C-имени и репрезентации — один
модуль ниже шва, держится стражем `check-novac-c-name-door.sh` (форматирование
имени/репрезентации вне двери — красное; вердикт показал, что без НАЗВАННОГО стража
«одна функция» — проза: две функции от одного канона легальны по всем рёбрам). То же
плечо убивает valuerecord-семью: две репрезентации одного канона — это два выхода одной
функции, невыразимо. Прецедент в малом — D315 (ретайр `type_ref_to_c`). Переатрибуция:
№483 — корень не имя, а фабрикация `nova_unit` для расходящегося хвоста (`Never`);
решается явным представлением расходимости в `lower`/MIR (§12, Э4); до Э4 держится
правилом `lower`: расходящееся выражение не материализует значения.
**Место:** `lower` + `emit_c` ниже шва; рёбра §3 запрещают бэкенду доступ к тексту
типов и к `syntax` — посайтному форматтеру негде взять вход. Уточнение контракта ребра
(внесено в §3): пониженная форма НЕСЁТ интернированный канон типов ДАННЫМИ — поэтому
«функция от `ResolvedType` в `emit_c`» не противоречит запрету ребра-ИМПОРТА к `types`.
**Минимальность:** пересчитана второй волной — несущий инвариант ОДИН, семантический —
«C-имя и репрезентация — функция от интернированного канона (`ResolvedType` +
`DeclId`-путь): один канон ⇒ ровно одно имя и одна репрезентация». Пункты (а) «ровно
одна функция» и (б) «вход — только канон» — его конструктивная РЕАЛИЗАЦИЯ, не отдельные
инварианты: (а) исключает два выхода (№581 — обе схемы выводились из типа двумя
функциями), (б) исключает вход, различающий написания (`[]T`=`Vec[T]`). Меньше нельзя,
потому что подмножества {а} и {б} падают каждое своим контрпримером — а семантический
инвариант целиком и есть их конъюнкция, выраженная одной фразой.

### К4. Второе вычисление уже решённого суждения

32 носителя (№480, №541, №634, P67-LEGACY-класс). Переатрибуция: №495 — в К6/К7 (его

### К5. Владение объявлено прозой; энфорс знает только канонические пути

Механизм: `ro`/`consume`/unsafe-обязанности не выражены в представлении (пара булевых

match-payload, defer, detach-капчер молча гасят обязательство.

**Решение** (три звена; третье добавлено второй волной — unsafe-плечо механизма первые
два не закрывали): (1) режим владения — в представлении: перечисление Ro/Mut/Consume в
типе, не пара булевых; обязанность из докстринга нелегальна; (2) дропы и
consume-обязательства — явные MIR-инструкции, проверка — баланс по ВСЕМ путям CFG;
(3) **unsafe — часть сигнатуры** (`unsafe fn`): фабрикация значений мимо конструктора
легальна только через unsafe-дверь, вызов — только из unsafe-контекста (носители №419
`append_zero`, №422 `Vec.new(ptr,len,cap)` — у них баланс владения сходится тривиально,
их держит именно звено 3).
**Верность:** rustc drop elaboration / move-check — продакшен-прецедент звеньев 1–2;
№456 — точно по реестру: «авто-cleanup срабатывает безусловно — дизарм на пути явного
close не виден», цена дерева вместо графа: по CFG путь close — обычное ребро. Оговорка:
«включая отмену и таймаут» держится только после закрытия §15.3 (открытый вопрос);
пометка источника: M-d180-семья живёт в backlog, не в №221.1.
**Место:** режимы и правила — `check`; баланс — пасс над MIR ПОСЛЕ `lower` (на дереве
нельзя — §12); диагностики пасса — по ребру `lower`→`diag`, внесено в §3 (иначе страж
рёбер краснил бы легальную реализацию).
**Минимальность:** ДВА инварианта (вердикт: одного мало — unsafe-носители проходят
зелёный баланс): (а) каждое обязательство выражено в представлении (режим в типе,
unsafe в сигнатуре) — снять: балансировать нечего, №467/№419/№422 возвращаются при
зелёном (б); (б) баланс обязательств по всем путям CFG — снять: путь
(match-payload, defer, detach-капчер) гасит обязательство молча — №456, M-d180.

### К6. Энфорс посажен на перечисление синтаксических форм

Носители после чистки второй волны: №466 — корнем B (четыре ветки конструирования мимо
обёртки; его же корни «нет правила на присваивание полю» — в К5, release-стирание
`#debug` — в К7), «пять из шести форм параметра» и родня. Переатрибуция: «семья №649» —
вне семи классов (род стражей гейта №645/№647/№648/№649: механизм отвечает не на тот
вопрос — не формы AST). Механизм: проверка написана по списку конкретных форм AST;
незанесённая форма проходит молча; рефакторинг пользователя обходит энфорс.

**Решение** (дом канонизации исправлен второй волной — прежняя формула «parse→lower»
противоречила §5-инв.1 и позиции `lower` после `check`): канонизирует **типизированная
проекция `syntax`** (§2): поверхностные формы живут только в зелёном дереве (лосслесс
не страдает), `check` по контракту ребра §3 видит ТОЛЬКО канонические узлы; правило
пишется один раз против канона (примеры в карте: метод=функция, «без дженериков» =
пустой список, позиция типа не выбирает конструктор).
**Верность:** «незанесённая форма» не существует для правил по построению — контракт
ребра `check`→`syntax`; сама проекция тотальна: исчерпывающий match без wildcard (родня
инварианта К7-(а)), непокрытая поверхностная форма — ошибка компиляции компилятора;
хвост давит `check-novac-diff-fuzz.sh` (после Э2); прецедент — desugar rustc.
**Место:** канонизация — `syntax` (проекция); правила — только `check`; зелёное дерево
держит лосслесс (§5), `emit` форм не знает.
**Минимальность:** счётом «ноль НОВЫХ инвариантов» (вердикт предлагал пару — берём
вариант сильнее): (а) «правило только на каноне» — это КОНТРАКТ ребра `check`→`syntax`,
посчитан в §3, отдельного инварианта не заводит; (б) «нормализация тотальна» — это
исчерпывающий match проекции, тот же механизм, что К7-(а). Снятие контракта ребра —
правила снова видят поверхностные формы, комбинаторика (форма × правило) возвращается;
снятие тотальности — молчаливый пропуск формы, №466-корень B.

### К7. Полуготовый механизм: возможность без обязательств

17 носителей (семья №652, `-> consume T` как no-op, `#zero_on_move` с молчаливым
непринятием, №465 как измеренный прецедент слабой фикстуры). Переатрибуция: №469 — вне
К7 (работающий `__sret` без грамматической формы; семья «спека↔реализация разошлись»,
№487). Механизм: синтаксис принят, а семантика/диагностика/энфорс не доведены —
конструкция парсится и молча не работает; в представлении нет Poisoned,
«недоведённость» неотличима от «законно неизвестного».

**Решение** (пересобрано по вердикту — прежняя опора на `check-test-fixture-coverage.sh`
не держит: тот страж дифф-базный и слеп к слиянию БЕЗ нового кода диагностики, ровно где
класс и рождается): главный инвариант — ПО ПОСТРОЕНИЮ: **диспетч `check` по видам узлов —
исчерпывающий match БЕЗ wildcard-арма**; вид узла, не получивший правила, не проходит
молча — компилируется только с явным армом `E_NOT_IMPLEMENTED` + Poisoned (генерализация
решения владельца по №465). Приёмкой сверху — карта «форма грамматики × фикстуры», где
фикстура обязана НАБЛЮДАТЬ обязательство (positive — эффект виден, negative — отказ
виден; №465 — измеренный контрпример слабой формулировки: A8.25–A8.28 были зелёными при
невставленном вызове хелпера).
**Верность:** зазор «принято парсером — не доведено чекером» невыразим: новый вид узла
без арма — ошибка КОМПИЛЯЦИИ компилятора (exhaustive match), арм-заглушка честно
диагностирует и травит. Уточнение второй волны: семью №652 exhaustive-диспетч НЕ
закрывает — её механизм живёт ВНУТРИ написанных армов (skip-on-unknown); её держит
дисциплина §7 как третий элемент: в `check` нет пермиссивного unknown — тип либо
известен, либо Poisoned с уже репортнутой первопричиной. №465 умер ниже чекера (вызов
хелпера не вставлен в кодоген) — этот ярус наблюдает только фикстура (б).
**Место:** `check` (exhaustive-диспетч) + `diag` (Poisoned §7) + приёмка (карта
форм × фикстур, свой страж `check-novac-grammar-fixture-coverage.sh`, Э1 — дифф-базный
`check-test-fixture-coverage.sh` этому классу не судья).
**Минимальность:** пересчитана второй волной — несущих инварианта ДВА — (б) карта
форм × наблюдающих фикстур и (в) запрет пермиссивного unknown (§7: «ошибка уже
репортнута» — единственная законная форма незнания это Poisoned). (а) исчерпывающий
диспетч — конструктивная механика РАННОСТИ, не несущий инвариант: при живом (б)
пропущенный арм ловится гейтом, (а) ловит его раньше — на компиляции компилятора.
Снятие (в) — семья №652 возвращается при зелёных (а) и (б); снятие (б) — №465/№616
живут до первого пользователя; снятие (а) класс не возвращает, но переносит отказ с
компиляции на гейт.
