**Свойство клетки, как я его назвал перед охотой:** имя разрешается голой строкой в одной плоской таблице `sem.DefTable` (пространство `NsDefs`), где последняя запись побеждает, — и потому ответ на вопрос «есть ли тип с таким именем» зависит от того, что ЕЩЁ носит это имя в том же CU. **Синтаксисы, в которых свойство встретилось** (вторую форму искал намеренно): (1) свободная `fn` того же имени; (2) `fn` с именем СИДИРОВАННОГО примитива; (3) `fn` с именем ПОДАННОЙ декларации std; (4) модульная `const` с именем поданной декларации std; (5) `type X alias Y` — имя не попадает в таблицу вовсе, и регистрация алиаса включается только когда имя уже кем-то занято. Пятая форма грепом по `defs.add(` не находится: она про ОТСУТСТВИЕ записи в той же таблице.

## 2. Что обошёл и почему

- **Гипотеза 5 (перегрузка, метод против свободной fn).** p07 (`fn pick(x int)` + `fn pick(x str)`) — оба зелёные, смоук байт-в-байт идентичен; p22 (две `fn pick(x int)` с той же сигнатурой) — оба отвергают (novac: «this call fits more than one function and none is more specific … (D84)», оракул: «duplicate definition `pick` with same signature»). Цепочка одноимённых вызываемых в `resolve` работает; носителя не нашёл.
- **Гипотеза 3 (параметр типа с именем объявленного типа).** p04 и p06 (`fn unwrap[Box](b Box)` при `type Box { v int }`) — оба принимают, смоук p06 идентичен. Зазор назван (`tparam_slot` спрашивается ПЕРЕД реестром, typeref_rules.nv:74-75), носителя не нашёл.
- **Гипотеза 7 (имя типа std без импорта).** p10 (`fn code(e Utf8Error) -> int`) — принимают ОБА; оракул тоже не гейтит видимость на этом входе. Не находка.
- **Гипотеза 9 (тень локалом имени fn; параметр с именем варианта).** p08 и p17 — оба принимают, смоук p08 идентичен.
- **Гипотеза 2 в форме `fn twice(int int)`** (p09): расхождение есть (novac эмитит `nova_int int`, clang падает), но класс НЕ мой и уже найден — это в точности проба `p16-c-keyword-param` принятого отчёта охоты emitc-К3 от 2026-09-05. Переоткрывать не стал.
- **`const` против типа ФАЙЛА** (p02, p03): novac отвергает «undeclared type name `Cel`», оракул отвергает «duplicate top-level name `Cel`». Оба отвергают — по правилу брифа не находка. Остаётся только качество текста: novac называет «необъявленным» тип, написанный двумя строками выше, и посылает читателя искать опечатку.
- **Границы подмножества, из-за которых пробы пришлось переписывать (3, это ширина, не находки):** `fn main() Io -> ()` → «syntax error: this is not a form of the language» (принимается только `fn main()`); `[]int.new()` → «outside the subset: a typed array literal is written `[]T.of(...)` -- this constructor is not the literal form»; `type Vec alias int` → «outside the subset: the interop shell already declares a struct under this name's C spelling».
- **Два входа, где отказал ОРАКУЛ, а не novac** (p05: `type Color enum Red | Green` + `fn Red()`; p19: тот же sum + `const Red = 5`): `check` зелёный у обоих компиляторов, но `nova build` оракула падает на C — `nova_print_int(nova_make_Color_Red())`, то есть оракул типизировал имя как int, а сэмитил конструктор варианта. novac на p05 зовёт `fn Red` и печатает 42. Это дефект оракула; в клетку check×К2 он не входит, но окну полезен как след того же класса у неподвижной точки.
- **`type f64 alias int`** (контроль `_t18b`): novac отвергает «a primitive is a closed type (D35)», ОРАКУЛ ПРИНИМАЕТ. Расхождение есть, но здесь novac строже и, похоже, прав по D35 — вердикт по спеке не мой, в находки не веду.
- **Куда не дошёл вовсе:** гипотеза 6 (`Self`/`@` вне метода), newtype с именем своего представления, алиас на алиас (первое звено и так не регистрируется — находка 6), импорт-формы (в подмножестве их нет) и вторая форма находки 5 — литерал записи через спред `{ ...src }` (ветка type_of.nv:344-349) осталась непромеренной.

## 3. Противоречия

**(1) Что делает реестр при повторе имени — «первый удерживает» или «последний побеждает».**

- `novac/src/check/literal_rules.nv:248-251`: «/// A top-level name declared twice in one file (#811). The name leaf is the /// first identifier of the declaration; the table answers "seen already", and /// the second declaration is the one refused -- **the first keeps the name, as** /// **sem's registry does**.»
- `novac/src/sem/defs.nv:95` и `:100`: «/// Register one name. **LAST PUT WINS**, and that is the rule rather than a /// shortcut» … «/// **LAST PUT WINS, AND SINCE 2026-08-23 THAT IS THE SHADOWING RULE ITSELF**.»

Оба верны для своей половины (тип-против-типа коллектор пропускает — «первый удерживает»; `fn` и `const` кладутся безусловно — «последний побеждает»), и именно на стыке живут находки 1–4. Выбирать между формулировками не мне.

**(2) «Разные сорта не могут делить NsDefs» — против того, что три сорта его делят.**

- `novac/src/names/names.nv:71-72`: «NsProtocols /// protocol names: **a CONTRACT is not a type, so it cannot share NsDefs**», «NsVariants /// bare variant names -> the head of a same-name chain in `variant_rows` (274.7 B6, #964): **a variant is a row of its sum, not a top-level name, so it cannot share NsDefs**».
- `novac/src/sem/defs.nv:42-45` и `:115-118`: «export type DefTarget enum | DefType(DeclId) | DefFn(FnRow) | DefConst(ConstRow)» — и все три регистрируются одной дверью «export fn DefTable mut @add(name str, target DefTarget) -> () { @names.put(name, @rows.len()) … }» в один `NsDefs`.

Принцип, которым обоснованы `NsProtocols` и `NsVariants`, к парам «тип против callable» и «тип против константы» не применён; §К2 архитектуры («резолв ключуется парой (`NamespaceId`, имя)») читается и как «одна пара на таблицу», и как «одна пара на СОРТ имени». Разрешение этого — не моя развилка.
