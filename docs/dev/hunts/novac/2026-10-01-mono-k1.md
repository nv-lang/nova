# Охота: подсистема `mono` × К1 (трек novac, 2026-10-01)

КЛЕТКА | mono | К1

**Клетка назначена интегратором** (2026-10-01, ~11:45): долг охоты трека novac на `main`
`e448f0193` — 1774 строки поверхности при бюджете 1500 (`check-hunter-debt`), `gate.sh` в CI
красный. Поверхность — волна Э.10 шаг 4c-1 Карины (`f9889ae54`): обобщённый метод std (или
модуля программы), экземпляра которого нет в шелле, Карина инстанцирует сама из переданного
тела — `Ctx @instantiates` (`sem/handed_bodies.nv:68`), рост множества в `mono`
(`mono/mono.nv:283`, `Reach @grow`), типизация тела в `instances_of` (`pipeline/pipeline.nv:591`,
ветка переданного тела `:620-647`), `subst_type`. Класс К1 — молча неверный результат: Карина
принимает программу и печатает не то, что оракул. Охотник — фоновый агент интегратора по
правилам `defect-hunter` (opus), 28 проб. Субъект — novac, собранный оракулом в worktree
`nova-hunt-mono` с `e448f0193`; оракул — `nova.exe`, собранный в том же дереве.

**Как выражена клетка.** Экземпляр над типом программы (`Vec[Pt]`) в исполняемой программе не
строится: литерал `[Pt {..}]`, `[]Pt.new()` и `Vec[Pt].of` отвергаются по имени (шаг 4c-2 ещё
не сделан). Но та же дверь работает над типами std, которых шелл не несёт: шелл собран из пробы
и несёт для `Vec[int]` только `cap`, `display`, `get`, `index`, `len`, `push`, `reserve`, —
значит `v.is_empty()`, `v.clear()`, `v.first()`, `v.slice()` над `Vec[int]`, `Vec[f64]`,
`Vec[str]` и над `Vec[Id]` (newtype программы) — экземпляры Карины из тела std. Вторая форма —
расширяющий метод `fn Vec[T] @m()` модуля программы, поданного через `NOVAC_SELF_PATH`: его тоже
инстанцирует единица вызывающего. Пробы — пакеты, однофайловые (`NOSELF=1`, как дымовой
`novac-e1-smoke.sh`) и многомодульные (как самосборка Э.10).

**Ответ.** Подозрение подтвердилось двумя механизмами К1.

1. **Переданное тело с возвратом `-> @` эмитится без `return`.** D409 (`spec/decisions/03-syntax.md:9147`)
   делает возврат приёмника автоматическим: тело без хвостового выражения — неявный
   `return @`. Тело std `Vec[T] mut @clear() -> @ { @len = 0 }` (`std/src/collections/vec/mutate.nv:300`)
   Карина эмитит как `static Nova_Vec____nova_int* novac_fn_clear__...(...) { (_novac_self->len) = 0; }` —
   C-функция «падает с конца», результат — мусор. `ro w = v.clear()` и `v.clear().is_empty()`:
   оракул `0 0` / `true`, Карина — segfault (rc 139). То же для `-> @`-метода модуля программы.
   Своё тело той же формы в компилируемом файле Карина ОТВЕРГАЕТ («fn declares a return type but
   its body ends without a value», `check/tail_rules.nv:306`) — суждение о хвосте есть у файла и
   нет у экземпляра; и сам отказ ложный по D409.
2. **Переданное тело типизируется в контексте ВЫЗЫВАЮЩЕГО файла.** `check_instance`
   (`check/run.nv:141`) получает текст тела, но `Ctx` компилируемого файла
   (`pipeline/pipeline.nv:634`), и имена тела решаются в его области: `helper()` в теле метода
   `hp.geo` зовёт `helper` модуля `hp` (оракул 2, Карина 1), `weight(@len())` — `weight` модуля
   `hp` (оракул 6, Карина 3000). Той же дверью: приватное поле std (`@len`) в теле экземпляра
   отвергается «unknown field», как только у файла есть строка `module` (без неё — проходит);
   диагностика тела экземпляра называет файл ПРОГРАММЫ со смещением в файле std/модуля; C-имя
   экземпляра std берёт префикс модуля файла (`novac_fn_hp_first__...`,
   `sem/mangle.nv:221-222`: у строки std `handed_from` пуст, и берётся `module_prefix(ctx)`).

Вне К1, тем же заходом: (3) вызов переданного обобщённого метода из СВОЕГО обобщённого тела не
инстанцируется — `mono` обходит тело своего обобщения один раз в канале файла (под абстрактным
`T`, `mono/mono.nv:190`), а эмиттер называет конкретный экземпляр, которого нет: check/emit
rc=0, отказывает линковщик; (4) C-имя экземпляра std совпадает с C-именем своего обобщения
той же формы — clang «redefinition»; (5) «несёт ли шелл экземпляр» спрашивается по ИМЕНИ
метода, а не по перегрузке (`sem/handed_bodies.nv:74`, `sem/mangle_instance.nv:70`) —
`v.cap(100)` и `v.index(1, 9)` над `Vec[int]` уходят в шелловые `cap()` и `index(i)`, clang
«too many arguments»; (6) под `??` экземпляр не доходит до проверки: `d.first() ?? 0.0` над
`Vec[f64]` — check rc=0, emit ICE, а `ro f = d.first()` честно отвергается.

Не подтвердилось (совпало с оракулом): один переданный `index` над `f64` и `str` в одной
программе (`ctl-multi-instance`), `requires` переданного тела срабатывает как у оракула
(`ctl-index-contract`, exit 101), экземпляры над `Vec[Id]` (newtype) — `is_empty`, `end_index`,
`slice` (проверено при охоте, проба не сохранена).

## Что обошёл и почему

- **Экземпляр над типом программы в исполняемой программе** (`Vec[Pt] @len` — прямой предмет
  4c-1): `[Pt {..}]` — «the shell carries no `Vec` instance for Pt», `Vec[Pt].of` — «a type
  applied to arguments», `[]Pt.new()` — шаг 4c-2; через обобщение `fn one[T](x T) -> []T => [x]`
  — ICE `mangle: a substituted type the checker never interned`. К1 на этой форме выразим только
  в мере 0.2 (check), где поведения нет. Проверены лишь newtype программы (`Vec[Id]`) — совпало.
- **Хвост `if` и голый `return` в переданных телах** (`truncate`, `append_zero`, `dedup`,
  `rotate_left`, `copy_within`): отказы «a tail `if` needs an `else`» / «`return` must carry a
  value» — следствие того же D409 (находка 1), отдельными находками не заведены.
- **Пара `[T]` / `[T consume]`** (`contains`, `index_of`, `is_sorted`, `binary_search`, `sort`):
  отказ «fits more than one method … (D84)», хотя амендмент D464 2026-09-25 п.1 берёт `[T]`
  (проба `ambiguity-linearity`, оракул `true`/`false`). Линейности в Карине нет целиком (№1099) —
  не новая находка; ложен только текст отказа.
- **ICE на переданных телах** — честная остановка, не К1: `v.split_at(1)` — `sem: a name in TYPE
  position that the registry does not hold (#652 class)` (`ice-split-at`); `d.cap(50)` над
  `Vec[f64]` — `check: a cast whose target type the registry does not…` (`ice-cap-n-f64`);
  `(v.first() ?? Id(0)) == Id(10)` над `Vec[Id]` — `lower: a block sealed twice` (родня №1130).
- **`[1, 2, 3].cap()`**: оракул `8`, Карина `3` — №783 (вместимость литерала оракула), не 4c-1.
- **Наблюдения об ОРАКУЛЕ (трек закрыт, не находки):** константа модуля в теле расширяющего
  метода — оракул не собирает (`use of undeclared identifier 'Nova_const_hp_geo_SCALE'`), Карина
  читает константу ВЫЗЫВАЮЩЕГО (`300` при ожидаемом `30`; проба `hygiene-const-oracle-fails` —
  третья форма находки 2 без неподвижной точки); приватный тип `Cell` с методом `@total` в двух
  модулях — оракул «undefined symbol: Nova_Cell_method_total», Карина `300` при ожидаемом `4`;
  `b.unwrap_or(9)` на `None` — C оракула не компилируется; `[M(1.5)]` над newtype `f64` — оракул
  не собирает; newtype со своим `@display` в слоте — оракул печатает представление (`10`), Карина
  `#` (не 4c-1, пробы не сохранены).

   „тело обязано завершаться `@`“)», «отсутствие хвостового выражения в теле → неявный `return @`»,

   D132 при этом не помечен как отменённый; находка 1 судит по D409 (оракул ведёт себя по нему).
