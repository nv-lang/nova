## Чем мерилось

Признак К1 — **оба компилятора приняли, а напечатанный ответ разный**. Мерил
готовый инструмент, который ровно это и делает (собирает оракулом, эмитит novac,
линкует его C аргументами оракула, гоняет оба и сравнивает stdout байт-в-байт):

```sh
sh scripts/tools/novac-e1-smoke.sh target/hunt-emitk1/<проба>/p.nv
```

Отдельно, когда нужен именно вывод каждой стороны:

```sh
./nova-cli/target/release/nova.exe build target/hunt-emitk1/<проба>/p.nv -o /tmp/o.exe && /tmp/o.exe ; echo "(exit $?)"
./novac/target/novac.exe        check target/hunt-emitk1/<проба>/p.nv ; echo "rc=$?"
./novac/target/novac.exe        emit  target/hunt-emitk1/<проба>/p.nv | grep -n -A 12 'nova_fn_main_impl'
```

Сырые результаты всех прогонов — `target/hunt-emitk1/results.txt` (чекпоинт писался
после каждой пробы).

## Пять классов расхождения ОТВЕТА

Каждый класс назван СВОЙСТВОМ, и под ним перечислены синтаксисы, в которых это
свойство встречается, — по правилу «клетка формулируется по свойству, а не по
конструкции».

### Н1. Хойст переносит эффекты аргумента ВПЕРЁД, через эффекты того же оператора

**Свойство:** многооператорная конструкция, стоящая в аргументе, строится ДО
строки-оператора, поэтому её эффекты обгоняют эффекты, которые оператор совершает
раньше по тексту.

| проба | оракул | novac |
|---|---|---|
| `hoist_ctor_before_print` | `headtick` / `1` | `tick` / `head1` |
| `hoist_arraylit_before_print` | `headtick` / `1` | `tick` / `head1` |

Источник — `println("head", grab(Pt { n: tick(1) }))`. Эмиссия (проба 1):

```c
static nova_unit nova_fn_main_impl(void) {
    Nova_Pt* _novac_tmp_t1 = (Nova_Pt*)nova_alloc(sizeof(Nova_Pt));
    _novac_tmp_t1->n = novac_fn_p_tick__nova_int__to_nova_int(((nova_int)1LL));
    nova_print_str(_novac_strlit_1);
    nova_print_int(novac_fn_p_grab__Pt__to_nova_int(_novac_tmp_t1));
```

Адреса: `novac/src/emit_c/emit_expr.nv:510` — `@hoist_array_lits(call)` стоит ПЕРЕД
циклом печатников, а печатник аргумента — `emit_expr.nv:513-544`. Оракул печатает
`head` до вызова `tick`, novac — после.

Второй синтаксис найден и подтверждён (литерал массива, `emit_c.nv:817`), то есть
свойство живёт минимум в двух формах; греп по `RecordCtor` его границу не задаёт.

### Н2. Конструкция, вложенная в ПОЛЕ конструктора, строится ДВАЖДЫ

**Свойство:** две двери хойста обходят одно и то же поддерево — рекурсивный спуск
`@hoist_array_lits` и повторный вызов того же хойста внутри `@emit_record_ctor`.
Вторая перезаписывает `@lit_tmp`, первая остаётся в C мёртвой переменной — но её
побочный эффект выполняется.

| проба | оракул | novac |
|---|---|---|
| `double_eval_nested_ctor` | `t2` / `3` | `t2` / **`t2`** / `3` |
| `double_eval_arraylit_in_ctor` | `t2` / `2` | `t2` / **`t2`** / `2` |
| `double_eval_stmt_call` | `t2` / `end` | `t2` / **`t2`** / `end` |

Эмиссия `double_eval_nested_ctor` — `tick(2)` вызван два раза, первый результат
выброшен:

```c
    Nova_Inner* _novac_tmp_t1 = (Nova_Inner*)nova_alloc(sizeof(Nova_Inner));
    _novac_tmp_t1->m = novac_fn_p_tick__nova_int__to_nova_int(((nova_int)2LL));   /* мёртвый */
    Nova_Pt* _novac_tmp_t2 = (Nova_Pt*)nova_alloc(sizeof(Nova_Pt));
    _novac_tmp_t2->a = ((nova_int)1LL);
    Nova_Inner* _novac_tmp_t3 = (Nova_Inner*)nova_alloc(sizeof(Nova_Inner));
    _novac_tmp_t3->m = novac_fn_p_tick__nova_int__to_nova_int(((nova_int)2LL));   /* тот же вызов второй раз */
    _novac_tmp_t2->b = novac_fn_p_take__Inner__to_nova_int(_novac_tmp_t3);
```

Два адреса, отвечающие на один вопрос «кто хойстит детей конструктора»:

* `novac/src/emit_c/emit_c.nv:803-805` — `for c in children { @hoist_array_lits(c) }`
  (спуск обходит ВСЁ поддерево оператора, включая поля конструктора);
* `novac/src/emit_c/emit_c.nv:862` — `@hoist_array_lits(fk[2])` внутри
  `@emit_record_ctor`, обходящий то же поле ещё раз.

Асимметрия названа замером: `@emit_array_lit` (`emit_c.nv:775`) своих детей НЕ
перехойстивает — поэтому внешний литерал массива не удваивает (контроль
`ctl_arraylit_no_double`), а внешний конструктор удваивает.

### Н3. Унарное отрицание эмитится сырым C — ловушка переполнения оракула теряется

**Свойство:** целочисленная арифметика идёт через `nova_int_checked_*`, а унарный
минус — нет.

| проба | оракул | novac |
|---|---|---|
| `neg_overflow` | `panic: negation overflow`, exit 101 | `-9223372036854775808`, exit 0 |
| `neg_via_param` | `panic: negation overflow`, exit 101 | `-9223372036854775808`, exit 0 |

Обе стороны видны в ОДНОЙ эмитированной функции — вычитание проверяется, отрицание
нет:

```c
    nova_int x = ((nova_int)-9223372036854775807LL);
    x = nova_int_checked_sub(x, ((nova_int)1LL));
    nova_print_int((-(x)));
```

Адреса: `novac/src/emit_c/emit_expr.nv:146` (`Negate => "-"` в `c_unary_form`)
против `novac/src/emit_c/emit_expr.nv:48-73` (`c_binary_form`, где Add/Sub/Mul/Div/
Modulo на int идут в `nova_int_checked_*`).

**Вторую форму искал и не нашёл:** в `c_unary_form` три оператора, переполниться
может только `Negate`; счётчик цикла `for` (`i++` сырым C, `emit_c.nv:742-751`)
проверен пробой `for_counter_overflow` — расхождения нет.

### Н4. `value`-запись передаётся ПО ЗНАЧЕНИЮ, и запись через `mut`-параметр пропадает

**Свойство:** novac представляет `type X value` как C-структуру по значению, оракул —
как `NovaValue_X*`; всякая мутация через `mut`-привязку такой записи в novac теряется.

| проба | оракул | novac |
|---|---|---|
| `valrec_mut_param` | `2` / `2` | `2` / **`1`** |
| `valrec_stmt_call_mut` | `2` | **`1`** |

Это в точности та причина, ради которой существует ИМЕНОВАННЫЙ отказ — но отказ
задаёт вопрос только про ПОЛУЧАТЕЛЯ метода:

* `novac/src/check/check.nv:326` — `if is_value_record(@ctx, @ctx.ty_of_name(recv_type_name(children) ?? "") ?? no_ty())`,
  с комментарием на 316-325: «novac passes a value receiver by VALUE ... so a `mut`
  method would write to a copy»;
* `novac/src/emit_c/emit_c.nv:425` — `@body.append(c_type(@ctx, ptype))`: ПАРАМЕТР
  value-записи печатается по значению, и ни одна проверка этот путь не спрашивает.

Оба места отвечают на один вопрос «может ли `mut` по value-записи дописать в чужую
запись» — первое отвечает «нет, отказываем», второе молча компилирует.

### Н5. Составное присваивание выбирает форму по таблице int/f64, не спросив ни диспетчер, ни носитель

**Свойство:** `a op= b` берёт C-форму из той же таблицы, что и `a op b`, но БЕЗ
правила «этот оператор на этих операндах диспетчеризуется» и БЕЗ `carrier_of`.
Объявленный тип newtype над `f64` не равен `f64_id`, поэтому выбирается целочисленный
хелпер, а печатник (он-то спрашивает носитель) печатает результат как f64.

| проба | оракул | novac |
|---|---|---|
| `newtype_f64_compound` (`a += Meters(2.25)`) | `3.75` | **`3`** |
| `newtype_f64_mul_compound` (`a *= Meters(3.0)`) | `4.5` | **`3`** |

```c
    nova_f64 a = ((nova_f64)1.5);
    a = nova_int_checked_add(a, ((nova_f64)2.25));
    nova_print_f64(a);
```

Адреса — три, и они складываются в один зазор:

* `novac/src/check/exprs.nv:342` — `if @report_if_operator_needs_protocol(kids) { return }`,
  ЕДИНСТВЕННЫЙ вызов правила, и он в ветке `Bin`;
* `novac/src/check/typing.nv:546-570` — ветка `AssignStmt`: типизирует обе стороны,
  записывает тип «чтобы эмиттер выбрал форму составного присваивания», и правило
  выше не зовёт ни разу;
* `novac/src/emit_c/emit_c.nv:717` — `ro is_float = @out.type_of(kids[2].id_of()) == @ctx.prims.f64_id`
  — ОБЪЯВЛЕННЫЙ тип, тогда как соседний печатник в `emit_expr.nv:524` спрашивает
  `carrier_of(@ctx, @out.type_of(c.id_of()))`.

**Вторая форма того же свойства найдена и подтверждена отдельно:** тот же путь на
`str` (`str_plus_assign`) даёт `nova_int_checked_add(a, _novac_strlit_1)` на
`nova_str` — оба компилятора приняли, clang эмиссию отверг. Это не К1 (не разный
ответ, а несобираемый C), см. раздел «Вне клетки».

Контраст, который делает класс классом: БИНАРНАЯ форма того же оператора на том же
newtype (`newtype_f64_add`) отвергается novac по имени —
«outside the subset: this operator on these operands dispatches through a protocol».
То есть правило есть, а форма `op=` проходит мимо него.

## Что обошёл и почему

* **Формы `match` как контраст** брались только контролями (`x_*`); отдельной
  охоты на `@emit_match`/`@emit_match_stmt` (`novac/src/emit_c/emit_match.nv`, 213
  строк) я не вёл — цель названа как эмиттер свежих форм, а бюджет ушёл на пять
  классов выше. Хвостовой `match` в паре с новым `if`-значением не скрещён.
* **`CtorSpread`** (`emit_c.nv:852-856`) прочитан, но не отстрелян: `@emit_expr`
  там зовётся БЕЗ хойста, то есть спред с вложенной конструкцией должен дать ICE
  той же породы, что `bind_ctor_arg`. Гипотеза, пробы нет.
* **Двойной хойст на глубине 2** (конструктор в поле конструктора в поле
  конструктора) не мерился: удвоится ли он в четыре раза — неизвестно.
* **Порядок аргументов при `NamedArg`** (F65-зазор) назван и подтверждён тем, что
  check пропускает, но РАЗНОГО ОТВЕТА показать не удалось: эмиссия падает ICE
  раньше, чем можно измерить порядок. Носитель зазора есть, наблюдаемого К1 нет.
* **Второй формы Н3 искал по образцу** «операция, которую оракул ловит, а novac
  печатает сырым C»: прошёл `c_unary_form` целиком (три оператора), счётчик `for`
  (`i++`), сдвиги, деление и остаток на INT_MIN/-1 и на ноль. Кроме `Negate` не
  нашёл ничего — так и записываю.
* **`std`, мега-CU и полный `nova test`** не гонял ни разу: только 56 своих проб и
  смоук по каждой.
