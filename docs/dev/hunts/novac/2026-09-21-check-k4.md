# Охота: подсистема `check` × К4 (трек novac, 2026-09-21)

КЛЕТКА | check | К4

**Клетка назначена окном.** Подсистема — `novac/src/check/**` (25 файлов, 9802
строки после разрезов 2026-09-20/21). Класс — К4: **второе вычисление уже
решённого суждения** — две функции с разными именами отвечают на ОДИН вопрос и
расходятся; в терминах приёмки проекта это отказы, которые не роняют тег, но
искажают диагностику или вердикт на ЗАКОННОМ коде.

**Почему эта клетка сейчас.** За сутки поверхность `novac/src` выросла на 1520
строк, и почти весь прирост — разрезы `check` на со-равные файлы. Разрез по
смыслу переносит функции, но НЕ склеивает суждения: после него один вопрос
легко оказывается у двух дверей в разных файлах, и это ровно К4.

**Метод.** Дифференциал против оракула на входах ВНЕ корпуса (корпус и фикстуры
зелены по построению — их судит `check-novac-differential.sh`), плюс чтение пар
«дверь ↔ дверь» с последующей пробой. Для каждого класса искалась ВТОРАЯ ФОРМА
свойства, а не второй носитель конструкции.

**Чем меряно.** `novac/target/novac.exe` сборки 2026-09-21 07:06 и
`nova-cli/target/release/nova.exe` — оба из ОСНОВНОЙ рабочей копии; адреса
`файл:строка` тоже из неё (моё дерево охоты стоит на более раннем коммите, и
номера строк в нём другие — сверять по основному дереву). Проб 18, каждая своим
каталогом с `cmd.sh` и записанным `run.out`; перепрогон всех разом —
`probes/2026-09-21-check-k4/rerun.sh`.

### Н1 — величина литерала считается ДВАЖДЫ, и первая дверь бьёт вторую

**Два адреса, отвечающие на один вопрос «влезает ли этот литерал».**

* `novac/src/check/literal_rules.nv:62` — `int_text_fits(t str)`: граница —
  «`int`'s own», 9223372036854775807, знак не участвует вовсе. Зовётся из
  `@report_if_int_too_large` (`literal_rules.nv:42`), а тот — из обхода на узле
  `Lit` (`check.nv:810`), то есть ДЛЯ ЛЮБОГО литерала в любой позиции, до того
  как что-либо известно о типе.
* `novac/src/check/literal_rules.nv:120` — `int_text_fits_row(t, r, neg)`:
  граница берётся у РЯДА (`int_max_text`), отрицательная сторона считается
  отдельно. Зовётся из `@lit_fits_or_refuse` (`:160`) — двери, которая по
  шапке и есть судья D227 п.3.

Вторая дверь отвечает ВЕРНО (контроль `p5-u8-300-control`: `u8 = 300` отвергнут
теми же словами, что у оракула), но до неё дело не доходит: обход на `Lit`
стоит раньше и уже отказал.

**Четыре формы одного свойства** (свойство — «величина судится без ряда», не
конструкция):

| проба | вход | novac | оракул |
|---|---|---|---|
| `p1-u64-max-arg` | `take(18446744073709551615)`, параметр `u64` | отказ | ok |
| `p2-int-min-arg` | `take(-9223372036854775808)`, параметр `int` | отказ | ok |
| `p3-hex-u64-max-arg` | `take(0xFFFFFFFFFFFFFFFF)`, параметр `u64` | отказ | ok |
| `p4-u64-return` | `fn big() -> u64 => 18446744073709551615` | отказ | ok |

Контроль `p17-u64-small-control` (`take(7)` при параметре `u64`) чист у обоих —
значит отказ про ВЕЛИЧИНУ, а не про тип вне подмножества. Ещё две формы того же
свойства замерены и не вынесены отдельными строками, потому что корень тот же:
значение по умолчанию (`fn take(x u64 = 18446744073709551615)`) и правая часть
равенства (`x == 18446744073709551615` при `x u64`) — обе отвергаются той же
фразой.

**Отдельно про коды.** Магнитудная дверь отвечает `E_NOVAC_SUBSET` («novac пока
не компилирует»), рядная — `E_NOVAC_LANG` («язык запрещает»). Один вопрос, два
КЛАССА ответа: читатель первой формы пойдёт ждать роста подмножества, хотя ждать
нечего.

**Это НЕ №878, и различие несущее.** №878 — про литерал, которому НЕ НАЗНАЧЕН
никакой ряд (`println(9223372036854775808)`): там novac строже оракула и ждёт
слова владельца. Здесь литерал ряд ВЗЯЛ, ряд его вмещает, и вторая дверь novac
это уже знает.

### Н2 — в образце `match` литерал не судит НИКТО, и C получается невалидный

`p6-match-literal-unjudged`: 23 десятичные цифры в образце. `novac check` —
чисто (rc=0); оракул отвергает файл. `novac emit` пишет

```
5856:    if (!_novac_matched_t0 && ((_novac_l1 == 99999999999999999999999LL))) {
```

а clang на эту строку отвечает «integer literal is too large to be represented
in any integer type» (шаг цикла в `cmd.sh`; вырезанная строка лежит рядом
самодостаточным `emitted_line.c`, чтобы вердикт не требовал сборки рантайма).

То есть обе двери Н1 сюда не дотягиваются, и получается ровно то, ради чего
магнитудная дверь заводилась (#810): «the emitter prints its text with an `LL`
suffix and C wraps it». Разница с 2026-08-30 только в том, что теперь падение
приходит не тихой порчей, а отказом СИШНОГО компилятора с координатой внутри
сгенерированного файла — чинить по ней автору Nova нечего.

Замерена и соседняя форма: `match x { 300 => … }` при `x u8` принимается обоими
компиляторами, и novac пишет `_novac_l1 == 300LL` при `uint8_t` слева —
сравнение, истинным не бывающее. Отдельной находкой не вынесена: здесь оракул
ведёт себя так же, а трек `oracle` закрыт.

### Н3 — «завершает ли хвостовой `if` функцию» считается дважды; мёртвая строка меняет вердикт

**Два адреса.**

* `novac/src/check/tail_rules.nv:33` — `stmt_terminates`: `if`, все ветви
  которого возвращают, ЗАВЕРШАЕТ функцию. Шапка (`:22-32`) написана про эту
  самую форму: правило чинили 2026-08-18, потому что отказ на
  `fn classify(n int) -> int { if .. { return 3 } else { return 1 } }` —
  «which the oracle accepts and which is the ordinary way to write such a
  function», и там же сказано, что отказ на верном коде есть дефект даже когда
  он в сторону строгости. Дверь `@report_if_tail_has_no_value`
  (`tail_rules.nv:102`) спрашивает это суждение и МОЛЧИТ.
* `novac/src/check/typing.nv:521` — `@type_branch_value`: тот же хвостовой `if`
  судится ВТОРОЙ РАЗ, теперь как значение, и ветвь, кончающаяся `return`,
  отвергается (`typing.nv:555`). Шапка признаёт выбор прямо: «A branch whose
  tail is not an expression -- a `return`, a binding -- is refused, and that is
  the boundary this wave DECLARED rather than discovered».

**Почему это дефект, а не объявленная граница подмножества.** Граница
объявлялась ДО того, как первая дверь научилась считать такой `if`
завершающим, — и теперь фикс первой двери невидим, потому что на тот же вопрос
отвечает вторая, по-старому. Замеры:

* `p7-tail-if-returns` — тело `if n > 0 { return 1 } else { return 2 }`: novac
  даёт ДВА отказа (по одному на ветвь), оракул — ok;
* `p8-dead-code-makes-it-legal` — **то же тело плюс `ro dead = 0` после него**:
  novac чист. Дописанная мёртвая строка — единственное различие;
* `p8` печатает и эмиссию: `if/else` с `return` в обеих ветвях эмитится
  правильно. Значит отказ Н3 — не ограничение эмиттера; форма ему по силам;
* `p9-binding-tail-alone` — та же привязка без `if`: отвергают оба. То есть в
  `p8` молчит именно `stmt_terminates`, а не «дверь спит».

Фикстура `novac/fixtures/control_flow/pos_1.nv` написана ВОКРУГ этого отказа
(её шапка называет его словами) — то есть корпус не может его увидеть по
построению, и дифференциал зелен.

### Н4 — терминатор перечислен формами, `while` в список не попал

`p10-while-true-return`: `while true { return n }` — «fn declares a return type
but its body ends without a value»; оракул принимает. Класс назван К6, а не К4,
честно: второй двери здесь нет, есть перечисление
(`tail_rules.nv:35-50` знает `RetStmt`, `IfLet`, `IfStmt`). Родня той же семьи,
что №1189 (там в списке не хватало `IfLet`), и потому стоит рядом: список,
пополняемый по одной форме, — это и есть носитель вместо класса.

### Н5 — режим привязки известен, записан и спрашивается ТОЛЬКО на вызове

**Два адреса.**

* `novac/src/check/scope.nv:131` — `Scope @mode_of_name`: режим (`ro`/`mut`/
  `consume`) хранится у каждой привязки; `type_of.nv:129` (`class_of_binding`)
  его читает и кладёт в ключ вызова.
* `novac/src/check/assign_rules.nv:67` — `@assigned_value_type`, «ТHE
  ASSIGNMENT DOOR»: судит ТИП значения и ни разу не спрашивает режим цели.

Следствие — молчаливое принятие того, что язык запрещает (D184/D246,
`E_LOCAL_NOT_MUT`), в ЧЕТЫРЁХ синтаксисах:

| проба | вход | novac | оракул |
|---|---|---|---|
| `p11-ro-assign-accepted` | `ro x = 1; x = 2` | rc=0 | `E_LOCAL_NOT_MUT` |
| `p12-ro-compound-assign` | `ro x = 1; x += 2` | rc=0 | `E_LOCAL_NOT_MUT` |
| `p13-param-assign` | `fn f(x int) { x = 5 … }` | rc=0 | `E_LOCAL_NOT_MUT` |
| `p18-ro-field-write` | `ro b = Pt { n: 1 }; b.n = 2` | rc=0 | `E_READONLY_FIELD` |

Четвёртая форма найдена ИМЕННО поиском второй формы свойства: греп по
присваиванию имени её не находит — цель там путь, а не имя. `p11` печатает и
эмиссию: `nova_int x = 1; x = 2;` — программа собирается и работает, то есть
это не «пока не проверяем», а тихо принятая программа вне языка.

Поиск по реестру (`E_LOCAL_NOT_MUT`, `NOT_MUT`) и по исходникам novac
(`E_LOCAL_NOT_MUT|not_mut|NOT_MUT`) даёт ноль вхождений: правила в novac нет
вовсе, и датированного долга подмножества на него я не нашёл (искал в
`docs/plans/274.7-subset-to-spec.md` и в реестре). Утверждать, что его нет
нигде, не могу — это названный предел моего поиска.

### Н6 — ключ без типов НЕСЁТ класс, а отказ читает его как аритет

**Два адреса, и они противоречат друг другу дословно.**

* `novac/src/check/typing.nv:589-594` (`unknown_args`): «The TYPE is what this
  key leaves unknown -- **the CLASS is not**».
* `novac/src/check/calls.nv:89-91` (`@refuse_free_call`): «The same question
  with the TYPES removed: **if nothing fits by arity alone, the arity is the
  cause** and the types never mattered» — и печатает «no function of this name
  takes this many arguments».

Замер: `p14-mut-param-arity-lie` — `fn bump(mut x int)`, вызов `bump(x)` при
`ro x`: один параметр, один аргумент, отказ про их ЧИСЛО. Контроль
`p15-mut-binding-control` — та же программа с `mut x = 1`: чисто. Значит
причина — класс привязки, и об этом в тексте нет ни слова. Оракул принимает обе
формы, а для настоящей несовместимости класса у него есть своё имя
(`E_MUT_ARG_NOT_MUTABLE` — замерено на `bump(1)`), то есть расходится и вердикт,
и формулировка.

### Н7 — отказ рассказывает про `println`, которого в этом месте нет

`p16-panic-tail-names-println`: хвостовой `panic("no")` (оракул принимает)
отвергается текстом `calls.nv:830`: «this name is not a callable novac knows in
an expression (println is a statement here, not a value)». Пример из истории
отказа (`println` попадал в позицию значения через висящий оператор) вшит в
сообщение как факт о текущем файле. Класс К2 — отказ верен по существу
(`panic` вне подмножества) и лжив по формулировке.

## Противоречия в дереве (выбор не охотника)

**П1.** `literal_rules.nv:29-41` (шапка магнитудной двери): «The bound is
`int`'s own… so the largest literal is 9223372036854775807». `literal_rules.nv:
113-119` (шапка рядной двери): «Does this integer literal's text fit the ROW it
was adapted to (D227 rule 3)?… A negative literal never fits an unsigned row».
Оба места про «влезает ли литерал», и на `u64`-максимум и на `int.MIN` отвечают
по-разному.

**П2.** `tail_rules.nv:22-32`: `if`, все ветви которого возвращают, завершает
функцию, и отказ на такой форме назван дефектом. `typing.nv:515-520`: ветвь
хвостового `if`, кончающаяся `return`, отвергается, и это названо объявленной
границей. Одна форма, два ответа.

**П3.** `typing.nv:589-594`: «the CLASS is not [оставлен неизвестным]».
`calls.nv:89-91`: «the same question with the TYPES removed… the arity is the
cause». Второе верно, только если класс из ключа УБРАН, а первое говорит, что
он там.

## Что обошёл и почему

* **`novac check` из каталога пробы** — печатает «cannot read declarations dir
  std/src» и судит файл БЕЗ объявлений std. Все пробы поэтому зовутся из корня
  (записано в `env.sh`); первые замеры я сделал иначе и выбросил;
* **вещественные литералы (D227 п.5, переполнение экспоненты)** — зазор назван,
  не проверялся: магнитудная дверь по построению смотрит только `IntLit`;
* **`as`-приведения и `#cfg`** — не трогал;
* **методы, обобщённые вызовы, протоколы** — вне прохода: К4-пары там есть
  (`method_call_key` / `method_arity_key` / `typed_call_key`), но одного
  прохода на них не хватило, и называть их ненайденными честнее, чем гадать;
* **вторая форма для Н3 и Н6** искалась и не нашлась: для Н3 — хвостовой
  `match`, все ветви которого `return` (принимается, расхождения нет), для Н6 —
  отказ по классу на МЕТОДЕ (форма вне подмножества, до двери не доходит);
* **оракульские странности, встреченные по дороге** — `match x { 300 => … }`
  при `x u8` оракул принимает; `bump(x)` при `ro x` и `mut`-параметре он тоже
  принимает. Трек `oracle` закрыт 2026-09-16, и находками я это не называю —
  записано, чтобы окно не приняло согласие novac с оракулом за доказательство
  правоты;
* **гейт, мега-CU, полный `nova test`, самопроверка novac** — не гонял (правило
  брифа); правок в дереве не делал ни одной, кроме файлов этой охоты;
* **собственный промах, названный:** первые прогоны проб дали rc=127 —
  `env.sh` выводил пути бинарей от корня МОЕГО worktree, где их нет вовсе.
  Молчаливое чтение этого как «расхождения нет» было в одном шаге; теперь
  `env.sh` краснеет явным сообщением, если бинаря нет.
