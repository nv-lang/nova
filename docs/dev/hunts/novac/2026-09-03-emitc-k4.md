## Класс А. «Это float-арифметика?» вычисляется дважды по двум разным правилам

* `emit_c/emit_expr.nv:557` — `@out.type_of(e.id_of()) == f64_id`: тип УЗЛА
  (результата), у `f + 2` он f64;
* `emit_c/emit_c.nv:649` — `carrier_of(@out.type_of(kids[2].id_of())) == f64`:
  тип ПРАВОГО ОПЕРАНДА, у `f += 2` он int.

Комментарий `emit_c.nv:640-648` утверждает «THE CARRIER OF THE TARGET… The
TARGET is a binding», а код строкой ниже читает `kids[2]` — правый операнд,
ровно тот источник, который тот же комментарий отвергает. Текст и код рядом
отвечают по-разному. Нарушено `emit_c.nv:13` («renders decisions already made,
decides nothing») и `emit_c.nv:120-122`.

## Класс Б. «Даёт ли хвост ЗНАЧЕНИЕ функции?» решается позицией, тип — в другом месте

* `emit_c.nv:325` — `@emit_block_stmts_fn(c, !@ctx.fns.is_entry_row(row))`:
  обязанность хвоста ПО ПОЗИЦИИ;
* `emit_c.nv:367` — `if !has_expr_body && ret == int_id`: то же суждение ПО ТИПУ,
  одной дверью ниже.

Следствия: `emit_c.nv:451` (`return <expr>;` в unit-функции), `emit_c.nv:432`
(хвостовой `if` уходит в `@emit_if_value`, спрашивающий тип, которого чекер для
оператора `if` не записывал).

**Обратная проба, ОДИН рычаг:** `p5_tail_call_not_last_control` — та же
unit-функция и тот же `println`, но после него присваивание, поэтому вызов
перестаёт быть последним ветвящимся ребёнком: смоук ok. Значит причина — правило
хвоста, а не вызов.

## Класс В. «Эту конструкцию строит хойст» решают две двери, печатающая не знает позиций строящей

* строит: `emit_c.nv:759` (`@hoist_array_lits`) — вызывается лишь из восьми
  позиций;
* печатает: `emit_expr.nv:347-352` (InterpStr) и `:353-360` (Coalesce) —
  «пусто ⇒ ice»;
* позиции БЕЗ обхода: `emit_c.nv:618-673` (AssignStmt), `:611-615` (RetStmt),
  `:571-575` (условие IfStmt), `emit_match.nv:64` (`@emit_arm_value`).

Граница класса задаётся не грепом по `InterpStr`: `??` несёт то же свойство
(p15), а `ArrayLit`/`RecordCtor`/`TupleExpr` в тех же позициях удерживаются
ИМЕННЫМИ отказами чекера. То есть класс закрыт не эмиттером, а списком позиций
в `check`, и каждая новая конструкция, которую `check` не ограничит позиционно,
попадает сюда автоматически.

## Подозрения без пробы

* `emit_expr.nv:405` — при пустом канале молча выбирается указательная форма;
  позиции, где канал молчит, не нашёл;
* `emit_expr.nv:419-427` — интероп-имя метода собирается заново из
  ДЕКЛАРИРОВАННОГО типа приёмника вместо строки, выбранной чекером;
* `emit_expr.nv:638` — «какой это вызов» решается по написанному тексту
  (`call_callee_text != PRINT_FN`);
* `emit_for.nv:41`, `emit_iflet.nv:35` — тип элемента и полезная нагрузка
  пересчитываются, хотя комментарий рядом говорит «this door only spells what
  was decided»;
* `emit_decls.nv:244-249` — недооценка, названная в самом коде (кортеж, чей
  компонент объявлен ниже); носителя нет, `check` отказывает раньше.
