## 2. Что обошёл и почему

* **`..=` вне for (B3).** Обошёл полностью: дверь `report_if_range_outside_for`
  признаёт оба оператора (rules.nv:468-474); открытые формы `..b`, `..=b`, голый
  `..` доходят до той же Bin-формы через error-node приём (expr.nv:240-262) и
  отвергаются; в index-позиции `slice_shape_of` (sem/slice.nv:38) знает только
  DotDot, но `..=` там всё равно падает в SLICE_MSG через ту же дверь — отказ
  есть в обеих позициях. Носителя обхода не нашёл; текст SLICE_MSG называет
  только `x[lo..hi]` — косметика, находкой не записываю.
* **`defer` (D90).** Форма читается целиком и отвергается по имени в одном плече
  (check.nv DeferStmt), typing глотает узел молча-OK своим финальным else
  (typing.nv:850-853) — согласовано с отказом. `defer` без блока — Err по
  ungrammar:251-252; `defer` в выражении и на верхнем уровне падает в recovery —
  отказано, не молча. Второй формы у свойства не нашёл (искал по позициям:
  value-position, match-arm, top-level).
* **Лексер `..=`.** Прочитал dot-run (lex.nv:873-885): longest match,
  `..=`/`...`/`..`/`.` разведены верно; граница с IntLit названа комментарием
  (`0..3` стабильно). Второго пути (`0..=3`, `..==`) не нашёл.
* **Маркеры типа (A1) внутри читателя.** Повтор маркера и инверсия
  (`type T value consume …`) отвергаются падением в хвост — отказ есть, хоть и
  не E_MODIFIER_ORDER; это известная ширина подмножества, не молчаливый обход.
  Записывать не стал.
* **fn-тип с рядом эффектов (`fn(T) E -> R`).** Проверил спеку: форма fn-типа
  в решениях фигурирует без ряда эффектов (02-types.md:683-684, :1156,
  03-syntax.md:118) — основания для находки нет; если форма с эффектами
  существует, дверь typeref молча прочитала бы результат как unit — гипотеза
  без носителя в норме, не записываю.
* **Позиция результата fn-типа ДО мисмача:** `-> fn(...)` бьётся
  TYPE_FORM_MSG ещё в walk (находка 1), поэтому отдельного пути «результат до
  ice» не требуется — он закрыт первой находкой.
* **Re-consume `consume X { body }` и multi-var (D188, Plan 201/174):** в
  комментарии двери честно названы непрочитанными; падают в путь связывания и
  получают Err по `=` — отказано, не молча. Не находка.
* **Перенос строки перед `{` в `consume x = e { body }`:** по D49 перенос
  завершает инструкцию; связка «consume-связывание + голый блок на следующей
  строке» — законная композиция двух форм, семантика соответствует написанному.
  Обхода нет; проверено и снято.
* **Вторая форма для К6-перечислений искалась вторым грепом** (правило «клетка
  по свойству»): для `KwFn` — грепом по всем вхождениям в check/ (нашёл
  четвёртое место static_call.nv:330 — это про `unsafe fn`, не про тип; не
  носитель); для ctor-двери — по читателю записей конструктора и ungrammar
  (нашлись `@x` и `...`, находка 3).
* **Замечание про цитату, не находка:** сообщение коммита 5aabbb4b4 ссылается
  на «ungrammar 362-363: five Range forms» — в nova.ungrammar правила Range нет
  вовсе; пять форм записаны в spec/decisions/03-syntax.md:2310 (и D58,
  :4352-4380). Ссылка в commit message, не в нормативном тексте.
