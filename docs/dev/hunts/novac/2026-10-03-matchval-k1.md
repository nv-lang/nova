## Проверенные клетки без находки

- SAME: `compound-assign-places` (`+=`/`-=`/`*=`/`=` по полю и элементу, рукава с привязкой и блоком,
  вложенный скрутини); `compound-arm-writes-target` (рукав пишет цель `+=` до выдачи значения — нормы о
  порядке нет, замер); `value-record-arm` (копия по D32 во всех пяти позициях); `narrow-decl-pos`
  (`u8`/`i16`/`Option[int]`/`f64`-локалы через `as`); `named-generic-str-arg`; `terminating-arm-in-arg`.
- Оба отказали: `decl-match-arm-literal-range` (Карина `E_LIT_OUT_OF_RANGE` по D489, оракул
  `E_IMPLICIT_NARROWING`); `neg-arm-type-vs-param` (`int`-рукава в параметр `f64`).
- SAME, но в нарушении: `order-arg-plain` — под `println` оба печатают `3 2 1` (это №1681).

## Что обошёл и почему

- `ro a u8 = 200` и `ro f f64 = 3` без `as`: Карина отказывает подмножеством, хотя `ro c u8 = match k {3 =>
  250 ..}` принимает и печатает верно (`decl-match-arm-literal-fit`). Отказ громкий, несимметрию не разбирал.
- Литерал-рукав рядом с узким значением без записанного типа: Карина «match arms produce different types»,
  D489 требует принять. Отказ громкий, пробы нет.
- `[]u8.new(cap: 4)` в пользовательском файле — отказ «a capacity … is not compiled yet», не исследовал.
- `unsafe { .. }` аргументом рядом с вызовами — по коду тот же класс, что двойное вычисление; пробы нет.
- `match` в интерполяции и операндом оператора — ожидаемый отказ (фикстура `neg_1.nv`), не проверял.
- Оракул на пользовательском типе `Acc` отказал `E_PREFIX_SHADOWS_NAMED_TYPE` в
  `std/src/collections/vec_iter/core.nv:647`; тип переименован, вне клетки.

## Противоречия

- **D489 против оракула** (`side-oracle-arm-literal`, `decl-match-arm-literal-fit`): D489 — «Если тип
  результата записан (`ro r int = match …`, возврат, аргумент), каждый рукав — позиция этого типа, и
  литерал в нём берёт этот тип»; оракул на `ro c u8 = match k { 3 => 250 _ => 0 }` отвечает
  `E_IMPLICIT_NARROWING`. Статус D489 называет расхождения оракула только для float (№1593).
