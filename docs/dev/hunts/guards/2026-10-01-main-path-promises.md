### 1. Закрытая строка читается открытой (p2)

`row_state` (строки 100–112) берёт ПЕРВОЕ вхождение жирного `**Статус:**` и
читает 60 знаков после него.

Строка 651 закрыта полем без жирного: «Статус: ЗАКРЫТ 2026-08-14», позиция 2114.
Дальше, на позиции 6355, она в прозе цитирует форму поля: «закрыты прозой вместо
поля `**Статус:**`». Страж судит по этой цитате и получает «open».

Что показала проба:
- **A, контроль:** каноническое жирное поле — отказ «is closed», как и обещано.
- **B:** синтетическая строка той же формы — ok.
- **C:** строка 651, скопированная дословно, — ok, исключение принято.

Ошибка в разрешающую сторону. Живого носителя в `ci-accepted-red.list` нет:
единственную запись #1442 оба сканера читают одинаково.

### 4. Прогон pull_request засчитан как доказательство sha (p5)

`refs/pull/N/merge`. Проба показывает только сторону стража. Поведение GitHub
здесь названо по знанию платформы, а не замерено.

### 7. Код в main через worktree (К5) и мимо списка префиксов (К6) — p8

Требование касается ветки main, а код проверяет рабочую копию. В пробе главная
копия стоит на ветке `park`, main выписан в worktree, и настоящий `git commit`

Самотест держит этот случай зелёным НАМЕРЕННО
(`test-check-main-no-direct-code.sh:84`). Значит, это расхождение двух строк одной
шапки, а не регрессия. Условие «не worktree» есть и у `check-main-docs-batched`
(её самотест, строка 86). В живой работе главная копия держит main, и
`git worktree add … main` без `-f` откажет.

Случай D: правка `build.rs` проходит. Вне шести префиксов ещё лежат
`compiler-codegen/Cargo.toml` и тесты крейтов (`*/tests`, 68 файлов). Возможно,
шапка считает тесты «фикстурами».

### 8. Код в main без pre-commit и под чужим MERGE_HEAD (p9)

- `cherry-pick` и `revert` создают коммит на main, не вызывая `pre-commit`.
  Контроль A — обычный `git commit` — даёт отказ.
- Случай D: `merge --no-commit`, затем собственная правка файла `b.nv`. Проба
  подтверждает, что результат отличается от ОБОИХ родителей. Страж отвечает ok.
- Попутно, не находка: `merge --squash` с последующим `commit` получает отказ,
  потому что MERGE_HEAD не пишется (см. противоречие 5).

### 9. «Пакет» из одного пути (p10)

Контроль: одиночный реестр без ключа — отказ. С `NOVA_DOCS_BATCH=1` или ключом из
пробела — ok, и строка вывода называет коммит из одного пути «пакетным».

### 10. Бумага рядом с бумагой проходит как «не наш случай» (p11)

Код (строка 62) пропускает любой путь вне четырёх образцов. Самотест держит
случай «реестр вместе с планом» зелёным (строки 65–66).

Замер истории main (first-parent, без слияний, с 2026-09-29):
- 152 коммита;
- 97 из них целиком из набора — их страж бы проверил;
- 15 — только бумага, но с путём вне набора;
- 5 из этих 15 несут ещё и реестр или записку — ровно форма этой находки.

Контроль D: `git commit --only -- реестр` при коде в индексе. Хук видит временный
индекс и отказывает, как и должен.

### 11. Прогон success — задания не читаются (p12)

Код (строки 200–201) пропускает прогон с success, не читая задания. Носитель среди
обязательных воркфлоу один: `nova-lint.yml:128`, информационное задание,
неблокирующее намеренно. Сегодня по сути ничего не пропущено, но обещание шапки
шире кода.

Рядом, вне кода стража: в `contracts-z3.yml:39,54` `continue-on-error` стоит на
единственном тестовом шаге каждого задания. Значит, «contracts-z3 зелёный»
доказывает, что всё собралось, а не что контракты прошли.

## Чего охота НЕ нашла

- **Выдуманных отказов** нет. Красного без адреса нет.
- **`git commit --only`** работает правильно (p11 D). Вторую форму через `--only`
  искал, не нашёл.
- **«Мишень потеряна» — зазор назван, носителя нет.** Main-стражи не проверяют,
  что их образцы указывают на существующие пути. Сегодня все шесть префиксов живы
  (130/61/29/32/129/329 файлов).
- **Новый тяжёлый воркфлоу вне `REQUIRED`** не будет требоваться молча — носителя
  нет, все 7 имён совпадают.
- **Фильтров `paths:` на push** у обязательных воркфлоу нет.
- **Не проверено (это пробел, а не отсутствие):**
  - `git am`, `rebase`, `update-ref` / `branch -f main`, `--no-verify`;
  - живой `gh`;
  - merge-ref у PR и `continue-on-error` уровня задания на стороне GitHub.
