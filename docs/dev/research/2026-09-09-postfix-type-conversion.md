# Постфиксная конверсия по имени типа: `a.Type().job()`

**Статус:** исследование закрыто 2026-09-09 с вердиктом «новый синтаксис не нужен»; открыты
решения владельца по противоречиям спеки (§5.5, §6) и по двум строкам реестра про `is` (§7).
Правки 2026-09-10 по решению владельца: D429 (снята фраза про `int→i64 widening`: `int` ≠ `i64`,
`uint` ≠ `u64`), страницы `conversions.*` (фраза «коэрсия — свойство позиции»).

## 0. Суть коротко

**Вопрос.** Конструктор-конверсию удобно объявлять статиком `Type.from(other)`, но в цепочке он
читается изнутри наружу. Нужна ли постфиксная запись «конверсия по имени типа» — `a.Type().job()`,
`a.int()`, `a.(Type)`, `a#Type`?

**Ответ: нет.** Действующая конвенция имён (D410/D30) уже покрывает оба случая, и покрывает
цепочно:

| хочу | пишу | почему это уже есть |
|---|---|---|
| дёшево посмотреть на значение как на `Type` (O(1), заём, без копии) | голое имя: `v.str()`, `z.datetime()` | строка «вид» таблицы D410; так уже названы аксессоры `JsonValue`, `SqlValue`, `ZonedDateTime` |
| получить новое значение `Type` из `a` (разбор, копия, валидация) | `a.to_type()`, объявленный **в модуле `Type`** | строка «трансформация» D410; orphan rule нет, поэтому метод на чужом источнике пишет модуль цели (`str @to_version()`, `str @to_csv()`) |
| то же, когда цель — параметр типа `T` | статик `T.from_x(...)` в протоколе (D143) | единственный случай, где метода на источнике быть не может |

Постфикс «по имени типа» как ОБЩАЯ конверсия невозможен, потому что в Nova имя метода кодирует
**стоимость** (голое = O(1) вид, `to_` = новое значение), а не цель. `s.int()` для разбора строки
обещал бы читателю O(1) и врал бы. А статик `Type.from(a)`, ради удобства которого всё
затевалось, — не «неудобная форма», а запрещённая стилем §1а дверь с линтом
`W_STATIC_CONVERSION`: в обычном коде его писать не надо вовсе.

**Что исследование дало помимо ответа «нет».**

1. **Четыре противоречия спеки вокруг `T.from(значение)`** — где-то разрешён, где-то запрещён
   (§5.5, таблица с рекомендацией по каждому). Это решения владельца; рекомендация одна на все:
   голого `from`/`try_from` с параметром не существует, `from_X` только для концепта.
2. **Пробелы документов** (§5.4): в глоссарии нет статей «вид» и «конверсия»; в D30/D410 не
   сказано, что «извлечение варианта суммы в `Option`» — вид; остаток ретракции `as_*` в
   `SqlValue @as_int()`.
3. **Факт про компилятор** (§5.3): `#coerce` в резолве вызова `a.name()` не участвует вовсе,
   порядок — blanket → метод на типе → поле без скобок; никакой «коэрции после метода» нет.

Разделы §1–§4 ниже — ход исследования до сверки с конвенцией: там `a.Type()` ещё был
кандидатом. Оставлены как история, чтобы следующий читатель не прошёл тот же круг; норма — §0
и §5.

## 3. Предложение — `a.Type()` в варианте «статик объявляет, постфикс вызывает» (ОТВЕРГНУТО, см. §5.2)

Две развилки семантики и выбор между ними:

- **(а) сахар над статиком.** `fn Type.from(a Other) -> …` объявляет конверсию; `a.Type()`
  — ЕДИНСТВЕННАЯ форма вызова; прямой `Type.from(a)` вне объявления — ошибка с подсказкой
  (`E_CONVERSION_CALL_POSTFIX`, «пишите `a.Type()`»). Одна дверь сохраняется запретом, как
  Plan 174.2 сохранил её сносом `str.from`.
- **(б) метод, названный типом.** `fn Other @Type() -> Type`; чекер требует, чтобы имя
  совпадало с типом возврата (с учётом `Option[T]`/`Result[T, E]`). Одна декларация, один
  вызов, форма-источник для `#coerce` без изменений D429. **Не покрывает обобщённый код:**
  в `fn[T Parse] read(s str) -> T` нельзя написать `s.T()` — баунд на `T` не может обещать
  метод на `str`. Остаётся статик D143, то есть две формы одной операции по признаку
  «конкретный тип или параметр».

**Выбор — (а).** Только она одновременно даёт цепочку, автоматическое имя, работу с
тип-параметром (`s.T()` под баундом опускается в `T.from(s)` — тот же статик, что D143 уже
разрешает) и одну дверь.

### 3.1. Правило (черновик нормы)

1. Имя после `.` в позиции вызова, резолвящееся в ТИП в области видимости, — конверсия в
   этот тип: `a.Type()` ≡ вызов объявленного `Type.from(a)` с перегрузкой по типу аргумента
   (D84). Регистр имени не важен: `x.u8()`, `x.str()`, `v.Vec[int]()` — та же конверсия.
2. Объявление — статик `fn Type.from(x Src) -> R`, где `R` ∈ {`Type`, `Option[Type]`,
   `Result[Type, E]`}; модель отказа — по D325 R4, имя вызова её не задаёт.
3. Прямой вызов `Type.from(a)` вне тела другого `from` — ошибка `E_CONVERSION_CALL_POSTFIX`.
4. Имена примитивов зарезервированы в позиции метода: объявить `fn X @str()` можно только
   как конверсию (то есть через `str.from(x X)`); иначе `E_METHOD_NAMED_AS_TYPE`.
5. Тип-параметр: `s.T()` законен под баундом с протокольным статиком `.from(s Src) -> Self`
   (D143); без баунда — обычная ошибка резолва.
6. `#coerce` на `Type.from` (форма-приёмник D429) — снять отложенность ТОЛЬКО для целей
   newtype/однополевая обёртка с `-> ro Self`, как D429 сам предлагал; остальное — по-прежнему
   `E_COERCE_RECEIVER_FORM_DEFERRED`.

### 3.2. Что это даёт std

- `to_i8()…to_f64()`, `to_char()`, `to_u8()` (Ф.1–Ф.4 плана 282) → `x.i8()`, `x.char()`,
  `c.u8()`; модели отказа не меняются (`Result[T, RangeError]` и т. д.).
- `JsonValue @str() -> Option[str]`, `@bool()`, `SqlValue @str()`, `ZonedDateTime @datetime()`
  — уже соответствуют правилу по смыслу и модели отказа (R4: одна причина, «нет» —
  нормальный исход); переписываются в `str.from(v JsonValue) -> Option[str]` и т. п.
- `@array() -> Option[[]JsonValue]`, `@object() -> Option[JsonObject]` — **край правила:**
  `object` → `v.JsonObject()`; для `[]JsonValue` постфиксного имени нет.

### 3.3. Края и открытые вопросы

- **Составные цели.** `[]T`, `(A, B)`, `fn(...)` именем не записываются. Для них остаётся
  snake_case-метод (`@array()`) или статик — это исключение надо назвать в норме, иначе
  «одна дверь» протекает.
- **Generic-цель с аргументами.** `v.Vec[int]()` парсится как метод с тип-аргументом (форма
  уже есть: `@to[T]()`, `@serialize[S]()`); `v.Vec()` с выводом `T` из источника — проверить.
- **Сумма vs конверсия.** `x.Option()` → `Some(x)`? Формально законно, если объявлен
  `Option.from`; решать, нужен ли запрет на «конверсию в собственную обёртку».
- **Модуль как приёмник.** Если в выражении допустим путь `mod.Type`, `json.Value()` двусмыслен
  между «статик-путь» и «конверсия значения `json`». Сегодня импортируются элементы, не
  модули (`import a.b.{x}`), проверить D78.
- **Диагностика.** Опечатка в имени типа (`x.Strng()`) должна давать «нет типа `Strng`» с
  подсказкой ближайшего типа, а не «нет метода».
- **Совместимость с `is`/`try_as[T]()` на `any`:** не пересекается — они про рантайм-проверку
  `type_id`, `.Type()` про объявленную конверсию; `any.Type()` без `Type.from(any)` — ошибка.

### 3.4. Амендменты, если решение «да»

D30 (регистр типов — требование; примитивы — зарезервированные имена методов), D410 (семья
`to_*` → постфикс именем типа; `to_str()` — отдельно решить: `x.str()`), D143 (статик `from`
как форма объявления; вызов — постфикс), D429 (частичное снятие отложенности приёмника),
D54 (таблица «одна операция» ссылается на `to_*` — переименовать). Страницы `conversions.*`
и `syntax.*` в обоих языках.

### 3.5. Пробы до решения

1. Парсер: `x.u8()`, `x.Vec[int]()`, `x.T()` в generic-теле, `a.Type().job()` в цепочке.
2. Чекер: `Type.from(a)` прямым вызовом — ошибка; `fn X @str()` без `str.from` — ошибка.
3. Перегрузка: два `Type.from` с разными источниками, выбор по D84.
4. Миграционная оценка: число сайтов `to_i8…to_f64`, `to_char`, `to_u8`, `to_str` в std.

## 4. Если решение «нет»

Статус-кво честен: `fn Other @to_type()` в модуле цели, статик по D143 для тип-параметра.
Единственная дешёвая правка — чекер проверяет соглашение имени `to_<snake(Type)>` для методов,
возвращающих `Type`/`Option[Type]`/`Result[Type, _]`, и заводит спеку для шести стихийных
методов std (`@str()`, `@bool()`, `@datetime()` …) как разрешённого исключения или требует их
переименовать в `to_str()`, `to_bool()`, `to_datetime()`.

## 5. Ревизия 2026-09-09: сверка с конвенцией имён `a.name()` / `a.to_name()`

Вопрос владельца: есть конвенция «голое имя против `to_`» — согласуется ли с ней конверсия
по имени типа; и верно ли, что `a.int()` резолвится «сначала метод, потом коэрция в `int`».
Читал через spec-reader (форма `read-spec`), цитаты сверены по файлам.

### 5.1. Норма: три оси имени, и имя кодирует СТОИМОСТЬ, а не цель

D410 (`03-syntax.md:12092-12110`) и та же таблица в D30 (`:1028-1042`):

| форма | смысл | требование |
|---|---|---|
| голое существительное (`bytes()`, `chars()`, `slice()`, `ptr()`) | O(1) вид/линза: заём, zero-copy, лениво | копия — `.clone()`/`.collect()` на месте вызова |
| `to_*` | трансформация в новое владеющее значение, «у которой вида не существует в принципе» | `-> Result` где fallible (D325 R2, D430) |
| `consume @into_*` | потребляющий финализатор | receiver `consume` (D131) |

Дополнения стиля (`docs/dev/nv-coding-style.md:58-87`): имя типа внутри `to_*` — snake_case по
границам CamelCase (`to_socket_addr`), лексикализованные `datetime`/`bigint` слитно; голое имя
на `consume`-receiver запрещено; **статики-конверсии `T.from(x)`/`T.parse(s)` — «ЗАПРЕЩЁННАЯ
пятая дверь», `from` уместен только для концепт-источника (`from_polar`).**

**Кто проверяет.** Только W-линты и текст, ни одной E-диагностики: `W_RETIRED_PREFIX`
(декларация с `as_`, `lints.rs:4069`), `W_RETIRED_NAME` (вызовы `.to_bytes(`/`.into()`,
`:7669`), `W_STATIC_CONVERSION` (статик `from`/`parse`/`from_str` с параметром, `:4196`),
`W_CONSUME_NAKED_NAME` (`:4312`). Стоимость голого имени (O(1), заём) компилятор НЕ проверяет
нигде; единственная компиляторная проверка zero-cost — D429 R2, и только на `#coerce`-функциях.

### 5.2. Согласуется ли `a.Type()` с осями — нет, запись занята

Оси D410 кодируют в имени **класс стоимости**: голое имя обещает читателю O(1) и заём.
Предложение §3 кодирует в том же месте **цель конверсии** и ничего не обещает о стоимости:
`s.int()` для `str → int` — разбор с тремя причинами отказа, то есть по D410 это `to_*`
(«трансформация, у которой вида не существует»), а не голое имя. Две кодировки не могут делить
одну запись. Значит `a.Type()` как «любая конверсия в `Type`» ломает D410 в самой её сути, а не
в частности.

Отсюда переоценка «шести стихийных методов std». `JsonValue @str() -> Option[str]`,
`@bool()`, `@num()`, `@array()`, `@object()`, `SqlValue @str()` — извлечение payload варианта
суммы: O(1), заём, без копии; `ZonedDateTime @datetime() -> DateTime => @dt` — читатель поля
(D117). По букве D410 все они — **виды**, названные по тому, что показывают, и их имена
совпадают с именем типа случайно, потому что вид на `str` естественно зовётся `str`. Это не
«стихийная постфиксная конверсия» (как записано в §1), а штатное применение первой строки
таблицы. Единственное, чего норма про них не говорит, — что «извлечение варианта в `Option`»
относится к видам (§2 отчёта spec-reader: определений «вид»/«конверсия» в глоссарии нет).

Вариант (а) из §3 бьёт и по второй норме: форма объявления «статик `Type.from(x)`» — та самая
«пятая дверь» §1а с линтом `W_STATIC_CONVERSION`. Вариант (б) (`fn Other @Type() -> Type`)
с осями совместим только если `Type()` — вид (O(1), заём); для трансформаций остаётся `to_*`.

### 5.3. Алгоритм резолва `a.int()` — «сначала метод, потом коэрция» НЕВЕРНО

Порядок по коду (`types/mod.rs:18279-18530`, `f3_check_member_ctx`) и норме:

1. str-специальные ретракции (`E_STR_NO_LEN` и т. п.);
2. blanket по имени;
3. конкретный метод на типе receiver'а — D285 §2: точный receiver побеждает blanket
   (`10-overloading.md:727-731`);
4. поле — только БЕЗ скобок (D117 AMEND: `t.x` поле, `t.x()` метод; одноимённый метод при
   чтении поля со скобками → `E_PRIV_FIELD_READ` «требует call-синтаксис»);
5. иначе ошибка «нет метода».

Статики в этой цепочке не участвуют: PascalCase-receiver парсер сворачивает в `ExprKind::Path`
(`types/mod.rs:3930-3945`). **`#coerce` в резолве вызова не участвует вовсе:** он применяется в
`assignable` при несовпадении типа в позиции с ожидаемым типом — `direct` → single-wrapper (D55)
→ `coerce_pairs` → generic-образцы (`types/mod.rs:21400-21470`; D429 R5/R6/R16). То есть
коэрция — про голое `a` в позиции типа `int`, а не про `a.int()`. Требований к методу с именем
`int` компилятор не предъявляет; D35 разрешает любой receiver и любое snake_case-имя.

Для предложения это значит: шаг «имя резолвится в тип → конверсия» пришлось бы ДОБАВИТЬ в
единственное окно резолва callable (compiler-conventions §3 `:314-320`: без name-keyed
спец-кейсов) — через реестр типов, не через список строк `int|str|…` (сегодня примитивы — как раз
список строк, `is_primitive_type_name`, `types/mod.rs:7718`).

### 5.3а. Гипотеза «приняли `a.Type()`»: как выглядел бы резолв и что пришлось бы проверять

Вопрос владельца был о гипотетическом правиле: если бы `a.Type()` приняли, верно ли, что для
`a.int()` сначала ищется метод, потом конверсия в тип `int`, какие требования к такому методу и
кто их проверяет.

**Порядок «метод → конверсия по имени» рабочий только с одним обязательным условием.** Без него
выражение имеет два смысла: `a.int()` — метод `int`, если он есть у типа `a`, иначе конверсия.
Появление метода `int` в чужом модуле молча меняет смысл существующего кода, а сам метод ничем
не ограничен (D35: любое snake_case-имя, любой возврат). Условие, делающее запись однозначной:
**метод, названный именем типа `T`, обязан возвращать `T`, `Option[T]` или `Result[T, _]`.** Тогда
обе ветви дают значение одного типа; разница остаётся только в стоимости, и она невидима —
это и есть конфликт с осью D410 (§5.2).

**Проверять условие может только компилятор.** Сегодня все правила имён (вид/`to_`, `as_`,
статик `from`) — W-линты, потому что нарушение меняет читаемость, не смысл. В гипотезе имя
метода определяет ветвь резолва и тип результата: правило имён впервые становится правилом
типов, и линт не годится — он предупреждает после того, как чекер уже решил. Нужна E-диагностика
на объявлении («метод `int` обязан возвращать `int`»).

**Где лежал бы шаг.** В окне резолва вызова (`f3_check_member_ctx`): после поиска метода, до
ошибки «нет метода». Не в присваиваемости и не в `#coerce`: D429 вставляет вызов по паре типов в
позиции с ожидаемым типом, а здесь ожидаемого типа нет, есть имя после точки. Это отдельная
«конверсия по имени», называть её коэрсией не стоит. Проверка «имя резолвится в тип» — через
реестр типов, не через список строк `int|str|…` (сегодня примитивы заданы именно списком,
`is_primitive_type_name`), иначе нарушается §3 конвенций компилятора.

**Обратный порядок «тип → метод» хуже.** Примитивы в области видимости всегда: `v.str()` на
`JsonValue` стал бы конверсией и потребовал `str.from(JsonValue)`, все шесть аксессоров std
сломались бы; импорт типа с именем, совпадающим с методом, менял бы смысл кода в чужом модуле.

**Итого под гипотезой:** порядок «метод, затем тип» + E-требование к возврату метода. Цена:
первое правило имён, ставшее правилом типов; новый шаг в окне резолва; неразличимость вида и
трансформации в одной записи. Это и привело к вердикту §5.4.

### 5.4. Рекомендация после ревизии

**Не вводить `a.Type()` как конверсию.** Конвенция уже отвечает на исходный вопрос владельца
двумя строками таблицы D410: дешёвый взгляд на значение как на `Type` — голое имя (`v.str()`,
`z.datetime()`), и это уже есть; трансформация в `Type` — `x.to_type()`, объявленная в модуле
цели (orphan rule нет), и она цепочная. Конструктор `Type.from(a)` в обычном коде — запрещённая

## 6. Вопрос владельца 2026-09-09: «инлайном нет синтаксиса для коэрсии — подумать про `as`»

**Смущение.** `ro a Type = b` — коэрсия может сработать; передача в параметр — тоже; а внутри
выражения (в середине цепочки) ожидаемого типа нет, и записать «примени коэрсию здесь» нечем.
Кандидат — `b as Type`.

**Это уже решалось владельцем, и решение стоит в D429 R10 (`02-types.md`, 2026-07-18):
`as` НЕ вызывает `#coerce`.** Довод R10 в трёх пунктах: (1) `as` — ЗАКРЫТОЕ спекой множество пар,
семантика каждой известна из таблицы D-блоков, а `#coerce` — ОТКРЫТЫЙ реестр пользовательских
функций; смешение сделало бы смысл `as` зависимым от атрибута в чужом модуле (ловушка
C++ conversion-operator под `static_cast`); (2) это была бы ТРЕТЬЯ дверь к одной паре — голое
значение в позиции / именованный метод / `as` — против D9; (3) finalize через `as` немыслим:
каст не потребляет операнд. Там же зафиксировано: **явная форма пары ровно одна — именованный
вызов** (`s.bytes()`, `sb.into_str()`), и диагностика на `s as O` при объявленной паре подсказывает
именно его.

**Поэтому инлайн-синтаксис для коэрсии ЕСТЬ — это имя метода.** Каждая `#coerce`-пара в V1
объявляется методом на источнике (R1); в середине цепочки пишется он: `s.bytes().len()`,
`sb.into_str().trim()`. Ничего невыразимого нет. Асимметрия «в позиции — голое значение, в
выражении — имя» намеренная (R9 даже флагует явный вызов там, где сработала бы позиция):
неявная форма — позиционное удобство с гарантией нулевой стоимости (R2), явная — всегда имя
операции. Читатель неявной формы имени не видит и так; читатель `as MyId` увидел бы цель, но
не операцию (`to_myid` — вид или финализация?).

**Что изменилось бы, если R10 снять.** Технически безопаснее, чем C++: R2 гарантирует
zero-cost, R3 — одну пару на `(I, O)`, R4 — один уровень (цепочки `as`-коэрсий не возникнут).
Пришлось бы: запретить `#coerce` на парах, уже покрытых таблицей D54 (иначе у `int as f64`
два хозяина); решить судьбу finalize-полосы под `as` (потреблять молча или запретить, R10 говорит
«запретить»); поправить R9-линт (`(b as T)` в типизированной позиции — избыточен). И принять,
что `as` перестаёт быть «спека знает каждую пару».

**Альтернатива, если нужна именно единообразная явная запись:** не `as`, а аскрипция типа —
Scala `(e: T)`, Haskell `e :: T`, OCaml `(e : T)`: «считай, что это выражение стоит в позиции типа
`T`». Она включала бы ВСЕ позиционные механизмы (типизация литерала D55/D227, single-wrapper
R11, `#coerce`, боксинг в `any`), не трогая `as`. Цена: новая синтаксическая форма (в Nova `:`
занят полями и именованными аргументами, `name Type` — объявлениями), и это четвёртая дверь к
той же паре. Не рекомендую.

**Рекомендация: R10 оставить.** Смущение снимается формулировкой, а не синтаксисом: «неявная
коэрсия — свойство ПОЗИЦИИ; в выражении та же операция всегда записывается своим именем». Эту
фразу стоит добавить на страницу `conversions.*` (обе языковые версии) рядом с таблицей
механизмов, потому что вопрос возник у владельца повторно — значит, страница его не
предупреждает.

**Найдено по дороге — противоречие №5 (в дополнение к §5.5).** Контекст D429 (`02-types.md`,
первый абзац блока) говорит: «доктрина D55: single-wrapper вкл. переменные, **int→i64 widening
„невидимо для автора"**». D405 амендмент 2026-09-04 (`:51`): «один и тот же конкретный числовой
тип — по имени, не по ширине (`int` ≠ `i64`, `uint` ≠ `u64`)», implicit widening запрещён
(`E_MIXED_WIDTH_ARITH`). Фраза D429 устарела на неделю; рекомендация — вычеркнуть «int→i64
widening» из контекста D429 со ссылкой на D405 2026-09-04. Нормы это не меняет: R11 говорит о
newtype-wrap и sum-lift, не о числовом расширении.

## 7. Оператор `is` — перепись форм D54 против оракула (2026-09-10)

Вопрос владельца: «`is` в std почти не встречается, думаю там куча нестыковок; уместно ли в
рамках этого исследования?». Уместно как приложение: `is` — вторая половина D54, «`as` — сделай
этим типом, `is` — проверь, какой тип сейчас», и различие `as`/`is`/коэрсия и было темой §5–§6.
Полный аудит (правила smart-cast, `is` внутри замыканий и после переприсваивания, дизайн
`match` по типам `any`) — отдельное исследование, если владелец решит формы реализовывать.

**Где `is` живёт в std.** 20 использований, все в тестах, два смысла: `e is TimeoutError` при
`e any` (сценарий 1, `concurrency/*_test.nv`) и `Err(e) => assert(e is OddLength)` на суммах
ошибок (сценарий 2: `hex`, `ini`, `ulid`, `uuid`, `snowflake`). В библиотечном коде — ноль: там
всё через `match`. Фикстура одна — `any_is/box_is_downcast.nv` (any: `is`, smart-cast, `try_as`).

**Восемь проб** (`docs/plans/repro/TBD-is-operator/`, таблица в README): работают и верны
`any is T`, smart-cast в `if`, `try_as[T]()`, variant-check на суммах включая `Option`/`Result`,
`E_IS_NON_ANY` на record. Не работают или расходятся со спекой:

| нестыковка | вид | куда записано |
|---|---|---|
| `x is int` при `x T` или `x []int` — чекер пропускает, кодоген падает «unknown variant» | проверка операнда живёт в кодогене и смотрит на форму `TypeRef`, не на тип | реестр №TBD (К2) |
| `is` на newtype над суммой — чекер пропускает, падает clang | ICE-класс, спека про newtype молчит | та же строка |
| `if r is Ok(n)` — «undefined identifier n» дважды, span `1:1` | нет D54-подсказки «пишите `if Ok(n) = r`» | та же строка, четвёртый носитель |
| `match x { n is int => … }` — parse error | D54 описывает форму, которой нет | реестр №TBD (К2) |
| `x.as[int]?` / `any.as[T]() Fail[TypeMismatch]` — parse error | D54 описывает форму, которой нет; `as` — ключевое слово; `Fail` наружу против D325 R5 | та же строка |
| пример smart-cast в D54 — `str.from(x)`, таблица — `let n = …` | мёртвые формы в нормативном тексте (D73, D184) | та же строка |

**Рекомендация.** `any.as[T]() Fail` вычеркнуть из D54: форма мертва по двум нормам сразу
(ключевое слово, `Fail` наружу), а `try_as[T]()` + `!!`/`?` покрывает «строгий» случай без
нового имени. `is`-паттерн в `match` — единственная форма, которая даёт исчерпывающий разбор
`any` по типам, без неё остаётся лестница `if x is A … else if x is B`; это решение владельца
«реализовать или вычеркнуть», рекомендую реализовать при следующем заходе в парсер паттернов, а
до того пометить в D54 «не реализовано». Проверку операнда `is` перенести в чекер целиком:
по типу, не по форме `TypeRef`, с явным решением про newtype над суммой.
