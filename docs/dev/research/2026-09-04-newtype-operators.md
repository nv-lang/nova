# Операторы над числовым newtype: стирание типа и решение (а)

> Исследование по вопросу владельца 2026-09-04: «арифметика и операторы сравнения в Нова
> работают над newtype от чисел?». Ответ — работают, и работают шире, чем должны. Всё
> проверено пробами `nova check` / `nova build` (оракул); пробы лежат в
> `docs/plans/repro/904-newtype-operators-erase/` (`.nv.txt` + README с замером). Решение
> владельца принято тем же днём, амендмент к D52 внесён. Выросло из исследования
> `2026-09-04-typed-index-vec.md`: типизированные индексы ничего не стоят, если индексы разных
> таблиц можно сравнить напрямую.

## 1. Что работает правильно

Над **одним** newtype операторы ведут себя как у представления, и результат остаётся newtype:

```nova
type FnRow int
type Price f64
ro a = 1 as FnRow
ro b = 2 as FnRow
a < b                          // true
a == b                         // false
(a + b) as int                 // 3 — a + b имеет тип FnRow, печать требует as
(b - a) as int                 // 1
(2.5 as Price) * (2.5 as Price)  // Price, 6.25
if a < b { b } else { a }      // FnRow
```

Проба `same.nv.txt`: собрано, печатает `true 3 2`. Это то, что обязано сохраниться при любом
фиксе.

## 2. Что работает неправильно — дефект К1

Операторы **стирают различие между newtype**, вызовы — нет:

| выражение | ожидание | факт (проба `mixed.nv.txt`) |
|---|---|---|
| `FnRow == TyId` | ошибка типа | `ok`, исполняется, печатает `true` |
| `FnRow < TyId`, `FnRow + TyId` | ошибка типа | `ok`, исполняется |
| `FnRow + n`, `n int` — переменная, не литерал | ошибка типа | `ok`, исполняется |
| `f(t)` при `fn f(r FnRow)`, `t TyId` — контроль `call.nv.txt` | ошибка | `[E7301] cannot pass TyId as argument r of type FnRow` |

Контроль последней строкой показывает: компилятор различие **знает** и применяет его на
вызовах. На операторах — не применяет. Это тот же класс, что у №894 (сахар `[]` не проверяет
ключ, а явный `.index(k)` проверяет): сахар идёт другой дверью, чем вызов, и на этой двери
newtype не смотрится.

Почему К1, а не К2: `if row_id == ty_id` сегодня компилируется и молча сравнивает два разных
пространства номеров — ровно та ошибка, ради которой newtype над числом заводят. Никакой
диагностики, никакого падения.

## 3. Спека молчала

D52 объявляет newtype «типизированно отличным от Y, Go-style» и ничего не говорит про операторы.
D46 (перегрузка операторов через `@`-методы) случай двух разных newtype одного представления не
описывает. Единственное упоминание — `spec/conversions.ru.md:276`: `n as MyNewtype` — identity,
одинаковое C-представление. То есть чекер не нарушал букву: буквы не было.

## 4. Два исхода и решение владельца — (а)

| | (а) операторы только внутри одного newtype | (б) стирание намеренно |
|---|---|---|
| `FnRow == TyId` | ошибка типа | законно |
| `FnRow + n` при `n int` | ошибка, путь — явный `as` | законно |
| `FnRow + 1` (литерал) | законно, литерал адаптируется (Plan 200) | законно |
| донор | **Go**: `type FnRow int` → `FnRow == TyId` mismatched types, `FnRow + 1` ok, `FnRow + n` error | нет |
| гарантия newtype | полная: вызовы, `[]`, операторы | дырявая ровно в сравнении |
| что писать в спеку | амендмент D52 с нормой | амендмент D52 «операторы стирают», и это надо объяснять |

**Решение владельца 2026-09-04 — (а).** Довод: смысл newtype над числом — чтобы два пространства
номеров нельзя было спутать; самое частое место такой путаницы — сравнение. Стирание в
операторах оставляло бы гарантию дырявой там, где она нужнее всего, и обесценивало бы
`IndexVec[I, T]`: защита на `[]` и вызовах ничего не стоит, если индексы можно сравнить напрямую.

## 5. Норма — как записана в D52

Амендмент внесён в `spec/decisions/02-types.md` (раздел «Амендмент (2026-09-04, решение
владельца): операторы над числовым newtype — только внутри одного newtype», перед D406), без
нового номера, датирован. Четыре пункта:

1. Бинарная арифметика (`+ - * / %`) и сравнение (`== != < <= > >=`) определены между операндами
   **одного** newtype `X`; результат арифметики — `X`, сравнения — `bool`.
2. Числовой литерал в позиции операнда адаптируется к `X`, как при присваивании (Plan 200).
3. Смешение — `X` с другим newtype или со **значением** представления (переменная, поле,
   результат вызова) — compile error; диагностика называет явный `as` как путь.
4. Унарные операторы и составные присваивания — по тем же правилам.

Требование к реализации, записанное в амендменте: операнды оператора проверяются **той же
дверью, что аргументы вызова**, не второй копией сверки — иначе дыра вернётся при следующем
операторе. Спека положена до фикса.

## 6. Реестр и порядок

- Строка **№904** (🔴 К1) в `docs/plans/221.1-bug-sweep.md`, с обоими исходами и решением;
  интегратор добавил маршрут («чинится: план 221, чекер, путь бинарных операторов») и вердикт
  **«блокирует тег: да»** — довод не в тяжести, а в цене отсрочки: решение (а) сужает язык, до тега
  это чинится молча, после — ломает уже написанный чужой код; проба `docs/plans/repro/904-newtype-operators-erase/`.
- Фикстуры — у чинящего (правило дома): негатив на `==`/`<`/`+` между двумя newtype и между
  newtype и `int`-переменной, line-pinned; позитив на операторы одного newtype с результатом того
  же типа и на литерал. Класс закрыт, когда операнды операторов проверяются той же дверью, что
  аргументы вызова.
- Место в очереди: вне порядка `IndexVec` (`2026-09-04-typed-index-vec.md` §7), но без неё
  гарантия newtype-индексов неполна — чинить до или вместе с №894. Вердикт «блокирует тег: да» поставлен интегратором (см. выше).

## 7. Перепись дверей newtype (по наблюдению интегратора)

Интегратор заметил: №821, №893, №894, №904 — одна форма, «одно правило, несколько дверей, на
одной из них оно не применяется», и предложил это как клетку для охоты. Клетка проверена
целиком для одного правила — «newtype отличен от представления и других newtype». Все двери,
через которые значение newtype встречает ожидаемый тип, — по пробе; каждая с контролем на
`int`/`str`, чтобы отделить «newtype стирается» от «чекер не смотрит вовсе». Пробы и полная
таблица: `docs/plans/repro/906-newtype-doors/README.md`. Те же файлы прогнаны из `examples/`
(внутри workspace) — `check` совпал до строки.

| дверь | newtype | контроль `int`/`str` | итог |
|---|---|---|---|
| объявление с типом `ro y FnRow = t` | `E7301` | `E7301` | держит |
| аргумент вызова, `insert(t, …)` | `E7301` | `E7301` | держит |
| литерал коллекции `[]FnRow = [a, t]` | `E7301` | — | держит |
| литерал в операнде / паттерне | ok | — | норма (Plan 200) |
| бинарные операторы | ok, исполняется | — | **А** №904 |
| `a += t`; `a + N` (`const N int`); `a..t`; `match a { ONE => }` (`const ONE TyId`); `[]str[a]` | ok; собрано (match — CC-FAIL) | — | **А** — пять носителей дописаны в №904 |
| переприсваивание `x = t` | ok, **исполняется** | `x = s` — ok, CC-FAIL | **Б** |
| `Option[FnRow] = Some(t)` | ok, исполняется | `Some(s)` — ok, CC-FAIL | **Б** |
| поле литерала записи `{ r: t }` | ok, исполняется | `{ r: s }` — ok, CC-FAIL | **Б** |
| ветви `if` | ok, исполняется | ok, CC-FAIL | **Б** |
| унификация `same[T](a, t)` | ok, исполняется | ok, CC-FAIL | **Б** |

**Класс А** — сахар стирает newtype: то, что №904 назвал для операторов, распространяется на
составное присваивание, типизированную константу в операнде, диапазон, const-паттерн и индекс
встроенного среза. Дописано в №904 пятью носителями; фикс — шесть дверей одним путём.

**Класс Б — новая строка реестра (К1), и она больше newtype.** В пяти позициях чекер **не сверяет
типы ни для кого**: `mut x int = 1; ro s str = "s"; x = s` проходит `nova check`. Это известное
«кольцо permissive» №262 — чекер permissive by design, «codegen выберет», — и корпус на него
опирается: 11 негативных фикстур ждут ошибку от Си маркером `EXPECT_CC_ERROR`, в том числе
`d128_char_distinct_from_int.nv` (различие `char`/`int` ловит только Си). Пока представления разные,
Си срабатывает — К2, отказ есть, хоть и не тот. **Для newtype представление то же, и Си не
срабатывает никогда:** все шесть newtype-проб собраны и исполнены молча. После амендмента D52 язык
обещает `FnRow ≠ TyId`, а пять дверей обещание не исполняют. Одна строка, не пять: фикс — провести
пять позиций через ту сверку, которая уже работает на объявлении и аргументе; приёмка — когда
`EXPECT_CC_ERROR` у этих фикстур можно сменить на `EXPECT_COMPILE_ERROR`.

**Что это даёт охоте.** Клетка интегратора подтверждена измерением на одном правиле: из
одиннадцати дверей держат три. Метод воспроизводим для любого правила: перечислить двери, через
которые проходит проверяемое значение, каждую — пробой с контролем на заведомо разных типах. Это
и есть готовый бриф для `defect-hunter` (план 278): цель — правило, а не подсистема.

## 8. Для Карины

Следствие для требований `2026-09-04-typed-index-vec.md` §8, и после переписи §7 оно шире:

**Одна дверь сверки «ожидаемый тип ← фактический».** Каждая позиция, где значение встречает
ожидаемый тип — объявление, переприсваивание, аргумент, возврат, поле литерала, полезная нагрузка
варианта (`Some(x)`), ветви `if`/`match`, унификация generic-параметра, операнды операторов и
составных присваиваний, границы диапазона, паттерн, ключ `[]` — проходит через **одну** функцию
сверки; кодоген никогда не первая линия и не последняя: `EXPECT_CC_ERROR` как форма приёмки в
Карине не существует. Это расширение пункта 3 требований (§8 там), не новый инвариант; счётчик
новых — ноль. Страж: фикстура на каждую позицию с парой «newtype→newtype» и «str→int», обе
`EXPECT_COMPILE_ERROR`.
