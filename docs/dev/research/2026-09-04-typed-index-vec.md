# Типизированный индекс для `Vec`: newtype над целым как ключ

> Исследование по вопросу владельца 2026-09-04: «индексировать `Vec` по newtype от целого, а не
> только по `int` — как в Rust и как лучше в Нова». Все утверждения о дереве проверены пробами
> `nova check` / `nova build` (оракул). **Пробы лежат в `docs/plans/repro/`** по правилу №695
> (`.nv.txt` + README с замером): `894-index-sugar-bypass/` (положил интегратор),
> `895-static-via-type-param/`, `896-set-blanket-conformance/`, `897-generic-alias-codegen/`,
> `898-alias-static-ctor/`, `899-d88-default-type-param/`, `628-user-index-codegen-generic/`.
> Найденные дефекты — в реестре `docs/plans/221.1-bug-sweep.md`: №894–№899 (номера присвоил
> интегратор 2026-09-04), второй носитель у №628. Все решения ниже — владельца, 2026-09-04.

## 1. Суть

Не учить `Vec` принимать любой newtype, а сделать **вектор, параметризованный своим индексом**:
сегодняшний `Vec` **переименовывается** в `IndexVec[I Ordinal, T]`, где `I` реализует маленький
протокол «упаковать / распаковать `int`»; `Vec[T]` и `[]T` остаются как alias `IndexVec[int, T]`.
Тогда `IndexVec[FnRow, FnDef]` нельзя проиндексировать `TyId` — это ошибка типа. Один тип, а не
два. `[N]T` вне ряда: особая форма на стеке, общего с `[]T` только часть протоколов.

Это ровно решение rustc: `IndexVec<I: Idx, T>` (`rustc_index`) — сотни таблиц компилятора
индексируются `DefId`, `BodyId`, `Local`; трейт `Idx` из двух функций (`new(usize)`, `index()`),
newtype'ы получают его макросом `newtype_index!`; `IndexVec<DefId, _>` **не** индексируется
`BodyId`. Std Rust этого не делает: `Vec<T>` реализует `Index` только для `usize` и диапазонов,
пишут `v[id.0]`.

## 2. Что уже есть в Nova

- **`Index[K, V]`** (D238): `@index(key K) -> V` — magic-метод для `a[key]`; перегрузки по типу
  ключа работают, у `Vec` три (`int`, `Range`, `mut` запись — `vec/access.nv:30,53`,
  `vec/slice.nv:39`).
- **Newtype** (D52): `export type TyId int`, распаковка явным `as`.
- **Статика в протоколе** (D143): leading-точка, `.from(t T) -> Self`.
- **Обобщённый alias** с частичным применением есть в спеке (`type StringMap[V] alias
  HashMap[str, V]`, `02-types.md:224`) — чекер принимает, кодоген не эмитирует (№897, §7).
- **novac уже делает это руками** (`sem/callables.nv:155-164`): `export type FnRow int`,
  `fn raw_row(r FnRow) -> int => r as int`, `fns.rows[raw_row(via_row)]`. Типизированный индекс
  есть, но на границе `Vec` каждый раз разворачивается своей дверью. Архитектура novac уже
  называет rustc `IndexVec` своим лагерем (`sem/sem.nv:4,29,216`, `channel.nv:181`).

## 3. Почему так, а не иначе

**Не расширять `Vec` приёмом «любой целочисленный newtype».** Это убирает разворотку, но
убивает единственную причину, ради которой `FnRow` заводили: `Vec[Def]` станет принимать и
`TyId`, и `FnRow`. Донора у такого решения нет.

**Bound для `I` — протокол, а не type-set.** `[T SignedInts]` (D310) не подходит по букве
спеки (`02-types.md:16796`): «члены — по идентичности, newtype `type MyI8 i8` **не** член set'а
`{i8}`, `~underlying` НЕТ» — set примет `int` и отвергнет `FnRow`, наоборот нужному. Свой set
`type RowIdx set int | FnRow | TyId` работает, но закрыт: std его не знает. Новый bound
«представление ∈ Ints» — изменение языка против D310. Протокол — открыт, лежит в prelude, `int`
в нём обычный член; это буквально донор.

## 4. Форма

```nova
// prelude
type Ordinal protocol {
    @ordinal() -> int                 // распаковать
    .from_ordinal(i int) -> Self      // упаковать
}
// законы (в текст D-блока; ensures на @next_ordinal проверяемо контрактами):
//   I.from_ordinal(x.ordinal()) == x    x.ordinal() >= 0
fn[T SignedInts] T @ordinal() -> int => @ as int          // все знаковые одним объявлением
fn[T SignedInts] T.from_ordinal(i int) -> T => i as T

// std/collections — сегодняшний Vec (vec/core.nv:67) с новым именем и параметром I
export type IndexVec[I Ordinal, T] priv { … как у Vec … }
export fn IndexVec[I Ordinal, T] @index(i I) -> T             // было (i int)
export fn IndexVec[I Ordinal, T] mut @index(i I, v T) -> ()   // было (i int, val T)
export fn IndexVec[I Ordinal, T] @index(r Range[I]) -> Self   // view; ordinal'ы от нуля view
export fn IndexVec[I Ordinal, T] mut @push(v T) -> @          // как сегодня, D181
export fn IndexVec[I Ordinal, T] @len() -> int                // длина — int, не I
export fn IndexVec[I Ordinal, T] @next_ordinal() -> I         // = I.from_ordinal(@len()); rustc next_index
export fn IndexVec[I Ordinal, T] @enumerate() -> …            // пары (I, T); rustc iter_enumerated
export fn IndexVec[I Ordinal, T] mut @append[S Contiguous[T]](other S) -> @   // Contiguous = ex-AsSlice

type Vec[T] alias IndexVec[int, T]                             // alias, не newtype
type Range[I Ordinal = int] value { ro start I; ro end I }     // D88 default, не alias

// novac
export type FnRow int
fn FnRow @ordinal() -> int => @ as int
fn FnRow.from_ordinal(i int) -> FnRow => i as FnRow
```

Пробы и строки реестра №894–№896 гонялись под рабочими именами `Idx` / `@idx()` / `.from_idx()`;
цитаты диагностик там оставлены как получены.

## 5. `Vec` после переименования

**Alias, не newtype.** D52 требует от alias полной прозрачности (`02-types.md:685`): тот же тип,
все методы видны, `fn f(v IndexVec[int, str])` принимает `Vec[str]`, существующий код не
меняется. Newtype — отдельный тип без методов базы (D52), `as` на каждой границе, 67 методов
переобъявлять — и ничего не покупает: `Vec[T]` и `IndexVec[int, T]` значат одно и то же.

**Что меняется в сигнатурах.** У `Vec` 67 экспортированных методов — счёт по
`grep -h '^export fn Vec\[T\]' std/src/collections/vec/*.nv`; с приватными (`fn Vec[T]` без
`export`) — 77 в `vec/`, 84 по всему `std/src`; экспортированных по всему `std/src` — 72. Ниже
речь об экспортированных в `vec/`. У 13 из них `int` стоит в **индексной** позиции и становится `I`: `@index` (обе), `@get`, `@insert`, `@remove`,
`@swap_remove`, `@swap`, `@splice`, `@insert_slice`, `@split_at`, `@index_of`, `@position`,
`@rposition`. Остальные 54 — про количество (`@len`, `@cap`, `@truncate`, `@push`…) и остаются
на `int`. Тот же принцип, что у rustc (`swap(a: I, b: I)`, но `len() -> usize`). Для `I = int`
все 13 совпадают с сегодняшними.

**Снятый риск.** Дублирования C-кода на каждый newtype-индекс не будет: оракул мангалит
newtype-параметр по представлению — `Table[FnRow, str]` и `Table[int, str]` получили одну
структуру `Nova_Table____nova_int__nova_str`. Все int-newtype'ы — одна инстанциация. Для Карины
это требование (§8 п. 4).

**Цена — в компиляторе, не в std.** Строка `"Vec"` захардкожена в оракуле **170 раз**
(`grep -rc '"Vec"' compiler-codegen/src --include=*.rs`, 2026-09-04), и список мест должен быть
полным, потому что на нём стоит довод «170 правок против одной константы»:

| файл | вхождений |
|---|---|
| `types/mod.rs` | 70 |
| `codegen/emit_c.rs` | 60 |
| `types/constraint_solver.rs` | 11 |
| `protocols/auto_derive.rs` | 6 |
| `lints.rs` | 6 |
| `callnorm.rs`, `ast/mod.rs` | 3 + 3 |
| `types/fiber_safety.rs`, `parser/mod.rs`, `const_fn_trampoline.rs`, `codegen/may_gc.rs` | 2 × 4 |
| `number_exprs.rs`, `field_cache.rs`, `codegen/gc_layout.rs` | 1 × 3 |

По каталогам: `types/` 83, `codegen/` 63, прочие 24 — первая редакция называла только два
каталога и читалась как «два файла»; интегратор поймал. В novac таких мест **одно** — константа
`SLICE_HEAD = "Vec"` (`builtins.nv:172`) под стражем `check-novac-no-name-hardcode.py`. Отсюда
порядок §6 и требования §8.

**Отклонено:** `type Vec[T, I Ordinal = int]` по D88 без переименования — 0 правок по имени,
но индекс вторым параметром против донора и нет отдельного имени для типизированной таблицы;
цена 170 правок ложится на Карину, где это одна константа. Отклонено также
`type Range alias Range[int]` — одно имя не может быть и обобщённым типом, и alias'ом на него;
правильный инструмент — D88.

## 6. Решения владельца (2026-09-04)

| вопрос | решение | довод |
|---|---|---|
| имя протокола | **`Ordinal`**, `@ordinal()`, `.from_ordinal()` | не `Idx`/`VecIdx`: `idx` разрешено конвенцией только для локалей (`nv-coding-style.md:855`); протокол не про `Vec` — тем же ключом индексируются bit-set'ы, карты, диапазоны; `Index` занято D238, `IndexMap` значит «порядок вставки». Полное слово, точный смысл «число-позиция» |
| set-blanket как конформер | **да** | D310 определяет set-blanket как «мономорфизация per член» — метод у члена есть; «есть для вызова, нет для bound» — два ответа на один вопрос. Оформление: сначала одна фраза амендмента к D310 «Семантика тела», потом чекер (№896). Как сделать быстро — Приложение Б |
| `Vec` после переименования | **alias** | §5 |
| `Vec[T, I = int]` вместо переименования | **отклонено** | §5 |
| порядок работ | **сначала novac, std после релиза оракула** | на шаге novac D-блок не нужен: `IndexVec` и `Ordinal` там обычные типы; std-волна — после починки №894+№628 (иначе alias-`Vec` унаследует небезопасный `[]`) и №897/№898 (иначе не эмитируется и не конструируется своим именем) |
| `Range[I]` | **да, `type Range[I Ordinal = int]`** (D88) | правила в D-блок дословно: `I` у литерала `a..b` — из операндов, `FnRow..int` — ошибка; `..=` через `I.from_ordinal(b.ordinal() + 1)`; `RangeIter` по `I`; `@index(r Range[I]) -> Self` — view индексируется своими ordinal'ами от нуля. Донора нет (rustc `IndexVec` типизированных диапазонов не держит) — расширение сверх донора |
| что возвращает `push` | **`-> @` как сегодня, индекс — `@next_ordinal() -> I`** (rustc `next_index`) | `-> @` нормативен по D181 (`02-types.md:8122`) с 8 фикстурами; путь «`push -> I` + перегрузка `@append(v T) -> @`» отвергнут ради нулевой цены в спеке и корпусе. Смягчение: таблица novac заводит свою дверь `@add(def) -> FnRow` (`next_ordinal` + `push` внутри). Исследование — Приложение А |
| `AsSlice[T]` | **переименовать в `Contiguous[T]`** | протокол — свойство хранения `{ @ptr(); @len() }`, не конверсия; D299 сам назван «contiguous-buffer abstraction» (`02-types.md:16148`); донор C++20 `contiguous_range`; ряд `Hash`/`Equal`/`Clone` без префиксов, `As` — вкус ретрагированных D410 `as_*`. 14 упоминаний, один реализатор; амендмент к D299 |
| blanket по `SignedInts` или `Ints` | **`SignedInts`** | индексы в Nova знаковые по решению — `docs/dev/research/08-int-width-and-literal-inference.md` §1 (7:3 за signed, регрет Stroustrup'а по `size_t`). Newtype над `u32` получает `Ordinal` только явно — исключение должно быть видно |
| итерация пар `(I, T)` | **свой `@enumerate` у `IndexVec`** | сегодня `@enumerate` — адаптер итераторов с `i int` (`vec_iter/core.nv:335`); для `I = int` поведение то же. Не смешивать букву `I` с `EnumerateIter[I, T]`, где `I` — источник |
| законы `Ordinal` | **принять** | без закона `from_ordinal(i) => (i * 2) as FnRow` удовлетворяет протоколу и ломает `next_ordinal`; rustc `Idx` документирует `new(x.index()) == x`. Для blanket и `as` выполняются сами |
| обобщённый alias не эмитируется | **дефект**, не амендмент | D52 требует полной прозрачности — форма обязана работать по букве (№897) |
| `#impl(Ordinal)` для newtype | позже | `#impl` для newtype не поддержан (`E_AUTO_DERIVE_UNSUPPORTED_KIND`, `02-types.md:14519`); две однострочки на newtype — удобство, не блокер |

Открытых вопросов дизайна не осталось.

## 7. Что упирается в дефекты оракула

Что доказано (контроли в тех же каталогах `docs/plans/repro/`): newtype с
`@ordinal`/`.from_ordinal` и `@ as int` — собрано, печатает 42 (`895/direct`); явные `t.index(k)` /
`t.index(k, v)` на обобщённой записи с фантомным `I` — собрано, печатает `B` (`628/explicit`);
alias через аннотацию или параметр — собрано, печатает 1 (`898/annotated`, `898/param`). Всё
остальное из §4 упирается в реестр; каталог пробы = номер строки:

| строка | класс | что | бьёт по |
|---|---|---|---|
| №894 | 🔴 К1 | сахар `a[k]` на user-`@index(k K)` **не проверяет тип ключа**: `IndexVec[FnRow, str]` индексируется `TyId` молча, `Table @index(i int)` — строкой (CC-FAIL). Контроль: `rows.index(t)` — `E7301`. Дверь — рука `ExprKind::Index` чекера (`types/mod.rs:12124`, «никакого user-@index здесь») | **главное**: без него newtype-индекс через скобки ничего не защищает |
| №628 (2-й носитель) | 🔴 К2 | `[]` на user-типе **в кодогене не маршрутизируется** ни на чтение, ни на запись; вместе с №894 D238/D240 для user-типов не реализованы ни с одной стороны | `[]` вообще |
| №897 | 🟡 К2 | **обобщённый alias не эмитируется** — включая пример спеки `StringMap[V]` (`undeclared identifier Nova_StringMap____nova_int`); дверь `emit_c.rs:18236`, `typedef … Nova_{t.name}` по голому имени | `type Vec[T] alias IndexVec[int, T]` |
| №895 | 🟡 К2 | статика через параметр типа `I.from_ordinal(n)` при `I = newtype` резолвится как `int.from_ordinal` → `E_UNKNOWN_STATIC_METHOD`; второй носитель — статический set-blanket (форма D310 `02-types.md:7578`, ни разу не исполнялась) → `INTERNAL-PANIC` | `@next_ordinal`, blanket по `SignedInts` |
| №898 | 🟡 К2 | `Alias.new()` **теряет тип** — метод на результате уходит в single-key fallback в `StringBuilder`; через аннотацию/параметр работает (семья №254/№627) | `Vec[str].new()` после переименования — на каждом втором файле std |
| №899 | 🟡 К2 | **D88 default-параметр на типе не реализован** (`E7310` / `E_RECV_SHAPE_MISMATCH`); в std и фикстурах ни одного `= Default`, форма принята в мае и не исполнялась | `Range[I Ordinal = int]` |
| №896 | 🟡 К2 | blanket по set **не засчитывается в конформанс** (`int is missing: ordinal()`), хотя вызов резолвится; `check_satisfaction_against_methods` (~31600) знает blanket'ы только с посылкой-протоколом (№111) | `int` как `Ordinal` одним объявлением |

**Порядок починки:** №894+№628 вместе (две половины `[]`) → №897 → №895 → №898 → №899 → №896
(после амендмента к D310). **Обходы для novac до починки:** `.index(k)` вместо `[]` и
`rows.len() as FnRow` в конкретной обёртке таблицы вместо `@next_ordinal` — обе вторые двери,
лучше дождаться реестра.

Не пробовалось: `@next_ordinal`, `@index(r Range)` на обобщённой записи, alias под именем `Vec`.
Замечено по дороге: instance-метод в теле протокола пишется `@idx()`, не `idx()`
(`E_PROTO_METHOD_NEEDS_AT`); в `897/spec_example` конструктор `StringMap[int].new()` резолвлен в
`EmbeddedDir.new` — при существующем typedef это была бы тихая подмена, не CC-FAIL (семья №898).

Два расхождения с пробой интегратора `894-index-sugar-bypass/`, не сглаженные: (1) его файлы лежат
как `.nv`, README каталога (`repro/README.md`, п. 2) требует `.nv.txt`; (2) его контроль даёт
`E_NO_MATCHING_OVERLOAD`, мой на другой форме записи — `E7301`; обе — отказ на явном вызове,
чинящему важно знать, что дверь отказа не одна.

## 8. Требования к Карине по `Vec` / `IndexVec`

Оракул знает `Vec` по строке в 170 местах; Карина обязана быть устроена так, чтобы переход
стоил одну константу. Пункты 1, 2, 5, 6 — следствия принятого §4а «Идентичность — не имя»
(`docs/dev/novac-architecture.md:1844`); пункты 3 и 4 — **новые**, их два, каждому страж или
фикстура (норма 253); пункт 7 — граница.

1. **Имя контейнера — одна дверь:** `builtins.SLICE_HEAD` (`builtins.nv:172`) под
   `check-novac-no-name-hardcode.py`; дальше только `DeclId`. Переименование = смена константы
   плюс форма типа. *(170 мест оракула.)*
2. **Alias — тот же `DeclId`/`TyId`.** `Vec[T]`, `[]T` разрешаются в инстанс цели; у alias'а нет
   собственного мэнглинга — эмиттер не видит его имени; частичное применение — обычная
   подстановка. *(№897, №898, №627.)*
3. **Сахар `[]` — обычный вызов.** `a[k]` и `a[k] = v` идут в `@index` тем же путём резолва и
   проверки аргументов, что явный `a.index(k)`, для всех типов; «быстрой» ветки для `Vec` в
   чекере нет, скорость — дело lower/emit. *(№894, №628.)*
4. **Инстанциация по представлению для newtype-параметров.** `I = FnRow` и `I = int` дают один
   мономорф и одну C-структуру; newtype в позиции параметра отличается от представления только
   в чекере. Свойство `mono` с фикстурой-счётчиком инстансов. *(Снимает дублирование 67 методов.)*
5. **Конформанс и диспатч — одна таблица методов.** Set-blanket разворачивается по членам при
   регистрации (D310 «per член»); blanket по протоколу индексируется по имени метода; вердикт
   `(тип, протокол)` кэшируется. *(№896.)*
6. **Статика через параметр типа — по `DeclId` подстановки:** `I.from_ordinal(n)` при `I = FnRow`
   есть `FnRow.from_ordinal`, не поиск по имени у `int`. *(№895.)*
7. **`[N]T` — отдельный тип**, не alias `Vec`; общая только реализация части протоколов.

Стражи: п. 1–2 покрыты `check-novac-no-string-keys.py` и `check-novac-no-name-hardcode.py`;
п. 3, 5, 6 — фикстуры при закрытии соответствующих строк; п. 4 — счётчик инстансов в `mono`.

## Приложение А. Исследование `push -> I` против `push -> @`

1. `-> @` у `push` — норма D181 «Array methods — `-> @` fluent mut chain» (`02-types.md:8122`),
   амендмент Plan 184: «поведение цепочек `a.push(1).push(2)` не меняется».
2. Цепочки `.push().push(` — 8 фикстур `spec_tests/conformance/` (в т.ч.
   `d181_fluent_mut_chain.nv`), `vec/mutate.nv`, `bench/corpus/03_generic_heavy.nv`; в пакетах
   (`nova-polaris`, `-http`, `-tls`, `-socks`, `-compress`, `-bignum`) — ноль.
3. `push` как выражение — 18 мест, все рукав `match` в позиции оператора (`Some(x) =>
   out.push(x)` / `None => return out`), от типа возврата не зависят; мест `ro v = x.push(...)` —
   ноль.

| | A. `push -> I` + `@append(v T) -> @` | Б. `push -> @` + `@next_ordinal()` — **принят** |
|---|---|---|
| спека / фикстуры | амендмент D181 / 8 переписать | 0 / 0 |
| донор | rustc `push -> I`; `@append` — `StringBuilder` (D84, семь перегрузок) | rustc `next_index()` |
| индекс в novac | одна строка | две — снимается дверью `@add` на таблицу |
| цена ошибки | забытый `@append` в цепочке — ошибка типа | `next_ordinal` после `push` — off-by-one, не ловится |

## Приложение Б. Конформанс через set-blanket — как не замедлить чекер

Правка №111 (`types/mod.rs:31492`) ищет blanket'ы **полным проходом по всей `method_table`** на
каждый требуемый метод, без кэша; распространить это на set'ы — умножить скан на число проверок.
Быстрая форма: (1) set-blanket разворачивать по членам при регистрации — set конечен, дальше
O(1)-lookup как у обычного метода; (2) blanket по протоколу (открытое множество) индексировать по
имени метода — индекс `blanket_method_names` (`mod.rs:3713`) уже есть; (3) кэшировать вердикт
`(тип, протокол)`. Принцип: конформанс спрашивает ту же таблицу тем же путём, что диспатч.
