## 1. Что предлагается

Пять частей, из них новых сущностей — две.

1. **Проброс строки через fn-параметры.** Строка в типе параметра-функции —
   минимум, а не потолок: при вызове параметра его эффекты добавляются к строке
   вызывающего. Синтаксиса не появляется.
2. **`forbid` в строке** — контракт «этого мне нельзя», в том числе на параметре.
   Отделяется запятой: `fn() Job Io, forbid Db -> ()`.
3. **`fn[E effects]`** — переменная строки эффектов, в одном слоте с `[T]`.
4. **Два класса эффектов.** Критерий: **есть обработчик — расширяет строку
   неявно; нет обработчика — только явно** (через объявление или `[E effects]`).
5. **Два новых эффекта** без обработчика: `SameThread` (нужен тот же поток ОС) и
   `Exclusive` (держу нечто, к чему нужен единоличный доступ). Имена — за
   владельцем, кандидаты в §6.

Исчезают: `#thread_affine`, отдельная механика подъёма у него, `#blocking`
(становится директивой `#os_thread`), и `E_FIBER_INDIRECT_CALL` как отдельный
механизм.

## 1.1. Режим транзитивности по классам — и амендмент к D62

> **Этот раздел первый по требованию ревизии интегратора и обязан открывать D-блок.**
> Именно здесь предложение задевает букву D62, и молчаливый спор со спекой в проекте
> запрещён: расхождение оформляется **явным амендментом**, а не умолчанием.

**Что говорит D62 сегодня** (проверено дословно, `04-effects.md:2608`):

- прямой эффект не объявлен → **compile error**;
- **транзитивный не объявлен → warning** (подавляемый `#allow_transit`, с ручкой
  проекта `[lints] transit_effects = "off" | "error"`);
- и это не случайность: D62 называет себя «большой ревизией философии», сознательно
  ослабившей принцип «сигнатура = полное описание».

**И там же уже есть исключение — Правило 2:** `Fail[E]` обязателен в сигнатуре и при
**транзитивном** throw, «иначе **compile error, не warning**».

То есть **два режима транзитивности в спеке уже существуют**, и предложение не вводит
новый — оно добавляет во второй класс двух членов и, главное, даёт ему **критерий**
вместо поимённого исключения.

| класс | члены | транзитивность | почему |
|---|---|---|---|
| **возможности** | `Io`, `Db`, `Net`, `Fs`, `Log`, `Time` | **warning**, ручка `transit_effects` — как сегодня, D62 Правило 1 | вызывающий получает обязательство, которое видит и может закрыть `with` |
| **строгие по контролю** | `Fail[E]` | **error** — D62 Правило 2, без изменений | необъявленный throw ломает поток управления у того, кто не поставил catch |
| **маркеры** (ново) | `Exclusive`, `SameThread` | **error** | обработчика нет и быть не может: warning советует «объяви или обработай», а обрабатывать нечем — совет пустой |

**Компромисс стоит между двумя измеренными полюсами доноров** (сверка
интегратора 2026-09-02). Java с checked exceptions — строгая транзитивность
возможностей: усталость авторов и массовый обход (`throws Exception`), Kotlin
снял механизм целиком. OCaml 5 — противоположный полюс: эффекты добавлены **без
следа в типах**, и необработанный эффект обнаруживается только падением
`Effect.Unhandled` во время работы. D62-warning для возможностей плюс строгий
класс для маркеров — средняя точка, и таблица выше впервые даёт ей критерий
вместо ощущения.

**Ключевое, чего не было в первой редакции:** §3 («строка = объявленное ∪ вызываемые ∪
fn-аргументы, неподвижная точка») **не распространяется на класс возможностей**. Для
них всё остаётся как в D62 — warning и ручка проекта. Строгий проброс включается
**только для маркеров**, и только потому, что для них warning бессмыслен.

Без этой оговорки исполнитель, прочитавший §3 буквально, включит строгость для всего —
и это будет **откат D62 без амендмента**.

**Отдельно про пробы §3.** Все четыре сняты под `--strict-effects` — под флагом,
который включает ровно ту строгость, которую D62 сделал не-дефолтом. Они доказывают,
что механика «минимум, а не потолок» **реализована**, но не доказывают, что она
**норма**. В D-блоке это должно быть сказано, иначе замер прочтут как санкцию.

**Форма амендмента к D62:** добавить в Правило 1 третью строку семантики проверки —
«эффект маркерного класса, не объявленный транзитивно → compile error; `#allow_transit`
и `transit_effects` на него не действуют» — и назвать критерий класса. Правило 2
(`Fail`) не трогается: у него своё основание, и объединять их в один критерий было бы
натяжкой.

## 2. Что есть сейчас — замеры

**Проверки написаны и выключены.** Это главный факт.

| механизм | состояние |
|---|---|
| `E_FIBER_INDIRECT_CALL` (эскейп замыкания через значение) | под `NOVA_FIBER_INDIRECT=1`, **0 фикстур** в корпусе; **включить по умолчанию нельзя** — §10 |
| `--strict-effects` (`E_UNDECLARED_TRANSITIVE_EFFECT`, `E_EFFECT_ERASED_IN_FN_TYPE`) | **выключен**; по умолчанию недекларированный транзитивный эффект — лишь warning (D62 §Правило 1) |

Таблица 15 проб авторов (`docs/plans/wip/PROGRESS-p238-f2.md` §7): **по умолчанию
молчат 11 из 15.** Ловятся только модуль-глобал (это язык: `E_MUT_AT_MODULE_LEVEL`),
канал и прямой захват.

**Покрытие несимметрично, и это контринтуитивно** (мои пробы, каждая с контролем):

| форма | по умолчанию |
|---|---|
| замыкание передано аргументом, один хоп до `spawn` | `E_CONCURRENT_MUT_CAPTURE` |
| то же, два хопа | `E_FIBER_UNSAFE_ARG` |
| `ro g = \|\| { acc += 1 }` и `spawn { g() }` рядом | **ПРИНЯТО** |
| то же с `NOVA_FIBER_INDIRECT=1` | `E_FIBER_INDIRECT_CALL` |

Больше косвенности — ловится; ноль косвенности — молчит. Причина: capture-check
смотрит свободные переменные тела `spawn`, где `g` — обычное `ro` fn-значение, и
внутрь него не заглядывает.

**Форма связывания, невидимая для capture-check** (проба с контролем):

```nova
fn f(mut acc int) -> () { spawn { acc = acc + 1 } }              // E_CONCURRENT_MUT_CAPTURE
ro g = fn(mut acc int) -> () { spawn { acc = acc + 1 } }         // ПРИНЯТО
```

Отличие одно — кто связал имя. Это третий экземпляр класса «форма, вводящая имя,
невидима для capture-check» после `detach` (2026-07-11) и match-паттернов
(2026-07-22), закрытых одним и тем же ходом.

**`#thread_affine` — механизм без потребителя.** Три фикстуры (2 neg + 1 pos), в
`std`/`examples`/пакетах — ноль носителей. Аудит 2026-07-31 по всей extern-поверхности
кандидатов не нашёл. Рантайм-половины нет вовсе: атрибут только отказывает на
компиляции, никто не проверяет, что лист исполнился на нужном потоке.

**Вызов `#thread_affine` вне границы файбера узаконен** pos-фикстурой дословно:
«the whole point is the CROSSING, not the call itself». Но `main` сам файбер
(`nova_fiber_spawn_into(&_nova_main_scope, _nova_main_fiber_entry)`), а инварианта
«главный файбер не исполняется на worker-потоке» в `fibers.h` и 06-concurrency.md
нет. Это был **инвариант на честном слове**, и на нём висела вся thread-affine
история — **закрыт замером и чтением механизма 2026-09-01 (интегратор), см. §12
«Решено»: main-файбер НЕ мигрирует, и не удачей, а тремя звеньями устройства.**

**Мёртвые эффекты.** `Async` — не эффект вовсе (D62: «ambient runtime-инфраструктура»);
единственное вхождение в `.nv` — слово в doc-комментарии. `Par` — ноль вхождений.
Таблица в D26, где они стоят рядом с `Io`/`Db`, описывает историю, а не набор.

**Семейство разрослось до ~45 кодов**, но это не 45 правил, а матрица
«свойство × носитель × граница», у которой каждая клетка получила своё имя *и свою
реализацию*. Отсюда и повторные закрытия одного класса.

## 3. Проброс строки через fn-параметры

**Правило.** Строка в типе fn-параметра — **минимум, а не потолок**. Когда функция
вызывает свой fn-параметр, эффекты фактического аргумента добавляются к её строке.

**Это не новое правило, а уже действующее.** Для лямбд оно работает сегодня —
проверено четырьмя пробами внутри дерева под `--strict-effects`:

| проба | итог |
|---|---|
| лямбда объявлена чистой, тело зовёт `Io`, объемлющая объявляет `Io` | ok |
| та же лямбда, объемлющая **без** `Io` | `E_UNDECLARED_TRANSITIVE_EFFECT` |

То есть написанное на лямбде не потолок; настоящая строка выводится из тела, а
обязательство предъявляется **тому, кто использует**. Предложение распространяет
ровно это на fn-параметры.

**Синтаксиса не появляется.** Ни одна подпись в `std` не меняется:

```nova
export fn measure[T](action fn() -> T) Time -> (T, Duration)
```

читается как «`Time` плюс всё, что принесёт `action`».

**Вывод.** Строка именованной функции = объявленное ∪ эффекты вызываемых ∪ эффекты
фактически переданных fn-аргументов; неподвижная точка по графу. Механика уже
написана трижды (`thread_affine_closure`, suspend-скан, realtime-скан) — новым
является только то, что узел графа теперь «функция с конкретными аргументами в
fn-позициях».

## 4. `forbid` в строке и `[E effects]`

**`forbid` в контракте параметра** — ограничение переезжает из тела в подпись:

```nova
fn sort(cmp fn(T, T) forbid Db Net Io -> bool)
```

Требование видно на месте вызова, проверяется при передаче аргумента, и диагностика
указывает на компаратор, а не в глубину `sort`.

**Полная форма — запятая обязательна**, потому что эффекты перечисляются пробелом
и без разделителя `Io forbid Db` двусмысленно:

```nova
fn () Job Io, forbid Db -> ()
```

Строка становится **парой границ**: снизу — что функция делает, сверху — чего ей
нельзя.

**У формы есть имя в теории** (сверка интегратора 2026-09-02): строка с запретом —
это ряд с флагами отсутствия (rows с presence/absence у Реми; lacks-констрейнты
Гастера–Джонса для рядов записей). В практических языках эффектов такой формы
почти нет — даже у Koka, эталона строк, — так что это публичное отличие Nova, но
стоящее на готовой теории, а не самоделка.

**Переменная строки** — в слоте дженериков, со словом-видом:

```nova
fn run[E effects](f fn() E -> ()) E -> ()          // отдаю ровно то, что принёс f
fn twice[E effects](f fn() E -> (), g fn() E -> ()) E -> ()
```

**Скрывает ли переменная строки эффекты?** (вопрос владельца 2026-09-02.) Нет —
она их **переносит, не называя**, ровно как `[T]` переносит тип: в подписи
`run[E …]` конкретных эффектов и не может быть, они у каждого вызова свои. Не
названы они только в параметрической подписи; в каждой точке использования `E`
инстанцируется конкретной строкой, и вызывающий её видит и несёт как ОБЪЯВЛЕННУЮ
(§12 В2: инстанцирование ≠ транзитивность — обязательство жёсткое, D62-послабление
не применяется). Противоположность — сегодняшний `Handler` Polaris (§4.1): там
строка не отложена, а ПОТЕРЯНА — в типе для неё нет места, и восстановить её на
вызове нечем. Отложить — не скрыть.

**Переменная нужна и в объявлении ТИПА**, а не только функции — см. §4.1:

```nova
export type Handler[E effects] fn(ServerRequest) E -> ServerResponse
```

**`forbid` как bound переменной строки** (форма из обсуждения владельца; короткая
запись без слова-вида — его же, 2026-09-02):

```nova
fn run[E forbid Exclusive Db](f fn() E -> ()) E -> ()
```

Доводы за неё как канон для параметрического случая:

1. ограничение пишется **один раз при объявлении `E`**, а не в каждой позиции,
   где `E` стоит;
2. это канонический дом lacks-констрейнта — в теории ограничение живёт на
   квантификаторе, ровно как `[T Ord]` живёт в скобках;
3. запись `f fn() E, forbid Exclusive` двусмысленна на глаз (чьё это
   ограничение — параметра `f` или переменной `E`?) — bound снимает вопрос;
4. **слово-вид в этой форме не нужно**: `forbid` применим только к эффектам и сам
   называет вид `E`. Проба парсером (интегратор, 2026-09-02): `[E forbid Db]`
   сегодня — чистая синтаксическая ошибка `expected type, got forbid`, место в
   грамматике свободно, существующий код так не пишет — ввод ничего не ломает.
   Бонус против `[E effects …]`: `effects` в bound-позиции парсится как ИМЯ
   протокола (`E_BOUND_UNKNOWN` выше) и его пришлось бы резервировать, а
   `forbid` — уже ключевое слово (D63).

Слово-вид `effects` остаётся обязательным только у переменной **без ограничений**
(`[E effects]`): голую `[E]` отдать нельзя — она уже означает типовую переменную, —
а выводить вид из использования — лишний механизм (норма 253). `nova fmt`
нормализует избыточную запись `[E effects forbid …]` в короткую.

**Канон двух домов:** у ПЕРЕМЕННОЙ строки запрет — bound в скобках; `forbid` внутри
самой строки остаётся для КОНКРЕТНЫХ строк без переменной
(`fn() Job Io, forbid Db`). Примеры §6–§7 — на bound-форме.

### 4.1. Заказчик найден: Polaris

Довод за полиморфизм до сих пор был умозрительным («иначе отравится `map`»). Живой
случай нашёлся в пакете `nova-polaris`, и он сильнее умозрения.

```nova
export type Handler    fn(ServerRequest) -> ServerResponse      // server.nv:535
export type Middleware fn(Handler) -> Handler                   // middleware.nv:93
export fn middleware(f fn(ServerRequest, Handler) -> ServerResponse) -> Middleware
```

**Строки пустые.** Во всём пакете эффект несут ровно **7** fn-типов, и все семь —
один и тот же фиксированный `Net` на websocket-хуке.

То есть центральная абстракция веб-фреймворка объявляет колбэки ЧИСТЫМИ, а реальные
обработчики пользователя делают `Db`, `Fail`, `Io`. Сегодня это компилируется не
потому, что «объявленное — минимум», а потому, что **на границе типа `Handler`
строка стирается**, и стирание никем не проверяется.

Правило «минимум» спасает автора ЛЯМБДЫ — ему не надо ничего писать. Оно не спасает
ТИП: как только лямбда легла в `Handler`, её строка потеряна, потому что в `Handler`
для строки нет места.

**Почему неявного вывода тут мало.** `Handler` — не параметр, вызванный тут же, а
ХРАНИМОЕ значение: оно лежит в таблице роутера и в цепочке middleware, живёт дольше
вызова. По правилу §3 оно оторвалось от места создания — значит строка обязана быть
в типе, предъявлять счёт больше некому.

```nova
export type Handler[E effects]    fn(ServerRequest) E -> ServerResponse
export type Middleware[E effects] fn(Handler[E]) -> Handler[E]

export fn middleware[E effects](
    f fn(ServerRequest, Handler[E]) E -> ServerResponse
) -> Middleware[E]
```

**Цена и где она останавливается.** `Handler[E]` расползётся по роутеру, серверу и
цепочке middleware — известная цена (в Rust так же расползаются `F: Fn`-дженерики).
Но расползание конечно: оно останавливается там, где эффекты ОБРАБАТЫВАЮТСЯ — у
Polaris это `server.run(...)`, точка установки хендлеров. Там `E` фиксируется
набором, который сервер умеет обслужить, и наружу параметричность не уходит.
Переменная строки живёт ровно на отрезке «пользователь написал обработчик → сервер
поставил хендлеры», то есть там, где эффект сегодня теряется молча.

> **Оговорка о методе.** Это чтение исходника, не замер: прогнать Polaris под
> `--strict-effects` не удалось — пакет не резолвит зависимости без локального
> override (47 import-ошибок, `compress`/`tls` не найдены).
>
> **«Один прогон» оказался сложнее — проверено интегратором 2026-09-01, три
> захода:** из репы polaris — те же 47 import-ошибок (override живёт в дереве
> nova и на чужую репу не действует); `nova check <файл флагмана>` — файловая
> резолюция, манифест не участвует (падает на `tls` теми же путями поиска);
> `nova build` каталог не принимает («requires a single .nv file»). То есть
> манифестная резолюция и `--strict-effects` сегодня не встречаются ни в одной
> команде. Замер требует либо `nova test` флагмана под флагом (если раннер его
> пробрасывает — проверить), либо временного размещения кода внутри дерева.
> Записано, чтобы следующий исполнитель не жёг тот же час.

**Слот `[E effects]` сегодня занят другим смыслом — и это шаг работ, а не деталь.**
Проверено пробой: `fn run[E effects](x int) -> int => x` даёт

```
[E_BOUND_UNKNOWN] unknown type `effects` used as generic bound —
not a declared protocol, stdlib alias, or primitive
```

То есть запись уже парсится — как «параметр `E` с bound'ом по имени `effects`», — и
падает в `check_generic_bound_declarations` (`types/mod.rs:27611`). Хорошая новость:
существующий код так не пишет, значит столкновения нет. Но слово `effects` придётся
**зарезервировать в позиции bound** и научить эту проверку исключению. В плане это
отдельный пункт шага 1.

**Отношение к D63 — и у него есть половина, которой у формы в строке нет.** Блок
`forbid X { body }` двухуровневый: compile-time проверка **плюс рантайм** — «при
операции forbid-эффекта runtime ловит и fail'ится, даже если функция была пропущена
compile-time». Эта вторая половина существует именно потому, что транзитивность по D62
дырява (warning, подавляемый).

`forbid` в строке — **чисто статический**. Для маркерного класса этого достаточно **по
построению**: у них строгий транзитивный проброс (§1.1), пропускать нечего. Для класса
возможностей — решето ровно в ту же дыру, что и у D62: `forbid Db` на параметре не
поймает `Db`, пришедший транзитивно и подавленный `#allow_transit`.

*Решение, которое обязано стоять в D-блоке:* `forbid` в строке **гарантирует** только
для маркеров; для возможностей он — контракт документирующей силы, а настоящую защиту
даёт блок D63 с его рантайм-половиной. Либо, вторым вариантом, рантайм-половина
распространяется и на параметр — но это отдельная работа, и её надо назвать, а не
подразумевать.

Канонический дом при этом прежний: строка — контракт на границе, блок — локальная
песочница.

## 5. Два класса эффектов

> **Есть обработчик — эффект расширяет строку неявно. Нет обработчика — только
> явно: объявлением или через `[E effects]`.**

`Io`, `Db`, `Net`, `Fs`, `Fail`, `Time`, `Log` — возможности: вызывающий получает
обязательство, которое видит и может закрыть `with`. Проброс безопасен.

`SameThread`, `Exclusive` — маркеры: обработчика нет и быть не может, единственный
исход — отказ на границе. Неявное расширение сделало бы компилируемость
`spawn { run(g) }` зависимой от факта, невидимого в подписи `run`, — «действие на
расстоянии», запрещённое везде в этом проекте.

**Правило заводится с пустым множеством.** Ни один существующий эффект в жёсткий
класс не попадает (`Async`/`Par` не эффекты вовсе), значит **ни одна существующая
подпись не меняется и ни один существующий вызов не краснеет**. Цена введения — ноль.

**Жёсткий эффект написан ВСЕГДА — исключения для лямбд нет** (решение владельца
2026-09-01; первая редакция заводила исключение сразу после правила). Короткая форма
лямбды запрещена, если в теле возникает жёсткий эффект:

```nova
ro g = || { acc += 1 }               // ошибка: жёсткий эффект не может быть неявным
ro g = fn() Exclusive { acc += 1 }   // так
```

Правило становится однородным: **жёсткий эффект нигде не появляется молча**, и место,
где создаётся опасность, видно в исходнике, а не в hover'е. Цена — автор пишет; она
снимается тем же способом, что и везде: выводит машина, **вписывает** машина
(`nova fmt`), читает человек.

*Форма синтаксически обеспечена уже сегодня* (проба интегратора 2026-09-01):
`ro g = fn() Io { println("x") }` собирается и работает — closure-full с
эффект-строкой в позиции значения парсится, для `Exclusive` новой грамматики
не нужно.

**Прецедент и его цена у донора** (сверка 2026-09-02). Ближайший аналог решения —
Swift strict concurrency: `@Sendable` на замыканиях, пересекающих границу, пишется
явно. Прецедент работает — и его миграционная боль в Swift 6 замерена сообществом
настолько, что Apple выпустила смягчающий режим. Урок не «не делать», а два
условия, оба уже в тексте: fixit + `nova fmt` обязательны с первого дня, и счёт
аннотаций на живом коде (`std`, пакеты) снимается ДО фиксации правила — он всё
равно нужен для В2 и В3 (§12).

> **Оба условия — НОВАЯ работа, не существующая машинерия** (проверено
> 2026-09-02): подкоманды `fmt` у CLI нет вовсе, `nova lint` печатает
> предупреждения и автофиксов не имеет. Каждое «вписывает машина» в этом
> документе — обязательство шага 3 (§10), а не ссылка на готовое.

## 6. Два новых эффекта

> **Читать первым, и в D-блоке это обязано стоять первым абзацем, а не сноской.**
> Оба эффекта существуют по одной причине — их предмет **невидим в типах** (захват
> замыкания, per-thread-слот) — и распространяются по одному закону: **эффект едет с
> тем, к чему привязан его предмет.** Привязан к ЗНАЧЕНИЮ (захват алиасит бокс) —
> лежит в типе значения и по вызовам не поднимается: `Exclusive` уезжает вместе с
> замыканием, куда бы его ни положили. Привязан к ИСПОЛНЕНИЮ (на каком потоке
> бежим) — поднимается по вызовам: `SameThread` доставляется к границе `spawn`,
> где только и решается, кто где бежит. Проверка законом: `#os_thread` ГАСИТ
> `SameThread` (обработчик места исполнения, §8), а `#share`/`#same_thread` на
> типах — вовсе не эффекты, их предмет в типе видим. (Переформулировка
> интегратора 2026-09-02; прежде здесь стояло «разная механика — исключение,
> объявленное заранее». Механика не менялась — исключение стало следствием.)
> Основание для половины про `Exclusive` — факт, а не память автора: **вложенные
> именованные `fn` в языке не парсятся** (проба: `fn inner()` внутри тела даёт
> `expected (, got identifier`; независимо перепроверено координатором), значит
> именованная функция не может ЗАВЕСТИ `Exclusive` сама.
>
> **Но получить — может, и это уточнение владельца 2026-09-01.** Именованная функция,
> принявшая `Exclusive`-значение параметром и вызвавшая его, ограничение наследует —
> иначе `run(g)` из §7 был бы дырой. Наследует **условно**: она несёт `Exclusive`
> тогда и только тогда, когда его несёт её аргумент. Безусловная запись отравила бы
> `map`, `filter` и `measure` навсегда. Условность и выражается переменной строки
> `[E effects]` (§4), а исключается контрактом `forbid Exclusive` — то есть весь
> полиморфизм §3–§4 вырос именно из этого вопроса.

### `SameThread` — «зови меня всегда с одного и того же потока ОС»

Смысл не «пока выполняюсь, останусь на потоке» (внутри одного вызова файбер и так
не переезжает), а **между вызовами**: состояние листа живёт на потоке, который
позвал первым (TLS, нереэнтерабельный хэндл, контекст библиотеки).

**Поднимается по вызовам**, потому что обёртка наследует ограничение целиком: если
`gl_draw` требует стабильного потока, то и `draw_frame`, которая её зовёт,
непригодна из мигрирующего файбера. Подъём доставляет требование к границе
`spawn`/`detach`, где только и можно судить.

Кандидаты имён: **`SameThread`** (прямее всего), `HomeThread`, `Resident`,
`ThreadAffine` (преемственность со спекой), `Stationary`.

### `Exclusive` — «держу нечто, к чему нужен единоличный доступ»

Ставится на fn-тип **замыкания**, когда захват создаёт **алиас** — то есть у
захваченного состояния больше одного держателя.

**Не ставится**, когда держатель один:

```nova
fn bump() -> fn() -> int {
    mut a int = 0
    return || { a += 1; a }      // строка ПУСТАЯ: после возврата a держит только замыкание
}
```

Это самодостаточный объект с приватным состоянием — увозить его в другой файбер
безопасно (аналог `move`-замыкания в Rust, которое `Send`, если состояние `Send`).

**Ставится**, когда держателей несколько:

```nova
fn caller() {
    mut acc = 0
    ro g = || { acc += 1 }       // g : fn() Exclusive -> ()
    spawn { g() }                // отказ
    println(acc)                 // ← второй держатель
}

fn two() -> (fn() -> int, fn() -> int) {
    mut n = 0
    (|| { n += 1; n }, || n)     // Exclusive: оба держат ОДИН бокс
}
```

Последнее не домысел: в порождённом C два окружения получают один и тот же
`_box_count`, тогда как в теле цикла каждой итерации достаётся своя коробка.

**Нужный факт у компилятора уже есть** — escape-анализ и так решает, уезжает ли
переменная в управляемую кучу, потому что замыкание её пережило.

**Не поднимается по вызовам** — едет **в типе значения**. `caller` чист: алиас
внутренний, увези весь `caller` в другой файбер, и оба держателя уедут вместе.

**Откуда `Exclusive` может взяться у именованной функции — и откуда не может.**

*Не может — сама.* Захватывать ей нечего: вложенные именованные `fn` не парсятся
(проверено пробой), модульных `mut` в языке нет (`E_MUT_AT_MODULE_LEVEL`), а
модульные `const`/`ro` неизменяемы. Спонтанно марка в её строке не появляется.

*Может — получив.* Приняла `Exclusive`-значение параметром и вызвала его — значит
исполнение этого значения происходит там, где исполняется она, и ограничение
наследуется:

```nova
fn run(f fn() -> ()) { spawn { f() } }
run(g)     // g : fn() Exclusive -> ()  — отказ на месте вызова
```

Наследование **условное**: `run` несёт `Exclusive` тогда и только тогда, когда его
несёт аргумент. Безусловная запись `fn run(f fn() -> ()) Exclusive -> ()` отравила бы
`map`, `filter`, `measure` навсегда — они стали бы непригодны внутри `spawn` при любом
колбэке. Условность выражается переменной строки, а исключается bound'ом на ней (§4):

```nova
fn run[E forbid Exclusive](f fn() E -> ()) E -> () {
    spawn { f() }        // законно: Exclusive исключён bound'ом E
}
```

Отсюда и порядок §10: **полиморфизм строки (§3–§4) не украшение, а прямое следствие
этого вопроса.** Без него у наследования нет условной формы, и остаются только два
плохих исхода — потерять эффект или отравить все высшие функции.

Кандидаты имён: **`Exclusive`** (что требуется), `Unshared` (что держится),
`Confined`, `FiberLocal`, `SameFiber`.

### Граница — всё, что уносит исполнение с текущего потока или файбера

`spawn`, `parallel for`, `detach` **и `#os_thread`** (решение владельца 2026-09-01).
Правило единое, без разбора случаев.

Причина для `#os_thread` другая, и её стоит записать точно (довод уточнён ревизией
интегратора: прежний — «cross-fiber-stack доступ» — не применяется к mut-захватам,
они боксируются в managed-кучу, шаг 1 алгоритма ниже, а вызывающий при `#os_thread`
паркуется, так что одновременности с ним действительно нет). Настоящий довод —
**видимость памяти**: тело исполняется на другом потоке ОС, и чтение/запись
не-atomic бокса с чужого потока без синхронизации — неопределённые видимость и
порядок, опасные и БЕЗ одновременности. Довод не зависит от того, где живёт бокс, и
потому переживает любые перестановки размещения.

### Алгоритм простановки `Exclusive`

Правило одной фразой: **марка ставится, если у захваченного состояния больше одного
держателя.**

Для каждого захвата `x`:

1. **Копия или ссылка.** `ro`-примитив копируется в окружение — алиаса нет, марки нет
   никогда. `mut`-примитив (боксируется) и объект (managed-reference) идут дальше.
2. **Сколько держателей у `x` после создания замыкания:** само замыкание (всегда);
   кадр-определитель, если трогает `x` после создания; другое замыкание того же кадра
   с тем же `x`; место, куда кадр сам положил `x` (поле, контейнер).
3. **Больше одного — `Exclusive`.** Ровно один (только замыкание) — чисто.
4. **Консервативный откат:** не удалось установить (тип из деструктуризации, доступ за
   ветвлением) — **требовать явной записи**: ошибка «не могу доказать единственность
   держателя — допишите `Exclusive` либо перестройте», с machine-applicable fixit.
   Недолов опаснее ложняка — направление то же, что у D415 («не выводим, значит
   флагуем»), — но МОЛЧА ставить марку нельзя: §5 (решение владельца) требует, чтобы
   жёсткий эффект нигде не появлялся неявно, и откат — не исключение. Цена отката
   при этом меняется с нулевой на «одна строка по fixit» — см. пересмотр позиции
   MVP ниже.

**Почему `bump()` чист** (код — в начале раздела): кадр умирает на `return` и
больше `a` не трогает; второго замыкания нет; никуда `a` не положено — держатель
один. Форма важная: так строятся счётчики, итераторы, генераторы.

**Уточнение владельца: правило грубое, его надо уточнить по потоку управления.**
Шаг 2 спрашивает «трогает ли кадр `x` после создания», не спрашивая, **может ли доступ
пересечься по времени**. Точный критерий:

> держателем считается кадр, который трогает `x` в области, где ребёнок МОЖЕТ БЕЖАТЬ —
> то есть между `spawn` и join'ом объемлющего scope.

Тогда перестают считаться: доступ ДО `spawn` (ребёнка ещё нет) и доступ ПОСЛЕ закрытия
`supervised` (ребёнок сжат).

**Но в разобранном примере грубость ни при чём — гонка там настоящая:**

```nova
supervised {
    spawn { g() }        // ребёнок ЗАПУЩЕН и бежит
    println(acc)         // родитель читает ЗДЕСЬ ЖЕ
}                        // join только тут
```

`spawn` — не `await`: ребёнок исполняется параллельно с родителем до конца объемлющего
`supervised`. «После» в тексте программы не означает «после» во времени.

**Позиция для MVP пересмотрена вслед за §5 (согласование интегратора 2026-09-01):
грубого правила по-прежнему достаточно, но довод «цена ложной марки нулевая» больше
не работает.** Он был верен для модели молчаливого вывода: марка тихо лежит в типе и
мешает только на границе. Решение §5 «жёсткий эффект написан всегда» делает ложную
марку **немедленной ошибкой** на законном коде — компилятор требует дописать
`Exclusive` там, где алиас есть, но по времени не пересекается. Цена не нулевая, а
«одна строка по fixit» — приемлемо для MVP, потому что явная марка на таком коде не
враньё (алиас существует, просто не гоняется), а документированная правда. Но у
грубости появился видимый счёт — и делать ли уточнение по потоку управления вообще,
теперь открытый вопрос **В3 (§12)**: донор говорит против, а лекарства для законного
кода уже в языке.

*Живой пример для В3:* «создал замыкание, отдал в `spawn`, дальше читаю переменную
ПОСЛЕ `supervised`» — законный код, который грубое правило пометит. Сегодняшние
лекарства: честная явная марка (алиас правда есть), `@share`-копия, `spawn consume`.

### Оговорка: без шага 1 марка теряется в любом контейнере

`Exclusive` живёт в fn-типе. Значит **любой пользовательский тип, хранящий колбэк,
стирает её ровно так же, как Polaris стирает эффекты хендлеров:**

```nova
type Callbacks { f fn() -> () }        // марка потеряна при укладке в поле
ro cb = Callbacks { f: g }             // g была fn() Exclusive -> ()
spawn { cb.f() }                       // молчит
```

Контейнеры колбэков есть не только в Polaris — это обычная форма (реестр обработчиков,
таблица роутов, список подписчиков, очередь задач). Поэтому **`Exclusive` сам по себе
дыряв ровно там же, где `Handler`**, и лечится тем же шагом 1: параметр строки в
объявлении типа (`type Callbacks[E effects] { f fn() E -> () }`).

Порядок работ (§10) это чинит — полиморфизм идёт первым, — но риск назван здесь жирно,
чтобы шаг 3 не выглядел самодостаточным.

### `Exclusive` — это не возвращённый `Mut[T]`

Возражение предвидено ревизией интегратора и обязано стоять в D-блоке заранее: D62
Правило 5 сняло `Mut[T]` из стандартного набора, и ревьюер скажет «вы вернули его под
другим именем». Не вернули, и вот чем это доказывается.

**Что такое был `Mut[T]`** (`04-effects.md:2933`) — обобщённый эффект «я меняю
состояние типа T»: мутация как таковая, вынесенная в строку и параметризованная тем,
что мутируется. Снят с доводом: локальные `mut` — без эффекта; глобальное изменяемое
состояние — **специализированными** эффектами с именами и операциями (`Counter`,
`Cache`, `IdGen`); атомики и мьютексы — **типами-значениями, не эффектами**. Принцип
Правила 5 дословно: «каждый раз когда возникает соблазн „нужен `Mut[T]`", есть лучшая
альтернатива: **дать состоянию имя**».

**Пять различий:**

| | `Mut[T]` (снят) | `Exclusive` |
|---|---|---|
| предмет | **действие**: функция мутирует | **факт о форме значения**: замыкание держит алиас |
| операции | подразумевались (читать/писать ячейку) | нет вовсе — это метка |
| обработчик | был бы: ячейку выдают | невозможен: нельзя выдать эксклюзивность двум файберам |
| параметр | по типу мутируемого — отсюда обобщённость, за которую и сняли | без параметра: важен факт алиасности, не «что» |
| кто носит | обычные функции с обычной мутацией — шум повсюду | только замыкания с алиасом, и мешает только на границе |

**И главное — он не спорит с Правилом 5, а достраивает его.** Совет «дай состоянию
имя» работает, пока имя **есть**: глобальный счётчик становится эффектом `Counter`,
разделяемая ячейка — типом `Atomic`/`Mutex` с `#share`. Ровно это предложение и делает:
сторона значений целиком отдана типам, новых эффектов там не заводится (§«Отношение к
`#share`» ниже).

Но у **захватов замыкания имени нет и быть не может** — они не видны в типе
`fn() -> ()`, и у каждого замыкания свой набор. Назвать их специализированным эффектом
нельзя в принципе.

> **Правило 5 запретило обобщённый эффект ВМЕСТО имени. `Exclusive` живёт там, где
> имени не существует.**

### Отношение к `#share`

`#share` не заменяется и не поглощается. Он отвечает на вопрос о **значении**
(«можно ли меня алиасить из другого файбера»), композиция по полям бесплатна,
обход графа не нужен. Эффект нужен только потому, что **захваты не видны в типе** —
он вытаскивает факт наружу и везёт его вместе со значением.

`#share` становится **источником вывода**: компилятор смотрит захват, спрашивает у
типа «ты share?», и если нет — ставит `Exclusive`.

## 7. Что это ловит

```nova
mut acc = 0
ro g = || { acc = acc + 1 }               // отказ УЖЕ ЗДЕСЬ (§5): жёсткий эффект
                                          // не может быть неявным — допишите его
ro g = fn() Exclusive { acc = acc + 1 }   // явная форма; марка в типе g
spawn { g() }                             // и граница отказывает по типу
```

Сегодня это молчит по умолчанию. В эффектной форме первый отказ происходит **ещё
раньше границы — на самой записи лямбды** (следствие §5, и это усиление: опасное
место названо в момент создания, а не в момент пересечения). Дописанная марка
физически лежит в типе `g` и едет с ним через переменную, поле, `Vec`, `Option`,
возврат, каррирование — то есть закрывает молчащие пробы **классом**, а не одну форму
за раз.

> **Это обещание, а не результат.** «Закрывает 11 из 15» — заявка, и приёмкой шага 3
> обязан быть **прогон всех 15 проб таблицы** `PROGRESS-p238-f2.md` §7, а не
> рассуждение. И заявка верна **только после шага 1**: без полиморфизма типов марка
> теряется в любом контейнере колбэков (§6, «Оговорка»).

Передача в чужую функцию становится обычной несовместимостью типов:

```nova
fn run(f fn() -> ()) { spawn { f() } }
run(g)                           // отказ ЗДЕСЬ, с g в руках
```

Условная форма — `run[E forbid Exclusive]` — показана в §6; `forbid`
оказался **тем самым bound'ом**, которого не хватало, и его не пришлось изобретать
отдельно (§4).

## 8. `SameThread` откладывается; чем закрывается тема TLS

> **Изменение против первой редакции.** Раздел назывался «чего не хватает: закреплённый
> файбер» и предлагал `pinned`. После замеров рекомендация другая: **`SameThread`
> отложить целиком**, а §8 читать как описание того, при каком условии он вернётся.

### Почему отложить

Все замеры против введения сейчас:

- у `#thread_affine` **ноль носителей** в `std`, примерах и пакетах;
- аудит 2026-07-31 по всей extern-поверхности `std` + `tls` + `compress` кандидатов
  **не нашёл**;
- рантайм-половины не существует — никто не проверяет, что лист исполнился на нужном
  потоке;
- выдать требование нечем: примитива закрепления в языке нет.

То есть эффект решал бы задачу, которой никто не ставил, — ровно то, про что норма 253
говорит «инвариантов как можно меньше». **Отложить его не потеря, а выигрыш:** вся
машинерия (§3–§5) строится так, что новый член семейства стоит почти ноль, а §8 и
вопрос про миграцию главного файбера уходят с критического пути. `#thread_affine`
остаётся как есть; уборка §9 по нему откладывается вместе с ним.

### Но отсрочка верна только для ОРАКУЛА — у `novac`/Vela носитель известен заранее

Уточнение владельца 2026-09-01. Первый настоящий носитель `SameThread` — не
FFI-библиотека, а **собственный рантайм Nova**: `active_scope`, `active_slot`,
`current_loop`, то есть ровно те переменные, что сегодня в C объявлены через
`__thread`.

Под M:N per-thread переменная опасна не гонкой, а хуже: файбер пишет её на потоке A,
мигрирует, читает на потоке B — и видит **другую копию**. Тихо неверное значение.
Значит всякая функция, которая её трогает, обязана нести `SameThread`, а `spawn` —
отказывать.

**В 274.1 это уже заложено — и как ДВЕРЬ, а не как объявление переменной.** Карта §2б,
строка «атомики и TLS — одна дверь», донор Go `runtime/internal/atomic`; стражи
`check-novac-atomics-door.py` и `check-novac-no-global-state.py` уже стоят. Причина
формы техническая, а не вкусовая: план 274 фиксирует, что **TCC не поддерживает TLS
вовсе** (второй блокер 220), поэтому доступ идёт через предсобранные функции-аксессоры
в dev и inline в release. Объявление переменной синтаксисом языка обязало бы кодоген
эмитить TLS на обоих бэкендах, а dev-бэкенд этого не умеет.

**Как это устроено у донора.** Go **не даёт** пользователю ни TLS, ни
goroutine-local — сознательно: горутины мигрируют, и «переменная потока» на уровне
языка была бы ловушкой. Сам рантайм при этом per-thread состоянием пользуется вовсю,
но добирается до него **через текущую горутину**: `getg()` — интринсик компилятора
(на amd64 с register ABI `g` живёт в выделенном регистре, до того — через сегментный
регистр), а состояние потока читается как `getg().m`. То есть дверь возвращает
контекст **исполнения**, а идентичность потока выводится из него.

Это и есть главный урок для нас: **дверь безопасна, а объявление — нет.** Через дверь
значение всегда свежее — вы спрашиваете «где я сейчас». Объявленная per-thread
переменная позволяет держать устаревшую копию, и после миграции она молча врёт.
Всё, что действительно должно стоять на одном потоке, Go закрепляет явно —
`runtime.LockOSThread()`.

**Вывод для порядка работ:** отсрочка `SameThread` остаётся верной для оракула и
перестаёт быть верной для трека `novac`/Vela. Там эффект нужен к тому же этапу, на
котором закладывается дверь TLS, — по 274.1 «СРАЗУ, чтобы Э6 лёг без переделки».

### Форма: две разные — на типе и на переменной

**Форм две, и это разные свойства** (уточнение владельца 2026-09-01; первая редакция
свела их в одну и ошибочно заключила, что формы объявления переменной не нужно):

- **`#same_thread` на ТИПЕ** — «значение привязано к потоку, который его создал». Про
  GL-контекст: его кладут в локаль, передают, хранят в записи — привязанность едет со
  значением. Ложится в один ряд с `#share`: memberwise-вывод, композиция бесплатна,
  запись с привязанным полем привязана сама.
- **`#per_thread` на ПЕРЕМЕННОЙ** — «у этого хранилища по копии на поток». Про
  `active_scope`: сам `FiberQueue` ничем не привязан, привязан **слот**. Это и есть то,
  что нужно Vela, и `#share` этого не покрывает (разбор — в
  [2026-09-01-module-mut-three-cases.md](2026-09-01-module-mut-three-cases.md)).

Оба дают один эффект `SameThread` у функции, которая их трогает, но по разным
причинам: у типа — «ты обязан быть на моём потоке», у переменной — «ты обязан не
переехать между обращениями».

Имя: `#thread_local` вводит в заблуждение («по копии на поток»), нужно «привязан к
своему потоку». Раз эффект зовётся `SameThread`, атрибут просится `#same_thread` —
источник и следствие одним корнем.

**Полярность двух атрибутов разная, и это надо сказать в D-блоке прямо:**

| | что значит | опасно, когда |
|---|---|---|
| `#share` | «меня можно алиасить из другого файбера» | **отсутствует** |
| `#same_thread` | «я привязан к своему потоку» | **присутствует** |

Первый — разрешение, второй — ограничение.

### Как гарантируется «владелец + канал»

Не дисциплиной, а **линейностью плюс эффектом**, и эти два не дублируют друг друга:

- **`consume` (линейность)** отвечает за **владение и жизненный цикл**: отдать можно
  только явным move (`spawn consume`), после чего у отдавшего значения нет
  (`E_CONSUMED_AFTER_USE`), а молчаливый захват в другое замыкание ловит
  `E_LINEAR_CAPTURE_IN_FIBER` (43 файла корпуса);
- **`#same_thread` на типе** отвечает за **поток**: всякая функция, трогающая такое
  значение, получает `SameThread`, и граница её не пропускает.

Вместе паттерн перестаёт быть уговором: послать сообщение владельцу — **единственная
форма, которая проходит проверку**, потому что хэндла у остальных просто нет.

Правило для авторов биндингов формулируется одной строкой и проверяемо: **ресурс,
привязанный к потоку, объявляется типом с `#same_thread`; если у него есть уничтожение
— ещё и линейным.**

*Чего это не гарантирует:* внутреннего состояния самой C-библиотеки, если до неё есть
второй путь мимо вашего типа. Язык отвечает за владение тем, что видит.

### Две линии защиты, и полагаться надо на вторую

«Добавить в язык и не дать пользователю» строго невозможно — это политика, а не
невыразимость. У Go граница проведена по пакету: `getg()` доступен `runtime` и
недоступен вам, потому что это интринсик компилятора, а не конструкция языка. У Nova
такая категория уже есть и записана — `docs/dev/module-conventions.md` §Применимость:
«**Только std / собственный рантайм Nova**: `extern "nova" fn` …; third-party код в
рантайм не добавляет». Дверь TLS ложится туда же.

Но это **вторая** линия. Первая — эффект: функция, трогающая привязанное значение,
несёт `SameThread`, и `spawn` её не пропустит. Даже если дверь однажды утечёт в
прикладной код, опасность останется пойманной **типом**, а не запретом.

| защита | от чего |
|---|---|
| привилегия (только std/рантайм) | от того, что дверь попадёт в чужие руки без нужды |
| эффект `SameThread` | от того, что ею воспользуются неверно, чьи бы руки ни были |

Привилегия держится на дисциплине и гейте — том самом «честном слове», которое проект
везде заменяет механизмом. Эффект держится на типе.

### `#os_thread` не НЕСЁТ `SameThread`, а ГАСИТ его

Полярность важна. `SameThread` — требование к вызывающему («зови меня всегда с одного
потока»). `#os_thread` от вызывающего не требует ничего: ему всё равно, кто позвал, он
уводит исполнение на свой поток. Значит внутри его тела требование **удовлетворено**, а
наружу не всплывает — поглощено, как эффект поглощается обработчиком.

Это же структурно подтверждает, почему `#os_thread` — атрибут, а не эффект: он ведёт
себя как обработчик, а обработчик членом строки не бывает.

**Но гасит он только на один вызов, если поток берётся из пула:** `setup()` попадёт на
воркер №3, `frame()` — на №7, и контекста там нет. Отсюда развилка дизайна, не
синтаксическая: **пул или выделенный постоянный поток.** Во втором случае гашение
работает и между вызовами, и `#os_thread` становится языковой формой паттерна
«владелец + канал». Цена — постоянный поток на каждый такой ресурс.

### Модульное изменяемое состояние — выделено в отдельное предложение

Тема сцеплена с M:N только носителем (Vela): глобальное состояние рантайма требует
модульного `mut`, которого в языке нет, а мутаторы атомиков объявлены с
`mut`-приёмником (59 подписей в `std/src/runtime/sync.nv`) — через `ro`-биндинг их
не позвать. **Сегодня Vela-на-Nova написать нельзя.** Разбор и предлагаемое правило
(«на модуле `mut` только у типа с `#share` либо под `#per_thread`») — в
[2026-09-01-module-mut-three-cases.md](2026-09-01-module-mut-three-cases.md):
это самостоятельное языковое предложение со своим будущим D-амендментом (нужное
множество типов уже определено D415 §1, mut-alias-safe). Для этого документа важно
одно: `#per_thread`-случай — третий ряд той таблицы, и его безопасность держится
на `SameThread`.

### Дверь возвращает ФИБЕРНОЕ, потоковое перечитывается

Первая редакция ставила здесь развилку «дверь против переменной с новым правилом про
удержание через точку приостановки». **Развилка снимается** разбором того, как это
устроено у донора (вопрос владельца 2026-09-01: «что возвращает `getg()` и что мешает
сохранить его в переменную?»).

**Ничего не мешает — и не должно.** `getg()` возвращает `*g`, указатель на **текущую
горутину**, а не на поток; поток достаётся уже через неё: `getg().m`. В рантайме Go
`gp := getg()` пишут постоянно, и это безопасно, потому что `g` — **это ты сам**:
горутина под тобой не меняется, мигрировала она на другой `m` или нет.

Небезопасно держать `gp.m` и `gp.m.p` — вот они меняются. Рантайм обращается с ними так:
где нужен текущий `m` — **перечитывают**, а не кэшируют; где он обязан не смениться —
`acquirem()` поднимает `m.locks` и запрещает вытеснение, потом `releasem()`; где нужен
настоящий поток ОС надолго — `LockOSThread`. Для пользователя вопрос не встаёт вовсе:
`getg()` — интринсик, доступный только пакету `runtime`.

**Отсюда правило для нашей двери, и оно снимает нужду в новом:**

> Дверь возвращает **сущность файбера**, а не потока. Тогда прочитанное можно держать
> через точку приостановки — оно едет вместе с файбером.

```nova
ro q = current_scope()   // это МОЙ scope — он едет со мной
some_suspending_call()   // файбер уехал на другой поток
q.push(...)              // верно: scope тот же, потому что файбер тот же
```

И это не натяжка на наш случай: `_nova_active_scope` **по смыслу и есть состояние
файбера**, просто лежащее в TLS ради скорости — в нём хранится scope того файбера,
который сейчас исполняется на этом потоке. Дверь `current_scope()` возвращала бы
фиберную сущность, кэшированную потоково, то есть ровно форму `getg()`.

**Опасным остаётся только то, что действительно принадлежит потоку** — `current_loop()`,
идентификатор воркера. Их правило простое и не новое: **не кэшировать, спрашивать
заново**, как Go перечитывает `getg().m`.

*Рекомендация:* **дверь, возвращающая фиберное**. Она уже выбрана планом (274.1 §2б,
донор Go), нового правила не требует, и вопрос «а если удержат копию» снимается по
построению — держать своё безопасно. Имя `current_scope()` в этом документе —
кандидат, не решение (вопрос владельца 2026-09-02: не длинно ли): дверь внутренняя
(std/рантайм, наружу не экспортируется), так что краткость безвредна — `scope()`
свободно (греп по `std` — ноль коллизий) и следует духу донора: внутренний `getg()`
у Go тоже не называется `get_current_goroutine()`. Финализировать при реализации
двери. Форма объявления `#per_thread` остаётся про
хранилища, которые действительно потоковые, и её опасность локализуется теми же двумя
именами: цикл и номер воркера.

**Дверь не заменяет два атрибута — трое закрывают три разных случая** (вопрос
владельца 2026-09-02: «если есть `current_scope()`, что с `#per_thread`,
`#same_thread`?»). Порядок вопросов автора:

1. *Состояние по смыслу фиберное и лежит в TLS лишь ради скорости?*
   (`active_scope`) — **дверь**: атрибуты не нужны, прочитанное едет с файбером.
2. *Значение привязано к потоку создания чужим кодом?* (GL-контекст, FFI-хэндл) —
   **`#same_thread` на типе**: дверь бессильна, привязку создала не наша машинерия,
   и она едет со значением.
3. *Слот честно потоковый — по копии на поток, фиберной сущности за ним нет?*
   (`current_loop`, номер воркера; собственные слоты Vela-рантайма) —
   **`#per_thread` на переменной** и правило «не кэшировать». Таких слотов
   горстка, и почти все — у автора рантайма: Vela на Nova сама рантайм, ей эта
   форма и нужна.

**Бутстрап: в оракул для компиляции Велы НЕ должно заезжать ничего** (вопрос
владельца 2026-09-02: «`#per_thread` должен заехать в Оракул, чтобы скомпилировать
Велу?»). Цепочка: Велу на первом обороте компилирует оракул (она часть Карины), но
план 274.1 §2 уже выбрал форму, которая это развязывает: «атомики и TLS — одна
дверь… весь код — рантайм и будущая Vela-на-Nova — ходит только через него». То
есть на этапе бутстрапа слоты живут в C-части рантайма, а Nova-код Велы зовёт
extern-функции двери — `extern "C" fn` оракул умеет давно, новых форм ноль. Три
варианта по нарастанию цены: **(1) ничего в оракул** — Вела на дверях, как уже
заложено (рекомендация: согласуется с остаточным принципом); (2) минимальный
`#per_thread` в оракуле — парсинг плюс кодоген через те же аксессоры, БЕЗ эффекта
`SameThread` — только если Вела захочет чистый Nova-вид слотов раньше самохоста;
(3) полный, с эффектом — это уже сама Карина, в оракул не просится вовсе. Синтаксис
`#per_thread` в этом документе — фича КАРИНЫ: появляется, когда Вела переписывает
слоты на чистый Nova и когда есть кому проверять `SameThread`.

**Слот и дверь — слои, а не конкуренты** (вопрос владельца 2026-09-02: «Велу
делаем на `#per_thread` или на `current_scope()`?» — ответ: на обоих, для разных
этажей). Слот планировщика Vela (её `active_scope`) **объявляется** `#per_thread` —
это форма ХРАНЕНИЯ; прямое обращение к слоту даёт `SameThread`, и таких обращений
единицы, все внутри планировщика. `current_scope()` — форма ДОСТУПА **поверх**
слота: единственная функция, читающая его, отдаёт наружу фиберную сущность, и
потому вызывающий эффекта не несёт — держать своё безопасно. Ровно устройство
`getg()` у Go: TLS-слот внутри, безопасная дверь наружу. И это не отменяет запрета
глобальных `mut`: сегодня запрещены все; вынесенное предложение
([2026-09-01-module-mut-three-cases.md](2026-09-01-module-mut-three-cases.md))
открывает ровно два вида — `#share`-тип и `#per_thread`-слот, третьего нет.

Дверь закрывает самый частый случай — и именно потому, что она есть, оба атрибута
сжимаются до редких и осмысленных.

### Тема TLS не решена — и решается паттерном, а не языком

Что есть: отказ на ОДНОЙ границе (`#thread_affine` внутри `spawn`, две neg-фикстуры).

Чего нет: положительной стороны — «как в Nova законно работать с ресурсом, привязанным
к потоку»; способа дать стабильный поток; проверки во время работы. И главное:
требование звучит «один поток ОТ ВЫЗОВА К ВЫЗОВУ», а закрепление файбера даёт
стабильность лишь в пределах его жизни — создали контекст в одном файбере, пользуетесь
из другого, не помогает ничто.

**Рабочий ответ сегодня — владелец-файбер плюс канал:** один файбер владеет ресурсом и
получает запросы сообщениями, остальные его не трогают. Выразимо прямо сейчас, ничего
добавлять не надо; так же поступают в Go (`LockOSThread` плюс горутина-цикл).

### В какой форме `SameThread` вернётся

Не через `pinned`, а через **`#os_thread` с телом на Nova** (идея владельца
2026-09-01). Сегодня `#blocking` уводит тело на libuv-worker **вне файберной
машинерии**: приостановка внутри бессмысленна, вложенный `spawn` — вопрос без ответа.
Если вместо этого на выделенном потоке заводить обычный Nova-контекст тем же кодом, что
и `main` (`nova_scope_init` + `nova_fiber_spawn_into` + `nova_supervised_run`), то:

- тело получает всё — эффекты, `spawn`, приостановку, отмену;
- «запустить Nova-контекст на потоке» становится **одной дверью** с двумя вызывающими:
  старт программы и `#os_thread`;
- и такой поток держит свой scope на своём потоке всё время вызова — то есть **дом для
  `SameThread` находится сам, без нового примитива**.

Три вопроса к этой форме: цена (scope плюс файбер со стеком 4 МБ на вызов — нужен пул
либо только для Nova-тел), наследование дедлайна и cancel-токена, и не крадут ли
файберы из этого scope (иначе смысла нет).

**Донор формы возврата** (сверка 2026-09-02): ближайший живой дизайн — глобальные
актёры Swift (`@MainActor`): функция статически привязана к исполнителю, привязка
пропагируется по вызовам, компилятор проверяет её и вставляет переходы. Наш
«`#os_thread` с Nova-телом» структурно и есть actor executor — выделенный поток с
собственным контекстом исполнения. При возврате темы изучить их isolation-правила
(`nonisolated`, наследование изоляции замыканиями) — там уже прожиты углы, которые
нам предстоят. И контраст с другого края: Rust такого эффекта не имеет, и
`thread_local` × async — его известный класс багов. То есть `SameThread` — не
велосипед, а закрытие дыры, которую один донор терпит, а второй закрыл актёрами.

### Разведка рантайма — вынесена в приложение

Разбор «чего стоит `#os_thread` с Nova-телом» по чтению `nova_rt` — в
[2026-09-01-mn-runtime-recon.md](2026-09-01-mn-runtime-recon.md). Итог в три
строки: per-thread машинерия уже есть (`_nova_active_scope` и соседи, N циклов
рантайм уже держит); ветвлений по виду потока почти нет; настоящая точка отказа —
сентинел `home_worker_id < 0 → nova_runtime_signal_main()` (`driver.c:512, 533,
607`): спящий файбер host-потока не проснётся никогда. **Кандидат в реестр при
принятии плана** — при старте работ заводится строкой 221.1 со ссылкой на файл
разведки; там же оценён объём замены сентинела на адрес пробуждения.

## 9. Что исчезает

| было | стало |
|---|---|
| `#thread_affine` + `thread_affine_closure` + своя диагностика | эффект `SameThread` в подписи extern'а |
| `#blocking` (называет симптом, означает решение) | директива **`#os_thread`** — «дайте мне отдельный поток ОС» |
| `E_FIBER_INDIRECT_CALL` как отдельный механизм под флагом | частный случай несовместимости fn-типов |
| `E_EFFECT_ERASED_IN_FN_TYPE` как источник ложняков | можно включать: стирания нет, есть проброс |
| `#realtime`, `nogc` со своими обходами | атрибуты-запреты: чтение строки + запрос про аллокацию |

`#blocking`/`#os_thread` **остаётся атрибутом**, а не эффектом, по критерию из §5 в
его втором прочтении: свойство **поглощается на границе** — рантайм уводит именно
этот вызов, вызывающий только ждёт. Наверх идёт не «нужен поток ОС», а более слабое
«здесь файбер может встать», и для этого механика уже есть.

Аллокация эффектом **не становится**: она повсеместна, и вызывающему безразлична.
Правило: **эффект оправдан, когда он редкий и вызывающему важно про него знать.**
Для `#realtime`/`nogc` это запрос по требованию, а не строка, которую все носят.

### 9.1. Что НЕ исчезает — семейство `E_CONCURRENT_*`

Формулировка §1 «исчезают…» читается страшнее, чем есть. **Исчезают обходы, а не
имена.**

На границе остаётся ОДНА проверка — прочитать строку. Но ПРИЧИНУ попадания марки в
строку чекер помнит рядом и по ней выбирает сообщение:

| причина | сообщение |
|---|---|
| захвачен `mut` из внешней области | `E_CONCURRENT_MUT_CAPTURE` |
| захвачено `consume`-значение без move | `E_LINEAR_CAPTURE_IN_FIBER` |
| то же в handler-литерале | `E_HANDLER_MUT_CAPTURE_IN_FIBER` |
| сырой указатель (ядовитая база D415 §1) | `E_POINTER_CROSS_FIBER` |
| лист с `SameThread` | `E_THREAD_AFFINE_IN_FIBER` |

Это прямое следствие правила, выведенного при разборе матрицы: **диагностик должно
быть много — пользователю нужен точный код на его случай; сокращать надо проверки.**

**Все существующие фикстуры остаются валидными** — только на первые три кода их
39 + 43 + 11. Они пинуют ПОВЕДЕНИЕ («на такой форме компилятор отказывает»), а не
устройство проверки, и потому переживают переделку. Более того, они и есть её
приёмка: позеленевшая фикстура означает, что переход сломал поведение.

**Исчезают ровно три вещи, и все три — механизмы:**

1. собственный транзитивный подъём `#thread_affine` (`thread_affine_closure`);
2. `E_FIBER_INDIRECT_CALL` как отдельный проход под флагом — становится обычной
   несовместимостью fn-типов;
3. `E_EFFECT_ERASED_IN_FN_TYPE` как источник ложняков — после полиморфизма он
   краснеет только на настоящей потере.

`E_SHARE_INVALID_KIND` схемы не касается вовсе: он про то, на каком виде типа можно
писать `#share`, а не про границу.

## 10. Порядок работ

Порядок обязателен: новые эффекты без полиморфизма не переживут первой встречи с
`map`. Трек — Carina (решение владельца 2026-09-02): работы планируются в русле 274;
оракул получает из списка только то, что попадёт по остаточному принципу.

1. **Проброс строки через fn-параметры** (§3) + `[E effects]` + `forbid` в строке
   (§4). Без этого всё остальное бессмысленно.
2. **Два класса эффектов** (§5) — правило с пустым множеством, цена ноль.
3. **`Exclusive`** (§6) — закрывает 11 молчащих проб; после него включается
   `E_EFFECT_ERASED_IN_FN_TYPE`. Сюда же — машинная сторона §5: fixit и
   вписыватель марок (`nova fmt` сегодня не существует, `nova lint` автофиксов
   не имеет — проверено 2026-09-02); без них цена явной записи ложится на руки.
4. **`SameThread` — ОТЛОЖЕН** (§8). Вводить, когда появится первый носитель;
   форма возврата — `#os_thread` с телом на Nova, а не `pinned`. До тех пор
   `#thread_affine` остаётся как есть.
5. **Уборка** (§9) — атрибуты, флаги, дублирующие обходы; часть по
   `#thread_affine` откладывается вместе с пунктом 4.

**Почему `E_EFFECT_ERASED_IN_FN_TYPE` нельзя включить раньше шага 1.** Polaris
покраснеет на каждом хендлере: его `Handler` объявлен чистым, а в него кладут
эффектные замыкания (§4.1). Это, вероятно, и есть настоящая причина, по которой флаг
до сих пор выключен, — не недоделка, а отсутствие полиморфизма.

**Включить `NOVA_FIBER_INDIRECT` по умолчанию НЕЛЬЗЯ — опровергнуто замером**
(координатор, реестр №866; первая редакция этого документа рекомендовала обратное).
Под флагом отвергается четырёхстрочный hello-world со `spawn { println(…) }`:
`println` — external fn, «nothing to prove from». Флаг не «строгий режим с долей
ложняков» — он исполняет правило «не доказано ⇒ небезопасно», а вне компиляционной
единицы недоказуемо ВСЁ.

**И это довод ЗА предложение, а не против.** Флаг структурно невключаем, потому что
доказательство ищется обходом графа, который упирается в границу единицы трансляции.
Строка эффектов границы не знает: она едет В ТИПЕ и пересекает пакеты вместе с
подписью. То есть путь через эффекты — не «красивее», а единственный, который
доводится до включённого состояния.

## 11. Границы гарантии

Исключаются **гонки за данные**: написать программу, где два файбера трогают одно
несинхронизированное изменяемое значение, нельзя — либо тип синхронизирован внутри
(`#share`), либо владение уехало (`consume`), либо компилятор отказал.

Не исключаются **логические гонки** (два порядка событий, оба безопасны по памяти,
один неверен по смыслу) и **взаимные блокировки**. Здесь Nova будет наравне с Rust,
и статикой это не закрывается ни у кого.

Ограничение касается **только пересечения границы**. Внутри одного файбера
изменяемое состояние и замыкания над ним работают как прежде; состояние, созданное
внутри `spawn`, свободно — оно не захвачено.

## 12. Вопросы: решённые и открытые (адресат, умолчание, срок)

### Решено владельцем 2026-09-01

1. **Имена.** `SameThread` — привязка к потоку ОС; **`Exclusive`** — замыкание держит
   состояние, к которому нужен единоличный доступ. Вариант `SameFiber` отброшен:
   `Exclusive` называет ТРЕБОВАНИЕ, а не место, и потому не прячет два из трёх
   лекарств (обернуть в `#share`-тип, отдать через `consume`).
2. **Канонический дом `forbid`.** В **строке** — контракт на границе («не смей
   приносить мне `Db`»), проверяется при передаче аргумента. **Блоком** (D63) —
   локальная песочница, ограничение автора на самого себя.
3. **Цена параметризации `Handler[E]`** — принята. Расползание по роутеру и цепочке
   middleware реально и останавливается на `server.run`; альтернатива — молчаливое
   стирание эффектов пользователя.
4. ~~**Порог ложняков для `NOVA_FIBER_INDIRECT`**~~ — закрыт замером координатора
   (реестр №866): включать нельзя ни при каком пороге. См. §10.
5. **D-блоки и спека** — пишутся при написании плана, отдельным вопросом не стоят.

### Решено замером интегратора 2026-09-01

**В1. Главный файбер НЕ мигрирует между потоками ОС — и не удачей, а механизмом.**
Рекомендация «проверить до плана» исполнена в тот же день, обе половины.

*Эмпирика:* проба с `extern "C" fn GetCurrentThreadId()` и печатью в четырёх точках —
старт `main`, после `sleep` (точка приостановки), после `supervised { spawn {…} }`,
после второго `supervised` — id потока стабилен **5/5 прогонов** при `NOVA_MAXPROCS=4`.

*Механизм — три звена, каждое проверено чтением:*

1. `dispatch_ready` у main-scope равен `NULL` — колбэк ставится только воркерам
   (`runtime.c:2063`), значит воркерский путь доставки main-файбер в чужую очередь
   не кладёт (`nova_sched.h:443`: «Single-thread: dispatch_ready == NULL — main loop
   resume'ит fiber сам»);
2. воркерская кража обходит **только** `_workers[i].runq` (`runtime.c:1440-1444`) —
   очередь main-насоса не в этом массиве;
3. пробуждение main-файбера жёстко адресовано в main-насос: `home_worker_id < 0 →
   nova_runtime_signal_main()` (`driver.c:512, 533, 607`).

*Щель проверена отдельно:* воркеры полят глобальную очередь (post-steal re-poll), но
оба `put` в `_nova_global_runq` (`runtime.c:1132, 1381`) исполняются только из
воркерского контекста — main-путь глобальную очередь лишь читает, свой файбер туда
не кладёт.

*Следствия:* обоснование pos-фикстуры `handler_thread_affine_pos.nv` («вне границы =
на стабильном потоке») — **истинно** и подлежит записи инвариантом: комментарий у
global-re-poll и у main-насоса плюс строка в 06-concurrency.md — задача на полчаса,
и до неё инвариант держится устройством, а не словом. Реестровая №867 закрывается
этим же замером. Объём §8 определён: примитив закрепления для оракула не нужен,
достаточно записанного инварианта.

*Граница честности:* это верно при ТЕКУЩЕМ устройстве; будущий рефактор, который
научит main-путь класть в глобальную очередь или заведёт host-потокам собственные
крадомые очереди, вскроет инвариант молча — потому запись комментарием у обеих
дверей обязательна, а не декоративна.

### Открыто

**В2. Что означает ненаписанная строка у fn-параметра** — владелец; **надо
исследовать**, решение определяет объём шага 1.

- **Вариант А — «пусто значит пусто» везде.** Единообразно; но все высшие функции
  `std` переписываются явно: `measure[E effects, T](action fn() E -> T) Time E -> …`.
- **Вариант Б — у параметра ненаписанная строка это свежая переменная.** `std` не
  меняется ни на символ; цена — одна запись `fn() -> ()` значит разное в позиции
  параметра и в объявлении переменной.

*Рекомендация:* **Б**, потому что чистоту всё равно можно потребовать явно —
bound'ом `forbid` (§4), то есть двусмысленность снимается записью, а не
переписыванием библиотеки. **И Б — канон доноров** (сверка 2026-09-02): у Koka,
эталона строк эффектов, ненаписанная строка fn-параметра означает ровно свежую
переменную; вариант А не выбрал ни один язык этого семейства.

**И одно следствие Б, которое обязано быть проговорено, иначе он молча спорит с
§1.1** (замечание интегратора): при Б возможности (`Io`, `Db`) поедут через все
высшие функции как инстанцированный дженерик — а инстанцированная переменная это
**объявленная** строка, не транзитивный вывод, и D62-warning к ней не применяется.
Это не противоречие §1.1 («для возможностей всё как в D62»), но только если сказать
явно: **инстанцирование ≠ транзитивность** — обязательство через `[E effects]`
предъявляется как часть подписи, жёстко, обоим классам одинаково; D62-послабление
остаётся ровно для НЕ-параметрических вызовов. Без этого абзаца читатель §1.1 и
читатель В2-Б увидят два разных правила для `Io`.

*Что исследовать перед решением:* сколько в `std` и пакетах fn-параметров, которым
чистота нужна ПО СУЩЕСТВУ (компараторы, предикаты, всё, что зовут под замком) — если
их мало, Б дешевле; если много, разница между А и Б стирается, и А честнее. **Плюс
второй счёт, добавленный следствием выше:** сколько существующих вызовов высших
функций получат при Б новые жёсткие обязательства (вызывающий `measure` с
`Io`-лямбдой обязан объявить `Io` уже не warning'ом) — это и есть настоящая цена Б.

*Первый счёт снят (интегратор, 2026-09-02, греп-эвристика по подписям):* высших
функций — **95** (std — 81, polaris — 14; http/tls/socks/compress/bignum — 0).
Объём переписывания при А конечен и назван; второй счёт — сколько ВЫЗОВОВ получат
жёсткие обязательства при Б — грепом не берётся, он требует резолва и остаётся
на шаг исследования.

**В3. Делать ли уточнение `Exclusive` по потоку управления** — владелец;
**умолчание: НЕ делаем**, пока замер не покажет, что ложняки того стоят. Уточнение
(§6: считать держателем только доступ, который может пересечься по времени с
ребёнком) снимает ложные марки на законном коде — но донор говорит, что жить можно
без него: Rust за 15 лет ни разу не сделал flow-sensitive анализ `Send`; «алиас
есть, но по времени не пересекается» там лечится явной формой (`move`), а не умным
чекером. Все три лекарства у Nova уже в языке: `spawn consume x { }` /
`detach consume x { }` (D415 §4), `@share`-копия, честная явная марка (§5 требует
её в любом случае). *Замер перед решением совмещается с В2* — та же прогулка по
`std` и пакетам, второй счётчик: сколько лямбд получат ложный `Exclusive` по
грубому правилу. Мало — уточнение не строим вовсе (минус целый анализ в чекере,
норма 253); много — оно возвращается первым кандидатом после MVP (точка join
известна синтаксически).

**Счёт снят (интегратор, 2026-09-02) — умолчание подтверждено.** Греп-эвристика по
`std` + шести пакетам (лямбда, присваивающая внешнему `mut`; самопроверка на
образцах §6 — 4/4, ложные `||`-операторы и with-блоки отсеяны глазами):
настоящих замыканий с алиасным mut-захватом — **21**. Из них:

- **12 чисты по грубому правилу** (держатель один): 10 степперов `vec_lazy`
  (`{ step: || { i += 1 … } }` — возвращаемая запись, кадр умер — форма `bump()`)
  и 2 генератора `stream_body` в polaris. Марки нет, писать нечего.
- **4 — ложняки грубого правила, все в тестах** (`retry_test`: счётчик в лямбде +
  `assert` после синхронного `execute`): пересечения по времени нет, уточнение
  сняло бы все 4. Цена без уточнения — 4 явные марки в тестовом коде, по строке
  fixit каждая.
- **5 — марка ПО ДЕЛУ, все в polaris** (счётчики в HTTP-хендлерах: `next_id += 1`
  в POST, `captured = Some(req)` в пробе): хендлер лежит в роутере и бежит в
  файбере сервера, кадр читает после — настоящий M:N-класс, ради которого
  `Exclusive` и заводится. Сегодня этот код молчит.
