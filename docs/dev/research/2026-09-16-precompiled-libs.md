# Прекомпилированные библиотеки: можно ли собрать `.nv` в lib и не перекомпилировать

**Статус:** исследование под вопрос владельца 2026-09-16: «насколько формат lib расширяем — можно
ли компилировать `.nv` в библиотеку, где функции без дженериков уже содержат код, а дженерики
инстанцируются в конечном приложении; какие варианты».

**Вердикт (решение владельца 2026-09-17, §9, уточнён §10 замером): `nlib` = сериализованный
проверенный MIR пакета + отпечаток компилятора; поверх него — кэш объектных файлов по модулям
(§10). Замер (проверен владельцем «проверь», 2026-09-17): из 6 с dev-сборки ~3 с — захват
`vcvars64.bat` на каждый запуск (снимает демон плана 219, opt-in), ~1,7 с — clang (из них 0,7 с —
разбор заголовков рантайма, 0,5 с — линковка, ~0,1 с — сам сгенерированный код при `-O0`), ~0,5–1 с —
Nova-часть. Объектный кэш выигрывает в release (`-O3`: 2,8 с компиляции) и на больших программах;
в dev главный рычаг — демон по умолчанию и precompiled header рантайма.** Дорогая Nova-часть (разбор, резолв, типы, эффекты,
контракты/SMT, понижение) делается один раз на пакет; кодоген остаётся целопрограммным, как сегодня,
поэтому §7–§8 (заголовки, дедуп инстансов, `type_id`) теряют предмет и оставлены как история
отвергнутого варианта. Единственное требование к Карине — сериализуемый MIR с устойчивыми
межпакетными ссылками (формат плана 274.8). Раскладка C по модулям и кэш объектников — отдельная
оптимизация драйвера, не часть формата.

Следствие: сегодня «lib» = исходники + кэш `.c` целой программы. Ничего модульного переиспользовать нельзя, потому что единица кодогена — вся программа.

## 2. Что именно хочется

Пакет `P` собран один раз. Приложение `A` импортирует `P` и:
- **не перекомпилирует** конкретные функции `P` (без тип-параметров) — берёт готовый объектный код;
- **инстанцирует** дженерики `P` под свои типы у себя;
- если `P` сам где-то инстанцировал `Vec[int]`, а `A` тоже — код один, не два.

Это ровно модель C++ (`.a` + заголовки с шаблонами), Rust (`rlib` = объекты + MIR дженериков), OCaml (`.cmxa` + `.cmx`), Swift (`.swiftmodule` с `@inlinable`-телами), Haskell (`.a` + `.hi` с unfoldings).

## 3. Варианты

| № | модель | донор | что даёт | цена | вердикт |
|---|---|---|---|---|---|
| 0 | статус-кво: целая программа + кэш `.c` | сегодня | просто, детерминизм, мега-CU-гейт | любое изменение входа = полная пересборка; чужой пакет компилируется у каждого потребителя | остаётся оракулу |
| 1 | **код по модулям + интерфейс с телами дженериков + все инстансы в финальном CU приложения** | rustc `rlib`+MIR (без share-generics), OCaml `.cmx` | конкретный код собирается один раз; дженерики zero-cost как сейчас; дубли инстансов невозможны по построению — печатает их только CU приложения, дедуп у драйвера до `.c` | нужны: (а) модульная единица кодогена вместо `resolve_imports_inline`; (б) формат интерфейса — сериализованный проверенный MIR дженериков + таблицы типов/протоколов/эффектов/контрактов; (в) устойчивые между сборками `DeclId`; (г) все «глобальные по CU» таблицы (теги сумм, typeinfo, схемы) — детерминированы по DeclId, не по порядку CU | **целевая** |

## 4. Что придётся решить для варианта 1 (по убыванию цены)

1. **Единица кодогена = модуль, не программа.** Сегодняшнее слияние в один `Module` даёт
   глобальную нумерацию всего (`@fresh_uniq`, теги, typeinfo). Каждое такое место — либо
   детерминированный ключ от `DeclId`/`TyId`, либо ленивая эмиссия в CU потребителя с weak-дедупом.
   Носители, где это уже болит: №136/№962 (варианты по голому имени на весь CU), №309
   (манглинг режима параметра). То есть требование «одно правило — одна дверь по DeclId» из
   Карины и есть предусловие раздельной компиляции.
2. **Интерфейс библиотеки.** Не исходник и не `.c`, а **проверенный MIR** (план 274.8) экспортных
   деклараций: сигнатуры с эффектами (вывод эффектов кросс-модульный — сигнатуры должны быть в
   интерфейсе явно, `novac-architecture.md:801`), контракты и результаты их доказательства
   (элизия bounds по контракту — Plan 140.2 — иначе потребитель не знает, что элидировать), тела
   дженериков и `#inline`-кандидатов, `#coerce`-пары (D429 R8: пара активна там, где видна),
   `#cfg`-раскладка. Формат версионируется отпечатком компилятора: несовпадение = пересборка из
   исходников, не ошибка.
3. **Дедуп инстансов — до `.c`, у драйвера** (поправка 2026-09-17, §7): библиотека не печатает
   инстансы вовсе, только ссылается на их символы; определения печатает финальный CU приложения по
   объединённому набору `Instance { def, args }` со всех библиотек (манглинг уже детерминирован у
   Карины). Weak/COMDAT-символы — не нужны; оптимизация «библиотека отдаёт свои инстансы»
   (`share-generics`) — потом, по бенчмарку сборки.
4. **Формат контейнера — `nlib`:** архив из `.c` по модулям + файл интерфейса (MIR) + манифест с
   отпечатком компилятора; лежит в `target/`, не в папке модуля. Не `.a`/`.o`: кэш сознательно не
   включает C-тулчейн в ключ, `.c` переносим между машинами, объектники — кэш второго уровня.
   Пакетный резолвер по тегу продолжает тянуть исходники; `nlib` — кэш рядом, не замена.
5. **Инстанцирование по представлению (вариант 2)** — после 1: только для дженериков, не
   вызывающих bound-методы (контейнеры: `Vec[T]`, `IndexVec[I, T]`, `Option[T]`); правило
   «представление = (size, align, GC-карта, consume)» в спеку; bound-вызовы оставляют инстанс
   по типу.

## 5. Чего не делаем

- Словари/стирание (вариант 3) — против D122 и D277.
- Стабильный бинарный ABI между версиями компилятора — интерфейс привязан к отпечатку
  компилятора; пересборка из исходников — норма.
- Раздельная компиляция в оракуле — это архитектура Карины (план 274), у оракула остаётся
  кэш целой программы.

## 6. Рекомендация

Модель 1 как цель Карины, модель 2 как её продолжение для контейнеров. **Заложить сейчас — одно:
устойчивое между сборками тождество декларации** (`DeclId` из пути пакет → модуль → элемент, не из
порядка разбора); остальное добавляется без переделки. Записать в
`novac-architecture.md` как требование к драйверу и коллектору (сейчас там «cross-crate
инстанцирования нет» констатацией, не решением); открыть план после 274.8, потому что интерфейс
библиотеки — это сериализованный MIR, и без него формат lib определять нечем. До этого
дешёвое улучшение оракулу — не нужно: кэш `.c` целой программы уже покрывает «не перекомпилировать
при неизменных входах», а модульный кэш без раздельной компиляции невозможен (шапка
`build_cache.rs` это и говорит).

## 7. Уточнения по вопросам владельца 2026-09-17

**rlib и `nlib`.** `rlib` — формат Rust, но устроен как обычный `ar`-архив: объектные файлы `.o` +
`lib.rmeta` (сигнатуры экспортов, таблицы типов, MIR дженериков и `#[inline]`, отпечаток
компилятора SVH — не совпал, крейт пересобирается). Берём идеи: метаданные в том же контейнере;
тела только у дженериков и инлайн-кандидатов; привязка к отпечатку компилятора без обещаний
совместимости. Формат — свой (`nlib`), метаданные — наш MIR. **Место — `target/`, не папка
модуля**: `nlib` — производный артефакт, как `target/.nova-cache/<key>.c`; в исходниках пакета
только `.nv`, иначе пакет по тегу привозит чужой бинарь.

**D122 / D277 — zero-cost.** D122: вызов по протокольному баунду `fn[T Hash]` разрешается при
компиляции, на каждый конкретный `T` — своя копия с прямым вызовом; vtable только у эффектов.
D277: обобщённая value-запись раскладывается как обычная структура с полями по размеру `T`, без
коробки. Цена дженерика уплачена копиями кода, в рантайме её нет. Словари (Swift, C#) дали бы
раздельную компиляцию дженериков ценой косвенного вызова — спека запрещает.

**`share-generics` (rustc).** Крейт `B` не печатает `Vec<i32>`, если зависимость `A` уже
инстанцировала его, а ссылается на символ `A`. По умолчанию в debug, выключен в release (копия `A`
могла быть собрана с другими оптимизациями). Для нас — не вариант, а следствие наличия в
интерфейсе списка напечатанных инстансов.

**Новое ли требование к Карине.** Да. Сегодня архитектура констатирует «cross-crate
инстанцирования нет». Предусловия уже есть по другим причинам (коллектор по `Instance`,
детерминированный манглинг, MIR 274.8, «одна дверь по `DeclId`»). **Закладывать сейчас — одно:
тождество декларации устойчиво между сборками** — `DeclId` выводится из пути пакет → модуль →
элемент, не из порядка разбора. Остальное (эмиттер по набору инстансов, корни коллектора =
экспорты) добавляется потом без переделки, если тождества стабильны. Записать в
`novac-architecture.md` решением владельца; кода сейчас не требуется.

**Дедуп инстансов — до `.c`, не на линковке (поправка к §4 п.3).** Дубли возникают только потому,
что библиотека собрана раньше и не знает инстансов приложения. Три способа:

| способ | как | цена |
|---|---|---|
| **все инстансы — в финальном CU приложения; в библиотеке только конкретный код** | конкретные функции библиотеки ссылаются на символ инстанса, определение печатает CU приложения | weak-символы не нужны, дедуп делает драйвер до `.c`; каждое приложение печатает все инстансы всех библиотек (как Rust в release) |
| интерфейс перечисляет уже напечатанные инстансы, потребитель пропускает | `share-generics` | только вдоль цепочки зависимостей; сиблинги печатают по копии |
| weak/COMDAT, линковщик оставляет одну копию | C++ шаблоны | покрывает сиблингов; зависит от тулчейна |

**Рекомендация — первый способ.** Совпадает с интуицией владельца, дедуп остаётся у нас до `.c`,
дженерики — ровно та часть, которую спека велит платить копиями. Weak-символы — оптимизация
потом, по бенчмарку сборки.

**`.a` и контейнер.** `.a` — статическая библиотека Unix: `ar`-архив из `.o`, на Windows — `.lib`.
Нам не нужна и неудобна: кэш сознательно не включает C-тулчейн в ключ, а `.o` к тулчейну привязан.
**`nlib` = архив из `.c` по модулям + файл интерфейса (MIR) + манифест с отпечатком компилятора.**
Clang компилирует эти `.c` с тем же хэш-кэшем, что сегодня; объектники — кэш второго уровня рядом.
`nlib` переносим между машинами и тулчейнами; «не перекомпилировать» относится к Nova-части —
самой дорогой.

## 8. Типы в `nlib`: где лежат определения и как дедуплицируются (вопрос владельца 2026-09-17)

**Факты сегодня.** Кодоген не эмитит ни одного своего `.h`: все `typedef struct` (записи `Nova_<X>`,
value-записи `NovaValue_<X>`, инстансы `NovaOpt_<T>`, `NovaRes_<T>_<E>`, фикс-массивы
`_NovaFixArr_…`) печатаются в единственный `.c` (`emit_c.rs:743, :1756, :4473`). Идентификаторы
типов для `any` — `#define NOVA_TID_<mangled> N`, где `N` — **монотонный счётчик от 17 в порядке
обхода CU** (`emit_c.rs:2248-2259, :2934, :3151`). Это ровно «глобальная нумерация по порядку CU»
из §4 п.1: два модуля, собранные порознь, дадут одному типу разные `type_id`.

**Правило C, которое решает половину вопроса.** У типов в C **нет линковки**: определение
`struct` нужно в каждой единице трансляции, которая его использует, и одинаковые определения в
разных `.c` законны. Линковщик типов не видит. Дедуплицировать надо только ВНУТРИ одной единицы
(один `.c` включил два заголовка с одним типом) — это делает include-guard. Значит для типов
никакой «дедупликации на линковке» не существует в принципе; проблема есть только у функций и
объектов с адресом (`NOVA_TYPEINFO_<T>`, vtable эффектов).

**Раскладка `nlib` по модулю `M`:**

| файл | содержимое | кто дедуплицирует |
|---|---|---|
| `M.h` | определения экспортных типов `M` (записи, суммы, value-записи) под guard `NOVA_T_<mangled>`; прототипы экспортных функций; **определения типов инстансов, которые `M` использует** (`Vec[int]` → `typedef struct … NovaVec_nova_int;` под своим guard'ом) — раскладка инстанса вычислима у `M` из определения `Vec` и `int`; прототипы функций инстансов (`extern`) | include-guard, компилятором C, в каждом TU отдельно |
| `M.c` | тела конкретных функций `M`; `#include "M.h"` и `.h` зависимостей | — (одна копия по построению) |
| `interface.mir` | проверенный MIR экспортов: сигнатуры с эффектами, тела дженериков, контракты и их вердикты, `#coerce`-пары, `#cfg`; список типов инстансов, чьи typedef'ы `M.h` уже несёт | драйвер |
| финальный CU приложения (`app_instances.c`) | **определения** функций всех инстансов (объединённый набор `Instance { def, args }` со всех библиотек, §7), **объекты** `NOVA_TYPEINFO_<T>` и vtable — по одному на программу | драйвер до `.c`, по манглированному имени |

Почему typedef инстанса в `M.h`, а функция инстанса — в финальном CU: `M.c` вызывает
`NovaVec_nova_int_push(&v, 3)` по значению и обязан знать раскладку `NovaVec_nova_int` при своей
компиляции; тело `push` ему знать не нужно — достаточно прототипа. Раскладка — чистая функция
от `(def, args)`, поэтому два модуля, независимо напечатавшие typedef `NovaVec_nova_int`, напечатают
его байт-в-байт (условие: детерминированный порядок полей и манглинг — уже требования Карины).

**Что надо поменять, и это конкретно.** `type_id` для `any` перестаёт быть счётчиком: он должен
быть **хэшем устойчивого `DeclId`** (путь пакет → модуль → элемент + аргументы инстанса) — тогда
`NOVA_TID_<mangled>` одинаков во всех TU без сговора, а объект `NOVA_TYPEINFO_<T>` печатается один
раз в финальном CU. Теги вариантов сумм проблемы не создают: они локальны определению типа и
считаются от порядка вариантов в объявлении. Vtable эффектов — как typeinfo: объект с адресом,
один на программу, финальный CU.

**Итого:** типы — в `.h` под include-guard, дедуп компилятором C внутри TU, одинаковые копии между
TU законны; функции инстансов и объекты с адресом — только в финальном CU, дедуп драйвером до
`.c`. Линковщик ничего не дедуплицирует, weak-символы не нужны.

## 9. Решение владельца 2026-09-17: `nlib` = только сериализованный MIR

Вопрос владельца: «если столько возни с C, можем просто писать сериализованный MIR в `nlib`?» — да,
и это лучше варианта 1 из §3.

**Модель.** Пакет один раз проходит Nova-часть до MIR включительно; результат — проверенный MIR
всех деклараций с телами (не только дженериков) — сериализуется в `nlib` с отпечатком компилятора.
Приложение грузит MIR зависимостей вместо исходников и дальше работает как сегодня: одна программа,
один коллектор инстансов, один `.c`, clang. Аналог: rustc держит MIR дженериков в `rlib`; схема
«MIR-only rlibs» (весь кодоген у листового крейта) обсуждалась в Rust как ускорение сборки. У нас
кодоген уже целопрограммный, так что это сохранение архитектуры с кэшем на уровне MIR.

**Что исчезает из §7–§8:**

| было проблемой | почему нет |
|---|---|
| `.h` по модулям, include-guard, копии typedef между TU | C печатается одним процессом с полным обзором, как сегодня |
| `type_id` как хэш `DeclId` вместо счётчика | счётчик остаётся: нумерация детерминирована в пределах одной сборки |
| инстансы только в финальном CU, дедуп до `.c` | все инстансы собирает один коллектор в одной сборке |
| один объект `NOVA_TYPEINFO_<T>`/vtable на программу | то же |
| контейнер с `.c`/`.o`, привязка к платформе и тулчейну | в `nlib` нет C — переносим без оговорок |

**Что остаётся требованием к Карине — одно.** MIR сериализуем, ссылки на декларации между
пакетами устойчивы: `DeclId` = (пакет, индекс внутри пакета), индекс стабилен внутри данного
`nlib`, пакет адресуется именем + версией + хэшем содержимого (модель rustc `DefId = (CrateNum,
DefIndex)` + crate map). Это вопрос формата плана 274.8, не архитектуры кодогена. Жёсткое
требование §7 «`DeclId` стабилен между сборками» смягчается до этого.

**Чем платим.** C для зависимостей печатается и компилируется clang'ом при каждой сборке
приложения — как и сегодня. Лечится не форматом библиотеки, а раскладкой вывода: печатать
целопрограммный C **несколькими `.c` по модулям с одним сгенерированным общим заголовком**,
объектники кэшировать по хэшу файла; clang перекомпилирует только модули с изменившимся C.
Это оптимизация драйвера, независимая от `nlib`. Побочный плюс целопрограммной печати:
межмодульный инлайн и DCE остаются, как сейчас (при раздельных объектах их пришлось бы отдать LTO).

**Что в MIR обязано лежать, чтобы потребитель ничего не пересчитывал:** сигнатуры с выведенными
эффектами; результаты доказательств контрактов (какие bounds/overflow-сайты элидировать — Plan
140.2/140.4); `#coerce`-пары (D429 R8: видимость); `#cfg`-раскладка (либо MIR на конкретный набор
features — тогда `nlib` на набор features, как `.c`-кэш сегодня); тела всех функций (инстансы
дженериков печатает приложение; конкретные функции — тоже, из MIR, это дёшево). Несовпадение
отпечатка компилятора = пересборка из исходников, не ошибка; исходники по тегу остаются источником
истины, `nlib` — кэш рядом в `target/`.

**Границы, которые сохраняются:** словари/стирание — нет (D122/D277); стабильный бинарный ABI — нет;
раздельная компиляция в оракуле — нет.

## 10. Замер 2026-09-17: где время сборки, и что это значит для `.obj` в `nlib`

Владелец: «реальное ускорение дадут прекомпилированные функции в готовом виде — не `.c`, а `.obj`;
не сбрасывать со счетов» — и затем «проверь». Замерено на оракуле, программа из 25 строк (пять
разборов чисел из `std`), Windows, режим по умолчанию (dev, `-O0 -g`), рантайм — prebuilt-архив
(Plan 218), машина под чужой нагрузкой 60–70 % CPU (минимум из трёх прогонов).

**Шаг 1 — грубый срез (кэш `.c` включён/выключен):** холодная сборка 6,0–6,4 с; попадание в кэш
5,5–5,9 с; разница ≈ 0,5 с = вся Nova-часть. Первое прочтение «остальное — clang» оказалось
**неверным**, шаг 2 это вскрыл.

**Шаг 2 — clang отдельно с точной командой nova** (снята обёрткой `--clang <wrapper.cmd>`,
логирующей аргументы):

| что | время | вывод |
|---|---|---|
| компиляция + линковка, как nova (`-O0 -g`) | 1,71 с | а не 5,5 |
| только компиляция `-c` (439 КБ, 7 206 строк, 408 функций) | 0,72 с | |
| только `-fsyntax-only` | 0,76 с | компиляция = разбор |
| TU из одного `#include "nova_rt/nova_rt.h"` | **0,72 с** | **весь `-c` — это заголовки рантайма (nova_rt + libuv + gc); сгенерированный код при `-O0` стоит ~0** |
| только линковка (`.o` → exe) | 0,52 с | |
| `-O3 -DNDEBUG -c` | 2,84 с | ~2,1 с — оптимизация кода; здесь объекты и параллель окупаются |
| `-O3 -flto -c` | 1,81 с | bitcode дешевле, работа уезжает в линковку |

**Шаг 3 — куда делись остальные ~4 с.** `detect_toolchain` (`test_runner.rs`) на Windows на КАЖДЫЙ
процесс `nova build` захватывает окружение `vcvars64.bat` (`capture_vcvars_env`, комментарий в коде:
«~7 s… paid once, not per-test» — per-test да, но не per-build). Замер `cmd /c vcvars64.bat && set`
отдельно: 2,9–4,3 с. Явные `--clang`/`--vcvars` этого не снимают (захват идёт всегда, когда vcvars
найден). Снимает **демон плана 219** (`nova daemon start`; резидентный toolchain-конфиг с
захваченным env; auto-spawn ТОЛЬКО под `NOVA_DAEMON=1`, opt-in):

| конфигурация | попадание в кэш `.c` | кэш выключен |
|---|---|---|
| без демона (по умолчанию) | 4,1–5,9 с | 6,0–6,4 с |
| с демоном | **1,34–1,67 с** | **2,4–2,9 с** |

**Итоговая раскладка dev-сборки 25-строчной программы (без демона ≈ 6 с):** захват vcvars ≈ 3 с;
разбор заголовков рантайма ≈ 0,7 с; линковка ≈ 0,5 с; Nova-часть ≈ 0,5–1 с; компиляция
сгенерированного кода ≈ 0,1 с.

**Что это значит для `.obj` в `nlib`:**

1. **В dev-режиме объектный кэш почти ничего не даёт:** кода там на 0,1 с, а 0,7 с заголовков платит
   КАЖДЫЙ TU — разбивка по модулям без precompiled header сделает хуже, не лучше. Рычаги dev —
   демон по умолчанию (уже есть, opt-in → сделать opt-out) и **PCH рантайма** (`nova_rt.h` + libuv +
   gc один раз на тулчейн; clang `-include-pch`), что срезает ~0,7 с с каждого TU.
2. **В release объекты нужны:** 2,8 с оптимизации на 25 строк пользователя — потому что в C лежит
   весь достижимый `std`; на реальном приложении это десятки секунд, и там неизменившиеся модули
   `std`/зависимостей в кэше объектов — прямой выигрыш плюс параллель по TU (16 ядер на этой машине).
   Требования к раскладке — как в предыдущей редакции этого раздела: текст `.c` модуля не зависит
   от порядка обхода CU (`type_id` — хэш `DeclId`, не счётчик `emit_c.rs:3151`); инстансы дженериков
   и объекты `NOVA_TYPEINFO_<T>`/vtable — в отдельном финальном `.c`; typedef'ы — в общем заголовке
   за сборку. Всё внутри одного процесса, weak-символы не нужны.
3. **Готовые `.obj` внутри `nlib`** — предзаполненный объектный кэш под конкретный отпечаток
   тулчейна; имеет смысл для `std` в поставке release-профиля. Слой 1 (`nlib` = MIR, §9) от этого
   не зависит.

**Рекомендация после проверки.** Порядок по выигрышу на секунду работы: (1) демон плана 219
включить по умолчанию или хотя бы захватывать vcvars-env в файл-кэш по отпечатку VS — минус 3 с
на каждую dev-сборку, ноль архитектуры; (2) PCH рантайма — минус 0,7 с на TU; (3) объектный кэш по
модулям с параллельным clang — для release и больших программ, с предусловиями из п. 2; (4) `nlib`
= MIR — для «не пересобирать Nova-часть зависимостей», ~0,5–1 с здесь, больше на больших пакетах.
Отдельная строка реестра: «`nova build` без демона платит ~3 с за `vcvars64.bat` на каждый запуск»
— как дефект удобства К3/К4, решение владельца о дефолте демона.
