# Автоматическое расширение чисел в смешанных операциях: почему от него отказываются и что в Nova

> Вопрос владельца 2026-09-04: «чем плохо автоматическое расширение типа числа при операциях над
> разными типами? раньше это делали многие компиляторы, теперь все отказываются — почему, и делать
> ли нам, включая, например, `-u8 → i16`?». Ответ спеки уже есть — **D405** (2026-06-30, owner
> sign-off). Проверено, где он держит; пробы: `docs/plans/repro/926-mixed-numeric-doors/`.

## 1. Почему отказываются — простыми словами

Автоматическое расширение кажется удобством: `u8 + u16` само становится `u16`, писать `as` не
надо. Плохо оно тремя вещами, и все три — молчаливые.

1. **Правило выбора результата нельзя удержать в голове.** В C оно называется «usual arithmetic
   conversions» и зависит от платформы: `u8 + u16` даёт `int`, `u32 + i32` даёт `u32`, и
   `-1 < 1u` — **ложь**, потому что `-1` стал `4294967295`. Java выбрала иначе: всё в `int`, всегда
   знаковый, `byte + short → int`, знаковость беззнакового теряется. Два языка, два разных ответа на
   один вопрос — значит ответ не очевиден, и читатель кода его не знает.
2. **Ошибка не видна ни компилятору, ни читателю.** `if (u == s)` выглядит правильно, компилируется
   без предупреждения и врёт. Это самый частый класс числовых ошибок C, и он не про переполнение,
   а про сравнение.
3. **Расширение помогает ровно там, где не нужно.** В `u8 + u16` программист и так знает, чего хочет;
   один `as` ничего не стоит. А там, где расширение опасно — знаковый против беззнакового, целое
   против float, — оно и срабатывает молча.

Поэтому Rust, Go, Zig, Swift требуют явный cast; Kotlin разрешает только расширение и запрещает
сужение, но за это платит правилом Java для беззнаковых. Тенденция одна: **программист выбирает
ширину, компилятор проверяет**.

## 2. Что уже решено в Nova

**D405** (`02-types.md`): `u8 + u16` — `E_MIXED_WIDTH_ARITH`, расширение только явным `as`,
«никакого автоматического „бери больший"». Таблица доноров в блоке — та же, что выше: Rust/Go/Zig/
Swift против Java/Kotlin/C. **D54**: неявных числовых конверсий нет нигде. Проба `ctrl_arith`:
`u8 + i16` → `E_MIXED_WIDTH_ARITH` — держит.

**Ответ на вопрос: делать так же — да, уже сделано. Автоматическое расширение не разрешать,
`-u8 → i16` — нет.** Довод против именно этого примера: результат зависит от того, куда «расширить»
— `i16`? `int`? — и это снова правило, которого читатель не знает. `-(a as i16)` — одна операция и
один явный выбор.

## 3. Где D405 не держит — три двери молчат

D405 перечисляет операторы `+ - * / % >> << & | ^` и говорит про целые операнды. Вне списка —
и вне проверки — три двери; все три собраны и печатают неверное:

| проба | выражение | результат |
|---|---|---|
| `cmp_signedness` | `u32(4294967295) == i32(-1)` | **`true`** — ловушка C, ради которой D405 писали, в сравнении не закрыта |
| `cmp_width` | `i64 < i32` | `true` — молча |
| `int_float` | `i64 + f64` | `6.5` — неявная промоция в float |
| `neg_unsigned` | `-a`, `a u8 = 200` | `56` — заворот по модулю 256 |
| `float_width` | `f32 + f64`, `f32 < f64` | `4 true` — смешение ширин float, молча |

Заведено строкой реестра `№TBD` (К1). Форма та же, что у №904 и №906: правило записано на одной
двери (бинарная целочисленная арифметика), а число проходит через четыре. Фикс — одна дверь
«операнды числового оператора» для всех операторов, не список из девяти.

### Что про float в спеке — ничего

Вопрос владельца 2026-09-04. Проверено грепом по `spec/decisions/*.md` и prelude:

- **Ни одного D-блока про арифметику float.** D405 — только целые («целочисленный тип»,
  `E_MIXED_WIDTH_ARITH`). Правило relational-операндов называет `float` лишь как ordered-категорию.
- **D55 п. 4 (numeric literal coercion) перечисляет цели `u8…u64`, `i8…i64`, `int` — float в списке
  нет.** При этом компилятор принимает `f64 + 1` и `ro x f32 = 1.5` (проба `float_lit_ok`, печатает
  `3.5 1.5`) и отвергает `ro n int = 1.5` (`E7301`). Поведение разумное, но не записанное.
- **Set `Floats`** был упомянут прозой в амендменте D310 («семейство `Ints`/`Floats`»), но не
  существовал ни в prelude, ни в спеке, ни в компиляторе. **Решение владельца 2026-09-04 — завести:**
  `type Floats set f32 | f64` добавлен в `prelude/protocols.nv` рядом с `Ints`, амендмент к D310
  записан; проба `fn[T Floats] T @half()` на `f32`/`f64` — чекер принимает. В `std/math` дублирования
  f32/f64-методов сегодня нет (0 пар), так что set — задел под blanket'ы, не снятие долга.
- **D54** описывает только `as` между float-ширинами (`f64 → f32` — IEEE rounding) и float↔int
  (saturation) — конверсии, не операторы.

Следствие проверено пробой `float_width`: `f32 + f64` и `f32 < f64` — `ok`, собрано, печатает
`4 true`, то есть `f32` молча расширен до `f64`. Это то же «бери больший», только для float, и
спека его ни разрешала, ни запрещала. Амендмент к D405 (§4) закрывает это: одинаковая ширина и
для float.

**Литералы и float — РЕШЕНО владельцем 2026-09-04, амендмент к D55 внесён** (оба «да»). Два случая,
оба сегодня принимаются компилятором, норма теперь записана:

| | сегодня | Rust | Go | рекомендация |
|---|---|---|---|---|
| float-литерал в `f32` (`ro x f32 = 1.5`) | принимается | принимается (литерал полиморфен) | принимается | **записать в D55 п. 4**: float-литерал адаптируется к любому float-типу — прямое продолжение правила для целых |
| int-литерал к float-операнду (`b + 1`, `b f64`) | принимается | **ошибка**, нужно `1.0` | принимается (untyped const) | **записать как разрешённое**: литерал без точки — «число», не «целое», пока у него нет типа; D55 уже трактует литерал как подгоняемый под цель; запрет дал бы `1.0` ради формы, не ради смысла. Донор — Go; принято владельцем |

### Спека или компилятор? — и то, и другое

Вопрос владельца 2026-09-04: «так должно везде работать — что в спеке? проблема только в
компиляторе?». По дверям:

| дверь | что говорит спека | вывод |
|---|---|---|
| сравнение разной знаковости/ширины | D405: правило перечисляет `+ - * / % >> << & \| ^` — сравнения нет; правило relational-операндов (`02-types.md:15226`) требует лишь «mutually-ordered тип (int/float/str/char)», не одинаковый | **спека уже: буква не покрывает**, компилятор исполняет букву |
| `int + float` | D405: «оба операнда … одинаковый **целочисленный** тип» — про float ни слова; прозой «Nova не имеет implicit numeric coercion нигде (D54)» | **спека уже**: принцип есть, норма про целые |
| `f32 + f64` | ничего — про float в спеке нет ни правила операторов, ни литералов | **спека молчала полностью**; амендмент к D405 добавляет одинаковую ширину для float |
| унарный `-x` на unsigned | **D427 R2** прямо: «always-on guard для унарного `-x`, SIGNED-ONLY. Unsigned `-x` НЕ трогается» — спека знала и оставляла сырой C (заворот) | **осознанное неделание спеки**; решение владельца 2026-09-04 — **ошибка компиляции** |

Принцип «никакого автоматического „бери больший“» в спеке есть — как проза D405 и как D54. Норма
уже принципа в трёх местах, и компилятор честно исполняет норму, не принцип. Порядок тот же, что
для D310 и D52: сначала амендмент, потом чекер. **Амендмент к D405 внесён 2026-09-04** (формулировка
категорией, не списком) плюс перекрёстная пометка у D427 R2 — см. §4.

**Решения владельца 2026-09-04:** принцип «никакого автоматического „бери больший“» действует везде;
унарный минус на unsigned — **ошибка компиляции** (Rust), путь `-(a as i16)`. Заворот `-200 → 56`
не нужен никому, кто его не просил явно.

### Расширяют ли другие языки `f32 → f64` автоматически

Вопрос владельца 2026-09-04. По языкам:

| язык | `f32 + f64` | `f64 d = f32` без cast | как устроено |
|---|---|---|---|
| C / C++ | да → `double` | да | usual arithmetic conversions — то же правило, что для `int`, с теми же сюрпризами |
| Java / C# | да → `double` | да | «widening primitive conversion»: float → double всегда неявно |
| Kotlin | да → `Double` в операторе | **нет** в присваивании | не конверсия, а перегрузка: `Float.plus(Double): Double` объявлена в std; `val d: Double = f` — ошибка |
| Zig | да → `f64` | да | «Integer and Float Widening»: coercion к типу, представляющему все значения старого — **и для целых тоже** (`u8` к `u16` расширяется). Таблица D405 записывала Zig в лагерь «compile error → явный cast» — неточно; поправлено 2026-09-04 по решению владельца: Zig в своей строке, доноры — Rust/Go/Swift |
| Go | **нет**, mismatched types | нет | только untyped-константы адаптируются |
| Rust | **нет**, `cannot add f64 to f32` | нет | явный `as f64` |
| Swift | **нет** | нет | явный `Double(f)` |

Счёт тот же, что для целых у D405: старые языки расширяют молча, новые требуют явности, Kotlin и
Zig — посередине. Для float довод за явность даже проще, чем для целых: `f32 + f64` вычисляется
в `f64`, и результат выглядит «точнее», чем есть — у `f32`-операнда всё равно 24 бита мантиссы,
и автор, читая `f64`, этого не видит. Решение владельца «везде одинаковый тип» покрывает float тем
же амендментом к D405 (§4).

## 4. Амендмент к D405 — как записан

Внесён 2026-09-04 в `spec/decisions/02-types.md`, раздел D405, перед «### Связь», без нового номера,
датирован, со ссылкой на решение владельца и пробы. Суть:

1. Операнды **любого** числового оператора — бинарного арифметического, битового, сравнения
   (`== != < <= > >=`), составного присваивания — имеют один и тот же конкретный числовой тип:
   одинаковую ширину и знаковость для целых; целое и float не смешиваются. Список операторов в
   тексте D405 — иллюстрация, не граница правила.
2. Исключение прежнее: литерал без явной ширины адаптируется к типу другого операнда (D55).
3. Унарный минус определён только для знаковых типов; `-x` при беззнаковом `x` — ошибка
   компиляции, диагностика называет путь `-(x as iN)`. D427 R2 получает пометку: «не трогается»
   → «отвергается чекером до кодогена».
4. Реализация: одна дверь сверки операндов для всех числовых операторов; чекер, не Си.

## 5. `as` между числовыми типами: спека, компилятор, другие языки

Вопрос владельца 2026-09-04. Норма — D54 «Семантика narrowing-конверсий» (`03-syntax.md`, таблица) и
`spec/conversions.ru.md` §Numeric ↔ numeric. Проверено пробой (`docs/plans/repro/928-as-int-uint-saturation/`).

### 5.1. Что говорит спека и что делает компилятор

| пара | D54 | компилятор | сходится |
|---|---|---|---|
| `iN → iM`, M < N | wraparound (mod 2^M): `0x1FFFF as i16 == -1` | `-1` | да |
| `iN → uM` | bit-pattern: `-1i32 as u16 == 65535` | `65535`; `(-1 as i8) as u8 == 255`; `(-1 as i64) as u64 == 2^64−1` | да |
| `uN → iM` | bit-pattern / wraparound: `0xFFFFu16 as i16 == -1` | `(2^64−1 as u64) as int == -1`, `as i32 == -1` | да |
| `f → iN` | **saturation** + NaN→0: `70000.5 as i16 == 32767` | `32767`; `1e20 as int == INT64_MAX`; `NaN as int == 0` | да |
| `f → uN` | saturation + neg→0: `-1.0 as u16 == 0` | `0` | да |
| `f64 → f32` | IEEE rounding | — | (не мерил) |
| `iN → f` | exact / nearest IEEE | — | (не мерил) |
| **`int → uint`** | по таблице — bit-pattern; **D130 Q2 отдельно: saturates (neg → 0)** | **`0`**; при этом `(-1 as int) as u64 == 2^64−1` и `(-5 as i32) as uint == 2^64−5` | **нет — спека противоречит себе** |

Всё, кроме одной строки, сходится, и это хорошая спека: defined behavior на любом входе, без UB.
Одна строка — исключение из общей таблицы, введённое D130 для единственной пары `int → uint`
(«Rust bit-cast hostile; Swift trap verbose»), и оно создаёт три ответа на одну операцию: замена
`uint` на `u64` (по D130 alias-пара!) или `int` на `i32` в источнике меняет результат с `0` на
`2^64−1` или `2^64−5`. Заведено строкой реестра `№TBD` (К1), решение — владельца, потому что D130 Q2
его же решение.

### 5.2. Как это устроено в других языках

| язык | int → узкое / знаковое → беззнаковое | float → int вне диапазона | как просят проверку |
|---|---|---|---|
| C | unsigned — wrap (defined); signed — implementation-defined | **UB** | руками |
| Java | усечение битов (wrap) | **saturation**, NaN → 0 | `Math.toIntExact` и т. п. |
| C# | `unchecked` (по умолчанию) — wrap; `checked` — исключение | unchecked — не определено, checked — исключение | контекст `checked` |
| Go | wrap | **implementation-defined** (не UB, но и не задано) | руками |
| **Rust** `as` | wrap / bit-pattern | **saturation** (с 1.45), NaN → 0 | `TryFrom`, `checked_*` |
| Zig | `@intCast` — паника в safe-режимах при потере; wrap только явным `@truncate` | `@intFromFloat` — паника при выходе | сам оператор и есть проверка |
| Swift | `UInt8(x)` — trap; wrap — явный `init(truncatingIfNeeded:)`; насыщение — явный `init(clamping:)` | `Int(x)` — trap | три явных инициализатора |

Два лагеря: «`as` — чистая операция с определённым результатом, проверка отдельным именем» (Rust,
Java, Go) и «конверсия сама проверяет и падает, wrap/clamp — явно» (Zig, Swift). Nova стоит в
первом лагере и повторяет Rust почти дословно: D54 говорит это прямо («saturation для float→int
согласован с Rust 1.45+»), проверка — `@try_to_i8()`…`@try_to_uint()` (D430), `as` — pure.

### 5.3. Хотели ли мы насыщение для всех знаковых → беззнаковых? Что говорит Plan 70.5

Вопрос владельца 2026-09-04. Источник решения — `docs/plans/70.5-uint-primitive-symmetry.md` Q2
(2026-05-19), и он отвечает так:

- **Принцип формулировался общим:** «Nova already has D54 saturation для `float → int`. Apply
  same pattern: out-of-range → boundary value». Rust `i64 as u64` назван «user-hostile surprise,
  often source of bugs», Go — «same pitfall», Swift trap — «safer but verbose».
- **Но решение записано для одной пары**, потому что план был про `uint`: «`int as uint`
  saturates; `int as u64` — direct bit-cast (существующее поведение сохранено)». Для bit-cast план
  предлагал отдельное имя — `(x as i64).bit_cast[u64]()` — «don't make это default», но метод не
  завели.
- D54-таблица «`iN → uM` — bit-pattern» и страницы `conversions.*` («`as` между целочисленными
  ширинами всегда wraparound») остались как были.

То есть да: довод Plan 70.5 относится ко всем знаковым → беззнаковым парам, а норма покрыла одну,
и сегодня у `as` два правила по имени типа. Честных исхода два, и оба лучше нынешнего:

| | (а) везде bit-pattern (снять D130 Q2) | (б) везде насыщение (обобщить D130 Q2) |
|---|---|---|
| правило | одна таблица D54, как есть | `iN → uM`: отрицательное → 0, слишком большое → MAX; сужение `iN → iM`, `uN → uM` — тоже насыщение, иначе снова два правила |
| донор | Rust `as`, Go, Java — все три wrap | у операторов-конверсий донора нет: Swift `clamping:`, Rust `saturating_*` — отдельные имена, не `as` |
| «мне нужны биты» (хэш, FFI, маски) | `x as u64` — как везде | нужен отдельный `@bit_cast[u64]()` (Plan 70.5 его предлагал, не завёл) |
| «мне нужно отсечь отрицательное» | `@try_to_uint()` (D430) или `max(0, x) as uint` — видно в коде | `as` делает это молча |
| что скрывает молча | биты «переехали»: `-1 → 2^64−1` — заметно сразу | `-1000 → 0`, `70000 as u16 → 65535` — правдоподобное число, ошибка живёт дольше |
| согласие с D430 R3 (арифметика трапит на переполнении) | `as` — единственное явно написанное место, где переполнение разрешено; роль Swift `truncatingIfNeeded` | `as` — единственное место, где переполнение молча зажимается; у Swift это `clamping:`, тоже явное имя |
| цена перехода | снять один helper `nova_int_to_uint`, поправить D130 Q2; страницы уже так говорят | переписать таблицу D54, страницы, семантику всех сужений; завести bit-cast |

**Решение владельца 2026-09-04 — (а); амендмент к D130 внесён (Q2 снят), попутно `uint` ≠ `u64` записано явно.** Рекомендация была (а), и не потому, что насыщение плохо само по себе, а потому, что у `as` роль
«я явно попросил переинтерпретацию» — это единственная операция в Nova, где программист
написал имя типа руками; для отсечения есть имена (`@try_to_*`, `max`), для битов имени, кроме
`as`, нет. Если же владелец разделяет тезис Plan 70.5 «Rust bit-cast hostile» как принцип — тогда
(б), но целиком: с bit-cast-методом и с насыщением для всех сужений, иначе через полгода найдётся
третья пара с третьим правилом. Решение — владельца; D130 Q2 — его же решение.

### 5.4. Как надо нам — рекомендация

1. **Оставить лагерь Rust.** `as` pure и infallible, результат определён на любом входе; проверка —
   отдельным именем `@try_to_*`. Это уже норма D54/D430, и она согласуется с «никакого
   автоматического „бери больший"»: `as` — единственное место расширения и сужения, и оно явное.
2. **Снять исключение D130 Q2.** Все `iN → uM` — bit-pattern по таблице D54, включая `int → uint`.
   Доноры — Rust, Go, Java; `uint ≡ u64` перестаёт лгать; тот, кому нужно «отрицательное → 0»,
   пишет `@try_to_uint()` или `max(0, x) as uint` и видит это в коде. Насыщение остаётся только
   у float → int, где у него есть донор и смысл (NaN и бесконечности иначе UB). Это амендмент к
   D130, решение владельца.
3. **Не вводить trap в `as`** (Zig/Swift). У Nova есть контракты и `@try_to_*`; trap в чистой
   операции нарушил бы D54 «`as` pure» и добавил бы вторую дверь для той же проверки.
4. **Одна таблица — одна дверь в компиляторе.** Сегодня для `int → uint` есть отдельный helper
   `nova_int_to_uint` — ровно вторая дверь, из которой и вырос дефект. Требование Карины: семантика
   `as` для числовой пары вычисляется одной функцией от (источник, цель), без частных случаев по
   имени типа.

### 5.5. Итоговая таблица `as` после амендментов 2026-09-04 — и что осталось

| пара | правило | пример |
|---|---|---|
| целое → шире, тот же знак | точно (sign-/zero-extend) | `(-1 as i8) as i64 == -1` |
| `iN → iM`, сужение | wraparound mod 2^M | `0x1FFFF as i16 == -1` |
| `iN → uM`, **любая пара, включая `int → uint`** | bit-pattern | `-1i32 as u16 == 65535`; `(-1 as int) as uint == 2^64−1` |
| `uN → iM` | bit-pattern / wraparound | `0xFFFFu16 as i16 == -1` |
| `int ↔ i64`, `uint ↔ u64` | явный `as`, no-op по битам на 64-бит; **типы разные** | `a as i64 + b` |
| `f → iN`, `f → uN` | насыщение, NaN → 0, ±∞ → границы | `70000.5 as i16 == 32767`, `-1.0 as u16 == 0` |
| `f64 → f32` | IEEE-округление | |
| `iN → f` | точно / ближайшее IEEE | |
| newtype ↔ представление | identity | `42 as UserId` |
| литерал в позиции типа | адаптация без `as`, вне диапазона — `E_LIT_OUT_OF_RANGE` (D55) | `ro a u8 = 300` — ошибка |
| проверка вместо wrap | `@try_to_i8()` … `@try_to_uint()` (D430) | `(300 as u32).try_to_u8()` → `Err(RangeError)` |

Одна таблица, одно правило на семейство, без частных строк по имени типа. **Что осталось после
этого:**

1. **Компилятор отстаёт от спеки в двух местах**, оба в реестре: `int as uint` всё ещё насыщает
   (`nova_int_to_uint`, №928 — снять helper); чекер считает `int ≡ i64` и `uint ≡ u64` (новая
   строка, К2) — сверяет ширину, не тип. Второе — с ценой: в std `i64` 637 раз, `u64` 453, и часть
   мест смешивает их с `int`/`uint`; после фикса они потребуют явных `as`. Довод за фикс до тега,
   не против: после тега менять нельзя.
2. **`uint.MAX` не разбирается парсером** (D130, открытый пункт acceptance) — мелочь, но с
   различением `uint`/`u64` обход через `u64.MAX` перестаёт быть тождеством по типу.
3. **Проверяемой конверсии float → целое нет вовсе, а D54 на неё ссылается.** Проба: `i16.try_from(f)`
   — чекер `ok`, кодоген `E_UNKNOWN_STATIC_METHOD`; D77 ретрагирован 2026-07-06. Заведена строка
   реестра (К3) с амендментом к D54 (мёртвая ссылка помечена) и предложением `fn[S Floats] S
   @try_to_<T>()` — set `Floats` заведён сегодня ровно под это; семантика — решение владельца:
   (а) усечение к нулю + проверка диапазона, `2.5 → Ok(2)`, `70000.5 → Err`, NaN → `Err`
   (рекомендация); (б) «точно представимо», Swift `Int16(exactly:)`, `2.5 → Err`.
4. **По дороге — К1:** set-bound blanket-метода не проверяется при вызове метода:
   `(2.5 as f64).try_to_i16()` собирается и печатает `true`, `"x".try_to_i16()` падает в Си;
   контроль на свободной функции `fn only_ints[T Ints](x T)` — `E_TYPE_NOT_IN_SET`. Тот же класс,
   что №896, зеркально: там конформанс не видел set-blanket, здесь диспатч не видит set-bound.
   Под удар — все ~30 `fn[T Ints]` blanket'ов prelude. Строка реестра, проба
   `docs/plans/repro/930-blanket-bound-unchecked/`.

**Ответы на вопросы владельца 2026-09-04 про `as` и `~` (пробы `_q1`–`_q3`, в дереве не хранятся —
результаты воспроизводимы одной строкой):**

- «wraparound mod 2^M» и «bit-pattern» — одна операция: младшие M бит, прочитанные как целевой
  тип. Так у всех (Rust `as`, Go, Java, C для беззнаковых). Амендмент к D54 объединяет четыре
  целочисленные строки таблицы в одно правило и отражён на страницах `conversions.*`.
- `u64 as u8`, `i32 as u16` — маска руками не нужна: `0x1234 as u8 == 52`, `70000 as u16 == 4464`,
  `-1 as u16 == 65535`, `0x1FFFF as i16 == -1`.
- `~` — сохраняет тип операнда: `~5u8 == 250`, `~5i32 == -6`, `~5int == -6`,
  `~5u64 == 18446744073709551610`; на newtype над целым работает (по D52-амендменту 2026-09-04 —
  результат тот же newtype); на `bool` — `E_UNARY_OPERAND_TYPE` (для отрицания есть `!`). Норма —
  D46, амендмент 2026-07-27: `~x == -(x + 1)` на знаковых.

## 6. Для Карины

Требование то же, что в `2026-09-04-newtype-operators.md` §8, и здесь оно подтверждается третьим
правилом подряд: проверка операндов — **одна дверь** для всех числовых операторов (бинарных,
унарных, сравнения, составных присваиваний), не список операторов в одном месте и другой список в
другом. Список операторов в D405 — описание нормы для читателя, а не форма реализации.
