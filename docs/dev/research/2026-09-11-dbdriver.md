# Драйвер БД для Nova: что уже решено языком и что остаётся драйверу

**Статус:** переписано целиком 2026-09-11. На этом месте лежала СТЕНОГРАММА ЧАТА —
три склеенных ответа на вопрос «как бы вы спроектировали работу с БД в новом языке»,
без единой ссылки на Nova (см. §1). Разбор ниже сделан чтением дерева; каждое
утверждение о дереве несёт файл и строку. Указание владельца на план 279 отработано:
замена механизмов M:N в Карине разобрана в §5.4 по тексту плана, а не по догадке.

## 0. Суть коротко

**Вопрос.** Каким быть слою работы с базами данных в Nova: что взять за образец, где
провести границы, что писать самим.

**Ответ: почти всё, что на этом месте предлагалось «заложить», Nova уже заложила —
но иначе и в другом месте.** Исходный текст рекомендовал повторить `database/sql` из
Go: интерфейс драйвера, пул в интерфейсе, `context.Context` для отмены, типизированный
`scan`. В Nova границей служит не интерфейс, а **эффект**; отмена приходит из
структурной конкурентности; ресурс закрывается линейностью, а не RAII; а
типизированный `scan` в самой границе **невозможен** — и это названный отказ чекера,
а не недосмотр.

| исходный текст требовал | в Nova это | где |
|---|---|---|

| «подмена драйвера для тестов» | `with Db = postgres_handler { … }` — один раз на границе, без моков | `spec/effects.md:84-87` |
| «typed scan: `Row.scan<T>(col)`» | **в операции эффекта невозможно**: generic через слот vtable — `E_EFFECT_OP_GENERIC_UNSUPPORTED` | D456, `04-effects.md:8466+`; реестр №570/№614 |
| «Transaction с явным begin/commit/rollback» | `consume`-тип `Tx` с `@cleanup`, откат по умолчанию, тело вызывающего — ВНЕ границы эффекта | `std/src/data/sql.nv:134-144`; дом — план 268 |
| «пометить FFI, который блокирует OS-поток» | `#blocking fn` — вся fn на libuv-threadpool worker, файбер паркуется (в Карине переименуется в `#os_thread`, атрибутом и остаётся) | D172, `06-concurrency.md:5527-5528`, кодоген `:5689`; план 279 `:70`, `:306` |

| «SQL без инъекций» | tagged template `` sql`…` `` — аргументы не становятся текстом запроса | D48; `std/src/data/sql.nv:120` |

**Главный вывод, которого в исходном тексте не было.** Там сказано: «pure-реализации
протоколов PostgreSQL и MySQL — не nice to have, а **архитектурная необходимость** для
M:N-языка», потому что блокирующий C-вызов съедает OS-поток. Для Nova это **неверно как
необходимость**: в языке есть ровно тот механизм, который текст велит «обязательно
заложить», и он final с мая 2026. Чистая реализация протокола остаётся хорошим выбором
по другим причинам (владение кодом, отсутствие сборочной зависимости, стоимость
дистрибутива) — но это выбор, а не безальтернативность. Разница существенна: из
«необходимости» следует «сначала пишем два бинарных протокола», из «выбора» — «сначала
берём то, что уже работает, и меряем».

## 3. Три слоя — но границы проходят не там

Исходный текст делил систему на «интерфейс драйвера / конкретные драйверы / ORM».
Деление разумное, но для Nova режет не по тем швам: у нас граница проходит по
**подменяемости**, а не по абстрактности.

```
потребитель:  fn report() Db Fail[DbError] -> Report
                    |
      ГРАНИЦА ЭФФЕКТА  — здесь и только здесь подменяется реализация
                    |
  ┌─────────────────┴─────────────────┐
  обработчик real_pg()      обработчик mock_db()
        |                          |
  фасад значений (Tx, Rows, Appender — методы на типах, consume+@cleanup)
        |
  слой extern "C" ffi.nv   ЛИБО   чистый протокол поверх std.net.tcp
```

Что это даёт по сравнению с делением «интерфейс / драйвер»: **тест не подменяет
драйвер — он подменяет обработчик**, и подмена происходит в одной строке `with`, а
не через конструктор, фабрику и контейнер. Именно это `std.net` называет «one
mockable dispatch point» (`std/src/net/effect.nv:4`), и ровно поэтому там рядом
лежат `tcp.nv` (настоящий) и `mock.nv` (подставной) — два обработчика одного эффекта.

## 4. Граница: эффект, а не trait

### 4.1. Что можно — почти всё

D456 формулирует это одной строкой: операция эффекта — обычная функция Nova, у
которой отнят **ровно один** элемент, получатель `@`, «потому что у эффекта нет
инстанса» (`04-effects.md:8469-8471`). Доступны и ожидаются: `Result`/`Option`,
записи и суммы, коллекции и кортежи, параметры-функции, именованные типы вместо
голых чисел, квалификаторы `consume`/`mut` на параметрах (`:8473-8477`).

Значит объявление интерфейса драйвера выглядит так (форма взята из `std`, не
придумана):

```nova
export type Db effect {
    query(q Sql) Fail[DbError] -> []DbRow
    exec(q Sql) Fail[DbError]  -> int
}
```

и потребитель пишет обычный последовательный код:

```nova
fn process(o Order) Db -> Receipt =>
    Db.query(sql`SELECT * FROM orders WHERE id = ${o.id}`)
```

а выбор реализации делается один раз, наверху:

```nova
fn main() Io -> () =>
    with Db = postgres_handler {
        handle_request(o)
    }
```

### 4.2. Чего нельзя — и это названный отказ, а не пробел

Исходный текст требует «typed scanning: `Row.scan<T>(column) -> Result<T>`».
**В границе эффекта такой операции быть не может.** До решения владельца 2026-08-12
обобщение принималось чекером на обеих осях и падало уже в СИ-компиляторе — «худший
из возможных исходов» (`04-effects.md:8479-8482`):

* ось 1, generic на ОПЕРАЦИИ (реестр №570): кодоген выпускает одну стёртую функцию,
  вторая инстанциация не приводится к типу;
* ось 2, generic на САМОМ эффекте (реестр №614): `nova check` зелёный, `nova build`
  падает `unknown type name 'NovaVtable_Store'`.

Обе оси — один класс: rank-2 полиморфизм через слот vtable с ОДНОЙ подписью; точное
правило значится открытым вопросом Q6. Сегодня обе отвергаются **на объявлении**:
`E_EFFECT_OP_GENERIC_UNSUPPORTED` и `E_EFFECT_GENERIC_UNSUPPORTED`.

### 4.3. Следствие, и оно определяет всю архитектуру

Раз обобщение не переходит границу, **типизированный доступ живёт на значениях,
которые границу уже перешли**. Это и есть то, что конвенции модулей называют
«mockable plumbing + type-method facade»: эффект несёт узкий, неподвижный набор
операций; богатый типизированный API — методы на `Rows`, `Row`, `Tx`, `Appender`.

Тот же принцип уже применён в `std.net` по другой причине (ABI границы): адреса не
ходят через vtable возвратом — операция заполняет 20-байтовый `[]u8`, а публичный
метод заворачивает его в `SocketAddr` (`std/src/net/effect.nv:15-18`). Для драйвера
БД это означает: **форму операций эффекта диктует ABI границы, а не удобство**, и
проектировать надо парой «узкая операция + богатый метод на значении».

### 4.4. Два расхождения между демонстрацией в std и нормативной конвенцией

Оба найдены сверкой `std/src/data/sql.nv` с `docs/dev/module-conventions.md`
(помечен «**Нормативно.** Изменения/отклонения — только по согласованию с
владельцем»). **Решать их не задача этого документа** — по правилу старшинства
источников противоречие между уровнями докладывается с обоими местами дословно, а
не разрешается окном. Но драйвер, написанный по образцу `sql.nv`, унаследует оба,
поэтому они здесь.

**Первое: `Fail` в строке операции против `Result` в возврате.**

* конвенция §3: «Все fallible-операции → `Result[T, XError]` (R1, D325); эффект
  `Fail` наружу не отдаём (throw = `!!`, Option = `.ok()`)»
  (`module-conventions.md:97`);
* код в std: `query(q Sql) Fail[DbError] -> []DbRow` и
  `exec(q Sql) Fail[DbError] -> int` (`std/src/data/sql.nv:146-147`) — то есть
  `Fail` стоит именно в строке операции, наружу.

Замечу, что это не мелочь формы: от неё зависит, пишет потребитель `match` по
`Result` или ставит `with Fail[DbError]` на границе (как это делает README
`nova-duckdb`). Два разных стиля вызывающего кода.

**Второе: плоская сумма ошибок против структурной.**

* конвенция §3: «**Один структурный `XError` на домен** …, а не flat sum без
  контекста», с образцом `type IoError value { ro kind ErrorKind, ro raw_os int,
  ro op str, ro path Option[Path], ro source Option[*IoError] }`, где `ErrorKind` —
  **OPEN** сумма с обязательным `Other(int)` (`module-conventions.md:91-95`);
* код в std: `type DbError enum Connection | Constraint(str) | Timeout | Other(str)`
  (`std/src/data/sql.nv:151`) — плоская сумма без контекста: нет ни кода СУБД, ни
  имени операции, ни текста запроса, ни причины-источника.

Для драйвера разница практическая: по `Constraint(str)` нельзя узнать, КАКОЕ
ограничение нарушено, а именно это потребитель и разбирает (дубликат ключа против
внешнего ключа — разные ветки прикладной логики). Структурная форма даёт `kind` для
ветвления и остальные поля для сообщения.

**Оговорка в пользу `sql.nv`, и она честная:** файл сам называет себя эталонной
демонстрацией, а `DbRow` в нём помечен «каркас для demo»
(`std/src/data/sql.nv:8, 156`). То есть он не нарушает конвенцию тайком — он не
заявлял себя production-модулем. Опасность в другом: он ЕДИНСТВЕННЫЙ пример `Db` в
дереве, и следующий драйвер будет написан по нему.

**И расхождение уже воспроизвелось в пакете.** `nova-duckdb` не копировал `DbError`,
но пришёл к той же форме: `DuckError.Type("column ${col} is an INTERVAL carrying
months…")` (`src/duckdb.nv:342`) — имя колонки попадает в ТЕКСТ сообщения, а не в
поле. Разобрать такую ошибку программой нельзя, её можно только показать человеку.
Это ровно то, против чего написан §3 конвенции, и это довод, что расхождение стоит
закрыть до следующего драйвера, а не после.

*Адресат обоих расхождений — владелец; см. §12, вопросы 6 и 7.*

## 5. M:N и FFI — раздел, переписанный по нашему рантайму

Это был главный технический раздел исходного текста, и он ошибался в выводе.

### 5.1. Осей не одна, а две, и их путают

`D172` (final с 2026-05-27) объявляет два РАЗНЫХ атрибута, и спека специально
предупреждает, что это разные оси:

* **`#blocking fn`** — «runtime threadpool offload: вся fn выполняется на libuv
  threadpool worker, fiber паркуется до завершения» (`06-concurrency.md:5527-5528`).
  Кодоген оборачивает вызов в `uv_queue_work` (`:5689`). Это и есть ровно тот
  механизм, который исходный текст велел «обязательно заложить».
* **`#thread_affine extern fn`** — «M:N-небезопасный лист»: маркирует `extern fn`,
  привязанную к ОС-потоку, который её впервые вызвал (thread-local состояние или
  нереэнтерабельный C-side handle). Семантика — «привязан к ОС-потоку», **НЕ
  «медленный»**: «`#blocking` — другая ось» (`:5530-5534`). Поднимается транзитивно
  по именованному графу вызовов; вызов на границе `spawn`/`detach`/`parallel for` —
  `E_THREAD_AFFINE_IN_FIBER` (`:5534-5537`).

Транзитивность — важная часть: функция, зовущая помеченный лист прямо или через
цепочку **в своём файбере**, сама становится thread-affine. То есть правило нельзя
обойти обёрткой.

### 5.2. Что из этого следует для трёх видов драйверов

| вид драйвера | чем помечается | что ловит компилятор |
|---|---|---|
| in-process C-библиотека с хендлом на поток (DuckDB, SQLite) | `#thread_affine` на КАЖДОМ extern | попытку увести соединение в `spawn` |
| сетевая C-библиотека через её АСИНХРОННЫЙ API, шим паркует фибру | ничего не нужно | — (ожидание уходит в libuv, как в `net.c`) |
| сетевая C-библиотека синхронным вызовом | `#blocking` — но см. оговорку ниже | ничего не ловит: переносит ожидание на threadpool |
| чистый протокол на Nova поверх `std.net.tcp` | ничего не нужно | — |

**Оговорка нормативная, и она РАЗНАЯ для std и для пакета — это главное, что здесь
надо не перепутать.**

`docs/dev/module-conventions.md` §4.6 описывает канонический I/O-путь: «блокирующие/
I/O-хуки **паркуют фибру** через libuv … User-API выглядит блокирующим, но не
блокирует OS-поток», образец — `compiler-codegen/nova_rt/net.c` (GC-heap state →
регистрация `stop_cb` → `nova_sched_park()` → колбэк libuv → `nova_sched_wake()` →
resume). И там же: «`Blocking`-эффект (Plan 83.3 / D50) — только для
**CPU-bound-обёрток**, не дефолтный I/O-путь».

Но раздел «Применимость» того же файла (`:19-22`) относит этот путь к **std и
собственному рантайму**, а для стороннего кода говорит обратное: «user/third-party
код в рантайм не добавляет → использует только `extern "C"`», и «**user-FFI обычно
синхронный или через `blocking { }`**, а не своя park/wake».

**Отсюда два разных ответа на один вопрос, и выбор между ними — это выбор МЕСТА
ЖИТЕЛЬСТВА драйвера, а не стиля:**

* драйвер **в std** (или его C-часть в рантайме) — асинхронный API библиотеки плюс
  парковка фибры в шиме; для libpq это `PQsendQuery` и его сокет, ровно то, подо
  что libuv и сделан. `#blocking` тут не место;
* драйвер **пакетом-спутником** (сегодня это `nova-duckdb`, завтра любой сетевой) —
  своей park/wake у него быть не может, значит остаются синхронный `extern "C"` и
  `#blocking`. И тогда цена известна заранее: каждый ожидающий вызов занимает воркер
  threadpool libuv на всё время ожидания.

Первая редакция этого абзаца (написана до чтения раздела «Применимость») ставила
парковку фибры первой для всех случаев — то есть советовала пакету механизм, который
конвенция пакетам не отдаёт. **Это делает вопрос «std или спутник» (§12.5) не
административным, а техническим: от него зависит, каким способом драйвер вообще
имеет право ждать.**

Третий случай бесплатен по ожиданию: операции `std.net`, которые ждут ввода-вывода,
«паркуют вызывающий файбер внутри `real_net` и возобновляются из цикла libuv»
(`std/src/net/effect.nv:20-22`). Никакого `async`, никакой окраски функций: вызывающий
видит обычный синхронный вызов, несущий эффект `Net`.

### 5.3. Значит «чистый протокол» — выбор, а не необходимость

Довод «иначе блокируется OS-поток» снимается `#blocking`. Остаются доводы, которые
исходный текст не назвал, а они и есть настоящие:

* **стоимость дистрибутива и сборки.** Замер по `nova-duckdb`: статическая линковка
  библиотеки добавляет **около 36 МБ** к бинарю на каждой платформе, а холодная
  сборка идёт **40–60 минут на 16 ядрах** (`nova-duckdb/README.ru.md`). Для сетевой
  БД чистый протокол снимает это целиком;
* **владение отказом.** Свой протокол — свои диагностики и своя сумма ошибок; чужая
  библиотека приносит свои коды, которые всё равно придётся переводить в `DbError`;
* **потолок потоков.** Пул M:N-воркеров материализуется на старте процесса (D451,
  `06-concurrency.md:4248`); каждый `#blocking`-вызов занимает воркер threadpool
  libuv на всё время ожидания. Для OLTP-нагрузки с сотнями одновременных запросов
  это упирается в размер пула — и вот здесь чистый протокол выигрывает
  количественно, а не идеологически.

К этому добавляется довод из §5.2: **пакету-спутнику парковка фибры не отдана**, то
есть сетевой драйвер, живущий пакетом, ждёт либо синхронно, либо через `#blocking` —
и в обоих случаях занимает воркер. Чистый протокол поверх `std.net.tcp` этой цены не
платит вовсе, потому что ожиданием там занимается уже существующий `Net`. Для
OLTP-нагрузки с сотнями одновременных запросов это и есть решающий довод — и он
количественный, а не идеологический.

**Порядок работ из этого получается обратный тому, что предлагал исходный текст:**
сперва FFI там, где библиотека и так in-process (DuckDB, SQLite) — он и правилен, и
уже сделан; затем сетевые БД, и решение «FFI с `#blocking` против чистого протокола»
принимается **замером** под ожидаемой конкурентностью, а не объявляется заранее.

### 5.4. Что из этого меняется в Карине — план 279

**Указано владельцем 2026-09-11.** Дом ответа — [план 279 «Безопасность M:N через
эффекты»](../../plans/279-mn-safety-via-effects.md), статус ⬛ ЧЕРНОВИК (номер назначен
2026-09-02, к исполнению не принят), адресат — **трек Carina (`novac`/Vela)**, решение
владельца 2026-09-02. В тег v0.1 план не входит; оракул получает из него только то,
что попадёт по остаточному принципу.

Первое, что снимает недоразумение: **`#blocking` эффектом НЕ становится.** План прямо
относит это к границам: «Не делаем аллокацию эффектом, `#os_thread`/`#blocking`
остаются **атрибутом**, а не членом строки» (`279:70-71`). Замена у него
**переименовательная** — `#blocking` → `#os_thread`, и она ОТЛОЖЕНА: «остаточный
принцип и отдельное решение владельца; в бюджет плана не входит» (`279:306`).
Значит §5.1–§5.3 остаются в силе целиком, и переименование их не тронет: механизм
тот же, слово другое.

**А вот `#thread_affine` в Карине заменяется по-настоящему, и это важнее.** Карине
прямо ЗАПРЕЩЕНО строить три механизма, которые research §9 удаляет (`279:299-303`):
собственный транзитивный подъём `thread_affine_closure`; `E_FIBER_INDIRECT_CALL`
отдельным проходом под флагом; стирание строки эффектов в fn-типе. После этапов
Э1–Э3 они не нужны: **первый становится частным случаем подъёма строки эффектов**,
второй — обычной несовместимостью fn-типов, третий не возникает. Приёмка машинная:
`grep -rn "thread_affine_closure|E_FIBER_INDIRECT_CALL|NOVA_FIBER_INDIRECT" novac/src`
обязан быть пуст, плюс новый страж с самотестом (`279:314-315`).

Имена эффектов решены владельцем 2026-09-01 (`279:36-38`): **`Exclusive`** — замыкание
держит алиас, к которому нужен единоличный доступ; **`SameThread`** — нужен тот же
поток ОС.

**Что это означает для драйвера БД — одной фразой: привязка к потоку переезжает из
атрибута на externs в СТРОКУ ЭФФЕКТОВ, то есть становится видна в подписи.** Сегодня
`nova-duckdb` пишет `#thread_affine` шестьдесят раз — по разу на каждый extern
(`nova-duckdb/src/ffi.nv`, замер 2026-09-11), а ограничение живёт в атрибутах и
проявляется отказом `E_THREAD_AFFINE_IN_FIBER` на попытке `spawn`. После 279 то же
ограничение будет частью строки — ровно как `Db` и `Net` сегодня, — и потребитель
увидит его там же, где видит остальные эффекты. Это последовательно: весь смысл
эффектов в том, что ограничение написано в подписи, а не в атрибуте сбоку.

**Условие входа, которое стоит проверить сейчас, а не потом.** `SameThread` отложен
этапом Э5, и одно из двух его условий входа — «появляется первый носитель на стороне
FFI — тип с привязкой к потоку создания» (`279:335`). **Соединение DuckDB — ровно
такой тип**: README пакета говорит «Соединение привязано к потоку», и все 60 externs
помечены соответственно. То есть условие, по букве, уже наступило.

Заметить это, однако, сегодня нечем, и по двум причинам сразу:

1. страж-растяжка `scripts/guards/check-per-thread-needs-samethread.py`, который план
   назначает сторожем этого условия (`279:348-353`), **не заведён** — что для
   черновика законно;
2. но даже когда он появится, он смотрит на `#per_thread`/`#same_thread` «в любом
   `.nv` дерева», а носитель помечен `#thread_affine` и живёт **в другом
   репозитории**. Ни по маркеру, ни по области страж носителя не увидит.

Это не поломка плана, а несовпадение ОБЛАСТИ проверки с её ПРЕДМЕТОМ, и дешевле
исправить его в черновике, чем после. Предложение (решение владельца/автора 279):
либо добавить `#thread_affine` к маркерам, за которыми следит страж, либо явно
записать в Э5, что пакеты-спутники вне его области и условие входа по ним
объявляется рукой. Второе честнее и дешевле; главное — чтобы отсутствие сигнала не
читалось как «носителей нет».

*Предпосылка, о которой план предупреждает первой, и она держит сроки:* **сегодня
`novac` не знает строки эффектов вовсе** — замер 2026-09-02, `grep -rn "effect"
novac/src/parse/*.nv` даёт ноль (`279:22-25`). Поэтому Э1 не «дописывает проброс», а
заводит строку в подмножестве с нуля и не начинается, пока `novac` не научится её
парсить и хранить (работа плана 274). Для драйвера это значит: до тех пор
действующая модель — атрибуты D172, и писать надо по ней.

## 6. Ресурсы: линейность вместо RAII и вместо «не забудьте закрыть»

Исходный текст писал: «Memory management критичен. DuckDB выделяет память под
результат — нужно правильно освобождать. Ваш FFI-слой должен обернуть это в RAII
или аналог». В Nova ответ сильнее RAII, потому что он **статический**.

Форма из `nova-duckdb/README.ru.md` (пакет владельца, не выдумана):

```nova
consume db = Database.open("limits.duckdb", DbOptions.defaults()) {
    consume con = db.connect() {
        consume app = con.appender("", "sample") {
            app.row([Value.Instant(now), Value.Int(74)])
            app.flush()
        }
    }
}
```

Каждый хендл — `consume`-тип с `@cleanup`, привязанный к блоку; **обращение после
закрытия — ошибка компиляции, а не use-after-free**. Разница с RAII не
стилистическая: RAII гарантирует освобождение, но не запрещает держать ссылку;
линейность запрещает саму ссылку.

Какие сущности драйвера обязаны быть `consume` — видно из того же образца:
соединение, транзакция, appender, курсор результата. Все они имеют состояние «уже
закрыт», обращение к которому должно быть невыразимо, а не проверяемо в рантайме.

**И у закрытия есть вторая половина, которую легко потерять: оно возвращает
`Result`.** Конвенция говорит это нормативно — ресурсы суть must-consume линейные,
и `@close(self) -> Result[…]` — «единственный способ разрядить обязательство;
незакрытый = **compile-error**», причём «`@close()`/`@wait()` **возвращает
`Result`** (ошибка close/flush — например `ENOSPC` — видна, не глотается)»
(`docs/dev/module-conventions.md:79-83`). Там же названа цена альтернатив: `defer
Close()` в Go глотает, `Drop` в Rust глотает, в Java/Kotlin ошибка становится
suppressed.

Для драйвера БД это самое практичное место всей конвенции: **`commit` — это
закрытие, которое может не удаться.** Транзакция, чей `commit` вернул ошибку
и чью ошибку проглотили, — это потерянные данные с зелёным логом. То же с
`flush` у appender: у него вся работа и происходит в момент сброса.

## 7. Транзакция: решение принято, дизайн отдан плану 268

Это место стоит прочитать дословно, потому что оно — готовый ответ на пункт
«Transaction — с явным begin/commit/rollback» и одновременно урок о границе:

операция `in_transaction[T, E](body fn() Db Fail[E] -> T)` **снята** 2026-08-12
(реестр №570). Она «проходила `nova check` и роняла `nova build`»
(`std/src/data/sql.nv:134-138`). Замена — **не эта операция, переписанная**:

> `consume`-типизированный `Tx` с `@cleanup` (операция возвращает
> `Result[Tx, DbError]`, тело вызывающего исполняется ВНЕ границы эффекта, так что
> `T` её никогда не пересекает — rank-2 не нужен — а `@cleanup` по умолчанию
> откатывает, если не было commit)
> — `std/src/data/sql.nv:139-143`

Три вещи разом: отмена rank-2, откат по умолчанию вместо забытого `rollback`, и
общий приём «что не проходит границу — выносим за границу». Дизайн оставлен плану
268 (решение владельца записано в плане 273 §4-тер) и **здесь не проектируется**.

## 8. Отмена и таймауты: `Outcome`, а не `context`

`context.Context` в Go решает две задачи разом — распространение отмены по стеку и
переноску значений. Первая в Nova решена структурной конкурентностью: исход отмены
выражен **значением области**, `supervised(cancel:)` даёт `Outcome[T]` (D455,
`06-concurrency.md:9051`). Вторая — задача эффекта, а не параметра.

**Но обещать отмену на лету нельзя, и это тоже записано нормативно.** Конвенция:
«Cancel — честно best-effort: queued-операция отменяется чисто (`uv_cancel`);
уже-летящий syscall на threadpool **не прерывается** (как Go/tokio/Java) —
abandon-result + well-defined состояние ресурса. **Не врать** про mid-syscall-cancel»
(`module-conventions.md:156-159`). Для драйвера это означает: отменённый долгий
запрос — это отказ от РЕЗУЛЬТАТА, а не гарантированная остановка работы на сервере;
если БД умеет отменять запрос своим протоколом (у PostgreSQL это отдельное
соединение с `CancelRequest`), это делает драйвер явно, и об этом надо писать в
документации словами, а не подразумевать.

Практическое следствие для драйвера: **отменяемость не добавляется в сигнатуру
каждой операции.** В `std.net` это уже проверено тестом
`std/src/net/supervised_cancel_accept_test.nv` — отмена долгого `accept` под
`supervised`. Драйверу нужно обеспечить не «принимать ctx», а корректно
разматывать своё состояние при отмене; для FFI-драйвера это означает, что
`@cleanup` обязан быть верен и на пути отмены.

## 9. Верность типов как дисциплина отказа

Раздела на эту тему в исходном тексте не было вовсе — там типы колонок упоминались
как таблица соответствий. Пакет `nova-duckdb` показывает, что это отдельное
архитектурное решение, и притом самое спорное для потребителя:

* **`DECIMAL` никогда не сворачивается в float**, даже для печати: «процент в
  `DECIMAL(5,2)` — точное число, которое человек сравнивает с порогом; float — это
  как 74.00 становится 73.999999»;
* **момент точнее микросекунды отвергается, а не срезается**: «срезанная запись —
  другой момент, и построенный по ней график неверен так, что этого не видно»;
* **`INTERVAL` с месяцами отвергается**: месяц не фиксированное число дней;
* `HUGEINT` отдаётся двумя половинами, потому что ABI `__int128` не переносим между
  тремя тулчейнами;
* `BLOB` имеет отдельный акцессор от текстового, потому что текстовый *преобразует*
  значение.

**Проверено кодом, а не README** (README сам говорит, что тесты ни разу не
запускались, поэтому верить ему на слово нельзя): отказ по месяцам стоит в
`nova-duckdb/src/duckdb.nv:342` — `if months != 0 { return
Err(DuckError.Type("column ${col} is an INTERVAL carrying months, which Duration
cannot hold")) }`; отказ по точности — в `src/types.nv:176-179`,
`micros_of_timestamp(t Timestamp) -> Option[i64]` возвращает `None`, когда момент
несёт точность мельче микросекунды; `DecimalValue` объявлен `value`-записью
(`src/types.nv:156`), то есть в float не сворачивается по устройству типа.

Общее правило, которое стоит перенести в любой следующий драйвер: **значение, которое
нельзя отдать ТАКИМ, каким оно записано, отвергается с именем колонки, а не
приводится молча.** Это дороже в использовании и дешевле в эксплуатации; ровно та же
логика, по которой шифрование и `read_only` в версии 0.1 отвергаются, а не
игнорируются — «настройка безопасности, которая молча ничего не делает, хуже отказа».

## 10. Свидетель: `nova-duckdb`

Пакет существует и отвечает на большинство вопросов исходного текста практикой.
Состояние по его собственному README (честное, и это отдельно ценно): Nova-часть
написана и `nova check` чистый; **C-шим написан и ни разу не компилировался**; тесты
написаны и **ни разу не запускались**; тега нет. «Ничто здесь не объявлено
проходящим».

Что он уже даёт и что из этого — общий приём, а не частность DuckDB:

* Appender как ПЕРВОКЛАССНЫЙ путь записи, а не оптимизация: построчный `INSERT`
  стоит около двух миллисекунд, сто тысяч строк через Appender — около десяти
  миллисекунд суммарно;
* `#thread_affine` на каждом extern (`nova-duckdb/src/ffi.nv:104+`) с объяснением в
  шапке файла: соединение привязано к потоку, поэтому вызов из `spawn` — ошибка
  компиляции;
* интеграция с тегом `sql`: `con.run(sql`SELECT … WHERE percent > ${threshold}`)`;
* расширения `core_functions` и `icu` влинкованы статически и автозагрузка выключена
  на соединении — потому что при включённой автозагрузке первый вызов
  отсутствующего расширения уходит в интернет и висит около двадцати двух секунд,
  прежде чем упасть. **Это обобщаемо:** драйвер не должен иметь путей, на которых
  он молча ходит в сеть во время работы.

**Чего в нём нет — и это главное наблюдение раздела: колоночного пути.** Замерено
2026-09-11 по `nova-duckdb/src/ffi.nv`: 60 объявлений `extern "C" fn`, и доступ к
данным ВЕСЬ построчный — `ddb_value_bool/i64/u64/f64/hugeint/decimal/timestamp/date/
time/interval/uuid/bytes/blob`, каждое с подписью `(result, row i64, col i64)`
(`:138-164`). Ни `duckdb_fetch_chunk`, ни `data_chunk`, ни `duckdb_vector` в пакете
не упомянуты ни разу. Результат при этом материализуется целиком: сначала
`ddb_result_rows`/`ddb_result_cols` (`:127-129`), потом обращение по ячейке.

То есть исходный текст был прав ровно в том пункте, где пакет его пока не
выполняет: для OLAP-движка построчный доступ по ячейке — это вызов C на каждое
значение, а `SUM(price)` по миллиарду строк сперва материализует миллиард строк.
**Это не упрёк пакету 0.1** — его README прямо говорит, что версия отдаёт «законченное
ядро и то, что нужно первому потребителю». Но это называет следующую волну: не
расширение типов, а chunk-путь. И он же — единственное место, где §12.3 (нужен ли
колоночный возврат в самой границе) перестаёт быть теоретическим.

Что в пакете ЕСТЬ сверх ожидаемого: полноценный слой подготовленных выражений —
`ddb_prepare`, `ddb_stmt_param_count`, `ddb_stmt_execute`, `ddb_stmt_clear` и
семейство `ddb_bind_*` (`:169-192`). В std-слое (`type Db effect`) подготовленных
выражений нет вовсе, так что пакет здесь опережает границу — и это ещё один довод,
что богатый API живёт на фасаде значений, а не в операциях эффекта (§4.3).

## 11. Что остаётся работой драйвера

Чек-лист исходного текста, пересчитанный: слева — что он требовал, справа — кто это
делает в Nova.

| требование | кто делает |
|---|---|
| async в ядре интерфейса | **не нужно**: файбер паркуется, вызов выглядит синхронным (`std/src/net/effect.nv:20-22`) |
| cancellation в каждом вызове | **язык**: `supervised(cancel:)` → `Outcome[T]` (D455) |
| structured errors | **язык даёт форму** (сумма), драйвер даёт перевод кодов БД в свою сумму |
| prepared statements с кэшем | **драйвер** — в std-слое этого нет |
| nullable-типы | **язык**: `Option[T]`; драйвер обязан различать NULL и «нет колонки» |
| connection pool в интерфейсе | **открытый вопрос** — см. §12 |
| batch-операции | **драйвер**; образец пути — Appender (§10) |
| миграции | вне слоя драйвера |
| typed scan | **фасад значений**, не эффект (§4.3) |

## 12. Открытые вопросы (адресат · умолчание · срок)

1. **Условие входа Э5 плана 279 наступило, а сторож его не увидит** — §5.4.
   `SameThread` отложен до «первого носителя на стороне FFI — типа с привязкой к
   потоку создания»; соединение DuckDB — такой тип, но назначенный страж следит за
   `#per_thread`/`#same_thread` в дереве, а носитель помечен `#thread_affine` и лежит
   в другом репозитории. *Адресат: владелец / автор плана 279* · умолчание: считаем
   условие ненаступившим и пишем по D172 · до принятия плана 279 к исполнению.
2. **Пул соединений: обработчик, значение или эффект?** Исходный текст требовал «пул
   в интерфейсе, чтобы драйверы получали его бесплатно». В Nova это не бесплатно:
   пул — состояние, а эффект — точка диспетчеризации без инстанса (D456). Три
   разложения: пул внутри обработчика (просто, но пул неподменяем отдельно); пул как
   `consume`-значение, отдаваемое операцией (симметрично `Tx` из §7); отдельный
   эффект `Pool` над `Db`. *Адресат: план 268* — там уже живёт граница эффекта ·
   умолчание: пул внутри обработчика · до первого сетевого драйвера.
   **Дополнительно:** пул и `#thread_affine` конфликтуют по смыслу — соединение,
   привязанное к потоку, нельзя отдать произвольному файберу; для in-process
   драйверов это, возможно, означает «пула нет», и так и надо записать.
3. **Колоночный путь в границе.** Нужен ли `Db` второй операции вида «дай батч
   колонок» или колоночный доступ живёт только на фасаде конкретного пакета?
   Вопрос упирается в стирание Ok-payload (§2): батч — многословный возврат.
   *Адресат: владелец/план 268* · умолчание: только фасад пакета, в `std.Db` не
   лезем · до волны OLAP-потребителя.
4. **Где живёт `std.data.sql`.** Файл сам пишет: «Когда-нибудь это переедет в
   `std.sql`» (`std/src/data/sql.nv:7-8`), и называет себя «эталонной реализацией на
   актуальной спеке». Переезд до тега или после? *Адресат: владелец* · умолчание: не
   трогаем до v0.1 · вместе с решением по `#stable`.
5. **Драйвер — std или пакет-спутник? Вопрос ТЕХНИЧЕСКИЙ, а не административный.**
   От ответа зависит, каким способом драйвер имеет право ждать: парковка фибры
   отдана только std и рантайму, пакету остаются синхронный `extern "C"` и
   `#blocking` (§5.2). Сегодня граница (`Db`, `SqlValue`) живёт в std, а реализация
   (`nova-duckdb`) — спутником; для in-process БД это неважно, для сетевой — решающе.
   *Адресат: владелец* · умолчание: граница в std, драйверы — спутники · **до начала**
   первого сетевого драйвера, не после.
6. **`Fail` или `Result` в операциях `Db`?** §4.4, расхождение первое. *Адресат:
   владелец* · умолчание: следуем конвенции (`Result`), демонстрацию в `sql.nv` не
   трогаем · вместе с решением по переезду `std.data.sql`.
7. **Структурный `DbError` вместо плоской суммы?** §4.4, расхождение второе.
   *Адресат: владелец* · умолчание: новый драйвер пишет свой структурный тип по
   образцу `IoError`, `DbError` из `sql.nv` не переиспользует · до первого драйвера с
   разбором ошибок СУБД.

## 13. Что из исходного текста отвергнуто и почему

* **«Взять `database/sql` практически без изменений».** Отвергнуто: его центральная
  идея — интерфейс, реализуемый драйвером и выбираемый по строке подключения. В Nova
  роль играет эффект, а выбор делается `with` на границе. Взято другое: минимализм
  набора операций и мысль, что пул не должен писать каждый драйвер.
* **«`context.Context` как образец».** Отвергнуто: §8.
* **«Typed scan в интерфейсе драйвера».** Отвергнуто как невыразимое: §4.2.
* **«Pure-реализация протокола — архитектурная необходимость».** Понижено до выбора
  с названными критериями: §5.3.
* **«Начните с FFI-обёрток, чистые протоколы потом; так прошли pgx и sqlx».**
  Историческая часть сомнительна (обе названные библиотеки начинались как чистые
  реализации протокола, а не как обёртки над libpq) и **здесь не используется как
  довод** — порядок работ в §5.3 выведен из наших замеров, а не из чужой истории.
* **«SQLite: пула нет, одно соединение»** (таблица прежней редакции). Не
  воспроизводится: SQLite допускает несколько соединений к одному файлу. Строка
  удалена, чтобы на неё не сослались.
* **Рекомендации про ORM (`ent` против GORM) и codegen из SQL (`sqlc`).** Вынесены
  из разбора: это слой НАД границей, у него нет ни потребителя, ни плана в проекте, а
  обсуждение его формы до появления первого сетевого драйвера — проектирование
  вперёд спроса. Одно наблюдение сохранено как ориентир: для статически
  типизированного языка генерация кода из SQL даёт проверку типов до запуска, а
  runtime-ORM с рефлексией эту возможность тратит впустую.
* **Схемы ASCII-боксами в трёх несовместимых нумерациях.** Заменены одной схемой §3,
  где границы проведены по подменяемости.
