# Ревью: имя модуля = два сегмента (D78 rev-3 «parent.target») — насколько удачен выбор

> **Статус: research-заметка** (2026-07-13, по запросу владельца). Решение о
> спек-изменении — за владельцем; здесь только анализ + варианты. Спека:
> [D29/D78, 07-modules.md](../../../spec/decisions/07-modules.md) («Объявление
> модуля — правило parent.X», rev-3 + rev-3.1).

## 1. Что зафиксировано сейчас

- Декларация: `module <parent>.<target>` — ровно **последние два сегмента**
  пути (target = файл для single-file, папка для folder-module), независимо
  от глубины. `E_D78_MODULE_PATH_MISMATCH` при несовпадении.
- Декларация — **identity-check, не routing key**: резолв импортов идёт через
  внутренний mapping decl ↔ канонический путь (D78 rev-3 «Свойства», п.4).
- История: rev-1 (полный путь от корня пакета) → мигрирован и **удалён**
  2026-06-01 (846 файлов, `[M-D78-strict-removal]`); rev-3.1 (Plan 42.13) —
  **исключение** для `internal/`: 3-сегментное `owner.internal.target`,
  потому что иначе `admin/internal/token.nv` и `billing/internal/token.nv`
  коллидируют в `internal.token`.

## 2. Эмпирика по корпусу (2026-07-13, std + examples + spec_tests)

- **Фактических коллизий деклараций: 0** (скрипт: decl → множество папок;
  ни один decl не приходит из двух разных директорий).
- **Но инвариант держится дисциплиной, не построением.** Конвенционные
  служебные подпапки уже делят namespace между далёкими поддеревьями:

  | Поддерево | Декларация |
  |---|---|
  | `std/collections/vec/neg/…` | `neg.vec_of_empty_panic` |
  | `std/encoding/compress/neg/…` | `neg.inflate_requires_max_output` |
  | `std/time/civil/neg/…` | `neg.period_not_duration` |
  | `std/time/civil/rt/…` | `rt.date_period_overflow_traps` |
  | `std/http/servernet/rt/…` | `rt.handle_connection_smoke` |

  Пять поддеревьев в двух общих namespace (`neg.*`, `rt.*`). Коллизии нет
  только потому, что имена **файлов** пока различаются. Появление
  `std/time/civil/neg/overflow.nv` и `std/collections/vec/neg/overflow.nv`
  = мгновенный дубль. Это ровно та форма, которую для `internal/` уже
  латали отдельным правилом rev-3.1 — прецедент, что схема течёт.
- **Глубина маскирует проблему:** почти весь std лежит на глубине 2 от корня
  пакета (`collections/hashmap.nv`, `http/server/`), где 2-сегментный decl
  **совпадает** с полным путём — усечение незаметно. Оно проявляется только
  с глубины 3 (`neg/`, `rt/`, будущие вложенные приложения — ср. Plan 187
  `backend/app/`, `backend/api/`).
- Диагностика **дубля decl из разных путей** в компиляторе явно не найдена
  (Rule E покрывает только конфликт `X.nv` + `X/` на одном уровне);
  REF-резолюция для package-root std использует suffix-match
  (см. D381-закрытие в backlog).

### 2а. Эксперимент: что реально происходит при дубле (2026-07-13)

Вопрос владельца: «роутинг же путевой — дубль декларации безвреден?»
Проверено пакетом-репро (scratchpad): `src/a/neg/x.nv` + `src/b/neg/x.nv`,
оба ПРИНУДИТЕЛЬНО `module neg.x` (rev-3 диктует декларацию — иначе
`E_D78_MODULE_PATH_MISMATCH`), одноимённые приватные `secret()`, разные
экспорты `who_a`/`who_b`; `main` импортирует оба по пути.

- **Роутинг подтверждён путевой:** `import demo.a.neg.x` не резолвится
  (первый сегмент ищется как папка от source root), `import a.neg.x` —
  резолвится. Сегменты импорта = папки, package-префикс не нужен внутри
  пакета.
- **Но реестр модулей керит по ДЕКЛАРАЦИИ:** экспорты второго модуля тихо
  исчезают — `who_b` → «undefined identifier» с якорем на строку
  module-decl, никакой duplicate-диагностики. Контроль: папка переименована
  (`neg2/` → decl `neg2.x`) → PASS.
- Итог: коллизия — не гипотеза, а **живой тихий дефект** с обманной
  диагностикой; пользователь не может обойти его сменой декларации
  (она диктуется путём) — только переименованием папок. Маркер:
  `[M-d78-duplicate-decl-module-swallow]` (backlog, P1).
- **Переинтерпретация rev-3.1:** исключение для `internal/` — не «для
  красоты» и не самостоятельное правило, а спековая заплатка вокруг этого
  же дефекта (два `internal/token.nv` глотались бы так же). После фикса
  keying'а — кандидат на ретракцию.
- Прецедент фикс-направления — свежезакрытые mangling-баги (D381
  collision-aware типы, `[M-178-server-typed-body]` bare-fn): там
  коллизии были ровно потому, что путь модуля НЕ учитывался, и чинились
  ДОБАВЛЕНИЕМ path/module-awareness. Тот же ход нужен реестру модулей.

## 3. Соседи

| Язык | Схема | Ключ импорта | Коллизии по построению |
|---|---|---|---|
| **rustc** (наш эталон) | у файла НЕТ самодекларации; путь модуля = полный путь от crate root, объявляет родитель (`mod x;`) | полный путь | невозможны |
| **Go** | package = **1 сегмент** (свободное имя в файле) | **полный fs-путь** (`import "a/b/c"`), имя пакета — только локальный идентификатор, при конфликте — alias | невозможны (ключ = путь) |
| Python / Node | нет декларации | полный путь | невозможны |
| Java | reverse-domain, полный, повторён в каждом файле | полный | невозможны, но многословно |
| **Nova rev-3** | 2 сегмента в файле | decl (parent.target) + package-префикс | **возможны**, сдерживаются дисциплиной + спецкейсом rev-3.1 |

Nova — единственная схема из ряда, где ключ импорта короче полного пути и
уникальность не гарантирована конструкцией. От эталона (rustc) отклонение
двойное: файл самоидентифицируется И идентичность усечена.

## 4. Оценка

**Что схема даёт (реальные плюсы):**
1. Краткость: нет Java/rev-1-многословия, декларация не растёт с глубиной.
2. Перенос верхних уровней дерева (re-parenting выше target) не трогает
   декларации — меньше churn при реорганизациях.
3. Mismatch-check ловит перемещённый файл (identity-check работает).
4. Единообразие single-file / folder-module.

**Чем платим:**
1. Уникальность decl внутри пакета — **инвариант без enforcement'а по
   построению**; корпус в одном переименовании файла от дубля (§2).
2. Исключения накапливаются: rev-3.1 (`internal/`), Rule E (facade);
   каждая новая конвенционная подпапка (`neg/`, `rt/`, `backend/app/`)
   — кандидат на следующий спецкейс.
3. Импорт-имя ≠ путь: по `import std.neg.vec_of_empty_panic` не найти файл
   грепом по пути; discoverability и tooling (go-to-module) опираются на
   mapping, а не на текст.
4. Поведение при дубле неопределено/непроверено (нет явной диагностики).

## 5. Варианты и рекомендация

- **(а) rev-3.2 — обобщить rev-3.1 (минимальный, рекомендую):** для target
  на глубине >2 от корня пакета декларация расширяется до 3 сегментов
  `grandparent.parent.target` (это autоматически покрывает `internal/`,
  `neg/`, `rt/` и будущие `backend/app/` ЕДИНЫМ правилом, спецкейс
  rev-3.1 растворяется в общем). Плюс: hard-error диагностика дубля decl
  с обоими путями (независимо полезна при любом варианте).
- **(б) вернуть полный путь (rev-1):** гарантия по построению, но миграция
  846+ файлов уже была В ОБРАТНУЮ сторону — откат дорог и противоречит
  зафиксированному решению.
- **(в) Go-модель:** decl = 1 сегмент, ключ импорта = полный путь. Самая
  чистая теоретически, но меняет синтаксис import по всему корпусу —
  объём как у rev-1-миграции, выигрыш против (а) мал.

**Вердикт (пересмотрен после эксперимента §2а):** первопричина — НЕ длина
декларации, а **keying реестра модулей по декларации вместо канонического
пути**. Правильный порядок фиксов:

1. **Корневой фикс: реестр по каноническому пути** (decl = чистая чексумма
   + членство-бит §6). Класс коллизий исчезает независимо от числа
   сегментов; rev-3.1 (`internal/`) ретрактируется как ставшая ненужной
   заплатка. Вариант (а)/rev-3.2 при этом НЕ нужен для корректности —
   остаётся чисто косметическим (читаемость decl глубоких модулей) и по
   умолчанию НЕ рекомендуется.
2. **Диагностика**: пока keying не починен (или как страховка после) —
   hard-error на дубль decl с обоими путями + негативная фикстура.
3. **Статтер-фикс `tls.tls`** (§7, root-модуль) — ортогонален, остаётся
   рекомендованным.

## 6. Зачем декларация в файле вообще, если резолв идёт по пути (вопрос владельца 2026-07-13)

Резолв импортов действительно идёт по пути (D78 rev-3 «Свойства» п.4:
декларация — identity-check, не routing key). Но декларация несёт **один
незаменимый бит + три вторичных**:

**Незаменимый бит — членство (peer vs независимый модуль).** В модели D78
папка может быть (а) одним модулем из co-equal файлов ИЛИ (б) контейнером
независимых модулей — а форма дерева одинаковая. Живой корпус:

| Файл | Декларация | Семантика |
|---|---|---|
| `std/collections/hashmap.nv` | `module collections.hashmap` | независимый файл-модуль; `collections/` — контейнер |
| `std/collections/vec/core.nv` | `module collections.vec` | **peer** модуля-папки `vec/` — один модуль на все файлы |

Одна и та же форма «папка/файл.nv», противоположная семантика; различает
их только декларация. Из пути этот бит НЕ выводится.

**Вторичные выгоды:**
1. **Чексумма при перемещении** — `E_D78_MODULE_PATH_MISMATCH` ловит
   перенесённый файл ошибкой В САМОМ файле, а не россыпью ошибок на
   call-sites (боль Rust: по содержимому файла его модульный путь
   не определить).
2. **Самоописание вне дерева** — в диффе / грепе / сниппете видно, чей
   это код, без контекста дерева.
3. **Фиксация намерения** — файл, скопированный в чужую папку/проект,
   не «переезжает» молча.

**Соседи:** декларация почти у всех где-то есть: Go — в файле
(`package foo`; заодно даёт локальный идентификатор и folder≠package),
Java/C# — в файле, Rust — у родителя (`mod x;`). Чистый путь без
декларации — Python/Node/Zig; у Zig это работает, потому что folder-модулей
НЕТ — каждый файл сам себе namespace.

**Можно ли выкинуть декларацию совсем?** Да, если убрать её незаменимый
бит структурным правилом, например: «direct-`.nv` файлы папки — ВСЕГДА
peers одного модуля; независимый модуль = только подпапка или файл на
уровне контейнера». Тогда членство выводится из дерева, импорты — чисто
по пути, и коллизионная история §2–§5 исчезает вместе с декларацией.
Цена: (а) миграция corpus-паттерна `collections/*.nv` (контейнер с
независимыми файл-модулями — пришлось бы либо признать `collections/`
модулем, либо разложить по подпапкам); (б) теряются чексумма перемещения
и самоописание. Это вариант **(г)** к §5 — радикальнее (а), но
концептуально самый чистый: один механизм (путь) вместо двух
(путь + декларация-проверка).

## 7. Кейс `tls.tls` — системный статтер внешних пакетов (владелец, 2026-07-13)

Живой пример из nova-tls (`d:/Sources/nv-lang/nova-tls`):

- `[package] name = "tls"`, `[lib] src = "src"`; весь код — `src/tls/*.nv`
  (folder-module) → декларация **`module tls.tls`**, импорт у потребителя
  **`import tls.tls.{TlsStream, ServerConfig}`** (examples/tls/echo_server.nv).
- Классический **статтер** (Go-линтеры флагают `http/http`, `tls/tls`).
- **Реализация разошлась с намерением:** комментарий в nova.toml nova-tls
  прямо обещает «`src/tls/stream.nv` → `module tls`» (одиночный сегмент!) —
  а фактические декларации `tls.tls`. Автор раскладки ожидал схлопывание.

**Почему это системно, а не разовый огрех:** у пакета НЕТ понятия
корневого модуля — модулем может быть только папка/файл ПОД source root.
Главную папку однодоменного пакета естественно звать именем пакета →
`parent(=имя пакета).target(=папка)` → `X.X`. Самый частый форм-фактор
пакета в любой экосистеме («один модуль, названный как пакет») в текущей
схеме даёт статтер ВСЕГДА. Peers: Rust — `lib.rs` = crate-root-модуль
(`tls::TlsStream`); Go — package в корне, импорт по пути, имя одно.

**Фикс — правило корневого модуля (root-module), две формы (совместимы):**
1. **Collapse:** folder-module на source root с именем == имени пакета →
   модуль = просто `<package>` (декларация `module tls`, импорт
   `import tls.{TlsStream}`). Минимальный дифф для nova-tls (файлы не
   двигать, поменять только декларации).
2. **Root peers:** `.nv`-файлы прямо в source root — peers корневого
   модуля `<package>` (аналог lib.rs). Для пакетов без под-модулей
   папка-обёртка вообще не нужна.

Оба ликвидируют статтер и НЕ трогают монорепный std (там пакет `std`
многомодульный, коллизий имени пакет==папка нет). Кандидат-маркер:
`[M-d78-package-root-module-stutter]` (checker/manifest + spec-амендмент
D78; миграция nova-tls = смена декларации в ~13 файлах + import-строки
потребителей).
