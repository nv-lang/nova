# Приложение: разведка рантайма для «M:N через эффекты»

> Приложение к [2026-09-01-mn-safety-via-effects.md](2026-09-01-mn-safety-via-effects.md)
> §8 («В какой форме `SameThread` вернётся»). Вынесено 2026-09-02 при сокращении
> основного документа: это материал ПЛАНА работ (адреса, объёмы), а не предложение.
> Метод: чтение заголовков `nova_rt`, без прогона.

### Вытеснение: состояние на 2026-09-02 — сетка уже плотнее «Go до 1.14»

Замер интегратора по коду (не по памяти), потому что стороннее исследование
назвало модель «кооперативная, проверка в прологе — тесный цикл без вызовов не
отдаёт управление». **Вторая половина неверна:**

- `nova_preempt_check()` эмитится кодогеном ДВАЖДЫ: первой инструкцией каждой
  Nova-функции (`emit_c.rs:29182`) **и в начале каждой итерации каждого цикла**
  (`emit_c.rs:30905`, покрывает и `continue`-ребро) — комментарий кодогена прямо
  называет цель: «a tight arithmetic loop with no function calls … would never
  reach a prologue safepoint» — и закрывает её;
- прологовая проверка элидируется у доказуемо листовых функций (Plan 143.2:
  KEEP только на циклах графа вызовов — рекурсия), бэк-ветвевая остаётся;
- `sysmon`-поток выставляет `preempt_flag`, когда воркер крутит одну файберу
  дольше `NOVA_PREEMPT_SLICE_NS` = 10 мс (`runtime.c:206`), флаг читается вживую
  через TLS-указатель.

Следствия: (1) дыра тесного цикла, ради которой Go в 1.14 строил сигнальное
вытеснение, у Nova закрыта кооперативно — сетка плотнее, чем у Go до 1.14
(тот проверял только прологи через morestack); (2) сигнальное вытеснение
(SIGURG/SuspendThread + безопасные PC-диапазоны) не оправдано: большая работа,
выигрыш только на коде, который и так покрыт; (3) чего сетка НЕ покрывает —
долгий `extern "C"`-вызов (C-библиотека крутится) — но его не вытесняет и Go:
cgo-кадры сигналом не прерываются, лечится только `#os_thread`-формой; (4)
`[M-211-preempt-flag-plain-race]` — TSan-гонка на флаге — **уже закрыта**:
доступ понижен до `__atomic_*(RELAXED)` (`runtime.c:110, 362`); первая версия
этой заметки назвала её живой по ИСТОРИЧЕСКОМУ комментарию (`runtime.c:82-105`
описывает гонку до фикса) — поправлено 2026-09-02 по чтению объявления, а не
комментария. Настоящий остаток назван планом 250 (Ф.1б): запрос вытеснения живёт
на ВОРКЕРЕ, а у Go 1.4 — на горутине (`g->stackguard0`); украденный в середине
слайса фибр теряет запрос, свежий на «горячем» воркере получает чужой. Лечение
уже заложено там же: бит запроса — в новом слове состояния фибра (инвариант №4).

### Разведка рантайма: чего это стоит

Проверено чтением заголовков `nova_rt`, без прогона.

**Per-thread машинерия уже есть.** `_nova_active_scope`, `_nova_active_slot`,
`_nova_current_loop` — все thread-local; дизайн записан прямо: «каждый worker thread
имеет own loop; main thread использует глобальный». N циклов рантайм уже держит.

**Ветвлений почти нет.** `_nova_on_worker_thread()` имеет **три** места использования:
два — сторожевой таймер, третье — кооперативный дренаж очереди воркера. Host-поток
честно попадает в ветку «не воркер», и это правильно: своей очереди у него нет.

**Настоящая точка отказа — сентинел в пути пробуждения.**

```c
// driver.c:512, 533, 607
if (st->home_worker_id < 0) nova_runtime_signal_main();
```

`home_worker_id` — адрес пробуждения, и комментарий рядом формулирует допущение
дословно: «the sleeper's home is a NovaWorker (>=0) or **the main OS thread (-1, the
ONLY genuinely-blocking pump in this runtime)**». Домов ровно два, блокирующийся насос
один. Host-поток — третий вид: его спящий файбер получит `-1`, пробуждение уйдёт в
единственный глобальный `_main_wake`, и файбер **никогда не проснётся**. Тихое
зависание — тот самый дефект, который уже однажды ловили (в комментарии описан прогон
2000 мс вместо 20 мс).

**Два меньших сцепления.** `_nova_main_fiber_co` — единственный глобал;
`nova_cross_effect_route_safe()` истинен только для корневого файбера main, значит
корневой файбер host-потока пойдёт по медленному отложенному пути (консервативно, не
смертельно). И `_nova_current_loop == NULL` молча откатывается на глобальный цикл:
host-поток, забывший выставить свой, получит колбэки в чужом цикле — зависание без
диагностики.

**Кандидат в реестр при принятии плана** (пометка интегратора): это латентный
дефект с точными адресами (`driver.c:512, 533, 607`), активируемый первой же
фичей «`#os_thread` с телом на Nova», — тихое зависание чужого вида потока. Чтобы
находка не утонула в research-доке, при старте работ она заводится строкой
221.1 со ссылкой сюда.

**Во что превращается работа.** Не «второй диспетчер», а **замена сентинела на
идентичность**: `home_worker_id` (−1 = main) становится адресом пробуждения (воркер N,
главный, host N), `nova_runtime_signal_main()` — `nova_runtime_signal(target)`, каждому
host-потоку нужен свой `uv_async_t` по образцу `_main_wake`. Объём: три вызова в
`driver.c`, одна функция и один статический хэндл в `runtime.c`, плюс поля структуры
сна.

*Проверяется фикстурой* «сон внутри `#os_thread`-тела» — но написать её не на чем, пока
`#os_thread` не реализован.
