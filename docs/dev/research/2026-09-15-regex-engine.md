# Регулярные выражения в Nova: чужая библиотека или своя

**Статус:** исследование под вопрос владельца 2026-09-15 «какая библиотека регулярок у Rust, Go,
Swift, Kotlin, JS, Python, PHP — какую интегрировать нам». Вердикт — свой движок RE2-семьи,
довести существующий `std/text/regex.nv`. План работ — [289-regex-own-engine.md](../../plans/289-regex-own-engine.md).

## 1. Кто что использует

| язык | библиотека | класс движка | backrefs / lookaround | откуда Unicode |
|---|---|---|---|---|
| Rust | крейт `regex` (BurntSushi); в std регулярок нет | автоматы: PikeVM, lazy DFA, one-pass, ограниченный backtracker; линейное время гарантировано | нет; отдельный `fancy-regex` для них | свои таблицы (`regex-syntax`) |
| Go | `regexp` stdlib, синтаксис RE2 (Russ Cox) | автоматы (NFA, one-pass, ограниченный backtrack); линейное время | нет | `unicode` stdlib |
| Swift | `Regex` в std с 5.7, литералы `/…/`, `RegexBuilder`; раньше `NSRegularExpression` поверх ICU | собственный backtracking-матчер, grapheme-семантика по умолчанию | есть | ICU |
| Kotlin | `kotlin.text.Regex` — обёртка платформы: JVM `java.util.regex`, JS `RegExp`, Native порт Apache Harmony | backtracking | есть | платформа |
| JavaScript | ECMAScript `RegExp`; V8 Irregexp с JIT, SpiderMonkey — форк Irregexp | backtracking; экспериментальный линейный режим (флаг `l`) | есть | флаги `u`/`v` |
| Python | `re` (собственный `sre`); сторонний `regex` | backtracking | есть | свои таблицы |
| PHP | PCRE2 с JIT (`preg_*`); `mb_ereg` поверх Oniguruma | backtracking | есть | PCRE2/UCP |
| для сравнения: .NET | `System.Text.RegularExpressions`; с .NET 7 режим `NonBacktracking` | обе семьи по флагу | только в backtracking-режиме | своё |

Две семьи. **Perl-линия** (PCRE2, Java, JS, Python, Swift): полный набор возможностей, время в
худшем случае экспоненциальное — ReDoS на пользовательских шаблонах. **RE2-линия** (RE2, Go, Rust,
.NET NonBacktracking, Hyperscan): линейное время гарантировано ценой отказа от backrefs и
lookaround. Все языки, проектировавшие регулярки заново за последние 15 лет, кроме Swift, выбрали
вторую; Swift выбрал первую ради grapheme-семантики и RegexBuilder.

## 2. Что уже есть в Nova

`std/src/text/regex.nv` (683 строки, `module text.regex`) — собственный движок RE2-семьи:
симуляция NFA Томпсона по Расcу Коксу, парсер шаблона → AST `RegexNode` → `[]NfaState`.
Синтаксис: `.`, классы `[a-z] [^…] \d \w \s`, якоря `^ $`, `* + ? {n} {n,m}`, группы `(…)` и
`(?:…)`, альтернация, экранирование. API: `Regex.compile(str) -> Result[Regex, CompileError]`,
`@matches`, `@find -> Option[(int, int)]`, `@find_all`. Нет захватов, именованных групп, нежадных
квантификаторов, `\b`, флагов, Unicode-классов. Тесты `regex_test.nv` — 20 блоков, в т. ч. «нет
катастрофического отката»; `nova test std --filter regex` → PASS (2026-09-15). `nova check`
проходит; записи в `std/src/STATUS.md:107, :173, :370` о check-fail устарели.

`std/src/unicode/` уже даёт `general_category`, `is_alphabetic`, `is_whitespace`, `is_numeric`,
регистры — сырьё для `\p{L}` и `(?i)`.

Спека D48 (теговые литералы) называет `regex` стандартным тегом MVP: `` regex`\d+\.\d+` `` без
двойного экранирования, валидация шаблона при компиляции через `@comptime` (сам `@comptime` —
v2 по D48).

## 3. Варианты

| вариант | плюс | минус | вердикт |
|---|---|---|---|
| **PCRE2** через `extern "C"` | полнота, JIT, PHP/Python-совместимость ожиданий | C-зависимость против Карины без libc; ReDoS на пользовательских шаблонах; обёртка под GC и владение; тег `regex` не проверить при компиляции без второго парсера | нет для std; допустим как пользовательский пакет |
| **RE2** (C++) через `cre2` | линейное время, эталон семьи | C++ в сборке каждой платформы; та же проблема тега | нет |
| **Oniguruma / TRE** (C) | C, малы | backtracking (Oniguruma) или устаревший (TRE); C-зависимость | нет |
| **Свой движок на Nova, RE2-диалект** | безопасность по умолчанию; собирается тем же кодогеном; парсер исполним на `@comptime` для тега; уже есть 683 строки и зелёные тесты | backrefs/lookaround не будет никогда; производительность требует lazy DFA — отдельная фаза | **да** |

Прецедент решения тем же владельцем: разбор float на Nova в отдельном файле (план 282 Ф.4 /
283), а не `strtod`-грамматика.

## 4. Решение и границы

Диалект — **RE2** (совпадает у Go и Rust, документирован, переносим). Обещание — линейное время
по длине входа для любого шаблона. **Никогда:** backrefs `\1`, lookaround `(?=…)` `(?<=…)`,
атомарные группы, possessive-квантификаторы. Кому нужны — PCRE2 пользовательским пакетом.

Две двери к регулярке, обе по канону: константный шаблон — тег `` regex`…` `` (D48, проверка при
компиляции, когда появится `@comptime`); динамический — `s.to_regex() -> Result[Regex, RegexError]`
(конверсия из значения — метод на источнике, D54/§1а; `Regex.compile(s)` — статик из значения,
та же дверь, что снятые `str.parse_*`). Ошибка домена — `RegexError` по D325 (`<Domain>Error`),
не `CompileError`. Оба переименования — решение владельца, см. план Ф.1.

## 5. Порядок работ — план 289

Ф.0 спека (D48 амендмент: диалект, гарантия, две двери; STATUS) → Ф.1 API по канону → Ф.2 захваты
(PikeVM с нитями захватов, именованные группы, `replace`/`split`/итерация) → Ф.3 синтаксис
(нежадные, `{n,}`, `\b`, флаги `(?i)(?m)(?s)`, `\p{…}` через `std/unicode`) → Ф.4 скорость
(литеральный префильтр, lazy DFA, бенч) → Ф.5 тег `regex` с проверкой при компиляции (зависит от
`@comptime`). Приёмка каждой фазы — в плане.
