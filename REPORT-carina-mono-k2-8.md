## D83 (`c7688aa04`)

**Носитель:** `type Wb { with int }` компилировался, оракул: «expected identifier, got `with`».

Просто поставить имя поля в дверь №1652 было нельзя. Перед режимом и именем поля может стоять
модификатор видимости D220: `priv`/`pub` (`priv mut money f64`). Карина читала его как ИМЯ поля, а имя —
как тип: `priv buf str` из std объявлял поле `priv` неизвестного типа `buf`.

**Попутно — существующий K1.** Из-за этого кривого чтения `"abc".chars()` с последующим `it.pos` (поле, которое
std держит приватным) молча компилировался. Оракул отказывает: `E_FIELD_MODULE_PRIVATE`.

**Что сделано:**
- в парсере поле читает необязательный `priv`/`pub`, имя идёт через `@push_name` (записи, именованные
  кортежи, поля вариантов-записей);
- `field_name_at` и правило формы поля в `check` перешагивают модификатор;
- сборщик учитывает модификатор поля: `priv` прячет поле от другого модуля, `pub` снимает типовой `priv`;
- имя параметра операции эффекта — через `@take_name`: та же дверь №1652, место, которое она пропускала.

Поверхность builtins 72 → 73 (`is_field_visibility_word`, строка хроники в базе).

**Фикстуры:**
- `reserved_name/neg_4` — поле `with`, словами оракула;
- `field_vis/pos_1` — `priv`/`pub`, `type X priv` с полем `pub`; байт-в-байт;
- `field_vis/neg_1` — `it.pos` отказан.

**В обе стороны, по поломке на каждую из пяти частей:** каждая краснит свою фикстуру.

**Упрощение (названо в коммите):** приватное поле Карина отказывает словами «unknown field», оракул —
`E_FIELD_MODULE_PRIVATE`. Отказывают оба. Док `@field_visible` («оракул отвечает "unknown"») устарел.

## №1678 (`bd26855a0`)

**Как решает оракул.** Правило оракула — «сумма собственного модуля побеждает», а не «приватная сумма
невидима». Из программы он сам видит `Slot.Empty`: голое `Tombstone` у него решается в `Slot[K, V]`.

**Что было у Карины.** В `variants_named` «своё» побеждало и раньше, но «своё» в теле поданного
экземпляра значило файл программы, а не модуль тела.

**Что сделано:**
- `Checker.home_sums` — суммы дерева тела (`NameTable` по `SumDecl`); заполняется только для поданного тела;
- дверь `@variants_named_here`: в поданном теле побеждают суммы его модуля, иначе ответ прежний;
- девять мест в `check` переведены на неё; `type_of` читает решение, записанное проверкой.

**Клетка** `pipeline/handed_variant_test` судится по числу диагностик (№1688):
- поданное необобщённое тело `mut a = Empty` рядом с приватной суммой другого модуля компилируется и
  эмитится;
- контроль: голое `Empty` в самой программе между двумя поданными суммами по-прежнему отказывает.

**В обе стороны:** набор пустой → клетка падает; восстановлено → модульные 10/10.

**Сам `LinkedList.from_array`** теперь проходит неоднозначность и упирается в подмножество — находки 1 и 2
ниже.

## НОВОЕ ДЛЯ РЕЕСТРА

1. **Карина: рекурсивная полезная нагрузка поданной ОБОБЩЁННОЙ суммы теряется, и дверь №1512 называет
   её «undeclared».** `Cons(xs[i], acc)` в теле `LinkedList.from_array` отказывает: «undeclared type name
   `LinkedList`». Это сама объявляемая сумма: нагрузка `LinkedList[T]` не прочитана при сборе вариантов,
   и `@refused_lost_payload` даёт ложный текст. Своя необобщённая рекурсивная сумма программы
   (`Cell(int, Lst)`) работает байт-в-байт. Появилось с синком: до него тот же вызов отказывал по арности.
2. **Карина: текст отказа для варианта без данных обобщённой суммы без ожидания говорит про `None`.**
   `mut acc = Empty` (`LinkedList`) → «a bare `None` here has no type to take…». Отказ законный
   (подмножество), но слова про чужой вариант.
3. **(уточнение к письму об отзыве №1691)** Ложная улика пришла от №1688. Пока он не починен, модульные
   пробы сужу условиями (`len() == 0`) или печатью, но не сообщением `assert`.
