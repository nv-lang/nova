# REPORT-p1338 — №1338 и №1337: методы пользовательской обобщённой суммы

Облачная сессия, 2026-09-30. Ветка `p1338-generic-sum-methods` (та же история запушена и под именем `p1338-generic-sum-methods-ylq8up`, которое выдала среда). База — `origin/integrate` c775a975d, перед сдачей слит свежий `origin/integrate` 04e9fe2d1.

**КОРЕНЬ:** все улики воспроизвелись на базе (три варианта №1338 — exit 134 или пустой вывод, вариант без собственного параметра — CC-FAIL `Nova_Opt____Nova_T_p`; улика №1337 сменила симптом на link-FAIL `Nova_Res_method_close`; встроенный носитель — CC-FAIL). Вывод `U` и тип результата вызова метода корнем не были: чекер уже клал в канал `Opt[str]` для `a.mapx(|x| "s${x}")`, мономорф метода был верен. Корней три, класс один — эмиттер выводил сам то, чего чекер не сказал:
1. №1337: `variant_ctor_type` (№1260) отказывал всякой обобщённой сумме, и `ro a = Som(3)` / `consume r = SomC(Res { .. })` оставались без типа.
2. №1338, полезный груз: `match_arm_bindings` отвечал только для необобщённой суммы, и `v` в `Som(v)` над `Opt[int]` не попадал в область, так что тип ветки и `match` в канал не доходил. Эмиттер брал раскладку груза из `sum_schemas[<инстанс>]`, которая заполняется только при выводе структуры инстанса, то есть после тел, где он впервые назван. Промах уходил в стёртый шаблон (`void*`), и дальше был segfault или тихий `0` для `p.x + p.y`. Красное или зелёное решал порядок объявлений: сигнатура `fn unw(o Opt[int])` выше по файлу спасала, поэтому «контроль» в улике и проходил. Даже `ro b Opt[int] = Som(4); match b {..}` в `main` падал.
3. №1338, «`T` не подставлен»: дело было не в мономорфе, а в стёртом теле метода. `annotate_expected_concrete` ставил на `match` в обобщённом теле тип `Opt[T]` из объявления: гейт считал голый `Named{T}` конкретным, и стёртое тело опускало его в `Nova_Opt____Nova_T_p`.

**ФИКС:**
- `compiler-codegen/src/types/generic_sum.rs:33` `generic_variant_ctor_type` — тип конструктора обобщённой суммы решается из типов аргументов (`constraint_solver`), незафиксированный параметр берёт default по D88, иначе остаётся без типа, как раньше; из более позднего использования ничего не выводится.
- `compiler-codegen/src/types/generic_sum.rs:75` `generic_sum_payload` — груз варианта с подстановкой аргументов суммы, вызывается из `match_arm_bindings` (`types/mod.rs:15782`).
- `compiler-codegen/src/types/generic_sum.rs:91` `expected_args_closed` — гейт `rt_is_closed` в `annotate_expected_concrete` (`types/mod.rs:21188`).
- `compiler-codegen/src/codegen/emit_c/generic_sum_schema.rs:28` `ensure_channel_sum_schema` — раскладка инстанса регистрируется из `resolved_types[scrutinee]` до привязок в `emit_match` и `if let` (два однострочных вызова в `emit_c.rs`, файл не вырос).

**ВОПРОСЫ ИНТЕГРАТОРУ:**
1. **Как типизировать получатель-конструктор с параметром, который не выводится** (`Some(Ok(1)).transpose()`, `ro o = Some(Ok(2)); o.transpose()`), и нужен ли на это D-блок. Спека молчит: таблица D88 (`spec/decisions/03-syntax.md`) говорит «не выводится и default нет — ОШИБКА» только для обобщённой функции (`first[]([])`), а `ro x = Ok(5)` сегодня законна. Варианты:
   - (а) ошибка чекера «нужна аннотация» при вызове метода на значении с невыведенным параметром, по букве D88. Громко, локально, ломает только то, что и так падает в C.
   - (б) правило умолчания (например, `E = str`, как уже делает эмиттер для голого `Ok`) — новое правило языка.
   - (в) ничего не менять: получатель без типа, как сейчас, и отказ C-компилятора.

   **Рекомендую (а):** оно продолжает уже записанное правило D88, не вводит нового умолчания и превращает CC-FAIL в диагностику на месте. Нужен номер D-блока или амендмент D88, которые выдаёшь ты; спеку я не правил. Пользовательских сумм это касается так же: для них решение из аргументов и default по D88 уже в ветке.
2. **Блокирует ли тег строка про `void*`-арифметику (№TBD, 🔴 К1).** Это тихая подмена значения, но живого носителя после ветки нет. Я поставил «НЕТ» по прецеденту №1338 («оракул в релиз не выходит»).
