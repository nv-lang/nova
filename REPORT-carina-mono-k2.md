# Отчёт облачной сессии `p274-carina-mono-k2` (№1522, №1524, №1525)

База — `origin/p274-carina-cloud` = `8405e5fcd`; пробы охотника принесены из `main` отдельным
коммитом `8f30944f4`. Окружение — облачный Linux, оракул и Карина собраны в нём
(`libgc-dev` из apt). Агентов не запускал: всё сделано в одном окне.

№1522 КОРЕНЬ: `mono` обходит тело СВОЕГО обобщения один раз, в канале файла, под абстрактным
`T` (`mono/mono.nv`, `has_row_instance`), и там `Vec[T] @is_empty` экземпляра не даёт. Потом
`instances_of` типизирует каждый экземпляр (`empty[int]`) в его собственный канал, но растит
множество только для ПЕРЕДАННЫХ тел (`reach.grow` стоял лишь в ветке `None`). Эмиттер же
называет конкретный экземпляр из этого канала через `Ctx @body_ours`. На «есть ли экземпляр»
отвечали две двери: абстрактная для множества, конкретная для имени. На базе ломались и вложенные
свои обобщения (`outer[T]` → `inner[T]`: `undefined symbol novac_fn_inner__…`) /
ФИКС: `pipeline/pipeline.nv` `instances_of` — экземпляр своего обобщения растит множество из
СВОЕГО типизированного канала через `Reach @grow`, ту же дверь, что у переданного тела
(13 строк, порядок и стоимость мономорфизации прежние, `mono` не перестраивался) /
ПРОБЫ: `gen-body-handed-call` — линковщик → SAME; `gen-body-handed-clear` — линковщик → SAME;
`ctl-direct-handed-call` — SAME → SAME /
ПРИЁМКА ПО ОГОВОРКЕ: да. Экземпляры из тела своего обобщения растут по конкретной подстановке
каждого его экземпляра. Решает `mark_ref` → `Ctx @instantiates` с конкретными аргументами — тот
же вопрос с теми же аргументами из того же канала, что задаёт эмиттер (`@body_ours`), то есть
одна дверь. Тело, которое вырастить нельзя, отвергается в check по имени («in the instance of …»):
`instances_of` идёт и в check. Проверены формы: явный вызов, `mut`-получатель, неявный `xs[0]`,
вложенные обобщения, обобщённый метод своего типа. Осталось: абстрактный обход в фикспойнте `mono`
на месте — он ничего обобщённого не растит, только простые вызовы /

№1524 КОРЕНЬ: «несёт ли шелл экземпляр и как он зовётся» спрашивалось по ИМЕНИ метода
(`c_method_symbol(ctx, t, name)`). У перегруженного метода несколько C-функций: оракул
пишет первую перегрузку имени на типе голой, а каждую следующую — с `__` и C-типами
параметров (`emit_c.rs`, генерик-метод). На базе было три сломанных формы: `v.cap(100)` и
`d.index(1, 9)` уходили в шелловые `cap()`/`index(i)`; запись `xs[i] = v` / `xs[i] op= v`
печаталась ВЫЗОВОМ ЧТЕНИЯ слева от `=` (clang «expression is not assignable», над
`Vec[int]`, `[str]`, `[f64]`); `v.index(r)` с `Range` передавал диапазон в `int`-параметр
чтения — это та «тихая по сигнатуре» форма, о которой говорит строка /
ФИКС: `sem/handed_bodies.nv` — цепочка одноимённых переданных строк в порядке чтения и
`Ctx @overload_ordinal`; `@instantiates` спрашивает по символу перегрузки.
`sem/mangle_instance.nv` — дверь `c_overload_symbol(ctx, row, recv_t, args)`; суффикс
собирается из дверей (`overload_param_spelling`), без правки строк.
`check/methods.nv`, `emit_c/emit_expr.nv` — явный вызов спрашивает и печатает через неё.
`check/binds.nv` (`@vec_op_carried`) и `sem/mangle.nv` (`vec_op_c`) — неявные операции сначала
находят строку, потом спрашивают по её перегрузке. Новый ключ операции `index=`
(`builtins.nv`, `VEC_INDEX_SET_OP`, `vec_op_method`) с формой `mut @index(i int, val T)`.
`check/typing.nv` + `@judge_index_store` и `emit_c/emit_place.nv` `@emit_element_store` —
запись в элемент стала вызовом перегрузки записи: получатель и индекс вычисляются один раз,
составная запись читает через перегрузку чтения. `sem/harvest.nv` передаёт имя в `@note` /
ПРОБЫ: `shell-overload-cap-n` — clang → SAME; `shell-overload-index-set` — clang → SAME;
`v[i] = x` и `v[i] op= x` — clang → SAME (фикстура, `Vec[int]`, `Vec[f64]`, `Vec[str]`,
запись идёт в экземпляр из тела std `access.nv:53`); `index(Range)` явным вызовом над
`Vec[int]`: было check 0 + clang (Range в `int`), стало ICE в check
`sem: a name in TYPE position that the registry does not hold (#652 class)` (`sem.nv:462`,
тело std `Self { .. }`). Перегрузка теперь выбрана верно и идёт в инстанцирование, а падает
тело — класс `ice-split-at` из отчёта охотника. Срезы `v[a..b]` идут своей дверью
(`check/slice.nv`) и не изменились /
ПРИЁМКА: да для методов экземпляров обобщённых ЗАПИСЕЙ — явный вызов, неявные операции,
запись в элемент: вопрос задаётся по символу выбранной перегрузки, а перегрузка, которой нет
в шелле, инстанцируется или отвергается по имени (unit-тест: std без сеттера → отказ
`index(i, v)`). Осталось: (а) `index(Range)` явным вызовом — ICE вместо отказа (см. новый
дефект ниже); (б) методы НЕобобщённых переданных типов (`check/methods.nv:221`) и семейные
суммы (`Nova_Option_method_*`) по-прежнему спрашиваются по имени — их схема перегрузок у
оракула другая (`external_registry.rs`, `_<последний параметр>`) и на шелле не замерялась;
(в) порядковый номер считается по ПЕРЕДАННЫМ строкам. Если harvest отбросит ранее
объявленную перегрузку из списка оракула, номер сдвинется. Сдвиг вниз до 0 даст вопрос по
голому имени — дыра узкая, но дверь её не исключает /
