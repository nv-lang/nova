# p-ovl-channel — design note (written BEFORE code, per brief)

Model: sonnet. Window: Ш.1 связки К1 (план 221), №34 + №309 + №317.

## Установленный факт, ОПРОВЕРГАЮЩИЙ посылку брифа

Бриф утверждает (со ссылкой на пробы интегратора 2026-08-04): пара `fn P309Bag
@put(v int)` / `fn P309Bag mut @put(consume v int)` эмитится в ОДИН C-символ
`Nova_P309Bag_method_put__nova_int` — то есть манглинг (`sig_registry.rs`
`param_modes`) не различает символы по режиму параметра.

**Прямая проверка (сборка probe.nv, чтение порождённого C,
`scratchpad/p309probe/probe.c`) это опровергает.** Зарегистрированы ДВА разных
символа:
- `Nova_P309Bag_method_put` — тело ro-перегрузки (`return 0`);
- `Nova_P309Bag_method_put__nova_int` — тело consume-перегрузки (`return v`).

Манглинг (emit_c.rs `mangle_fn` / регистрация в `method_overloads`,
~7650-7970) уже даёт разные имена ЛЮБОЙ паре перегрузок, отличающихся по
типам параметров ИЛИ по `recv_mutable`, даже без специального
`param_modes`-тайбрейка — просто за счёт правила «первая регистрация → голое
имя, вторая → suffix по param C-типам». `param_modes`-тайбрейк в `mangle_fn`
(строки 18774-18785) и в регистрации (7690-7707, 7923-7936) — рабочий
защитный код на случай коллизии suffix'ов, но в проверенном случае он даже
не требовался: коллизии suffix'ов не было.

**Реальный корень (доказан трассировкой генерируемого C для 4 тестов):**
ВСЕ ЧЕТЫРЕ call-site эмитят `Nova_P309Bag_method_put__nova_int` — т.е. дело
не в манглинге, а в ВЫБОРЕ кандидата на call-site. Два независимых дефекта
эмита (`emit_c.rs`, метод-диспатч ~42779-42892):

1. **Receiver-mutable pre-filter (Plan 135, `exact_mut`, ~42802-42815)
   схлопывает `pool` ДО `narrow_by_param_mode`.** Когда получатель вызова —
   `mut`-переменная (типичный случай, `mut b = ...`), а перегрузки СВЕРХ
   режима параметра ЕЩЁ различаются по `recv.mutable` (как в примере брифа:
   ro-receiver `@put` vs `mut @put`), этот фильтр УЖЕ схлопывает `pool` до
   1 кандидата — того, чей `recv_mutable` совпал с получателем — вне
   зависимости от режима переданного аргумента. `narrow_by_param_mode`
   (Plan 184) вызывается только при `pool.len() > 1` — и уже никогда не
   видит второго кандидата. Проверено пробой `p309probe`: обычная и
   ro-привязка (обе используют `mut b`) обе получают consume-перегрузку.
2. **`is_rvalue_temp` (mode=2 ветка `narrow_by_param_mode`) слеп к форме
   ИМЕНОВАННОЙ привязки** — судит только по синтаксической форме выражения
   аргумента (Ident никогда не «temp»), не по тому, что переменная была
   объявлена `consume`. Это ТЕКСТУАЛЬНО дефект №309 как он записан в реестре.
   Проверено пробой `p309probe2` (пара БЕЗ разницы в `recv.mutable` — тут
   дефект (1) не маскирует): `consume t = 7; b.put(t)` выбирает ro-перегрузку
   вместо consume — потому что `t` это `Ident`, не rvalue-temp.

Вывод: задача канала — НЕ переносить манглинг (он уже корректен), а перенести
ВЫБОР кандидата (расширить `resolved_callees` на режимные перегрузки) — ровно
то, что канал уже делает для типовых перегрузок (`check_instance_overload`),
только без учёта режима/формы привязки.

## Дизайн фикса

### Канал (чекер, `types/mod.rs`)

- Новое поле `consume_binding_names: RefCell<HashSet<String>>` — зеркало
  СУЩЕСТВУЮЩЕГО `ro_binding_names` (тот же snapshot/restore на границах
  fn-entry и `f1_block`), populate в `Stmt::Let` по `d.consume` + в
  fn-параметрах по `p.consume`.
- Новые чистые предикаты `expr_mode_axis_mutable_place`/
  `expr_mode_axis_consume_eligible` — зеркало `emit_c::is_place_mutable`/
  `is_rvalue_temp`, НО consume-ветка ДОПОЛНИТЕЛЬНО признаёт Ident,
  зарегистрированный в `consume_binding_names` (закрывает дефект 2).
- `check_instance_overload`: когда единственность по типам не достигнута
  (`compat_spans.len() > 1`, после существующих D84-тайбреков), НОВЫЙ шаг
  `mode_axis_tiebreak` — если весь `compat_fns` структурно идентичен по
  типам параметров (`typeref_equal` попарно) и отличается ТОЛЬКО по
  `recv.mutable`/`param.consume`/`param.is_mut` (закрывает дефект 1 —
  единое решение по ОБЕИМ осям разом, не два жадных фильтра подряд), выбрать
  единственного наиболее специфичного пригодного кандидата
  (consume > mut > ro, receiver mut required ⇒ receiver must be a mutable
  place) и записать его `span` в `resolved_callees`.
- `f1_check_call`, свободные функции (Ident-callee, `compat.len() >= 2`
  ветка): тот же тайбрейк (без receiver-оси).

### Codegen (`emit_c.rs`)

- Метод-диспатч (~42849 `channel_choice`) УЖЕ читает `resolved_callees`
  ПЕРЕД `pool`/`narrow_by_param_mode` — ничего менять не нужно, чек-фикс
  срабатывает "бесплатно" через существующий канальный приоритет.
- Свободные функции (~38900-38963) канал НЕ читали вовсе — добавлен
  channel-first консult (по `resolved_callees.get(&call_id)` +
  `overloads.iter().find(fn_span==...)`) ПЕРЕД легаси arg-C-type
  фильтром/`narrow_by_param_mode`, зеркало метод-сайта.

### Что НЕ делается (и почему)

- Манглинг/`sig_registry.rs`/`param_modes`-тайбрейк в `mangle_fn` НЕ
  трогается — эмпирически уже корректен (см. факт выше). Гипотеза брифа о
  «коллизии ключа» и связанный риск («смена ключа вскроет коллизии в
  корпусе») отпадает — ключ не меняется, корпус-сканирование на коллизии не
  требуется.
- `narrow_by_param_mode`/`exact_mut`-фильтр в `emit_c.rs` НЕ удаляются —
  они остаются fallback для вызовов, которые чекер не резолвит (сложные
  receiver'ы вне `check_instance_overload`, `BoundCtx::infer_arg_ty` miss
  и т.д.). Итог: `emit_c.rs` **не худеет на 69 строк** — это МЕНЬШЕ, чем
  просил бриф, честно отражено в отчёте; посылка брифа («долг сидит именно
  в этой машинерии диспатча») была основана на неверном факте, автономно
  удалять рабочий fallback без верификации по всему корпусу — риск,
  непропорциональный этому окну.
- №34 не трогается: `spec_tests/conformance/arity_overload_concrete_vs_bound_generic.nv`
  уже покрывает ровно репро брифа (call-expression-as-argument) и уже
  ЗАКРЫТО (реестр 221.1 №34, окно p34); проверяется как регресс, не
  переписывается.
