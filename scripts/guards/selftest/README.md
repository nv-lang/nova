# scripts/guards/selftest/ — регресс-тесты механизмов принуждения

## Зачем

Скрипты в `scripts/guards/` (гейт, ratchet'ы, хуки) — это код, который
может тихо перестать ловить то, для чего создан: ландшафт меняется,
появляются новые пути в командах, кто-то рефакторит хук (в буквальном
смысле — эта самая папка переехала на уровень глубже волной
`p231-scripts-docs` 2026-07-27, и три `REPO_ROOT`-вычисления в самотестах
сломались бы молча, если бы их не перепроверили прогоном). **Механизм
принуждения без собственного регресс-теста — это доверие на слово.**
Хуже того: страж, который молча разучился что-то ловить, ХУЖЕ отсутствия
стража вовсе — он создаёт ложное ощущение защиты, пока конвенция уже
нарушается никем не замеченной.

Это план [231](../../../docs/plans/231-bug-cycle-exit.md) трек Ж (§4в):
«скрипты и автоматизированные функции проверки должны сами быть
подтверждены регресс-тестами, что ничего не пропускают» (вопрос владельца
2026-07-26).

## Что обязан проверять каждый самотест

Ровно ДВА свойства (без обоих — тест неполный):

1. **ЛОВИТ нарушение.** Синтетический случай, воспроизводящий то, против
   чего страж создан (испорченный лог, копия рантайма, запрещённая
   git-команда, ...) → страж обязан упасть/заблокировать.
2. **НЕ ловит законный случай.** Синтетический ЧИСТЫЙ случай (или сама
   реальная репа nova, если применимо) → страж обязан пропустить его без
   ложного срабатывания. Ложняк дорог: если страж ложно блокирует legit-
   случаи, из него быстро начинают выкручиваться обходами, и он теряет
   доверие даже там, где прав.

Образец формы — [`test-check-no-runtime-copy.sh`](test-check-no-runtime-copy.sh):
временный каталог (`mktemp -d` + `trap rm -rf ... EXIT`), несколько
`check()`-кейсов (имя, ожидаемый код, фактический код), сводный
счётчик `fails`, итоговый `exit 1`, если хоть один кейс не совпал.
[`test-check-guard-wiring.sh`](test-check-guard-wiring.sh) добавляет к
этому ещё один слой: он строит ИГРУШЕЧНЫЕ РЕПЫ-ФИКСТУРЫ (свой
`scripts/guards/` + `scripts/guards/selftest/` + `gate.sh`) — при
рефакторе структуры каталогов эти фикстуры нужно обновлять СИНХРОННО с
реальной структурой (см. «Пути после переезда» ниже — этой волной уже
наступили на эти грабли и почини­ли).

## Как добавить новый самотест

Один файл `test-<имя-стража>.sh` (или `.py`, если страж на Python) на
каждый механизм. **Правка `gate.sh` НЕ нужна** — `gate.sh` обходит этот
каталог циклом:

```sh
for st in "$ROOT"/scripts/guards/selftest/test-*.sh; do
    [ -e "$st" ] || continue
    bash "$st" || fail "самотест стража: $(basename "$st")"
done
```

т.е. новый файл, названный по маске `test-*.sh`, подхватывается
автоматически при следующем прогоне `gate.sh`.

## Пути после переезда (2026-07-27)

Эта папка была `scripts/selftest/`, стала `scripts/guards/selftest/` (на
уровень глубже, вместе со всеми стражами). Каждый `test-*.sh` вычисляет
`REPO_ROOT` от своего расположения — обновлено с `.../../..` (два уровня)
на `.../../../..` (три уровня), и путь к проверяемому стражу — с
`$REPO_ROOT/scripts/check-X.sh` на `$REPO_ROOT/scripts/guards/check-X.sh`.
`test-check-guard-wiring.sh` дополнительно строит фикстуры-репы — их
внутренняя структура (`scripts/guards/check-*.sh` + `scripts/guards/
selftest/test-*.sh` вместо плоского `scripts/`) тоже обновлена, иначе
мета-страж на фикстурах не находил бы вообще ничего (ложный «стражей нет,
проверять нечего» вместо реальной проверки трёх свойств).
