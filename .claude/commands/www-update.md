**КОМУ ЭТА КОМАНДА: тому, кто публикует.** Сайт — единственное, что видит внешний
читатель, и единственное место, где наша ошибка видна не нам.

Обнови сайт: $ARGUMENTS

## САЙТОВ ДВА, И ЭТО ПЕРВОЕ, ЧТО НАДО ЗНАТЬ

| репозиторий | домен | кто его обновляет |
|---|---|---|
| `nv-lang/www` | `nv-lang.org` | **ты** — здесь живёт исходник (Astro) |
| `nv-lang/www.nv-lang.ru` | `nv-lang.ru` | **никто руками** — зеркало пересобирается само |

**Зеркало правится САМО и трогать его не надо** (проверено чтением
`.github/workflows/sync-from-www.yml`): по расписанию `*/15 * * * *` оно клонирует
апстрим `nv-lang/www`, собирает его заново и применяет своё: подменяет `CNAME` на
`nv-lang.ru`, вставляет `ru-RU` hreflang, переписывает домен в `sitemap.xml`.
Канонический адрес остаётся `.org` — это осознанная SEO-политика, а не недоделка.
Правка, внесённая в зеркало руками, будет затёрта следующей пересборкой.

**Из этого следует практическое:** обновив `.org`, ты не обязан ничего делать с `.ru`,
но **обязан не считать работу законченной, пока не прошёл и его прогон** — иначе один
домен показывает новое, другой старое, и узнает об этом читатель.

## Дом процедуры — НЕ здесь

Устройство репозитория, команды `npm`, раскладка `site/`, поиск, кодировка и деплой
описаны в `CLAUDE.md` самого репозитория `nv-lang/www`. **Читай его перед работой и не
переписывай сюда:** вторая копия разойдётся на первой правке, а устаревшая инструкция
по сайту стоит дороже прочих — по ней публикуют.

Здесь — только то, чего в том файле нет: связь с `nova`, порядок между тремя
репозиториями и вердикт.

## ПОРЯДОК ЖЁСТКИЙ, И ПРИЧИНА У НЕГО МЕХАНИЧЕСКАЯ

1. **Сначала `nova main` ЗАПУШЕНА** (не «закоммичена») и её гейт зелёный.
2. Затем локальная сборка сайта — она же проверка.
3. Затем пуш `www` **во все три зеркала** (`origin`, `gitverse`, `sourcecraft`).
4. Затем ожидание зелёного деплоя `.org`, и следом — прогона `.ru`.

**Почему не наоборот** (замер 2026-09-17, чтением `site/scripts/sync-decisions.mjs`):
синк тянет спеку не из соседнего каталога, а с
`raw.githubusercontent.com/<repo>/<branch>` — то есть **с remote**. Непушенная правка в
`nova` для сайта не существует: сборка молча возьмёт прежнюю спеку и будет зелёной, а
на сайте окажется вчерашнее. Ошибку такого рода не показывает ни один лог — только
глаза на живой странице.

## Где работать

**В worktree, стоящем на `main`, а не в первом попавшемся каталоге `www*`.** У репы
сайта несколько рабочих копий, и главный чекаут может стоять на чужой ветке — рядом
работают другие окна. Проверяется ДО коммита, одной командой:

```sh
git -C <дерево> branch --show-current    # обязано быть main
git -C <дерево> remote -v                # обязано быть nv-lang/www, а не зеркало .ru
```

Вторая строка не лишняя: каталоги называются похоже, и репозиторий `www.nv-lang.ru` —
другой. Стейдж — по именам файлов: индекс общий с соседом.

## Что сайт берёт из `nova` — и чего НЕ берёт

- **Дока — ТОЛЬКО `docs/guide/`** (пары en+ru). `docs/dev/` не попадает на сайт
  никогда: это внутренние конвенции и промпты, публиковать их нельзя.
- **Спека — `spec/decisions/*.md`**, её тянет `prebuild`.
- Встретил в контенте сайта ссылку на `docs/<имя>.md` или на `docs/dev/…` — это дефект
  контента, а не «старый путь»: чини ссылку, а не обходи её.

## ПРАВКА ТОЛЬКО В `nova`? Тогда коммит в `www` НЕ НУЖЕН

Частый случай: в самом сайте ничего не меняется, а обновить надо, потому что в `nova`
уехала спека или дока. **Пустой коммит ради запуска сборки не делается** — у сборки
есть ручной запуск:

```sh
gh workflow run "Deploy to GitHub Pages" --repo nv-lang/www --ref main
```

Он поднимает тот же `prebuild`, то есть заново тянет спеку с remote `nova`. Зеркало
`.ru` подхватит результат своим расписанием.

**Почему это надо знать, а не догадываться** (замер 2026-09-17, чтением
`.github/workflows/deploy.yml`): у `.org` триггеры — `push` в `main` и
`workflow_dispatch`, **расписания НЕТ**. Значит правка спеки в `nova` сама по себе
сайт не пересобирает и может стоять неопубликованной сколько угодно: в тот день между
последним деплоем и текущей спекой лежало больше двух недель D-блоков. Из этого
следствие для ритма: **после слияния, менявшего `spec/` или `docs/guide/`, сайт
обновляется тем же днём** — иначе публичная спека расходится с деревом молча.

## Локальная сборка — до пуша, и она же проверка

Из каталога `site/`: `npm run build`. Это не только сборка — `prebuild` делает синк,
`postbuild` строит индекс поиска и **проверяет битые ссылки и якоря**; падение любого
шага валит сборку. Ровно этот прогон ловит класс «спека переехала, сайт ссылается на
старое» ДО публикации, а не после.

## ВЕРДИКТ — ЗЕЛЁНЫЙ ДЕПЛОЙ, А НЕ ПУШ. И ДЕПЛОЯ ДВА

```sh
gh run list --repo nv-lang/www          --limit 1 --json conclusion,status,headSha
gh run list --repo nv-lang/www.nv-lang.ru --limit 1 --json conclusion,status,createdAt
```

Первый обязан быть `success` **на ТВОЁМ SHA**. Второй — `success` и **позже** первого:
прогон зеркала, начавшийся раньше твоего деплоя, собрал ещё старый `.org`. Ждать его по
расписанию до пятнадцати минут — законно; торопить — `workflow_dispatch` в его репе.

**Почему это правило есть:** отчёт «запушил, готово» уже был дан при КРАСНОМ деплое —
сборка падала на переименованных файлах спеки. Пуш прошёл, сайт остался старым, и
заметил это владелец, а не автор правки.

## Чего эта команда НЕ делает

- **Не чинит `nova` ради сайта.** Красная сборка из-за спеки чинится в `nova` своим
  порядком — иначе правка уедет мимо гейта.
- **Не публикует незакоммиченное в `nova`.** Правка доки ещё не в `main` — сперва её
  слияние и пуш, потом сайт.
- **Не правит зеркало `.ru` руками** — см. первый раздел: правку затрёт.
- **Не трогает чужие ветки www** и не мержит их: их состояние — дело их авторов.
