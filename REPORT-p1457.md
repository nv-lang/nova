# REPORT-p1457 — Карина принимает пустой вектор `[]T.new()` (№1457)

Облачная сессия, Linux x86_64 (clang 18, libgc 8.2.6), 2026-10-01. Ветка
`p1457-novac-vec-new` (она же `p1457-novac-vec-new-1tj0vu` — имя, выданное средой
облачной сессии; оба указателя на одном коммите) от `origin/integrate` ed90b40, затем
слит `origin/integrate` bf2c8ba; к сдаче `integrate` не сдвинулся.

**КОРЕНЬ:** `[]T.new()` парсер Карины кладёт в тот же узел `ArrayLit`, что и литерал
`[]T.of(...)`, и чекер судил его дверью литерала: любое имя конструктора, кроме `of`,
давало «this constructor is not the literal form» (`check/binds.nv`, `@type_array_lit`).
Вторая половина — позиционные ворота литерала в обходе (`check/check.nv`): правая часть
`=` и хвост ветки `if`-значения не входили в список, отсюда «array literal is compiled
only as an initializer». Эмиссии правка не понадобилась: `@emit_array_lit` уже печатает
конструктор шелла с числом элементов (0) и по `push` на элемент (ни одного) — ровно
пустой вектор; присваивание строит литерал через `@build_value`, ветка `if` — через
`@lower_place`. Запрещённые файлы волны Э.10 не тронуты.

**ФИКС:**
- `novac/src/check/binds.nv:588` — `new` уходит в свою дверь `@type_empty_vec` (`:686`):
  тип — срез записанного типа элемента, у шелла спрашивается только конструктор
  экземпляра; `new(cap)` отвергается по имени (274.5 P3), тип без экземпляра в шелле —
  отказом шелла (E2-b).
- `novac/src/builtins/builtins.nv:254` — константа `EMPTY_CTOR = "new"` (донор —
  `Vec[T].new(cap int = 0)`, `std/src/collections/vec/core.nv:116`).
- `novac/src/check/check.nv` — ворота `AssignStmt` открывают `init_pos` для `ArrayLit` на
  простом `=`; пара флагов обхода `if_branch`/`if_tail` открывает хвост ветки
  `if`-значения ТОЛЬКО воротам литерала (конструктор записи и `match` в том же месте дают
  ICE «no type recorded» в типизации — замерено, поэтому `arm_pos` не переиспользован).

**КЛЕТКИ** (тип × позиция → до / после):
- `int`, `str` × инициализатор `ro`/`mut` → отказ «not the literal form» / принято,

- `int`, `str` × хвост ветки `if`-значения (инициализатор, `=`, аргумент, тело ветки
  `match`) → «only as an initializer» / принято (`pos_3`);
- свой тип записи/суммы (`[]Item.new()`, `[]Shape.new()`) → «not the literal form» /
  форма принята, остаётся отказ шелла «carries no `Vec` instance for Item» (`neg_1`) —
  шелл не несёт экземпляр чужого типа; это Э.10, не прячется;
- `bool` → «not the literal form» / отказ шелла «carries no `Vec` instance for bool»;
- вложенный: `[][]int.new()` не принимает и ОРАКУЛ («unexpected `]` in expression»);
  `[]Vec[int].new()` оракул принимает, Карина — нет: разбирает как пустой литерал `[]`
  плюс применённый тип, два отказа (274.5 P4) — до и после одинаково (см. вопрос 3);
- `[]int.new(4)` → «not the literal form» / отказ по имени «takes no arguments here»

**ОТКРЫТО:**
1. **Недетерминизм Карины на Linux (уже №1461).** Без `GC_DONT_GC=1` один и тот же бинарь
   на одной фикстуре даёт то 0, то 4 отказа («slice head `Vec` is not among the
   declarations»); с `setarch -R` — всегда неверно, с `GC_DONT_GC=1` — всегда верно. Мера
   0.2 без этой переменной плавала между 92/128 и 105/128. Все числа этого отчёта сняты
   под `GC_DONT_GC=1`; на нём числа Карины воспроизводятся точно.
2. **Две фикстуры `NOVAC_EXPECT` и два модульных теста красные на базе** (Linux,
   bf2c8ba, с `GC_DONT_GC=1`, без моей правки): `pattern_depth/neg_3` (ждёт «a `for`
   header takes an irrefutable pattern», получает «carries no `len` for Vec[Sh]»),
   `slice_vs_range/neg_1` (ждёт текст среза, получает «carries no `end_index` for
   Vec[u8]»); тесты `subset_pattern_test.nv:449` и `subset_test.nv:775`. Похоже на ту же
   дверь №1170 (`for` спрашивает шелл раньше паттерна) — не моё, не трогал.
3. **ICE на базе:** `println(inc(if c { 1 } else { 2 }))` — `if`-значение внутри вызова,
   который сам аргумент `println`, даёт «internal compiler error: emit: expression kind
   outside the subset» (без `println` — `ro r = inc(if ...)` — работает). В `pos_3`
   аргумент поэтому сначала связан. Строки реестра нет: номер не мой (см. вопрос 2).
4. `[]Vec[int].new()` — два отказа на одну форму, и первый лжёт («an empty array literal
   -- the oracle panics on it», а оракул эту форму строит без паники).

**ВОПРОСЫ ИНТЕГРАТОРУ:**
1. **Имя ветки.** Задание называло `p1457-novac-vec-new`, среда облачной сессии выдала
   `p1457-novac-vec-new-1tj0vu`. Запушены ОБЕ (один коммит). Решить: какую сливать.
   Рекомендация — `p1457-novac-vec-new` (её называет реестр); вторую можно удалить.
2. **Номер для ICE из «ОТКРЫТО» п.3.** Варианты: (а) завести отдельную строку
   (🟠 К2, класс «`if`-значение в аргументе вложенного вызова под `println` проходит
   чекер и роняет эмиссию»; печать `println` не поднимает (hoist) вложенные построения
   так, как это делает обычный вызов); (б) приписать к строке двери печати, если такая
   есть. Рекомендация — (а): это «принято чекером — ICE в эмиссии», класс К1/К2 отдельно
   от №1457, и молчащий носитель в фикстуре спрятал бы его.
3. **`[]Vec[int].new()`** (ОТКРЫТО п.4): (а) строка реестра К3 на ложный текст и каскад
   (парсер `[]` + применённый тип; лечится чтением применённого типа элемента в
   `parse/expr.nv` и одним отказом P4); (б) оставить до волны применённых типов в
   выражениях. Рекомендация — (а), дёшево и снимает ложь в тексте; носителей в
   исходниках Карины нет, поэтому на меру 0.2 не влияет.
4. **Мерить ли меру 0.2 на Linux без `GC_DONT_GC`.** Пока №1461 открыт, число без неё
   случайно. Рекомендация: в любых линуксовых замерах и смоуках Карины ставить
   `GC_DONT_GC=1` и писать это рядом с числом — до закрытия №1461.
